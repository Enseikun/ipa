# レクチャーノート：情報セキュリティ対策技術（1）侵入検知・防御 ― 5.2 ホストの要塞化

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ対策」（知識項目例：不正アクセス対策、アカウント管理、ログ管理、脆弱性管理、アクセス制御 ほか）、「情報セキュリティ」（知識項目例：脆弱性、多層防御 ほか）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

5.1 の地図で、第5章の最初に置いたのが**ホストの要塞化**でした。ホストの要塞化とは、OSをはじめとするソフトウェアに内在するバグや設定ミスなどによる**セキュリティホール**を塞ぎ、ホスト（サーバやPC）を堅牢な状態にすることです。5.1 の分類では「機密性・完全性の侵害／**予防**」の升目に入る、最も基本的な対策です。

なぜ最初なのか。第2章を振り返ると、攻撃者はポートスキャン（2.2）で開いているポートを探し、そこで動いている古いサービスのバッファオーバフロー（2.3）を突き、推測しやすいパスワード（2.4）でログインし、setuid プログラムの脆弱性で管理者権限を奪いました。これらはすべて、**ホストに残っていた弱点**を足掛かりにしています。ファイアウォールやIPSが「入口の門番」だとすれば、要塞化は「建物そのものの扉や窓に鍵をかける」作業です。門番がすり抜けられても、建物に隙がなければ攻撃は成立しません。

本ノートは次の順で進めます。

1. **要塞化の概要**：何をする作業か、なぜ必要か、ファイアウォールがあっても不要にならないのはなぜか。攻撃者から要塞化がどう見えるかを、ポートスキャンの結果で確かめます。
2. **要塞化の主な実施項目**：パーティション設計からログ設定まで9項目を、「システム管理者は、何のために、何をどうすべきか」の形で、実際の設定やコマンド出力を見ながら学びます。
3. **要塞化後の維持管理**：一度固めたホストを堅牢なまま保つ方法と、要塞化チェックリスト。

科目Bの業務観点では「③利用におけるセキュリティ対策の適用」のうち「ネットワーク及び機器のセキュリティ管理」「脆弱性への対応」「アカウント管理及びアクセス管理」と、「②企画・設計・開発・運用」の「製品・サービスのセキュアな導入」「運用・保守」に対応します。科目A-2では setuid や不要サービスの停止が単独で問われることがあり、科目Bでは「このサーバ構成の問題点」「侵入の原因となった設定」を指摘させる設問の根拠として頻出します。

## 1. ホストの要塞化の概要

### 1.1 要塞化で行う作業

システム管理者がホストの要塞化のために行う作業には、次のようなものがあります。

- OSやアプリケーションの**バージョンの最新化**
- **パッチの適用**
- **不要なサービスや機能の停止**

通常、要塞化にあたって特別なツールなどを購入する必要はありません。導入している各製品の保守契約を締結していれば、パッチや最新版の入手を含めて実施可能です。

ただし、システム管理者が誤った設定を行えば、正常にサービスを提供できなくなったり、より深刻なセキュリティホールを残したりすることにもなりかねないので注意が必要です。たとえば、「不要そうだから」と時刻同期のサービスを止めた結果、ログの時刻がずれて事後調査ができなくなる、ということが起こります。そのため、システム管理者は、まず信頼できる情報（製品ベンダーのセキュリティ設定ガイド、CIS Benchmarks のような第三者の設定基準、JVN などの脆弱性情報）を確実に入手し、正しい手順に則って作業を実施することが重要です。

### 1.2 要塞化の必要性 ― 初期状態のサーバは「開けっぱなし」

**アプライアンス製品**（特定用途向けに専用化された機器）であれば、出荷時点で一定レベルのセキュリティ対策が行われていると考えてよいでしょう。しかし、汎用的なサーバ製品などの場合、梱包を解いてケーブル類を接続し、IPアドレスなど必要最小限の設定をすれば、すぐにでもサーバとして稼働させることができてしまいます。

このような初期状態のサーバでは、不要なサービスが起動したままになっていたり、既知の脆弱性を修正するパッチが適用されていなかったりすることが多くあります。したがって、攻撃者に侵入を許したり、管理者権限を奪われたりするような深刻な脆弱性が内在している可能性も十分にあります。

こうしたことから、システム管理者は、ホストを本格的に稼働させる**前に**、その用途に応じた要塞化対策を施す必要があります。特に、インターネットに公開するサーバ（**公開サーバ**）においては必須の作業です。公開サーバは、接続した瞬間から世界中のスキャンにさらされるからです。

### 1.3 要塞化の重要性 ― ファイアウォールがあっても不要にならない

通常、企業などのインターネット接続環境にはファイアウォールが設置されています。しかし、それでホストの要塞化が不要になるということはありません。

例として、ファイアウォールによって、WebサーバへのHTTP（80/TCP）通信以外は一切通さない設定になっているサイトがあったとします。この場合、一般的なファイアウォールは、WebサーバへのHTTP通信についてはほぼ無条件で通過させてしまいます。ファイアウォールはIPアドレスとポート番号を見て判断しており、HTTPの中身までは見ていないからです（1.4、5.5）。そのため攻撃者は、Webサーバの脆弱性を突いた**BOF**（バッファオーバフロー）攻撃や**SQLインジェクション**などを、そのままWebサーバに送り付けることができます。

仮にWebサーバに重大なセキュリティホールがあれば、攻撃者はファイアウォールを堂々とすり抜けてWebサーバに侵入したり、その背後にあるデータベースから情報を盗み出したりすることもできてしまいます。

このような攻撃からWebサーバを守るには、IPSやWebアプリケーションファイアウォール（WAF）を設置する方法などがありますが、システム管理者が**最初に実施すべき対策はWebサーバを要塞化すること**です。IPSやWAFはシグネチャに一致しない攻撃を見逃すことがありますが、サーバ側の弱点そのものがなくなっていれば、見逃された攻撃も成立しないからです。

> **用語：ファイアウォール**
> インターネットなどの外部ネットワークからの不正アクセスから、内部ネットワークを保護するための仕組み。あらかじめ定められたルールに従い、パケットの通過／遮断を制御するとともに、その結果をログに記録する（5.5 で解説）。

> **用語：IPS（Intrusion Prevention System）**
> 侵入防御システム。ネットワーク上の通信を監視し、不正な通信や攻撃を検知すると、その通信を自動的に遮断する（5.7 で解説）。

> **用語：Webアプリケーションファイアウォール（WAF）**
> XSS（クロスサイトスクリプティング）、SQLインジェクション、OSコマンドインジェクション、セッションハイジャックなど、Webアプリケーションに対する攻撃を検知・防御し、セキュアなWebサイトの運用を実現する仕組み。5.8節で解説する。

**図：Webサーバへの攻撃のイメージ**

```
攻撃者 ──(HTTP 80/TCP:BOF攻撃・SQLインジェクション)──▶ ファイアウォール(通過)
                                                         │
                                                         ▼
                                                  Webサーバ(脆弱)
                                                         │
                                                         ▼
                                              データベース(情報漏えい)
```

### 1.4 攻撃者から見た要塞化 ― ポートスキャンの結果が物語るもの

インターネット上では、**ポートスキャン**などの調査行為が無差別かつ日常的に行われています。そのため、要塞化の施されていないサーバなどはすぐに見つかってしまう可能性があります。

このような脆弱なサーバを見つけた攻撃者は、そのサイト全体のセキュリティレベルが低いと判断し、さらに徹底的な調査を行い、攻撃を仕掛けるでしょう。逆に、要塞化が十分に施されているサイトについては、攻撃者はセキュリティレベルが高く侵入が困難と判断します。そして、攻撃者はそのサイトへの侵入や攻撃を思いとどまり、他の脆弱なサイトを探しに行くはずです。

このように、要塞化の実施状況によって、攻撃を受ける可能性は大きく左右されることになります。攻撃者の目にどう映るかを、2.2 で学んだ nmap の出力で比べてみましょう（例示用アドレス 203.0.113.10 の公開Webサーバを想定）。

```
【要塞化前】
$ nmap -sS -sV 203.0.113.10
PORT     STATE SERVICE     VERSION
21/tcp   open  ftp         vsftpd 2.3.4
22/tcp   open  ssh         OpenSSH 5.3 (protocol 2.0)
23/tcp   open  telnet      Linux telnetd
25/tcp   open  smtp        Postfix smtpd
80/tcp   open  http        Apache httpd 2.2.15
111/tcp  open  rpcbind     2-4 (RPC #100000)
3306/tcp open  mysql       MySQL 5.1.73
8080/tcp open  http        Apache Tomcat (管理画面 /manager/html)

【要塞化後】
$ nmap -sS -sV 203.0.113.10
PORT    STATE    SERVICE  VERSION
22/tcp  filtered ssh                    ← 管理用。特定の管理端末からのみ許可
443/tcp open     https    nginx
（他の 998 ポートは closed/filtered）
```

要塞化前の結果を見た攻撃者は、「telnet（平文でパスワードが流れる）が開いている」「古いバージョンのソフトウェアが並んでいる（既知の脆弱性を検索できる）」「DB（3306）がインターネットから直接見えている」「Tomcat の管理画面が公開されている」と読み取り、攻撃の足掛かりを複数手に入れます。バージョン番号まで表示されることで、攻撃者は脆弱性データベースで攻撃手段をすぐに調べられます。要塞化後は、見える入口が HTTPS だけで、攻撃者が得られる情報も最小限です。

**図：要塞化されていないサイトとされているサイトの違い**

| | 要塞化されていないサイト | 要塞化されているサイト |
| --- | --- | --- |
| ポートスキャンの結果 | 不要なポートが多数開いている | 必要最小限のポートのみ開いている |
| 攻撃者の判断 | セキュリティレベルが低い | セキュリティレベルが高く、侵入困難 |
| 攻撃者の行動 | さらに徹底的な調査・攻撃を行う | 攻撃を断念し、他のサイトを探す |

1.2 の4機能でいえば、要塞化は本来「予防」の対策ですが、攻撃者に「このサイトは手強い」と思わせて攻撃を思いとどまらせる点では、「**抑止**」の効果ももっています。

## 2. 要塞化の主な実施項目

要塞化の具体的な実施項目や内容は、OSの種類やサーバの用途によって異なりますが、ここでは、環境や条件にかかわらず実施する必要のある対策の概要を、実施する順序に沿って解説します。①〜③はOSのインストール時、④〜⑨はインストール後の設定で行う作業です。

### 2.1 ① 最適なパーティション設計

**パーティション**とは、ハードディスクの中に作成する区画のことです。用途や性質の異なるデータを別々の区画に分けて管理し、障害や攻撃の影響範囲を局所化することは、セキュリティ対策の基本的な考え方ともいえます。具体的には、システム管理者は、次のように用途や性質の異なる領域について、別のパーティションを割り当てるのが望ましいとされます。

- OSの中核となる部分（**カーネル**）の保存領域
- アプリケーションプログラム（ソフトウェア）の保存領域
- ユーザのデータ保存領域
- ログの保存領域

ハードディスクを複数のパーティションに仕切ることにより、次のようなメリットがあります。

- バックアップやバージョンアップが実施しやすくなる
- ハードディスクの論理的な障害への対応がしやすくなる
- アプリケーション領域の容量増加がシステム領域に影響を及ぼさない

その反面、システム管理者がパーティションを細かく仕切りすぎたり、設計を誤ったりすると、使用されない細かな空き領域が増加したり、特定の領域の容量が満杯状態になったりすることによって、システム全体に影響が及ぶなどの問題が発生することがあります。

> **補足**
> 例えば、ログの保存領域をシステム領域と同じパーティションに置くと、大量のログ出力（攻撃によって意図的に引き起こされる場合もある）によってディスクが満杯になり、OS全体が停止するおそれがある。ログ領域を分離しておくことで、このような事態を防ぐことができる。

Linux のサーバでは、パーティションごとにマウントオプションを付けて、領域の性質に合わない使い方を禁止することもできます。次は `/etc/fstab` の例です。

```
# /etc/fstab（抜粋・例）
# デバイス        マウント先   種類  オプション                         
/dev/vg0/root    /           xfs   defaults                          0 1
/dev/vg0/var     /var        xfs   defaults,nodev                    0 2
/dev/vg0/log     /var/log    xfs   defaults,nodev,nosuid,noexec      0 2
/dev/vg0/home    /home       xfs   defaults,nodev,nosuid             0 2
tmpfs            /tmp        tmpfs defaults,nodev,nosuid,noexec      0 0
```

`noexec` は「この領域に置いたファイルを実行させない」、`nosuid` は「この領域の setuid 属性を無効にする」という意味です。攻撃者は、侵入後に誰でも書き込める `/tmp` へ攻撃ツールを置いて実行しようとすることが多いので、システム管理者が `/tmp` を `noexec` にしておくと、その手口を一段難しくできます。

### 2.2 ② セキュアなファイルシステムの選択

OSの種類によっては、インストール時にいくつかの**ファイルシステム**を選択できる場合があります。ファイルシステムの種類によって、ファイルやディレクトリごとのアクセス権の設定ができる／できない、暗号化機能の有／無などの違いがあるため、システム管理者は、最もセキュアな設定が可能なファイルシステムを選択すべきです。

> **補足**
> 例えばWindows環境では、**FAT32**ではファイル単位のアクセス権を設定できないが、**NTFS**ではアクセス制御リスト（**ACL**）によるきめ細かなアクセス権の設定や、**EFS**（Encrypting File System）による暗号化が可能である。

| 観点 | FAT32 | NTFS |
|---|---|---|
| ファイル単位のアクセス権 | 設定できない（誰でも読み書きできる） | ACLで利用者・グループごとに設定できる |
| 暗号化 | なし | EFSでファイル単位に暗号化できる（ディスク全体の暗号化は BitLocker） |
| 主な用途 | USBメモリなど、機器間の互換性重視 | Windowsのシステム領域・データ領域 |

### 2.3 ③ 最新バージョンのソフトウェアを最小構成でインストールする

古いバージョンのOSや各種のソフトウェアには、既知の重大な脆弱性が存在していることが多くあります。そのため、システム管理者は、インストールする際には原則として最新バージョンのものを使用し、必要な設定を確実に施さなければなりません。

また、システム管理者は、インストール時にいわゆる「**標準インストール**」や「**フルインストール**」ではなく、「**最小インストール**」を選択するか、「**カスタムインストール**」を選択し、必要最小限のソフトウェアをインストールすべきです。そうすることにより、不要なソフトウェアや機能がインストールされるのをある程度防ぐことができます。インストールされていないソフトウェアは、脆弱性が見つかっても攻撃に使われることがなく、パッチを当てる手間も発生しません。

### 2.4 ④ パッチの適用

システム管理者は、必要最小限のソフトウェアをインストールしたら、続いて既知のセキュリティホールを塞ぐために、ベンダーから提供されている**パッチ**（修正プログラム）を適用（インストール）します。たとえ最新バージョンのインストールパッケージを使用していたとしても、最新のパッチまで含まれているとは限りません。インストールメディアが作られた後に公開された修正は、別途適用する必要があるからです。

なお、パッチを適用するということはソフトウェアの一部を変更することであるため、それによって動作が不安定になったり、他のソフトウェアや機能に影響を及ぼしてシステムが正常に動作しなくなったりする可能性があります。そのため、システム管理者は、本番環境のシステムに適用する場合には、事前にそのパッチを適用することによる**影響度を調査**したり、**検証用の環境**を使って実際に適用した場合の動作状況を確認したりすることが必要となります。

| 手順 | システム管理者が行うこと | 目的 |
|---|---|---|
| 1. 情報収集 | ベンダーの公開情報、JVN、JPCERT/CC の注意喚起を確認する | 自社の製品に関係する脆弱性を漏れなく把握する |
| 2. 影響度の調査 | 脆弱性の深刻度（CVSS、5.3）と、パッチの変更内容・既知の不具合を確認する | 適用の緊急度と、業務への影響を見積もる |
| 3. 検証 | 検証環境に適用し、業務アプリケーションが正常に動くかを確認する | 本番での障害を防ぐ |
| 4. 本番適用 | 計画した時間帯に適用し、切り戻し手順を用意しておく | 万一の障害時にすぐ元に戻せるようにする |
| 5. 確認・記録 | 適用後のバージョンを確認し、構成管理台帳に記録する | 適用漏れを防ぎ、次回の判断材料にする |

検証に時間がかかる一方で、攻撃者は脆弱性の公開から短期間で攻撃を始めます。そのため、すぐにパッチを適用できない場合には、システム管理者は、該当機能の無効化やWAF・IPSでの遮断などの**回避策**（緩和策）で、パッチ適用までの期間を守るべきです。

### 2.5 ⑤ 不要なサービスや機能の停止

ソフトウェアを最小構成でインストールしても、まだ不要な機能（**サービス**）が自動的に起動するようになっていたり、不要なコマンドなどが有効になっていたりする場合があります。システム管理者は、必要最小限のものを除き、これらをすべて削除するか無効にすべきです。

また、ソフトウェアによっては、インストール時に**サンプル用のファイルやディレクトリ**が作成されるものもあります。これらは通常、本番環境のシステムには不要であるため、すべて削除します。

> **補足**
> サンプルファイルや**サンプルCGI**には脆弱性が含まれていることがあり、攻撃の足掛かりとして悪用された事例も多い。また、起動しているサービスはそれぞれが待ち受けポートを開くため、不要なサービスを停止することは**攻撃対象領域（アタックサーフェス）**の縮小につながる。

システム管理者は、まず「今、どのポートで何が待ち受けているか」を自分のサーバの内側から確認します。Linux では `ss` コマンドを使います。

```
$ sudo ss -tlnp
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      128          0.0.0.0:22         0.0.0.0:*     users:(("sshd",pid=812,fd=3))
LISTEN 0      64           0.0.0.0:23         0.0.0.0:*     users:(("xinetd",pid=790,fd=5))
LISTEN 0      32           0.0.0.0:21         0.0.0.0:*     users:(("vsftpd",pid=801,fd=3))
LISTEN 0      511          0.0.0.0:80         0.0.0.0:*     users:(("httpd",pid=950,fd=4))
LISTEN 0      80           0.0.0.0:3306       0.0.0.0:*     users:(("mysqld",pid=1022,fd=20))
LISTEN 0      4096         0.0.0.0:111        0.0.0.0:*     users:(("rpcbind",pid=640,fd=4))
```

この出力から、システム管理者は次のように判断します。

| 待ち受け | 判断 | 理由と対処 |
|---|---|---|
| 22/tcp sshd | 残す（制限付き） | 管理に必要。接続元を管理端末に限定し、パスワード認証を無効にして鍵認証にする |
| 23/tcp telnet | 停止・削除 | 通信が平文でパスワードが盗聴される。SSHで代替できる |
| 21/tcp ftp | 停止・削除 | 平文。ファイル転送が必要ならSFTPを使う |
| 80/tcp httpd | 残す | 公開Webサービス本体（HTTPSへの転送に限定するのが望ましい） |
| 3306/tcp mysqld | 待ち受けを 127.0.0.1 に限定 | DBは同一ホストのアプリケーションからだけ使う。外部から直接接続させない |
| 111/tcp rpcbind | 停止 | NFS等を使っていないなら不要 |

不要と判断したサービスは、止めるだけでなく自動起動も無効にしておきます。

```
$ sudo systemctl disable --now telnet.socket vsftpd.service rpcbind.service rpcbind.socket
$ systemctl list-unit-files --state=enabled --type=service
UNIT FILE          STATE   PRESET
chronyd.service    enabled enabled     ← 時刻同期（ログの時刻の正確さに必要なので残す）
httpd.service      enabled disabled
mysqld.service     enabled disabled
rsyslog.service    enabled enabled
sshd.service       enabled enabled
```

Windows では `netstat -ano` で待ち受けポートとプロセスIDを、「サービス」管理ツールで各サービスの起動状態を確認します。停止後は、1.4 のように外部からもう一度ポートスキャンをかけ、意図したポートしか見えないことを確かめます。内側（`ss`）と外側（nmap）の両方から確認するのは、ホストの設定とファイアウォールの設定の食い違いに気づくためです。

### 2.6 ⑥ 不要なアカウントの削除と管理者アカウントの管理

インストール直後のOSには、**ゲストアカウント**や**テスト用アカウント**など、運用上不要なアカウントが存在する場合があります。攻撃者は、こうした管理の目が届かないアカウントを侵入に使います。システム管理者は、これらを削除するか無効にすべきです。また、管理者アカウントなど、名称が広く知られているアカウントについては、推測されにくい名称に変更するのが望ましいとされます。攻撃者がパスワードリスト攻撃やブルートフォース攻撃（2.4）を仕掛けるには、ユーザIDとパスワードの両方を当てる必要があり、IDが推測できなければ攻撃の難易度が上がるからです。

例えば、Windows環境には「**Administrator**」という管理者アカウントがありますが、この名称を変更することができます。セキュリティ対策の観点からすれば、本来の「Administrator」については名称を変更し、最小限の権限しかもたない**ダミーの「Administrator」**を作成しておくのも有効です。攻撃者がダミーのAdministratorを攻撃すれば、その認証失敗ログが攻撃の検知にも役立ちます。

```
C:\> net user
\\WEB01 のユーザー アカウント
-------------------------------------------------------------------------------
Administrator            DefaultAccount           Guest
svc_backup               test01                   WDAGUtilityAccount
```

この一覧を見たシステム管理者は、「Guest と test01 は無効化または削除する」「Administrator は名称を変更する」「svc_backup（バックアップ用サービスアカウント）は対話ログオンを禁止し、必要最小限の権限にする」と判断します。

また、Windows環境では、管理者権限でログイン可能な場合に、ネットワークを介してアクセス可能な状態（共有状態）になっているディレクトリやドライブ（**管理共有**。`C$`、`ADMIN$` など）が存在する場合があります。攻撃者は、奪った管理者の認証情報でこの管理共有に接続し、ネットワーク内の他のサーバへ横展開します。そのため、システム管理者は、それらについて共有状態を解除しておくのが望ましいとされます。

加えて、Windows環境では、ログインすることなく他のコンピュータの共有資源情報やアカウント情報を取得できる「**匿名接続**」（**ヌルセッション**）機能が有効になっている場合があります。攻撃者は匿名接続でアカウント名の一覧を入手し、パスワード攻撃の標的リストにします。これについても、システム管理者はレジストリ（`RestrictAnonymous` などの値）やグループポリシの設定によって無効にすべきです。なお、近年のWindowsでは匿名接続は既定で強く制限されていますが、古いシステムとの互換性のために設定が緩められていることがあるため、確認が必要です。

### 2.7 ⑦ 推測困難なパスワードの設定、及びパスワードチェック機能の有効化

システム管理者は、有効なすべてのアカウントに対し、推測困難なパスワードを設定させます。一般的に次のようなパスワードは推測されやすく、脆弱とされています。

| 脆弱なパスワード | 例 | 攻撃者がどう突くか |
|---|---|---|
| 短いパスワード（8文字未満など） | `a1b2c3` | ブルートフォース攻撃で全組合せを短時間で試せる |
| 複数の文字種（数字、英大文字、英小文字、特殊記号など）を使用していないパスワード | `12345678` | 試す組合せの数が少なくて済む |
| ユーザIDと同じ、もしくはユーザIDに酷似したパスワード | ID `tanaka` に `tanaka1` | 攻撃者は最初にIDの変形を試す |
| 名前や生年月日などの個人情報を用いたパスワード | `taro0401` | SNSなどで調べた個人情報から推測される |
| 初期設定のまま変更されずに使用されているパスワード | `admin` / `password` | 製品マニュアルで公開されている |
| 長期間変更されていないパスワード | 10年前に設定したまま | 過去に漏えいしたパスワードが使われ続ける |
| 辞書に載っている単語をそのまま用いたパスワード | `sunshine` | 辞書攻撃（2.4）の単語リストに含まれている |

各ユーザが設定するパスワードがこれらの条件に合致することのないよう、システム管理者は、OSなどが備える**パスワードチェック機能**（**パスワードポリシー**の設定）を有効にし、脆弱なパスワードが設定できないようにします。設定の例を示します。

```
# Linux：/etc/security/pwquality.conf（抜粋・例）
minlen = 12          # 最低12文字
minclass = 3         # 4種類の文字種のうち3種類以上
dictcheck = 1        # 辞書に載っている単語を拒否
usercheck = 1        # ユーザ名を含むパスワードを拒否

# Linux：/etc/security/faillock.conf（抜粋・例）
deny = 5             # 5回連続で失敗したらアカウントをロック
unlock_time = 900    # 900秒（15分）後に自動解除
```

```
C:\> net accounts
パスワードの最短有効期間 (日):                   1
パスワードの最長有効期間 (日):                   無制限
パスワードの最小長:                              12
保持されるパスワードの履歴の数:                  24
ロックアウトのしきい値:                          5
ロックアウト期間 (分):                           15
ロックアウトのカウンターのリセット (分):         15
```

ロックアウトのしきい値は、2.4 で学んだブルートフォース攻撃（1つのIDに大量のパスワードを試す）を止めるための設定です。ただし、1つのパスワードを多数のIDに試すリバースブルートフォース攻撃やパスワードスプレー攻撃には効きにくいので、多要素認証（第6章）と組み合わせるべきです。

> **補足（考え方の変化）**
> 以前は「パスワードは定期的に（例：90日ごとに）変更させる」「文字種を必ず混在させる」ことが一般的な推奨とされていた。しかし現在は、NIST SP 800-63B などのガイドラインや国内の行政機関の注意喚起で、**漏えいの疑いがない限り定期変更を強制しない**こと、文字種の組合せを強制するよりも**長さを重視**し、既知の漏えいパスワードや辞書の単語との照合で弱いパスワードを拒否することが推奨されている。定期変更を強制すると、利用者が `Pass2026!` → `Pass2027!` のように規則的な変更をしがちで、かえって推測しやすくなるためである（1.2 の「セキュリティと利便性のバランス」）。上の表の「長期間変更されていないパスワード」は、変更しないこと自体よりも、「過去に漏えいしたパスワードが使われ続けること」が問題の本質だと理解しておくとよい。上の `net accounts` の例で最長有効期間を「無制限」にしているのは、この考え方に沿った設定である。

### 2.8 ⑧ ディレクトリ、ファイル、プログラムなどのアクセス権の設定

インストールしたばかりのOSは、ディレクトリやファイル（Windows環境ではこれに加えて**レジストリ**）の**アクセス権**（**パーミッション**）が適切に設定されておらず、管理者以外のユーザにも必要以上の権限が与えられている場合があります。システム管理者は、各ユーザに対し、必要最小限の権限のみを与えるよう設定を見直し（1.2 の**最小権限の原則**）、プログラムの実行権限の設定も見直すべきです。

UNIX環境では、2.3「バッファオーバフロー攻撃」で解説したように、**setuid/setgid**属性をもつプログラムを悪用したBOF攻撃などが行われる可能性もあります。攻撃者は、root 所有の setuid プログラムの脆弱性を突くことで、一般ユーザの権限から root 権限に昇格します。そのため、システム管理者は不要な setuid/setgid 属性を解除すべきです。まず、setuid 属性をもつファイルの一覧を確認します。

```
$ find / -perm -4000 -type f 2>/dev/null
/usr/bin/passwd
/usr/bin/su
/usr/bin/sudo
/usr/bin/mount
/usr/bin/chfn
/opt/legacyapp/bin/report_gen        ← 業務で使っていない古いツール。要確認

$ ls -l /usr/bin/passwd /opt/legacyapp/bin/report_gen
-rwsr-xr-x 1 root root  32648 ... /usr/bin/passwd
-rwsr-xr-x 1 root root 118320 ... /opt/legacyapp/bin/report_gen
    ↑ 所有者の実行権限が "s" になっているのが setuid の印
```

`passwd` は一般ユーザが自分のパスワードを変更する（root しか書き込めない `/etc/shadow` を更新する）ために setuid が必要なので残します。一方、使っていない `report_gen` はシステム管理者が `chmod u-s` で属性を外すか、ソフトウェアごと削除すべきです。

Webアプリケーションに対する攻撃においても、CGIプログラムを格納するディレクトリのパーミッション設定が深刻な脆弱性となる場合もあるため、十分な注意が必要です。たとえば、CGIディレクトリに Webサーバのプロセスが書き込める設定になっていると、攻撃者はアップロード機能などを使って自作のスクリプトを置き、Webサーバに実行させることができてしまいます。

> **用語：setuid/setgidプログラム**
> 実行したユーザの権限ではなく、そのプログラムファイルの所有者（setuid）または所有グループ（setgid）の権限で実行されるプログラム。UNIX系OSには、passwdコマンド、pingコマンド（/bin/ping）、suコマンドなど、所有者がrootでsetuid属性が設定されたプログラムがいくつかある。これらに脆弱性があると、一般ユーザが管理者（root）権限を奪取できてしまうおそれがある。
> なお、pingコマンドは以前は多くのUNIX系OSで root 所有の setuid プログラムとされていたが、現在の多くのLinuxディストリビューションでは、setuid の代わりに必要な権限だけを与える**ケーパビリティ**（`cap_net_raw`）や、特権を必要としないICMPソケットの仕組みで動作するようになっている。setuid が root の全権限を与えるのに対し、ケーパビリティは必要な権限だけを与えるので、最小権限の原則により適合する。

### 2.9 ⑨ ログの設定

システム管理者は、重要なファイルへのアクセス履歴やログインの成功／失敗の履歴、その他セキュリティに関する警告やエラーメッセージが、**ログ**として適切に記録されるように設定します。ログがなければ、攻撃を受けても気づけず、侵入された後に「いつ、どこから、何をされたか」を調べることもできないからです。

たとえば、SSHへのパスワード攻撃を受けると、Linux の認証ログには次のような行が並びます。

```
Sep 30 03:12:41 web01 sshd[2101]: Invalid user admin from 198.51.100.23 port 51230
Sep 30 03:12:43 web01 sshd[2101]: Failed password for invalid user admin from 198.51.100.23 port 51230 ssh2
Sep 30 03:12:47 web01 sshd[2104]: Failed password for root from 198.51.100.23 port 51244 ssh2
Sep 30 03:12:52 web01 sshd[2107]: Failed password for invalid user test from 198.51.100.23 port 51260 ssh2
Sep 30 03:13:05 web01 sshd[2115]: Accepted password for test01 from 198.51.100.23 port 51301 ssh2   ← 危険
```

同じ送信元から存在しないユーザ（`admin`、`test`）や `root` への失敗が短時間に続き、最後に `test01` でログインに**成功**しています。このログから、システム管理者は「⑥で削除すべきだったテスト用アカウントが、⑦の弱いパスワードのまま残っていて侵入された」と読み取れます。Windows では、ログオン失敗はセキュリティログのイベントID 4625、成功は 4624 として記録されます。

> **補足**
> ログは不正アクセスの検知や事後の原因調査に欠かせない証跡である。攻撃者による改ざんや消去を防ぐため、ログサーバへの転送やアクセス権の適切な設定、ログ領域の容量管理などもあわせて検討するとよい。

攻撃者は侵入に成功すると、痕跡を消すためにまずログを削除・改ざんしようとします。そこでシステム管理者は、ログを発生と同時に別のログサーバへ転送しておくべきです。rsyslog での設定例を示します。

```
# /etc/rsyslog.d/90-forward.conf（例）
# 認証関連を含むすべてのログを、ログサーバ 192.0.2.50 へTCPで転送する
*.*  @@192.0.2.50:514
```

転送先のログサーバでは、Webサーバの管理者とは別の担当者だけが書込み・削除の権限をもつようにしておけば、Webサーバが乗っ取られてもログは守られます（1.2 の職務分離、4.10 の監査証拠としてのログの完全性）。また、各サーバの時刻を NTP で同期しておかないと、複数サーバのログを突き合わせたときに前後関係がわからなくなります。

## 3. 要塞化後の維持管理

### 3.1 堅牢さは時間とともに失われる

いったん要塞化が完了したホストであっても、堅牢な状態がいつまでも維持できるわけではありません。新たな脆弱性は日々発見されており、サーバの構成や設定が一部変更されただけでも、それが重大な脆弱性になってしまう場合があります。たとえば、障害調査のために一時的にデバッグ用ポートを開け、そのまま閉じ忘れる、といったことが現場ではよく起こります。

そのため、システム管理者は、常に最新のセキュリティ関連情報を収集して重要な情報を見落とさないよう留意するとともに、ホストの堅牢さを維持できるよう随時点検すべきです。点検の手段としては、5.3 で学ぶ**脆弱性診断**を定期的に受けること、設定の基準値（ベースライン）を決めておき、それとの差分を定期的に確認することが有効です。

### 3.2 要塞化チェックリスト

本ノートの実施項目を、システム管理者が構築時と定期点検で使えるチェックリストの形にまとめます。

| No. | 確認項目 | 確認方法の例 | 実施時期 |
|---|---|---|---|
| 1 | ログ領域・一時領域が別パーティションで、`/tmp` に `noexec,nosuid` が付いている | `/etc/fstab`、`mount` の出力 | 構築時 |
| 2 | アクセス権を設定できるファイルシステム（NTFS、ext4／xfs 等）を使っている | ディスクの管理画面、`df -T` | 構築時 |
| 3 | 最小インストールで構築し、不要なパッケージが入っていない | パッケージ一覧 | 構築時・年1回 |
| 4 | 最新のセキュリティパッチが適用されている（検証済み） | 更新の確認コマンド、構成管理台帳 | 月1回＋緊急時 |
| 5 | 待ち受けポートが業務に必要なものだけである | 内側から `ss -tlnp`／`netstat -ano`、外側から nmap | 構築時・変更時・四半期ごと |
| 6 | サンプルファイル・サンプルCGI・管理画面の公開が残っていない | ドキュメントルートの確認 | 構築時・変更時 |
| 7 | ゲスト・テスト用アカウントが無効化・削除されている | `net user`、`/etc/passwd` | 月1回（人事異動と突合） |
| 8 | 管理者アカウントの名称変更、管理共有の解除、匿名接続の無効化がされている | ユーザ一覧、共有一覧、レジストリ・グループポリシ | 構築時・年1回 |
| 9 | パスワードポリシ（長さ、辞書照合、ロックアウト）が有効である | `pwquality.conf`、`net accounts` | 構築時・年1回 |
| 10 | 不要な setuid/setgid 属性がなく、ディレクトリ・ファイルの権限が最小である | `find / -perm -4000`、`ls -l` | 構築時・四半期ごと |
| 11 | 認証の成功／失敗、重要ファイルへのアクセスがログに記録され、ログサーバに転送されている | ログ設定ファイル、ログサーバでの受信確認 | 構築時・月1回 |
| 12 | 時刻がNTPで同期されている | `chronyc tracking` などの出力 | 構築時・月1回 |

このチェックリストは、4.10 で学んだ監査で監査人が用いる「チェックリスト法」の材料にもなります。システム管理者が自ら点検した結果を記録として残しておくことは、監査の際の監査証拠にもなります。

## 4. 確認問題

### 4.1 理解度チェック

- **Q1**：ホストの要塞化とは何か。
  - 解答例：OSをはじめとするソフトウェアに内在するバグや設定ミスなどによるセキュリティホールを塞ぎ、ホストを堅牢な状態にすることである。具体的には、OSやアプリケーションのバージョンの最新化、パッチの適用、不要なサービスや機能の停止などを行う。
- **Q2**：なぜ、ホストの要塞化が重要なのか。
  - 解答例：一般的なファイアウォールは、公開サーバへの許可された通信（例：HTTP）をほぼ無条件で通過させるため、サーバの脆弱性を突くBOF攻撃やSQLインジェクションはファイアウォールをすり抜けて届いてしまう。また、ポートスキャンは無差別かつ日常的に行われており、要塞化されていないサーバはすぐに見つかり、サイト全体のセキュリティレベルが低いと判断されて集中的に攻撃される。逆に要塞化されたサイトは侵入困難と判断され、攻撃を受けにくくなる。
- **Q3**：ホストの要塞化の具体的な実施事項として何があるか。
  - 解答例：①最適なパーティション設計、②セキュアなファイルシステムの選択、③最新バージョンのソフトウェアを最小構成でインストール、④パッチの適用、⑤不要なサービスや機能の停止（サンプルファイルの削除を含む）、⑥不要なアカウントの削除と管理者アカウントの管理、⑦推測困難なパスワードの設定とパスワードチェック機能の有効化、⑧ディレクトリ・ファイル・プログラムなどのアクセス権の設定、⑨ログの設定がある。
- **Q4**：パッチ適用における注意事項として何があるか。
  - 解答例：パッチはソフトウェアの一部を変更するため、動作が不安定になったり、他のソフトウェアや機能に影響を及ぼしたりする可能性がある。そのため、本番環境に適用する前に影響度を調査し、検証用の環境で実際に適用して動作状況を確認する必要がある。また、最新バージョンのインストールパッケージでも最新のパッチが含まれているとは限らないため、インストール後に別途適用する。
- **Q5**：アカウント及びパスワードの設定における注意事項として何があるか。
  - 解答例：ゲストアカウントやテスト用アカウントなどの不要なアカウントは削除または無効にする。Administratorのように名称が広く知られた管理者アカウントは名称を変更し、最小権限のダミーを作成することも有効である。Windowsでは管理共有の解除や匿名接続（ヌルセッション）の無効化も行う。すべての有効なアカウントには推測困難なパスワードを設定させ、パスワードチェック機能（パスワードポリシー）を有効にして、短い、文字種が少ない、ユーザIDに酷似、個人情報を使用、初期設定のまま、長期間未変更、辞書の単語、といった脆弱なパスワードを設定できないようにする。

## 5. 試験対策まとめ（重要ポイント）

### 5.1 知識の確認（科目A-2向け）

- **要塞化の定義**：ソフトウェアのバグや設定ミスによるセキュリティホールを塞ぎ、ホストを堅牢にすること。主な作業はバージョンの最新化、パッチ適用、不要なサービス・機能の停止。特別なツールの購入は通常不要（保守契約があれば実施可能）。
- **アプライアンス と 汎用サーバ**：アプライアンスは出荷時点で一定の対策済み、汎用サーバは初期状態では不要なサービスやパッチ未適用が残りやすい。公開サーバでは要塞化が必須。
- **ファイアウォールがあっても要塞化は必要**：許可したポート（80/TCP など）への攻撃はファイアウォールを通過する。IPSやWAFより先に、まず要塞化を行う。
- **パーティション**：カーネル、アプリケーション、ユーザデータ、ログを分ける。ログ領域を分けるとログの大量出力でOS全体が止まるのを防げる。細かく分けすぎると空き領域の無駄や特定領域の満杯を招く。
- **ファイルシステム**：FAT32はファイル単位のアクセス権なし、NTFSはACLとEFSが使える。
- **インストール**：標準・フルではなく最小・カスタムインストール。
- **パッチ**：最新版のパッケージでも最新パッチが含まれるとは限らない。本番適用前に影響度調査と検証環境での確認。
- **サービス**：不要なサービス・コマンド・サンプルファイル（サンプルCGI）を削除・無効化。アタックサーフェスの縮小。
- **アカウント**：ゲスト・テスト用を削除、Administratorは名称変更＋ダミー作成、管理共有の解除、匿名接続（ヌルセッション）はレジストリで無効化。
- **パスワード**：8文字未満、文字種不足、ID酷似、個人情報、初期設定、長期間未変更、辞書の単語は脆弱。パスワードポリシーで設定を禁止する。現在のガイドラインは定期変更の強制より長さと漏えいパスワードの排除を重視。
- **setuid/setgid**：所有者（所有グループ）の権限で実行される。root所有のsetuidプログラムの脆弱性は root 権限の奪取につながるため、不要なものは属性を解除する。
- **ログ**：重要ファイルへのアクセス、ログイン成功／失敗、警告・エラーを記録。改ざん対策としてログサーバへ転送。

### 5.2 記述式で問われる観点（科目B向け）

- **侵入原因を設定の不備で説明する**：「テスト用アカウントが削除されず、推測容易なパスワードのまま残っていたため、SSHへのパスワード攻撃で侵入された」のように、ログやスキャン結果を根拠に、どの実施項目が欠けていたかを特定する。
- **不要サービスの判断理由を書く**：「telnet は通信が平文で認証情報が盗聴されるため停止し、SSHで代替する」「DBの待ち受けを外部に公開する必要がないため、ローカルホストに限定する」のように、止める理由と代替手段をセットで書く。
- **パッチを即時適用できない場合**：検証が必要な理由（業務停止のリスク）と、それまでの回避策（該当機能の無効化、WAF・IPSでの遮断）を答える。
- **ファイアウォールとの役割分担**：「ファイアウォールは許可したポートへの通信の中身を検査しないため、サーバ側の要塞化が必要である」と、多層防御の観点で説明する。
- **ログを守る**：「侵入者によるログの消去・改ざんを防ぐため、ログを別管理のログサーバへリアルタイムに転送する」「複数サーバのログを突き合わせるため、NTPで時刻を同期する」を書けるようにする。
- **維持管理**：要塞化は一度で終わらない。脆弱性情報の継続的な収集、定期的な脆弱性診断、設定変更時の再点検を提案する。
