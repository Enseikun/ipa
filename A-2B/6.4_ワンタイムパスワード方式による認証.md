# 6.4 ワンタイムパスワード方式による認証

ここでは、パスワードを用いた認証システムのうち、「ワンタイムパスワード方式」について解説する。

## 6.4.1 ワンタイムパスワード方式とは

ワンタイムパスワード（One Time Password：OTP）方式とは、その名のとおり、認証を行うたびに毎回異なるパスワードを使用する方式である。一度使用したパスワードは再利用せずに使い捨てるため、**使い捨てパスワード方式**とも呼ばれる。

脆弱な固定式パスワードの認証プロセスを暗号化することでセキュリティを高める方式もある。これに対してOTP方式は、パスワードの生成方法や使用方法などのメカニズムを工夫することでセキュリティを高めようとするものである。

OTP方式では毎回異なるパスワードを使用する。そのため、ある時点の認証プロセスが盗聴されたとしても、そのパスワードは二度と使用されない。したがって、なりすましによる不正アクセスを受ける可能性が著しく減少するというメリットがある。

ただし、単に毎回異なるパスワードになっていれば問題がないというわけではない。パスワードの強度や運用管理面を考慮すると、次のような要件を満たして、はじめて実運用に耐え得るOTP方式といえる。

- **生成するパスワードに規則性や連続性がなく、ランダムであること**
  ある時点のパスワードが分かったとしても、そこから次回以降のパスワードを推測できないようになっている必要がある。
- **パスワードの生成・入力が利用者にとって容易であること**
  利用者に過度な負担を強いる方式では、メモ書きなどの不適切な運用を招き、かえってセキュリティを低下させるおそれがある。
- **認証側（サーバ）と利用者側（クライアント）で、同じパスワードを正しく生成・照合できること**
  サーバとクライアントの間で、パスワード生成に用いる情報（時刻、カウンタ、シーケンス番号など）の整合性が保たれるような仕組みでなければならない。

OTP方式は、次のような方法で実現されている。それぞれ次項以降で解説する。

- チャレンジレスポンス方式
- S/Key（チャレンジレスポンス方式の一種）
- トークンカード（携帯認証装置）：代表例は時間同期式

## 6.4.2 チャレンジレスポンス方式によるOTP認証

チャレンジレスポンス方式とは、認証プロセスにおいて、「シード」（Seed：種）と呼ばれる固定パスワードそのものをネットワーク中に流さないようにする方式である。これにより、盗聴によってパスワードが盗まれるのを防ぐ。

### チャレンジレスポンス方式の仕組み

チャレンジレスポンス方式では、次のような仕組みで認証が行われる（下図参照）。

1. サーバが「チャレンジ」と呼ばれる乱数文字列をクライアントに送る。
2. クライアントは、「チャレンジ」と、保存してある自身のパスワードである「シード（Seed）」を組み合わせる。これをハッシュ関数に通して得た文字列（レスポンス）をサーバに返す。
3. サーバは、あらかじめ登録されているクライアントのパスワードを用いて同様の計算を行う。その結果と、クライアントから返されたレスポンスとを比較し、ユーザを認証する。つまり、両者が同じであれば認証可と判断する。

> **ハッシュ関数**
> 任意の長さのデータから、固定長の疑似乱数（ハッシュ値）を生成する演算手法。生成された値は「メッセージダイジェスト」とも呼ばれる。入力データがわずかでも異なれば、出力されるハッシュ値も大きく異なる。また、ハッシュ値から元のデータを求めることは困難である（一方向性）。

```
クライアント                              サーバ
    |  ―――― ① 認証要求 ――――――――――――――→  |
    |  ←――― ② チャレンジ（乱数）―――――――  |
    |                                        |
  チャレンジ＋Seed                            |
    → ハッシュ関数 → レスポンス              |
    |  ―――― ③ レスポンス ――――――――――――→  |
    |                          登録済みのパスワード＋チャレンジ
    |                            → ハッシュ関数 → 比較
    |  ←――― ④ 認証結果（一致すれば可）――  |
```

*図：チャレンジレスポンス方式による認証のイメージ*

Seedは固定だが、チャレンジの内容は認証のたびに毎回変化する。そのためレスポンスの内容も毎回変化し、OTPとなる。

### 認証プロトコルの例

チャレンジレスポンス方式によるOTP認証システムを実装している認証プロトコルとして、次のものがある。

- **CHAP（Challenge Handshake Authentication Protocol）**
  PAP（Password Authentication Protocol）と同様に、PPP（Point to Point Protocol）で使われている認証方式の一つである。PAPではパスワードが平文のまま送信される。これに対しCHAPでは上記の仕組みで認証が行われるため、PAPに比べて安全である。

> **PAP と CHAP**
> PAPはユーザIDとパスワードを平文でそのまま送信するため、盗聴に対して極めて弱い。CHAPはチャレンジとハッシュ関数（一般にMD5）を用いるため、パスワードそのものが回線上を流れない。

### チャレンジレスポンス方式のメリット

チャレンジレスポンス方式には、次のようなメリットがある。

- パスワードそのものがネットワーク中を流れることがない。
- 一方向性のハッシュ関数を用いているため、チャレンジ及びレスポンスが盗聴されたとしても、そこから計算に用いたパスワード（Seed）を求めるのは困難である。
- チャレンジの内容が毎回変わるため、ある時点のレスポンスが保存されたとしても、リプレイ攻撃をされる可能性は低い。
- 認証成立後も繰り返しチャレンジを送信して認証を行える。これにより、セッションハイジャックなどによるなりすまし行為を防止できる。

### チャレンジレスポンス方式の脆弱性

チャレンジレスポンス方式も万全とはいえず、次のような脆弱性がある。

- 安易なパスワードを設定している場合、盗聴されたチャレンジとレスポンスを基にオフラインパスワードクラックが行われ、パスワードが解析されてしまう可能性がある。
- CHAPには認証サーバの信頼性を確認する仕組みがない。そのため、偽の認証サーバによってセッションハイジャックが行われる可能性がある。

> **オフラインパスワードクラック**
> チャレンジとレスポンスを盗聴し、辞書攻撃や総当たり攻撃によってオフラインでパスワードを解析する手法。代表的なクラックツールとして、Windowsのパスワード解析などに用いられた「L0phtCrack」などが知られている。

## 6.4.3 S/KeyによるOTP認証システム

S/Keyは、チャレンジレスポンスによるOTP方式の一種であり、フリーウェアとして提供されている。S/Keyでは、次のような仕組みでOTPを生成する。

### OTPの生成に用いられる要素

- **Seed（種）**：サーバがユーザごとに生成する任意の短い文字列
- **パスワード**：ユーザが設定する秘密の文字列（パスフレーズの基となる）
- **シーケンス番号**：ログイン可能な残り回数を表す番号。ログインのたびに1ずつ減少する
- **ハッシュ関数**：MD4、MD5などの一方向性ハッシュ関数

### 初期処理

クライアントは、サーバに対してSSHなどでログインするか、ローカル環境からアクセスして、クライアント自身の1回目のパスフレーズを生成・登録しておく。

パスフレーズは、「Seed」と「パスワード」を連結した文字列（s）を入力値として、ハッシュ関数（f）をログインの最大回数（n）分繰り返し演算した結果である。

1. 1回目の計算では、文字列sとハッシュ関数fにより、P1が求められる。
2. 次に、P1とハッシュ関数fにより、P2が求められる。
3. これをログインの最大回数（n）分繰り返す。
4. 最終的に求められたPnを初期値（1回目のパスフレーズ照合用の値）としてサーバに保存する。
5. nをシーケンス番号の初期値としてサーバに保存する。

- s：Seedとパスワードを連結した文字列
- f：MD4、MD5などのハッシュ関数

```
P1 = f(s)
P2 = f(f(s))       = f(P1)
P3 = f(f(f(s)))    = f(P2)
P4 = f(f(f(f(s)))) = f(P3)
  ⋮
Pn = fⁿ(s)         = f(Pn-1)
```

> **SSH（Secure Shell）**
> ネットワークを介して別のコンピュータにログインし、コマンドを実行するためのアプリケーション及びプロトコル。通信内容を暗号化して送受信する方式である。主に、BSD系UNIXのrlogin・rshなどのrコマンドや、X11などのリモート操作を安全に行うための手段として利用されている。暗号化アルゴリズムとしてはTriple DES、Blowfish、AESなどが採用されており、セッションごとに異なる使い捨ての共通鍵が生成される。

ここでポイントとなるのは、ハッシュ関数の一方向性である。Pn-1からPnを求めることは可能だが、PnからPn-1を求める（逆算する）ことはできない。

つまり、初期処理で最終的に求められたPnを照合の起点とし、ログインのたびにPn-1、Pn-2、……というように演算回数を1回ずつ減らした値をパスワードとして使用する。こうすることで、ある時点のパスワードが盗聴されたとしても、そこから次回のパスワードを求めることはできない。

### 1回目のログイン時の処理

前提として、サーバには次の二つが保存されている。

- シーケンス番号の最大値n
- クライアントが初期処理でハッシュ関数をn回繰り返して求めたパスフレーズPn

```
クライアント（A）                                   サーバ
    |  ―― ① ログイン要求（ユーザID）――――――――――→  |
    |  ←― ② チャレンジ（シーケンス番号 n-1、Seed）―  |
    |                                                  |
  ③ Seed＋パスワード → f を n-1 回演算 → Pn-1         |
    |  ―― ③ レスポンス（Pn-1）――――――――――――――→  |
    |                          ④ f(Pn-1) を計算し、保存済みの Pn と比較
    |                          ⑤ Pn を破棄し Pn-1 を保存、番号を n-1 に更新
    |  ←― 認証結果 ――――――――――――――――――――――  |
```

*図：S/Keyによる認証のイメージ*

1. クライアントがサーバに対しログインを要求する（ユーザIDの入力）。
2. サーバはクライアントからの要求を受け取ると、保存していたシーケンス番号を1減じた値（n-1）と、Seedをチャレンジとしてクライアントに送る。
3. クライアントは、受け取ったSeedと自身のパスワードを連結した文字列sに対し、ハッシュ関数をn-1回繰り返し演算してPn-1を求める。これをレスポンスとしてサーバに送る。
4. サーバは、受け取ったPn-1にもう1回ハッシュ関数で演算を行い、Pnを求める。これと、もともと保存されていたPnを比較し、両者が同じ値であれば正当な利用者だと判断する。
5. サーバは保存していたPnを破棄し、代わりに今回レスポンスとして受け取ったPn-1を保存する。加えて、シーケンス番号を1減じて保存しておく。

以降は、新たに保存された二つの値（パスフレーズ：Pn-1、シーケンス番号：n-1）を基に、同様の処理を行う。サーバがチャレンジとして送るシーケンス番号が1になるまで、ログインが可能である。これが0になるとログインできなくなるため、その前にクライアントは新たなパスフレーズを生成する処理（再初期化）を行う必要がある。

> **S/Keyのポイント**
> サーバには「前回使用されたパスワード」しか保存されない。そのため、サーバに保存された値が漏えいしても、次回のパスワードを求めることはできない。

### S/Keyにおけるセキュリティ上の留意点

チャレンジレスポンス方式で解説したように、S/Keyにもサーバの正当性を確認する仕組みがない。そのため、正規のサーバとクライアントの通信経路上に不正なサーバが介在すると、セッションをハイジャックされてしまう可能性がある。これを**Man-in-the-middle Attack（中間者攻撃）**と呼ぶ。

このような脅威に対しては、SSL/TLSのように、通信に先立ちデジタル証明書によってクライアントがサーバの正当性を確認する方式の採用などが対抗策となる。

また前述のように、S/Keyでは、初期処理でパスフレーズをサーバに登録する際に盗聴されないようにする必要がある。そのため、SSHなどの暗号化通信を用いるか、サーバのローカル環境で操作を行わなければならない。

さらに、シーケンス番号が小さい値のチャレンジを偽サーバから送られると、攻撃者はそこから大きい番号のパスワードを計算できてしまう。そのため、シーケンス番号の不自然な減少にも注意を払う必要がある。

## 6.4.4 トークン（携帯認証装置）によるOTP認証

トークンと呼ばれる携帯型の認証装置（又はソフトウェア）を利用者に配布し、これを用いてOTPを生成する方式である。トークンによるOTP認証システムには、主に次のような方式がある。

- **時間同期式**：時刻情報を基にOTPを生成する方式（代表例）
- **イベント同期式（カウンタ同期式）**：トークンのボタン押下回数などのカウンタ値を基にOTPを生成する方式
- **チャレンジレスポンス式**：サーバから提示されたチャレンジをトークンに入力し、その結果をOTPとして用いる方式

> **HOTPとTOTP**
> イベント同期式の標準的なアルゴリズムとしてHOTP（HMAC-based One-Time Password、RFC 4226）がある。時間同期式の標準的なアルゴリズムとしてはTOTP（Time-based One-Time Password、RFC 6238）がある。近年では、スマートフォンの認証アプリなどでTOTPが広く用いられている。

### 時間同期式OTP認証システム

この方式では、認証を行う各サーバとクライアント（トークン）との間で時間の同期をとる。そのうえで、日付／時刻とユーザの個人識別番号（Personal Identification Number：PIN）によってOTPを生成する。

```
利用者 ─ トークン（トークンコード表示）
   │  PINコード＋トークンコード（＝パスコード）を入力
   ▼
クライアント ── インターネット ── エージェント（アクセスサーバ）
                                        │ 問合せ／応答
                                        ▼
                                   認証サーバ（ユーザ情報DB）
                          ※トークンと認証サーバは時刻を同期
```

*図：時間同期式によるOTP認証システムの例*

### システムの構成要素

時間同期式OTP認証システムは、次の要素によって構成される。

#### トークン

認証サーバと時間同期し、一定時間（60秒など）ごとに変化するパスワード（トークンコード）を生成する。ユーザは、あらかじめ設定したPINコードとトークンコードをパスコードとして入力し、認証を行う。

トークンは、ユーザの利用形態などに応じて、次のような様々な種類から選択できる。

- **ハードウェアトークン**：キーホルダー型、カード型など、トークンコードを液晶画面に表示する専用装置
- **ソフトウェアトークン**：PCやスマートフォンにインストールして利用するソフトウェア
- **USBトークン／ICカード型**：端末に接続して利用するもの

#### 認証サーバ

トークンのシリアル番号、ユーザ名、PINコードなどのユーザ情報をDBで管理する。クライアントからの問合せがあると、DBに登録された情報から自らもパスコードを生成する。そして、それとクライアントが送ってきたパスコードとを比較し、ユーザを認証する。

認証サーバには、ユーザ情報の管理方法などによって、次のような様々な機能をもった製品がある。

- 自身が管理するユーザ情報と、ディレクトリサーバが管理するユーザ情報とを自動的に同期させる機能をもつもの
- RADIUSサーバに専用のプラグインソフトウェアをインストールすることで、同サーバを認証サーバとして用いることができるもの

ユーザ情報の管理が煩雑にならないよう、既存の環境との親和性やユーザ情報の一元管理などを考慮し、最適な認証システムを設計・構築する必要がある。

また、認証システムの可用性を十分に確保することも重要である。そのため、プライマリ認証サーバの障害時に処理を代行するセカンダリ認証サーバ（レプリカサーバ）の設置も検討する必要がある。

なお、トークンの内部時計には誤差（時間のずれ）が生じ得る。そのため認証サーバには、一定範囲の時間のずれを許容し、補正する機能が備わっているのが一般的である。

#### エージェント（アクセスサーバ）

クライアントからのアクセス要求を受け付け、認証サーバへの問合せと認証結果の応答を行うもの。通常は、RASサーバやファイアウォールなどがこの役割を担う。アクセスサーバとして使用する機器には、専用のエージェントソフトウェアをインストールする必要がある。

このようなOTP認証システムは、ほかの認証・通信システムと連携させることで、セキュアで使い勝手のよいリモートアクセス環境を構築できる。連携先としては、次のようなものがある。

- 6.8節で解説するシングルサインオン
- RADIUS、TACACS+による認証システム
- SSL-VPN、IPsec-VPNによる認証＆暗号通信システム

> **シングルサインオン（SSO）**
> 認証を必要とする複数のシステムが存在する環境で、1回認証に成功すれば、利用が許可されている範囲のシステムに、認証を繰り返すことなくそのままアクセスできるようにする認証システム（6.8節で解説）。

> **RADIUS（Remote Authentication Dial In User Service）**
> ネットワーク利用者の認証、認可、アカウンティング（利用記録）を一元的に行うためのシステム及びプロトコル。

> **TACACS+（Terminal Access Controller Access Control System Plus）**
> TACACSは、利用者の認証やネットワーク機器の利用記録などを一元管理するシステム。TACACS+はその拡張・強化版であり、認証・認可・アカウンティングの各機能を分離して扱える。

> **SSL-VPN**
> SSL/TLSを用いて通信を暗号化し、Webブラウザなどを通じて安全なリモートアクセスを実現するVPN方式。

> **IPsec（IP Security）**
> パケットをIP層（OSI基本参照モデルのネットワーク層）で暗号化・認証するプロトコル群。IPsec-VPNで用いられる。

### トークンの運用管理上の留意点

トークンは、OTPを生成するための重要な装置である。そのため、紛失・盗難が発生しないよう管理面での対策を徹底する必要がある。具体的には、トークンの悪用を防ぐため、次のような対策が必要となる。

- トークンの使用にあたっては、最初にPINコードなどの入力を必要とするようにする。
- PINコードには、一般的なパスワードと同様に推測されにくいものを設定する。
- トークン（ハードウェアの場合）に組織名や氏名などを記載しないようにする。社員証と併用するような運用は避けなければならない。
- 紛失・盗難が判明した場合に、直ちに当該トークンを無効化できる手順と連絡体制を整備しておく。

## 確認問題

### 確認問題1

S/KEYワンタイムパスワードに関する記述のうち、適切なものはどれか。

- ア　クライアントは認証要求のたびに、サーバへシーケンス番号と種（Seed）から生成したチャレンジデータを送信する。
- イ　サーバはクライアントから送られた使い捨てパスワードを演算し、サーバで記憶している前回の使い捨てパスワードと比較することによって、クライアントを認証する。
- ウ　時刻情報を基にパスワードを生成し、クライアント、サーバ間でパスワードを同期させる。
- エ　利用者が設定したパスフレーズは1回ごとに使い捨てる。

［情報セキュリティスペシャリスト試験・H22春・午前Ⅱ］

#### 解答・解説

S/KEY（S/Key）ワンタイムパスワードでは、サーバが、クライアントから送られた使い捨てパスワードにハッシュ関数による演算を1回行う。そして、記憶している前回の使い捨てパスワードと比較することによって、クライアントを認証する。よって、**イ**が正解である。

- ア：シーケンス番号と種（Seed）をチャレンジとして送信するのは、クライアントではなくサーバである。
- ウ：時刻情報を基にパスワードを生成するのは、トークンによる時間同期式の説明である。
- エ：使い捨てるのは、パスフレーズから生成された使い捨てパスワードである。利用者が設定したパスフレーズ（パスワード）自体は、繰り返し使用される。

### 確認問題2

チャレンジレスポンス認証方式の特徴はどれか。

- ア　TLSによって、クライアント側で固定パスワードを暗号化して送信する。
- イ　端末のシリアル番号を、クライアント側で秘密鍵を使って暗号化して送信する。
- ウ　トークンという装置が表示する毎回異なったデータを、パスワードとして送信する。
- エ　利用者が入力したパスワードと、サーバから送られてきたランダムなデータとをクライアント側で演算し、その結果を送信する。

［情報処理技術者試験 高度共通・H28秋・午前Ⅰ］

#### 解答・解説

チャレンジレスポンス方式とは、次のような仕組みで利用者を認証する方式である。

1. サーバが「チャレンジ」と呼ばれる乱数文字列をクライアントに送る。
2. クライアントは、「チャレンジ」と、利用者があらかじめ入力しておいたパスワードを組み合わせる。これをハッシュ関数などで演算した結果（レスポンス）をサーバに返す。
3. サーバは、登録されている利用者のパスワードを用いて同様の演算を行い、その結果とレスポンスとを比較して利用者を認証する。

したがって、**エ**が正解である。

- ア：TLSによる通信経路の暗号化の説明であり、チャレンジレスポンス方式の特徴ではない。
- イ：秘密鍵を用いた端末認証（デジタル署名など）の説明である。
- ウ：トークンによるワンタイムパスワード方式（時間同期式など）の説明である。
