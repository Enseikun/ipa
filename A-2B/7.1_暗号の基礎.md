## 1. 暗号の概念

### 1.1 暗号とは ― アルゴリズムと鍵

まず、言葉を正確に定義しておきましょう。**暗号** とは、何らかの意味のある文字や記号などを、①「ある定められた約束事」に従い、②「固有の値」を用いて、他の文字や記号などに変換することです。この変換操作を **暗号化**、暗号化によって得られた文字列や記号を元に戻す操作を **復号** といいます。

①は何らかの数学的な処理であり、通常は **暗号アルゴリズム**、あるいは単に **アルゴリズム** と呼びます。また、同じアルゴリズムでも異なる結果を出すために与える②を **鍵** と呼びます。鍵には、暗号化に用いる **暗号鍵** と、復号に用いる **復号鍵** があります。鍵は数バイトから数百バイトのデータであり、その長さはビット単位で表現することが多い（例：128ビット鍵、2048ビット鍵）です。同じアルゴリズムであれば、利用者が長い鍵を用いるほど暗号の強度は高まります。つまり、攻撃者にとって解読されにくくなります。

現代の暗号では、アルゴリズムは公開されているのが普通です（AES や RSA の仕様は誰でも読めます）。安全性を支えているのは「鍵が秘密であること」と「鍵が十分に長いこと」です。したがって、暗号を運用する管理者が守るべき対象は、アルゴリズムではなく **鍵** だということになります。科目Bで「鍵管理」が独立した業務観点として挙げられているのは、このためです。

> **用語解説：平文と暗号文**
> 暗号化する前の元のデータを「**平文**（ひらぶん）」、暗号化した後のデータを「**暗号文**」という。暗号鍵をもたない第三者が、暗号文から平文を推測・導出することを「**解読**」という。正規の受信者が復号鍵を使って元に戻す「復号」とは区別される。

| 操作 | 誰が行うか | 鍵を持っているか | 目的 |
|---|---|---|---|
| 暗号化 | 送信者（正規の利用者） | 暗号鍵を持つ | 平文を第三者に読めない暗号文にする |
| 復号 | 受信者（正規の利用者） | 復号鍵を持つ | 暗号文を平文に戻して読む |
| 解読 | 第三者（攻撃者） | 持たない | 鍵なしで暗号文から平文を推測・導出する |

### 1.2 暗号技術の二つの機能

暗号技術には、次の二つの機能があります。

- 情報などの **秘匿**
- 情報などの **認証**（メッセージ認証）及び **署名**

後者は、ハッシュ関数やデジタル署名によって実現されています。第1章 1.2 の特性と対応づけると、次のようになります。どの技術がどの特性を守るのかを区別できることが、科目A-2 の正誤判定でも科目Bの記述でも土台になります。

| 機能 | 守る特性（第1章 1.2） | 実現する技術（本ノートの節） | 守れないもの |
|---|---|---|---|
| 秘匿 | 機密性 | 共通鍵暗号（2節）、公開鍵暗号（3節）、ハイブリッド方式（4節） | 改ざんの検知（暗号化だけでは、書き換えられても気づけないことがある） |
| メッセージ認証 | 完全性・真正性 | ハッシュ関数（6.1）、MAC・HMAC（6.4・6.5） | 否認防止（MAC は受信者も作れるため） |
| 署名 | 完全性・真正性・否認防止 | デジタル署名（3.6） | 機密性（署名しただけでは中身は読める） |

### 1.3 古典暗号から現代暗号へ

古典的な暗号方式には、次の二つがあります。

- **転置式暗号**：一定の規則に基づいて文字の順番を入れ替え、暗号文を生成する方式（例：password → drowssap）
- **換字式暗号**：一定の規則に基づいて、文字を別の文字や記号などに変換する方式（例：各文字をアルファベット順で3文字ずらすシーザー暗号。abc → def）

これらの古典暗号は、攻撃者に規則が知られてしまうと容易に解読されます。たとえばシーザー暗号であれば、ずらす文字数は25通りしかないため、攻撃者は全部試すだけで平文を得られます。そのため現代の暗号は、数学的に解読が困難な処理を行うアルゴリズムと、秘密にすべき鍵を組み合わせて安全性を確保しています。現代の暗号方式は、鍵の扱い方によって **共通鍵暗号方式** と **公開鍵暗号方式** に大別されます。以下、それぞれについて解説します。

## 2. 共通鍵暗号方式

### 2.1 仕組み ― 送信者と受信者が同じ鍵を持つ

共通鍵暗号方式は、暗号化と復号に同じ鍵を用いる方式であり、**対称鍵暗号方式** とも呼ばれます。送信者と受信者は、暗号鍵と復号鍵（共通の鍵）を送信者・受信者以外に知られないよう秘密にしておく必要があることから、**秘密鍵暗号方式** とも呼ばれます（公開鍵暗号方式の「秘密鍵」と紛らわしいので、試験では文脈で区別してください）。

**図：共通鍵暗号方式のイメージ**

```
 送信者                                              受信者
 平文 ──[暗号化(共通鍵K)]──> 暗号文 ──(送信)──> [復号(共通鍵K)]──> 平文
        └──────────── 同一の共通鍵Kを双方が保持 ────────────┘
```

誰がどの鍵を持ち、何に使うかを整理すると次のとおりです。

```
  ┌─────────┐   鍵Kを事前に安全な手段で共有    ┌─────────┐
  │ 送信者A │ ───────────────────────── │ 受信者B │
  │ 持つ: K │                                   │ 持つ: K │
  └────┬────┘                                   └────┬────┘
       │ Kで暗号化                                   │ Kで復号
       └──────── 暗号文（盗聴者Eには読めない） ──────┘
                        ↑
                  盗聴者E（Kを持たない）
```

ここで問題になるのが、「鍵Kを事前に安全な手段で共有」の部分です。送信者Aが鍵Kをメールで送れば、通信路を盗聴している攻撃者Eも鍵Kを手に入れ、以後の暗号文をすべて復号できてしまいます。これが共通鍵暗号方式の最大の弱点である **鍵配送問題** です。

共通鍵暗号方式は、次の3節で解説する公開鍵暗号方式と並んで、様々な暗号化技術や製品の基礎となる方式です。両方式の比較は3.2でまとめて示します。

### 2.2 ストリーム暗号

共通鍵暗号方式は、**ストリーム暗号** と **ブロック暗号** に大別されます。

ストリーム暗号は、平文をビット、バイト、あるいは文字ごとに逐次処理する暗号方式です。代表的なものに RC4 があります。主な特徴は次のとおりです。

- 暗号化する側は、**キーストリーム**（鍵ストリーム）と呼ばれる疑似乱数を暗号鍵として使用する。平文とキーストリームの XOR 演算によって暗号文を生成する
- ブロック暗号よりも処理を単純化できるため、処理速度が速い
- 暗号化してもデータサイズが増加しないため、通信での利用に適している

```
 平文       : 0 1 1 0 1 0 0 1 ...
 キーストリーム: 1 1 0 1 0 0 1 1 ...   ← 鍵から生成した疑似乱数
 XOR        ────────────────────
 暗号文     : 1 0 1 1 1 0 1 0 ...   （受信者は同じキーストリームとXORして平文に戻す）
```

**表：主なストリーム暗号方式**

| 名称 | 概要 |
|---|---|
| RC4 | Ronald Rivest 氏が1987年に開発したストリーム暗号方式。SSL/TLS や無線LAN（WEP、WPA）などで広く使用されていたが、近年は脆弱性の研究が進み、利用を禁止する動きが広がっている（TLS では RFC 7465 で使用が禁止された）。無線LAN での経緯は第7章 7.6 で扱う |
| KCipher-2 | 後述する CRYPTREC 暗号リスト推奨のストリーム暗号方式で、九州大学と KDDI研究所によって共同開発された。鍵と初期ベクトルの長さはそれぞれ128ビット |

ストリーム暗号を使う開発者は、**同じ鍵と同じ初期ベクトルの組合せを二度使ってはいけません**。同じキーストリームで二つの平文を暗号化すると、二つの暗号文を XOR するだけでキーストリームが打ち消され、平文どうしの XOR が攻撃者に漏れてしまうからです（後述の CTR モードでも同じ注意が必要です）。

### 2.3 ブロック暗号

ブロック暗号は、平文を一定のサイズ（ブロック）に分割し、ブロックごとに暗号処理を行う方式です。代表的なものに DES があります。ブロック長は64ビットや128ビットが一般的です。平文の長さがブロック長の整数倍にならない場合、暗号化する側は **パディング** を付加してブロック長に揃えます。

```
 平文（40バイト）: [ 16バイト ][ 16バイト ][ 8バイト + パディング8バイト ]
                     ブロック1    ブロック2    ブロック3（128ビット=16バイトに揃える）
```

**表：主なブロック暗号方式**

| 名称 | ブロック長 | 鍵長 | 概要 |
|---|---|---|---|
| DES | 64ビット | 56ビット | Data Encryption Standard。1975年に米国商務省標準局（NBS、現 NIST）で公表され、1977年以降は米国政府の標準暗号として採用された。鍵長が短く、現在では総当たり攻撃による解読が現実的な脅威となっている |
| Triple DES（3DES） | 64ビット | ― | DES を三重に適用することによって強度を高めたもの。解読されるリスクの高まりから、CRYPTREC 暗号リストでは運用監視暗号リストに掲載されており、互換性維持のための継続利用に限られる |
| AES | 128ビット | 128／192／256ビットから選択 | Advanced Encryption Standard。DES の後継となる米国政府の次世代標準暗号方式。段数（ラウンド数）は鍵の長さに応じて10段、12段、14段となる。CRYPTREC 暗号リスト推奨のブロック暗号方式である |
| Camellia | 128ビット | 128／192／256ビットから選択 | CRYPTREC 暗号リスト推奨のブロック暗号方式で、NTT と三菱電機により共同開発された。安全性と効率性の高さが評価されている |
| IDEA | 64ビット | 128ビット | International Data Encryption Algorithm。スイス連邦工科大学チューリッヒ校の James L. Massey 氏と Xuejia Lai 氏によって考案された方式。初期の PGP（第3章 3.4）で用いられた |

DES の56ビット鍵は、鍵の候補が $2^{56}$（約7.2京）通りしかありません。現在の計算機では攻撃者がこれを総当たりで試し切れるため、DES は使ってはいけない暗号です。AES-128 の候補は $2^{128}$ 通りで、$2^{56}$ の $2^{72}$ 倍（約 $4.7 \times 10^{21}$ 倍）に当たります。鍵長が1ビット増えるごとに総当たりの手間は2倍になる、という感覚を持っておきましょう。

### 2.4 暗号モード（暗号利用モード）

**なぜ暗号モードが必要か**

ブロック暗号には、各ブロックを単純に同じ鍵とアルゴリズムで暗号化すると、解読されやすくなるという弱点があります。同じ内容の平文ブロックからは同じ暗号ブロックが生成され、平文のパターンが暗号文に現れてしまうためです。そこで、処理を複雑にして暗号の強度を高める暗号化手法が確立されています。この手法を「**暗号モード**」もしくは「**暗号利用モード**」と呼びます。

実際に見てみましょう。同じ文字 `A` を32バイト（2ブロック分）並べた平文を、同じ AES-128 鍵で ECB モードと CBC モードで暗号化し、16バイト（1ブロック）ずつ16進数で表示すると次のようになります。

```
$ printf 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA' > rep.txt
$ openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f -nopad -in rep.txt | od -An -tx1 -w16 -v
 dd 4b 1a 0b 47 da a7 06 7d 0b 59 d9 5d 58 a6 ae    ← ブロック1
 dd 4b 1a 0b 47 da a7 06 7d 0b 59 d9 5d 58 a6 ae    ← ブロック2（ブロック1と同じ！）

$ openssl enc -aes-128-cbc -K 000102...0f -iv 0f0e0d...00 -nopad -in rep.txt | od -An -tx1 -w16 -v
 15 86 b9 7f 7a e7 54 2a 36 68 a6 ac b0 4d b8 79    ← ブロック1
 6b 30 c8 a2 5d 47 12 98 b5 10 6b 03 9a 61 f2 f2    ← ブロック2（まったく違う値）
```

ECB モードでは、攻撃者は鍵を知らなくても「ブロック1とブロック2の中身は同じだ」と分かってしまいます。画像を ECB で暗号化すると輪郭が透けて見える、という有名な例もこの性質によるものです。主な暗号モードを次に示します。

**ECB（Electronic Code Book）モード**

ECB は、暗号ブロック間に関連性をもたせず、単に平文をブロックごとに区切って暗号化する方式です。各ブロックが独立しているため、並列処理が可能で高速です。ただし暗号の強度は低いため、開発者は ECB を使用すべきではありません。

**CBC（Cipher Block Chaining）モード**

CBC は、一つ前の平文ブロックの暗号結果（暗号ブロック）と次の平文ブロックを XOR 演算し、その結果を暗号化する方式です。最初のブロックの暗号化では、外部から与えた **初期ベクトル**（Initial Vector：IV）を用いて XOR 演算を行います。暗号の強度が高く、広く使用されています。暗号化は前のブロックの結果に依存するため並列処理ができませんが、復号は並列処理が可能です。

**図：CBCモードのイメージ**

```
      平文1         平文2         平文3
        │             │             │
 IV ─→ XOR   ┌──→ XOR   ┌──→ XOR
        │     │       │     │       │
     暗号化(K)│    暗号化(K)│    暗号化(K)
        │     │       │     │       │
     暗号文1 ─┘    暗号文2 ─┘    暗号文3
```

**CFB（Cipher Feedback）モード**

CFB は、最初に IV を暗号化し、それと1番目の平文ブロックとの XOR 演算によって1番目の暗号ブロックを生成します。続いて1番目の暗号ブロックを暗号化し、それと2番目の平文ブロックとの XOR 演算によって2番目の暗号ブロックを生成します。以降もこれを繰り返します。暗号の強度は高く、ブロック暗号をストリーム暗号のように利用できます。

**OFB（Output Feedback）モード**

OFB は、最初に IV を暗号化し、それと1番目の平文ブロックとの XOR 演算によって1番目の暗号ブロックを生成します（ここまでは CFB と同じ）。続いて、暗号化された IV をさらに暗号化し、それと2番目の平文ブロックとの XOR 演算によって2番目の暗号ブロックを生成します。以降もこれを繰り返します。暗号の強度は高く、各ブロックの独立性も高いです。暗号文の1ビットの誤りが他のブロックに波及しないという特徴があります。

**図：OFBモードのイメージ**

```
 IV ─→ 暗号化(K) ─→ 暗号化(K) ─→ 暗号化(K) ─→ …
          │              │              │
 平文1 ─→ XOR   平文2 ─→ XOR   平文3 ─→ XOR
          │              │              │
       暗号文1        暗号文2        暗号文3
```

**CTR（Counter）モード**

CTR は、nonce（使い捨てのランダム値）と、1ずつ増加するカウンタから成る値を暗号化して鍵ストリームを生成し、それと平文ブロックとの XOR 演算によって暗号ブロックを生成する方式です。ブロック長が128ビット（16バイト）の場合、たとえば前半8バイトを nonce、後半8バイトをカウンタとします（nonce とカウンタの分け方は方式によって異なり、後述の GCM では IV 96ビット＋カウンタ32ビットが標準です）。各ブロックが独立しているため、暗号化・復号ともに並列で高速に処理できます。

```
 [nonce | ctr=1]  [nonce | ctr=2]  [nonce | ctr=3]   ← 互いに独立なので同時に計算できる
       ↓                ↓                ↓
   暗号化(K)        暗号化(K)        暗号化(K)
       ↓                ↓                ↓
 平文1→XOR        平文2→XOR        平文3→XOR
       ↓                ↓                ↓
    暗号文1          暗号文2          暗号文3
```

> **用語解説：XOR（排他的論理和）**
> 二つのビットが異なれば1、同じであれば0を出力する演算。同じ値で2回 XOR 演算すると元の値に戻る（A ⊕ B ⊕ B = A）。この性質を利用して、多くの暗号モードやストリーム暗号で暗号化と復号の処理に用いられている。

**暗号モードの比較**

試験では「並列処理ができるのはどれか」「パディングが要るのはどれか」「ビット誤りがどこまで広がるか」が問われます。表で対比しておきましょう。

| モード | 暗号化の並列処理 | 復号の並列処理 | パディング | 暗号文の1ビット誤りの影響 | 安全性 |
|---|---|---|---|---|---|
| ECB | 可 | 可 | 必要 | そのブロックのみ | 低い（使用すべきでない） |
| CBC | 不可 | 可 | 必要 | そのブロック全体と、次のブロックの対応するビット | 高い |
| CFB | 不可 | 可 | 不要 | 対応するビットと、次のブロック全体 | 高い |
| OFB | 不可（鍵ストリームは事前計算可） | 不可（同左） | 不要 | 対応するビットのみ | 高い |
| CTR | 可 | 可 | 不要 | 対応するビットのみ | 高い |

なお、CBC や CTR は「秘匿」だけを提供し、改ざんの検知はできません。そのため現在の TLS（第7章 7.4）では、暗号化と改ざん検知を同時に行う **認証付き暗号**（GCM、CCM、ChaCha20-Poly1305）が使われます。これらは5節の CRYPTREC 暗号リストにも「認証付き秘匿モード」「認証暗号」として掲載されています。

## 3. 公開鍵暗号方式

### 3.1 仕組み ― 鍵を「公開する鍵」と「秘密にする鍵」に分ける

2節で見た鍵配送問題を解くために考え出されたのが、公開鍵暗号方式です。公開鍵暗号方式は、暗号化と復号に別々の鍵を用いる方式であり、**非対称鍵暗号方式** とも呼ばれます。利用者は、同時に生成された一対の鍵のうち、一方を **公開鍵** として公開し、他方を **秘密鍵** として厳重に管理します。

**図：公開鍵暗号方式のイメージ**

```
 送信者                                                     受信者
 平文 ──[暗号化(受信者の公開鍵)]──> 暗号文 ──(送信)──> [復号(受信者の秘密鍵)]──> 平文
          ↑                                                   │
          └────────── 受信者が公開鍵を公開 ───────────────────┘
```

公開鍵で暗号化したデータは、対になる秘密鍵でしか復号できません。逆に、秘密鍵で処理したデータは対になる公開鍵で検証できます。この性質はデジタル署名に利用されています（3.6）。

ここで、「誰の鍵を、誰が、何に使うか」を取り違えないことが最重要です。科目A-2 の選択肢は、この組合せを入れ替えて誤りを作るのが定番です。

```
  受信者Bが鍵ペアを生成する： Bの公開鍵（誰に配ってもよい） / Bの秘密鍵（B だけが持つ）

  【秘匿（暗号化）に使う場合】
   送信者A ── Bの公開鍵 で暗号化 ──> 暗号文 ──> 受信者B ── Bの秘密鍵 で復号
             （誰でも暗号化できる）                       （B だけが復号できる）

  【署名に使う場合】（Aが鍵ペアを持つ）
   署名者A ── Aの秘密鍵 で署名 ──> 文書＋署名 ──> 検証者（誰でも） ── Aの公開鍵 で検証
             （A だけが署名できる）                      （誰でも検証できる）
```

| 目的 | 処理する側が使う鍵 | 受け取る側が使う鍵 | 何が保証されるか |
|---|---|---|---|
| 秘匿（暗号化） | **受信者の公開鍵** で暗号化 | **受信者の秘密鍵** で復号 | 受信者以外は読めない（機密性） |
| 署名 | **署名者の秘密鍵** で署名 | **署名者の公開鍵** で検証 | 署名者本人が作成し、改ざんされていない（真正性・完全性・否認防止） |

公開鍵暗号方式にも残る課題があります。送信者Aが手にした「Bの公開鍵」が、本当にBのものかどうかを確かめる手段がなければ、攻撃者が自分の公開鍵を「Bの公開鍵です」と偽って配ることで、暗号文を読めてしまいます。この「公開鍵の持ち主を保証する」仕組みが、第7章 7.7 で学ぶ PKI（認証局とデジタル証明書）です。

### 3.2 共通鍵暗号方式と公開鍵暗号方式の比較

ここまでの二つの方式を対比します。

**表：共通鍵暗号方式と公開鍵暗号方式の比較**

| 暗号方式 | 特徴 | 仕組み |
|---|---|---|
| 共通鍵暗号方式（秘密鍵暗号方式） | 暗号化と復号に同じ鍵を用いる方式（DES、AES、IDEA など） | ・送信者は、暗号鍵（共通鍵）でデータを暗号化して送る<br>・送信者は、何らかの安全な手段で相手に復号鍵（共通鍵）を送る<br>・暗号化データを受け取った相手は、受け取った共通鍵で復号する |
| 公開鍵暗号方式 | 暗号化と復号に異なる鍵（公開鍵と秘密鍵のペア）を用いる方式（RSA、楕円曲線暗号など） | ・受信者は、公開鍵と秘密鍵のペアを生成し、公開鍵を公開する<br>・送信者は、受信者の公開鍵でデータを暗号化して送る<br>・暗号化データを受け取った受信者は、自身の秘密鍵で復号する |

**表：共通鍵暗号方式と公開鍵暗号方式のメリット・デメリット**

| 暗号方式 | メリット | デメリット |
|---|---|---|
| 共通鍵暗号方式（秘密鍵暗号方式） | ・ロジックがシンプルであるため、システムへの組込みが容易<br>・暗号化・復号の処理が速い | ・送信相手に安全に鍵を送るのが困難（**鍵配送問題**）<br>・相手ごとに異なる鍵を送受信し、厳重に管理する必要がある。相手先が多くなると鍵の管理が困難 |
| 公開鍵暗号方式 | ・自分の秘密鍵（1個）だけを厳重に管理すればよく、管理が容易<br>・相手に鍵を送る必要がない（自分の公開鍵を公開しておくだけ） | ・ロジックが複雑であるため、システムへの組込みが困難<br>・処理が遅く、大量データの暗号化には向かない |

両者の長所と短所はちょうど裏返しになっています。この裏返しの関係が、4節のハイブリッド方式につながります。

### 3.3 主な公開鍵暗号方式

**表：主な公開鍵暗号方式**

| 名称 | 概要 |
|---|---|
| RSA（Rivest Shamir Adleman） | Ronald Rivest、Adi Shamir、Leonard Adleman によって1977年に開発された暗号方式。3人の名前の頭文字をとって RSA と名付けられた。公開鍵暗号方式の標準として広く普及している。桁数の大きな整数の **素因数分解** が困難であることを安全性の根拠にしている。以前は1024ビットの鍵が標準的に使用されていたが、現在は危殆化が懸念されており、2048ビット以上の鍵への移行が進められている（現在は1024ビット鍵は使用すべきでなく、2048ビットも NIST の指針では2030年までの利用とされ、それ以降は3072ビット以上が求められる。5.3 参照） |
| 楕円曲線暗号（Elliptic Curve Cryptography） | 楕円曲線上の離散対数問題（ECDLP）の難しさを安全性の根拠にする暗号方式。RSA よりも短い鍵長で同程度の暗号強度を実現でき、その分処理が高速という長所がある。ただし、条件（曲線パラメータ）の選び方によっては逆に脆弱になってしまうといわれている。160ビットの鍵長で、鍵長1024ビットの RSA と同程度の安全性があるとされている（同様に、256ビットの楕円曲線暗号は3072ビットの RSA と同程度とされる） |

> ※ECDLP：Elliptic Curve Discrete Logarithm Problem

楕円曲線暗号は、鍵が短く計算が軽いため、IC カード（第6章 6.6）、スマートフォン、IoT 機器のように計算資源が限られた機器や、TLS の鍵交換（ECDHE、第7章 7.4）で広く使われています。

> **Column：RSAの安全性**
>
> 公開鍵暗号方式の標準となっている RSA では、桁数の大きな整数（合成数）を素因数分解するのが困難であるということを安全性の根拠にしている。次の例で説明しよう。
>
> 1. 二つの素数 a、b を挙げる
>    a = 523、b = 613
> 2. その二つの素数を掛け算する
>    a × b = 523 × 613 = 320,599 → 単なる掛け算なので容易
> 3. 2.の結果から、元の素数を求める
>    320,599 = □ × △ → □と△を求めるのは非常に困難
>
> 数字の桁数が大きくなればなるほど、素因数分解はより困難になる。つまり、数字の桁数の大きさがそのまま「安全強度」につながる。実際の RSA では、元の素数（上記の例でいう素因数）として、数百桁にも及ぶ数字を使用する。
>
> 素因数分解については、数学界において様々な方法が研究されているが、いまだ効率的に解く方法は発見されていない。この現状が RSA の安全性の背景となっている。

この「掛け算は簡単だが、元に戻すのは難しい」という一方向の性質が、公開鍵暗号の本質です。RSA では、公開鍵に含まれる大きな合成数（上の例の 320,599 に当たるもの）は誰でも見られますが、秘密鍵を作るには素因数（523 と 613 に当たるもの）が必要です。攻撃者は、公開鍵から秘密鍵を逆算しようとすると素因数分解を解かなければならず、それが現実的な時間ではできないので安全、という構造です。

### 3.4 共通鍵暗号方式／公開鍵暗号方式における鍵の数

鍵の管理の手間は、利用者の人数が増えたときに決定的な差になります。

共通鍵暗号方式では、n 人が互いに相手以外に知られずに暗号を使ってやり取りする場合、2人の組合せごとに異なる鍵が必要となります。必要な鍵の数は次の式で求められます。

$$
{}_n\mathrm{C}_2 = \frac{n(n-1)}{2}
$$

この式の意味は、「n 人の中から通信する2人を選ぶ組合せの数」です。1人あたり自分以外の $n-1$ 人と鍵を共有するので $n(n-1)$ になりますが、A–B 間の鍵と B–A 間の鍵は同じ1本なので、2で割ります。人数が増えると、鍵の数はおおよそ人数の2乗に比例して増えます。

一方、公開鍵暗号方式では、各人がそれぞれ秘密鍵と公開鍵の二つの鍵をもてばよいため、必要な鍵の数は **2n個** となります。

$$
2n \quad (\text{1人あたり公開鍵1個＋秘密鍵1個})
$$

こちらは人数に比例して増えるだけです。1,000人の場合で比較すると、次のようになります。

| 暗号方式 | 計算式 | 必要な鍵の数 |
|---|---|---|
| 共通鍵暗号方式 | 1,000 × 999 ÷ 2 | 499,500個 |
| 公開鍵暗号方式 | 2 × 1,000 | 2,000個 |

利用者が増えるほど、公開鍵暗号方式の方が鍵の管理面で圧倒的に有利となることが分かります。なお、試験では「鍵の総数」ではなく「秘密に管理しなければならない鍵の数」を問われることがあります。その場合、公開鍵暗号方式は秘密鍵の n 個、共通鍵暗号方式は n(n-1)/2 個のすべてが秘密です。問題文の問い方を確認してください。

### 3.5 鍵ファイルの見た目 ― openssl で確かめる

公開鍵と秘密鍵は、実務では PEM 形式（Base64 で文字列にしたテキスト）のファイルとして扱われます。サーバの管理者が `openssl` で RSA 2048ビットの鍵ペアを作ると、次のように見えます（鍵の中身は途中を省略しています）。

```
$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out server.key
$ openssl pkey -in server.key -pubout -out server.pub

$ head -2 server.key            ← 秘密鍵：絶対に外部に出さない
-----BEGIN PRIVATE KEY-----
MIIEvQIBADANBgkqhkiG9w0BAQEFAASCBKcwggSjAgEAAoIBAQC5V34f1DLQkmFG...

$ head -2 server.pub            ← 公開鍵：配布してよい
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEAuVd+H9Qy0JJhRpnAkr5+...

$ openssl pkey -pubin -in server.pub -text -noout
Public-Key: (2048 bit)          ← 鍵長
Modulus:                        ← 大きな合成数 n（3.3 の 320,599 に当たるもの）
    00:b9:57:7e:1f:d4:32:d0:92:61:46:99:c0:92:be:...
Exponent: 65537 (0x10001)       ← 公開指数 e

$ ls -l server.key
-rw------- 1 root root 1704 ... server.key   ← 所有者以外は読めない権限にする
```

管理者は、秘密鍵ファイルが漏えいすると「その鍵で守っていたものすべて」が危険にさらされるため、秘密鍵をパーミッション 600 などで保護し、可能であればパスフレーズで暗号化するか、HSM（ハードウェアセキュリティモジュール）や IC カードの中に格納して取り出せないようにすべきです。鍵を作るのも、保管するのも、廃棄するのも人間なので、鍵の **生成・配布・保管・更新・廃棄** の各段階を手順として定めておくことが鍵管理の基本になります。

### 3.6 デジタル署名の作成と検証の流れ

3.1 で見た「秘密鍵で処理したデータは対になる公開鍵で検証できる」という性質を使うのが **デジタル署名** です。署名者は、文書のハッシュ値（6.1 で学ぶ固定長の要約値）を自分の秘密鍵で処理して署名を作り、検証者は署名者の公開鍵で署名を検証します。文書そのものではなくハッシュ値に署名するのは、公開鍵暗号の処理が遅い（3.2）ため、短いハッシュ値だけを処理して高速化するためです。

```
 【署名者A】                                         【検証者B（誰でもよい）】
  文書 ──→ ハッシュ関数 ──→ ハッシュ値h                文書 ──→ ハッシュ関数 ──→ h'
              │                                                       │
              ↓ Aの秘密鍵で署名                                        │ 比較
            署名 s ──────────(文書と署名 s を送る)──────→ 署名 s ─→ Aの公開鍵で検証 ─→ h
                                                                      │
                                                    h = h' なら「A本人が作成し、改ざんされていない」
                                                    h ≠ h' なら「改ざん、又は A 以外が作成」
```

`openssl` で署名と検証を行うと、次のように見えます。文書を1文字でも書き換えると、検証は失敗します。

```
$ printf '請求書 金額 100,000円' > invoice.txt
$ openssl dgst -sha256 -sign server.key -out invoice.sig invoice.txt     ← 署名者が秘密鍵で署名
$ openssl dgst -sha256 -verify server.pub -signature invoice.sig invoice.txt
Verified OK                                                              ← 公開鍵で検証成功

$ printf '請求書 金額 900,000円' > invoice.txt                            ← 第三者が金額を改ざん
$ openssl dgst -sha256 -verify server.pub -signature invoice.sig invoice.txt
Verification failure                                                     ← 改ざんを検知
```

デジタル署名で得られる性質は、**完全性**（改ざんされていない）、**真正性**（署名者本人が作成した）、**否認防止**（署名者は後から「作っていない」と言い逃れできない）の三つです。否認防止が成り立つのは、署名を作れる秘密鍵を署名者だけが持っているからです。6.4 の MAC との違いは、ここにあります。ただし、検証者が使う「Aの公開鍵」が本当に A のものであることは、署名だけでは保証できません。それを保証するのが第7章 7.7 の PKI です。なお、「秘密鍵で暗号化する」という説明は RSA を念頭に置いた表現で、DSA・ECDSA・EdDSA などの署名方式は暗号化とは異なる計算で署名を作ります。いずれの方式でも「秘密鍵で署名し、公開鍵で検証する」という役割分担は同じです。

## 4. ハイブリッド方式

### 4.1 仕組み ― 速い共通鍵と、配りやすい公開鍵を組み合わせる

共通鍵暗号方式は処理が高速ですが、鍵の配送と管理に難があります。公開鍵暗号方式は鍵の管理が容易ですが、処理が遅いです。**ハイブリッド方式** は、両者を組み合わせて利用する方式です。

送信者は、データ本体を、処理の速い共通鍵暗号方式で暗号化します。送信者は、暗号化に用いた共通鍵暗号方式の鍵（**セッション鍵**）を安全に相手に渡すために、鍵自体を公開鍵暗号方式（通信相手の公開鍵）を用いて暗号化します。受信者は、自身の秘密鍵で共通鍵を復号し、取り出した共通鍵でデータ本体を復号します。

**図：ハイブリッド方式のイメージ**

```
 送信者                                                受信者
 ① データ ──[共通鍵で暗号化]──> 暗号化データ ──────> [共通鍵で復号] ──> データ
                                                            ↑
 ② 共通鍵 ──[受信者の公開鍵で暗号化]──> 暗号化された共通鍵 ──> [受信者の秘密鍵で復号] ──> 共通鍵
```

| 鍵 | 誰が作るか | 誰が持つか | 何に使うか |
|---|---|---|---|
| セッション鍵（共通鍵） | 送信者が通信・メールごとに乱数で生成 | 送信者と受信者（受信者は②を復号して得る） | データ本体の暗号化・復号 |
| 受信者の公開鍵 | 受信者が生成し公開 | 誰でも | セッション鍵の暗号化 |
| 受信者の秘密鍵 | 受信者が生成 | 受信者だけ | 暗号化されたセッション鍵の復号 |

### 4.2 ハイブリッド方式のメリット

ハイブリッド方式では、共通鍵暗号方式と公開鍵暗号方式それぞれの欠点を、互いの長所によって補い合います。この方式には、次のようなメリットがあります。

- データの暗号化に共通鍵暗号方式を用いるため、サイズの大きいデータを扱う場合でも高速な処理が可能
- 公開鍵暗号方式で暗号化するのは数十バイト程度の共通鍵のみであるため、処理速度の問題は生じない
- 暗号化に用いる共通鍵は公開鍵暗号方式で保護されるため、結果として鍵管理を公開鍵暗号方式の枠組みで行うことが可能

ハイブリッド方式は、SSL/TLS や S/MIME、PGP など、実際の多くの暗号化プロトコルで採用されています。第3章 3.4 で見た S/MIME の暗号化メール（`smime-type=enveloped-data`）は、まさに「暗号化された本文」と「受信者の公開鍵で暗号化されたセッション鍵」を封筒（envelope）に入れた構造です。なお、TLS 1.3（第7章 7.4）では、セッション鍵の素材を公開鍵で暗号化して送る方式（RSA 鍵交換）は廃止され、7節の Diffie-Hellman 鍵交換でセッション鍵を共有する方式に変わっています。その理由が7.4 の前方秘匿性です。

> **試験に出た**
> 情報セキュリティスペシャリスト試験の午後I問2で、ハイブリッド方式の仕組みと安全性に関する問題が出題された。

## 5. どの暗号を使ってよいか ― CRYPTREC 暗号リストと危殆化

### 5.1 CRYPTREC とは

暗号は、時間とともに弱くなります。計算機が速くなり、新しい解読手法が見つかるからです。システムを設計する人は「どのアルゴリズムと鍵長を、今選んでよいのか」を判断しなければなりませんが、それを個人で判断するのは困難です。そこで参照されるのが CRYPTREC の評価です。

**CRYPTREC**（Cryptography Research and Evaluation Committees）とは、デジタル庁、総務省、経済産業省が運営するプロジェクトです。CRYPTREC は、電子政府推奨暗号の安全性を評価・監視し、暗号技術の適切な実装法・運用法を調査・検討しています。

CRYPTREC は、「電子政府における調達のために参照すべき暗号のリスト（**CRYPTREC暗号リスト**）」を公表しています。CRYPTREC 暗号リストは、次の三つのリストで構成されます。

- **電子政府推奨暗号リスト**：CRYPTREC によって安全性及び実装性能が確認された暗号技術のうち、市場における利用実績が十分であるか、今後の普及が見込まれると判断され、利用を推奨するもののリスト
- **推奨候補暗号リスト**：安全性及び実装性能は確認されているが、今後、電子政府推奨暗号リストに掲載される可能性のある暗号技術のリスト
- **運用監視暗号リスト**：解読のリスクが高まるなどして推奨すべき状態ではなくなったが、互換性維持のために継続利用を容認する暗号技術のリスト

| リスト | 新しいシステムで採用してよいか | 位置づけ |
|---|---|---|
| 電子政府推奨暗号リスト | 採用を推奨 | 安全性・実装性能・利用実績がそろっている |
| 推奨候補暗号リスト | 採用は可能（将来推奨に上がる可能性） | 安全性・実装性能は確認済み、実績はこれから |
| 運用監視暗号リスト | 新規採用は避け、既存システムの互換性維持に限る | 推奨すべき状態ではなくなった。移行を計画する |

> **試験に出た**
> 情報セキュリティスペシャリスト試験では、CRYPTREC暗号リストに関する問題が出題された。また、情報処理安全確保支援士試験の午後問2でも、関連する問題が出題された。

### 5.3 鍵長・アルゴリズムの推奨状況

設計者がアルゴリズムと鍵長を選ぶときは、「セキュリティ強度」（攻撃者が鍵を総当たりするのに必要な計算量を、共通鍵暗号の鍵長に換算したビット数）をそろえて考えます。NIST SP 800-57 は、セキュリティ強度ごとに同等とされる鍵長を次のように示しています。CRYPTREC も同様の考え方で、鍵長の選択基準を公表しています。

| セキュリティ強度 | 共通鍵暗号 | RSA・DH の鍵長 | 楕円曲線暗号の鍵長 | 署名用ハッシュ関数 | 利用の目安 |
|---|---|---|---|---|---|
| 80ビット | （2-key Triple DES） | 1024ビット | 160ビット | SHA-1 | 使用不可（移行済みであるべき） |
| 112ビット | （3-key Triple DES） | 2048ビット | 224ビット | SHA-224 | 2030年まで（NIST の指針）。3DES は NIST では2023年末で暗号化への利用を終了 |
| 128ビット | AES-128 | 3072ビット | 256ビット | SHA-256 | 推奨 |
| 192ビット | AES-192 | 7680ビット | 384ビット | SHA-384 | 推奨 |
| 256ビット | AES-256 | 15360ビット | 512ビット | SHA-512 | 推奨 |

この表から、RSA は強度を上げるほど鍵が急激に長くなり、楕円曲線暗号は鍵長が強度のおよそ2倍で済むことが読み取れます。3.3 で「楕円曲線暗号は短い鍵で同程度の強度」と述べたのは、この関係のことです。

| 用途 | 新規に採用してよい | 既存システムの互換性維持に限る | 使ってはいけない（移行すべき） |
|---|---|---|---|
| 共通鍵暗号 | AES、Camellia、KCipher-2 | 3DES | DES、RC4 |

| 公開鍵暗号（守秘・署名） | RSA 2048ビット以上（RSA-OAEP、RSA-PSS）、ECDSA、EdDSA | ― | RSA 1024ビット |
| 鍵共有 | ECDHE、DHE（7節） | RSA 鍵交換（TLS 1.3 では廃止） | ― |
| ハッシュ関数 | SHA-256 以上、SHA-3 | SHA-1（署名以外の用途） | MD4、MD5、SHA-1（デジタル署名） |

システムの管理者は、暗号が危殆化したときに速やかに別のアルゴリズムへ切り替えられるよう、使用中の暗号アルゴリズムと鍵長を台帳で管理し、設定変更だけで切り替えられる設計（**暗号の移行性**、クリプトアジリティ）にしておくべきです。

> **用語解説：危殆化**
> 暗号技術において、計算機の性能向上や新たな解読手法の発見などにより、暗号アルゴリズムや鍵の安全性が低下し、解読や偽造の危険性が高まることをいう。

### 5.4 量子暗号及び耐量子暗号の概要

危殆化の最大の要因として今注目されているのが、量子コンピュータです。ここでは名前の似た二つの技術を区別します。

**量子暗号**（Quantum Cryptography）とは、量子力学に基づく共通鍵暗号方式の一種です。量子暗号では、送信者は暗号化／復号に用いる共通鍵を、光子（光の粒子）の偏光状態などの量子状態に乗せて送信します（**量子鍵配送**：Quantum Key Distribution、QKD）。量子力学の性質上、量子状態は観測すると変化してしまいます。そのため、第三者が通信経路上で盗聴（観測）を行うと、該当する光子が正常に届かなくなり、受信者側で盗聴を検知できます。この仕組みにより、第三者に解読されない秘匿通信を実現できることが大きな特長となっています。

量子暗号と似た用語に、**耐量子暗号**（Post-Quantum Cryptography：PQC）、もしくは **耐量子計算機暗号** があります。こちらは、量子コンピュータを用いた攻撃に対しても安全性を保つことができる暗号方式のことです。量子コンピュータが実用化されると、ショアのアルゴリズムなどによって素因数分解や離散対数問題が効率的に解けるようになります。その結果、RSA や楕円曲線暗号など現在広く普及している公開鍵暗号技術が危殆化し、暗号化されたデータが解読されてしまう可能性があります。

これに対応するため、PQC に関する調査や研究が行われています。米国では NIST が耐量子暗号の標準化を進めてきました。以前は「標準化を進めている段階」とされていましたが、2024年8月に最初の標準として FIPS 203（ML-KEM：鍵カプセル化）、FIPS 204（ML-DSA：署名）、FIPS 205（SLH-DSA：署名）が公表されています。国内では、CRYPTREC のサイトで、量子コンピュータによる暗号技術の安全性への影響調査結果や、PQC の研究動向調査報告書等が公開されています。

| 観点 | 量子暗号（QKD） | 耐量子暗号（PQC） |
|---|---|---|
| 何を使うか | 量子力学（光子の量子状態） | 数学（量子コンピュータでも解きにくい問題） |
| 何をするか | 共通鍵を盗聴を検知できる形で配送する | 公開鍵暗号・署名を量子コンピュータに耐える方式に置き換える |
| 必要な設備 | 専用の量子通信路（光ファイバーなど） | 既存の計算機・ネットワークでよい（ソフトウェアの更新） |
| 対応するもの | 鍵配送問題 | ショアのアルゴリズムによる RSA・楕円曲線暗号の危殆化 |

量子コンピュータが実用化される前でも、攻撃者が今のうちに暗号化通信を記録しておき、将来解読するという脅威が指摘されています。長期間秘密にすべきデータを扱う組織の管理者は、この脅威を踏まえて PQC への移行計画を早めに検討すべきです。

## 6. 改ざんに気づく道具 ― ハッシュ関数、MAC、フィンガプリント

暗号化は「読まれない」ための技術でした。しかし攻撃者は、読めなくても通信を書き換えることはできます。受信者が「届いたデータは送信者が送ったものと同じか」を確かめる道具が、この節で学ぶハッシュ関数・MAC・フィンガプリントです。

### 6.1 ハッシュ関数と三つの性質

**ハッシュ関数** とは、任意の長さの入力データ（x）を基に、固定長のビット列（**ハッシュ値**：y = H(x)）を出力する関数 H(x) です。入力データを「**メッセージ**」、求められるハッシュ値を「**メッセージダイジェスト**（MD）」ともいいます。ハッシュ関数には、次の三つの性質が求められます。

- **衝突発見困難性**
  同一のハッシュ値を生成する（H(x) = H(x')）異なる二つのデータ（x、x'）を求めることが、計算量的に困難であること
- **第2原像計算困難性**
  データ（x）と、それに対するハッシュ値（y = H(x)）が与えられたとき、同じハッシュ値を生成する（y = H(x')）別のデータ（x' ≠ x）を求めることが、計算量的に困難であること
- **原像計算困難性（一方向性）**
  ハッシュ値（y）が与えられたとき、y = H(x) となるデータ（x）を求めることが、計算量的に困難であること

攻撃者にとっては、衝突発見 → 第2原像計算 → 原像計算の順に、攻撃がより困難となります。言い換えると、衝突発見は攻撃者が「どんなペアでもよいから」同じハッシュ値の二つを探せばよいので最も易しく、原像計算は「この値になる入力」をゼロから探さなければならないので最も難しい、ということです。

| 性質 | 攻撃者に与えられるもの | 攻撃者が探すもの | 破られると何が起きるか（例） |
|---|---|---|---|
| 原像計算困難性（一方向性） | ハッシュ値 y だけ | y になる入力 x | 保存されたパスワードのハッシュ値から、パスワードが割り出される |
| 第2原像計算困難性 | 入力 x と y | 同じ y になる別の入力 x' | 正規の文書と同じハッシュ値の偽文書を作られ、署名を流用される |
| 衝突発見困難性 | 何もない（自由に選べる） | 同じハッシュ値になる任意の x と x' | 攻撃者が無害な文書と悪意ある文書のペアを作り、無害な方に署名させて悪意ある方に流用する |

ハッシュ関数はこのような性質をもつことから、メッセージ認証（データの改ざん検出）やワンタイムパスワードの生成（第6章 6.4 の S/Key）、デジタル署名（3.6）、パスワードの保存（第2章 2.4）などに広く用いられています。例えば、インターネットを介してあるデータを送る場合に、送信者が送信前のハッシュ値を保存しておき、受信者が送信後のハッシュ値と比較することにより、途中で改ざんやエラーなどが発生したことを検出できます。

ハッシュ関数は暗号という名称を冠してはいませんが、暗号技術の一種であり、非常に重要な役割を果たしています。

> **試験に出た**
> 情報セキュリティスペシャリスト試験の午後I問1で、ハッシュ関数の危殆化への対応に関する問題が出題された。

### 6.2 ハッシュ値の見た目

ハッシュ値は、入力の長さに関係なく常に同じ長さの16進数の文字列として表示されます。`openssl dgst` で確かめると、次のような性質が目で見て分かります。

```
$ printf 'IPA2026' | openssl dgst -sha256
SHA2-256(stdin)= fd2b0bb0fcad6e39561f1b2f292480935b0bc1af4e81f951b8bb84df3e25f7ae
$ printf 'IPA2026' | openssl dgst -sha256
SHA2-256(stdin)= fd2b0bb0fcad6e39561f1b2f292480935b0bc1af4e81f951b8bb84df3e25f7ae   ← 同じ入力なら必ず同じ値
$ printf 'IPA2027' | openssl dgst -sha256
SHA2-256(stdin)= d0e6cce36524ecfa7e8f581262bb64e7a993c8dd461a2cf910955d61f09a5759   ← 1文字違うだけで全く違う値

$ printf 'IPA2026' | openssl dgst -md5
MD5(stdin)= b6c9739a28eb4b64af2c519dea8963fe                                         ← 128ビット（16進32桁）
$ printf 'IPA2026' | openssl dgst -sha1
SHA1(stdin)= 434393fd4528693c3d2138ce3dc23f07cdc4a1d2                                ← 160ビット（16進40桁）
$ printf 'IPA2026' | openssl dgst -sha3-256
SHA3-256(stdin)= 6b1a7b7ad625fa4f28ea3e80c84df20819def81bdeed4d93cafd6c17de3560af   ← 256ビット（16進64桁）
```

1文字違いの入力で出力が似ても似つかない値になる性質を、雪崩効果と呼びます。もし似た入力から似たハッシュ値が出るなら、攻撃者は少しずつ入力を変えて目的の値に近づけられてしまいます。ソフトウェアの配布元が公開する「SHA-256 チェックサム」は、この値を利用者に照合させるためのものです。

```
$ sha256sum installer-1.2.3.tar.gz
fd2b0bb0fcad6e39...（略）...3e25f7ae  installer-1.2.3.tar.gz   ← 配布ページに掲載の値と一致するか照合する
```

### 6.3 主なハッシュ関数

**表：主なハッシュ関数**

| 名称 | 出力長 | 概要 |
|---|---|---|
| MD4（Message Digest 4） | 128ビット | Ronald Rivest 氏が開発した一方向性ハッシュ関数。128ビットのハッシュ値（メッセージダイジェスト）を出力する。S/Key などで使用されていたが、アルゴリズムの脆弱性が発見されている |
| MD5（Message Digest 5） | 128ビット | Ronald Rivest 氏が開発した一方向性ハッシュ関数。MD4 と同様に128ビットのハッシュ値を出力する。MD4 のアルゴリズムを複雑化して安全性を向上させたものだが、現在は衝突を発見する手法が確立されており、安全性を必要とする用途での利用は推奨されない |
| SHA-1（Secure Hash Algorithm 1） | 160ビット | NIST（米国国立標準技術研究所）が MD4 を基に改良・標準化した一方向性ハッシュ関数。160ビットのハッシュ値を出力する。米国政府標準のハッシュ関数として採用されたこともあり広く使用されてきたが、近年は危殆化が懸念されており、SHA-2、SHA-3 への移行が進められている |
| SHA-2（Secure Hash Algorithm 2） | 224／256／384／512ビット | SHA-224、SHA-256、SHA-384、SHA-512 などの総称であり、「-」以降の数字はそれぞれ出力されるハッシュ値のビット数を表す。SHA-256、SHA-384、SHA-512 は CRYPTREC 暗号リスト推奨のハッシュ関数である |
| SHA-3（Secure Hash Algorithm 3） | 224／256／384／512ビット、SHAKE は任意長 | NIST による次世代暗号コンペティションの結果、2012年10月に「Keccak」が選出され、2015年に FIPS 202 として標準化された。SHA3-224/256/384/512 と、任意長の出力が可能な SHAKE128/SHAKE256 から成る。SHA-2 とは異なるスポンジ構造と呼ばれる内部構造を採用している |

SHA-1 には、ある条件下でハッシュ値の衝突を意図的に起こすことができるという脆弱性が発見されています（2017年には、実際に同じ SHA-1 ハッシュ値をもつ異なる二つの PDF ファイルが公表されました）。そのため、次世代ハッシュ関数（SHA-3）が決定されるまでの措置として、SHA-2 に移行することが推奨されていました。その後、NIST 主催の次世代暗号コンペティションの結果、2012年10月に「Keccak」が SHA-3 に選出されました。なお、以前は「SHA-2 は SHA-3 までのつなぎ」と説明されることがありましたが、現在も SHA-2 に有効な攻撃は見つかっておらず、SHA-2 と SHA-3 はどちらも CRYPTREC の推奨リストに並んで掲載されています（5.2）。SHA-3 は、SHA-2 とは異なる構造をもつ「予備」として併存していると理解してください。

### 6.4 MAC（メッセージ認証コード）

**MAC**（Message Authentication Code）とは、メッセージと、送信者と受信者が共有する秘密鍵とを基に生成される固定長のデータです。送信者はメッセージに MAC を付けて送り、受信者は、受信したメッセージと共有する秘密鍵から同様に MAC を計算し、受信した MAC と比較します。これにより、受信者は、メッセージが改ざんされていないこと（完全性）と、正当な送信者から送られたこと（真正性）を確認できます。

```
 送信者A（鍵Kを持つ）                                   受信者B（鍵Kを持つ）
  メッセージM ─┬───────────(M と MAC を送る)──────→ M ─→ MAC計算(K) ─→ MAC'
               └→ MAC計算(K) ─→ MAC ─────────────→ MAC ──────────────┐
                                                                 比較 ←┘
                                         一致すれば「改ざんなし、鍵Kを持つ相手から届いた」
```

MAC には、ブロック暗号を用いた **CMAC**（Cipher-based MAC）や、ハッシュ関数を用いた **HMAC** などがあります。CMAC と HMAC は、CRYPTREC 暗号リスト推奨のメッセージ認証コードです。なお、MAC は **メッセージ認証符号** とも呼ばれます。

> **用語解説：MACとデジタル署名の違い**
> MAC は送信者と受信者が同じ秘密鍵を共有するため、受信者も MAC を生成できる。したがって、第三者に対して「送信者本人が作成したこと」を証明すること（否認防止）はできない。否認防止が必要な場合は、公開鍵暗号方式を用いたデジタル署名を利用する。

| 観点 | ハッシュ値のみ | MAC（HMAC、CMAC） | デジタル署名 |
|---|---|---|---|
| 使う鍵 | なし | 送信者と受信者が共有する共通鍵 | 署名者の秘密鍵（作成）と公開鍵（検証） |
| 作成できる人 | 誰でも | 共通鍵を持つ送信者と受信者 | 秘密鍵を持つ署名者だけ |
| 検証できる人 | 誰でも | 共通鍵を持つ人だけ | 公開鍵を入手できる誰でも |
| 完全性 | 偶発的な誤りは検知できるが、攻撃者がハッシュ値も再計算すると検知できない | ○ | ○ |
| 真正性 | × | ○（当事者の間で） | ○（第三者に対しても） |
| 否認防止 | × | ×（受信者も作れるため） | ○ |
| 処理速度 | 速い | 速い | 遅い（公開鍵暗号を使うため） |

### 6.5 HMAC

ハッシュ関数は通信データなどの改ざん検知に有効な技術です。しかし、そのアルゴリズムは公開されているため、悪意のある者がデータを改ざんした後にハッシュ値も再計算してセットすれば、受信者は改ざんを検知できなくなるという問題があります。

このような問題に対処するため、第7章 7.3 で解説する IPsec などでは、**HMAC**（keyed-Hashing for Message Authentication Code：鍵付きハッシュ関数）が用いられています。HMAC は、ハッシュ値の計算時に、通信を行う両者が共有している秘密鍵の値を加えます。これにより、同じデータに同じハッシュ関数を用いて計算しても、その通信固有のハッシュ値が求められるようになります。たとえ悪意のある者が通信データを改ざんしても、秘密鍵を知らなければ正しいハッシュ値を求めることはできないため、受信者は改ざんを検知できます。

同じ入力に同じ SHA-256 を使っても、鍵が違えば HMAC の値はまったく違います。

```
$ printf 'IPA2026' | openssl dgst -sha256
SHA2-256(stdin)= fd2b0bb0fcad6e39561f1b2f292480935b0bc1af4e81f951b8bb84df3e25f7ae   ← 鍵なし：誰でも再計算できる
$ printf 'IPA2026' | openssl dgst -sha256 -hmac 'secret-key-A'
HMAC-SHA2-256(stdin)= 383cd8f8c14b9fe8aa24e355b2d7186781c3e6feefd8187638bb63af891b74ca   ← 鍵Aを持つ者だけが計算できる
$ printf 'IPA2026' | openssl dgst -sha256 -hmac 'secret-key-B'
HMAC-SHA2-256(stdin)= 3dae397a8aa354f74f45bdc95dcd4c4c60015e46db8861a74d3d35995ff0dbb8   ← 鍵が違えば別の値
```

なお、MD5 を用いた MAC は HMAC-MD5（もしくは MD5 MAC）、SHA-256 を用いた MAC は HMAC-SHA-256（もしくは SHA-256 MAC）などと呼ばれます。

### 6.6 フィンガプリント（拇印、指紋）

**フィンガプリント** とは、デジタル証明書（第7章 7.7 で解説）や公開鍵、メールなどの電子データが改ざんされていないことを証明するために使用するデータです。フィンガプリントは、ハッシュ関数を用いて、対象となる電子データから生成します。公開鍵や証明書そのものは数百〜数千バイトあって人間が目で照合するのは困難ですが、フィンガプリントは短いので、電話口で読み上げたり紙で照合したりできます。

証明書のフィンガプリントは、たとえば次のように表示されます（値は例です）。第7章 7.5 で学ぶ SSH の初回接続時に表示される「ホスト鍵のフィンガプリント」も同じ考え方です。

```
$ openssl x509 -in www.example.com.crt -noout -fingerprint -sha256
sha256 Fingerprint=FD:2B:0B:B0:FC:AD:6E:39:56:1F:1B:2F:29:24:80:93:5B:0B:C1:AF:4E:81:F9:51:B8:BB:84:DF:3E:25:F7:AE
```

公的機関等のフィンガプリントは、通常その組織のホームページに掲載されています。しかし、インターネット上の情報は改ざんされている可能性もあります。攻撃者がホームページを改ざんし、偽の証明書と偽のフィンガプリントを同時に差し替えてしまえば、利用者は両者を照合しても偽物と気づけません。正当性や完全性を担保するためには、利用者は、インターネットを経由せずに、相手から直接入手するか、電話や郵送などの別の経路（**アウトオブバンド**）で確認することが望ましいです。

## 7. Diffie-Hellman 鍵交換

### 7.1 盗聴される通信路で鍵を共有したい

2節の鍵配送問題に対する、公開鍵暗号とは別の解き方が **Diffie-Hellman鍵交換** です。Diffie-Hellman 鍵交換とは、Whitfield Diffie 氏と Martin E. Hellman 氏が考案した鍵交換・共有のためのアルゴリズムです。Diffie-Hellman 鍵交換は、**離散対数問題** が困難であることを安全性の根拠としており、安全でない通信路を使って、暗号化に用いる秘密鍵を生成し、共有することを可能にします。ポイントは、「鍵そのものを送らずに、双方が同じ値を計算で得る」ことです。

> **離散対数問題**
> 素数 $n$、整数 $g$、および $p = g^x \bmod n$ が与えられたとき、指数 $x$ を求める問題。$g^x \bmod n$ を計算するのは容易だが、その逆を求めるのは $n$ が大きくなると計算量的に極めて困難になる。このように一方向にだけ計算しやすい性質を「**一方向性関数**」と呼ぶ。

### 7.2 鍵交換の手順（具体例）

具体例を次に示します。

1. Diffie-Hellman 鍵交換を行う A、B の両者は、あらかじめ $g$、$n$（例としてそれぞれ $g = 2$、$n = 41$ とする）という二つの数を共有していることを前提とします（ここで、$n$ は素数、$g$ は $n$ よりも小さい整数という条件が満たされている必要があります）。
2. 鍵交換に際し、A は乱数 $x$ を生成し、$g$ の $x$ 乗を $n$ で割った余り $p$（**DH公開値**）を B に送信します。乱数 $x$ が15だとすれば、$p = 2^{15} \bmod 41 = 9$ となります。これを B に送信します。
3. B も A と同様に乱数 $y$ を生成し、$g$ の $y$ 乗を $n$ で割った余り $q$（DH公開値）を A に送信します。乱数 $y$ が22だとすれば、$q = 2^{22} \bmod 41 = 4$ を A に送信します。
4. A は、B が送ってきた $q$ と、先ほど生成した乱数 $x$ によって、$q$ の $x$ 乗を $n$ で割った余り $a$ を求めます。つまり、$a = 4^{15} \bmod 41 = 40$ が求められます。
5. B も、A が送ってきた $p$ と、先ほど生成した乱数 $y$ によって、$p$ の $y$ 乗を $n$ で割った余り $b$ を求めます。つまり、$b = 9^{22} \bmod 41 = 40$ が求められます。
6. この結果、A と B は40という数を共有することに成功したので、この値を基に秘密の対称鍵（共通鍵）を生成し、通信を行います。

```
        A                      通信路（盗聴者Eにも見える）                 B
  共有: g=2, n=41  ←───────────── g=2, n=41 ─────────────→  共有: g=2, n=41
  秘密の乱数 x=15                                            秘密の乱数 y=22
  p = 2^15 mod 41 = 9  ───────────── p = 9 ──────────────→
                       ←──────────── q = 4 ───────────────  q = 2^22 mod 41 = 4
  a = 4^15 mod 41 = 40                                       b = 9^22 mod 41 = 40
        └──────────── 共有値 40（通信路には一度も流れていない）───────────┘
```

| 値 | A が知っている | B が知っている | 盗聴者 E が知っている |
|---|---|---|---|
| $g$、$n$（2、41） | ○ | ○ | ○ |
| DH 公開値 $p$、$q$（9、4） | ○ | ○ | ○ |
| A の乱数 $x$（15） | ○ | × | × |
| B の乱数 $y$（22） | × | ○ | × |
| 共有値（40） | ○ | ○ | ×（$x$ か $y$ を求めない限り得られない） |

このようにして、A と B は、それぞれが生成した乱数 $x$、$y$ と、事前に共有している $g$、$n$ を用いることで、乱数そのものを相手に送ることなく同じ値を得ることができます。これは、次の関係が成り立つためです。

$$
q^x \bmod n = g^{xy} \bmod n = p^y \bmod n
$$

この式は、「A が計算する $q^x$ も、B が計算する $p^y$ も、どちらも $g$ を $xy$ 乗したものと同じになる」という意味です。$q = g^y$ を $x$ 乗すると $g^{yx}$、$p = g^x$ を $y$ 乗すると $g^{xy}$ となり、掛け算の順序は入れ替えても同じだからです。上記の数字を代入すると、次のようになります。

$$
4^{15} \bmod 41 = 2^{15 \times 22} \bmod 41 = 9^{22} \bmod 41 \;(= 40)
$$

> **補足：計算の確認**
> $2^{10} = 1024 = 41 \times 24 + 40$ より、$2^{10} \equiv -1 \pmod{41}$、$2^{20} \equiv 1 \pmod{41}$ となる。
> したがって、$2^{15} = 2^{10} \times 2^5 \equiv -32 \equiv 9$、$2^{22} = 2^{20} \times 2^2 \equiv 4$、$2^{330} = (2^{20})^{16} \times 2^{10} \equiv 40 \pmod{41}$ となり、例の値と一致する。

### 7.3 安全性の根拠

Diffie-Hellman 鍵交換が、第7章 7.3 で後述する IPsec（IKE）などで実際に使われているケースでは、$g$、$n$ の値として幾つかの組合せ（**DHグループ**）があらかじめ用意されており、通信する機器はその中から選択することになります。したがって、乱数 $x$、$y$ のみが秘密となります（$g$ には2、$n$ には非常に桁数の大きな定数（素数）を用います）。

しかし、攻撃者が $g$、$n$ 及び $p$、$q$ を知っていたとしても、$x$、$y$ の値（離散対数）を求めるのは非常に困難です。つまり、上記の例であれば、攻撃者は $2^x \bmod 41 = 9$、$2^y \bmod 41 = 4$ を満たす離散対数 $x$、$y$ を求め、次の式における共有値を導かなければならないことになります。

$$
4^x \bmod 41 = 2^{xy} \bmod 41 = 9^y \bmod 41
$$

これは、素数である41の値が大きくなればなるほど困難（数百桁にもなれば事実上不可能）になります。Diffie-Hellman 鍵交換では、これを安全性の根拠としています。例のように $n = 41$ であれば、攻撃者は $x$ を1から順に試すだけで数十回以内に見つけられますが、実際の DH グループでは $n$ が2048ビット（約617桁）以上の素数なので、総当たりは現実的ではありません。

> **補足：中間者攻撃への注意**
> Diffie-Hellman 鍵交換そのものには通信相手を認証する仕組みがないため、通信経路上の攻撃者が A、B それぞれになりすまして公開値を差し替える中間者攻撃（**MITM攻撃**）を受けるおそれがある。実際のプロトコルでは、デジタル署名や事前共有鍵などを組み合わせて相手を認証する。

中間者攻撃の因果を整理すると、「攻撃者は、A と B の通信を読むことを目的に、A には自分の公開値を B のものと偽って渡し、B には自分の公開値を A のものと偽って渡す → その結果、A と攻撃者、攻撃者と B がそれぞれ別の共有値を持ち、攻撃者は中継しながらすべての通信を復号・改ざんできる」となります。これを防ぐため、TLS（第7章 7.4）ではサーバが DH 公開値にデジタル署名を付け、クライアントはサーバ証明書の公開鍵でその署名を検証します。IPsec の IKE（第7章 7.3）では、事前共有鍵やデジタル署名で相手を認証します。

### 7.4 前方秘匿性

Diffie-Hellman 鍵交換は、**前方秘匿性**（Forward Secrecy）を有しています。前方秘匿性とは、鍵交換に使った秘密鍵が漏えいしたとしても、それより前の暗号文は解読されないという性質であり、鍵交換プロトコルに求められる性質の一つです。これを実現するためには、データ暗号化の鍵から別の鍵を生成しない、暗号鍵の基となる情報は使い捨てとする、といったことが求められます。正確には、前方秘匿性が得られるのは、下のボックスのように通信ごとに使い捨ての乱数を使う DH（DHE／ECDHE）の場合です。同じ乱数を使い回す固定の DH では、その乱数が漏えいすると過去の通信も解読されます。

一方、RSA による鍵交換には前方秘匿性がないため、第7章 7.4 で学ぶ TLS 1.3 では、鍵交換の技術として使用できなくなりました。

> **前方秘匿性とDHE／ECDHE**
> 前方秘匿性を得るには、通信（セッション）ごとに使い捨ての乱数（一時鍵）を生成する **DHE**（Ephemeral Diffie-Hellman）や、楕円曲線を用いた **ECDHE** を使用する。RSA 鍵交換では、サーバの秘密鍵で暗号化された共通鍵の素材が通信路を流れるため、サーバの秘密鍵が漏えいすると、過去に記録された通信もすべて復号されてしまう。TLS 1.3 では鍵交換が DHE／ECDHE に限定されている（事前共有鍵〈PSK〉だけを使うモードを除く）。前方秘匿性は **PFS**（Perfect Forward Secrecy）とも呼ばれる。

| 観点 | RSA 鍵交換 | DHE／ECDHE |
|---|---|---|
| セッション鍵の素材の渡し方 | クライアントが生成し、サーバの公開鍵で暗号化して送る | 双方が使い捨ての乱数から DH 公開値を作って交換する |
| サーバの秘密鍵の役割 | セッション鍵の素材の復号 | DH 公開値への署名（認証）だけ |
| サーバの秘密鍵が後日漏えいしたら | 攻撃者は、過去に記録した通信からセッション鍵の素材を復号し、すべての過去の通信を解読できる | 使い捨ての乱数は通信終了時に消去されているため、過去の通信は解読されない |
| 前方秘匿性 | なし | あり |
| TLS 1.3 | 使用不可 | 使用する |

サーバの管理者が TLS の設定で ECDHE を含む暗号スイートを優先するのは、「サーバの秘密鍵が将来漏えいしても、それまでの利用者の通信内容を守るため」です。科目Bでは、この理由を1文で書けるようにしておきましょう。

### 7.5 Column：ゼロ知識証明

暗号分野における **ゼロ知識証明**（Zero Knowledge Proof：ZKP）とは、相手に秘密の情報そのものを一切明かすことなく、自分がその情報を知っていることを証明する手法です。

> **ゼロ知識証明の性質**
> ゼロ知識証明には、一般に次の三つの性質が求められる。
> - **完全性**：主張が真であれば、証明者は検証者を納得させることができる。
> - **健全性**：主張が偽であれば、不正な証明者が検証者を納得させることはできない（無視できる確率を除く）。
> - **ゼロ知識性**：検証者は、主張が真であるという事実以外の情報を一切得られない。
>
> パスワードそのものを送らない認証方式や、ブロックチェーンにおける取引内容の秘匿などに応用されている。

ここでいう「完全性」は、第1章 1.2 の情報セキュリティの完全性（Integrity）とは別の意味（証明として漏れがないこと）なので、混同しないようにしてください。

> - Q6：任意長の入力から固定長のハッシュ値を出力し、衝突発見困難性・第2原像計算困難性・原像計算困難性（一方向性）が求められる。改ざん検出、ワンタイムパスワード、デジタル署名、パスワードの保存などに用いる（本ノート6.1）。
> - Q7：デジタル証明書や公開鍵などの電子データが改ざんされていないことを確認するために、ハッシュ関数で生成するデータ。インターネット上の掲載情報は改ざんされている可能性があるため、相手から直接入手するか、電話や郵送などの別経路（アウトオブバンド）で確認する（本ノート6.6）。

> - Q9：鍵交換に使った秘密鍵が漏えいしても、それより前の暗号文は解読されないという性質。通信ごとに使い捨ての乱数を使う DHE／ECDHE で実現でき、RSA 鍵交換にはないため TLS 1.3 では RSA 鍵交換が廃止された（本ノート7.4）。

### 8.2 確認問題1：CTRモード

ブロック暗号の暗号利用モードの一つである CTR（Counter）モードに関する記述のうち、適切なものはどれか。

- ア　暗号化と復号の処理において、出力は、入力されたブロックと鍵ストリームとの排他的論理和である。
- イ　暗号化の処理において、平文のデータ長がブロック長の倍数でないときにパディングが必要である。
- ウ　ビット誤りがある暗号文を復号すると、ビット誤りのあるブロック全体と次のブロックの対応するビットが平文ではビット誤りになる。
- エ　複数ブロックの暗号化の処理は並列に実行できないが、複数ブロックの復号の処理は並列に実行できる。

*〔情報処理安全確保支援士試験・R5春〕*

> **解答・解説**
> CTR モードは、nonce と1ずつ増加するカウンタから成る値を暗号化して鍵ストリームを生成し、それと平文ブロックとの排他的論理和（XOR）演算によって暗号文ブロックを生成する。復号も同じ鍵ストリームと暗号文ブロックとの XOR 演算で行う。CTR モードでは各ブロックの処理が独立しているため、暗号化・復号ともに並列で高速に処理することが可能である。したがって **ア** が正解。
>
> - イ：CTR モードはストリーム暗号のように動作するため、パディングは不要である。
> - ウ：CBC モードの特徴である。CTR モードでは、誤りのあるビットに対応する平文のビットのみが誤りとなる。
> - エ：CBC モードの特徴である。

### 8.3 確認問題2：ハッシュ関数の衝突発見困難性

ハッシュ関数の性質の一つである衝突発見困難性に関する記述のうち、適切なものはどれか。

- ア　SHA-256 の衝突発見困難性を示す、ハッシュ値が一致する二つの元のメッセージの発見に要する最大の計算量は、256 の 2 乗である。
- イ　SHA-256 の衝突発見困難性を示す、ハッシュ値の元のメッセージの発見に要する最大の計算量は、2 の 256 乗である。
- ウ　衝突発見困難性とは、ハッシュ値が与えられたときに、元のメッセージの発見に要する計算量が大きいことによる、発見の困難性のことである。
- エ　衝突発見困難性とは、ハッシュ値が一致する二つの元のメッセージの発見に要する計算量が大きいことによる、発見の困難性のことである。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> ハッシュ関数は、任意の長さの入力データ（$x$）を基に、固定長のビット列（ハッシュ値）を生成する関数（$H(x)$）であり、次の三つの性質が求められる。
>
> - **衝突発見困難性（強衝突耐性）**：同一のハッシュ値を生成する（$H(x) = H(x')$）異なる二つのデータ（$x$、$x'$）を求めることが計算量的に困難であること
> - **第2原像計算困難性（弱衝突耐性）**：データ（$x$）と、それに対するハッシュ値（$y = H(x)$）が与えられたとき、同じハッシュ値となる（$H(x') = H(x)$）別のデータ（$x'$）を求めることが計算量的に困難であること
> - **原像計算困難性（一方向性）**：ハッシュ値（$y = H(x)$）が与えられたとき、それを生成するデータ（$x$）を求めることが計算量的に困難であること
>
> これらは、衝突発見困難性 → 第2原像計算困難性 → 原像計算困難性（一方向性）の順に、要求される条件が厳しい（強い）性質となる。つまり、攻撃者にとって最も見つけやすいのが衝突なので、それを防ぐ衝突発見困難性が、ハッシュ関数にとって最も満たすのが難しい要求である（6.1 の「攻撃者にとっては衝突発見が最も易しい」と表裏の関係）。
>
> - ア：ハッシュ値が256ビットの場合、ハッシュ値が一致する二つの元のメッセージの発見に要する計算量は、誕生日のパラドックスにより、平均して $2^{256/2} = 2^{128}$ となる。
> - イ：同じハッシュ値を出力するメッセージは複数存在する可能性があるため、$2^{256}$ 回試行しても元のメッセージが発見できるとは限らない。
> - ウ：原像計算困難性（一方向性）に関する記述である。
> - エ：適切な記述である。
>
> したがって **エ** が正解。

> **誕生日のパラドックス**
> 23人が集まると、その中に誕生日が同じ人が存在する確率が50%を超えるという、直感に反する確率論上の事実。ハッシュ関数に当てはめると、出力が $n$ ビットの場合、約 $2^{n/2}$ 回の試行で衝突が見つかる可能性が高くなる。これを利用した攻撃を **誕生日攻撃** という。

誕生日のパラドックスの式の意味を言葉で補うと、次のとおりです。

$$
\text{衝突を見つけるまでの試行回数の目安} \approx 2^{n/2} \quad (n = \text{ハッシュ値のビット数})
$$

特定の1人と同じ誕生日の人を探す（第2原像に相当）のは難しくても、「誰か2人が同じ誕生日」（衝突に相当）は、組合せの数が人数の2乗に比例して増えるので、ずっと早く起こります。したがって、ハッシュ関数の衝突に対する強度は出力長の半分のビット数になります。SHA-256 の衝突に対する強度は128ビットで、5.3 の表で SHA-256 がセキュリティ強度128ビットの行に置かれているのはこのためです。

### 8.5 確認問題4：AESの鍵長

NIST が制定した、AES における鍵長の条件はどれか。

- ア　128ビット、192ビット、256ビットから選択する。
- イ　256ビット未満で任意に指定する。
- ウ　暗号化処理単位のブロック長よりも32ビット長くする。
- エ　暗号化処理単位のブロック長よりも32ビット短くする。

*〔情報処理安全確保支援士試験・R3春〕*

> **解答・解説**
> AES（Advanced Encryption Standard）はブロック長が128ビットで、使用する鍵の長さは128、192、256ビットの中から選択することができる。段数（ラウンド数）は鍵長により、それぞれ10段、12段、14段となる。したがって **ア** が正解。

| 鍵長 | ブロック長 | ラウンド数 |
|---|---|---|
| 128ビット | 128ビット | 10 |
| 192ビット | 128ビット | 12 |
| 256ビット | 128ビット | 14 |

ブロック長は鍵長にかかわらず常に128ビットである点が引っかけになりやすいところです。「AES-256 はブロック長が256ビット」という誤りに注意してください。

### 8.6 確認問題5：量子暗号

量子暗号の特徴として、適切なものはどれか。

- ア　暗号化と復号の処理を、量子コンピュータを用いて瞬時に行うことができるので、従来のコンピュータでの処理に比べて大量のデータの秘匿を短時間で実現できる。
- イ　共通鍵暗号方式であり、従来の情報の取扱量の最小単位であるビットの代わりに量子ビットを用いることによって、瞬時のデータ送受信が実現できる。
- ウ　量子雑音を用いて疑似乱数を発生させて共通鍵を生成し、公開鍵暗号方式で配送することによって、解読が困難な秘匿通信が実現できる。
- エ　量子通信路を用いて安全に共有した乱数列を使い捨ての暗号鍵として用いることによって、原理的に第三者に解読されない秘匿通信が実現できる。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> 量子暗号（Quantum Cryptography）とは、量子力学に基づく共通鍵暗号方式の一種であり、暗号化・復号に用いる共通鍵を、光ファイバーによる量子通信路を通じて光子（光の粒子）で配送する。通信路上で光子を盗み見た場合、量子の性質により光子の状態が変化し正常に届かなくなるため、受信者側で盗聴を検知することができる。そのため、第三者に解読されない秘匿通信を実現できる。したがって **エ** が正解。

> **量子鍵配送（QKD）とワンタイムパッド**
> 量子暗号の中核技術は量子鍵配送（QKD：Quantum Key Distribution）であり、代表的なプロトコルに **BB84** がある。QKD で共有した乱数列を、平文と同じ長さの使い捨て鍵（**ワンタイムパッド**）として用いることで、情報理論的に安全な（計算能力に依存しない）秘匿通信が実現できる。なお、量子コンピュータでも解読が困難な数学的問題に基づく暗号は「耐量子暗号（PQC：Post-Quantum Cryptography）」と呼ばれ、量子暗号とは別の概念である。

### 8.7 確認問題6：前方秘匿性

前方秘匿性（Forward Secrecy）の説明として、適切なものはどれか。

- ア　鍵交換に使った秘密鍵が漏えいしたとしても、それより前の暗号文は解読されない。
- イ　時系列データをチェーンの形で結び、かつ、ネットワーク上の複数のノードで共有するので、データを改ざんできない。
- ウ　対となる二つの鍵の片方の鍵で暗号化したデータは、もう片方の鍵でだけ復号できる。
- エ　データに非可逆処理をして生成される固定長のハッシュ値からは、元のデータを推測できない。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> 前方秘匿性とは、鍵交換に使った秘密鍵が漏えいしたとしても、それより前の暗号文は解読されないという性質である。したがって **ア** が正解。
>
> - イ：ブロックチェーンの特徴に関する記述である。
> - ウ：公開鍵暗号方式の特徴に関する記述である。
> - エ：ハッシュ関数の原像計算困難性（一方向性）に関する記述である。

### 8.8 確認問題7：メッセージ認証符号（MAC）

送信者から受信者にメッセージ認証符号（MAC：Message Authentication Code）を付与したメッセージを送り、次に受信者が第三者に転送した。そのときの MAC に関する記述のうち、適切なものはどれか。ここで、共通鍵は送信者と受信者だけが知っており、送信者と受信者のそれぞれの公開鍵は第三者を含めた3名が知っているものとする。

- ア　MAC は、送信者がメッセージと共通鍵を用いて生成する。MAC を用いると、受信者がメッセージの完全性を確認できる。
- イ　MAC は、送信者がメッセージと共通鍵を用いて生成する。MAC を用いると、第三者が送信者の真正性を確認できる。
- ウ　MAC は、送信者がメッセージと受信者の公開鍵を用いて生成する。MAC を用いると、第三者がメッセージの完全性を確認できる。
- エ　MAC は、送信者がメッセージと送信者の公開鍵を用いて生成する。MAC を用いると、第三者が送信者の真正性を確認できる。

*〔情報処理安全確保支援士試験・R6春〕*

> **解答・解説**
> MAC は、通信データの改ざんの有無を検知し、完全性を保証するために、通信データと共通鍵から生成するコード（ビット列）である。MAC には、ブロック暗号を用いた CMAC（Cipher-based MAC）や、ハッシュ関数を用いた HMAC などがある。MAC を用いることで、共通鍵を知る受信者がメッセージの完全性を確認できる。したがって **ア** が正解。
>
> - イ：第三者は共通鍵を知らないため、MAC を検証できず、送信者の真正性も確認できない。
> - ウ、エ：MAC の生成には公開鍵ではなく共通鍵を用いる。

> **MACとデジタル署名の違い**
> MAC は送信者と受信者が同じ共通鍵を持つため、受信者も MAC を生成できる。そのため、第三者に対して「送信者が作成した」ことを証明できず、否認防止の機能は持たない。第三者に対しても真正性や否認防止を示す必要がある場合は、送信者の秘密鍵で署名し、公開鍵で検証するデジタル署名を用いる。

## 9. 試験対策まとめ（重要ポイント）

### 9.1 知識の確認（科目A-2向け）

- **暗号の構成要素**：暗号＝アルゴリズム（約束事）＋鍵（固有の値）。暗号化・復号は正規の利用者、解読は鍵を持たない第三者の行為。同じアルゴリズムなら鍵が長いほど強い。
- **共通鍵（対称鍵・秘密鍵）暗号**：同じ鍵で暗号化・復号。速いが鍵配送問題があり、鍵の数は $n(n-1)/2$（1,000人で499,500個）。
- **公開鍵（非対称鍵）暗号**：受信者の公開鍵で暗号化し、受信者の秘密鍵で復号。署名は署名者の秘密鍵で作り、署名者の公開鍵で検証。鍵の数は $2n$（1,000人で2,000個）。遅いので大量データに向かない。
- **ハイブリッド方式**：データ本体は共通鍵（セッション鍵）、セッション鍵は受信者の公開鍵で暗号化。SSL/TLS、S/MIME、PGP。
- **ストリーム暗号とブロック暗号**：ストリーム＝キーストリームとの XOR で逐次処理、サイズが増えない（RC4〈TLS では RFC 7465 で禁止〉、KCipher-2）。ブロック＝ブロック単位、端数はパディング（DES 64ビット／56ビット鍵、IDEA 64ビット／128ビット鍵、AES・Camellia 128ビット／128・192・256ビット鍵）。
- **AES のラウンド数**：鍵長128／192／256ビットで10／12／14段。ブロック長は常に128ビット。
- **暗号モード**：ECB は同じ平文ブロックが同じ暗号ブロックになり使用すべきでない。CBC は IV を使い、暗号化は並列不可・復号は並列可、ビット誤りは当該ブロック全体と次ブロックの対応ビット。CTR は nonce＋カウンタで暗号化・復号とも並列可、パディング不要、誤りは対応ビットのみ。OFB は誤りが波及しない。
- **CRYPTREC**：デジタル庁・総務省・経済産業省のプロジェクト。電子政府推奨暗号リスト／推奨候補暗号リスト／運用監視暗号リストの三つ。暗号技術評価委員会と暗号技術活用委員会。NISC（政策）、ISMS 適合性評価制度、JCMVP（暗号モジュールの試験・認証）と区別する。
- **推奨リストの中身**：署名＝DSA・ECDSA・EdDSA・RSA-PSS・RSASSA-PKCS1-v1_5、守秘＝RSA-OAEP、鍵共有＝DH・ECDH、128ビットブロック暗号＝AES・Camellia、ストリーム＝KCipher-2、ハッシュ＝SHA-256 以上・SHA-3、認証付き秘匿モード＝CCM・GCM、MAC＝CMAC・HMAC、認証暗号＝ChaCha20-Poly1305。3DES は運用監視、ECB は載っていない。
- **鍵長の同等性**：セキュリティ強度128ビット ≒ AES-128 ≒ RSA 3072ビット ≒ 楕円曲線256ビット。RSA 1024ビットと楕円曲線160ビットが同程度。
- **RSA と楕円曲線暗号**：RSA は素因数分解、楕円曲線暗号は ECDLP、DH は離散対数問題の困難性が根拠。楕円曲線暗号は短い鍵で同程度の強度。
- **量子暗号と耐量子暗号**：量子暗号＝量子鍵配送（QKD、BB84）で盗聴を検知できる共通鍵暗号の一種。耐量子暗号（PQC）＝量子コンピュータ（ショアのアルゴリズム）でも破られない数学的暗号で、NIST が FIPS 203／204／205 として標準化。
- **ハッシュ関数の三つの性質**：衝突発見困難性（強衝突耐性）・第2原像計算困難性（弱衝突耐性）・原像計算困難性（一方向性）。攻撃者にとっては衝突発見が最も易しい。衝突は誕生日攻撃で約 $2^{n/2}$ 回（SHA-256 なら $2^{128}$）。
- **主なハッシュ関数**：MD4・MD5 は128ビット、SHA-1 は160ビットで危殆化。SHA-2（SHA-224/256/384/512）と SHA-3（Keccak、FIPS 202、スポンジ構造、SHAKE は任意長）を使う。
- **MAC とデジタル署名**：MAC（CMAC、HMAC）は共通鍵で生成・検証し、完全性と当事者間の真正性を確認できるが、受信者も生成できるため否認防止は不可。否認防止にはデジタル署名。
- **HMAC**：ハッシュ計算に共有の秘密鍵を加え、攻撃者がハッシュ値を再計算して改ざんを隠すことを防ぐ（IPsec など）。
- **フィンガプリント**：証明書や公開鍵のハッシュ値。Web 掲載値は改ざんの可能性があるので、直接入手かアウトオブバンドで確認する。
- **Diffie-Hellman 鍵交換**：$q^x \bmod n = g^{xy} \bmod n = p^y \bmod n$。秘密は乱数 $x$、$y$ だけ。相手認証がないので中間者攻撃に注意。
- **前方秘匿性（PFS）**：鍵交換に使った秘密鍵が漏えいしても過去の暗号文は解読されない。DHE／ECDHE で実現。RSA 鍵交換にはないので TLS 1.3 で廃止。
- **引っかけ**：ブロックチェーン（改ざんできない分散台帳）、公開鍵暗号（片方の鍵で暗号化したらもう片方でだけ復号）、一方向性（ハッシュ値から元データを推測できない）は、前方秘匿性の誤答選択肢の定番。

### 9.2 記述式で問われる観点（科目B向け）

科目Bの暗号に関する設問は、「どの鍵を誰が使うか」「その方式で何が保証され、何が保証されないか」「鍵が漏れたら何が起きるか」を、事例の登場人物に当てはめて書かせます。次の形で答えられるようにしておきましょう。

- **鍵の使い方を答える**：「送信者は、受信者の公開鍵でセッション鍵を暗号化する。受信者だけが対応する秘密鍵を持つため、受信者以外はセッション鍵を取り出せないからである。」署名なら「署名者の秘密鍵で署名し、検証者は署名者の公開鍵で検証する。」主語と鍵の持ち主を必ず書く。
- **ハイブリッド方式を選ぶ理由**：「大容量のデータを公開鍵暗号で暗号化すると処理が遅いため、データ本体は高速な共通鍵暗号で暗号化し、鍵配送問題を解決するために共通鍵だけを公開鍵暗号で保護する。」
- **MAC では不十分な理由**：「MAC は送信者と受信者が同じ共通鍵を持つため、受信者も同じ MAC を作成できる。したがって、第三者に対して送信者が作成したことを証明できない（否認防止ができない）。否認防止が必要な取引ではデジタル署名を用いるべきである。」
- **ハッシュ値だけでは改ざんを検知できない理由**：「ハッシュ関数のアルゴリズムは公開されているため、攻撃者はデータを改ざんした後にハッシュ値を再計算して差し替えられる。秘密鍵を加えた HMAC を用いれば、鍵を知らない攻撃者は正しい値を計算できない。」
- **フィンガプリントの確認方法**：「Web サイトに掲載されたフィンガプリントは、サイトごと改ざんされているおそれがあるため、利用者は電話や郵送などインターネットとは別の経路で発行元に確認すべきである。」
- **前方秘匿性の効果**：「サーバの秘密鍵が漏えいしても、DHE／ECDHE では通信ごとの一時鍵が破棄されているため、攻撃者が過去に記録した通信は解読されない。RSA 鍵交換では、秘密鍵でセッション鍵の素材を復号できるため、過去の通信がすべて解読される。」
- **秘密鍵が漏えいしたときの対応**：管理者は、漏えいした鍵に対応する証明書を失効させ（第7章 7.7）、新しい鍵ペアを生成して証明書を再発行し、その鍵で保護していたデータや通信の影響範囲を特定する。
- **アルゴリズム選定の根拠**：「CRYPTREC の電子政府推奨暗号リストに掲載された AES と SHA-256 を採用する。DES や MD5 は危殆化しており、3DES は運用監視暗号リストに移され互換性維持のための利用に限られるため、新規システムでは採用しない。」暗号モードは「ECB は同一平文ブロックが同一暗号文になりパターンが漏れるため、GCM などの認証付き暗号を用いる。」
- **危殆化への備え**：使用中のアルゴリズム・鍵長・有効期限を台帳で管理し、設定変更で切り替えられるようにしておく。量子コンピュータによる将来の解読に備え、長期間秘密にすべきデータは耐量子暗号への移行を計画する。
- **鍵管理の要点**：秘密鍵は HSM や IC カードに格納して取り出せないようにし、ファイルで保管する場合はアクセス権限を所有者のみに絞り、パスフレーズで保護する。鍵の生成・配布・保管・更新・廃棄の手順を定め、担当者を限定する。
- **DH 鍵交換の弱点と対策**：「DH 鍵交換には相手を認証する仕組みがないため、中間者が公開値を差し替えると、双方と別々の鍵を共有して通信を中継・盗聴できる。デジタル署名や事前共有鍵で相手を認証して防ぐ。」
