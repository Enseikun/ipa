# レクチャーノート：情報セキュリティにおける脅威 ― 2.6 DNSサーバに対する攻撃

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ」（知識項目例：脅威，サイバー攻撃〈DoS攻撃，フィッシング ほか〉）／「技術要素」＞「ネットワーク」＞「通信プロトコル」（知識項目例：DNS）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

組織のネットワークをインターネットに接続するうえで欠くことができない要素の一つに、名前解決を行う**DNSサーバ**があります。利用者がWebサイトを見るときも、メールサーバがメールを送るときも、最初にDNSサーバに「この名前のIPアドレスは何か」を尋ねます。重要な役割を担うだけに、DNSサーバは攻撃の標的にもなりやすいのです。DNSが偽の答えを返せば、利用者は正しいURLを入力したのに偽サイトへ連れて行かれます。DNSが止まれば、Webサーバやメールサーバが無事でも、利用者からは「インターネット全体が止まった」ように見えます。

本ノートでは、DNSサーバに対する攻撃を、攻撃者の狙いで4つに分けて学びます。

1. **情報を盗む**：ゾーン転送で登録情報を収集する攻撃（2章）
2. **偽の答えを覚え込ませる**：DNSキャッシュポイズニングとカミンスキー攻撃（3章）
3. **サービスを止める**：不正なリクエストによるサービス不能、DNSリフレクション攻撃、DNS水責め攻撃（4章）
4. **通信路として悪用する**：DNSトンネリング（5章）

前提となるDNSの仕組み（リゾルバ、権威DNSサーバとキャッシュサーバ、再帰的問合せ）は [1.4](1.4_TCPIPの主なプロトコルとネットワーク技術の基礎.md) の 6章で学びました。本ノートは「攻撃の仕組み」に重心を置き、設定の詳細は [3.5 DNSの脆弱性と対策](3.5_DNSの脆弱性と対策.md) で掘り下げます。2.5 で学んだUDPのセッションハイジャックは、3章のキャッシュポイズニングの土台です。

科目Bとの関係では、DNSサーバの設計・運用（業務観点②③：サーバの分離配置、アクセス制限、ログ監視）と、DNSを悪用したマルウェア通信の発見（業務観点④：ログ分析による検知）に直結します。科目A-2では、キャッシュポイズニングの対策（ID・送信元ポート番号のランダム化、DNSSEC）、カミンスキー攻撃、DNS水責め攻撃、オープンリゾルバの定義が定番です。

## 1. DNSサーバに対する攻撃の全体像

### 1.1 6つの代表的な攻撃

DNSサーバに対する攻撃としては、次のものが代表的です。攻撃ごとに、攻撃者の狙い、損なわれる特性、主な対策を先に一覧にしておきます。

| 攻撃 | 攻撃者の狙い | 主に損なわれる特性 | 主な対策（DNSサーバの管理者が行う） |
|---|---|---|---|
| ゾーン転送要求による登録情報の収集 | 攻撃の下調べ（ネットワーク構成の把握） | 機密性 | ゾーン転送の許可先をセカンダリに限定 |
| DNSキャッシュポイズニング（汚染）攻撃（キャッシュに偽の情報を登録する攻撃） | 利用者を偽サイトに誘導する | 完全性（→機密性） | ID・送信元ポート番号のランダム化、DNSSEC、オープンリゾルバにしない |
| 不正なリクエストによりサービス不能状態を引き起こす攻撃 | DNSサービスを止める | 可用性 | バージョンアップ、設定変更 |
| DNSリフレクション攻撃（DNS amp攻撃） | DNSサーバを踏み台に第三者を攻撃する | 可用性（第三者と踏み台自身） | オープンリゾルバにしない、応答レート制限 |
| DNS水責め攻撃（ランダムサブドメイン攻撃） | 特定ドメインの権威DNSサーバを止める | 可用性 | オープンリゾルバにしない、問合せ数の制限 |
| DNSトンネリング | DNSを抜け道にしてマルウェアとC&Cサーバが通信する | 機密性（情報の持出し） | DNSクエリログの分析 |

最後のDNSトンネリングだけは、DNSサーバ自体に弱点がなくても成立する点が、ほかの5つと異なります。

### 1.2 ファーミングとフィッシング

2番目のDNSキャッシュポイズニング（汚染）攻撃は古くから知られている攻撃手法の一つですが、近年フィッシング詐欺に悪用されたことで、その危険性や影響の大きさが再認識されています。DNSサーバのキャッシュに偽の情報を登録することで、多くの一般ユーザを次々に偽のサイトに誘導するこの手法は、**ファーミング（Pharming）** とも呼ばれており、個別のユーザをターゲットにした**フィッシング（Phishing）** よりも大きな被害をもたらす可能性があります。

| 観点 | フィッシング | ファーミング |
|---|---|---|
| 攻撃者が細工する対象 | 個々の利用者（メールの文面とリンク） | DNSサーバのキャッシュ（名前解決の結果） |
| 利用者から見た異常 | メールのリンクのドメイン名が本物と違う | 正しいURLを入力しても偽サイトに着く（アドレスバーは本物の名前） |
| 被害の広がり | 騙された利用者だけ | そのDNSサーバを使う利用者全員 |
| 利用者の注意で防げるか | ある程度防げる（リンクを踏まない） | 防ぎにくい。サーバ証明書の警告に気づくことが最後の砦 |

ファーミングでは利用者の注意がほとんど役に立たないため、対策の主役はDNSサーバの管理者です。そして利用者側に残る最後の防御がHTTPSのサーバ証明書の検証です。偽サイトは本物のドメイン名の正規の証明書を持てないため、ブラウザは警告を出します。利用者はこの警告を無視してはいけません。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰ問2で、DNSサーバに対する攻撃とその対策に関する問題が出題された。

## 2. 情報を盗む ― ゾーン転送要求による登録情報の収集

**ゾーン転送**とは、DNSサーバが管理するゾーン情報（ホスト名とIPアドレスの対応など）を、別のDNSサーバへ一括して複製する機能です。通常の名前解決は**53/UDP**ポートで行われますが、ゾーン転送要求は**53/TCP**ポートで行われ、セカンダリのDNSサーバからプライマリのDNSサーバに対して定期的に実行されます。

問題は、特に制限をしていない場合、セカンダリDNSサーバ以外のホストからでも `nslookup` コマンド（`ls -d` サブコマンド）や `dig` コマンド（AXFR要求）を使用して容易に実行可能だという点です。攻撃者はゾーン転送要求を行うことにより、ターゲットサイトのネットワーク構成やサーバの構成を知ることができ、これらは攻撃者にとって有用な情報となります。たとえば「vpn」「db」「test」といった名前のホストとそのIPアドレスの一覧が手に入れば、攻撃者は次に狙うべき機器の地図を得たことになります（2.2 のポートスキャンの前段階の情報収集です）。

```
図：ゾーン転送要求による情報収集のイメージ

攻撃者 ──(ゾーン転送要求 53/TCP)──▶ プライマリDNSサーバ
       ◀──(ゾーン情報一式：ホスト名・IPアドレス等)──
```

**管理者は何をすべきか**：DNSサーバの管理者は、ゾーン情報を第三者に渡さないために、ゾーン転送を許可するホストをセカンダリDNSサーバに限定すべきです。BINDでの設定は次のような見た目になります。

```
// named.conf（プライマリDNSサーバ）の抜粋
zone "example.jp" {
    type primary;
    file "example.jp.zone";
    allow-transfer { 198.51.100.53; };   // セカンダリDNSサーバだけにゾーン転送を許可する
};
```

許可されていない相手からの要求は拒否され、DNSサーバのログに `zone transfer 'example.jp/AXFR/IN' denied` という行が残ります。運用者は、この行が繰り返し出ていれば「誰かが情報収集を試みている」兆候として監視すべきです。さらに、公開DNSサーバには内部のホスト名をそもそも登録しない（公開用と内部用の分離）ことで、万一制限を誤っても漏れる情報を公開して差し支えないものに限定できます（[3.5](3.5_DNSの脆弱性と対策.md) の 3.5・3.6）。

> **補足：53/TCP＝ゾーン転送、とは限らない**
> 以前は「53/TCPはゾーン転送のためのもの」と理解し、ゾーン転送が不要なら53/TCPをファイアウォールで遮断する対策が紹介されていました。現在はDNSSECなどで応答サイズが大きくなり、通常の名前解決でもTCPが使われることがあります（[3.5](3.5_DNSの脆弱性と対策.md) の 4章）。そのため管理者は、53/TCPを一律に遮断するのではなく、DNSサーバの設定でゾーン転送の許可先を限定することを基本とすべきです。

## 3. 偽の答えを覚え込ませる ― DNSキャッシュポイズニング攻撃

### 3.1 仕組み

**DNSキャッシュポイズニング攻撃**とは、DNSサーバ（キャッシュサーバ）から上位サーバ（権威DNSサーバ）への名前解決要求に対し、悪意あるDNSサーバが、正当な上位サーバからの応答が返る前に、悪意あるサイトに誘導するための不正な名前解決情報を返すことで、DNSのキャッシュに登録させる攻撃です。そのようにしてキャッシュが汚染されたDNSサーバを利用したユーザが悪意あるサイトに誘導され、機密情報が盗まれるなどの被害を受けます。

2.5 の 2.2 で見た「UDPでは、正規のサーバより先に偽の応答を返せばセッションを奪える」という性質を、DNSのキャッシュサーバに対して使ったものです。しかもキャッシュサーバは、覚えた答えをTTLの間ずっと使い回すため、1回の成功が、そのキャッシュサーバを使う**利用者全員**への被害に広がります。

```
図：DNSキャッシュポイズニングのイメージ

 利用者 ──①問合せ──→ キャッシュサーバ ──②問合せ──→ 正当な権威DNSサーバ
                            ↑   ↑                            │
                            │   └──── ④正当な応答（後着・捨てられる）
                            └─ ③偽の応答（先着・キャッシュに登録される）── 悪意あるDNSサーバ
 利用者 ←─⑤偽のIPアドレス── キャッシュサーバ  → 利用者は偽サイトへ誘導される
```

> **試験に出る**
> 情報処理安全確保支援士試験の令和3年度・午後Ⅰ問2で、DNSを悪用したサイバー攻撃を題材にした問題が出題された。

### 3.2 成立条件と、それぞれへの対策

この攻撃を成立させるためには、攻撃者は次の条件を満たす必要があります。どの条件が攻撃を容易にしているか、管理者はどの条件を断てるかを並べると、対策の意味がはっきりします。

| 成立条件 | 攻撃を容易にしていた要因 | 管理者が条件を断つ対策 |
|---|---|---|
| (1) 標的となるDNSサーバのキャッシュに、該当するドメインの情報が登録されていない（またはTTLが切れている）こと | ― | （当初はTTLを長くする対策がとられたが、カミンスキー攻撃で無効になった） |
| (2) 名前解決要求の送信元ポート番号と、応答のあて先ポート番号を合致させること | 送信元ポート番号を53番固定としているDNSサーバが多数存在した | 送信元ポート番号のランダム化（ソースポートランダマイゼーション） |
| (3) 名前解決要求のID（トランザクションを識別するためのID）と応答のIDを合致させること | IDが16ビット（最大65,536通り）しかない | IDを固定せずランダムにする |
| (4) 正当な上位サーバからの応答よりも早く応答を返すこと | UDPは先着の応答を採用する | DNSSECで、先着しても署名のない偽の応答を採用しない |

(1)の条件があるため、当初はDNSキャッシュ情報の**TTL**（Time To Live：有効時間）を長く設定することが有効な対策の一つとされていました。キャッシュに正しい情報が残っている間は、キャッシュサーバは上位サーバに問い合わせないので、攻撃者が偽の応答を差し込む機会がないからです。しかし、その後この攻撃をより強力にした**カミンスキー攻撃**（3.3）が公表されたことにより、この設定は対策として意味を成さなくなりました。

(2)(3)は、攻撃者が「当てなければならない値」の多さの問題です。IDだけなら最大65,536通りで、攻撃者が大量の偽応答を送れば当たりうる数です。送信元ポート番号もランダムにすると、組み合わせは \(2^{16} \times 2^{16} = 2^{32}\)（約43億通り）に増え、当たる確率は大きく下がります（計算の詳細は [3.5](3.5_DNSの脆弱性と対策.md) の 3.3）。

> **補足：「53番固定」は以前の状況**
> 原本の記述どおり、以前は送信元ポート番号を53番に固定したDNSサーバが多数存在し、これが攻撃を容易にしていました。2008年のカミンスキー攻撃の公表を受けて、主要なDNSサーバソフトウェアはソースポートランダマイゼーションを標準の動作とするよう改められ、現在は既定で有効になっています。ただし、ファイアウォールやNAPT機器が送信元ポート番号を規則的に書き換えてしまうと、せっかくのランダム化が失われます。管理者は、DNSサーバの設定だけでなく、経路上の機器の動作も確認すべきです。

### 3.3 カミンスキー攻撃（Kaminsky's attack）

**カミンスキー攻撃**は、セキュリティ研究者のDan Kaminsky氏によって**2008年**に考案・公表されたDNSキャッシュポイズニング攻撃の一種です。攻撃手法の概要を次に示します。

1. 攻撃者は、標的となるDNSサーバに対し、汚染情報を登録したいドメイン名と同じドメインかつ存在しないFQDN（例：`001.sample.poisoningdata.jp`）の名前解決要求を行う
2. ①の名前解決要求を受けたDNSサーバは、キャッシュに登録されていないため、上位サーバに対して問い合わせる
3. 攻撃者は、②の応答が返る前に「`001.sample.poisoningdata.jp` は `www.sample.poisoningdata.jp` という権威DNSサーバが知っている」「`www.sample.poisoningdata.jp` のIPアドレスは `aaa.bbb.ccc.ddd`」というような偽の応答を任意のIDで返す（攻撃者は偽の権威DNSサーバ `aaa.bbb.ccc.ddd` をあらかじめ用意しておく）
4. ①のFQDNと③のIDを変化させながら①～③を繰り返すうちに、前述の条件が成立すると、汚染情報が標的となったDNSサーバのキャッシュに登録される

存在しないFQDNを毎回変えて問い合わせるため、キャッシュのTTLに左右されずに何度でも攻撃を試行できる点が、従来のキャッシュポイズニング攻撃との大きな違いです。存在しない名前は毎回「キャッシュにない」ので、3.2 の条件(1)が常に満たされてしまうのです。さらに、偽の応答で書き換えるのは1つのホストのアドレスではなく「このドメインの権威DNSサーバはここだ」という情報なので、成功すればドメイン全体の名前解決が攻撃者の偽の権威DNSサーバに向けられます。

| 観点 | 従来のキャッシュポイズニング | カミンスキー攻撃 |
|---|---|---|
| 問い合わせさせる名前 | 実在する名前（例：www） | 存在しないランダムな名前（例：001、002…） |
| 試行できる回数 | キャッシュのTTLが切れるたびに1回 | TTLに関係なく何度でも |
| TTLを長くする対策 | 有効 | 無効 |
| 汚染される範囲 | 1つの名前 | ドメイン全体（権威DNSサーバの情報を書き換える） |
| 有効な対策 | ID・ポートのランダム化、DNSSEC | 同左（とくにソースポートランダマイゼーションとDNSSEC）、外部からの再帰的問合せの拒否 |

最後の行の「外部からの再帰的問合せの拒否」が効くのは、手順1の「標的のキャッシュサーバに問合せを送る」ことを、外部の攻撃者ができなくなるからです。キャッシュサーバがオープンリゾルバでなければ、攻撃者は攻撃の起点を失います。

**管理者の確認ポイント**：DNSサーバの管理者は、キャッシュサーバで次の3点が有効になっているかを確認すべきです（設定例は [3.5](3.5_DNSの脆弱性と対策.md) の 3.7）。

```
// named.conf（内部キャッシュサーバ）の抜粋
acl "internal" { 192.0.2.0/24; };
options {
    allow-recursion { internal; };   // 再帰的な問合せは社内だけ（オープンリゾルバにしない）
    dnssec-validation auto;          // DNSSECの署名を検証し、偽の応答を採用しない
    // query-source port 53;         // ← このように送信元ポートを固定する古い設定が残っていれば削除する
};
```

## 4. サービスを止める ― DNSを狙う・DNSを使う妨害

### 4.1 不正なリクエストによりサービス不能状態を引き起こす攻撃

攻撃者は、DNSサーバの仕様上の脆弱性や実装上の脆弱性を突いて不正な要求を与えることにより、サービス不能状態を引き起こします。

2002年10月には、世界に13台あるルートDNSサーバが一斉にDDoS攻撃を受け、うち9台が一時的に正常なサービスを提供できなくなるという事件が発生しました。こうした問題は数多く報告されていますが、いずれもDNSサーバソフトウェアのバージョンアップや設定変更によって対処可能です。DNSサーバの管理者は、JPRSやJPCERT/CCの注意喚起を継続的に確認し、公表された脆弱性に速やかにパッチを当てる運用を決めておくべきです。

> **補足：ルートDNSサーバの「13台」**
> 2002年当時の説明では「13台」とされていましたが、現在のルートDNSサーバは A〜M の13の名前（13系統）で運用され、各系統が**エニーキャスト**（同じIPアドレスを世界各地の多数のサーバで分担する方式）によって多数の拠点に分散配置されています。このため、特定の1か所を攻撃しても全体が止まりにくい構成になっています。「13」は台数ではなく系統の数と理解するのが現在は正確です。

### 4.2 DNSリフレクション攻撃（DNS amp攻撃）

**DNSリフレクション（反射）攻撃**（「**DNSリフレクタ攻撃**」とも呼ばれる）とは、2.7 で解説する反射・増幅型DDoS攻撃の一種であり、攻撃者が、他のサイトを攻撃するために、DNSサーバ（キャッシュサーバ）を攻撃パケットの踏み台として悪用する手法です。この攻撃により、踏み台となったDNSサーバ自体の負荷が高まり、サービス不能状態となる場合もあります。応答メッセージを増幅（amplification）させて負荷を高めることから「**DNS amp攻撃**」とも呼ばれます。

DNSリフレクション攻撃の仕組みを次に示します。

1. 攻撃者は、送信元アドレスを最終的なターゲットとなるホストのIPアドレスに詐称したうえで、攻撃に加担させるDNSサーバあてにクエリを送る。このとき、応答メッセージのサイズができるだけ大きくなるようにする（例：ANYタイプの問合せや、DNSSEC関連のレコードを含む問合せなど）
2. クエリを受け取ったDNSサーバは、偽装された送信元アドレス（最終的なターゲットホスト）に対して応答を返す

これを数多くのDNSサーバに対して一斉に行うと、反射・増幅型DDoS攻撃となります。

```
図：DNSリフレクション攻撃のイメージ

 攻撃者 ──小さなクエリ（送信元＝ターゲットに詐称）──→ オープンリゾルバ群（踏み台）
                                                        │ │ │
                                   大きな応答が一斉に ──┘ │ └──→ ターゲットホスト
                                                          └────→ （回線があふれる）
```

この攻撃の要点は2つです。1つは、DNSがUDPで動くため、送信元IPアドレスの詐称を確かめる手順がないこと（[1.4](1.4_TCPIPの主なプロトコルとネットワーク技術の基礎.md) の 2.1）。もう1つは、小さな問合せに大きな応答が返るため、攻撃者の送信量が何倍にも**増幅**されることです。ターゲットから見ると、攻撃パケットの送信元は正規のDNSサーバなので、真犯人をたどれません。

> **DDoS攻撃**
> Distributed Denial of Service（分散型サービス不能攻撃）。インターネット上にある多数の踏み台にあらかじめ仕掛けておいた攻撃プログラム（ボットなど）から一斉にDoS攻撃を仕掛け、ターゲットサイトのネットワーク帯域をあふれさせる攻撃。2.7 で解説。

> **反射・増幅型DDoS攻撃**
> TCP、UDP、ICMPなどのIPプロトコルにおける通信手順やアプリケーションの仕様において生成される応答パケットを悪用したDDoS攻撃のこと。小さな要求パケットで大きな応答パケットを発生させることで、攻撃の効果を増幅させる。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰで、DNSリフレクション攻撃を題材とした問題が出題された。

**管理者は何をすべきか**：DNSサーバの管理者が最優先ですべきことは、自組織のキャッシュサーバを**オープンリゾルバにしない**ことです（4.3 の用語解説、3.3 の設定例の `allow-recursion`）。踏み台にされると、自組織が加害者側になり、自組織の回線やサーバも過負荷になるからです。権威DNSサーバはインターネット全体からの問合せに答える必要があるため問合せ元を絞れませんが、同じ応答を短時間に大量に返さない**応答レート制限**（RRL：Response Rate Limiting）を設定すれば、反射役に使われる被害を抑えられます。

```
// named.conf（公開権威DNSサーバ）の抜粋
options {
    recursion no;                        // 権威DNSサーバは再帰的な問合せを受け付けない
    rate-limit { responses-per-second 10; };   // 同一宛先への同じ応答を毎秒10件までに抑える（RRL）
};
```

また、以前はANYタイプの問合せに対して全レコードを返すのが一般的で、これが増幅に悪用されていました。現在は、ANYタイプの問合せに最小限の応答だけを返すことが仕様（RFC 8482）で認められ、主要なDNSサーバソフトウェアや大手のDNSサービスはそのように動作しています。

### 4.3 DNS水責め攻撃（ランダムサブドメイン攻撃）

**DNS水責め攻撃**とは、攻撃者が、オープンリゾルバとなっているDNSキャッシュサーバに対し、攻撃対象のドメインのランダムなサブドメイン名（例：`abc123.example.jp`、`xyz789.example.jp` など）を大量に発生させ、不正な名前解決要求を行う手法です。存在しないサブドメイン名はキャッシュされていないため、問合せはすべて権威DNSサーバへ転送されます。これにより、攻撃対象ドメインの権威DNSサーバ（コンテンツサーバ）を過負荷にさせます。

「存在しないランダムな名前を問い合わせて、キャッシュを素通りさせる」という点は、3.3 のカミンスキー攻撃と同じ発想です。ただし目的が違います。カミンスキー攻撃の目的はキャッシュサーバに偽の情報を覚えさせること（完全性の侵害）、水責め攻撃の目的は権威DNSサーバを止めること（可用性の侵害）です。そして水責め攻撃では、キャッシュサーバは被害者であると同時に、攻撃を権威DNSサーバへ中継させられる加担者にもなります。

> **オープンリゾルバ**
> 問合せ元のアドレスや問合せ対象ドメインを制限せず、インターネット上の誰からの名前解決要求にも応答してしまうDNSキャッシュサーバのこと。DNSリフレクション攻撃やDNS水責め攻撃の踏み台として悪用される。

**運用者はどう気づくか**：水責め攻撃を受けている権威DNSサーバ、あるいは中継させられているキャッシュサーバのクエリログには、次のような傾向が現れます（例示用のログ）。

```
30-Sep-2026 10:15:42.101 queries: client 198.51.100.7#40211: query: abc123.example.jp IN A -E
30-Sep-2026 10:15:42.102 queries: client 198.51.100.7#40212: query: xyz789.example.jp IN A -E
30-Sep-2026 10:15:42.102 queries: client 198.51.100.9#51877: query: q8w2e5.example.jp IN A -E
30-Sep-2026 10:15:42.103 queries: client 198.51.100.7#40213: query: m3n7b1.example.jp IN A -E
        ↑ 同じドメインの、意味のないランダムなサブドメインが、ミリ秒単位で次々に問い合わせられている
          （応答はいずれも「存在しない」＝NXDOMAIN）
```

運用者は、「同一ドメインあてのNXDOMAIN応答が急増している」「サブドメイン部分がランダムな文字列ばかり」という2点から、正常な利用ではないと判断できます。キャッシュサーバの管理者は、オープンリゾルバの状態を解消するとともに、クライアントからの問合せ数に上限を設けることで、中継役にされる被害を抑えます（[3.5](3.5_DNSの脆弱性と対策.md) の 3.7）。

## 5. 通信路として悪用する ― DNSトンネリング

**DNSトンネリング**とは、内部に侵入したマルウェアが、外向けDNSキャッシュサーバを介して、攻撃者がC&Cサーバとしてインターネット上に設置した不正な権威DNSサーバと通信する手法です。マルウェアは、侵入した組織の外向けDNSキャッシュサーバに対し、不正な権威DNSサーバが管理するドメインについての**再帰的クエリ**を送信します。すると、外向けDNSキャッシュサーバが不正な権威DNSサーバ（C&Cサーバ）に対して**非再帰的クエリ**を送信することで、C&C通信が確立します。データはサブドメイン名やTXTレコードなどにエンコードされて送受信されます。

> **C&Cサーバ**
> Command and Control server（指令サーバ）。ボットに感染したPC等に対して指令を送り、遠隔から制御したり、窃取した情報を受け取ったりする役割を持つサーバ。詳細は 2.9 のボットネットの節で扱う。

```
図：DNSトンネリングの構造

 [社内] 感染PC(マルウェア) ──再帰的クエリ──→ 外向けDNSキャッシュサーバ
                                                   │ 非再帰的クエリ（正規のDNSの動作）
 [インターネット]                                  ↓
                                         不正な権威DNSサーバ（＝C&Cサーバ）
   ・問合せの名前（サブドメイン）に、持ち出すデータを埋め込む
   ・応答（TXTレコードなど）に、攻撃者からの指令を埋め込む
```

ファイアウォールでWebやメールの通信を厳しく制限している組織でも、名前解決は業務に不可欠なので、社内のキャッシュサーバから外部へのDNS通信は許可されています。マルウェアはこの「必ず開いている出口」を抜け道として使います。この攻撃は組織の外向けDNSキャッシュサーバに脆弱性がなくとも成立する可能性があり、防ぐことは容易ではありません。キャッシュサーバは、DNSの仕様どおりに正しく動作しているだけだからです。

とはいえ、不正な権威DNSサーバとの通信に用いられるホスト名にはランダムな長い文字列が使われることが多く、当該サーバとの間で多数のDNSクエリが発生するため、**DNSクエリログを分析することによって検知することは可能**です。外向けキャッシュサーバのクエリログは、たとえば次のように見えます（例示用のログ。文字列は省略して示す）。

```
30-Sep-2026 10:20:01.331 queries: client 192.0.2.45#53120: query: mzxw6ytboi4dcmrt...gezdg.t1.example.net IN TXT +
30-Sep-2026 10:20:01.874 queries: client 192.0.2.45#53121: query: nbswy3dpeb3w64tm...mqqgs.t1.example.net IN TXT +
30-Sep-2026 10:20:02.402 queries: client 192.0.2.45#53122: query: ojsxg5dfon2gk3tb...ebqw4.t1.example.net IN TXT +
        ↑ 社内の1台の端末から、同じドメインあてに、意味のない長いサブドメイン付きの問合せが
          秒単位で繰り返されている（業務で使うドメインでもない）
```

運用者は、「同一の端末から」「同じ見慣れないドメインあてに」「異常に長くランダムなサブドメイン名で」「TXTなど普段少ないレコード型の問合せが大量に」という特徴の組合せから、DNSトンネリングを疑います。疑わしい端末を特定したら、2.9 と 4.8 で学ぶ手順に従ってネットワークから隔離し、調査します。組織の管理者は、社内の端末が社内のキャッシュサーバ以外のDNSサーバに直接問い合わせられないようファイアウォールで制限しておくべきです。そうすれば、すべてのDNS通信が社内のキャッシュサーバを通り、クエリログという検知の材料が必ず手元に残るからです。

## 6. DNSサーバに対する攻撃への対策

これまでの対策を、1.2 の対策の4機能に沿って整理します。「誰が」は、特記がなければDNSサーバの管理者です。各対策の設定方法の詳細は [3.5 DNSの脆弱性と対策](3.5_DNSの脆弱性と対策.md) の 3章で扱います。

### 6.1 予防・防止

| 対策 | 何のために | 主に効く攻撃 |
|---|---|---|
| DNSサーバのソフトウェアのバージョンを最新にする | 既知の実装上の脆弱性を突かせない | サービス不能攻撃ほか全般 |
| DNSの送信元ポート番号をランダムにする（ソースポートランダマイゼーション） | 偽の応答を一致させにくくする | キャッシュポイズニング、カミンスキー攻撃 |
| DNS問合せに使用するIDを固定せずランダムにする | 偽の応答を一致させにくくする | キャッシュポイズニング |
| ゾーン転送を許可するホストをセカンダリDNSサーバに限定する | ゾーン情報を第三者に渡さない | ゾーン転送による情報収集 |
| DNSSEC（DNS Security Extensions）を導入し、応答の正当性を電子署名によって検証する | 先着した偽の応答を採用しない | キャッシュポイズニング、カミンスキー攻撃 |
| 脆弱性検査を実施し、DNS関連のセキュリティホールの有無を確認する（問題箇所があれば対処する） | 設定の不備や古い版を見つけて直す | 全般 |
| DNSキャッシュサーバが不要なクエリを拒否するようアクセス制限を施す（オープンリゾルバにしない） | 外部の攻撃者に使わせない・踏み台にさせない | リフレクション、水責め、カミンスキー攻撃 |
| 公開用の権威DNSサーバと内部向けのキャッシュDNSサーバを分離する | 機能ごとに最適なアクセス制御をかけ、被害の波及を防ぐ | キャッシュポイズニング、リフレクション、情報収集 |

DNSSECは、ソースポートランダマイゼーションやIDのランダム化と性質が違います。ランダム化は「当たりにくくする」対策で、確率をゼロにはできません。DNSSECは「当たっても見抜ける」対策で、偽の応答に正しい署名を付けられない以上、先着しても採用されません。そのぶん、署名する側（権威DNSサーバ）と検証する側（キャッシュサーバ）の両方で導入と鍵の運用が必要になります。

### 6.2 検知・追跡

- セキュリティ運用担当者は、ネットワーク監視型IDS、IPSを用いてDNSサーバに対する攻撃を検知します（第5章 [5.6](<5.6_侵入検知システム(IDS).md>)・[5.7](<5.7_侵入防御システム(IPS).md>)）。
- セキュリティ運用担当者は、DNSクエリログを分析することで、DNSサーバを悪用した攻撃（水責め攻撃、DNSトンネリングなど）を検知します。4.3 と 5章で見たように、ランダムなサブドメイン名、NXDOMAIN応答の急増、特定端末からの長い名前の大量問合せが、読み取るべき兆候です。そのためにDNSサーバの管理者は、クエリログを取得する設定を有効にし、十分な期間保存しておく必要があります。

### 6.3 回復

- DNSサーバの管理者は、攻撃を受けた原因となった脆弱性を特定するとともに、予防・防止に挙げた対策を実施します。
- キャッシュが汚染された場合は、DNSサーバの管理者はDNSキャッシュをクリアします。汚染された情報はTTLの間使われ続けるため、原因となった脆弱性を塞いだうえで、キャッシュを消して正しい情報を取り直させる必要があります。あわせて、汚染されていた期間に偽サイトへ誘導された利用者がいないかを調査し、該当者にはパスワードの変更などを案内します。

## 7. 確認問題

### 7.1 理解度チェック（Check!）

- **Q1**：DNSサーバに対する攻撃にはどのような種類があるか。
- **Q2**：DNSキャッシュポイズニング攻撃によってどのような影響があるか。
- **Q3**：DNSサーバに対する攻撃への対策としてはどのようなものがあるか。

> **解答の要点**
> - Q1：ゾーン転送要求による登録情報の収集、DNSキャッシュポイズニング攻撃（カミンスキー攻撃を含む）、不正なリクエストによるサービス不能攻撃、DNSリフレクション攻撃（DNS amp攻撃）、DNS水責め攻撃（ランダムサブドメイン攻撃）、DNSトンネリング（1.1）。
> - Q2：汚染されたキャッシュサーバを使う利用者全員が、正しい名前を入力しても偽サイトに誘導され、機密情報を盗まれるなどの被害を受ける（ファーミング）（1.2・3.1）。
> - Q3：ソフトウェアの最新化、送信元ポート番号とIDのランダム化、ゾーン転送の制限、DNSSEC、脆弱性検査、オープンリゾルバにしないアクセス制限、権威DNSサーバとキャッシュサーバの分離、IDS/IPSとクエリログ分析による検知、キャッシュのクリア（6章）。

### 7.2 問1

DNSキャッシュポイズニング攻撃に対して有効な対策はどれか。

- ア　DNSサーバにおいて、侵入したマルウェアをリアルタイムに隔離する。
- イ　DNS問合せに使用するDNSヘッダ内のIDを固定せずにランダムに変更する。
- ウ　DNS問合せに使用する送信元ポート番号を53番に固定する。
- エ　外部からのDNS問合せに対しては、宛先ポート番号53のものだけに応答する。

［情報処理安全確保支援士試験・H31春］

> **解答・解説**
> DNSキャッシュポイズニング攻撃を成功させるには、攻撃者は名前解決要求のIDと応答のIDを合致させる必要がある。IDを固定せずランダムに変更すれば、攻撃者が偽の応答のIDを一致させることが困難になり、攻撃の成功率を下げることができる。ウは送信元ポート番号を固定することで逆に攻撃を容易にしてしまう。したがって**イ**が正解。

### 7.3 問2

DNS水責め攻撃（ランダムサブドメイン攻撃）の手口と目的に関する記述のうち、適切なものはどれか。

- ア　ISPが管理するDNSキャッシュサーバに対して、送信元を攻撃対象のサーバのIPアドレスに詐称してランダムかつ大量に生成したサブドメイン名の問合せを送り、その応答が攻撃対象のサーバに送信されるようにする。
- イ　オープンリゾルバとなっているDNSキャッシュサーバに対して、攻撃対象のドメインのサブドメイン名をランダムかつ大量に生成して問い合わせ、攻撃対象の権威DNSサーバを過負荷にさせる。
- ウ　攻撃対象のDNSサーバに対して、攻撃者が管理するドメインのサブドメイン名をランダムかつ大量に生成してキャッシュさせ、正規のDNSリソースレコードを強制的に上書きする。
- エ　攻撃対象のWebサイトに対して、当該ドメインのサブドメイン名をランダムかつ大量に生成してアクセスし、非公開のWebページの参照を試みる。

［情報処理安全確保支援士試験・H29］

> **解答・解説**
> DNS水責め攻撃とは、問合せ元のアドレスや問合せ対象ドメインの制限なく名前解決を行うサーバ（オープンリゾルバ）となっているDNSキャッシュサーバに対し、攻撃対象のドメインのランダムなサブドメイン名を大量に発生させ、不正な名前解決要求を行う手法である。これにより、攻撃対象ドメインの権威DNSサーバ（コンテンツサーバ）を過負荷にさせる。したがって**イ**が正解。
>
> アは「送信元を詐称して応答を攻撃対象に送らせる」点でDNSリフレクション攻撃の説明が混ざっている。攻撃の「被害者がどこか」（水責め＝権威DNSサーバ、リフレクション＝送信元に詐称されたホスト）で区別するとよい。

### 7.4 問3

企業のDMZ上で1台のDNSサーバをインターネット公開用と社内用で共用している。このDNSサーバが、DNSキャッシュポイズニングの被害を受けた結果、直接引き起こされ得る現象はどれか。

- ア　DNSサーバのハードディスク上のファイルに定義されたDNSサーバ名が書き換えられ、インターネットからの参照者が、DNSサーバに接続できなくなる。
- イ　DNSサーバのメモリ上にワームが常駐し、DNS参照元に対して不正プログラムを送り込む。
- ウ　社内の利用者が、インターネット上の特定のWebサーバを参照しようとすると、本来とは異なるWebサーバに誘導される。
- エ　社内の利用者間で送信された電子メールの宛先アドレスが書き換えられ、正常な送信ができなくなる。

［情報処理技術者試験・過去問題］

> **解答・解説**
> DNSキャッシュポイズニングは、DNSサーバのキャッシュに偽の名前解決情報を登録させる攻撃である。このDNSサーバを名前解決に利用している社内の利用者が、インターネット上のWebサーバのFQDNを問い合わせると、汚染されたキャッシュに基づいた偽のIPアドレスが返され、本来とは異なるWebサーバ（攻撃者が用意した偽サイト）に誘導されることになる。アはハードディスク上のゾーンファイルの改ざん、イはワーム感染、エはメールの改ざんであり、いずれもキャッシュポイズニングによって直接引き起こされる現象ではない。したがって**ウ**が正解。
>
> 問題文の「公開用と社内用で共用」は、6.1 の「権威DNSサーバとキャッシュサーバの分離」ができていない構成である。科目Bでは、この構成の問題点と改善策（機能ごとにサーバを分ける）を問われることが多い。

### 7.5 問4

DNSに対するカミンスキー攻撃（Kaminsky's attack）への対策はどれか。

- ア　DNSキャッシュサーバと権威DNSサーバとの計2台の冗長構成とすることによって、過負荷によるサーバダウンのリスクを大幅に低減させる。
- イ　SPF（Sender Policy Framework）を用いてDNSリソースレコードを認証することによって、電子メールの送信元ドメインが詐称されていないかどうかを確認する。
- ウ　問合せ時の送信元ポート番号をランダム化することによって、DNSキャッシュサーバに偽の情報がキャッシュされる確率を大幅に低減させる。
- エ　プレースホルダを用いたエスケープ処理を行うことによって、不正なSQL構文によるDNSリソースレコードの書換えを防ぐ。

［情報処理安全確保支援士試験・R5春］

> **解答・解説**
> カミンスキー攻撃とは、セキュリティ研究者のDan Kaminsky氏によって考案・公表されたDNSキャッシュポイズニング攻撃の一種である。攻撃者が、汚染情報を登録したいドメイン名と同じドメインかつ存在しないFQDNの名前解決要求を行うことで、従来よりも効率良く攻撃を成立させる手法である。
>
> 攻撃を成功させるためには、攻撃者は、送信ポート番号（名前解決要求の送信元ポート番号であり、応答時のあて先ポート番号となる）、トランザクションIDを本来の応答レコードと合致させる必要がある。送信ポート番号、あて先ポート番号ともに53番に固定する設定となっているDNSサーバは（以前は）数多く存在し、これが攻撃を容易にさせていた。また、トランザクションIDが16ビット（最大65,536通り）であることも攻撃を容易にさせている。
>
> そのため、DNSの送信元ポート番号をランダム化（ソースポートランダマイゼーション）することで、カミンスキー攻撃をはじめとしたDNSキャッシュポイズニング攻撃が成功する確率を大きく低減させることができる。したがって**ウ**が正解。
>
> **補足**：アは可用性向上策、イは電子メールの送信ドメイン認証技術、エはSQLインジェクション対策であり、いずれもカミンスキー攻撃への対策とはならない。より根本的な対策としては、DNS応答に電子署名を付与して正当性を検証するDNSSECの導入が挙げられる。

## 8. 試験対策まとめ（重要ポイント）

### 8.1 知識の確認（科目A-2向け）

- **名前解決とゾーン転送のポート**：通常の名前解決は53/UDP、ゾーン転送は53/TCP（ただし現在は通常の名前解決でもTCPを使うことがある）。ゾーン転送の許可先はセカンダリDNSサーバに限定する。
- **キャッシュポイズニングの成立条件**：キャッシュにない（TTL切れ）、送信元ポート番号の一致、ID（16ビット＝65,536通り）の一致、正規より先着。対策は**IDのランダム化**と**ソースポートランダマイゼーション**（組合せ約43億通り）、根本策は**DNSSEC**。「ポートを53番に固定」は逆効果という引っかけが定番。
- **カミンスキー攻撃（2008年）**：存在しないFQDNを毎回変えて問い合わせるので、TTLを長くする対策が無効になる。権威DNSサーバの情報を書き換えるためドメイン全体が汚染される。
- **ファーミングとフィッシング**：DNSを汚染して多数を誘導するのがファーミング、個別の利用者を騙すのがフィッシング。
- **DNSリフレクション（DNS amp）と水責め**：リフレクションは送信元を詐称して**第三者**に大きな応答を送らせる（反射・増幅型DDoS）。水責めはランダムなサブドメインで**権威DNSサーバ**を過負荷にする。どちらもオープンリゾルバが踏み台になる。
- **オープンリゾルバ**：誰からの再帰的問合せにも答えるキャッシュサーバ。再帰的問合せを自組織だけに制限して解消する。
- **DNSトンネリング**：DNSサーバに脆弱性がなくても成立。マルウェアが再帰的クエリで不正な権威DNSサーバ（C&Cサーバ）と通信し、データはサブドメイン名やTXTレコードに埋め込む。**DNSクエリログの分析**で検知する。
- **回復**：汚染されたらDNSキャッシュをクリアする。

### 8.2 記述式で問われる観点（科目B向け）

- **構成図から問題点を指摘する**：「1台のDNSサーバが権威DNSサーバとキャッシュサーバを兼ねている」「キャッシュサーバがインターネットからの再帰的問合せに応答する」といった構成を見つけ、「機能ごとにサーバを分離し、キャッシュサーバの再帰的問合せを社内のアドレスに限定する」と、改善策と理由をセットで書く。
- **対策の効き方の違いを説明する**：ランダム化は「偽応答が一致する確率を下げる」、DNSSECは「署名検証で偽応答を採用しない」。なぜDNSSECが根本策かを1文で言えるようにする。
- **ログから攻撃を特定する**：クエリログで「ランダムなサブドメイン＋NXDOMAIN急増」なら水責め、「社内の特定端末から長いサブドメイン名とTXTレコードの大量問合せ」ならDNSトンネリング、と兆候と攻撃名を結びつける。
- **DNSトンネリングの検知を可能にする設計**：「社内端末から外部DNSサーバへの直接の通信をファイアウォールで禁止し、社内キャッシュサーバ経由に限定する。すべての問合せのログを取得できるようにするため」と、制限と目的を結びつける。
- **踏み台にならない責任**：自組織のDNSサーバがリフレクション攻撃に悪用されると加害者側になる。オープンリゾルバの解消と応答レート制限を、自組織と第三者の双方を守る対策として説明する。
- **汚染時の初動**：原因の脆弱性を塞ぐ→キャッシュをクリアする→汚染期間中にアクセスした利用者を調査・案内する、の順序で書く。
