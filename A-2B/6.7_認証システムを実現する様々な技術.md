# 情報セキュリティ対策技術(2)アクセス制御と認証

## 6.7 認証システムを実現する様々な技術

ここでは、認証システムを実現する技術として、RADIUS、TACACS/TACACS+、Kerberos、ディレクトリサービス、EAPを取り上げて解説する。

### 6.7.1 RADIUS

RADIUS(Remote Authentication Dial-In User Service)は、ネットワーク利用者の**認証**と**利用記録(アカウンティング)**を一元的に行うシステムである。当初はその名のとおり、公衆電話網を通じたダイヤルアップ接続サービスのために開発された。近年はその利用範囲が拡大し、光ファイバによるブロードバンドネットワークや携帯電話でのネットワークサービスなどでも広く採用されている。

```
図:RADIUSによる認証システムのイメージ

 [利用者]            [アクセスサーバ]            [RADIUSサーバ]
 ダイヤルアップ ──┐   (RADIUSクライアント)        (認証サーバ)
 ブロードバンド ──┼──▶  NAS / VPN装置 等  ──────▶  認証情報DB
 無線LAN       ──┘                     ◀──────  認証結果・
                                                   アカウンティング
```

一般的なサーバOSに標準装備されている簡易なRAS(Remote Access Service)では、ユーザからのアクセス要求を受け付けるアクセスサーバと、ユーザの認証を行う認証サーバが分離しておらず、1台のサーバで処理を行う。一方、RADIUSでは、アクセスサーバの機能と認証サーバの機能を分離した構成をとっている。このような構成にすることにより、認証情報を一元管理し、複数のアクセス手段を用いる場合でも統一的な認証と利用記録の管理が行えるようになっている。

また、当初は固定式のユーザIDとパスワードによる認証のみを想定していたが、現在では、デジタル証明書による認証、OTP(ワンタイムパスワード)認証、バイオメトリクスによる認証などを提供する他の認証サーバに対して認証要求をフォワードすることにより、各種の認証方式が利用できるようにプロトコルが拡張されている。

> **RADIUSの主な仕様**
> RADIUSは RFC 2865(認証)及び RFC 2866(アカウンティング)で規定されており、トランスポートにはUDPを用いる。標準ポートは認証が1812番、アカウンティングが1813番である。アクセスサーバ(NAS:Network Access Server)はRADIUSサーバから見て「RADIUSクライアント」として動作し、両者間では共有シークレット(shared secret)を用いてパスワード属性の秘匿やメッセージの正当性確認を行う。

#### RADIUSの脆弱性

RADIUSでは、過去に次のような脆弱性が発見されている。

- **メッセージダイジェスト処理におけるBOFの脆弱性**
  RADIUSサーバがMD5によるクライアントからのメッセージダイジェストを処理する際に、入力データのサイズをチェックしていないため、BOF(バッファオーバフロー)が発生する可能性があるというもの。この脆弱性により、RADIUSサーバが停止したり、管理者権限を奪われて任意のコードを実行されたりするおそれがある。

- **vendor-lengthの検証を適切に行わないことによるDoSの脆弱性**
  ベンダー特有の属性(Vendor-Specific Attribute)内にあるフィールドであり、属性全体の長さを示すvendor-lengthの検証を適切に行わないというもの。この脆弱性により、vendor-lengthに2以下の値を指定された場合に正しい処理が実行できず、RADIUSサーバが停止してしまうおそれがある。

これらの脆弱性はいずれもRADIUSの仕様によるものではなく、ベンダーが製品に実装する際のバグが原因となっている。現在広く使用されているバージョンでは、いずれも修正されている。

> **BOF(Buffer OverFlow)**
> プログラムが確保したメモリ領域(バッファ)の大きさを超えるデータを書き込むことで、隣接するメモリ領域を破壊する現象。攻撃者に悪用されると、プログラムの異常終了や任意コードの実行につながる。

### 6.7.2 TACACS/TACACS+

TACACS(Terminal Access Controller Access Control System)は、RADIUSと同様に、リモートアクセスにおけるユーザ認証を一元的に行うための認証システムである。もともとはUNIXネットワーク環境向けに開発されたもので、その後、シスコシステムズ社によって拡張版のXTACACS、TACACS+が開発された。

TACACS+は、認証(Authentication)、認可(Authorization)、アカウンティング(Accounting)のいわゆる**AAA**の各機能を分離して提供できる点や、パケットのボディ部全体を暗号化する点(RADIUSではパスワード属性のみを秘匿する)に特徴があり、ネットワーク機器の管理者認証などで利用されている。なお、TACACSとTACACS+の間には互換性はない。

現在広く使用されているのはTACACS+である。また、TACACSがUDPによって認証処理を行うのに対し、TACACS+はTCP(標準ポート49番)によって、より信頼性の高い認証処理を行う。

> **RADIUSとTACACS+の比較**
>
> | 項目 | RADIUS | TACACS+ |
> |------|--------|---------|
> | トランスポート | UDP | TCP |
> | 暗号化の範囲 | パスワード属性のみ | パケットのボディ部全体 |
> | AAAの扱い | 認証と認可を一体的に処理 | 認証・認可・アカウンティングを分離 |
> | 標準化 | IETF標準(RFC 2865 等) | シスコ社が策定(RFC 8907 で情報提供) |

### 6.7.3 Kerberos

Kerberosは、米国マサチューセッツ工科大学(MIT)のアテナプロジェクト(Project Athena)で開発された認証及び暗号化システムである。Kerberosは「Trusted Third Party Authentication(信頼された第三者機関による認証方式)」という考えに基づいており、レルム(realm)と呼ばれる管理領域を、プリンシパル(Principals:レルム内のすべてのクライアント及びサーバの総称)と、信頼される第三者であるKDC(Key Distribution Center:鍵配布センタ)で構成する。

#### 特徴

Kerberosでは、レルムの範囲内において、KDCがサーバへのアクセスを要求するクライアントを認証し、共通鍵で暗号化された有効期限付きのチケットを発行する。クライアントはKDCから発行されたチケットを用いて目的のサーバにアクセスする。レルム内では、サーバとクライアント間での二者間認証は一切行われず、すべてKDCを介した三者間で認証が行われる。

一度TGTを取得すれば、その有効期限内はパスワードを再入力することなく複数のサーバを利用できるため、Kerberosはシングルサインオン(SSO)を実現する仕組みとしても利用されている。

Kerberosは、次の三つのサーバ(機能)から構成される。ただし、実際には、1台のサーバですべての機能を提供する場合が多い。

- **認証サーバ(Authentication Server:AS)**
  KDBに保存されている認証情報に基づいてクライアントを認証し、チケット交付チケット(Ticket Granting Ticket:TGT)を発行する。
- **チケット交付サーバ(Ticket Granting Server:TGS)**
  クライアントから提示されたTGTを検証し、クライアントがアクセスを要求するサーバを利用するためのサービスチケット(Service Ticket:ST)を発行する。
- **Kerberosデータベース(Kerberos Database:KDB)**
  プリンシパル(クライアント及びサーバ)の識別情報や、パスワードから生成した秘密鍵(パスワードハッシュ)などの認証情報を保存する。

> **Kerberos利用上の注意点**
> チケットにはタイムスタンプや有効期限が含まれ、リプレイ攻撃対策に利用されるため、レルム内のKDC・クライアント・サーバ間で時刻を同期させておく必要がある(一般的な許容誤差は5分程度)。また、KDCが停止するとレルム内の認証がすべて行えなくなるため、KDCは単一障害点となりやすく、冗長化などの対策が求められる。

#### Kerberosの認証の仕組み

Kerberosでは、次のような流れで認証が行われる(図参照)。

1. **クライアントがASにTGT発行を要求する(AS-REQ)**
   クライアントがASに対してTGTの発行を要求する。

2. **ASがクライアントを認証し、TGTを発行する(AS-REP)**
   ASはKDBに登録されている情報を参照し、クライアントを認証する。正しく認証が行われた場合には、TGSのパスワードハッシュで暗号化したTGTと、クライアントのパスワードハッシュで暗号化したSession Key(SK1)を発行する。SK1はTGSとクライアント間の通信で使用する。

3. **クライアントがTGSにサービスチケット発行を要求する(TGS-REQ)**
   クライアントはアクセスを要求するサーバの情報等をSK1で暗号化し、TGTとともにTGSに送信してサービスチケット(ST)の発行を要求する。

4. **TGSがサービスチケットを発行する(TGS-REP)**
   TGSはクライアントからの要求を確認し、クライアントがアクセスを要求するサーバとの間で使用するサービスチケット(ST)を発行する。STには、クライアントがアクセスを要求するサーバとの通信で使用するSession Key(SK2)やクライアントの識別情報等が含まれている。STはSK1で暗号化されている。

5. **クライアントがSTを用いて目的のサーバにアクセス要求を行う(AP-REQ)**
   クライアントはSK1で復号してSTを取り出し、アクセス先のサーバに送る。

6. **サーバがクライアントのアクセスを許可する(AP-REP)**
   サーバがクライアントからのSTを確認し、アクセスを許可する。必要に応じて、サーバからクライアントへ応答を返すことで、サーバとクライアントの相互認証も行われる。

```
図:Kerberosによる認証の仕組み

 ┌──────────── レルム(KDCが管理する範囲) ────────────┐
 │                                                        │
 │   ┌──────────── KDC ────────────┐                     │
 │   │  AS  ─── KDB ───  TGS       │                     │
 │   └──▲──┬──────────────▲──┬─────┘                     │
 │  ①AS-REQ│②AS-REP  ③TGS-REQ│④TGS-REP                   │
 │      │  ▼              │  ▼                            │
 │   ┌──┴────────────────┴──┐   ⑤AP-REQ   ┌────────┐   │
 │   │    クライアント       │ ──────────▶ │ サーバ │   │
 │   │                       │ ◀────────── │        │   │
 │   └───────────────────────┘   ⑥AP-REP   └────────┘   │
 └────────────────────────────────────────────────────────┘
```

### 6.7.4 ディレクトリサービス

ディレクトリサービスとは、ユーザID、パスワード、所属などのユーザ情報や、ファイル、プリンタなどのネットワーク資源の情報を一元的に管理し、利用者やアプリケーションからの検索・参照要求に応じてそれらの情報を提供するサービスである。代表的な製品として、Windows環境のActive Directoryや、オープンソースのOpenLDAPなどがある。

#### ディレクトリサービス導入の利点

従来のように、認証を行う複数のサーバ上でそれぞれ別個にユーザ情報が管理されていると、ユーザは認証を行うシステムの数だけ認証情報を管理しなければならないため、それが業務遂行上の大きな妨げとなってしまう可能性がある。その結果、パスワードなどの認証情報の管理がずさんになり、システム全体を脆弱な状態にしてしまうおそれもある。さらに、ユーザの異動や転入などに伴うユーザ情報の登録・更新処理が煩雑になり、作業ミスや抜けなどによる問題が発生しやすくなる。

ディレクトリサービスを導入することで、次の効果が得られる。

- ユーザ情報が一元管理されることにより、ユーザは管理する認証情報を集約することが可能となるため、業務効率の向上につながる。これにより、シングルサインオンによる認証システムに移行しやすくなる
- ユーザ情報の登録・更新作業を効率的かつ確実に行うことが可能となる

#### ディレクトリサービスの仕組み

ディレクトリサービスを提供するサーバをディレクトリサーバ、もしくはLDAPサーバと呼ぶ。ディレクトリサーバは、人、サーバ、各種資源などに関する情報(エントリ)をツリー構造(DIT:Directory Information Tree)で管理する。

LDAP(Lightweight Directory Access Protocol)は、ディレクトリサービスにアクセスするプロトコルとして広く使われている。LDAPはITU-T勧告のX.500を簡略化したものであり、標準でTCPポートの389番を使用する。X.500は、ITU-Tが定めたディレクトリサービスに関する規格であり、通信プロトコルとしてDAP(Directory Access Protocol)が規定されている。

```
図:ディレクトリサービスのイメージ

                    dc=example,dc=co,dc=jp
                    ┌─────────┴─────────┐
               ou=People             ou=Resources
             ┌─────┴─────┐          ┌─────┴─────┐
         uid=tanaka   uid=suzuki  cn=printer01  cn=server01
       (氏名・所属・  (氏名・所属・ (設置場所・  (IPアドレス・
        パスワード等)  パスワード等)  機種等)     用途等)

  各種サーバ・アプリケーション ──(LDAP:TCP/389)──▶ ディレクトリサーバ
```

> **LDAPS**
> LDAPの通信は標準では暗号化されないため、認証情報を扱う場合にはSSL/TLSで保護したLDAPS(TCPポート636番)や、StartTLSによる暗号化を利用することが推奨される。

> **Column:Windows Active Directory に対する攻撃**
>
> Active Directory(AD)は、Windows環境におけるディレクトリサービスシステム(ドメインコントローラー)である。ADでは、標準的な認証システムとしてKerberosが実装されている。
>
> Windows環境において、ADは認証情報やシステムリソース情報などを管理する重要なシステムであるため、サイバー攻撃の対象となりやすい。攻撃者は、ADのドメイン管理者権限を奪取できれば、当該ADが管理するドメインにおいて全能の存在となれるため、これを取得すべく様々な攻撃を仕掛ける。ADに対する主な攻撃として、次のような手法が知られている。
>
> - **Pass the Hash**
>   2.4.4項のColumnで解説している攻撃である。設定によるが、通常Windowsでは、PCを社外に持ち出した場合など、PCがADと通信ができない状態であってもドメインアカウントによる認証が行えるようにするため、ハッシュ化されたパスワードがキャッシュに保存されている。Pass the Hashは、このハッシュ化されたパスワードを不正に取得し、平文のパスワードを知らなくても、そのハッシュ値を用いて認証を突破する攻撃であり、攻撃用のツールも出回っている。Pass the Hashにより、攻撃者がドメイン管理者のグループに所属しているアカウントのパスワードハッシュを盗むことに成功すれば、ADを自在に操作することが可能になる。
> - **Pass the Ticket**
>   端末のメモリ上に保存されているKerberosのチケット(TGTやST)を窃取し、それを再利用することで正規ユーザになりすまして各種サーバにアクセスする攻撃である。
> - **Golden Ticket**
>   TGTの暗号化に使用されるkrbtgtアカウントのパスワードハッシュを窃取し、任意の権限・有効期限をもつTGTを偽造する攻撃である。偽造されたTGT(ゴールデンチケット)を用いれば、ドメイン内のあらゆるリソースに長期間アクセスできてしまう。対策として、krbtgtアカウントのパスワードを2回連続で変更してハッシュを無効化するといった措置がとられる。
> - **Silver Ticket**
>   特定のサービスアカウントのパスワードハッシュを窃取し、そのサービス向けのSTを偽造する攻撃である。KDCを経由しないため、検知が難しいとされる。

### 6.7.5 EAP

EAP(Extensible Authentication Protocol)とは、PPPの認証機能を強化・拡張したユーザ認証プロトコルである。EAPはIEEE 802.1X規格を実装した標準的な認証プロトコルとなっており、無線LAN環境のセキュリティを強化する技術として普及しているほか、有線LANにおいてもクライアントの正当性や安全性を認証する技術として普及している。

> **PPP(Point-to-Point Protocol)**
> 2点間のノードを接続するためのデータリンク層のプロトコル。電話回線やシリアル回線などで接続された二つのノード間において、ユーザ認証やネットワーク層プロトコルの設定、誤り検出などを行い、様々なネットワーク層プロトコルのデータ転送を可能にする。PPPの認証プロトコルとしては、PAP(Password Authentication Protocol)やCHAP(Challenge Handshake Authentication Protocol)がある。

#### IEEE 802.1Xとは

IEEE 802.1Xとは、IEEEによって策定された、ネットワーク環境においてユーザ認証を行うための規格である。もともとは有線LAN向けの仕様として策定が進められたが、その後EAPとして実装され、現在では無線LAN(IEEE 802.11x)環境における認証システムの標準仕様として広く利用されている。IEEE 802.1Xは次の図のように、階層構造のプロトコルスタックの組合せからなる。EAPは、複数種類のネットワーク(データリンク層)と、複数種類のアプリケーション(認証方式)とをつなぐ役割を担っている。

> **IEEE(The Institute of Electrical and Electronics Engineers)**
> 米国に本部を置く電気電子技術者協会。LAN関連の規格(IEEE 802シリーズ)をはじめ、電気・電子・情報通信分野の様々な標準規格を策定している。

```
図:IEEE 802.1Xのプロトコルスタック

 ┌──────────────────────────────────────────┐
 │ Authentication層  TLS │ TTLS │ PEAP │ MD5 │ S/Key … │
 ├──────────────────────────────────────────┤
 │ EAP層        EAP(Extensible Authentication Protocol) │
 │              EAPOL(Extensible Authentication Protocol over LAN)│
 ├──────────────────────────────────────────┤
 │ データリンク層  PPP │ IEEE 802.3(有線LAN)│ IEEE 802.11(無線LAN)│
 └──────────────────────────────────────────┘
```

なお、IEEE 802.1Xに準拠した認証システムは、次の三つの要素から構成される。

- **サプリカント(Supplicant)**:認証を要求するクライアント側の装置やソフトウェア
- **認証装置(Authenticator:オーセンティケータ)**:アクセスポイントやLANスイッチなど、認証の窓口となる機器
- **認証サーバ**:RADIUSサーバなど、実際に認証を行うサーバ

認証サーバにRADIUSを用いる場合には、オーセンティケータがRADIUSクライアントとなる。IEEE 802.1Xでは、前掲の図に示すように各層において様々なプロトコルが用いられる。各層の概要について解説しておこう。

- **データリンク層**
  EAP層とデータリンク層との間ではEAPOL(EAP over LAN)プロトコルが使用される。これは、LAN上にあるサプリカントシステム(クライアント)と認証装置との間でEAPパケットをやり取りするためのプロトコルである。なお、認証装置と認証サーバとの間では、EAPメッセージはRADIUSパケットにカプセル化されて転送される。
- **EAP層**
  アプリケーション層の各種認証プロトコルとのインタフェースとなるEAPと、EAPOLからなる。
- **Authentication層**
  認証を行う各種プロトコル(TLS、MD5、S/Keyなど)。

> **試験に出る**
> 情報セキュリティスペシャリスト試験や情報処理安全確保支援士試験の午後問題では、EAPやIEEE 802.1Xを用いた無線LAN認証に関する問題が出題されている。

#### EAPがサポートしている認証方式

EAPは、MD5によるチャレンジレスポンス、TLS、S/Keyなど様々な認証方式に対応している。主な方式の概要を次の表に示す。

表:EAPがサポートしている認証方式

| 名称 | 概要 | サーバ認証 | サプリカントの認証 |
|------|------|:---:|------|
| EAP-TLS | サーバ・サプリカントでTLSによる相互認証を行う方式。認証成立後には、TLSのマスタシークレットを基にユーザごとに異なる暗号鍵を生成・配付し、定期的に変更するため、無線LANのセキュリティを高めることができる | ○(デジタル証明書) | デジタル証明書 |
| EAP-TTLS(EAP-Tunneled TLS) | TLSによるサーバ認証によってEAPトンネルを確立後、そのトンネル内で様々な方式を用いてサプリカントを認証する。EAP-TLSと同じ仕組みにより、無線LANのセキュリティを高めることができる。標準的に対応しているクライアントOSがないため、別途サプリカントソフトウェアが必要となる | ○(デジタル証明書) | 各種方式から選択(オプション) |
| PEAP(Protected EAP) | 認証の仕組みはEAP-TTLSとほぼ同じだが、サプリカントの認証はEAP準拠の方式に限られる。EAP-TLS、EAP-TTLSと同じ仕組みにより、無線LANのセキュリティを高めることができる | ○(デジタル証明書) | EAP準拠の方式から選択(オプション) |
| EAP-MD5 | MD5によるチャレンジレスポンス方式によってパスワードを秘匿化し、サプリカントの認証のみを行う方式。無線LANでの使用には向かない(有線LAN向き) | × | MD5によるチャレンジレスポンス |

EAP-TLSは、認証サーバ(RADIUSサーバ)とクライアント(サプリカント)の双方がデジタル証明書による相互認証を行う方式である。

EAP-TTLSとPEAPはほぼ同様な方式であり、まず第1段階でデジタル証明書によるサーバ認証を行い、暗号化されたEAPトンネルを確立する。第2段階で、安全なEAPトンネルを用いてサプリカントを認証する。サプリカントの認証には、チャレンジレスポンス方式(MS-CHAPv2など)が用いられることが多いが、それに限らず、デジタル証明書による認証をはじめ、様々な方式が選択可能である。

EAP-TLS、EAP-TTLS、PEAPに共通する特徴は次のとおりである。

- デジタル証明書によって認証サーバの正当性を確認できるため、偽の認証サーバ(偽アクセスポイント)によるなりすましを防止できる
- TLSによって認証プロセスそのものが暗号化されるため、認証情報の盗聴を防止できる
- 認証成立後に、ユーザごと・セッションごとに異なる暗号鍵を動的に生成・配付できるため、無線LANの通信の安全性を高めることができる

> **TLS(Transport Layer Security)**
> SSL(Secure Sockets Layer)の後継としてIETF(Internet Engineering Task Force:インターネット技術タスクフォース)によって標準化が行われた、トランスポート層におけるセキュリティプロトコル。公開鍵暗号やデジタル証明書を用いたサーバ・クライアントの認証、通信データの暗号化及び改ざん検知の機能を提供するもので、SSLに代わって広く普及している。

一方、EAP-MD5は上表の上の三つの方式とは大きく異なり、MD5によるチャレンジレスポンス方式によってサプリカントの認証のみを行う方式である(認証サーバの正当性の確認は行わない)。認証情報はMD5によって秘匿化されるが、認証プロセスそのものは暗号化されず、暗号鍵の生成も行わないため、無線LANでの使用には向かない。

近年、EAPに対応した無線LANブリッジ装置や、LANスイッチ(認証スイッチ)が広く普及している。認証スイッチは、外部から持ち込まれたクライアントPCなどがLANに接続する際に、その正当性や安全性(パッチの適用状況やウイルス定義ファイルの更新状況など)を確認してから正規のLANへの接続を許可するシステム(いわゆる検疫ネットワーク)などで使用されている。

```
図:IEEE 802.1X(EAP)による認証システムの構成

 [サプリカント]      EAPOL       [認証装置]        RADIUS       [認証サーバ]
 (クライアント) ◀──────────▶ (アクセスポイント/ ◀──────────▶ (RADIUSサーバ)
                                認証スイッチ)
                                     │ 認証成功後にポートを開放
                                     ▼
                                [正規のLAN]
```

## 確認問題

### 確認問題1

IEEE 802.1Xで使われるEAP-TLSが行う認証はどれか。

- ア CHAPを用いたチャレンジレスポンスによる利用者認証
- イ あらかじめ登録した共通鍵によるサーバ認証と、時刻同期のワンタイムパスワードによる利用者認証
- ウ デジタル証明書による認証サーバとクライアントの相互認証
- エ 利用者IDとパスワードによる利用者認証

[情報処理安全確保支援士試験・R3]

**●解答・解説**

EAP-TLSは、サーバとクライアント(サプリカント)間で、デジタル証明書による相互認証を行う方式である。EAPは、PPPの認証機能を強化・拡張したユーザ認証プロトコルであり、無線LAN環境のセキュリティを強化する技術として普及しているほか、有線LANにおいてもクライアントの正当性や安全性を認証する技術として用いられている。したがって**ウ**が正解。

### 確認問題2

IEEE 802.1Xにおけるサプリカントはどれか。

- ア 一度の認証で複数のサーバやアプリケーションを利用できる認証システム
- イ クライアント側から送信された認証情報を受け取り、認証を行うシステム
- ウ クライアント側と認証サーバの仲介役となり、クライアント側から送信された認証情報を受け取り、認証サーバに送信するネットワーク機器
- エ 認証を要求するクライアント側の装置やソフトウェア

[情報処理安全確保支援士試験・R6春]

**●解答・解説**

IEEE 802.1Xとは、ネットワーク環境においてユーザ認証を行うための規格である。IEEE 802.1Xに準拠した認証システムは、クライアントであるサプリカント、アクセスポイントやLANスイッチなど認証の窓口となる機器であるオーセンティケータ、認証サーバ(RADIUSサーバなど)から構成される。認証サーバにRADIUSを用いる場合には、オーセンティケータがRADIUSクライアントとなる。したがって**エ**が正解。

なお、アはシングルサインオン、イは認証サーバ、ウはオーセンティケータの説明である。

### 確認問題3

リモートアクセス環境において、認証情報やアカウンティング情報をやり取りするプロトコルはどれか。

- ア CHAP
- イ PAP
- ウ PPTP
- エ RADIUS

[情報処理安全確保支援士試験・R2秋]

**●解答・解説**

問題文に該当するのはRADIUS(Remote Authentication Dial-In User Service)であり、**エ**が正解。RADIUSは、リモートアクセス環境において、利用者の認証情報やアカウンティング情報を一元的に管理し、利用者の認証と利用記録を一元的に行う。

なお、CHAPはチャレンジレスポンス方式による認証プロトコル、PAPは平文のパスワードを送信する認証プロトコルであり、いずれもPPPで用いられる。PPTP(Point-to-Point Tunneling Protocol)は、PPPフレームをIPネットワーク上でトンネリングしてVPNを構築するためのプロトコルである。
