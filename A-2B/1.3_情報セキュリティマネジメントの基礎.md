# レクチャーノート：情報セキュリティ及びITの基礎 ― 1.3 情報セキュリティマネジメントの基礎

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ管理」（知識項目例：ISMS、情報セキュリティ管理策〈組織的管理策、人的管理策、物理的管理策、技術的管理策〉、情報セキュリティリスクアセスメント及びリスク対応 ほか）

## 0. 全体像 ― なぜこの分野を学ぶのか

1.1 と 1.2 で、「何を守るか（情報資産とCIA）」「対策はどう働くか（4つの機能）」「どう考えて対策を選ぶか（設計原則）」を整理しました。しかし、どれほど良い対策を選んでも、それを**誰が決め、誰が実行し、うまくいっているかを誰が確かめ、どう直していくか**が決まっていなければ、対策はすぐに形骸化します。導入直後は守られていたルールが1年後には誰も気にしなくなる、新しいシステムが入ったのにリスク評価が古いまま、という状況は、どの組織でも起こりがちです。

この「対策を組織として回し続ける仕組み」が**情報セキュリティマネジメント**であり、その国際標準が **ISMS**（Information Security Management System）です。本ノートは次の順で進みます。

1. **PDCAサイクル**：情報セキュリティマネジメントの基本エンジンを理解します。
2. **ISMSの規格と認証制度**：ISO/IEC 27001・27002 の構成と、第三者が「この組織のISMSは適切だ」と保証する仕組みを学びます。
3. **ISMSの確立と運用**：実際に組織がISMSを立ち上げ、運用する手順を、ステップごとに追います。

第4章（情報セキュリティマネジメントの実践）ではリスクアセスメント、ポリシ、組織、監査などを個別に深掘りしました。本ノートはそれらを「ISMSという一本の流れ」の中に配置し直す回です。第4章の各ノートを読んだときに「全体のどこにあたるのか」がわかりにくかった人は、本ノートの 3章をその地図として使ってください。

科目Bの4つの業務観点のうち「①情報セキュリティマネジメントの推進又は支援」（方針の策定、リスクアセスメント、リスク対応計画、諸規程の策定、監査）の中核です。科目A-2では、ISO/IEC 27001 と 27002 の役割の違い、管理策の数と分類、リスク対応の選択肢、適用宣言書の記載内容などが定番論点です。

## 1. 情報セキュリティマネジメントとPDCAサイクル

### 1.1 情報セキュリティマネジメントとは

**情報セキュリティマネジメント**とは、「明確な方針や規定に基づいて、組織の情報資産の機密性・完全性・可用性などの特性を適切に維持・管理すること」と定義できます。

ここで「マネジメントシステム」という言葉を押さえておきましょう。JIS Q 27000 ファミリーでは、**マネジメントシステム**を「方針、目的及びその目的を達成するためのプロセスを確立するための、相互に関連する又は相互に作用する、組織の一連の要素」と定義しています。少し難しい表現ですが、要するに「方針を決め、目標を立て、それを達成するための仕事の流れ（プロセス）を、組織の仕組みとして定着させたもの」です。個人の頑張りではなく、**担当者が入れ替わっても回り続ける仕組み**であることがポイントです。

### 1.2 PDCAサイクル ― 継続的改善のエンジン

情報セキュリティマネジメントは、計画・策定（**Plan**）、導入・運用（**Do**）、評価・点検（**Check**）、見直し（**Act**）の4つのステップを繰り返しながら継続的に推進するのが望ましい姿です。各ステップの頭文字をとって**PDCAサイクル**と呼びます。PDCAサイクルは品質管理の分野で生まれた考え方で（提唱者の名からデミングサイクルとも呼ばれます）、情報セキュリティに限らず、品質（ISO 9001）や環境（ISO 14001）など多くのマネジメント手法に共通しています。

情報セキュリティマネジメントに当てはめると、各ステップで行うことは次のとおりです。

| ステップ | 主な活動 | 第4章との対応 |
|---|---|---|
| **Plan**（計画・策定） | 推進計画の立案、リスクアセスメントの実施、情報セキュリティポリシの策定 など | 4.1 リスクアセスメント、4.2 リスク対応、4.3 ポリシの策定 |
| **Do**（導入・運用） | ポリシに基づく対策の実施、教育の実施、システムの正常稼働・不正アクセスの監視 | 4.5〜4.7 資産管理・物理的・人的セキュリティ、4.8 インシデント管理 |
| **Check**（評価・点検） | ポリシ遵守状況の評価、ポリシの適切性の監査 など | 4.10 情報セキュリティ監査 |
| **Act**（見直し） | ポリシの見直し、問題箇所の是正・改善 など | 監査結果を受けた是正処置、マネジメントレビュー |

PDCAの肝は「一周して終わりではない」ことです。Actで見直した結果が次のPlanの入力になり、サイクルが回るたびに管理のレベルが少しずつ上がっていきます（螺旋状に上昇するイメージから「スパイラルアップ」と呼ばれます）。攻撃手法も組織の業務も変わり続ける以上、情報セキュリティ対策も変わり続けなければならない、という考え方の表れです。

## 2. ISMSに関する規格と認証制度

### 2.1 ISO/IEC 27000 ファミリーの全体像

ISMSに関する国際規格は、ISO/IEC 27000〜27007、TR 27008、27010、27011 などからなり、まとめて **ISO/IEC 27000 ファミリー**と呼ばれます。日本ではその一部を JIS 化しています。すべてを覚える必要はありませんが、主な規格の役割は押さえておきましょう。

| 規格 | JIS | 内容 | 位置づけ |
|---|---|---|---|
| ISO/IEC 27000 | JIS Q 27000 | ISMSの概要と**用語**の定義 | 用語集 |
| **ISO/IEC 27001** | JIS Q 27001 | ISMSの**要求事項** | 認証審査の基準（「〜しなければならない」） |
| **ISO/IEC 27002** | JIS Q 27002 | 情報セキュリティ**管理策**の実践の規範 | 管理策の手引き（「〜することが望ましい」） |
| ISO/IEC 27005 | ― | 情報セキュリティリスクマネジメントの指針 | リスクアセスメントの詳細な手引き |
| ISO/IEC 27006 | ― | 認証機関に対する要求事項 | 審査する側のルール |
| ISO/IEC 27017 | JIS Q 27017 | クラウドサービスの情報セキュリティ管理策 | クラウド向けの追加管理策（1.5 参照） |
| ISO/IEC 27018 | JIS Q 27018 | パブリッククラウドにおける個人情報（PII）保護 | クラウド事業者向け |
| ISO/IEC 27701 | ― | プライバシー情報マネジメント（PIMS） | ISMSのプライバシー拡張 |

試験で最も重要なのは、**27001 と 27002 の違い**です。27001 は「ISMSとして何をしなければならないか」という**要求事項**を定めた規格で、認証審査はこれに適合しているかで判定されます。27002 は、27001 の附属書Aに列挙された管理策を「具体的にどう実施するとよいか」を解説した**ガイドライン**です。27002 自体は認証の基準ではありません。

これらの規格文書群に基づく認証制度が **ISMS適合性評価制度**（ISMS認証制度とも呼ばれます）です。

### 2.2 ISO/IEC 27001:2022（JIS Q 27001:2023）の概要と構成

**ISO/IEC 27001**（情報セキュリティ、サイバーセキュリティ及びプライバシー保護－情報セキュリティマネジメントシステム－要求事項）は、組織がISMSを確立し、実施し、維持し、継続的に改善するための要求事項を規定しています。情報セキュリティのリスクアセスメントとリスク対応を行うための要求事項もここに含まれます。2022年10月に改訂されましたが、主な変更は2022年2月に改訂された ISO/IEC 27002 に合わせた**附属書A**（管理策の一覧）の差し替えで、規格本文は2013年版からほとんど変わっていません。旧版（2013年版）の認証は、3年間の移行期間を経て2025年10月末で失効しています。

規格の構成は次のとおりです。

| 箇条 | 内容 | PDCAとの対応 |
|---|---|---|
| 0〜3 | 序文（ISMSの概要）、適用範囲、引用規格、用語及び定義 | ― |
| 4 | 組織の状況（内外の課題、利害関係者のニーズ、ISMSの適用範囲の決定） | Plan の前提 |
| 5 | リーダーシップ（トップマネジメントのコミットメント、方針、役割・責任・権限） | Plan の前提 |
| 6 | 計画（リスクアセスメント、リスク対応、情報セキュリティ目的） | **Plan** |
| 7 | 支援（資源、力量、認識、コミュニケーション、文書化した情報） | **Do** の基盤 |
| 8 | 運用（リスクアセスメント・リスク対応の実施） | **Do** |
| 9 | パフォーマンス評価（監視・測定、内部監査、マネジメントレビュー） | **Check** |
| 10 | 改善（不適合及び是正処置、継続的改善） | **Act** |
| 附属書A | 情報セキュリティ管理策の一覧（93項目） | 管理策選択のチェックリスト |

箇条4〜10がPDCAにきれいに対応していることに注目してください。この構成は、ISOの専門委員会が定めた、マネジメントシステム規格（**MSS**：Management System Standards）の**上位構造**（High Level Structure、現在は Harmonized Structure と呼ばれます）、**共通テキスト**（Identical Core Text）、共通用語・定義に基づいています。

MSS共通テキストの目的は、品質（QMS：ISO 9001）、環境（EMS：ISO 14001）、情報セキュリティ（ISMS）など複数のマネジメントシステムを導入する組織が、それらの整合を図り、負担を減らせるようにすることです。章立てがどの規格でも同じなので、「内部監査は品質と情報セキュリティで合同で実施する」「マネジメントレビューを一本化する」といった**統合運用**がしやすくなります。

また、情報セキュリティリスクアセスメントとリスク対応のプロセスは、リスクマネジメントの汎用規格である **ISO 31000**（リスクマネジメント－原則及び指針、JIS Q 31000）に整合するように作られています。

### 2.3 ISO/IEC 27002:2022（JIS Q 27002:2024）の概要と構成

**ISO/IEC 27002**（情報セキュリティ、サイバーセキュリティ及びプライバシー保護－情報セキュリティ管理策）は、組織がISMSを実践するための規範となる文書（ガイドライン）で、2022年2月に改訂されました。

2022年の改訂では、従来の14のカテゴリが次の**4つ**に再編されました。1.1 で見た対策の分類と同じ切り口です。

| 分類 | 管理策数 | 主な内容 |
|---|---|---|
| **組織的管理策** | 37 | 情報セキュリティのための方針群、役割・責任、資産の管理、アクセス制御の方針、供給者関係、インシデント管理、事業継続、法令遵守 など |
| **人的管理策** | 8 | 選考、雇用条件、教育・訓練、懲戒手続、雇用終了後の責任、秘密保持契約、リモートワーク、事象の報告 |
| **物理的管理策** | 14 | 物理的セキュリティ境界、入退室、オフィスの保護、クリアデスク・クリアスクリーン、装置の保護・処分 など |
| **技術的管理策** | 34 | エンドポイント機器、特権的アクセス権、認証、マルウェア対策、ログ取得、ネットワークセキュリティ、暗号、セキュアコーディング など |

従来114個あった管理策も見直され、**93個**になりました。個数は減っていますが、内容が削除されたわけではなく、重複していた管理策が集約された結果です。一方で、時代の変化に合わせて**新たに11の管理策**が追加されています。

| 新規管理策（2022年版） | 追加の背景 |
|---|---|
| 脅威インテリジェンス | 攻撃の情報を集めて先回りする必要性 |
| クラウドサービス利用における情報セキュリティ | クラウド利用の一般化（1.5 参照） |
| 事業継続のためのICTの備え | ICTの停止が事業停止に直結 |
| 物理的セキュリティの監視 | 監視カメラ等による継続的な監視 |
| 構成管理 | 設定ミスによる事故の多発 |
| 情報の削除 | 不要になった情報の確実な消去 |
| データマスキング | 開発・分析時の個人情報保護 |
| データ漏えい防止 | DLPの普及（1.7 参照） |
| 監視活動 | 異常な振る舞いの検知 |
| ウェブフィルタリング | 悪性サイトへのアクセス防止 |
| セキュアコーディング | 脆弱性の作り込み防止（第8章） |

さらに2022年版では、各管理策に**属性**（タグ）が付けられました。たとえば「管理策の種類」という属性は「予防・検知・是正」の3値をとり、1.2 で学んだ対策の機能（予防・防止、検知・追跡、回復）と同じ発想です。ほかにも「情報セキュリティ特性（C・I・A）」「サイバーセキュリティ概念（識別・防御・検知・対応・復旧）」といった属性があり、1つの管理策をさまざまな切り口から検索・整理できるようになっています。

### 2.4 ISMS適合性評価制度 ― 第三者による「お墨付き」

**ISMS適合性評価制度**は、組織のISMSが規格に適合していることを第三者が審査し、認証する制度です。取引先から「御社の情報管理は大丈夫ですか」と聞かれたとき、自己申告ではなく第三者の認証を示せることに価値があります。官公庁の入札や、大手企業との取引で認証取得を条件にされることも少なくありません。

制度の沿革は次のとおりです。2001年4月にパイロット運用として開始され（当初は国内制度の位置づけ）、1年間は申請できる業種が情報処理サービス業に限られていました。2002年4月にこの制限がなくなり、本格運用が始まりました。2006年には ISO/IEC 27001・27002 の JIS 化に伴い、国際的な制度に移行しています。運営は当初 JIPDEC（日本情報経済社会推進協会）が担っていましたが、2018年からは同協会から独立した**一般財団法人情報マネジメントシステム認定センター（ISMS-AC）**が主管しています。

制度の運用体制は、「**認定**」と「**認証**」という2つの言葉の違いを押さえると理解しやすくなります。

| 役割 | 担い手 | 何をするか |
|---|---|---|
| **認定機関** | ISMS-AC | 認証機関・要員認証機関が適切に業務を行えるかを審査し、**認定**する |
| **認証機関** | ISMS-ACから認定を受けた審査機関 | 組織のISMSが JIS Q 27001（ISO/IEC 27001）に適合しているかを審査し、**認証**する |
| **要員認証機関** | ISMS-ACから認定を受けた機関 | 審査員に資格を付与する |
| 申請組織 | 企業・団体など | 認証機関の審査を受ける |

つまり「認定機関が認証機関を認定し、認証機関が組織を認証する」という二段構えで、審査の質を担保しているわけです。

審査の流れは、おおむね次のようになっています。まず申請を受けた認証機関が、**第一段階審査**で文書類やISMSの構築状況を確認し、**第二段階審査**で実際にISMSが有効に運用されているかを現地で確認します。その結果をもとに認証の可否が判定され、登録されます。

ISMS認証は一度取得すれば終わりではなく、その後もマネジメントシステムが適切に機能し続けることが求められます。そのため、半年から1年に1回の頻度（認証機関によって異なる）で**継続審査**（サーベイランス審査）を受け、**3年に1回**は**更新審査**（再認証審査）を受けなければなりません。これはPDCAサイクルが本当に回っているかを、外部の目で定期的に確かめる仕組みだといえます。

## 3. ISMSの確立と運用 ― 組織は実際に何をするのか

ここからは、ISO/IEC 27001 の要求事項に従って組織がISMSを立ち上げ、運用する流れを追います。第4章の各ノートで学んだことが、どのステップで登場するかを意識しながら読んでください。

### 3.1 ISMS確立までの10ステップ

ISMSの確立は、準備（ステップ0）から適用宣言書の作成（ステップ9）までの10ステップで進みます。

| ステップ | 内容 | ひとことで言うと |
|---|---|---|
| 0 | ISMS認証取得に向けた準備 | 体制と日程を決める |
| 1 | ISMSの適用範囲及び境界の定義 | どこを守るか |
| 2 | 情報セキュリティ方針の確立 | 何を目指すか |
| 3 | リスクアセスメントに対する取組み方の決定 | どう測るか |
| 4 | リスクの特定 | 何が起こりうるか |
| 5 | リスクの分析及び評価 | どれくらい危ないか |
| 6 | リスク対応のための選択肢の特定及び評価 | どう手を打つか（方向性） |
| 7 | リスク対応のための管理策の決定 | 具体的に何をするか |
| 8 | 残留リスクの受容についてリスク所有者の承認を得る | 残ったリスクを誰が引き受けるか |
| 9 | 適用宣言書の作成 | 選んだ管理策とその理由を宣言する |

「範囲→方針→測り方→特定→分析・評価→対応→承認→宣言」という流れは、第4章 4.1〜4.2 のリスクマネジメントのプロセスそのものです。以下、ステップごとに要点を見ていきます。

### 3.2 ステップ0〜2：体制・範囲・方針を固める

**ステップ0：ISMS認証取得に向けた準備**では、まず推進組織を作ります。推進組織の責任者は、人材や予算などの経営資源を割り当てる**権限**をもっている必要があります。権限のない担当者が推進役になると、各部門に協力を依頼しても動いてもらえないからです。構成メンバーは、セキュリティの専門家よりも、**対象業務の経験が豊富な社員**が望ましいとされます。リスクを洗い出すには、現場の業務と情報の流れを熟知していることが欠かせないためです。あわせて、認証取得までのスケジュールと、審査を依頼する認証機関（審査登録機関）を決めます。

**ステップ1：ISMSの適用範囲及び境界の定義**では、事業の特徴、組織、所在地、情報システム、情報の種類などの観点から、ISMSを適用する範囲を明確にします。ISMS適合性評価制度では、会社全体でなくても、特定の事業（サービス）、組織（部門）、拠点（事務所、フロア）などの単位で認証を取得できます。範囲の内外の境界は、組織図、レイアウト図、ネットワーク構成図、システム構成図などを使って明確にします。適用範囲から除外する部分については、その詳細と除外が正当である理由を明らかにしておく必要があります。

範囲を狭くすれば認証は取りやすくなりますが、取引先が期待する業務が範囲外なら、認証をもっていても安心材料になりません。「その認証は、自分たちが委託する業務をカバーしているか」を確認することは、委託元の立場で重要な視点です（第4章のサプライチェーンの議論にも関係します）。

**ステップ2：情報セキュリティ方針の確立**では、**トップマネジメント**（経営層）が、組織の情報セキュリティ活動の方向性や、事業に関連する法令・規制・契約上のセキュリティ義務を考慮したうえで、情報セキュリティ方針を確立します。方針には、適用される要求事項を満たすことへの**コミットメント**（責任をもって取り組むという約束）を含める必要があります。ISO/IEC 27001 の箇条5（リーダーシップ）が求めているのは、まさにこの「経営層が自ら方針を示し、責任を引き受けること」です。

### 3.3 ステップ3〜5：リスクを測る

**ステップ3：リスクアセスメントに対する取組み方の決定**では、ISMSの要求事項、事業上のセキュリティ要求、法令・規制などに適したリスクアセスメントの方法を決めます。あわせて、トップマネジメントが**リスクの受容基準**（どのレベルまでならリスクを受け入れるか）と、リスクアセスメントの実施基準を承認します。受容基準を先に決めておかないと、後のステップ5で「このリスクは対応が必要か」を判断できません。

**ステップ4：リスクの特定**では、機密性・完全性・可用性の喪失によって情報資産にどのような影響が出るかといった観点から、リスクを洗い出します。

**ステップ5：リスクの分析及び評価**では、ステップ4で洗い出したリスクの特質を理解し、そのレベル（**リスクレベル**）を算定します。そのうえで、ステップ3で決めた受容基準に照らし、各リスクを受容できるか、対応が必要かを判断します。1.2 で見た「資産価値×脅威×脆弱性」のような式や、「発生可能性×影響度」のマトリクスがここで使われます。具体的な手法（ベースラインアプローチ、詳細リスク分析、組合せアプローチ等）は第4章 4.1 を参照してください。

### 3.4 ステップ6〜7：リスクに手を打つ

**ステップ6：リスク対応のための選択肢の特定及び評価**では、次の選択肢を検討します。

| 選択肢 | 内容 | ISO 31000 等での呼び方 | 例 |
|---|---|---|---|
| **リスクコントロール**（管理策の適用） | 適切な管理策を講じて、リスクの影響や発生可能性を小さくする | リスク低減（修正） | 暗号化の導入、アクセス制御の強化 |
| **リスクの受容** | 対策をとらず、リスクをそのまま受け入れる | リスク保有 | 影響が小さく、対策費用が見合わないリスクを受け入れる |
| **リスクの回避** | リスクの発生要因そのものを排除し、リスクが発生する可能性をなくす | リスク回避 | 危険なサービスを提供しない、個人情報を保持しない |
| **リスクの移転** | 保険や契約などを通じて、リスクを組織の外部（第三者）に移す | リスク共有 | サイバー保険への加入、運用の外部委託 |

「受容」は「放置」とは違います。リスクを認識し、受容基準に照らして意図的に受け入れる判断をした、という点が重要です。また「移転」の注意点として、外部委託でリスクの一部を移すことはできても、**説明責任や信用失墜という影響まで移せるわけではない**ことも押さえておきましょう。委託先から情報が漏れても、顧客から責任を問われるのは委託元です。

**ステップ7：リスク対応のための管理策の決定**では、ステップ6で選んだ選択肢を実施するのに必要な管理策をすべて決めます。決めた管理策は、ISO/IEC 27001 の**附属書A**に示されている管理策と比較し、必要な管理策の見落としがないかを検証します。附属書Aは「この中から選べ」というカタログではなく、「自分たちで決めた管理策に抜けがないか確かめるチェックリスト」として使うのが正しい理解です。

あわせて、管理策の適用によって低減されるリスクと、適用しても残る**残留リスク**を算出します。選んだ管理策はルールとして文書化し（対策基準・実施手順の策定）、管理策の実施に伴って残すべき文書化した情報（記録、証拠）も明確にします。

### 3.5 ステップ8〜9：承認と宣言

**ステップ8：残留リスクの受容についてリスク所有者の承認を得る**では、ステップ7の結果をもとに**情報セキュリティリスク対応計画**を策定し、残留リスクの受容について**リスク所有者**の承認を得ます。リスク所有者とは、そのリスクを管理する責任と権限をもつ人（多くは該当業務の部門長）です。担当者レベルで「このリスクは残るが仕方ない」と決めてしまうのではなく、責任ある立場の人が明示的に引き受けることが求められています。

**ステップ9：適用宣言書の作成**では、**適用宣言書**（SoA：Statement of Applicability）を作ります。記載する主な項目は次のとおりです。

- 選択した管理目的及び管理策と、それらを選択した理由
- 実施済みの管理目的及び管理策
- ISO/IEC 27001 の附属書Aに規定されている管理策のうち、**適用除外**としたものと、それが正当である理由
- 管理策を実施するための文書化した情報（対策基準、手順書など）
- 管理策の実施に伴う文書化した情報（記録及び証拠）

適用宣言書は、「附属書Aの93項目それぞれについて、採用したか・しなかったか・その理由は何か」を一覧にした文書です。審査員はこれを見て、組織の管理策の選択が妥当かどうかを確認します。「除外した管理策とその正当な理由」を書く点が、試験でよく問われます。

### 3.6 ISMSの導入・運用段階 ― 回し続けるための4つの活動

ISMSを確立したら、いよいよ導入・運用段階（PDCAのDo〜Act）に入ります。主な活動は次の4つです。

**①管理策を実施する**：対策基準と実施手順に従って管理策を実施します。リスクアセスメントの結果によっては、新たに入退室管理システムを導入したり、ネットワーク構成を変更したりするなど、物理環境やシステム環境を大きく変える必要が生じることもあります。

**②ISMSの浸透を図る**：適用対象者全員にISMSを浸透させるための方策を検討・実施します。具体的には、ISMS教育の実施、情報セキュリティポリシや関連文書の周知徹底、定期的な意識向上の啓発活動などです。どれほど立派な規程も、現場が知らなければ存在しないのと同じです。

**③文書化した情報（記録）を管理する**：管理策の実施手順とあわせて、実施した証拠となる記録を文書化した情報として整理します。通常業務の中では記録が残らないもの（不測の事態が発生したときの対応など）については、訓練を実施し、その結果を記録として残すようにします。審査では「やっていること」だけでなく「やったことを示す記録」が求められるためです。

**④内部監査を実施し、問題点を改善する**：ISMSの運用開始から一定期間後に**内部監査**を行い、ISMSの浸透度合いや記録の収集状況などを確認します。そのうえで**マネジメントレビュー**を実施し、問題箇所の改善を図ります。ISMSの運用によって業務に支障が出ていないか、現場から不満が出ていないかも、ヒアリングなどで確認します。その結果、管理策や実施手順の内容に問題があれば該当部分を修正し、運用方法や記録の収集方法に問題があれば改善します。この取組みは、ISMSを常に有効な状態に保つために継続的に行う必要があります。

> **マネジメントレビュー**：経営陣がISMSの妥当性、適切性及び有効性を評価し、改善できる点を特定するために行う一連のレビュー。

ここで、似た言葉を区別しておきましょう。

| 活動 | 実施者 | 目的 |
|---|---|---|
| **内部監査** | 組織内の監査員（監査対象の業務から独立した者） | ISMSが規格と自社のルールに適合し、有効に運用されているかを確認する（第一者監査） |
| **マネジメントレビュー** | トップマネジメント（経営陣） | 監査結果や状況の変化を踏まえ、ISMS全体の方向性と改善点を経営として判断する |
| **認証審査** | 外部の認証機関 | 第三者の立場で規格への適合を審査する（第三者監査） |

また ISO/IEC 27001 の箇条10では、不適合（ルールどおりにできていないこと）が見つかったときに、**修正**（その不適合を応急的に直すこと）だけでなく、**是正処置**（不適合の根本原因を取り除き、再発を防ぐこと）をとることを求めています。たとえば「退職者のアカウントが残っていた」という不適合に対して、そのアカウントを削除するのが修正、人事部門からの退職連絡をアカウント削除の手順に組み込むのが是正処置です。

## 5. 試験対策まとめ（重要ポイント）

### 5.1 知識の確認（科目A-2向け）

- **PDCAサイクル**：Plan（リスクアセスメント・ポリシ策定）→Do（対策実施・教育・監視）→Check（遵守状況の評価・監査）→Act（見直し・是正）。ISO/IEC 27001 の箇条6〜10がPDCAに対応する。
- **ISO/IEC 27001 と 27002**：27001 は認証審査の基準となる**要求事項**、27002 は管理策の実施の**手引き（ガイドライン）**。27002 は認証の基準ではない。
- **27001:2022 の改訂点**：主に附属書A（管理策）の差し替え。本文は2013年版からほぼ不変。MSSの共通構造によりQMS・EMS等との統合運用がしやすい。リスクの部分はISO 31000に整合。
- **27002:2022 の管理策**：14カテゴリ・114項目から、**4分類（組織的37・人的8・物理的14・技術的34）・93項目**へ。脅威インテリジェンス、クラウドサービス利用、データマスキング、DLP、セキュアコーディングなど11項目が新規。
- **認定 と 認証**：ISMS-ACが認証機関を「認定」し、認証機関が組織を「認証」する。
- **審査の周期**：継続（サーベイランス）審査は半年〜1年に1回、更新（再認証）審査は3年に1回。
- **リスク対応の4選択肢**：リスクコントロール（低減）・受容（保有）・回避・移転（共有）。「発生要因の排除＝回避」「保険・委託＝移転」の区別が頻出。
- **附属書Aの使い方**：自ら決めた管理策の見落としを確認するための比較対象。
- **適用宣言書**：選択した管理策と理由、適用除外した管理策と**正当な理由**を記載する。
- **残留リスクの承認者**：リスク所有者。推進担当者ではない。
- **内部監査・マネジメントレビュー・認証審査**：実施者が組織内の監査員・経営陣・外部の認証機関と異なる。

### 5.2 記述式で問われる観点（科目B向け）

- **リスク対応の選択理由**：「なぜ低減ではなく移転（または受容）を選んだのか」を、影響の大きさ・発生可能性・対策コストの観点から説明できるようにしておく。
- **適用範囲の妥当性**：委託先がISMS認証を取得していても、委託する業務が適用範囲に含まれているかを確認すべき、という指摘は事例問題で問われやすい。
- **是正処置の書き方**：不適合に対して「その場の修正」だけでなく「根本原因を取り除く仕組みの変更」を答える。手順・連絡フロー・承認プロセスの改善として書くと具体的になる。
- **経営層の関与**：方針の確立、受容基準の承認、残留リスクの承認、マネジメントレビューなど、どの判断が経営層（またはリスク所有者）の責任かを押さえ、「担当者が独断で決めている」ことを問題点として指摘できるようにする。
- **記録の重要性**：訓練や対応の結果を記録として残すことが、ISMSの有効性を示す証拠になる点を理由として書けるようにする。
