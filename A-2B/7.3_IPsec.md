## 0. 全体像 ― なぜこの分野を学ぶのか

第7章 7.2 では、VPN が「下位層で通信路そのものを守る」技術であり、インターネットVPNを実現する代表的なプロトコルが **IPsec** であることを見ました。本ノートでは、その IPsec の中身に踏み込みます。

IPsec（IP security protocol）は、その名のとおりIP（Internet Protocol）を拡張してセキュリティを高めるプロトコルです。IETFで標準化が進められています。本節では、IPsecを構成するプロトコルや機能、セキュリティ上の留意点などについて解説します。

> **IETF（Internet Engineering Task Force）**
> インターネットで利用される技術の標準化を推進する任意団体です。IETFが策定した技術仕様は、RFC（Request For Comments）として公開されます。IPsecは、RFC 4301をはじめとする一連のRFCで規定されています。

IPsec を学ぶ難しさは、部品が多いことにあります。AH、ESP、IKE、SA、SPD、SPI、ISAKMP、メインモード、クイックモード、NATトラバーサル……と略語が並ぶと、どれが何の役なのか見失いがちです。そこで本ノートでは、IPsec の仕事を次の3段階のストーリーとして整理します。

| 段階 | 何をするか | 担当する部品 | 本ノートの節 |
|---|---|---|---|
| ① 方針を決める | 「どのパケットを、IPsec でどう守るか」をあらかじめ定めておく | SPD（セキュリティポリシーデータベース） | 4節 |
| ② 相手と約束する | 相手を認証し、暗号アルゴリズムと鍵を取り決めて、論理的なトンネル（SA）を作る | IKE（IKEv1／IKEv2）、ISAKMP、SA | 6節・8節 |
| ③ 守って送る | 取り決めた鍵でパケットを暗号化・認証して送る | AH、ESP（トランスポートモード／トンネルモード） | 2節・5節 |

その前提として、1節で IPsec の利用形態を、2節で2つのモードを、3節で IPsec が提供する機能を確認します。7節ではリモートアクセスや NAT 環境で生じる問題とその対策を、9節ではファイアウォールのルールやVPN装置の設定といった運用の実物を扱います。

> **試験対策のポイント**
> IPsecは、情報セキュリティ関連の試験で繰り返し出題されている重要テーマです。午後問題でも、VPNの構成やファイアウォールの設定と組み合わせた形で出題されることがあります。

現行の試験制度では、旧・午後問題に当たるのが科目Bです。科目Bの業務観点では「②企画・設計・開発・運用におけるセキュリティ確保」（アーキテクチャ設計、製品のセキュアな導入）と「③利用におけるセキュリティ対策の適用」（暗号利用と鍵管理、ネットワーク及び機器のセキュリティ管理）に対応します。科目A-2では AH と ESP の機能の違い、トンネルモードで暗号化される範囲、IKE のポート番号が定番です。科目Bでは、拠点間VPNの構成図とファイアウォールのルール表を読み、「IPsec を通すためにどのルールを追加すべきか」「NAT 越しに通信できない原因は何か」「アグレッシブモードを使うリスクは何か」を記述させます。第1章 1.4 で学んだ IPヘッダとプロトコル番号、第5章 5.5 で学んだファイアウォールのルール表と NAPT が、本ノートの土台になります。

## 1. IPsecの概要

### 1.1 IPsecの特徴

IPsecには、次のような特徴があります。

- パケットをインターネット層（ネットワーク層）でカプセル化し、暗号化する
- 上位層のアプリケーションに依存せずに暗号化通信ができる
- VPNゲートウェイ製品などを用いた拠点間通信によるIPsec VPNでは、ユーザは暗号化通信を行っていることを意識する必要がない
- IPv4とIPv6のどちらでも利用できる。IPv6では、当初の仕様では IPsec の実装が必須（MUST）とされていたが、現在は推奨（SHOULD）に改められている（2011年の RFC 6434 による。第1章 1.4 参照）

最後の項目は、原本の教材では「IPv6では、IPsecの実装が必須とされている」と書かれていました。以前はそのとおりでしたが、現在は「推奨」です。また、実装が必須だった当時でも、それは「IPv6 機器が IPsec の機能を備えていること」を求めたものであり、「IPv6 の通信が自動的に暗号化される」という意味ではありません。IPsec で通信を守るには、管理者が SPD や鍵を設定する必要があります。

> **補足**
> SSL/TLSはトランスポート層より上位で動作するため、アプリケーション側の対応が必要になる場合があります。これに対してIPsecはインターネット層で動作するので、TCPやUDPを用いる任意のアプリケーションの通信をまとめて保護できます。

第1章 1.4 で、IPv4 ヘッダには上位プロトコルを示す**プロトコル番号**（IPv6 では次ヘッダ）があり、TCP は 6、UDP は 17、ESP は 50、AH は 51 だと学びました。IPsec を使うと、IPヘッダの次に TCP や UDP ではなく ESP や AH のヘッダが来ます。つまり、IPヘッダのプロトコル番号が 50 や 51 に変わります。これが、後で見るファイアウォールのルールで「ポート番号ではなくプロトコル番号で許可する」理由です。

### 1.2 拠点間接続によるインターネットVPN（IPsec VPN）

IPsec VPNによってセキュアな拠点間接続環境を構築する例を、次の図に示します。

- 各拠点のネットワークにVPNゲートウェイ装置を設置し、接続に必要な設定を行う。ファイアウォールがVPNゲートウェイを兼ねる場合もある
- ファイアウォールでは、IPsecで使用するポートを許可するように設定する（UDP 500番ポート（500/UDP）など）

**図：拠点間接続によるインターネットVPN（IPsec VPN）のイメージ**

```
[拠点A LAN]──[VPNゲートウェイ/FW]══(暗号化トンネル)══[VPNゲートウェイ/FW]──[拠点B LAN]
                          └──────── インターネット ────────┘
```

> **IPsecで許可が必要となる主な通信**
> - 500/UDP：IKE（Internet Key Exchange）による鍵交換
> - 4500/UDP：NATトラバーサル（NAT-T）使用時のIKEおよびESP
> - IPプロトコル番号50：ESP
> - IPプロトコル番号51：AH
>
> ESPとAHはTCPやUDPではないため、ポート番号ではなくIPプロトコル番号で許可を設定します。

この4つは、科目A-2・科目Bの両方で繰り返し問われる最重要の数字です。具体的なルール表の書き方は本ノート9.1 で扱います。

### 1.3 拠点対端末接続によるインターネットVPN（IPsec VPN）

モバイルPCやSOHO（Small Office Home Office）の端末からいったんISPに接続し、インターネットを介して組織のネットワークに接続する場合にも、IPsec VPNを使用できます。その例を次の図に示します。

- 組織内のネットワークにVPNゲートウェイ装置を設置し、拠点間接続と同様に接続に必要な設定を行う
- ファイアウォールについても、拠点間接続と同様に、IPsecで使用するポートを許可するように設定する

この形態では、端末側にIPsecに対応したVPNクライアントソフトウェアを導入する必要があります。また、端末を利用するユーザの認証や、鍵交換のプロセスにおいて留意すべき点があります（詳細は本ノート7節で解説します）。

**図：拠点対端末接続によるインターネットVPN（IPsec VPN）のイメージ**

```
[モバイルPC/SOHO端末(VPNクライアント)]──[ISP]══(暗号化トンネル)══[VPNゲートウェイ/FW]──[組織内LAN]
                                          └──── インターネット ────┘
```

| 観点 | 拠点間接続 | 拠点対端末接続（リモートアクセス） |
|---|---|---|
| トンネルの両端 | VPNゲートウェイ ⇔ VPNゲートウェイ | VPNクライアント（端末） ⇔ VPNゲートウェイ |
| 端末側の準備 | 不要（利用者は意識しない） | VPNクライアントソフトウェアの導入 |
| 相手のIPアドレス | 固定であることが多い | ISP から動的に割り当てられ、毎回変わる |
| 追加で必要な仕組み | 特になし | ユーザ認証（XAUTH／EAP）、アドレスの動的割当て（モードコンフィグ）、NATトラバーサル |

右列の「追加で必要な仕組み」は、すべて「端末が社外を移動し、IPアドレスが毎回変わり、家庭用ルータなどの NAPT の内側にいる」という事情から生まれたものです。7節でひとつずつ見ていきます。

## 2. IPsec VPNにおける二つの暗号化モード

IPsecには、パケットのどの部分を暗号化の対象にするかによって、トランスポートモードとトンネルモードという二つの方法が用意されています。

### 2.1 トランスポートモード

トランスポートモードでは、IPパケットのデータ部分（ペイロード）だけをカプセル化して暗号化し、元のIPヘッダはそのまま使って送信します。

元のIPヘッダは暗号化されないため、送信元と宛先のIPアドレスは第三者から見える状態になります。主に、通信を行う端末同士が直接IPsecで通信する場合（ホスト間のエンドツーエンド通信）に使用します。

**図：トランスポートモードのイメージ**

```
元のパケット  ：[IPヘッダ][TCPヘッダ][データ]
送信パケット  ：[IPヘッダ][IPsecヘッダ][TCPヘッダ][データ][IPsecトレーラ]
                                    └────暗号化の対象────┘
```

### 2.2 トンネルモード

トンネルモードでは、IPヘッダとデータ部分をまとめてカプセル化して暗号化し、そのうえで新たなIPヘッダを付加（カプセル化）して送信します。

VPNゲートウェイ装置による拠点間接続をはじめ、前述の二つの接続形態では、通常はどちらもトンネルモードが使用されています。拠点対端末接続や、モバイル端末によるRAS接続の場合は、個々のクライアント自体にVPNゲートウェイ装置が組み込まれているような形になります。そのため、VPN接続が確立されている間、クライアントには二つのIPアドレスが割り当てられていることになります。一つは本来のクライアントのIPアドレス、もう一つはVPNゲートウェイが新たに付加したIPアドレスです。

**図：トンネルモードのイメージ**

```
元のパケット  ：[IPヘッダ][TCPヘッダ][データ]
送信パケット  ：[新IPヘッダ][IPsecヘッダ][IPヘッダ][TCPヘッダ][データ][IPsecトレーラ]
                                      └────────暗号化の対象────────┘
```

> **RAS（Remote Access Service）**
> 組織外の端末から、電話回線やインターネットなどを経由して組織内のネットワークに接続するためのサービスです。

### 2.3 2つのモードを具体的なアドレスで比べる

「二つのIPアドレス」の意味を、具体的なアドレスで確かめましょう。在宅勤務の社員のノートPCが、ISP から 192.0.2.45 を割り当てられているとします。VPN接続すると、VPNゲートウェイ（203.0.113.1）は社内用のアドレス 172.16.100.23 をこの PC に割り当てます（割当ての仕組みは本ノート7.2 のモードコンフィグ）。PC が社内のファイルサーバ 172.16.2.20 にアクセスするとき、インターネット上を流れるパケットは次のようになります。

```
トンネルモード（リモートアクセス）
┌──────────────────────┬─────┬──────────────────────────────┬──────┬────┐
│新IPヘッダ             │ESP  │元のIPヘッダ                    │TCP+  │ESP │
│送信元 192.0.2.45      │ヘッダ│送信元 172.16.100.23           │データ│トレ│
│宛先   203.0.113.1     │     │宛先   172.16.2.20             │      │ーラ│
│プロトコル番号 50(ESP) │     │                               │      │    │
└──────────────────────┴─────┴──────────────────────────────┴──────┴────┘
 ↑ 経路上の誰からも見える   └──────── 暗号化されて見えない ────────────┘

トランスポートモード（ホスト間で直接 IPsec を使う場合）
┌──────────────────────┬─────┬──────┬────┐
│IPヘッダ               │ESP  │TCP+  │ESP │
│送信元 192.0.2.45      │ヘッダ│データ│トレ│
│宛先   198.51.100.80   │     │      │ーラ│
│プロトコル番号 50(ESP) │     │      │    │
└──────────────────────┴─────┴──────┴────┘
 ↑ 通信の両端のアドレスが見える  └暗号化┘
```

| 観点 | トランスポートモード | トンネルモード |
|---|---|---|
| 暗号化の対象 | 元のIPパケットのペイロード（TCPヘッダとデータ） | 元のIPパケット全体（元のIPヘッダを含む） |
| 新しいIPヘッダ | 付加しない（元のIPヘッダをそのまま使う） | 付加する（送信元・宛先はVPNゲートウェイなど） |
| 経路上から見えるアドレス | 通信の両端（エンドツーエンド）のアドレス | トンネルの両端（VPNゲートウェイ）のアドレス |
| 主な用途 | ホスト間のエンドツーエンド通信、L2TP/IPsec や GRE over IPsec の暗号化 | 拠点間接続、リモートアクセス（RAS 接続） |
| オーバーヘッド | 小さい | 新IPヘッダの分（IPv4 で20バイト）大きい |

トンネルモードでは、攻撃者が経路上で盗聴しても、社内のどの端末（172.16.100.23）がどのサーバ（172.16.2.20）と通信しているかを知ることはできません。これが、組織が拠点間接続でトンネルモードを選ぶ理由です。内部ネットワークのアドレス体系は、攻撃者が侵入後の攻撃対象を絞り込むための貴重な情報だからです。

## 3. IPsecによって提供される機能

IPsecでは、次のような機能が提供されます。①～④は、本ノート5節で解説するAHプロトコルとESPプロトコルのどちらでも使用できます。⑤は、ESPプロトコルの場合にのみ使用できます。

1. **アクセス制御機能**
   パケットフィルタリング方式のファイアウォールと同様に、送信元アドレス、宛先アドレス、宛先ポート番号、プロトコル種別などに基づいて、IPsecを使用するかどうかや、使用する機能（暗号化、メッセージ認証など）を制御できます。

2. **メッセージ認証機能**
   メッセージ認証コード（Message Authentication Code：MAC）を用いて通信データが改ざんされていないかを確認し、完全性を保証する機能です。

3. **送信元の認証機能**
   MACを用いて、データの送信元が正当であることを確認する機能です。

4. **通信データの重複検知機能**
   この機能を使用すると、盗聴した通信データを再送するリプレイアタックを防ぐことができます。

5. **通信データ（ペイロード、ヘッダ情報）の暗号化機能**
   トランスポートモードでは、ペイロードとTCPヘッダだけを暗号化します。トンネルモードでは、ペイロードとTCPヘッダに加えて、元のIPヘッダも暗号化します。

> **MAC（Message Authentication Code）**
> 送信者と受信者が共有する秘密鍵とメッセージから算出する認証用のデータです。IPsecでは、HMAC-SHA-256などのHMAC方式が広く使われています。受信側で同じ計算を行って値が一致すれば、改ざんがないこと（完全性）と、鍵を共有する正当な相手から送られたこと（送信元の認証）を確認できます。

> **リプレイアタック（反射攻撃）**
> 正規の通信データを盗聴して記録し、それをそのまま再送することで、不正に認証を突破したり処理を重複して実行させたりする攻撃です。IPsecでは、パケットごとに付与されるシーケンス番号によって重複を検知し、この攻撃を防ぎます。

5つの機能を、攻撃者の狙いと CIA に結びつけて整理しておきましょう。科目Bで「なぜ IPsec でこの攻撃を防げるか」を書くときの根拠になります。

| 機能 | 防ぐ攻撃（攻撃者は何をするか） | 守る特性 | 使う仕組み | AH | ESP |
|---|---|---|---|---|---|
| ① アクセス制御 | 守るべき通信が平文のまま送られる、不要な通信が通る | 機密性 | SPD のセレクタ | ○ | ○ |
| ② メッセージ認証 | 経路上でパケットの中身を書き換える | 完全性 | MAC（ICV） | ○ | ○ |
| ③ 送信元の認証 | 正規の拠点になりすましてパケットを送り込む | 真正性 | MAC（鍵を共有する相手だけが正しい値を作れる） | ○ | ○ |
| ④ 重複検知 | 盗聴したパケットをそのまま再送する（リプレイアタック） | 完全性 | シーケンス番号とリプレイウィンドウ | ○ | ○ |
| ⑤ 暗号化 | 経路上でパケットを盗聴する | 機密性 | 共通鍵暗号（AES など） | × | ○ |

重複検知の仕組みを少し補います。送信側は SA ごとにシーケンス番号を1から順に増やして付与します。受信側は、すでに受け取った番号を記録しておき（一定の幅の「リプレイウィンドウ」で管理します）、同じ番号のパケットや、ウィンドウより古い番号のパケットが届いたら破棄します。攻撃者がシーケンス番号を書き換えて再送しても、番号は ICV の計算対象に含まれているため、ICV が一致せず破棄されます。

## 4. 方針と約束 ― SPD と SA

### 4.1 IPsecを構成するプロトコルや機能

IPsecは、次のようなプロトコルや機能によって構成されます。0節の表で示した3段階に沿って、まず「方針」を定める SPD と、「約束」の結果である SA から見ていきます。

| 部品 | 一言でいうと | 段階 |
|---|---|---|
| SPD | どのパケットをどう扱うかのルール表 | ① 方針 |
| SA | 相手と取り決めた片方向の論理的なコネクション（トンネル） | ② 約束 |
| SAD | 確立した SA の鍵・アルゴリズム・SPI などを保持するデータベース | ② 約束 |
| IKE | SA を作り、鍵を交換するプロトコル | ② 約束 |
| AH／ESP | 実際にパケットを認証・暗号化するプロトコル | ③ 守って送る |

### 4.2 SPD ― どのパケットをどう扱うか

IPsecでは、パケットの処理に関するルール(セレクタ)をあらかじめSPD(Security Policy Database)に登録しておくことで、次のような制御ができます。SPDは入力用と出力用をそれぞれ作成します。

- パケットを破棄する
- IPsecの機能を適用せずに通過させる
- IPsecの機能を適用して処理する

セレクタでは、パケットの送信元アドレス、あて先アドレス、あて先ポート番号、プロトコル種別などをもとに、次のような設定を行います。

- IPsecの適用有無
- 使用するプロトコル(AH、ESP)
- 使用する転送モード(トランスポートモード、トンネルモード)
- 暗号アルゴリズム
- メッセージ認証のアルゴリズム

> **SPD(Security Policy Database)**
> どのパケットにどのセキュリティポリシーを適用するかを定義したデータベース。実際に確立されたSAの情報(鍵、SPIなど)は、別途SAD(Security Association Database)で管理される。

SPD は、第5章 5.5 で学んだファイアウォールのルール表とよく似ています。上から順に評価され、条件に一致した最初のエントリの処理が適用されます。違いは、動作が「許可／拒否」の2択ではなく、「破棄（DISCARD）／IPsec を適用せず通過（BYPASS）／IPsec を適用（PROTECT）」の3択である点です。本社側 VPN ゲートウェイの出力用 SPD は、たとえば次のような見た目になります。

| No. | 送信元 | 宛先 | プロトコル／ポート | 処理 | 適用内容 |
|---|---|---|---|---|---|
| 1 | 172.16.1.0/24 | 172.16.2.0/24 | any | PROTECT | ESP、トンネルモード（トンネル端点 198.51.100.1 → 203.0.113.1）、AES-256-GCM |
| 2 | 172.16.1.0/24 | any | TCP/443 | BYPASS | IPsec を適用せずインターネットへ |
| 3 | any | any | any | DISCARD | 上記以外は破棄 |

No.1 は「支店宛ての通信は必ず暗号化してトンネルに入れる」という方針です。ネットワーク管理者は、支店宛ての業務通信が平文でインターネットに出ることを防ぐために、このエントリを BYPASS のエントリより上に置くべきです。順序を誤ると、守るべき通信が暗号化されずに送られてしまいます。これが 3節①の「アクセス制御機能」の実体です。

### 4.3 SA ― 相手と取り決めた論理的なトンネル

SA(Security Association)とは、IPsecにおける論理的なコネクション(トンネル)です。IKEv1には、制御用に用いるISAKMP SAと、実際の通信データを送るために用いるIPsec SAがあります。

IKEv1でIPsecゲートウェイ同士が通信を始める際には、最初のフェーズ(フェーズ1)で制御用のISAKMP SAが作られ、次のフェーズ(フェーズ2)でIPsec SAが作られます。ISAKMP SAは双方向で一つ作られます。一方、IPsec SAは片方向の通信ごとに作られるため、送信用と受信用の二つが必要になります。AHとESPを併用する場合は、それぞれについてIPsec SAが作られます。

> **ISAKMP(Internet Security Association and Key Management Protocol)**
> SAの確立や鍵管理の手順・メッセージ形式を規定したプロトコル。

**図:SAのイメージ(VPN端末A — VPN G/W 間)**

| SAの種類 | 方向 |
|---|---|
| ISAKMP SA | VPN G/W ⇔ VPN端末A(双方向) |
| AH用のIPsec SA | VPN端末A → VPN G/W |
| AH用のIPsec SA | VPN G/W → VPN端末A |
| ESP用のIPsec SA | VPN端末A → VPN G/W |
| ESP用のIPsec SA | VPN G/W → VPN端末A |

各IPsec SAは、SPI(Security Parameter Index)という識別子で区別されます。

SA と SPI の関係は、受信側の立場で考えるとわかりやすくなります。VPN ゲートウェイは、多数の端末や拠点と同時に SA を張っています。暗号化されたパケットが届いたとき、ゲートウェイは「どの SA の鍵で復号・検証すればよいか」を知る必要があります。そこで送信側は、AH／ESP のヘッダに SPI（32ビットの番号）を入れて送ります。受信側は、SPI（と宛先アドレス、プロトコル）を手がかりに SAD から該当する SA を引き、鍵とアルゴリズムを取り出します。SAD のエントリは、たとえば次のような見た目です。

```
SAD (本社 VPN G/W, 198.51.100.1)
SPI=0x1a2b3c4d  dir=out  src=198.51.100.1  dst=203.0.113.1  proto=ESP mode=tunnel
                enc=AES-256-GCM  seq=000184a2  lifetime: 3600s / 4GB  (残り 1287s)
SPI=0x9f8e7d6c  dir=in   src=203.0.113.1   dst=198.51.100.1 proto=ESP mode=tunnel
                enc=AES-256-GCM  replay-window=64  lifetime: 3600s / 4GB  (残り 1287s)
```

送信用（out）と受信用（in）で SPI が異なる、つまり片方向ごとに SA がある、ということが読み取れます。また、SA には**寿命**（ライフタイム）が時間とデータ量の両方で設定されており、寿命が尽きる前に新しい鍵で SA を作り直します。同じ鍵で大量のデータを暗号化し続けると、攻撃者が解読の手がかりを得やすくなり、鍵が漏えいしたときの被害も大きくなるためです。

## 5. 守って送る ― AH と ESP

### 5.1 AH ― 認証だけを行うヘッダ

AH(Authentication Header:認証ヘッダ)は、主に通信データの認証(メッセージ認証)に使用するプロトコルであり、通信データを暗号化する機能はありません。メッセージ認証の機能はESPにもあるため、暗号化通信が主目的であればAHを使用する必要はありません。

AHのパケット構成を下図に示します。トランスポートモードでは、IPヘッダとTCPヘッダの間にAHヘッダが挿入されます。一方、トンネルモードでは、元のIPヘッダと、VPNゲートウェイが新たに付加するIPヘッダの間にAHヘッダがセットされます。

**図:AHのパケット構成**

```
通常のTCP/IP通信のときのパケット構成
+----------+-----------+----------+
| IPヘッダ | TCPヘッダ |  データ  |
+----------+-----------+----------+

トランスポートモードのときのAHのパケット構成
+----------+----------+-----------+----------+
| IPヘッダ | AHヘッダ | TCPヘッダ |  データ  |
+----------+----------+-----------+----------+
|<------------- 認証範囲(ICV) ------------->|

トンネルモードのときのAHのパケット構成
+--------------+----------+----------+-----------+----------+
| 新IPヘッダ   | AHヘッダ | IPヘッダ | TCPヘッダ |  データ  |
+--------------+----------+----------+-----------+----------+
|<-------------------- 認証範囲(ICV) -------------------->|
```

AHヘッダのレイアウトを下図に示します。

**図:AHヘッダのレイアウト**

```
0               8               16                              31
+---------------+---------------+-------------------------------+
|   次ヘッダ    | ペイロード長  |             予約              |
+---------------+---------------+-------------------------------+
|              SPI(Security Parameter Index)                   |
+---------------------------------------------------------------+
|                       シーケンス番号                          |
+---------------------------------------------------------------+
|                    認証データ(ICV:可変長)                   |
+---------------------------------------------------------------+
```

ヘッダの各フィールドが、3節の機能とどう対応しているかを確認しましょう。「次ヘッダ」には AH の後ろに続くプロトコルの番号（トランスポートモードなら TCP の 6、トンネルモードなら元のIPヘッダを示す 4〈IPv4〉）が入ります。第1章 1.4 のプロトコル番号が、ここでも使われています。「SPI」は本ノート4.3 で見た SA の識別子、「シーケンス番号」は重複検知（リプレイアタック対策）、「認証データ（ICV）」はメッセージ認証と送信元の認証のための値です。

AHでは、MACを用いてIPヘッダも含めたパケット全体のICV(Integrity Check Value:完全性をチェックするための値)を生成し、AHヘッダの認証データにセットします。ICVの生成に用いるMACの種類(HMAC-SHA-256など)は選択できます。ただし、TTLなど経路上で変化するフィールドはICVの計算対象から除外されます。

このように、AHはパケット全体のICVを使用するため、完全性チェックの精度を高められます。その反面、NATを使用している場合には経路上でIPアドレスが変更されるため、完全性チェックが正常に行えなくなるという問題があります(詳細は本ノート7.3で後述)。

> **MAC(Message Authentication Code)**
> 共通鍵を用いてメッセージから生成する認証用の値。改ざんの検知と送信者の確認に用いる。IPsecではHMACが広く使われる。

### 5.2 ESP ― 暗号化と認証の両方を行う

ESP(Encapsulating Security Payload:暗号化ペイロード)は、通信データの認証(メッセージ認証)と暗号化の両方の機能を提供するプロトコルです。

ESPのパケット構成を下図に示します。ESPでは、AHと異なり、ヘッダ情報に加えてトレーラと呼ばれる情報も付加されます。

トランスポートモードでは、IPヘッダとTCPヘッダの間にESPヘッダが挿入され、ペイロードの後にESPトレーラとICVが付加されます。トンネルモードでは、元のIPヘッダと、VPNゲートウェイが新たに付加するIPヘッダの間にESPヘッダがセットされ、ペイロードの後にESPトレーラとICVが付加されます。

**図:ESPのパケット構成**

```
通常のTCP/IP通信のときのパケット構成
+----------+-----------+----------+
| IPヘッダ | TCPヘッダ |  データ  |
+----------+-----------+----------+

トランスポートモードのときのESPのパケット構成
+----------+-----------+-----------+--------+-------------+-----+
| IPヘッダ | ESPヘッダ | TCPヘッダ | データ | ESPトレーラ | ICV |
+----------+-----------+-----------+--------+-------------+-----+
                       |<-------- 暗号化範囲 ------------>|
           |<------------- 認証範囲 --------------------->|

トンネルモードのときのESPのパケット構成
+------------+-----------+----------+-----------+--------+-------------+-----+
| 新IPヘッダ | ESPヘッダ | IPヘッダ | TCPヘッダ | データ | ESPトレーラ | ICV |
+------------+-----------+----------+-----------+--------+-------------+-----+
                         |<------------- 暗号化範囲 --------------->|
             |<------------------ 認証範囲 ------------------------>|
```

ESPのICVは、ESPヘッダからESPトレーラまでを対象として計算し、IPヘッダは対象としていません。このため、ESPではNAT(アドレスのみの変換)を行ってもICVは影響を受けません。ただし、後述のとおりNAPTは正常に行えないため、対処が必要となります。

**図:ESPのパケットレイアウト**

```
0                               16              24              31
+---------------------------------------------------------------+ --+
|              SPI(Security Parameter Index)                   |   | ESPヘッダ
+---------------------------------------------------------------+   |
|                       シーケンス番号                          |   |
+---------------------------------------------------------------+ --+
|                ペイロードデータ(可変長)                      |
+---------------------------------------------------------------+ --+
|                    パディング(0〜255バイト)                  |   | ESPトレーラ
+-------------------------------+---------------+---------------+   |
|                               | パディング長  |   次ヘッダ    |   |
+-------------------------------+---------------+---------------+ --+
|                    認証データ(ICV:可変長)                   |
+---------------------------------------------------------------+
```

> **パディング**
> ブロック暗号のブロック長に合わせるため、またはペイロード長を隠ぺいするために付加されるデータ。

ESPのレイアウトで注目してほしいのは、「次ヘッダ」がヘッダ側ではなく**トレーラ側**にある点です。次ヘッダは「中身が TCP なのか、元のIPパケットなのか」を示す情報なので、それ自体が中身を推測する手がかりになります。ESP は次ヘッダを暗号化範囲のトレーラに置くことで、経路上の第三者から中身のプロトコルまで隠しています。逆に SPI とシーケンス番号は、受信側が復号する**前**に SA を特定し、リプレイを検査するために使うので、暗号化されていません。

なお現在は、暗号化と認証を1つのアルゴリズムで同時に行う **AES-GCM** のような認証付き暗号（AEAD）が ESP で広く使われています。この場合、暗号アルゴリズムとは別に HMAC を選ぶ必要はありません（第7章 7.1 参照）。

### 5.3 AH と ESP の比較 ― 範囲の違いを一目で

AH と ESP の違いは、「何をするか」と「どこまでを範囲とするか」の2軸で整理します。トンネルモードで並べると、違いがはっきりします。

```
AH（トンネルモード）
[新IPヘッダ][AHヘッダ][元IPヘッダ][TCPヘッダ][データ]
|<──────────────── 認証範囲（新IPヘッダの可変フィールドを除く）──────────────>|
 暗号化：なし（すべて平文）

ESP（トンネルモード）
[新IPヘッダ][ESPヘッダ][元IPヘッダ][TCPヘッダ][データ][ESPトレーラ][ICV]
             |<───────────────── 認証範囲 ─────────────────────────>|
                        |<──────────── 暗号化範囲 ─────────────────>|
 新IPヘッダ：認証も暗号化もされない
```

| 観点 | AH | ESP |
|---|---|---|
| 正式名称 | Authentication Header（認証ヘッダ） | Encapsulating Security Payload（暗号化ペイロード） |
| IPプロトコル番号 | 51 | 50 |
| 暗号化 | できない | できる |
| メッセージ認証・送信元の認証・重複検知 | できる | できる |
| 認証範囲 | IPヘッダを含むパケット全体（TTL など経路上で変化するフィールドを除く） | ESPヘッダから ESPトレーラまで（IPヘッダは含まない） |
| 付加するもの | AHヘッダのみ | ESPヘッダ、ESPトレーラ、ICV |
| NAT（アドレスのみの変換） | ICV が一致しなくなり通信できない | トンネルモードなら問題なし |
| NAPT | 通信できない | そのままでは通信できない（NATトラバーサルで対応） |
| 現在の使われ方 | 暗号化が不要で、IPヘッダまで改ざんを検知したい特殊な場合に限られる | VPN のほぼすべて |

試験で最も問われるのは「AH には暗号化機能がない」と「ESP は IPヘッダを認証範囲に含まない」の2点です。実務では、暗号化が必要な VPN では ESP だけを使うのが一般的で、AH はほとんど使われません。NAT との相性が悪く、ESP で十分に認証できるからです。

## 6. 相手と約束する ― IKEv1

### 6.1 IKEv1の位置づけとパケット構成

IKE(Internet Key Exchange:鍵交換)は、SAの作成や、暗号化に用いる鍵の交換などに使用するプロトコルです。IKEにはバージョン1(IKEv1)とバージョン2(IKEv2)がありますが、両者に互換性はないため、IKEv1とIKEv2の間で通信を行うことはできません。ここでは、主にIKEv1について解説し、IKEv2は本ノート8節で扱います。

なぜ IKE が必要なのでしょうか。ESP で暗号化するには、両端が同じ共通鍵をもっていなければなりません。しかし、その鍵をインターネット上で平文のまま送れば、攻撃者に盗聴されて意味がなくなります。かといって、管理者が拠点ごとに手作業で鍵を設定し、定期的に入れ替えるのは手間がかかり、鍵の使い回しにもつながります。そこで IKE は、**相手を認証したうえで、盗聴されても安全な方法（Diffie-Hellman 鍵交換）で鍵を共有し、定期的に自動で更新する**役割を担います。

IKEv1は独立したプロトコルとして、500/UDPを使用します。IKEv1は、SAと鍵管理の仕様を規定したISAKMP/Oakley(ISAKMP:Internet Security Association and Key Management Protocol)をベースにしており、IKEv1のパケットにはISAKMPヘッダがセットされます。

**図:IKEv1のパケット構成(ISAKMPメッセージフォーマット)**

```
+----------+-----------+---------------+-----------+-----------+-----
| IPヘッダ | UDPヘッダ | ISAKMPヘッダ  | ISAKMP    | ISAKMP    | ...
|          |           |               | ペイロード| ペイロード|
+----------+-----------+---------------+-----------+-----------+-----
```

**ISAKMPヘッダのレイアウト**

```
0               8       12      16              24              31
+---------------------------------------------------------------+
|                 イニシエータCookie(64ビット)                  |
|                                                               |
+---------------------------------------------------------------+
|                 レスポンダCookie(64ビット)                    |
|                                                               |
+---------------+-------+-------+---------------+---------------+
| 次ペイロード  |メジャー|マイナー|  交換タイプ  |    フラグ     |
|               |バージョン|バージョン|          |               |
+---------------+-------+-------+---------------+---------------+
|                         メッセージID                          |
+---------------------------------------------------------------+
|                         全メッセージ長                        |
+---------------------------------------------------------------+
```

**表:ISAKMPペイロードの種類**

| 番号 | ISAKMPペイロード |
|---|---|
| 1 | SAペイロード |
| 2 | Proposalペイロード |
| 3 | Transformペイロード |
| 4 | 鍵交換ペイロード |
| 5 | IDペイロード |
| 6 | 証明書ペイロード |
| 7 | 証明書要求ペイロード |
| 8 | ハッシュペイロード |
| 9 | 署名ペイロード |
| 10 | 乱数(Nonce)ペイロード |
| 11 | 通知ペイロード |
| 12 | 削除ペイロード |
| 13 | ベンダーIDペイロード |
| 14 | 属性ペイロード |

パケットには、IPヘッダ、UDPヘッダ、ISAKMPヘッダ、ISAKMPペイロードの順にデータがセットされます。ISAKMPヘッダのイニシエータとは送信側のホスト、レスポンダとは受信側のホストを意味します（正確には、ネゴシエーションを開始した側がイニシエータ、それに応答する側がレスポンダです）。交換タイプはIKEv1通信の種類を表し、メインモード、アグレッシブモード、クイックモードなどがあります(詳細は後述)。ISAKMPペイロードには上表のような種類があり、通信ごとに必要なものがセットされます。

ヘッダ先頭の**Cookie**は、イニシエータとレスポンダがそれぞれ生成する値で、ISAKMP SA を識別するとともに、送信元を偽装した大量の要求によってレスポンダに重い DH 計算をさせる DoS 攻撃を緩和する役割もあります。また、ISAKMP ペイロードは「次ペイロード」フィールドで数珠つなぎになっており、たとえばメインモードの最初のメッセージは「SAペイロード（その中に Proposal → Transform）」、2往復目は「鍵交換ペイロード＋乱数(Nonce)ペイロード」という組合せになります。

次に、IKEv1の主な機能と動作を示します。

### 6.2 通信相手の認証

次表のいずれかの手段で、通信相手が正当であるかを認証します。

**表:IKEv1で使用可能な通信相手の認証方式**

| 認証方式 | 概要 |
|---|---|
| 事前共有鍵認証(Pre-Shared Key認証) | 通信を行う者同士があらかじめ鍵を共有しておき、それによって相手を認証する方式。最も簡便な方式であり、広く使用されている |
| デジタル署名認証 | 通信を行う者同士が、互いのデジタル署名を検証することで相手を認証する方式。送信者はハッシュペイロードを自身の秘密鍵で暗号化(署名)し、署名ペイロードにセットして送信する。受信者は送信者の公開鍵証明書を用いて署名を検証する。そのため、通信を行う者はあらかじめCA(認証局)から公開鍵証明書を取得しておく必要がある |
| 公開鍵暗号認証 | 通信を行う者同士が相手の公開鍵を入手し、IDペイロードと乱数(Nonce)ペイロードを暗号化して送信する。受信側がそれを自身の秘密鍵で復号することによって相手を認証する方式。公開鍵証明書を使用しないため、デジタル署名認証よりも簡便だが、ほとんど普及していない |
| 改良型公開鍵暗号認証 | 公開鍵で暗号化する部分を乱数ペイロードのみとし、IDペイロードと鍵交換ペイロードは生成した秘密対称鍵を用いて暗号化することで、従来の公開鍵暗号認証の処理を高速化したもの |

実務で使われるのは、事実上、上の2つです。管理者がどちらを選ぶかは、拠点や端末の数と鍵管理の手間で決まります。

| 観点 | 事前共有鍵認証 | デジタル署名認証 |
|---|---|---|
| 事前に必要なもの | 両端で同じ秘密の文字列を設定する | CA が発行した公開鍵証明書と秘密鍵（第7章 7.7） |
| 導入の手軽さ | 手軽（数拠点なら十分） | PKI の準備が必要 |
| 拠点・端末が増えたとき | 相手ごとに鍵を配布・管理する手間が増える。全員で同じ鍵を共有すると、1台の漏えいで全体が危うくなる | CA が証明書を発行するだけでよく、失効も CRL／OCSP で管理できる |
| 漏えい時の影響 | 鍵を知る者は誰でも正規の相手になりすませる | 該当する証明書を失効させればよい |
| 向いている用途 | 少数の拠点間接続 | 多数の端末のリモートアクセス、大規模な拠点間接続 |

### 6.3 フェーズ1とフェーズ2 ― SAの作成と管理の全体像

IKEv1は、①ISAKMP SA、②IPsec SAの順番でSAを作成します。各SAの作成には、パケットの交換方法によって幾つかの交換タイプ(Exchange type)があります。通常、ISAKMP SAの作成にはメインモードかアグレッシブモードが、IPsec SAの作成にはクイックモードが使用されます。ここでは、最も一般的な事前共有鍵(Pre-Shared Key)による認証を前提として、三つのモードの処理の概要を示します。

まず全体の流れを1枚の図で見ておきましょう。フェーズ1で「制御用の安全な通り道（ISAKMP SA）」を作り、フェーズ2でその通り道の中を使って「データ用のトンネル（IPsec SA）」を作る、という2段構えです。

```
 イニシエータ                                              レスポンダ
 (支店 VPN G/W 203.0.113.1)                    (本社 VPN G/W 198.51.100.1)
     │                                                           │
     │ ━━━━━━ フェーズ1：ISAKMP SA の作成（UDP 500） ━━━━━━━━━━ │
     │   メインモード（3往復・6メッセージ）                        │
     │     または アグレッシブモード（1往復半・3メッセージ）       │
     │   ・アルゴリズムの合意 ・DH鍵交換 ・相手の認証              │
     │                    ↓                                       │
     │          ISAKMP SA 確立（双方向で1つ）                     │
     │                                                           │
     │ （リモートアクセスでは、ここで XAUTH・モードコンフィグ）   │
     │                                                           │
     │ ━━━━━━ フェーズ2：IPsec SA の作成（ISAKMP SA で暗号化） ━ │
     │   クイックモード（1往復半・3メッセージ）                    │
     │   ・AH/ESP、暗号・認証アルゴリズム、モードの合意             │
     │                    ↓                                       │
     │          IPsec SA 確立（片方向ごとに1つ＝送信用・受信用）   │
     │                                                           │
     │ ════════ ESP（プロトコル番号50）でデータ通信 ════════════ │
     │                                                           │
     │   IPsec SA の寿命が近づくと、クイックモードで鍵を更新      │
```

| 観点 | フェーズ1 | フェーズ2 |
|---|---|---|
| 作る SA | ISAKMP SA（制御用、双方向で1つ） | IPsec SA（データ用、片方向ごと） |
| 使う交換タイプ | メインモード または アグレッシブモード | クイックモード |
| 主な目的 | 相手の認証、以降の制御通信を守る鍵の共有 | AH／ESP で使う鍵とパラメータの合意 |
| 通信の保護 | 途中まで平文（DH 交換後に暗号化） | 最初から ISAKMP SA で暗号化 |
| 寿命の目安 | 長め（例：8〜24時間） | 短め（例：1時間） |

### 6.4 メインモード

ISAKMP SAの作成に使用します。送信側(イニシエータ)と受信側(レスポンダ)が、次の3往復のパケット交換によってISAKMP SAを作成します。

**図:メインモードによるISAKMP SAの作成イメージ(★は暗号化される部分)**

```
イニシエータ                                         レスポンダ
    | ①[IP][UDP][ISAKMP] 暗号化アルゴリズム、認証方式などの提案  |
    |------------------------------------------------------------>|
    |   [IP][UDP][ISAKMP] 受諾可能なアルゴリズム、認証方式など     |
    |<------------------------------------------------------------|
    | ②[IP][UDP][ISAKMP] DH公開値、イニシエータ乱数              |
    |------------------------------------------------------------>|
    |   [IP][UDP][ISAKMP] DH公開値、レスポンダ乱数                |
    |<------------------------------------------------------------|
    | ③[IP][UDP][ISAKMP] ★イニシエータID、★ハッシュ値          |
    |------------------------------------------------------------>|
    |   [IP][UDP][ISAKMP] ★レスポンダID、★ハッシュ値            |
    |<------------------------------------------------------------|
```

**① ネゴシエーション**

イニシエータがISAKMPパラメータ(暗号化アルゴリズム、ハッシュアルゴリズム、認証方式など)を提案し、レスポンダがその中から受諾可能なパラメータを選択します。

**② 鍵交換**

イニシエータとレスポンダがDiffie-Hellman鍵交換アルゴリズムの公開値(DH公開値)と乱数(Nonce)を交換し、DH秘密鍵(共有秘密)を共有します。さらに、次の四つの秘密対称鍵を生成します。

- SKEYID:他の鍵を生成する基となる鍵(事前共有鍵認証の場合は事前共有鍵から生成)
- SKEYID_d:IPsec SAで使用する秘密対称鍵を生成する際の基となる鍵(SKEYID、DH秘密鍵などから生成)
- SKEYID_a:ISAKMPメッセージ認証用の鍵(SKEYID、SKEYID_d、DH秘密鍵などから生成)
- SKEYID_e:これ以降のISAKMP SAの通信を暗号化するための秘密対称鍵(SKEYID、SKEYID_a、DH秘密鍵などから生成)

> **Diffie-Hellman鍵交換**
> 盗聴される可能性のある通信路上で、互いの公開値を交換するだけで、第三者に知られることなく共通の秘密値を得られる鍵共有方式。

4つの鍵の関係は、「親鍵 SKEYID から、用途別の子鍵を3本作る」と覚えると整理できます。

```
 事前共有鍵 ＋ 両者の乱数 ──▶ SKEYID（親鍵）
                               │ ＋ DH秘密鍵 など
                               ├──▶ SKEYID_d … フェーズ2で IPsec SA の鍵を作る元（derive）
                               ├──▶ SKEYID_a … ISAKMP メッセージの認証用（authentication）
                               └──▶ SKEYID_e … ISAKMP メッセージの暗号化用（encryption）
```

**③ 相手の認証**

IDと認証用のハッシュ値によって相手を認証し、ISAKMP SAが確立します。IDと認証用のハッシュ値はSKEYID_eによって暗号化されます。

ここで認証が成り立つ理由を確認しておきましょう。認証用のハッシュ値は SKEYID を鍵として計算されており、SKEYID は事前共有鍵から作られています。つまり、正しいハッシュ値を作れるのは事前共有鍵を知っている相手だけです。事前共有鍵そのものはネットワークに一度も流れません。

メインモードで事前共有鍵認証を行う場合、③でIDを交換する前に、②の段階で通信相手の事前共有鍵を特定しておく必要があります。これを行うには、通信相手のIPアドレスを手がかりにするしかありません。そのため、③のIDにはIPアドレスしか使用できないという制約があります。

したがって、通信を行うホストのIPアドレスが固定であれば問題ありませんが、モバイル接続のように毎回動的にIPアドレスが設定される環境では事前共有鍵が特定できなくなります。そのため、この組合せ(事前共有鍵認証によるメインモード)は使用できません。これには、次のアグレッシブモードを用いて対処するのが一般的です。

### 6.5 アグレッシブモード

メインモードと同様に、ISAKMP SAの作成に使用します。イニシエータとレスポンダが、次の1往復半のパケット交換によってISAKMP SAを作成します。

**図:アグレッシブモードによるISAKMP SAの作成イメージ(★は暗号化される部分)**

```
イニシエータ                                              レスポンダ
    | ①[IP][UDP][ISAKMP] 暗号化アルゴリズム、認証方式などの提案、     |
    |                     DH公開値、イニシエータ乱数、イニシエータID  |
    |---------------------------------------------------------------->|
    | ②[IP][UDP][ISAKMP] 受諾可能なアルゴリズム、認証方式など、       |
    |                     DH公開値、レスポンダ乱数、レスポンダID、    |
    |                     レスポンダハッシュ値                        |
    |<----------------------------------------------------------------|
    | ③[IP][UDP][ISAKMP] ★イニシエータハッシュ値                    |
    |---------------------------------------------------------------->|
```

**① イニシエータが、ISAKMPパラメータ、DH公開値、ID、認証用乱数を送信**

メインモードとは異なり、秘密対称鍵を生成する前の最初のパケットでIDを送るため、IDは暗号化されません。

**② レスポンダが、受諾するパラメータ、DH公開値、ID、認証用乱数、認証用ハッシュ値を送信**

これにより、イニシエータとレスポンダがDH秘密鍵を共有し、メインモードと同様に四つの秘密対称鍵を生成します。

**③ イニシエータが、認証用のハッシュ値をレスポンダに送信**

これにより相互認証が完了し、ISAKMP SAが確立します。

アグレッシブモードでは、最初のパケットでIDを受け取ったレスポンダが、そのIDを基に事前共有鍵を特定できます。そのため、IDにはIPアドレス以外の情報(FQDNやユーザFQDN(メールアドレス形式)など)を使用できます。したがって、IPアドレスが動的に設定されるモバイルPCなどでも使用することが可能です。

> **アグレッシブモードの注意点**
> IDが平文で送信されるため、メインモードに比べて機密性が低い。また、傍受した認証用ハッシュ値を基に、事前共有鍵へのオフライン辞書攻撃を受けるおそれがある。そのため、十分に長く推測困難な事前共有鍵を設定する必要がある。

オフライン辞書攻撃の因果を、科目Bで書ける形にしておきます。攻撃者は、②のメッセージ（DH公開値、乱数、ID、ハッシュ値がまとめて流れる）を盗聴して記録します。その結果、攻撃者は手元で事前共有鍵の候補を次々に試し、記録したハッシュ値と一致するものを探せます。オンラインの総当たりと違ってVPN装置に試行の記録が残らず、ロックアウトも効かないため、短い鍵や辞書にある単語の鍵はいずれ見つかってしまいます。そこで VPN装置の管理者は、辞書攻撃で推測されないように、十分に長くランダムな事前共有鍵を設定すべきです。より根本的には、アグレッシブモードを避け、デジタル署名認証や IKEv2 を使うべきです。

| 観点 | メインモード | アグレッシブモード |
|---|---|---|
| メッセージ数 | 3往復（6メッセージ） | 1往復半（3メッセージ） |
| ID の保護 | SKEYID_e で暗号化される | 平文で送られる |
| 事前共有鍵認証での ID | IPアドレスのみ | FQDN、ユーザFQDN なども可 |
| 動的IPアドレスの端末 | 事前共有鍵認証では使えない | 使える |
| 主なリスク | 特になし（固定IP の拠点間向き） | ID の漏えい、事前共有鍵へのオフライン辞書攻撃 |

なお、IKEv2ではメインモードとアグレッシブモードが統合され、動的に設定されるIPアドレスにも標準で対応しています。

### 6.6 クイックモード

IPsec SAの作成に使用します。イニシエータとレスポンダが、次の1往復半のパケット交換によってIPsec SAを作成します。この通信は前フェーズで確立したISAKMP SAを使用して行われるため、パケットのペイロード部分は暗号化されます。

また、IPsec SAで使用する秘密対称鍵の生成には、前フェーズで生成したSKEYID_dを使用します。そのため、通常はDiffie-Hellman鍵交換アルゴリズムによる新たな秘密対称鍵の生成は行いません(オプションで新たに鍵を生成することも可能)。

**図:クイックモードによるIPsec SAの作成イメージ(★は暗号化される部分)**

```
イニシエータ                                              レスポンダ
    | ①[IP][UDP][ISAKMP] ★ハッシュ値、★暗号化アルゴリズム、         |
    |                     ★認証方式などの提案、★イニシエータ乱数    |
    |---------------------------------------------------------------->|
    | ②[IP][UDP][ISAKMP] ★ハッシュ値、★受諾可能なアルゴリズム、     |
    |                     ★認証方式など、★レスポンダ乱数            |
    |<----------------------------------------------------------------|
    | ③[IP][UDP][ISAKMP] ★ハッシュ値                                |
    |---------------------------------------------------------------->|
```

**① イニシエータが、IPsec SAのパラメータ、認証用乱数、認証用ハッシュ値を送信**

イニシエータが、IPsec SAで使用するパラメータ(プロトコル(AH/ESP)、暗号化アルゴリズム、認証アルゴリズム、転送モードなど)を提案します。

**② レスポンダが、受諾するパラメータ、認証用乱数、認証用ハッシュ値を送信**

この後、イニシエータとレスポンダは、SKEYID_d、SPI、イニシエータ認証用乱数、レスポンダ認証用乱数などから、IPsec SAで使用する秘密対称鍵を生成します。

**③ イニシエータが、認証用のハッシュ値をレスポンダに送信**

これによりIPsec SAが確立し、以降IPsec通信が可能となります。

なお、セキュリティ確保のため、IPsec通信の開始後もSAは定期的に更新され、両ホスト間で再認証と秘密対称鍵の更新が行われます。

> **PFS(Perfect Forward Secrecy)**
> クイックモードでDH鍵交換を再度行い、新たな秘密対称鍵を生成するオプション。ある時点の鍵が漏えいしても、過去や将来の通信の鍵が推測されないようにできる。

PFS がなぜ効くのかを補足します。PFS を使わない場合、すべての IPsec SA の鍵は同じ SKEYID_d から作られます。攻撃者が何らかの方法で SKEYID_d を手に入れると、記録しておいた過去の通信も、これからの通信も、まとめて復号できてしまいます。PFS を有効にすると、IPsec SA を作るたびに新しい DH 鍵交換を行い、その結果を鍵の材料に加えます。DH の秘密値は使い終わると捨てられるので、ある時点の鍵が漏えいしても他の SA の鍵は推測できません。VPN装置の管理者は、鍵の漏えい時に被害を1つの SA の範囲に限定するために、PFS を有効にすべきです。代償は、鍵更新のたびに DH 計算の負荷がかかることです。

## 7. リモートアクセスにおける留意点及び対策

モバイル機器など、リモートアクセス環境でIPsecを使用する場合には、次のような点に留意する必要があります。本ノート1.3 の表で挙げた「端末が社外を移動する」「IPアドレスが毎回変わる」「NAPT の内側にいる」という3つの事情に、それぞれ対応する仕組みがあります。

| リモートアクセス特有の事情 | 生じる問題 | 対策の仕組み | 本ノートの節 |
|---|---|---|---|
| 端末が社外に持ち出される | 盗難・紛失した端末から不正に接続される | ユーザ認証（XAUTH／IKEv2 の EAP） | 7.1 |
| 社内用のアドレスが端末にない | 社内LANで通信できない | アドレスの動的割当て（モードコンフィグ） | 7.2 |
| 家庭用ルータやホテルの NAPT の内側にいる | ESP が NAPT を通過できない | NATトラバーサル（NAT-T） | 7.3 |

### 7.1 端末機器の不正使用への対策 ― XAUTH

物理的なセキュリティ対策が施された区画内で行う拠点間接続のIPsec通信とは異なり、外出先などのリモートアクセス環境では、モバイルPCの盗難などによって不正にIPsec通信が行われ、社内ネットワークに侵入されるリスクがあります。そのため、リモートアクセス環境でのIPsec通信では、SAの作成時に端末機器を認証(デバイス認証)するだけでなく、端末の使用者も認証(ユーザ認証)する必要があります。IPsecでは、これを行う手段としてXAUTHが広く利用されています。

XAUTHでは、ISAKMP SAの作成フェーズでデバイス認証が行われた後、ユーザIDとパスワードによってユーザ認証を行います(設定によって、チャレンジレスポンス方式やワンタイムパスワード方式による認証なども選択可能)。認証に成功すれば、そのままIPsec SAの作成(クイックモード)に進みます。認証に失敗した場合は通信が遮断されます。

> **XAUTH(Extended Authentication)**
> IKEv1のフェーズ1とフェーズ2の間でユーザ認証を行うための拡張仕様。RADIUSサーバなどと連携して認証を行う構成が一般的である。

攻撃者の視点で因果を整理しましょう。攻撃者は、電車に置き忘れられたノートPCを拾い、VPNクライアントを起動します。PC には事前共有鍵や証明書が保存されているので、デバイス認証は通ってしまいます。その結果、ユーザ認証がなければ、攻撃者は社員と同じように社内ネットワークに入れます。XAUTH でユーザ ID とパスワード（さらにワンタイムパスワード）を求めれば、端末だけを手に入れた攻撃者は接続できません。VPN装置の管理者は、端末の盗難・紛失による不正接続を防ぐために、デバイス認証に加えてユーザ認証を必須にすべきです。

```
[ノートPC] ──フェーズ1（デバイス認証：証明書/事前共有鍵）──▶ [VPN G/W]
           ──XAUTH（ユーザID＋パスワード＋OTP）─────────▶ [VPN G/W] ──問合せ──▶ [RADIUSサーバ]
           ◀────────────────────────── 成功/失敗 ──────────────────────────
           ──フェーズ2（クイックモード：IPsec SA の作成）──▶  ※失敗なら通信を遮断
```

### 7.2 IPアドレスなどの動的な割当て ― モードコンフィグ

リモートアクセス端末がIPsec VPN網に接続して正常に通信を行うには、端末機器に適切なIPアドレスやサブネットマスクなどを動的に割り当てる仕組みが必要です。これを行う手段としては、ISAKMP Configuration Method(モードコンフィグ)が広く利用されています。モードコンフィグでは、次の二つの方式が使用可能です。

- イニシエータが必要な情報をレスポンダに要求し、受け取る方式
- イニシエータが具体的な設定内容をレスポンダに通知し、了解を得る方式

モードコンフィグでは、IPアドレスやサブネットマスクのほか、DNSサーバやWINSサーバのアドレスなども通知できます。これらの情報は、ISAKMPペイロードの属性ペイロードを用いてやり取りされます。

本ノート2.3 で見た「クライアントに二つのIPアドレスが割り当てられる」状態は、このモードコンフィグで作られます。端末の VPN クライアントの状態表示は、たとえば次のような見た目になります。

```
VPN接続状態 : 接続済み (IKEv1 / ESP tunnel)
接続先      : vpn.example.jp (203.0.113.1)
物理アダプタ: 192.0.2.45        ← ISP が割り当てたアドレス（新IPヘッダの送信元）
仮想アダプタ: 172.16.100.23/24  ← モードコンフィグで割り当てられた社内用アドレス
DNSサーバ   : 172.16.1.53
```

### 7.3 NAT、NAPTを使用する際の留意点 ― NATトラバーサル

**なぜ問題が起きるのか**

家庭用ルータやホテルのネットワークは、ほぼ例外なく NAPT（第5章 5.5 の 4.3 で学んだ、IPアドレスとポート番号をまとめて変換する方式）を使っています。NAPT 装置は、TCP/UDPヘッダのポート番号を書き換えることで、1つのグローバルアドレスを複数の端末で共有します。ところが IPsec のパケットでは、ポート番号が暗号化されていたり、IPヘッダが改ざん検知の対象になっていたりするため、NAPT 装置の書き換えとぶつかります。

NATやNAPTを使用するとパケットのヘッダ情報が変更されるため、IPsecで使用するプロトコルやモードによって、それぞれ次の表のような問題が発生します。

**表:IPsecでNAT、NAPTを使用する場合に発生する問題**

| アドレス変換方式 | プロトコル | 転送モード | 問題の有無など |
|---|---|---|---|
| NAT | AH | トランスポートモード | 変換前のIPヘッダを含めてICVが生成されるため、経路上でIPアドレスが変更されるとICVが一致しなくなる |
| NAT | AH | トンネルモード | 同上(新たに付加されたIPヘッダもICVの計算対象となるため、ICVが一致しなくなる) |
| NAT | ESP | トランスポートモード | ・IPアドレスはICVの計算対象外のため、変換されても問題は生じない<br>・IPアドレスの変換に伴ってTCPヘッダのチェックサムを変更する必要が生じるが、TCPヘッダは暗号化されているため変更できない |
| NAT | ESP | トンネルモード | 新たに付加されたIPヘッダについては、アドレスが変換されても特に問題は生じない |
| NAT | IKE | − | アドレスが変換されても特に問題は生じない |
| NAPT | AH | トランスポートモード/トンネルモード | NATと同様の問題が生じる |
| NAPT | ESP | トランスポートモード/トンネルモード | ポート番号はペイロードの一部として暗号化されているため、変換できない。また、ESPヘッダにはポート番号がないため、NAPT装置が複数端末の通信を識別できない |

ESP と NAPT の問題を、NAPT 装置の立場で見てみましょう。

```
 自宅LAN                        家庭用ルータ(NAPT)                  インターネット
 PC1 192.168.1.10 ─┐          グローバル 192.0.2.45
                   ├──▶ [IP 192.168.1.x → 203.0.113.1][ESP: SPI, 暗号化された TCP...]
 PC2 192.168.1.11 ─┘
                     NAPT装置：「ポート番号を書き換えたいが…」
                       ・TCP/UDPヘッダが暗号化されていて見えない・書き換えられない
                       ・ESPヘッダには書き換えられるポート番号がない
                     → 戻りのパケットが PC1 宛てか PC2 宛てか区別できない
```

**解決策：UDPでもう一度包む**

そのため、一般的な製品では、次の図のようにIPsecのパケットに新たなUDPヘッダを追加(カプセル化)して対応する方法が広く用いられています。NAPT装置は追加されたUDPヘッダのポート番号を変換することで、IPsecパケットを中継できるようになります。

なお、この機能は「UDP encapsulation」(RFC 3948)としてIETFで標準化されています。一般には、NATの存在を検出する仕組み(RFC 3947)と合わせてNATトラバーサル(NAT-T)と呼ばれ、4500/UDPが使用されます。

**図:ESPパケットをUDPでカプセル化することによってNAPTに対応する例**

```
通常のTCP/IP通信のときのパケット構成
+----------+-----------+----------+
| IPヘッダ | TCPヘッダ |  データ  |
+----------+-----------+----------+

ESP(トランスポートモード)をUDPでカプセル化したときのパケット構成
+----------+-----------+-----------+-----------+--------+-------------+-----+
| IPヘッダ | UDPヘッダ | ESPヘッダ | TCPヘッダ | データ | ESPトレーラ | ICV |
+----------+-----------+-----------+-----------+--------+-------------+-----+
            ↑ 新たに追加(NAPTはこのポート番号を変換する)
```

リモートアクセスで実際に使われるトンネルモードでも、考え方は同じです。

```
ESP(トンネルモード)をUDPでカプセル化したときのパケット構成
+------------+-----------+-----------+----------+-----------+--------+-------------+-----+
| 新IPヘッダ | UDPヘッダ | ESPヘッダ | IPヘッダ | TCPヘッダ | データ | ESPトレーラ | ICV |
+------------+-----------+-----------+----------+-----------+--------+-------------+-----+
              ↑ 宛先ポート 4500。NAPT装置は送信元ポートを書き換える
```

NAT-T の動きは次のとおりです。IKE は最初 UDP 500 で始まり、フェーズ1の中で互いに「自分から見た送信元・宛先のアドレスとポート」のハッシュ値を交換します。受け取った値と実際のパケットのヘッダが一致しなければ、途中で NAT が書き換えたと判断できます（RFC 3947 の NAT 検出）。NAT が見つかると、両端は以降の IKE と ESP をすべて **UDP 4500** に載せ替えます。さらに、NAPT 装置の変換表のエントリが無通信で消えないよう、端末は定期的に小さなパケット（NAT キープアライブ）を送ります。

| 誰が | 何を | 何のために |
|---|---|---|
| VPN装置の管理者 | NAT-T を有効にする | NAPT の内側にいる端末や拠点からも IPsec で接続できるようにするため |
| ファイアウォールの管理者 | UDP 500 に加えて UDP 4500 を許可する | NAT 検出後に IKE と ESP が UDP 4500 に移るため（許可しないとフェーズ1の途中で失敗する） |
| ネットワーク設計者 | NAT を通る区間では AH を使わず ESP を使う | AH は IPヘッダを認証範囲に含むため、NAT-T を使っても通信できないため |

## 8. IKEv2

### 8.1 IKEv2の概要とSAの種類

ここでは、IKEv2の概要について、主にIKEv1との相違点を中心に解説します。

前述のように、IKEv2は動的に設定されるIPアドレスに標準で対応しています。また、IKEv1の仕様を複雑にする要因となっていた各種の拡張技術(NATトラバーサル、ユーザ認証、アドレスの動的割当て、DPD(Dead Peer Detection)など)を取り込みつつ、仕様を明確かつ簡潔にしています。さらに、SA確立までに必要なメッセージ数も、最小で2往復(4メッセージ)に削減されています(RFC 7296)。

IKEv1 では、XAUTH もモードコンフィグも NAT-T も、後から追加された拡張仕様でした。製品ごとに対応状況が異なり、異なるメーカーの装置どうしでつながらない原因になっていました。IKEv2 はこれらを本体の仕様に取り込んだので、管理者は相互接続性の問題に悩まされにくくなりました。

IKEv2では、次の2種類のSAが使用されます。

- **IKE SA**
  IKEv1のISAKMP SAに相当するもので、通信相手の認証、CHILD SAのネゴシエーション、鍵計算用パラメータの交換などに用いる。ISAKMP SAは通信の上り・下り兼用で、一つのIPsec通信につき一つ生成される。
- **CHILD SA**
  IKEv1のIPsec SAに相当するもので、AH、ESP通信のデータを送るために用いる。

IKE SA の数については、原本の教材では「IKE SAは通信の方向(イニシエータからレスポンダ、レスポンダからイニシエータ)により、一つのIPsec通信で二つ作成される」と説明されていました。しかし RFC 7296 の規定はそうではなく、IKE SA は ISAKMP SA と同じく一つで双方向の制御通信を扱い、送信用・受信用の一対で作られるのは CHILD SA の方です。本ノートでは RFC の規定に従って整理します。

> **補足**
> RFC 7296では、IKE SAは一つで双方向の制御通信を扱い、CHILD SAが送信用・受信用の一対で作成されると規定されている。実装や資料によって説明の仕方が異なる場合があるため、試験対策では出題文の定義に従って解答するとよい。

| IKEv1 | IKEv2 | 役割 | 数（RFC の規定） |
|---|---|---|---|
| ISAKMP SA | IKE SA | 制御用（認証、鍵計算用パラメータの交換） | 双方向で1つ |
| IPsec SA | CHILD SA | データ用（AH、ESP） | 片方向ごとに1つ（送信用・受信用の一対） |

### 8.2 4種類の交換

IKEv2では、イニシエータとレスポンダのメッセージ交換の単位を「交換(Exchange)」と呼んでおり、次の4種類があります。

- **IKE_SA_INIT**
  暗号化方式、認証方式などのネゴシエーションと鍵計算用パラメータの交換を行い、IKE SAを生成する。
- **IKE_AUTH**
  生成されたIKE SAで通信相手を認証するとともに、CHILD SAのネゴシエーションと鍵計算用パラメータの交換を行い、CHILD SAを生成する。なお、IKE_AUTHは必ずIKE_SA_INITに続いて実行される。
- **CREATE_CHILD_SA**
  既にIKE SA、CHILD SAが存在する通信相手と別のCHILD SAを生成する場合や、IKE SA、CHILD SAのリキーを行う場合などに用いる。CHILD SAの生成時には、CHILD SAのネゴシエーションと鍵計算用パラメータの交換を行い、CHILD SAを生成する。なお、リキーとは、イニシエータ、レスポンダそれぞれに設定されたSAのライフタイムが満了する前に、新たな鍵でSAを作り直すことをいう。
- **INFORMATIONAL**
  エラー通知、SAの削除、通信相手の生存確認(DPD)など、制御情報のやり取りに用いる。

「最小で2往復（4メッセージ）」とは、IKE_SA_INIT と IKE_AUTH の2つの交換で、最初の CHILD SA まで一気に作れるという意味です。

```
 イニシエータ                                                   レスポンダ
     │ ━━ IKE_SA_INIT（平文、UDP 500）━━━━━━━━━━━━━━━━━━━━━━━━━ │
     │ ① 暗号・認証方式の提案、DH公開値、乱数(Nonce)  ─────────▶ │
     │ ② 選択した方式、DH公開値、乱数(Nonce)         ◀───────── │
     │        （NAT を検出したら以降は UDP 4500 へ）               │
     │                     ↓ IKE SA 生成                           │
     │ ━━ IKE_AUTH（IKE SA で暗号化）━━━━━━━━━━━━━━━━━━━━━━━━━━ │
     │ ③ ID、認証データ（署名/事前共有鍵/EAP）、             │
     │    CHILD SA の提案、保護する通信の範囲 ─────────────▶ │
     │ ④ ID、認証データ、選択した CHILD SA のパラメータ ◀──── │
     │                     ↓ 最初の CHILD SA 生成                  │
     │ ══ ESP でデータ通信 ════════════════════════════════════ │
     │ ━━ CREATE_CHILD_SA … 追加の CHILD SA、リキー             │
     │ ━━ INFORMATIONAL   … エラー通知、SA の削除、DPD          │
```

| 観点 | IKEv1 | IKEv2 |
|---|---|---|
| SA確立までのメッセージ数 | メインモード6＋クイックモード3＝9（アグレッシブモードなら3＋3＝6） | 最小4（IKE_SA_INIT＋IKE_AUTH） |
| 動的IPアドレスの端末 | 事前共有鍵ではアグレッシブモードが必要 | 標準で対応 |
| ユーザ認証 | XAUTH（拡張仕様） | EAP（本体の仕様） |
| アドレスの動的割当て | モードコンフィグ（拡張仕様） | 本体の仕様（設定ペイロード） |
| NAT トラバーサル | 拡張仕様（RFC 3947／3948） | 本体の仕様 |
| 生存確認（DPD） | 拡張仕様 | INFORMATIONAL 交換で標準対応 |
| 互換性 | IKEv1 と IKEv2 の間では通信できない | 同左 |

### 8.3 通信相手の認証方式

IKEv2では、通信相手を認証する方式として、次のような方式が使用可能です。

- 事前共有鍵(Pre-Shared Key)認証方式
- RSAデジタル署名認証方式
- DSSデジタル署名認証方式
- EAP(Extensible Authentication Protocol)認証方式

> **DSS(Digital Signature Standard)**
> 米国国立標準技術研究所(NIST)によって標準化されたデジタル署名方式。署名アルゴリズムとしてDSA(Digital Signature Algorithm)を用いる。

> **EAP認証**
> IKEv2で標準化されたユーザ認証の仕組み。IKEv1におけるXAUTHの役割を担い、RADIUSサーバなどと連携した多様な認証方式を利用できる。

EAP そのものは IKEv2 専用ではなく、無線LANの IEEE 802.1X（第7章 7.6）などでも使われる汎用の認証フレームワークです。IKEv2 はその EAP を IKE_AUTH 交換の中で使えるように仕様に組み込みました。典型的な構成では、VPN ゲートウェイは**証明書（デジタル署名）で自分を証明**し、端末の利用者は **EAP でユーザ ID とパスワードやワンタイムパスワードを提示**します。こうすると、利用者は偽の VPN ゲートウェイにパスワードを渡してしまう危険を避けられます。なお、署名方式としては、現在は DSS（DSA）より RSA や楕円曲線の署名（ECDSA など）が多く使われています。

## 9. IPsec VPNの設計と運用 ― 実務で目にするもの

### 9.1 IPsecを通すためのファイアウォールのルール

第5章 5.5 で学んだように、ファイアウォールのルール表は上から順に評価され、最後は暗黙の拒否で終わります。VPN ゲートウェイがファイアウォールの内側（DMZ）にある場合、ファイアウォールの管理者は IPsec の通信を明示的に許可しなければなりません。本社の VPN ゲートウェイを 198.51.100.1、支店の VPN ゲートウェイを 203.0.113.1 とすると、インターネット側からのルールは次のようになります。

| No. | 送信元 | 宛先 | プロトコル／宛先ポート | 動作 | 目的 |
|---|---|---|---|---|---|
| 1 | 203.0.113.1 | 198.51.100.1 | UDP/500 | 許可 | 支店との IKE（鍵交換） |
| 2 | 203.0.113.1 | 198.51.100.1 | UDP/4500 | 許可 | 支店との NATトラバーサル（IKE と ESP） |
| 3 | 203.0.113.1 | 198.51.100.1 | IPプロトコル番号50（ESP） | 許可 | 支店との暗号化データ通信 |
| 4 | any | 198.51.100.1 | UDP/500、UDP/4500 | 許可 | リモートアクセス端末の IKE と NAT-T（端末のアドレスは動的なので送信元を絞れない） |
| （暗黙） | any | any | any | 拒否 | 上記以外 |

このルール表を読むときの注意点をまとめます。

- **ESP は「TCP/50」や「UDP/50」ではない**：ESP と AH は TCP や UDP の上に載るのではなく、IPヘッダの直後に来るプロトコルです（第1章 1.4 のプロトコル番号）。ポート番号ではなくプロトコル番号 50（AH なら 51）で指定します。試験の選択肢でもよく使われる引っかけです。
- **AH は使う場合だけ許可する**：暗号化が必要な VPN では通常 ESP だけを使うので、プロトコル番号 51 は許可しないのが最小権限の考え方に沿います。
- **逆方向も忘れない**：拠点間VPNでは、どちらの拠点もネゴシエーションを開始（リキーも含む）しうるので、本社から支店への方向にも同じ許可が必要です。ESP にはTCPのような接続状態がないため、ステートフルインスペクションの戻り通信の自動許可に頼れない製品もあります。
- **送信元はできるだけ絞る**：拠点間接続では対向の VPN ゲートウェイのアドレスに限定し、攻撃者が VPN ゲートウェイの IKE に直接攻撃を試みる余地を減らします。
- **復号後の通信もルールで制御する**：トンネルから出てきた通信は、社内側のファイアウォールや VPN ゲートウェイの ACL で、業務に必要な宛先だけに絞ります。VPN を通ったから信頼する、という扱いはゼロトラストの観点（第1章 1.7）からは避けるべきです。

科目Bで「VPN が確立しない」「確立するがデータが流れない」という事例が出たら、ファイアウォールのルールと次の対応表を照らし合わせます。

| 症状 | ありがちな原因 |
|---|---|
| フェーズ1（IKE SA／ISAKMP SA）が確立しない | UDP 500 が遮断されている、提案するアルゴリズムが一致しない、事前共有鍵や証明書が一致しない |
| NAT の内側の端末だけフェーズ1が途中で止まる | UDP 4500 が遮断されている、NAT-T が無効 |
| フェーズ1は成功するがフェーズ2が失敗する | 保護するネットワークの範囲（セレクタ）や PFS の設定が両端で一致しない |
| SA は確立するがデータが流れない | ESP（プロトコル番号50）が遮断されている、NAT の内側で AH を使っている |

### 9.2 拠点間VPNルータの設定項目

拠点間VPNを構築するネットワーク管理者は、両拠点の VPN ルータに次のような項目を設定します。本ノートで学んだ用語が、そのまま設定項目として現れていることを確認してください。

```
crypto ipsec-vpn to-branch-osaka          ! 接続の定義（本社側）
 peer-address          203.0.113.1         ! 対向 VPN G/W
 local-id              hq.example.jp       ! 自分の ID (FQDN)
 ike-version           2
 ! --- フェーズ1 (IKE SA) ---
 ike-proposal  encryption aes-256-gcm  prf sha-256  dh-group 19
 authentication        certificate         ! 証明書(デジタル署名)。少数拠点なら pre-shared-key
 ike-sa-lifetime       86400               ! 秒 (24時間)
 dpd interval 30 retry 3                    ! 生存確認
 nat-traversal         enable              ! UDP 4500
 ! --- フェーズ2 (CHILD SA / IPsec SA) ---
 protocol              esp                 ! AH は使わない
 mode                  tunnel
 esp-proposal  encryption aes-256-gcm  pfs dh-group 19
 traffic-selector  local 172.16.1.0/24  remote 172.16.2.0/24   ! SPD のセレクタ
 ipsec-sa-lifetime     3600 seconds  4608000 kilobytes          ! 時間とデータ量の寿命
```

| 設定項目 | 本ノートの節 | 管理者が判断すべきこと |
|---|---|---|
| IKE バージョン | 6節・8節 | 新規構築では IKEv2 を選ぶ（IKEv1 のアグレッシブモードを避けられる） |
| 認証方式 | 6.2・8.3 | 拠点や端末が多い、または漏えい時の影響を限定したいなら証明書 |
| 暗号アルゴリズム | 5.2 | AES（GCM など）を選び、DES・3DES は使わない |
| DH グループ | 6.4 | 十分な強度のグループを選ぶ |
| SA の寿命 | 4.3・6.6 | IKE SA は長め、IPsec SA は短めにして定期的に鍵を更新する |
| PFS | 6.6 | 鍵漏えい時の被害を限定するため有効にする |
| セレクタ | 4.2 | 両端で鏡像（ローカルとリモートが逆）になるよう一致させる |
| NAT-T、DPD | 7.3・8.2 | NAT を越える構成では NAT-T、障害検知には DPD を有効にする |

### 9.3 アルゴリズムの選び方

IPsec のアルゴリズムは両端の合意で決まるため、古い装置に合わせて弱いアルゴリズムを残すと、全体の強度がそこまで下がります。暗号の強度の考え方は第7章 7.1 で扱いますが、IPsec の設定では次の区別を押さえておきましょう。

| 用途 | 選ぶべきもの | 避けるべきもの | 理由 |
|---|---|---|---|
| 暗号化（ESP、IKE） | AES-GCM、AES-CBC（128／256ビット） | DES、3DES | DES は鍵長が短く総当たりで破られる。3DES はブロック長が短く大量データで安全性が下がる |
| メッセージ認証 | HMAC-SHA-256／384／512（AES-GCM を使う場合は不要） | HMAC-MD5（HMAC-SHA1 は互換性のために残るが、新規には SHA-2 系を選ぶ） | ハッシュ関数の安全性の低下 |
| DH グループ | 2048 ビット以上の MODP（グループ14 以上）、楕円曲線（グループ19、20 など） | 768／1024 ビットの MODP（グループ1、2） | 短い DH は事前計算によって解読されるおそれがある |
| IKE のモード | IKEv2、または IKEv1 のメインモード＋証明書 | IKEv1 のアグレッシブモード＋事前共有鍵 | ID の平文送信とオフライン辞書攻撃（本ノート6.5） |

### 9.4 VPN装置のログ

運用担当者は、VPN装置のログで SA の確立・失敗を監視します。製品によって表記は異なりますが、たとえば次のような行が記録されます。

```

Oct  2 09:00:01 vpngw01 charon: CHILD_SA to-branch-osaka established with SPIs c1a2b3d4_i 5e6f7a8b_o and TS 172.16.1.0/24 === 172.16.2.0/24
Oct  2 03:12:44 vpngw01 charon: received AUTHENTICATION_FAILED notify from 192.0.2.77, user=sato
Oct  2 03:12:51 vpngw01 charon: received AUTHENTICATION_FAILED notify from 192.0.2.77, user=sato
```

上の2行は正常な確立（IKE SA と CHILD SA、SPI とセレクタが読み取れます）、下の2行は深夜に同じ送信元から認証失敗が続いている記録です。運用担当者は、パスワード推測やリスト型攻撃の兆候を早期に検知するために、認証失敗の回数・送信元・時刻を監視し、しきい値を超えたら SOC や CSIRT にエスカレーションすべきです（第4章 4.8）。

## 10. 確認問題

### 10.1 理解度チェック（Check!）

- 【Q1】IPsec VPNの利用形態にはどのような種類があるか。
- 【Q2】IPsecにおけるトランスポートモードとトンネルモードにはどのような違いがあるか。
- 【Q3】AHプロトコルとESPプロトコルでは、それぞれどのような機能が提供されるか。
- 【Q4】IPsecにおけるSAとは何か。
- 【Q5】IKEv1で通信相手を認証する方式として、どのような種類があるか。
- 【Q6】IKEv1のSAにはどのような種類があるか。
- 【Q7】IKEv1とIKEv2を比較した場合の、IKEv2の特徴や利点を述べよ。
- 【Q8】IKEv2のSAにはどのような種類があるか。
- 【Q9】IKEv2で通信相手を認証する方式として、どのような種類があるか。

> **解答例**
> - **Q1**：VPNゲートウェイ装置どうしで拠点のネットワークをつなぐ拠点間接続と、モバイルPCやSOHOの端末から ISP とインターネットを経由して組織のVPNゲートウェイにつなぐ拠点対端末接続（リモートアクセス）がある。
> - **Q2**：トランスポートモードは、IPパケットのペイロードだけを暗号化し、元のIPヘッダをそのまま使って送る。主にホスト間のエンドツーエンド通信で使う。トンネルモードは、元のIPヘッダを含むパケット全体を暗号化し、新たなIPヘッダを付加して送る。主に拠点間接続やリモートアクセスで使う。
> - **Q3**：AHは、メッセージ認証、送信元の認証、重複検知（リプレイアタックの防止）、アクセス制御を提供するが、暗号化機能はない。ESPは、これらに加えて通信データの暗号化機能を提供する。
> - **Q4**：IPsecにおける論理的なコネクション（トンネル）であり、通信相手と取り決めた暗号アルゴリズムや鍵などの情報をもつ。IPsec SA は片方向ごとに作られ、SPI で識別される。
> - **Q5**：事前共有鍵認証、デジタル署名認証、公開鍵暗号認証、改良型公開鍵暗号認証。
> - **Q6**：フェーズ1で作成する制御用の ISAKMP SA（双方向で一つ）と、フェーズ2で作成するデータ通信用の IPsec SA（片方向ごとに一つ）。
> - **Q7**：動的に設定されるIPアドレスに標準で対応している。NATトラバーサル、ユーザ認証、アドレスの動的割当て、DPDなどの拡張技術を取り込み、仕様が明確かつ簡潔になっている。SA確立までに必要なメッセージ数が最小で2往復（4メッセージ）に削減されている。
> - **Q8**：IKEv1のISAKMP SAに相当する制御用の IKE SA と、IKEv1のIPsec SAに相当するデータ通信用の CHILD SA。
> - **Q9**：事前共有鍵認証方式、RSAデジタル署名認証方式、DSSデジタル署名認証方式、EAP認証方式。

### 10.2 過去問題1：IPsecに関する記述

IPsecに関する記述のうち、適切なものはどれか。

- ア IKEはIPsecの鍵交換のためのプロトコルであり、ポート番号80が使用される。
- イ 暗号化アルゴリズムとして、HMAC-SHA1が使用される。
- ウ トンネルモードを使用すると、エンドツーエンドの通信で用いるIPのヘッダまで含めて暗号化される。
- エ ホストAとホストBとの間でIPsecによる通信を行う場合、認証や暗号化アルゴリズムを両者で決めるために、ESPヘッダではなくAHヘッダを使用する。

[情報セキュリティスペシャリスト試験 過去問題]

> **解答・解説**
>
> - ア:IKEが使用するのは500/UDPである(NATトラバーサル使用時は4500/UDP)。80番はHTTPのポート番号であり、誤りである。
> - イ:HMAC-SHA1はメッセージ認証(完全性の確認)に用いるアルゴリズムであり、暗号化アルゴリズムではない。
> - ウ:トンネルモードでは、元のIPパケット全体(エンドツーエンドの通信で用いるIPヘッダを含む)がカプセル化され、ESPによって暗号化される。適切な記述である。
> - エ:認証や暗号化アルゴリズムを両者で決めるのはIKEの役割であり、AHヘッダの役割ではない。
>
> したがって**ウ**が正解。

### 10.3 過去問題2：ESPやAHを含むインターネットVPNの技術

インターネットVPNを実現するために用いられる技術であり、ESP(Encapsulating Security Payload)やAH(Authentication Header)などのプロトコルを含むものはどれか。

- ア IPsec
- イ MPLS
- ウ PPP
- エ SSL

[情報セキュリティスペシャリスト試験・H26春]

> **解答・解説**
>
> インターネットVPNを実現するために用いられる技術としては、IPsec(Internet Protocol Security)やSSL(Secure Sockets Layer)が代表的だが、ESP、AHなどのプロトコルを含むのはIPsecである。
>
> AHは、主に通信データの認証(メッセージ認証)のために使用されるプロトコルであり、通信データを暗号化する機能はない。一方、ESPは、通信データの認証と暗号化の両方の機能を提供するプロトコルである。
>
> したがって**ア**が正解。

### 10.4 過去問題3：IPv6でネットワーク層の暗号化に使うもの

PCからサーバに対し、IPv6を利用した通信を行う場合、ネットワーク層で暗号化を行うときに利用するものはどれか。

- ア IPsec
- イ PPP
- ウ SSH
- エ TLS

[情報処理安全確保支援士試験・R4秋]

> **解答・解説**
>
> 問題文に該当するのはIPsecである。IPsecには、次のような特徴がある。
>
> - パケットをネットワーク層でカプセル化し、暗号化する
> - 上位層のアプリケーションに依存せずに暗号化通信が可能
> - IPv4、IPv6のどちらでも利用でき、IPv6では当初IPsecの実装が必須とされていた(現在は推奨に変更されている)
>
> なお、PPPはデータリンク層、SSHとTLSはトランスポート層より上位で動作するプロトコルである。
>
> したがって**ア**が正解。

## 11. 試験対策まとめ（重要ポイント）

### 11.1 知識の確認（科目A-2向け）

- **IPsec の位置**：ネットワーク層（インターネット層）で動作し、上位のアプリケーションに依存せずに保護する。IPv4・IPv6 の両方で使える。IPv6 では当初「実装必須」、現在は「推奨」。IETF の RFC 4301 などで規定。
- **トランスポートモード と トンネルモード**：ペイロード（TCPヘッダ＋データ）だけを暗号化し元のIPヘッダを使う／元のIPヘッダを含むパケット全体を暗号化し新IPヘッダを付ける。拠点間接続・リモートアクセスはトンネルモード。
- **AH と ESP**：AH（プロトコル番号51）は認証のみで暗号化なし、IPヘッダも認証範囲。ESP（プロトコル番号50）は暗号化＋認証、認証範囲は ESPヘッダ〜ESPトレーラで IPヘッダを含まない。
- **5つの機能**：アクセス制御、メッセージ認証、送信元の認証、重複検知（シーケンス番号でリプレイアタック防止）は AH・ESP 共通。暗号化は ESP のみ。
- **SPD・SA・SAD・SPI**：SPD は方針（破棄／通過／適用）、SA は片方向の論理的なトンネル、SAD は SA の鍵などの保管庫、SPI は SA の識別子。
- **IKEv1 の2フェーズ**：フェーズ1でISAKMP SA（双方向で1つ、メインモード3往復／アグレッシブモード1往復半）、フェーズ2で IPsec SA（片方向ごと、クイックモード1往復半）。IKE は 500/UDP。
- **メインモード と アグレッシブモード**：事前共有鍵＋メインモードは ID が IPアドレスに限られ動的IPの端末では使えない。アグレッシブモードは FQDN なども使えるが、ID が平文で、事前共有鍵へのオフライン辞書攻撃のおそれがある。
- **SKEYID の4つの鍵**：SKEYID（親）、SKEYID_d（IPsec SA の鍵の元）、SKEYID_a（認証用）、SKEYID_e（暗号化用）。
- **PFS**：クイックモードで DH を再実行し、鍵漏えい時に他の SA の鍵を推測させない。
- **IKEv1 の認証方式**：事前共有鍵、デジタル署名、公開鍵暗号、改良型公開鍵暗号。IKEv2 は事前共有鍵、RSA署名、DSS署名、EAP。
- **NAT／NAPT との相性**：AH は NAT で ICV 不一致。ESP は NAT（トンネルモード）なら可、NAPT はポート番号が暗号化されていて不可 → NAT-T（RFC 3948 の UDP encapsulation＋RFC 3947 の NAT 検出、4500/UDP）。
- **XAUTH とモードコンフィグ**：IKEv1 のフェーズ1と2の間でユーザ認証／IPアドレス・DNSサーバなどを属性ペイロードで割り当て。IKEv2 では EAP と本体の仕様に取り込まれた。
- **IKEv2**：IKE SA と CHILD SA、4つの交換（IKE_SA_INIT、IKE_AUTH、CREATE_CHILD_SA、INFORMATIONAL）、最小4メッセージ、IKEv1 と互換性なし。
- **引っかけ**：IKE はポート80ではなく UDP 500。HMAC-SHA1 は暗号化ではなくメッセージ認証。アルゴリズムを決めるのは AH ではなく IKE。ESP は「TCP/50」ではなくプロトコル番号50。

### 11.2 記述式で問われる観点（科目B向け）

- **ファイアウォールに追加するルール**：「VPN ゲートウェイ宛ての UDP 500（IKE）、UDP 4500（NAT-T）、プロトコル番号50（ESP）を、対向の VPN ゲートウェイのアドレスからに限って許可する」の形で、送信元・宛先・プロトコル・目的をそろえて書く。
- **NAT 越しに通信できない原因**：「NAPT 装置は ESP のポート番号を変換できない（暗号化されている／ESPヘッダにポート番号がない）ため」と根拠を述べ、対策として「NAT-T を有効にし、UDP 4500 を許可する」と答える。AH なら「IPヘッダが認証範囲に含まれるため NAT で ICV が一致しない」。
- **アグレッシブモードのリスクと対策**：「ID が平文で送られ、盗聴したハッシュ値から事前共有鍵をオフライン辞書攻撃で推測されるおそれがある」→「十分に長くランダムな事前共有鍵にする／証明書認証や IKEv2 に移行する」。
- **リモートアクセスでユーザ認証が必要な理由**：「端末の盗難・紛失時に、端末に保存された鍵や証明書だけでデバイス認証が通り、第三者に社内へ接続されるため」→「XAUTH または EAP でユーザ認証（多要素認証）を追加する」。
- **トンネルモードを選ぶ理由**：「内部ネットワークのアドレスを含む元のIPヘッダまで暗号化し、経路上の第三者に内部のアドレス体系や通信相手を知られないようにするため」。
- **PFS を有効にする理由**：「ある時点の鍵が漏えいしても、過去・将来の通信の鍵を推測されず、被害を1つの SA に限定するため」。
- **VPN を通った通信の扱い**：トンネルの出口より内側は平文に戻ることを踏まえ、復号後の通信をアクセス制御で絞る、VPN の認証失敗ログを監視する、といった運用面の対策まで書けるようにする。
