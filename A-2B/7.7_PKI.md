## 0. 全体像 ― なぜこの分野を学ぶのか

第7章 7.1 で学んだ公開鍵暗号は、「公開鍵は誰に配ってもよい」という便利な性質をもっています。しかし、ここに大きな落とし穴があります。受け取った公開鍵が**本当にその相手のものか**を、公開鍵そのものは何も教えてくれないのです。攻撃者が「これは example.com の公開鍵です」と偽って自分の公開鍵を配れば、利用者は攻撃者に向けて暗号化し、攻撃者の署名を本物と信じてしまいます。

**PKI**（Public Key Infrastructure：**公開鍵基盤**）とは、公開鍵暗号技術を基盤とし、**デジタル証明書**や**CA**（認証局）によって実現される相互認証の基盤です。PKI は「この公開鍵はこの人（このサーバ）のもの」という結びつきを、信頼できる第三者が署名して保証する仕組みです。本ノートでは、PKIを構成する要素や仕組みを解説し、あわせてPKIに関連する技術として、電子文書の長期保存に関する技術についても解説します。

本ノートは次の順で進みます。

1. **なぜ PKI が必要か**（本ノート1節）：鍵の正当性と中間者攻撃。
2. **デジタル証明書の中身**（2節）：X.509v3 の項目を、`openssl x509 -text` の実際の出力で確認します。CSR、ブラウザの検証項目、Certificate Transparency、属性証明書もここで扱います。
3. **証明書の一生**（3節）：発行申請から失効・期限満了までの流れを「誰が何をするか」で追い、DV／OV／EV の違いを整理します。
4. **PKI の登場人物**（4節）：CA の階層構造と証明書チェーン、トラストアンカー、CP/CPS、自己署名証明書、RA。
5. **失効をどう確かめるか**（5節）：CRL、VA、OCSP、OCSPステープリング、SCVP。
6. **PKI の使い道**（6節・7節）：デジタル署名、XMLデジタル署名、コードサイニング。
7. **時間を超えて証明する**（8節）：タイムスタンプ、長期保存のファイル形式、アーカイブタイムスタンプ、長期署名フォーマット。

PKI は単独で使われることはほとんどなく、ほかの技術の「信頼の土台」として働きます。TLS のサーバ認証（第7章 7.4）、S/MIME によるメールの署名・暗号化（第3章 3.4、第7章 7.5）、クライアント証明書による利用者認証や EAP-TLS（第6章、第7章 7.6）は、いずれも本ノートの仕組みの上に成り立っています。電子署名法やタイムビジネスの制度面は第9章 9.5 で扱います。

科目Bの業務観点では、「③情報及び情報システムの利用におけるセキュリティ対策の適用」（暗号利用と鍵管理）と「②企画・設計・開発・運用におけるセキュリティ確保」（セキュリティ機能の設計・実装、運用・保守）に対応します。科目A-2では CRL・OCSP・RA・CPS・XML署名の識別が定番で、科目Bでは「ブラウザがサーバ証明書の何を検証するか」「秘密鍵が漏えいしたときに何をすべきか」「プライベートCAを構築するときの留意点」が記述で問われます。

> **試験に出る**
> 情報セキュリティスペシャリスト試験（現・情報処理安全確保支援士試験）の午後問題では、PKI構築に関する問題が出題されたことがある。

## 1. PKIの概要 ― 鍵の正当性をどう保証するか

公開鍵暗号技術はアルゴリズムが公開されているため、誰でも公開鍵と秘密鍵を生成できます。攻撃者も例外ではありません。したがって、公開鍵暗号技術による認証や署名では、**公開鍵や秘密鍵の正当性が保証されていること**が非常に重要です。

**鍵の正当性**とは、その鍵が真の所有者のものであることを適切に証明できている状況をいいます。これを実現するため、信頼できる第三者（認証局）が署名して発行する**デジタル証明書**（**公開鍵証明書**）が用いられています。PKIは、デジタル証明書と、それを発行・管理する機関である認証局によって築かれる相互認証の基盤ととらえることができます。

> **公開鍵の正当性が問題となる理由**
> 公開鍵の真正性を確認する手段がなければ、攻撃者が自身の公開鍵を他人の公開鍵と偽って配布する「なりすまし」や、通信の間に割り込む**中間者攻撃**（**MITM**：Man-In-The-Middle attack）が可能になる。PKIは、第三者による保証によってこのリスクを低減する仕組みである。

中間者攻撃の因果を具体的に書くと次のようになります。攻撃者は、利用者とWebサーバの通信経路（たとえば偽の無線LANアクセスポイント、第7章 7.6）に割り込み、利用者には自分の公開鍵を「サーバの公開鍵」として渡し、サーバには利用者のふりをして接続します。利用者が攻撃者の公開鍵で暗号化したデータは攻撃者に復号され、読まれた後でサーバへ転送されます。利用者もサーバも暗号化しているつもりなのに、機密性と完全性が失われるのです。PKI を使えば、利用者は「この公開鍵は example.com のものである」と CA が署名した証明書を検証できるため、攻撃者が差し出した公開鍵（CA の署名がない、または名前が違う）を見破れます。

これは、身分証明書の仕組みとよく似ています。初対面の人が「私は佐藤です」と名乗っても信じる根拠はありませんが、役所が発行した写真付きの身分証を見せられれば、私たちは役所を信頼しているので本人だと判断できます。PKI では、役所の役割を CA が、身分証の役割をデジタル証明書が、役所の印影の役割を CA のデジタル署名が担います。

## 2. デジタル証明書

### 2.1 デジタル証明書とは

**デジタル証明書**とは、個人や組織に関する電子的な身分証明書であり、**CA**（認証局）と呼ばれる第三者機関（**Trusted Third Party**：**TTP**）によって発行されます。デジタル証明書には、その信頼性を保証するため、発行者であるCAのデジタル署名が付されます。

デジタル証明書は**ITU-T**勧告の**X.509**で定義されています。用途に応じて、次のように呼ばれる場合もあります。

| 呼び名 | 用途 | 主な利用場面 |
|---|---|---|
| **クライアント証明書** | クライアントの認証に用いるデジタル証明書 | VPN接続、社内システムへのログイン、EAP-TLS（第6章、第7章 7.6） |
| **サーバ証明書** | サーバの認証に用いるデジタル証明書 | HTTPS の Webサーバ、メールサーバ |
| **SSL証明書** | SSL（SSL/TLS）で用いるデジタル証明書 | SSL は既に廃止されたプロトコルで、実際に使われるのは TLS（第7章 7.4）のため、「SSL/TLSサーバ証明書」「TLS証明書」とも呼ぶ |
| **S/MIME証明書** | S/MIMEで用いるデジタル証明書 | メールへの署名と暗号化（第3章 3.4、第7章 7.5） |
| （**コードサイニング証明書**） | ソフトウェアへの署名に用いる証明書 | 本ノート7節 |

### 2.2 デジタル証明書（X.509v3）の構成要素

**図：デジタル証明書の概要**

```
┌──────────── デジタル証明書(X.509v3) ────────────┐
│ ┌─ 署名対象部分(tbsCertificate) ─────────────┐ │
│ │ バージョン / シリアル番号 / 署名アルゴリズム     │ │
│ │ 発行者(Issuer) / 有効期間 / 主体者(Subject)     │ │
│ │ 主体者の公開鍵情報  ← 証明したい「公開鍵」本体    │ │
│ │ 拡張領域(鍵用途、SAN、CRL配布点、AIA など)       │ │
│ └──────────────────────────────┘ │
│   ↑ この部分のハッシュ値を、発行者CAの秘密鍵で署名  │
│ CAのデジタル署名                                  │
└────────────────────────────────┘
```

デジタル証明書（X.509v3）の主な構成要素は次のとおりです。

| 項目 | 内容 | 検証者（ブラウザ等）がこの項目で確かめること |
|---|---|---|
| バージョン | X.509のバージョン（v3など） | 拡張領域を解釈する形式か |
| シリアル番号 | CAが証明書ごとに割り当てる一意の番号 | CRL・OCSP で失効を照会するときのキー |
| 署名アルゴリズム | CAが署名に用いたアルゴリズム（sha256WithRSAEncryptionなど） | 危殆化したアルゴリズム（SHA-1 など）でないか |
| 発行者（**Issuer**） | 証明書を発行したCAの識別名 | 上位の CA 証明書をたどるための手がかり |
| 有効期間 | 有効期間の開始日時（**notBefore**）と終了日時（**notAfter**） | 現在時刻が期間内か |
| 主体者（**Subject**） | 証明書の所有者の識別名（コモンネーム、組織名など） | 誰の証明書か |
| 主体者の公開鍵情報 | 所有者の公開鍵と、その公開鍵のアルゴリズム | 鍵長が十分か（RSA 2048ビット以上など） |
| 拡張領域 | 鍵用途、**SAN**（Subject Alternative Name）、CRL配布点、**AIA**（OCSPレスポンダの所在など） | 接続先のFQDNがSANに含まれるか、用途が合っているか、失効情報の取得先 |
| CAのデジタル署名 | 上記の内容に対する発行者CAの署名 | 発行者CAの公開鍵で検証でき、改ざんされていないか |

表だけでは実感が湧きにくいので、実物を見てみましょう。サーバの管理者は、手元の証明書ファイルの中身を `openssl x509 -text` コマンドで確認できます。次は、example.com の Webサーバ証明書を表示した出力の抜粋です（値は例示用）。

```
$ openssl x509 -in www.example.com.crt -noout -text

    Data:
        Version: 3 (0x2)                                    ← バージョン(v3)
        Serial Number:
            04:7a:3c:91:5e:2b:d8:10:6f:a2:33:c4:9e:01:7b:55   ← シリアル番号
        Signature Algorithm: sha256WithRSAEncryption         ← 署名アルゴリズム
        Issuer: C=JP, O=Example Trust Inc., CN=Example TLS CA G2   ← 発行者(中間CA)
        Validity
            Not Before: Apr  1 00:00:00 2026 GMT             ← notBefore
            Not After : Oct 17 23:59:59 2026 GMT             ← notAfter
        Subject: C=JP, ST=Tokyo, L=Chiyoda-ku, O=Example Corp., CN=www.example.com
        Subject Public Key Info:                             ← 主体者の公開鍵情報
            Public Key Algorithm: rsaEncryption
                Public-Key: (2048 bit)
        X509v3 extensions:                                   ← 拡張領域
            X509v3 Basic Constraints: critical
                CA:FALSE                                     ← CAではない(他の証明書に署名できない)
            X509v3 Key Usage: critical
                Digital Signature, Key Encipherment          ← 鍵用途
            X509v3 Extended Key Usage:
                TLS Web Server Authentication                ← サーバ認証用
            X509v3 Subject Alternative Name:
                DNS:www.example.com, DNS:example.com         ← SAN(この名前で使える)
            X509v3 CRL Distribution Points:
                URI:http://crl.example.jp/tls-g2.crl         ← CRL配布点
            Authority Information Access:
                OCSP - URI:http://ocsp.example.jp            ← AIA(OCSPレスポンダ)
                CA Issuers - URI:http://cert.example.jp/tls-g2.crt   ← 上位CA証明書の所在
            CT Precertificate SCTs:                          ← CTログへの登録証明(2.5)
                Signed Certificate Timestamp: ...
    Signature Algorithm: sha256WithRSAEncryption
    Signature Value:
        5b:1e:9a:...                                         ← CAのデジタル署名
```

この出力から読み取れることを、科目Bの設問の形で確認しておきます。

- **この証明書はどの名前のサーバで使えるか**：SAN に列挙された www.example.com と example.com です。現在のブラウザは、コモンネーム（CN）ではなく **SAN** を照合します。SAN に含まれない名前（たとえば mail.example.com）でアクセスすると、名前不一致の警告が出ます。
- **誰が発行したか**：Issuer の「Example TLS CA G2」で、これは中間CAです。ブラウザはこの中間CAの証明書、さらにその上のルートCAの証明書へとたどって検証します（4.2）。
- **何に使える鍵か**：Key Usage と Extended Key Usage から、TLS のサーバ認証用であり、**CA:FALSE** のため他の証明書に署名する権限はありません。攻撃者がこの証明書と秘密鍵を盗んでも、それを使って偽の証明書を発行することはできない、という制限になっています。
- **失効をどこで確かめるか**：CRL配布点と AIA の OCSP の URI です（5節）。

### 2.3 CSR（証明書署名要求）

Webサーバで用いるデジタル証明書の発行をCAに申請する際、申請者（サーバの管理者）は**CSR**（Certificate Signing Request：**証明書署名要求**）を生成する必要があります。CSRには申請者の公開鍵のほか、次の情報が含まれます。

- **コモンネーム**（当該証明書を使用するサーバのFQDN）
- 組織名
- 部門名
- 市区町村名
- 都道府県名
- 国別番号（日本であれば国コードの「JP」）

これらの情報は、そのままデジタル証明書を構成する要素となります。次は、サーバの管理者が OpenSSL で鍵ペアを作り、CSR を生成するときの入力画面の例です。

```
$ openssl genrsa -out www.example.com.key 2048        ← ①鍵ペアを生成(秘密鍵はサーバ内に保管)
$ openssl req -new -key www.example.com.key -out www.example.com.csr   ← ②CSRを生成
Country Name (2 letter code) []:JP                    ← 国別番号
State or Province Name (full name) []:Tokyo           ← 都道府県名
Locality Name (eg, city) []:Chiyoda-ku                ← 市区町村名
Organization Name (eg, company) []:Example Corp.      ← 組織名
Organizational Unit Name (eg, section) []:IT Dept.    ← 部門名
Common Name (e.g. server FQDN) []:www.example.com     ← コモンネーム(FQDN)
```

なお、CSRは**申請者の秘密鍵で署名される**ため、CAは申請者が対応する秘密鍵を保有していることを確認できます。重要なのは、**CSR に入るのは公開鍵だけで、秘密鍵は申請者の手元から一度も出ない**ことです。サーバの管理者は、秘密鍵のファイルのアクセス権を最小限にし、CA や外部の業者に秘密鍵を送ってはいけません。なお、パブリックなサーバ証明書では、CA/Browserフォーラムの基準改定により、2022年以降は部門名（OU）が証明書に記載されなくなっています。

### 2.4 ブラウザによるサーバ証明書の検証

ブラウザがWebサーバとSSL/TLS通信を行う際には、次のような事項によってサーバ証明書の正当性を検証し、問題があった場合には警告メッセージを表示します（TLS ハンドシェイクのどの時点で証明書が送られるかは第7章 7.4 を参照）。

| 検証項目 | 何を確かめるか | 失敗したときに疑われること |
|---|---|---|
| ① 有効期間 | サーバ証明書が有効期間内であること | 更新忘れ、端末の時計の狂い |
| ② 名前の一致 | サーバ証明書のコモンネーム（またはSAN）と、アクセスしたURLのFQDNが一致していること | 別サイトの証明書の流用、中間者攻撃、フィッシングサイト |
| ③ 失効の有無 | サーバ証明書が失効していないこと（CRLやOCSPによる確認） | 秘密鍵の漏えい後に失効された証明書の悪用 |
| ④ 発行元の信頼性 | サーバ証明書が信頼できるCAによって発行されていること（証明のパスをルートCAまでたどって信頼性を確認できること。詳細は 4.2） | 自己署名証明書、偽のCAによる証明書、中間CA証明書の設定漏れ |

利用者が警告画面で「詳細設定」から先へ進んでしまうと、これらの検証が無意味になります。組織は、利用者に「証明書の警告が出たら接続をやめて報告する」ことを教育し、社内システムでは警告が出ないように正規の証明書（またはプライベートCAのルート証明書を端末に配布）を使うべきです。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後問題では、ブラウザがサーバ証明書の正当性を確認する際の検証内容に関する問題が出題されたことがある。

### 2.5 Certificate Transparency（CT）

CA が攻撃を受けたり誤ったりして、ドメインの所有者が知らないうちに、その名前の証明書が発行されてしまう事件が過去に起きています。そうした証明書は「正規の CA が署名した本物」なので、ブラウザの検証（2.4）を通ってしまいます。この問題に対し、認証局が発行したデジタル証明書の記録をログとして公開し、それを監視・検証することで、不正なデジタル証明書の発行や使用を防ぐ技術があります。これは**Certificate Transparency**（**CT**：証明書の透明性）と呼ばれ、**RFC 9162**で規定されています。

> **Certificate Transparency**
> CTでは、CAが証明書を発行する際に、誰でも検証可能な追記型のログサーバ（CTログ）へ証明書を登録する。ログサーバは登録の証拠として**SCT**（Signed Certificate Timestamp）を返す。ドメイン所有者や監視者（モニタ）はCTログを監視することで、自分のドメインに対して身に覚えのない証明書が発行されていないかを検出できる。CTは当初**RFC 6962**（実験的仕様）として公開され、RFC 9162はその改訂版（バージョン2.0）にあたる。

2.2 の出力例にあった「CT Precertificate SCTs」が、この SCT です。主要なブラウザは、SCT が付いていないパブリックなサーバ証明書を信頼しない運用をしているため、CA は CT ログへの登録を事実上避けられません。ドメインの管理者は、CT ログの検索サービスで自社ドメインを定期的に監視し、身に覚えのない証明書を見つけたら CA に失効を依頼すべきです。CT は「不正発行そのものを止める」のではなく「不正発行を**検知できるようにする**」技術である点を押さえてください（第1章 1.2 の対策の4機能では検知・追跡にあたります）。

> **試験に出る**
> 情報処理安全確保支援士試験の令和年間の午後問題では、クライアントシステムに対する攻撃とその防御策として、Certificate Transparency等に関する問題が出題されたことがある。

> **CRL**
> **CRL**（Certificate Revocation List：証明書失効リスト）とは、デジタル証明書の悪用や誤発行などの不測事態が発生し、有効期限内に失効させる必要が生じたデジタル証明書を登録したリストである（本ノート 5.1 参照）。

### 2.6 X.509の概要と属性証明書

**X.509**は、ITU-Tが1988年に勧告したデジタル証明書及びCRL（Certificate Revocation List）の標準仕様です。現在は、1996年に勧告された**X.509v3**が広く使用されています。v3 で追加された「拡張領域」により、2.2 で見た SAN や鍵用途を記載できるようになりました。2000年にはX.509v3の改訂が行われ、新たに次のものが定義されました。

- **AC**（Attribute Certificate：**属性証明書**）
- **ACRL**（Attribute Certificate Revocation List：属性証明書失効リスト）

デジタル証明書が所有者の**本人性**を証明するのに対し、ACは所有者の**役割（role）や権限（privilege）などの属性情報**を証明します。一般に、こうした属性情報はデジタル証明書の有効期間よりも短いサイクルで変更されます。たとえば、社員の公開鍵証明書は数年使えても、「経理部の承認者」という役割は人事異動で毎年変わるかもしれません。役割が変わるたびに公開鍵証明書を発行し直すのは非効率なため、属性情報をデジタル証明書から分離し、ACによって管理することになりました。

ACは**AA**（Attribute Authority：**属性認証局**）から発行され、通常は所有者のデジタル証明書と関連付けられます（アプリケーションプログラムなどに対して発行される場合もあります）。なお、AAやACによる属性情報管理の仕組みは、**PMI**（Privilege Management Infrastructure：**権限管理基盤**）と呼ばれます。

| 比較 | 公開鍵証明書（PKI） | 属性証明書（PMI） |
|---|---|---|
| 証明する内容 | 本人性（この公開鍵は誰のものか） | 属性（役割・権限） |
| 発行者 | CA（認証局） | AA（属性認証局） |
| 失効リスト | CRL | ACRL |
| 変更の頻度 | 低い（有効期間は数年程度まで） | 高い（異動・権限変更のたび） |
| 対応する考え方 | 認証（第6章 6.2） | 認可・アクセス制御（第6章 6.1） |

インターネット上での取引などでは、送信相手が確かに実在することや、公開鍵が正当なものであることを、デジタル証明書によって確認できます。しかし、**相手の財務状況や支払能力、商取引における信用度までは確認できません**。したがって、取引における信用度などを確認するには、ACのような属性情報を証明する仕組みや、信用調査機関などによる別途の確認手段を組み合わせる必要があります。「証明書がある＝信用できる取引相手」ではない、という点は引っかけとして問われやすいところです。

> **インターネット上で用いられるデジタル証明書の標準**
> インターネット上では、X.509v3をベースにIETFが策定した**RFC 5280**（Internet X.509 Public Key Infrastructure Certificate and CRL Profile）に準拠した証明書が一般的に用いられている。

## 3. 証明書の一生と認証レベル

### 3.1 デジタル証明書のライフサイクル

デジタル証明書は、ユーザとCAの間で一般に次のようなライフサイクルをたどります。

1. **鍵ペアの生成**：ユーザが公開鍵と秘密鍵の鍵ペアを生成する
2. **発行申請**：ユーザがCSRを作成し、CA（またはRA）に証明書の発行を申請する
3. **審査・発行**：CA（RA）が申請者の本人性などを審査し、CAの秘密鍵で署名したデジタル証明書を発行する
4. **利用**：ユーザはデジタル証明書を用いて認証、暗号化、署名などを行う
5. **更新**：有効期限が近づいた時点で、ユーザは証明書の更新を申請する
6. **失効**：秘密鍵の漏えいや登録情報の変更などが発生した場合、ユーザは失効を申請する。CAはその証明書をCRLに登録する
7. **期限満了**：有効期限が満了した証明書は無効となる

この流れを、Webサーバ証明書を例に「誰が何をするか」で図にすると次のようになります。

**図：デジタル証明書のライフサイクル（ユーザとCAの関係）**

```
 申請者(サーバ管理者)        RA(登録局)              CA(発行局)             リポジトリ          利用者(ブラウザ)
      │                        │                       │                       │                    │
 ①鍵ペア生成                   │                       │                       │                    │
 (秘密鍵はサーバ内に保管)       │                       │                       │                    │
      │──②CSRを提出(公開鍵)─▶│                       │                       │                    │
      │                   審査(本人性・ドメイン       │                       │                    │
      │                   の使用権・組織の実在性)     │                       │                    │
      │                        │──発行を依頼────▶│                       │                    │
      │                        │                ③CAの秘密鍵で署名           │                    │
      │◀────────────────③証明書を発行───────│──証明書を公開──▶│                    │
 サーバに証明書を設置          │                       │                       │                    │
      │◀════════════════════④TLS接続で証明書を提示・利用═════════════════════════════▶│ 証明書を検証
 ⑤期限前に更新申請(①へ)       │                       │                       │                    │
      │                        │                       │                       │                    │
 [秘密鍵漏えい発覚]            │                       │                       │                    │
      │──⑥失効申請───────▶│──失効を依頼────▶│                       │                    │
      │                        │                 CRLに登録・OCSPに反映──▶│ CRL公開 ──────▶│ 失効を確認
      │                        │                       │                       │                    │
 ⑦有効期限の満了で無効(CRLからも削除される)                                                        │
```

科目Bで問われやすいのは⑤と⑥です。

- **更新（⑤）**：サーバの管理者は、証明書の期限切れでサービスが止まらないよう、有効期限を台帳や監視ツールで管理し、期限前に更新すべきです。パブリックなサーバ証明書の最大有効期間は、CA/Browserフォーラムの決定により段階的に短縮されています（2026年3月から最大200日、2027年3月から100日、2029年3月には47日まで短縮される予定）。期間が短いほど、漏えいした鍵が悪用され続ける期間が短くなる一方、手作業での更新は現実的でなくなるため、ACME プロトコルなどによる**更新の自動化**が前提になりつつあります。
- **失効（⑥）**：秘密鍵が漏えいした（またはその疑いがある）とき、サーバの管理者は**直ちに CA に失効を申請**し、新しい鍵ペアを生成して証明書を再発行してもらうべきです。古い鍵のまま証明書だけ再発行しても、漏えいした秘密鍵で攻撃者がなりすませる状態は変わりません。

### 3.2 サーバ証明書の認証レベル ― DV・OV・EV

**EV**（Extended Validation）**証明書**とは、CAとWebブラウザベンダーで構成する業界団体「**CA/Browserフォーラム**」が定めた、Webサーバ用のデジタル証明書です。従来のデジタル証明書よりも発行時の審査基準を厳しく設定しているため、EV証明書を所有するサイトは、通常の証明書を所有するサイトよりも、運営組織の実在性について高い信頼性があるといえます。

> **サーバ証明書の認証レベル**
> サーバ証明書は、審査の厳格さによって一般に次の3種類に分類される。
> - **DV**（Domain Validation）**証明書**：ドメインの使用権のみを確認して発行する
> - **OV**（Organization Validation）**証明書**：ドメインの使用権に加え、組織の実在性を確認して発行する
> - **EV**（Extended Validation）**証明書**：CA/Browserフォーラムのガイドラインに基づき、組織の法的・物理的な実在性などを厳格に確認して発行する
>
> かつて主要ブラウザは、EV証明書を用いたサイトでアドレスバーを緑色にするなどの特別な表示を行っていた。しかし、現在ではこうした表示は廃止されている。

| 項目 | DV証明書 | OV証明書 | EV証明書 |
|---|---|---|---|
| CA（RA）が確認すること | ドメインの使用権のみ | ドメインの使用権＋組織の実在性 | ドメインの使用権＋組織の法的・物理的な実在性、申請者の権限などを厳格に |
| 確認の方法の例 | 指定のDNSレコードやWebページ上のファイルを置かせる、ドメインの管理者宛てメールで確認 | 登記情報や第三者のデータベースで組織を確認 | OV の確認に加え、電話確認、申請責任者の在籍・権限の確認など |
| 発行までの時間 | 数分〜（自動化可能） | 数日程度 | 数日〜数週間程度 |
| 証明書の Subject に載る情報 | ドメイン名（CN）のみ | ドメイン名＋組織名・所在地 | OV の情報＋登記番号、事業の種類など |
| 暗号の強さ | 3種類とも同じ（審査の厳格さが違うだけ） | 同左 | 同左 |
| 主な利用 | 個人サイト、一般のWebサイト | 企業サイト | 金融機関、ECサイトなど |

ここで注意したいのは、**DV証明書でも通信の暗号化の強さは EV と変わらない**ことと、**DV証明書は「そのドメインを管理している者」しか保証しない**ことです。攻撃者が example-bank.jp のような紛らわしいドメインを取得すれば、そのドメインの DV証明書は正規の手順で取得できます。つまり「鍵マークが付いている（HTTPSである）」ことは、「そのサイトの運営者が信頼できる」ことを意味しません。利用者はドメイン名そのものを確認し、組織は利用者にそのことを教育すべきです（フィッシングについては第2章を参照）。

## 4. デジタル証明書による認証基盤を構成する要素

### 4.1 構成要素の全体像

デジタル証明書をベースとした認証基盤を構成する要素を次に示します。

- 認証局（CA）
- 登録局（RA）
- 証明書失効リスト（CRL）
- 証明書有効性検証局（VA）
- OCSPレスポンダ
- **リポジトリ**（デジタル証明書やCRLを公開するディレクトリなど）

**図：デジタル証明書による認証基盤を構成する要素**

```
                  ┌───────────── 認証局(CA)側 ─────────────┐
 申請者 ─申請─▶ │ 登録局(RA)  ──審査結果──▶  認証局(CA/IA)        │
 (証明書の所有者)│ 本人確認・登録              証明書の発行・失効      │
        ◀─証明書─│                              CRLの発行             │
                  └──────────────┬──────────────────┘
                                   │ 証明書・CRLを公開
                                   ▼
                     リポジトリ(ディレクトリ、Webサーバ)
                                   │ CRLを取り込む
                                   ▼
                   証明書有効性検証局(VA) / OCSPレスポンダ
                                   ▲
                                   │ 「この証明書は有効か」と問合せ
                  検証者(ブラウザ、メールソフト、署名の受信者)
```

以下、それぞれの要素を「誰が・何を・何のために」の形で見ていきます。

### 4.2 認証局（CA）と証明書チェーン

認証局は、一般に**CA**（Certification Authority）と呼ばれ、次のような役割を担っています。

- 利用者からの申請に基づいてデジタル証明書を発行する
- 必要に応じてデジタル証明書を失効させ、CRLを発行する
- **CPS**（認証局運用規程）を公開する
- 発行したデジタル証明書を検証するためのCA自身のデジタル証明書を公開する
- デジタル証明書に署名するためのCA自身の秘密鍵を厳重に管理する

最後の項目が CA の生命線です。CA の秘密鍵が盗まれれば、攻撃者はどんな名前の証明書でも「本物」として発行できてしまい、その CA を信頼するすべての利用者が中間者攻撃にさらされます。そのため CA は、署名用の秘密鍵を **HSM**（Hardware Security Module：耐タンパ性のある鍵保管装置）に格納し、複数人の立会いがないと操作できないようにするのが一般的です。

CAは、上位CAが下位CAを認証して証明書を発行するという**階層構造**になっており、最上位のCAは**ルートCA**と呼ばれます。ある証明書の正当性を検証する場合には、当該証明書を発行したCAからルートCAまでの経路（**証明のパス**）を順にたどり、経路上のすべてのCAの証明書の正当性を確認する必要があります。CAの構造を下図に示します。

**図：CAの階層構造**

```
        ルートCA(最上位)
            │ 証明書を発行
        中間CA(下位CA)
            │ 証明書を発行
   一般ユーザ又は下位CA
```

- 上位CAは、下位CAを認証して証明書を発行します（最上位はルートCA）。
- 最下層では、一般ユーザ又は下位CAに対して証明書が発行されます。

ブラウザがサーバ証明書を検証するときに実際にたどる**証明書チェーン**（証明のパス）を、2.2 の例に当てはめると次のようになります。

**図：ルートCA→中間CA→サーバ証明書のチェーン**

```
 ┌───────────────────────────────┐
 │ ルートCA証明書(自己署名)                     │ ← OS/ブラウザのルート証明書ストアに
 │  Subject: CN=Example Root CA                 │   あらかじめ格納(トラストアンカー)
 │  Issuer : CN=Example Root CA  (自分自身)     │
 │  CA:TRUE   有効期間: 20年程度                 │
 └───────────────┬───────────────┘
                 │ ルートCAの秘密鍵で署名
                 ▼  検証:中間CA証明書の署名を、ルートCA証明書の公開鍵で確かめる
 ┌───────────────────────────────┐
 │ 中間CA証明書                                 │ ← Webサーバが、サーバ証明書と一緒に
 │  Subject: CN=Example TLS CA G2               │   TLSハンドシェイクで送る
 │  Issuer : CN=Example Root CA                 │
 │  CA:TRUE, pathlen:0  有効期間: 数年〜10年程度 │
 └───────────────┬───────────────┘
                 │ 中間CAの秘密鍵で署名
                 ▼  検証:サーバ証明書の署名を、中間CA証明書の公開鍵で確かめる
 ┌───────────────────────────────┐
 │ サーバ証明書(エンドエンティティ証明書)        │ ← Webサーバが送る
 │  Subject: CN=www.example.com                 │
 │  Issuer : CN=Example TLS CA G2               │
 │  CA:FALSE  SAN: www.example.com, example.com │
 └───────────────────────────────┘
```

ブラウザは、下の Issuer と上の Subject が一致する証明書を順につなぎ、各段の署名を上位の公開鍵で検証し、各段の有効期間と失効状態を確認し、最後に自分のルート証明書ストアにあるルートCAにたどり着けたら「信頼できる」と判断します。どこか1か所でも途切れれば警告になります。運用上よくある失敗は、**サーバの管理者が中間CA証明書をWebサーバに設定し忘れる**ことです。この場合、チェーンがつながらず、一部のブラウザやアプリで警告やエラーが出ます。

なぜルートCAの下に中間CAを置くのでしょうか。ルートCAの秘密鍵が漏えいすると、そのルートCAの配下すべてが信頼できなくなり、全世界の端末からルート証明書を削除・入れ替える必要があります。そこで CA は、ルートCAの秘密鍵をネットワークから切り離して（オフラインで）厳重に保管し、日々の証明書発行は中間CAに行わせます。中間CAの鍵が漏えいしても、ルートCAがその中間CA証明書を失効させれば被害をその範囲に限定できます。これは第1章 1.2 で学んだ多層防御・被害局所化の考え方です。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後問題では、公開鍵証明書の検証の仕組みや証明書のパスに関する問題が出題されたことがある。

> **トラストアンカー**
> 証明のパスの検証の起点となる、無条件に信頼するルートCAの証明書を**トラストアンカー**という。OSやブラウザには、あらかじめ信頼できるルートCAの証明書が組み込まれている（**ルート証明書ストア**）。

トラストアンカーは「検証の起点なので、それ自体は検証されない」証明書です。したがって、攻撃者やマルウェアが端末のルート証明書ストアに偽のルート証明書を追加すると、その偽CAが発行したあらゆる証明書が警告なしに信頼されてしまいます。管理者は、端末のルート証明書ストアへの追加を管理者権限に限定し、資産管理ツールなどで不審なルート証明書の追加を監視すべきです。

### 4.3 CAに求められる要件と、パブリックCA・プライベートCA

CAには、次のような要件が求められます。

| 要件 | 具体的な内容 | 守れなかった場合に起きること |
|---|---|---|
| 第三者による偽造の防止 | 鍵管理の徹底 | CA の秘密鍵が盗まれ、偽の証明書が発行される |
| デジタル証明書の発行ミスの防止 | 発行申請者の認証 | なりすました申請者に証明書が発行される |
| セキュリティ対策の徹底 | 物理的侵入・不正アクセス・災害・障害対策など | CA システムが侵害・停止する |
| 保守/運用体制の確立 | 証明書の変更、取消しなどのメンテナンス体制の整備 | 失効申請に迅速に対応できない |
| 不測事態発生時の対応 | 不慮の事故や災害などが発生した場合の対応体制や手順の整備 | 鍵漏えい時に被害が拡大する |

CAには、第三者機関として対外的な取引を行う**パブリックCA**（**商用CA**）と、特定の組織内などの閉じた環境でのみ機能する**プライベートCA**（**自営CA**）とがあります。

| 比較 | パブリックCA（商用CA） | プライベートCA（自営CA） |
|---|---|---|
| 運営者 | 商用の認証事業者 | 自組織（社内の情報システム部門など） |
| ルート証明書 | OS・ブラウザに最初から組み込まれている | 自組織の端末に管理者が配布・登録する必要がある |
| 信頼される範囲 | インターネット全体 | 自組織の中だけ |
| 主な用途 | 公開Webサイトのサーバ証明書、S/MIME 証明書 | 社内システムのサーバ証明書、社員・端末のクライアント証明書（VPN、EAP-TLS） |
| 留意点 | 費用がかかる。CA/Browserフォーラムの基準に従う | 鍵管理・失効運用・監査をすべて自組織が担う。CA の秘密鍵漏えいは組織全体に影響する |

CAの設置及び運営にあたっては、**CP**（Certificate Policy：**証明書ポリシ**）と**CPS**（Certification Practice Statement：**認証局運用規程**）を策定する必要があります。

CPとは、CAが証明書を発行する際の運用方針を定めた文書です。また、CPSとは、CAなどの信頼される第三者機関が、自組織の運営体制や認証業務の運用などに関する詳細を規定した文書です。CPSは、認証を利用する者が信頼性、安全性、経済性などを評価できるようにするために作成されます。

> **CPとCPSの関係**
> CPは「どのような方針で証明書を発行するか」という“何を（What）”を定めた文書であり、CPSは「その方針をどのように実施するか」という“どのように（How）”を具体的に定めた文書である。両者の記載項目の枠組みは**RFC 3647**で示されている。

CPS の記載項目の書きぶりを、要旨で例示すると次のようになります（RFC 3647 の章立てに沿った架空の例）。

```
Example Trust Inc. 認証局運用規程(CPS) 抜粋(要旨)
 3.2 初回の本人性確認
   3.2.2 組織の認証: OV証明書の申請では、登記事項証明書により組織の実在性を確認する。
 4.9 証明書の失効
   4.9.1 失効事由: 加入者の秘密鍵の危殆化又はその疑い、登録事項の変更、…
   4.9.5 失効申請の処理期間: 秘密鍵の危殆化の申請を受けた場合、24時間以内に失効する。
   4.9.7 CRLの発行頻度: 少なくとも7日ごとに発行する。
 5.1 物理的管理: CA の秘密鍵を格納する HSM は、入退室管理された区画に設置する。
 6.1.5 鍵長: 加入者の RSA 鍵は 2048 ビット以上とする。
```

利用者（証明書を信頼する側）や監査人は、CPS を読むことで「この CA はどの程度厳格に審査し、失効申請にどれだけ早く対応するのか」を評価できます。プライベートCAを構築する組織も、同様に CP/CPS を定め、それに従って運用すべきです。

### 4.4 自己署名証明書

前述のように、デジタル証明書には通常、それを発行したCAの秘密鍵によってデジタル署名が付与されます。一方、デジタル証明書の利用者自身の秘密鍵でデジタル署名を付した証明書を**自己署名証明書**といいます。自己署名証明書は、Issuer と Subject が同じ証明書です。

ルートCAには上位のCAが存在しないため、ルートCAの公開鍵は自己署名証明書として配付されます。自己署名証明書は第三者の介在なしに、一対の公開鍵と秘密鍵さえあれば生成できます。そのため、組織内部でのみ使用するSSL/TLS証明書として用いられる場合があります。ただし、インターネット上には信頼性の低い自己署名証明書を使用しているサイトもあるため、注意が必要です。

自己署名証明書は「自分で自分を保証している」だけなので、攻撃者も同じ名前の自己署名証明書を簡単に作れます。そのため、利用者が自己署名証明書の警告を毎回無視して接続する運用を続けると、攻撃者が中間者攻撃で差し替えた偽の証明書の警告も同じように無視してしまいます。組織内のサーバであっても、管理者はプライベートCAで発行した証明書を使い、そのルート証明書を端末に配布して、警告が出ない状態を保つべきです。そうすれば「警告が出たら異常」と利用者に教育できます。

### 4.5 登録局（RA）

登録局は、一般に**RA**（Registration Authority）またはRA局と呼ばれ、次のような役割を担っています。

- 証明書の発行や失効などに関する資格審査の実施
- デジタル証明書利用者情報の登録
- 鍵の一括管理
- 公開鍵を公開するためのディレクトリへの保管
- 証明書や鍵の配付

CAがデジタル証明書の保持者と公開鍵の信頼性を保証するのに対し、**RAはデジタル証明書保持者の身元を保証します**。RAの役割をCAが兼ねる場合もあります。たとえば企業の社員証明書では、人事部門が RA として「この申請者は在籍している社員か」を確認し、情報システム部門が運営する CA がその結果に基づいて証明書を発行する、という分担がよく見られます。

> **IA（Issuing Authority）**
> CAの機能のうち、RAの審査結果に基づいて実際に証明書を発行する機能を、**IA**（Issuing Authority：**発行局**）と呼んで区別する場合もある。

| 機関 | 何を保証・担当するか | 一言で |
|---|---|---|
| RA（登録局） | 申請者の身元の審査・登録 | 「この人は本人か」を確かめる窓口 |
| IA（発行局） | RA の審査結果に基づく証明書の発行（署名） | 証明書に判を押す |
| CA（認証局） | 公開鍵と保持者の結びつきの保証、失効・CRL発行、CPS公開（IA を含む全体） | 証明書の発行と管理の責任者 |
| VA（検証局） | 証明書の有効性の検証（5.3） | 「今も有効か」に答える |
| AA（属性認証局） | 属性証明書の発行（2.6） | 役割・権限を証明する |

## 5. 失効の確認 ― CRL・VA・OCSP

### 5.1 証明書失効リスト（CRL）

証明書失効リストは、一般に**CRL**（Certificate Revocation List）と呼ばれます。CRLは、デジタル証明書の悪用や誤発行などの不測事態が発生し、有効期限内に失効させる必要が生じたデジタル証明書を登録したリストです。

なぜ失効の仕組みが必要なのでしょうか。証明書は有効期間が数か月〜数年あり、その間に秘密鍵が漏えいしても、証明書自体には「もう使えない」という情報を書き込めません（書き換えれば CA の署名が無効になります）。そこで CA は、「有効期限内だが無効になった証明書」の一覧を別に発行し、検証者がそれを参照する、という仕組みをとっています。

CRLはCAから随時発行されます。デジタル証明書が悪用されるなどの事故が発生した場合には、証明書の所有者は直ちにデジタル証明書の発行機関に連絡し、CRLへの登録などの失効手続を行う必要があります。

デジタル証明書の有効性を検証する場合は、検証者は証明書の署名の確認とあわせて、検証対象の証明書がCRLに記載されていないかを確認する必要があります。ただし、デジタル証明書は有効期限が満了した段階でCRLから削除されます。そのため、有効期間中に失効された証明書であっても、最新のCRLにはその失効情報が含まれていない可能性があります。証明書の有効性を過去にさかのぼって検証する場合は、その時点でのCRLを確認する必要があります（この問題は 8.7 のアーカイブタイムスタンプで、当時の失効情報を保存することにつながります）。

> **CRLの別称**
> CRLは、失効した証明書を列挙したリストであることから、証明書の**ブラックリスト**と呼ばれることもある。

CRLの更新間隔が長いと、失効の事実がCRLに反映されるまでの間に、失効すべき証明書が有効なものとして扱われるおそれがあります。一方、更新間隔を短くすると、CAによるCRLの発行処理や、利用者によるCRLの取得処理の負荷が増大します。CRLの更新間隔の検討ではこれらの点に留意する必要がありますが、一般には12時間ごとに更新されることが多いとされます。

**図：CRLの構造**

| 項目 | 内容 |
|---|---|
| バージョン | CRLのバージョン（v2など） |
| 署名アルゴリズム | CAがCRLの署名に用いたアルゴリズム |
| 発行者 | CRLを発行したCAの識別名 |
| 今回更新日時（**thisUpdate**） | このCRLの発行日時 |
| 次回更新予定日時（**nextUpdate**） | 次のCRLの発行予定日時 |
| 失効証明書リスト | 失効した証明書のシリアル番号、失効日時、失効理由など |
| 拡張領域 | CRL番号、デルタCRL指示子など |
| CAのデジタル署名 | 上記の内容に対する発行者CAの署名 |

実物は次のように見えます（`openssl crl -text` の出力の抜粋）。CRL に載るのは証明書そのものではなく**シリアル番号**であること、そして CRL 自体にも CA の署名が付いていて改ざんできないことを確認してください。

```
$ openssl crl -in tls-g2.crl -noout -text
Certificate Revocation List (CRL):
        Version 2 (0x1)
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: C=JP, O=Example Trust Inc., CN=Example TLS CA G2
        Last Update: Oct  2 12:00:00 2026 GMT          ← thisUpdate
        Next Update: Oct  3 00:00:00 2026 GMT          ← nextUpdate(12時間後)
        CRL extensions:
            X509v3 CRL Number:
                5821                                   ← CRL番号
Revoked Certificates:
    Serial Number: 0B12E4A0C3D9...                     ← 失効した証明書のシリアル番号
        Revocation Date: Sep 28 03:15:00 2026 GMT      ← 失効日時
        CRL entry extensions:
            X509v3 CRL Reason Code:
                Key Compromise                         ← 失効理由(秘密鍵の危殆化)
    Serial Number: 1F07A9B2...
        Revocation Date: Oct  1 09:40:00 2026 GMT
        CRL entry extensions:
            X509v3 CRL Reason Code:
                Superseded                             ← 失効理由(新しい証明書に置換)
    Signature Algorithm: sha256WithRSAEncryption
    Signature Value: 3a:7c:...                         ← CAのデジタル署名
```

> **デルタCRL**
> 失効した証明書が増えるとCRLのサイズが大きくなり、配布や取得の負荷が増大する。そこで、基準となるCRL（ベースCRL）の発行以降に追加された失効情報のみを差分として配布し、負荷を軽減する方法がある。この差分のみを記載したCRLを**デルタCRL**という。

### 5.2 CRLを利用する上での注意点

CRL を使う検証者が気をつけるべき点を、まとめておきます。

- **反映の遅れ**：失効してから次の CRL が発行されるまでの間（最大で更新間隔ぶん）は、失効した証明書が有効に見えます。
- **期限満了後の削除**：有効期限が満了した証明書は CRL から削除されるため、過去の時点の有効性を検証するには、その時点の CRL を保存しておく必要があります。
- **取得の負荷とサイズ**：失効が多い CA の CRL は大きくなり、端末の取得負荷が増えます（デルタCRLで軽減）。
- **取得できないときの扱い**：検証者が CRL を取得できなかったときに「有効とみなす（ソフトフェイル）」設定だと、攻撃者は CRL の取得を妨害するだけで失効確認をすり抜けられます。重要なシステムでは「取得できなければ接続しない（ハードフェイル）」を検討すべきです。

### 5.3 証明書有効性検証局（VA）

証明書有効性検証局は、一般に**VA**（Validation Authority）と呼ばれ、次のような役割を担うシステムや機関です。

- デジタル証明書の失効情報の集中管理
- CAの公開鍵による署名の検証
- デジタル証明書内に記載された有効期限の確認
- CRLの確認

利用者は、証明書の検証処理をVAに委ねることで、個々のCAからCRLを取得して照合する負担を軽減できます。複数の CA が発行した証明書を扱うシステム（たとえば、多くの取引先から署名付き文書を受け取るシステム）では、VA に検証を任せると、検証ロジックを一か所に集約できます。

### 5.4 OCSPレスポンダ

**OCSP**（Online Certificate Status Protocol）とは、デジタル証明書の有効性をリアルタイムで確認する仕組みであり、**RFC 6960**で規定されています。OCSPを実装したサーバを**OCSPレスポンダ**（OCSPサーバ）といい、CAやVAが運営します。クライアントはOCSPレスポンダに問い合わせることで、自力でCRLを取得・照合する手間を省くことができます。

OCSPレスポンダの仕組みを次に示します。

**図：OCSPレスポンダの仕組み**

```
 クライアント(ブラウザ等)                OCSPレスポンダ(CA/VAが運営)           CA
        │                                       │ ◀──①CRL(失効情報)を取り込む── │
        │──②OCSP要求(証明書のシリアル番号)──▶│                                   │
        │                                       │ 失効情報を検索                    │
        │◀─③OCSP応答(good/revoked/unknown)──│                                   │
        │      ＋レスポンダの署名                │                                   │
```

1. OCSPレスポンダは、あらかじめCRLを自身の中に取り込んでおきます。
2. クライアントは、有効性を確認したいデジタル証明書のシリアル番号をOCSPレスポンダに送信します（OCSPプロトコルが使われます）。
3. OCSPレスポンダは、有効性検証の結果（**good**／**revoked**／**unknown**）をクライアントに返答します。

OCSP 応答の実物は次のように見えます（`openssl ocsp` で問い合わせたときの出力の抜粋）。

```
$ openssl ocsp -issuer tls-g2.crt -cert www.example.com.crt -url http://ocsp.example.jp -resp_text
OCSP Response Data:
    OCSP Response Status: successful (0x0)
    Responder Id: CN=Example TLS CA G2 OCSP Responder
    Produced At: Oct  3 01:05:00 2026 GMT
    Responses:
    Certificate ID:
      Serial Number: 047A3C915E2BD8106FA233C49E017B55   ← 問い合わせた証明書のシリアル番号
    Cert Status: good                                   ← good / revoked / unknown
    This Update: Oct  3 01:00:00 2026 GMT
    Next Update: Oct 10 01:00:00 2026 GMT               ← この応答をキャッシュしてよい期限
    Signature Algorithm: sha256WithRSAEncryption       ← 応答にもレスポンダの署名が付く
www.example.com.crt: good
```

OCSPレスポンダ自身がボトルネックとならないように、通常はCRLの検索を高速化する仕組みなどが実装されています。

> **OCSPステープリング**
> TLS通信では、Webサーバが自らOCSPレスポンダから取得した応答（CAの署名付き）をTLSハンドシェイク時にクライアントへ提示する方式もある。これを**OCSPステープリング**（OCSP Stapling）という。クライアントがOCSPレスポンダへ直接問い合わせる必要がなくなるため、応答遅延の低減や、利用者の閲覧履歴がOCSPレスポンダに知られることの防止（プライバシ保護）に効果がある。

OCSP 応答には CA（またはレスポンダ）の署名が付いているため、Webサーバが中継しても改ざんできません。ステープル（ホチキス留め）という名前のとおり、サーバが「自分の証明書は今も有効です」という CA の証明を証明書に添えて渡すイメージです。TLS ハンドシェイクでの位置づけは第7章 7.4 を参照してください。

以前は「OCSPの実装状況は、OSやブラウザの種類及びバージョンによって異なる。例えば、Windows Vista以降かつIE7以降であれば、OCSPによってデジタル証明書の失効状態をリアルタイムに確認する機能が標準でサポートされている」と説明されていました。現在、IE（Internet Explorer）はサポートが終了しており、この例は古くなっています。実装状況が OS・ブラウザごとに異なる点は今も同じで、主要なブラウザの中には、OCSP への都度の問合せをやめ、ブラウザベンダーが集約した失効情報を配信する方式に移行しているものもあります。また、CA/Browserフォーラムの基準改定により、パブリックなサーバ証明書では CRL の提供が必須、OCSP は任意となり、OCSP の提供を終了した大手の CA もあります。試験では「CRL＝リストを取得して照合」「OCSP＝問合せてリアルタイムに確認」という原理の対比を押さえておけば十分です。

### 5.5 OCSPの限界とSCVP

OCSPレスポンダは、要求のあったデジタル証明書の**失効情報のみ**をチェックし、信頼関係（有効期限、署名など）についてはチェックしません。また、OCSPレスポンダはネットワーク上のすべてのCAが発行しているCRLを保持しているわけではありません。そのため、利用者が自主的に複数のOCSPレスポンダに問合せを行う必要が生じることもあります（下図参照）。

**図：複数のOCSPレスポンダへの問合せ**

```
                       ┌──▶ OCSPレスポンダA (CA-A のCRLのみ保持) … CA-A発行の証明書を確認
 クライアント ─────┼──▶ OCSPレスポンダB (CA-B のCRLのみ保持) … CA-B発行の証明書を確認
 (証明のパス上に複数   └──▶ OCSPレスポンダC (CA-C のCRLのみ保持) … CA-C発行の証明書を確認
  のCAがある場合)       ※ 有効期限・署名・パスの検証はクライアント自身が行う必要がある
```

これらの問題の解決策として、OCSPの拡張である**DPV**（Delegated Path Validation）や**DPD**（Delegated Path Discovery）といった方法や、**SCVP**（Simple Certificate Validation Protocol）などの新たなプロトコルが考案されています。

> **DPVとDPD**
> - **DPV（Delegated Path Validation）**：証明のパスの検証処理そのものをサーバに委任する方式
> - **DPD（Delegated Path Discovery）**：検証に必要な証明のパスの構築（探索）をサーバに委任し、検証はクライアント自身が行う方式

**SCVP**（Simple Certificate Validation Protocol）は、OCSPと同様に証明書の有効性検証をリアルタイムで行う仕組みであり、**RFC 5055**で規定されています。OCSPがデジタル証明書の失効情報のみをチェックするのに対し、SCVPでは有効期限や証明のパスの正当性も含めてチェックします。SCVP は、DPV と DPD の考え方を一つのプロトコルとして実現したものといえます。

### 5.6 CRL・OCSP・SCVP の比較

**表：失効確認の方式の比較**

| 項目 | CRL | OCSP | OCSPステープリング | SCVP |
|---|---|---|---|---|
| 規格 | X.509、RFC 5280 | RFC 6960 | TLS の拡張 | RFC 5055 |
| 誰が確認するか | 検証者（クライアント）がCRLを取得して自分で照合 | クライアントがOCSPレスポンダに問合せ | Webサーバが取得した応答をクライアントが確認 | クライアントがSCVPサーバに問合せ |
| 確認できる内容 | 失効情報（一覧） | 失効情報のみ（good/revoked/unknown） | 失効情報のみ | 失効情報＋有効期限＋証明のパスの正当性 |
| 鮮度 | CRLの更新間隔に依存（一般に12時間程度） | リアルタイム（ただしレスポンダが取り込むCRLの鮮度に依存） | サーバが取得した時点の応答 | リアルタイム |
| クライアントの負荷 | CRL のサイズが大きいと重い（デルタCRLで軽減） | 1件ずつの問合せで軽い | 問合せ不要で最も軽い | 検証処理を委任でき軽い |
| プライバシ | どの証明書を確認したかは CA に知られない | 閲覧先がレスポンダに知られる | 知られない | 問合せ先に知られる |
| オフライン環境 | 事前に取得したCRLで検証可能 | 不可 | サーバが応答を持っていれば可 | 不可 |

## 6. デジタル署名

### 6.1 デジタル署名の概要

ここからは、PKI が「何に使われるか」を見ていきます。最も基本的な使い道が**デジタル署名**です。デジタル署名は、ハッシュ関数とPKIの技術を組み合わせた電子的な署名です。送信者が電子メールや文書ファイルなどにデジタル署名を付すことで、受信者は次の点を確認できます。

- その文書ファイルなどを、本当にその人（送信者）が送ってきたのか（**本人性・真正性・否認防止**）
- 経路上で何者かによって改ざんされていないか（**完全性**）

否認防止が成り立つのは、署名を作れるのが秘密鍵の持ち主だけだからです。送信者が後から「私はそんな文書は送っていない」と主張しても、送信者の公開鍵で検証できる署名がある以上、その主張は通りません（第1章 1.2 の付加的特性）。ただし、これは「秘密鍵が本人以外に使われていない」ことが前提であり、秘密鍵の管理が否認防止の要になります。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後問1で、デジタル署名を題材に、なりすましが行われる手口とその対策に関する問題が出題されている。

### 6.2 デジタル署名の手順

デジタル署名は次の手順で行われます。

1. 送信者Aは、ハッシュ関数を用いて、送信する文書の**メッセージダイジェスト**（**MD**）を作成する。
2. 送信者Aは、作成したMDを送信者Aの秘密鍵で暗号化し、デジタル署名を作成する。
3. 送信者Aは、文書（平文）、デジタル署名、デジタル証明書を併せて送信する。
4. 受信者Bは、受信データから文書のみを取り出し、送信者と同じハッシュ関数を用いてMDを作成する（①と同じ作業）。
5. 受信者Bは、受信データからデジタル署名と送信者Aのデジタル証明書を取り出し、デジタル証明書に含まれる送信者Aの公開鍵を用いてデジタル署名を復号する。
6. 受信者Bは、④と⑤で得られた二つのMDを比較する。一致すれば、文書の完全性（改ざんされていないこと）と、送信者Aが送ったこと（本人性）が確認できる。

「秘密鍵で暗号化」「公開鍵で復号」という表現は、RSA 署名の仕組みに即した伝統的な説明です。ECDSA など RSA 以外の署名方式では「暗号化・復号」という操作にはならないため、一般には「秘密鍵で**署名を生成**し、公開鍵で**署名を検証**する」と表現します。試験ではどちらの表現も使われます。

> **ハッシュ関数の選択**：かつてはMD5などが用いられていたが、MD5や**SHA-1**は危殆化しているため、現在は**SHA-256**などのSHA-2系列や**SHA-3**を用いるのが一般的である（**CRYPTREC**暗号リストなどを参照。第7章 7.1）。

**図：デジタル署名の仕組み**

```
【送信者A】                                         【受信者B】
 文書 ──ハッシュ関数──▶ MD                             文書 ──ハッシュ関数──▶ MD ─┐
              │                                                                │ ⑥比較
       Aの秘密鍵で暗号化                                                        │ 一致すれば
              ▼                                                                │ 完全性・本人性を確認
        デジタル署名 ───────③ 文書＋署名＋証明書を送信──▶ デジタル署名           │
                                                            │                  │
                                                 Aの公開鍵（証明書）で復号       │
                                                            ▼                  │
                                                           MD ─────────────────┘
```

ハッシュ値（MD）は、文書が1文字でも変われば全く別の値になる、固定長のデータです。たとえば SHA-256 のハッシュ値は次のような64桁の16進数で表されます（値は例示）。文書全体ではなくこの短い値に署名するので、大きな文書でも署名処理が速く済みます。

```
$ sha256sum contract.pdf
3f8a1c0e9b7d42e6a5c1f0d38b2e7a9c4d6f1e0b8a3c5d7e9f1a2b3c4d5e6f70  contract.pdf
```

> **送信者のデジタル証明書の検証**
> 手順⑤で用いる送信者Aの公開鍵が正当であることを確認するため、受信者Bは、送信者Aのデジタル証明書についても、CAの署名、有効期限、失効状態（CRLやOCSP）、証明のパスを検証する必要がある。

この検証を省くと、攻撃者は「自分で作った鍵ペアで署名し、自分の公開鍵を『A の公開鍵』と称して添付する」だけでなりすませます。6.2 の⑥で MD が一致しても、それは「添付された公開鍵の持ち主が署名した」ことしか示さないからです。デジタル署名の安全性は、公開鍵の正当性を保証する PKI があって初めて成り立ちます。S/MIME による署名付きメール（第3章 3.4、第7章 7.5）でも、メールソフトはまさにこの手順で送信者の証明書を検証しています。

### 6.3 デジタル証明書の有効期間に関する留意点

デジタル署名の検証には、通常、送信者のデジタル証明書に登録されている公開鍵が用いられます。デジタル証明書には有効期限があり、期限が切れるとデジタル署名の検証が行えなくなるため、デジタル署名自体が無効になってしまいます。

そのため、署名者（証明書の所有者）は、デジタル証明書を署名の検証に用いる場合には、デジタル署名の有効期間を十分に確保できるよう、デジタル証明書の有効期間が十分に残っているうちに、次のデジタル証明書を発行（更新）する必要があります。この「証明書の期限を超えて署名を有効に保つ」問題を根本的に解決するのが、8節の長期署名の技術です。

なお、デジタル署名フォーマットの標準となっているのが、第7章 7.5（S/MIME）で解説した**CMS**（Cryptographic Message Syntax）です。また、CMS以外のデジタル署名方式として普及しているのが、次に示す「XMLデジタル署名」です。

### 6.4 XMLデジタル署名

**XMLデジタル署名**は、W3CとIETFが共同で標準化した、XML文書に対するデジタル署名の方式です。XMLデジタル署名では、署名対象や署名アルゴリズムをXMLで記述します。また、XML文書全体だけでなく、文書の一部（エレメント）に対しても署名できます。たとえば、複数の部署が順に承認する電子申請書で、各部署が自分の記入欄（エレメント）だけに署名する、といった使い方ができます。SAML のアサーション（第6章 6.9）にも XMLデジタル署名が使われています。

XML署名には、次の三つの形式があります。

| 署名形式 | 署名と署名対象の関係 | イメージ |
|---|---|---|
| **Enveloped署名** | 署名対象のオブジェクトの内部に署名が置かれる | 文書の中に署名が埋め込まれる（文書が署名を包む） |
| **Enveloping署名** | 署名の内部に署名対象のオブジェクトが置かれる | 署名が文書を包む |
| **Detached署名** | 署名対象のオブジェクトと署名が独立しており、オブジェクトはURI（Uniform Resource Identifier）で参照される | 署名と文書が別々で、参照でつながる |

```
Enveloped署名                Enveloping署名               Detached署名
<文書>                       <Signature>                  <Signature>
  <データ>…</データ>           <SignedInfo>…</SignedInfo>   <SignedInfo>
  <Signature>                  <SignatureValue>…            <Reference URI="http://
    <SignedInfo>…              <Object>                        www.example.jp/a.xml"/>
    <SignatureValue>…            <文書>…</文書>             </SignedInfo>
  </Signature>                 </Object>                    <SignatureValue>…
</文書>                      </Signature>                 </Signature>
```

> **Detached署名の補足**：署名対象はURIで参照されるため、別ファイルのデータだけでなく、署名と同じXML文書内にあるエレメントを署名対象にすることもできる。

## 7. コードサイニング（コード署名）の概要

ファームウェアをはじめ、配布するソフトウェアやコードなどの正当性や真正性を証明する技術として、**コードサイニング**があります。攻撃者は、正規のソフトウェアの配布サイトや更新サーバを乗っ取ってマルウェアを仕込んだ偽のプログラムを配布したり（サプライチェーン攻撃）、IoT機器に改ざんしたファームウェアを書き込んだりします。コードサイニングは、利用者や機器がこうした改ざんを実行前に見破るための仕組みです。

コードサイニングでは、ソフトウェアの開発元が、対象とするソフトウェアなどにデジタル署名を行い、署名に用いた秘密鍵と対になる公開鍵を、**コードサイニング証明書**としてソフトウェアとともに公開します。ソフトウェアの利用者は、次の手順で確認を行います。

1. コードサイニング証明書を検証し、正当な組織が公開したソフトウェアであることを確認する。
2. 検証済みのコードサイニング証明書に含まれる公開鍵を用いて、ダウンロードしたソフトウェアのデジタル署名を検証し、真正性（改ざんされていないこと）を確認する。

利用者が実際に目にするのは、たとえば Windows でプログラムを実行しようとしたときの確認画面です。署名があれば「確認済みの発行元：Example Corp.」と表示され、署名がない、または検証に失敗すると「発行元：不明」と警告されます。IoT機器では、機器自身が起動時やファームウェア更新時に署名を検証し、検証に失敗したファームウェアは書き込まない・起動しない（セキュアブート）ように設計します。

コードサイニングの安全性も、秘密鍵の管理にかかっています。開発元の署名用秘密鍵が盗まれると、攻撃者はマルウェアに「正規の署名」を付けて配布できます。開発元は、署名用の秘密鍵を HSM に格納し、署名を行える人と端末を限定し、署名の操作をログに記録すべきです。鍵の漏えいが判明したら、直ちに CA に証明書の失効を申請します。

> **試験に出る**
> 情報処理安全確保支援士試験の令和4年度午後問1で、IoT機器のファームウェアやアプリケーションへのコード署名に関する問題が出題された。

## 8. 電子文書の長期保存のための技術

### 8.1 電子文書の長期保存の必要性

企業や行政機関などの組織が活動を行う上では、様々な文書の作成・保存が法令によって義務付けられています。2005年に施行された**e-文書法**などにより、こうした法定文書を電子データで保存することが認められるようになりました（法令の詳細は第9章 9.5）。電子化によって、保管スペースやコストの削減、検索性・業務効率の向上など、様々な効果が期待されます。その反面、電子データの長期保存を前提とした場合、その特性に起因する多くの問題を解決しなければなりません。

### 8.2 電子文書の原本性確保及び長期保存における課題

従来、法定文書を電子データで保存することが認められていなかったのは、次のような電子データの特性によって、文書としての**原本性**が確保されないという問題があったためです。

- 電子データは完全な複製が可能である
- 電子データは作成日時の操作（偽造）が可能である
- 電子データは時間が経過しても劣化しない（原本と複製の区別がつかない）

→ 文書が作成された日時や作成者などを特定することが困難

これらの問題の幾つかを解決する技術として、デジタル署名があります。しかし、デジタル署名が保証できるのは、署名された電子文書を「誰が」作成したか（本人性）と、内容の完全性（第三者によって改ざんされていないこと）です。**「いつ」作成されたのかは保証できません**。コンピュータのシステム日付は、署名者が自由に設定できるためです。また、**本人による文書の改ざんを防げない**という問題もあります（署名者本人なら、内容を書き換えて署名し直せます）。加えて、デジタル署名は、関連するすべての公開鍵証明書が有効な期間内（通常は数年程度）でしか、その有効性を検証できません。

| 保証したいこと | デジタル署名 | タイムスタンプ | 両方を併用 |
|---|---|---|---|
| 誰が作成したか（本人性） | ○ | × | ○ |
| 改ざんされていないか（完全性） | ○（署名時点以降） | ○（付与時刻以降） | ○ |
| いつ存在したか（存在証明） | ×（システム日付は操作できる） | ○ | ○ |
| 本人による後からの改ざんの防止 | ×（署名し直せる） | ○（付与時刻以降の変更を検知） | ○ |

### 8.3 タイムスタンプとは

このようなデジタル署名の問題を解決するものとして、**タイムスタンプ**があります。タイムスタンプとは、信頼される第三者機関である**時刻認証局**（Time Stamp Authority：**TSA**）が電子文書に対して付す、時刻情報を含んだ電子データです。タイムスタンプは、その電子文書がその時刻に存在していたこと（**存在証明**）と、その時刻以降に改ざんされていないこと（**完全性証明**）を証明します。

> **タイムスタンプの信頼性を担保する認定制度**
> 一般財団法人日本データ通信協会の「**タイムビジネス信頼・安心認定制度**」は、**タイムビジネス**（時刻配信及び時刻認証業務の総称）を提供する事業者が、適切な技術・運用・設備の基準を満たし、業務を厳正に実施していることを認定するものである。現在は、総務大臣による時刻認証業務の認定制度に移行している（第9章 9.5 参照）。

デジタル署名とタイムスタンプを併用すれば、電子文書の原本性を確保できます。ただし、電子文書の長期保存には、まだ次のような大きな課題があります。

1. **電子文書を保存する記録媒体の劣化**
   現在広く使われている磁気テープ、光ディスク、磁気ディスクなどの記録媒体の寿命は、種別や保存環境、使用環境などの条件によって異なりますが、おおよそ10年から30年程度です。一方、法定文書には永久保存を求められるものもあります。そのため、文書の管理者は、媒体の劣化によって読み出せなくなる前に、新しい媒体に移行（**マイグレーション**）する必要があります。
2. **電子文書や媒体を取り扱う技術の陳腐化・衰退**
   ①の問題を解決しても、数十年後には、電子文書を作成したアプリケーションや記録媒体を読み込む装置などが既に存在しないか、使用できなくなっている可能性があります。したがって、特定ベンダーの技術から脱却し、長期保存が可能な標準的なファイル形式を採用する必要があります（具体的な解決策は 8.4）。
3. **ハッシュ関数や暗号技術の危殆化**
   時間の経過とともに、デジタル署名やタイムスタンプの基盤であるハッシュ関数や公開鍵暗号技術などが**危殆化**（脆弱化）し、電子文書や署名データが改ざんされる可能性があります。したがって、デジタル署名やタイムスタンプを長期間にわたって検証可能とする技術や仕組みを確立する必要があります（具体的な解決策は 8.7）。

### 8.4 電子文書の長期保存に適したファイル形式

電子文書の長期保存における要件や技術は、電子商取引推進協議会（**ECOM**）と**JIPDEC**電子商取引推進センターが発行した「電子文書の長期保存と見読性に関する調査報告書」（2004年3月）と「電子文書の長期保存と見読性に関するガイドライン」（2005年2月）にまとめられています。同報告書とガイドラインでは、電子文書の保存性と**見読性**を考慮した長期保存用の文書形式の要件として、次の四つを挙げています。

1. **人間可読なプレゼンテーションを記述できること**
   アプリケーションシステムだけが解釈できるデータ形式ではなく、人間が読み取る、あるいは聞き取ることが可能な文書形式であること。
2. **フォーマットが公開されていること**
   特定ベンダーなどのアプリケーションに依存せず、誰もが文書を正しく表示するアプリケーションを作成できること。
3. **正規表現可能な形式であること**
   様々な文書形式から変換できる、正規表現可能な形式であること。
4. **活用段階から保存段階への移行の連続性があること**
   文書を活用段階から保存段階へ移行する際に、情報の欠落や表現の変化などが発生しないことが望ましい。

また、上記の要件を考慮した推奨ファイル形式として、次の表の三つを挙げています。

**表：電子文書の長期保存において推奨されるファイル形式**

| ファイル形式 | 特徴 |
|---|---|
| **PDF/A**（PDF Archive）形式 | PDFはフォーマットが公開されており、各種の文書形式から変換できる。PDF形式の長期保存向け標準フォーマットとして、文書の表現に関するデータを自己完結的に保持する（フォントの埋め込みなど）PDF/Aの仕様が策定された（**ISO 19005**）。電子文書の活用段階ではPDF形式で利用し、保存段階に移行する際にPDF/A形式へ変換することが想定されている |
| イメージ形式（**TIFF**など） | イメージ形式にはBMP、JPEG、TIFFなど様々な形式がある。TIFFは比較的OSやアプリケーションに依存せずに利用でき、JPEGに比べて画像の劣化が少ないため、地図やマイクロフィルムのデータ変換サービスなどで利用されている。ただし、変換によって表現は保たれるものの、文字情報や構造情報など多くの情報が失われるため、移行の連続性には問題がある |
| **XML**形式 | XML自体はプレゼンテーションではなく、主に意味や構造を記述する言語である。しかし、プレゼンテーションを記述するための言語（**XSL**などのスタイルシート言語）を併用すれば、XMLでプレゼンテーションを扱える。フォーマットが公開されており、各種の文書形式と相互変換できる。文書の活用段階と保存段階で形式を変換する必要がない |

### 8.5 タイムスタンプの生成方法

前述のとおり、タイムスタンプは電子文書の存在時刻と完全性を証明するものです。タイムスタンプが発行されるまでの流れは、通常、次のようになります。

**図：タイムスタンプの発行の流れ**

```
 時刻配信局（TA）
      │ ③正確な時刻を配信
      ▼
 時刻認証局（TSA） ── ④ハッシュ値＋時刻情報からタイムスタンプを生成
      ▲         │
 ②ハッシュ値を送信  │ ⑤タイムスタンプを返信
      │         ▼
 タイムスタンプ取得要求者（A） ── ①電子文書のハッシュ値を生成
```

1. タイムスタンプの取得要求者（A）が、電子文書のハッシュ値を生成する。
2. Aは、①のハッシュ値を時刻認証局（TSA）に送る。
3. TSAは、**時刻配信局**（Time Authority：**TA**）から時刻を受け取り、常に正確な時刻を保持する。
4. TSAは、Aから受け取ったハッシュ値に時刻情報を連結したデータに、改ざん防止の処理を施したものをタイムスタンプとして生成する。
5. TSAは、生成したタイムスタンプをAに返信する。

> 取得要求者が送るのは電子文書そのものではなくハッシュ値であるため、文書の内容をTSAに開示することなくタイムスタンプを取得できる。

デジタル署名方式のタイムスタンプ（RFC 3161 のタイムスタンプトークン）の中身を要約すると、次のような項目が入っています。

```
タイムスタンプトークン(RFC 3161, デジタル署名方式)の主な項目
  ポリシ ............ TSA の運用ポリシの識別子
  メッセージインプリント ... ハッシュアルゴリズム(SHA-256) と 文書のハッシュ値
  シリアル番号 ........ TSA がトークンごとに付ける一意の番号
  生成時刻(genTime) .... 2026-10-03 01:23:45.123Z   ← TAから受け取った正確な時刻
  精度 ................ ±1秒
  TSA名 ............... CN=Example Time Stamp Authority, O=Example Trust Inc., C=JP
  TSAのデジタル署名 ..... 上記全体に対する署名(TSA証明書の秘密鍵で生成)
```

④のタイムスタンプの生成方式には、次の三つがあります。

- **Time-Stamp Protocol**（**TSP**、**RFC 3161**）に準拠し、デジタル署名を用いる**デジタル署名方式**
- 不特定多数のハッシュ値を相互に関連付けるリンク情報に基づいてタイムスタンプを生成する**リンキング方式**
- TSAがハッシュ値と正確なタイムスタンプ付与時刻を特定する情報を安全に記録・保管する**アーカイビング方式**

### 8.6 タイムスタンプの3方式と検証手順

各方式の概要と、タイムスタンプの検証手順を次に示します。

**デジタル署名方式**

TSAがタイムスタンプを生成する際、CAから公開鍵証明書の発行を受けた専用の暗号鍵を用いて、各タイムスタンプにデジタル署名を施す方式です。このデジタル署名によって、タイムスタンプの信頼性を確保します。

〈タイムスタンプの検証手順〉

1. 検証者（タイムスタンプ保有者）が、タイムスタンプ付与対象文書のハッシュ値を確認する。
2. 検証者が、タイムスタンプに付与されたデジタル署名を検証する。
3. 検証者が、TSA証明書の失効情報を含む証明書パスを検証する。

> **試験に出る**
> 情報処理安全確保支援士試験（旧 情報セキュリティスペシャリスト試験）の午後問題で、タイムスタンプの仕組みと検証に関する問題が出題されている。

**リンキング方式**

TSAが、不特定多数のタイムスタンプ付与対象文書のハッシュ値を相互に関連付けるリンク情報を生成し、それをタイムスタンプに含める方式です。リンク情報は照合用データとしても保管され、これによってタイムスタンプの信頼性を確保します。後から特定の文書の時刻だけを書き換えようとしても、前後の文書のハッシュ値とつながっているため、整合性が崩れて発覚します。

〈タイムスタンプの検証手順〉

1. 検証者が、タイムスタンプ付与対象文書のハッシュ値を確認する。
2. 検証者が、タイムスタンプを含む照合要求情報をTSAへ送る。
3. TSAが、送られてきたタイムスタンプに含まれるハッシュ値とリンク情報が、保管している照合用データと整合しているかを照合する。
4. TSAが、照合結果情報を検証者へ通知する。

**アーカイビング方式**

TSAが、サービス利用者から受け取ったタイムスタンプ付与対象文書のハッシュ値と、正確なタイムスタンプ付与時刻を特定する情報を照合用データとして安全に記録・保管し、タイムスタンプの検証に用いる方式です。

〈タイムスタンプの検証手順〉

1. 検証者が、タイムスタンプ付与対象文書のハッシュ値を確認する。
2. 検証者が、タイムスタンプを含む照合要求情報をTSAへ送る。
3. TSAが、送られてきたタイムスタンプと、そこに含まれるインデックス情報で特定される照合用データとを照合する。
4. TSAが、照合結果情報を検証者へ通知する。

> リンキング方式とアーカイビング方式は、検証時にTSAへの問合せが必要となる。デジタル署名方式は、検証者が自らタイムスタンプを検証できる。

| 比較 | デジタル署名方式 | リンキング方式 | アーカイビング方式 |
|---|---|---|---|
| 信頼性を確保する仕組み | TSA のデジタル署名 | ハッシュ値同士を関連付けるリンク情報 | TSA が保管する照合用データ |
| 検証する者 | 検証者が自ら検証できる | TSA に照合を依頼 | TSA に照合を依頼 |
| 検証に必要なもの | TSA証明書と失効情報（証明書パス） | TSA の照合用データ | TSA の照合用データ |
| 弱点 | TSA証明書の有効期限・暗号の危殆化 | TSA の存続に依存 | TSA の存続に依存 |
| 規格 | RFC 3161（TSP） | － | － |

### 8.7 デジタル署名やタイムスタンプを長期間にわたって検証可能とするための技術や仕組み

デジタル署名は、ある時点での電子文書の真正性を証明できる技術です。しかし前述のように、時間の経過とともに、署名に関連する公開鍵証明書の有効期限切れや失効、ハッシュ関数や暗号技術の危殆化などによって、その有効性が失われてしまいます。電子文書の存在時刻と完全性を証明するタイムスタンプも同様であり、TSAの公開鍵証明書の有効期限（通常は10年程度）を過ぎたり、暗号アルゴリズムが危殆化したりすれば、有効性を検証できなくなります。

過去のある時点でデジタル署名が有効であったことを検証するには、その署名に対する公開鍵証明書が、当時有効であったことが保証されていなければなりません。そして公開鍵証明書の有効性を検証するには、その証明書からルート証明書（ルートCAの証明書）に至るまでのパス上のすべての公開鍵証明書と、それらの失効情報を確認する必要があります（4.2 のチェーンを、過去の時点で再現するということです）。

つまり、過去のある時点でデジタル署名が有効であったことを検証するには、次のデータをすべて集め、それらにタイムスタンプを付与しておく必要があります。このタイムスタンプを**アーカイブタイムスタンプ**といいます。

- 署名済みの電子文書
- 署名済みの電子文書に対するタイムスタンプ（**署名タイムスタンプ**）
- 署名検証のための参照情報（パス上の公開鍵証明書や失効情報への参照情報）
- 署名検証のための公開鍵証明書と失効情報（CRL、OCSPレスポンダの応答結果など）

アーカイブタイムスタンプのイメージを次に示します。

**図：アーカイブタイムスタンプのイメージ**

```
┌───────────────────────────────────────────────┐
│ アーカイブタイムスタンプ（2回目）                  │
│ ┌───────────────────────────────────────────┐ │
│ │ アーカイブタイムスタンプ（1回目）              │ │
│ │ ┌───────────────────────────────────────┐ │ │
│ │ │ 検証情報（公開鍵証明書・CRL/OCSP応答）      │ │ │
│ │ │ 検証のための参照情報                      │ │ │
│ │ │ 署名タイムスタンプ                        │ │ │
│ │ │ 署名済みの電子文書（文書＋デジタル署名）     │ │ │
│ │ └───────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────┘ │
└───────────────────────────────────────────────┘
```

アーカイブタイムスタンプにも有効期限があり、暗号アルゴリズムが危殆化するおそれもあります。そのため、文書の管理者は、アーカイブタイムスタンプの有効期限が切れる前、又は使用している暗号アルゴリズムが危殆化する前に、それまでのデータ全体に対して次のアーカイブタイムスタンプを取得する必要があります。この作業は、電子文書を保存している限り、必要に応じて繰り返し行わなければなりません。

なぜこれで有効性が保てるのでしょうか。2回目のアーカイブタイムスタンプは、「1回目のアーカイブタイムスタンプがまだ有効で、暗号も安全だった時点で、このデータ全体が存在していた」ことを、新しい（安全な）アルゴリズムで証明します。こうして、古い署名やタイムスタンプが検証できなくなる前に、新しい証明で「上書きではなく外側から包む」ことを繰り返すことで、何十年にもわたって「当時は有効だった」ことを示し続けられるのです。

アーカイブタイムスタンプは、デジタル署名のフォーマットを拡張した**長期署名フォーマット**に則って生成されます。

> **長期署名フォーマット**：**ETSI**（欧州電気通信標準化機構）が規定した**CAdES**（CMSベース）、**XAdES**（XML署名ベース）、**PAdES**（PDFベース）がある。国内では**JIS X 5092**（CAdES）、**JIS X 5093**（XAdES）として規格化されている。

> **Column：ヒステリシス署名**
> **ヒステリシス**（Hysteresis：履歴）**署名**とは、デジタル署名を付与する際に、過去のすべての署名情報を取り込んで、署名間の連鎖構造を作る技術である。ヒステリシス署名では、あるデジタル署名の有効期限が切れても、署名間の連鎖構造を検証することで文書の改ざんを検知できる。そのため、単独の署名を行うよりも、長期間にわたってデジタル署名の有効性を維持できる。

- **Q3**：CAとRAはそれぞれどのような役割を担うのか。
- **Q4**：CRLとはどのような用途に使用するのか。
- **Q5**：CRLを利用する上での注意点とは何か。

> **解答例**
> - Q1：公開鍵とその所有者の結びつきを、CAのデジタル署名によって保証する電子的な身分証明書であり、クライアントやサーバの認証、TLSの鍵交換、S/MIMEの署名・暗号化、コード署名などに使用する（本ノート 2 節）。
> - Q2：認証局（CA）、登録局（RA）、証明書失効リスト（CRL）、証明書有効性検証局（VA）、OCSPレスポンダ、リポジトリ（本ノート 4.1）。
> - Q3：CAは証明書の発行・失効、CRLの発行、CPSの公開、自身の証明書の公開と秘密鍵の管理を担い、保持者と公開鍵の結びつきを保証する。RAは発行・失効の資格審査、利用者情報の登録、鍵の一括管理、ディレクトリへの保管、証明書や鍵の配付を担い、保持者の身元を保証する（本ノート 4.2、4.5）。
> - Q4：有効期限内に失効させた証明書のシリアル番号・失効日時・失効理由を列挙したリストであり、検証者が証明書の失効の有無を確認するために使用する（本ノート 5.1）。
> - Q5：更新間隔の間は失効が反映されないこと、有効期限が満了した証明書はCRLから削除されるため過去の時点の検証にはその時点のCRLが必要なこと、CRLが大きくなると取得負荷が増えること（本ノート 5.1、5.2）。
> - Q6：証明書のシリアル番号を問い合わせ、失効状態（good/revoked/unknown）をリアルタイムで確認するために使用する。クライアントがCRLを取得・照合する手間を省ける（本ノート 5.4）。
> - Q7：本人性・真正性・否認防止（その人が送ったこと）と、完全性（改ざんされていないこと）（本ノート 6.1）。
> - Q8：送信者の証明書のCAの署名・有効期限・失効状態・証明のパスを検証すること。証明書の有効期限が切れると署名を検証できなくなるため、有効期間が十分残っているうちに更新すること（本ノート 6.2、6.3）。
> - Q9：時刻認証局（TSA）が電子文書に付す時刻情報を含んだ電子データであり、その時刻に文書が存在したこと（存在証明）と、その時刻以降に改ざんされていないこと（完全性証明）を保証する（本ノート 8.3）。
> - Q10：電子データは完全な複製や作成日時の偽造が可能で劣化もしないため原本性の確保が難しいこと。加えて、記録媒体の劣化、文書や媒体を扱う技術の陳腐化・衰退、ハッシュ関数や暗号技術の危殆化（本ノート 8.2、8.3）。
> - Q11：PDF/A形式、イメージ形式（TIFFなど）、XML形式（本ノート 8.4）。

### 9.2 確認問題1

デジタル証明書に関する記述のうち、適切なものはどれか。

- ア　S/MIMEやTLSで利用するデジタル証明書の規格は、ITU-T X.400で標準化されている。
- イ　TLSにおいて、デジタル証明書は、通信データの暗号化のための鍵交換や通信相手の認証に利用されている。
- ウ　認証局が発行するデジタル証明書は、申請者の秘密鍵に対して認証局がデジタル署名したものである。
- エ　ルート認証局は、下位の認証局の公開鍵にルート認証局の公開鍵でデジタル署名したデジタル証明書を発行する。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> デジタル証明書はITU-T勧告のX.509で定義されており、発行の際には、申請者の公開鍵に対して認証局（CA）がデジタル署名を付す。デジタル証明書は、TLSで通信データの暗号化のための鍵交換や通信相手の認証に利用されるほか、S/MIMEでメールの暗号化やデジタル署名などに利用されている。したがって**イ**が正解。
>
> - ア：X.400はメッセージ通信処理システム（MHS）に関する勧告である。
> - ウ：認証局が署名するのは、申請者の秘密鍵ではなく公開鍵である。
> - エ：ルート認証局は、自身の公開鍵ではなく秘密鍵でデジタル署名する。

### 9.3 確認問題2

PKIを構成するOCSPを利用する目的はどれか。

- ア　誤って破棄してしまった秘密鍵の再発行処理の進捗状況を問い合わせる。
- イ　デジタル証明書から生成した鍵情報の交換が、OCSPクライアントとOCSPレスポンダの間で失敗した際、認証状態を確認する。
- ウ　デジタル証明書の失効情報を問い合わせる。
- エ　有効期限の切れたデジタル証明書の更新処理の進捗状況を確認する。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> OCSPとは、デジタル証明書の失効情報をリアルタイムで確認する仕組みである。OCSPの応答を返すサーバをOCSPレスポンダ（OCSPサーバ）といい、CA（Certification Authority）やVA（Validation Authority：検証局）が運営する。クライアントはOCSPレスポンダに問い合わせることで、デジタル証明書が失効していないかを確認できる。したがって**ウ**が正解。

### 9.4 確認問題3

X.509におけるCRLに関する記述のうち、適切なものはどれか。

- ア　RFC 5280では、発行したデジタル証明書のうち失効したものについて、シリアル番号を失効後1年間CRLに記載するよう義務付けている。
- イ　Webサイトの利用者のWebブラウザは、そのWebサイトにサーバ証明書を発行した認証局の公開鍵がWebブラウザに組み込まれていれば、CRLを参照しなくてもよい。
- ウ　認証局は、発行した全てのデジタル証明書の有効期限をCRLに記載する。
- エ　認証局は、有効期限内のデジタル証明書が失効されたとき、そのシリアル番号をCRLに記載する。

*〔情報処理安全確保支援士試験・令和6年度春期〕*

> **解答・解説**
> CRLとは、秘密鍵の漏えいやデジタル証明書の悪用・誤発行などの不測の事態によって、有効期限内に失効させる必要が生じた証明書を登録したリストである。CRLには、その証明書のシリアル番号と失効した日時が掲載される。CRLに登録された証明書の情報は、その証明書の有効期限が満了した時点でCRLから削除される。したがって**エ**が正解。
>
> - ア：RFC 5280に「失効後1年間記載する」という義務はない。
> - イ：認証局の公開鍵が組み込まれていても、証明書の失効状態は確認する必要がある。
> - ウ：CRLに記載されるのは失効した証明書だけであり、発行した全証明書の有効期限ではない。

### 9.5 確認問題4

XMLデジタル署名の特徴として、適切なものはどれか。

- ア　XML文書中のエレメントに対するデタッチ署名（Detached Signature）を、同じXML文書に含めることができる。
- イ　エンベローピング署名（Enveloping Signature）では、一つの署名対象に必ず複数の署名を付与する。
- ウ　署名の書式として、CMS（Cryptographic Message Syntax）を用いる。
- エ　デジタル署名では、署名対象と署名アルゴリズムをASN.1によって記述する。

*〔情報処理安全確保支援士試験・令和5年度秋期〕*

> **解答・解説**
> XMLデジタル署名は、W3C（World Wide Web Consortium）とIETFが標準化した署名方式であり、署名対象や署名アルゴリズムをXMLで記述する。デタッチ署名では署名対象をURIで参照するため、同じXML文書中のエレメントを署名対象とし、その署名を同じXML文書に含めることができる。したがって**ア**が正解。
>
> - イ：エンベローピング署名は、署名の内部に署名対象を置く形式であり、複数の署名を必須とするものではない。
> - ウ：CMSはS/MIMEなどで用いられる署名書式であり、XMLデジタル署名の書式ではない。
> - エ：XMLデジタル署名ではASN.1ではなくXMLで記述する。

### 9.6 確認問題5

PKIを構成するRA（Registration Authority）の役割はどれか。

- ア　デジタル証明書にデジタル署名を付与する。
- イ　デジタル証明書に紐づけられた属性証明書を発行する。
- ウ　デジタル証明書の失効リストを管理し、デジタル証明書の有効性を確認する。
- エ　本人確認を行い、デジタル証明書の発行申請の承認又は却下を行う。

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> RA（登録局）は、次のような役割を担っている。
>
> - 証明書の発行や失効などに関する資格審査の実施
> - デジタル証明書利用者の情報の登録
> - 鍵の一括管理
> - 公開鍵を公開するためのディレクトリへの保管
> - 証明書や鍵の配付
>
> CA（Certification Authority）がデジタル証明書の保持者と公開鍵の結び付きの信頼性を保証するのに対し、RAはデジタル証明書保持者の身元を保証する。RAの役割をCAが兼ねる場合もある。したがって**エ**が正解。
>
> - ア：CA（IA）の役割である。
> - イ：AA（属性認証局）の役割である。
> - ウ：CA（CRLの発行）や VA の役割である。

### 9.7 確認問題6

公開鍵基盤におけるCPS（Certification Practice Statement）に該当するものはどれか。

- ア　認証局が発行するデジタル証明書の所有者が策定したセキュリティ宣言
- イ　認証局でのデジタル証明書発行手続を代行する事業者が策定したセキュリティ方針
- ウ　認証局の認証業務の運用などに関する詳細を規定した文書
- エ　認証局を監査する第三者機関の運用などに関する詳細を規定した文書

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> CPS（認証局運用規程）とは、CA（認証局）などの信頼される第三者機関が、認証を利用する者に対して、自らの認証業務の運用方法や手続、責任範囲などの詳細を規定して公開する文書である。したがって**ウ**が正解。
>
> **CPとCPSの関係**：CP（Certificate Policy：証明書ポリシー）は、証明書の適用範囲や利用条件などの方針を定めたものである。CPSは、そのCPを実現するための具体的な運用手順を定めたものである。いずれもRFC 3647で枠組みが示されている。

## 10. 試験対策まとめ（重要ポイント）

### 10.1 知識の確認（科目A-2向け）

- **PKI の目的**：公開鍵と所有者の結びつき（鍵の正当性）を、信頼できる第三者（CA）の署名で保証し、なりすましや中間者攻撃を防ぐ。
- **デジタル証明書**：ITU-T X.509（現在は X.509v3、インターネットでは RFC 5280）。CA が**申請者の公開鍵**に**CAの秘密鍵**で署名したもの（「秘密鍵に署名」「公開鍵で署名」は誤り。X.400 はメッセージ通信の勧告）。
- **X.509v3 の主な項目**：バージョン、シリアル番号、署名アルゴリズム、Issuer、有効期間（notBefore/notAfter）、Subject、公開鍵情報、拡張領域（鍵用途、SAN、CRL配布点、AIA）、CAの署名。ブラウザは CN ではなく SAN を照合する。
- **CSR**：公開鍵＋コモンネーム（FQDN）・組織名・部門名・市区町村名・都道府県名・国別番号。申請者の秘密鍵で署名され、秘密鍵の保有を示す。秘密鍵は CSR に含まれない。
- **ブラウザの検証4項目**：有効期間、FQDN と CN/SAN の一致、失効していないこと（CRL/OCSP）、信頼できる CA までの証明のパス。
- **CT（RFC 9162、当初 RFC 6962）**：CA が CT ログに証明書を登録し、SCT を受け取る。不正発行を「検知」する仕組み。
- **AC（属性証明書）と PMI**：AA が発行し、役割・権限を証明する。失効は ACRL。公開鍵証明書より短いサイクルで変わる属性を分離する。証明書では取引相手の信用度は分からない。
- **DV／OV／EV**：ドメインの使用権のみ／＋組織の実在性／＋CA/Browserフォーラムのガイドラインに基づく厳格な確認。暗号の強さは同じ。EV の緑色表示は廃止済み。
- **CA の階層とトラストアンカー**：ルートCA（自己署名）→中間CA→エンドエンティティ。証明のパスをルートCAまでたどる。トラストアンカーはルート証明書ストアに組み込まれたルートCA証明書。
- **CP と CPS**：CP＝証明書発行の方針（What）、CPS＝認証局の運用の詳細（How）。枠組みは RFC 3647。
- **パブリックCAとプライベートCA**：前者は商用・ルート証明書が OS/ブラウザに組込み済み。後者は組織内のみで、ルート証明書の配布が必要。
- **RA と IA**：RA は身元の審査・登録（発行申請の承認・却下）。IA は審査結果に基づき証明書を発行する機能。CA は公開鍵と保持者の結びつきを保証。
- **CRL**：有効期限内に失効させた証明書のシリアル番号・失効日時・失効理由のリスト（ブラックリスト）。thisUpdate/nextUpdate。期限満了で削除される。一般に12時間ごと更新。差分はデルタCRL。
- **VA**：失効情報の集中管理、署名検証、有効期限確認、CRL確認を代行する。
- **OCSP（RFC 6960）**：シリアル番号で問い合わせ、good/revoked/unknown を返す。失効情報のみを確認する。OCSPステープリングは Webサーバが応答を TLS ハンドシェイクで提示する（遅延低減・プライバシ保護）。
- **SCVP（RFC 5055）**：失効情報に加え、有効期限や証明のパスの正当性まで検証する。DPV は検証を委任、DPD はパスの探索を委任（検証は自分）。
- **デジタル署名**：本人性・真正性・否認防止と完全性を確認する。「いつ」は保証しない。ハッシュ関数は SHA-256 などの SHA-2 系列や SHA-3（MD5、SHA-1 は危殆化）。
- **XMLデジタル署名**：W3C と IETF が標準化。XML で記述（ASN.1 ではない、CMS でもない）。エレメント単位で署名可。Enveloped（文書の中に署名）、Enveloping（署名の中に文書）、Detached（URI で参照。同じ文書内のエレメントも可）。
- **コードサイニング**：証明書を検証して発行元を確認し、その公開鍵で署名を検証して改ざんがないことを確認する。
- **タイムスタンプ**：TSA が付与し、存在証明と完全性証明を行う。TA から時刻を受ける。要求者はハッシュ値だけを送る。方式はデジタル署名方式（RFC 3161、自分で検証可）、リンキング方式、アーカイビング方式（後二者は TSA に照合を依頼）。
- **長期保存のファイル形式**：PDF/A（ISO 19005）、イメージ形式（TIFF など）、XML 形式（XSL 併用）。要件は人間可読・フォーマット公開・正規表現可能・移行の連続性。
- **アーカイブタイムスタンプと長期署名フォーマット**：署名済み文書、署名タイムスタンプ、参照情報、証明書と失効情報をまとめてタイムスタンプを付け、期限切れ・危殆化の前に繰り返す。CAdES・XAdES・PAdES（ETSI）、JIS X 5092・JIS X 5093。ヒステリシス署名は署名間の連鎖構造で長期の有効性を維持する。

### 10.2 記述式で問われる観点（科目B向け）

- **ブラウザの警告の原因を特定する**：「証明書の SAN にアクセスした FQDN が含まれていない」「有効期限が切れている」「中間CA証明書がサーバに設定されておらず、ルートCAまでの証明のパスを構築できない」「自己署名証明書でありトラストアンカーにたどれない」のどれかを、事例の記述から根拠を示して答える。
- **秘密鍵の漏えい時の対応**：「サーバ管理者は直ちに CA に証明書の失効を申請し、新しい鍵ペアを生成して CSR を作り直し、証明書を再発行してもらう。古い鍵のまま再発行しても、漏えいした秘密鍵によるなりすましを防げないためである。」
- **CRL の限界を指摘する**：「CRL は更新間隔ごとに発行されるため、失効から次の発行までの間は失効した証明書が有効と判定されるおそれがある。リアルタイムに確認するには OCSP を用いる。」
- **OCSPステープリングを採用する理由**：「クライアントが OCSP レスポンダに問い合わせる必要がなくなるため、接続時の遅延を減らし、利用者の閲覧先がレスポンダに知られることを防げる。」
- **中間CAを置く理由**：「ルートCAの秘密鍵をオフラインで保管して漏えいリスクを下げ、中間CAの鍵が漏えいした場合でもその中間CA証明書の失効で影響範囲を限定できるため。」
- **プライベートCAを構築するときの留意点**：「CA の秘密鍵を HSM 等で厳重に管理し、CP/CPS を定め、RA による申請者の本人確認、失効の手順と CRL/OCSP の提供、ルート証明書の端末への配布を計画する。」
- **自己署名証明書の運用が危険な理由**：「利用者が証明書の警告を無視する習慣がつき、中間者攻撃で偽の証明書が提示されても気づけなくなるため。プライベートCAで発行した証明書を使い、警告が出ない状態にすべきである。」
- **CT ログを監視する目的**：「自組織のドメインに対して身に覚えのない証明書が発行されていないかを検知し、不正に発行された証明書を CA に失効させるため。」
- **DV 証明書の限界**：「DV 証明書はドメインの使用権しか確認しないため、紛らわしいドメインを取得した攻撃者も取得できる。HTTPS であることは運営者の信頼性を保証しない。」
- **デジタル署名で受信者が確認すべきこと**：「署名の検証に加え、添付された送信者の証明書について、CA の署名、有効期限、失効状態、証明のパスを検証する。検証しないと、攻撃者が自分の公開鍵を送信者のものと偽って添付するなりすましを見抜けない。」
- **コード署名の鍵管理**：「署名用の秘密鍵が盗まれるとマルウェアに正規の署名を付けて配布されるため、HSM に格納し、署名操作を行える者と端末を限定し、操作ログを記録する。」
- **タイムスタンプを併用する理由**：「デジタル署名は作成者と完全性を保証するが、作成時刻はシステム日付を操作できるため保証できず、署名者本人による改ざんも防げない。TSA のタイムスタンプで存在時刻と、それ以降の非改ざんを証明する。」
- **長期保存で繰り返し行う作業**：「証明書の有効期限切れや暗号アルゴリズムの危殆化の前に、署名済み文書・署名タイムスタンプ・検証用の証明書と失効情報を含むデータ全体に、新たなアーカイブタイムスタンプを付与する。」
