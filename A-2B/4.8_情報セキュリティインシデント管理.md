# レクチャーノート：情報セキュリティマネジメントの実践 ― 4.8 情報セキュリティインシデント管理

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ管理」（知識項目例：情報セキュリティ組織・機関〈CSIRT、SOC ほか〉、情報セキュリティ継続 ほか）、「情報セキュリティ対策」（知識項目例：ログ管理、マルウェア・不正プログラム対策、ランサムウェア対策、セキュリティ製品・サービス〈SIEM ほか〉、デジタルフォレンジックス ほか）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

4.5〜4.7 では、情報資産・物理環境・人に対する「予防」の管理策を学びました。しかし 1.2 で確認したとおり、どれほど対策を施してもインシデントの発生を完全に防ぐことは不可能です。情報セキュリティに関する事件・事故など（**インシデント**）による損害を最小限に抑えるには、組織は予防策を講じるとともに、**インシデント発生時の対応方法をあらかじめ定めておく**必要があります。火事が起きてから消火器の置き場所を探し始める組織は、被害を広げてしまいます。

インシデント対応で問われるのは、つまるところ「**誰が、いつ、何を判断し、何を指示するか**」です。本ノートは、この問いに答えられるよう次の順で進みます。

1. **誰が対応するか**：CSIRTとSOCの役割、外部組織（JPCERT/CC、ISAC など）との連携、発見者・部門長・経営層の役割分担
2. **どう対応するか**：インシデント管理の6段階（①備え → ②検知・連絡受付 → ③トリアージ → ④影響範囲の特定・応急処置 → ⑤対応策の決定・実施 → ⑥収束後の対応）と、各段階で使う書類・判断表・ログの実物
3. **証拠をどう残すか**：デジタルフォレンジックスの手順と揮発性の順序（RFC 3227）
4. **どう強くなるか**：サイバーレジリエンスとOODAループ

科目Bの業務観点では「④情報セキュリティインシデント管理の推進又は支援」（管理体制の構築、事象の評価〈検知・連絡受付、初動対応、インシデント判断、優先順位〉、対応〈原因特定、復旧、報告・情報発信、再発防止〉、証拠の収集と分析）にそのまま対応します。科目Bでは毎回のようにインシデント対応の事例が出題され、「この時点でCSIRTは何をすべきか」「なぜPCの電源を切ってはいけないか」「どの順で証拠を保全するか」を記述させます。科目A-2では、揮発性の順序、SIM3、問題管理とインシデント管理の区別、OODAループが問われます。本ノートは、他のノートより記述式の観点を厚めにしています。

## 1. 誰が対応するのか ― CSIRTとSOC

### 1.1 CSIRTの役割

4.4「情報セキュリティのための組織」で見たように、情報セキュリティインシデント（以下「インシデント」）に対応するため、**CSIRT**（Computer Security Incident Response Team）を設置する組織が増えています。

広義のCSIRTには、国際連携を行うCSIRTや、CSIRT間の情報連携を行う「**コーディネーションセンター**」等も含まれます。ここでは、特定の組織で活動する「**組織内CSIRT**」を前提として説明します。

特定の組織におけるCSIRTには、次の役割が求められます。

- インシデント発生時に**対応を主導する**。
- 情報を集約し、顧客、株主、経営者、監督官庁等に**適時報告する**。
- 現場組織等に**適時対応を指示する**。

つまりCSIRTは、自ら手を動かすだけのチームではなく、**情報の集約点であり、指示の発信点**です。現場の部門やシステム管理者が個別に判断して動くと、ある部門は機器を再起動して証拠を消し、別の部門は未確認の情報を顧客に伝える、といった混乱が起きます。CSIRTが一元的に判断し指示することで、組織としての対応が一貫します。

インシデント発生時の対応だけでなく、**平常時の活動**もCSIRTの重要な役割です。CSIRTは、情報セキュリティに関する最新情報を収集したり、外部のセキュリティベンダーや関連機関、ISAC等の業界団体、他のCSIRT等と連携して情報を共有したりして、インシデント発生に備えます。加えて、インシデント収束後には再発防止のための対応なども求められます。

なお、上記のようなCSIRTが行う一連の業務をまとめて「**インシデントマネジメント**」もしくは「**インシデントハンドリング**」と呼ぶことがあります（後述の図では、②〜⑤の対応を狭い意味でのインシデントハンドリングとしています）。

> **試験に出た**
> 情報処理安全確保支援士試験の午後問2で、サイバー攻撃を利用したインシデントへの対応に関する問題が出題された。

### 1.2 CSIRTの成熟度評価 ― SIM3

CSIRTを作っただけで機能するとは限りません。組織のCSIRTが「どこまで育っているか」を測るモデルとして、Open CSIRT Foundation が開発した **SIM3**（Security Incident Management Maturity Model）があります。SIM3 では、**組織**（Organisation）、**人**（Human）、**ツール**（Tools）、**プロセス**（Processes）の4分類について評価項目が設定されています。CSIRTの成熟度は、評価項目ごとに**レベル0〜4の5段階**で評価します。CISOは、SIM3 で自組織のCSIRTを評価し、弱い項目（たとえば「プロセス」の中の「インシデント報告の手順が文書化されていない」）を改善計画に反映させる、という使い方をします。

### 1.3 CSIRTを取り巻く組織

組織内CSIRTは単独で動くわけではありません。攻撃者は同じ手口を複数の組織に使い回すため、ある組織で観測された攻撃の情報（攻撃元のIPアドレス、マルウェアのハッシュ値、フィッシングメールの件名など）を他の組織が早く知れば、同じ被害を防げます。CSIRT同士が連携するのはこのためです。

> **用語解説：ISAC（Information Sharing and Analysis Center）**
> 金融、通信、電力など、同じ業界に属する組織同士が、サイバー攻撃や脆弱性などのセキュリティ情報を共有・分析するための組織。金融ISAC、ICT-ISACなどがある。

**図：CSIRT及び関連組織間の連携イメージ**

```
  [海外のCSIRT/コーディネーションセンター]
                  │ 国際連携
       [JPCERT/CC(コーディネーションセンター)]
                  │ 情報連携
 ┌────────┬────────┼────────┬────────┐
[ISAC]  [日本シーサート協議会]  [他社CSIRT]  [セキュリティベンダー]
                  │
          [組織内CSIRT] ── [SOC(内部/外部)]
                  │
   [経営者・現場組織・顧客・監督官庁 等]
```

> **用語解説：JPCERT/CC（JPCERTコーディネーションセンター）**
> 日本国内のインシデントに関する報告の受付、対応の支援、手口の分析、再発防止策の検討・助言などを行う組織。特定の政府機関や企業から独立した中立の立場で活動している。国内のCSIRT間の連携に加え、海外のCSIRTとの国際連携の窓口として、コーディネーションセンターの役割も担う。

**日本シーサート協議会**は、国内の組織内CSIRTが加盟し、CSIRT同士の情報共有や人材育成を行う団体です。

### 1.4 SOCの役割

CSIRTの一機能、もしくは関連組織として、**SOC**（Security Operation Center）を設置するケースも多くあります。セキュリティ専門ベンダー等が運営する外部のSOCと契約するケースもあります。

SOCの主な役割は、IDS、IPS、**SIEM**、統合ログ管理システム等からのアラートや、各種ログの分析を行い、その結果を適時CSIRTに**エスカレーション**することです。SOCが「24時間ログとアラートを見張り、異常を見つけて知らせる」役、CSIRTが「知らせを受けて判断し、組織を動かす」役と覚えると区別しやすいでしょう。なお、ログの取得・分析や SIEM の仕組みは、5.1「情報セキュリティ対策の全体像」と 5.6「侵入検知システム(IDS)」で扱います（原本では「7.8節で解説」とされていましたが、本ノート群では第7章は暗号のため、参照先を改めています）。

| 観点 | SOC | CSIRT |
|---|---|---|
| 主な仕事 | 監視・検知・一次分析 | 判断・指示・調整・報告 |
| 時間軸 | 常時（24時間365日の監視が多い） | インシデント発生時が中心＋平常時の備え |
| 主な相手 | IDS/IPS、SIEM、EDR などの機器とログ | 経営層、現場部門、顧客、監督官庁、外部CSIRT |
| 出力 | アラートの分析結果とエスカレーション | 対応方針、指示、報告書、公表文 |

### 1.5 インシデント対応の役割分担 ― 登場人物を整理する

科目Bの事例には、CSIRT・SOC以外にも多くの登場人物が出てきます。設問で「〇〇は何をすべきか」と問われたときに迷わないよう、役割を表にまとめておきます。

| 立場 | 何をすべきか | 何のために | してはいけないこと |
|---|---|---|---|
| **発見者**（一般社員） | 異常に気づいたら、定められた窓口（ヘルプデスク・CSIRT）へ直ちに報告する。マルウェア感染が疑われるPCはLANケーブルを抜く（無線LANを切る）が、**電源は切らない** | 早期に組織が把握し、被害拡大を止め、証拠を残すため | 自分で原因を調べる、再起動する、黙っている |
| **ヘルプデスク** | 連絡を受け付け、受付票に記録し、セキュリティに関わる事象はCSIRTにエスカレーションする | 情報を漏れなくCSIRTに集めるため | 「よくあること」として自分で完結させる |
| **SOC** | アラートとログを分析し、誤検知か否かを一次判定し、真の脅威をCSIRTにエスカレーションする | CSIRTが判断に必要な情報を早く得るため | 分析結果を抱え込む、エスカレーションを遅らせる |
| **CSIRT** | トリアージ、対応方針の決定、現場への指示、情報の集約、経営層・外部への報告 | 組織として一貫した対応をとるため | 原因究明にこだわって復旧・報告を遅らせる |
| **システム管理者** | CSIRTの指示に従い、ネットワーク遮断、アカウント停止、ログ保全、復旧作業を行う | 被害を封じ込め、証拠を保全し、業務を戻すため | 指示なく機器を初期化する（証拠が消える） |
| **部門長**（被害部門） | 業務影響を把握してCSIRTに伝え、部門内の業務継続（代替手段）を指揮する | 業務影響の大きさをトリアージに反映させるため | 部門内だけで収めようとして報告しない |
| **経営層**（CISO・経営者） | 重大インシデントで事業継続・公表・外部報告・予算投入を意思決定し、最終責任を負う | 事業や組織の存続にかかわる判断は経営の責任であるため | 現場任せにする、公表を不当に遅らせる |
| **広報・法務** | 公表文・FAQの作成、監督官庁・警察への届出や契約上の義務の確認 | 対外的な説明の一貫性と法令遵守のため | CSIRTと調整せずに発表する |

## 2. インシデント管理の流れ

インシデント管理の大まかな流れを次の図に示します。なお、②〜⑤の対応を**インシデントハンドリング**と呼びます。

**図：インシデント管理/インシデントハンドリングの流れ**

```
①インシデント発生に備えた対応
  ・CSIRT体制/システム/環境等の整備
  ・インシデント対応方針/計画/規程/手順の策定
  ・セキュリティ情報(脅威/脆弱性/インシデント等)の収集/対応
  ・教育/訓練の実施
  ・他のCSIRT関連組織との連携/情報交換等
        ↓
┌─ インシデントハンドリング ───────────┐
│ ②インシデントの検知/連絡受付              │
│        ↓                                   │
│ ③トリアージ/対応要否の決定                │
│        ↓                                   │
│ ④影響範囲の特定/応急処置                  │
│        ↓                                   │
│ ⑤対応策(復旧措置・連絡・広報など)の決定/実施 │
└──────────────────────┘
        ↓
⑥インシデント収束後の対応
  ・評価/改善策・再発防止策の検討
  ・対応体制/手順の見直し等 → ①へフィードバック
```

この6段階は、米国NISTのインシデント対応ガイド SP 800-61 Rev.2 の4フェーズ（準備／検知と分析／封じ込め・根絶・復旧／事件後の対応）とほぼ対応します。2025年に公開された Rev.3 では、1.2 で触れた CSF 2.0 の6機能に沿って整理し直されていますが、「備える→気づく→止める→戻す→学ぶ」という骨格は変わりません。

| 本ノートの段階 | NIST SP 800-61 Rev.2 のフェーズ | 中心となる問い |
|---|---|---|
| ① 備え | 準備 | 起きたときに誰が何をするか決まっているか |
| ② 検知・連絡受付 | 検知と分析 | 異常に気づけるか、報告が届くか |
| ③ トリアージ | 検知と分析 | 本当にインシデントか、どれから対応するか |
| ④ 影響範囲の特定・応急処置 | 封じ込め | 被害の広がりを止め、証拠を残せるか |
| ⑤ 対応策の決定・実施 | 根絶・復旧 | 原因を除去し、業務を戻し、関係者に伝えたか |
| ⑥ 収束後の対応 | 事件後の対応 | 同じことを繰り返さないために何を変えるか |

以下、この流れに沿って、それぞれ留意すべき事項を見ていきます。

## 3. ① インシデント発生に備えた対応

### 3.1 平常時に整えておくもの

インシデント発生に備えた体制の整備や、平常時に行う各種作業等であり、CSIRTと情報セキュリティ推進部門は、次のような事項を実施します。

- CSIRT体制の整備
- CSIRTの活動範囲、対象とするインシデントの明確化
- インシデント対応計画（中長期計画、年度計画など）、規定類の策定
- 想定されるインシデントに対する個別の対応手順、連絡体制の整備
- インシデントの検知・対応に必要なシステム（IPS、IDS、SIEM、統合ログ管理システムなど）の導入・構築
- 各種セキュリティ情報（脅威動向、脆弱性、他組織で発生したインシデントなど）の収集、ピックアップ、対応（周知、影響度分析、パッチ適用、対策強化など）
- インシデント発生に備えた教育・訓練の実施
- 他のCSIRT関連組織（JPCERT/CC、日本シーサート協議会、ISAC、他社CSIRTなど）との連携・情報交換

「個別の対応手順、連絡体制」は、実際には**連絡網（エスカレーションフロー）**として1枚にまとめ、夜間・休日でも誰に連絡すればよいか分かるようにしておきます。

```text
インシデント連絡体制（抜粋）                             改訂：2026/04/01  CSIRT
 発見者 ──→ ヘルプデスク（内線 1234／平日 8:30-18:00）
          └→ 夜間・休日：CSIRT当番携帯 090-XXXX-XXXX（24時間）
 SOC（外部委託・24時間）──→ CSIRT当番（重大度High以上は15分以内に電話、それ以外はチケット）
 CSIRT当番 ──→ CSIRTリーダ ──→ CISO ──→ 経営会議（重大度 P1 の場合は1時間以内に第一報）
                           ├→ 被害部門の部門長
                           ├→ 広報部・法務部（個人情報漏えい・対外影響のおそれがある場合）
                           └→ 外部：セキュリティベンダー（フォレンジック契約 No.F-2026-01）、
                                   JPCERT/CC、所轄警察署、個人情報保護委員会（該当時）
```

### 3.2 経営者が関与すべき理由

インシデントは、その内容や対応方法によっては、事業の継続や組織の存続にかかわる重大な問題にまで発展する可能性があります。したがって、対応策の検討や、対応に必要な各種リソースの整備には、**適切な権限を有する者（企業であれば経営者）**が関与するのが望ましいとされます。たとえば「ECサイトを止めて調査するか、売上を優先して稼働を続けるか」「身代金を要求されたときにどう判断するか」「いつ、どこまで公表するか」は、CSIRTの担当者が決められる範囲を超えています。経営者が平常時から方針を示し、予算と権限をCSIRTに与えておくことで、発生時の判断が速くなります。

> **試験に出た**
> 情報セキュリティマネジメント試験の午後問4で、インシデント対応に関する問題が出題された。
> 情報セキュリティマネジメント試験の午後問2で、マルウェア感染などによるインシデント対応に関する問題が出題された。
> 情報処理安全確保支援士試験の午後問2で、インシデント対応体制に関する問題が出題された。

## 4. ② インシデントの検知/連絡受付

### 4.1 2つの検知経路 ― システムと人

インシデントの検知には2つの経路があります。

- システムログ、アクセスログ、EPP、EDR、IDS、SIEM、統合ログ管理システムなどからの**アラート**（警報）によってインシデントを検知する。
- 顧客、社員、その他社外の第三者などからの**連絡**（通報）によってインシデントを検知する。

インシデントは多種多様であるため、組織には、システムやツールを用いた検知の仕組みと、人からの連絡による検知の仕組みの**両方**が必要です。PCの紛失はどのセンサにも引っかかりませんし、逆に深夜の不正ログインに気づく社員はいません。この2つの仕組みによるインシデント検知の例を次に示します。

**システムやツールによるインシデント検知の例**

- 認証サーバのログからの不審なログイン失敗/成功の検知
- IDS/IPSのアラートによる不正な通信の検知
- EPP/EDRのアラートによるマルウェア感染や不審な挙動の検知
- SIEMによる複数ログの相関分析に基づく異常の検知

**社員や顧客などからの連絡・通報などによるインシデント検知の例**

- PCを紛失した社員からの連絡による検知
- システムダウンや動作異常を発見した社員からの連絡による検知
- 取引先や顧客からの連絡によるマルウェア拡散の検知
- 第三者からの通報による情報漏えいの検知

上の例のほか、SNSやインターネット上の匿名掲示板の書込みなどによって、情報漏えいの発生を初めて知るというケースもあります。そのため、CSIRTは迅速にインシデントを検知するために、インターネット上でやり取りされている情報などにも注意する必要があります。

**図：インシデント検知体制のイメージ**

```
[システム/ツール]                  [人]
 ログ・EPP・EDR・IDS/IPS・SIEM      社員・顧客・取引先・第三者
 統合ログ管理システム               SNS/掲示板などの外部情報
        │ アラート                         │ 連絡・通報
        ↓                                  ↓
      [SOC] ─ エスカレーション ─→ [CSIRT(窓口)] ←─ [ヘルプデスク等]
```

### 4.2 システムによる検知の実物 ― ログとアラート

SOCのアナリストは、次のようなログやアラートを見てインシデントの兆候を拾い上げます。1件1件は平凡でも、並べると攻撃の筋書きが浮かび上がる点に注目してください。

**認証サーバのログ（パスワードスプレー攻撃の後に成功が混じる例）**

```text
2026-09-14 02:11:03 sshd[2231]: Failed password for invalid user admin from 203.0.113.45 port 51122 ssh2
2026-09-14 02:11:05 sshd[2233]: Failed password for invalid user test  from 203.0.113.45 port 51130 ssh2
2026-09-14 02:11:08 sshd[2235]: Failed password for yamada from 203.0.113.45 port 51141 ssh2
   ……（同一の送信元から約40分間に 3,812 件の失敗）……
2026-09-14 02:52:47 sshd[6120]: Accepted password for suzuki from 203.0.113.45 port 53307 ssh2
```

大量の失敗の後に「Accepted（成功）」が1行あれば、攻撃者がパスワードを当てた可能性が高いと判断できます（2.4「パスワードクラック」参照）。失敗だけなら「攻撃を受けたが防げた」事象ですが、成功が混じると「侵入された」インシデントに変わります。

**IDSのアラート（Snort 形式の例）**

```text
09/14-03:05:12.441 [**] [1:2027865:3] ET TROJAN Observed Malicious SSL Cert (C2 Server) [**]
  [Classification: A Network Trojan was detected] [Priority: 1]
  {TCP} 192.0.2.23:49812 -> 198.51.100.77:443
```

社内PC（192.0.2.23）から、既知のC2サーバ（攻撃者の指令サーバ）の証明書をもつ外部アドレスへ通信が発生した、というアラートです（5.6「侵入検知システム(IDS)」参照）。

**SIEMの相関分析アラート**

```text
[SIEM Correlation] Rule: "外部からの不正ログイン成功後の横展開"   Severity: Critical
  02:52:47  auth   : suzuki が 203.0.113.45（国外）から SSH ログイン成功（通常は社内からのみ）
  03:05:12  ids    : 192.0.2.23 → 198.51.100.77:443 C2通信の疑い
  03:07:40  edr    : 192.0.2.23 で mimikatz 類似の資格情報窃取ツールの挙動を検知
  03:15:02  ad     : suzuki のアカウントで 12 台のサーバへ連続ログオン
  → 単体では Low〜Medium の事象4件を、同一アカウント・短時間の連鎖として Critical に格上げ
```

SIEMは、別々の機器のログを時刻と主体（アカウント、IPアドレス）で結び付け、単体では見逃されるような事象の連鎖を1件のアラートにまとめます。これが「相関分析」です。

### 4.3 人からの連絡を受け付ける ― CSIRT連絡票（受付票）

人からの連絡は、受け付けた担当者によって聞き取る内容がばらつきやすい経路です。そこでCSIRTは、ヘルプデスクや窓口担当者が必ず同じ項目を聞き取れるよう、**インシデント連絡票（受付票）**の様式を定めておきます。記入例は次のようになります。

```text
インシデント連絡票（受付票）                         受付番号：IR-2026-0147
 受付日時   : 2026/09/14 09:12        受付者 : ヘルプデスク 小林
 報告者     : 営業部 佐藤 太郎（内線 5678 / sato@example.co.jp）
 発見日時   : 2026/09/14 09:05 頃
 発見の経緯 : 取引先A社の担当者から「御社の佐藤さんから請求書のメールが届いたが、添付の
              ZIPを開いたら何も表示されない。念のため確認したい」と電話があった。
              佐藤本人はそのメールを送っていない。
 対象       : 佐藤のPC（資産番号 NB-2026-0412、IP 192.0.2.23）、佐藤のメールアカウント
 現在の状態 : PCは起動したまま。LANケーブルは 09:10 に佐藤が抜いた（電源は切っていない）。
 事象の分類 : □不正アクセス ■マルウェア感染の疑い □情報漏えい □紛失・盗難 □サービス停止 □その他
 影響の可能性: 取引先へのなりすましメール送信（マルウェア拡散）、メール内容の漏えい
 報告者が既に行った処置: LANケーブルの抜去のみ。再起動・スキャンはしていない。
 エスカレーション: 09:15 CSIRT当番（中村）へ電話で連絡済み
```

「発見の経緯」「現在の状態」「報告者が既に行った処置」の3項目が特に重要です。CSIRTは、PCがまだ起動しているか（メモリ上の証拠が残っているか）、ネットワークから切り離されたか（被害が広がっていないか）、誰が何を触ったか（証拠が変わっていないか）を、この票から最初に読み取るからです。

> **試験に出た**
> 情報処理安全確保支援士試験の令和4年度午後問2で、ソフトウェアの脆弱性に起因するセキュリティインシデントを題材とした、原因調査や再発防止策に関する問題が出題された。
> 情報処理安全確保支援士試験の令和4年度午後問3で、オンラインサービス事業者でのセキュリティインシデントを題材とした、インシデントハンドリングを行う問題が出題された。

> **用語解説：EPP（Endpoint Protection Platform）**
> ウイルス定義ファイルとのパターンマッチングなどによって、既知のマルウェアの侵入を防ぐ、従来型のウイルス対策（AV）ツール。

> **用語解説：EDR（Endpoint Detection & Response）**
> PC、サーバなどのエンドポイント環境で発生する事象を監視・分析し、マルウェアの侵入後の不審なふるまいなどを検知・対処するツールやサービス（2.9「マルウェアによる攻撃」、4.5 も参照。原本では「詳細は7章で解説」とされていたが、本ノート群では第7章は暗号のため参照先を改めている）。

## 5. ③ トリアージ/対応要否の決定

### 5.1 トリアージとは何か

- 検知・受け付けたインシデントに関する情報を、速やかにCSIRTにエスカレーションする。
- CSIRTは、インシデントの内容を確認し、あらかじめ定めた判断基準に従って**トリアージ**（優先度を決定して選別）し、対応の要否や方法を決定する。

トリアージはもともと、災害医療で多数の負傷者の治療の優先順位を決める手法を指す言葉です。この段階でCSIRTに求められるのは、インシデントを速やかに検知してエスカレーションするとともに、**当面の対応方針を決定する**ことです。CSIRTの人手は限られているため、軽微なものまで含めてすべてのインシデントに同じ力で対応することはできません。そのため、CSIRTは**トリアージの判断基準を可能な限り詳細に定めておく**必要があります。基準が曖昧だと、担当者によって判断が変わったり、判断そのものに時間がかかったりして、初動が遅れます。

トリアージでは、まず「そもそもインシデントか」を判断します。ログに現れる**事象**（イベント）の多くは、正常な動作や、防御が機能して被害のなかった攻撃です。そのうち、情報セキュリティを損なう、または損なうおそれが高いものだけが**インシデント**です。前節の認証ログでいえば、「失敗が大量にある」だけなら事象ですが、「成功が混じった」時点でインシデントになります。誤検知（アラートは出たが実際には脅威でない）を早く切り分けることも、トリアージの一部です。

### 5.2 トリアージの判断表

CSIRTは、影響の大きさと緊急度の組合せで優先度を決める判断表を、あらかじめ作っておきます。判断表は、たとえば次のような形になります。

**表：トリアージ判断表（優先度の決定）の例**

| 優先度 | 判断基準（いずれかに該当） | 事象の例 | 初動の目標時間 | 報告先 |
|---|---|---|---|---|
| **P1（緊急）** | 基幹業務・顧客向けサービスが停止している／個人情報・機密情報の漏えいが確認された、又は進行中である／攻撃が複数の端末・サーバに拡大している | ランサムウェアによるファイルサーバの暗号化、顧客DBの不正取得 | 15分以内に対応開始、1時間以内に経営層へ第一報 | CISO、経営層、広報・法務 |
| **P2（高）** | 1台以上の端末・アカウントへの侵入が確認されたが拡大は未確認／重要情報を含む媒体の紛失・盗難 | C2通信を行うPC1台、不正ログイン成功1件、暗号化済みでないノートPCの紛失 | 1時間以内に対応開始 | CSIRTリーダ、被害部門の部門長 |
| **P3（中）** | 侵入の兆候はあるが被害は未確認／防御は機能したが同種の攻撃が継続している | EPPがマルウェアを駆除済み、大量のログイン失敗（成功なし） | 当日中に確認 | CSIRT内 |
| **P4（低）** | 被害のおそれがほとんどない／誤検知の可能性が高い | 一般的なポートスキャン、既知の誤検知ルールによるアラート | 定期レビューで確認 | 記録のみ |

判断表を作る際には、ノート 4.5 で学んだ情報資産の分類結果（その資産の機密性・可用性のレベル）が直接使われます。同じ「不正ログイン1件」でも、機密性Ⅰの顧客DBにアクセスできるアカウントならP1寄りに、公開情報しか扱わないアカウントならP3寄りに判断する、という具合です。本ノート 4.3 節の連絡票の事例（取引先へのなりすましメール、C2通信の疑い）であれば、「侵入が確認され、取引先に影響が出始めている」ため P2 以上と判断し、横展開の有無を確かめたうえで P1 への格上げを検討します。

## 6. ④ 影響範囲の特定/応急処置

### 6.1 誰が何をするか

- CSIRTは、対応を要するインシデントについて、被害拡大を回避するための処置を行うよう、システム管理者等に指示する。
- CSIRTは、SOC担当、システム管理者、セキュリティベンダー等と連携し、インシデントの**影響範囲を特定**するとともに、**暫定復旧処置（応急処置）**を行う。
- インシデント対応の内容について、確実に**記録**を残す。

一連の対応において、CSIRTは、**インシデントの正確な確認**、**被害の最小化**、**証拠となる記録類の確保**の3つに努める必要があります。この3つはときに衝突します。被害を最小化しようと急いで機器を初期化すれば、証拠が消えてしまいます。逆に証拠の確保にこだわって遮断が遅れれば、被害が広がります。CSIRTは、「まずネットワークから切り離して広がりを止め、機器そのものは触らずに証拠を保全する」という順序で、両立を図ります。

### 6.2 切り離しと証跡の保全 ― なぜ電源を切ってはいけないのか

不正アクセスやマルウェアによるインシデントの場合、システム管理者は、CSIRTの指示に従って、被害を受けたと思われる機器を**ネットワークから切り離し**ます。あわせて、インシデントの内容や原因を分析するため、ログやハードディスクの内容を別の媒体に物理的にコピーするなどして、インシデントの**痕跡や証跡を保全**します。

ここで大切なのは、「切り離す」と「電源を切る」は違うという点です。

| 処置 | 効果 | 失うもの | 判断 |
|---|---|---|---|
| LANケーブルを抜く／無線LANを無効にする／スイッチのポートを閉じる／EDRで端末を隔離する | 感染拡大と外部への情報送信（C2通信）を止める | ほとんどない | **まず行う** |
| 電源を切る・再起動する | 暗号化処理などの進行を止められる場合がある | メモリ上のプロセス、通信の接続状態、復号鍵、マルウェア本体（ファイルを残さず、メモリ上だけで動くものがある） | 原則として行わない（CSIRTの判断による） |
| ウイルス対策ソフトでスキャン・駆除する | マルウェアを除去できる場合がある | マルウェアの検体、感染の痕跡（ファイルが削除・隔離される） | 証拠保全の後に行う |

電源を切るとメモリ上の情報はすべて失われます。後述の「揮発性の順序」で最も上位にある証拠を、自分の手で消してしまうことになるのです。ただし、ランサムウェアがファイルサーバの暗号化を現在進行形で続けているような場合には、被害の最小化を優先して停止を選ぶこともあります。どちらを優先するかをCSIRTが判断し、その理由を記録に残すことが大切です。

保全した証拠が後で法的な証拠として使える（改ざんされていないと示せる）ように、システム管理者やフォレンジック担当者は、取得したデータのハッシュ値を計算して記録し、誰がいつ受け取り、どこに保管したかを記録し続けます。これを**証拠保全の一貫性（Chain of Custody）**の確保といいます。

```text
証拠保全記録（Chain of Custody）                         事案番号：IR-2026-0147
 証拠No. | 内容                           | 取得日時          | 取得者        | ハッシュ値（SHA-256）         | 保管場所
---------+--------------------------------+-------------------+---------------+-------------------------------+-------------
 E-01    | NB-2026-0412 メモリダンプ（16GB） | 2026/09/14 09:48 | CSIRT 中村    | 3f2a9c…e81b                   | 証拠保管庫A
 E-02    | NB-2026-0412 ディスクイメージ     | 2026/09/14 11:20 | ベンダー 岡田 | 9b71d0…04ac                   | 証拠保管庫A
 E-03    | メールサーバ送信ログ（9/13-14）   | 2026/09/14 10:05 | 情シス 山田   | c05e44…7d12                   | 証拠保管庫A
 受渡し履歴：E-01, E-02 を 2026/09/15 09:00 ベンダー岡田へ貸出（CSIRT 中村 → 岡田、双方署名）
```

### 6.3 影響範囲の特定

応急処置と並行して、CSIRTはSOCやシステム管理者と協力して影響範囲を特定します。影響範囲とは、「どの端末・サーバ・アカウントが侵害されたか」「どの情報が、何件、誰に関わる形で漏えいした可能性があるか」「いつから侵害されていたか」の3点です。前述のSIEMのアラートの例なら、攻撃者が suzuki のアカウントで12台のサーバにログオンしているので、影響範囲はPC1台ではなく、その12台と suzuki のアカウントが権限をもつすべての情報に広がっている可能性があります。影響範囲の見積もりが甘いと、一部だけを復旧して攻撃者を残したまま「収束」と判断してしまいます。

## 7. ⑤ 対応策（復旧措置・連絡・広報など）の決定/実施

### 7.1 原因の除去と復旧

- CSIRTは、インシデントの原因を除去し、システムやサービスを復旧するための対応策を検討し決定する。
- CSIRTは、インシデントの内容やレベルに応じて**デジタルフォレンジックス**の専門家に調査を依頼するとともに、復旧措置の実施をシステム管理者等に指示する。
- インシデントの収束が確認されたら、顧客や社内外の関係者に対し、その旨を連絡/公表する。

> **用語解説：デジタルフォレンジックス（Digital Forensics）**
> フォレンジック、コンピュータフォレンジックともいう。不正アクセスや情報漏えいなどが発生した際に、コンピュータやネットワーク機器などに残された電子的記録を収集・解析し、法的な証拠として利用できるように保全する技術や手続のこと。

インシデントの原因究明には多くの時間を要する可能性があります。そのため、CSIRTは、**原因究明よりも復旧のための対応策を優先させなければなりません**。攻撃の全容を解明するのに数週間かかることは珍しくなく、その間ずっとサービスを止めていれば、攻撃そのものより大きな損害を組織が自ら招くことになります。ただし「優先」は「省略」ではありません。復旧の前に証拠を保全しておき（6.2）、原因の調査は復旧と並行して、あるいは復旧後に続けます。また、侵入口（脆弱性や盗まれた認証情報）を塞がないまま元の状態に戻すと、攻撃者は同じ入口から戻ってきます。システム管理者は、少なくとも侵入口の遮断（パッチ適用、パスワード変更、不正アカウントの削除）を済ませたうえで、クリーンなバックアップやOSの再インストールから復旧するべきです。

この「原因究明より復旧を優先する」考え方は、ITサービスマネジメントの**インシデント管理**と**問題管理**の区別と同じです。インシデント管理は「サービスを早く元に戻す」ことを目的とし、問題管理は「根本原因を特定して恒久的に再発を防ぐ」ことを目的とします（確認問題1で問われます）。

### 7.2 デジタルフォレンジックスの手順と揮発性の順序

> **Column：デジタルフォレンジックスによる調査手順**
> デジタルフォレンジックスは、次のような手順で行う。
>
> 1. 対象PCを隔離するなどして保全する。
> 2. 対象PCのキャッシュやメモリの内容を取得する。
> 3. 対象PCのディスクの複製（ディスクイメージ）を作成する。
> 4. 複製したデータを解析し、インシデントの痕跡や原因を調査する。
> 5. 調査結果を報告書にまとめる。
>
> デジタルフォレンジックスで証拠を収集する際は、**揮発性の高いものから順に**進める必要がある。**RFC 3227**「証拠収集とアーカイビングのためのガイドライン」では、揮発性の順序が次のように例示されている（上のものほど揮発性が高い）。
>
> 1. レジスタ、キャッシュ
> 2. ルーティングテーブル、ARPキャッシュ、プロセステーブル、カーネル統計、メモリ
> 3. テンポラリファイルシステム
> 4. ディスク
> 5. 当該システムと関連する遠隔ロギングと監視データ
> 6. 物理的設定、ネットワークトポロジ
> 7. アーカイブ用メディア

揮発性とは「放っておくと、あるいは電源を切ると消えてしまう度合い」です。メモリの内容は電源を切れば消え、ARPキャッシュは数分で書き換わりますが、ディスクの内容は電源を切っても残ります。したがって、消えやすいものから先に取らなければ、後で取ろうとしたときにはもう存在しません。手順の4番目で「複製したデータを解析する」とあるのは、原本を直接解析すると、解析作業そのものがファイルのアクセス日時などを書き換えて証拠を変えてしまうためです。調査者は必ず複製（ディスクイメージ）を解析し、原本はハッシュ値とともに保管しておきます。

揮発性の高い情報は、ディスクイメージを取る前に、コマンドで取得して記録しておきます。たとえば、ネットワーク接続の状態（どの外部アドレスと通信中か）を取得すると、次のような出力が得られます。

```text
C:\> netstat -ano
  Proto  Local Address          Foreign Address        State           PID
  TCP    192.0.2.23:49812       198.51.100.77:443      ESTABLISHED     4412
  TCP    192.0.2.23:49820       192.0.2.10:445         ESTABLISHED     4412
C:\> tasklist /FI "PID eq 4412"
  Image Name        PID  Session Name   Mem Usage
  rundll32.exe     4412  Console        18,204 K
```

「rundll32.exe（正規のWindowsプログラム）が外部のC2サーバと社内のファイルサーバ（445番ポート＝SMB）の両方と通信している」という情報は、電源を切った瞬間に失われます。この一画面が、マルウェアの正体と横展開の経路を示す決定的な証拠になることもあるのです。

### 7.3 連絡・公表 ― 誰に、何を、いつ伝えるか

インシデントが取引先や第三者に影響を及ぼしている場合、CSIRTは、経営層・広報・法務と連携して、次の対応を迅速に行う必要があります。

- 関係者、監督官庁、捜査機関等への連絡
- ホームページ等を通じたインシデントの公表
- 問合せ窓口の設置
- 正式な調査結果報告

そのため、CSIRTは、インシデントの**正確な情報を集約**し、経営者や関係部門の責任者などに適時伝える必要があります。経営層が誤った情報に基づいて公表すると、後で訂正を重ねることになり、組織の信頼をさらに損ないます。

個人データの漏えい等が発生した場合、個人情報取扱事業者は、個人情報保護法に基づき、一定の要件（要配慮個人情報が含まれる、財産的被害のおそれがある、不正の目的によるおそれがある、本人の数が1,000人を超える、のいずれか）に該当すれば、**個人情報保護委員会への報告**と**本人への通知**を行わなければなりません。報告は、事態を知った後速やかに行う**速報**（おおむね3〜5日以内が目安）と、原則として30日以内（不正の目的によるおそれがある場合は60日以内）に行う**確報**の2段階です（第9章で扱います）。CSIRTと法務部門は、どの報告義務がいつ発生するかを、インシデント発生直後から確認しておく必要があります。

なお、インシデントを公表すると、顧客や関係者からの問合せが殺到することも想定されます。そのため、CSIRTと広報部門は、対応手順や説明内容、**FAQ**等を明確にして社内に周知しておく必要があります。これにより、たまたま問合せを受けた従業員等が不適切な対応（推測に基づく説明、公表前の情報の漏えいなど）をすることがないよう徹底します。

### 7.4 復旧後の監視

さらに、CSIRTとSOCは、復旧後にインシデントが**再発しないよう**細心の注意を払わなければなりません。攻撃者は、最初の侵入時にバックドアや別の不正アカウントを仕込んでいることがあり、見つけ損ねた1か所から再侵入してきます。CSIRTは、復旧しても当面の間はシステムの状態を注意深く監視し（C2宛て通信の再発、不審なログオン、新規アカウントの作成などに監視ルールを追加する）、わずかでも異常が見つかった場合には直ちに対応できる体制を整えておく必要があります。

## 8. ⑥ インシデント収束後の対応

### 8.1 評価・改善・再発防止

インシデントが収束したら、CSIRTと関係者は次の対応を行います。

- 一連のインシデント対応の結果を関係者で評価して問題点を洗い出し、改善策を検討・決定する（SLA、体制、手順、検知システム、対応方法の見直しなど）。
- インシデントの再発を防止するための対策（即時実施すべきもの、中長期的な取組みを要するものなど）を検討・決定する。
- インシデントの評価結果に基づき、必要な各種リソースを確保し、改善策、再発防止策を実施する。
- 新たに必要となった各種リソース（要員、設備、システム、サービス等）を確保・整備する。
- 顧客との契約内容（SLA、責任範囲など）を見直す。
- インシデント対応体制、対応手順を見直す。
- 見直した内容に基づき、要員の教育・訓練を実施する。

> **用語解説：SLA（Service Level Agreement）**
> サービスの提供者と利用者の間で、提供されるサービスの品質（サービスレベル）について合意した契約。ISPやクラウドサービスの場合は、通信速度や稼働率、平均遅延時間、障害復旧時間の上限などのサービスレベルの項目と、それらが達成されなかった場合の利用料金の減額に関する規定などを含めているケースが多い。これに限らず、ITアウトソーシングサービスや運用関連サービスなどでも締結される。

評価では、次のような観点を確認します。

- 判断基準や手順に不備や誤りなどがなかったか。
- 対応者のスキルレベルは十分であったか。
- 状況判断が適切に行われ、余裕をもって対応できたか。

インシデントの原因が組織体制や業務手順などにあった場合、情報システムの見直しや再構築のみを実施しても、同様の問題が再発する可能性は高いです。たとえば「パッチ適用の承認に1か月かかる業務手順のせいで、公開済みの脆弱性が放置されていた」のが原因なら、侵害されたサーバを作り直しても、次の脆弱性で同じことが起きます。そのような場合は、組織体制、業務内容及び手順、要員の教育方法などの**抜本的な見直し**が必要になります。

### 8.2 インシデント報告書の実例

評価と再発防止策の検討結果は、**インシデント報告書**にまとめ、経営層に報告するとともに、次の対応の教訓として保存します。報告書の項目は、たとえば次のようになります。科目Bでは、この報告書の空欄（原因、再発防止策など）を埋めさせる形の設問がよく出ます。

```text
インシデント報告書（最終報告）                    事案番号：IR-2026-0147   作成：CSIRT   承認：CISO
1. 概要       : 標的型メールの添付ファイルを開いたことによるマルウェア感染。感染PCから取引先へ
               なりすましメールが送信され、社内PC計3台が外部のC2サーバと通信していた。
2. 検知の経緯 : 2026/09/14 09:05 取引先A社からの電話連絡（人による検知）。
               同日 03:05 にIDSがC2通信のアラートを出していたが、優先度Mediumとして未対応だった。
3. 時系列     : 別紙「対応記録（タイムライン）」のとおり。
4. 影響範囲   : 感染端末 3台／なりすましメール送信先 取引先 42社 57件／
               ファイルサーバへの不正アクセス 1台（個人データの持出しは確認されず）。
5. 原因       : 直接原因  ― マクロ付き文書の開封によるマルウェアの実行。
               根本原因  ― ①インターネット由来ファイルのマクロ実行を許可していた。
                            ②IDSのC2通信アラートの優先度設定が低く、夜間に検知しながら対応されなかった。
6. 実施した対処: 端末の隔離・初期化、C2宛て通信の遮断、パスワードリセット、取引先への注意喚起。
7. 再発防止策 : 即時   ― インターネット由来ファイルのマクロをグループポリシで無効化（9/20完了）。
               短期   ― C2通信系アラートを High に格上げし、SOCから夜間でも電話連絡する（10月）。
               中長期 ― 標的型メール訓練の年2回化と、報告率を評価指標に追加（来年度計画）。
8. 対外対応   : 取引先42社へ個別連絡（9/14）。個人データ漏えいは確認されず、個人情報保護委員会への
               報告は不要と法務部が判断（判断根拠を別紙に記載）。
9. 対応の評価 : 発見者の初動（LAN切断のみで電源は維持）は適切。一方、夜間アラートの見逃しにより
               検知から対応開始まで約6時間を要した。
```

報告書の5番目で「直接原因」と「根本原因」を分けているのがポイントです。「社員がメールを開いたから」で止めると、再発防止策は「社員に注意する」しか出てきません。「なぜ開いただけで感染したのか（マクロが有効だった）」「なぜ検知しながら止められなかったのか（アラートの優先度設定）」まで掘り下げると、組織として変えるべき仕組みが見えてきます。

## 9. サイバーレジリエンスとOODA

### 9.1 サイバーレジリエンス

インシデント管理においては、組織の**レジリエンス**（resilience）を高めることが重要となります。レジリエンスとは「回復力」や「復元力」を意味する用語です。サイバー攻撃によるインシデント発生時に、その影響を最小化し、元の状態に回復させる組織の能力を**サイバーレジリエンス**といいます。「侵入されないこと」だけを目標にするのではなく、「侵入されても事業を止めず、早く戻れること」を目標に加える考え方で、1.7 で学んだゼロトラストの「侵害を前提とする」発想や、4.9 の事業継続管理と地続きです。

### 9.2 OODAループ

サイバーレジリエンスを高めるためには、**OODA（ウーダ）ループ**による取組みが重要とされています。OODAループとは、次に示すように、**観察**（Observe）、**状況判断**（Orient）、**意思決定**（Decide）、**実行**（Act）を繰り返すことです。

**図：OODAループ**

```
      ①観察(Observe)
   対象システムやサービスにおける
   インシデントの発生状況や、
   対応策実施後の状態を観察する
     ↗                    ↘
④実行(Act)              ②状況判断(Orient)
決定した方針に基づき、     発生したインシデントの内容や
対応策を実行する           対象システム/サービスの状態から、
                           対応の優先度等を判断する
     ↖                    ↙
      ③意思決定(Decide)
   インシデントの内容や状況に応じ、
   組織としての方針や対応策を決定する
```

**PDCAサイクル**は、計画（Plan）の策定から始まり、計画に沿って実行・評価・改善を行うことを前提としています。これに対して**OODAループ**は、計画ありきではなく、観察した状況に基づいて柔軟に判断し、迅速に意思決定・実行することを前提としています。そうすることで、組織はセキュリティインシデント等の突発的な事象に迅速に対応し、サイバーレジリエンスを向上させることが可能となります。

| 観点 | PDCAサイクル | OODAループ |
|---|---|---|
| 出発点 | 計画（Plan） | 観察（Observe） |
| 前提 | 状況がある程度予測でき、計画を立てられる | 状況が刻々と変わり、計画どおりに進まない |
| 1周の速さ | 月・年単位（ISMSの年次改善など） | 分・時間単位（インシデント対応中の判断） |
| 向いている場面 | ①の備えや⑥の再発防止など、平常時の継続的改善 | ②〜⑤のインシデントハンドリング中の意思決定 |

6.4 のタイムラインを見返すと、09:35 に「他にPC2台で同じ通信」を**観察**し、それを「複数端末に拡大している」と**状況判断**し、09:45 にP1への格上げを**意思決定**し、隔離と遮断を**実行**して、また次の観察に戻っています。インシデント対応の現場では、この小さなループが何度も回っているのです。両者は対立するものではなく、平常時はPDCAで仕組みを改善し、有事にはOODAで素早く動く、という使い分けになります。

### 9.3 インシデント管理のまとめ

インシデントの発生は、企業の存続やビジネスの継続にまで影響を及ぼす可能性があります。組織は、発生したインシデントには迅速かつ適切に対応し、対応後には徹底的に評価・見直しを行うことが重要です。そのうえで、二度と同じことを繰り返さないよう、組織全体で取り組んでいく必要があります。

## 10. 確認問題

### 10.1 理解度チェック

- **Q1**：インシデント発生に備えた対応において行うべき事項と留意点について述べよ。
- **Q2**：インシデント検知/連絡受付における留意点について述べよ。
- **Q3**：インシデントのトリアージ/対応要否の決定における留意点について述べよ。
- **Q4**：影響範囲の特定/応急処置における留意点について述べよ。
- **Q5**：対応策（復旧措置・連絡・広報など）の決定/実施における留意点について述べよ。
- **Q6**：インシデント収束後の対応における留意点について述べよ。
- **Q7**：サイバーレジリエンスとは何か。
- **Q8**：PDCAに対するOODAの特徴と実施内容について述べよ。

> **解答例**
> - Q1：CSIRT体制・活動範囲・対応計画・規定類・個別手順・連絡体制の整備、検知システムの導入、セキュリティ情報の収集と対応、教育・訓練、外部CSIRT関連組織との連携を行う。事業の存続にかかわるため、経営者など適切な権限を有する者が関与する（本ノート 3 節）。
> - Q2：システム・ツールによる検知と、人からの連絡による検知の両方の仕組みを用意する。SNSや掲示板などインターネット上の情報にも注意する。受付時の聞き取り項目を様式で統一する（本ノート 4 節）。
> - Q3：速やかにCSIRTへエスカレーションし、あらかじめ可能な限り詳細に定めた判断基準に従って優先度を決め、対応の要否と当面の方針を決める（本ノート 5 節）。
> - Q4：CSIRTがシステム管理者等に被害拡大回避の処置を指示し、SOC・ベンダー等と連携して影響範囲を特定し応急処置を行う。正確な確認・被害の最小化・証拠の確保に努め、機器はネットワークから切り離し（電源は切らず）、ログやディスクの内容を保全する。対応内容を記録する（本ノート 6 節）。
> - Q5：原因除去と復旧の対応策を決め、必要に応じてフォレンジック調査を依頼する。原因究明より復旧を優先する。第三者に影響がある場合は関係者・監督官庁・捜査機関への連絡、公表、問合せ窓口の設置、正式な調査報告を行い、FAQ等を社内に周知する。復旧後も当面は監視を強化する（本ノート 7 節）。
> - Q6：対応結果を評価して改善策・再発防止策を決め、リソースを確保し、SLA・体制・手順を見直し、教育・訓練を行う。原因が組織体制や業務手順にある場合は抜本的に見直す（本ノート 8 節）。
> - Q7：サイバー攻撃によるインシデント発生時に、その影響を最小化し、元の状態に回復させる組織の能力（本ノート 9.1 節）。
> - Q8：PDCAが計画を起点とするのに対し、OODAは観察を起点に、状況判断・意思決定・実行を迅速に繰り返し、突発的な事象に柔軟に対応する（本ノート 9.2 節）。

### 10.2 確認問題1

サービスマネジメントにおける問題管理において実施する活動はどれか。

ア　インシデントの発生後に暫定的にサービスを復旧させ、業務を継続できるようにする。
イ　インシデントの発生後に未知の根本原因を特定し、恒久的な解決策を策定する。
ウ　インシデントの発生に備えて、復旧のための設計をする。
エ　インシデントの発生を記録し、関係する部署に状況を連絡する。

> **解答・解説**
> 問題管理は、インシデントの根本原因を特定し、恒久的な解決策を策定して再発を防止する活動である。よって、**イ**が正解。
>
> - ア、エ：インシデント管理の活動である。
> - ウ：可用性管理やサービス継続管理の活動である。

### 10.3 確認問題2

マルウェア感染の調査対象のPCに対して、電源を切る前に全ての証拠保全を行いたい。ARPキャッシュを取得した後に保全すべき情報のうち、最も優先して保全すべきものはどれか。

ア　調査対象のPCで動的に追加されたルーティングテーブル
イ　調査対象のPCに増設されたHDDにある個人情報を格納したテキストファイル
ウ　調査対象のPCのVPN接続情報を記録しているVPNサーバ内のログ
エ　調査対象のPCのシステムログファイル

*〔情報処理安全確保支援士試験・R5〕*

> **解答・解説**
> デジタルフォレンジックスで証拠を収集する際は、揮発性の高いものから順に進める必要がある。RFC 3227「証拠収集とアーカイビングのためのガイドライン」では、揮発性の順序が次のように例示されている（上のものほど揮発性が高い）。
>
> 1. レジスタ、キャッシュ
> 2. ルーティングテーブル、ARPキャッシュ、プロセステーブル、カーネル統計、メモリ
> 3. テンポラリファイルシステム
> 4. ディスク
> 5. 当該システムと関連する遠隔ロギングと監視データ
> 6. 物理的設定、ネットワークトポロジ
> 7. アーカイブ用メディア
>
> 解答群の中で、ARPキャッシュと同じ揮発性の区分に属し、最も揮発性が高いのはルーティングテーブルである。イとエはディスク（4）、ウは遠隔ロギング（5）に該当する。よって、**ア**が正解。

### 10.4 確認問題3

組織のセキュリティインシデント管理の成熟度を評価するために、Open CSIRT Foundationが開発したモデルはどれか。

ア　CMMC
イ　CMMI
ウ　SAMM
エ　SIM3

*〔情報処理安全確保支援士試験〕*

> **解答・解説**
> SIM3（Security Incident Management Maturity Model）は、Open CSIRT Foundationが開発した、CSIRTなどのセキュリティインシデント管理の成熟度を評価するモデルである。組織、人、ツール、プロセスの4分類の評価項目について、成熟度を5段階で評価する。よって、**エ**が正解。
>
> - ア：CMMC（Cybersecurity Maturity Model Certification）は、米国国防総省が調達先企業に求めるサイバーセキュリティの成熟度認証制度である。
> - イ：CMMI（Capability Maturity Model Integration）は、ソフトウェア開発などのプロセスの成熟度を評価するモデルである。
> - ウ：SAMM（Software Assurance Maturity Model）は、OWASPが提供する、ソフトウェアセキュリティの成熟度を評価するモデルである。

## 11. 試験対策まとめ（重要ポイント）

### 11.1 知識の確認（科目A-2向け）

- **組織内CSIRTの3つの役割**：対応の主導、情報の集約と適時報告（顧客・株主・経営者・監督官庁）、現場への適時指示。平常時の情報収集・連携と、収束後の再発防止も担う。
- **SOC と CSIRT**：SOCはIDS/IPS・SIEM・統合ログ管理システムのアラートとログを分析してCSIRTにエスカレーションする。CSIRTは判断・指示・報告を担う。
- **JPCERT/CC**：国内のインシデント報告の受付・対応支援・手口分析・再発防止の助言を行う中立の組織。国内CSIRT間の連携と国際連携の窓口（コーディネーションセンター）。
- **ISAC**：同業種の組織間でセキュリティ情報を共有・分析する組織（金融ISAC、ICT-ISACなど）。
- **SIM3**：Open CSIRT Foundation のCSIRT成熟度モデル。組織・人・ツール・プロセスの4分類、レベル0〜4の5段階。CMMC（米国防総省）、CMMI（開発プロセス）、SAMM（OWASPのソフトウェアセキュリティ）と区別する。
- **インシデントハンドリング**：②検知/連絡受付 → ③トリアージ → ④影響範囲の特定/応急処置 → ⑤対応策の決定/実施。①備えと⑥収束後の対応を加えてインシデント管理。
- **トリアージ**：優先度を決定して選別する。判断基準を可能な限り詳細に定めておく。
- **揮発性の順序（RFC 3227）**：レジスタ・キャッシュ → ルーティングテーブル・ARPキャッシュ・プロセステーブル・カーネル統計・メモリ → テンポラリファイルシステム → ディスク → 遠隔ロギング・監視データ → 物理的設定・ネットワークトポロジ → アーカイブ用メディア。
- **フォレンジックの手順**：隔離・保全 → キャッシュ・メモリ取得 → ディスクイメージ作成 → 複製を解析 → 報告書。原本は解析しない。
- **原因究明より復旧を優先**：ITサービスマネジメントでは、暫定復旧＝インシデント管理、根本原因の特定と恒久対策＝問題管理。
- **サイバーレジリエンス**：影響を最小化し元の状態に回復させる組織の能力。
- **OODA と PDCA**：観察→状況判断→意思決定→実行。計画ありきではなく、観察した状況に基づき迅速に判断・実行する。

### 11.2 記述式で問われる観点（科目B向け）

科目Bのインシデント対応問題は、事例の時系列を読ませたうえで「この時点で〇〇は何をすべきか」「なぜその対応が不適切か」を問います。次の観点は、設問で書かされる内容の形で覚えておきましょう。

- **初動で電源を切らせない理由**：「感染PCの利用者は、LANケーブルを抜いてネットワークから切り離すべきである。電源を切ると、メモリ上のプロセスや通信先の情報など揮発性の高い証拠が失われ、原因と影響範囲の特定ができなくなるからである。」
- **証拠保全の順序を答える**：「揮発性の高いメモリ、ネットワーク接続状態を先に取得し、次にディスクイメージを作成する」。問題文の選択肢にディスク上のログと遠隔サーバのログがあれば、ディスク（4）が遠隔ロギング（5）より先。
- **原本を解析しない理由**：「解析作業によってファイルのアクセス日時などが書き換わり、証拠の完全性が損なわれるため、ハッシュ値を記録した複製を解析する。」
- **エスカレーションの不備を指摘する**：事例で「アラートは出ていたが対応が遅れた」場合、「SOCからCSIRTへのエスカレーション基準（どの重大度なら夜間でも電話するか）が定められていなかった」「アラートの優先度設定が不適切だった」を問題点として挙げる。
- **トリアージの根拠を書く**：「侵害された端末が顧客情報（機密性レベルⅠ）にアクセスできるアカウントを使っていたため、優先度を上げるべきである」のように、影響を受ける情報資産の重要度と、拡大しているかどうかを根拠にする。
- **影響範囲の特定で見るべきもの**：侵害されたアカウントがアクセスできた範囲、同じC2宛て通信をしている他端末、侵入の開始時期。「感染端末1台だけ」と早合点して収束させない。
- **復旧の前提条件を答える**：「侵入口（脆弱性、窃取された認証情報）を塞いでから、クリーンなバックアップから復旧する。塞がずに戻すと同じ経路で再侵入されるため。」復旧後も当面は監視を強化する。
- **復旧と原因究明の優先順位**：「原因究明には時間を要するため、証拠を保全したうえで復旧を優先し、原因調査は並行又は事後に行う。」
- **経営層への報告と判断事項**：サービス停止の判断、公表、外部報告、予算投入は経営層が意思決定する。CSIRTは正確な情報を集約して適時に伝える。
- **対外対応の内容を列挙する**：関係者・監督官庁・捜査機関への連絡、公表、問合せ窓口の設置、正式な調査結果報告。個人データの漏えい等で要件に該当すれば、個人情報保護委員会への報告（速報・確報）と本人通知。社内にはFAQを周知し、問合せを受けた従業員の不適切な回答を防ぐ。
- **再発防止策を「直接原因」と「根本原因」に分けて書く**：「社員への注意喚起」だけで終わらせず、仕組み（マクロの無効化、アラート設定、パッチ適用手順、権限設計）を変える策を挙げる。原因が組織体制や手順にある場合は抜本的見直しと書く。
- **訓練・評価の観点**：対応後の評価では、判断基準や手順の不備、対応者のスキル、状況判断の適切さと余裕を確認し、見直した手順で教育・訓練を行う。
- **OODAを選ぶ理由**：「状況が刻々と変わるインシデント対応では、事前の計画に沿うPDCAより、観察した状況に基づいて迅速に判断・実行を繰り返すOODAが適している。」
