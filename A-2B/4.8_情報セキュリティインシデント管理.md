# 4.8 情報セキュリティインシデント管理

## 4.8 情報セキュリティインシデント管理

情報セキュリティに関する事件、事故など(インシデント)による損害を最小限に抑えるためには、予防策を講じるとともに、インシデント発生時の対応方法をあらかじめ定めておく必要がある。ここでは、情報セキュリティインシデント管理における要点について解説する。

### 4.8.1 情報セキュリティインシデント管理の流れ

#### ● CSIRTとSOCの概要

4.4.1項にあるように、情報セキュリティインシデント(以下「インシデント」)に対応するため、CSIRT(Computer Security Incident Response Team)を設置する組織が増えている。

広義のCSIRTには、国際連携を行うCSIRTや、CSIRT間の情報連携を行う「コーディネーションセンター」等も含まれる。ここでは、特定の組織で活動する「組織内CSIRT」を前提として解説する。

特定の組織におけるCSIRTには、次の役割が求められる。

- インシデント発生時に対応を主導する。
- 情報を集約し、顧客、株主、経営者、監督官庁等に適時報告する。
- 現場組織等に適時対応を指示する。

インシデント発生時の対応だけでなく、平常時の活動も重要な役割となる。具体的には、情報セキュリティに関する最新情報を収集したり、外部のセキュリティベンダーや関連機関、ISAC等の業界団体、他のCSIRT等と連携して情報を共有したりして、インシデント発生に備えた対応を行う。加えて、インシデント収束後には再発防止のための対応なども求められる。

なお、上記のようなCSIRTが行う一連の業務をまとめて「インシデントマネジメント」もしくは「インシデントハンドリング」と呼ぶことがある。

CSIRTの成熟度を評価するモデルとして、Open CSIRT Foundationが開発したSIM3(Security Incident Management Maturity Model)がある。SIM3では、組織(Organisation)、人(Human)、ツール(Tools)、プロセス(Processes)の4分類について評価項目が設定されている。CSIRTの成熟度は、評価項目ごとにレベル0〜4の5段階で評価する。

> **試験に出た**
> 情報処理安全確保支援士試験の午後問2で、サイバー攻撃を利用したインシデントへの対応に関する問題が出題された。

> **用語解説:ISAC(Information Sharing and Analysis Center)**
> 金融、通信、電力など、同じ業界に属する組織同士が、サイバー攻撃や脆弱性などのセキュリティ情報を共有・分析するための組織。金融ISAC、ICT-ISACなどがある。

**図:CSIRT及び関連組織間の連携イメージ**

```
  [海外のCSIRT/コーディネーションセンター]
                  │ 国際連携
       [JPCERT/CC(コーディネーションセンター)]
                  │ 情報連携
 ┌────────┬────────┼────────┬────────┐
[ISAC]  [日本シーサート協議会]  [他社CSIRT]  [セキュリティベンダー]
                  │
          [組織内CSIRT] ── [SOC(内部/外部)]
                  │
   [経営者・現場組織・顧客・監督官庁 等]
```

> **用語解説:JPCERT/CC(JPCERTコーディネーションセンター)**
> 日本国内のインシデントに関する報告の受付、対応の支援、手口の分析、再発防止策の検討・助言などを行う組織。特定の政府機関や企業から独立した中立の立場で活動している。国内のCSIRT間の連携に加え、海外のCSIRTとの国際連携の窓口として、コーディネーションセンターの役割も担う。

また、CSIRTの一機能、もしくは関連組織として、SOC(Security Operation Center)を設置するケースも多い。セキュリティ専門ベンダー等が運営する外部のSOCと契約するケースもある。

SOCの主な役割は、IDS、IPS、SIEM、統合ログ管理システム等からのアラートや、各種ログの分析を行い、その結果を適時CSIRTにエスカレーションすることである。なお、ログの分析/管理等については7.8節で解説する。

#### ● インシデント管理における留意点

インシデント管理の大まかな流れを次の図に示す。なお、②〜⑤の対応をインシデントハンドリングと呼ぶ。

**図:インシデント管理/インシデントハンドリングの流れ**

```
①インシデント発生に備えた対応
  ・CSIRT体制/システム/環境等の整備
  ・インシデント対応方針/計画/規程/手順の策定
  ・セキュリティ情報(脅威/脆弱性/インシデント等)の収集/対応
  ・教育/訓練の実施
  ・他のCSIRT関連組織との連携/情報交換等
        ↓
┌─ インシデントハンドリング ───────────┐
│ ②インシデントの検知/連絡受付              │
│        ↓                                   │
│ ③トリアージ/対応要否の決定                │
│        ↓                                   │
│ ④影響範囲の特定/応急処置                  │
│        ↓                                   │
│ ⑤対応策(復旧措置・連絡・広報など)の決定/実施 │
└──────────────────────┘
        ↓
⑥インシデント収束後の対応
  ・評価/改善策・再発防止策の検討
  ・対応体制/手順の見直し等 → ①へフィードバック
```

この流れに沿って、それぞれ留意すべき事項を次に示す。

##### ① インシデント発生に備えた対応

インシデント発生に備えた体制の整備や、平常時に行う各種作業等であり、次のようなものが該当する。

- CSIRT体制の整備
- CSIRTの活動範囲、対象とするインシデントの明確化
- インシデント対応計画(中長期計画、年度計画など)、規定類の策定
- 想定されるインシデントに対する個別の対応手順、連絡体制の整備
- インシデントの検知・対応に必要なシステム(IPS、IDS、SIEM、統合ログ管理システムなど)の導入・構築
- 各種セキュリティ情報(脅威動向、脆弱性、他組織で発生したインシデントなど)の収集、ピックアップ、対応(周知、影響度分析、パッチ適用、対策強化など)
- インシデント発生に備えた教育・訓練の実施
- 他のCSIRT関連組織(JPCERT/CC、日本シーサート協議会、ISAC、他社CSIRTなど)との連携・情報交換

インシデントは、その内容や対応方法によっては、事業の継続や組織の存続にかかわる重大な問題にまで発展する可能性がある。したがって、対応策の検討や、対応に必要な各種リソースの整備には、適切な権限を有する者(企業であれば経営者)が関与するのが望ましい。

> **試験に出た**
> 情報セキュリティマネジメント試験の午後問4で、インシデント対応に関する問題が出題された。
> 情報セキュリティマネジメント試験の午後問2で、マルウェア感染などによるインシデント対応に関する問題が出題された。
> 情報処理安全確保支援士試験の午後問2で、インシデント対応体制に関する問題が出題された。

##### ② インシデントの検知/連絡受付

- システムログ、アクセスログ、EPP、EDR、IDS、SIEM、統合ログ管理システムなどからのアラート(警報)によってインシデントを検知する。
- 顧客、社員、その他社外の第三者などからの連絡(通報)によってインシデントを検知する。

インシデントは多種多様であるため、システムやツールを用いた検知の仕組みと、人からの連絡による検知の仕組みの両方が必要となる。この二つの仕組みによるインシデント検知の例を次に示す。

**システムやツールによるインシデント検知の例**

- 認証サーバのログからの不審なログイン失敗/成功の検知
- IDS/IPSのアラートによる不正な通信の検知
- EPP/EDRのアラートによるマルウェア感染や不審な挙動の検知
- SIEMによる複数ログの相関分析に基づく異常の検知

**社員や顧客などからの連絡・通報などによるインシデント検知の例**

- PCを紛失した社員からの連絡による検知
- システムダウンや動作異常を発見した社員からの連絡による検知
- 取引先や顧客からの連絡によるマルウェア拡散の検知
- 第三者からの通報による情報漏えいの検知

上の例のほか、SNSやインターネット上の匿名掲示板の書込みなどによって、情報漏えいの発生をはじめて知るというケースもある。そのため、迅速にインシデントを検知するためには、インターネット上でやり取りされている情報などにも注意する必要がある。

**図:インシデント検知体制のイメージ**

```
[システム/ツール]                  [人]
 ログ・EPP・EDR・IDS/IPS・SIEM      社員・顧客・取引先・第三者
 統合ログ管理システム               SNS/掲示板などの外部情報
        │ アラート                         │ 連絡・通報
        ↓                                  ↓
      [SOC] ─ エスカレーション ─→ [CSIRT(窓口)] ←─ [ヘルプデスク等]
```

> **試験に出た**
> 情報処理安全確保支援士試験の令和4年度午後問2で、ソフトウェアの脆弱性に起因するセキュリティインシデントを題材とした、原因調査や再発防止策に関する問題が出題された。
> 情報処理安全確保支援士試験の令和4年度午後問3で、オンラインサービス事業者でのセキュリティインシデントを題材とした、インシデントハンドリングを行う問題が出題された。

> **用語解説:EPP(Endpoint Protection Platform)**
> ウイルス定義ファイルとのパターンマッチングなどによって、既知のマルウェアの侵入を防ぐ、従来型のウイルス対策(AV)ツール。

> **用語解説:EDR(Endpoint Detection & Response)**
> PC、サーバなどのエンドポイント環境で発生する事象を監視・分析し、マルウェアの侵入後の不審なふるまいなどを検知・対処するツールやサービス(詳細は7章で解説)。

##### ③ トリアージ/対応要否の決定

- 検知・受け付けたインシデントに関する情報を、速やかにCSIRTにエスカレーションする。
- CSIRTは、インシデントの内容を確認し、あらかじめ定めた判断基準に従ってトリアージ(優先度を決定して選別)し、対応の要否や方法を決定する。

ここでは、インシデントを速やかに検知してエスカレーションするとともに、当面の対応方針を決定することが求められる。軽微なものまで含めてすべてのインシデントに対応することはできない。そのため、トリアージの判断基準を可能な限り詳細に定めておく必要がある。

##### ④ 影響範囲の特定/応急処置

- CSIRTは、対応を要するインシデントについて、被害拡大を回避するための処置を行うよう、システム管理者等に指示する。
- CSIRTは、SOC担当、システム管理者、セキュリティベンダー等と連携し、インシデントの影響範囲を特定するとともに、暫定復旧処置(応急処置)を行う。
- インシデント対応の内容について、確実に記録を残す。

一連の対応においては、インシデントの正確な確認、被害の最小化、証拠となる記録類の確保に努める必要がある。

不正アクセスやマルウェアによるインシデントの場合は、被害を受けたと思われる機器をネットワークから切り離す。あわせて、インシデントの内容や原因を分析するため、ログやハードディスクの内容を別の媒体に物理的にコピーするなどして、インシデントの痕跡や証跡を保全する。

##### ⑤ 対応策(復旧措置・連絡・広報など)の決定/実施

- CSIRTは、インシデントの原因を除去し、システムやサービスを復旧するための対応策を検討し決定する。
- CSIRTは、インシデントの内容やレベルに応じてデジタルフォレンジックスの専門家に調査を依頼するとともに、復旧措置の実施をシステム管理者等に指示する。
- インシデントの収束が確認されたら、顧客や社内外の関係者に対し、その旨を連絡/公表する。

> **用語解説:デジタルフォレンジックス(Digital Forensics)**
> フォレンジック、コンピュータフォレンジックともいう。不正アクセスや情報漏えいなどが発生した際に、コンピュータやネットワーク機器などに残された電子的記録を収集・解析し、法的な証拠として利用できるように保全する技術や手続のこと。

インシデントの原因究明には多くの時間を要する可能性がある。そのため、原因究明よりも復旧のための対応策を優先させなければならない。

また、インシデントが取引先や第三者に影響を及ぼしている場合は、次の対応を迅速に行う必要がある。

- 関係者、監督官庁、捜査機関等への連絡
- ホームページ等を通じたインシデントの公表
- 問合せ窓口の設置
- 正式な調査結果報告

そのため、CSIRTは、インシデントの正確な情報を集約し、経営者や関係部門の責任者などに適時伝える必要がある。

なお、インシデントを公表すると、顧客や関係者からの問合せが殺到することも想定される。そのため、対応手順や説明内容、FAQ等を明確にして社内に周知しておく必要がある。これにより、たまたま問合せを受けた従業員等が不適切な対応をすることがないよう徹底する。

さらに、復旧後にインシデントが再発しないよう細心の注意を払わなければならない。復旧しても当面の間はシステムの状態を注意深く監視し、わずかでも異常が見つかった場合には直ちに対応できる体制を整えておく必要がある。

> **Column:デジタルフォレンジックスによる調査手順**
> デジタルフォレンジックスは、次のような手順で行う。
>
> 1. 対象PCを隔離するなどして保全する。
> 2. 対象PCのキャッシュやメモリの内容を取得する。
> 3. 対象PCのディスクの複製(ディスクイメージ)を作成する。
> 4. 複製したデータを解析し、インシデントの痕跡や原因を調査する。
> 5. 調査結果を報告書にまとめる。
>
> デジタルフォレンジックスで証拠を収集する際は、揮発性の高いものから順に進める必要がある。RFC 3227「証拠収集とアーカイビングのためのガイドライン」では、揮発性の順序が次のように例示されている(上のものほど揮発性が高い)。
>
> 1. レジスタ、キャッシュ
> 2. ルーティングテーブル、ARPキャッシュ、プロセステーブル、カーネル統計、メモリ
> 3. テンポラリファイルシステム
> 4. ディスク
> 5. 当該システムと関連する遠隔ロギングと監視データ
> 6. 物理的設定、ネットワークトポロジ
> 7. アーカイブ用メディア

##### ⑥ インシデント収束後の対応

- 一連のインシデント対応の結果を関係者で評価して問題点を洗い出し、改善策を検討・決定する(SLA、体制、手順、検知システム、対応方法の見直しなど)。
- インシデントの再発を防止するための対策(即時実施すべきもの、中長期的な取組みを要するものなど)を検討・決定する。
- インシデントの評価結果に基づき、必要な各種リソースを確保し、改善策、再発防止策を実施する。
- 新たに必要となった各種リソース(要員、設備、システム、サービス等)を確保・整備する。
- 顧客との契約内容(SLA、責任範囲など)を見直す。
- インシデント対応体制、対応手順を見直す。
- 見直した内容に基づき、要員の教育・訓練を実施する。

> **用語解説:SLA(Service Level Agreement)**
> サービスの提供者と利用者の間で、提供されるサービスの品質(サービスレベル)について合意した契約。ISPやクラウドサービスの場合は、通信速度や稼働率、平均遅延時間、障害復旧時間の上限などのサービスレベルの項目と、それらが達成されなかった場合の利用料金の減額に関する規定などを含めているケースが多い。これに限らず、ITアウトソーシングサービスや運用関連サービスなどでも締結される。

評価では、次のような観点を確認する。

- 判断基準や手順に不備や誤りなどがなかったか。
- 対応者のスキルレベルは十分であったか。
- 状況判断が適切に行われ、余裕をもって対応できたか。

インシデントの原因が組織体制や業務手順などにあった場合、情報システムの見直しや再構築のみを実施しても、同様の問題が再発する可能性は高い。そのような場合は、組織体制、業務内容及び手順、要員の教育方法などの抜本的な見直しが必要になる。

#### ● サイバーレジリエンスとOODA

インシデント管理においては、組織のレジリエンス(resilience)を高めることが重要となる。レジリエンスとは「回復力」や「復元力」を意味する用語である。サイバー攻撃によるインシデント発生時に、その影響を最小化し、元の状態に回復させる組織の能力を**サイバーレジリエンス**という。

サイバーレジリエンスを高めるためには、**OODA(ウーダ)ループ**による取組みが重要とされている。OODAループとは、次に示すように、観察(Observe)、状況判断(Orient)、意思決定(Decide)、実行(Act)を繰り返すことである。

**図:OODAループ**

```
      ①観察(Observe)
   対象システムやサービスにおける
   インシデントの発生状況や、
   対応策実施後の状態を観察する
     ↗                    ↘
④実行(Act)              ②状況判断(Orient)
決定した方針に基づき、     発生したインシデントの内容や
対応策を実行する           対象システム/サービスの状態から、
                           対応の優先度等を判断する
     ↖                    ↙
      ③意思決定(Decide)
   インシデントの内容や状況に応じ、
   組織としての方針や対応策を決定する
```

PDCAサイクルは、計画(Plan)の策定から始まり、計画に沿って実行・評価・改善を行うことを前提としている。これに対してOODAループは、計画ありきではなく、観察した状況に基づいて柔軟に判断し、迅速に意思決定・実行することを前提としている。そうすることで、セキュリティインシデント等の突発的な事象に迅速に対応し、サイバーレジリエンスを向上させることが可能となる。

#### ● インシデント管理のまとめ

インシデントの発生は、企業の存続やビジネスの継続にまで影響を及ぼす可能性がある。発生したインシデントには迅速かつ適切に対応し、対応後には徹底的に評価・見直しを行うことが重要である。そのうえで、二度と同じことを繰り返さないよう、組織全体で取り組んでいく必要がある。

#### 確認問題1

サービスマネジメントにおける問題管理において実施する活動はどれか。

- ア インシデントの発生後に暫定的にサービスを復旧させ、業務を継続できるようにする。
- イ インシデントの発生後に未知の根本原因を特定し、恒久的な解決策を策定する。
- ウ インシデントの発生に備えて、復旧のための設計をする。
- エ インシデントの発生を記録し、関係する部署に状況を連絡する。

**解答・解説**

問題管理は、インシデントの根本原因を特定し、恒久的な解決策を策定して再発を防止する活動である。よって、**イ**が正解。

- ア、エ:インシデント管理の活動である。
- ウ:可用性管理やサービス継続管理の活動である。

#### 確認問題2

マルウェア感染の調査対象のPCに対して、電源を切る前に全ての証拠保全を行いたい。ARPキャッシュを取得した後に保全すべき情報のうち、最も優先して保全すべきものはどれか。

- ア 調査対象のPCで動的に追加されたルーティングテーブル
- イ 調査対象のPCに増設されたHDDにある個人情報を格納したテキストファイル
- ウ 調査対象のPCのVPN接続情報を記録しているVPNサーバ内のログ
- エ 調査対象のPCのシステムログファイル

〔情報処理安全確保支援士試験・R5〕

**解答・解説**

デジタルフォレンジックスで証拠を収集する際は、揮発性の高いものから順に進める必要がある。RFC 3227「証拠収集とアーカイビングのためのガイドライン」では、揮発性の順序が次のように例示されている(上のものほど揮発性が高い)。

1. レジスタ、キャッシュ
2. ルーティングテーブル、ARPキャッシュ、プロセステーブル、カーネル統計、メモリ
3. テンポラリファイルシステム
4. ディスク
5. 当該システムと関連する遠隔ロギングと監視データ
6. 物理的設定、ネットワークトポロジ
7. アーカイブ用メディア

解答群の中で、ARPキャッシュと同じ揮発性の区分に属し、最も揮発性が高いのはルーティングテーブルである。イとエはディスク(4)、ウは遠隔ロギング(5)に該当する。よって、**ア**が正解。

#### 確認問題3

組織のセキュリティインシデント管理の成熟度を評価するために、Open CSIRT Foundationが開発したモデルはどれか。

- ア CMMC
- イ CMMI
- ウ SAMM
- エ SIM3

〔情報処理安全確保支援士試験〕

**解答・解説**

SIM3(Security Incident Management Maturity Model)は、Open CSIRT Foundationが開発した、CSIRTなどのセキュリティインシデント管理の成熟度を評価するモデルである。組織、人、ツール、プロセスの4分類の評価項目について、成熟度を5段階で評価する。よって、**エ**が正解。

- ア:CMMC(Cybersecurity Maturity Model Certification)は、米国国防総省が調達先企業に求めるサイバーセキュリティの成熟度認証制度である。
- イ:CMMI(Capability Maturity Model Integration)は、ソフトウェア開発などのプロセスの成熟度を評価するモデルである。
- ウ:SAMM(Software Assurance Maturity Model)は、OWASPが提供する、ソフトウェアセキュリティの成熟度を評価するモデルである。
