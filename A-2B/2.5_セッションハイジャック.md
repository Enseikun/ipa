# レクチャーノート：情報セキュリティにおける脅威 ― 2.5 セッションハイジャック

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ」（知識項目例：脅威，不正のメカニズム，サイバー攻撃 ほか）／「セキュリティ実装技術」（知識項目例：セキュアプロトコル，ネットワークセキュリティ，アプリケーションセキュリティ）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

2.4 のパスワードクラックでは、攻撃者が「ログインの関門そのもの」を突破しようとしました。本ノートで扱う**セッションハイジャック**は発想が逆です。攻撃者は関門と正面から戦わず、正規の利用者が関門を通過した**後**にできあがった通信（セッション）を横取りします。パスワードを多要素認証で強くしても、ログイン後のセッションが奪われれば、攻撃者は本人として振る舞えてしまいます。

セッションハイジャックとは、クライアントとサーバの間で確立されている正規のセッションに割り込み、そのセッションを奪い取る行為です。「セッション」はプロトコルの層ごとに姿が違うため、攻撃の手口も層ごとに違います。本ノートは次の順で進みます。

1. **乗っ取ると何ができるか**：セッションハイジャックで可能になる不正行為と、中間者攻撃との関係を整理します。
2. **下位層の手口**：TCP、UDP、ARP のセッションがどう奪われるかを、1.4 で学んだプロトコルの仕組みと結びつけて見ます。
3. **Webの手口**：現在もっとも警戒すべき、セッションIDを使ったハイジャックと、その変形であるセッションフィクセーションを学びます。
4. **対策**：管理者・開発者・利用者が、何を、何のためにすべきかを、予防・検知・回復の順に整理します。

科目Bとの関係では、Webアプリケーションのセッション管理の設計・実装（業務観点②）と、LAN内のARPポイズニングの検知・機器管理（業務観点③）に直結します。科目A-2では、中間者攻撃の定義、CookieのSecure／HttpOnly属性の役割、セッションフィクセーションの対策（ログイン後のセッションID再発行）が繰り返し出題されています。

## 1. セッションハイジャックとは何か

### 1.1 乗っ取った攻撃者は何ができるか

攻撃者がセッションハイジャックに成功すると、攻撃者はサーバになりすます、クライアントになりすます、あるいは両者になりすますなどして、次のような不正行為を働くことが考えられます。

| 攻撃者がなりすます相手 | 攻撃者が働く不正行為 | 主に損なわれる特性 |
|---|---|---|
| 正規のサーバ | クライアントの機密情報（クレジットカード番号、暗証番号、個人情報など）を盗む | 機密性 |
| 正規のサーバ（DNSサーバなど） | クライアントに偽の応答を返し、不正なサイトに誘導する | 完全性・真正性 |
| 正規のクライアント | サーバに侵入し、不正なリクエストの発行、管理者権限の奪取、機密情報の閲覧、情報の改ざんや消去などを行う | 機密性・完全性・真正性 |
| 両者（クライアントには正規のサーバ、サーバには正規のクライアント） | 通信データを盗聴しながら不正なリクエストやレスポンスを紛れ込ませるなどして、セッションをコントロールする | 機密性・完全性 |

表の最後の行、つまり両者の間に入り込んでセッションをコントロールする手法は、**Man-in-the-middle Attack（中間者攻撃）** とも呼ばれます。

> **Man-in-the-middle Attack（中間者攻撃）**
> 通信を行う二者の間に攻撃者が割り込み、双方に対して相手になりすますことで、通信内容の盗聴や改ざんを行う攻撃。MITM攻撃とも略される。通信相手の真正性を確認する仕組み（デジタル証明書による認証など）がない場合に成立しやすい。

中間者攻撃が「真正性を確認する仕組みがないと成立しやすい」という点は、本ノートの対策すべてに通じる軸です。1.2 で見たとおり、真正性は「相手が主張どおりの相手か」を問う特性でした。セッションハイジャックは、通信の途中で相手が入れ替わっても、どちらの当事者もそれに気づけないという**真正性の欠如**を突く攻撃だと言えます。

### 1.2 攻撃者が突く3種類の脆弱性

セッションハイジャックは、主に次のような脆弱性を突いて行われます。どの脆弱性を突くかによって、対策の担い手も変わります。

| 突かれる脆弱性 | 該当する手口（本ノートの節） | 主な対策の担い手 |
|---|---|---|
| プロトコルの仕様上の脆弱性 | UDPのハイジャック（2.2）、偽装ARP（2.3）、rコマンドの信頼関係（2.1） | ネットワーク管理者、サーバ管理者 |
| プロトコルの実装上（OSレベル）の脆弱性 | 初期シーケンス番号の推測によるTCPのハイジャック（2.1） | OSベンダ、サーバ管理者（パッチ適用） |
| Webアプリケーションなどにおけるセッション管理の脆弱性 | Webのハイジャック（3章）、セッションフィクセーション（4章） | Webアプリケーションの開発者、Webサーバの運用者 |

仕様の脆弱性は「プロトコルがそもそも相手を確かめない」ことが原因なので、個々の機器を直しても消えません。管理者は、暗号化プロトコルに置き換える、ネットワーク側で監視するといった**外側からの補強**で対処します。一方、実装やセッション管理の脆弱性は作り方の問題なので、ベンダや開発者が**直すこと**で消せます。この区別は、科目Bで「この対策は誰が行うべきか」を答えるときの根拠になります。

## 2. 下位層のセッションハイジャック ― TCP・UDP・ARP

### 2.1 TCPにおけるセッションハイジャック

[1.4](1.4_TCPIPの主なプロトコルとネットワーク技術の基礎.md) の 3.2 で見たとおり、TCPでは、コネクションの確立時（3ウェイハンドシェイク）に、互いのシーケンス番号（初期シーケンス番号）が交換されます。コネクション確立後は、送信者が送信したデータを**オクテット単位**で数え、その値をシーケンス番号に加算して相手に送ります。これにより受信者は、データが欠落や重複なく正しく受信できていることを確認できます。

TCPはこの仕組みによって通信の信頼性を高めていますが、裏を返せば、受信者は「シーケンス番号のつじつまが合っているパケット」を正規の相手からのものと信じます。攻撃者がシーケンス番号を矛盾なく操作できれば、セッションハイジャックが可能になります（当然、IPアドレスなどの偽装も必要です。1.4 の 2.1 で見たように、IPには送信元アドレスが本物かを確かめる仕組みがありません）。

TCPセッションのハイジャックでは、攻撃者は初期シーケンス番号の**推測**、もしくはパケットの**盗聴**によってシーケンス番号を突き止め、それを基に偽装したパケットを送信することで、正規の相手ホストになりすまします。

```
図：TCPにおけるセッションハイジャックのイメージ

 クライアント ════ ① TCPコネクション確立済み・通信中 ════ サーバ
                                                          ↑
 攻撃者 ── ② 盗聴または推測で現在のシーケンス番号を把握   │
        ── ③ 送信元IPアドレスをクライアントに偽装し、        │
             正しいシーケンス番号を付けたパケットを送信 ──────┘
                      ④ サーバは正規のクライアントからのパケットとして受け入れる
                         → セッションが攻撃者に乗っ取られる
```

1. クライアントとサーバの間でTCPコネクションが確立され、通信が行われている
2. 攻撃者は、盗聴または推測によって現在のシーケンス番号を把握する
3. 攻撃者は、送信元IPアドレスをクライアントのものに偽装し、正しいシーケンス番号を付与したパケットをサーバへ送信する
4. サーバは偽装パケットを正規のクライアントからのものとして受け入れ、セッションが攻撃者に乗っ取られる

**なぜ初期シーケンス番号は乱数なのか**：各OSのTCPの実装では、初期シーケンス番号を推測されないようにするため、コネクションごとに乱数が用いられます。しかし、一部の旧バージョンのOSでは、乱数を用いていながらもそこに一定の規則性があったため、初期シーケンス番号を推測することが可能でした。これが「実装上の脆弱性」の典型例です。

この脆弱性を悪用した攻撃としては、1994年にケビン・ミトニック（Kevin Mitnick）が下村努氏のコンピュータに対して行ったとされる攻撃がよく知られています。この手法は、送信元のIPアドレス（ソースIPアドレス）だけで接続を許可する rcp、rlogin などのサービスが稼働している場合に有効であるため、今日のインターネット環境で行われる可能性は極めて低いといえます。

> **rコマンド（rcp、rlogin、rshなど）**
> BSD系UNIXで利用されてきたリモート操作用のコマンド群。.rhostsファイルなどによってホスト単位の信頼関係を設定すると、パスワードなしで接続できるため、IPアドレスの偽装に対して脆弱である。現在は SSH に置き換えられている。

ここから管理者が学ぶべき教訓は「**送信元IPアドレスを認証の根拠にしてはいけない**」ということです。サーバの管理者は、IPアドレスだけで接続を許すサービス（rコマンドなど）を停止し、利用者認証と暗号化を備えたSSHに置き換えるべきです。IPアドレスは偽装できるため、アクセス制御の補助にはなっても、本人確認の代わりにはならないからです。

### 2.2 UDPにおけるセッションハイジャック

UDPにはTCPのようなコネクション確立手順やシーケンス番号がないため（1.4 の 3.4）、セッションハイジャックの手法もより単純かつ容易です。UDPでは、攻撃者はクライアントからのリクエストに対し、正規のサーバよりも**先に**偽のレスポンスを返すことでセッションハイジャックを行います。

```
図：UDPセッションハイジャックのイメージ

 クライアント ── ① リクエスト ─────────────────→ 正規のサーバ
      ↑                                              │
      │← ② 偽のレスポンス（先着）── 攻撃者（正規のサーバになりすます）
      │                                              │
      └←──────── ③ 正規のレスポンス（後着・破棄される）┘
```

1. クライアントがサーバにリクエストを送信する
2. 攻撃者は、正規のサーバになりすまし、正規の応答よりも先に偽のレスポンスをクライアントへ返す
3. クライアントは先に届いた偽のレスポンスを受け入れ、後から届いた正規のレスポンスは破棄される

UDPのクライアントは「最初に届いた、つじつまの合う応答」を信じるしかありません。これは仕様上の脆弱性なので、クライアント側の設定では根本的に防げません。UDPセッションハイジャックが行われる具体的な例としては、**DNSキャッシュポイズニング攻撃**（[2.6](2.6_DNSサーバに対する攻撃.md) の 3章参照）などがあります。DNSが送信元ポート番号やIDのランダム化、さらに電子署名（DNSSEC）という「外側からの補強」を積み重ねてきたのは、この仕様上の弱さを補うためです。

### 2.3 偽装ARPによるセッションハイジャック（ARPポイズニング／ARPスプーフィング）

LANの中では、もう一段下の層でもセッションが奪われます。

> **ARP（Address Resolution Protocol）**
> IPアドレスから対応するMACアドレスを求めるためのプロトコル。問い合わせ結果は一定時間ARPキャッシュに保持される。ARPには応答の正当性を検証する仕組みがないため、偽装に対して脆弱である。

攻撃者は、ハイジャックの対象となるセッションが張られているLAN上で、攻撃者自身のMACアドレスと正規のホストのIPアドレスとを組み合わせた偽のARP応答パケットを送信することでARPキャッシュの内容を書き換え、セッションをハイジャックします。この手法は**ARPポイズニング**もしくは**ARPスプーフィング**と呼ばれます。多くのOSが、ARP応答パケットを受け取ると（自らが要求を出していなくても）無条件にARPキャッシュを更新することを悪用した攻撃です。

```
図：ARPポイズニングの前後（PCから見たデフォルトゲートウェイの対応表）

 【正常時】PC のARPキャッシュ
   192.0.2.1（ゲートウェイ） → 00:00:5e:00:53:01（ゲートウェイの本物のMAC）

 【攻撃後】PC のARPキャッシュ
   192.0.2.1（ゲートウェイ） → 00:00:5e:00:53:99（攻撃者のPCのMAC）
                                  ↑ 偽のARP応答で書き換えられた
 → PCが外部へ送るつもりのフレームは、スイッチによって攻撃者のPCへ届けられる
```

ARPキャッシュが書き換えられると、1.4 の 8.1 で学んだ「スイッチは宛先MACアドレスのポートにだけフレームを送るので盗聴しにくい」という前提が崩れます。スイッチは正しく動いているのに、宛先MACアドレスそのものが攻撃者のものにすり替わっているからです。攻撃者はこうして自分を経由させた通信を中継しながら盗聴・改ざんでき、中間者攻撃の足場になります。

ハイジャックを成立させるためには、偽のARP応答パケットを送信するだけでなく、TCPシーケンス番号も偽装する必要がありますが、これらを自動的に行うツールも存在します。つまり、攻撃者に高度な技術は必要なく、**LANに機器をつなげられること**が実質的な成立条件です。このため、対策の中心は「不正な機器をLANにつながせない」「つながれたら気づく」という物理・運用面になります（5.5節）。

> **試験に出る**
> 情報処理安全確保支援士試験の平成29年度午後I問1で、ARPポイズニング（ARPスプーフィング）を題材にした問題が出題された。

## 3. Webサーバとクライアント間のセッションハイジャック

### 3.1 なぜWebではセッションIDが狙われるのか

Webサーバのセッション管理の脆弱性を突いてセッションハイジャックを成立させる手法は、Webアプリケーション全盛の今日において、最も警戒すべき手法の一つです。下位層の攻撃がLANへの接続やパケットの偽装を必要とするのに対し、Webのハイジャックは「セッションIDという文字列を1つ手に入れる」だけで成立するからです。

1.4 の 7.7 で見たとおり、**HTTPはステートレス**なプロトコルであり、それ自体にはセッションを管理する仕組みがありません。そのため、Webアプリケーションでは、サーバ側でセッション管理情報（セッションID）を生成し、URLやCookieにセットしてクライアントとやり取りすることで、各クライアントの識別や状態管理を行う必要があります。ログイン後のWebサーバにとって、**セッションIDは「ログイン済みの本人である」ことの唯一の証拠**です。したがって、セッションIDを手に入れた攻撃者は、パスワードを知らなくても本人になりすませます。Webアプリケーションの開発では、この仕組みを安全かつ確実に実装することが最大の課題となっていますが、脆弱な状態で公開されているサイトも数多くあります。

攻撃者は、URL、Cookie、hiddenフィールドなどにセットされたセッション管理情報を**推測**するか、**盗聴**することによって自身のパケットを偽装し、Webサーバとのセッションをハイジャックします。セッションIDの受渡し手段の比較は 1.4 の 7.8 で整理しました。

> **hiddenフィールド（隠しフィールド）**
> HTMLのフォームにおいて、ブラウザの画面上には表示されない入力フィールド（`<input type="hidden">`）。画面間での値の受け渡しや計算結果の保持などに使用されるが、HTMLソースを参照すれば容易に内容を確認・改変できるため、機密情報やセッション管理情報をそのまま格納するのは危険である。

```
図：Webサーバとクライアント間のセッションハイジャックのイメージ

 正規のユーザ ── ① ログイン ──────────────→ Webサーバ
              ←─ セッションID発行（Set-Cookie）─┘
                        │
                        │ ② 推測・盗聴などでセッションIDが攻撃者に渡る
                        ↓
 攻撃者 ── ③ 入手したセッションIDを自分のリクエストにセット ──→ Webサーバ
                                      ④ Webサーバは攻撃者を正規のユーザと誤認する
```

1. 正規のユーザがWebサーバにログインし、セッションIDが発行される
2. 攻撃者は、推測や盗聴などによってそのセッションIDを入手する
3. 攻撃者は、入手したセッションIDを自身のリクエストにセットしてWebサーバにアクセスする
4. Webサーバは攻撃者を正規のユーザと誤認し、攻撃者がなりすましに成功する

### 3.2 攻撃を成立させるセッション管理の脆弱性

次のようなセッション管理の脆弱性により、この攻撃が成立する可能性が高まります。表の右2列は、それぞれの脆弱性に対して「誰が、何のために、どうすべきか」を先取りしたものです（詳細は 5.3節と [3.6](3.6_HTTP及びWebアプリケーションの脆弱性と対策.md) の 2章）。

| セッション管理の脆弱性 | 攻撃者は何ができるか | 対策（誰が・どうする） | なぜ有効か |
|---|---|---|---|
| セッションIDが単純（連番、日時やユーザIDから生成されるなど） | 他人のセッションIDを推測・偽装する | 開発者が、暗号論的に安全な疑似乱数で十分な長さのIDを生成する | 推測の手掛かりがなくなる |
| 詳細なセッション管理情報が丸見えになっている | 丸見えの情報（ユーザID、権限など）を書き換えて悪用する | 開発者が、IDだけをクライアントに渡し、詳細はサーバ側に置く | 書き換えられる情報をクライアントに置かない |
| 通信が暗号化されていない | 経路上でセッションIDを盗聴する | 運用者がTLS（HTTPS）を使い、開発者がCookieにSecure属性を付ける | 経路上でIDを読めなくする |
| URLにセッションIDが埋め込まれている | Refererヘッダやアクセスログを通じて漏えいしたIDを使う | 開発者が、IDをURLでなくCookieに格納する | URLに残らないので外部に漏れない |
| XSS（クロスサイトスクリプティング）の脆弱性がある | スクリプトでCookieに格納されたセッションIDを盗む | 開発者が、出力をエスケープし、CookieにHttpOnly属性を付ける | スクリプトからCookieを読ませない |
| セッションの有効期限が長すぎる、ログアウト後もセッションが無効化されない | 盗んだIDを長期間使い続ける | 開発者が、適切な有効期限を設け、ログアウト時にサーバ側でセッションを破棄する | 盗まれたIDの使える期間を短くする |

URLにセッションIDが埋め込まれている場合の漏えいは、1.4 の 7.6 で見た Referer の性質によるものです。利用者が画面内の外部リンクをクリックすると、リンク先のサーバのアクセスログには次のような行が残ります（例示用のログ）。

```
203.0.113.50 - - [30/Sep/2026:10:15:42 +0900] "GET /index.html HTTP/1.1" 200 5120 "https://shop.example.jp/mypage;jsessionid=8F3A9C2E1B7D4F60" "Mozilla/5.0 ..."
                                                                                   ↑ Referer 欄に、別サイトのセッションIDがそのまま記録されている
```

外部サイトの管理者（やそのログを見られる誰か）の手元に、有効なセッションIDが残ってしまうわけです。Webアプリケーションの開発者は、この行が生まれないように、セッションIDをURLに載せない設計にすべきです。

> **XSS（Cross Site Scripting：クロスサイトスクリプティング）**
> Webアプリケーションが入力値を適切にエスケープせずに出力することを悪用し、攻撃者が用意したスクリプトを利用者のブラウザ上で実行させる攻撃。CookieにHttpOnly属性を付与することで、スクリプトからのCookieの読み取りを防止できる。XSSの仕組みと対策の詳細は [2.8](2.8_Webアプリケーションに不正なスクリプトや命令を実行させる攻撃.md) と [3.6](3.6_HTTP及びWebアプリケーションの脆弱性と対策.md) で扱う。

### 3.3 認証サーバとクライアント間のセッションハイジャック

攻撃者が、認証を行っているサーバ（認証サーバ）になりすましてクライアントからのアクセス要求を受け付け、セッションハイジャックを成立させる手法もあります。認証プロセスにおいて、クライアント側でサーバの信頼性（正当性）を確認する手段がない場合に、この問題が発生する可能性があります。

多くの認証方式は「サーバがクライアントを確かめる」ことに注意が向きがちですが、逆向き、つまり「**クライアントがサーバを確かめる**」ことができないと、利用者は偽の認証サーバに自分から資格情報を渡してしまいます。偽の無線LANアクセスポイントや偽のログイン画面が成立するのも同じ理由です。システムの設計者は、クライアントがサーバの正当性を検証できる方式（サーバ証明書による認証、相互認証）を選ぶべきです（第6章）。

## 4. セッションフィクセーション ― セッションIDを「押し付ける」攻撃

### 4.1 仕組み

**セッションフィクセーション（Session Fixation：セッションIDの固定化）** とは、Webアプリケーションシステムにおけるセッションハイジャックの手法の一つです。3章の攻撃が既に確立されているセッションのIDを「盗む」のに対し、セッションフィクセーションでは、攻撃者は自分が生成（入手）したセッションIDを含む不正なURLをターゲットユーザに送り付けることで意図的にセッションを確立させ、そのセッションを乗っ取ります。攻撃者は「盗む」必要がなく、「**最初から知っているIDを相手に使わせる**」のです。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後I問1で、セッションフィクセーションの仕組みと対策が出題された。

典型的な攻撃の手順は次のとおりです。

1. 攻撃者がターゲットサイトにアクセスし、正規のセッションIDを入手する（例：`sessionid=98765`）
2. 攻撃者は、入手したセッションIDを含むURL（例：`https://www.example.com/login?sessionid=98765`）をリンク先としてセットしたフィッシングメールをターゲットユーザに送付する（もしくは他の手段でそのURLをクリックさせる）
3. ターゲットユーザがそのリンクをクリックし、（そのセッションIDを使って）ターゲットサイトにログインする
4. 攻撃者も同じセッションIDを使ってターゲットサイトへのアクセスに成功し、正規のユーザになりすまして不正な操作などを行う

```
図：セッションフィクセーションのイメージ

 攻撃者 ────────── ① アクセスしてセッションIDを入手 ──────────→ ターゲットサイト
   │
   └─ ② セッションID付きURLを記載したメールを送付 ─→ ターゲットユーザ
                                                          │
                     ③ そのURLからログイン（セッションIDは固定されたまま）
                                                          └──→ ターゲットサイト
 攻撃者 ────────── ④ 同じセッションIDでアクセスし、なりすましに成功 ─→ ターゲットサイト
```

> **フィッシング（Phishing）**
> 銀行、クレジットカード会社、オンラインショッピングサイトなどを装った電子メールを送り付け、本物のサイトに見せかけた偽のページに誘導して、口座番号、クレジットカード番号、パスワードなどの情報を盗む詐欺の手口。

セッションフィクセーションで利用者が誘導される先は**本物の**ターゲットサイトであり、利用者は本物のサイトに正しいパスワードを入力しているだけです。偽サイトに誘導するフィッシングと違い、利用者がURLのドメイン名を確かめても見抜けません。だからこそ、対策の主役は利用者ではなくWebアプリケーションの開発者になります。

### 4.2 成立条件と、それぞれを断つ対策

この攻撃が成立するのは、次のような条件を**すべて**満たす場合です。裏返せば、開発者と運用者はどれか1つを確実に断てば攻撃を止められます。

| 成立条件 | 条件を断つ対策（誰が・どうする） |
|---|---|
| 正規のセッションIDを容易に入手可能であること（会員制サイトであっても、ログイン前の段階でセッションIDが発行される場合など） | 開発者が、ログイン前のIDをログイン後に引き継がない設計にする（下の再発行と同じ） |
| WebサーバがURLに含まれるセッションIDを受け付けること（URL Rewriting機能が有効になっているなど） | Webサーバの運用者が、URL Rewriting機能を無効にする |
| ユーザのログイン成功後も、ログイン前と同じセッションIDが引き続き使用されること | 開発者が、ログインに成功した時点で新しいセッションIDを発行し直す（**最も確実**） |
| 攻撃者がターゲットユーザにフィッシングメールなどを送ることが可能であること | 組織の管理者が、利用者への注意喚起や迷惑メール対策を行う（補助的） |
| ユーザがフィッシングメールに騙され、ログインすること | 利用者が、メール中のリンクからではなく、ブックマークなどからログインする（補助的） |

こうしたことから、成立する可能性は決して高いとはいえませんが、Webサーバの設定やWebアプリケーションのセッション管理の実装については見直す必要があります。表の3行目の「ログイン成功後のセッションID再発行」が最も確実な理由は、攻撃者が事前に知っているIDを、ログインという**権限が変わる瞬間**に無効化できるからです。攻撃者の手元のIDは「ログイン前の、権限のないセッション」を指したまま取り残されます。

### 4.3 Cookie Monster Bug と CSRF

なお、"Cookie Monster Bug" のあるブラウザでは、この攻撃が成立する可能性が高まります。"Cookie Monster Bug" とは、Cookieのdomain属性が正しく機能せず、指定した範囲を超えてCookieが有効となってしまうバグです（例えば、`.co.jp` のような広い範囲に対してCookieが設定できてしまう）。この場合、攻撃者は自分が管理する別の `.co.jp` のサイトから、ターゲットサイトにも送られるCookieを利用者のブラウザにセットでき、URLを使わなくてもセッションIDを押し付けられてしまいます。これにより、セッションフィクセーションのほか、クロスサイトリクエストフォージェリ（CSRF）なども成立しやすくなります（CSRFについては [3.6](3.6_HTTP及びWebアプリケーションの脆弱性と対策.md) のCSRFの節を参照）。

> **補足：現在のブラウザでの扱い**
> Cookie Monster Bug は、主に古いブラウザで問題になったものです。現在の主要なブラウザは、`.co.jp` や `.com` のように誰でも登録できる上位のドメイン（パブリックサフィックス）を一覧（Public Suffix List）で管理し、そこを対象とするCookieを拒否します。1.4 の 7.7 の表で「『.co.jp』『.com』など上位ドメインだけの指定は無効」とあるのは、この扱いを指しています。ただし、同じ組織のサブドメイン間（例：`a.example.jp` と `b.example.jp`）ではCookieを共有できるため、信頼できないサブドメインを同居させない、Domain属性を不用意に指定しないといった注意は今も必要です。

> **CSRF（Cross Site Request Forgery：クロスサイトリクエストフォージェリ）**
> ログイン状態にある利用者に、攻撃者が用意した罠ページなどを経由して意図しないリクエストを送信させ、利用者の権限で不正な処理（書込み、送金、設定変更など）を実行させる攻撃。

## 5. セッションハイジャックへの対策

### 5.1 対策の全体像

セッションハイジャックへの対策を、手口ごとに「誰が・何のために」をそろえて一覧にします。1.2 の対策の4機能のうち、予防・防止が中心で、検知・回復がそれを補います。

| 手口 | 対策の担い手 | 何のために | 予防・防止の中心 | 検知 |
|---|---|---|---|---|
| TCP、UDPにおけるセッションハイジャック | OS・サーバの管理者 | 偽装パケットを受け入れさせない | パッチ適用、TLS・IPsec・SSHの使用 | IDS |
| Webサーバとクライアント間 | 開発者、Webサーバの運用者 | セッションIDを推測・盗聴・漏えいさせない | TLS＋Secure属性、安全なID生成、Cookie＋HttpOnly属性、有効期限、WAF | IDS、WAFのログ |
| 認証サーバとクライアント間 | システムの設計者 | クライアントが偽サーバを見抜けるようにする | サーバ証明書で正当性を確認できるプロトコル（TLSなど） | ― |
| 偽装ARP | ネットワーク管理者 | 不正な機器とARP偽装をLANに入れない | スイッチの物理的保護、不正PC接続検知、ARP防御機能付きスイッチ、静的ARP | ARPキャッシュの監視 |
| セッションフィクセーション | 開発者、Webサーバの運用者 | 攻撃者が知っているIDを使わせない | URL Rewriting無効化、ログイン後のID再発行 | ― |

### 5.2 予防・防止：TCP、UDPにおけるセッションハイジャック

**パッチ適用**：OS及びサーバの管理者は、初期シーケンス番号の予測可能性のような実装上の脆弱性を残さないために、OS及び使用しているソフトウェアのバージョンを最新化し、パッチを適用すべきです。

**暗号化プロトコルの使用**：システムの設計者・管理者は、TLS、IPsec、SSHなど、パケットの偽装が困難な暗号化プロトコルを使用すべきです。これらのプロトコルは、暗号化に加えて通信相手の認証と改ざん検知を行うため、攻撃者がシーケンス番号やIPアドレスを正しく偽装できても、正しい鍵を持たない限り、受信者は偽装パケットを改ざんされたものとして破棄します。「つじつまが合えば信じる」TCP/UDPの上に、「鍵を持つ相手だけを信じる」層をかぶせる、という発想です。

**脆弱性検査**：管理者は、脆弱性検査を実施し、セッションハイジャックにつながる可能性のあるセキュリティホールの有無を確認します。問題箇所があれば対処します（検査の進め方は第5章 5.3）。

> **TLS（Transport Layer Security）**
> SSL 3.0 をベースに、IETF（Internet Engineering Task Force：インターネット技術タスクフォース）によって標準化されたトランスポート層における暗号化プロトコル。通信の暗号化に加え、デジタル証明書によるサーバ（及びクライアント）の認証、改ざん検知の機能を提供する。
> なお、SSL 3.0 と TLS 1.0／1.1 は現在では脆弱性のため使用が非推奨（廃止）とされており、サーバの管理者は TLS 1.2 以上だけを有効にすべきである（第7章）。

> **IPsec（IP Security）**
> IPパケットを暗号化・認証するためのプロトコル群。ネットワーク層で動作するため、上位のアプリケーションに依存せずに通信を保護できる。VPNの構築などに広く使用される。

> **SSH（Secure Shell）**
> ネットワークを介して他のコンピュータにログインしたり、コマンドを実行したりするための通信を暗号化して行う方式及びそのプロトコル。telnet や rlogin、rcp などBSD系のrコマンドに代わり、リモート操作を安全に行う手段として広く使用されている。暗号化アルゴリズムとしてAESなどが用意されており、セッションごとに異なる鍵が生成される。

### 5.3 予防・防止：Webサーバとクライアント間のセッションハイジャック

Webアプリケーションの開発者とWebサーバの運用者は、次の対策を組み合わせます。

**通信の暗号化**：Webサーバの運用者は、経路上でセッションIDを盗聴させないために、TLSを使用してWeb通信を暗号化します。あわせて開発者は、CookieにSecure属性を付与し、暗号化されていない通信でセッションIDが送信されないようにします。サイト全体をHTTPSにしても、利用者が一度でも `http://` のURLにアクセスすれば、Secure属性のないCookieは平文で送られてしまうからです。

**セッション管理機能の安全な実装**：開発者は、セッション管理情報の推測、漏えい、偽装などが発生しにくいように、利用形態やサーバ構成などに応じたセッション管理機能を実装します。

- セッションIDは、暗号論的に安全な疑似乱数を用いて十分な長さで生成する
- セッションIDはURLではなくCookieに格納し、HttpOnly属性を付与する
- セッションに適切な有効期限を設け、ログアウト時にはセッションを確実に無効化する

これらを満たしたCookieの発行は、レスポンスヘッダで次のように見えます。1.4 の 7.7 で見た属性が、どれも「盗ませない・送らせない」方向に設定されていることを確認してください。

```
HTTP/1.1 200 OK
Set-Cookie: SESSIONID=f3Kq9vX2mL7pR0tZ8wB4nC6yD1sH5jA; Path=/; Secure; HttpOnly; SameSite=Lax
             ↑ 推測困難な長い乱数       ↑ Domain を指定しない（発行したホストだけに送る）
                                              ↑ HTTPSのときだけ送る（盗聴対策）
                                                      ↑ スクリプトから読ませない（XSS対策）
                                                                ↑ 他サイトからのPOSTで送らない（CSRF対策）
             Expires／Max-Age を指定しない → ブラウザを閉じると消えるセッションCookie
```

| 属性 | 開発者が設定する目的 | 付けないと何が起きるか |
|---|---|---|
| Secure | HTTPS通信のときだけCookieを送らせる | `http://` へのアクセス時にセッションIDが平文で流れ、盗聴される |
| HttpOnly | JavaScriptからCookieを読ませない | XSSの脆弱性があると、スクリプトでセッションIDを抜き取られる |
| SameSite（Lax／Strict） | 他サイトを起点とするリクエストにCookieを付けさせない | CSRFで、ログイン中の利用者の権限を使われる |
| Domain（指定しない） | 発行したホストだけにCookieを送らせる | 同じドメインの別ホスト（信頼できないサブドメインなど）にもセッションIDが送られる |

実装の具体例（PHPでの設定、セッションIDの再発行など）は [3.6](3.6_HTTP及びWebアプリケーションの脆弱性と対策.md) の 2.3 で扱います。なお、開発者はセッション管理を自作するより、フレームワークやアプリケーションサーバのセッション管理機能を使うほうが安全です。安全な乱数生成やID再発行の機能が検証済みの形で用意されているからです。

**脆弱性検査**：開発者・運用者は、Webアプリケーションに対する脆弱性検査を実施し、セッション管理に関するセキュリティホールの有無を確認します。問題箇所があれば対処します。

**リバースプロキシ・WAF**：運用者は、Webサーバのフロント（前面）にリバースプロキシサーバやWebアプリケーションファイアウォール（WAF）を設置し、セッション管理の脆弱性を突いた攻撃を排除します。ただし、WAFは「攻撃らしい文字列」を見る装置なので、正しい形式のセッションIDを使ったなりすましまでは見抜けません。WAFはアプリケーションの改修の代わりではなく、改修までの時間を稼ぐ補助策と位置づけるべきです（第5章 [5.8](5.8_Webアプリケーションファイアウォール.md)）。

> **WAF（Web Application Firewall）**
> Webアプリケーションへの通信内容をアプリケーション層で検査し、SQLインジェクションやXSS、不正なセッション操作などの攻撃パターンを検知・遮断する仕組み。

### 5.4 予防・防止：認証サーバとクライアント間のセッションハイジャック

システムの設計者は、TLSなど、**サーバの正当性が確認でき**、かつパケットの偽装が困難なプロトコルを使用すべきです。クライアントがサーバ証明書を検証することで、偽の認証サーバに資格情報を渡すことを防げます。あわせて利用者は、ブラウザが証明書の警告を表示したときに、それを無視して先へ進まないことが求められます。警告を無視すれば、せっかくの正当性確認が働かないからです。

### 5.5 予防・防止：偽装ARPによるセッションハイジャック

ARPの弱点は仕様そのものにあるため、ネットワーク管理者は「攻撃者をLANにつながせない」「ARPの偽装を機器で止める」という2方向から補強します。

- **ハブ（スイッチ）の物理的保護**：ネットワーク管理者は、ハブ（スイッチ）を施錠できるラックなどで物理的に保護することで、不正な機器が物理的に接続されるのを防ぎます。
- **不正PC接続検知システム**：ネットワーク管理者は、不正PC接続検知システムによって、登録されていない機器の接続を排除します。
- **ARP防御機能をもつ製品**：ネットワーク管理者は、ARPポイズニングを検知／防止する機能をもった製品（ハブ）を用います。代表的なのは、DHCPで正規に払い出したIPアドレスとMACアドレスの対応を覚えておき、それと矛盾するARP応答を破棄するスイッチの機能（ダイナミックARPインスペクションなどと呼ばれます）です。
- **静的ARPエントリ**：サーバの管理者は、重要なホスト（デフォルトゲートウェイ、基幹サーバなど）について、ARPキャッシュに静的なエントリを登録します。静的なエントリは偽のARP応答では上書きされないからです。ただし、機器の交換のたびに全端末の設定を直す必要があるため、対象は重要なホストに絞ります。

```
静的ARPエントリの登録と確認の例（Linux の場合）
# ip neigh replace 192.0.2.1 lladdr 00:00:5e:00:53:01 dev eth0 nud permanent
# ip neigh show 192.0.2.1
192.0.2.1 dev eth0 lladdr 00:00:5e:00:53:01 PERMANENT      ← PERMANENT＝静的エントリ（偽のARP応答で書き換わらない）
```

### 5.6 予防・防止：セッションフィクセーション

前述の「Webサーバとクライアント間のセッションハイジャック」の対策に加えて、次の対策を実施します。

- **URL Rewriting機能の無効化**：Webサーバの運用者は、WebサーバのURL Rewriting機能を無効にし、URLに含まれるセッションIDを受け付けないようにします。攻撃者がURLでIDを押し付ける経路を断つためです。
- **ログイン成功後のセッションID再発行**：セッション管理を自社で開発している場合、開発者は、ユーザがログインに成功した後で新たにセッションIDを発行するようにします。ログイン権限のない者がセッションIDを入手して悪用するのを防ぐためです。フレームワークを使う場合も、ログイン処理で再発行の関数（例：PHPの `session_regenerate_id(true)`）が呼ばれているかを確認します。

### 5.7 検知

- **IDS**：セキュリティ運用担当者は、IDS（侵入検知システム）によってセッションハイジャックの兆候を検知します。ただし、検知できるのは典型的な一部のパターンのみです。暗号化された通信の中身や、正しい形式のセッションIDによるなりすましは、IDSからは正常な通信に見えるからです（第5章 [5.6](<5.6_侵入検知システム(IDS).md>)）。
- **ARPキャッシュの監視**：ネットワーク管理者は、ARPキャッシュを監視するツールによって、IPアドレスとMACアドレスの対応関係の不正な変化を検知します。
- **不正PC接続検知**：ネットワーク管理者は、不正PC接続検知システムによって、LAN上に接続された不正な機器を検知します。

ARPの監視ツールは、対応関係が変わると次のようなログを出します（例）。運用者は、これを「ゲートウェイのような、めったに変わらないはずの対応が変わった」という兆候として読み取ります。

```
Sep 30 10:15:42 mon01 arpwatch: changed ethernet address 192.0.2.1 00:00:5e:00:53:99 (00:00:5e:00:53:01) eth0
                                                        ↑ ゲートウェイの   ↑ 新しいMAC        ↑ 以前のMAC
                                                          IPアドレス         （攻撃者の機器？）
```

このログを見た運用者は、まず新しいMACアドレスがどのスイッチのどのポートにつながっているかを確認し、ゲートウェイ機器の正規の交換作業でなければ、そのポートを切り離して調査します。

Webのハイジャックについては、アプリケーションのログで「同じセッションIDが、短時間のうちに地理的に離れたIPアドレスや異なるブラウザ（User-Agent）から使われている」といった不自然さが兆候になります。開発者は、こうした調査ができるように、セッションIDそのものではなくそのハッシュ値などをログに残しておくと、ログ自体が新たな漏えい源になることを避けられます。

### 5.8 回復

- セキュリティ運用担当者は、被害状況を調査し、必要に応じてシステム及びデータの復旧作業を行います。Webのハイジャックでは、攻撃者が使っているセッションをサーバ側で強制的に無効化し、影響を受けた利用者にはパスワードの変更を依頼します。
- 管理者は、攻撃が成立した原因となった脆弱性を特定し、必要な対策を実施します。
- 管理者は、再発防止のため、予防・防止に挙げた対策を実施します。

## 6. 確認問題

### 6.1 理解度チェック

- **Q1**：セッションハイジャックにはどのような手法があるか。
- **Q2**：Webサーバとクライアント間のセッションハイジャックが成立する原因となる脆弱性とは何か。
- **Q3**：Webサーバとクライアント間のセッションハイジャックに対しては、どのような対策が有効か。
- **Q4**：認証サーバとクライアント間のセッションハイジャックに対しては、どのような対策が有効か。
- **Q5**：セッションフィクセーションとはどのような攻撃手法か。
- **Q6**：どのような脆弱性があると、セッションフィクセーションが成立する可能性が高まるか。
- **Q7**：セッションフィクセーションへの対策にはどのようなものがあるか。

> **解答の要点**
> - Q1：TCPにおけるセッションハイジャック、UDPにおけるセッションハイジャック、Webサーバとクライアント間、認証サーバとクライアント間、偽装ARPによるもの（ARPポイズニング）、セッションフィクセーション（2〜4章）。
> - Q2：単純なセッションID、丸見えのセッション管理情報、暗号化されていない通信、URLへのセッションIDの埋め込み、XSSの脆弱性、長すぎる有効期限とログアウト後も無効化されないセッション（3.2）。
> - Q3：TLSによる暗号化とSecure属性、安全な疑似乱数による十分な長さのID、Cookieへの格納とHttpOnly属性、適切な有効期限とログアウト時の無効化、脆弱性検査、リバースプロキシ・WAFの設置（5.3）。
> - Q4：TLSなど、サーバの正当性が確認でき、パケットの偽装が困難なプロトコルを使用する（5.4）。
> - Q5：攻撃者が入手したセッションIDを含むURLを利用者に踏ませてログインさせ、同じIDで利用者になりすます攻撃（4.1）。
> - Q6：ログイン前にIDが発行される、URL中のIDを受け付ける（URL Rewriting）、ログイン後も同じIDを使い続ける、など（4.2）。
> - Q7：Webのハイジャック対策に加え、URL Rewriting機能の無効化と、ログイン成功後のセッションID再発行（5.6）。

### 6.2 演習問題（過去問題）

デジタル証明書を使わずに、通信者同士が、通信によって交換する公開鍵を用いて行う暗号化通信において、通信内容を横取りする目的で当事者になりすますものはどれか。

- ア　Man-in-the-middle攻撃
- イ　war driving
- ウ　トロイの木馬
- エ　ブルートフォース攻撃

> **解答・解説**
> デジタル証明書を使わない場合、受け取った公開鍵が本当に通信相手のものかを確認できない。そのため、攻撃者が通信経路の途中で双方の公開鍵を自身の公開鍵にすり替えれば、双方になりすまして通信内容を復号・盗聴・改ざんできる。これはMan-in-the-middle攻撃（中間者攻撃）である。
> - イ　war driving は、無線LANのアクセスポイントを探して移動しながら不正利用を試みる行為である。
> - ウ　トロイの木馬は、有用なプログラムを装って侵入し、不正な動作を行うマルウェアである。
> - エ　ブルートフォース攻撃は、パスワードや鍵の考えられる全ての組合せを試す総当たり攻撃である。
>
> **正解：ア**
>
> 1.1 の中間者攻撃の説明どおり、「真正性を確認する仕組み（デジタル証明書）がない」ことが成立の条件になっている点に注目してほしい。暗号化していても、鍵の持ち主を確かめなければ中間者攻撃は防げない。

## 7. 試験対策まとめ（重要ポイント）

### 7.1 知識の確認（科目A-2向け）

- **セッションハイジャックと中間者攻撃**：セッションハイジャックは確立済みのセッションを奪う行為の総称。双方になりすまして中継するものが中間者攻撃（MITM）。中間者攻撃は「相手の真正性を確認できない（デジタル証明書がない）」ときに成立する。
- **層ごとの手口**：TCPはシーケンス番号の推測・盗聴＋IPアドレス偽装、UDPは正規より先に偽応答を返す（例：DNSキャッシュポイズニング）、LANは偽のARP応答でARPキャッシュを書き換える（ARPポイズニング／ARPスプーフィング）。
- **初期シーケンス番号**：推測されないよう乱数を使う。旧OSでは規則性があり推測できた（1994年のミトニックの攻撃）。IPアドレスだけで接続を許すrコマンドが前提で、現在はSSHに置き換えられた。
- **Webのハイジャックの原因**：単純なID、URLへの埋め込み（Referer漏えい）、平文通信、XSS、長い有効期限・ログアウト後の未無効化。
- **Cookieの属性**：Secure＝盗聴対策、HttpOnly＝XSSによる窃取対策、SameSite＝CSRF対策。Domainは「指定しない」ほうが安全。
- **セッションフィクセーション**：IDを「盗む」のではなく「押し付ける」。決め手の対策は**ログイン成功後のセッションID再発行**と**URL Rewriting機能の無効化**。
- **ARPポイズニングの対策**：スイッチの物理的保護、不正PC接続検知、ARP防御機能付きスイッチ、重要ホストの静的ARPエントリ、ARPキャッシュの監視。
- **IDSの限界**：検知できるのは典型的な一部のパターンだけ。

### 7.2 記述式で問われる観点（科目B向け）

- **なりすましが成立した理由を特定する**：「サーバはセッションIDだけで本人と判断しているため」「ARPには応答の正当性を検証する仕組みがないため」のように、真正性を確かめていない箇所を根拠として書く。
- **セッションIDが漏れた経路を答える**：事例のログやURLにセッションIDが現れていれば、「URLに埋め込まれたセッションIDがRefererヘッダによって外部サイトに送信された」のように、経路と仕組みを1文で説明する。
- **Cookie属性を目的とセットで答える**：「Secure属性を付与し、HTTPS通信の場合だけCookieが送信されるようにする（盗聴による窃取を防ぐため）」のように、属性名・効果・理由をそろえる。
- **セッションフィクセーション対策の理由**：「ログイン成功後にセッションIDを再発行する。攻撃者が事前に入手したIDを、権限が付与される時点で無効にできるため」と、なぜ有効かまで書く。
- **ARPポイズニングの検知と初動**：監視ツールのログからIPアドレスとMACアドレスの対応の変化を読み取り、MACアドレスから接続ポートを特定して切り離す、という手順を説明できるようにしておく。
- **対策の担い手を区別する**：仕様の弱点（UDP、ARP）は管理者が外側から補強し、実装・セッション管理の弱点は開発者が直す。設問が「開発者として」か「運用者として」かを読み分ける。
