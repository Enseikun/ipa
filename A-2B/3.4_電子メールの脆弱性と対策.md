# 3.4 電子メールの脆弱性と対策

電子メールを実現しているSMTP（Simple Mail Transfer Protocol）やPOP3（Post Office Protocol Version 3）は、DNSやHTTPと並んで古くから使われているサービスです。長く使われてきた分、プロトコルの仕様や実装について多くのセキュリティ上の問題点が指摘されています。ここでは、SMTPやPOP3の仕様と実装における脆弱性と、その対策について解説します。

> **用語：電子メールシステムの構成要素**
>
> - **MUA（Mail User Agent）**：メールの作成・閲覧を行うクライアントソフトウェア（メーラ）
> - **MSA（Mail Submission Agent）**：MUAからのメール投稿を受け付けるサーバ機能
> - **MTA（Mail Transfer Agent）**：メールサーバ間でメールを中継・配送するサーバ機能（SMTPサーバ）
> - **MDA（Mail Delivery Agent）**：受信したメールを利用者のメールボックスへ格納する機能

## 3.4.1 SMTPの脆弱性

メールの利用において近年最も大きな問題となっているのは、インターネット上を常に飛び交っている膨大な迷惑メール（スパムメール）です。全世界で送信されるメールのうち、実に80％がスパムメールといわれています。これほどスパムメールが横行する原因は、旧バージョンのメールサーバソフトウェアの仕様にある脆弱性（次に挙げる①と②）です。

迷惑メールは、スパムメール（spamメール）のほか、UBE（Unsolicited Bulk Email）やUCE（Unsolicited Commercial Email）とも呼ばれます。宣伝や嫌がらせなどの目的で、不特定多数に大量に送信されるメール全般を指します。迷惑メールの多くは、送信元のメールアドレス（ドメイン名）を詐称するUBEです。また、第三者中継を許可している複数のサーバを経由して配信されるケースが多く見られます。

SMTPの脆弱性には、次のようなものがあります。

### ① メールの投稿や中継などがすべて同じ仕組みで行われている

旧バージョンのメールサーバソフトウェアでは、MSAの機能はMTAに統合されていました。そのため、次の2種類の通信が、いずれも同じ25番ポート（SMTP）で同じ仕組みによって処理されていました。

- MUAからのメールの投稿（Submission）
- MTA間のメールの中継（Relay）

その結果、サーバ側では「自組織の利用者による投稿」と「他のサーバからの中継」を区別して制御することが困難でした。

### ② メールの投稿にあたってユーザを認証する仕組みがない

広く普及しているメールサーバソフトウェアの旧バージョンには、メールの投稿時にユーザを認証する仕組みがありませんでした。そのため、次のような問題が生じます。

- 送信元メールアドレスの詐称が堂々と行われる
- 本来受け付ける必要のない組織外の第三者から、別の第三者へのメール投稿を受け付けて中継してしまう

後者を**第三者中継（Third-Party Mail Relay）**といいます。第三者中継は**オープンリレー**とも呼ばれ、それを行うSMTPサーバを**オープンリレー（SMTP）サーバ**と呼びます。

現在一般に普及しているメールサーバソフトウェアには、後述するSMTP-AUTHが実装されています。したがって、メールの投稿時にユーザ認証を行うことが可能です。

インターネットと内部ネットワークの境界でメールを中継する一般的なMTA（SMTPサーバ）は、本来、次の条件に合致するメールだけを中継すればよいはずです。

- **自サイト内のユーザが任意のアドレスあてに送信するメール**
  （送信元メールアドレスに自サイトのドメイン名が含まれているもの）
- **任意のアドレスから自サイト内のユーザあてに送られてくるメール**
  （あて先メールアドレスに自サイトのドメイン名が含まれているもの）

> **試験に出る**
> 情報処理安全確保支援士試験の午後問題では、第三者中継やメールサーバの設定を題材にした問題が出題されています。

**図：正常なメール中継の例**

```
【送信】自サイトのユーザ(user@example.co.jp) ──> 自サイトのMTA ──> 任意のあて先ドメインのMTA
        （送信元ドメイン = 自サイト）

【受信】任意の送信者 ──> 自サイトのMTA ──> 自サイトのユーザ(user@example.co.jp)
        （あて先ドメイン = 自サイト）

【第三者中継（拒否すべき）】
        第三者(spammer@other1.example) ──> 自サイトのMTA ──> 別の第三者(victim@other2.example)
        （送信元・あて先ともに自サイトと無関係）
```

ところが第三者中継では、自サイトとは関係のない第三者（送信者）が、自サイトとは関係のない別の第三者にメールを中継させようとします。そのため、送信元メールアドレスとあて先メールアドレスのいずれも、自サイトとは関係のないドメイン名になっています。

中継対象のメールが上記の条件に合致するかどうかは、送信元メールアドレスとあて先メールアドレスを見れば容易に確認できます。したがって、条件に合致しないメールの中継を拒否すればよいだけです。しかし実際には、条件に合致しないメールでも無条件に中継してしまうメールサーバ（オープンリレーサーバ）が、インターネット上にまだ数多く存在しています。こうしたサーバはスパマー（スパムメールの送信者）の踏み台となり、スパムメールの中継に悪用されています。

オープンリレーサーバは、スパムメールの発信源としてブラックリストに登録される可能性があります。メールサーバがいったんブラックリストに登録されると、そのサーバから送信されるメールは、ブラックリストを利用しているメールサーバで受信を拒否されてしまいます。

> **用語：ブラックリスト（DNSBL / RBL）**
> スパムメールの発信源やオープンリレーサーバのIPアドレスを登録したリストです。DNSの仕組みを利用して参照できるものが多く、DNSBL（DNS-based Blackhole List）やRBL（Realtime Blackhole List）と呼ばれます。受信側のメールサーバは、接続元IPアドレスがリストに登録されていれば受信を拒否します。

また、**NDR（Non-Delivery Report：配送不能通知）メール**を悪用してスパムを送り付ける手法もあります。NDRメールは、送信先のメールアドレスが存在しないなどの理由でメールを正常に送信できなかった場合に、それを通知するためのメールです。送信できなかったメールを添付して、送信元のアドレスに送られます。

スパマーはこの機能を次のように悪用します。

1. 送信元アドレスを、スパムメールを届けたいアドレスに詐称する
2. 意図的に配送不能となるメールを、踏み台となるメールサーバあてに送り付ける
3. 詐称された送信元アドレスあてに、NDRメール（**NDRスパム**、バックスキャッタとも呼ぶ）が送り付けられる

NDRメールの受信者は、自分が送ったどのメールが配送不能になったのかを確認しようとして、添付されたメール（実際にはスパムや不正なプログラムを含むメール）を開いてしまうおそれがあります。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後問題では、NDRメールを悪用したスパム（バックスキャッタ）に関する問題が出題されています。

この手法への対策には、次のような方法があります。

- NDRスパムの発信源とならないよう、NDRメールを送信しないように設定する
- NDRスパムを遮断するため、NDRメールをすべてフィルタリングする

ただし、こうした対策を行うと、NDRメール本来の目的は達成できなくなります。現実的には、受信時点で存在しないあて先を拒否する（SMTPセッション中にエラー応答を返し、受信後にNDRを生成しない）設定が推奨されます。

### ③ メールの暗号化機能が標準装備されていないため、平文でネットワークを流れる

SMTPにはメールの暗号化機能がありません。そのため、クライアントアプリケーション側で暗号化を行わない限り、メールは平文でネットワーク中を流れます。したがって、パケット盗聴によってメールの内容が漏えいしたり、改ざんされたりする可能性があります。

### ④ MTAの実装・設定によってユーザのメールアカウント情報が漏えいする可能性がある

一般的なMTAには、**VRFY**、**EXPN**というコマンドがあります。これらのコマンドを使用すると、次の情報を確認できます。

- そのサーバにおけるメールアカウントの有無
- メールアカウント名がエイリアスやメーリングリストの場合の、実際の配送先情報

攻撃者はこれらのコマンドを悪用して、有効なメールアドレスの収集（アカウントの列挙）を行うことができます。

### ⑤ MTAの種類・バージョンによってBOF攻撃を受ける脆弱性がある

MTAの中には非常に古くから使われているものがあります。特に旧バージョンのMTAについては、BOF攻撃を受ける脆弱性など、数多くの脆弱性が報告されています。

> **用語：BOF攻撃**
> バッファオーバフロー（Buffer OverFlow）攻撃のことです。アプリケーションプログラムの入力データの長さのチェック不備を突き、バッファ（データを一時的に格納するメモリ領域）を意図的にあふれさせます。これにより、もともとメモリに格納されていたプログラムの実行制御情報（サブルーチンの戻りアドレスなど）を書き換え、攻撃者が用意したコードを実行させます。管理者権限で動作するプログラムが狙われると、システムの管理者権限を奪われるおそれがあります。

## 3.4.2 SMTPの脆弱性への対策

### ① MTAの設定による送信元メールアドレスの制限

MTAの設定により、送信元メールアドレスとあて先メールアドレスのいずれにも自サイトのドメイン名が含まれていないメールの中継を拒否します。これにより、第三者中継を禁止します。

あわせて、次のような制限も有効です。

- 中継を許可する送信元を、自組織内のIPアドレス（ネットワークアドレス）に限定する
- 自組織内から送信されるメールについては、送信元メールアドレスのドメインが自組織のものであることを確認する

### ② SMTP Authentication（SMTP-AUTH）によるユーザ認証

SMTPにユーザ認証機能を追加した方式です（RFC 4954、旧RFC 2554）。使用するには、MTA（MSA）とMUAの双方がこの方式に対応している必要があります。

SMTP-AUTHの認証機構は、**SASL（Simple Authentication and Security Layer）**に基づいています。SASLは、ユーザ名とパスワードを安全にサーバに送る手段として、次のような認証機構を規定しています。

- Kerberos
- GSSAPI（Generic Security Service Application Programming Interface）
- S/Key

SMTP-AUTHのユーザ認証方式には次のような種類があり、一般的に使用されているのはCRAM-MD5です。

**表：SMTP-AUTHにおけるユーザ認証方式**

| 種類 | RFC | 概要 |
| --- | --- | --- |
| PLAIN | RFC 2595（現RFC 4616） | 平文のままユーザIDとパスワードを送信する方式。実装によってはBase64でエンコードするものもあるが、容易に復号できる |
| LOGIN | ― | PLAINと同様、平文（Base64エンコード）のままユーザIDとパスワードを送信する方式。RFCで規定されていないため、実装方法がベンダによって異なる |
| CRAM-MD5 | RFC 2195 | CRAMは「Challenge-Response Authentication Mechanism」の略。メールサーバから受け取った任意の文字列（チャレンジ）とパスワードを基にしたMD5のメッセージダイジェストで認証する方式 |
| DIGEST-MD5 | RFC 2831 | CRAM-MD5のセキュリティ機能を強化した方式。辞書攻撃やブルートフォース（総当たり）攻撃への対処が行われているほか、realm（レルム：Kerberosの管理領域）やURLの指定、HMAC（Keyed-Hashing for Message Authentication Code）による完全性保護・暗号化などをサポートする |

> **用語：MD5（Message Digest 5）**
> ハッシュ関数の一つです。与えられた任意長のデータから、128ビットの固定長の疑似乱数（ハッシュ値）を生成します。生成される値は「メッセージダイジェスト」と呼ばれます。元のデータが少しでも異なれば、生成される値は大きく変化します。また、生成された値から元のデータを復元することはほぼ不可能です。この性質から、データの改ざん検出やデジタル署名などに利用されてきました。ただし現在は衝突耐性の脆弱性が指摘されており、SHA-256などへの移行が推奨されています。

### ③ POP before SMTPによるユーザ認証

メールの送信に先立ってPOP3によるユーザ認証を行い、認証に成功した場合だけ、一定時間メールの送信を許可する方式です。正式な規定は存在しませんが、RFC 2476の中で言及されています。

仕組みは次のとおりです。

1. POPサーバは、認証に成功したクライアントのIPアドレスを一定時間記録する
2. SMTPサーバは、記録されているIPアドレスからのメール送信だけを受け付ける

SMTP-AUTHに対応していないMUAでも利用できる点が利点です。一方で、次のような弱点があります。

- 認証はPOP3で行われるため、APOPなどを使わなければ認証情報が平文で流れる
- NAT環境などで同一のIPアドレスを共有する別の利用者も、許可された時間内であれば送信できてしまう

### ④ Outbound Port 25 Blocking によるメール送信制限

前述①の対策によって多くのサイトでメールの第三者中継が禁止されると、スパマーは別の手法を多用するようになりました。ボットなどを用いて、送信先サイトのメールサーバと直接SMTPコネクションを確立し、スパムを送り付ける手法です。この手法は第三者中継を用いていないため、第三者中継を禁止してもスパムを受信してしまいます。

こうした手法によるスパムを防ぐための対策として考え出されたのが、**Outbound Port 25 Blocking（OP25B）**です。

OP25Bは、ISP（Internet Service Provider）のメールサーバを経由せずにインターネット方向（外向き）に出ていく、25番ポートあてのパケット（SMTP）を遮断する方式です。主に動的IPアドレスを割り当てたネットワークを対象とし、既に多くのISPで採用されています。OP25Bのイメージを次の図に示します。

**図：OP25Bのイメージ**

```
[ISP管理下のネットワーク（動的IPアドレス）]
   ├─ 利用者PC ──(25/TCP)──> ISPのメールサーバ ──(25/TCP)──> 外部のメールサーバ   ○ 許可
   └─ ボット感染PC ──(25/TCP)────────────────×──> 外部のメールサーバ           × 遮断（OP25B）
```

OP25Bを導入すると、ISPの利用者が自社のメールサーバなどISP外部のメールサーバへ直接メールを送信できなくなります。この問題を解決するため、次のような仕組みが用いられます。

- 正当な利用者が自社のメールサーバなどと直接SMTPコネクションを確立してメールを送信する必要がある場合には、25番ポートではなく、投稿専用の**587番ポート（Submission）**を使用する（RFC 6409、旧RFC 2476）
- これを実現するため、従来のMTAの機能をMSAとMTAに分離する
- MSAでは、Submissionポートへアクセスしてきたユーザを**SMTP-AUTH**によって認証し、スパマーからの投稿を受け付けないようにする。さらに、TLSによって通信を秘匿化することも可能である（**Submission over TLS**）
- MTAは従来どおり25番ポートを使用し、MTA間でのメールの中継と受信を担当する

**図：Submissionポートによるメール投稿のイメージ**

```
[ISP管理下のネットワーク]                          [自社ネットワーク]
  利用者PC(MUA) ──(587/TCP + SMTP-AUTH)──────────> 自社メールサーバ(MSA)
                                                          │
                                                   自社メールサーバ(MTA) ──(25/TCP)──> 他社MTA
  ボット感染PC ──(25/TCP)──×（OP25Bにより遮断）
```

### ⑤ Inbound Port 25 Blocking によるメール着信制限

**Inbound Port 25 Blocking（IP25B）**は、他社ISPのネットワークの動的IPアドレスから、自社ISP内のメールサーバへのSMTP通信（25/TCP）を遮断する方式です。

OP25Bは「自社ISPの利用者からスパムを送信させない」ための対策です。これに対しIP25Bは、「OP25Bを導入していない他社ISPのネットワークから送られてくるスパムを受信しない」ための対策です。

### ⑥ IPアドレス・デジタル署名による送信ドメイン認証

送信元情報を偽装したメールを発見して排除する技術として、**送信ドメイン認証**が広く普及しています。これは、送信元のIPアドレスやデジタル署名を使って、メールの受信側で送信元SMTPサーバを認証する仕組みです。主な方式を次に示します。

> **用語：デジタル署名**
> PKI技術を用いて文書などに電子的に行う署名です。その文書が確かに本人から送信されたものであり、途中で改ざんされていないことを証明する技術です。

#### IPアドレスによる方式

**● Sender Policy Framework（SPF）**

あらかじめ、送信元ドメインのDNSサーバのTXTレコードに、正当なSMTPサーバのIPアドレス（**SPFレコード**）を登録しておきます。これによって送信元のSMTPサーバを認証する仕組みであり、次のような機能があります（RFC 7208）。

- メールを受信した受信側ドメインのSMTPサーバは、送信元のDNSサーバに問い合わせる。そして、エンベロープ（SMTPプロトコルのMAIL FROM）のメールアドレスのドメインと、接続元SMTPサーバのIPアドレスとの適合性を検証する
- 上記によって送信元SMTPサーバの正当性が確認された場合だけメールを受け入れ、それ以外のメールは排除する

SPFレコードの記述例を次に示します。

例1：`shoeisha.co.jp` ドメインからはメールを送信しない場合

```
shoeisha.co.jp.  IN  TXT  "v=spf1 -all"
```

例2：MXレコードに指定したホストからだけメールを送信する場合

```
shoeisha.co.jp.  IN  TXT  "v=spf1 mx -all"
```

> **補足：SPFレコードの主な記述要素**
>
> - `v=spf1`：SPFのバージョン
> - `ip4:` / `ip6:`：送信を許可するIPアドレス
> - `mx`：MXレコードに登録されたホストを許可
> - `include:`：他ドメインのSPFレコードを参照
> - `-all`：上記以外は認証失敗（fail）とする。`~all` はソフトフェイル（softfail）

> **試験に出る**
> 情報処理安全確保支援士試験では、平成30年度の午後問題（問2）でSPFに関する問題が出題されました。そのほかにもSPFは頻出のテーマです。

**● Sender ID Framework（Sender ID）**

SPFの機能に加えて、受信したメールのヘッダ情報（From:、Sender: など）のメールアドレスのドメインの正当性も検証します。エンベロープとヘッダのどちらか一方を検証するか、両方を検証するかを選択できます。

**図：SPF、Sender IDによる送信者認証のイメージ**

```
 送信側ドメイン(example.co.jp)                         受信側ドメイン
 ┌──────────────┐                                  ┌───────────────┐
 │ SMTPサーバ   │ ─────①メール送信────────────────> │ SMTPサーバ    │
 │ (192.0.2.10) │                                  └───────┬───────┘
 └──────────────┘                                          │②SPFレコード問合せ
 ┌──────────────┐ <────────────────────────────────────────┘
 │ DNSサーバ    │ ─────③SPFレコード応答（192.0.2.10を許可）──>
 └──────────────┘         ④接続元IPアドレスと照合し、一致すれば受理
```

#### デジタル署名による方式

**● DomainKeys**

あらかじめ、送信元ドメインのDNSサーバに正当なメールサーバの公開鍵を登録しておきます。そして、SMTPサーバが付したデジタル署名によって、送信元メールサーバの正当性を検証する仕組みです（米国ヤフー社が中心となって策定）。次のような機能があります。

- 送信側SMTPサーバは、秘密鍵を用いてメールにデジタル署名を付与する
- 受信側SMTPサーバは、送信元ドメインのDNSサーバから公開鍵を取得し、デジタル署名を検証する
- 上記によってデジタル署名（送信元SMTPサーバ）の正当性が確認された場合だけメールを受け入れ、それ以外のメールは排除する

**● DomainKeys Identified Mail（DKIM）**

DomainKeysと、米国シスコシステムズ社らが提案していたIdentified Internet Mail（IIM）の仕様を統一し、IETFが標準化したデジタル署名による送信ドメイン認証技術です（RFC 6376）。

DKIMの仕組みはDomainKeysと同様です。ただし、署名を検証するための公開鍵に関する情報をメールのヘッダに添付するIIMの技術が追加されています。将来的には、ドメイン単位だけでなくユーザ単位での署名と検証も可能とされています。DKIMの署名は、メールヘッダの「DKIM-Signature:」フィールドに格納されます。

**表：送信ドメイン認証方式の比較**

| 名称 | 方式 | メリット | デメリット |
| --- | --- | --- | --- |
| Sender Policy Framework（SPF） / Sender ID Framework（Sender ID） | IPアドレス | ・送信元情報の偽装を配送経路上で検知して排除できる<br>・シンプルな方式であるため導入が容易<br>・送信側SMTPサーバには設定等が不要（DNSへの登録のみ）<br>・受信側SMTPサーバにかかる負荷が比較的少ない | ・送信元情報を偽っていないスパムは排除できない<br>・DNSに登録されていないサーバからのメールは、正当なものであっても排除されるおそれがある<br>・直近のSMTPサーバのアドレスで検証するため、複数のSMTPサーバを経由（転送）したメールは検証が困難 |
| DomainKeys / DomainKeys Identified Mail（DKIM） | デジタル署名 | ・送信元情報の偽装を配送経路上で検知して排除できる<br>・複数のSMTPサーバを経由したメールについても検証できる<br>・メール本文やヘッダの改ざんも検知できる | ・送信側・受信側双方のSMTPサーバが方式に対応する必要がある<br>・署名の生成・検証により、双方のSMTPサーバに負荷がかかる<br>・メーリングリストや広告が付加されるメールなど、配送経路で内容が変更されるメールは検証が困難 |

近年社会問題化しているスパムメールは、必ずしも送信元情報を偽装しているわけではありません。そのため、これらの技術を用いても完全な対策にはなりませんが、ある程度の効果は期待できます。

一方、フィッシングメールは送信元情報が偽装されているケースが大半であるため、送信ドメイン認証による削減効果が期待されます。ただし、送信ドメイン認証には次のような限界があります。

- **SPFの限界**：SPFは、エンベロープのドメイン（**Envelope-From**）の正当性を検証する仕組みです。そのため、メール送信者が独自ドメインでSPFレコードを設定したうえで、受信者が目にするメールヘッダの送信者ドメイン（**Header-From**）をEnvelope-Fromとは異なるものに詐称している場合、偽装を検出できません。
- **DKIMの限界**：メール送信者の独自ドメインによる正規の署名が付与されていれば、Header-Fromが詐称されていても検出できません。

こうした問題は、後述するDMARCを組み合わせることで検出精度を高められます。

> **用語：フィッシング（Phishing）**
> 銀行、クレジットカード会社、ショッピングサイトなどを装った電子メールを送り付け、本物のWebサイトに見せかけた偽のページに誘導する手口です。偽のページでは、口座番号、クレジットカード番号、パスワードなどの個人情報を入力させて盗みます。

#### 送信ドメイン認証を補完する仕組み

**● DMARC（Domain-based Message Authentication, Reporting and Conformance）**

DMARCは、SPFやDKIMによる認証結果とHeader-Fromのドメインとの整合性（アライメント）を検証する仕組みです。あわせて、認証に失敗したメールの取扱いポリシを送信側ドメインの管理者が表明し、受信側がそのポリシに従って処理します。これによって、送信ドメイン認証を補完します（RFC 7489）。

DMARCのポリシ表明は、SPFと同様に、DNSサーバにTXTレコード（`_dmarc.ドメイン名`）を追加し、タグに値を設定して行います。

例えばDMARCのpタグでは、認証に失敗したメールについて次のような指定が可能です。

- `none`：何もしない（モニタリングのみ）
- `quarantine`：メールを隔離する（迷惑メールフォルダへの振分けなど）
- `reject`：メールを拒否（排除）する

```
_dmarc.example.co.jp.  IN  TXT  "v=DMARC1; p=reject; rua=mailto:dmarc-report@example.co.jp"
```

DMARCには、メール受信側が送信側に対し、認証の結果をレポートとして通知する機能があります（ruaタグで集計レポート、rufタグで失敗レポートの送付先を指定）。送信側はこのレポートによって、自組織のメールシステムが適切に稼働しているかどうか、自ドメインを詐称したメールが送られていないかどうかを確認できます。

また、DMARCでは、Envelope-FromをHeader-Fromと同じドメインにするか、Header-Fromのサブドメインで運用したうえで、SPF等の送信ドメイン認証を行うことを求めています。そのため、DMARCとSPF等の送信ドメイン認証を組み合わせることで、前述のように独自ドメインを用いてSPFやDKIMをすり抜ける、Header-Fromを詐称したメールも検出できるようになります。

### ⑦ メールフィルタリング

迷惑メールやマルウェアが添付されたメールを検出して除去するため、メールフィルタリングツールやサービスが広く普及しています。導入形態には、次のようなものがあります。

- ISP（Internet Service Provider）のメールサービスを利用している場合は、標準的に提供される
- 自社でメールサーバを設置している場合は、サーバに製品を導入し、経路上で迷惑メールをフィルタリングするのが一般的である
- メールクライアントソフトウェアのフィルタリング機能を利用して、クライアント側で振り分ける

従来のフィルタリングは、キーワードや送信元アドレス、ブラックリストなどのルールに基づいて判定する方式が中心でした。この方式には、次のような問題がありました。

- 次々に文面や送信元を変える迷惑メールに対応するため、ルールを頻繁に更新しなければならない
- ルールに合致しない新しい迷惑メールに対しては、フィルタリングが有効に機能しない

こうした問題を改善する迷惑メール検知手法として、**ベイジアンフィルタリング（Bayesian Filtering）**があります。ベイジアンフィルタリングは、ベイズの定理を応用して迷惑メールの特徴を自己学習し、統計的に解析して判定するフィルタリング手法です。学習量が増えるにつれて、フィルタリングの精度が向上します。

### ⑧ 「SMTP over TLS」によるメールの暗号化とユーザ認証

TLSを用いてSMTP通信を暗号化する方式です。ただし暗号化されるのは、あくまでもクライアント（MUA）から送信元（自サイト内）のメールサーバまでの通信だけです。インターネット上では、メールは平文で流れます。

この方式では、メールの暗号化に加えて、デジタル証明書によるユーザ認証も行えます（そのためには、各ユーザがデジタル証明書を取得している必要があります）。

SMTP over TLS（SMTPS）では、465/TCPポートが用いられます。

> **用語：TLS（Transport Layer Security）**
> SSL（Secure Sockets Layer）の後継として、IETF（Internet Engineering Task Force：インターネット技術タスクフォース）によって標準化が行われた、インターネットにおける暗号化通信プロトコルです。SSLと同様に、デジタル証明書によるサーバ認証、クライアント認証、通信データの暗号化などの機能を備えています。SSLの脆弱性が相次いで発見されたことから、現在ではTLS（TLS 1.2 / TLS 1.3）が広く普及しています。

### ⑨ 「STARTTLSコマンド」によるメールの暗号化

STARTTLSは、主に送信側のメールサーバと受信側のメールサーバの間の通信を暗号化するために使用されます（RFC 3207）。処理の流れは次のとおりです。

1. まず暗号化されていない状態で通信を開始する
2. 送信側のメールサーバが「STARTTLSコマンド」を発行する
3. 受信側のメールサーバがSTARTTLSに対応していれば、TLSによる暗号化通信が開始される。対応していない場合は、暗号化されないまま通信が行われる

このように、STARTTLSは明示的に暗号化通信を行う方式です。これに対し、⑧のSMTP over TLSは暗黙的な暗号化方式（接続開始時から常にTLSを用いる方式）といえます。

SMTPでSTARTTLSを用いる場合は、暗号化通信か非暗号化通信かにかかわらず、共通して25/TCPポートが用いられます。なお、MUAからMSAへの投稿時にも、587/TCPポート上でSTARTTLSを用いることができます。

> **補足：STARTTLSの注意点**
> STARTTLSでは、相手が非対応の場合に平文通信へフォールバックします。そのため、中間者がSTARTTLSの応答を削除して暗号化を妨害する攻撃（STARTTLSストリッピング）を受けるおそれがあります。対策として、MTA-STS（RFC 8461）やDANE（RFC 7672）などの仕組みがあります。

### ⑩ S/MIME、PGP等によるメールの暗号化

これらのソフトウェアを用いてアプリケーション層でメールを暗号化することで、すべての通信経路でメールを秘匿化します（エンドツーエンドの暗号化）。デジタル署名を付与すれば、送信者の真正性とメールの完全性も確認できます。

> **用語：S/MIME（Secure Multipurpose Internet Mail Extensions）**
> 米国RSA Security社が開発した暗号化電子メールの規格です。MIMEは、画像などのバイナリファイルをメールで送受信するための規格です。S/MIMEはMIMEを拡張したものであるため、添付ファイルを含めて暗号化できます。公開鍵の正当性は、認証局（CA）が発行するデジタル証明書によって保証されます。

> **用語：PGP（Pretty Good Privacy）**
> 1991年にフィリップ・ジマーマン（Philip Zimmermann）によって開発された電子メール暗号化ツールです。当初フリーソフトウェアとしてインターネット上で公開されたため、広く普及しました。暗号化アルゴリズムには、当初RSAとIDEAが用いられました。公開鍵の正当性は、利用者同士が相互に署名し合う「信頼の輪（Web of Trust）」によって保証されます。

### ⑪ MTAの不要なコマンドの無効化

前述のVRFY、EXPNなど、不要なコマンドを無効とするようにMTAを設定します。

### ⑫ その他、MTAの実装面での対策

- MTAのバージョンを最新にし、パッチを適用する
- AVソフトを導入し、中継するメールに添付されたウイルスを駆除する
- インターネット上のSMTPサーバと社内LAN上のSMTPサーバとの間で相互にメールを中継する中継専用メールサーバ（外向けSMTPサーバ）を、DMZ上に設置する
- 外向けメールサーバと同じDMZセグメント上にゲートウェイ型AVサーバを設置し、メールに添付された不正なコードを駆除する
- MTAが出力するバナー（応答メッセージ）から、ソフトウェア名やバージョン情報を削除する

## 3.4.3 POP3の脆弱性

POP3（Post Office Protocol Version 3）は、MUAがサーバからメールを受信するための代表的なプロトコルとして広く使用されています（110/TCPポートを使用）。POP3では、メールの受信時にメールサーバとの間でユーザ認証を行う仕組みになっていますが、その仕様には幾つかの脆弱性が指摘されています。

### ① 認証情報が平文でネットワーク中を流れる

標準的なPOP3では、USER/PASSコマンドによってユーザ認証を行います。このとき、ユーザIDとパスワードが平文のままネットワーク中を流れます。そのため、経路上でのパケット盗聴によって認証情報が漏えいし、第三者にメールを不正に読まれたり、なりすましに悪用されたりする可能性があります。

### ② 受信データ（メール）が平文でネットワーク中を流れる

POP3では、認証情報だけでなく、メールの内容自体も平文のままネットワーク中を流れます。そのため、経路上でのパケット盗聴によってメールの内容が漏えいしたり、改ざんされたりする可能性があります。

## 3.4.4 POP3の脆弱性への対策

### ① APOPによるユーザ認証情報の秘匿化

**APOP（Authenticated Post Office Protocol）**は、メールサーバとMUAの間の認証でチャレンジレスポンス方式のユーザ認証を行い、認証情報が平文のままネットワーク中を流れるのを防ぎます。認証の流れは次のとおりです。

1. サーバからMUAに文字列（チャレンジ）が送られる
2. MUAは、チャレンジとパスワードを連結した文字列から、MD5を用いてメッセージダイジェストを生成する
3. MUAは、生成したメッセージダイジェストをレスポンスとしてサーバに返す
4. サーバは、同じ計算を行った結果とレスポンスを照合して認証する

パスワードそのものがネットワーク中を流れることはないため、認証プロセスが盗聴されても問題ありません。ただし、APOPはあくまでも認証情報だけを秘匿化する方式です。APOPを用いてもメールそのものは平文のままネットワーク中を流れるため、注意が必要です。

> **補足**
> APOPで用いられるMD5には衝突攻撃の脆弱性が指摘されています。そのため、中間者攻撃によってパスワードが解読されるおそれがあることが報告されています。現在では、POP3S（POP3 over TLS）やIMAPSの利用が推奨されます。

### ② 「POP3 over TLS」による認証情報とメールの暗号化

TLSを用いて、POP3通信（認証情報から受信するメールまですべて）を暗号化する方式です。ただし暗号化されるのは、あくまでも直接通信するPOP3サーバとクライアント（MUA）の間の通信だけであるため、注意が必要です。

「POP3 over TLS（POP3S）」では、通常のPOP3（110/TCP）とは異なり、995/TCPポートを使用します。

### ③ 「IMAP over TLS（IMAPS）」による認証情報とメールの暗号化

IMAP（Internet Message Access Protocol）は、POP3と同じくクライアントがメールサーバからメールを読み出すためのプロトコルです。POP3がメールをクライアントにダウンロードしてクライアント上で管理するのに対し、IMAPはサーバ上のメールボックスでメールを管理します。そのため、複数の端末（PCやスマートフォンなど）から同じメールボックスを参照できます。

IMAPSは、TLSを用いてIMAP通信（認証情報からメール本文まですべて）を暗号化する方式です。近年はMicrosoft 365等のクラウドメールサービスの普及に伴い、そうした環境と親和性の高いIMAPSが電子メールの受信プロトコルとして広く使われています。なお、IMAPSは993/TCPポートを使用します（通常のIMAPは143/TCP）。

### ④ SSHのポートフォワーディング機能による認証情報とメールの暗号化

SSH（Secure SHell）のポートフォワーディング機能を用いて、POP3通信（認証情報から受信するメールまですべて）を暗号化する方式です。ただし「POP3S」と同様に、暗号化されるのはあくまでも直接通信するPOP3サーバとクライアント（MUA）の間の通信だけであるため、注意が必要です。

SSHのポートフォワーディング機能とは、暗号化機能を備えていないアプリケーションの通信をSSHが間に入って中継し、暗号化するものです。この機能を用いると、POP3やFTPをはじめ、通信データの暗号化機能を備えていないアプリケーションの通信を暗号化できます。

SSHのポートフォワーディング機能を用いた場合は、通常のPOP3とは異なり、22/TCPポートを使用します。そのため、インターネット側からファイアウォールを介してSSHで社内のPOP3サーバからメールを受信するには、SSHの設定に加えて、22/TCPの通信を許可するようにファイアウォールを設定する必要があります。

**表：電子メール関連プロトコルと使用ポート番号**

| プロトコル | ポート番号 | 用途・暗号化 |
| --- | --- | --- |
| SMTP | 25/TCP | MTA間の中継（STARTTLSにより暗号化可能） |
| Submission | 587/TCP | MUAからMSAへの投稿（SMTP-AUTH、STARTTLS） |
| SMTPS（SMTP over TLS） | 465/TCP | 投稿時の暗号化（暗黙的TLS） |

| IMAPS（IMAP over TLS） | 993/TCP | メール受信・サーバ上での管理（暗号化） |
| SSH（ポートフォワーディング） | 22/TCP | 任意のアプリケーション通信の暗号化 |

## 確認問題

### 問題1

SPFによるドメイン認証を実施する場合、SPFの導入時に、電子メール送信元アドレスのドメイン所有者側で行う必要がある設定はどれか。

- ア　DNSサーバにSPFレコードを登録する。
- イ　DNSの問合せを受け付けるポート番号を変更する。
- ウ　メールサーバにデジタル証明書を導入する。
- エ　メールサーバのTCPポート25番を利用不可にする。

［情報処理安全確保支援士試験・R4秋・午前Ⅱ問15］

#### 解答・解説

SPF（Sender Policy Framework）は、電子メールの送信元ドメインのDNSサーバにあらかじめ正当なSMTPサーバのIPアドレス（SPFレコード）を登録しておくことにより、送信元を詐称した電子メールを拒否する仕組みである。

電子メールを受信したSMTPサーバは、送信元のDNSサーバに問い合わせ、エンベロープ（SMTPプロトコルのMAIL FROM）のメールアドレスのドメインと送信サーバのIPアドレスの適合性を検証する。その結果、送信元のSMTPサーバの正当性が確認された場合のみメールを受け入れ、それ以外のメールは排除する。したがって、**ア**が正解である。

### 問題2

インターネットサービスプロバイダ（ISP）が、スパムメール対策として導入するIP25Bに該当するものはどれか。

- ア　自社ISPのネットワークの動的IPアドレスから他社ISPの管理するメールサーバへのSMTP通信を制限する。
- イ　自社ISPのメールサーバで受信した電子メールのうち、スパムメールのシグネチャに一致する電子メールを隔離する。
- ウ　他社ISPのネットワークの動的IPアドレスから自社ISPのメールサーバへのSMTP通信を制限する。
- エ　他社ISPのメール不正中継の脆弱性をもつメールサーバから自社ISPのメールサーバに送信された電子メールを隔離する。

［情報処理安全確保支援士試験・R2秋・午前Ⅱ問17］

#### 解答・解説

IP25B（Inbound Port 25 Blocking）は、ISPが、他社ISPのネットワークの動的IPアドレスから自社ISP内のメールサーバへのSMTP通信をブロックする方法である。したがって、**ウ**が正解である。

### 問題3

DKIM（DomainKeys Identified Mail）の説明はどれか。

- ア　送信側メールサーバにおいてデジタル署名を電子メールのヘッダに付加し、受信側メールサーバにおいてそのデジタル署名を公開鍵によって検証する仕組み
- イ　送信側メールサーバにおいて利用者が認証された場合、電子メールの送信が許可される仕組み
- ウ　電子メールのヘッダや配送経路の情報から得られる送信元情報を用いて、メール送信元のIPアドレスを検証する仕組み
- エ　ネットワーク機器において、内部ネットワークから外部のメールサーバのTCPポート番号25への直接の通信を禁止する仕組み

［情報処理安全確保支援士試験・R5春・午前Ⅱ問15］

#### 解答・解説

DKIMは、送信側SMTPサーバがメールヘッダに付与したデジタル署名を受信側SMTPサーバで検証することによって、送信元の正当性を確認する仕組みである。そのため、あらかじめ送信側ドメインのDNSサーバに正当なメールサーバの公開鍵を登録しておく必要がある。したがって、**ア**が正解である。

- イ　SMTP-AUTHの説明である。
- ウ　SPF（Sender Policy Framework）の説明である。
- エ　OP25B（Outbound Port 25 Blocking）の説明である。

### 問題4

電子メールをスマートフォンのメールアプリケーションプログラムで受信する際のメールサーバとスマートフォンとの間の通信を、メール本文を含めて暗号化するプロトコルはどれか。

- ア　APOP
- イ　IMAPS
- ウ　POP3
- エ　SMTP Submission

［情報処理安全確保支援士試験・R5秋・午前Ⅱ問16］

#### 解答・解説

問題文に該当するのはIMAPS（Internet Message Access Protocol over TLS）であり、**イ**が正解である。

IMAPはクライアントがメールサーバからメールを読み出すためのプロトコルだが、同じ目的で広く利用されているPOP3がクライアント上でメールを管理するのに対し、サーバ上のメールボックスでメールを管理する。

TLS（Transport Layer Security）には、デジタル証明書によるサーバ認証機能、クライアント認証機能に加え、アプリケーション層とトランスポート層（TCP層）の間で通信データを暗号化する機能がある。TLSは、HTTPをはじめ、SMTP、FTP、Telnet、POP3、IMAP4など、多くのTCPアプリケーションに対応している。

- ア　APOPでは認証情報のみが暗号化される。
- ウ　POP3では認証情報もメール本文も平文で通信経路上を流れる。
- エ　SMTP Submissionはメール投稿（送信）時に用いるプロトコルであり、暗号化の仕組みは実装されていない。

### 問題5

インターネットサービスプロバイダ（ISP）が、OP25Bを導入する目的の一つはどれか。

- ア　ISP管理外のネットワークに対するISP管理下のネットワークからのICMPパケットによるDDoS攻撃を遮断する。
- イ　ISP管理外のネットワークに向けてISP管理下のネットワークから送信されるスパムメールを制限する。
- ウ　ISP管理下のネットワークに対するISP管理外のネットワークからのICMPパケットによるDDoS攻撃を遮断する。
- エ　ISP管理下のネットワークに向けてISP管理外のネットワークから送信されるスパムメールを制限する。

［情報処理安全確保支援士試験・R5春・午前Ⅱ問16］

#### 解答・解説

OP25B（Outbound Port 25 Blocking）とは、ISPが動的IPアドレスを割り当てた（ISP管理下の）ネットワークから、当該ISPのメールサーバを経由せずに、ISP管理外のネットワーク（外向き）に直接出ていく25番ポートあてのパケット（SMTP）を遮断する方式である。このようなパケットは、ISP管理外のネットワークに向けたスパムメールである可能性が高い。したがって、**イ**が正解である。

### 問題6

TCPのサブミッションポート（ポート番号587）の説明として、適切なものはどれか。

- ア　FTPサービスで、制御用コネクションのポート番号21とは別にデータ転送用に使用する。
- イ　Webサービスで、ポート番号80のHTTP要求とは別に、サブミットボタンをクリックした際の入力フォームのデータ送信に使用する。
- ウ　コマンド操作の遠隔ログインで、通信内容を暗号化するためにTELNETのポート番号23の代わりに使用する。
- エ　電子メールサービスで、迷惑メール対策などのためにSMTPのポート番号25の代わりに使用する。

［情報処理安全確保支援士試験・R6春・午前Ⅱ問19］

#### 解答・解説

サブミッションポートは、スパムメール対策としてSMTPポートの代わりに投稿専用のポートとして使用する。

ボットなどが迷惑メールを送信する際に、ISP（Internet Services Provider）のメールサーバを経由せず、直接送信先のメールサーバの25番ポートに接続してSMTPコネクションを確立する手口が用いられたため、これをOP25B（Outbound Port 25 Blocking）によって遮断する対策が行われるようになった。

OP25Bとは、ISPが動的IPアドレスを割り当てたネットワークから、当該ISPのメールサーバを経由せずに、ISP管理外のネットワーク（外向き）に直接出ていく25番ポートあてのパケット（SMTP）を遮断する方式である。

OP25Bが設定されている環境で正当な利用者が自社のメールサーバなどと直接SMTPコネクションを確立してメールを送信する必要がある場合には、25番ポートではなくサブミッションポートを使用する必要がある。

サブミッションポートへアクセスしてきたメール送信者をSMTP-AUTHによって認証することで、ボットなどからの投稿を受け付けないようにするほか、TLSによって通信を秘匿化することも可能である（Submission over TLS）。したがって、**エ**が正解である。

### 問題7

SMTP-AUTHの特徴はどれか。

- ア　ISP管理下の動的IPアドレスから管理外ネットワークのメールサーバへのSMTP接続を禁止する。
- イ　電子メール送信元のメールサーバが送信元ドメインのDNSに登録されていることを確認してから、電子メールを受信する。
- ウ　メールクライアントからメールサーバへの電子メール送信時に、利用者IDとパスワードによる利用者認証を行う。
- エ　メールクライアントからメールサーバへの電子メール送信は、POP接続で利用者認証済みの場合にだけ許可する。

［情報処理安全確保支援士試験・R4秋・午前Ⅱ問14］

#### 解答・解説

SMTP-AUTHは、SMTPにユーザ認証機能を追加した方式であり、クライアントがSMTPサーバにアクセスしたときにユーザアカウントとパスワードによる利用者認証を行うことで、許可された利用者だけから電子メールの送信を受け付ける。したがって、**ウ**が正解である。

- ア　OP25B（Outbound Port 25 Blocking）の説明である。
- イ　SPF（Sender Policy Framework）の説明である。
- エ　POP before SMTPの説明である。
