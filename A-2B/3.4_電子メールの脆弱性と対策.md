# レクチャーノート：情報セキュリティにおける脆弱性 ― 3.4 電子メールの脆弱性と対策

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「セキュリティ実装技術」（知識項目例：セキュアプロトコル、認証プロトコル、ネットワークセキュリティ ほか）、「情報セキュリティ」（知識項目例：サイバー攻撃〈フィッシング、標的型攻撃ほか〉、認証技術 ほか）、「情報セキュリティ対策」（知識項目例：不正アクセス対策、マルウェア・不正プログラム対策 ほか）

## 0. 全体像 ― なぜこの分野を学ぶのか

### 0.1 1.4 で見たメールの仕組みを「弱点」の目で見直す

電子メールを実現している **SMTP**（Simple Mail Transfer Protocol）や **POP3**（Post Office Protocol Version 3）は、DNSやHTTPと並んで古くから使われているサービスです。長く使われてきた分、プロトコルの仕様や実装について多くのセキュリティ上の問題点が指摘されています。

1.4 で見たメールの仕組みを思い出してください。メールは MUA → MSA → MTA → … → MDA → MRA → MUA というバケツリレーで届き、送信者情報には封筒にあたるエンベロープ（MAIL FROM）と便箋にあたるヘッダ（From:）があって、**どちらも送信者が自由に書ける**のでした。1.4 ではこれを「研究者どうしが互いを信頼していた時代の設計」と説明しました。本ノートでは、この設計上の前提が具体的にどんな弱点になり、攻撃者（スパマー、フィッシング詐欺師）がそれをどう突き、メールサーバの管理者やISPがどう塞いできたのかを、脆弱性と対策の視点で深掘りします。

メールの対策の歴史は、攻撃者と防御側のいたちごっこの歴史でもあります。

```
 攻撃者の手口                                防御側の対策
 ─────────────────────────────────────────────────────────────────
 他社のメールサーバを踏み台にしてスパムを送る ──→ 第三者中継の禁止（MTAの設定、SMTP-AUTH）
 ボット感染PCから相手のサーバへ直接送る    ──→ OP25B／IP25B、サブミッションポート（587）
 送信元のドメインを詐称する                ──→ 送信ドメイン認証（SPF、DKIM）
 ヘッダFromだけを詐称してSPF/DKIMをすり抜ける ──→ DMARC
 経路上でメールや認証情報を盗聴する          ──→ SMTP over TLS、STARTTLS、APOP、POP3S/IMAPS、S/MIME
```

### 0.2 本ノートの地図

本ノートでは、SMTPの脆弱性5つと、それに対する対策12個、POP3の脆弱性2つと対策4つを扱います。数が多いので、まず対応関係を頭に入れておきましょう。

| 脆弱性 | 付け込まれた結果 | 主な対策（本ノートの節） |
|---|---|---|
| SMTP① 投稿と中継が同じ仕組み | 自組織の利用者と外部のサーバを区別できない | サブミッションポートとMSAの分離（3.4） |
| SMTP② 投稿時にユーザを認証しない | 第三者中継、送信元の詐称、NDRスパム | MTAの中継制限（3.1）、SMTP-AUTH（3.2）、POP before SMTP（3.3）、OP25B／IP25B（3.4〜3.5）、送信ドメイン認証とDMARC（4章）、メールフィルタリング（5章） |
| SMTP③ 暗号化機能がない | 盗聴・改ざん | SMTP over TLS、STARTTLS、S/MIME・PGP（6章） |
| SMTP④ VRFY・EXPNでアカウント情報が漏れる | 有効なメールアドレスの収集 | 不要なコマンドの無効化（7.1） |
| SMTP⑤ 古いMTAにBOFなどの脆弱性 | サーバの乗っ取り | パッチ適用、DMZでの中継、AV、バナーの秘匿（7.2） |
| POP3① 認証情報が平文 | パスワードの盗聴 | APOP、POP3S、IMAPS、SSHポートフォワーディング（9章） |
| POP3② メール本文が平文 | メール内容の盗聴・改ざん | POP3S、IMAPS、SSHポートフォワーディング（9章） |

科目Bの業務観点では、「③利用におけるセキュリティ対策の適用」のうち「ネットワーク及び機器のセキュリティ管理」「マルウェア対策」と、「②企画・設計・開発・運用におけるセキュリティ確保」のうち「製品・サービスのセキュアな導入」に対応します。また、なりすましメールやフィッシングの被害が起きた事例では「④インシデント管理」（メールヘッダからの原因調査）にもつながります。科目Bでは、メールサーバの構成図やDNSのTXTレコード、メールヘッダが示され、「なぜこのなりすましメールが届いたのか」「SPF・DKIM・DMARCのどれをどう設定すべきか」を答えさせる設問が頻出です。科目A-2では、OP25BとIP25Bの区別、SPFとDKIMの仕組み、APOPとIMAPSの暗号化範囲が毎年のように問われています。

## 1. 電子メールシステムの構成要素（おさらい）

本ノートで使う用語を、1.4 の5節から再確認しておきます。

> **用語：電子メールシステムの構成要素**
>
> - **MUA（Mail User Agent）**：メールの作成・閲覧を行うクライアントソフトウェア（メーラ）
> - **MSA（Mail Submission Agent）**：MUAからのメール投稿を受け付けるサーバ機能
> - **MTA（Mail Transfer Agent）**：メールサーバ間でメールを中継・配送するサーバ機能（SMTPサーバ）
> - **MDA（Mail Delivery Agent）**：受信したメールを利用者のメールボックスへ格納する機能
> - **MRA（Mail Retrieval Agent）**：利用者を認証し、メールボックスからメールを取り出させる機能（POP3／IMAPサーバ）

本ノートの前半（2〜7章）は、送信側の MUA → MSA → MTA → MTA の区間、つまりSMTPが使われる区間の弱点を扱い、後半（8〜9章）は受信側の MRA → MUA の区間、つまりPOP3・IMAPが使われる区間の弱点を扱います。

## 2. SMTPの脆弱性

### 2.1 迷惑メールという最大の問題

メールの利用において最も大きな問題となってきたのは、インターネット上を常に飛び交っている膨大な**迷惑メール**（**スパムメール**）です。かつては、全世界で送信されるメールのうち実に**80％**がスパムメールといわれていました。近年はISPやメールサービス事業者の対策が進み、各種の調査ではおおむね半数前後とされていますが、依然として送信されるメールの大きな割合を占めています。これほどスパムメールが横行する原因は、旧バージョンのメールサーバソフトウェアの仕様にある脆弱性（次に挙げる①と②）です。

迷惑メールは、スパムメール（spamメール）のほか、**UBE**（Unsolicited Bulk Email：受信者が求めていない大量送信メール）や **UCE**（Unsolicited Commercial Email：受信者が求めていない商業目的のメール）とも呼ばれます。宣伝や嫌がらせなどの目的で、不特定多数に大量に送信されるメール全般を指します。迷惑メールの多くは、送信元のメールアドレス（ドメイン名）を詐称するUBEです。また、第三者中継を許可している複数のサーバを経由して配信されるケースが多く見られます。

迷惑メールは単に「うっとうしい」だけではありません。フィッシング詐欺への誘導、マルウェア（ランサムウェアや情報窃取型マルウェアのEmotetなど）の添付、標的型攻撃の入口として使われるため、組織にとっては重大な脅威の運び手です。

SMTPの脆弱性には、次のようなものがあります。

### 2.2 ① メールの投稿や中継などがすべて同じ仕組みで行われている

旧バージョンのメールサーバソフトウェアでは、MSAの機能はMTAに統合されていました。そのため、次の2種類の通信が、いずれも同じ**25番ポート**（SMTP）で同じ仕組みによって処理されていました。

- MUAからのメールの**投稿**（Submission）
- MTA間のメールの**中継**（Relay）

その結果、サーバ側では「自組織の利用者による投稿」と「他のサーバからの中継」を区別して制御することが困難でした。郵便でたとえると、郵便局の窓口（差出人が手紙を出しに来る場所）と、他の郵便局から郵便物が運ばれてくる搬入口が同じで、窓口に来た人が本当に地元の住民かどうかを確かめる手段がない状態です。

### 2.3 ② メールの投稿にあたってユーザを認証する仕組みがない

広く普及しているメールサーバソフトウェアの旧バージョンには、メールの投稿時にユーザを認証する仕組みがありませんでした。そのため、次のような問題が生じます。

- **送信元メールアドレスの詐称**が堂々と行われる
- 本来受け付ける必要のない組織外の第三者から、別の第三者へのメール投稿を受け付けて中継してしまう

後者を**第三者中継**（Third-Party Mail Relay）といいます。第三者中継は**オープンリレー**とも呼ばれ、それを行うSMTPサーバを**オープンリレー（SMTP）サーバ**と呼びます。

現在一般に普及しているメールサーバソフトウェアには、後述する **SMTP-AUTH** が実装されています。したがって、メールの投稿時にユーザ認証を行うことが可能です。

**中継すべきメールの条件**：インターネットと内部ネットワークの境界でメールを中継する一般的なMTA（SMTPサーバ）は、本来、次の条件に合致するメールだけを中継すればよいはずです。

- **自サイト内のユーザが任意のアドレスあてに送信するメール**
  （送信元メールアドレスに自サイトのドメイン名が含まれているもの）
- **任意のアドレスから自サイト内のユーザあてに送られてくるメール**
  （あて先メールアドレスに自サイトのドメイン名が含まれているもの）

> **試験に出る**
> 情報処理安全確保支援士試験の午後問題（現・科目B）では、第三者中継やメールサーバの設定を題材にした問題が出題されています。

**図：正常なメール中継の例**

```
【送信】自サイトのユーザ(user@example.co.jp) ──> 自サイトのMTA ──> 任意のあて先ドメインのMTA
        （送信元ドメイン = 自サイト）

【受信】任意の送信者 ──> 自サイトのMTA ──> 自サイトのユーザ(user@example.co.jp)
        （あて先ドメイン = 自サイト）

【第三者中継（拒否すべき）】
        第三者(spammer@other1.example) ──> 自サイトのMTA ──> 別の第三者(victim@other2.example)
        （送信元・あて先ともに自サイトと無関係）
```

ところが第三者中継では、自サイトとは関係のない第三者（送信者）が、自サイトとは関係のない別の第三者にメールを中継させようとします。そのため、送信元メールアドレスとあて先メールアドレスのいずれも、自サイトとは関係のないドメイン名になっています。

中継対象のメールが上記の条件に合致するかどうかは、送信元メールアドレスとあて先メールアドレスを見れば容易に確認できます。したがって、条件に合致しないメールの中継を拒否すればよいだけです。管理者が自組織のMTAを外部から試験すると、正しく設定されたMTAは次のように第三者中継を拒否します。

```
$ nc mail.example.co.jp 25
220 mail.example.co.jp ESMTP
HELO other1.example
250 mail.example.co.jp
MAIL FROM:<spammer@other1.example>
250 2.1.0 Ok
RCPT TO:<victim@other2.example>
554 5.7.1 <victim@other2.example>: Relay access denied     ← 第三者中継を拒否している（正しい）
QUIT
```

最後の行が「250 2.1.5 Ok」になっていたら、そのサーバはオープンリレーです。しかし実際には、条件に合致しないメールでも無条件に中継してしまうメールサーバ（オープンリレーサーバ）が、インターネット上にまだ存在しています。こうしたサーバは**スパマー**（スパムメールの送信者）の**踏み台**となり、スパムメールの中継に悪用されています。スパマーにとっては、自分の身元を隠せるうえ、踏み台のサーバの送信能力を使って大量に送れるという利点があります。

**ブラックリストへの登録という二次被害**：オープンリレーサーバは、スパムメールの発信源として**ブラックリスト**に登録される可能性があります。メールサーバがいったんブラックリストに登録されると、そのサーバから送信されるメールは、ブラックリストを利用しているメールサーバで受信を拒否されてしまいます。つまり、踏み台にされた組織は、取引先への正規の業務メールまで届かなくなるという形で、可用性の被害を受けるのです。

> **用語：ブラックリスト（DNSBL / RBL）**
> スパムメールの発信源やオープンリレーサーバのIPアドレスを登録したリストです。DNSの仕組みを利用して参照できるものが多く、**DNSBL**（DNS-based Blackhole List）や **RBL**（Realtime Blackhole List）と呼ばれます。受信側のメールサーバは、接続元IPアドレスがリストに登録されていれば受信を拒否します。

DNSBLの参照は、接続元IPアドレスのオクテットを逆順に並べ、リストのドメイン名を後ろに付けて問い合わせる形で行います。

```
接続元 203.0.113.45 がリストに載っているかを調べる（dnsbl.example.net はリスト運営者のドメインの例）
$ dig +short 45.113.0.203.dnsbl.example.net A
127.0.0.2          ← 応答があれば「登録されている」。応答がなければ（NXDOMAIN）未登録

受信を拒否されたときのSMTPの応答の例
550 5.7.1 Service unavailable; client [203.0.113.45] blocked using dnsbl.example.net
```

**NDRメールの悪用（NDRスパム）**：また、**NDR**（Non-Delivery Report：**配送不能通知**）**メール**を悪用してスパムを送り付ける手法もあります。NDRメールは、送信先のメールアドレスが存在しないなどの理由でメールを正常に送信できなかった場合に、それを通知するためのメールです。送信できなかったメールを添付して、送信元のアドレスに送られます。

スパマーはこの機能を次のように悪用します。

1. 送信元アドレスを、スパムメールを届けたいアドレスに**詐称**する
2. 意図的に配送不能となるメール（存在しないあて先のメール）を、踏み台となるメールサーバあてに送り付ける
3. 詐称された送信元アドレスあてに、NDRメール（**NDRスパム**、**バックスキャッタ**とも呼ぶ）が送り付けられる

```
 NDRスパムの流れ

 [スパマー] ──①MAIL FROM:<victim@example.jp>（詐称）
            ──  RCPT TO:<nosuchuser@other.example>（存在しない）──→ [踏み台のメールサーバ other.example]
                                                                   │ いったん受信してから配送不能と判明
                                                                   │ ②NDRを「送信元」に返す
                                                                   ▼
                                                        [被害者 victim@example.jp]
```

被害者に届くNDRメールは、たとえば次のような見た目です。

```
From: MAILER-DAEMON@mx.other.example (Mail Delivery System)
To: victim@example.jp
Subject: Undelivered Mail Returned to Sender

This is the mail system at host mx.other.example.
I'm sorry to have to inform you that your message could not
be delivered to one or more recipients.

<nosuchuser@other.example>: 550 5.1.1 User unknown

[添付] Undelivered Message（元のメール。実際はスパムの本文や不正なファイル）
```

NDRメールの受信者は、自分が送ったどのメールが配送不能になったのかを確認しようとして、添付されたメール（実際にはスパムや不正なプログラムを含むメール）を開いてしまうおそれがあります。正規のメールサーバ（踏み台）から届くため、スパムフィルタにも引っかかりにくいのが厄介な点です。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後問題では、NDRメールを悪用したスパム（バックスキャッタ）に関する問題が出題されています。

この手法への対策には、次のような方法があります。

- NDRスパムの発信源とならないよう、NDRメールを送信しないように設定する
- NDRスパムを遮断するため、NDRメールをすべてフィルタリングする

ただし、こうした対策を行うと、NDRメール本来の目的（送信者に配送の失敗を知らせること）は達成できなくなります。現実的には、メールサーバの管理者は、自サーバが踏み台にならないように、**受信時点で存在しないあて先を拒否する**（SMTPセッション中にエラー応答を返し、受信後にNDRを生成しない）設定にすべきです。SMTPのやり取りの中で「550 5.1.1 User unknown」を返せば、エラーを知らせる相手は「今つながっている送信元のサーバ」になり、詐称された第三者にNDRが送られることはありません。

### 2.4 ③ メールの暗号化機能が標準装備されていないため、平文でネットワークを流れる

SMTPにはメールの暗号化機能がありません。そのため、クライアントアプリケーション側で暗号化を行わない限り、メールは**平文**でネットワーク中を流れます。したがって、パケット盗聴によってメールの内容が漏えいしたり、改ざんされたりする可能性があります。ノート3.3 で見たTCP/IP全般の「暗号化機能がない」という弱点が、メールというアプリケーションでもそのまま残っているわけです。

### 2.5 ④ MTAの実装・設定によってユーザのメールアカウント情報が漏えいする可能性がある

一般的なMTAには、**VRFY**、**EXPN** というコマンドがあります。これらのコマンドを使用すると、次の情報を確認できます。

- そのサーバにおける**メールアカウントの有無**（VRFY：verify）
- メールアカウント名がエイリアスやメーリングリストの場合の、**実際の配送先情報**（EXPN：expand）

これらのコマンドが有効なMTAとのやり取りは、次のように見えます。

```
VRFY taro
250 2.1.5 Taro Yamada <taro@example.co.jp>          ← taro というアカウントは存在する
VRFY hanako
550 5.1.1 <hanako>: Recipient address rejected: User unknown   ← hanako は存在しない
EXPN sales
250-2.1.5 <suzuki@example.co.jp>                   ← メーリングリスト sales の実際の配送先
250 2.1.5 <tanaka@example.co.jp>
```

攻撃者はこれらのコマンドを悪用して、よくある名前を次々に問い合わせ、有効なメールアドレスの収集（**アカウントの列挙**）を行うことができます。収集したアドレスは、スパムの送信先や、標的型攻撃メールの宛先、パスワードリスト攻撃のIDとして使われます。

### 2.6 ⑤ MTAの種類・バージョンによってBOF攻撃を受ける脆弱性がある

MTAの中には非常に古くから使われているものがあります。とくに旧バージョンのMTAについては、**BOF攻撃**を受ける脆弱性など、数多くの脆弱性が報告されています。MTAはインターネットからの接続を常時受け付けるため、脆弱性があれば世界中の攻撃者から狙われます。

> **用語：BOF攻撃**
> バッファオーバフロー（Buffer OverFlow）攻撃のことです。アプリケーションプログラムの入力データの長さのチェック不備を突き、バッファ（データを一時的に格納するメモリ領域）を意図的にあふれさせます。これにより、もともとメモリに格納されていたプログラムの実行制御情報（サブルーチンの戻りアドレスなど）を書き換え、攻撃者が用意したコードを実行させます。管理者権限で動作するプログラムが狙われると、システムの管理者権限を奪われるおそれがあります（第2章 2.3）。

攻撃者は、狙うべき脆弱性を知るために、まずMTAの種類とバージョンを調べます。その手がかりになるのが、接続したときにMTAが最初に返す**バナー**（応答メッセージ）です。

```
$ nc mail.example.co.jp 25
220 mail.example.co.jp ESMTP Sendmail 8.12.8/8.12.8; Wed, 30 Sep 2026 10:00:00 +0900
    ↑ 製品名とバージョンがそのまま表示されている。攻撃者は「この版の既知の脆弱性」を探せる
```

## 3. SMTPの脆弱性への対策（1）― 送信を正しく制御する

ここからは対策です。まず、第三者中継とボットからのスパム送信を防ぐための、「誰にメールを送らせるか」を制御する対策を見ていきます。

### 3.1 ① MTAの設定による送信元メールアドレスの制限

メールサーバの管理者は、自サーバがスパムの踏み台にならないように、MTAの設定により、**送信元メールアドレスとあて先メールアドレスのいずれにも自サイトのドメイン名が含まれていないメールの中継を拒否**すべきです。これにより、第三者中継を禁止します。

あわせて、次のような制限も有効です。

- 中継を許可する送信元を、自組織内のIPアドレス（ネットワークアドレス）に限定する
- 自組織内から送信されるメールについては、送信元メールアドレスのドメインが自組織のものであることを確認する

送信元メールアドレスは詐称できるので、「送信元のドメインが自サイトなら中継する」という条件だけでは、スパマーが送信元を自サイトのアドレスに詐称すれば通ってしまいます。そのため、実際の設定では「接続元IPアドレスが自組織内であるか、SMTP-AUTHで認証済みの利用者であれば中継する。それ以外は、あて先が自サイトのドメインである場合だけ受け付ける」という形にします。代表的なMTAである Postfix の設定例を示します。

```
# /etc/postfix/main.cf（抜粋）
mydomain = example.co.jp
# 中継を許可する自組織のネットワーク
mynetworks = 127.0.0.0/8, 10.1.0.0/16
# 外部から受け取る（自サイトの）宛先ドメイン
mydestination = $mydomain
# 中継の判定：自組織のネットワークか、SMTP-AUTHで認証済みなら許可。それ以外で宛先が自サイトでなければ拒否
smtpd_relay_restrictions = permit_mynetworks, permit_sasl_authenticated, reject_unauth_destination
```

`reject_unauth_destination` が「自サイト宛てでも、許可された送信元でもないメールは中継しない」という、第三者中継禁止の中核の設定です。

### 3.2 ② SMTP Authentication（SMTP-AUTH）によるユーザ認証

**SMTP-AUTH**（SMTP Authentication）は、SMTPにユーザ認証機能を追加した方式です（RFC 4954、旧RFC 2554）。メールサーバの管理者は、正規の利用者だけにメールを投稿させるために、MUAからの投稿時にユーザIDとパスワードなどで利用者を認証すべきです。使用するには、MTA（MSA）とMUAの双方がこの方式に対応している必要があります。

SMTP-AUTHの認証機構は、**SASL**（Simple Authentication and Security Layer）に基づいています。SASLは、アプリケーションのプロトコルから認証の方式を切り離して共通化する枠組みで、ユーザ名とパスワードを安全にサーバに送る手段として、次のような認証機構を規定しています。

- **Kerberos**
- **GSSAPI**（Generic Security Service Application Programming Interface）
- **S/Key**

SMTP-AUTHのユーザ認証方式には次のような種類があります。以前は「一般的に使用されているのは **CRAM-MD5**」とされていましたが、現在は、MD5の弱さ（下の用語を参照）やサーバ側でパスワードを平文に近い形で保管する必要があることから CRAM-MD5 や DIGEST-MD5 は推奨されなくなっており（DIGEST-MD5 は2011年に RFC 6331 で歴史的な扱いに移されました）、**TLSで通信路を暗号化したうえで PLAIN や LOGIN を使う**形が主流です。さらに、大手のクラウドメールサービスでは、パスワードを使わない OAuth 2.0 による認証へ移行する動きも進んでいます。

**表：SMTP-AUTHにおけるユーザ認証方式**

| 種類 | RFC | 概要 | 現在の位置づけ |
| --- | --- | --- | --- |
| **PLAIN** | RFC 2595（現RFC 4616） | 平文のままユーザIDとパスワードを送信する方式。実装によってはBase64でエンコードするものもあるが、容易に復号できる | TLSと組み合わせることが前提。現在の主流 |
| **LOGIN** | ― | PLAINと同様、平文（Base64エンコード）のままユーザIDとパスワードを送信する方式。RFCで規定されていないため、実装方法がベンダによって異なる | TLSと組み合わせて広く使われている |
| **CRAM-MD5** | RFC 2195 | CRAMは「Challenge-Response Authentication Mechanism」の略。メールサーバから受け取った任意の文字列（チャレンジ）とパスワードを基にしたMD5のメッセージダイジェスト（HMAC-MD5）で認証する方式 | パスワード自体は流れないが、MD5の弱さなどから推奨されない |
| **DIGEST-MD5** | RFC 2831 | CRAM-MD5のセキュリティ機能を強化した方式。辞書攻撃やブルートフォース（総当たり）攻撃への対処が行われているほか、realm（レルム：認証を行う管理領域。Kerberosの管理領域に相当するもの）やURLの指定、HMAC（Keyed-Hashing for Message Authentication Code）による完全性保護・暗号化などをサポートする | 仕様が複雑で相互運用性に問題があり、歴史的な扱いに移された |

> **用語：MD5（Message Digest 5）**
> ハッシュ関数の一つです。与えられた任意長のデータから、**128ビット**の固定長の疑似乱数（ハッシュ値）を生成します。生成される値は「**メッセージダイジェスト**」と呼ばれます。元のデータが少しでも異なれば、生成される値は大きく変化します。また、生成された値から元のデータを復元することはほぼ不可能です。この性質から、データの改ざん検出やデジタル署名などに利用されてきました。ただし現在は衝突耐性の脆弱性が指摘されており、**SHA-256** などへの移行が推奨されています。

PLAINとCRAM-MD5の違いは、実際のやり取りを見ると一目でわかります。次は、MUA（利用者 taro、パスワード secret123）がMSAに認証するときのSMTPのやり取りです。

```
（PLAIN の場合）
EHLO pc01.example.co.jp
250-mail.example.co.jp
250-AUTH PLAIN LOGIN CRAM-MD5          ← サーバが対応している認証方式の一覧
250 8BITMIME
AUTH PLAIN AHRhcm8Ac2VjcmV0MTIz
235 2.7.0 Authentication successful

  "AHRhcm8Ac2VjcmV0MTIz" を Base64 でデコードすると → \0taro\0secret123
  暗号化ではなく単なる符号化なので、盗聴されればパスワードがそのまま読まれる
```

```
（CRAM-MD5 の場合）
AUTH CRAM-MD5
334 PDE4OTYuNjk3MTcwOTUyQG1haWwuZXhhbXBsZS5jby5qcD4=
    ← チャレンジ。デコードすると <1896.697170952@mail.example.co.jp>（毎回変わる文字列）
dGFybyBhMzBjMzA1MjY4OTcxY2ZlMmViYWM2MGM0NmU2NjkxOQ==
    ← デコードすると "taro a30c305268971cfe2ebac60c46e66919"
       （パスワードを鍵にしてチャレンジから計算したHMAC-MD5の値。パスワード自体は流れない）
235 2.7.0 Authentication successful
```

PLAINは、一見すると意味不明な文字列が流れていますが、Base64は誰でも元に戻せる符号化にすぎません。したがって、メールサーバの管理者は、PLAINやLOGINを使うなら、必ず 6章の SMTP over TLS や STARTTLS で通信路を暗号化した後に認証させるべきです。

### 3.3 ③ POP before SMTPによるユーザ認証

**POP before SMTP** は、メールの送信に先立って POP3 によるユーザ認証を行い、認証に成功した場合だけ、一定時間メールの送信を許可する方式です。正式な規定は存在しませんが、RFC 2476 の中で言及されています。SMTP-AUTHが普及する前に、「SMTPには認証がないが、POP3には認証がある」ことを利用して考え出された回避策です。

仕組みは次のとおりです。

1. POPサーバは、認証に成功したクライアントのIPアドレスを一定時間記録する
2. SMTPサーバは、記録されているIPアドレスからのメール送信だけを受け付ける

```
 利用者PC(192.0.2.57) ──①POP3で認証（USER/PASS）──→ POPサーバ：「192.0.2.57 を10分間許可」と記録
 利用者PC(192.0.2.57) ──②SMTPで送信─────────────→ SMTPサーバ：記録を確認して受け付ける
 別の利用者(192.0.2.57) ─③SMTPで送信─────────────→ SMTPサーバ：同じIPアドレスなので受け付けてしまう
   （NATで同じグローバルアドレスを共有している別人）
```

SMTP-AUTHに対応していないMUAでも利用できる点が利点です。一方で、次のような弱点があります。

- 認証は POP3 で行われるため、APOPなどを使わなければ**認証情報が平文で流れる**
- NAT環境などで**同一のIPアドレスを共有する別の利用者**も、許可された時間内であれば送信できてしまう

認証の単位が「人」ではなく「IPアドレス」になってしまう点が根本的な弱さです。現在はSMTP-AUTHが広く普及しているため、新たに採用すべき方式ではありません。

### 3.4 ④ Outbound Port 25 Blocking によるメール送信制限

**スパマーの手口の変化**：本ノート3.1 の対策によって多くのサイトでメールの第三者中継が禁止されると、スパマーは別の手法を多用するようになりました。**ボット**などを用いて、送信先サイトのメールサーバと**直接SMTPコネクションを確立**し、スパムを送り付ける手法です。マルウェアに感染した一般家庭のPC（ボット）が、それぞれ自分でMTAのように振る舞い、宛先ドメインのMXレコードを調べて直接25番ポートに接続するのです。この手法は第三者中継を用いていないため、第三者中継を禁止してもスパムを受信してしまいます。

こうした手法によるスパムを防ぐための対策として考え出されたのが、**Outbound Port 25 Blocking**（**OP25B**）です。

OP25Bは、**ISP**（Internet Service Provider）が、自社のメールサーバを経由せずにインターネット方向（外向き）に出ていく、**25番ポートあてのパケット**（SMTP）を遮断する方式です。主に**動的IPアドレス**を割り当てたネットワーク（一般家庭向けの接続サービスなど）を対象とし、すでに多くのISPで採用されています。一般の利用者のPCが外部のメールサーバの25番ポートに直接接続する正当な理由はほとんどなく、そうした通信の多くはボットによるスパム送信だからです。OP25Bのイメージを次の図に示します。

**図：OP25Bのイメージ**

```
[ISP管理下のネットワーク（動的IPアドレス）]
   ├─ 利用者PC ──(25/TCP)──> ISPのメールサーバ ──(25/TCP)──> 外部のメールサーバ   ○ 許可
   └─ ボット感染PC ──(25/TCP)────────────────×──> 外部のメールサーバ           × 遮断（OP25B）
```

**OP25Bの副作用とサブミッションポート**：OP25Bを導入すると、ISPの利用者が、自社のメールサーバなどISP外部のメールサーバへ直接メールを送信できなくなります。たとえば、自宅からテレワークで会社のメールサーバを使って送信しようとしても、25番ポートが遮断されて送れません。この問題を解決するため、次のような仕組みが用いられます。

- 正当な利用者が自社のメールサーバなどと直接SMTPコネクションを確立してメールを送信する必要がある場合には、25番ポートではなく、投稿専用の **587番ポート**（**Submission**、サブミッションポート）を使用する（RFC 6409、旧RFC 2476）
- これを実現するため、従来のMTAの機能を **MSA と MTA に分離**する（2.2 の脆弱性①への対策）
- MSAでは、Submissionポートへアクセスしてきたユーザを **SMTP-AUTH** によって認証し、スパマーからの投稿を受け付けないようにする。さらに、TLSによって通信を秘匿化することも可能である（**Submission over TLS**）
- MTAは従来どおり25番ポートを使用し、MTA間でのメールの中継と受信を担当する

**図：Submissionポートによるメール投稿のイメージ**

```
[ISP管理下のネットワーク]                          [自社ネットワーク]
  利用者PC(MUA) ──(587/TCP + SMTP-AUTH)──────────> 自社メールサーバ(MSA)
                                                          │
                                                   自社メールサーバ(MTA) ──(25/TCP)──> 他社MTA
  ボット感染PC ──(25/TCP)──×（OP25Bにより遮断）
```

こうして、2.2 で見た「投稿と中継が同じ25番ポートで区別できない」という弱点は、「投稿は587番（認証あり）、中継は25番（MTA間）」とポートごと分けることで解消されました。1.4 の5.3で見た「認証がある入り口と、認証のないサーバ間の入り口を分けた」というのは、このことです。

### 3.5 ⑤ Inbound Port 25 Blocking によるメール着信制限

**Inbound Port 25 Blocking**（**IP25B**）は、ISPが、**他社ISPのネットワークの動的IPアドレス**から、**自社ISP内のメールサーバ**へのSMTP通信（25/TCP）を遮断する方式です。

OP25Bは「自社ISPの利用者からスパムを**送信させない**」ための対策です。これに対しIP25Bは、「OP25Bを導入していない他社ISPのネットワークから送られてくるスパムを**受信しない**」ための対策です。

| 観点 | OP25B（Outbound Port 25 Blocking） | IP25B（Inbound Port 25 Blocking） |
|---|---|---|
| 遮断する通信 | 自社ISPの動的IPアドレス → ISP外部のメールサーバ（25/TCP） | 他社ISPの動的IPアドレス → 自社ISPのメールサーバ（25/TCP） |
| 方向 | 外向き（出ていく） | 内向き（入ってくる） |
| 目的 | 自社の利用者（ボット）をスパムの**送信元にしない** | 他社のボットからのスパムを**受け取らない** |
| 守るもの | インターネット全体（他組織） | 自社ISPの利用者 |
| 副作用と回避策 | 利用者が外部のメールサーバに直接送れなくなる → サブミッションポート（587）とSMTP-AUTH | 動的IPアドレスから直接送る正規の送信者も拒否される → 送信者はISPのメールサーバかサブミッションポートを使う |

試験では「自社ISP／他社ISP」「動的IPアドレスから／メールサーバへ」の組合せで選択肢が作られるので、「OP25Bは自分のところから外へ出すな、IP25Bはよそから入れるな」と方向で覚えておきましょう。

## 4. SMTPの脆弱性への対策（2）― ⑥ IPアドレス・デジタル署名による送信ドメイン認証で「なりすまし」を見抜く

3章の対策は「自組織のサーバを悪用させない」ためのものでした。しかし、スパマーやフィッシング詐欺師は、自分で用意したサーバから、送信元を有名企業や銀行のアドレスに詐称してメールを送ることもできます。これを受信側で見抜くのが送信ドメイン認証です。

### 4.1 送信ドメイン認証とは

送信元情報を偽装したメールを発見して排除する技術として、**送信ドメイン認証**が広く普及しています。これは、**送信元のIPアドレス**や**デジタル署名**を使って、メールの受信側で送信元SMTPサーバを認証する仕組みです。

> **用語：デジタル署名**
> PKI技術を用いて文書などに電子的に行う署名です。その文書が確かに本人から送信されたものであり、途中で改ざんされていないことを証明する技術です（第7章）。

送信ドメイン認証を理解するには、1.4 の5.4で学んだ2種類の送信者情報の区別が欠かせません。

| 送信者情報 | 別名 | たとえると | 主に検証する技術 |
|---|---|---|---|
| エンベロープのFrom（SMTPの MAIL FROM。受信後は Return-Path: ヘッダになる） | **Envelope-From** | 封筒の差出人 | SPF |
| ヘッダのFrom（メール本文の一部の From:。受信者の画面に表示される） | **Header-From** | 便箋に書かれた署名 | DKIM（署名したドメイン）、DMARC（整合性） |

主な方式を、IPアドレスによる方式、デジタル署名による方式、それらを補完する仕組みの順に見ていきます。

### 4.2 IPアドレスによる方式 ― SPF

**● Sender Policy Framework（SPF）**

**SPF** は、送信元ドメインの管理者が「うちのドメインのメールは、このIPアドレスのサーバからしか送りません」とDNSで宣言しておき、受信側がそれと照合する仕組みです。あらかじめ、送信元ドメインのDNSサーバの **TXTレコード**に、正当なSMTPサーバのIPアドレス（**SPFレコード**）を登録しておきます。これによって送信元のSMTPサーバを認証する仕組みであり、次のような機能があります（RFC 7208）。

- メールを受信した受信側ドメインのSMTPサーバは、送信元のDNSサーバに問い合わせる。そして、エンベロープ（SMTPプロトコルの MAIL FROM）のメールアドレスのドメインと、接続元SMTPサーバのIPアドレスとの適合性を検証する
- 上記によって送信元SMTPサーバの正当性が確認された場合だけメールを受け入れ、それ以外のメールは排除する

SPFで照合に使う「接続元のIPアドレス」は、受信側のサーバがTCPの接続相手として直接観測したものです。1.4 の5.4で「自組織のサーバが記録した Received: ヘッダの () 内のIPアドレスは詐称できない」と学んだのと同じ理屈で、送信者がいくらヘッダを書き換えても、このIPアドレスはごまかせません。ここにSPFの強みがあります。

SPFレコードの記述例を次に示します。

例1：`shoeisha.co.jp` ドメインからはメールを送信しない場合

```
shoeisha.co.jp.  IN  TXT  "v=spf1 -all"
```

例2：MXレコードに指定したホストからだけメールを送信する場合

```
shoeisha.co.jp.  IN  TXT  "v=spf1 mx -all"
```

例3：自社のメールサーバ2台と、外部のメール配信サービスから送信する場合（例示用のドメインとアドレス）

```
example.co.jp.  IN  TXT  "v=spf1 ip4:192.0.2.10 ip4:192.0.2.11 include:_spf.mailservice.example -all"
```

> **補足：SPFレコードの主な記述要素**
>
> - `v=spf1`：SPFのバージョン
> - `ip4:` / `ip6:`：送信を許可するIPアドレス
> - `mx`：MXレコードに登録されたホストを許可
> - `include:`：他ドメインのSPFレコードを参照
> - `-all`：上記以外は認証失敗（fail）とする。`~all` はソフトフェイル（softfail）

例1の「メールを送信しないドメイン」にもSPFレコードを設定する意味は大きい点に注意してください。Webサイト専用のドメインや、使っていないドメインにSPFレコードがないと、攻撃者はそのドメインを送信元に詐称しても「SPFの判定結果：none（レコードなし）」になるだけで、fail にはなりません。管理者は、自組織が所有するすべてのドメインについて、送信しないものには `v=spf1 -all` を登録しておくべきです。また、`include:` などDNSの問合せを伴う記述は、1回の評価で合計10回までという上限があるため、外部サービスを多数追加するときは注意が必要です。

受信側で SPF がどう記録されるかも見ておきましょう。DNSへの問合せと、受信したメールに付くヘッダの例です。

```
$ dig +short TXT example.co.jp
"v=spf1 ip4:192.0.2.10 ip4:192.0.2.11 include:_spf.mailservice.example -all"

受信側のメールサーバが付けるヘッダの例
Received-SPF: pass (mx.example.jp: domain of sender@example.co.jp designates 192.0.2.10 as permitted sender)
    client-ip=192.0.2.10; envelope-from=sender@example.co.jp;
```

SPFの判定結果には、pass（許可されたサーバ）、fail（許可されていない。`-all` に該当）、softfail（おそらく許可されていない。`~all` に該当）、neutral（判断しない）、none（SPFレコードがない）などがあります。

> **試験に出る**
> 情報処理安全確保支援士試験では、平成30年度の午後問題（問2）でSPFに関する問題が出題されました。そのほかにもSPFは頻出のテーマです。

**● Sender ID Framework（Sender ID）**

**Sender ID** は、SPFの機能に加えて、受信したメールのヘッダ情報（From:、Sender: など）のメールアドレスのドメインの正当性も検証します。エンベロープとヘッダのどちらか一方を検証するか、両方を検証するかを選択できます。米マイクロソフト社が中心となって提案した方式ですが、現在はほとんど使われておらず、ヘッダFromの検証という役割は後述の DMARC に引き継がれています。

**図：SPF、Sender IDによる送信者認証のイメージ**

```
 送信側ドメイン(example.co.jp)                         受信側ドメイン
 ┌──────────────┐                                  ┌───────────────┐
 │ SMTPサーバ   │ ─────①メール送信────────────────> │ SMTPサーバ    │
 │ (192.0.2.10) │                                  └───────┬───────┘
 └──────────────┘                                          │②SPFレコード問合せ
 ┌──────────────┐ <────────────────────────────────────────┘
 │ DNSサーバ    │ ─────③SPFレコード応答（192.0.2.10を許可）──>
 └──────────────┘         ④接続元IPアドレスと照合し、一致すれば受理
```

### 4.3 デジタル署名による方式 ― DomainKeys と DKIM

**● DomainKeys**

**DomainKeys** は、あらかじめ、送信元ドメインのDNSサーバに正当なメールサーバの**公開鍵**を登録しておき、SMTPサーバが付したデジタル署名によって、送信元メールサーバの正当性を検証する仕組みです（米国ヤフー社が中心となって策定）。次のような機能があります。

- 送信側SMTPサーバは、**秘密鍵**を用いてメールにデジタル署名を付与する
- 受信側SMTPサーバは、送信元ドメインのDNSサーバから公開鍵を取得し、デジタル署名を検証する
- 上記によってデジタル署名（送信元SMTPサーバ）の正当性が確認された場合だけメールを受け入れ、それ以外のメールは排除する

**● DomainKeys Identified Mail（DKIM）**

**DKIM** は、DomainKeysと、米国シスコシステムズ社らが提案していた **IIM**（Identified Internet Mail）の仕様を統一し、IETFが標準化したデジタル署名による送信ドメイン認証技術です（RFC 6376）。現在、DomainKeys は DKIM に置き換えられ、実際に使われているのは DKIM です。

DKIMの仕組みはDomainKeysと同様です。ただし、署名を検証するための公開鍵に関する情報をメールのヘッダに添付するIIMの技術が追加されています。具体的には、署名ヘッダの中に「どのドメインの（d=）、どのセレクタの（s=）公開鍵で検証すればよいか」が書かれており、受信側はそれを手がかりにDNSから公開鍵を取り出します。将来的には、ドメイン単位だけでなく**ユーザ単位での署名と検証**も可能とされています（i= タグ）。DKIMの署名は、メールヘッダの「**DKIM-Signature:**」フィールドに格納されます。

```
送信側のメールサーバが付与する DKIM-Signature ヘッダの例
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=example.co.jp; s=sel2026;
        t=1790730000; h=from:to:subject:date:message-id;
        bh=（本文のSHA-256ハッシュ値をBase64で表したもの）;
        b=（ヘッダと bh から計算した署名値。長いBase64文字列）

送信側ドメインのDNSに登録する公開鍵（セレクタ sel2026 の場合）
sel2026._domainkey.example.co.jp.  IN  TXT  "v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA…（公開鍵、省略）"
```

| タグ | 意味 | 例の値 |
|---|---|---|
| v | バージョン | 1 |
| a | 署名アルゴリズム | rsa-sha256（RSA署名とSHA-256ハッシュ） |
| c | 正規化方式（転送中の空白の変化などを許容する度合い） | relaxed/relaxed |
| d | 署名したドメイン（DMARCの整合性チェックに使う） | example.co.jp |
| s | セレクタ（どの公開鍵かを指す名前。鍵の切替えに使う） | sel2026 |
| h | 署名の対象にしたヘッダの一覧 | from:to:subject:date:message-id |
| bh | 本文のハッシュ値 | ― |
| b | 署名値 | ― |

h= に From: が含まれていることに注目してください。署名の対象にヘッダFromも入っているので、経路上で From: を書き換えると署名の検証に失敗します。DKIMが「メール本文やヘッダの改ざんも検知できる」のはこのためです。

**表：送信ドメイン認証方式の比較**

| 名称 | 方式 | メリット | デメリット |
| --- | --- | --- | --- |
| Sender Policy Framework（SPF） / Sender ID Framework（Sender ID） | IPアドレス | ・送信元情報の偽装を配送経路上で検知して排除できる<br>・シンプルな方式であるため導入が容易<br>・送信側SMTPサーバには設定等が不要（DNSへの登録のみ）<br>・受信側SMTPサーバにかかる負荷が比較的少ない | ・送信元情報を偽っていないスパムは排除できない<br>・DNSに登録されていないサーバからのメールは、正当なものであっても排除されるおそれがある<br>・直近のSMTPサーバのアドレスで検証するため、複数のSMTPサーバを経由（転送）したメールは検証が困難 |
| DomainKeys / DomainKeys Identified Mail（DKIM） | デジタル署名 | ・送信元情報の偽装を配送経路上で検知して排除できる<br>・複数のSMTPサーバを経由したメールについても検証できる<br>・メール本文やヘッダの改ざんも検知できる | ・送信側・受信側双方のSMTPサーバが方式に対応する必要がある<br>・署名の生成・検証により、双方のSMTPサーバに負荷がかかる<br>・メーリングリストや広告が付加されるメールなど、配送経路で内容が変更されるメールは検証が困難 |

SPFの「転送に弱い」というデメリットは、具体的にはこういうことです。社員が会社のメールを個人のアドレスに自動転送する設定をしていると、転送先のサーバから見た接続元は「会社のメールサーバ」になり、元の送信者のSPFレコードに載っていないので fail になります。DKIMは署名がメールそのものに付いているので、内容が変わらなければ転送されても検証できます。逆に、メーリングリストが件名に「[ml:123]」を付けたり、末尾に広告を付けたりすると、DKIMの署名は壊れます。両者は弱点を補い合う関係にあるので、送信側の管理者はSPFとDKIMの両方を設定すべきです。なお、転送やメーリングリストで元の認証結果が失われる問題に対しては、中継したサーバが「受け取った時点の認証結果」を署名付きで引き継ぐ **ARC**（Authenticated Received Chain、RFC 8617）という仕組みも使われ始めています。

### 4.4 送信ドメイン認証の限界

近年社会問題化しているスパムメールは、必ずしも送信元情報を偽装しているわけではありません。スパマーが自分で取得したドメインから、自分のドメインのSPFやDKIMを正しく設定して送ってくれば、送信ドメイン認証は pass になります。そのため、これらの技術を用いても完全な対策にはなりませんが、ある程度の効果は期待できます。

一方、**フィッシング**メールは、銀行や有名企業になりすます必要があるため、送信元情報が偽装されているケースが大半です。そのため、送信ドメイン認証による削減効果が期待されます。ただし、送信ドメイン認証には次のような限界があります。

- **SPFの限界**：SPFは、エンベロープのドメイン（**Envelope-From**）の正当性を検証する仕組みです。そのため、メール送信者が独自ドメインでSPFレコードを設定したうえで、受信者が目にするメールヘッダの送信者ドメイン（**Header-From**）をEnvelope-Fromとは異なるものに詐称している場合、偽装を検出できません。
- **DKIMの限界**：メール送信者の独自ドメインによる正規の署名が付与されていれば、Header-Fromが詐称されていても検出できません。

つまり、攻撃者は「封筒の差出人（Envelope-From）と署名（DKIMのd=）は自分のドメインで正しく認証を通し、受信者が目にする便箋の差出人（Header-From）だけを銀行に詐称する」ことで、SPFとDKIMを両方すり抜けられるのです。こうした問題は、後述する **DMARC** を組み合わせることで検出精度を高められます。

> **用語：フィッシング（Phishing）**
> 銀行、クレジットカード会社、ショッピングサイトなどを装った電子メールを送り付け、本物のWebサイトに見せかけた偽のページに誘導する手口です。偽のページでは、口座番号、クレジットカード番号、パスワードなどの個人情報を入力させて盗みます。

### 4.5 送信ドメイン認証を補完する仕組み ― DMARC

**● DMARC（Domain-based Message Authentication, Reporting and Conformance）**

**DMARC** は、SPFやDKIMによる認証結果と **Header-From のドメインとの整合性**（**アライメント**）を検証する仕組みです。あわせて、認証に失敗したメールの取扱いポリシを送信側ドメインの管理者が表明し、受信側がそのポリシに従って処理します。これによって、送信ドメイン認証を補完します（RFC 7489）。

DMARCの判定は、「SPFが pass し、かつSPFで認証したドメイン（Envelope-From）がHeader-Fromと整合している」か、「DKIMが pass し、かつ署名したドメイン（d=）がHeader-Fromと整合している」の、**どちらか一方**を満たせば pass になります。単にSPFやDKIMが pass するだけでは足りず、「受信者が目にする差出人のドメインで」認証が通っていることを求めるのがDMARCの核心です。

**表：DMARCによる判定の例**

| ケース | Header-From | Envelope-From（SPF） | DKIM署名（d=） | SPF | DKIM | DMARC |
|---|---|---|---|---|---|---|
| 正規のメール | example.co.jp | example.co.jp | example.co.jp | pass | pass | **pass** |
| 正規のメール（配信用のサブドメインを使用） | example.co.jp | bounce.example.co.jp | ― | pass | none | **pass**（サブドメインは整合とみなす緩和モード） |
| SPFをすり抜けるなりすまし | bank.example.jp（詐称） | mailer.example.net（攻撃者のドメイン） | なし | pass | none | **fail**（どちらも整合しない） |
| SPFとDKIMをすり抜けるなりすまし | bank.example.jp（詐称） | mailer.example.net | mailer.example.net（攻撃者が正規に署名） | pass | pass | **fail**（どちらも整合しない） |
| 単純な詐称 | bank.example.jp（詐称） | bank.example.jp（詐称） | なし | fail | none | **fail** |

DMARCのポリシ表明は、SPFと同様に、DNSサーバにTXTレコード（`_dmarc.ドメイン名`）を追加し、タグに値を設定して行います。

例えばDMARCの **pタグ**では、認証に失敗したメールについて次のような指定が可能です。

- `none`：何もしない（モニタリングのみ）
- `quarantine`：メールを隔離する（迷惑メールフォルダへの振分けなど）
- `reject`：メールを拒否（排除）する

```
_dmarc.example.co.jp.  IN  TXT  "v=DMARC1; p=reject; rua=mailto:dmarc-report@example.co.jp"
```

| タグ | 意味 | 例 |
|---|---|---|
| v | バージョン（必須） | DMARC1 |
| p | 認証に失敗したメールの取扱いポリシ（必須） | none／quarantine／reject |
| sp | サブドメインに適用するポリシ | reject |
| rua | 集計レポートの送付先 | mailto:dmarc-report@example.co.jp |
| ruf | 失敗レポート（個々の失敗メールの情報）の送付先 | mailto:dmarc-forensic@example.co.jp |
| pct | ポリシを適用するメールの割合（%） | 100 |
| adkim／aspf | DKIM／SPFの整合性の判定を厳格（s）にするか緩和（r）にするか | r（サブドメインも整合とみなす） |

**レポート機能**：DMARCには、メール受信側が送信側に対し、認証の結果をレポートとして通知する機能があります（**rua**タグで集計レポート、**ruf**タグで失敗レポートの送付先を指定）。送信側はこのレポートによって、自組織のメールシステムが適切に稼働しているかどうか、自ドメインを詐称したメールが送られていないかどうかを確認できます。集計レポートはXML形式で届き、たとえば次のような行が含まれます。

```xml
<record>
  <row>
    <source_ip>203.0.113.45</source_ip>   <!-- 自社のものではない送信元 -->
    <count>120</count>                    <!-- 120通 -->
    <policy_evaluated><disposition>reject</disposition><dkim>fail</dkim><spf>fail</spf></policy_evaluated>
  </row>
  <identifiers><header_from>example.co.jp</header_from></identifiers>
</record>
```

「自社のものではないIPアドレスから、自社のドメインを名乗るメールが120通送られ、ポリシに従って拒否された」ことがわかります。

**導入の進め方**：いきなり `p=reject` にすると、SPFやDKIMの設定漏れがある正規のメール（外部の配信サービスから送っているメルマガなど）まで拒否されてしまいます。そこで送信側の管理者は、まず `p=none` でレポートを集めて正規の送信経路をすべて把握し、SPF・DKIMの設定を直してから、`p=quarantine`、`p=reject` へと段階的に強めていくべきです。逆に言えば、`p=none` のままでは、なりすましメールは受信者に届き続けます。

**アライメントの要求**：また、DMARCでは、Envelope-FromをHeader-Fromと同じドメインにするか、Header-Fromのサブドメインで運用したうえで、SPFなどの送信ドメイン認証を行うことを求めています。そのため、DMARCとSPFなどの送信ドメイン認証を組み合わせることで、前述のように独自ドメインを用いてSPFやDKIMをすり抜ける、Header-Fromを詐称したメールも検出できるようになります。

**普及の状況**：2024年からは、Gmail などの大手メールサービスが、大量にメールを送る送信者に対して SPF・DKIM・DMARC の設定を求めるようになり、国内でもクレジットカード会社などにDMARCの導入が要請されるなど、DMARCは「設定して当然」の技術になりつつあります。

**DMARCでも防げないもの**：DMARCが守るのは「自分のドメインそのもの」を詐称されることだけです。攻撃者が本物とよく似た別のドメイン（例：本物が bank.example.jp なら、bank-example.example.com のようなもの）を取得し、そのドメインでSPF・DKIM・DMARCを正しく設定して送ってくれば、すべて pass になります。受信者が表示名（「エグザンプル銀行」）だけを見て判断すれば、だまされてしまいます。このため、技術的な対策に加えて、利用者への教育（差出人のアドレスやリンク先のドメインを確認する）や、公式サイトにブックマークからアクセスするよう周知することが欠かせません。

### 4.6 なりすましメールのヘッダを読む

ここまでの知識を使って、実際になりすましメールのヘッダを読んでみましょう。自社（example.jp）の社員 taro が受信した、銀行を名乗るメールのヘッダです。

```
Return-Path: <info@mailer.example.net>
Authentication-Results: mx.example.jp;
        spf=pass smtp.mailfrom=mailer.example.net;
        dkim=none;
        dmarc=fail (p=NONE) header.from=bank.example.jp
Received: from bank.example.jp (unknown [203.0.113.45])
        by mx.example.jp (Postfix) with ESMTP id 4F2A1C0001
        for <taro@example.jp>; Wed, 30 Sep 2026 09:12:38 +0900
From: "エグザンプル銀行" <support@bank.example.jp>
To: taro@example.jp
Subject: 【重要】お客様の口座のご利用を一時停止しました
Date: Wed, 30 Sep 2026 09:12:30 +0900

エグザンプル銀行をご利用いただき、ありがとうございます。
お客様の口座で不審な取引を検知したため、ご利用を一時停止しております。
24時間以内に、下記URLより本人確認のお手続きをお願いいたします。
  https://bank-example.example.com/login/verify
お手続きがない場合、口座を凍結させていただく場合がございます。
```

読み解きのポイントは次のとおりです。

| 箇所 | 読み取れること |
|---|---|
| Received: の `from bank.example.jp` | HELOで名乗ったホスト名。送信者が自由に書けるので根拠にならない |
| Received: の `(unknown [203.0.113.45])` | 自社の受信サーバが記録した実際の接続元IPアドレス。逆引きできず（unknown）、銀行のサーバではない |
| Return-Path: と `spf=pass smtp.mailfrom=mailer.example.net` | 封筒の差出人は攻撃者のドメイン。攻撃者は自分のドメインでSPFを通している |
| `dkim=none` | DKIM署名がない。本物の銀行のメールなら、通常は銀行のドメインで署名されている |
| `dmarc=fail (p=NONE) header.from=bank.example.jp` | 表示されている差出人（bank.example.jp）と認証されたドメインが一致しない。**なりすましの決定的な証拠**。ただし銀行側のポリシが none なので、受信側は拒否せずに配送してしまった |
| 本文のURL | 本物のドメイン（bank.example.jp）とは別のドメインに誘導している。緊急性をあおり、期限を切る文面はフィッシングの典型 |

このメールからわかる対策は2つあります。1つは、銀行（送信側）が DMARC のポリシを `p=reject` に強めることで、このようななりすましメールが受信者に届かないようにすること。もう1つは、受信側の組織が、DMARCで fail になったメールに警告を表示したり隔離したりする設定をし、社員にヘッダやURLの確認方法を教育することです。

## 5. SMTPの脆弱性への対策（3）― ⑦ メールフィルタリング

送信ドメイン認証は「送信元の詐称」を見抜く技術でしたが、詐称していない迷惑メールや、正規のアカウントが乗っ取られて送られてきたマルウェア付きメールは見抜けません。そこで、メールの**内容**を検査するのがメールフィルタリングです。

迷惑メールやマルウェアが添付されたメールを検出して除去するため、**メールフィルタリング**ツールやサービスが広く普及しています。導入形態には、次のようなものがあります。

- ISP（Internet Service Provider）のメールサービスを利用している場合は、標準的に提供される
- 自社でメールサーバを設置している場合は、サーバに製品を導入し、経路上で迷惑メールをフィルタリングするのが一般的である
- メールクライアントソフトウェアのフィルタリング機能を利用して、クライアント側で振り分ける

従来のフィルタリングは、キーワードや送信元アドレス、ブラックリストなどの**ルールに基づいて判定する方式**が中心でした。この方式には、次のような問題がありました。

- 次々に文面や送信元を変える迷惑メールに対応するため、ルールを頻繁に更新しなければならない
- ルールに合致しない新しい迷惑メールに対しては、フィルタリングが有効に機能しない

こうした問題を改善する迷惑メール検知手法として、**ベイジアンフィルタリング**（Bayesian Filtering）があります。ベイジアンフィルタリングは、**ベイズの定理**を応用して迷惑メールの特徴を**自己学習**し、統計的に解析して判定するフィルタリング手法です。学習量が増えるにつれて、フィルタリングの精度が向上します。

考え方は、過去に利用者が「迷惑メール」「正常なメール」と分類したメールから、単語ごとの出現頻度を学習し、新しいメールに含まれる単語から「このメールが迷惑メールである確率」を計算する、というものです。

$$
P(\text{迷惑メール} \mid \text{単語}) = \frac{P(\text{単語} \mid \text{迷惑メール}) \times P(\text{迷惑メール})}{P(\text{単語})}
$$

左辺は「その単語が含まれていたときに、そのメールが迷惑メールである確率」、右辺の分子は「迷惑メールの中にその単語が出てくる確率」×「そもそも迷惑メールが届く確率」です。たとえば「当選」という単語が迷惑メールには頻繁に出てきて、正常なメールにはほとんど出てこなければ、「当選」を含むメールが迷惑メールである確率は高く計算されます。メールに含まれる多数の単語について計算を組み合わせ、確率がしきい値を超えれば迷惑メールと判定します。ルールを人が書くのではなく、利用者の分類結果から自動で学ぶので、新しい文面にも追随しやすいのです。

現在のメールフィルタリング製品・サービスは、これに加えて、送信ドメイン認証の結果、送信元IPアドレスの評判（レピュテーション）、添付ファイルのマルウェア検査、添付ファイルを仮想環境で実際に開いて挙動を調べる**サンドボックス**（第5章 5.9）、本文中のURLのクリック時に安全性を再確認する機能などを組み合わせて判定しています。

## 6. SMTPの脆弱性への対策（4）― メールの暗号化

次は、2.4 で見た「平文で流れる」という弱点への対策です。メールの暗号化には、**通信路（区間）を暗号化する**方式と、**メールそのものを暗号化する**方式の2種類があり、守られる範囲が大きく違います。最初に全体像を示します。

```
 メールの暗号化方式と守られる範囲

   MUA ──投稿──→ MSA/MTA ──中継──→ 相手のMTA ──→ MDA ──受信──→ MUA
 (送信者)     (自社のサーバ)        (相手のサーバ)             (受信者)

 ⑧ SMTP over TLS（465）      ├──暗号化──┤
 ⑨ STARTTLS（587/25）        ├──暗号化──┤├──暗号化──┤
 POP3S・IMAPS（995/993）                                      ├──暗号化──┤
   ※区間ごとの暗号化では、各サーバの上ではメールは平文で保存・処理される

 ⑩ S/MIME・PGP               ├────────────── 送信者から受信者まで暗号化（エンドツーエンド）──────────────┤
```

### 6.1 ⑧「SMTP over TLS」によるメールの暗号化とユーザ認証

**SMTP over TLS** は、TLSを用いてSMTP通信を暗号化する方式です。ただし暗号化されるのは、あくまでもクライアント（MUA）から送信元（自サイト内）のメールサーバまでの通信だけです。インターネット上では、メールは平文で流れます（中継区間を暗号化するには ⑨ の STARTTLS が必要です）。

この方式では、メールの暗号化に加えて、デジタル証明書によるユーザ認証も行えます（そのためには、各ユーザがデジタル証明書を取得している必要があります）。

SMTP over TLS（**SMTPS**）では、**465/TCP**ポートが用いられます。接続した瞬間からTLSで通信する「暗黙的なTLS」なので、SMTPのやり取り（認証情報を含む）はすべて暗号化されます。なお、465番ポートは一時期、正式な割当てが取り消されてSTARTTLS（587番）の利用が推奨された経緯がありますが、2018年の RFC 8314 で「メール投稿用の暗黙的TLS」として改めて位置づけられ、現在はむしろ投稿時には465番（暗黙的TLS）の利用が推奨されています。

> **用語：TLS（Transport Layer Security）**
> SSL（Secure Sockets Layer）の後継として、IETF（Internet Engineering Task Force：インターネット技術タスクフォース）によって標準化が行われた、インターネットにおける暗号化通信プロトコルです。SSLと同様に、デジタル証明書によるサーバ認証、クライアント認証、通信データの暗号化などの機能を備えています。SSLの脆弱性が相次いで発見されたことから、現在ではTLS（**TLS 1.2** / **TLS 1.3**）が広く普及しています。

### 6.2 ⑨「STARTTLSコマンド」によるメールの暗号化

**STARTTLS** は、主に送信側のメールサーバと受信側のメールサーバの間の通信を暗号化するために使用されます（RFC 3207）。処理の流れは次のとおりです。

1. まず暗号化されていない状態で通信を開始する
2. 送信側のメールサーバが「STARTTLSコマンド」を発行する
3. 受信側のメールサーバがSTARTTLSに対応していれば、TLSによる暗号化通信が開始される。対応していない場合は、暗号化されないまま通信が行われる

実際のやり取りは次のようになります。

```
220 mx.example.jp ESMTP
EHLO mta.example.co.jp
250-mx.example.jp
250-PIPELINING
250-STARTTLS                         ← 受信側が「STARTTLSに対応している」と通知
250 8BITMIME
STARTTLS                             ← 送信側が暗号化への切替えを要求
220 2.0.0 Ready to start TLS
（ここでTLSハンドシェイク。以降の EHLO、MAIL FROM、RCPT TO、本文はすべて暗号化される）
```

このように、STARTTLSは平文で始めてから**明示的に**暗号化に切り替える方式です。これに対し、⑧のSMTP over TLSは**暗黙的な暗号化方式**（接続開始時から常にTLSを用いる方式）といえます。

SMTPでSTARTTLSを用いる場合は、暗号化通信か非暗号化通信かにかかわらず、共通して **25/TCP**ポートが用いられます。なお、MUAからMSAへの投稿時にも、**587/TCP**ポート上でSTARTTLSを用いることができます。

> **補足：STARTTLSの注意点**
> STARTTLSでは、相手が非対応の場合に平文通信へ**フォールバック**します。そのため、中間者がSTARTTLSの応答を削除して暗号化を妨害する攻撃（**STARTTLSストリッピング**）を受けるおそれがあります。対策として、**MTA-STS**（RFC 8461）や **DANE**（RFC 7672）などの仕組みがあります。

STARTTLSストリッピングでは、中間者が上のやり取りの「250-STARTTLS」の行を消してしまいます。すると送信側は「相手は暗号化に対応していない」と判断して、平文のままメールを送ってしまうのです。MTA-STS は、受信側のドメインが「うちのサーバは必ずTLSに対応しているので、TLSが使えなければ送らないでほしい」という方針をWebサーバ（HTTPS）で公開する仕組みで、送信側はその方針に従ってフォールバックを拒否します。

```
MTA-STS の設定例（受信側ドメイン example.jp の管理者が公開する）
DNS:   _mta-sts.example.jp.  IN  TXT  "v=STSv1; id=20260930"
HTTPS: https://mta-sts.example.jp/.well-known/mta-sts.txt の内容
       version: STSv1
       mode: enforce          ← TLSで接続できなければ配送しない
       mx: mx.example.jp
       max_age: 86400
```

DANE は、DNSSEC（ノート3.5）で保護したDNSに、受信サーバの証明書の情報（TLSAレコード）を登録しておく方式です。

### 6.3 ⑩ S/MIME、PGP等によるメールの暗号化

**S/MIME** や **PGP** などのソフトウェアを用いて**アプリケーション層でメールを暗号化**することで、すべての通信経路でメールを秘匿化します（**エンドツーエンドの暗号化**）。メールは送信者のMUAで暗号化され、受信者のMUAで初めて復号されるので、途中のメールサーバの管理者や、サーバに侵入した攻撃者にも内容を読まれません。デジタル署名を付与すれば、**送信者の真正性**と**メールの完全性**も確認できます。これは、4章の送信ドメイン認証（サーバ単位・ドメイン単位の認証）よりも細かい、「送信者本人」の認証になります。

> **用語：S/MIME（Secure Multipurpose Internet Mail Extensions）**
> 米国RSA Security社が開発した暗号化電子メールの規格です。**MIME** は、画像などのバイナリファイルをメールで送受信するための規格です。S/MIMEはMIMEを拡張したものであるため、添付ファイルを含めて暗号化できます。公開鍵の正当性は、**認証局（CA）**が発行するデジタル証明書によって保証されます。

> **用語：PGP（Pretty Good Privacy）**
> **1991年**に**フィリップ・ジマーマン**（Philip Zimmermann）によって開発された電子メール暗号化ツールです。当初フリーソフトウェアとしてインターネット上で公開されたため、広く普及しました。暗号化アルゴリズムには、当初 **RSA** と **IDEA** が用いられました。公開鍵の正当性は、利用者同士が相互に署名し合う「**信頼の輪（Web of Trust）**」によって保証されます。

S/MIMEで暗号化・署名されたメールは、ヘッダの Content-Type で見分けられます。

```
暗号化されたメール
Content-Type: application/pkcs7-mime; smime-type=enveloped-data; name="smime.p7m"

署名付きのメール（本文は平文のまま読め、署名が別パートで添付される）
Content-Type: multipart/signed; protocol="application/pkcs7-signature"; micalg=sha-256
```

| 観点 | 区間の暗号化（SMTP over TLS、STARTTLS、POP3S、IMAPS） | エンドツーエンドの暗号化（S/MIME、PGP） |
|---|---|---|
| 暗号化の単位 | 通信路（サーバとサーバ、サーバとクライアントの間） | メールそのもの |
| サーバ上のメール | 平文 | 暗号化されたまま |
| 利用者の負担 | ほとんどない（サーバとMUAの設定だけ） | 送信者・受信者の双方が鍵や証明書を用意する必要がある |
| 送信者本人の証明 | できない（サーバやドメインの認証まで） | デジタル署名でできる |
| 注意点 | 経路上の1区間でも暗号化されなければ、その区間は平文 | 暗号化されたメールはサーバ側のウイルス検査やフィルタリングで中身を検査できない |

## 7. SMTPの脆弱性への対策（5）― MTAそのものを堅くする

最後に、2.5 と 2.6 で見たMTAの実装・設定の弱点への対策です。これは第5章 5.2 で学んだ「ホストの要塞化」を、メールサーバに当てはめたものです。

### 7.1 ⑪ MTAの不要なコマンドの無効化

メールサーバの管理者は、攻撃者に有効なメールアドレスを収集させないために、前述の **VRFY**、**EXPN** など、不要なコマンドを無効とするようにMTAを設定すべきです。Postfix なら `disable_vrfy_command = yes` を設定します。無効化したMTAは、次のように応答します。

```
VRFY taro
502 5.5.1 VRFY command is disabled
```

あわせて、存在しないあて先へのメールに対するエラー応答の違いからもアカウントの有無を推測できるため、短時間に大量の存在しないあて先を試す接続元を制限するなどの対策を組み合わせます。

### 7.2 ⑫ その他、MTAの実装面での対策

MTAの実装面では、次のような対策を実施します。

- MTAのバージョンを最新にし、パッチを適用する（2.6 のBOF攻撃などの既知の脆弱性を塞ぐため）
- **AVソフト**（ウイルス対策ソフト）を導入し、中継するメールに添付されたウイルスを駆除する
- インターネット上のSMTPサーバと社内LAN上のSMTPサーバとの間で相互にメールを中継する**中継専用メールサーバ**（**外向けSMTPサーバ**）を、**DMZ**上に設置する
- 外向けメールサーバと同じDMZセグメント上に**ゲートウェイ型AVサーバ**を設置し、メールに添付された不正なコードを駆除する
- MTAが出力する**バナー**（応答メッセージ）から、ソフトウェア名やバージョン情報を削除する

3つ目と4つ目は、ノート3.2 で学んだDMZの考え方をメールに当てはめたものです。インターネットから直接接続されるのはDMZの中継専用サーバだけにし、社内のメールサーバ（利用者のメールボックスがあるサーバ）には、DMZの中継サーバとゲートウェイ型AVサーバを経由したメールしか届かないようにします。

```
 インターネット ─ FW ─┬─ DMZ ─────────────────────────────────┐
                     │  [外向けSMTPサーバ（中継専用）] ⇔ [ゲートウェイ型AVサーバ] │
                     │                                          │
                     └─ 内部LAN ─ [社内メールサーバ（メールボックス）] ─ 利用者のPC
      ・インターネットからの25番ポートは、DMZの外向けSMTPサーバにだけ許可する
      ・社内メールサーバへのSMTPは、DMZの中継サーバからだけ許可する
```

外向けのSMTPサーバが侵害されても、そこには利用者のメールボックスがないので被害は限定され、社内メールサーバへの直接の攻撃経路もありません。

バナーの修正は、攻撃者に「どの脆弱性を狙えばよいか」を教えないための対策です。2.6 の例のバナーは、次のように製品名とバージョンを出さない形にします（Postfix なら `smtpd_banner = $myhostname ESMTP`）。

```
220 mail.example.co.jp ESMTP
```

ただし、バナーを隠しても脆弱性そのものが消えるわけではありません。攻撃者は応答の細かな違いから製品を推測することもできます。ノート3.3 で学んだとおり「隠すことによるセキュリティ」は根本対策ではないので、バナーの秘匿はパッチ適用の代わりではなく、あくまで補助的な対策です。

## 8. POP3の脆弱性

ここからは受信側（MRA → MUA）の区間に移ります。

**POP3**（Post Office Protocol Version 3）は、MUAがサーバからメールを受信するための代表的なプロトコルとして広く使用されています（**110/TCP**ポートを使用）。POP3では、メールの受信時にメールサーバとの間でユーザ認証を行う仕組みになっていますが、その仕様にはいくつかの脆弱性が指摘されています。

### 8.1 ① 認証情報が平文でネットワーク中を流れる

標準的なPOP3では、**USER/PASS**コマンドによってユーザ認証を行います。このとき、ユーザIDとパスワードが**平文**のままネットワーク中を流れます。そのため、経路上でのパケット盗聴によって認証情報が漏えいし、第三者にメールを不正に読まれたり、なりすましに悪用されたりする可能性があります。メールのパスワードは社内の他のシステムと共通であることも多いため、漏えいの影響はメールだけにとどまりません。

### 8.2 ② 受信データ（メール）が平文でネットワーク中を流れる

POP3では、認証情報だけでなく、メールの内容自体も平文のままネットワーク中を流れます。そのため、経路上でのパケット盗聴によってメールの内容が漏えいしたり、改ざんされたりする可能性があります。

POP3のやり取りを盗聴すると、次のように認証情報もメール本文もそのまま読めます（ノート3.3 で見たキャプチャ結果と同じものです）。

```
+OK POP3 server ready <1896.697170952@mail.example.co.jp>
USER taro
+OK
PASS secret123                         ← パスワードが平文（脆弱性①）
+OK taro has 2 messages (3120 octets)
RETR 1
+OK 1520 octets
From: suzuki@example.co.jp
Subject: 来期の価格改定案
（本文が平文で流れる）                ← メール内容も平文（脆弱性②）
```

## 9. POP3の脆弱性への対策

POP3の2つの脆弱性に対する4つの対策は、「何を守れるか」「どの区間を守れるか」で違いがあります。先に比較表を示します。

| 対策 | 認証情報を守れるか | メール本文を守れるか | 暗号化される区間 | 使用ポート |
|---|---|---|---|---|
| ① APOP | ○（チャレンジレスポンス） | ×（平文のまま） | ― | 110/TCP |
| ② POP3 over TLS（POP3S） | ○ | ○ | POP3サーバとMUAの間 | 995/TCP |
| ③ IMAP over TLS（IMAPS） | ○ | ○ | IMAPサーバとMUAの間 | 993/TCP |
| ④ SSHのポートフォワーディング | ○ | ○ | SSHサーバとMUA（SSHクライアント）の間 | 22/TCP |

### 9.1 ① APOPによるユーザ認証情報の秘匿化

**APOP**（Authenticated Post Office Protocol）は、メールサーバとMUAの間の認証で**チャレンジレスポンス方式**のユーザ認証を行い、認証情報が平文のままネットワーク中を流れるのを防ぎます。認証の流れは次のとおりです。

1. サーバからMUAに文字列（**チャレンジ**）が送られる
2. MUAは、チャレンジとパスワードを連結した文字列から、**MD5**を用いてメッセージダイジェストを生成する
3. MUAは、生成したメッセージダイジェストを**レスポンス**としてサーバに返す
4. サーバは、同じ計算を行った結果とレスポンスを照合して認証する

実際のやり取りは次のとおりです（利用者 taro、パスワード secret123 の場合）。

```
+OK POP3 server ready <1896.697170952@mail.example.co.jp>   ← 山括弧の中がチャレンジ（接続ごとに変わる）
APOP taro 4aa5dd4e19909f81228eed44b2548748
     ↑ MD5("<1896.697170952@mail.example.co.jp>" + "secret123") の値
+OK taro has 2 messages
```

パスワードそのものがネットワーク中を流れることはないため、認証プロセスが盗聴されても、パスワードをそのまま知られることはありません。また、チャレンジが接続ごとに変わるので、盗聴したレスポンスを後で再送しても認証は通りません（リプレイ攻撃への耐性）。ただし、APOPはあくまでも**認証情報だけを秘匿化**する方式です。APOPを用いても**メールそのものは平文のまま**ネットワーク中を流れるため、注意が必要です。

> **補足**
> APOPで用いられるMD5には衝突攻撃の脆弱性が指摘されています。そのため、中間者攻撃によってパスワードが解読されるおそれがあることが報告されています。現在では、POP3S（POP3 over TLS）やIMAPSの利用が推奨されます。

### 9.2 ②「POP3 over TLS」による認証情報とメールの暗号化

**POP3 over TLS** は、TLSを用いて、POP3通信（認証情報から受信するメールまですべて）を暗号化する方式です。ただし暗号化されるのは、あくまでも**直接通信するPOP3サーバとクライアント（MUA）の間の通信だけ**であるため、注意が必要です。送信者から自社のメールサーバまでの区間が暗号化されていたかどうかは、POP3Sでは保証されません（6章の図を参照）。

「POP3 over TLS（**POP3S**）」では、通常のPOP3（110/TCP）とは異なり、**995/TCP**ポートを使用します。

### 9.3 ③「IMAP over TLS（IMAPS）」による認証情報とメールの暗号化

**IMAP**（Internet Message Access Protocol）は、POP3と同じくクライアントがメールサーバからメールを読み出すためのプロトコルです。POP3がメールをクライアントに**ダウンロード**してクライアント上で管理するのに対し、IMAPは**サーバ上のメールボックス**でメールを管理します。そのため、複数の端末（PCやスマートフォンなど）から同じメールボックスを参照できます。

**IMAPS** は、TLSを用いてIMAP通信（認証情報からメール本文まですべて）を暗号化する方式です。スマートフォンやPCなど複数の端末から同じメールボックスを使う利用形態が一般的になったことから、IMAPSは電子メールの受信プロトコルとして広く使われています。なお、IMAPSは **993/TCP**ポートを使用します（通常のIMAPは **143/TCP**）。

以前は「Microsoft 365 などのクラウドメールサービスの普及に伴い、そうした環境と親和性の高い IMAPS が広く使われている」と説明されることがありました。しかし実際には、Microsoft 365 や Google Workspace などのクラウドメールでは、Webブラウザや専用のアプリケーション（HTTPS上の独自の通信方式）での利用が中心です。IMAP・POP・SMTPで接続する場合も、IDとパスワードだけで認証する方式（基本認証）は廃止・制限され、OAuth 2.0 による認証が求められる方向にあります。パスワードが漏えいしても、それだけではメールボックスに入れないようにするためです。

### 9.4 ④ SSHのポートフォワーディング機能による認証情報とメールの暗号化

**SSH**（Secure SHell）の**ポートフォワーディング**機能を用いて、POP3通信（認証情報から受信するメールまですべて）を暗号化する方式です。ただし「POP3S」と同様に、暗号化されるのはあくまでも直接通信するPOP3サーバとクライアント（MUA）の間の通信だけであるため、注意が必要です。

SSHのポートフォワーディング機能とは、暗号化機能を備えていないアプリケーションの通信を、SSHが間に入って中継し、暗号化するものです。この機能を用いると、POP3やFTPをはじめ、通信データの暗号化機能を備えていないアプリケーションの通信を暗号化できます。

```
 利用者のPCで実行するコマンドの例
$ ssh -L 10110:mail.example.co.jp:110 taro@gw.example.co.jp
  → 自分のPCの 10110番ポートへの接続を、SSHで暗号化して gw.example.co.jp まで運び、
    そこから mail.example.co.jp の 110番ポート（POP3）へ中継する

 MUAの受信サーバの設定
  サーバ: localhost   ポート: 10110   （MUAは自分のPCに接続しているつもりで動く）

 [MUA] → localhost:10110 ═══ SSH（22/TCP、暗号化）═══ [gw.example.co.jp] ── 110/TCP ── [POPサーバ]
                                                      （社内の短い区間は平文）
```

SSHのポートフォワーディング機能を用いた場合は、通常のPOP3とは異なり、**22/TCP**ポートを使用します。そのため、インターネット側からファイアウォールを介してSSHで社内のPOP3サーバからメールを受信するには、SSHの設定に加えて、22/TCPの通信を許可するようにファイアウォールを設定する必要があります。この場合、SSHサーバは社外からログインを試みられる対象になるため、パスワード認証ではなく公開鍵認証にするなど、SSHサーバ自体の防御も必要になります。

**表：電子メール関連プロトコルと使用ポート番号**

| プロトコル | ポート番号 | 用途・暗号化 |
| --- | --- | --- |
| SMTP | 25/TCP | MTA間の中継（STARTTLSにより暗号化可能） |
| Submission | 587/TCP | MUAからMSAへの投稿（SMTP-AUTH、STARTTLS） |
| SMTPS（SMTP over TLS） | 465/TCP | 投稿時の暗号化（暗黙的TLS） |
| POP3 | 110/TCP | メール受信（平文） |
| POP3S（POP3 over TLS） | 995/TCP | メール受信（暗号化） |
| IMAP | 143/TCP | メール受信・サーバ上での管理（平文） |
| IMAPS（IMAP over TLS） | 993/TCP | メール受信・サーバ上での管理（暗号化） |
| SSH（ポートフォワーディング） | 22/TCP | 任意のアプリケーション通信の暗号化 |

- **Q2**：メールの第三者中継を防止する方法としては何が有効か。
- **Q3**：OP25Bの必要性と仕組みについて挙げよ。
- **Q4**：Submissionポートによるメール投稿の必要性と仕組みについて挙げよ。
- **Q5**：送信ドメイン認証によって何が可能となるのか。
- **Q6**：IPアドレスによる送信ドメイン認証とデジタル署名による送信ドメイン認証の特徴を挙げよ。

> **解答の要点**
> - Q1：旧バージョンのメールサーバソフトウェアで、投稿と中継が同じ仕組み（25番ポート）で行われていたこと、投稿時にユーザを認証する仕組みがなかったこと。これにより第三者中継や送信元の詐称が可能になった。

> - Q4：OP25Bの環境でも、正当な利用者が外部（自社など）のメールサーバから送信できるようにするため。MTAの機能をMSAとMTAに分離し、MSAは587番ポートで投稿を受け付け、SMTP-AUTHで利用者を認証する。TLSで暗号化することもできる。
> - Q5：受信側で、送信元のIPアドレスやデジタル署名を使って送信元SMTPサーバ（送信ドメイン）の正当性を確認し、送信元を詐称したメールを検知・排除できる。
> - Q6：IPアドレスによる方式（SPF）は、DNSへの登録だけで導入でき負荷も小さいが、転送されたメールの検証が困難で、Envelope-Fromしか検証しない。デジタル署名による方式（DKIM）は、転送されたメールも検証でき改ざんも検知できるが、送受信双方の対応と署名処理の負荷が必要で、経路上で内容が変わるメールは検証が困難。
> - Q7：SPFやDKIMの認証結果とHeader-Fromのドメインとの整合性を検証し、認証に失敗したメールの取扱いポリシ（none／quarantine／reject）を送信側がDNSのTXTレコードで表明する仕組み。受信側から送信側へ認証結果のレポートを送る機能もある。
> - Q8：平文で通信を始め、STARTTLSコマンドで明示的にTLSによる暗号化に切り替える方式。主にメールサーバ間（25番ポート）で使い、587番の投稿でも使える。相手が非対応なら平文にフォールバックするため、STARTTLSストリッピングに注意が必要（MTA-STS、DANEで対策）。
> - Q9：USER/PASSによる認証情報が平文で流れること、メールの内容も平文で流れること。
> - Q10：POP3S（995番）、IMAPS（993番）、SSHのポートフォワーディング（22番）。APOPは認証情報だけを守り、本文は平文のままなので不十分。

### 10.2 過去問題1：SPFの導入時に必要な設定

SPFによるドメイン認証を実施する場合、SPFの導入時に、電子メール送信元アドレスのドメイン所有者側で行う必要がある設定はどれか。

ア　DNSサーバにSPFレコードを登録する。
イ　DNSの問合せを受け付けるポート番号を変更する。
ウ　メールサーバにデジタル証明書を導入する。
エ　メールサーバのTCPポート25番を利用不可にする。

*［情報処理安全確保支援士試験・R4秋・午前Ⅱ問15］*

> **解答・解説**
> SPF（Sender Policy Framework）は、電子メールの送信元ドメインのDNSサーバにあらかじめ正当なSMTPサーバのIPアドレス（SPFレコード）を登録しておくことにより、送信元を詐称した電子メールを拒否する仕組みである。
>
> 電子メールを受信したSMTPサーバは、送信元のDNSサーバに問い合わせ、エンベロープ（SMTPプロトコルのMAIL FROM）のメールアドレスのドメインと送信サーバのIPアドレスの適合性を検証する。その結果、送信元のSMTPサーバの正当性が確認された場合のみメールを受け入れ、それ以外のメールは排除する。したがって、**ア**が正解である。
>
> なお、ウのデジタル証明書（公開鍵の登録）はDKIMやS/MIMEに関係する設定であり、SPFでは不要である。

### 10.3 過去問題2：IP25B

インターネットサービスプロバイダ（ISP）が、スパムメール対策として導入するIP25Bに該当するものはどれか。

ア　自社ISPのネットワークの動的IPアドレスから他社ISPの管理するメールサーバへのSMTP通信を制限する。
イ　自社ISPのメールサーバで受信した電子メールのうち、スパムメールのシグネチャに一致する電子メールを隔離する。
ウ　他社ISPのネットワークの動的IPアドレスから自社ISPのメールサーバへのSMTP通信を制限する。
エ　他社ISPのメール不正中継の脆弱性をもつメールサーバから自社ISPのメールサーバに送信された電子メールを隔離する。

*［情報処理安全確保支援士試験・R2秋・午前Ⅱ問17］*

> **解答・解説**
> IP25B（Inbound Port 25 Blocking）は、ISPが、他社ISPのネットワークの動的IPアドレスから自社ISP内のメールサーバへのSMTP通信をブロックする方法である。したがって、**ウ**が正解である。
>
> なお、アはOP25B（Outbound Port 25 Blocking）の説明である。本ノート3.5 の比較表で「方向」を確認しておくこと。

### 10.4 過去問題3：DKIM

DKIM（DomainKeys Identified Mail）の説明はどれか。

ア　送信側メールサーバにおいてデジタル署名を電子メールのヘッダに付加し、受信側メールサーバにおいてそのデジタル署名を公開鍵によって検証する仕組み
イ　送信側メールサーバにおいて利用者が認証された場合、電子メールの送信が許可される仕組み
ウ　電子メールのヘッダや配送経路の情報から得られる送信元情報を用いて、メール送信元のIPアドレスを検証する仕組み
エ　ネットワーク機器において、内部ネットワークから外部のメールサーバのTCPポート番号25への直接の通信を禁止する仕組み

*［情報処理安全確保支援士試験・R5春・午前Ⅱ問15］*

> **解答・解説**
> DKIMは、送信側SMTPサーバがメールヘッダに付与したデジタル署名を受信側SMTPサーバで検証することによって、送信元の正当性を確認する仕組みである。そのため、あらかじめ送信側ドメインのDNSサーバに正当なメールサーバの公開鍵を登録しておく必要がある。したがって、**ア**が正解である。
>
> - イ　SMTP-AUTHの説明である。
> - ウ　SPF（Sender Policy Framework）の説明である。
> - エ　OP25B（Outbound Port 25 Blocking）の説明である。

### 10.5 過去問題4：メール本文を含めて暗号化する受信プロトコル

電子メールをスマートフォンのメールアプリケーションプログラムで受信する際のメールサーバとスマートフォンとの間の通信を、メール本文を含めて暗号化するプロトコルはどれか。

ア　APOP
イ　IMAPS
ウ　POP3
エ　SMTP Submission

*［情報処理安全確保支援士試験・R5秋・午前Ⅱ問16］*

> **解答・解説**
> 問題文に該当するのはIMAPS（Internet Message Access Protocol over TLS）であり、**イ**が正解である。
>
> IMAPはクライアントがメールサーバからメールを読み出すためのプロトコルだが、同じ目的で広く利用されているPOP3がクライアント上でメールを管理するのに対し、サーバ上のメールボックスでメールを管理する。
>
> TLS（Transport Layer Security）には、デジタル証明書によるサーバ認証機能、クライアント認証機能に加え、アプリケーション層とトランスポート層（TCP層）の間で通信データを暗号化する機能がある。TLSは、HTTPをはじめ、SMTP、FTP、Telnet、POP3、IMAP4など、多くのTCPアプリケーションに対応している。
>
> - ア　APOPでは認証情報のみが暗号化される（正確には、パスワードそのものを流さずにチャレンジレスポンスで認証するだけで、メール本文は平文のまま）。
> - ウ　POP3では認証情報もメール本文も平文で通信経路上を流れる。
> - エ　SMTP Submissionはメール投稿（送信）時に用いるプロトコルであり、暗号化の仕組みは実装されていない（STARTTLSと組み合わせれば投稿の通信を暗号化できるが、そもそも受信のためのプロトコルではない）。

### 10.6 過去問題5：OP25Bの目的

インターネットサービスプロバイダ（ISP）が、OP25Bを導入する目的の一つはどれか。

ア　ISP管理外のネットワークに対するISP管理下のネットワークからのICMPパケットによるDDoS攻撃を遮断する。
イ　ISP管理外のネットワークに向けてISP管理下のネットワークから送信されるスパムメールを制限する。
ウ　ISP管理下のネットワークに対するISP管理外のネットワークからのICMPパケットによるDDoS攻撃を遮断する。
エ　ISP管理下のネットワークに向けてISP管理外のネットワークから送信されるスパムメールを制限する。

*［情報処理安全確保支援士試験・R5春・午前Ⅱ問16］*

> **解答・解説**
> OP25B（Outbound Port 25 Blocking）とは、ISPが動的IPアドレスを割り当てた（ISP管理下の）ネットワークから、当該ISPのメールサーバを経由せずに、ISP管理外のネットワーク（外向き）に直接出ていく25番ポートあてのパケット（SMTP）を遮断する方式である。このようなパケットは、ISP管理外のネットワークに向けたスパムメールである可能性が高い。したがって、**イ**が正解である。
>
> なお、エは IP25B の目的に近い。

### 10.7 過去問題6：サブミッションポート

TCPのサブミッションポート（ポート番号587）の説明として、適切なものはどれか。

ア　FTPサービスで、制御用コネクションのポート番号21とは別にデータ転送用に使用する。
イ　Webサービスで、ポート番号80のHTTP要求とは別に、サブミットボタンをクリックした際の入力フォームのデータ送信に使用する。
ウ　コマンド操作の遠隔ログインで、通信内容を暗号化するためにTELNETのポート番号23の代わりに使用する。
エ　電子メールサービスで、迷惑メール対策などのためにSMTPのポート番号25の代わりに使用する。

*［情報処理安全確保支援士試験・R6春・午前Ⅱ問19］*

> **解答・解説**
> サブミッションポートは、スパムメール対策としてSMTPポートの代わりに投稿専用のポートとして使用する。
>
> ボットなどが迷惑メールを送信する際に、ISP（Internet Services Provider）のメールサーバを経由せず、直接送信先のメールサーバの25番ポートに接続してSMTPコネクションを確立する手口が用いられたため、これをOP25B（Outbound Port 25 Blocking）によって遮断する対策が行われるようになった。
>
> OP25Bとは、ISPが動的IPアドレスを割り当てたネットワークから、当該ISPのメールサーバを経由せずに、ISP管理外のネットワーク（外向き）に直接出ていく25番ポートあてのパケット（SMTP）を遮断する方式である。
>
> OP25Bが設定されている環境で正当な利用者が自社のメールサーバなどと直接SMTPコネクションを確立してメールを送信する必要がある場合には、25番ポートではなくサブミッションポートを使用する必要がある。
>
> サブミッションポートへアクセスしてきたメール送信者をSMTP-AUTHによって認証することで、ボットなどからの投稿を受け付けないようにするほか、TLSによって通信を秘匿化することも可能である（Submission over TLS）。したがって、**エ**が正解である。
>
> なお、アのFTPのデータ転送用は20番、ウのTELNETの代わりに使う暗号化された遠隔ログインはSSHの22番である。

### 10.8 過去問題7：SMTP-AUTH

SMTP-AUTHの特徴はどれか。

ア　ISP管理下の動的IPアドレスから管理外ネットワークのメールサーバへのSMTP接続を禁止する。
イ　電子メール送信元のメールサーバが送信元ドメインのDNSに登録されていることを確認してから、電子メールを受信する。
ウ　メールクライアントからメールサーバへの電子メール送信時に、利用者IDとパスワードによる利用者認証を行う。
エ　メールクライアントからメールサーバへの電子メール送信は、POP接続で利用者認証済みの場合にだけ許可する。

*［情報処理安全確保支援士試験・R4秋・午前Ⅱ問14］*

> **解答・解説**
> SMTP-AUTHは、SMTPにユーザ認証機能を追加した方式であり、クライアントがSMTPサーバにアクセスしたときにユーザアカウントとパスワードによる利用者認証を行うことで、許可された利用者だけから電子メールの送信を受け付ける。したがって、**ウ**が正解である。
>
> - ア　OP25B（Outbound Port 25 Blocking）の説明である。
> - イ　SPF（Sender Policy Framework）の説明である。
> - エ　POP before SMTPの説明である。
>
> 過去問題3・5・7はいずれも、SMTP-AUTH／SPF／DKIM／OP25B／POP before SMTP の説明を並べて1つを選ばせる形式である。「誰が（送信側／受信側／ISP）」「何を使って（パスワード／IPアドレス／署名／ポート遮断）」確認するかで区別できるようにしておくこと。

## 11. 試験対策まとめ（重要ポイント）

### 11.1 知識の確認（科目A-2向け）

- **スパムが横行した原因**：旧MTAでは投稿と中継が同じ25番ポートで区別できず、投稿時の認証もなかった。
- **第三者中継（オープンリレー）**：送信元・あて先のいずれも自サイトと無関係なメールを中継すること。踏み台にされ、ブラックリスト（DNSBL／RBL）に登録されると正規のメールも届かなくなる。
- **NDRスパム（バックスキャッタ）**：送信元を被害者に詐称し、配送不能のメールを送ってNDRを被害者に送らせる。対策は受信時点で存在しないあて先を拒否すること。
- **VRFY／EXPN**：アカウントの有無、エイリアスやメーリングリストの配送先を確認できる。アカウントの列挙に悪用されるため無効化する。
- **SMTP-AUTH**：SMTPに利用者認証を追加（RFC 4954）。SASLに基づく。PLAIN・LOGINはBase64で平文同然なのでTLSと併用する。CRAM-MD5はチャレンジレスポンス。
- **POP before SMTP**：POP3の認証に成功したIPアドレスから一定時間だけ送信を許可。認証情報が平文になりうる、同じIPアドレスを共有する別人も送れる、が弱点。
- **OP25B と IP25B**：OP25Bは自社ISPの動的IPアドレスから外部の25番への通信を遮断（送らせない）。IP25Bは他社ISPの動的IPアドレスから自社のメールサーバへの25番を遮断（受け取らない）。
- **サブミッションポート**：587番。MSAとMTAを分離し、SMTP-AUTHで認証。465番は暗黙的TLS（SMTPS）。
- **SPF**：送信元ドメインのDNSのTXTレコードに正当なSMTPサーバのIPアドレスを登録。受信側はEnvelope-From（MAIL FROM）のドメインと接続元IPアドレスを照合。導入は容易だが転送に弱い。`-all`＝fail、`~all`＝softfail。
- **Sender ID**：SPF＋ヘッダ（From:、Sender:）の検証。
- **DKIM**：送信側サーバが秘密鍵で署名（DKIM-Signature: ヘッダ）、受信側がDNSの公開鍵で検証（RFC 6376）。転送に強く改ざんも検知できるが、メーリングリストなど内容が変わると失敗する。DomainKeys＋IIMを統合。
- **SPF・DKIMの限界**：攻撃者が自分のドメインで認証を通し、Header-Fromだけを詐称すると検出できない。
- **DMARC**：SPF・DKIMの結果とHeader-Fromの整合性（アライメント）を検証。ポリシは `_dmarc.ドメイン名` のTXTレコードのpタグ（none／quarantine／reject）。rua＝集計レポート、ruf＝失敗レポート（RFC 7489）。
- **ベイジアンフィルタリング**：ベイズの定理で迷惑メールの特徴を自己学習し、統計的に判定。学習量が増えるほど精度が上がる。
- **SMTP over TLS と STARTTLS**：接続時から暗号化（暗黙的、465番）か、平文で始めてSTARTTLSで切り替える（明示的、25番・587番）か。STARTTLSはフォールバックを突くストリッピングに注意（MTA-STS、DANE）。
- **S/MIME と PGP**：エンドツーエンドの暗号化と署名。公開鍵の正当性はS/MIMEが認証局（CA）、PGPが信頼の輪（Web of Trust）。
- **MTAの堅牢化**：パッチ適用、AV、DMZに中継専用の外向けSMTPサーバとゲートウェイ型AVサーバ、バナーからのバージョン情報の削除。
- **POP3の脆弱性と対策**：認証情報も本文も平文。APOPは認証情報だけを守る（MD5の弱さから非推奨）。本文まで守るのはPOP3S（995）、IMAPS（993）、SSHポートフォワーディング（22）。いずれも暗号化されるのはサーバとMUAの間だけ。
- **ポート番号**：25（SMTP）、587（Submission）、465（SMTPS）、110（POP3）、995（POP3S）、143（IMAP）、993（IMAPS）、22（SSH）。

### 11.2 記述式で問われる観点（科目B向け）

- **なりすましメールが届いた原因の説明**：メールヘッダの Authentication-Results から「SPFは攻撃者のドメインで pass しているが、Header-Fromのドメインと整合せずDMARCが fail になっている。送信側のDMARCポリシが none だったため受信側で拒否されなかった」のように、どの仕組みがなぜ効かなかったかを説明する。
- **送信側として行うべき設定**：自社ドメインを詐称されないために、「全送信経路をSPFレコードに登録する」「DKIMで署名する」「DMARCレコードを登録し、レポートで正規の経路を確認してから p=quarantine／reject に強める」「メールを送信しないドメインにも v=spf1 -all を登録する」と、順序も含めて提案する。
- **外部のメール配信サービスを使うときの注意**：配信サービスのサーバをSPFに include し、配信サービスに自社ドメインでDKIM署名させないと、DMARCで正規のメールが fail になることを指摘する。
- **踏み台にされないための設定**：MTAの中継制限（自組織のネットワークか認証済みの利用者だけに中継を許可する）、受信時点での存在しないあて先の拒否（NDRスパム対策）、VRFY・EXPNの無効化を、それぞれ防ぐ攻撃とともに述べる。
- **テレワーク時の送受信の設計**：OP25Bの環境では25番で送れないため、587番（または465番）でSMTP-AUTHとTLSを使って投稿させ、受信はPOP3SかIMAPSにする、と理由付きで提案する。APOPでは本文が守れないことも指摘する。
- **暗号化の範囲の説明**：「SMTP over TLS やPOP3Sで守られるのはMUAとサーバの間だけで、サーバ上や他の区間では平文になりうる。送信者から受信者まで秘匿するにはS/MIMEなどのエンドツーエンドの暗号化が必要」と、区間と範囲を区別して書く。
- **利用者への教育**：DMARCで防げない類似ドメインからのフィッシングに対して、差出人のアドレスとURLのドメインを確認する、メール内のリンクではなくブックマークから公式サイトにアクセスする、といった利用者の行動面の対策を併せて提案する。
