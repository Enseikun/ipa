# レクチャーノート：情報セキュリティに関する法制度 ― 9.1 情報セキュリティ及びITサービスに関する規格と制度

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「セキュリティ技術評価」（知識項目例：ISO/IEC 15408（コモンクライテリア），JISEC，JCMVP ほか）、「情報セキュリティ管理」（知識項目例：ISMS，PCI DSS ほか）、「企業と法務」＞「法務」（知識項目例：標準化関連〈JIS，ISO，IEEE，国際認証の枠組み，JIS Q 15001，ISO 9000，ISO 14000〉ほか）

## 0. 全体像 ― なぜこの分野を学ぶのか

第1〜8章では、情報セキュリティを「技術」と「マネジメント」の両面から学んできました。第1章 1.3 では ISMS を、第4章ではリスクアセスメント・ポリシ・監査といったマネジメントの実務を、第5〜8章では対策技術を扱いました。しかし、組織が「どこまでやれば十分か」「自社の対策が十分であることを、取引先や社会にどう示すか」という問いには、技術やマネジメントの知識だけでは答えられません。この問いに答えるのが、最後の第9章で扱う**法制度**と**規格・認証制度**です。

### 0.2 規格・法律・ガイドラインの違い

第9章では「法律」「ガイドライン」「規格」という言葉が繰り返し登場します。この3つは、**誰が定め、誰が守り、守らなかったら何が起きるか**がまったく異なります。科目A-2では「〜は法的拘束力をもつ」「〜は任意である」といった記述の正誤が問われ、科目Bでは「この対策は法令上の義務か、規格上の要求か」を区別して書く必要があるため、最初に整理しておきます。

| 観点 | 法律（法令） | ガイドライン | 規格（標準） | 業界基準・契約上の基準 |
|---|---|---|---|---|
| 誰が定めるか | 国会（法律）、内閣（政令）、各省庁・委員会（省令・規則） | 省庁、個人情報保護委員会、IPA などの公的機関、業界団体 | 国際標準化機関（ISO、IEC）、国の標準化機関（日本では JISC の審議を経て主務大臣が JIS を制定） | 業界団体（例：PCI SSC） |
| 誰が守るか | 対象となるすべての者（事業者、個人） | 法律の対象者や、指針を採用する組織 | 自ら採用を決めた組織 | 契約を結んだ組織（例：カード加盟店） |
| 強制力 | **あり**（違反すると罰則、行政処分、損害賠償） | **原則なし**。ただし法律の解釈を示すガイドラインは、従わないと法違反と判断され得る | **なし**（任意）。ただし契約・調達要件・認証の条件になると事実上守らざるを得ない | 契約による拘束（違反すると契約解除、取引停止、違約金） |
| 違反の結果 | 刑事罰、行政指導・命令、民事責任 | 監督官庁からの指導の根拠になる、社会的信用の低下 | 認証の取消し、取引条件を満たせない | 取引の停止、ペナルティ |
| 例 | 個人情報保護法、不正アクセス禁止法 | 個人情報保護法ガイドライン、サイバーセキュリティ経営ガイドライン | ISO/IEC 27001、JIS Q 15001、ISO/IEC 15408 | PCI DSS |

ポイントは、**規格そのものには法的な強制力がない**ことです。組織が規格を守るのは、法律で命じられているからではなく、「認証を取得して取引先に示したい」「政府調達の条件を満たしたい」「業界の契約で求められている」からです。逆に、個人情報保護委員会のガイドラインのように法律の解釈を示すものは、「しなければならない」と書かれた事項に従わないと法違反と判断され得るため、単なる努力目標と考えてはいけません。

> **JIS の名称の変更**
> 以前は「日本工業規格」（根拠法は工業標準化法）と呼ばれていましたが、2019年7月の法改正で、現在は「**日本産業規格**」（根拠法は産業標準化法）に改められています。略称の JIS（Japanese Industrial Standards）は変わりません。データやサービスなども標準化の対象に加えるための改正です。

### 0.3 本ノートのストーリーと章立て

本ノートは、規格と認証制度を「誰が、何を、何のために評価するのか」という切り口で整理します。

1. **なぜ規格と制度が必要になったか**：対策がベンダー任せだった時代の反省と、規格番号の読み方、主な規格の一覧（本ノート1節）
2. **認証の仕組み**：認定機関→認証機関→組織という三層構造、主な認証制度の比較、取得までの流れ（本ノート2節）
3. **製品を評価する規格**：ISO/IEC 15408（コモンクライテリア）と JISEC、暗号モジュールの JCMVP（本ノート3節）
4. **組織の能力を評価するモデル**：CMMI と SSE-CMM（本ノート4節）
5. **業界・分野ごとの基準**：PCI DSS（クレジットカード）、ISO/IEC 20000 と ITIL（ITサービス）、EDSA（制御機器）（本ノート5〜7節）
6. **リスク管理の枠組み**：NIST サイバーセキュリティフレームワーク（本ノート8節）

科目Bの業務観点では、「①情報セキュリティマネジメントの推進又は支援」（規程の策定、監査、動向の収集）と「③利用におけるセキュリティ対策の適用」（サプライチェーン、コンプライアンス管理）に対応します。とくに委託先や製品を選ぶ場面で「どの認証を確認すれば何がわかるか」を問う設問の判断材料になります。科目A-2では、ISO/IEC 15408 の ST・PP・EAL、CMMI の成熟度レベル、PCI DSS の要件、NIST CSF の機能（CSF 2.0 では6つ）が単独で出題されます。

## 1. なぜ規格と制度が必要になったのか

### 1.1 背景 ― 「ベンダー任せ」からの脱却

インターネットやPCが企業等に広く普及し始めた当時、多くの組織はファイアウォールを設置したり、AVツールを導入したりするなど、セキュリティ対策に取り組み始めました。しかし、その実態は次のようなものでした。

- 組織は、セキュリティ対策をすべてシステムを構築しているベンダー任せにしていた。
- 情報システム部門は、インターネット接続環境での対策のみを実施していた。

> **用語解説：AVツール**
> Anti-Virus（アンチウイルス）ツールの略。コンピュータウイルスなどのマルウェアを検知・駆除するソフトウェアを指す。

この結果、組織はインターネットなど外部からのサイバー攻撃を防ぐことについては、ある程度の成果を上げました。しかし近年は、対策を行っていたにもかかわらず、悪質なマルウェア、内部犯行、管理不備、設定ミス、操作ミスなどによって、重要情報の破壊、漏えい、紛失などの事件が頻発しています。業務の中断、信用の失墜、損害賠償にまで至るケースも出てきました。境界のファイアウォールは、内部犯行や設定ミスを防げないからです（第1章 1.7 のゼロトラストの発想につながる反省です）。

こうした問題への対策として、組織全体で、技術的な対策にとどまらず、技術面と運用管理面を含めた**総合的かつ継続的な情報セキュリティ対策**に取り組もうという動きが盛んになりました。組織の情報セキュリティ対策への取組み状況が顧客や社会から問われるようになる一方で、組織の側には次のような疑問が生じました。

- 一体どこまで対策を実施すればよいのか。
- 自社の情報セキュリティの水準は、同業他社や世間一般と比較してどの程度なのか。

そこで、組織やシステムの情報セキュリティの水準を**客観的に評価するための基準や制度**が必要になりました。基準（規格）があれば、組織は「どこまでやればよいか」の目安を得られます。第三者がその基準で評価する制度（認証制度）があれば、組織は「自社は基準を満たしている」と取引先に示せますし、取引先は相手の水準を自分で一から調べなくても判断できます。規格は「物差し」、認証制度は「物差しで測った結果の証明書」だと考えるとわかりやすいでしょう。

### 1.2 規格番号の読み方

規格は番号で呼ばれます。番号の読み方がわかると、一覧表を眺めたときに「これは国際規格か国内規格か」「何年版か」「何部構成のどの部か」がすぐに読み取れます。

```
  ISO/IEC 27001:2022            JIS Q 27001:2023
  ─┬──── ──┬── ─┬─            ─┬─ ┬ ──┬── ─┬─
   │        │    └ 発行年        │  │   │    └ 発行年（JIS化した年）
   │        └ 規格番号           │  │   └ 規格番号（国際規格と同じ番号にそろえることが多い）
   └ 策定した機関                 │  └ 部門記号（Q＝管理システム）
     （ISO と IEC の共同）         └ 日本産業規格

  ISO/IEC 15408-3:2022         ISO/IEC TS 20000-5:2022
                ┬                        ┬
                └ 部（Part）の番号        └ TS＝技術仕様書（Technical Specification）
                  （第3部）                 ※TR＝技術報告書（Technical Report）
```

> **JIS規格の番号**
> JIS規格の番号では、「JIS」と数字の間にあるアルファベットが部門を表す。例えば「X」は情報処理、「Q」は管理システムの部門を示す。

**ISO/IEC 27001 と JIS Q 27001 の関係**は、試験でも実務でも必ず押さえておくべき点です。国際規格の ISO/IEC 27001 を、日本の標準化機関が日本語に翻訳し、技術的内容を変えずに国内規格として発行したものが JIS Q 27001 です（このように内容が一致する JIS を「一致規格」と呼びます）。翻訳と審議に時間がかかるため、JIS の発行年は国際規格より1〜2年遅れるのが普通です（ISO/IEC 27001:2022 → JIS Q 27001:2023）。ISMS の認証審査は「JIS Q 27001（ISO/IEC 27001）に適合しているか」で行われ、どちらで認証しても同じ内容を満たしていることになります。

一方、国際規格のすべてが JIS 化されているわけではありません。下の一覧表で国内規格番号が「―」になっているものは、組織が英語版（または翻訳版）の国際規格をそのまま参照します。また、JIS 化された時点の版が古いまま残っている場合もあります。たとえば ISO/IEC 27014 は2020年版が最新ですが、JIS Q 27014:2015 は旧版（2013年版）に対応しています。

### 1.3 規格ファミリーの一覧

規格は単独ではなく、同じ番号帯でまとまった「**ファミリー**」として作られます。ファミリーの中には、認証の基準となる「**要求事項**」（〜しなければならない）の規格と、それを実践するための「**手引・指針**」（〜することが望ましい）の規格があります。認証審査で使われるのは要求事項の規格だけです。この区別は、第1章 1.3 で学んだ「27001 は要求事項、27002 は管理策のガイドライン」と同じ構造です。

## 2. 認証の仕組み ― 誰が誰を評価するのか

### 2.1 認定と認証の三層構造

規格に適合していることを組織が自分で「適合しています」と宣言しても、取引先はそれを信用しきれません。そこで、利害関係のない第三者が審査する**認証制度**が作られました。ところが、その第三者（認証機関）の審査がずさんだったら、認証の価値はなくなります。そこで、認証機関そのものを審査する**認定機関**が置かれています。第1章 1.3 で見た「認定機関が認証機関を**認定**し、認証機関が組織を**認証**する」という二段構えは、ISMS に限らず多くの制度に共通する構造です。

```
  ┌──────────────────────┐
  │ 認定機関                │  例：ISMS-AC（ISMS・ITSMS・BCMS）
  │ 「審査する人を審査する」  │      IAJapan（JISEC の評価機関・JCMVP の試験機関）
  └───────────┬──────────┘
              │ 認定（Accreditation）：審査能力があると認める
              ▼
  ┌──────────────────────┐
  │ 認証機関（審査登録機関）  │  例：ISMS の審査登録機関、
  │ ／評価機関・試験機関      │      JISEC の評価機関（評価）と IPA（認証）
  └───────────┬──────────┘
              │ 認証（Certification）：規格に適合していると証明する
              ▼
  ┌──────────────────────┐
  │ 組織・製品               │  登録証・認証書・マークを取得
  └───────────┬──────────┘
              │ 提示・公開リストへの掲載
              ▼
  ┌──────────────────────┐
  │ 取引先・顧客・調達者      │  登録証の「適用範囲」「有効期限」を確認して判断
  └──────────────────────┘
```

「認定」と「認証」は字面が似ていますが、対象が違います。**認定**の対象は認証機関（審査する側）、**認証**の対象は組織や製品（審査される側）です。科目A-2では、この2語を入れ替えた誤り選択肢がよく出ます。

### 2.2 主な認証・評価制度の比較

規格と制度は数が多く、混同しやすい分野です。そこで、主な制度を「何を対象に、誰が評価し、何を保証するか」で横並びにします。最も大切なのは**評価対象が組織（マネジメントの仕組み）なのか、製品なのか、サービスなのか**という区別です。

| 制度 | 基準となる規格 | 評価の対象 | 誰が評価・認証するか | 何を保証するか | 何を保証しないか |
|---|---|---|---|---|---|
| **ISMS適合性評価制度**（ISMS認証） | JIS Q 27001（ISO/IEC 27001） | 組織の ISMS（**適用範囲**を部門・拠点・業務単位で限定できる） | ISMS-AC が認定した認証機関 | 適用範囲内で、リスクに基づいて管理策を選び、PDCA を回す仕組みが規格どおり運用されていること | 事故が起きないこと、適用範囲外の部門の管理 |
| **プライバシーマーク制度** | JIS Q 15001 | 事業者の個人情報保護マネジメントシステム（原則として**法人単位**、全社） | JIPDEC（付与機関）と指定審査機関 | 個人情報を JIS Q 15001 に沿って適切に取り扱う体制が全社で整っていること | 情報セキュリティ全般、個人情報以外の情報資産の管理 |
| **ISMAP**（政府情報システムのためのセキュリティ評価制度） | ISMAP 管理基準（JIS Q 27001・27002・27017 などを基に策定） | **クラウドサービス** | ISMAP に登録された監査機関が監査し、制度の運営主体が審査・登録 | 政府が求めるセキュリティ要求を満たすクラウドサービスであること | 利用者側の設定・運用の適切さ |
| **JISEC**（ITセキュリティ評価及び認証制度） | ISO/IEC 15408（CC）、ISO/IEC 18045（CEM） | IT**製品**・システム（TOE） | IAJapan が認定した評価機関が評価し、IPA が認証 | 出荷時点で、ST に書かれたセキュリティ機能が、選んだ保証レベル（EAL など）で正しく実装されていること | 導入後の運用の適切さ |
| **JCMVP**（暗号モジュール試験及び認証制度） | ISO/IEC 19790（JIS X 19790）、ISO/IEC 24759 | **暗号モジュール**（暗号機能を実装したハードウェア・ソフトウェア） | IAJapan が認定した試験機関が試験し、IPA が認証 | 承認された暗号アルゴリズムが正しく実装され、鍵などの重要情報が保護されていること | 暗号モジュールを組み込んだ製品全体の安全性 |
| **ITSMS適合性評価制度** | JIS Q 20000-1（ISO/IEC 20000-1） | ITサービスを提供する組織のサービスマネジメントシステム | ISMS-AC が認定した認証機関 | 顧客の求めるサービス品質を維持・改善する仕組みがあること | 個々のサービスの性能 |
| **BCMS適合性評価制度** | JIS Q 22301（ISO 22301） | 組織の事業継続マネジメントシステム | ISMS-AC が認定した認証機関 | 事業継続計画を策定・訓練・見直す仕組みがあること | 災害時に必ず業務が継続できること |
| **PCI DSS 準拠** | PCI DSS | カード会員データを扱う組織の環境 | QSA（訪問審査）、ASV（脆弱性スキャン）、または自己問診（SAQ） | カード会員データ環境が PCI DSS の要件を満たしていること | カード会員データ環境の外 |
| **EDSA認証** | EDSA 仕様（ISCI） | 制御システム用の**組込み機器** | ISCI が認めた認証機関（国内では CSSC の認証ラボラトリー） | 機器の通信堅牢性、セキュリティ機能、開発プロセスが基準を満たすこと | 機器を組み合わせたシステム全体や運用組織 |
| **CMMI アプレイザル** | CMMI モデル | 開発組織のプロセス | 認定されたリードアプレイザー | 組織のプロセスの成熟度（成熟度レベル） | 個々の製品の品質 |

この表から、科目Bでよく問われる判断が導けます。たとえば「委託先が ISMS 認証を取得しているから安心」とは言い切れません。委託する業務がその認証の**適用範囲**に含まれていなければ、認証は委託業務の管理を何も保証しないからです。また「JISEC 認証製品を導入したから安全」とも言い切れません。JISEC が保証するのは出荷時点の実装であり、導入後に管理者が設定を誤れば安全性は失われます。

**各制度で、組織は何のために取得し、取引先は何を確認できるか**を整理すると、次のようになります。

| 制度 | 組織（取得する側）の目的 | 取引先・調達者が確認できること | 確認するときに見るべき項目 |
|---|---|---|---|
| ISMS認証 | 取引条件・入札条件を満たす。自社の管理水準を第三者に示す。社内の PDCA を外部の目で定期点検する | 対象業務がリスクに基づいて管理されていること | **適用範囲**（委託業務が含まれるか）、登録の有効期限、適用宣言書の版 |
| プライバシーマーク | 消費者に「個人情報を適切に扱う会社」と示す。個人情報を扱う業務委託の受注条件を満たす | 事業者全体として個人情報保護の体制があること | 登録番号と有効期間（2年ごとの更新）、マークの使用が正規か |
| ISMAP | 政府機関にクラウドサービスを提供する（政府は原則として登録済みサービスから調達する） | 政府基準を満たしたクラウドサービスであること | ISMAP クラウドサービスリストへの掲載、登録の対象範囲（どのサービス・リージョンか） |
| JISEC（CC 認証） | 政府調達や国際市場で製品のセキュリティ品質を示す | 製品の ST に書かれた機能が評価済みであること | 認証製品リストへの掲載、評価した**版**（バージョン）、EAL・適合 PP、ST の前提条件（運用環境の条件） |
| JCMVP | 製品に組み込んだ暗号機能の正しさを示す（政府調達の要件など） | 暗号モジュールが基準どおり実装されていること | 認証番号、対象モジュールの版、セキュリティレベル |
| PCI DSS 準拠 | カードブランド・アクワイアラーとの契約上の義務を果たす | カード会員データ環境の安全性 | 準拠証明書（AOC）、評価の範囲、評価日 |

> **補足：ISMAP**
> ISMAP の詳細（制度の目的、ISMAP クラウドサービスリスト、リスクの小さな業務向けの ISMAP-LIU）は第1章 1.5 で扱った。本ノートでは「政府調達向けのクラウドサービス評価・登録制度」として、他の認証制度との位置づけを確認するにとどめる。

### 2.3 認証取得までの流れ

ここでは、最も代表的な ISMS 認証を例に、組織が認証を取得するまでの流れを示します。第1章 1.3 の「ISMS確立までの10ステップ」と第4章のリスクアセスメントが、この流れの前半に入ります。プライバシーマークや ITSMS も、規格が違うだけで大枠は同じです。

```
 [組織]                                         [認証機関]
  ① 経営者が取得を決定し、推進体制をつくる
  ② 適用範囲を決める（どの部門・拠点・業務か）
```

## 3. 製品を評価する ― ISO/IEC 15408（コモンクライテリア）とJCMVP

前節の比較表で、評価対象が「製品」である制度が2つありました。JISEC（ISO/IEC 15408）と JCMVP です。ISMS が「組織がきちんと管理しているか」を見るのに対して、こちらは「製品そのものに必要なセキュリティ機能が正しく作り込まれているか」を見ます。政府機関や企業が複合機やファイアウォール、ICカードを調達するとき、カタログの「セキュリティ機能あり」という自己申告だけでは信用できないため、第三者評価の結果が使われます。

### 3.1 ISO/IEC 15408の概要

**ISO/IEC 15408**は、IT関連製品や情報システムのセキュリティレベルを評価するための国際規格です。評価の対象となるのは、オペレーティングシステム、アプリケーションプログラム、通信機器、情報家電など、セキュリティ機能を備えたすべてのIT関連製品と、それらを組み合わせた一連の情報システムです。対象はあくまでも**製品やシステム**です。ISO/IEC 15408 は、企業全体や、組織内のセキュリティ規程の整備状況・運用状況などを評価するものではありません。

評価の範囲は、IT関連製品や情報処理システムの**出荷や運用に先立ち**、必要なセキュリティ対策が実装されているかどうかまでです。導入後にそれらが正しく運用されているかどうかの監査は対象外としています。導入後の運用は、利用する組織が ISMS（第1章 1.3）や監査（第4章 4.10）で管理すべき領域です。

> **用語解説：ISO/IEC**
> ISOはInternational Organization for Standardization（国際標準化機構）の略で、電気・電子分野を除く幅広い分野の国際標準化機関である。1947年に設立され、本部はスイスのジュネーブにある。
> IECはInternational Electrotechnical Commission（国際電気標準会議）の略で、電気・電子分野の国際標準化機関である。1906年に設立され、本部は同じくジュネーブにある。
> ISOとIECはジョイント組織（JTC 1：合同技術委員会）を設置し、情報処理分野の標準化を共同で行っている。規格番号が「ISO/IEC」で始まるのは、この JTC 1 で作られた規格である。

> **ISO/IEC 15408の成り立ち**
> 米国では、オレンジブックとして知られるTCSEC（Trusted Computer System Evaluation Criteria）が評価基準として用いられていた。欧州ではITSECなどが用いられていた。1990年代にこれらの基準が統合され、共通セキュリティ評価基準であるCC（Common Criteria）が策定された。CCバージョン2.1は国際標準化されてISO/IEC 15408:1999となった。その後のCCバージョン3.1、CC:2022に合わせて、ISO/IEC 15408も改訂が行われている。

TCSEC は第5章 5.4「Trusted OS」で見た評価基準でもあります。国ごとにばらばらだった基準を統合したことで、ベンダーは一度の評価で複数の国の市場に製品を出せるようになりました。これが後述の国際協定（CCRA）の土台です。

### 3.2 ISO/IEC 15408の構成

ISO/IEC 15408は、次の五つのパートから構成されています。

1. 概説と一般モデル
2. セキュリティ機能コンポーネント
3. セキュリティ保証コンポーネント
4. 評価方法及び評価アクティビティの仕様のための枠組み
5. セキュリティ要件の定義済みパッケージ

5つのパートの関係を一言でいえば、「Part1 の枠組み（ST・PP）に、Part2 の部品で**何を守る機能を持つか**を書き、Part3 の部品で**それが正しく作られていることをどこまで確かめるか**を書き、Part5 のパッケージ（EAL など）で確かめる深さを選び、Part4 の枠組みで評価方法を定める」となります。

| パート | 一言でいうと | 誰が使うか |
|---|---|---|
| Part1 概説と一般モデル | 評価の枠組みと ST・PP の書き方 | 開発者（ST）、調達者・業界団体（PP） |
| Part2 セキュリティ機能コンポーネント | 「何ができるか」の部品カタログ（**SFR**） | ST・PP の作成者 |
| Part3 セキュリティ保証コンポーネント | 「正しく作ったことの証拠」の部品カタログ（**SAR**） | ST・PP の作成者、評価者 |
| Part4 評価方法及び評価アクティビティの枠組み | 評価方法の書き方の枠組み | 評価方法の策定者 |
| Part5 定義済みパッケージ | よく使う要件のセット（**EAL** など） | ST・PP の作成者、調達者 |

各パートの内容を順に見ていきます。

### 3.3 Part1 概説と一般モデル ― STとPP

Part1 は、情報処理製品や情報処理システムの開発において最も重要な事項として、開発者が**セキュリティ基本設計書**（**Security Target**：**ST**）を作成することを規定しています。STとは、**評価対象**（**Target Of Evaluation**：**TOE**）に関するセキュリティ仕様書のことで、次の図のような内容を含みます。

> **STとは**
> STは、ITシステムにおけるセキュリティの基本設計書に相当するものである。評価対象となる製品の開発者が、TOEのセキュリティ機能やその保証内容を明確に記述する。

**図：STの内容**

- **ST概説**
  - ST参照
  - TOE参照
  - TOE概要
  - サブTSF構成（マルチ保証のみ）
  - TOE記述
- **適合主張**
  - 標準主張（適用されるISO/IEC 15408及びISO/IEC 18045標準への参照、ISO/IEC 15408-2、ISO/IEC 15408-3（適合/拡張））
  - PP主張、パッケージ主張
  - 適合種別（完全、正確、論証）
  - 評価方法/評価アクティビティへの参照
- **セキュリティ課題定義**
  - 脅威
  - 組織のセキュリティ方針
  - 前提条件
- **セキュリティ対策方針**
  - TOEのセキュリティ対策方針
  - 運用環境のセキュリティ対策方針
  - セキュリティ対策方針根拠
- **拡張コンポーネント定義**
- **セキュリティ要件**
  - セキュリティ機能要件（SFR）
  - セキュリティ保証要件（SAR）
  - セキュリティ要件根拠
- **TOE要約仕様**

出典：独立行政法人情報処理推進機構「情報技術セキュリティ評価のためのコモンクライテリア」
https://www.ipa.go.jp/security/jisec/about/kijun.html

ST の流れは、第4章で学んだリスク対応の考え方と同じです。まず「**セキュリティ課題定義**」で、TOE が直面する脅威、組織として守るべき方針、TOE が動く環境についての**前提条件**（例：管理者は信頼できる、TOE は施錠された部屋に置かれる）を書きます。次に「**セキュリティ対策方針**」で、それぞれの課題を TOE 自身が解決するのか、運用環境（利用者の組織）に任せるのかを振り分けます。最後に「**セキュリティ要件**」で、TOE が担う対策を Part2・Part3 の部品で具体的に書きます。調達者が ST を読むときは、とくに**前提条件**と**運用環境のセキュリティ対策方針**を確認すべきです。そこに書かれた条件を自組織が満たさなければ、評価結果は自組織の環境では成り立たないからです。

ST の実物は、たとえば次のような構成の文書になります（ネットワーク複合機を例にした架空の抜粋です）。

```
  〇〇複合機 セキュリティターゲット 第1.2版（抜粋・例）

  1 ST概説
    1.1 ST参照  : 〇〇複合機 セキュリティターゲット 第1.2版 2026年4月1日
    1.2 TOE参照 : 〇〇複合機 制御ソフトウェア Ver.3.0.1
  2 適合主張
    CC:2022 Part2 適合、Part3 適合／PP主張：ハードコピーデバイス向けPP
  3 セキュリティ課題定義
    脅威 T.UNAUTH_ACCESS : 権限のない者が、蓄積された文書データを閲覧する
    前提 A.ADMIN         : TOE の管理者は信頼でき、手順書に従って操作する
  4 セキュリティ対策方針
    O.USER_AUTH  (TOE)      : TOE は利用者を識別・認証してから操作を許可する
    OE.PHYSICAL  (運用環境) : TOE は入退室管理された場所に設置される
  6 セキュリティ要件
    6.1 セキュリティ機能要件（SFR）
        FIA_UAU.2  アクション前の利用者認証
        FDP_ACC.1  サブセットアクセス制御
        FAU_GEN.1  監査データ生成
        FCS_COP.1  暗号操作（蓄積データの暗号化）
    6.2 セキュリティ保証要件（SAR）
        EAL2 パッケージ
```

SFR の名前は「**クラス**（FIA＝識別と認証）＿**ファミリ**（UAU＝利用者認証）．**コンポーネント**の番号（2）」という3階層になっています。この階層構造が次の Part2 の内容です。

STは評価対象となる個々の製品ごとに作成されます。これに対して、**セキュリティ要求仕様書**（**Protection Profile**：**PP**）は、同一分野の製品で共通して使用できるように汎用化された仕様書です。開発者は、STを作成する際にPPへの準拠を示すことで、記述の一部を省略できます。

> **PPとは**
> PPは、特定の製品分野（例：ファイアウォール、ICカード、複合機など）に求められるセキュリティ要件を共通化したテンプレートと考えるとよい。調達者や業界団体が作成することが多い。

| 観点 | ST（セキュリティターゲット） | PP（プロテクションプロファイル） |
|---|---|---|
| 日本語名 | セキュリティ基本設計書 | セキュリティ要求仕様書 |
| 誰が作るか | 製品の**開発者** | **調達者**や業界団体 |
| 単位 | 個々の製品（TOE）ごと | 製品分野ごと（汎用） |
| 立場 | 「この製品はこう守る」という**実装側**の宣言 | 「この分野の製品はこう守るべき」という**要求側**の仕様 |
| 関係 | PP への適合を主張すると記述の一部を省略できる | 複数の ST から参照される |

### 3.4 Part2 セキュリティ機能コンポーネント

Part2 は、TOEが備えるべきセキュリティ機能要件を、**11の機能クラス**に分類して規定しています（下表参照）。各機能クラスは、**機能ファミリ**、**機能コンポーネント**という階層構造によって詳細化されています。ST や PP の作成者は、このセキュリティ機能要件を部品として選んで、ST や PP を作成します。

**表：セキュリティ機能要件の概要**

| 機能クラス | 略称 | 概要 |
|---|---|---|
| セキュリティ監査<br>（Security audit） | FAU | セキュリティ事象に関連した情報の認識、記録、保存、分析に関する要件 |
| 通信<br>（Communication） | FCO | データ通信への参加者の識別を保証する否認防止に関する要件 |
| 暗号サポート<br>（Cryptographic support） | FCS | 暗号鍵の生成/配付/失効の管理、データの暗号化/復号、ディジタル署名の生成/検証などの暗号操作に関する要件 |
| 利用者データ保護<br>（User data protection） | FDP | アクセス制御、情報フロー制御、利用者データのインポート時のセキュリティ属性保護、利用者データ転送時の機密性保護などに関する要件 |
| 識別と認証<br>（Identification and authentication） | FIA | 利用者のアイデンティティを確立し、検証する要件 |
| セキュリティ管理<br>（Security Management） | FMT | セキュリティ属性や、セキュリティ機能に関連するデータ（セキュリティ方針DBなど）の管理に関する要件 |
| プライバシー<br>（Privacy） | FPR | 他者によるアイデンティティの発見（探り出し）と悪用からの保護に関する要件 |
| TSFの保護<br>（Protection of the TOE Security Function） | FPT | セキュリティ機能を提供するメカニズムと、内部データの完全性に関する要件 |
| 資源利用<br>（Resource utilization） | FRU | 資源の耐障害性、優先度制御、資源割当てに関する要件 |
| TOEアクセス<br>（TOE access） | FTA | ユーザセッション（TOEと利用者との間の対話路）の確立の制御に関する要件 |
| 高信頼パス/チャネル<br>（Trusted path/channels） | FTP | 利用者とTOEとの間の高信頼な通信路に関する要件 |

※TSF：TOE Security Function（TOEのセキュリティ機能）

略称はすべて「F」（Functional）で始まります。次の Part3 の保証クラスはすべて「A」（Assurance）で始まるので、略称を見れば機能要件か保証要件かを区別できます。各クラスは、これまでの章で学んだ技術と対応しています。FAU は第7章 7.8 のログ管理、FCS は第7章の暗号、FIA は第6章の認証、FDP は第6章 6.1 のアクセス制御、FCO は第1章 1.2 の否認防止に当たります。

### 3.5 Part3 セキュリティ保証コンポーネント

Part3 は、Part2 のセキュリティ機能要件が**正しく実装されていることを保証するための要件**を、**保証クラス**として規定しています（下表の9項目）。各保証クラスは、第2レベルの**保証ファミリ**、第3レベルの**保証コンポーネント**という階層構造によって詳細を規定しています。機能要件が「何ができるか」なら、保証要件は「それが本当にできると、どんな証拠でどこまで確かめたか」です。

**表：セキュリティ保証要件のコンポーネント**

| 保証クラス | 略称 | 概要 |
|---|---|---|
| プロテクションプロファイル評価<br>（Protection Profile evaluation） | APE | PPが信頼でき、内部的に一貫していることを実証する。PPが一つ又は複数のPP又はパッケージに基づいている場合は、それらのPPやパッケージをPPが正しく具体化していることも実証する |
| プロテクションプロファイル構成評価<br>（Protection Profile Configuration evaluation） | ACE | PP構成が信頼でき、一貫していることを実証する |
| セキュリティターゲット評価<br>（Security Target evaluation） | ASE | STが信頼でき、内部的に一貫していることを実証する。STが一つ又は複数のPP又はパッケージに基づいている場合は、それらのPP構成、PP及びパッケージをSTが正しく具体化していることも実証する |
| 開発<br>（Development） | ADV | TOEに関する情報を提供する。この情報は、AVAクラス及びATEクラスで記述されている脆弱性分析とテストを実施するための基礎となる |
| ガイダンス文書<br>（Guidance documents） | AGD | すべての利用者の役割に対するガイダンス文書の要件を提供する。TOEをセキュアに準備し運用するためには、TOEのセキュアな取扱いに関連するすべての側面を記述する必要がある。このクラスでは、TOEの意図しない誤った取扱いの可能性についても扱う |
| ライフサイクルサポート<br>（Life cycle support） | ALC | TOEの開発、製造、配付及び保守における規律と管理策を確立する側面である。セキュリティ分析とその証拠の作成が、開発、製造、配付及び保守アクティビティの不可欠な部分として標準的に行われるならば、TOEのセキュリティ要件との対応の信頼度はより大きくなる |
| テスト<br>（Tests） | ATE | TSFが記述（機能仕様、TOE設計及び実装表現）のとおりに振る舞うことの保証を提供する。テストシナリオからセキュリティ機能要件（SFR）への直接的な追跡可能性は求めない |
| 脆弱性評定<br>（Vulnerability assessment） | AVA | TOEの開発又は運用で生じる、悪用可能な脆弱性の可能性を扱う |
| 統合<br>（Composition） | ACO | 統合TOEが、既に評価されたソフトウェア、ファームウェア又はハードウェアコンポーネントが提供するセキュリティ機能に依存する場合に、セキュアに動作するという信頼を得るために策定された保証要件を特定する |

保証クラスは、第8章 8.1 で学ぶ開発工程の各段階に対応すると覚えると整理しやすくなります。設計書（ADV）、マニュアル（AGD）、開発環境と配付・保守（ALC）、テスト（ATE）、脆弱性診断（AVA。第5章 5.3 の脆弱性診断に相当）です。評価機関は、開発者が提出したこれらの証拠資料を調べ、必要に応じて自ら試験を行います。

### 3.6 Part4 評価方法の枠組みと Part5 定義済みパッケージ（EAL）

**Part4 評価方法及び評価アクティビティの仕様のための枠組み**は、客観的で、反復可能かつ再現可能な評価方法及び評価アクティビティを規定するための標準化された枠組みとして、評価方法と評価アクティビティの構造や仕様等について規定しています。評価機関によって結果がばらつかないようにするための部分です。

**Part5 セキュリティ要件の定義済みパッケージ**は、あらかじめ定義されたセキュリティ要件のパッケージを規定しています。代表的なものが、保証の厳格さを7段階で示す**評価保証レベル**（**Evaluation Assurance Level**：**EAL**）です。EALの数字が大きいほど、評価の範囲・深さ・厳密さが増し、より高い保証が得られます。ただし、EAL は**保証の深さ**（どれだけ厳しく確かめたか）を表すものであり、セキュリティ機能の多さや強さを表すものではありません。EAL4 の製品が EAL2 の製品より多くの機能を持つとは限らない点は、科目A-2 の引っかけになりやすいところです。

**表：EAL（Evaluation Assurance Level）の概要**

| EAL | 概要 | 適用する状況 |
|---|---|---|
| EAL1<br>機能テスト | 限定されたSTと、そのST内のセキュリティ機能要件の分析により、基本レベルの保証を提供する。この分析は、TOEの振る舞いを理解するために、機能とインタフェースの仕様及びガイダンス証拠資料を使用して行われる | 正しい運用について一定の信頼が要求されるが、セキュリティへの脅威が重大とはみなされない場合に適用する |
| EAL2<br>構造テスト | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能とインタフェースの仕様、ガイダンス証拠資料、及びTOEのアーキテクチャの基本的な記述を使用して行われる | 開発者又は利用者が、完全な開発記録を簡単には使用できない状況において、低レベルから中レベルの独立に保証されたセキュリティを必要とする環境で適用する |
| EAL3<br>方式テスト及びチェック | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能とインタフェースの仕様、ガイダンス証拠資料、及びTOEの設計のアーキテクチャ記述を使用して行われる | 開発者又は利用者が、中レベルで独立して保証されたセキュリティを必要とし、大幅な再エンジニアリングを伴わずに、TOEとその開発の完全な調査を必要とする状況で適用する |
| EAL4<br>方式設計、テスト及びレビュー | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能と完全なインタフェースの仕様、ガイダンス証拠資料、TOEの基本モジュール設計の記述、及び実装のサブセットを使用して行われる | 開発者又は利用者が、従来型の製品としてのTOEについて、独立して保証された中レベルから高レベルのセキュリティを必要とし、セキュリティ特有のエンジニアリングコストを追加で負担する準備ができている状況で適用する |
| EAL5<br>準形式的設計及びテスト | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能と完全なインタフェースの仕様、ガイダンス証拠資料、TOEの設計の記述、及び実装を使用して行われる。また、モジュール化されたTSF設計も必要となる | 開発者又は利用者が、計画された開発において独立して保証された高レベルのセキュリティを必要とし、専門的なセキュリティエンジニアリング技法による厳格な開発手法を、不合理なコストを伴わずに必要とする状況で適用する |
| EAL6<br>準形式的検証済み設計及びテスト | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能と完全なインタフェースの仕様、ガイダンス証拠資料、TOEの設計、及び実装を使用して行われる。追加の保証が、選択されたTOEセキュリティ方針の形式的モデル、及び機能仕様とTOE設計の準形式的表現を通して得られる。モジュール化され、階層化された、簡潔なTSF設計も必要となる | 高リスクの状況で使用される特殊なTOEの開発に適用し、保護される資産の価値が追加コストを正当化する状況で適用する |
| EAL7<br>形式的検証済み設計及びテスト | 完全なSTと、そのST内のセキュリティ機能要件の分析により保証を提供する。この分析は、セキュリティの振る舞いを理解するために、機能と完全なインタフェースの仕様、ガイダンス証拠資料、TOEの設計、及び構造化された実装表現を使用して行われる。追加の保証が、選択されたTOEセキュリティ方針の形式的モデル、及び機能仕様とTOE設計の形式的表現を通して得られる。モジュール化され、階層化された、簡潔なTSF設計も必要となる | リスクが非常に高い状況、又は資産の高い価値がさらに高いコストを正当化する状況において、セキュリティを重視したTOEの開発に適用する |

EAL の7段階は、名前の変化で流れをつかむと覚えやすくなります。EAL1〜2 は「テスト」中心、EAL3〜4 は「方式（設計）」まで踏み込み、EAL5〜6 は「準形式的」（形式に近い記法）、EAL7 は「形式的検証」（数学的な証明）です。市販の商用製品は EAL2〜4 で評価されることが多く、EAL5 以上は IC チップなどの特殊な製品に限られます。また、評価の際に EAL の要件に保証コンポーネントを追加したものは「EAL4+」（「EAL4 augmented」）のように「+」を付けて表記されます。

### 3.7 ISO/IEC 15408の効果と国内の制度（JISEC）

**ISO/IEC 15408適用による効果**は、開発者とユーザの双方にあります。

- IT関連製品や情報システムの**開発者**は、ISO/IEC 15408に則って開発することで、国際的に通用するセキュリティ品質をもった製品を出荷できます。また、認証を取得すれば、ある程度の宣伝効果も期待できます。
- **ユーザ**は、製品の購入やシステムの導入の際にISO/IEC 15408の認証を受けた製品を選定することで、セキュリティ面での不安を軽減できます。調達担当者は、自ら製品を検査しなくても、認証製品リストと ST を確認するだけで一定の水準を判断できます。

**ISO/IEC 15408に関する国内の対応状況**は次のとおりです。日本国内では、2000年7月にISO/IEC 15408:1999がJIS化され、JIS X 5070:2000として発行されました。その後、2011年にJIS X 5070が改訂され、現在は次に示す第1部のみが発行されています。

- JIS X 5070-1:2011 セキュリティ技術－情報技術セキュリティの評価基準－第1部：総則及び一般モデル

つまり JIS は ISO/IEC 15408 の旧版（第1部のみ）に対応したままであり、実際の評価・認証は国際規格（CC:2022 など）を直接参照して行われています。

日本国内では現在、**ITセキュリティ評価及び認証制度**（Japan Information Technology Security Evaluation and Certification Scheme：**JISEC**）が運用されています。制度の主な関係者と流れは次のとおりです。

1. **申請者（開発者・ベンダーなど）**：申請者は評価機関に評価を依頼し、認証機関に認証を申請する。
2. **評価機関**：評価機関はISO/IEC 15408及び評価方法（ISO/IEC 18045）に基づいて、STとTOEを評価する。評価機関は、独立行政法人製品評価技術基盤機構（NITE）の認定センター（**IAJapan**）による認定を受けている。
3. **認証機関**：独立行政法人情報処理推進機構（**IPA**）が認証機関として評価結果を検証し、適切であれば認証書を発行する。
4. **公開**：認証された製品は、認証製品リストとして公開される。

```
   ┌────────────┐ 認定  ┌────────────┐
   │ IAJapan(NITE)│─────→│  評価機関     │
   └────────────┘        └──────┬─────┘
                                   │ ②ST・TOE を評価し、評価報告書を提出
   ┌────────────┐ ①評価依頼    │
   │ 申請者       │─────────→│
   │（開発者）    │                ▼
   │             │ ①認証申請 ┌────────────┐ ③検証・認証書発行
   │             │─────────→│ 認証機関(IPA) │──────────→ 申請者
   └────────────┘            └──────┬─────┘
                                           │ ④認証製品リストを公開
                                           ▼
                                  調達者・利用者（ST・認証報告書を確認）
```

評価と認証が別の機関に分かれている点に注意してください。評価機関が実際に調べ（評価）、IPA がその評価が正しく行われたかを確かめて証明する（認証）という分業です。

> **ISO/IEC 18045**
> ISO/IEC 15408に基づく評価を行う際の評価方法を規定した国際規格。CCの評価方法であるCEM（Common Evaluation Methodology）に相当する。

**ISO/IEC 15408に関する国際協定**として、日本は2003年10月に、ISO/IEC 15408の国際協定ともいえる**CCRA**（Common Criteria Recognition Arrangement：共通基準承認アレンジメント）に加盟しました。CCRAは、加盟国のいずれかで評価・認証された製品の認証書を、加盟国間で相互に通用させるための協定です。ベンダーは、日本の JISEC で取得した認証書を、他の加盟国への輸出や政府調達でも使えます。

CCRAの加盟形態には、次の2種類があります。

- **Certificate authorizing participants**：自国で認証制度をもつ国が加盟する（認証書を発行し、かつ受け入れる）。
- **Certificate consuming participants**：認証制度をもたない国が加盟する（他国の認証書を受け入れるだけ）。

日本は、Certificate authorizing participantsとして加盟しています。

なお、加盟国間で相互承認される保証レベルには上限があります。以前は EAL4 までが相互承認の対象でしたが、2014年のアレンジメント改定以降は、加盟国が共同で作成した PP（cPP）に基づく評価、または EAL2 までが相互承認の対象になっています。それより高い EAL の認証は、認証を発行した国では有効ですが、他国で自動的に通用するとは限りません。

### 3.8 暗号モジュールの評価 ― JCMVP

ISO/IEC 15408 が製品全体のセキュリティ機能を評価するのに対して、製品の中の**暗号機能だけ**を評価する制度が **JCMVP**（Japan Cryptographic Module Validation Program：**暗号モジュール試験及び認証制度**）です。第7章 7.1 で学んだように、AES や RSA といったアルゴリズムが安全でも、それを実装したプログラムに誤りがあったり、鍵がメモリから簡単に読み出せたりすれば、暗号は役に立ちません。JCMVP は、この「実装」と「鍵の保護」を確かめる制度です。

| 項目 | 内容 |
|---|---|
| 対象 | **暗号モジュール**（暗号機能を実装したハードウェア、ソフトウェア、ファームウェア。例：HSM、IC カード、暗号ライブラリ） |
| 基準 | ISO/IEC 19790（JIS X 19790：暗号モジュールのセキュリティ要件）、試験方法は ISO/IEC 24759（JIS X 24759） |
| 誰が評価するか | IAJapan が認定した試験機関が試験し、IPA が認証する（JISEC と同じ分業） |
| 何を保証するか | 承認された暗号アルゴリズム（CRYPTREC 暗号リストなど）が正しく実装されていること、暗号鍵などの重要情報が適切に保護されていること |
| レベル | セキュリティレベル1〜4（数字が大きいほど、物理的な耐タンパ性などの要求が厳しい） |
| 海外の対応制度 | 米国・カナダの CMVP（FIPS 140 シリーズ） |

調達者は、暗号化を前提にした製品（VPN 装置、暗号化 USB メモリなど）を選ぶとき、「暗号化対応」というカタログの記載だけでなく、暗号モジュールが JCMVP（または CMVP）の認証を受けているかを確認できます。

## 4. 組織の能力を評価する ― CMMI と SSE-CMM

3節の ISO/IEC 15408 は、完成した**製品**を評価する仕組みでした。しかし、ソフトウェアは出荷後も改修が続きますし、受託開発では完成品を事前に評価することができません。そこで、「この組織なら、良いものを安定して作れる」という**開発組織の能力**を評価する発想が生まれました。それが能力成熟度モデル（CMM）です。

### 4.1 CMMIの概要

**CMMI**（Capability Maturity Model Integration：能力成熟度モデル統合版）は、能力成熟度モデルの一つです。米国国防総省（DoD）が米国カーネギーメロン大学（CMU）に設置したソフトウェア工学研究所（**SEI**）で考案されました。CMMI は、システム開発を行う組織が、**プロセス改善**を行うためのガイドラインとなるものです。国防総省がソフトウェアを外部に発注する際に、発注先の開発能力を見極める物差しが必要だったことが出発点です。

CMMへの取組みは1980年代から始まり、次のように様々な分野のCMMが開発されました。

- SA-CMM（Software Acquisition CMM）
- IPD-CMM（Integrated Product Development CMM）
- SW-CMM（CMM for Software）

これらを発展・統合させたのがCMMIです。ソフトウェア開発組織のためのCMMIの正式名称は「**CMMI for Development**」（**CMMI-DEV**）です。

> **CMMIのその後の動向**
> CMMIの管理は、SEIから2013年にCMMI Instituteへ移管された。CMMI Instituteは現在ISACAの傘下にある。2018年にはCMMI V2.0、2023年にはCMMI V3.0が公開されており、開発、サービス、調達などの領域を統合したモデルとなっている。

### 4.2 CMMIにおける二つの評価モデル

CMMIには、組織の成熟度や能力を評価するためのモデルとして、**段階表現**と**連続表現**の二つがあります。段階表現は「組織全体として何段目まで上がったか」を見る物差し、連続表現は「プロセス領域ごとにどこまでできているか」を見る物差しです。

**表：CMMI（バージョン1.3）における二つの評価モデル**

| 評価モデル | 内容 |
|---|---|
| 段階表現（成熟度レベル） | 組織の成熟度を1から5までの5段階の**成熟度レベル**で表し、段階的にプロセス改善に取り組むことを前提としたモデル。主に、組織を構成する部署やプロジェクトを、複数のプロセス領域にわたって評価する場合に用いられる |
| 連続表現（能力レベル） | 組織を成熟度ではなく、0から3までの4段階の**能力レベル**で表すモデル。主に、個々のプロセス領域におけるプロセス改善の達成度を評価する場合に用いられる。なお、バージョン1.2では0から5までの6段階であったが、バージョン1.3から4段階に変更された |

**表：段階表現と連続表現のレベル**

| レベル | 段階表現（成熟度レベル） | 連続表現（能力レベル） |
|---|---|---|
| レベル0 | ― | 不完全な |
| レベル1 | 初期 | 実施された |
| レベル2 | 管理された | 管理された |
| レベル3 | 定義された | 定義された |
| レベル4 | 定量的に管理された | ― |
| レベル5 | 最適化している | ― |

成熟度レベルの意味は、組織の状態として具体的に思い浮かべると覚えやすくなります。

| 成熟度レベル | 組織の状態のイメージ |
|---|---|
| 1 初期 | 成功は個人の力量しだい。同じ組織でもプロジェクトごとに品質がばらつく |
| 2 管理された | プロジェクト単位で計画・進捗・構成管理が行われている |
| 3 定義された | 組織標準のプロセスが文書化され、各プロジェクトがそれを調整して使う |
| 4 定量的に管理された | プロセスの実績（欠陥密度、工数など）を数値で管理し、ばらつきを統計的に把握している |
| 5 最適化している | 定量データに基づいてプロセスを継続的に改善している |

### 4.3 CMMIにおけるアプレイザルの概要

CMMIのモデルを使って組織のプロセスの状況を診断することを「**アプレイザル**」といいます。アプレイザルの概要を次に示します。

- 客観的でばらつきのない結果を得るために、アプレイザルの方法やレベル判定の基準などが明確に決められています。
- 正式なアプレイザルは、認定された**リードアプレイザー**によって実施される必要があります。以前は、米国国防総省（DoD）が米国カーネギーメロン大学（CMU）に設置したソフトウェア工学研究所（SEI）がリードアプレイザーを認定していましたが、CMMI の管理が移管された現在は、CMMI Institute（ISACA 傘下）が認定しています。

> **SCAMPI**
> SCAMPI（Standard CMMI Appraisal Method for Process Improvement）は、CMMIの公式なアプレイザル手法である。最も厳格なクラスAのアプレイザルによってのみ、公式な成熟度レベルや能力レベルの評定が得られる。SCAMPI は CMMI V1.3 までの公式手法で、V2.0 以降はベンチマークアプレイザルなどの新しい区分に再編されている。

発注者が委託先を選ぶときは、「CMMI レベル3」という表示だけでなく、どの組織単位（部署・拠点）が、いつ、どの版のモデルでアプレイザルを受けたかを確認すべきです。ISMS の適用範囲と同じく、評定は評価を受けた組織単位にしか及ばないからです。

### 4.4 SSE-CMMの概要

**SSE-CMM**（Systems Security Engineering-Capability Maturity Model）は、**システム開発におけるセキュリティの確保**を目的としたCMMです。CMMI が開発プロセス全般の品質を見るのに対して、SSE-CMM はセキュリティ工学のプロセスに特化しています。

米国の国家安全保障局（NSA）がスポンサーとなって作成が進められ、1996年にバージョン1.0が発表されました。以後は、米国の非営利団体ISSEA（International Systems Security Engineering Association）が主体となって運用・改善などを行っています。2002年10月にはISO/IEC 21827（システムセキュリティ工学－能力成熟度モデル）として国際規格化され、2008年10月に改訂版が発行されました。

発注者や開発組織自身は、SSE-CMMを用いることで、セキュアなシステムの開発を行う組織の能力を診断・評価できます。

### 4.5 ISO/IEC 15408とCMMI-DEVの比較

ここまでの「製品を評価する」ISO/IEC 15408 と、「組織を評価する」CMMI-DEV を比較すると、次のようになります。

**表：ISO/IEC 15408とCMMI-DEVの比較**

| 比較項目 | ISO/IEC 15408 | CMMI-DEV |
|---|---|---|
| 評価の対象となるもの | 製品・システム | ソフトウェア開発を行う組織・団体 |
| 評価において要求されるもの | セキュリティ機能を実装した製品・システムの詳細な仕様書と、厳密な完成品 | システム開発のプロセスにおいて、品質確保のための取組みが組織的に行われており、継続的に改善されていること |
| 用途として適切と思われるもの | 比較的アップデートが少ないパッケージソフトウェアやIT製品を開発し、広く提供しているベンダーが、自社製品のセキュリティ品質を高めるために認証を取得する | パッケージ/業務用などを問わず、大規模なソフトウェア開発を行っているベンダーが、開発プロセス全般における組織の品質を高めるために、定期的に測定・評価を行う |
| 評価の結果 | 認証書（EAL などの保証レベル） | 成熟度レベル・能力レベルの評定 |

CMMI-DEVでは、個別のシステムや製品は評価されません。しかし、ソフトウェア開発を行う組織自体が評価基準を満たすことで、その組織が開発する製品やシステムの品質について、一定の信頼性を確保できます。逆に ISO/IEC 15408 は「評価した版の製品」についてだけ保証するため、アップデートが頻繁な製品では、改版のたびに評価を受け直す負担が大きくなります。「比較的アップデートが少ない製品」に向くとされるのはこのためです。

## 5. 業界の基準 ― PCI DSS

ここからは、特定の業界・分野に向けて作られた基準を見ていきます。最初は、クレジットカード業界の PCI DSS です。ISO の規格と違い、PCI DSS は業界団体が定めた基準であり、カードブランドとの**契約**を通じて守ることが求められます（0.2 の表の「業界基準・契約上の基準」に当たります）。

### 5.1 PCI DSSの概要

**PCI DSS**（Payment Card Industry Data Security Standard）とは、**クレジットカード情報や取引情報の保護**を目的として、MasterCard、VISA、JCB、American Express、Discoverの**国際ペイメントブランド5社**が共同で策定したセキュリティ基準です。攻撃者は、カード番号を盗んで不正利用したり闇市場で売ったりするために、カード情報を保存・処理する加盟店や決済代行事業者のシステムを狙います。ある1社の管理が甘いだけで、そこを経由して多数のカード会員が被害を受けるため、業界全体で同じ水準の対策を義務付ける必要がありました。

PCI DSSは「PCIデータセキュリティ基準」とも呼ばれ、「PCI Security Standards Council：**PCI SSC**」によって管理、改訂、普及のための活動などが行われています。版の変遷は次のとおりです。

| 版 | 公開 | 主な内容 |
|---|---|---|
| バージョン3.1 | 2015年4月 | SSL 3.0及び一部のTLS 1.0、TLS 1.1で存在が確認された「**POODLE**」脆弱性への対応等を反映 |
| バージョン3.2.1 | 2018年5月 | ― |
| バージョン4.0 | 2022年3月 | 「ネットワークセキュリティコントロール（NSC）」などの新しい用語、要件の再構成 |
| バージョン4.0.1 | 2024年6月 | 4.0 の記述の明確化などの限定的な改訂 |

以前は、バージョン4.0が「最新版」とされていましたが、現在は2024年6月に公開されたバージョン4.0.1が有効な版です（4.0 は2024年末で廃止）。4.0.1 は記述の明確化が中心で、本ノートで扱う12の要件の構成は変わっていません。「POODLE」脆弱性については第7章 7.4 で解説しています。

PCI DSS 3.1では、当該脆弱性の存在するSSLの全バージョン及びTLSの初期バージョンについて、2016年6月30日を期限として利用を停止することとしていました。PCI DSS 3.2ではこれを2年間延長し、2018年6月30日を期限としていました。つまり、カード情報を扱う事業者は、遅くとも2018年6月末までに SSL と初期の TLS を停止し、TLS 1.2 以上へ移行することを求められたわけです。

> **試験における出題**
> 情報セキュリティスペシャリスト試験（現在の情報処理安全確保支援士試験の前身）の午後試験（現在の科目B）では、PCI DSSの要件を読み解きながら解答する問題が出題されている。

> **POODLE（Padding Oracle On Downgraded Legacy Encryption）**
> SSL 3.0のCBCモードにおけるパディング処理の不備を突き、暗号化された通信内容の一部を解読される脆弱性である。TLS接続をSSL 3.0にダウングレードさせる攻撃と組み合わせて悪用される。

### 5.2 PCI DSSの要件と特徴

PCI DSSは、次の表に示すように**12の要件**から構成され、要件ごとにさらに詳細な要件が示されています。12の要件は6つの目標にまとめられており、目標を見ると、これまで学んだ対策の分類（ネットワーク防御、データ保護、脆弱性管理、アクセス制御、監視、ポリシ）がそのまま並んでいることがわかります。

**表：PCI DSSの12の要件（バージョン4.0）**

| 目標 | 要件 | 内容 | 関連ノート |
|---|---|---|---|
| 安全なネットワークとシステムの構築と維持 | 要件1 | ネットワークセキュリティコントロールの導入と維持 | 第5章 5.5 |
| | 要件2 | すべてのシステムコンポーネントにセキュアな設定を適用する | 第5章 5.2 |
| アカウントデータの保護 | 要件3 | 保存されたアカウントデータの保護 | 第7章 7.1 |
| | 要件4 | オープンな公共ネットワークでの送信時に、強力な暗号化技術でカード会員データを保護する | 第7章 7.4 |
| 脆弱性管理プログラムの維持 | 要件5 | 悪意のあるソフトウェアからすべてのシステムおよびネットワークを保護する | 第2章 2.9 |

| | 要件8 | ユーザの識別とシステムコンポーネントへのアクセスの認証 | 第6章 |

| ネットワークの定期的な監視とテスト | 要件10 | システムコンポーネントおよびカード会員データへのすべてのアクセスをログに記録し、監視すること | 第7章 7.8 |
| | 要件11 | システムおよびネットワークのセキュリティを定期的にテストする | 第5章 5.3 |
| 情報セキュリティポリシーの維持 | 要件12 | 組織の方針とプログラムによって情報セキュリティをサポートする | 第4章 4.3 |

出典：PCI Security Standards Council「要件とテスト手順 バージョン4.0」を基に著者が作成
<https://listings.pcisecuritystandards.org/documents/PCI-DSS-v4_0-JA.pdf>

PCI DSSの要件は、情報システム／ネットワークにおいて求められる**技術的なセキュリティ対策**が中心となっています。例えば、次のように、**対策を実施する頻度や許容期間などが具体的に示されている**のが大きな特徴です。ISO/IEC 27001 が「組織がリスクに応じて自ら決める」ことを求めるのに対し、PCI DSS は「何を、どの頻度で」を基準側が数値で決めている、という対比で覚えておきましょう。

- 「ネットワークセキュリティコントロール（NSC）の設定は、少なくとも**6か月に1回**は見直しを行い、適切かつ効果的であることを確認する」
- 「監査ログの履歴を少なくとも**12か月間**保持し、少なくとも直近の**3か月間**は分析のために直ちに利用できるようにする」
- 「重要または高セキュリティなパッチ／アップデートがリリース後**1か月以内**にインストールされている」

また、PCI DSS には情報システムの技術的な対策のみでなく、情報セキュリティポリシの整備、物理的なアクセス制限などの要件も含まれています。

要件が数値で示されているため、運用担当者はそれをそのまま社内規程や設定に落とし込めます。たとえばログ保存の要件は、社内規程と syslog サーバの設定で次のように実装されます（例示）。

```
  【ログ管理規程（抜粋・例）】
  第8条（保存期間）
    システム管理者は、カード会員データ環境のサーバ及びネットワーク機器の
    監査ログを12か月以上保存し、そのうち直近3か月分は、
    SIEM 上で即時に検索できる状態に置かなければならない。

  【ログサーバのローテーション設定（例）】
  /var/log/cde/*.log {
      monthly
      rotate 12          # 12か月分を保持（PCI DSS 要件10）
      compress
      delaycompress      # 直近分は非圧縮で即時検索可能に
  }
```

> **ネットワークセキュリティコントロール（NSC）**
> PCI DSS 4.0で導入された用語で、ファイアウォールをはじめ、ネットワーク間のトラフィックを制御するための技術（仮想ファイアウォール、クラウドのセキュリティグループ、ルータのアクセス制御リストなど）を総称したものである。バージョン3.2.1までは主に「ファイアウォール」として記述されていた。

### 5.3 PCI DSSに基づく認定プログラムの概要

PCI DSSの**認定プログラム**は、カードブランドごとに、それぞれ定められています。認定の対象となるのは、**加盟店**、カード発行会社（**イシュアー**）、加盟店契約会社（**アクワイアラー**）、カード決済処理代行会社である**TPP**（Third Party Processors）など、主にクレジットカード関連の業務を行っている組織です。

認定プログラムごとに、年間の取引件数やトランザクション量などによる認定対象者のレベル分けと、それに応じた**バリデーション**（要求事項）が決められています。バリデーションとは、「**認定対象者が受けなければならない診断の種類と頻度**」について定めたものであり、次のような診断方法が示されています。取引量が多い組織ほど、厳しい第三者診断が求められます。

- **QSA**（Qualified Security Assessor）によるオンサイト調査
- **ASV**（Approved Scanning Vendor）による脆弱性スキャン
- 問診票（**SAQ**：Self-Assessment Questionnaire）による自己診断

> **QSA／ASV**
> QSA、ASVは、PCI SSCによって公式に認定された診断実施会社である。QSAは訪問審査（オンサイト調査）を、ASVはインターネット側からの外部脆弱性スキャンを実施する。

| 診断方法 | 誰が行うか | 何を見るか | 主な対象 |
|---|---|---|---|
| オンサイト調査 | QSA（第三者） | 現地でのすべての要件への準拠 | 取引量の多い加盟店、サービスプロバイダ |
| 脆弱性スキャン | ASV（第三者） | インターネット側から見える脆弱性 | 外部公開システムをもつ組織 |
| 自己診断 | 組織自身（SAQ に回答） | 該当する要件への準拠 | 取引量の少ない加盟店 |

PCI DSSは、本来クレジットカード関連サービスを提供している組織向けのセキュリティ基準ではありますが、それに限らず、多くの企業が、ITインフラやWebアプリケーションの技術的なセキュリティ基準として利用することができます。実際、米国では既にPCI DSSが業界を超えたセキュリティ標準として広く普及しており、日本でも普及が進んでいます。対策の頻度や期間が数値で書かれているため、自社の規程を作るときの「具体的な目安」として参照しやすいからです。

## 6. ITサービスの基準 ― ISO/IEC 20000及びITIL

### 6.1 ISO/IEC 20000の概要

**ISO/IEC 20000**とは、IT関連サービスを提供する組織が、**顧客の求める品質を確保し、維持・改善するための要求事項**を規定した国際規格であり、これに基づいた評価・認証制度も運用されています。データセンター事業者やクラウド事業者、社内の情報システム部門が「サービスを止めない、止まってもすぐ戻す、約束した品質を守る」仕組みを持っていることを示すための規格です。可用性（CIA の A）を組織の仕組みとして支える規格だといえます。

ISO/IEC 20000は、主に次の二つの部から構成されます。

- **第1部（ISO/IEC 20000-1）**：サービスマネジメントシステム要求事項
- **第2部（ISO/IEC 20000-2）**：サービスマネジメントシステムの適用の手引

第1部は、ISMSにおけるISO/IEC 27001の位置付けと同様に、ITサービスマネジメントを実装するための**要求仕様**であり、認証取得のための基準となっています。一方、第2部は、ISMSにおけるISO/IEC 27002の位置付けと同様に、組織が最適なITサービスマネジメントを実践するための**規範（ガイドライン）**となっています。

| ISMS | ITSMS | 役割 |
|---|---|---|
| ISO/IEC 27001 | ISO/IEC 20000-1 | 要求事項（認証の基準） |
| ISO/IEC 27002 | ISO/IEC 20000-2 | 実践の手引（ガイドライン） |

### 6.2 ITILの概要

ISO/IEC 20000は、英国商務局（Office of Government Commerce：OGC）が発行した、ITサービスマネジメントにおける業務プロセスや管理手法を体系的に整理した書籍群である**ITIL**（Information Technology Infrastructure Library）に基づいています。ITIL は規格ではなく、成功事例を集めた**ベストプラクティス**の書籍群です。ITIL の考え方を、認証可能な要求事項として規格化したものが ISO/IEC 20000 だと整理しておきましょう。

> **ITILの発行元**
> ITIL発行当初の発行元は、英国のCCTA（Central Computer and Telecommunications Agency：中央電子計算機局）である。CCTAはその後OGCに統合された。現在、ITILの管理・運営は民間企業（AXELOS社を経てPeopleCert社）に移管されている。

ITILには、バージョン2、2007年5月にリリースされたバージョン3、バージョン3をマイナーチェンジしたITIL 2011、2019年2月にリリースされたITIL 4などがあります。以前は「バージョン2が現在も広く普及している」と説明されていましたが、現在の最新版はITIL 4であり、バージョン2は歴史的な版として、ISO/IEC 20000 の成り立ちを理解するために学ぶ位置づけです。バージョン2、バージョン3／2011の書籍群を次に示します。

**〈バージョン2〉**

次の七つの書籍からなります。

1. Service Support（サービスサポート）
2. Service Delivery（サービスデリバリ）
3. ICT Infrastructure Management（ICT基盤管理）
4. Security Management（セキュリティ管理）
5. The Business Perspective（ビジネスの観点）
6. Application Management（アプリケーション管理）
7. Planning to Implement Service Management（サービスマネジメント導入計画）

> **ICT**
> Information and Communication Technology（情報通信技術）の略。

**〈バージョン3／2011〉**

次の五つの書籍からなります。

1. Service Strategy（サービスストラテジ）
2. Service Design（サービスデザイン）
3. Service Transition（サービストランジション）
4. Service Operation（サービスオペレーション：サービス運用）
5. Continual Service Improvement（継続的サービス改善：サービスの継続的向上）

| 版 | 着眼点 | 構成 |
|---|---|---|
| バージョン2 | 各**プロセス**に着目 | 7冊（サービスサポート、サービスデリバリが中核） |
| バージョン3／2011 | サービスの**ライフサイクル**に着目 | 5冊（ストラテジ→デザイン→トランジション→オペレーション→継続的改善） |
| ITIL 4 | サービスの**価値**に着目 | サービスバリューシステム（SVS） |

ITILバージョン2では、各プロセスに着目して解説が行われていますが、バージョン3／2011ではサービスのライフサイクルに着目した解説となっています。一方ITIL 4では、サービスの価値に着目した**サービスバリューシステム**（**SVS**）という考えに基づく構成となっています。

ISO/IEC 20000は、ITILに基づき、**PDCAサイクル**によって顧客の要求に組織のITサービス品質を適合させるための最適な体制（**ITサービスマネジメントシステム**：**ITSMS**）を確立・運用し、継続的に評価・改善していくためのフレームワークを提供しています。ITSMS の中には、インシデント管理や問題管理、変更管理といったプロセスが含まれ、第4章 4.8 で学んだセキュリティインシデント管理も、この IT サービスマネジメントの枠組みと連携して運用されます。

> **サービスバリューシステム（SVS）**
> ITIL 4の中核となる概念で、組織が様々な要素や活動を組み合わせて、どのように価値を共創するかを示したモデルである。従うべき原則（Guiding Principles）、ガバナンス、サービスバリューチェーン、プラクティス、継続的改善の要素から構成される。

### 6.3 ISO/IEC 20000の国内における対応状況

ISO/IEC 20000については、2007年4月にJIS化（JIS Q 20000-1:2007、JIS Q 20000-2:2007）され、2020年にJIS Q 20000-1の最新の改訂版が、2023年にJIS Q 20000-2の最新の改訂版が発行されました。

同規格に基づいて組織を評価・認証する「**ITSMS適合性評価制度**」は、一般財団法人日本情報経済社会推進協会（**JIPDEC**）が認定機関となり、2006年7月よりパイロット運用が行われ、2007年4月より本格運用が開始されました。以前は JIPDEC が認定機関でしたが、ISMS適合性評価制度と同じく、2018年からは JIPDEC から独立した一般財団法人情報マネジメントシステム認定センター（ISMS-AC）が認定機関を担っています（第1章 1.3 参照）。組織が ITSMS 認証を取得すると、取引先は「この事業者はサービス品質を維持・改善する仕組みを第三者に確認されている」と判断できます。

## 7. 制御機器の基準 ― EDSA認証

### 7.1 EDSA認証の概要

**EDSA**（Embedded Device Security Assurance）は、**組込み機器である制御機器**のセキュリティ保証に関する認証制度です。米国の**ISCI**（ISA Security Compliance Institute）が運営しており、国内では技術研究組合制御システムセキュリティセンター（**CSSC**）の認証ラボラトリーが認証機関として認証業務を行っています。

> **制御機器のセキュリティ**
> 工場やプラント、社会インフラなどで用いられるPLC（Programmable Logic Controller）やDCS（分散制御システム）のコントローラなどの制御機器は、かつては閉じたネットワーク内で運用されることが前提であった。しかし、近年はネットワーク接続が進み、サイバー攻撃の対象となるリスクが高まったことから、機器単体のセキュリティを第三者が評価・認証する仕組みが求められるようになった。

制御機器が攻撃されると、情報漏えいにとどまらず、工場の停止や設備の破壊、人命にかかわる事故につながります。制御システムでは CIA のうち**可用性**と**完全性**（正しい制御値）が特に重視されるのはこのためです。プラントの発注者は、制御機器を調達するときに EDSA 認証の有無を確認することで、機器が異常な通信を受けても止まらない堅牢性をもつかを判断できます。

### 7.2 EDSA認証における評価項目の概要

EDSA認証の仕様として、**EDSA 2010.1**と新バージョンである**EDSA 2.0.0**の2種類があります。それぞれのバージョンにおける評価項目（カテゴリ）を次に示します。カテゴリごとに詳細な評価項目が設定されています。

| EDSA 2010.1 | EDSA 2.0.0 |
|---|---|
| 通信ロバストネス（堅牢性）試験 | 組込み機器ロバストネス試験 |
| 機能セキュリティ評価 | 組込み機器機能セキュリティ評価 |
| ソフトウェア開発セキュリティ評価 | セキュリティ開発ライフサイクルプロセス評価 |
| ― | 組込み機器セキュリティ開発成果物 |

**EDSA 2010.1**

- 通信ロバストネス（堅牢性）試験
- 機能セキュリティ評価
- ソフトウェア開発セキュリティ評価

**EDSA 2.0.0**

- 組込み機器ロバストネス試験
- 組込み機器機能セキュリティ評価
- セキュリティ開発ライフサイクルプロセス評価
- 組込み機器セキュリティ開発成果物

EDSA 2010.1、EDSA 2.0.0ともに、**3段階の認証レベル**が設定されており、レベルによって評価対象項目数が異なります。ただし、評価対象機器の堅牢性を評価するための試験であるEDSA 2010.1の通信ロバストネス試験及びEDSA 2.0.0の組込み機器ロバストネス試験については、3段階の認証レベルによる違いはなく、評価項目数は同じです。どのレベルを目指す機器でも、異常な通信に耐えることは最低限の条件だからです。

EDSA の評価項目は、製品そのもの（ロバストネス試験・機能評価）と、それを作る開発プロセス（開発ライフサイクル評価）の両方を見ている点で、3節の ISO/IEC 15408 と 4節の CMMI を組み合わせたような構成になっています。

> **ロバストネス（堅牢性）試験**
> 異常なパケットや大量のパケットを機器に送信するなどして、通信上の負荷や想定外の入力に対して、機器が正常に動作し続けられるかを確認する試験である。

> **補足：その後の動向**
> ISCI の認証プログラム（ISASecure）では、EDSA の後継として、制御システムのセキュリティに関する国際規格 IEC 62443 シリーズ（4-1：開発ライフサイクル、4-2：コンポーネントの技術要件）に基づく CSA（Component Security Assurance）認証が設けられている。試験では EDSA の評価項目が問われているため、まず EDSA を押さえる。

## 8. リスク管理の枠組み ― NISTサイバーセキュリティフレームワーク

### 8.1 NISTサイバーセキュリティフレームワークの概要

**NIST**（National Institute of Standards and Technology：米国国立標準技術研究所）の**サイバーセキュリティフレームワーク**（Cyber Security Framework：**CSF**）は、サイバーセキュリティリスクを管理するための指針として策定されたフレームワークです。当初は「重要インフラのサイバーセキュリティを改善するためのフレームワーク」として2014年2月に1.0版が公開され、2018年4月に1.1版、2024年2月に2.0版（**CSF 2.0**）が公開されました。CSF 2.0では、対象が重要インフラに限らず、あらゆる規模・業種の組織に拡大されています。

CSF は認証制度ではありません。組織が自らの現状（現在のプロファイル）と目標（目標のプロファイル）を同じ物差しで比べ、ギャップを埋める計画を立てるための**共通言語**です。経営者・CISO・現場が「いま、どの機能が弱いか」を同じ言葉で話せるようにすることが目的です。

> **試験における出題**
> 情報処理安全確保支援士試験の平成30年度秋期午前Ⅱ（現在の科目A-2）問1で、NISTサイバーセキュリティフレームワークに関する問題が出題されている。

### 8.2 フレームワークコア ― 6つの機能

CSFの中核である「**フレームワークコア**」では、サイバーセキュリティ対策を機能ごとに分類しています。1.1版では**識別、防御、検知、対応、復旧**の五つの機能から構成されていましたが、CSF 2.0では新たに「**統治（Govern）**」が追加され、次の六つの機能から構成されます。

- **統治（Govern）**：組織は、サイバーセキュリティリスクマネジメント戦略や方針を確立し、伝達・監視する。
- **識別（Identify）**：組織は、自組織のサイバーセキュリティリスクを識別する。
- **防御（Protect）**：組織は、リスクの多寡に応じて適切な予防策を講じる。
- **検知（Detect）**：組織は、攻撃や侵害（インシデント）を検知・分析する。
- **対応（Respond）**：組織は、インシデントに対して必要な措置を講じる。
- **復旧（Recover）**：組織は、影響を受けた資産や運用を元通りの状態に復旧する。

> **「識別」の表記**
> 「識別（Identify）」は「特定」と表記される場合もある。

6つの機能は、第1章 1.2 で学んだ対策の4機能と次のように対応します。また、第1章 1.3 で見た ISO/IEC 27002:2022 の属性「サイバーセキュリティ概念（識別・防御・検知・対応・復旧）」は、CSF 1.1 の5機能をそのまま借りたものです。

| CSF 2.0 の機能 | 1.2 の対策の4機能との対応 | 具体策の例 | 関連ノート |
|---|---|---|---|
| 統治 | （すべての土台） | セキュリティ方針、役割と責任、サプライチェーンリスク管理 | 第4章 4.3・4.4 |
| 識別 | （前提となる把握） | 資産台帳、リスクアセスメント | 第4章 4.1・4.5 |
| 防御 | 抑止・抑制、予防・防止 | アクセス制御、暗号化、教育 | 第5〜7章 |
| 検知 | 検知・追跡 | IDS、SIEM、ログ監視 | 第5章 5.6、第7章 7.8 |
| 対応 | （回復の前段） | CSIRT による封じ込め、報告 | 第4章 4.8 |
| 復旧 | 回復 | バックアップからの復元、事業継続 | 第4章 4.9、第7章 7.9 |

「統治」が追加されたのは、技術的な対策（防御・検知など）だけでは不十分で、経営者が方針を決め、責任を持って監督することが全ての土台になる、という考え方を明確にするためです。9.3 で学ぶサイバーセキュリティ経営ガイドラインの「経営者の責務」と同じ方向の変化です。

### 8.3 フレームワークインプリメンテーションティア

CSFでは、組織のサイバーセキュリティリスク管理策がどの程度達成できているかを示す段階として、**フレームワークインプリメンテーションティア**（**ティア**）1から4までを次のように定義しており、ティア4が最も高い段階です。

| ティア | 名称 | 一言でいうと |
|---|---|---|
| ティア1 | 部分的である（Partial） | 場当たり的。事後対処 |
| ティア2 | リスク情報を活用している（Risk Informed） | 経営層は承認しているが、全社ポリシにはなっていない |
| ティア3 | 繰り返し適用可能である（Repeatable） | 全社ポリシとして定められ、定期的に更新される |
| ティア4 | 適応している（Adaptive） | 教訓と兆候を基に継続的に改善し、変化に順応する |

**ティア1：部分的である（Partial）**

リスクマネジメントプロセス ― 組織のサイバーセキュリティリスクマネジメントプラクティスが定められておらず、リスクは場当たり的に、場合によっては事後に対処される。サイバーセキュリティ対策の優先順位付けが、組織のリスク目標、脅威環境、またはビジネス・ミッションの要求事項に基づいていない。

**ティア2：リスク情報を活用している（Risk Informed）**

リスクマネジメントプロセス ― リスクマネジメントプラクティスは経営層によって承認されているが、組織全体にわたるポリシーとして定められていない場合がある。サイバーセキュリティ対策と保護ニーズの優先順位付けは、組織のリスク目標、脅威環境、またはビジネス・ミッション上の要求事項に直接基づいて行われている。

**ティア3：繰り返し適用可能である（Repeatable）**

リスクマネジメントプロセス ― 組織のリスクマネジメントプラクティスは経営層によって承認され、ポリシーとして明確に定められている。組織のサイバーセキュリティプラクティスは、ビジネス・ミッション上の要求事項の変化や、脅威及び技術を取り巻く状況の変化に応じて、リスクマネジメントプロセスを適用することにより定期的に更新されている。

**ティア4：適応している（Adaptive）**

リスクマネジメントプロセス ― 自組織は過去と現在のサイバーセキュリティプラクティス（そこから学んだ教訓と、それらの対策から得た兆候を含む）を基に、サイバーセキュリティ対策を調整する。自組織は最新のサイバーセキュリティ技術及びプラクティスを組み入れた継続的な改善のためのプロセスを介して、変化するサイバーセキュリティの技術と実践に進んで順応し、進化・高度化する脅威にタイムリーかつ効果的に対応している。

> **ティアの位置付け**
> ティアは成熟度モデルそのものではなく、組織がサイバーセキュリティリスクをどの程度厳格かつ高度に管理しているかを示す指標である。必ずしもすべての組織がティア4を目指す必要はなく、組織のリスク目標や資源に応じて目標とするティアを設定することが推奨されている。

ここが 4節の CMMI との違いです。CMMI の成熟度レベルは「高いほど良い」段階ですが、CSF のティアは「自組織のリスクに見合った水準を選ぶ」ものです。小規模な組織がティア4を目指して過剰な投資をする必要はありません。

### 9.1 理解度チェック（Check!）

- 【Q1】ISO/IEC 15408では何を評価・認証の対象としているか。
- 【Q2】ST、PPとは何か。
- 【Q3】セキュリティ機能コンポーネントとは何か。
- 【Q4】セキュリティ保証コンポーネントとは何か。
- 【Q5】EALの概要について述べよ。
- 【Q6】CMMIは何を目的としているか。
- 【Q7】CMMIの二つの評価モデルの概要を述べよ。
- 【Q8】ISO/IEC 15408とCMMI-DEVはそれぞれどのような特徴があり、どのような場面に用いるべきか。
- 【Q9】PCI DSSの概要について述べよ。
- 【Q10】PCI DSSの主な要件と、その特徴について述べよ。
- 【Q11】PCI DSSに基づく認定プログラムの概要について述べよ。
- 【Q12】ITSMSとは何か。
- 【Q13】ITILとは何に関する書籍群か。
- 【Q14】EDSA認証の概要について述べよ。
- 【Q15】NIST CSF 2.0における6つの機能について述べよ。

### 9.2 解答例

- **A1**：OS、アプリケーション、通信機器、情報家電など、セキュリティ機能を備えたIT関連**製品**と、それらを組み合わせた**情報システム**を対象とする。出荷・運用に先立って必要なセキュリティ対策が実装されているかまでを評価し、組織の規程の整備・運用状況や、導入後の運用は対象外である（本ノート3.1）。
- **A2**：ST（セキュリティターゲット、セキュリティ基本設計書）は、開発者が評価対象（TOE）ごとに作成するセキュリティ仕様書で、セキュリティ課題定義、対策方針、セキュリティ機能要件・保証要件などを記述する。PP（プロテクションプロファイル、セキュリティ要求仕様書）は、同一分野の製品に共通して使えるように汎用化した要求仕様書で、調達者や業界団体が作成することが多い。ST は PP への適合を示すことで記述の一部を省略できる（3.3）。
- **A3**：ISO/IEC 15408 Part2 で規定される、TOE が備えるべきセキュリティ**機能要件**（SFR）の部品群。FAU（セキュリティ監査）、FIA（識別と認証）、FCS（暗号サポート）など11の機能クラスに分類され、クラス→ファミリ→コンポーネントの階層で詳細化される（3.4）。
- **A4**：ISO/IEC 15408 Part3 で規定される、機能要件が**正しく実装されていることを保証するための要件**（SAR）の部品群。ASE（ST評価）、ADV（開発）、ATE（テスト）、AVA（脆弱性評定）など9の保証クラスに分類され、クラス→ファミリ→コンポーネントの階層で詳細化される（3.5）。
- **A5**：EAL（評価保証レベル）は、Part5 の定義済みパッケージの代表で、保証の厳格さを EAL1（機能テスト）から EAL7（形式的検証済み設計及びテスト）までの7段階で示す。数字が大きいほど評価の範囲・深さ・厳密さが増す。機能の多さではなく保証の深さを表す（3.6）。
- **A6**：システム開発を行う組織が、自らの開発プロセスの成熟度を評価し、**プロセス改善**を行うためのガイドラインとすることを目的とする（4.1）。
- **A7**：段階表現は、組織の成熟度を1〜5の**成熟度レベル**（初期、管理された、定義された、定量的に管理された、最適化している）で表し、段階的な改善を前提に複数のプロセス領域にわたって評価する。連続表現は、0〜3の**能力レベル**（不完全な、実施された、管理された、定義された）で、個々のプロセス領域ごとの改善の達成度を評価する（V1.3。4.2）。
- **A8**：ISO/IEC 15408 は**製品・システム**を対象に、詳細な仕様書と厳密な完成品を評価するもので、アップデートが比較的少ない製品を広く提供するベンダーが、製品のセキュリティ品質を示すために認証を取得する場面に向く。CMMI-DEV は**開発組織**を対象に、品質確保の取組みが組織的に行われ継続的に改善されているかを評価するもので、大規模開発を行うベンダーが組織の開発品質を高めるために定期的に測定・評価する場面に向く（4.5）。
- **A9**：国際ペイメントブランド5社（MasterCard、VISA、JCB、American Express、Discover）が、クレジットカード情報や取引情報の保護を目的として共同で策定したセキュリティ基準で、PCI SSC が管理・改訂する。現在有効な版は4.0.1（2024年6月）である（5.1）。
- **A10**：6つの目標の下に12の要件（ネットワークセキュリティコントロール、セキュアな設定、保存データの保護、送信時の暗号化、マルウェア対策、安全な開発、Need to Know によるアクセス制限、識別と認証、物理アクセス制限、ログ記録と監視、定期的なテスト、方針）がある。技術的対策が中心で、NSC の設定を6か月に1回見直す、監査ログを12か月保持し直近3か月は即時利用可能にする、重要なパッチを1か月以内に適用する、のように**頻度や期間が具体的に示されている**のが特徴。ポリシ整備や物理的対策も含む（5.2）。
- **A11**：認定プログラムはカードブランドごとに定められ、加盟店、イシュアー、アクワイアラー、TPP などが対象となる。年間の取引件数などで対象者をレベル分けし、レベルに応じたバリデーション（受けるべき診断の種類と頻度）として、QSA によるオンサイト調査、ASV による脆弱性スキャン、SAQ による自己診断が定められている（5.3）。
- **A12**：ITサービスマネジメントシステム。ITIL に基づき、PDCA サイクルによって顧客の要求に組織の IT サービス品質を適合させるための体制を確立・運用し、継続的に評価・改善する仕組みで、ISO/IEC 20000-1（JIS Q 20000-1）が要求事項、ITSMS適合性評価制度がその認証制度である（6.2・6.3）。
- **A13**：IT サービスマネジメントにおける業務プロセスや管理手法を体系的に整理した、ベストプラクティスの書籍群（英国 OGC が発行。現在の最新版は ITIL 4）（6.2）。
- **A14**：組込み機器である制御機器のセキュリティ保証に関する認証制度で、米国 ISCI が運営し、国内では CSSC の認証ラボラトリーが認証業務を行う。EDSA 2.0.0 では、組込み機器ロバストネス試験、組込み機器機能セキュリティ評価、セキュリティ開発ライフサイクルプロセス評価、組込み機器セキュリティ開発成果物の4カテゴリを評価し、3段階の認証レベルがある（ロバストネス試験はレベルによらず同じ）（7節）。
- **A15**：統治（リスクマネジメント戦略・方針の確立・伝達・監視）、識別（リスクの識別）、防御（適切な予防策）、検知（インシデントの検知・分析）、対応（インシデントへの措置）、復旧（資産・運用の復旧）の6つ。1.1版の5機能に「統治」が追加された（8.2）。

### 9.3 過去問題1：NISTサイバーセキュリティフレームワーク

NIST"サイバーセキュリティフレームワーク：重要インフラのサイバーセキュリティを改善するためのフレームワーク1.1版"における"フレームワークコア"を構成する機能はどれか。

- ア　観察、状況判断、意思決定、行動
- イ　識別、防御、検知、対応、復旧
- ウ　準備、検知と分析、封じ込め／根絶／復旧、事件後の対応
- エ　責任、戦略、パフォーマンス、適合、人間行動

［情報処理安全確保支援士試験 午前Ⅱ］

**解答・解説**

NISTサイバーセキュリティフレームワーク1.1版では、セキュリティ対策を、識別、防御、検知、対応、復旧の五つのフレームワークコアに分類している。したがって**イ**が正解。なお、CSF 2.0 では「統治」が加わって6機能になっているため、問題文の版（1.1版）を必ず確認すること。

> **他の選択肢について**
> アは意思決定プロセスであるOODAループ（第4章 4.8）、ウはNIST SP 800-61（コンピュータセキュリティインシデント対応ガイド）におけるインシデント対応のライフサイクル、エはISO/IEC 38500（ITガバナンス）の六つの原則のうちの五つである。

### 9.4 過去問題2：EDSA認証

EDSA認証における評価対象と評価項目について、適切な組合せはどれか。

| | 評価対象 | 評価項目 |
|---|---|---|
| ア | 組込み機器である制御機器 | 組込み機器ロバストネス試験 |
| イ | 組込み機器である制御機器が運用されている施設 | 入退室管理の評価 |
| ウ | 複数の制御機器から構成される制御システム | 脆弱性試験 |
| エ | 複数の制御機器から構成される制御システムを管理する組織 | セキュリティポリシーの評価 |

［情報処理安全確保支援士試験 午前Ⅱ］

**解答・解説**

EDSA（Embedded Device Security Assurance）は、組込み機器である制御機器を評価対象とした認証制度である。EDSAの新バージョンであるEDSA 2.0.0における評価項目は「組込み機器ロバストネス（堅牢性）試験」「組込み機器機能セキュリティ評価」「セキュリティ開発ライフサイクルプロセス評価」「組込み機器セキュリティ開発成果物」の4項目である。したがって**ア**が正解。イ〜エは、評価対象を施設・システム・組織に広げている点で誤りである。EDSA は名前のとおり「Embedded Device（組込み機器）」単体の認証だと覚えておけば、評価対象の列だけで正解を選べる。

## 10. 試験対策まとめ（重要ポイント）

### 10.1 知識の確認（科目A-2向け）

- **規格・法律・ガイドライン**：法律は国会が定め強制力（罰則）がある。規格は任意だが、契約・調達要件・認証の条件になると事実上の義務になる。法律の解釈を示すガイドラインは、従わないと法違反と判断され得る。
- **規格番号の読み方**：ISO/IEC 27001:2022 の「:2022」は発行年。JIS Q 27001:2023 はその一致規格で、Q は管理システム、X は情報処理の部門記号。JIS は以前「日本工業規格」、現在は「日本産業規格」。
- **要求事項と手引**：認証の基準は要求事項の規格（27001、20000-1、JIS Q 15001、22301）。27002・20000-2 はガイドラインで認証基準ではない。
- **認定と認証**：認定機関（ISMS-AC、IAJapan）が認証機関・評価機関を「認定」し、認証機関が組織・製品を「認証」する。入れ替えた選択肢に注意。
- **評価対象の区別**：ISMS・Pマーク・ITSMS・BCMS は**組織**、ISO/IEC 15408（JISEC）は**製品・システム**、JCMVP は**暗号モジュール**、ISMAP は**クラウドサービス**、EDSA は**制御機器**、CMMI は**開発組織のプロセス**。
- **ISMS と Pマーク**：ISMS は適用範囲を限定でき3年ごとに更新審査、Pマークは原則法人単位で2年ごとに更新。
- **ISO/IEC 15408**：出荷前の実装までを評価し、導入後の運用は対象外。ST は開発者が製品ごと、PP は調達者等が分野ごとに作る。
- **機能と保証**：Part2 の機能クラスは「F」で始まる11クラス（FAU、FCS、FIA、FDP など）、Part3 の保証クラスは「A」で始まる9クラス（ASE、ADV、ATE、AVA など）。
- **EAL**：EAL1（機能テスト）〜EAL7（形式的検証済み設計及びテスト）。数字が大きいほど保証が深い。機能の強さではない。
- **JISEC の分業**：評価機関（IAJapan が認定）が評価し、IPA が認証。評価方法は ISO/IEC 18045（CEM）。日本は2003年に CCRA に Certificate authorizing participants として加盟。
- **CMMI**：段階表現は成熟度レベル1〜5、連続表現は能力レベル0〜3（V1.3。V1.2 では0〜5）。公式な評定は SCAMPI クラスA（V1.3 まで）。管理は SEI から CMMI Institute（ISACA 傘下）へ。
- **SSE-CMM**：セキュリティ工学に特化した CMM。NSA がスポンサー、ISSEA が運用、ISO/IEC 21827。
- **PCI DSS**：国際ペイメントブランド5社、PCI SSC が管理。12要件、頻度・期間が具体的（NSC 見直し6か月、ログ12か月保持・3か月即時利用、重要パッチ1か月以内）。QSA＝オンサイト調査、ASV＝外部脆弱性スキャン、SAQ＝自己診断。現在の版は4.0.1。
- **ISO/IEC 20000 と ITIL**：20000-1 が要求事項（27001 相当）、20000-2 が手引（27002 相当）。ITIL はベストプラクティスの書籍群で、V2＝プロセス、V3/2011＝ライフサイクル（5冊）、ITIL 4＝価値（SVS）。
- **EDSA**：組込み機器である制御機器が対象。ISCI 運営、国内は CSSC。EDSA 2.0.0 は4カテゴリ、3段階の認証レベル、ロバストネス試験はレベル共通。
- **NIST CSF**：1.1版は識別・防御・検知・対応・復旧の5機能、2.0版（2024年2月）は統治を加えた6機能。ティア1〜4 は成熟度モデルそのものではなく、全組織がティア4を目指す必要はない。

### 10.2 記述式で問われる観点（科目B向け）

- **委託先の選定**：「委託先の ISMS 認証の**適用範囲**に、委託する業務・拠点が含まれているか、登録が有効期限内で現行版（JIS Q 27001:2023）によるものかを確認すべきである。適用範囲外の業務は認証によって何も保証されないからである。」
- **製品の選定**：「調達担当者は、JISEC の認証製品リストで、導入する製品の**版**が認証されたものか、ST の**前提条件**と運用環境の対策方針を自組織が満たせるかを確認すべきである。CC 認証は出荷時点の実装を保証するだけで、導入後の運用を保証しないからである。」
- **認証の限界**：「認証を取得していても、インシデントが起きないことは保証されない。認証は仕組みが規格どおり運用されていることの確認であり、発注者は契約で報告義務や監査権を定めて、自らも委託先を管理すべきである。」
- **PCI DSS の要件の当てはめ**：事例のログ保存期間やパッチ適用期間を PCI DSS の数値（12か月・3か月、1か月以内、6か月ごとの見直し）と照らし、「どの要件を満たしていないか」「どう是正すべきか」を指摘できるようにする。
- **規格と法律の区別**：「この対策は個人情報保護法上の義務か、JIS Q 15001 上の要求か」を区別して書く。法律上の義務は全事業者に及ぶが、規格上の要求は認証を取得・維持する組織に及ぶ。
- **フレームワークによる現状評価**：NIST CSF の6機能で自組織の対策を棚卸しし、「検知と対応が弱い」のように不足する機能を特定して、目標とするティアと優先順位を経営層に説明する、という流れで改善計画を書けるようにしておく。
