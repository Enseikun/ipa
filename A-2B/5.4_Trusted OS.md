## 0. 全体像 ― なぜこの分野を学ぶのか

5.2「ホストの要塞化」と 5.3「脆弱性診断」で、サーバの弱点を減らし、残った弱点を見つける方法を学びました。それでも、未知の脆弱性（ゼロデイ）を突かれてサーバに侵入されることは完全には防げません。そして一般的なOSでは、攻撃者が管理者（root）の権限を奪った瞬間に、ファイルの読み書き、ログの消去、別のサーバへの攻撃まで、何でもできてしまいます。

「侵入されても、被害をそのプロセスの中に閉じ込められないか」「rootを奪われても、なお守れないか」。この問いに対するOS側の答えが、本ノートで学ぶ **Trusted OS**（信頼されたオペレーティングシステム）と、その考え方を取り入れた **SELinux** です。Trusted OSとは、セキュリティ機能を強化するとともに、設計仕様書やマニュアル類を整備し、定められた検証テストをクリアしたOSのことです。

本ノートは次の順で進みます。

1. **Trusted OSとは何か**：「信頼された」の意味と、評価基準TCSEC
2. **通常のOSとの違い**：任意アクセス制御（DAC）と強制アクセス制御（MAC）を、パーミッション表示とラベルの見た目で対比する
3. **TCSECとレインボーシリーズ**：評価基準の歴史と、コモンクライテリアへの発展
4. **SELinux**：セキュリティコンテキスト、TE、RBAC、Flaskアーキテクチャ
5. **セキュアOS**：日本での呼び方と、SELinux以外の実装

1.2 で学んだ設計原則でいえば、Trusted OSは「最小権限の原則」をOSのカーネルで強制する仕組みです。対策の4機能では、侵入後の被害拡大を抑える「予防・防止」と、操作を記録する「検知・追跡」を担います。アクセス制御モデル（DAC・MAC・RBAC）の一般論は第6章 6.1「アクセス制御」で扱うので、ここではOSへの実装に焦点を当てます。

科目Bの業務観点では「②情報システムの企画・設計・開発・運用におけるセキュリティ確保」（サーバのセキュリティ機能の設計）と「③利用におけるセキュリティ対策の適用」（アカウント管理とアクセス管理）に対応します。科目A-2では強制アクセス制御の定義、DACとの違い、SELinuxの特徴（rootも制限される）が問われます。

## 1. Trusted OSとは何か

### 1.1 「信頼された」の意味

もともとは、米国国防総省が定めたセキュリティ評価認証基準である **TCSEC**（Trusted Computer System Evaluation Criteria：通称「**オレンジブック**」）に代表される「**レインボーシリーズ**」において、「**B DIVISION**」以上の要求基準をクリアしたOSを「Trusted OS」と呼びます。

> **Trusted OS**
> 「信頼された（Trusted）」とは、単にセキュリティ機能が豊富であることを指すのではない。機能の正しさが設計文書や検証によって第三者に示され、評価基準に基づいて保証されていることを意味する。

この「機能があること」と「機能が正しいと保証されていること」の区別は、Trusted OSを理解するうえで最も大切な点です。鍵がたくさん付いたドアでも、鍵の作りに欠陥があれば意味がありません。Trusted OSは、鍵の設計図を公開し、第三者の検査に合格したドアにあたります。後で見るように、SELinuxは強力なセキュリティ機能をもちながら、この「保証」の面を理由に、開発元のNSA自身がTrusted OSとは呼んでいません。

## 2. 通常のOSとの違い ― DACとMAC

### 2.1 通常のOSの弱点 ― 任意アクセス制御とrootへの権限集中

一般的なOSでは、ファイルの所有者が自由にアクセス権を設定できる**任意アクセス制御**（**DAC**：Discretionary Access Control）が採用されています。また、管理者（UNIX系OSでは **root**）にはすべての権限が集中しています。そのため、攻撃者が管理者権限を奪うと、システム全体が攻撃者の支配下に置かれてしまいます。

DACの「見た目」を確認しましょう。Linuxで `ls -l` を実行すると、ファイルごとに所有者と、所有者・グループ・その他の利用者それぞれの読み（r）・書き（w）・実行（x）の許可が表示されます。

```
$ ls -l /var/www/html/index.html /home/taro/salary.xlsx /etc/shadow
-rw-r--r--. 1 apache apache 1024 Sep 30 10:00 /var/www/html/index.html
-rw-rw-rw-. 1 taro   taro   8192 Sep 30 09:12 /home/taro/salary.xlsx
----------. 1 root   root   1350 Sep 30 08:00 /etc/shadow
```

2行目に注目してください。所有者の taro が、うっかり（あるいは共有したくて）`chmod 666` を実行したために、給与ファイルが「その他の利用者」にも読み書き可能（`rw-`）になっています。DACでは、アクセス権を決めるのは**所有者の裁量**（discretion）なので、組織のポリシ上は許されない設定でも、OSはそのまま受け入れます。

3行目の `/etc/shadow`（パスワードのハッシュ値が入ったファイル）は誰にも権限がありませんが、rootはパーミッションの検査を受けずに読み書きできます。つまり、DACのもとでは次の2つの弱点があります。

- 利用者（や、利用者の権限で動くマルウェア）が、ファイルのアクセス権を勝手に緩められる。
- rootを奪われると、パーミッションは一切の歯止めにならない。

### 2.2 Trusted OSの特徴 ― 強制アクセス制御と最小特権

これに対してTrusted OSは、主に次のような特徴を備えています。

- **強制アクセス制御**（**MAC**：Mandatory Access Control）：OSは、システム全体のセキュリティポリシに基づき、管理者を含むすべての利用者のアクセスを強制的に制限する。
- **最小特権**：OSは、管理者の権限を細分化し、各プロセスや利用者には業務に必要な最小限の権限だけを与える。
- **監査機能**：OSは、セキュリティに関わる操作を記録し、追跡を可能にする。
- **保証（アシュアランス）**：開発者は、設計仕様書やマニュアル類を整備し、第三者による評価・検証を受けている。

MACの「見た目」は、ファイルやプロセスに付いた**ラベル**です。SELinuxを有効にしたLinuxで `ls -Z` を付けると、パーミッションに加えてラベル（セキュリティコンテキスト）が表示されます。先ほどの `ls -l` の出力で、パーミッションの末尾にあった「`.`」は、このラベルが付いていることを示す印でした。

```
$ ls -lZ /var/www/html/index.html /home/taro/salary.xlsx /etc/shadow
-rw-r--r--. 1 apache apache system_u:object_r:httpd_sys_content_t:s0 1024 Sep 30 10:00 /var/www/html/index.html
-rw-rw-rw-. 1 taro   taro   unconfined_u:object_r:user_home_t:s0     8192 Sep 30 09:12 /home/taro/salary.xlsx
----------. 1 root   root   system_u:object_r:shadow_t:s0            1350 Sep 30 08:00 /etc/shadow

$ ps -eZ | grep httpd
system_u:system_r:httpd_t:s0     2345 ?        00:00:01 httpd
```

そしてポリシには、「`httpd_t`（Webサーバのプロセス）は `httpd_sys_content_t`（Web公開用のファイル）を読んでよい」とだけ書かれています。すると、Webアプリケーションの脆弱性を突かれてWebサーバのプロセスが乗っ取られ、攻撃者がさらにroot権限を得たとしても、そのプロセスのドメインが `httpd_t` である限り、`user_home_t` の給与ファイルも `shadow_t` のパスワードファイルも読めません。taro が `chmod 666` でパーミッションを緩めても、ラベルによる制限は所有者には変えられないので、結果は同じです。

拒否されたアクセスは、監査ログに次のような1行として記録されます。

```
type=AVC msg=audit(1790731522.123:456): avc:  denied  { read } for  pid=2345 comm="httpd"
  name="shadow" dev="dm-0" ino=12345 scontext=system_u:system_r:httpd_t:s0
  tcontext=system_u:object_r:shadow_t:s0 tclass=file permissive=0
```

「httpd プロセス（`scontext`＝主体のラベル `httpd_t`）が、shadow ファイル（`tcontext`＝対象のラベル `shadow_t`）の read を拒否された（`denied`）」と読みます。Webサーバが /etc/shadow を読もうとすることは正常な業務ではありえないので、この1行は侵入の強い兆候です。MACは被害を止めると同時に、検知・追跡の手がかりも残してくれるわけです。

### 2.3 DACとMACの対比

| 観点 | 任意アクセス制御（DAC） | 強制アクセス制御（MAC） |
|---|---|---|
| 誰がアクセス権を決めるか | オブジェクト（ファイル）の**所有者**が任意に決める | **セキュリティ管理者**が定めたシステム全体のポリシで決まる |
| 判断材料 | 所有者・グループ・パーミッション（`rw-r--r--`） | 主体と対象のラベル（`httpd_t` と `shadow_t` など） |
| 所有者による変更 | できる（`chmod` で自由に緩められる） | できない |
| rootへの適用 | rootは検査を受けない（全権限） | rootも含めてすべての利用者・プロセスが制限される |
| 乗っ取られた場合の被害 | 乗っ取られたプロセスの利用者権限すべて（rootならシステム全体） | そのプロセスのドメインに許された範囲だけ |
| 代表例 | 一般的なUNIX/Linux、Windowsのアクセス権 | SELinux、Trusted Solaris |
| TCSECでの位置づけ | C1（DAC）、C2 | B1以上（ラベルによるMAC） |

TCSECが本来想定していたMACは、軍事用の機密区分（例：「機密」「極秘」）をラベルとして人とファイルに付け、「自分より上の区分の文書は読めない」「自分より下の区分に書き出せない（情報を漏らせない）」という規則をOSが強制する**多段階セキュリティ**（MLS）でした（ベル・ラパドゥラモデル）。SELinuxのラベル末尾にある `s0` は、この区分（レベル）を表す欄です。

### 2.4 代表的な製品

代表的なTrusted OS製品としては、Trusted Solaris（現在は Solaris Trusted Extensions に統合）、HP-UX BLS、PitBull などがあります。

## 3. TCSECとレインボーシリーズ（Column）

### 3.1 TCSECのセキュリティ要求レベル

TCSECは、米国国防総省下の **NSA**（National Security Agency：国家安全保障局）に設置された **NCSC**（National Computer Security Center：国立コンピュータセキュリティセンター）により、軍用調達のためのコンピュータシステムの評価基準として1983年に作成されました。その後、1985年の改定を経て国防総省標準（DoD 5200.28-STD）となりました。TCSECは、徹底的なアクセス制御によって高い機密性を確保することを求めており、システムのセキュリティ要求レベルを次のような「DIVISION」と「CLASS」に分類しています。

**表：TCSECにおけるセキュリティ要求レベルの分類**

| DIVISION | CLASS | 概要 |
|---|---|---|
| D：MINIMAL PROTECTION | ― | 上位クラスの要件を満たさないもの |
| C：DISCRETIONARY PROTECTION | C1：DISCRETIONARY SECURITY PROTECTION | 利用者の識別・認証と任意アクセス制御（DAC） |
| | C2：CONTROLLED ACCESS PROTECTION | C1に加え、監査ログ、オブジェクト再利用の防止など |
| B：MANDATORY PROTECTION | B1：LABELED SECURITY PROTECTION | セキュリティラベルによる強制アクセス制御（MAC） |
| | B2：STRUCTURED PROTECTION | 形式的セキュリティポリシモデル、隠れチャネル分析、最小特権 |
| | B3：SECURITY DOMAINS | 参照モニタの実装、セキュリティ管理者の役割分離 |
| A：VERIFIED PROTECTION | A1：VERIFIED DESIGN | 形式的手法による設計の検証 |

表を下に行くほど要求が厳しくなります。DIVISIONの名前がそのまま特徴を表しているので、「C＝Discretionary（任意）」「B＝Mandatory（強制）」「A＝Verified（検証済み）」と覚えると、「Trusted OS＝B以上＝MACをもつOS」という定義とつながります。B3の**参照モニタ**は、すべてのアクセス要求を必ず仲介し、ポリシに照らして許可・拒否する仕組みのことで、4.2 で見るSELinuxのFlaskアーキテクチャはこの考え方を実装したものです。

なお、TCSECはスタンドアロンシステムとしての堅牢さを評価しているため、ネットワークからの侵入や攻撃に対する堅牢さについては保証していません。TCSECの規定をネットワークに適用させるとともに、暗号化などの機能を追加した規格としては、1987年に発行された **TNI**（Trusted Network Interpretation of the TCSEC：通称「**レッドブック**」）があります。なお、「オレンジブック」や「レッドブック」などの呼称は、表紙の色から付けられたものです。

### 3.3 TCSECのその後 ― コモンクライテリアへ

> **TCSECのその後**
> TCSECは、欧州の **ITSEC**、カナダの **CTCPEC** などと統合される形で、国際標準の**コモンクライテリア**（**CC**：**ISO/IEC 15408**）へと発展した。現在は、CCに基づく**保護プロファイル**（PP）と**評価保証レベル**（**EAL**）によってOSのセキュリティ評価が行われている。

OS向けの保護プロファイルについては、以前は CAPP（DAC相当）、**LSPP**（ラベルによるMAC相当）、**RBACPP**（ロールベースアクセス制御）などが使われていましたが、現在はこれらを統合した汎用OS向けの保護プロファイル（OSPP など）に移行しています。TCSECの「B1＝ラベルによるMAC」の考え方は、LSPPを経て現在の保護プロファイルに受け継がれています。日本では、CCに基づく製品評価の制度として **JISEC**（ITセキュリティ評価及び認証制度）がIPAによって運営されています。

| 観点 | TCSEC | コモンクライテリア（ISO/IEC 15408） |
|---|---|---|
| 策定 | 米国国防総省（NCSC） | 国際標準（ISO/IEC） |
| 評価の軸 | D〜A1のクラスで「機能」と「保証」を一体で評価 | 保護プロファイルで「機能要件」を、EALで「保証の深さ」を分けて評価 |
| ネットワーク | 対象外（TNIで補完） | 製品ごとに保護プロファイルで定義 |

## 4. SELinux

### 4.1 SELinuxとは

**SELinux**（Security-Enhanced Linux）は、NSAが中心となって開発したLinux向けのセキュリティ拡張機能です。2000年にオープンソースとして公開され、その後、**LSM**（Linux Security Modules）の仕組みを通じてLinuxカーネル2.6系に標準で取り込まれました。現在では、Red Hat Enterprise LinuxやFedoraなど多くのディストリビューションで利用されています。

SELinuxでは、すべてのプロセスに対して、セキュリティポリシで許可された範囲のアクセスだけが認められます。従来のLinux環境では絶対的な権限をもつ「root」であっても、この制限を回避することはできません。そのため、仮に攻撃者に侵入や攻撃を受けたとしても、システム全体が乗っ取られることはなく、被害を最小限にとどめることができます。2.2 で見た「乗っ取られたWebサーバのプロセスが、root権限でも /etc/shadow を読めない」という動きがこれです。

SELinuxのセキュリティアーキテクチャは、**Flask**（Flux Advanced Security Kernel）と呼ばれます。Flaskは、NSAがSecure Computing社とユタ大学の支援を受けて開発した技術であり、柔軟な強制アクセス制御（Mandatory Access Control：MAC）を実現します。

### 4.2 SELinuxにおけるセキュリティ機能

SELinuxにおける主なセキュリティ機能の概要を次に示します。4つの機能は、「ラベルを付ける（①）」「ラベル同士の関係でアクセスを決める（②）」「人の役割で使えるラベルを絞る（③）」「判断を一か所に集める（④）」という役割分担になっています。

**① セキュリティコンテキストによる強制アクセス制御**

SELinuxは、スーパユーザ（root）を含むすべてのユーザに対して、プロセス（**サブジェクト**）やファイルなどのリソース（**オブジェクト**）に付与されたセキュリティラベルに応じた、強力かつきめ細かなアクセス制御を行います。このセキュリティラベルは、**セキュリティコンテキスト**と呼ばれています。

> **セキュリティコンテキスト**
> 一般に「ユーザ:ロール:タイプ（:レベル）」の形式で表される。例えば、Webサーバのプロセスには `system_u:system_r:httpd_t` のようなコンテキストが付与される。ファイルのコンテキストは `ls -Z`、プロセスのコンテキストは `ps -Z` コマンドで確認できる。

```
system_u : system_r : httpd_t : s0
   │          │          │       └ レベル（MLS/MCSの区分。2.3 の多段階セキュリティ）
   │          │          └ タイプ（プロセスなら「ドメイン」。アクセス判断の主役）
   │          └ ロール（③ RBAC で使う）
   └ SELinuxユーザ（Linuxのログイン名とは別に対応づけられる）
```

**② TE（Type Enforcement）**

SELinuxは、ファイル、デバイス、ディレクトリ、ソケットなど各オブジェクトの種類ごとに、**アクセスベクタ**と呼ばれる詳細なパーミッションの集合を定義してアクセス制御を行います。あるサブジェクトがオブジェクトにアクセスするためには、両者の関係において、そのアクセス方法が、対象となるサブジェクトのアクセスベクタの定義上で許可されている必要があります。

パーミッションの種類は非常に細かく定義されており、例えばファイルに対するパーミッションとしては、read、write、append、poll、ioctl、create、execute、link、unlink、lock、rename などがあります。この仕組みを **TE**（**Type Enforcement**）と呼びます。TEでは、プロセスに付与されるタイプを特に「**ドメイン**」と呼び、「どのドメインが、どのタイプのオブジェクトに対して、どの操作を行えるか」をポリシとして記述します。ポリシの1行は、たとえば次のような形です。

```
allow httpd_t httpd_sys_content_t : file { read getattr open };
      ─┬───── ─────┬───────────   ─┬─  ──────────┬──────────
     ドメイン     対象のタイプ     クラス     許可する操作（アクセスベクタ）
```

DACの `rwx` が3種類しかないのに対し、TEでは「追記（append）はよいが上書き（write）は不可」のように細かく決められます。たとえばログファイルに `append` だけを許可すれば、侵入者がプロセスを乗っ取っても過去のログを書き換えて痕跡を消すことはできません。ポリシに書かれていない組合せはすべて拒否される点も重要で、これは 5.5 で学ぶファイアウォールの「暗黙の拒否」と同じ発想です。

**③ RBAC（Role-Based Access Control）**

**RBAC** は、ユーザに「**ロール**（役割）」を割り当て、ロールごとに遷移可能なドメインを制限する仕組みです。これにより、同じrootユーザであっても、割り当てられたロールによって実行できる操作が制限されます。従来のrootに集中していた権限を役割ごとに分割することで、最小特権を実現できます。

たとえば、Webサーバの運用担当者にはWebサーバの設定変更に必要なロールだけを、バックアップ担当者にはバックアップに必要なロールだけを与えます。どちらも `sudo` でrootになれるとしても、ロールが違えば入れるドメインが違うので、Webサーバの担当者がデータベースのファイルに触れることはできません。1.2 で学んだ「職務分離」をOSの機能として実現したものといえます。

**④ Flaskアーキテクチャによるアクセス制御**

Flaskアーキテクチャは、実際にアクセス制御を実施する**オブジェクトマネージャ**と、アクセス可否の判断を行う**セキュリティサーバ**とから構成されています。オブジェクトマネージャは、アクセス要求が発生するとセキュリティサーバに問い合わせ、その判断結果に従ってアクセスを許可または拒否します。判断結果は **AVC**（Access Vector Cache）にキャッシュされるため、問い合わせによる性能低下が抑えられています。2.2 の監査ログの先頭にあった `type=AVC` は、このAVCで拒否が判断されたことを示しています。

セキュリティサーバは、起動時にセキュリティポリシを読み込み、外部からパーミッションチェック要求があると、自身の保持しているセキュリティポリシに基づいたパーミッションチェックを実行し、その結果を通知します。また、システム稼働中にセキュリティポリシを動的に読み込み、変更する機能も提供しています。

```
 [プロセス] ──アクセス要求──▶ [オブジェクトマネージャ]（ファイル、ソケット等を管理）
                                   │  ①まず AVC を確認
                                   │  ②キャッシュになければ問合せ
                                   ▼
                             [セキュリティサーバ] ◀── セキュリティポリシ（起動時・稼働中に読込み）
                                   │  ③許可／拒否を回答（AVC にキャッシュ）
                                   ▼
                         オブジェクトマネージャが結果に従って許可／拒否を実施
```

このように、SELinuxで採用されているFlaskアーキテクチャでは、アクセス制御機構とセキュリティポリシ管理機構（セキュリティサーバ）とが切り離されているのが大きな特徴です。判断の仕組みと実施の仕組みを分けておけば、ポリシを差し替えるだけで、カーネルのコードを変えずに別のセキュリティモデルを適用できます。これらの仕組みによって、SELinuxは強力かつ柔軟なセキュリティ機能を実現しています。

しかし、その開発元であるNSAは、ドキュメント類の不備などを理由に、SELinuxを「Trusted OS」とはしていません。1.1 で見た「機能があること」と「保証されていること」の違いが、ここに表れています。なお、SELinuxを搭載したディストリビューション製品として、コモンクライテリアの評価認証を取得したものはあります。

### 4.3 運用上の注意 ― SELinuxを無効化しない

SELinuxには、ポリシ違反を拒否する Enforcing、拒否せずログだけ記録する Permissive、機能を停止する Disabled の3つの動作モードがあり、`getenforce` コマンドで確認できます。

```
$ getenforce
Enforcing
```

導入現場でよくある失敗は、アプリケーションが動かない原因がSELinuxの拒否だとわかった途端に、管理者が `setenforce 0`（Permissiveへの切替え）や設定ファイルでの Disabled 化によって、SELinux全体を止めてしまうことです。これでは 2.2 で見た「rootを奪われても守れる」という効果がすべて失われます。サーバの管理者は、監査ログ（`type=AVC ... denied`）で何が拒否されたかを確認し、ファイルのラベルを正しく付け直す、必要な操作だけをポリシで許可する、といった**最小限の変更**で対処すべきです。Permissiveは、新しいポリシを適用する前に影響を確認する期間に限って使います。

## 5. セキュアOS

日本では、強制アクセス制御と最小特権によってセキュリティを強化したOSを、**セキュアOS**（Security-focused Operating System）と呼んでいます。Trusted OSが「評価基準による保証」まで含む言葉であるのに対し、セキュアOSは「MACと最小特権という機能をもつこと」に着目した呼び方です。

> **セキュアOSの例**
> SELinuxのほかに、同じくLSMを利用した **TOMOYO Linux**（NTTデータが開発し、カーネル2.6.30で標準採用）、**AppArmor**、**Smack** などがある。これらは、評価認証の取得を前提とするTrusted OSとは区別して扱われることが多い。

| 呼び方 | 必要な要件 | 例 |
|---|---|---|
| Trusted OS | MAC・最小特権・監査などの機能＋設計文書の整備と第三者評価による**保証** | Trusted Solaris、HP-UX BLS、PitBull |
| セキュアOS | MACと最小特権の**機能** | SELinux、TOMOYO Linux、AppArmor、Smack |

なお、TOMOYO Linux と AppArmor は、ファイルに付けたラベルではなくファイルの**パス名**を基準にアクセスを制御する方式で、SELinuxのラベル方式より設定が理解しやすいとされます。

## 6. 確認問題

- **Q1**：Trusted OSとは何か。
- **Q2**：通常のOSとはどのような点が異なるか。
- **Q3**：SELinuxは通常のLinuxとどのような点が異なるのか。
- **Q4**（追加）：Webサーバのプロセスが乗っ取られた場合、DACだけのOSとSELinuxを有効にしたOSとで、被害の範囲はどう変わるか。
- **Q5**（追加）：アプリケーションがSELinuxに拒否されて動作しないとき、管理者はどう対処すべきか。

> **解答のポイント**
> - Q1：TCSECなどの評価基準において、B DIVISION以上の要求基準を満たしたOSである。セキュリティ機能を強化したうえで、設計仕様書やマニュアル類を整備し、定められた検証テストをクリアしている。
> - Q2：任意アクセス制御に加えて強制アクセス制御と最小特権を備えている。そのため、管理者を含むすべての利用者のアクセスがセキュリティポリシによって制限される。また、第三者による評価・検証によって安全性が保証されている。
> - Q3：セキュリティコンテキスト、TE、RBACによる強制アクセス制御が導入されており、rootであってもポリシの制限を回避できない。また、Flaskアーキテクチャによってアクセス制御機構とセキュリティポリシ管理機構が分離されている。
> - Q4：DACだけのOSでは、攻撃者はそのプロセスの実行ユーザの権限すべてを使え、root権限を奪えばシステム全体を支配できる。SELinuxでは、プロセスのドメイン（`httpd_t`）にポリシで許可された操作しかできないため、root権限を奪われても被害はWeb公開用のファイルなどの範囲にとどまる。
> - Q5：SELinuxを無効化（Permissive化・Disabled化）するのではなく、監査ログで拒否された操作を確認し、ファイルのラベルの修正や必要な操作だけをポリシで許可するなど、最小限の変更で対処する。

## 7. 試験対策まとめ（重要ポイント）

### 7.1 知識の確認（科目A-2向け）

- **Trusted OSの定義**：TCSEC（オレンジブック）でB DIVISION以上を満たすOS。「機能が豊富」ではなく「正しさが設計文書と第三者評価で保証されている」ことが要点。
- **DAC と MAC**：所有者が任意に設定するか、システム全体のポリシで強制されるか。MACではrootを含むすべての利用者が制限され、所有者もアクセス権を変えられない。
- **TCSECの区分**：D（最小限）、C（任意＝DAC、C2で監査）、B（強制＝MAC、B1ラベル・B2隠れチャネル分析と最小特権・B3参照モニタ）、A（形式的検証）。TNI（レッドブック）がネットワークを補完。
- **TCSEC → CC**：ITSEC、CTCPECと統合されてISO/IEC 15408（コモンクライテリア）へ。保護プロファイルとEALで評価する。日本の制度はJISEC。
- **SELinux**：NSAが開発、LSM経由でカーネル2.6に統合。セキュリティコンテキスト（ユーザ:ロール:タイプ:レベル）、TE（ドメインとタイプの組合せでアクセスベクタを許可）、RBAC（ロールで遷移可能なドメインを制限）、Flask（オブジェクトマネージャとセキュリティサーバの分離、AVCでキャッシュ）。
- **SELinuxはTrusted OSではない**：NSA自身がドキュメント類の不備などを理由にTrusted OSとしていない。日本では「セキュアOS」と呼ぶ。
- **セキュアOSの仲間**：TOMOYO Linux（NTTデータ、2.6.30）、AppArmor、Smack。いずれもLSMを利用する。

### 7.2 記述式で問われる観点（科目B向け）

- **MACを導入する理由を書く**：「Webサーバの脆弱性を突かれてroot権限を奪われても、強制アクセス制御によってプロセスがアクセスできる範囲をポリシで制限し、重要ファイルの窃取や改ざんを防ぐため」という型で、侵入後の被害の局所化を根拠にする。
- **DACだけでは防げない事象を指摘する**：利用者が誤ってアクセス権を緩めた、マルウェアが利用者権限でファイルを持ち出した、rootを奪われた、の3つがDACの限界。
- **最小特権・職務分離の実装**：rootに集中した権限をRBACのロールに分割し、運用担当者ごとに必要な操作だけを許可する、と説明できるようにしておく。
- **ログから侵入の兆候を読む**：AVCの拒否ログで、Webサーバのドメインが本来アクセスしないファイル（/etc/shadow など）に触れようとしていれば、侵入を疑う根拠になる。
- **運用上の判断**：動作不良を理由にSELinuxを無効化するのは不適切であり、ラベルの修正や必要最小限のポリシ追加で対処すべきと答える。
