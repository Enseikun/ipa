# Trusted OS

## 5.4 Trusted OS

Trusted OS（信頼されたオペレーティングシステム）とは、セキュリティ機能を強化するとともに、設計仕様書やマニュアル類を整備し、定められた検証テストをクリアしたOSのことを意味する。ここでは、Trusted OSの概要と、具体的な製品の例としてSELinuxを紹介する。

### Trusted OSの概要

もともとは、米国国防総省が定めたセキュリティ評価認証基準であるTCSEC（Trusted Computer System Evaluation Criteria：通称「オレンジブック」）に代表される「レインボーシリーズ」において、「B DIVISION」以上の要求基準をクリアしたOSを「Trusted OS」と呼ぶ。

> **Trusted OS**
> 「信頼された（Trusted）」とは、単にセキュリティ機能が豊富であることを指すのではない。機能の正しさが設計文書や検証によって第三者に示され、評価基準に基づいて保証されていることを意味する。

#### Column：TCSECとレインボーシリーズの概要

TCSECは、米国国防総省下のNSA（National Security Agency：国家安全保障局）に設置されたNCSC（National Computer Security Center：国立コンピュータセキュリティセンター）により、軍用調達のためのコンピュータシステムの評価基準として1983年に作成された。その後、1985年の改定を経て国防総省標準（DoD 5200.28-STD）となった。TCSECでは、徹底的なアクセス制御によって高い機密性を確保することが求められており、システムのセキュリティ要求レベルを次のような「DIVISION」と「CLASS」に分類している。

**表：TCSECにおけるセキュリティ要求レベルの分類**

| DIVISION | CLASS | 概要 |
|---|---|---|
| D：MINIMAL PROTECTION | ― | 上位クラスの要件を満たさないもの |
| C：DISCRETIONARY PROTECTION | C1：DISCRETIONARY SECURITY PROTECTION | 利用者の識別・認証と任意アクセス制御（DAC） |
| | C2：CONTROLLED ACCESS PROTECTION | C1に加え、監査ログ、オブジェクト再利用の防止など |
| B：MANDATORY PROTECTION | B1：LABELED SECURITY PROTECTION | セキュリティラベルによる強制アクセス制御（MAC） |
| | B2：STRUCTURED PROTECTION | 形式的セキュリティポリシモデル、隠れチャネル分析、最小特権 |
| | B3：SECURITY DOMAINS | 参照モニタの実装、セキュリティ管理者の役割分離 |
| A：VERIFIED PROTECTION | A1：VERIFIED DESIGN | 形式的手法による設計の検証 |

なお、TCSECはスタンドアロンシステムとしての堅牢さを評価しているため、ネットワークからの侵入や攻撃に対する堅牢さについては保証していない。TCSECの規定をネットワークに適用させるとともに、暗号化などの機能を追加した規格としては、1987年に発行されたTNI（Trusted Network Interpretation of the TCSEC：通称「レッドブック」）がある。なお、「オレンジブック」や「レッドブック」などの呼称は、表紙の色から付けられたものである。

NCSCが発行しているこれらの文書類は「レインボーシリーズ」と呼ばれており、主に次のような種類がある。

> **TCSECのその後**
> TCSECは、欧州のITSEC、カナダのCTCPECなどと統合される形で、国際標準のコモンクライテリア（CC：ISO/IEC 15408）へと発展した。現在は、CCに基づく保護プロファイル（例：LSPP、RBACPPなど）と評価保証レベル（EAL）によってOSのセキュリティ評価が行われている。

#### 通常のOSとの違い

一般的なOSでは、ファイルの所有者が自由にアクセス権を設定できる任意アクセス制御（DAC：Discretionary Access Control）が採用されている。また、管理者（UNIX系OSではroot）にはすべての権限が集中している。そのため、管理者権限を奪われると、システム全体が攻撃者の支配下に置かれてしまう。

これに対してTrusted OSでは、主に次のような特徴を備えている。

- **強制アクセス制御（MAC）**：システム全体のセキュリティポリシに基づき、管理者を含むすべての利用者のアクセスを強制的に制限する。
- **最小特権**：管理者の権限を細分化し、各プロセスや利用者には業務に必要な最小限の権限だけを与える。
- **監査機能**：セキュリティに関わる操作を記録し、追跡を可能にする。
- **保証（アシュアランス）**：設計仕様書やマニュアル類を整備し、第三者による評価・検証を受けている。

代表的なTrusted OS製品としては、Trusted Solaris（現在はSolaris Trusted Extensionsに統合）、HP-UX BLS、PitBullなどがある。

### SELinuxとは

SELinux（Security-Enhanced Linux）は、NSAが中心となって開発したLinux向けのセキュリティ拡張機能である。2000年にオープンソースとして公開され、その後、LSM（Linux Security Modules）の仕組みを通じてLinuxカーネル2.6系に標準で取り込まれた。現在では、Red Hat Enterprise LinuxやFedoraなど多くのディストリビューションで利用されている。

SELinuxでは、すべてのプロセスに対して、セキュリティポリシで許可された範囲のアクセスだけが認められるようになっている。従来のLinux環境では絶対的な権限をもつ「root」であっても、この制限を回避することはできない。そのため、仮に侵入や攻撃を受けたとしても、システム全体が乗っ取られることはなく、被害を最小限にとどめることができる。

SELinuxのセキュリティアーキテクチャは、Flask（Flux Advanced Security Kernel）と呼ばれる。Flaskは、NSAがSecure Computing社とユタ大学の支援を受けて開発した技術であり、柔軟な強制アクセス制御（Mandatory Access Control：MAC）を実現する。

### SELinuxにおけるセキュリティ機能

SELinuxにおける主なセキュリティ機能の概要を次に示す。

#### ① セキュリティコンテキストによる強制アクセス制御

スーパユーザ（root）を含むすべてのユーザに対して、プロセス（サブジェクト）やファイルなどのリソース（オブジェクト）に付与されたセキュリティラベルに応じた、強力かつきめ細かなアクセス制御が行われる。このセキュリティラベルは、セキュリティコンテキストと呼ばれている。

> **セキュリティコンテキスト**
> 一般に「ユーザ:ロール:タイプ（:レベル）」の形式で表される。例えば、Webサーバのプロセスには `system_u:system_r:httpd_t` のようなコンテキストが付与される。ファイルのコンテキストは `ls -Z`、プロセスのコンテキストは `ps -Z` コマンドで確認できる。

#### ② TE（Type Enforcement）

ファイル、デバイス、ディレクトリ、ソケットなど各オブジェクトの種類ごとに、アクセスベクタと呼ばれる詳細なパーミッションの集合を定義してアクセス制御を行う。あるサブジェクトがオブジェクトにアクセスするためには、両者の関係において、そのアクセス方法が対象となるサブジェクトのアクセスベクタの定義上で許可されている必要がある。

パーミッションの種類は非常に細かく定義されており、例えばファイルに対するパーミッションとしては、read、write、append、poll、ioctl、create、execute、link、unlink、lock、renameなどがある。この仕組みをTE（Type Enforcement）と呼ぶ。TEでは、プロセスに付与されるタイプを特に「ドメイン」と呼び、「どのドメインが、どのタイプのオブジェクトに対して、どの操作を行えるか」をポリシとして記述する。

#### ③ RBAC（Role-Based Access Control）

ユーザに「ロール（役割）」を割り当て、ロールごとに遷移可能なドメインを制限する仕組みである。これにより、同じrootユーザであっても、割り当てられたロールによって実行できる操作が制限される。従来のrootに集中していた権限を役割ごとに分割することで、最小特権を実現できる。

#### ④ Flaskアーキテクチャによるアクセス制御

Flaskアーキテクチャは、実際にアクセス制御を実施するオブジェクトマネージャと、アクセス可否の判断を行うセキュリティサーバとから構成されている。オブジェクトマネージャは、アクセス要求が発生するとセキュリティサーバに問い合わせ、その判断結果に従ってアクセスを許可または拒否する。判断結果はAVC（Access Vector Cache）にキャッシュされるため、問い合わせによる性能低下が抑えられている。

セキュリティサーバは、起動時にセキュリティポリシを読み込み、外部からパーミッションチェック要求があると、自身の保持しているセキュリティポリシに基づいたパーミッションチェックを実行し、その結果を通知する。また、システム稼働中にセキュリティポリシを動的に読み込み、変更する機能も提供している。

このように、SELinuxで採用されているFlaskアーキテクチャでは、アクセス制御機構とセキュリティポリシ管理機構（セキュリティサーバ）とが切り離されているのが大きな特徴である。これらの仕組みによって、SELinuxは強力かつ柔軟なセキュリティ機能を実現している。しかし、その開発元であるNSAは、ドキュメント類の不備などを理由に、SELinuxを「Trusted OS」とはしていない。

なお、日本では、強制アクセス制御と最小特権によってセキュリティを強化したOSを、セキュアOS（Security-focused Operating System）と呼んでいる。

> **セキュアOSの例**
> SELinuxのほかに、同じくLSMを利用したTOMOYO Linux（NTTデータが開発し、カーネル2.6.30で標準採用）、AppArmor、Smackなどがある。これらは、評価認証の取得を前提とするTrusted OSとは区別して扱われることが多い。

### 確認問題

- 【Q1】Trusted OSとは何か。
- 【Q2】通常のOSとはどのような点が異なるか。
- 【Q3】SELinuxは通常のLinuxとどのような点が異なるのか。

> **解答のポイント**
> - Q1：TCSECなどの評価基準において、B DIVISION以上の要求基準を満たしたOSである。セキュリティ機能を強化したうえで、設計仕様書やマニュアル類を整備し、定められた検証テストをクリアしている。
> - Q2：任意アクセス制御に加えて強制アクセス制御と最小特権を備えている。そのため、管理者を含むすべての利用者のアクセスがセキュリティポリシによって制限される。また、第三者による評価・検証によって安全性が保証されている。
> - Q3：セキュリティコンテキスト、TE、RBACによる強制アクセス制御が導入されており、rootであってもポリシの制限を回避できない。また、Flaskアーキテクチャによってアクセス制御機構とセキュリティポリシ管理機構が分離されている。
