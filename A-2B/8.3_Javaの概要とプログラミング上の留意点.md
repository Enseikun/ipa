## 0. 全体像 ― なぜこの分野を学ぶのか

8.2 では、C/C++ が「メモリを直接操作できる」代わりに、`gets`・`strcpy`・`sprintf` などの関数が引き起こすバッファオーバフロー（第2章 2.3）を開発者自身が防がなければならないことを学びました。本ノートで扱う **Java** は、その反省を言語と実行環境の設計に取り込んだ言語です。ポインタを持たず、メモリを自動で回収し、配列の範囲外アクセスを実行時に止めます。では、Java で書けば安全なのでしょうか。答えは「いいえ」です。Java が防いでくれるのはメモリ破壊の類いであり、**クラス設計の甘さ、マルチスレッドでの競合、例外処理の不備、入力値の扱いの誤り**は、開発者が書き方で防ぐしかありません。

本ノートでは、Javaによるプログラム開発におけるセキュリティ上の留意点を、次の順で見ていきます。

1. **Javaの概要**（1節）：Javaテクノロジの全体像と、ソース → バイトコード → JVM という実行の仕組み、言語としての安全上の特徴
2. **Javaのセキュリティ機構**（2節）：サンドボックスモデル、クラスローダ、セキュリティマネージャ、ポリシ、アクセスコントローラ（現在は廃止に向かっているが試験では問われる）
3. **クラス設計の留意点**（3節）：アクセス修飾子、カプセル化、読出し専用インタフェース、不変オブジェクト、不正なクラス継承の防止
4. **レースコンディション対策**（4節）：サーブレットのインスタンス変数の競合、スレッドセーフな実装、データベース更新時の競合と楽観的ロック
5. **例外処理**（5節）：try-catch-finally、検査例外と非検査例外、内部情報を出さない書き方、try-with-resources によるリソースの確実な解放
6. **入力を扱う箇所の書き方**（6節）：PreparedStatement によるプレースホルダ、ファイルパスの正規化、信頼できないデータのデシリアライズを避ける書き方
7. **静的解析とコードレビュー**（7節）：ツールの指摘の見た目、コーディング規約の条文例、レビューのチェックリスト

6節は、第2章 2.8 で攻撃側から見た SQLインジェクションやディレクトリトラバーサルを、第3章 3.6 で整理した「Webアプリケーションの実装による脆弱性」の対策として、**Java の開発者がどう書くか**に落とし込む節です。2.8 と 3.6 が PHP 中心の例だったのに対し、本ノートでは Java で同じことを確認します。

科目Bの業務観点では、「②情報システムの企画・設計・開発・運用におけるセキュリティ確保の推進又は支援」のうち、セキュリティ機能の実装、**セキュアプログラミング**、セキュリティテスト（脆弱性診断）に直結します。科目Bでは Java のソースコードを示して「下線部の処理にはどのような問題があるか」「（ a ）に入れるべき字句を答えよ」「どのように修正すべきか」を問う設問が繰り返し出題されています。科目A-2では、ガーベジコレクション、サンドボックス、`final`、例外の種類のような知識が単独で問われます。

### 0.1 本ノートを通じた「記述の型」

科目Bのソースコード問題では、解答者は**どの行が・なぜ危険で・どう直すか**を、限られた字数で書かなければなりません。本ノートでは、修正前と修正後のコードを示すたびに、次の3項目の表で指摘をまとめます。読者は、この型をそのまま解答の骨組みとして使ってください。

| 項目 | 書くこと | 書き方の例 |
|---|---|---|
| どの行が | 問題のある行・変数・メソッドを特定する | 「`doGet` メソッド内で、インスタンス変数 `tempPDF` に値を代入している行」 |
| なぜ危険か | その書き方で、誰が・何をすると・何が起きるかを因果で書く | 「複数の利用者のリクエストが別スレッドで同時に処理されると、`tempPDF` が他の利用者の値に書き換わり、他人のファイルへのリンクが表示される」 |
| どう直すか | 何を・どう変えるかを具体的に書き、なぜそれで防げるかを1文添える | 「`tempPDF` を `doGet` のローカル変数にする。ローカル変数はスレッドごとに確保されるため、他のリクエストと共有されない」 |

## 1. Javaの概要 ― 言語と実行環境の両方で守る

### 1.1 Javaテクノロジ ― 言語だけを指す言葉ではない

Javaは、狭義にはC++言語のようなオブジェクト指向型のプログラミング言語である**Java言語**を指すこともあります。しかし実際のJavaは単なる言語ではなく、Javaプログラムを開発するための環境（Java Development Kit：**JDK**）や、Javaで開発されたプログラムを実行するための環境（Java Runtime Environment：**JRE**）を含めた各種技術の総称です。そのため、総称としては「**Javaテクノロジ**」という表現が用いられます。

| 構成要素 | 中身 | 主に使う人 |
|---|---|---|
| **Java言語** | 文法・型・クラスなどの言語仕様 | 開発者 |
| **JDK** | コンパイラ（`javac`）、デバッガ、各種ツール、JRE 相当の実行環境 | 開発者 |
| **JRE** | JVM と標準クラスライブラリ（実行に必要な部分だけ） | 利用者・運用者 |
| **JVM** | バイトコードを解釈・実行する仮想マシン | （JRE の中核） |

試験で「JREのセキュリティ」が問われたのは、利用者のPCにインストールされたJREが古いまま放置され、その脆弱性がマルウェア感染の入口になった時期があったからです。運用者は、開発者が作ったプログラムだけでなく、それを動かす**実行環境（JRE／JDK）のバージョンとセキュリティ更新**も管理する必要があります（第5章 5.2 のホストの要塞化、第3章 3.1 の脆弱性管理と同じ考え方です）。なお現在の Oracle の JDK は、Java 11 以降 JRE を単体では配布しておらず、アプリケーションに必要な部分だけを含む実行環境を `jlink` で作って同梱する形が一般的になっています。

### 1.2 実行の仕組み ― ソース → バイトコード → JVM

Javaの最大の特徴は、プログラムが**どこで、どの段階で検査されるか**にあります。C/C++ をはじめ、多くのプログラミング言語は、実行するプラットフォーム（主にCPU）に依存したネイティブコードにコンパイルすることを前提としています。これに対しJavaは、プラットフォームに依存しない**中間バイトコード**にコンパイルされ、**Java仮想マシン**（Java Virtual Machine：**JVM**）上で実行されるよう設計されています。

**図：Javaプログラムの実行の仕組み（C/C++ との対比）**

```
【Java】
  開発者のPC                                     実行するマシン（OS・CPUは問わない）
 ┌──────────────┐  javac    ┌──────────────┐  配布  ┌──────────────────────────────────┐
 │ UserInfo.java│ ───────▶ │UserInfo.class│ ─────▶ │ JVM                              │
 │ (ソースコード)│ コンパイル │(中間バイトコード)│        │ ①クラスローダ：.class を読み込む   │
 └──────────────┘ 型検査    └──────────────┘        │ ②バイトコードベリファイア：検証    │
                                                     │ ③インタプリタ／JITコンパイラで実行 │
                                                     │   ・配列境界チェック・型チェック    │
                                                     │   ・ガーベジコレクション            │
                                                     └───────────────┬──────────────────┘
                                                                     ▼
                                                           OS（Windows/Linux/macOS）・CPU

【C/C++】
 ┌──────────┐ コンパイル ┌────────────────────┐            ┌──────────────────────┐
 │ main.c   │ ───────▶ │ 実行ファイル        │ ─────────▶ │ OS・CPU が直接実行    │
 │(ソース)  │          │(特定のOS・CPU向け   │            │（境界チェックなし）   │
 └──────────┘          │  ネイティブコード)  │            └──────────────────────┘
                        └────────────────────┘
```

この図から、Javaでは検査が3段階で入ることがわかります。コンパイル時に `javac` が型の誤りを検出し、ロード時にバイトコードベリファイアがクラスファイルの不正を検出し、実行時にJVMが配列の範囲外アクセスや不正な型変換を例外として止めます。C/C++ では、コンパイル後のネイティブコードがOS・CPU上で直接動くため、範囲外の書込みは止められずにメモリを壊します（8.2）。

実体としてのバイトコードは、`javap -c` コマンドで逆アセンブルすると次のような命令列として見えます。開発者がこれを読む機会は多くありませんが、「CPUの機械語ではなく、JVM向けの命令」であることを確認しておきましょう。

```
$ javap -c UserInfo
public java.lang.String getUserID();
  Code:
     0: aload_0
     1: getfield      #7     // Field userID:Ljava/lang/String;
     4: areturn
```

### 1.3 Javaの特徴とセキュリティ

Javaには、主に次のような特徴があります。

- 中間バイトコードとJVMの組合せによって、OSやCPUに依存しないソースコードや中間バイトコードの状態でソフトウェアを配布することができます（"Write Once, Run Anywhere"）。
- Java言語はオブジェクト指向型プログラミングの思想に基づいて設計された言語であり、開発者はソフトウェア開発の効率と保守性を高めることができます。
- Java言語の文法はC/C++から多くを引き継いでいますが、**ポインタ**の概念を排除しており、プログラマがメモリアドレスを直接操作することはできません。そのため、不正なメモリアクセスやバッファオーバフローなどの脆弱性が生じにくくなっています。
- メモリ管理は**ガーベジコレクション**によって自動的に行われ、プログラマが明示的にメモリを解放する必要がありません。これにより、メモリリークや解放済み領域の再利用（use-after-free）といった問題を防ぎやすくなります。
- 配列の境界チェックや型チェックが実行時に行われ、範囲外アクセスや不正な型変換は例外として検出されます。
- **サンドボックスモデル**に基づいたセキュリティ機構を備えています（本ノート2節で解説）。
- Javaで開発されたプログラムから、C/C++言語等で開発されたネイティブコード（特定のプラットフォームでそのまま動作する実行プログラム）を呼び出す仕組み（API）として、**JNI**（Java Native Interface）があります。

これらを C/C++ と並べると、Javaが「どの種類の脆弱性を言語側で引き受けているか」がはっきりします。

| 観点 | C/C++（8.2） | Java | 開発者に残る責任 |
|---|---|---|---|
| メモリアドレスの操作 | ポインタで直接操作できる | ポインタがなく、直接操作できない | （JNI 経由のネイティブコードを除き）なし |
| 配列の範囲外アクセス | 検出されず、隣のメモリを壊す（バッファオーバフロー） | 実行時に `ArrayIndexOutOfBoundsException` で止まる | 例外が起きたときの処理を書く |
| メモリの解放 | `free`／`delete` を開発者が書く（二重解放、use-after-free の危険） | ガーベジコレクションが自動回収 | ファイル・DB接続などメモリ以外の資源は自分で閉じる（5.4） |
| 型変換 | 任意のキャストが通る | 不正なキャストは `ClassCastException` | ― |
| 実行環境 | OS・CPUが直接実行 | JVM が検証してから実行 | JRE/JDK を最新に保つ（運用者） |

表の右端の列が、本ノート3節以降のテーマです。Javaが引き受けてくれない部分こそ、開発者が書き方で守る部分になります。

### 1.4 JNI ― Javaの守りの外側

> **補足:JNI利用時の注意**
> JNIを介して呼び出されるネイティブコードは、JVMによるメモリ保護やセキュリティ機構の管理外で動作する。そのため、ネイティブコード側にバッファオーバフロー等の脆弱性があると、Javaの安全性が損なわれる点に注意が必要である。

開発者は、JNI を使う場合、呼び出すネイティブコードについては 8.2 の C/C++ の留意点（境界チェック、安全な関数の使用）がそのまま当てはまることを意識し、ネイティブ側に渡すデータの長さや形式を Java 側で検証してから渡すべきです。ネイティブコードの脆弱性を突かれると、攻撃者は JVM の保護を素通りしてプロセスのメモリを書き換えられるからです。

こうした多くの特徴から、Javaは他の言語と比べ、セキュアなソフトウェア開発を行うのに適した言語であるといえます。しかし、そのためには開発者がJavaテクノロジの全体像をある程度理解しておく必要があります。次節では、JVM の内側にある「外から来たコードを閉じ込める仕組み」を見ます。

## 2. Javaのセキュリティ機構の概要 ― サンドボックスモデル

### 2.1 サンドボックスモデルとは

**サンドボックスモデル**とは、ネットワークなどを通じて外部から受け取ったプログラムを、セキュリティが確保された領域で動作させることによって、プログラムが不正な操作や動作をするのを防ぐ仕組みです。第5章 5.9 で学んだサンドボックス（マルウェアを隔離環境で動かして挙動を観察する製品）と、「信頼できないコードを閉じ込めて、外の資源に触らせない」という発想は同じです。Java の場合は、それを言語の実行環境（JVM）の中で実現していました。

### 2.2 サンドボックスモデルの変遷

Javaで当初（JDK 1.0）採用されたサンドボックスモデルは、次のようなものです。

- ローカル環境のコード（ローカルコード）は信頼できるため、重要なものを含め、あらゆるシステム資源に対する完全なアクセス権をもつ。
- ネットワークを通じてダウンロードされたコード（リモートコード、アプレット）は信頼できないため、サンドボックスの中の限定されたシステム資源にのみアクセスを許可する。

その後、JDK 1.1ではデジタル署名された「署名付きアプレット」をローカルコードと同様に信頼する仕組みが導入されました。さらにJava 2（JDK 1.2）以降では、ローカルコードかリモートコードかを問わず、すべてのコードが**セキュリティポリシ**に基づいてアクセス制御されるモデルへと拡張されました。このモデルでは、ポリシによって適切なアクセス権が与えられていれば、リモートコードであっても重要なシステム資源にアクセスすることができます。逆に、ローカルコードであってもアクセス権が与えられていなければ、システム資源へのアクセスは制限されます。

| 版 | 信頼の単位 | ローカルコード | リモートコード（アプレット） | 弱点・改善点 |
|---|---|---|---|---|
| JDK 1.0 | 「どこから来たか」の二択 | 完全なアクセス権 | サンドボックス内の限定された資源のみ | 便利なリモートコードも何もできない |
| JDK 1.1 | ＋デジタル署名の有無 | 完全なアクセス権 | 署名付きアプレットはローカルコードと同様に信頼。署名なしはサンドボックス内 | 信頼するかしないかの二択のまま |
| Java 2（JDK 1.2）以降 | セキュリティポリシ（コードの出所・署名者ごとに細かく） | ポリシで与えられた権限のみ | ポリシで与えられた権限のみ | 必要な権限だけを与えられる（最小権限） |

JDK 1.2 以降の考え方は、第1章 1.2 で学んだ**最小権限の原則**を、コード単位で適用したものと捉えると理解しやすいでしょう。第6章 6.1 のアクセス制御で言えば、主体が「コード（出所と署名者）」、客体が「ファイルやネットワークなどのシステム資源」、アクセス制御リストに当たるのが「ポリシ」です。

> **補足:現在のJavaにおける位置付け**
> アプレットはJava 9で非推奨となり、Java 11以降のJDKでは実行環境が提供されなくなった。また、セキュリティマネージャもJava 17(JEP 411)で非推奨となり、Java 24(JEP 486)では恒久的に無効化されている。ただし、サンドボックスモデルの考え方は試験で問われることがあるため、概要を理解しておく必要がある。

つまり、以前はJavaアプリケーション内部のサンドボックスで信頼できないコードを隔離していましたが、現在のJavaでは、その役割はOSのプロセス分離、コンテナ（第1章 1.5）、最小権限のサービスアカウントといったJVMの外側の仕組みが担っています。運用者は、Javaアプリケーションを専用の権限の低いOSユーザで動かし、アクセスできるファイルやネットワークをOS・コンテナ側で制限すべきです。

Java 2以降のセキュリティ機構は、主に次の要素から構成されます（2.3〜2.6）。

### 2.3 クラスローダ

**クラスローダ**は、クラスファイルの検索と取得、セキュリティポリシの参照、及び適切なアクセス権をもたせたクラスオブジェクトの定義などを行う機構です。すべてのクラスは、クラスローダによってロードされます。クラスローダ自体もクラスであり、別のクラスローダによってロードされます。この機構により、Javaプラットフォーム上でソフトウェアコンポーネントを実行時にインストールすることが可能となります。

なお、クラスローダは一つではありません。JVMが用途によって使い分ける複数のクラスローダ（ブートストラップクラスローダ、プラットフォームクラスローダ、アプリケーションクラスローダ等）のほか、クラスに特定のセキュリティ属性を割り当てるような独自のクラスローダを、プログラマが定義することも可能です。

| クラスローダ | 読み込むもの | 備考 |
|---|---|---|
| ブートストラップクラスローダ | `java.lang` などJavaの中核クラス | JVM に組み込まれている |
| プラットフォームクラスローダ | 標準ライブラリの一部のモジュール | Java 8 以前の拡張クラスローダに相当 |
| アプリケーションクラスローダ | アプリケーションのクラスパス上のクラス | 開発者が書いたクラスは通常ここから |
| 独自のクラスローダ | プログラマが定義した場所・方法 | 特定のセキュリティ属性を割り当てられる |

> **補足:バイトコード検証**
> クラスローダによってロードされたクラスファイルは、**バイトコードベリファイア**によって、不正な命令や型の不整合、スタックのオーバフローなどがないかが検証されてから実行される。

バイトコード検証が必要なのは、クラスファイルが `javac` で正しく作られたものとは限らないからです。改ざんされたクラスファイルや手作りのクラスファイルが、型の規則を破って JVM の保護をすり抜けることを防ぐために、JVM は実行前に必ず検証します（1.2 の図の②）。

### 2.4 セキュリティマネージャ

**セキュリティマネージャ**（`java.lang.SecurityManager`）は、各クラスのサンドボックスに対するアクセスを制御します。開発者は、次の記述によってセキュリティマネージャを起動します。

```java
System.setSecurityManager(new SecurityManager());
```

なお、運用者がJavaアプリケーションの起動時にコマンドラインオプション `-Djava.security.manager` を指定することによっても有効化できます（2.2 の補足のとおり、Java 24 以降では有効化できません）。

### 2.5 ポリシ（セキュリティポリシ）

**ポリシ**は、各コードがどのようなアクセス権を使用できるかを指定するものです。ポリシは `Policy` オブジェクトにより表現され、デフォルトの実装では、一つ又は複数のポリシ構成ファイルからポリシを指定できます。

ポリシ構成ファイルの記述例を次に示します。

```
grant codeBase "file:/home/user/app/-" {
    permission java.io.FilePermission "/tmp/test", "read";
};
```

この例では、`/home/user/app/` 以下に配置されたコードに対して、`/tmp/test` ファイルの読取り権限を付与しています。読み方を分解すると次のとおりです。

| 記述 | 意味 |
|---|---|
| `grant codeBase "file:/home/user/app/-"` | 誰に：`/home/user/app/` 以下（末尾の `-` はサブディレクトリを含む）に置かれたコードに |
| `java.io.FilePermission` | 何の種類の権限を：ファイルへのアクセス権を |
| `"/tmp/test"` | どの資源に：`/tmp/test` ファイルに |
| `"read"` | どの操作を：読取りだけを |

ここに書かれていない操作（`/tmp/test` への書込み、他のファイルの読取り、ネットワーク接続など）は、すべて拒否されます。許可リスト（ホワイトリスト）方式のアクセス制御です。

### 2.6 アクセスコントローラ

**アクセスコントローラ**（`java.security.AccessController`）は、ポリシに基づいたアクセス制御の操作と決定に使用されます。`checkPermission` メソッドを用いて、`/tmp/test` ファイルへの読取りを許可するかどうかを決定する例を次に示します。

```java
FilePermission perm = new FilePermission("/tmp/test", "read");
AccessController.checkPermission(perm);
```

アクセス権がない場合には、`AccessControlException` がスローされます。

ここまでの4つの要素の関係を図にまとめます。

**図:Javaのセキュリティ機構のイメージ**

```
 [ローカルコード]   [リモートコード]
        │                 │
        └──────┬──────────┘
               ▼
        [クラスローダ] ──参照──▶ [ポリシ(ポリシ構成ファイル)]
               ▼
      [JVM上で実行されるクラス]
               │ システム資源へのアクセス要求
               ▼
   [セキュリティマネージャ] → [アクセスコントローラ]
               │ 許可/拒否
               ▼
   [システム資源(ファイル、ネットワーク等)]
```

図を上から読むと、①クラスローダがコードを読み込む際にポリシを参照して権限を割り当て、②クラスがファイルなどにアクセスしようとするとセキュリティマネージャが呼ばれ、③アクセスコントローラがポリシに照らして許可か拒否かを決める、という流れです。対策の4機能（第1章 1.2）で言えば、これは「予防・防止」の仕組みです。

ここまでは「JVM が外から来たコードをどう閉じ込めるか」という実行環境の話でした。次節からは、開発者が自分で書くクラスの中身に移ります。

## 3. クラス設計の留意点 ― データを守る「壁」をどこに置くか

### 3.1 アクセス修飾子 ― 誰からフィールドやメソッドが見えるか

Javaでは、クラス・フィールド・メソッドの宣言に**アクセス修飾子**を付けて、どこからアクセスできるかを決めます。開発者は、この修飾子を「公開範囲の設定」として、第6章 6.1 のアクセス制御と同じ発想で使います。

| 修飾子 | 同じクラス | 同じパッケージ | 別パッケージのサブクラス | それ以外（別パッケージ） | 主な用途 |
|---|---|---|---|---|---|
| `public` | ○ | ○ | ○ | ○ | 外部に公開するAPI（メソッド） |
| `protected` | ○ | ○ | ○ | × | サブクラスに拡張させたい部分 |
| （指定なし：パッケージプライベート） | ○ | ○ | × | × | パッケージ内部だけで使う部品 |
| `private` | ○ | × | × | × | フィールド、内部処理用のメソッド |

原則は「**できるだけ狭く**」です。開発者は、フィールドを `private` にし、外部に必要なものだけをメソッドとして `public` にすべきです。公開範囲が広いほど、どこから書き換えられるかを追えなくなり、レビューでも保証できなくなるからです。修飾子と組み合わせて使う `final`（変更・継承の禁止）、`static`（クラス単位で共有）も、本節と4節で重要になります。

### 3.2 カプセル化されていないフィールドにおける問題

次の例のように、クラスのフィールド（メンバ変数）を `public` 属性で宣言すると、他のクラスから当該フィールドを直接参照・書換えすることが可能となります。そのため、不正なプログラムや誤ったプログラムによって、意図しない値に書き換えられてしまうおそれがあります。

〈例〉（修正前）

```java
public class UserInfo {
    public String userID;    // ユーザID      ← 行①
    public String userName;  // ユーザ名      ← 行②
}
```

```java
// 利用側のどこか（別パッケージ）で、次のように書けてしまう
UserInfo u = session.getUserInfo();
u.userID = "admin";        // 認可判定に使うユーザIDを、どのクラスからでも書き換えられる
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①・行②：フィールド `userID`・`userName` を `public` で宣言している |
| なぜ危険か | どのクラスからでも値を直接書き換えられるため、不正なプログラムや誤ったプログラムがユーザIDを別人の値にすると、そのユーザIDで権限判定する処理が誤った判断をする（完全性が損なわれる） |
| どう直すか | フィールドを `private` にしてメソッド経由でのみアクセスさせる（3.3）。読出しだけが必要な利用者にはインタフェースで書込みを隠す（3.4）。生成後に変える必要がなければ不変にする（3.5） |

### 3.3 対策① ― カプセル化

こうした問題への対策としては、次のような方法があります。

① 開発者は、フィールドを `private` 属性にして隠蔽するとともに、フィールドを操作するメソッドを作成し、当該フィールドへのアクセスはメソッドを介して行うようにします（これを**カプセル化**という）。

〈例〉

```java
public class UserInfo {
    private String userID;    // ユーザID
    private String userName;  // ユーザ名

    public void setUserID(String arg) {     // ←ユーザIDを設定するメソッド
        userID = arg;
    }

    public String getUserID() {             // ←ユーザIDを読み出すメソッド
        return userID;
    }

    public void setUserName(String arg) {   // ←ユーザ名を設定するメソッド
        userName = arg;
    }

    public String getUserName() {           // ←ユーザ名を読み出すメソッド
        return userName;
    }
}
```

カプセル化の利点は、値の出入口がメソッドの1か所に集まることです。開発者は、`setUserID` の中に形式チェック（文字種・長さ）を入れたり、変更をログに記録したりできます。しかし、上記のように変更しても、メソッドを使用しさえすれば、他のプログラムからフィールドの値を書き換えることができてしまいます。

### 3.4 対策② ― 読出し専用のインタフェース

② そこで開発者は、値の読出しだけを必要とするプログラムに対しては、読出し用のメソッドのみを定義した**インタフェース**を用意し、そのインタフェースを介してアクセスさせるようにします。

〈例〉

```java
// ユーザ情報読出しインタフェース
public interface UserInfoReadOnly {
    String getUserID();     // ←ユーザIDを読み出すメソッド
    String getUserName();   // ←ユーザ名を読み出すメソッド
}

// ユーザ情報クラスの実装
public class UserInfo implements UserInfoReadOnly {
    private String userID;
    private String userName;

    public void setUserID(String arg) {     // ←ユーザIDを設定するメソッド
        userID = arg;
    }

    public String getUserID() {             // ←ユーザIDを読み出すメソッド
        return userID;
    }

    public void setUserName(String arg) {   // ←ユーザ名を設定するメソッド
        userName = arg;
    }

    public String getUserName() {           // ←ユーザ名を読み出すメソッド
        return userName;
    }
}
```

こうすることにより、`UserInfoReadOnly` 型として受け取った他のプログラムが、ユーザIDやユーザ名に誤った値を設定するのを防ぐことが可能となります。そして、ユーザIDやユーザ名を設定する必要がある場合のみ、`UserInfo` クラスを使用するようにします。

```java
// 画面表示を担当するクラスには、読出し専用の型で渡す
public void render(UserInfoReadOnly user) {
    out.println(user.getUserName());   // 読出しはできる
    // user.setUserName("x");          // UserInfoReadOnly には定義がないためコンパイルエラー
}
```

これは「必要な人に必要な操作だけを見せる」という最小権限の原則を、型の設計で実現したものです。コンパイラが違反を検出してくれるので、レビューで見落とす心配もありません。

### 3.5 不変オブジェクトと防御的コピー

> **補足:不変(イミュータブル)オブジェクト**
> 生成後に値を変更する必要がない場合は、フィールドを `private final` とし、コンストラクタでのみ値を設定する不変クラスとして設計する方法も有効である。Java 16以降では、`record` を用いて簡潔に不変クラスを定義できる。

```java
// 従来の書き方による不変クラス
public final class UserInfo {
    private final String userID;
    private final String userName;

    public UserInfo(String userID, String userName) {
        this.userID = userID;
        this.userName = userName;
    }
    public String getUserID()   { return userID; }
    public String getUserName() { return userName; }
    // setter を作らない。値を変えたければ新しいオブジェクトを作る
}

// Java 16 以降の record による同等の定義
public record UserInfo(String userID, String userName) { }
```

不変オブジェクトは、生成後に誰も値を変えられないため、複数のスレッドで共有しても競合が起きません（4節のレースコンディション対策にもなります）。

ただし注意点が1つあります。フィールドが `private final` でも、そのフィールドが配列や `List`、`Date` のように**中身を変更できるオブジェクト**を指していると、getter で参照を返した時点で呼出し側に中身を書き換えられてしまいます。開発者は、そのようなフィールドについては、受け取るときと返すときに複製（**防御的コピー**）を作るか、変更できないコレクションを返すべきです。

```java
// 修正前：内部の配列への参照をそのまま返している
public String[] getRoles() { return roles; }               // ← 呼出し側が roles[0] = "admin" と書き換えられる

// 修正後：複製を返す（List なら List.copyOf で変更不可のコピーを返す）
public String[] getRoles() { return roles.clone(); }
```

### 3.6 不正なクラス継承による問題と対策

継承可能な状態でクラスを作成すると、意図しないクラスの継承によって不正なサブクラスが作成され、メソッドのオーバライドなどによって本来の処理が改変されてしまう可能性があります。

```java
// 修正前：継承可能なクラスのまま、検証処理を持っている
public class PasswordPolicy {
    public boolean isValid(String pw) {           // ← 行①
        return pw.length() >= 12 && containsDigit(pw);
    }
}

// 不正なサブクラス（誤って、又は悪意で作られる）
public class LoosePolicy extends PasswordPolicy {
    @Override
    public boolean isValid(String pw) { return true; }   // 検証を無効化
}
// PasswordPolicy 型の変数に LoosePolicy が渡されると、呼出し側は気づかずに検証をすり抜ける
```

| 項目 | 内容 |
|---|---|
| どの行が | クラス宣言 `public class PasswordPolicy` と行①：継承とオーバライドが禁止されていない |
| なぜ危険か | サブクラスが `isValid` を上書きすると、`PasswordPolicy` 型として受け取った呼出し側は本来の検証が行われたと信じたまま処理を進める（検証の迂回） |
| どう直すか | 継承を禁止すべきクラスに `final` を付ける。特定のメソッドだけを守るならメソッドに `final` を付ける |

**対策方法**

開発者は、継承を禁止すべきクラスには、次のように `final` 属性を指定します。

〈例〉

```java
public final class UserInfo {
    (省略)
}
```

> **補足**
> クラス全体ではなく、特定のメソッドのみオーバライドを禁止したい場合は、メソッドに `final` を指定する。また、Java 17以降では `sealed` クラスにより、継承を許可するサブクラスを限定することもできる。

```java
// メソッド単位でオーバライドを禁止する
public class PasswordPolicy {
    public final boolean isValid(String pw) { ... }
}

// Java 17 以降：継承を許すサブクラスを列挙して限定する
public sealed class Payment permits CardPayment, BankPayment { ... }
```

| 指定 | 効果 | 使いどころ |
|---|---|---|
| `final` クラス | どのクラスも継承できない | 値オブジェクト、検証・認可を担うクラス |
| `final` メソッド | そのメソッドだけオーバライドできない | 拡張は許すが、セキュリティ上重要な処理は固定したい |
| `sealed` クラス | `permits` に列挙したクラスだけが継承できる | 継承関係を開発者の管理下に置きたい |
| `final` フィールド | 一度代入したら再代入できない | 不変オブジェクト（3.5） |

ここまでは「1つのオブジェクトを誰が触れるか」の話でした。しかし、正しく `private` にしたフィールドでも、**同じオブジェクトを複数のスレッドが同時に触る**と壊れることがあります。それが次節のレースコンディションです。

## 4. レースコンディション対策

### 4.1 レースコンディションとは

**レースコンディション**（競合状態）とは、並列して動作する複数のプロセスやスレッドが同一の資源に同時にアクセスした結果、処理の実行順序やタイミングによって、予期しない結果が生じてしまう状態をいいます。ファイルの存在や権限を確認してから実際に使うまでの間に状態が変わってしまう TOCTOU（Time of Check to Time of Use）も、その一種です。

レースコンディションはJavaに限らず、C/C++言語をはじめ、他の言語を用いたプログラミングにおいても発生する可能性がありますが、過去の本試験問題でJavaプログラミングにおける問題として取り上げられています。それらから抜粋したプログラムを例に挙げて解説します。テストでは同時アクセスがほとんど起きないため見つかりにくく、本番で利用者が増えたときに初めて表面化するのが厄介な点です。

### 4.2 サーブレットにおけるインスタンス変数の競合

〈例〉（修正前）

```java
package jp.co.s_sha.kinmuhyo;

(省略)

public class PDFDownloader extends HttpServlet {
    private static final long serialVersionUID = 1L;
    (省略)
    static final String KINMUHYO_LOCAL_PATH = "(省略)";
    static final String KINMUHYO_URL_PATH = "(省略)";

    File tempPDF;  // "tempPDF"をメンバ変数として定義          ← 行①

    public void init() {
        (省略)  // データベースへ接続
    }

    public void destroy() {
        (省略)  // データベースから切断
    }

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        String tempUserID = request.getRemoteUser();  // tempUserIDに利用者IDを代入
        tempPDF = new File(KINMUHYO_LOCAL_PATH, tempUserID + ".pdf");   // ← 行②
        makePDF(tempUserID, tempPDF);  // 利用者IDの勤務時間集計表を作成
        response.setContentType("text/html; charset=utf-8");
        PrintWriter out = response.getWriter();
        (省略)  // 定型的なHTML出力
        out.println("<a href=\"" + KINMUHYO_URL_PATH + tempPDF.getName()
                + "\">勤務時間集計表</a>");                              // ← 行③
        (省略)
    }
    (省略)
}
```

上記の例において、`PDFDownloader` クラスの冒頭で `tempPDF` がメンバ変数として定義されています。メンバ変数はクラス内のメソッドの外側に定義され、クラス内のメソッドから共通してアクセス可能です。なお、`tempPDF` のように `static` 指定のないメンバ変数は、インスタンスごとに確保されるため、**インスタンス変数**と呼ばれます。

一方、`tempUserID` のように、特定のメソッドやコンストラクタ内のみで使用する変数は**ローカル変数**と呼ばれ、当該メソッド、コンストラクタ内で定義します。

| 変数の種類 | 宣言する場所 | 確保される単位 | サーブレットでの共有 |
|---|---|---|---|
| ローカル変数（例：`tempUserID`） | メソッド・コンストラクタの中 | メソッドの呼出しごと（スレッドのスタック上） | 共有されない（安全） |
| インスタンス変数（例：`tempPDF`） | クラス内・メソッドの外（`static` なし） | インスタンスごと | 1つのインスタンスを全リクエストが共有（危険） |
| クラス変数（`static` 付き） | クラス内・メソッドの外（`static` あり） | クラスごとに1つ | すべてのインスタンス・スレッドで共有（危険。定数の `static final` は可） |

上記の例では、`doGet` メソッドにおいて、ローカル変数 `tempUserID` に利用者IDを代入した後、勤務表のローカルパスと、利用者IDに拡張子 `.pdf` を連結したものをファイル名として、インスタンス変数 `tempPDF` にセットしています。

続く `makePDF` メソッド（記述を省略）では、利用者IDで示されるパートの勤務時間集計表ファイルを作成し、その後、`out.println` メソッドで勤務時間集計表へアクセスするためのリンク情報を含んだHTML文書を出力しています。

サーブレットは通常、一つのインスタンスが生成され、複数の利用者からのリクエストを複数のスレッドで並行して処理します。そのため、こうした一連の処理を複数の利用者が同時に行った場合、インスタンス変数 `tempPDF` に対するレースコンディションが発生し、ある利用者が勤務時間集計表ファイルを作成してリンク情報を出力する前に、`tempPDF` が別な利用者によって書き換えられてしまう可能性があります。その結果、他人の勤務時間集計表へのリンクが表示されるなど、情報漏えいにつながるおそれがあります。

**図：インスタンス変数 tempPDF の競合（時間は上から下へ）**

```
 スレッドA（利用者 u001）             インスタンス変数 tempPDF          スレッドB（利用者 u002）
   │ 行②：tempPDF = u001.pdf ─────▶   u001.pdf
   │ makePDF(u001, tempPDF)            │
   │                                   u002.pdf ◀───── 行②：tempPDF = u002.pdf │
   │ 行③：リンクを出力 ◀───────────   u002.pdf                                 │
   ▼ （u001 の画面に u002 の勤務時間集計表へのリンクが表示される）                  ▼
```

これを修正するには、開発者は、ローカル変数 `tempUserID` と同様に、`tempPDF` を `doGet` メソッドのローカル変数として定義するとよいでしょう。ローカル変数はスレッドごとに個別に確保されるため、レースコンディションの発生を防ぐことができます。

〈修正例〉

```java
protected void doGet(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    String tempUserID = request.getRemoteUser();
    File tempPDF = new File(KINMUHYO_LOCAL_PATH, tempUserID + ".pdf");  // ローカル変数として定義
    makePDF(tempUserID, tempPDF);
    (省略)
}
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：リクエストごとに値が変わる `tempPDF` をインスタンス変数として宣言し、行②で `doGet` から代入している |
| なぜ危険か | サーブレットは1つのインスタンスを複数スレッドで共有するため、同時に処理された別の利用者のリクエストが `tempPDF` を上書きし、行③で他人の勤務時間集計表へのリンクを出力してしまう（機密性の侵害） |
| どう直すか | `tempPDF` を `doGet` メソッドのローカル変数として宣言する（行①を削除）。ローカル変数はスレッドごとに確保されるため、他のリクエストと共有されない |

科目Bでこの種の設問に答えるときのコツは、「`doGet`／`doPost` の中で、メソッドの外で宣言された変数に代入している行」を探すことです。サーブレットのフィールドに置いてよいのは、`static final` の定数や、`init()` で一度だけ設定して以後は読むだけのスレッドセーフなオブジェクトに限られます。

### 4.3 スレッドセーフな実装

> **補足:スレッドセーフ**
> 複数のスレッドから同時に呼び出されても正しく動作する性質を**スレッドセーフ**という。共有資源を扱う必要がある場合は、`synchronized` による排他制御や、`java.util.concurrent` パッケージのクラス(`ConcurrentHashMap`、`AtomicInteger` 等)を利用する。

どうしても複数のスレッドで共有する値が必要な場合（アクセス回数のカウンタ、ログイン失敗回数の記録など）について、修正前と修正後を対比します。

```java
// 修正前：共有のカウンタとマップを、排他制御なしで更新している
public class LoginServlet extends HttpServlet {
    private int totalCount = 0;                                        // ← 行①
    private final Map<String, Integer> failCount = new HashMap<>();    // ← 行②

    void recordFailure(String userId) {
        totalCount++;                                                  // ← 行③
        Integer n = failCount.get(userId);                             // ← 行④
        failCount.put(userId, n == null ? 1 : n + 1);                  // ← 行⑤
    }
}
```

```java
// 修正後①：java.util.concurrent のスレッドセーフなクラスを使う
public class LoginServlet extends HttpServlet {
    private final AtomicInteger totalCount = new AtomicInteger();
    private final ConcurrentHashMap<String, Integer> failCount = new ConcurrentHashMap<>();

    void recordFailure(String userId) {
        totalCount.incrementAndGet();               // 読出し・加算・書込みを不可分に行う
        failCount.merge(userId, 1, Integer::sum);   // 取得と更新を不可分に行う
    }
}

// 修正後②：synchronized で、同時に1スレッドしか入れない区間（クリティカルセクション）を作る
private final Object lock = new Object();
void recordFailure(String userId) {
    synchronized (lock) {
        totalCount++;
        Integer n = failCount.get(userId);
        failCount.put(userId, n == null ? 1 : n + 1);
    }
}
```

| 項目 | 内容 |
|---|---|
| どの行が | 行③の `totalCount++`、行④〜⑤の「`get` してから `put`」：行①・②の共有フィールドを排他制御なしで更新している |
| なぜ危険か | `++` は「読む・足す・書く」の3段階で、2つのスレッドが同時に読むと一方の加算が失われる。行④〜⑤も間に別スレッドが割り込むと更新が消える。ログイン失敗回数が正しく数えられないと、アカウントロックが働かず、パスワードの総当たり（第2章 2.4）を許す |
| どう直すか | `AtomicInteger`・`ConcurrentHashMap` の不可分な操作（`incrementAndGet`、`merge`）を使うか、`synchronized` で読出しから書込みまでを1つのクリティカルセクションにする |

`HashMap` や、日付の書式化に使う `SimpleDateFormat` は、スレッドセーフではない代表的なクラスです。開発者は、`static` フィールドに `SimpleDateFormat` を置いて共有するのではなく、不変でスレッドセーフな `java.time.format.DateTimeFormatter` を使うべきです。4.2 のローカル変数化、3.5 の不変オブジェクト、本項の並行処理用クラスという順に、「共有しない → 変更しない → 正しく排他する」と考えるのが、スレッドセーフな設計の優先順位です。

### 4.4 データベース更新時の競合

レースコンディションは、プログラム内の変数だけでなく、データベースの行でも起きます。次に、美容室の予約管理システムを題材とした例を示します。

**予約管理システムの機能概要**

- 顧客は、予約状況確認画面で希望する予約枠（美容師と時間帯の組合せ）を参照し、「空き」状態であれば「仮予約」に更新し、予約画面に進む。
- 希望する予約枠が既に「仮予約」状態の場合、システムは仮予約の有効期間（10分間）を確認し、有効期間を過ぎていれば新たに「仮予約」状態に置き換えた後、予約画面に進む。
- 顧客が予約画面で注文メニューを選択し、「予約する」ボタンを押すと「本予約」状態となり、予約確定画面に氏名、メールアドレス、予約内容等が表示される。

```
 予約枠の状態遷移
   「空き」 ──仮予約──▶ 「仮予約」 ──予約する──▶ 「本予約」
                          │ 10分経過（有効期間切れ）
                          └──別の顧客が選択──▶ 「仮予約」（置換え）
```

**〈競合状態が発生するケース①〉**

下図のように、顧客αと顧客βが、「空き」状態であった同一の予約枠をほぼ同時に選択した場合に、顧客αの仮予約がデータベースに反映されません。

**図:競合状態が発生するケース①のイメージ**

```
顧客α                     データベース(予約枠)          顧客β
  │ 参照 ─────────────▶  「空き」
  │                       「空き」  ◀───────────── 参照 │
  │ 「仮予約」に更新 ───▶ 「仮予約(α)」
  │                       「仮予約(β)」◀── 「仮予約」に更新 │
  ▼                     (αの仮予約が上書きされる)           ▼
```

**〈競合状態が発生するケース②〉**

次の図のように、顧客αが「仮予約」状態に更新後、10分以上経過してから「本予約」状態に更新するのと並行して、顧客βが同一の予約枠を選択し、有効期間切れの仮予約として「仮予約」状態に置き換えた場合、顧客αの本予約が顧客βの仮予約によって上書きされたり、同じ予約枠が二重に予約されたりしてしまいます。

**図:競合状態が発生するケース②のイメージ**

```
顧客α                       データベース(予約枠)         顧客β
  │ 「仮予約」に更新 ───▶ 「仮予約(α)」
  │   (10分以上経過)
  │                       「仮予約(α)・期限切れ」◀── 参照 │
  │ 「本予約」に更新 ───▶ 「本予約(α)」
  │                       「仮予約(β)」◀── 「仮予約」に置換え │
  ▼                     (αの本予約が上書きされる)             ▼
```

このような問題が発生したのは、データベースを参照してから更新するまでの間に、他の顧客によって同じ予約枠のデータが更新されたことを確認することなく更新処理を行っていたことが原因です。これを修正するには、開発者は、仮予約処理で使用するSQL文にWHERE句の条件を追加し、予約状態や最終更新日時等が他の顧客によって更新されていないことを確認する必要があります。

```sql
-- 修正前：参照時の状態を確認せずに更新している
UPDATE 予約枠
   SET 予約状態 = '仮予約', 顧客ID = ?, 最終更新日時 = CURRENT_TIMESTAMP
 WHERE 美容師ID = ? AND 時間帯 = ?
```

〈修正例(SQL)〉

```sql
UPDATE 予約枠
   SET 予約状態 = '仮予約', 顧客ID = ?, 最終更新日時 = CURRENT_TIMESTAMP
 WHERE 美容師ID = ? AND 時間帯 = ?
   AND 予約状態 = ?        -- 参照時の予約状態
   AND 最終更新日時 = ?    -- 参照時の最終更新日時
```

更新件数が0件であれば、参照後に他の顧客によって更新されたと判断し、予約状況確認画面に戻るなどの処理を行います。Javaでは、`executeUpdate` の戻り値（更新件数）でこれを判定します。

```java
int updated = ps.executeUpdate();     // WHERE 句に参照時の予約状態・最終更新日時を含めた UPDATE
if (updated == 0) {
    // 参照後に他の顧客が更新した：上書きせず、予約状況確認画面に戻して選び直してもらう
    return "redirect:/reserve/status";
}
```

| 項目 | 内容 |
|---|---|
| どの行が | 仮予約・本予約の `UPDATE` 文の WHERE 句：美容師IDと時間帯だけで行を特定し、参照時から状態が変わっていないかを確認していない |
| なぜ危険か | 参照してから更新するまでの間に他の顧客が同じ予約枠を更新すると、その更新を上書きしてしまい、仮予約の消失や二重予約が起きる（完全性の侵害） |
| どう直すか | WHERE 句に参照時の予約状態と最終更新日時を条件として加え、更新件数が0件なら他者が先に更新したと判断して処理を中断する（楽観的ロック） |

> **用語:楽観的ロック(楽観的排他制御)**
> データ参照時にはロックをかけず、更新時に「参照時から変更されていないか」をバージョン番号や更新日時で確認する排他制御方式。競合が少ない場合に有効である。これに対し、参照時点でロックを取得する方式(`SELECT ... FOR UPDATE` 等)を**悲観的ロック**という。

| 方式 | ロックの時点 | 競合の検出 | 向いている場面 | 注意点 |
|---|---|---|---|---|
| **楽観的ロック** | ロックしない | 更新時に、バージョン番号・更新日時で変更の有無を確認 | 競合が少ない（予約枠のように同じ行を同時に触ることがまれ） | 競合したら利用者にやり直してもらう処理が必要 |
| **悲観的ロック** | 参照時（`SELECT ... FOR UPDATE`） | 他者はロック解放まで待たされる | 競合が多い、やり直しが許されない処理 | ロック中に画面入力を待つと長時間ブロックし、デッドロックの危険もある |

Web アプリケーションでは、利用者が画面で入力している間（数分間）ずっと行をロックしておくのは現実的でないため、本例のように楽観的ロックがよく使われます。

## 5. 例外発生に備えた処理

### 5.1 try-catch-finally の構文

Javaのプログラム実行時に発生するランタイムエラー等の想定外の事象（**例外**）に備え、開発者は `try`、`catch`、`finally` 等を用いて次のように記述します。これはJavaに限らず、C++、C#等のプログラム言語でも同様です。

```java
try {
    // 例外が発生する可能性のある処理
} catch (例外クラス名 変数名) {
    // 例外が発生した場合に実行する処理
} catch (例外クラス名 変数名) {
    // 例外が発生した場合に実行する処理
} finally {
    // 例外の発生有無に関係なく、最後に必ず実行する処理
}
```

> **試験に出た!**
> 情報処理安全確保支援士試験の令和6年度の問4で、Javaで構築されたWebアプリケーションプログラムにおける、try-catchによる例外処理に関する問題が出題された。

複数の例外が発生する可能性があり、例外処理（try-catch）が必要な場合には、開発者は `catch` ブロックを複数記述します。このとき、JVM は `catch` を上から順に照合するため、サブクラス（より具体的な例外）を先に、スーパークラス（より一般的な例外）を後に書きます。逆に書くと、後ろの `catch` に到達できずコンパイルエラーになります。

### 5.2 例外クラスの種別 ― 検査例外と非検査例外

例外クラスの種別と例を次に示します。まず、例外クラスの継承関係を図で確認しておきましょう。

```
                     Throwable
                ┌───────┴────────┐
              Error            Exception
     （JVMの深刻な異常：         ├── IOException ── FileNotFoundException   ┐
      OutOfMemoryError 等。      ├── ClassNotFoundException                 ├ 検査例外
      通常は catch しない）       ├── SQLException                           ┘
                               └── RuntimeException                         ┐
                                     ├── NullPointerException                │ 非検査例外
                                     ├── IllegalArgumentException            │
                                     └── ArithmeticException                 ┘
```

**検査例外**

Javaの実行環境以外の環境が原因で発生するもので、例外処理が必要です（処理しない場合はコンパイルエラーとなる）。

- `FileNotFoundException`：ファイルが見つからない場合に発生
- `ClassNotFoundException`：クラスが見つからない場合に発生
- `SQLException`：データベースへのリクエストが正常に実行されなかった場合に発生

**非検査例外**

プログラムの誤りなど、Javaの実行環境が原因で発生するもので、例外処理は必須ではありません。スーパークラス（上位クラス）は `RuntimeException` です。

- `NullPointerException`：値がnullのオブジェクトにアクセスした場合に発生
- `IllegalArgumentException`：不正な引数をメソッドに渡した場合に発生
- `ArithmeticException`：ゼロ除算を行う等、算術計算でのエラー時に発生

| 種別 | 原因 | 例外処理 | スーパークラス | 例 |
|---|---|---|---|---|
| **検査例外** | Javaの実行環境以外の環境（ファイル、DB、ネットワーク） | 必須（`catch` するか `throws` で宣言しないとコンパイルエラー） | `Exception`（`RuntimeException` 以外） | `FileNotFoundException`、`ClassNotFoundException`、`SQLException` |
| **非検査例外** | プログラムの誤りなど | 必須ではない | `RuntimeException` | `NullPointerException`、`IllegalArgumentException`、`ArithmeticException` |

「検査」とは、コンパイラが「この例外の処理が書かれているか」を検査する、という意味です。

### 5.3 例外処理とセキュリティ

> **補足:例外処理とセキュリティ**
> - 例外発生時にスタックトレースやSQL文などの詳細情報を利用者の画面に出力すると、攻撃者に内部構造を知られる手掛かりとなる。詳細はログに記録し、利用者には汎用的なエラーメッセージのみを表示する。
> - ファイルやデータベース接続などの資源は `finally` ブロック、又はJava 7以降の try-with-resources 構文で確実に解放する。
> - 例外を `catch` して何もしない(握りつぶす)と、異常が検知されず、不正な状態のまま処理が継続されるおそれがある。

この3点を、それぞれ修正前・修正後のコードで確認します。

**(1) 例外の詳細を利用者に見せない**

```java
// 修正前
} catch (SQLException e) {
    PrintWriter out = response.getWriter();
    out.println("エラーが発生しました：" + e.getMessage());    // ← 行①
    e.printStackTrace(out);                                     // ← 行②
}
```

修正前のコードで利用者の画面に表示されるのは、たとえば次のような内容です。表の名前、列の名前、DB製品の種類、クラス名とメソッド名、ソースファイルの行番号まで、そのまま外部に出てしまいます。

```
エラーが発生しました：ERROR: column "card_no" does not exist
java.sql.SQLException: ERROR: column "card_no" does not exist
    at org.example.jdbc.PgStatement.executeQuery(PgStatement.java:224)
    at jp.example.shop.OrderDao.findByNo(OrderDao.java:42)
    at jp.example.shop.OrderServlet.doGet(OrderServlet.java:57)
```

```java
// 修正後
private static final Logger LOGGER = Logger.getLogger(OrderServlet.class.getName());

} catch (SQLException e) {
    String errorId = UUID.randomUUID().toString();               // 問合せ用の参照番号
    LOGGER.log(Level.SEVERE, "注文検索に失敗 errorId=" + errorId, e);   // 詳細はサーバ側のログへ
    request.setAttribute("errorId", errorId);
    response.setStatus(HttpServletResponse.SC_INTERNAL_SERVER_ERROR);
    request.getRequestDispatcher("/WEB-INF/error.jsp").forward(request, response);
    // error.jsp：「処理を完了できませんでした。お問合せの際は参照番号 xxxx をお伝えください。」
}
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：例外メッセージ `e.getMessage()` を画面に出力している。行②：スタックトレースを画面に出力している |
| なぜ危険か | 攻撃者は、表名・列名・DB製品名・クラス構成を知り、SQLインジェクション（第2章 2.8 の3.3「被害を招く2つの要因」）などの次の攻撃を組み立てる手掛かりにする（機密性の侵害） |
| どう直すか | 詳細（例外メッセージとスタックトレース）はサーバ側のログに記録し、利用者には汎用的なエラーメッセージと参照番号だけを表示する。参照番号でログと問合せを突き合わせられるため、運用上の調査も困難にならない |

ログに記録する際も、開発者はパスワードやクレジットカード番号などの秘密情報をメッセージに含めないこと、利用者の入力をログに書くときは改行コードを除去してログの偽装を防ぐことに注意すべきです（ログの管理は第7章 7.8）。また、Webアプリケーションサーバの設定で、未処理の例外が起きたときに既定のエラーページ（スタックトレースを含む）を表示しないようにしておくと、`catch` 漏れがあっても内部情報が出ません（第3章 3.6 の4節「Webサーバの実装や設定の不備」）。

**(2) 例外を握りつぶさない**

```java
// 修正前
try {
    auditLog.write(userId, "権限変更");
} catch (IOException e) {
    // 何もしない                                            ← 行①
}
grantAdminRole(userId);
```

```java
// 修正後
try {
    auditLog.write(userId, "権限変更");
} catch (IOException e) {
    LOGGER.log(Level.SEVERE, "監査ログの書込みに失敗", e);
    throw new IllegalStateException("監査ログを記録できないため権限変更を中止", e);
}
grantAdminRole(userId);
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：`catch` ブロックが空で、例外を握りつぶしている |
| なぜ危険か | 監査ログの書込みが失敗しても処理が続き、記録の残らない権限変更が行われる。異常が検知されず、不正な状態のまま処理が継続される（追跡可能性・完全性の喪失） |
| どう直すか | 例外をログに記録し、続行してはいけない処理なら中止して呼出し元に例外を通知する。処理を安全側に倒す（フェールセーフ、第1章 1.2） |

### 5.4 リソースの確実な解放 ― try-with-resources

ガーベジコレクションはメモリを回収しますが、ファイルハンドル、DB接続、ソケットといった**OSやDBの資源**は、開発者が `close` しない限り解放されません。例外の発生時に `close` が飛ばされると、資源が少しずつ漏れて、やがて接続数の上限に達し、サービスが止まります（可用性の侵害）。

```java
// 修正前：例外が起きると close に到達しない
Connection con = dataSource.getConnection();
PreparedStatement ps = con.prepareStatement(SQL);       // ← 行①
ResultSet rs = ps.executeQuery();                       // ← 行②（ここで SQLException が起きると…）
while (rs.next()) { ... }
rs.close();                                             // ← 行③
ps.close();
con.close();                                            //    以下の close が実行されない
```

```java
// 修正後①（Java 6 以前の書き方）：finally で必ず閉じる
Connection con = null;
PreparedStatement ps = null;
try {
    con = dataSource.getConnection();
    ps = con.prepareStatement(SQL);
    ...
} finally {
    if (ps != null)  { try { ps.close(); }  catch (SQLException e) { LOGGER.log(Level.WARNING, "close失敗", e); } }
    if (con != null) { try { con.close(); } catch (SQLException e) { LOGGER.log(Level.WARNING, "close失敗", e); } }
}

// 修正後②（Java 7 以降）：try-with-resources
try (Connection con = dataSource.getConnection();
     PreparedStatement ps = con.prepareStatement(SQL);
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) { ... }
}   // ブロックを抜けると、例外の有無にかかわらず rs → ps → con の順に自動で close される
```

| 項目 | 内容 |
|---|---|
| どの行が | 行③以降：`close` を通常の処理の流れの最後に書いているため、行①・②で例外が発生すると到達しない |
| なぜ危険か | 例外が起きるたびにDB接続が解放されずに残り、コネクションプールが枯渇してサービスが停止する（可用性の侵害）。攻撃者が例外を起こしやすいリクエストを繰り返すと、DoS（第2章 2.7）と同じ結果になる |
| どう直すか | try-with-resources 構文で資源を宣言する（Java 7 以降）。`AutoCloseable` を実装した資源は、ブロックを抜けるときに宣言と逆の順で必ず `close` される。古い環境では `finally` で `null` チェックのうえ閉じる |

try-with-resources は、`finally` を手書きする方法より短く、`close` 自体が例外を投げた場合も元の例外を失わない（抑制された例外として保持する）点で優れています。

### 5.5 throw と throws ― 例外を報告する

なお、例外はキャッチ（catch）するだけでなく、プログラム実行時に回復不能な例外が発生した場合等は、開発者が意図的にシステムにスロー（throw）して報告し、例外処理を実行させることもあります。その場合には次のように `throw` を用います。

```java
throw new 例外クラス名();
```

また、メソッド内で処理せず呼出し元に例外を伝播させる場合は、メソッド宣言に `throws` 節を記述します。

```java
// 入力値の検証で、不正な引数を呼出し元に知らせる
public void setQuantity(int q) {
    if (q < 1 || q > 99) {
        throw new IllegalArgumentException("数量は1〜99で指定してください");
    }
    this.quantity = q;
}

// 検査例外を自分では処理せず、呼出し元に伝播させる
public Order findByNo(String orderNo) throws SQLException { ... }
```

| 構文 | 書く場所 | 意味 |
|---|---|---|
| `throw` | メソッドの本体（文） | 例外オブジェクトを生成して投げる |
| `throws` | メソッドの宣言（シグネチャ） | このメソッドが呼出し元に例外を伝播させうることを宣言する |

`throws` で伝播させた例外も、最終的にはどこかで `catch` し、5.3 の(1)のように「詳細はログへ、利用者には汎用メッセージ」で処理する必要があります。開発者は、画面に近い層（サーブレットやフレームワークの共通エラーハンドラ）で一括して処理する設計にしておくと、漏れを防げます。

## 6. 入力を扱う箇所の書き方 ― 第2章 2.8・第3章 3.6 を Java で実装する

第2章 2.8 では、攻撃者がデータの中に命令として解釈される記号を紛れ込ませる攻撃（SQLインジェクション、ディレクトリトラバーサルなど）を見ました。第3章 3.6 の5節では、その原因が「利用者が入力したデータが、別の言語の中に区切りを意識せずに埋め込まれること」だと整理しました。本節では、Java の開発者がこれを**どう書いて防ぐか**を、3つの典型で確認します。どれも共通の原則は「**データと命令を分けて渡す**」「**検証は正規化した後で行う**」「**信頼できないデータからオブジェクトを復元しない**」です。

### 6.1 SQL文の組立て ― PreparedStatement によるプレースホルダ

```java
// 修正前：入力値を文字列連結でSQL文に埋め込んでいる
String sql = "SELECT * FROM orders WHERE order_no = '" + orderNo + "'";   // ← 行①
Statement st = con.createStatement();
ResultSet rs = st.executeQuery(sql);                                    // ← 行②
```

```java
// 修正後：プレースホルダ（?）でSQL文の構造を先に確定させ、値は後から割り当てる
String sql = "SELECT * FROM orders WHERE order_no = ?";
try (PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setString(1, orderNo);              // 1番目の ? に、文字列として割り当てる
    try (ResultSet rs = ps.executeQuery()) {
        ...
    }
}
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：外部から受け取った `orderNo` を文字列連結でSQL文に埋め込み、行②で `Statement` により実行している |
| なぜ危険か | `orderNo` に引用符などSQLとして意味をもつ文字が含まれると、SQL文の構造そのものが変わり、攻撃者が意図したSQL文が実行される（SQLインジェクション：機密性・完全性の侵害） |
| どう直すか | `PreparedStatement` を使い、変数部分をプレースホルダ `?` にして、値は `setString` などで割り当てる。SQL文の構造が値の割当て前に確定するため、入力値は単なる文字列定数として扱われ、命令として解釈されない |

科目Bでは、このコードの `prepareStatement` や `setString` の部分を空欄にして字句を答えさせる設問がよく出ます（第2章 2.8 の3.4、令和5年春期 午後Ⅰ問1）。注意点が2つあります。1つは、`PreparedStatement` を使っていても、SQL文の文字列自体を `"... WHERE " + column + " = ?"` のように入力値で組み立てると意味がないことです。表名・列名・`ORDER BY` の並び順のようにプレースホルダにできない部分は、開発者がプログラム内に用意した候補（許可リスト）から選ばせるべきです。もう1つは、LIKE 句で `%` `_` をワイルドカードでなく文字として扱いたい場合、割り当てる値の側でエスケープが必要なことです（第2章 2.8 の3.4）。

### 6.2 ファイルパスの正規化 ― ディレクトリトラバーサル対策

```java
// 修正前：受け取ったファイル名をそのままパスに連結している
private static final String BASE_DIR = "/var/app/files/";
String fileName = request.getParameter("file");
File f = new File(BASE_DIR + fileName);                       // ← 行①
if (fileName.contains("../")) { throw new SecurityException(); }   // ← 行②
Files.copy(f.toPath(), response.getOutputStream());
```

```java
// 修正後：正規化してから、基準ディレクトリの中にあるかを検証する
private static final Path BASE_DIR = Paths.get("/var/app/files").toAbsolutePath().normalize();

String fileName = request.getParameter("file");
Path target = BASE_DIR.resolve(fileName).normalize();         // 「.」「..」を解決した絶対パス
if (!target.startsWith(BASE_DIR)) {                           // 基準ディレクトリの外なら拒否
    response.sendError(HttpServletResponse.SC_NOT_FOUND);
    return;
}
Path real = target.toRealPath();                              // シンボリックリンクも解決して実体を確認
if (!real.startsWith(BASE_DIR.toRealPath())) {
    response.sendError(HttpServletResponse.SC_NOT_FOUND);
    return;
}
Files.copy(real, response.getOutputStream());
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：利用者が指定したファイル名をそのままパスに連結している。行②：正規化する前の文字列に対して、特定の文字列だけを拒否している |
| なぜ危険か | パスに上位ディレクトリを表す要素が含まれると、公開ディレクトリの外にある非公開ファイルが読み出される（機密性の侵害）。行②のような文字列検査は、区切り文字の違い、エンコード、シンボリックリンクなどの別表現で迂回されるため、検査として不十分である |
| どう直すか | `Path.normalize()`（さらに `toRealPath()`）でパスを正規化してから、`startsWith` で基準ディレクトリ配下にあることを検証する。最も確実なのは、利用者にファイル名を指定させず、ID を受け取ってサーバ側の対応表からファイル名を決める設計にすること |

ここでのポイントは「**検証は正規化の後**」という順序です。同じファイルを指す書き方は何通りもあるため、正規化（一意の表現に変換すること）をせずに検査しても、別の書き方で通り抜けられます。`Path.startsWith` は文字列の前方一致ではなく、パスの要素単位で比較するため、`/var/app/files2` のような紛らわしい名前を誤って許可することもありません。第2章 2.8 の6.2「ディレクトリトラバーサル攻撃への対策」で見た `basename()`（ディレクトリ部分を取り除く）や、デコード・正規化後のチェックを、Java ではこのように書きます。

### 6.3 信頼できないデータのデシリアライズを避ける

**シリアライズ**（直列化）は、Javaのオブジェクトをバイト列に変換して保存・送信することで、その逆に、バイト列からオブジェクトを復元することを**デシリアライズ**といいます。Java 標準の仕組みでは、`ObjectOutputStream` でシリアライズし、`ObjectInputStream.readObject()` でデシリアライズします。4.2 の例にあった `serialVersionUID` は、このシリアライズの互換性を管理するための番号です。

問題は、`readObject()` が「バイト列に書かれたクラスのオブジェクトを、そのクラスの復元処理を呼びながら組み立てる」点にあります。外部から受け取ったバイト列をそのまま復元すると、開発者が想定していないクラスのオブジェクトが生成され、その復元処理が連鎖的に実行されて、任意のコードの実行やサービス停止につながることがあります（CWE-502「信頼できないデータのデシリアライゼーション」）。開発者がチェックするつもりでも、`readObject()` の後でキャストや検証をする時点では、危険な処理はもう終わっています。

```java
// 修正前：Cookie で受け取ったバイト列を、そのままオブジェクトに復元している
byte[] data = Base64.getDecoder().decode(cookieValue);
try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(data))) {
    Cart cart = (Cart) in.readObject();                    // ← 行①
}
```

```java
// 修正後①：Java のシリアライズを使わず、JSON などのデータ形式で受け取り、
//          決まったクラスの決まった項目だけに変換したうえで値を検証する
//          （Jackson などのJSONライブラリ。多態型の自動復元〈型情報の埋込み〉は無効のまま使う）
CartDto dto = objectMapper.readValue(json, CartDto.class);
validate(dto);                                            // 商品ID の形式、数量の範囲などを検証

// 修正後②：Cookie には状態を持たせず、サーバ側のセッションに保存する（最も確実）
Cart cart = (Cart) request.getSession().getAttribute("cart");

// 修正後③：どうしても ObjectInputStream を使う場合は、復元を許すクラスを許可リストで限定する
//          （Java 9 以降の ObjectInputFilter。許可したクラス以外は readObject の途中で拒否される）
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
        "jp.example.shop.Cart;jp.example.shop.CartItem;java.base/*;maxdepth=5;!*");
in.setObjectInputFilter(filter);
```

| 項目 | 内容 |
|---|---|
| どの行が | 行①：利用者が改変できる Cookie の値を、`ObjectInputStream.readObject()` で検証せずにデシリアライズしている |
| なぜ危険か | 攻撃者がバイト列を細工すると、想定外のクラスのオブジェクトが生成され、その復元処理を通じて任意のコードが実行されたり、サービスが停止したりするおそれがある。キャストや検証は復元の後なので間に合わない |
| どう直すか | 信頼できないデータを Java のシリアライズ形式で受け取らない。JSON などのデータ形式で受け取り、決まったクラスへの変換と値の検証を行うか、状態をサーバ側に保持する。やむを得ず使う場合は `ObjectInputFilter` で許可するクラスを限定する |

なお、サーバ側で生成したデータを利用者に預ける場合でも、改ざんされていないことを確かめたいなら、開発者はデータにMAC（メッセージ認証コード、第7章 7.1）を付けて検証すべきです。

### 6.4 入力処理の対策のまとめ

| 脆弱性（第2章 2.8） | 原因になる Java の書き方 | 安全な書き方 | CWE |
|---|---|---|---|
| SQLインジェクション | 文字列連結したSQL文を `Statement` で実行 | `PreparedStatement` とプレースホルダ | CWE-89 |
| ディレクトリトラバーサル | 入力値をそのままパスに連結、正規化前の文字列検査 | `normalize()`／`toRealPath()` の後に `startsWith` で検証。ファイル名を受け取らない設計 | CWE-22 |
| 信頼できないデータのデシリアライズ | 外部データを `ObjectInputStream.readObject()` で復元 | JSON 等＋決まったクラスへの変換と検証、サーバ側に保持、`ObjectInputFilter` | CWE-502 |
| OSコマンドインジェクション | `Runtime.exec("sh -c ...")` のようにシェル経由で入力値を連結 | シェルを使わず、Java の API で処理する。外部プログラムが必要なら `ProcessBuilder` にプログラム名と引数を別々に渡す（8.2 の `system` 関数の注意と同じ考え方） | CWE-78 |
| XSS | 入力値をエスケープせずに JSP・HTML へ出力 | テンプレートエンジンの自動エスケープ（JSTL の `<c:out>` など）を使う（第3章 3.6 の5.2） | CWE-79 |
| エラーメッセージによる情報露出 | 例外の詳細を画面に出力 | 詳細はログ、画面は汎用メッセージ（本ノート5.3） | CWE-209 |

## 7. 静的解析とコードレビュー ― 書いたコードを誰がどう確かめるか

### 7.1 静的解析ツールの指摘の見た目

ここまでの書き方の誤りは、人のレビューだけで漏れなく見つけるのは困難です。開発者とレビュー担当者は、プログラムを実行せずにソースコードやバイトコードを解析して欠陥を指摘する**静的解析**ツールを、ビルドの工程（CI、8.1）に組み込んで使います。Java では SpotBugs（とセキュリティ向けプラグインの Find Security Bugs）などが使われます。指摘は、おおむね次の形で出力されます（表示形式はツールや設定により異なります。下はイメージです）。

### 7.2 コーディング規約の条文例

開発組織は、本ノートで扱った書き方を、各自の判断に任せるのではなく**コーディング規約**として明文化し、レビューと静的解析の基準にします。Java では、JPCERT/CC が日本語訳を公開している「CERT/Oracle版 Javaセキュアコーディングスタンダード」がよく参照されます。条文の例を本ノートの節と対応づけると次のとおりです。

| 規則ID | 規則の要旨 | 本ノート |
|---|---|---|
| OBJ01-J | フィールドへのアクセスを制限する | 3.2〜3.4 |
| OBJ00-J | 不変条件をもつクラスやメソッドの拡張を、信頼できるサブクラスだけに限定する | 3.6 |
| VNA02-J | 共有変数への複合操作が不可分に行われるようにする | 4.3 |
| ERR00-J | 検査例外を抑制したり無視したりしない | 5.3 (2) |
| ERR01-J | 例外によって機密情報を漏えいさせない | 5.3 (1) |
| FIO04-J | 不要になったリソースは解放する | 5.4 |
| IDS00-J | SQLインジェクションを防ぐ | 6.1 |
| FIO16-J | パス名を検証する前に正規化する | 6.2 |
| SER12-J | 信頼できないデータのデシリアライズを防ぐ | 6.3 |

社内規約の条文は、たとえば「SQL文の組立てには `PreparedStatement` を用い、外部から受け取った値を文字列連結でSQL文に含めてはならない（理由：SQLインジェクションを防ぐため）」のように、**禁止事項・推奨する書き方・理由**をそろえて書くと、レビューで判断がぶれません。

- **Q6**：例外処理の概要について述べよ。

> **解答例**
> - Q1：Javaはポインタの概念を排除しており、プログラマがメモリアドレスを直接操作できないため、不正なメモリアクセスやバッファオーバフローが生じにくい。メモリはガーベジコレクションによって自動的に解放されるため、メモリリークや use-after-free を防ぎやすい。配列の境界チェックや型チェックが実行時に行われ、範囲外アクセスは例外として検出される（本ノート1.3）。
> - Q2：ネットワークなどを通じて外部から受け取ったプログラムを、セキュリティが確保された領域で動作させ、不正な操作や動作を防ぐ仕組み。JDK 1.0 ではリモートコードを限定された資源にのみアクセスさせ、Java 2 以降はすべてのコードをセキュリティポリシに基づいてアクセス制御する。クラスローダ、セキュリティマネージャ、ポリシ、アクセスコントローラで構成される（本ノート2節）。
> - Q3：フィールドを `private` にしてメソッド経由でアクセスさせる（カプセル化）。読出しだけが必要なプログラムには読出し用メソッドのみを定義したインタフェースを介してアクセスさせる。変更不要なら `private final` の不変クラス（`record`）にする（本ノート3.3〜3.5）。
> - Q4：並列して動作する複数のプロセスやスレッドが同一の資源に同時にアクセスし、実行順序やタイミングによって予期しない結果が生じる状態。対策は、リクエストごとの値をローカル変数にする、共有資源は `synchronized` や `java.util.concurrent` のクラスで排他制御する、DB更新ではWHERE句に参照時の状態・更新日時を加えて他者の更新を確認する（楽観的ロック）（本ノート4節）。
> - Q5：継承を禁止すべきクラスに `final` を指定する。特定のメソッドのオーバライドだけを禁止するならメソッドに `final` を指定し、Java 17 以降は `sealed` で継承を許すサブクラスを限定できる（本ノート3.6）。
> - Q6：例外が発生する可能性のある処理を `try` で囲み、例外の種類ごとに `catch` で処理を書き、例外の有無にかかわらず実行する処理を `finally` に書く。検査例外は処理が必須、非検査例外（`RuntimeException` の系統）は必須ではない。詳細はログに記録して利用者には汎用メッセージを表示し、資源は `finally` か try-with-resources で解放し、例外を握りつぶさない。回復不能な場合は `throw` で報告し、`throws` で呼出し元に伝播させる（本ノート5節）。

### 8.2 確認問題（過去問題）

プログラム実行時の主記憶管理に関する記述として、適切なものはどれか。

- ア 主記憶の空き領域を結合して一つの連続した領域にすることを、可変区画方式という。
- イ プログラムが使用しなくなったヒープ領域を回収して再度使用可能にすることを、ガーベジコレクションという。
- ウ プログラムの実行中に主記憶内でモジュールの格納位置を移動させることを、ローディングという。
- エ プログラムの実行中に必要になった時点でモジュールをロードすることを、動的リンキングという。

*〔情報処理技術者試験 高度共通・H28秋 午前I〕*

> **解答・解説**
>
> **正解:イ**
>
> ガーベジコレクションは、不要になったメモリ領域を自動的に解放する機能であり、Javaなどの言語で採用されている。これにより、プログラマがメモリを管理する負担を軽減しているが、実行時にはシステム資源（CPU時間）を消費するため、同機能の実行による応答性への影響等を考慮する必要がある。したがってイが正解である。
>
> - ア：主記憶の空き領域を結合して一つの連続した領域にすることは、**コンパクション**という。可変区画方式は、プログラムの大きさに応じて主記憶を区画に分割して割り当てる方式である。
> - ウ：プログラムの実行中に主記憶内でモジュールの格納位置を移動させることは、**再配置(リロケーション)**という。
> - エ：プログラムの実行中に必要になった時点でモジュールをロードすることは、**動的ローディング**という。動的リンキングは、実行時に必要なモジュールを結合（リンク）することである。

ガーベジコレクションやコンパクションは、科目A-1の `A-1/4.2_記憶管理と同期・排他制御.md` で扱った実記憶管理の用語です。科目A-2・Bでは、これを「Javaではメモリの解放を開発者が書かないため、use-after-free が起きにくい（ただしメモリ以外の資源は自分で解放する）」というセキュリティの観点で説明できるようにしておきましょう。

### 8.3 演習：どの行が・なぜ危険で・どう直すか

科目Bの形式に合わせた練習です。次のサーブレットの問題点を、0.1 の型で3つ挙げてください。

```java
public class ReportServlet extends HttpServlet {
    private String reportName;                                              // (a)

    protected void doGet(HttpServletRequest req, HttpServletResponse res)
            throws IOException {
        reportName = req.getParameter("name");                              // (b)
        try {
            Connection con = ds.getConnection();                            // (c)
            Statement st = con.createStatement();
            ResultSet rs = st.executeQuery(
                "SELECT * FROM reports WHERE name = '" + reportName + "'"); // (d)
            ...
            con.close();
        } catch (SQLException e) {
            res.getWriter().println(e.toString());                          // (e)
        }
    }
}
```

> **解答例**
> - **(a)・(b)**：リクエストごとの値 `reportName` をインスタンス変数に代入している。サーブレットは1インスタンスを複数スレッドで共有するため、同時に処理された他の利用者のリクエストで値が書き換わり、別の利用者のレポートを処理・表示するおそれがある。`reportName` を `doGet` のローカル変数にする（本ノート4.2）。
> - **(d)**：外部から受け取った `reportName` を文字列連結でSQL文に埋め込んでいる。SQLとして意味をもつ文字を含む値によりSQL文の構造が変えられ、SQLインジェクションが成立する。`PreparedStatement` のプレースホルダ `?` を使い、`setString` で値を割り当てる（本ノート6.1）。
> - **(e)**：例外の詳細を画面に出力している。表名やDB製品などの内部情報が攻撃者に知られる。詳細はログに記録し、利用者には汎用的なエラーメッセージを表示する（本ノート5.3）。
> - 加えて **(c)**：例外が発生すると `con.close()` に到達せず、DB接続が解放されない。接続が枯渇してサービスが停止するおそれがあるため、try-with-resources で `Connection`・`Statement`・`ResultSet` を宣言する（本ノート5.4）。

## 9. 試験対策まとめ（重要ポイント）

### 9.1 知識の確認（科目A-2向け）

- **Javaテクノロジ**：Java言語だけでなく、開発環境 JDK、実行環境 JRE を含む各種技術の総称。JRE の脆弱性も攻撃の入口になるため、運用者が更新を管理する。
- **実行の仕組み**：ソースコード → `javac` → プラットフォームに依存しない中間バイトコード → JVM 上で実行（"Write Once, Run Anywhere"）。C/C++ はネイティブコードに直接コンパイル。
- **言語としての安全性**：ポインタの排除（メモリアドレスを直接操作できない）、ガーベジコレクション（メモリリーク・use-after-free の防止）、実行時の配列境界チェックと型チェック。ただし JNI 経由のネイティブコードは JVM の保護の外。
- **ガーベジコレクション**：使用しなくなったヒープ領域を回収して再利用可能にする。CPU時間を消費し応答性に影響。コンパクション（空き領域の結合）、再配置（リロケーション）、動的ローディングと区別する。
- **サンドボックスモデルの変遷**：JDK 1.0＝ローカルコードは完全なアクセス権、リモートコード（アプレット）はサンドボックス内のみ → JDK 1.1＝署名付きアプレットをローカルコード同様に信頼 → Java 2（JDK 1.2）以降＝すべてのコードをセキュリティポリシで制御。
- **4つの構成要素**：クラスローダ（クラスの検索・取得、ポリシの参照、権限を付けたクラス定義。ブートストラップ／プラットフォーム／アプリケーション）、セキュリティマネージャ（`java.lang.SecurityManager`、`-Djava.security.manager`）、ポリシ（`grant codeBase … permission …`）、アクセスコントローラ（`checkPermission`、権限がなければ `AccessControlException`）。ロード後はバイトコードベリファイアが検証。
- **現在の位置付け**：アプレットは Java 9 で非推奨、Java 11 以降は実行環境なし。セキュリティマネージャは Java 17（JEP 411）で非推奨、Java 24（JEP 486）で恒久的に無効化。
- **アクセス修飾子**：`public`（どこからでも）＞ `protected`（同一パッケージ＋サブクラス）＞ 指定なし（同一パッケージ）＞ `private`（同一クラスのみ）。フィールドは `private`。
- **フィールドの保護**：カプセル化（`private`＋アクセスメソッド）→ 読出し専用インタフェース → 不変オブジェクト（`private final`、Java 16 以降の `record`）。可変オブジェクトは防御的コピー。
- **継承の制限**：クラスに `final`（継承禁止）、メソッドに `final`（オーバライド禁止）、Java 17 以降の `sealed`（許可するサブクラスを限定）。
- **変数の種類**：ローカル変数（スレッドごと、安全）／インスタンス変数（`static` なし、サーブレットでは全リクエストで共有）／クラス変数（`static`）。
- **スレッドセーフ**：`synchronized`、`java.util.concurrent`（`ConcurrentHashMap`、`AtomicInteger`）。`HashMap`、`SimpleDateFormat` はスレッドセーフでない。
- **楽観的ロックと悲観的ロック**：楽観的＝ロックせず更新時にバージョン番号・更新日時で確認（競合が少ない場合）、悲観的＝参照時に `SELECT ... FOR UPDATE` でロック。
- **検査例外と非検査例外**：検査例外（`FileNotFoundException`、`ClassNotFoundException`、`SQLException`）は処理しないとコンパイルエラー。非検査例外（`RuntimeException` の系統：`NullPointerException`、`IllegalArgumentException`、`ArithmeticException`）は処理が必須ではない。
- **try-with-resources**：Java 7 以降。`AutoCloseable` の資源をブロック終了時に自動で close。`finally` での解放の代替。
- **`throw` と `throws`**：`throw` は例外を投げる文、`throws` は呼出し元に伝播させることをメソッド宣言に書く節。
- **入力処理の CWE**：SQLインジェクション CWE-89、パストラバーサル CWE-22、デシリアライズ CWE-502、エラーメッセージによる情報露出 CWE-209。

### 9.2 記述式で問われる観点（科目B向け）

- **答え方の型**：「（どの行が）〇〇行目で、外部から受け取った値を〜している。（なぜ危険か）その結果、攻撃者／他の利用者が〜でき、〜が起きる。（どう直すか）〜に変更する。〜なので防げる。」の3段で書く。
- **サーブレットのレースコンディション**：「`doGet` で、リクエストごとに異なる値をインスタンス変数に代入しているため、複数の利用者のリクエストが同時に処理されると値が上書きされ、他人の情報が表示される。当該変数を `doGet` のローカル変数にする（ローカル変数はスレッドごとに確保される）。」
- **DB更新の競合**：「参照してから更新するまでの間に他の顧客が同じ予約枠を更新したことを確認していないため、二重予約や上書きが起きる。UPDATE 文の WHERE 句に参照時の予約状態と最終更新日時を加え、更新件数が0件なら予約状況確認画面に戻す。」空欄補充では WHERE 句の追加条件が問われやすい。
- **SQLインジェクション**：「入力値を文字列連結でSQL文に埋め込んでいる行」を特定し、「`PreparedStatement` でプレースホルダを使い、`setString` で値を割り当てる。SQL文の構造が先に確定するため、入力値が命令として解釈されない」と書く（第2章 2.8、第3章 3.6）。
- **例外処理の不備**：「スタックトレースや例外メッセージを画面に出力しているため、攻撃者に内部構造（表名・製品名）を知られる。詳細はログに記録し、利用者には汎用的なエラーメッセージを表示する。」空の `catch` は「異常が検知されず、不正な状態のまま処理が継続される」と指摘する。
- **リソースの解放漏れ**：「例外が発生すると close に到達せず、DB接続が解放されないため、接続が枯渇してサービスが停止する。try-with-resources（又は finally）で解放する。」
- **ファイルパス**：「利用者が指定したファイル名を検証せずにパスに連結しているため、公開ディレクトリ外のファイルが読み出される。正規化した後で基準ディレクトリ配下か検証する。ファイル名を利用者に指定させない設計がより確実。」「検証は正規化の後」という順序を必ず書く。
- **デシリアライズ**：「利用者が改変できるデータを `readObject` で復元しているため、想定外のクラスが生成され任意のコード実行につながる。Java のシリアライズ形式で受け取らず、JSON 等で受け取って決まったクラスに変換し値を検証する（又はサーバ側に保持する）。」
- **クラス設計**：「フィールドが `public` のため、他のクラスから値を書き換えられる。`private` にしてメソッド経由にし、読出しのみの利用者には読出し専用インタフェースを渡す。」「検証処理をもつクラスが継承可能なため、サブクラスでオーバライドされ検証を迂回される。`final` を指定する。」
- **Javaを選ぶ理由・Javaでも残る課題**：「Javaはポインタがなく配列の境界チェックが行われるため、C/C++ と比べてバッファオーバフローが生じにくい。ただし JNI で呼ぶネイティブコード、マルチスレッドの競合、入力値の扱いは開発者が対策する必要がある。」
- **開発プロセスでの確認方法**：「静的解析ツールをビルドに組み込み、指摘を1件ずつ確認する。誤検知と検知漏れがあるため、コーディング規約に基づくレビューと脆弱性診断で補う」（8.1、第5章 5.3）。
