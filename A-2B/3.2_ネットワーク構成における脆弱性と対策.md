## 0. 全体像 ― なぜこの分野を学ぶのか

3.1 では、脆弱性を「リスクを発生しやすくしたり、拡大させたりする弱点」と定義しました。本ノートからは、情報システムの構成要素ごとに具体的な脆弱性を見ていきます。最初に取り上げるのは、個々のサーバやソフトウェアではなく、それらをつなぐ**ネットワークの構成**そのものの弱点です。

ネットワーク構成の脆弱性は、ソフトウェアのバグと違ってパッチでは直せません。設計段階で作り込まれ、一度作ると変えにくいからです。たとえば、公開Webサーバと社内のファイルサーバを同じセグメントに置いた「フラットなネットワーク」では、Webサーバに1つ脆弱性があっただけで、攻撃者は社内のすべての機器に手が届きます。第2章 2.9 で学んだマルウェアの**ラテラルムーブメント**（横展開）や、ランサムウェアによる全社規模の暗号化が起きる背景には、たいていこの構成上の弱点があります。逆に言えば、構成を適切に設計しておけば、個々の機器が突破されても被害を局所化できます。これはノート1.2 で学んだ多層防御と「重要なシステムの分離」を、ネットワークの形で実現することにほかなりません。

本ノートは、ネットワーク構成の脆弱性を、損なわれる特性で2つに分けて整理します。

1. **機密性・完全性の侵害につながる脆弱性**：フラットなネットワーク、アクセス制限のない外部接続、多すぎる接続口、無防備な無線LAN、リピータハブ。対策は、セグメント分割とDMZ、接続口の集約、無線LANの暗号化と認証、スイッチの使用、物理的保護。
2. **可用性の低下につながる脆弱性**：帯域・処理能力の不足、単一障害点、帯域制限の欠如、大きすぎるブロードキャストドメイン。対策は、十分な帯域、冗長化と負荷分散、帯域制限、VLANによる分割。

前提となるスイッチやVLANの仕組みは 1.4 の8節で学びました。本ノートはそれを「構成の弱点をどう塞ぐか」という設計の視点で使います。ファイアウォールの詳しい機能は第5章 5.5 で扱います。

科目Bの業務観点では、「②企画・設計・開発・運用におけるセキュリティ確保」のうち「アーキテクチャ設計」と、「③利用におけるセキュリティ対策の適用」のうち「ネットワーク及び機器のセキュリティ管理」に直結します。科目Bでは、事例のネットワーク構成図を読み、「どこにどの機器を置き、どのセグメント間の通信を許可すべきか」「マルウェア感染がなぜ全社に広がったのか」を答えさせる設問が頻出です。科目A-2では、VLANやブロードキャストに関連するプロトコル（ARP、DHCP）の知識が問われます。

## 1. ネットワーク構成における脆弱性

ここでいう**ネットワーク構成**とは、トポロジ（接続の形）、セグメンテーション（ネットワークの区切り方）、回線、通信機器の種類・配置などを指します。ネットワーク構成における脆弱性には、**機密性、完全性の侵害**につながるものと、**可用性の低下**につながるものがあります。

### 1.1 機密性・完全性の侵害につながる脆弱性

機密性、完全性の侵害につながる脆弱性の例として、次の表のようなものがあります。いずれも「攻撃者が入り込む口が多い」か「入り込んだあとに動き回れる範囲が広い」という形の弱点です。

**表：機密性、完全性の侵害につながる脆弱性の例**

| No. | 脆弱性 | 想定されるリスク | 付け込む攻撃者の行動の例 |
| :---: | --- | --- | --- |
| ① | インターネットに公開するWebサーバと社内専用のファイルサーバなど、アクセスを許可する範囲（人、機器等）が明らかに異なるホストがセグメント分割されておらず、同一セグメントに混在している（**境界のないフラットなネットワーク**） | 公開サーバが不正アクセスを受けた場合、その被害が社内サーバにまで波及する可能性がある | Webアプリケーションの脆弱性でWebサーバを乗っ取り、そこから社内ファイルサーバに直接接続する |
| ② | 社内LANと関連会社のLANが専用線で直接接続されており、アクセス制限が施されていない | 接続先のネットワークから不正アクセスを受ける可能性がある | セキュリティ対策の甘い関連会社に先に侵入し、専用線を通って本社に入り込む（サプライチェーン攻撃） |
| ③ | 社内LANの各セグメント間でアクセス制限を行っていないネットワーク | 内部犯行を誘発するほか、LAN内の1台がマルウェアに感染すると、一気に社内中に感染が広がる可能性がある | 標的型攻撃メールで1台のPCに感染させ、ファイル共有（445番ポート）などを使って次々に他のPCやサーバに広げる |
| ④ | インターネットへの接続口や社内へのアクセスポイントが必要以上に数多く存在するネットワーク | 接続口が多ければ多いほど、不正アクセスを受けるリスクは高まり、セキュリティ対策にも多くの手間とコストを要する | 部署が独自に契約した回線や、管理者が把握していないVPN装置など、監視の手薄な接続口を探して侵入する |
| ⑤ | 十分なセキュリティ対策の施されていない無線LANアクセスポイントが存在するネットワーク | 無線LANは有線LANに比べてアクセス範囲の制限や秘匿化が困難であるため、十分なセキュリティ対策が施されていないと不正接続や情報漏えいにつながる可能性がある | 建物の外や駐車場から電波を拾い、暗号化の弱いアクセスポイントに接続する、通信を傍受する |
| ⑥ | **リピータハブ**が多用されているネットワーク | 通信データが同一セグメント上の全ポートに一斉に送出されるため、盗聴による情報漏えいの可能性がある | 同じハブにつながったPCでパケットキャプチャを動かし、他人の平文の通信（パスワードなど）を読み取る |

①の「フラットなネットワーク」がどれほど危険かを図で確認しましょう。

**図：脆弱なネットワーク構成の例（セグメント分割がされていないフラットなネットワーク）**

```
                    インターネット
                         │
                  ┌──────┴──────┐
                  │ ファイアウォール │  ← 外からは Webサーバの 443番だけ許可しているつもり
                  └──────┬──────┘
                         │ 192.168.1.0/24（1つのセグメントにすべてが混在）
   ──────┬──────────┬────┴─────┬──────────┬──────────
         │          │          │          │
   ┌─────┴────┐┌────┴─────┐┌───┴──────┐┌──┴───────┐
   │公開Webサーバ││社内ファイル ││ 業務用PC  ││顧客DB    │
   │（侵害される）││ サーバ    ││          ││サーバ    │
   └──────────┘└──────────┘└──────────┘└──────────┘
         └──────── 攻撃者は乗っ取った Webサーバから、同じセグメントの全ホストに直接アクセスできる
```

公開Webサーバ、社内ファイルサーバ、業務用PCなどが、ファイアウォールの内側の同一セグメントにすべて混在しています。ファイアウォールは「インターネットと内側の境界」しか見ていないので、同じセグメントの中でのWebサーバから顧客DBサーバへの通信は、ファイアウォールを通らず、検査も制限もされません。この構成では、公開サーバが侵害されると社内のすべてのホストに直接アクセスされてしまいます。

### 1.2 可用性の低下につながる脆弱性

可用性の低下につながる脆弱性の例として、次の表のようなものがあります。こちらは「攻撃者が入り込む」のではなく、「ネットワークが詰まる・止まる」形の弱点です。攻撃（DoS攻撃）だけでなく、アクセスの集中や機器の故障といった攻撃ではない原因でも顕在化する点が特徴です。

**表：可用性の低下につながる脆弱性の例**

| No. | 脆弱性 | 想定されるリスク | 顕在化するきっかけの例 |
| :---: | --- | --- | --- |
| ① | 十分な帯域が確保されていないネットワークや十分な処理能力を有していないネットワーク機器（ルータ、スイッチ、ファイアウォールなど）を使用しているネットワーク | DoS攻撃、接続機器の増加、アクセスの集中などによって**輻輳**状態となり、可用性が低下する | DDoS攻撃（2.7）、テレワーク移行でVPN装置に接続が集中する |
| ② | 重要なネットワーク、ネットワーク機器、サーバなどが二重化、冗長化されていないネットワーク | 回線障害、ネットワーク機器の障害などが**単一障害点**（**SPOF**）となり、サービス全体が停止する | 1台しかないコアスイッチの電源故障、1本しかない回線の工事による切断 |
| ③ | インターネット接続口において帯域制限が行われていないネットワーク | 外部からの大量トラフィックによって内部ネットワークの帯域が占有され、業務通信が阻害される | 外部からのフラッド攻撃 |
| ④ | 特定のプロトコル（動画配信、ファイル共有ソフトなど）の通信量に制限を設けていないネットワーク | 特定の通信が帯域を占有し、重要な業務通信に必要な帯域が確保できなくなる | 社員が業務時間中に大容量の動画を視聴する、OSの大規模な更新が一斉に配信される |
| ⑤ | **ブロードキャストドメイン**が適切に分割されておらず、多数のホストが単一のブロードキャストドメインに属しているネットワーク | ブロードキャストフレームが大量に発生して帯域やホストの処理能力を浪費し、**ブロードキャストストーム**などによって可用性が低下する | 数千台のPCが1つのセグメントに属している、配線のループが発生する |

表中の⑤に関連して、ブロードキャストフレームを発信する通信の例を次の表に示します。

**表：ブロードキャストフレームを発信する通信の例**

| プロトコル | 正式名称 | 概要 | ブロードキャストを使う理由 |
| --- | --- | --- | --- |
| **ARP** | Address Resolution Protocol | IPアドレスからMACアドレスを取得するためのプロトコル | 相手のMACアドレスがわからないので、全員に「このIPアドレスの人は誰？」と尋ねる |
| **DHCP** | Dynamic Host Configuration Protocol | IPアドレスなど必要な情報を自動的に割り当てるためのプロトコル | 自分のIPアドレスもDHCPサーバの場所もわからないので、全員に向けて要求を出す |
| **NetBEUI** | NetBIOS Extended User Interface | Windows環境でファイル共有などを行うためのプロトコル | 名前の登録や検索をブロードキャストで行う（古いWindows環境のプロトコルで、現在はほとんど使われない） |
| **RARP** | Reverse Address Resolution Protocol | MACアドレスからIPアドレスを取得するためのプロトコル | 自分のIPアドレスがわからないので全員に尋ねる（現在はDHCPに置き換えられている） |
| **RIP** | Routing Information Protocol | ルータなどが経路情報を相互に交換するためのプロトコル | 隣接するルータ全員に経路表を定期的に送る（RIPバージョン1。バージョン2ではマルチキャストを使う） |

> **フレーム**
> OSI参照モデルのデータリンク層（第2層）における通信データの単位。
>
> **ブロードキャストフレーム**
> 同一ネットワーク上のすべてのホストを宛先とするフレーム（宛先MACアドレスは FF:FF:FF:FF:FF:FF）。一般的なネットワークでは、ARPやDHCPなどによってブロードキャストが常時発生しており、ブロードキャストドメインが大きいと、限られた帯域やホストの処理能力を浪費する原因となる。

ブロードキャストがどれほど日常的に流れているかは、パケットキャプチャを取ると実感できます。次は、あるPCで tcpdump を実行したときの出力のイメージです。

```
$ sudo tcpdump -n -i eth0 broadcast
10:15:01.120 ARP, Request who-has 192.0.2.1 tell 192.0.2.57, length 28
10:15:01.348 ARP, Request who-has 192.0.2.23 tell 192.0.2.104, length 28
10:15:02.004 IP 0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from 00:00:5e:00:53:2a, length 300
10:15:02.310 ARP, Request who-has 192.0.2.80 tell 192.0.2.12, length 28
   ……（同じセグメントの全ホスト分、絶え間なく続く）
```

「who-has 192.0.2.1 tell 192.0.2.57」は、「192.0.2.1 を持っている人は、192.0.2.57 に教えてください」というARP要求です。1行1行は小さなフレームですが、セグメントに数千台がいれば、全ホストがこれを受け取って処理しなければなりません。しかもこれは、同じセグメントにいる攻撃者が、どのIPアドレスの機器が存在するかを労せずに知る手がかりにもなります（1.4 で見たARPスプーフィングの下準備）。

**ブロードキャストストーム**は、ブロードキャストフレームがネットワーク内を際限なく回り続け、帯域とスイッチの処理能力を使い果たしてしまう現象です。典型的な原因は、スイッチ間の配線がループ（輪）になってしまうことです。ブロードキャストは全ポートに転送されるため、ループがあると同じフレームが延々と増殖し、数秒でネットワーク全体が通信不能になります。スイッチには、ループを検出して一部のポートを論理的に止める**スパニングツリープロトコル**（STP）や、ループ検知機能が備わっており、ネットワーク管理者はこれらを有効にしておくべきです。

## 2. 機密性・完全性の侵害につながる脆弱性への対策

ネットワーク構成における脆弱性への対策は、次のとおりです。まずは機密性・完全性の側から見ていきます。本ノート1.1 の表の①〜⑥にそれぞれ対応しています。

| 1.1 の脆弱性 | 対策 |
|---|---|
| ①フラットなネットワーク、②アクセス制限のない外部接続、③セグメント間のアクセス制限なし | 2.1 セキュリティレベルに応じた適切なセグメント分割及びアクセス制御 |
| ④多すぎる接続口 | 2.2 インターネット接続口の集約化 |
| ⑤無防備な無線LAN | 2.3 無線LANのセキュリティ対策 |
| ⑥リピータハブ | 2.4 スイッチの使用、2.5 ハブ本体の物理的保護及び空きポートのロック |

### 2.1 セキュリティレベルに応じた適切なセグメント分割及びアクセス制御

ネットワークの設計者は、1台が侵害されても被害が組織全体に広がらないようにするために、ネットワークを**求められるセキュリティレベルに応じて**分割し、その間の通信を必要最小限に制限すべきです。具体的には次のとおりです。

- インターネット、公開サーバ設置セグメント、社内共通LANセグメント、機密情報を取り扱う**セキュアLANセグメント**など、求められるセキュリティレベルに応じて**セグメントを分割**し、各セグメント間のアクセスをファイアウォールやスイッチ（1.4 の8節参照）、ルータを用いて制御する。
- 公開サーバについては **DMZ**（De-Militarized Zone：非武装領域）に設置することで、インターネットからのアクセスを制限しつつ、**DMZから内部セグメントへのアクセスについても制限する**ことで、マルウェア感染や不正侵入などの不測事態発生時の被害を最小限にする。
- 関連会社など外部組織のネットワークと接続する場合も、ファイアウォールを介して必要な通信のみを許可する。

DMZの考え方で最も大事なのは、2つ目の「DMZから内部へのアクセスも制限する」という点です。DMZに置く公開サーバは、インターネットから直接アクセスされる以上、いつか侵害される可能性があるものとして扱います。そのサーバが乗っ取られても、そこから社内に入れなければ被害はDMZの中にとどまります。

**図：セキュリティレベルに応じたセグメント分割の例**

```
                         インターネット
                              │
                     ┌────────┴────────┐
                     │  ファイアウォール  │
                     └──┬──────────┬───┘
                        │          │
      DMZ（203.0.113.0/24）│          │
   ┌──────────┬─────────┘          │
   │          │                    │
 ┌─┴──────┐ ┌─┴───────┐            │
 │公開Web   │ │メール中継  │            │
 │サーバ    │ │サーバ     │            │
 │.10      │ │.25       │            │
 └─────────┘ └─────────┘            │
                          ┌─────────┴─────────┐
                          │ 内部FW／レイヤ3スイッチ │
                          └───┬───────────┬───┘
                              │           │
          社内共通LANセグメント  │           │  セキュアLANセグメント
          （10.1.0.0/16）       │           │  （10.9.0.0/24）
          ┌──────────┬────────┘           └────────┬──────────┐
       ┌──┴───┐  ┌───┴────┐                    ┌───┴────┐ ┌───┴────┐
       │業務用PC│  │社内メール│                    │顧客DB   │ │人事システム│
       │       │  │サーバ    │                    │サーバ    │ │         │
       └──────┘  └────────┘                    └────────┘ └────────┘
```

インターネットとの境界にファイアウォールを設置し、公開Webサーバ・メールサーバなどをDMZに配置します。内部は、社内共通LANセグメントと、機密情報を扱うセキュアLANセグメントに分割し、それぞれの間の通信をファイアウォールやレイヤ3スイッチで制御します。

この構成で、ファイアウォールのルールは次のような考え方で設定します（第5章 5.5 で詳しく学びます）。

**表：セグメント間のアクセス制御ルールの例**

| No. | 送信元 | 宛先 | サービス | 動作 | 目的 |
|---|---|---|---|---|---|
| 1 | インターネット | 公開Webサーバ（203.0.113.10） | TCP/443（HTTPS） | 許可 | Webサイトを公開する |
| 2 | インターネット | メール中継サーバ（203.0.113.25） | TCP/25（SMTP） | 許可 | 外部からのメールを受け取る |
| 3 | メール中継サーバ | 社内メールサーバ | TCP/25（SMTP） | 許可 | 受け取ったメールを社内へ渡す |
| 4 | 社内共通LAN | インターネット | TCP/80、443（プロキシ経由） | 許可 | 業務でのWeb閲覧 |
| 5 | 社内共通LAN（人事部のPCのみ） | 人事システム | TCP/443 | 許可 | 権限のある部署だけが機密情報にアクセスする |
| 6 | DMZ | 社内共通LAN、セキュアLAN | すべて | **拒否** | DMZのサーバが侵害されても内部に入らせない |
| 7 | すべて | すべて | すべて | **拒否** | 明示的に許可したもの以外はすべて遮断する |

このようにルールを設定しておくと、公開Webサーバが侵害されて攻撃者が内部を探ろうとしても、ルール6で遮断され、その記録がファイアウォールのログに残ります。

```
2026-09-30T02:14:07+09:00 fw01 action=DENY rule=6 proto=TCP src=203.0.113.10:49822 dst=10.1.20.15:445
2026-09-30T02:14:07+09:00 fw01 action=DENY rule=6 proto=TCP src=203.0.113.10:49823 dst=10.1.20.16:445
2026-09-30T02:14:08+09:00 fw01 action=DENY rule=6 proto=TCP src=203.0.113.10:49824 dst=10.1.20.17:445
```

本来Webページを返すだけのWebサーバ（203.0.113.10）が、深夜に社内の複数のPCのファイル共有ポート（445番）へ次々に接続しようとしています。これは侵害されたWebサーバからの横展開の試みと考えられます。セグメント分割は、被害を止めるだけでなく、**異常に気づくための監視点**も作ってくれるのです（ノート1.2 の検知・追跡機能）。

### 2.2 インターネット接続口の集約化

ネットワーク管理者は、監視と防御を一か所に集中させるために、インターネットへの接続口や社内への接続口を**可能な限り集約し、そこを徹底的に守る**ようにすべきです。接続口が10か所あれば、ファイアウォールの設定、ログの監視、機器のパッチ適用もすべて10か所分必要になり、どこか1か所の抜けが侵入口になります。接続口を1か所にまとめれば、限られた予算と人手をそこに集中できます。

部署ごとに勝手に契約した回線、検証用に一時的に設置したまま放置されたVPN装置やリモートアクセス用の機器は、管理者が把握していない「隠れた接続口」になりがちです。管理者は、定期的に外部からスキャンして、自組織のアドレス範囲で想定外のサービスが公開されていないかを確認しておくべきです。

### 2.3 無線LANのセキュリティ対策

無線LANの電波は壁を越えて建物の外にも届くため、有線LANのように「物理的に接続させない」という対策がとれません。そこでネットワーク管理者は、第三者による不正接続と通信の傍受を防ぐために、次の対策を実施すべきです。

- **WPA2／WPA3** などの強固な暗号化方式を使用する。以前使われていた WEP や、初代の WPA（TKIP）には既知の脆弱性があり、短時間で解読されるため使用してはならない。
- **IEEE 802.1X** による利用者認証を導入し、無線LANアクセスポイントへの不正接続を防止する。全員で1つのパスフレーズを共有する方式（PSK）では、退職者や来訪者にパスフレーズが漏れると誰でも接続できてしまうが、802.1X では利用者ごとに認証するため、個別に無効化できる（第6章）。
- 無許可のアクセスポイント（**不正アクセスポイント**）が設置されていないかを定期的に検査する。社員が持ち込んだ家庭用のアクセスポイントを社内LANにつなぐと、ファイアウォールを迂回する接続口になってしまうためである。

なお、SSIDを隠す（ステルス化する）設定や、MACアドレスによる接続制限は、通信を傍受すればSSIDや許可されたMACアドレスを知ることができ、MACアドレスは偽装もできるため、それだけでは十分な対策になりません。暗号化と認証を基本とし、これらは補助的な対策と位置づけます。

### 2.4 スイッチ（スイッチングハブ、レイヤ2スイッチ）の使用

リピータハブを**スイッチにリプレイス**することで、LAN上での通信データ盗聴の危険性を低減できます。1.4 の8節で学んだとおり、スイッチはMACアドレステーブルを使って、宛先のホストがつながるポートにだけフレームを転送するからです。

ただし、スイッチを用いても**ブロードキャストフレームは接続された他のすべてのホストに届く**ため、ブロードキャストで流れる情報（ARPによるアドレス情報など）については盗聴の危険性に変わりはありません。以前は「スイッチを用いても盗聴の危険性に変わりはない」とまで説明されることがありましたが、正確には、宛先を特定したユニキャストの通信はスイッチで盗聴しにくくなり、ブロードキャストの通信は引き続き全ホストに届く、という区別になります。ブロードキャストフレームの転送先を限定するには **VLAN** を構築する必要があります。

また、スイッチであっても、MACフラッディングやARPスプーフィングを受けると盗聴が可能になります（1.4 の8.1）。ネットワーク管理者は、ポートセキュリティやダイナミックARPインスペクションなどのスイッチの機能を有効にしておくべきです。

### 2.5 ハブ本体の物理的保護及び空きポートのロック

どれほど論理的な対策をしても、攻撃者がハブやスイッチの空きポートにPCをつなげれば、LANの内側に入り込めます。そこで、ネットワーク管理者は、物理的な不正接続を防ぐために次の対策を実施すべきです。

- ハブ本体を床下に配置する、施錠できるラックに収容するなどして、不正接続を防止する。
- ハブの**空きポートを物理的に塞ぐ**（ポートロックと呼ばれる器具で差込口を塞ぐ）ことで、不正な接続を防止する。あわせて、スイッチの設定で未使用ポートを無効化しておくとよい。

物理的な対策には限界があるため、実務では、1.4 で学んだ IEEE 802.1X によるポート単位の認証や、ネットワークに接続した機器を検査して未許可の機器を隔離する仕組み（検疫ネットワーク、第6章）を組み合わせます。

## 3. 可用性の低下につながる脆弱性への対策

次は可用性の側です。本ノート1.2 の表の①〜⑤に対応する対策を、「誰が・何を・何のために・どうするか」の形で整理します。

| No. | 対策 | 誰が・何のために・どうするか |
|---|---|---|
| 1 | ネットワークの帯域を十分に確保するとともに、十分な処理能力をもつネットワーク機器を使用する | ネットワークの設計者は、アクセスの集中や接続機器の増加で輻輳を起こさないように、将来の増加も見込んだ回線帯域と、処理性能に余裕のあるルータ・スイッチ・ファイアウォールを選定する |
| 2 | 重要なネットワーク、ネットワーク機器、サーバなどを**二重化、冗長化**するとともに、**ロードバランサ**を用いて負荷分散を行う | 設計者は、1台の故障や1本の回線断でサービス全体が止まる単一障害点をなくすために、機器や回線を二重化し、ロードバランサで複数のサーバに処理を振り分ける |
| 3 | インターネット接続口においてルータやスイッチによる**帯域制限**を行う | ネットワーク管理者は、外部からの大量トラフィックで内部の帯域が占有されないように、接続口で流入する通信量に上限を設ける |
| 4 | プロトコルによって割り当てる帯域の最大値を設定する | ネットワーク管理者は、動画配信などの特定の通信が業務通信を圧迫しないように、プロトコルやアプリケーションごとに使える帯域の上限を設定する（QoS制御、帯域制御） |
| 5 | スイッチ（レイヤ2スイッチ、レイヤ3スイッチなど）を用いて **VLAN** を構築し、ブロードキャストドメイン（ブロードキャストフレームが届く範囲）を効率的に分割する | 設計者は、ブロードキャストによる帯域と処理能力の浪費を防ぐために、部署や用途ごとにVLANを分け、1つのブロードキャストドメインに属するホスト数を抑える |

> **VLAN（Virtual LAN）**
> 物理的な接続形態とは独立して、論理的にネットワークを分割する技術。VLANに対応したスイッチングハブを用いることで、同じスイッチに接続されたホストであっても異なるブロードキャストドメインに分けることができる。**ポートベースVLAN** や **タグVLAN**（**IEEE 802.1Q**）などの方式がある。
>
> **ロードバランサ（load balancer）**
> 複数のサーバに処理要求を振り分け、負荷を分散させる装置。特定のサーバへの負荷集中を防ぐとともに、一部のサーバに障害が発生した場合でもサービスを継続できるため、可用性の向上に寄与する。

5のVLANは、可用性だけでなく機密性にも効く対策です。ブロードキャストの届く範囲が狭まれば、2.4 で見た「ブロードキャストで流れる情報の盗聴」の範囲も狭まり、セグメント間の通信をファイアウォールで制御すれば 2.1 のアクセス制御にもなります。このように1つの構成上の対策が複数の特性を守ることはよくあるので、科目Bで対策を答えるときは「どの特性を、なぜ守れるのか」を添えるようにしましょう。

冗長化については、「二重化したつもりで実は単一障害点が残っている」という落とし穴に注意が必要です。サーバを2台にしても、両方が同じスイッチにつながっていればそのスイッチが単一障害点になり、回線を2本契約しても同じ電柱・同じ管路を通っていれば1回の工事事故で両方が切れます。設計者は、構成図を1つずつたどって「ここが壊れたら何が止まるか」を確認すべきです。

## 4. 確認問題

### 4.1 理解度チェック

- **Q1**：ネットワーク構成における脆弱性を、損なわれる特性の観点から2つに分類し、それぞれの例を挙げよ。
- **Q2**：公開サーバをDMZに設置する際、DMZから内部セグメントへのアクセスも制限すべき理由は何か。
- **Q3**：リピータハブをスイッチに置き換えることによる効果と、その限界を述べよ。
- **Q4**：ブロードキャストドメインが大きすぎると、どのような問題が生じるか。対策とともに述べよ。
- **Q5**：単一障害点（SPOF）とは何か。

> **解答の要点**
> - Q1：機密性・完全性の侵害につながるもの（フラットなネットワーク、アクセス制限のない外部接続、セグメント間のアクセス制限なし、多すぎる接続口、対策の不十分な無線LAN、リピータハブ）と、可用性の低下につながるもの（帯域・処理能力の不足、冗長化されていない構成、帯域制限の欠如、プロトコルごとの帯域制限の欠如、大きすぎるブロードキャストドメイン）。
> - Q2：公開サーバはインターネットから直接アクセスされるため侵害される可能性があり、侵害されたサーバを踏み台に内部へ侵入されたり、マルウェアが広がったりするのを防ぐため。
> - Q3：宛先のポートにだけフレームを転送するため、ユニキャスト通信の盗聴の危険性を低減できる。ただしブロードキャストフレームは全ホストに届くため、ブロードキャストで流れる情報は盗聴され得る。転送範囲を限定するにはVLANが必要。
> - Q4：ARPやDHCPなどのブロードキャストが大量に発生して帯域やホストの処理能力を浪費し、ブロードキャストストームなどによって可用性が低下する。VLANでブロードキャストドメインを分割する。
> - Q5：その1か所が故障するとシステムやサービス全体が停止してしまう箇所。二重化・冗長化によって解消する。

### 4.2 過去問題：DHCPクライアントによるアドレスの重複確認

DHCPのクライアントが、サーバから配布されたIPv4アドレスを、クライアント自身のアドレスとして設定する際に、そのアドレスが他のホストに使用されていないことを、クライアント自身でも確認することが推奨されている。この確認に使用するプロトコルとして、適切なものはどれか。

ア　ARP
イ　DNS
ウ　ICMP
エ　RARP

*［情報処理安全確保支援士試験・R5秋・午前Ⅱ］*

> **解答・解説**
> DHCPサーバから割り当てられたIPアドレスが他のホストで使用されていないかをクライアント自身で確認する際には、ARP（Address Resolution Protocol）が用いられる。ARPはIPアドレスからMACアドレスを得るために使われるプロトコルであり、DHCPクライアントは、サーバから割り当てられたIPアドレスを対象としてARPリクエストをブロードキャストし、応答の有無を確認する。その結果、どのホストからも応答がなければ、他のホストがそのIPアドレスを使用していないことが確認できる。したがって**ア**が正解。
>
> **補足**
> このような確認のために送信されるARPは、**GARP**（**Gratuitous ARP**）や **ARP Probe** と呼ばれることがある。厳密には、ARP Probe はまだ自分のアドレスとして使っていない段階で送信元IPアドレスを 0.0.0.0 にして「このアドレスを使っている人はいますか」と尋ねるもの、Gratuitous ARP は自分のIPアドレスを宛先にしたARPを送って周囲に自分のアドレスを知らせたり重複を検出したりするもので、どちらもアドレスの重複確認に関係する。なお、DNSは名前解決、ICMPは通信の制御・エラー通知、RARPはMACアドレスからIPアドレスを取得するためのプロトコルであり、いずれもアドレスの重複確認には用いられない。

```
DHCPでアドレスを受け取ったクライアントが送るARP Probe のイメージ（tcpdump の出力）
10:20:11.001 ARP, Request who-has 192.0.2.77 tell 0.0.0.0, length 28
   → 誰からも応答がなければ、192.0.2.77 を自分のアドレスとして使い始める
```

## 5. 試験対策まとめ（重要ポイント）

### 5.1 知識の確認（科目A-2向け）

- **ネットワーク構成の脆弱性の2分類**：機密性・完全性の侵害につながるもの（入り込む口が多い・動き回れる範囲が広い）と、可用性の低下につながるもの（詰まる・止まる）。
- **フラットなネットワーク**：アクセスを許可する範囲が異なるホストが同一セグメントに混在。公開サーバの侵害が社内に波及する。
- **DMZ**：公開サーバを置く非武装領域。インターネット→DMZ を制限するだけでなく、**DMZ→内部**も制限するのがポイント。
- **接続口の集約**：接続口が多いほど不正アクセスのリスクと対策コストが増える。集約して徹底的に守る。
- **無線LAN**：WPA2/WPA3、IEEE 802.1X による利用者認証、不正アクセスポイントの検査。WEP・WPA（TKIP）は使わない。SSIDの隠蔽やMACアドレス制限だけでは不十分。
- **リピータハブ と スイッチ**：全ポートに送出するか、宛先ポートにだけ送るか。スイッチでもブロードキャストは全ホストに届く。転送範囲を限定するにはVLAN。
- **物理的対策**：ハブ本体の床下配置、空きポートのロック。
- **可用性の対策**：十分な帯域と処理能力、二重化・冗長化とロードバランサ、接続口での帯域制限、プロトコルごとの帯域の上限、VLANによるブロードキャストドメインの分割。
- **ブロードキャストを使うプロトコル**：ARP、DHCP、NetBEUI、RARP、RIP（v1）。
- **DHCPクライアントのアドレス重複確認**：ARP（ARP Probe／Gratuitous ARP）を使う。
- **単一障害点（SPOF）**：そこが壊れると全体が止まる箇所。冗長化で解消する。

### 5.2 記述式で問われる観点（科目B向け）

- **被害拡大の原因の指摘**：「公開サーバと社内サーバが同一セグメントにあり、セグメント間のアクセス制御がなかったため、公開サーバの侵害が社内に波及した」のように、構成の弱点を被害の経路と結びつけて書く。
- **サーバ配置の提案**：「インターネットからアクセスされるサーバはDMZに置き、DMZから内部への通信は必要なもの（メール中継サーバから社内メールサーバへのSMTPなど）に限定する」という形で、配置と許可する通信をセットで答える。
- **ファイアウォールのルールの不備の指摘**：ルール表から「DMZから内部への通信がすべて許可されている」「関連会社の接続にアクセス制限がない」などの過剰な許可を見つけ、どのルールをどう変えるべきかを述べる。
- **ログからの横展開の発見**：公開サーバから内部への多数の接続試行（445番ポートなど）が拒否ログとして残っていれば、そのサーバの侵害を疑い、切り離しと調査を提案する。
- **無線LANの対策の理由付け**：「PSKでは退職者などにパスフレーズが漏れると不正接続を防げないため、IEEE 802.1X による利用者ごとの認証を導入する」のように、方式の選択理由を書く。
- **可用性の設計**：単一障害点を指摘し、二重化の際には経路や電源まで独立させること、帯域制限やVLAN分割で業務通信を守ることを提案する。
