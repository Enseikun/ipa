## 0. 全体像 ― なぜこの分野を学ぶのか

2.1 で描いたサイバーキルチェーンの7段階を思い出してください。攻撃はいきなり「侵入」から始まるのではなく、まず**偵察**から始まります。攻撃者は、標的のネットワークに「どんな入り口（サービス）が開いているか」を調べ、そこに攻撃可能な弱点がないかを探ります。この偵察の代表的な手法が、本ノートで学ぶ**ポートスキャン**です。

**ポートスキャン**とは、ターゲットとなるホスト上で開いている（通信可能な状態になっている）ポートをスキャン（探査）することです。家に例えると、泥棒が押し入る前に、どの窓や扉に鍵がかかっていないかを一つずつ確認して回る行為に当たります。攻撃者は、開いているポートとそこで動くサービスが分かれば、次にそのサービスの既知の脆弱性を突く攻撃（2.3 のバッファオーバフロー攻撃など）へ進めます。つまりポートスキャンは、後続の本格的な攻撃の「下調べ」なのです。

ポートスキャンを理解するには、1.4 で学んだTCP/IPの知識が前提になります。とくに次の2つが土台です。

1. **ポート番号**：TCP/UDPは0〜65535のポート番号でアプリケーション（サービス）を識別します。ポートが「開いている」とは、そのポートでサービスが待ち受けている状態を指します（1.4 の主なポート番号の表）。
2. **3ウェイハンドシェイクとTCPフラグ**：TCPは①SYN→②SYN/ACK→③ACKの3往復で接続を確立します。ポートスキャンは、この手順の途中の応答（SYN/ACKかRST/ACKか、無応答か）を見てポートの状態を判定します（1.4 の3ウェイハンドシェイク）。

本ノートでは、次の順序で学びます。まず 1 でポートスキャンの目的と実行方法を、2 でその仕組み（TCPコネクトスキャン、SYNスキャン、UDPスキャン、各種ステルススキャン）を、3 で対策を、1.2 の対策の4機能（予防・防止／検知・追跡／回復）に沿って整理します。

科目Bの4つの業務観点との関係では、本ノートは「③利用におけるセキュリティ対策の適用」のうち「ネットワーク及び機器のセキュリティ管理」「セキュリティ監視並びにログの取得及び分析」に直結します。事例問題では、ファイアウォールやIDSのログからポートスキャンの痕跡を読み取り、「これは何を狙った偵察か」「検知されにくい手法か」を答えさせる形で問われます。科目A-2では、TCPコネクトスキャンとSYNスキャンの違い（ログに残るか）、UDPスキャンの判定方法、ステルススキャンの種類が繰り返し出題されています。

## 1. ポートスキャンの目的と実行

### 1.1 前段としてのアドレススキャン（pingスイープ）

攻撃者は、ポートを調べる前に「そもそもどのIPアドレスにホストが存在するか」を確かめることがあります。これが 2.1 の攻撃手法一覧にもあった**アドレススキャン（pingスイープ）**で、攻撃者はアドレスの範囲に対して ICMP Echo Request（ping）などを順に送り、応答（Echo Reply）が返ってきたアドレスを「生きているホスト」として記録します（ICMPは 1.4 で扱いました）。結果は、たとえば次のように見えます（例示）。

```
$ nmap -sn 192.0.2.0/28
Nmap scan report for 192.0.2.1     Host is up (0.0010s latency).
Nmap scan report for 192.0.2.10    Host is up (0.0021s latency).
Nmap scan report for 192.0.2.11    Host is up (0.0019s latency).
Nmap done: 16 IP addresses (3 hosts up)
```

攻撃者は、こうして見つけた3台に対して、次のポートスキャンを集中させます。ネットワーク管理者が外部からのICMP Echo Requestをファイアウォールで遮断しておくと、この段階の情報収集を難しくできます（ただしTCPを使った生存確認もあるため、完全には防げません）。

### 1.2 ポートスキャンの仕組みの基本

ポートスキャンでは、攻撃者はターゲットホストの各ポートに対してパケットを送信し、その**応答**から、ポートが**アクティブ状態**（サービスが稼働し、通信を受け付けている状態）か、**非アクティブ状態**かを判断します。「反応の返り方の違い」で開いているかどうかを見分ける、というのが共通の原理です。

TCPコネクションを確立するタイプのポートスキャンでは、攻撃者は単にポートの状態を確認するだけでなく、ターゲットホストが返す**バナー情報**から、そのポートに対応したサービスを提供しているアプリケーションの種類やバージョンなども確認できます。また、稼働しているアプリケーションの種類や、ターゲットホストの振る舞い（アクセス要求に対する応答の仕方など）から、OSの種類やバージョンまで推定することも可能です。このような手法を**スタックフィンガープリンティング**とも呼びます。OSやアプリごとにTCP/IPの実装（応答の細かなクセ）が異なるため、その「指紋（フィンガープリント）」から製品を言い当てるわけです。

バナー情報は、たとえば攻撃者が23番ポート（telnet）や25番ポート（SMTP）に接続したときに、次のような形で返ってきます（例示）。バージョン番号まで分かるため、攻撃者は「このバージョンには既知の脆弱性がある」と調べて次の攻撃につなげます。

```
$ nc 192.0.2.10 25
220 mail.example.jp ESMTP Postfix (2.10.1)     ← アプリ名とバージョンが分かる
```

> **バナー（banner）**
> バナーは旗、横断幕を意味し、Webの分野ではホームページ上の広告画像などを指す。本書では、サーバプログラムが接続時などに返すメッセージ（アプリケーション名やバージョン番号などを含む識別情報）の意味として使用している。

### 1.3 ポートスキャンで見つかるもの

攻撃者はポートスキャンを行うことで、侵入の足がかりになる次のようなサービスを見つけることができます。

**セキュリティ上問題のあるサービス**：もともとイントラネットなどの閉じたネットワークの中で使用することを前提としたプロトコルやサービスは数多くあります。仮にそうしたサービスがインターネットから利用可能であれば、その機能上の脆弱さから侵入や攻撃が容易に行える可能性があるため、侵入者にとっては非常に好都合です。機能上の脆弱さからインターネットに公開すべきではないサービスの例を表に示します。これらは、認証が弱い・通信が平文である・リモートからコマンドを実行できるなどの理由で、外部にさらすべきではないものです。

**表：インターネットに公開すべきではないサービスの例**

| サービス名 | ポート番号 | 概要 |
| --- | --- | --- |
| telnet | 23 | Telnet |
| tftp | 69 | 簡易FTPサービス |
| pop3 | 110 | メール受信 |
| sunrpc | 111 | SUN Remote Procedure Call |
| epmap | 135 | DCE準拠のRPC |
| netbios-ns | 137 | NetBIOS名前サービス |
| netbios-dgm | 138 | NetBIOSデータ通信 |
| netbios-ssn | 139 | NetBIOSセッション通信 |
| snmp | 161 | SNMP（ネットワーク管理） |
| snmptrap | 162 | SNMP（ネットワーク管理：異常報告用） |
| microsoft-ds | 445 | ダイレクトホスティングSMBサービス |
| rexec | 512 | UNIX環境のリモートコマンド実行 |
| rlogin | 513 | UNIX環境のリモートログインサービス |
| rsh | 514 | リモートシェル（TCP） |
| syslog | 514 | シスログ（UDP） |
| ms-sql-s | 1433 | Microsoft SQL Server |
| ms-sql-m | 1434 | Microsoft SQL Monitor |
| nfs | 2049 | Network File System - Sun Microsystems |

> **補足**
> rsh と syslog はいずれもポート番号514を使用するが、rsh はTCP、syslog はUDPであり、トランスポート層のプロトコルが異なるため別のサービスとして扱われる。ファイアウォールのルールを書くときも、ポート番号だけでなくプロトコル（TCP/UDP）まで指定する必要があるのはこのためである。

**既知のセキュリティホールをもつサービス**：一般的に利用されている市販ソフトウェアやフリーウェアなどには、既知の**セキュリティホール（脆弱性）**が数多くあります。通常は開発元が提供しているパッチを適用したり、バージョンアップを行ったりすることによって対策は可能ですが、そうした対処が行われずにインターネット上に公開されているホストも数多くあります。前述のように、攻撃者はターゲットホストからのバナー情報を調べることにより、セキュリティホールをもつサービスが稼働していることを確認できる可能性があります。「古いバージョンを動かしっぱなしにしている」ことが、攻撃者に格好の標的を教えてしまうわけです。

### 1.4 ポートスキャンの実行

ポートスキャンは、**nmap**に代表される専用のツールを用いることで、特別な知識がなくても容易に実行できます。こうしたツールが無償で容易に入手可能であることに加え、ワームやトロイの木馬に組み込まれている場合も多くあります。そのため、インターネット上では無差別的に実行されたポートスキャンのパケットが絶えず飛び交っているのが実情です。公開サーバを立てれば、数分以内に世界中から自動化されたスキャンを受ける、と考えておくべきです。

nmapを実行すると、たとえば次のような結果が表示されます（例示）。どのポートが開いていて（open）、何のサービスがどのバージョンで動いているかが一覧化されます。攻撃者にとっては攻撃計画表、管理者にとっては「意図せず開いているポートがないか」の点検表になります。

```
$ nmap -sV 192.0.2.10
PORT     STATE  SERVICE  VERSION
22/tcp   open   ssh      OpenSSH 8.9
23/tcp   open   telnet   Linux telnetd        ← 平文の telnet が開いている（危険）
80/tcp   open   http     Apache httpd 2.4.52
445/tcp  open   microsoft-ds
3389/tcp closed ms-wbt-server
```

> **nmap（Network Mapper）**
> オープンソースで公開されている代表的なポートスキャンツール。TCPコネクトスキャン、SYNスキャン、UDPスキャン、各種ステルススキャンのほか、OSやサービスのバージョン検出機能も備えている。本来は**ネットワーク管理者によるセキュリティ診断**のためのツールである。攻撃者も管理者も同じツールを使う点が重要で、正規の脆弱性診断（5.3）でもnmapは基本ツールとして使われる。

## 2. ポートスキャンの種類と仕組み

ポートスキャンには、その仕組みによって**TCPコネクトスキャン**、**SYNスキャン（TCPハーフスキャン）**、**UDPスキャン**などの種類があります。違いのポイントは「コネクションを最後まで確立するか」で、それがそのまま「ターゲットのログに残るか（＝検知されやすいか）」を決めます。

### 2.1 TCPコネクトスキャン

TCPコネクトスキャンは、TCPのポート（サービス）を対象とした手法です。攻撃者は、1.4 で学んだ**3ウェイハンドシェイク**を最後まで行い、ターゲットポートとTCPコネクションを**確立できるかどうか**によって状態を確認します。多くのツールが存在することから、最もよく使われている手法です。

ポートが開いている場合には、攻撃者とターゲットはコネクションを確立します。コネクションが確立するということは、ターゲット上のサービス（アプリケーション）がその接続を受け付けたということなので、**ターゲットサーバのログに記録されます**。したがって、サーバの管理者は、サーバのログを分析することによって、ポートスキャンを受けたことを確認できる可能性があります。

**図：TCPコネクトスキャンのイメージ**

```
攻撃者                              ターゲット
  |  ---- SYN（接続要求） -------->  |
  |  <--- SYN/ACK（アクティブ状態）- |   ※非アクティブ状態の場合は RST/ACK
  |  ---- ACK -------------------->  |   → コネクション確立（ログに記録される）
```

### 2.2 SYNスキャン（TCPハーフスキャン）

SYNスキャンも、TCPのポートを対象とした手法です。攻撃者は、3ウェイハンドシェイクの**最初のSYNパケットだけ**を送信し、ターゲットからSYN/ACKが返ってきた場合は**アクティブ状態**、RST/ACKが返ってきた場合は**非アクティブ状態**と判断します。ここが巧妙な点で、アクティブ状態であった場合でも、攻撃者はACKを返信せず、代わりに**RST**を返信してコネクションを打ち切ります。そのため、コネクションは確立されません。

コネクションが確立されないということは、ターゲット上のサービスは「接続があった」と認識しないため、**ターゲットホストのログには記録されません**。これは、侵入者が自身の行為を発見されにくくするために用いる手法であり、**ステルススキャン**とも呼ばれます。ハンドシェイクを半分（ハーフ）でやめるので「TCPハーフスキャン」の別名があります。

ただし「ログに記録されない」とは、正確には**サービス（アプリケーション）のログに残らない**という意味です。SYNパケット自体はネットワーク上を流れるので、ファイアウォールの通信ログやIDSには記録・検知されますし、OSの設定によってはカーネルが接続試行を記録することもあります。1.4 で「SYNスキャンはアプリケーションのログに残りにくい」と表現したのはこのためです。

TCPコネクトスキャンとの違いは、次の一点に集約されます。攻撃者は「開いているか」の情報だけが欲しいので、SYN/ACKが返ってきた時点で目的は達成しており、わざわざACKを返してログに残る必要がないのです。

| 観点 | TCPコネクトスキャン | SYNスキャン（TCPハーフスキャン） |
|---|---|---|
| ハンドシェイク | 最後（③ACK）まで行い確立する | ②SYN/ACKを受けたら③を送らずRSTで打ち切る |
| コネクション | 確立する | 確立しない |
| ターゲットのアプリログ | 記録される（検知されやすい） | 記録されにくい（ステルス） |
| 必要な権限 | 一般的なOS機能で実行可 | 生パケットを作るため管理者権限が必要なことが多い |

> **試験に出た**
> 情報セキュリティスペシャリスト試験の午後問題において、SYNスキャンに関する問題が出題されている。

**図：SYNスキャンのイメージ**

```
攻撃者                              ターゲット
  |  ---- SYN（接続要求） -------->  |
  |  <--- SYN/ACK（アクティブ状態）- |   ※非アクティブ状態の場合は RST/ACK
  |  ---- RST -------------------->  |   → コネクションは確立されない（ログに残らない）
```

### 2.3 UDPスキャン

UDPでは、通信にあたって**コネクションを確立する手順が省略されています**（1.4 で学んだとおり、UDPはコネクションレス型です）。そのため、TCPに比べてポートスキャンの手段が限られます。SYN/ACKのような「開いています」という明確な返事の仕組みがないからです。

UDPスキャンでは、攻撃者はターゲットポートにデータ（パケット）を送り、その結果、**何の応答もなければアクティブ状態**、「**ICMP port unreachable**」が返ってきた場合は**非アクティブ状態**と判断します。閉じているポートは「そのポートには誰もいません」という意味のICMPエラー（port unreachable）を返すのに対し、開いているポートは（アプリ次第で）黙っていることが多い、という性質を利用しています。また、UDPアプリケーションの仕様によっては特定の応答を返すものもあるため、攻撃者はそれを利用してUDPスキャンの精度を高めることも可能です。

**図：UDPスキャンのイメージ**

```
攻撃者                              ターゲット
  |  ---- データ ------------------>  |
  |  <--- ICMP port unreachable ---- |   → 非アクティブ状態
  |       （応答なし）                |   → アクティブ状態
```

> **補足**
> UDPスキャンでは「応答なし」をアクティブ状態とみなすため、途中のファイアウォールでパケットが破棄された場合やパケットが消失した場合も、アクティブ状態と誤判定されることがある。このため、TCPのスキャンに比べて精度が低くなりやすい。「応答がない理由」が、開いているからなのか、途中で遮断されたからなのか区別できないのが弱点である。

### 2.4 その他のステルススキャン

SYNスキャン以外にも、ターゲットホストのログに記録されにくいステルススキャンとして、次の表のような手法があります。これらはいずれも、TCPの正常なコネクションでは**あり得ないフラグの組合せ**のパケットを送ることにより、ターゲットポートの状態を判別するものです。正常な手順から外れたパケットに対するOSの反応の違いを突く、という発想です。

**表：ステルススキャンの手法**

| 種類 | 内容 |
| --- | --- |
| FINスキャン | FINフラグをONにしたパケットを送り、それに対する反応からポートの状態を判別する |
| ACKスキャン | ACKフラグをONにしたパケットを送り、それに対する反応からポートの状態を判別する |
| Nullスキャン | コードビットのすべてのフラグをOFFにしたパケットを送り、それに対する反応からポートの状態を判別する |
| クリスマスツリースキャン | FIN、PSH、URGのフラグをすべてONにしたパケットを送り、それに対する反応からポートの状態を判別する |

「クリスマスツリー」という名前は、複数のフラグがすべてONになった様子を、電飾が全部点灯したツリーに見立てたものです。

> **補足**
> FINスキャン、Nullスキャン、クリスマスツリースキャンでは、一般に、非アクティブ状態のポートはRSTを返し、アクティブ状態のポートは応答しない（パケットを破棄する）という**RFC 793**の仕様を利用している（TCPの仕様書は2022年に RFC 9293 として改訂・統合され、RFC 793 は廃止扱いになったが、この応答の挙動は引き継がれている）。ただし、OSの実装によってはこの仕様どおりに動作しないものもある（たとえばWindowsは仕様どおりに動かないため、この手法が効きにくい）。**ACKスキャン**は主に、ファイアウォールによってパケットがフィルタリングされているかどうかを調べる目的で用いられる（ポートの開閉ではなく「その通信が通るか」を確かめる用途）。

## 3. ポートスキャンへの対策

ポートスキャンは**調査行為**であり、ポートスキャンのみでシステムへの侵入を許したり、データが破壊されたりすることはありません。したがって、次に挙げる予防・防止対策が行われていれば特に問題はありません。しかし、そうでない場合には、ポートスキャンを受けることによって多くの脆弱性を露呈し、本格的な攻撃を受けることにつながることも十分にあり得ます。「スキャンされること自体」ではなく「スキャンで弱点が見つかること」が問題だ、という切り分けが対策を考えるうえでの要点です。

### 3.1 予防・防止 ― 狙われる入り口と弱点をなくす

サーバの管理者は、攻撃者にスキャンされても攻撃可能な弱点を見つけられないよう、次の予防・防止策を講じるべきです。

- **不要なサービスを停止する（ポートを閉じる）**：管理者は、攻撃者に侵入口を与えないために、業務で使っていないサービス（例：telnet の23番ポート）を停止し、ポートを閉じておくべきです。開いているポートが少なければ、攻撃者が調べられる入り口（1.2 のアタックサーフェス＝攻撃対象領域）そのものが減ります。これは 5.2「ホストの要塞化」の中心的な考え方です。
- **OS及びアプリケーションのバージョンを最新化し、パッチを適用する**：管理者は、既知のセキュリティホールを突かれないために、バナー情報から古いバージョンだと分かっても攻撃が成立しないよう、常に最新の状態に保つべきです。
- **脆弱性検査を実施し、セキュリティホールが塞がれていることを確認する**：管理者（または診断担当者）は、攻撃者に先んじて自らスキャン・診断を行い、塞ぎ漏れがないことを確認すべきです（5.3「脆弱性診断」）。
- **ファイアウォールを用いて、外部からの不要なポートへのアクセスを遮断する**：ネットワーク管理者は、業務に必要なポート以外を外部から到達できないようにし、そもそもスキャンのパケットがサービスに届かないようにすべきです（5.5「ファイアウォール」）。

### 3.2 検知・追跡 ― スキャンされたことに気づく

管理者やSOCは、攻撃者が偵察段階にいることをいち早く察知し、本格的な攻撃に備えるために、次の検知・追跡策を講じるべきです。

- **IDSやIPSを用いて検知する**：ネットワークを流れるパケットを監視し、短時間に多数のポートへアクセスするといったスキャンの特徴を検知します。
- **ファイアウォールのログから検知する**：拒否されたアクセスのログに、同一送信元から多数のポートへの接続試行が並んでいないかを分析します。
- **ホストのログから検知する（TCPコネクトスキャンの場合）**：コネクションが確立するTCPコネクトスキャンは、サーバのアプリケーションログに痕跡が残るため、そこから検知できます。

**IDS**や**IPS**を用いると、SYNスキャンなどのステルススキャンについても検知することが可能です（ホストのログに残らなくても、ネットワーク上のパケットの動きは監視できるからです）。一方、攻撃者が各ポートへのアクセスを連続して行うのではなく、**1ポートごとにある程度の時間を空け、かつポート番号をランダムに選択して**行った場合などは、「短時間に多数のポートへアクセスする」という特徴が現れないため、検知が非常に困難になります（スロースキャン）。

ファイアウォールのログには、ポートスキャンは次のような「同一送信元から、多数の宛先ポートへの拒否」の連続として現れます（例示）。SOCの分析担当者は、この規則性からスキャンだと判断します。

```
2026-09-28 03:12:01 DENY TCP 198.51.100.77:51000 -> 192.0.2.10:21   SYN
2026-09-28 03:12:01 DENY TCP 198.51.100.77:51001 -> 192.0.2.10:22   SYN
2026-09-28 03:12:01 DENY TCP 198.51.100.77:51002 -> 192.0.2.10:23   SYN
2026-09-28 03:12:01 DENY TCP 198.51.100.77:51003 -> 192.0.2.10:25   SYN
2026-09-28 03:12:02 DENY TCP 198.51.100.77:51004 -> 192.0.2.10:80   SYN
   ...（同一送信元から連番ポートで多数の宛先ポートへ）...
```

> **IDS（Intrusion Detection System）**
> 侵入検知システム。ネットワークを流れるパケットや、ホスト上の各種イベント（ログイン、プログラムの実行など）をリアルタイムに監視して、不正なアクセスや異常を検知し、管理者に通知する製品。詳細は 5.6 で扱う。

> **IPS（Intrusion Prevention System）**
> 侵入防止システム。従来のネットワーク型IDSやファイアウォールに、不正アクセスを防御する機能を追加したもの。不正アクセスを検知するだけでなく、遮断まで行う。以前は「IPSはネットワーク型IDSと同様に、導入にあたっては新たにハードウェアを設置する必要がある」とされていたが、現在は仮想アプライアンスやクラウド型のサービスとして提供されるもの、次世代ファイアウォール（NGFW）やUTMの一機能として組み込まれているものも多く、専用ハードウェアの設置は必須ではない。ただし、通信経路上に配置（インライン接続）する必要がある点は変わらない。詳細は 5.7 で扱う。

### 3.3 回復

ポートスキャンは調査行為にとどまるため、回復（復旧）の観点は限定的です。

- 予防・防止対策が万全であれば、ポートスキャンを受けても特に問題はないため、回復処置は不要です。ただし、スキャンを受けたことをきっかけに予防・防止対策を点検し、不十分な箇所があれば対処すべきです（スキャンは「弱点がないか点検せよ」という警告として活用できます）。

## 4. 確認問題

### 4.1 理解度チェック

- **【Q1】** TCP、UDPによるポートスキャン方法の違いは何か。
- **【Q2】** 検知されやすいポートスキャン手法と、検知されにくいポートスキャン手法は何か。また、後者はなぜ検知されにくいか。
- **【Q3】** 検知されにくいポートスキャンへの対処方法にはどのようなものがあるか。

> **解答例**
>
> - **Q1**：TCPでは3ウェイハンドシェイクの応答（SYN/ACKかRST/ACKか）によってポートの状態を判別する。UDPではコネクション確立の手順がないため、データを送信し、応答がなければアクティブ状態、「ICMP port unreachable」が返ればそれを非アクティブ状態と判断する。
> - **Q2**：検知されやすいのはTCPコネクトスキャンである。検知されにくいのはSYNスキャンやFIN/Null/クリスマスツリースキャンなどのステルススキャンであり、TCPコネクションを確立しないため、ターゲットホストのログに記録されないからである。
> - **Q3**：IDSやIPSを導入してネットワーク上のパケットを監視する。また、ファイアウォールのログを分析する。

### 4.2 確認問題（過去問題）

TCPのコネクション確立方式である3ウェイハンドシェイクを表す図はどれか。

*［情報処理安全確保支援士試験・平成30年度］*

> **解答・解説**
> TCPの3ウェイハンドシェイクとは、「3ウェイ」の名が示すように、次の①〜③の3回のパケットのやり取りによってコネクションを確立する方式である。
>
> 1. SYN（要求元が送信）
> 2. SYN/ACK（要求先が送信）
> 3. ACK（要求元が送信）
>
> ```
> 要求元（クライアント）              要求先（サーバ）
>   |  ---- ① SYN ------------------>  |
>   |  <--- ② SYN/ACK --------------- |
>   |  ---- ③ ACK ------------------>  |
>   |      コネクション確立             |
> ```
>
> したがって、要求元からSYN、要求先からSYN/ACK、要求元からACKの順にパケットが送信されている図が正解となる。
>
> **補足**：①のSYNでは要求元が自身の初期シーケンス番号を通知し、②のSYN/ACKでは要求先がこれに対する確認応答（ACK）と自身の初期シーケンス番号（SYN）を同時に通知する。③のACKで要求元が要求先のシーケンス番号に対する確認応答を返すことで、双方向の通信路が確立される。この「初期シーケンス番号の伝え合い」を途中で打ち切るのがSYNスキャン、番号を予測して割り込むのがTCPセッションハイジャック（2.5）である。同じハンドシェイクが、正常な接続にも複数の攻撃にも関わっていることを押さえておきたい。

## 5. 試験対策まとめ（重要ポイント）

### 5.1 知識の確認（科目A-2向け）

- **ポートスキャンの位置づけ**：キルチェーンの「偵察」段階の手法。開いているポートと稼働サービス（種類・バージョン）を調べ、本格的な攻撃の下調べをする。
- **アドレススキャン（pingスイープ） と ポートスキャン**：前者はICMP Echo Request等で「どのアドレスにホストがいるか」を調べ、後者はそのホストの「どのポートが開いているか」を調べる。
- **バナー情報 と スタックフィンガープリンティング**：バナーはサービスが返す識別情報（アプリ名・バージョン）。スタックフィンガープリンティングはTCP/IP実装のクセからOSやサービスを推定する手法。
- **TCPコネクトスキャン と SYNスキャン**：前者は3ウェイハンドシェイクを完了させ確立するのでログに残る。後者は②SYN/ACKの後にRSTで打ち切り確立しないのでログに残らない（ステルススキャン＝TCPハーフスキャン）。
- **UDPスキャン**：応答なし＝アクティブ、ICMP port unreachable＝非アクティブ。途中のFWでの破棄と区別できず精度が低い。
- **ステルススキャンの種類**：FIN／ACK／Null／クリスマスツリー（FIN・PSH・URGをON）。RFC 793の「閉ポートはRST、開ポートは無応答」を利用。ACKスキャンはFWのフィルタリング状況の調査に使う。
- **検知の難所**：ステルススキャンもIDS/IPSでネットワーク監視すれば検知可能。ただしポートをランダムに選び間隔を空けるスロースキャンは検知が困難。
- **予防・防止**：不要サービスの停止（ポートを閉じる）、パッチ適用、脆弱性検査、FWでの不要ポート遮断。

### 5.2 記述式で問われる観点（科目B向け）

- **ログからスキャンを読み取る**：同一送信元IPから多数の宛先ポートへの接続試行（多くは拒否）が短時間に並んでいれば、ポートスキャン（偵察）と判断できる、と根拠を添えて説明する。
- **検知されにくい理由を書く**：「SYNスキャンはコネクションを確立せずRSTで打ち切るため、サーバのアプリケーションログに記録されず、ホストのログだけでは検知できない。ネットワーク上のパケットを監視するIDS/IPSで検知する必要がある」のように、なぜ・何でを結びつけて書く。
- **対策を目的とセットで書く**：「攻撃者に侵入口を与えないため、業務で使わないサービス（telnet の23番など）を停止してポートを閉じる」「古いバージョンを突かれないためパッチを適用する」のように、対策と狙いを1文で結びつける。
- **スキャンを警告として活かす**：スキャンを受けたこと自体を、予防・防止対策（開いているポート・古いサービス・脆弱性）を点検する契機として使う運用を提案できるようにする。
