## 0. 全体像 ― なぜこの分野を学ぶのか

7.3 では、ネットワーク層（IP）で暗号化を行う **IPsec** を学びました。IPsec は拠点と拠点をまるごと結ぶのには向いていますが、「世界中の不特定多数のブラウザが、初めて訪れる Web サイトと安全に通信する」という場面には向きません。利用者の PC に専用の設定を入れてもらうことができないからです。そこで、アプリケーションに組み込まれ、証明書を使って「初対面の相手」を確かめられるセキュアプロトコルとして普及したのが、ここで学ぶ **SSL/TLS** です。ここでは、セキュアな通信を実現する代表的な技術として、IPsec と並んで広く利用されている SSL/TLS について解説します。

SSL/TLS は、第3章 3.6 で学んだ HTTP の弱点（送受信データが平文でネットワークを流れる、通信相手を確かめられない）に対する標準的な答えであり、第3章 3.4 で見たメールの SMTP over TLS や STARTTLS の中身でもあります。さらに、SSL/TLS が通信相手を確かめるために使うデジタル証明書は、7.7 で学ぶ **PKI**（公開鍵基盤）によって発行・失効が管理されています。つまり本ノートは、「7.1 の暗号の部品（共通鍵暗号、公開鍵暗号、ハッシュ、MAC、デジタル署名）」を「7.7 の証明書」と組み合わせて、実際の通信路に仕立てる回だと考えてください。

本ノートは次の順で進みます。

1. **SSL/TLS とは何か**：SSL から TLS への歴史、バージョンの扱い、3つの機能、プロトコル構造（本ノート1節）
2. **どうやって安全な通信路を作るか**：ハンドシェイクの13のメッセージ、暗号スイートの読み方、TLS 1.2 と TLS 1.3 の違い、セッションとコネクション（2節）
3. **鍵はどう作られ、データはどう守られるか**：PRF による鍵生成と Record プロトコルの処理（3節）
4. **Web サイトの管理者は何を設定すべきか**：サーバの TLS 設定例、証明書の確認、HSTS（4節）
5. **過去の脆弱性から何を学ぶか**：ダウングレード攻撃、Heartbleed、POODLE、FREAK（5節）
6. **SSL-VPN**：SSL/TLS をリモートアクセスに応用する技術と、その機器を狙う攻撃（6節）

科目Bの業務観点では、主に「②情報システムの企画・設計・開発・運用におけるセキュリティ確保」（Web システムの方式設計、製品のセキュアな導入）と「③利用におけるセキュリティ対策の適用」（暗号利用と鍵管理、脆弱性への対応、ネットワーク機器のセキュリティ管理）に対応します。SSL-VPN 機器の脆弱性を起点とした侵入事例では「④インシデント管理」にもつながります。科目A-2では TLS 1.3 の暗号スイートの構成、ダウングレード攻撃、HSTS の動作が繰り返し出題され、科目Bではクライアント認証を用いたシステム設計や、証明書の検証・HSTS の設定の意味を記述させる問題が出ます。

## 1. SSL/TLS の概要 ― 何を、どの層で守るのか

### 1.1 SSL の誕生と TLS への継承

**SSL**（Secure Sockets Layer）は、米国 Netscape Communications 社（現在は他社に吸収合併）が開発した、認証と暗号化を行うための方式です。SSL は主に Web ブラウザと Web サーバの間でデータを安全にやり取りするための業界標準プロトコルとして使用されていました。

その後、IETF が SSL のバージョン 3.0 に基づいて標準化したのが **TLS**（Transport Layer Security）です。TLS は、トランスポート層における暗号化プロトコルを中心とした規格であり、その機能は SSL と同様に、デジタル証明書によるサーバ・クライアント間の認証及び通信路の暗号化です。TLS は SSL を継承するものと位置付けられます。

原本では「SSL は TLS として標準化されており、現在は TLS への移行が進められている」と説明されていました。現在は移行の段階を過ぎており、**SSL は全バージョンが使用禁止**です（SSL 2.0 は RFC 6176、SSL 3.0 は RFC 7568 で使用禁止とされました）。現場では今も「SSL 証明書」「SSL 化」という呼び方が残っていますが、実際に使われているのは TLS です。

5節の Column で見るように、近年 SSL 及び TLS に重大な脆弱性が相次いで発見されました。このため、SSL の全バージョンに加えて TLS の初期バージョン（TLS 1.0、TLS 1.1）も使用は推奨されていません。原本では「TLS 1.0、TLS 1.1 の一部の実装」が推奨されないと書かれていましたが、2021年の RFC 8996 により TLS 1.0 と TLS 1.1 はバージョンそのものが廃止（非推奨）とされています。したがって、Web サイトの管理者は、SSL/TLS を使用する場合には TLS の最新バージョン（TLS 1.3、互換性のために必要なら TLS 1.2 まで）だけを有効にするべきです。

**表：SSL/TLS のバージョン**

| バージョン | 規格 | 公開年 | 現在の扱い |
|---|---|---|---|
| SSL 2.0 | （Netscape 社の仕様） | 1995年 | 使用禁止（RFC 6176） |
| SSL 3.0 | RFC 6101（後年に記録として公開） | 1996年 | 使用禁止（RFC 7568）。POODLE の対象 |
| TLS 1.0 | RFC 2246 | 1999年 | 非推奨（RFC 8996で廃止） |
| TLS 1.1 | RFC 4346 | 2006年 | 非推奨（RFC 8996で廃止） |
| TLS 1.2 | RFC 5246 | 2008年 | 利用可 |
| TLS 1.3 | RFC 8446 | 2018年 | 推奨 |

### 1.2 HTTPS と URI

SSL/TLS によって確立されるセキュアな通信経路の上で HTTP 通信を行う仕組みが、「**HTTP over SSL**」「**HTTP over TLS**」です。両者をまとめて「**HTTP over SSL/TLS**」と表記し、URI スキーム「https」で表されます。第3章 3.6 で学んだ「重要な情報を扱うページでは HTTPS を使う」「Cookie に secure 属性を付ける」という対策は、すべてこの仕組みを前提にしています。

> **URI**
> **URI**（Uniform Resource Identifier）は、一定の書式によってインターネット上に存在する情報資源（リソース）の場所や名前を一意に指し示すための識別子である。URL は URI の一種であり、「https://」のようにスキームを先頭に記述する。

### 1.3 SSL/TLS の特徴 ― 3つの機能

SSL/TLS が何をしてくれるのかを、CIA（1.2 参照）と結び付けて整理しておきます。SSL の特徴は次のとおりです（TLS も同じです）。

- SSL/TLS は、アプリケーション層とトランスポート層の間で暗号化を行う。
- SSL/TLS は、デジタル証明書（公開鍵証明書）を用いて、サーバ・クライアント間の相互認証を行う。
- SSL/TLS は、通信経路上のデータの暗号化と、改ざん検知（完全性の確保）を行う。
- SSL/TLS はアプリケーションに依存せず、SSL/TLS に対応したさまざまなアプリケーションプロトコル（HTTP、SMTP、POP3、IMAP4、FTP など）で利用できる。

ここで「相互認証」という言葉に注意してください。SSL/TLS では、**サーバ認証は毎回行われますが、クライアント認証は任意（オプション）**です。ふだんブラウザで HTTPS のサイトを見るとき、ブラウザはサーバの証明書を検証してサーバを確かめますが、サーバはブラウザの証明書を求めません（利用者の確認は、TLS の上でパスワードなどにより行います）。サーバが「この会社の社員の PC だけを接続させたい」といった目的でクライアント証明書を要求する構成をとったときに、初めて相互認証になります。この区別は、科目Bで「クライアント認証を用いたシステムの設計」として問われます。

| 機能 | 守る特性 | 使う技術（7.1 参照） | 防ぐ攻撃 |
|---|---|---|---|
| 通信相手の認証（サーバ認証、任意でクライアント認証） | 真正性 | デジタル証明書、デジタル署名 | なりすまし（偽サイト）、中間者攻撃 |
| 通信データの暗号化 | 機密性 | 鍵交換（RSA、DH/ECDHE）＋共通鍵暗号（AES など） | 盗聴 |
| 改ざん検知 | 完全性 | MAC（HMAC）、AEAD | 改ざん、データの差し込み |

> **試験での出題例**
> 情報セキュリティスペシャリスト試験の午後問題では、SSL/TLS のクライアント認証を用いたシステムの設計に関する問題が出題された。また、HTTP over SSL/TLS（HTTPS）を用いた Web システムのセキュリティに関する問題も出題されている。

### 1.4 SSL/TLS のプロトコル構造

SSL/TLS は、トランスポート層（TCP）とアプリケーション層の間に位置付けられます。その内部は、下位層の **Recordプロトコル**と、上位層の四つのプロトコル（**Handshakeプロトコル**、**Change Cipher Specプロトコル**、**Alertプロトコル**、**Application Dataプロトコル**）から構成されます。上位の4つは「何を送るか」を決める係で、Record プロトコルは「どう包んで送るか」（分割・MAC・暗号化）を担う係だと考えると分かりやすいでしょう。

**図：SSL/TLS のプロトコル構造**

| TCP/IP階層 | プロトコル |
|---|---|
| アプリケーション層 | HTTP、SMTP、POP3、IMAP4、FTP など |
| SSL/TLS(上位層) | Handshakeプロトコル / Change Cipher Specプロトコル / Alertプロトコル / Application Dataプロトコル |
| SSL/TLS(下位層) | Recordプロトコル |
| トランスポート層 | TCP |
| インターネット層 | IP |
| ネットワークインタフェース層 | Ethernet など |

**表：SSL/TLS を構成するプロトコルの概要**

| プロトコル名 | 概要 |
|---|---|
| Recordプロトコル | 上位層からのデータを 2<sup>14</sup> バイト（16,384バイト）以下のブロックに分割し、圧縮、MAC の付与、暗号化の処理を行って送信する。データ受信時には、復号、MAC の検証、伸張の処理を行って上位層に引き渡す |
| Handshakeプロトコル | サーバ・クライアント間で新たにセッションを確立する、もしくはセッションを再開する際に、暗号化アルゴリズム、鍵、デジタル証明書などのパラメータを相手とネゴシエーションして決定する |
| Change Cipher Specプロトコル | 暗号化に関するパラメータが決定した、あるいは変更したことを相手に通知するために用いる |
| Alertプロトコル | 通信中に発生したイベントやエラーを通信相手に通知するために用いる。アラートには Warning（警告）と Fatal（致命的）の2種類がある。Fatal アラートを送信したホストと、それを受け取ったホストは、直ちにその通信（コネクション）を切断する |
| Application Dataプロトコル | Handshake プロトコルによって決定したパラメータに従って、アプリケーションデータを透過的に送受信する |

SSL/TLS がトランスポート層の「上」にあることは、IPsec との最大の違いです。IPsec はIP パケットそのものを守るので、どのアプリケーションの通信もまとめて保護できます。SSL/TLS はアプリケーションごとに組み込む必要がある代わりに、ブラウザやメールソフトに最初から入っているので利用者の設定が要りません。この性格の違いが、6節の「IPsec VPN と SSL-VPN の比較」にそのまま表れます。

## 2. ハンドシェイク ― セッション及びコネクションの確立

### 2.1 ハンドシェイクが解かなければならない問題

ブラウザが初めて Web サーバに接続するとき、両者は共通の鍵を何ももっていません。しかも、その間のネットワークには盗聴者や中間者がいるかもしれません。この状況で、クライアントとサーバは次の3つを同時に達成しなければなりません。

1. **何で暗号化するかを決める**（両者が使える暗号アルゴリズムの組＝暗号スイートの合意）
2. **相手が本物かを確かめる**（証明書によるサーバ認証、必要ならクライアント認証）
3. **盗聴者に知られずに共通鍵を共有する**（鍵交換）

これを行う一連のやり取りが**ハンドシェイク**で、ほとんどの処理は Handshake プロトコルが担います。

### 2.2 確立手順の全体像（TLS 1.2 まで）

SSL/TLS では、次のような手順でセッション及びコネクションを確立します。なお、これらの処理は、特に記述がないものについてはすべて Handshake プロトコルによって行われます。

**図：SSL/TLS におけるセッション及びコネクションの確立手順**

```
      クライアント                              サーバ
          |  ① Client Hello                        |
          |--------------------------------------->|
          |                        ② Server Hello  |
          |                        ③ Certificate   |
          |               ④ Server Key Exchange    |
          |   ⑤ Certificate Request(クライアント認証時) |
          |                   ⑥ Server Hello Done  |
          |<---------------------------------------|
          |  ⑦ Certificate(クライアント認証時)        |
          |  ⑧ Client Key Exchange                 |
          |  ⑨ Certificate Verify(クライアント認証時)  |
          |  ⑩ Change Cipher Spec                  |
          |  ⑪ Finished                            |
          |--------------------------------------->|
          |                  ⑫ Change Cipher Spec  |
          |                           ⑬ Finished   |
          |<---------------------------------------|
          |        アプリケーションデータ(暗号化通信)         |
          |<======================================>|
```

13個のメッセージは、目的ごとに4つのまとまりに分けると覚えやすくなります。

| まとまり | メッセージ | 目的 |
|---|---|---|
| 挨拶と条件の合意 | ① Client Hello、② Server Hello | 暗号スイートを決め、鍵の材料になる乱数を交換する |
| サーバの身元証明 | ③ Certificate、④ Server Key Exchange、⑤ Certificate Request、⑥ Server Hello Done | サーバが証明書を示し、鍵交換の材料を渡す（必要ならクライアント証明書を要求する） |
| クライアントの応答 | ⑦ Certificate、⑧ Client Key Exchange、⑨ Certificate Verify | クライアントが鍵の材料を送り、クライアント認証時は自分の証明書と署名を示す |
| 暗号化の開始と検証 | ⑩〜⑬ Change Cipher Spec、Finished | 双方が鍵を生成して暗号化に切り替え、ここまでのやり取りが改ざんされていないことを確かめ合う |

### 2.3 各メッセージの役割

**① Client Hello**

クライアントは、利用可能な暗号化/ハッシュアルゴリズムの一覧（**暗号スイート**）と、生成した乱数（クライアント乱数）をサーバに送信し、通信の開始を通知します。TLS 1.2 までの暗号スイートは、鍵交換アルゴリズム、署名アルゴリズム、認証暗号アルゴリズム、ハッシュアルゴリズムの四つで構成されていました。TLS 1.3 からは、認証暗号アルゴリズム（**AEAD**）とハッシュアルゴリズムの組みで構成されるようになりました。暗号スイート名の読み方は 2.4 で詳しく扱います。

**② Server Hello**

サーバは、クライアントから提示された暗号スイートの中から使用するものを選択します。そして、生成した乱数（サーバ乱数）及び**セッションID**とともに、選択結果をクライアントに通知します。サーバがどれを選ぶかはサーバの設定で決まるため、管理者が弱い暗号スイートを無効にしておくことが、5節のダウングレード攻撃への根本的な対策になります。

**③ Certificate**

サーバは、自身のデジタル証明書（公開鍵証明書）を、ルート CA までの証明書のリスト（**証明書チェーン**）を含めてクライアントに送信します。クライアントは、この証明書について「信頼する CA の署名があるか」「有効期間内か」「接続先のホスト名と一致するか」「失効していないか」を検証します（証明書の検証と失効確認の仕組みは 7.7 で学びます）。この検証こそが中間者攻撃を防ぐ要であり、利用者がブラウザの警告を無視して接続を続けると、SSL/TLS の認証機能は意味を失います。

> **CA**
> **CA**（Certification Authority：認証局）は、デジタル証明書を発行する機関である。利用者からの証明書発行要求（**CSR**）に基づき、申請者の本人確認を行ったうえで、CA 自身の秘密鍵で署名したデジタル証明書を発行する。

**④ Server Key Exchange**

原本では「③でサーバのデジタル証明書を送信しない場合などに、一時的な RSA 鍵か DH（Diffie-Hellman）鍵を生成し、クライアントに送信する」と説明されています。これは古い時代の説明を含んでいるので、現在の実態と合わせて理解しておきましょう。

- **一時的な RSA 鍵**：かつての「輸出グレード」暗号（5.4 の FREAK 参照）で、短い RSA 鍵を一時的に生成して送る用途がありました。現在は使われません。
- **一時的な DH 鍵（DHE／ECDHE）**：現在の主流です。鍵交換に DHE や ECDHE を使う暗号スイートでは、サーバは証明書を送ったうえで、さらに一時的な DH 公開値を Server Key Exchange で送り、その値に証明書の秘密鍵で署名を付けます。クライアントはこの署名を検証することで、「DH 公開値が本物のサーバから届いた（中間者に差し替えられていない）」ことを確かめます。
- **RSA 鍵交換**：証明書の公開鍵でプリマスタシークレットを暗号化する方式（⑧）では、Server Key Exchange は送られません。

**⑤ Certificate Request（クライアント認証を行う場合のみ）**

サーバがクライアントに対し、デジタル証明書の提示を要求します。

**⑥ Server Hello Done**

サーバがクライアントに対して、Server Hello から始まる一連のメッセージが完了したことを通知します。

**⑦ Certificate（クライアント認証を行う場合のみ）**

クライアントは、自身のデジタル証明書（公開鍵証明書）を、ルート CA までの証明書のリスト（証明書チェーン）を含めてサーバに送信します。

**⑧ Client Key Exchange**

クライアントは、暗号化通信に使用するセッション鍵を生成する基となる情報（**プリマスタシークレット**）を生成します。そして、デジタル証明書に含まれるサーバの公開鍵で暗号化してサーバに送信します。サーバの秘密鍵をもつ本物のサーバだけがこれを復号できるので、盗聴者はプリマスタシークレットを知ることができません。

これは RSA 鍵交換の場合の動きです。DHE／ECDHE を使う場合、クライアントは自分の一時的な DH 公開値を Client Key Exchange で送り、クライアントとサーバはそれぞれ相手の公開値と自分の秘密値からプリマスタシークレットを計算します。プリマスタシークレットそのものはネットワークを流れません。

**⑨ Certificate Verify（クライアント認証を行う場合のみ）**

クライアントは、Client Hello から直前までの通信内容のダイジェスト（ハッシュ値）に対し、自身の秘密鍵を用いてデジタル署名（Certificate Verify）を作成し、サーバに送信します。これを受信したサーバは、⑦でクライアントから受け取ったデジタル証明書に含まれる公開鍵を使い、デジタル署名を検証します。

なぜ証明書（⑦）だけでは足りないのでしょうか。証明書は公開情報なので、誰でもコピーして送れるからです。サーバは、「その証明書に対応する秘密鍵を、いま通信している相手が本当にもっている」ことを Certificate Verify の署名で確かめて、初めてクライアントを認証できます。秘密鍵をもたない攻撃者は、今回のやり取りに対する正しい署名を作れません。

**⑩ Change Cipher Spec**

クライアントは、プリマスタシークレットと、①②で交換した乱数（クライアント乱数、サーバ乱数）を用いて**マスタシークレット**を生成します。続いて Record プロトコルが、Handshake プロトコルから受け取ったマスタシークレットを基に、次の鍵などを生成します（詳しくは3節）。

- 完全性の検証に用いる **MAC鍵**
- **暗号鍵**
- ブロック暗号の CBC モードで使用する**初期ベクトル（IV）**

そして、Change Cipher Spec プロトコルが、使用する暗号アルゴリズムの準備が整ったことをサーバに通知します。

**⑪ Finished**

クライアントは、鍵交換と認証処理が成功したことをサーバに通知します。このメッセージは、⑩で生成した鍵を使用して暗号化して送信します。Finished には、それまでのハンドシェイクのメッセージ全体から計算した検証値が入っています。もし中間者が途中で Client Hello の暗号スイート一覧を書き換えていれば、両者の計算結果が一致せず、改ざんが発覚します。

**⑫ Change Cipher Spec**

サーバは、クライアントから受信した暗号化されたプリマスタシークレットを、自身の秘密鍵を用いて復号します。そして、それと乱数を用いて、クライアントと同様にマスタシークレットを生成します。続いて Record プロトコルが、Handshake プロトコルから受け取ったマスタシークレットを基に、完全性の検証に用いる MAC 鍵、暗号鍵、ブロック暗号の CBC モードで使用する初期ベクトル（IV）を生成します。そして、Change Cipher Spec プロトコルが、使用する暗号アルゴリズムの準備が整ったことをクライアントに通知します。

**⑬ Finished**

サーバは、鍵交換と認証処理が成功したことをクライアントに通知します。このメッセージは、⑫で生成した鍵を使用して暗号化して送信します。これによって SSL/TLS のセッション及びコネクションが確立し、以降はアプリケーションによる暗号化通信が行われます。

### 2.4 暗号スイート名の読み方

暗号スイートの名前は、それ自体が「どの部品を組み合わせるか」の仕様書になっています。サーバの設定やスキャン結果に出てくる名前を、管理者が自分で読めるようにしておきましょう。

> **暗号スイートの表記例**
> - TLS 1.2：`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`（鍵交換：ECDHE、署名：RSA、認証暗号：AES-128-GCM、ハッシュ：SHA-256）
> - TLS 1.3：`TLS_AES_128_GCM_SHA256`（AEAD：AES-128-GCM、ハッシュ：SHA-256）。鍵交換や署名のアルゴリズムは、暗号スイートとは別の拡張（supported_groups、signature_algorithms など）でネゴシエーションする。

**表：TLS 1.2 の暗号スイート `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` の分解**

| 部分 | 意味 | 役割 | 評価のポイント |
|---|---|---|---|
| `TLS` | プロトコル名 | ― | ― |
| `ECDHE` | 鍵交換（楕円曲線 DH、Ephemeral＝使い捨て） | プリマスタシークレットを共有する | DHE/ECDHE は前方秘匿性（PFS）あり。`RSA`（鍵交換）は PFS なし |
| `RSA` | 署名（認証） | サーバ証明書の鍵の種類。Server Key Exchange の署名に使う | `RSA` または `ECDSA` |
| `WITH` | 区切り | ― | ― |
| `AES_128_GCM` | 暗号化（認証付き暗号） | アプリケーションデータの暗号化と改ざん検知 | GCM や CHACHA20_POLY1305 は AEAD。`CBC` は避ける。`RC4`、`3DES`、`NULL`、`EXPORT` は不可 |
| `SHA256` | ハッシュ | PRF（鍵生成）や、CBC 方式なら HMAC に使う | `MD5` は不可 |

**表：TLS 1.3 で定義されている主な暗号スイート**

| 暗号スイート | AEAD | ハッシュ |
|---|---|---|
| `TLS_AES_128_GCM_SHA256` | AES-128-GCM | SHA-256 |
| `TLS_AES_256_GCM_SHA384` | AES-256-GCM | SHA-384 |
| `TLS_CHACHA20_POLY1305_SHA256` | ChaCha20-Poly1305 | SHA-256 |

**前方秘匿性**（PFS：Perfect Forward Secrecy）とは、「サーバの秘密鍵が将来漏えいしても、過去に記録された通信は解読されない」という性質です。RSA 鍵交換では、攻撃者が暗号化通信を録りためておき、後でサーバの秘密鍵を入手すれば、録りためた分のプリマスタシークレットをすべて復号できてしまいます。ECDHE では、通信ごとに使い捨ての DH 鍵から鍵を作り、終わったら捨てるので、秘密鍵が漏れても過去の通信の鍵は再現できません。これが、TLS 1.3 が RSA 鍵交換を廃止した理由です（5.2 の Heartbleed で秘密鍵が漏えいしたおそれがある場合の影響の大きさにも関わります）。

### 2.5 TLS 1.3 におけるハンドシェイクの変更点 ― 往復回数の比較

2.2 の手順は、主に TLS 1.2 までの RSA 鍵交換を前提としたものです。TLS 1.3 では、次のような変更が加えられています。

> **TLS 1.3 におけるハンドシェイクの変更点**
> - RSA による鍵輸送（プリマスタシークレットをサーバの公開鍵で暗号化して送る方式）を廃止した。代わりに、前方秘匿性（PFS）をもつ（EC）DHE による鍵交換に一本化された
> - Server Key Exchange/Client Key Exchange を廃止し、鍵共有の情報を Client Hello/Server Hello の拡張（**key_share**）に含めることで、ハンドシェイクを1往復（**1-RTT**）で完了できるようにした
> - Server Hello 以降のハンドシェイクメッセージ（証明書など）も暗号化されるようになった
> - Change Cipher Spec は互換性維持のためのダミーメッセージとなった

ECDHE を使う通常のハンドシェイクで、TLS 1.2 と TLS 1.3 を並べると、往復回数の違いがはっきりします（RTT：Round Trip Time＝1往復にかかる時間）。

**図：TLS 1.2（ECDHE）のフルハンドシェイク ― 2往復（2-RTT）**

```
 クライアント                                        サーバ
   ClientHello  ─────────────────────────────▶                ┐
                ◀─────────────────────────────  ServerHello    │ 1往復目
                                                Certificate    │（平文）
                                                ServerKeyExchange
                                                ServerHelloDone┘
   ClientKeyExchange                                           ┐
   ChangeCipherSpec                                            │ 2往復目
   Finished     ─────────────────────────────▶                 │
                ◀─────────────────────────────  ChangeCipherSpec
                                                Finished       ┘
   アプリケーションデータ  ◀══════════════════▶   ← 2往復の後に送信開始
```

**図：TLS 1.3 のフルハンドシェイク ― 1往復（1-RTT）**

```
 クライアント                                        サーバ
   ClientHello                                                 ┐
    + key_share（DH公開値）                                     │
    + supported_versions（TLS 1.3 を希望）                      │
    + signature_algorithms ────────────────▶                   │ 1往復目
                ◀─────────────────────────────  ServerHello    │
                                                 + key_share   │
                                                {EncryptedExtensions}
                                                {Certificate}  │
                                                {CertificateVerify}
                                                {Finished}     ┘
   {Finished}
   アプリケーションデータ  ═══════════════════▶   ← 1往復の後に送信開始
   { } ＝ key_share から導いたハンドシェイク用の鍵で暗号化されている部分
```

TLS 1.3 で1往復に縮められたのは、クライアントが最初の Client Hello の時点で「サーバはきっと ECDHE を選ぶだろう」と見込んで、DH 公開値（key_share）を先に送ってしまうからです。サーバは Server Hello で自分の公開値を返した時点で鍵を計算でき、続く証明書以降を最初から暗号化できます。そのため盗聴者は、TLS 1.3 では「どのサーバ証明書が使われたか」すら見ることができません。

また TLS 1.3 では、Server Key Exchange の署名の代わりに、サーバが **CertificateVerify**（ハンドシェイク全体への署名）を送ります。RSA 鍵輸送がなくなったので、「秘密鍵で復号できたから本物」という確認ができません。そこでサーバは、証明書の秘密鍵でハンドシェイクの内容に署名し、「この証明書の秘密鍵を自分がもっている」ことを毎回証明するのです。

**表：TLS 1.2 と TLS 1.3 の比較**

| 項目 | TLS 1.2 | TLS 1.3 |
|---|---|---|
| フルハンドシェイクの往復数 | 2-RTT | 1-RTT |
| 鍵交換 | RSA 鍵輸送、DHE、ECDHE | (EC)DHE のみ（PFS 必須） |
| 暗号スイートの構成 | 鍵交換・署名・暗号化・ハッシュ | AEAD・ハッシュ |
| 使える暗号 | CBC モード、RC4 なども規格上は可 | AEAD のみ（AES-GCM、ChaCha20-Poly1305 など） |
| 証明書の送信 | 平文 | 暗号化 |
| 圧縮 | 規格上は可（無効化を推奨） | 廃止 |
| 鍵導出 | PRF | HKDF |
| セッション再開 | セッションID、セッションチケット | PSK（0-RTT も可） |
| ダウングレード検知 | Finished による検証 | 加えて Server Hello の乱数に検知用の値を埋め込む |

### 2.6 実物で確かめる ― ブラウザの証明書表示と openssl s_client

ハンドシェイクの結果は、利用者や管理者が実際に目で確かめることができます。

**ブラウザで見える証明書情報**

ブラウザのアドレスバーの鍵アイコン（または「サイト情報」）から証明書を開くと、③ Certificate で受け取ったサーバ証明書の中身が、次のような項目で表示されます（表示の文言はブラウザによって異なります）。

```text
証明書ビューア：www.example.com
 ┌ 全般 ────────────────────────────────────────────────────────
 │ 発行先
 │   共通名 (CN)          www.example.com
 │   組織 (O)             Example Corporation      ← OV/EV 証明書の場合に表示
 │ 発行者
 │   共通名 (CN)          Example TLS CA 2026
 │   組織 (O)             Example Trust Services
 │ 有効期間
 │   発行日               2026年4月1日
 │   有効期限             2027年4月30日
 │ フィンガープリント
 │   SHA-256              5C:1A:9E:…:7B:03
 ├ 詳細 ────────────────────────────────────────────────────────
 │ 証明書の階層           Example Root CA R1
 │                         └ Example TLS CA 2026
 │                             └ www.example.com
 │ サブジェクトの別名(SAN) DNS:www.example.com, DNS:example.com
 │ 公開鍵                  ECDSA P-256（または RSA 2048ビット）

 │ 拡張鍵使用法            TLS Web サーバ認証
 │ CRL配布ポイント / 機関情報アクセス(OCSP)  http://ocsp.example.com/ …
 └──────────────────────────────────────────────────────────────
```

利用者や管理者が確かめるべきなのは、「SAN に接続先のホスト名が含まれているか」「発行者が信頼できる CA か（証明書の階層がルート CA までつながっているか）」「有効期限が切れていないか」の3点です。どれかが満たされないとブラウザは警告を出します。その警告は「中間者が偽の証明書を出している」可能性を示しているので、利用者は警告を無視して先に進んではいけません。各項目の意味と、CRL／OCSP による失効確認は 7.7 で詳しく学びます。

**openssl s_client の出力**

サーバ管理者は、自分のサーバが正しく設定されているかを、`openssl s_client` コマンドで確かめられます。次は、TLS 1.3 で接続できたときの出力の抜粋です。

```text
$ openssl s_client -connect www.example.com:443 -servername www.example.com
CONNECTED(00000003)
depth=2 C = US, O = Example Trust Services, CN = Example Root CA R1
verify return:1
depth=1 C = US, O = Example Trust Services, CN = Example TLS CA 2026
verify return:1
depth=0 CN = www.example.com
verify return:1
---
Certificate chain
 0 s:CN = www.example.com
   i:C = US, O = Example Trust Services, CN = Example TLS CA 2026
 1 s:C = US, O = Example Trust Services, CN = Example TLS CA 2026
   i:C = US, O = Example Trust Services, CN = Example Root CA R1
---
Peer signing digest: SHA256
Peer signature type: ECDSA
Server Temp Key: X25519, 253 bits
---
New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256
Server public key is 256 bit
Verify return code: 0 (ok)
```

読み方は次のとおりです。

| 出力 | 意味 | 確認すべきこと |
|---|---|---|
| `depth=2 … depth=0` と `verify return:1` | ルート CA から順に証明書チェーンを検証し、各段で成功 | 中間 CA 証明書がサーバから送られているか（欠けると一部の環境で検証に失敗する） |
| `Certificate chain` の `s:`（subject）と `i:`（issuer） | 各証明書の発行先と発行者 | 0番の発行者と1番の発行先が一致し、チェーンがつながっているか |
| `Server Temp Key: X25519` | 鍵交換に使った一時的な DH 鍵（ECDHE） | 一時鍵が使われている＝前方秘匿性あり |
| `New, TLSv1.3, Cipher is …` | 合意したバージョンと暗号スイート | 想定したバージョン・暗号スイートか |
| `Verify return code: 0 (ok)` | 証明書の検証結果 | 0 以外（期限切れ、ホスト名不一致など）なら設定を見直す |

管理者は、古いバージョンを無効にできているかも同じコマンドで確かめます。たとえば `openssl s_client -connect www.example.com:443 -tls1_1` を実行して、ハンドシェイクが失敗（protocol version のアラートなど）すれば、TLS 1.1 は正しく無効化されています。

### 2.7 セッションとコネクションの違い

SSL/TLS では、「**セッション**」と「**コネクション**」は明確に区別されており、それぞれ次のような意味をもちます。

**セッション**

セッションは、Handshake プロトコルによるサーバとクライアントとのネゴシエーションによって確立される論理的な関連付けです。セッションでは、次のような暗号化に関するパラメータが両者の間で共有されます。

- セッションID
- 相手のデジタル証明書
- 使用する暗号スイート（暗号化アルゴリズム、ハッシュアルゴリズムなど）
- 圧縮方式
- マスタシークレット
- 一つのセッションに複数のコネクションを許可するかどうかを示すフラグ

**コネクション**

コネクションは、セッションに従属して存在する通信チャネルであり、一つのセッションには、必要に応じて複数のコネクションが存在します。同じセッションに属するコネクションは一つのマスタシークレットを共有します。一方、MAC 鍵、暗号鍵、IV はコネクションごとに新たな乱数を用いて生成するため、コネクションごとに別個のものを使用することになります。なお、コネクションはトランスポート層に該当するため、クライアント側ではコネクションごとに異なるポート番号が割り当てられます。

| 項目 | セッション | コネクション |
|---|---|---|
| 性格 | 論理的な関連付け（合意内容） | 実際の通信チャネル（TCP コネクションに対応） |
| 数の関係 | 1つ | 1つのセッションに複数 |
| 共有するもの | セッションID、相手の証明書、暗号スイート、圧縮方式、マスタシークレット | 同じセッションのマスタシークレットを共有 |
| 個別にもつもの | ― | MAC 鍵、暗号鍵、IV（コネクションごとの乱数から生成）、クライアント側のポート番号 |

ブラウザが1つの Web ページを表示するとき、画像や CSS を取得するために複数の TCP コネクションを並行して張ることがあります。それぞれが1から完全なハンドシェイクをしていたら、サーバの負荷も表示の待ち時間も大きくなります。SSL/TLS では、サーバとクライアントとの完全な Handshake（新規セッションの確立）を行うと、多くのシステム資源を消費します。特に負荷が高いのは、プリマスタシークレットの生成及び共有の処理（公開鍵暗号の演算）です。そのため、既にセッションを確立しているホスト間で、そのセッションに複数のコネクションを許可するフラグが設定されている場合には、Handshake のプロセスを省略してコネクションを作成できるようになっています。具体的には、2.2 の「SSL/TLS におけるセッション及びコネクションの確立手順」における③〜⑨の処理、及び⑩、⑫のマスタシークレットの生成処理が省略されます。

> **セッション再開（Session Resumption）**
> このように Handshake を簡略化する仕組みを、**セッション再開**という。TLS 1.2 まではセッションIDや**セッションチケット**（RFC 5077）を用いる方式があり、TLS 1.3 では **PSK**（Pre-Shared Key）を用いる方式に統合されている。TLS 1.3 では、再開時に最初のメッセージからアプリケーションデータを送信できる **0-RTT** モードも規定されている。ただし、0-RTT モードはリプレイ攻撃に注意が必要である。

0-RTT のデータは、攻撃者が録っておいたものをもう一度サーバに送り直す（リプレイする）と、サーバがそれを再び受け付けてしまうおそれがあります。そのため、Web アプリケーションの開発者は、0-RTT を有効にする場合でも「注文の確定」「送金」のように何度実行されると困る処理を 0-RTT のデータで受け付けないよう設計するべきです。

## 3. 鍵生成と Record プロトコルによる送信データの処理

### 3.1 鍵生成の仕組み

2節のハンドシェイクで両者が共有したのは、プリマスタシークレットと2つの乱数だけです。実際の通信には、送信方向ごとの暗号鍵、MAC 鍵、IV が必要です。SSL/TLS では、セッション及びコネクションの確立過程において、次のように鍵を生成します（2.3 で解説した確立手順⑩、⑫）。鍵を生成するための演算処理には、**PRF**（Pseudo-Random Function：疑似乱数関数）が使用されます。

1. プリマスタシークレット、クライアント乱数、サーバ乱数を入力として PRF で演算し、マスタシークレット（48バイト）を生成する。
2. マスタシークレット、サーバ乱数、クライアント乱数を入力として PRF で演算し、必要な長さの**鍵ブロック**を生成する。
3. 鍵ブロックを分割して、送信方向（クライアント→サーバ、サーバ→クライアント）ごとに次の鍵などを取り出す。

**図：SSL/TLS における鍵生成のイメージ**

```
 プリマスタシークレット + クライアント乱数 + サーバ乱数
                 │
                 ▼ PRF
          マスタシークレット(48バイト)
                 │ + サーバ乱数 + クライアント乱数
                 ▼ PRF
              鍵ブロック
   ┌─────────┬─────────┬─────────┬─────────┬─────────┬─────────┐
   │クライアント │ サーバ   │クライアント │ サーバ   │クライアント │ サーバ   │
   │ MAC鍵   │ MAC鍵   │ 暗号鍵   │ 暗号鍵   │  IV     │  IV     │
   └─────────┴─────────┴─────────┴─────────┴─────────┴─────────┘
```

乱数を毎回混ぜるのには理由があります。クライアント乱数とサーバ乱数は接続のたびに変わるので、同じセッション（同じマスタシークレット）から作るコネクションであっても、鍵ブロックはコネクションごとに別のものになります（2.7 の「MAC 鍵、暗号鍵、IV はコネクションごとに別個」はこの仕組みによります）。また、攻撃者が過去の通信を録って再送しても、乱数が違うので鍵が合わず、リプレイ攻撃は成立しません。方向ごとに鍵を分けているのは、ある方向の暗号文を逆方向に送り返す攻撃を防ぐためです。

> **PRF**
> TLS 1.2 の PRF は、**HMAC**（SHA-256 など）を繰り返し適用して任意長の疑似乱数列を生成する関数である。TLS 1.3 では、PRF に代えて **HKDF**（HMAC-based Key Derivation Function）を用いた鍵導出方式が採用されている。

### 3.2 Record プロトコルが行う処理の概要

Record プロトコルは、前述のように、SSL/TLS のセッション及びコネクションの確立プロセスにおいて、マスタシークレットから鍵や IV を生成する処理を行います。また、確立したコネクションを通じて実際にデータを送受信する際には、次のような処理を行います。

**データ送信時**

Record プロトコルは、アプリケーションからのデータを 2<sup>14</sup> バイト以下のブロックに分割し、圧縮、HMAC の生成、暗号化の処理を行って SSL/TLS レコードに加工し、下位層のプロトコルに引き渡します。

**データ受信時**

Record プロトコルは、下位層のプロトコルから受け取った SSL/TLS レコードを復号し、HMAC を検証してデータが改ざんされていないことを確認します。そのうえで伸張し、分割されたデータを再結合して上位層のアプリケーションに引き渡します。HMAC の検証に失敗した場合、受信側は Alert プロトコルで Fatal アラートを送り、コネクションを切断します。

**図：Record プロトコルによる送信データ処理のイメージ（ブロック暗号を行う場合）**

```
 アプリケーションデータ
        │ ① 分割(2^14バイト以下)
        ▼
 ┌──────────┐
 │ フラグメント │
 └──────────┘
        │ ② 圧縮
        ▼
 ┌──────────┐
 │ 圧縮データ  │
 └──────────┘
        │ ③ HMACの生成・付加(MAC鍵を使用)
        ▼
 ┌──────────┬──────┐
 │ 圧縮データ  │ HMAC │
 └──────────┴──────┘
        │ ④ パディング付加、暗号化(暗号鍵・IVを使用、CBCモード)
        ▼
 ┌────────┬───────────────────────────┐
 │ ヘッダ  │ 暗号化データ(圧縮データ+HMAC+パディング) │
 └────────┴───────────────────────────┘
        │ ⑤ 下位層(TCP)へ引渡し
```

この図の方式は「先に MAC を付けてから暗号化する」（MAC-then-Encrypt）順序で、受信側は「復号してからパディングと MAC を確かめる」ことになります。この順序のせいで、パディングの検証結果の違いを手掛かりに暗号文を推測される弱点（5.3 の POODLE など、パディングオラクルと呼ばれる類型）が生まれました。AEAD はこの問題を設計から取り除いています。

> **圧縮機能の廃止**
> SSL/TLS の圧縮機能は、圧縮後のデータ長の変化から秘密情報を推測する **CRIME**攻撃に悪用されることが判明した。このため、現在は無効化が推奨されており、TLS 1.3 では圧縮機能そのものが廃止されている。また、TLS 1.2 以降で AEAD（AES-GCM など）を使用する場合は、暗号化と改ざん検知が一体として処理される。

圧縮が危ないのは、「同じ文字列が繰り返すほど短くなる」という圧縮の性質が、暗号化しても隠せない「長さ」に表れてしまうからです。攻撃者は中身を読めなくても長さは観測できるので、秘密情報（Cookie など）の推測に使われます。Web サーバの管理者は、TLS の圧縮を無効にしておくべきです（HTTP レベルの圧縮を悪用する同種の手法は BREACH と呼ばれます。確認問題3の選択肢イ参照）。

**図：SSL/TLS レコードのイメージ**

| フィールド | サイズ | 内容 |
|---|---|---|
| コンテンツタイプ | 1バイト | 上位プロトコルの種別（Change Cipher Spec=20、Alert=21、Handshake=22、Application Data=23） |
| バージョン | 2バイト | SSL/TLS のバージョン（例：TLS 1.2=0x0303） |
| 長さ | 2バイト | 後続のデータ部の長さ |
| データ部 | 可変長 | 暗号化されたデータ（圧縮データ、MAC、パディング） |

TLS 1.3 のレコードでも、古い中継機器との互換性のため、バージョンフィールドには TLS 1.2 と同じ 0x0303 が入ります。実際のバージョンは、ハンドシェイクの supported_versions 拡張で合意されます。パケットキャプチャで「0x0303 だから TLS 1.2」と早合点しないように注意しましょう。

**表：TLS 1.2 の2つの暗号化方式の比較**

| 項目 | CBC モード＋HMAC（MAC-then-Encrypt） | AEAD（AES-GCM、ChaCha20-Poly1305） |
|---|---|---|
| 処理 | HMAC を付けてからパディングして暗号化 | 暗号化と改ざん検知を一度に行う |
| 使う鍵 | 暗号鍵＋MAC 鍵＋IV | 暗号鍵＋ナンス（IV に相当） |
| 弱点 | パディングの検証を悪用される類型の攻撃（POODLE、Lucky Thirteen など） | 設計上この類型を受けない |
| TLS 1.3 | 使用不可 | 使用可（これのみ） |

## 4. Web サイトの管理者がすべき設定 ― TLS 設定と HSTS

### 4.1 サーバの TLS 設定例

ここまで学んだ仕組みを、Web サーバの管理者が実際に書く設定に落とし込んでみます。次は nginx での設定例です（Apache などでも、設定項目の考え方は同じです）。

```nginx
# /etc/nginx/conf.d/www.example.com.conf（抜粋）
server {
    listen 443 ssl;
    server_name www.example.com;

    # サーバ証明書は中間CA証明書と連結したもの（チェーン）を指定する
    ssl_certificate     /etc/nginx/tls/www.example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/www.example.com.key;   # 所有者 root、パーミッション 600

    # 有効にするプロトコルバージョン：SSL 3.0、TLS 1.0、TLS 1.1 は有効にしない
    ssl_protocols TLSv1.2 TLSv1.3;

    # TLS 1.2 で使う暗号スイート：ECDHE（前方秘匿性）＋AEAD のみ
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers off;

    # HSTS：以後1年間、サブドメインも含めて HTTPS でしか接続させない（4.3）
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}

# HTTP（80番）で来たアクセスは HTTPS へリダイレクトする
server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;
}
```

`ssl_ciphers` の名前は OpenSSL 流の表記で、たとえば `ECDHE-RSA-AES128-GCM-SHA256` は 2.4 の `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` と同じものです。この指定は TLS 1.2 にだけ効き、TLS 1.3 の暗号スイート（2.4 の3種類）はすべて AEAD なので既定のままで問題ありません。

| 設定 | 誰が・何のために・どうするか |
|---|---|
| プロトコルバージョン | Web サーバの管理者は、ダウングレード攻撃や既知の脆弱性の対象にならないよう、TLS 1.2 と TLS 1.3 だけを有効にし、SSL 3.0／TLS 1.0／TLS 1.1 を無効にする |
| 暗号スイート | 管理者は、解読しやすい暗号を交渉で選ばせないよう、ECDHE＋AEAD の組だけを許可し、RC4・3DES・EXPORT・NULL・CBC を外す |
| 証明書チェーン | 管理者は、クライアントが検証に失敗しないよう、中間 CA 証明書を含めたチェーンを設定する |
| 秘密鍵の保護 | 管理者は、秘密鍵が漏えいしてなりすましや過去通信の解読に使われないよう、ファイルの権限を最小にし（または HSM に格納し）、漏えいが疑われたら鍵を作り直して証明書を再発行し、旧証明書を失効させる |
| HTTP からのリダイレクトと HSTS | 管理者は、利用者が HTTP で来ても平文の通信を続けさせないよう、HTTPS へリダイレクトし、HSTS ヘッダで以後の HTTP 接続そのものをブラウザにさせない |
| 定期的な確認 | 管理者は、設定の劣化や証明書の期限切れを防ぐため、`openssl s_client` や診断サービスで定期的にバージョン・暗号スイート・証明書の期限を確認する |

推奨する設定の根拠としては、IPA と CRYPTREC が公開している「TLS暗号設定ガイドライン」が国内の標準的な参照先です。

### 4.2 常時 SSL/TLS

かつては、ログイン画面や決済画面だけを HTTPS にし、それ以外は HTTP のままにする Web サイトが多くありました。しかし、HTTP のページを改ざんされてログインフォームの送信先を書き換えられたり、Cookie を盗聴されたりする危険が残ります。そこで現在は、Web サイトの全ページを TLS で保護する**常時 SSL/TLS**（常時 HTTPS 化）が標準です。その効果は確認問題4で扱います。

### 4.3 HSTS 機構による HTTPS 通信の強制

常時 HTTPS にしても、利用者がアドレスバーに `www.example.com` とだけ入力したり、古いブックマークから `http://` でアクセスしたりすると、ブラウザの最初の1回の通信は HTTP（平文）になります。ここを中間者に狙われると、攻撃者は HTTPS へのリダイレクトを握りつぶし、利用者とは HTTP のまま、サーバとは HTTPS で中継することができます（**SSLストリッピング攻撃**）。利用者の画面には警告が出ないので、利用者は気づけません。

これを防ぐのが **HSTS**（HTTP Strict Transport Security）です。HSTS は、Web サイトが、HTTP でアクセスしたブラウザに対し、当該ドメイン（サブドメインにも適用可能）への次回以降のアクセスにおいて、「**max-age**」で指定した有効期限（秒単位）まで、HTTPS の使用を強制させる機構です。HSTS は、HTTP の応答ヘッダに「**Strict-Transport-Security**」を指定することによって有効になります。

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

> **HSTSヘッダの主なディレクティブ**
> - `max-age`：HTTPS を強制する期間（秒）。上記例の 31536000秒は1年に相当する。
> - `includeSubDomains`：サブドメインにも適用する。
> - `preload`：ブラウザの HSTS プリロードリストへの登録を希望することを示す。

ヘッダを受け取ったブラウザは、そのドメインを「HTTPS 専用」として記憶します。以後は、利用者が `http://` のリンクをクリックしても、ブラウザ自身が通信を送る前に `https://` に書き換えます。さらに、HSTS が有効なサイトで証明書エラーが起きた場合、ブラウザは「警告を無視して続行」の選択肢を出しません。HSTS は、利用者の判断に頼らず、ブラウザに HTTPS を強制させる仕組みなのです。ブラウザの開発者ツールで応答ヘッダを見ると、次のように確認できます。

```text
HTTP/2 200
content-type: text/html; charset=utf-8
strict-transport-security: max-age=31536000; includeSubDomains
```

Web サイトが HSTS を有効に設定していない場合、当該 Web サイトが HTTPS 通信だけを受け付けるようになっていても、中間者攻撃（SSL ストリッピング攻撃など）が行われると、ブラウザが HTTP で接続してしまい、攻撃者によってパケットが盗聴されてしまう可能性があります。なお、Web サイトが HSTS を有効に設定していたとしても、初回にブラウザが HTTP で Web サイトにアクセスした場合には（まだヘッダを受け取っていないので）HSTS が有効にならず、攻撃者によってパケットが盗聴されてしまう可能性があります。

> **HSTSプリロード**
> 初回アクセス時の弱点を補う仕組みとして、**HSTSプリロード**リストがある。主要ブラウザにあらかじめ組み込まれたリストにドメインを登録しておくことで、初回アクセスからHTTPSが強制される。

Web サイトの管理者は、HSTS を導入する前に、サブドメインを含むすべてのサイトが HTTPS で提供できることを確かめるべきです。`includeSubDomains` を付けたのに HTTP でしか動かないサブドメインが残っていると、そのサブドメインは max-age の期間中、利用者のブラウザから接続できなくなるからです。最初は短い max-age で試し、問題がなければ1年程度に延ばすのが安全な進め方です。

| 状態 | 初回アクセス | 2回目以降（max-age 内） |
|---|---|---|
| HSTS なし | HTTP で送られ、SSL ストリッピングを受けうる | 同左（毎回危険） |
| HSTS あり | HTTP で送られ、SSL ストリッピングを受けうる | ブラウザが HTTPS に書き換えて送る（安全） |
| HSTS あり＋プリロード | ブラウザが最初から HTTPS で送る（安全） | 同左 |

> **試験での出題**
> HSTS に関しては、情報処理安全確保支援士試験の午前Ⅱ・午後問題でも繰り返し出題されている。

## 5. 過去の重大な脆弱性から学ぶ ― 管理者は何をすべきか

SSL/TLS は、仕様の弱点と実装の欠陥の両方で、何度も重大な脆弱性を経験してきました。科目A-2では名前と仕組みの対応が、科目Bでは「なぜ古いバージョンを無効にしなければならないのか」「脆弱性が見つかったら何をすべきか」が問われます。ここでは、各脆弱性が**なぜ危険で、管理者が何をすべきか**に焦点を当てて整理します。

| 名前 | 公表 | 種類 | 損なわれる特性 | 管理者の対策 |
|---|---|---|---|---|
| バージョンロールバック（ダウングレード）攻撃 | ― | 仕様・設定の弱点 | 機密性 | 古いバージョン・弱い暗号スイートを無効化する |
| Heartbleed | 2014年4月 | 実装の欠陥（OpenSSL） | 機密性（秘密鍵まで漏えい） | 更新＋鍵の再生成・証明書の再発行 |
| POODLE | 2014年10月 | 仕様の弱点（SSL 3.0 の CBC パディング） | 機密性 | SSL 3.0 を無効化、CBC を避ける |
| FREAK | 2015年3月 | 実装の欠陥（輸出グレード RSA の受入れ） | 機密性 | 輸出グレード暗号スイートを無効化、更新 |

### 5.1 Column：SSL/TLS のバージョンロールバック攻撃

**バージョンロールバック攻撃**とは、SSL/TLS 等の通信プロトコルの古いバージョンを通信相手に使用させることにより、当該バージョンに存在する脆弱性を突いて暗号化通信の解読を試みる手法です。クライアントとサーバは、互いに対応する中で最も新しいバージョンを選ぶはずですが、中間者がハンドシェイクに介入して「古いバージョンしか使えない」ように見せかけると、両者は気づかずに弱いバージョンで通信してしまいます。

例えば、SSL/TLS を実装したオープンソースのライブラリである「**OpenSSL**」0.9.8系の一部のバージョンには問題がありました。サーバのオプションとして、クライアントの不具合を回避する SSL_OP_MSIE_SSLV2_RSA_PADDING（SSL_OP_ALL に含まれる）を指定した場合、バージョンロールバック攻撃により、SSL 2.0 プロトコルによる通信が強制されてしまいます（CVE-2005-2969）。SSL 2.0 には既知の脆弱性があるため、暗号化通信が解読され、重要な情報が漏えいする可能性があります。

この事例の教訓は、「古いクライアントとの互換性のために残した設定が、攻撃者の入口になる」ということです。サーバの管理者は、互換性のために古いバージョンや回避オプションを有効にしていないかを棚卸しし、不要なものは無効にするべきです。古いバージョンがサーバ側で無効になっていれば、中間者がいくら介入しても、そのバージョンで通信が成立することはありません。

### 5.2 Column：OpenSSL の「Heartbleed」脆弱性

OpenSSL のバージョン 1.0.1 で実装された SSL/TLS の死活監視機能である「**Heartbeat**」拡張に、重大な脆弱性が存在することが2014年4月に公表されました（CVE-2014-0160）。この脆弱性は「**Heartbleed**」と名付けられています。悪用されると、SSL 通信を行っているサーバのメモリに格納されている情報（1回のリクエストで最大64Kバイト）が第三者によって閲覧され、暗号化通信の内容や SSL 証明書の秘密鍵などの機密情報が漏えいする可能性があります。

**なぜ危険か**：Heartbleed は暗号の仕組みではなく実装の欠陥（受け取ったデータの長さを正しく検証していなかった）なので、どれほど強い暗号スイートを設定していても防げませんでした。しかもサーバのログに痕跡が残りにくく、「漏えいしたかどうか」を後から確かめることが困難でした。最も深刻なのは**証明書の秘密鍵**が漏れうる点です。秘密鍵を入手した攻撃者は、そのサーバになりすました偽サイトを作れ、RSA 鍵交換を使っていた場合は録りためた過去の通信まで復号できます（2.4 の前方秘匿性を参照）。

この脆弱性への対応としては、OpenSSL を安全なバージョン（1.0.1g 以降）に更新する必要があります。加えて、秘密鍵が漏えいした可能性を考慮し、秘密鍵と CSR（7.7 で解説）を新たに作成し、SSL 証明書を再発行／再登録する必要があります。管理者がすべき対応を、順序立てて書くと次のようになります。

1. 管理者は、脆弱な OpenSSL を使っている機器・ソフトウェアを洗い出し、修正版に更新する（更新後にサービスを再起動し、古いライブラリがメモリに残らないようにする）。
2. 管理者は、秘密鍵が漏えいした前提で、新しい鍵ペアと CSR を作成し、証明書を再発行してもらう。
3. 管理者は、古い証明書を CA に**失効**させ、盗まれた鍵でなりすまされても利用者のブラウザが拒否できるようにする（失効の仕組みは 7.7）。
4. 管理者は、メモリから漏れた可能性のある利用者のパスワードやセッションを無効化し、利用者にパスワード変更を依頼する。

### 5.3 Column：SSL 3.0 及び TLS 1.0、TLS 1.1 の「POODLE」脆弱性

SSL 3.0 において、中間者攻撃によって暗号化された通信が解読されてしまう脆弱性が存在することが2014年10月に公表されました（CVE-2014-3566）。この脆弱性は **POODLE**（Padding Oracle On Downgraded Legacy Encryption）と名付けられています。攻撃者は、プロトコルのダウングレードによって SSL 3.0 を使用させたうえで、CBC モードのパディングの検証の不備を突いて暗号文を1バイトずつ解読します。名前のとおり「ダウングレード」と「パディングオラクル」（3.2 の MAC-then-Encrypt の弱点）の組合せです。

その後、この脆弱性が一部の TLS 1.0、TLS 1.1 の実装においても存在することが報告されました。こうした状況を受け、クレジットカード業界におけるセキュリティ基準である **PCI DSS**（Payment Card Industry Data Security Standard）は、2015年4月にバージョン 3.0 から 3.1 にバージョンアップしました（PCI DSS については第9章 9.1 で解説）。バージョン 3.1 以降の PCI DSS では、SSL の全バージョン及び TLS の初期バージョンについては強力な暗号化技術とみなすことができず、使用することができないとされています。PCI DSS はその後も改訂が続き、現在はバージョン 4.0 系が使われていますが、この扱いは変わっていません。

**なぜ危険か**：SSL 3.0 の弱点は仕様そのものにあるため、パッチでは直せません。サーバが SSL 3.0 を「互換性のために」残しているだけで、ダウングレードの的になります。**管理者がすべきこと**は、サーバとクライアントの双方で SSL 3.0（および TLS 1.0／1.1）を無効化することです。カード情報を扱う事業者にとっては、PCI DSS への準拠という契約上の要求にもなります。

### 5.4 Column：SSL/TLS の「FREAK」脆弱性

SSL/TLS において、輸出グレードの弱い暗号強度の RSA 暗号をサポートしている実装に脆弱性が存在することが2015年3月に公表されました。この脆弱性は **FREAK**（Factoring RSA Export Keys）と名付けられています。中間者攻撃によって、鍵長512ビットの輸出グレードの RSA 暗号の使用を強制されると、攻撃者は短時間で鍵を素因数分解して暗号化通信を解読できます。対策としては、サーバ・クライアントの双方で輸出グレードの暗号スイートを無効化するとともに、ソフトウェアを脆弱性が修正されたバージョンに更新する必要があります。

「輸出グレード」とは、1990年代に米国が暗号の輸出を規制していたころ、国外向けに意図的に弱くした暗号のことです。規制はとうに撤廃されていましたが、実装の中に互換性のための機能として残り続け、20年後に攻撃の足場になりました。5.1 の教訓（使っていない古い選択肢を残さない）がここでも当てはまります。

### 5.5 脆弱性への備えをまとめる

4つの脆弱性から、管理者が平常時にすべきことは次の3点に集約できます。

- **選択肢を減らす**：サーバの管理者は、ダウングレード攻撃の余地をなくすため、TLS 1.2／1.3 と AEAD の暗号スイートだけを有効にする（4.1 の設定例）。
- **すばやく更新する**：管理者は、実装の欠陥（Heartbleed、FREAK）に備え、自組織が使う TLS ライブラリと製品を資産として把握し、脆弱性情報（JVN、ベンダーの告知など）を受けたら速やかに更新する。
- **鍵の漏えいを前提にした手順をもつ**：管理者は、秘密鍵が漏えいしたおそれがあるときに、鍵の再生成・証明書の再発行・旧証明書の失効を迷わず行えるよう、手順と連絡先（CA の窓口）を決めておく。また前方秘匿性のある鍵交換（ECDHE）を使い、鍵が漏れても過去の通信が解読されないようにしておく。

## 6. SSL/TLS によるインターネット VPN（SSL-VPN）

### 6.1 SSL-VPN の概要

7.2・7.3 で学んだ IPsec VPN は、利用者の PC に専用ソフトウェアと設定が必要でした。社外から社内システムを使いたい利用者すべてに、それを配って設定してもらうのは大きな負担です。そこで、ブラウザに最初から入っている SSL/TLS を使ってリモートアクセスを実現するのが **SSL-VPN** です。

SSL-VPN は、SSL/TLS と**リバースプロキシ**の技術を組み合わせることで VPN 通信を実現する技術です。SSL-VPN の構成イメージを下図に示します。SSL-VPN 装置（**SSL-VPNゲートウェイ**）は、SSL/TLS による認証と暗号化通信を行います。また、リバースプロキシとして、クライアントに代わって各サーバにアクセスしてデータのやり取りを行います。

**図：SSL-VPN の構成イメージ**

```
                   インターネット                        社内ネットワーク
 ┌───────────┐    SSL/TLSによる暗号化通信    ┌──────────────┐        ┌────────────┐
 │ クライアント │<============================>│ SSL-VPN装置   │<──────>│ Webサーバ    │
 │(ブラウザ)   │         (HTTPS)             │(リバースプロキシ)│<──────>│ メールサーバ  │
 └───────────┘                             └──────────────┘<──────>│ ファイルサーバ │
                                                 FW                 └────────────┘
```

SSL-VPN は、IPsec VPN とは異なり、使用するアプリケーションが Web（HTTPS）の場合にはブラウザのみで使用できます。そのため、クライアント環境に特別なソフトウェアなどをインストールする必要がありません（**クライアントレス**）。導入にあたってユーザへの負担が少なく、容易に VPN 環境を実現できます。

HTTPS は PC に限らず、携帯電話、スマートフォン、タブレット端末など数多くのクライアント環境で利用でき、設定作業なども特に必要ありません。このため、SSL-VPN はリモートアクセス環境での VPN 通信に適しています。ただし、デジタル証明書を用いてクライアント認証を行う場合には、HTTPS であってもクライアント環境での作業（クライアント証明書のインストールなど）が必要となります。

> **SSL-VPNの主な方式**
> - **リバースプロキシ方式**：SSL-VPN 装置が Web アプリケーションへのアクセスを中継する。ブラウザだけで利用できるが、対象は Web アプリケーションに限られる
> - **ポートフォワーディング方式**：クライアントにダウンロードした Java アプレットなどが、特定のポート宛ての通信を SSL/TLS でカプセル化して転送する。Web 以外の TCP アプリケーションにも対応できる
> - **L2フォワーディング（L3フォワーディング）方式**：専用のクライアントソフトウェアにより、IP パケットなどをまるごと SSL/TLS でカプセル化する。IPsec VPN と同様に、ほぼすべてのアプリケーションを利用できる

| 方式 | クライアントに必要なもの | 使えるアプリケーション | 向いている場面 |
|---|---|---|---|
| リバースプロキシ方式 | ブラウザのみ | Web アプリケーション | 社外から社内 Web システムを閲覧させる |
| ポートフォワーディング方式 | 中継用のプログラム（かつては Java アプレット） | 特定ポートの TCP アプリケーション | メールなど決まったアプリだけを使わせる |
| L2／L3 フォワーディング方式 | 専用クライアントソフトウェア | ほぼすべて（IP レベル） | 社内 LAN にいるのと同じ環境が必要な場合 |

### 6.2 SSL-VPN 使用における留意点

SSL/TLS は上位層で暗号化を行う方式であるため、使用するアプリケーションに依存します。例えば、SSL/TLS 対応のアプリケーションによって使用するポートが異なります（下表参照）。したがって、使用するアプリケーションの種類が増えれば、管理者はそれに応じてファイアウォールの設定を変更するなどの作業が必要となります。

**表：主な SSL/TLS 対応アプリケーションが使用するポート**

| プロトコル名 | ポート番号 | 備考 |
|---|---|---|
| HTTPS | 443 | HTTP over TLS/SSL |
| LDAPS | 636 | LDAP over TLS/SSL |
| FTPS-DATA | 989 | FTP, data, over TLS/SSL |
| FTPS | 990 | FTP, control, over TLS/SSL |
| TELNETS | 992 | TELNET over TLS/SSL |
| IMAPS | 993 | IMAP4 over TLS/SSL |
| POP3S | 995 | POP3 over TLS/SSL |

メールの暗号化に使う SMTP over TLS（SMTPS：465/TCP）と STARTTLS（25／587/TCP）は、第3章 3.4 で詳しく扱いました。

クライアント環境においても、Web 以外のアプリケーションを使用する場合には、利用者は SSL/TLS に対応したクライアントソフトウェアを使用するとともに、設定を一部変更する必要があります。SSL-VPN 製品の中には、通信に先立って専用の Java アプレットや ActiveX をクライアント環境にダウンロードするものもあります。このような製品では、Web 以外の SSL/TLS 通信もすべて HTTPS にカプセル化することで、アプリケーションによるプロトコルの違いを解消します。これによってファイアウォールの設定変更は不要となります。ただし、クライアント環境では、Web 以外の SSL/TLS 通信を localhost 上の Java アプレットや ActiveX に対して行うよう、アプリケーションの設定を変更する必要があります。

> **Javaアプレット・ActiveXの現状**
> Java アプレットや ActiveX は、主要な Web ブラウザでサポートが終了している。そのため、現在の SSL-VPN 製品では、専用のクライアントソフトウェア（エージェント）をインストールして Web 以外の通信を中継する方式が一般的となっている。

このように、7.3 で解説した IPsec VPN とこの SSL-VPN では、使用するアプリケーションなどによって一長一短があります。また、セキュリティ要件や運用管理の負荷なども考慮し、システムの設計者は、システムの目的に応じて適切な方式を選択する必要があります。

**表：IPsec VPN と SSL-VPN の比較**

| 比較項目 | IPsec VPN | SSL-VPN |
|---|---|---|
| 暗号化を行う層 | ネットワーク層 | トランスポート層とアプリケーション層の間 |
| 対応アプリケーション | 依存しない（IP 上のすべての通信） | 方式により異なる（リバースプロキシ方式では Web のみ） |
| クライアント環境 | 専用ソフトウェアのインストール・設定が必要 | Web であればブラウザのみで利用可能（クライアントレス） |
| 主な用途 | 拠点間接続（LAN 間接続） | リモートアクセス |
| NAT環境・ファイアウォール | NAT トラバーサルなどの考慮が必要 | 通常の HTTPS（443/TCP）を通過できる |

SSL-VPN を利用する際、クライアント側でサーバ証明書の検証を適切に行わず、ブラウザが表示する証明書の警告を無視して接続を続けると、攻撃者が用意した不正な SSL/TLS 証明書を受け入れてしまい、通信データが盗聴されたり改ざんされたりする可能性があるため、注意が必要です。SSL-VPN の通信路の安全性は、2.3 の③で見た「クライアントによる証明書の検証」にすべてかかっています。組織の管理者は、利用者に「証明書の警告が出たら接続を中止し、ヘルプデスクに連絡する」ことを周知し、専用クライアントを使う場合は証明書エラー時に接続しない設定にしておくべきです。

### 6.3 SSL-VPN と SSO を組み合わせたシステムの例

SSL-VPN 機能とリバースプロキシ方式の SSO システムを兼ね備えた製品を用いることで、セキュアなリモートアクセス環境を構築できます。

SSL-VPN と SSO を組み合わせたシステムの例を下図に示します。この例では、個々のユーザは固有の認証情報を保存した USB メモリ（**認証トークン**）を用いて、**ワンタイムパスワード**（OTP）による認証を行います。これにより、システムは正当な認証トークンをもたない者からのアクセスを排除します。認証トークン内には SSO サーバの URL を保存しません。このため、アクセス権限をもたない者が万一紛失した認証トークンを手に入れたとしても、それ単体では不正アクセスができないようになっています。

また、この例では、認証終了後にサーバからダウンロードされる Java アプレットが、SSL/TLS 対応アプリケーションの通信を制御（HTTPS にカプセル化）します。このため、クライアント環境では、前述のように localhost 上の Java アプレットと通信するための設定が必要になります。

**図：SSL-VPN と SSO を組み合わせたシステムのイメージ**

```
 ┌───────────────┐                         ┌───────────────────┐       ┌──────────┐
 │ クライアントPC   │ ① OTPによる認証(HTTPS)   │ SSL-VPN / SSO装置   │       │ 業務サーバA │
 │ + 認証トークン   │========================>│(リバースプロキシ)     │──────>│ 業務サーバB │
 │  (USBメモリ)    │ ② Javaアプレットのダウンロード │ 認証後、各サーバへ    │──────>│ 業務サーバC │
 │ Javaアプレット   │<========================│ シングルサインオン    │       └──────────┘
 │ (localhost)    │ ③ HTTPSにカプセル化した通信 │                   │
 └───────────────┘<=======================>└───────────────────┘
```

> **SSO**
> **SSO**（Single Sign-On）は、一度の認証で、複数のサーバやアプリケーションを追加の認証なしで利用できるようにする仕組みである。リバースプロキシ方式の SSO では、利用者とサーバの間に設置したリバースプロキシサーバが認証を一元的に行い、認証済みの利用者のアクセスを各サーバに中継する。
> SSO には、リバースプロキシ方式のほか、エージェント方式やフェデレーション方式（SAML など）がある。リバースプロキシ方式ではすべてのアクセスがリバースプロキシを経由するため、SSL-VPN 装置との親和性が高い。SSO の方式は第6章 6.8 で詳しく扱う。

### 6.4 Column：SSL-VPN 機器の重大な脆弱性

SSL-VPN 装置は、社外から社内へ入るための「玄関」としてインターネットに直接公開されます。そのため、装置そのものに脆弱性があれば、攻撃者は認証を通過する前に社内ネットワークへの足場を得てしまいます。

2019年、攻撃者がリモートから任意のコードを実行したり、キャッシュやログから認証情報を取得したりすることができる重大な脆弱性が、複数のベンダの SSL-VPN 製品で相次いで公表されました。これらの脆弱性を悪用するエクスプロイトコードも公開されており、当該脆弱性を狙った攻撃も観測されていると、同年9月に **JPCERT/CC** が注意喚起を行いました。

例えば、SSL-VPN アプライアンス「**Pulse Secure**」の脆弱性（CVE-2019-11510）では、当該機器が Windows ドメインに参加し、**Active Directory**（AD）と連携している場合、ドメイン管理者やドメインユーザの ID やパスワードを平文で取得される可能性があります。取得された認証情報は、**Pass the Ticket**攻撃（第6章 6.7 の Column で解説）などによって、侵入した組織の内部ネットワークにおける横展開（**ラテラルムーブメント**）に悪用されるおそれがあります。

> **同時期に公表された主なSSL-VPN製品の脆弱性**
> - Pulse Connect Secure：CVE-2019-11510（任意のファイル読取り）
> - Fortinet FortiOS：CVE-2018-13379（パストラバーサルによる認証情報の窃取）
> - Palo Alto Networks GlobalProtect：CVE-2019-1579（リモートコード実行）
>
> SSL-VPN 機器はインターネットに直接公開されるため、攻撃の標的になりやすい。迅速なパッチ適用に加え、パッチ適用前に認証情報が窃取されていた可能性を考慮し、パスワードの変更なども併せて実施することが重要である。

この事例は、ランサムウェア被害の侵入口として VPN 機器が多く使われた近年の傾向の先駆けでもあります。SSL-VPN 機器の管理者がすべきことを、「誰が・何を・何のために」の形でまとめます。

| 対策 | 何のために | 対策の機能（1.2） |
|---|---|---|
| 管理者は、ベンダーの脆弱性情報と JPCERT/CC の注意喚起を常に確認し、修正版を速やかに適用する | 公開された脆弱性を突かれる期間を短くする | 予防 |
| 管理者は、パッチ適用前に侵害された可能性を考え、全利用者のパスワードを変更させ、AD 連携アカウントの認証情報も更新する | 窃取済みの認証情報による再侵入を防ぐ | 回復・予防 |
| 管理者は、SSL-VPN の認証に多要素認証（OTP など）を組み合わせる | パスワードが漏れても、それだけではログインできないようにする | 予防 |
| 管理者は、SSL-VPN 機器と AD のログ（ログイン元・時刻・失敗回数）を監視し、通常と異なる国や時間帯からのログインを検知する | 侵入を早期に発見する | 検知・追跡 |
| 設計者は、VPN 経由の利用者がアクセスできる社内サーバを業務に必要な範囲に絞る | 侵入された場合の横展開の範囲を小さくする | 抑制 |

## 7. 確認問題

### 7.1 理解度チェック（Check!）

- **Q1**：SSL/TLS にはどのような機能があるか。
- **Q2**：SSL/TLS はどのようなプロトコルから構成されるか。
- **Q3**：SSL/TLS はどのような手順でセッション及びコネクションを確立するか。
- **Q4**：SSL/TLS におけるセッションとコネクションの違いは何か。
- **Q5**：SSL/TLS ではどのようにして鍵を生成するか。
- **Q6**：SSL/TLS の Record プロトコルでは送信データをどのように処理するか。
- **Q7**：SSL-VPN は IPsec VPN と比較してどのようなメリットがあるか。
- **Q8**：SSL-VPN を Web 以外のアプリケーションで使用する場合にはどのような設定が必要になるか。
- **Q9**：HSTS 機構とは何か。

> **解答例**
> - Q1：デジタル証明書による通信相手の認証（サーバ認証は必須、クライアント認証は任意）、通信経路上のデータの暗号化、MAC による改ざん検知（完全性の確保）。アプリケーションに依存せず HTTP、SMTP、POP3、IMAP4、FTP などで利用できる（本ノート 1.3）。
> - Q2：下位層の Record プロトコルと、上位層の Handshake、Change Cipher Spec、Alert、Application Data の4つのプロトコル（本ノート 1.4）。
> - Q3：Client Hello と Server Hello で暗号スイートと乱数を交換し、サーバが証明書（必要に応じて Server Key Exchange、Certificate Request）を送る。クライアントはプリマスタシークレットを Client Key Exchange で送り（クライアント認証時は Certificate と Certificate Verify も送る）、双方がマスタシークレットと鍵を生成して Change Cipher Spec と Finished を交換する（本ノート 2.2・2.3）。
> - Q4：セッションはハンドシェイクで確立される論理的な関連付けで、セッションID、相手の証明書、暗号スイート、圧縮方式、マスタシークレットなどを共有する。コネクションはセッションに従属する通信チャネルで、1セッションに複数存在でき、マスタシークレットは共有するが MAC 鍵・暗号鍵・IV はコネクションごとに別個に生成する（本ノート 2.7）。
> - Q5：プリマスタシークレットと両者の乱数から PRF でマスタシークレット（48バイト）を作り、さらにマスタシークレットと乱数から PRF で鍵ブロックを作り、送信方向ごとの MAC 鍵・暗号鍵・IV に分割する（本ノート 3.1）。
> - Q6：2<sup>14</sup> バイト以下に分割し、圧縮し、MAC 鍵で HMAC を付加し、パディングを付けて暗号鍵・IV で暗号化し、ヘッダを付けて TCP に渡す（本ノート 3.2）。
> - Q7：Web アプリケーションであればブラウザだけで利用でき（クライアントレス）、専用ソフトウェアの導入や設定が不要で、スマートフォンなど多様な端末から利用できる。通常の HTTPS（443/TCP）としてファイアウォールや NAT を通過できる（本ノート 6.1・6.2）。
> - Q8：SSL/TLS に対応したクライアントソフトウェアを使い、使用するポートに応じてファイアウォールを設定する。HTTPS にカプセル化する製品では、アプリケーションの接続先を localhost 上の中継プログラム（Java アプレット、ActiveX、現在は専用エージェント）に変更する（本ノート 6.2）。
> - Q9：Web サイトが応答ヘッダ Strict-Transport-Security でブラウザに指示し、max-age で指定した期間、そのドメイン（includeSubDomains でサブドメインも）へのアクセスを HTTPS に強制させる機構。SSL ストリッピングなどの中間者攻撃を防ぐ。初回アクセスの弱点はプリロードリストで補う（本ノート 4.3）。

### 7.2 確認問題1

TLS1.3 の暗号スイートに関する説明のうち、適切なものはどれか。

- ア AEAD（Authenticated Encryption with Associated Data）とハッシュアルゴリズムの組みで構成されている。
- イ TLS1.2 で規定されている共通鍵暗号 AES-CBC をサポート必須の暗号アルゴリズムとして継続利用できるようにしている。
- ウ Wi-Fi アライアンスにおいて規格化されている。
- エ サーバとクライアントのそれぞれがお互いに別の暗号アルゴリズムを選択できるようにしている。

〔情報処理安全確保支援士試験・R5秋・午前Ⅱ〕

> **解答・解説**
> TLS1.2 までの暗号スイートは、鍵交換アルゴリズム、署名アルゴリズム、AEAD（認証付き暗号）、ハッシュアルゴリズムの4つで構成されていたが、TLS1.3 からは、AEAD とハッシュアルゴリズムの組みで構成されている（例：`TLS_AES_128_GCM_SHA256`）。したがって**ア**が正解。
>
> - イ：TLS1.3 では AES-CBC などの AEAD でない暗号は廃止され、AES-GCM や ChaCha20-Poly1305 などの AEAD のみが利用できる。
> - ウ：TLS1.3 は IETF によって RFC 8446 として規格化されている。
> - エ：暗号スイートはハンドシェイクで合意した一つのものをサーバとクライアントの双方で使用する。

### 7.3 確認問題2

SSL/TLS のダウングレード攻撃に該当するものはどれか。

- ア 暗号化通信中にクライアント PC からサーバに送信するデータを操作して、強制的にサーバのデジタル証明書を失効させる。
- イ 暗号化通信中にサーバからクライアント PC に送信するデータを操作して、クライアント PC の Web ブラウザを古いバージョンのものにする。
- ウ 暗号化通信を確立するとき、弱い暗号スイートの使用を強制することによって、解読しやすい暗号化通信を行わせる。
- エ 暗号化通信を盗聴する攻撃者が、暗号鍵候補を総当たりで試すことによって解読する。

〔情報処理安全確保支援士試験・H29秋・午前Ⅱ〕

> **解答・解説**
> SSL/TLS の**ダウングレード攻撃**とは、中間者攻撃によってバージョンの古い脆弱な暗号スイートやプロトコルバージョンの使用を強制し、暗号化通信の解読を試みるものである。攻撃者は SSL/TLS の暗号化通信の確立時のハンドシェイクに介入することにより、この攻撃を成立させる。したがって**ウ**が正解。
>
> **代表的なダウングレード攻撃**
> POODLE 攻撃（SSL3.0 へのダウングレード）、FREAK 攻撃・**Logjam**攻撃（輸出グレードの弱い暗号へのダウングレード）などが知られている。TLS1.3 では、ダウングレードを検知する仕組みが ServerHello の乱数部分に組み込まれている。
>
> 本ノート 5節で見たとおり、管理者の根本対策は、サーバ側で古いバージョンと弱い暗号スイートを無効にし、「強制される選択肢」そのものをなくすことである。

### 7.4 確認問題3

HTTP Strict Transport Security（HSTS）の動作はどれか。

- ア HTTP over TLS（HTTPS）によって接続しているとき、接続先のサーバ証明書が EV SSL 証明書である場合とない場合で、Web ブラウザのアドレス表示部分の表示を変える。
- イ Web サーバからコンテンツをダウンロードするとき、どの文字列が秘密情報かを判別できないように圧縮する。
- ウ Web サーバと Web ブラウザとの間の TLS のハンドシェイクにおいて、一度確立したセッションとは別の新たなセッションを確立するとき、既に確立したセッションを使ってハンドシェイクを行う。
- エ Web ブラウザは、Web サイトにアクセスすると、以降の指定された期間、当該サイトには全て HTTPS によって接続する。

〔情報処理安全確保支援士試験・R6春・午前Ⅱ〕

> **解答・解説**
> HSTS は、Web サイトが応答ヘッダ「Strict-Transport-Security」によってブラウザに指示することで、max-age で指定された期間、当該サイトへのアクセスを全て HTTPS で行わせる機構である。したがって**エ**が正解。
>
> - ア：**EV SSL証明書**の表示に関する説明である（EV 証明書については 7.7 で扱う）。
> - イ：圧縮を悪用した攻撃（CRIME/BREACH 攻撃）への対策に関する説明である。
> - ウ：TLS のセッション再ネゴシエーションに関する説明である。

### 7.5 確認問題4

Web サイトにおいて、全ての Web ページを TLS で保護するよう設定する常時 SSL/TLS のセキュリティ上の効果はどれか。

- ア Web サイトでの SQL 組立て時にエスケープ処理が施され、SQL インジェクション攻撃による個人情報などの非公開情報の漏えいやデータベースに蓄積された商品価格などの改ざんを防止する。
- イ Web サイトへのアクセスが人間によるものかどうかを確かめ、Web ブラウザ以外のプログラムで自動化された Web クライアントによる大量のリクエストへの応答を避ける。
- ウ Web サイトへのブルートフォース攻撃によるログイン試行を検出してアカウントをロックし、Web サイトへの不正ログインを防止する。
- エ Web ブラウザと Web サイトとの間における中間者攻撃による通信データの漏えいと改ざんを防止し、サーバ証明書によって偽りの Web サイトの見分けを容易にする。

〔情報処理安全確保支援士試験・R元秋・午前Ⅱ〕

> **解答・解説**
> Web ページを TLS で保護することによる効果は次のとおりである。
>
> - サーバ証明書により、Web ブラウザ側で Web サイトの正当性を検証可能となる。
> - Web ブラウザと Web サイト間の通信が暗号化され、通信データが盗聴できなくなる。また、改ざんを検知できる。
>
> これにより、中間者攻撃を防止し、偽りの Web サイトの見分けを容易にすることができる。
>
> なお、**中間者攻撃**とは、Web ブラウザと Web サイトの間に不正なホストが介在し、通信データを中継しつつ不正なリクエストやレスポンスを紛れ込ませるなどしてセッションをコントロールしたり、通信データを盗み取りしたりする行為である。したがって**エ**が正解。
>
> - ア：プレースホルダの利用やエスケープ処理など、SQL インジェクション対策に関する説明である（第3章 3.6、第8章で扱う）。
> - イ：**CAPTCHA**に関する説明である。
> - ウ：**アカウントロックアウト**に関する説明である。
>
> TLS が守るのはあくまで「通信経路」であり、Web アプリケーションの脆弱性（SQL インジェクションなど）や不正ログインの試行は防げない、という切り分けがこの問題の要点である。

## 8. 試験対策まとめ（重要ポイント）

### 8.1 知識の確認（科目A-2向け）

- **SSL と TLS**：SSL は Netscape 社が開発、TLS は SSL 3.0 を基に IETF が標準化。SSL 2.0／3.0 は使用禁止、TLS 1.0／1.1 は RFC 8996 で廃止。TLS 1.2（RFC 5246）は利用可、TLS 1.3（RFC 8446）が推奨。
- **位置付け**：アプリケーション層とトランスポート層（TCP）の間。IPsec（ネットワーク層）との対比で問われる。
- **機能**：認証（サーバ認証は必須、クライアント認証は任意）、暗号化、改ざん検知。
- **構成プロトコル**：下位層 Record、上位層 Handshake／Change Cipher Spec／Alert／Application Data。Alert には Warning と Fatal があり、Fatal を送受信したら直ちに切断。
- **ハンドシェイク**：Client Hello（暗号スイート一覧＋乱数）→ Server Hello（選択結果＋乱数＋セッションID）→ Certificate → Server Key Exchange → （Certificate Request）→ Server Hello Done → （Certificate）→ Client Key Exchange（プリマスタシークレット）→ （Certificate Verify）→ Change Cipher Spec → Finished。カッコ内はクライアント認証時のみ。
- **Certificate Verify**：クライアントがそれまでのやり取りのハッシュ値に自分の秘密鍵で署名し、秘密鍵の所持を証明する。
- **暗号スイート**：TLS 1.2 は鍵交換・署名・認証暗号・ハッシュの4要素（`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`）、TLS 1.3 は AEAD とハッシュの組（`TLS_AES_128_GCM_SHA256`）。鍵交換と署名は supported_groups、signature_algorithms 拡張で決める。
- **TLS 1.3 の変更点**：RSA 鍵輸送の廃止と (EC)DHE への一本化（PFS 必須）、key_share による 1-RTT、Server Hello 以降の暗号化、Change Cipher Spec はダミー、圧縮廃止、PRF に代えて HKDF、AEAD のみ、ServerHello の乱数によるダウングレード検知。
- **前方秘匿性（PFS）**：サーバの秘密鍵が後から漏れても過去の通信を解読されない性質。DHE／ECDHE にあり、RSA 鍵交換にはない。
- **鍵生成**：プリマスタシークレット＋2つの乱数 →（PRF）→ マスタシークレット48バイト →（PRF）→ 鍵ブロック → 方向別の MAC 鍵・暗号鍵・IV。
- **セッションとコネクション**：セッションは論理的な関連付け（マスタシークレットを共有）、コネクションはその下の通信チャネル（MAC 鍵・暗号鍵・IV は別個、ポート番号も別）。セッション再開では③〜⑨とマスタシークレット生成を省略。TLS 1.3 は PSK に統合、0-RTT はリプレイ攻撃に注意。
- **Record プロトコル**：分割（2<sup>14</sup>＝16,384バイト以下）→ 圧縮 → HMAC → パディング・暗号化。レコードヘッダはコンテンツタイプ（20／21／22／23）、バージョン（TLS 1.2＝0x0303）、長さ。
- **圧縮**：CRIME 攻撃のため無効化。TLS 1.3 で廃止。HTTP 圧縮の悪用は BREACH。
- **脆弱性の名前と原因**：バージョンロールバック（OpenSSL 0.9.8 系、CVE-2005-2969、SSL 2.0 を強制）、Heartbleed（OpenSSL 1.0.1 の Heartbeat 拡張、CVE-2014-0160、メモリ最大64Kバイト漏えい、1.0.1g 以降に更新＋鍵・CSR 再作成・証明書再発行）、POODLE（SSL 3.0 の CBC パディング、CVE-2014-3566）、FREAK（輸出グレード RSA 512ビット）、Logjam（輸出グレード DH）。
- **PCI DSS**：2015年4月の 3.1 以降、SSL 全バージョンと初期 TLS は強力な暗号とみなさない。
- **HSTS**：応答ヘッダ Strict-Transport-Security、max-age（秒、31536000＝1年）、includeSubDomains、preload。初回アクセスは守れない→プリロードリストで補う。EV 証明書表示、圧縮対策、再ネゴシエーションと混同させる選択肢に注意。
- **常時 SSL/TLS の効果**：中間者攻撃による盗聴・改ざんの防止とサーバ証明書による偽サイトの見分け。SQL インジェクション対策、CAPTCHA、アカウントロックアウトとは別物。
- **SSL-VPN**：SSL/TLS＋リバースプロキシ。リバースプロキシ方式（Web のみ、クライアントレス）、ポートフォワーディング方式、L2／L3 フォワーディング方式。主な用途はリモートアクセス（IPsec VPN は拠点間）。
- **ポート番号**：HTTPS 443、LDAPS 636、FTPS-DATA 989、FTPS 990、TELNETS 992、IMAPS 993、POP3S 995。

### 8.2 記述式で問われる観点（科目B向け）

- **証明書の警告を無視させない理由**：「利用者が証明書の警告を無視して接続すると、中間者が提示した不正な証明書を受け入れることになり、通信が盗聴・改ざんされるおそれがあるため、警告が出たら接続を中止すべきである。」
- **クライアント認証の意味を説明する**：「サーバは、クライアント証明書と Certificate Verify の署名を検証することで、正当な秘密鍵をもつ端末（利用者）からの接続だけを受け付けられる。証明書だけでは複製できるため、秘密鍵による署名で所持を確認する。」設計では、秘密鍵をエクスポートできない形で端末に格納することも併せて答える。
- **古いバージョンを無効化する理由**：「サーバが SSL 3.0 や TLS 1.0／1.1、弱い暗号スイートを有効にしていると、中間者がハンドシェイクに介入してそれらを使わせるダウングレード攻撃を受け、通信が解読されるおそれがあるため、TLS 1.2 以上と AEAD の暗号スイートだけを有効にする。」
- **Heartbleed 型の脆弱性への対応手順**：「ライブラリを修正版に更新するだけでなく、秘密鍵が漏えいした前提で鍵ペアと CSR を作り直して証明書を再発行し、旧証明書を失効させ、利用者のパスワードやセッションを無効化する。」
- **前方秘匿性を選ぶ理由**：「ECDHE による鍵交換を使えば、将来サーバの秘密鍵が漏えいしても、過去に記録された通信を解読されないため。」
- **HSTS の効果と限界を書く**：「HSTS を設定すると、ブラウザは max-age の期間、HTTP での接続を自ら HTTPS に切り替えるため、SSL ストリッピングによる盗聴を防げる。ただし初回アクセスは保護されないため、プリロードリストに登録する。」導入時は全サブドメインの HTTPS 対応を先に確認する。
- **TLS が守らないものを切り分ける**：TLS は通信経路の盗聴・改ざん・なりすましを防ぐが、サーバ側に保存されたデータ、Web アプリケーションの脆弱性、端末のマルウェアは守らない。設問の「TLS を導入すれば十分か」には、この切り分けで答える。
- **SSL-VPN と IPsec VPN の選択理由**：「社外の多様な端末から Web システムに接続させるリモートアクセスでは、クライアントレスで HTTPS としてファイアウォールを通過できる SSL-VPN が適する。拠点間をすべてのアプリケーションでつなぐ場合は IPsec VPN が適する。」
- **SSL-VPN 機器の脆弱性が見つかったとき**：「修正版を速やかに適用し、パッチ適用前に認証情報が窃取された可能性を考慮して全利用者のパスワードを変更させ、ログイン履歴を調査して不審なログインの有無を確認する。」再発防止として多要素認証、アクセス範囲の限定、ログ監視を挙げる。
- **SSL-VPN と SSO の構成の意図**：「認証トークンに SSO サーバの URL を保存しないのは、トークンを紛失・盗難されても、それ単体では接続先が分からず不正アクセスできないようにするためである。」
