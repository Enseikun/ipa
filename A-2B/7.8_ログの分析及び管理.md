## 0. 全体像 ― なぜこの分野を学ぶのか

第7章 7.1〜7.7 では、暗号・VPN・TLS・PKI といった「情報を守るための仕組み」を学びました。しかし、どれほど堅牢な仕組みを作っても、それが**実際に正しく働いているか**、**誰かがすり抜けようとしていないか**は、仕組みの外から記録を見なければわかりません。その記録が**ログ**です。情報システムで発生している事象や利用状況、不正アクセスの有無等を把握するには、ログを分析するのが有効です。本ノートでは、ログ分析による効果や運用管理上の留意点等を解説します。

ログは、第1章 1.2 で整理した対策の4機能のうち主に「**検知・追跡**」を担います。加えて、「操作はすべて記録されている」と利用者に周知すれば内部不正の「**抑止**」にもなり、インシデント後には原因究明と「**回復**」の判断材料にもなります。ログが改ざんされていれば完全性が、ログが取れていなければ説明責任（第1章 1.2 の責任追跡性）が損なわれます。

本ノートは、次の順で進みます。

1. **ログとは何か**：主なログの種類と、実物（syslog の1行、Webアクセスログ、Windowsイベントログ、ファイアウォールログ）の読み方
2. **ログ分析で何がわかるか**：発見できる事象、ログの限界（人までは特定できない）、複数のログを時刻で突き合わせて事象を再構成する方法
3. **ログをどう管理するか**：運用管理上の5つの留意点（①ポリシ、②保全、③記録のための工夫、④要員・手順、⑤定期的な分析）に、時刻同期と保存規程の実例を加えて解説
4. **ログを証拠として使う**：デジタルフォレンジックスとの関係

前後のノートとのつながりも確認しておきましょう。第4章 4.8「情報セキュリティインシデント管理」では、SOC がログとアラートを見てインシデントの兆候を拾い、CSIRT へエスカレーションする流れを学びました。第5章 5.6「侵入検知システム(IDS)」では、NIDS・HIDS のアラートを SIEM に集約して突き合わせる運用を見ました。本ノートは、その**材料となるログを、どう取り、どう守り、どう読むか**を扱います。第5章 5.2「ホストの要塞化」の「⑨ログの設定」で個々のサーバに施した設定を、組織全体の仕組みに広げる回だと考えてください。

科目Bの業務観点では「③情報及び情報システムの利用におけるセキュリティ対策の適用」（セキュリティ監視とログ分析）と「④情報セキュリティインシデント管理」（証拠の収集と分析）に対応します。科目Bでは、問題文に掲載されたログを読んで「攻撃は成功したか」「どの端末が感染したか」を答えさせる設問や、「不審な通信を検知するために追加で取得すべきログ」を問う設問が頻出です。科目A-2では SIEM の定義、syslog、XFF、ログの保存要件（PCI DSS）などが問われます。

## 1. ログとは何か

### 1.1 ログの定義と目的

**ログ**は、OS、アプリケーション、通信機器などが、稼働状態、処理の実行状況、障害・異常の発生状況などについて出力した記録です。システムの管理者は、ログの分析結果に基づいて問題箇所を修正することで、発生中のトラブルを解決したり、将来発生が予想されるトラブル（ディスク容量の枯渇、証明書の期限切れなど）を未然に防いだりできます。セキュリティ担当者にとっては、ログは「攻撃者が何をしたか」を後から知るための、ほぼ唯一の手がかりです。

ファイアウォール、Webサーバ、メールサーバ、プロキシサーバ、IDS/IPSなどを設置したインターネット接続環境では、様々なログが出力されます。実際に出力されるログの種類や内容は、出力元であるサーバやセキュリティ製品の**設定によって決まります**。つまり、管理者が設定しなかったログは、インシデントが起きた後でいくら探しても存在しません。主なログの種類を次の表に示します。

> **試験にはこう出る**
> - 情報セキュリティスペシャリスト試験の午後Ⅰ問1で、ログ分析に関する問題が出題された。
> - 情報セキュリティスペシャリスト試験の午後Ⅱ問2で、ログ管理システムの設計を題材とした問題が出題された。
> - 情報処理安全確保支援士試験の令和5年度の午後問2で、セキュリティインシデントを題材として、被害状況の調査を行う上で各種ログを分析する旨や、その分析方法を調査する能力を問う問題が出題された。

### 1.2 主なログの種類

**表：主なログの種類**

| 分類 | ログの種類 | 概要 | セキュリティ上の主な用途 |
|---|---|---|---|
| OSが出力するログ | **UNIXシステムログ** | UNIX系OSが出力するログ。ログイン、プロセスの起動・停止、コマンド実行などが記録される（**syslog**等） | 不正ログイン、権限昇格（sudo）、不審なプロセスの発見 |
| | **Windowsイベントログ**（**EventLog**）／**PowerShellログ** | Windows系OSが出力するログ。アプリケーションの起動、ネットワークへの接続、システム設定の変更など各種イベントのほか、PowerShellの実行履歴などが記録される | ログオンの成否、アカウント作成、攻撃者によるスクリプト実行の追跡 |
| 一般的なサーバソフトウェアが出力するログ | **Webサーバアクセスログ** | Webサーバが出力するログ。各クライアントからのアクセス履歴（送信元IPアドレス、日時、リクエストURL、ステータスコード等）が記録される | Webアプリケーションへの攻撃の有無と成否（ステータスコード・応答サイズ） |
| | **SMTPサーバログ** | SMTPサーバが出力するログ。メールの配送履歴が記録される | 標的型メールの受信者の特定、なりすまし送信・大量送信の発見 |
| | **プロキシサーバログ** | プロキシサーバが出力するログ。内部ネットワークから外部のWebサイトへのアクセス履歴などが記録される | C&Cサーバとの通信、不審なサイトへのアップロードの発見 |
| | **DNSクエリログ** | DNSサーバ（キャッシュサーバ）が出力するログ。名前解決の問合せ履歴が記録され、DNSクエリを悪用するマルウェアの検知に利用できる | C&Cドメインの問合せ元端末の特定、DNSトンネリングの兆候 |
| | **ディレクトリサーバ／認証サーバログ** | Windows環境におけるActive Directoryなどのディレクトリサーバや認証サーバが出力するログ。ログインの成功・失敗、権限昇格などが記録される | パスワード攻撃、乗っ取られたアカウントによる横展開の追跡 |
| | **DBログ** | DBMSが出力するログ。DBへのアクセス履歴、操作履歴などが記録される | 大量の個人データの抽出、権限外のテーブル操作の発見 |
| セキュリティ関連製品が出力するログ | **ファイアウォールログ** | ファイアウォールが出力するログ。パケットの接続許可（**Accept**）、通知なしの破棄（**Drop**）、接続拒否通知及び破棄（**Reject**）の履歴や、ファイアウォール自体の稼働状況などが記録される | ポートスキャン、許可されていない外向き通信の発見 |
| | **IDS/IPSログ** | IDS/IPSが出力するログ。検知・遮断した攻撃や不審な通信が記録される | 攻撃の種類・送信元・宛先の把握 |
| | **AVログ** | AV（ウイルス対策）ソフトが出力するログ。コンピュータウイルスの検知・駆除の履歴が記録される。各PCのログをAV管理サーバに集約する製品が多い | 感染端末の特定、定義ファイル未更新端末の発見 |
| | **EDRログ** | EDR製品が出力するログ。PC、サーバ等のエンドポイントで発生する事象（プロセス生成、ファイル操作、レジストリ更新、通信など）が記録される。分析によりマルウェアの活動等を検知できる | 侵入後の不審な振る舞いの検知、感染経路の再構成 |
| その他 | **URLフィルタログ** | URLフィルタリングツールが出力するログ。Webアクセスに対するフィルタリング結果が記録される | 不正サイトへのアクセス試行の把握 |
| | **サンドボックスログ** | サンドボックス製品が出力するログ。不審なファイルの解析結果が記録される | 添付ファイルの危険度判定、同じ検体を受け取った利用者の特定 |
| | **VPNログ** | IPsecやTLSによるVPN機能を提供する機器が出力するログ。VPNへ接続した端末のIPアドレス、認証の成功・失敗の履歴などが記録される | 窃取された認証情報による社外からの不正接続の発見（第7章 7.2〜7.4 参照） |
| | **クラウドサービスログ** | Microsoft 365、Google Workspace等のパブリッククラウドサービスが出力するログ。アクセス履歴、ログインの成功・失敗、各種操作の履歴などが記録される | 海外からの不審なログイン、メール転送ルールの不正設定の発見 |

### 1.3 ログの1行を読む ― 実物の見た目

ログ分析の第一歩は、1行に何が書かれているかを正確に読むことです。代表的なログの実物を見ておきましょう。

**(1) syslog の1行（UNIX系OS）**

**syslog** は、UNIX系OSやネットワーク機器がログメッセージを出力し、ネットワーク経由で転送するための仕組みです（第5章 5.6 でも触れました）。従来の形式（RFC 3164）の1行は次のように見えます。

```text
<38>Sep 14 02:52:47 web01 sshd[6120]: Accepted password for suzuki from 203.0.113.45 port 53307 ssh2
 ①   ②               ③     ④    ⑤     ⑥
```

| 番号 | 項目 | この例の値 | 読み方 |
|---|---|---|---|
| ① | PRI（優先度） | `<38>` | ファシリティ×8＋重大度。38＝4（auth：認証関係）×8＋6（info：情報） |
| ② | タイムスタンプ | `Sep 14 02:52:47` | 年とタイムゾーンを含まない。機器ごとの時計がずれていると突合せができない（3.2 で扱う） |
| ③ | ホスト名 | `web01` | ログを出力した機器 |
| ④ | プログラム名 | `sshd` | 出力したプロセス（SSHサーバ） |
| ⑤ | プロセスID | `[6120]` | 同じプロセスの前後の行を追うときに使う |
| ⑥ | メッセージ | `Accepted password for suzuki from 203.0.113.45 …` | 「suzuki が 203.0.113.45 からパスワードでログインに成功した」 |

重大度（severity）は 0（emerg：システム使用不能）から 7（debug：デバッグ情報）までの8段階で、0 emerg／1 alert／2 crit／3 err／4 warning／5 notice／6 info／7 debug の順に軽くなります。新しい形式（RFC 5424）では、タイムスタンプが年とタイムゾーンを含む形（例：`2026-09-14T02:52:47.120+09:00`）になり、時刻の突合せがしやすくなっています。

**(2) Webサーバアクセスログ（Apache の combined 形式）**

```text
198.51.100.20 - - [14/Sep/2026:10:15:32 +0900] "GET /mypage/order?id=1024 HTTP/1.1" 200 5123 "https://www.example.jp/mypage/" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ..."
 送信元IP       認証名 日時（タイムゾーン付き）   リクエスト行                     状態 応答サイズ 参照元（Referer）             User-Agent
```

Webサーバの管理者は、ステータスコード（200＝成功、403＝拒否、404＝存在しない、500＝サーバエラー）と応答サイズを見て、リクエストが成功したかを判断します。第5章 5.6 で見たように、攻撃のリクエストに対して 200 と大きな応答サイズが返っていれば、攻撃が成功した可能性があります。

**(3) Windowsイベントログ（セキュリティログ）**

```text
ログの名前:   Security
ソース:       Microsoft-Windows-Security-Auditing
日付:         2026/09/14 3:15:02
イベント ID:  4624
タスクのカテゴリ: Logon
レベル:       情報
キーワード:   成功の監査
コンピューター: FS01.corp.example.jp
説明: アカウントが正常にログオンしました。
  アカウント名:     suzuki
  ログオン タイプ:  3（ネットワーク）
  ソース ネットワーク アドレス: 192.0.2.23
```

Windowsのセキュリティログはイベント ID で事象の種類を識別します。管理者が覚えておくと便利な代表例は、4624（ログオン成功）、4625（ログオン失敗）、4672（特権の割当て＝管理者権限でのログオン）、4688（プロセスの作成）、4720（ユーザアカウントの作成）、1102（監査ログの消去）です。とくに 1102 は、攻撃者が痕跡を消そうとした兆候であり、見つけたら直ちに調査すべきイベントです。

**(4) ファイアウォールログ**

```text
2026-09-14 03:05:12 action=accept proto=tcp src=192.0.2.23:49812  dst=198.51.100.77:443 rule=OUT-HTTPS-ALL bytes_out=1840 bytes_in=512
2026-09-14 03:06:40 action=drop   proto=tcp src=203.0.113.9:40122  dst=192.0.2.10:3389  rule=DEFAULT-DENY
2026-09-14 03:06:41 action=reject proto=tcp src=192.0.2.31:51001  dst=203.0.113.200:25 rule=OUT-SMTP-DENY
```

1行目は社内PCからの外向き HTTPS 通信を許可（accept）した記録、2行目は外部からのリモートデスクトップ（3389番）への接続を黙って破棄（drop）した記録、3行目は社内PCから外部のメールサーバへの直接送信を拒否通知付きで破棄（reject）した記録です。3行目は、メールサーバを経由せずに外部へメールを送ろうとする端末＝マルウェア感染の疑いがある端末を示している可能性があります。ここで注目してほしいのは1行目です。**許可された通信は、遮断ログだけを取っていると記録に残りません**。この点は 3.1 で詳しく扱います。

## 2. ログ分析で何がわかるか

### 2.1 ログ分析による効果

セキュリティ担当者は、ログを分析することで、次のような事象を発見できます。また、ログは不正アクセスなどのインシデント発生時に原因究明や被害範囲の特定を行う上で**重要な証拠データ**となるため、システムの管理者はログを適切に出力・保存する必要があります。

| 発見できる事象 | 主に使うログ | 何が読み取れるか |
|---|---|---|
| 内部ネットワークからインターネットへの不審なファイルの送信 | プロキシサーバログ、ファイアウォールログ（許可ログ） | 業務時間外に、普段使わない宛先へ大きなサイズの送信がある |
| 内部に侵入したマルウェア等による不審な通信（**C&Cサーバ**との通信など） | プロキシサーバログ、DNSクエリログ、IDS/IPSログ | 一定間隔で同じ宛先へ繰り返し接続している（ビーコン通信） |
| 一定時間内に何度も繰り返されるログインの試み（**パスワードリスト攻撃**、**ブルートフォース攻撃**など） | 認証サーバログ、syslog、VPNログ | 同一送信元から短時間に大量の失敗、その後に成功が混じる |
| 管理者権限の取得に何度も失敗している一般ユーザの存在 | syslog（sudo、su）、Windowsイベントログ | 権限昇格の試行（内部不正や乗っ取られたアカウント） |
| システム管理者が認識していない設定変更 | 機器の設定変更ログ、Windowsイベントログ | 変更管理の記録と突き合わせて、承認のない変更を見つける |

たとえば、パスワードを総当たりされた認証サーバのログは、第4章 4.8 で見たとおり、大量の `Failed password` の後に1行だけ `Accepted password` が現れる形になります。失敗だけなら「攻撃を受けたが防げた」事象ですが、成功が混じれば「侵入された」インシデントです。

> **試験にはこう出る**
> - 情報セキュリティスペシャリスト試験の午後Ⅰ問2で、Webサーバのアクセスログから攻撃や不審なアクセスを見つけ出す問題が出題された。ログによる不正アクセスの検知を題材とした問題は頻出である。
> - 平成24年度の試験で、ログのモニタリングを題材とした問題が出題された。

### 2.2 ログの限界 ― 人までは特定できない

ただし、ログはあくまでも**システムの振る舞いの記録**であり、実際にシステムを操作していた**人間までは特定できません**。ログに残るのは「suzuki というアカウントが、192.0.2.23 から操作した」という事実であって、「鈴木さん本人が操作した」という事実ではありません。そのため、他人のユーザIDなどを用いた**なりすまし**による不正アクセスなどの発見は困難です。こうした行為を発見するには、セキュリティ担当者は日頃から次のような情報を集めておき、ログの内容と比較するのが有効です。

- 各ユーザの平均的なシステム利用時間や利用時間帯
- 各ユーザが通常使用しているIPアドレス及びアプリケーション

この「普段の姿（ベースライン）」と比べる考え方は、第5章 5.6 で学んだ**異常検知（アノマリ検知）**と同じ発想です。たとえば「経理部の suzuki は平日 9〜18 時に社内の 192.0.2.0/24 からしかログインしない」という情報があれば、「深夜 2 時に国外の 203.0.113.45 からログイン成功」は、パスワードが正しくても異常だと判断できます。現在では、利用者や端末ごとの普段の振る舞いを機械的に学習し、外れた振る舞いを知らせる **UEBA**（User and Entity Behavior Analytics）という機能を備えた SIEM 製品もあります。

### 2.3 複数のログを時刻で突き合わせる ― 事象の再構成

1種類のログだけでは、攻撃の一場面しか見えません。セキュリティ担当者は、複数のログを**時刻**と**主体**（IPアドレス、アカウント、ホスト名）で並べ替えて突き合わせることで、攻撃の筋書き全体を再構成します。第4章 4.8 の事例（標的型メールによるマルウェア感染）を、ログの側から見直すと次のようになります。

```text
事象の再構成（全ログを JST に揃えて時刻順に並べたもの）            事案番号：IR-2026-0147
時刻(JST)            | ログの出所          | 記録内容（要旨）                                          | 読み取れること
---------------------+---------------------+-----------------------------------------------------------+------------------------------
2026-09-13 17:42:10  | SMTPサーバログ       | 外部 203.0.113.80 → sato@example.co.jp 宛て、添付 invoice.zip | 標的型メールの受信
2026-09-13 17:58:31  | EDRログ             | sato の PC(192.0.2.23) で WINWORD.EXE が子プロセスを生成     | 添付文書のマクロが実行された
2026-09-13 17:58:35  | DNSクエリログ        | 192.0.2.23 が cdn-update.example.com を問合せ              | 初めて現れる不審ドメイン
```

## 3. ログの運用管理上の留意点

組織がログを役立てるには、システムの管理者とセキュリティ担当者が、ログの運用管理に当たって次の点に留意する必要があります。

| 番号 | 留意点 | 目的（何のために） |
|---|---|---|
| ① | ログの取得・保存・管理に関するポリシの策定及び設定 | 必要なログが、必要な期間、確実に残るようにする |
| （補） | 時刻同期 | 複数のログを正確に突き合わせられるようにする |
| ② | ログの保全 | 攻撃者による改ざん・消去や容量不足による消失を防ぐ |
| ③ | 必要な情報を記録するためのシステム面での工夫 | 「誰が」「どこから」を後でたどれるようにする |
| ④ | ログの運用管理要員の確保及び手順書等の整備 | ログを見る人と手順を確保する |
| ⑤ | ログの定期的な分析 | インシデントを早期に検知する |

（補）の時刻同期は原本の5項目にはありませんが、2.3 の突合せの前提であり、試験でも問われるため本ノートで補っています。

### 3.1 ① ログの取得・保存・管理に関するポリシの策定及び設定

機器の標準設定のままでは、十分なログが出力されなかったり、逆に不要なログが大量に出力されたりすることがあります。例えばファイアウォールでは、通信の**遮断ログのみを記録**し、許可ログは量が膨大になるため記録しない運用も多くあります。DNSクエリログも同様です。しかし、内部に侵入したマルウェアの不正な通信を検知するには、インターネット側へ出ていく通信（**アウトバウンド通信**）の**許可ログ**や**DNSクエリログ**も取得しておくのが望ましいとされます。マルウェアの C&C 通信は、攻撃者がファイアウォールに許可されたポート（443番など）を選んで行うため、遮断ログには決して現れないからです。

このように、組織は取得すべきログの種類、保存期間、管理方法などを**ポリシ**として定め、システムの管理者はそれに従って各機器を設定する必要があります。ポリシは、たとえば次のような規程の形で文書化します。

```text
ログ管理規程（抜粋）                                    制定：2026/04/01  情報セキュリティ委員会
第3条（取得対象）  システム管理者は、別表1に定めるログを取得しなければならない。
                   ファイアウォールは、遮断ログに加え、内部から外部への通信の許可ログを取得する。
                   キャッシュDNSサーバは、問合せ元IPアドレスを含むクエリログを取得する。
第4条（記録項目）  ログには、少なくとも日時（タイムゾーンを含む）、送信元・宛先、利用者ID、
                   操作内容、結果（成功／失敗）を含めなければならない。
第5条（時刻同期）  すべての機器は、社内NTPサーバ（ntp1.example.jp、ntp2.example.jp）に時刻を同期させる。
第6条（保存期間）  ログは、取得日から1年間保存する。直近3か月分は、統合ログ管理システム上で
                   即時に検索できる状態に置く。カード会員データ環境のログはPCI DSSに従う。
第7条（保全）      ログは、取得後5分以内にログサーバへ転送する。ログサーバのログは、
                   システム管理者が削除・変更できない権限設定とし、日次でハッシュ値を記録する。
第8条（閲覧）      ログの閲覧は、CSIRT及びログ管理担当者に限る。閲覧の記録を残す。
第9条（分析）      SOCは、統合ログ管理システムのアラートを常時監視し、重大度High以上は
                   直ちにCSIRTへ連絡する。ログ管理担当者は、月次でログイン失敗・権限変更を確認する。

別表1（抜粋）
 対象            | 取得するログ                        | 保存期間 | 備考
-----------------+-------------------------------------+----------+------------------------
 ファイアウォール | 許可・遮断（内→外は全件）            | 1年      |
 プロキシ         | 全アクセス（URL・送受信サイズ）       | 1年      | X-Forwarded-For を含む
 認証サーバ(AD)   | ログオン成否、アカウント・権限変更    | 1年      | イベントID 4624/4625/4720/1102 等
 業務DB           | ログイン、個人データテーブルへの参照  | 1年      | アプリ利用者IDを記録
```

規程で「ログには利用者IDを含める」「ログの閲覧を限定する」と定めているのは、ログそのものが個人の行動記録（個人情報を含みうる情報）であり、ログ自体も守るべき情報資産だからです。

> **PCI DSSにおけるログの保存期間**
> PCI DSSでは、監査ログ（監査証跡の履歴）を**少なくとも12か月間**保持し、**少なくとも直近3か月分**はすぐに分析できる状態にしておくことを要求している（PCI DSSについては第9章 9.1 で解説。原本では「9.1.4項」と記載）。

### 3.2 （補）時刻同期 ― ログの時計をそろえる

2.3 の表で、仮にプロキシサーバの時計が5分遅れていたとしたら、「マクロ実行（17:58:31）」より先に「C&C接続」が起きたように見え、因果関係を誤って読んでしまいます。そこでシステムの管理者は、すべての機器の時計を **NTP**（Network Time Protocol：UDP 123番ポート）で同じ時刻源に同期させておくべきです。一般には、社内に NTP サーバを2台以上置いて外部の信頼できる時刻源に同期させ、社内の各機器はその社内 NTP サーバに同期させる階層構成をとります（NTP では時刻源からの段数を**ストラタム**と呼びます）。

Linux サーバで chrony を使う場合の設定と確認の例は次のとおりです。

```text
# /etc/chrony.conf（抜粋）
server ntp1.example.jp iburst      # 社内NTPサーバ1
server ntp2.example.jp iburst      # 社内NTPサーバ2（1台が止まっても同期を続けるため）
makestep 1.0 3                     # 起動直後に大きくずれていれば一気に合わせる

$ chronyc tracking
Reference ID    : C0000201 (ntp1.example.jp)
Stratum         : 3
System time     : 0.000012345 seconds fast of NTP time
Leap status     : Normal
```

`System time` の行が「NTP 時刻とのずれ」で、ここが十分小さい（この例では約 0.01 ミリ秒）ことを確認します。Windows の端末やサーバは、Active Directory のドメインに参加していればドメインコントローラから自動的に時刻を受け取ります（`w32tm /query /status` で同期先を確認できます）。

時刻同期については、次の点にも留意します。

- **タイムゾーンをそろえるか、明記する**：syslog の従来形式（RFC 3164）は年もタイムゾーンも含みません。クラウドサービスのログは UTC で記録されることが多く、そのまま並べると9時間ずれます。管理者は、ログを集約する時点で同じタイムゾーン（または UTC）に正規化するべきです。
- **NTP自体を攻撃から守る**：攻撃者が偽の時刻を配れば、ログの順序を乱したり、証明書の有効期限の判定を狂わせたりできます。管理者は、同期先を信頼できるサーバに限定し、必要に応じて NTP の認証（共通鍵による認証や、TLS を利用して時刻情報を保護する NTS〈Network Time Security〉）を使います。また、外部から社内 NTP サーバへの不要な問合せはファイアウォールで遮断します（NTP は DoS 攻撃の反射に悪用されることがあるため。第2章 2.7 参照）。

### 3.3 ② ログの保全 ― 改ざん防止と集中管理

ログを出力元の機器上にだけ保存していると、侵入した攻撃者により、痕跡を隠すための**ログの改ざんや消去**が行われる可能性があります。攻撃者は管理者権限を奪えば、そのサーバのログファイルを書き換えることができるからです。また、個々の機器でログ保存に使用できるストレージ容量は限られており、長期間の保存は困難です（多くの場合、設定した容量の上限に達すると**古いログから上書き**されます）。

そこで組織は、十分なストレージ容量を備えた**ログ保存専用のシステム**を構築するなどして、ログを必要な期間にわたって安全に保存（**保全**）できる仕組みを整える必要があります。後述する統合ログ管理システムやSIEMと専用のストレージを組み合わせて実現するケースも多くあります。

集中管理の第一歩は、各機器のログを発生と同時にログサーバへ転送する設定です。rsyslog の場合は次のように書きます。

```text
# /etc/rsyslog.d/90-forward.conf（各サーバ側）
*.*  @@logsrv.example.jp:514        # @@ は TCP で転送（@ 1つなら UDP）
# 実運用では TLS（6514番ポート）で暗号化して転送し、経路上での盗聴・改ざんも防ぐ
```

syslog の転送は伝統的に UDP 514番ポートで行われてきましたが、UDP では途中でログが失われても送信側は気づけません。そのため、取りこぼしが許されないログは TCP で、経路上の盗聴・改ざんまで防ぎたい場合は TLS（syslog over TLS）で転送するのが望ましいとされます。

> **ログの完全性の確保**
> ログの改ざんを防止・検知するために、追記のみ可能な**WORM**（**Write Once Read Many**）ストレージの利用、ログへの**ハッシュ値**や**電子署名**の付与、syslogサーバへの**リアルタイム転送**などの対策が採られる。

それぞれの対策が「何を防ぐか」を整理しておきます。

| 対策 | 誰が何をするか | 防げること | 防げないこと |
|---|---|---|---|
| リアルタイム転送 | 管理者が各機器からログサーバへ即時転送を設定する | 侵入されたサーバ上での事後の消去（転送済みの分は残る） | 転送前の改ざん、転送の停止そのもの |
| WORMストレージ | 管理者がログ保存先を追記専用の媒体・領域にする | 保存後の上書き・削除（管理者権限でも消せない） | 書き込まれる前の偽装 |
| ハッシュ値・電子署名 | ログサーバが一定期間ごとにハッシュ値を計算し、署名して別の場所に記録する | 改ざんの**検知**（後から値が一致しなければ改ざんがわかる） | 改ざんそのものの防止 |
| アクセス権の分離 | ログサーバの管理者と各システムの管理者を別の人にする | システム管理者による自分の操作記録の消去（内部不正） | ログサーバ管理者自身の不正（監査で補う） |

ハッシュ値で改ざんを検知するという考え方は、第7章 7.1 で学んだハッシュ関数の性質（入力が1ビットでも変わればハッシュ値が大きく変わる）をそのまま利用しています。

### 3.4 ③ 必要な情報を記録するためのシステム面での工夫

ログが残っていても、「誰が」「どこから」が記録されていなければ追跡はできません。例えば**3層構造のWebシステム**では、DBMSにアクセスするのはWebアプリケーションサーバであるため、DBMSでログを残しても**個々の利用者を識別できない**場合が多くあります。DBMSのログには、すべての操作がWebアプリケーションサーバの接続用アカウント（例：`appuser`）によるものとして記録されてしまうからです。このような場合には、開発者はアプリケーションを改修し、ユーザ情報をDBMSに引き渡すようにする（またはアプリケーション側で利用者IDと操作内容をログに出力する）必要があります。

```text
（改修前）DBログ：2026-09-14 10:15:33 user=appuser host=192.0.2.50 SELECT * FROM customer WHERE ...
（改修後）アプリログ：2026-09-14 10:15:33 app_user=tanaka@example.jp src=198.51.100.20 action=customer_search rows=1
```

また、**プロキシサーバ**や**負荷分散装置**を使用している場合などには、**X-Forwarded-For**（**XFF**）ヘッダフィールドにより、実際の送信元ホストのIPアドレスがログに記録されるようにしておく必要があります。

> **X-Forwarded-For（XFF）**
> プロキシサーバや負荷分散装置を経由すると、Webサーバから見た送信元IPアドレスは中継装置のものになる。XFFは、中継装置が元のクライアントのIPアドレスを格納して転送するHTTPヘッダフィールドであり、これをログに出力することで実際のアクセス元を把握できる。

見た目で比べると、違いは明らかです。

```text
（XFFを記録しない場合）全リクエストが負荷分散装置のアドレスになり、攻撃元を特定できない
192.0.2.5 - - [14/Sep/2026:10:15:32 +0900] "GET /mypage/order?id=1024 HTTP/1.1" 200 5123

（XFFを記録する場合）Apache の LogFormat に "%{X-Forwarded-For}i" を加える
192.0.2.5 198.51.100.20 - - [14/Sep/2026:10:15:32 +0900] "GET /mypage/order?id=1024 HTTP/1.1" 200 5123
          └ 実際のクライアントのアドレス
```

なお、XFF ヘッダはクライアント側でも自由に書けるため、Webサーバの管理者は「信頼できる中継装置（自組織の負荷分散装置）が付けた値」だけを採用するよう設定すべきです。

### 3.5 ④ ログの運用管理要員の確保及び手順書等の整備

組織は、ログの分析及び運用管理を行う**要員を確保**するとともに、**手順書等を整備**し、**教育・訓練**を実施しておく必要があります。ログは「取っているだけ」では何も教えてくれません。誰が、どの頻度で、どのログを、何を基準に確認し、異常を見つけたら誰に連絡するのかを手順書に書いておかなければ、ログは誰にも読まれないまま上書きされていきます。3.1 の規程例の第9条は、この「誰が・何を」を定めた部分です。

### 3.6 ⑤ ログの定期的な分析 ― 統合ログ管理システムとSIEM

インシデントを早期に検知するには、セキュリティ担当者がログを**定期的に分析**する必要があります。とはいえ、各機器に分散しているログを個々に分析するのは非効率であり、ログ同士の**相関**を見ることも困難です。そのため組織は、各種のログを効率的に収集・集約し、**相関分析**を行う**統合ログ管理システム**や**SIEM**を運用し、必要に応じて結果を**CSIRT**に**エスカレーション**します。ただし、統合ログ管理システムやSIEMにできることには**限界**があるため、最終的には**人間の分析力や判断力**が重要であることを認識しておく必要があります。SIEM は「設定されたルールに当てはまるもの」しか知らせてくれず、未知の手口や業務上の文脈（その時間に保守作業が予定されていたか等）は人が判断するしかないからです。

> **試験にはこう出る**
> 情報セキュリティスペシャリスト試験の午後問題で、マルウェアによる不審な通信を検知するために取得しなければならないログを問う問題が出題された。

> **SIEM（Security Information and Event Management）**
> 様々な機器やソフトウェアのログを一元的に収集・管理し、相関分析によってセキュリティインシデントの兆候をリアルタイムに検知・通知する仕組み。

**図：統合ログ管理システム／SIEMによるログの集約と分析の実施イメージ**

```
[ファイアウォール] [IDS/IPS] [Webサーバ] [メールサーバ]
[プロキシサーバ]  [DNSサーバ] [認証サーバ] [PC（AV/EDR）] ...
            │ 各種ログを転送・収集
            ▼
 ┌───────────────────────────┐
 │ 統合ログ管理システム／SIEM │──── 専用ストレージ（ログの保全）
 │ ・ログの集約・正規化        │
 │ ・相関分析・アラート通知    │
 └───────────────────────────┘
            │ 分析・監視
            ▼
     [運用管理要員（SOC等）]
            │ 必要に応じてエスカレーション
            ▼
          [CSIRT]
```

図の「**正規化**」とは、機器ごとに形式の違うログ（syslog、Windowsイベントログ、Webアクセスログなど）を、「日時（タイムゾーンをそろえる）」「送信元」「宛先」「利用者」「操作」「結果」といった共通の項目に変換することです。正規化しておくことで、SIEM は異なる機器のログを同じ項目で結び付けられるようになります。

SIEM の**相関ルール**は、「単体では弱い兆候でも、組み合わさると強い兆候になる」という考え方で作ります。防御側が設定するルールの例を、考え方だけ示します。

| ルール名（例） | 条件の組合せ | なぜ危険と判断するか | 重大度 |
|---|---|---|---|
| ログイン失敗の後の成功 | 同一アカウントに10分間で20回以上の失敗 ＋ その後の成功 | パスワードを当てられた可能性が高い | High |
| ありえない移動 | 同一アカウントが30分以内に国内と国外の両方からログイン | 認証情報が第三者に渡っている | High |
| 不審ドメインの後の大量送信 | 初めて問い合わせたドメインへの接続 ＋ 1時間以内に同じ宛先へ大容量の送信 | C&C通信と情報の持出しの組合せ | Critical |
| 痕跡の消去 | Windowsイベント ID 1102（監査ログの消去）の発生 | 正規の運用ではほぼ起きない | Critical |

第4章 4.8 で見た SIEM の相関アラート（「外部からの不正ログイン成功後の横展開」）は、このようなルールが4種類のログを同じアカウントと短い時間幅で結び付けた結果でした。

## 4. ログを証拠として使う ― デジタルフォレンジックスとの関係

インシデントが起きた後、ログは「何が起きたか」を説明する**証拠**になります。第4章 4.8 で学んだ**デジタルフォレンジックス**では、コンピュータやネットワーク機器に残された電子的記録を収集・解析し、法的な証拠として利用できるように保全します。そこで示した RFC 3227 の揮発性の順序では、「当該システムと関連する**遠隔ロギング**と監視データ」は5番目に位置づけられていました。ログサーバに転送済みのログは、感染した端末の電源が切れても消えないため、メモリやディスクより後回しにしてよい、という意味です。逆にいえば、ログを遠隔のログサーバに転送していない組織では、端末を初期化した時点で証拠が失われます。

ログを証拠として使えるようにするには、平常時から次の3つを満たしておく必要があります。

| 要件 | 何のために | 本ノートの対応箇所 |
|---|---|---|
| 必要なログが取得されている | 攻撃の各段階を記録として残すため | 3.1（ポリシ、許可ログ・DNSクエリログ） |
| 時刻が正確である | 複数のログを突き合わせて因果関係を示すため | 3.2（NTP による時刻同期） |
| 改ざんされていないことを示せる | 証拠としての信頼性（完全性）を保つため | 3.3（転送、WORM、ハッシュ値、権限の分離） |

インシデント発生後に CSIRT がログを証拠として保全するときは、第4章 4.8 の「証拠保全記録（Chain of Custody）」と同じく、対象期間のログを複製してハッシュ値を記録し、誰がいつ取り出したかを記録します。調査者は複製したログを解析し、原本のログには触れないようにします。

## 5. 確認問題

原本には理解度チェックと確認問題がないため、本ノートの要点を確認する問いを用意しました。

### 5.1 理解度チェック

- **Q1**：ログ分析によって発見できる事象を挙げよ。また、ログ分析だけでは発見が難しい行為と、その発見のために平常時から集めておくべき情報を述べよ。
- **Q2**：内部に侵入したマルウェアの不正な通信を検知するために、ファイアウォールとDNSサーバでどのようなログを取得すべきか。理由とともに述べよ。
- **Q3**：ログを出力元の機器上にだけ保存することの問題点と、その対策を述べよ。
- **Q4**：3層構造のWebシステムやプロキシサーバ・負荷分散装置を使う環境で、ログに「誰が」「どこから」を残すための工夫を述べよ。
- **Q5**：複数の機器のログを突き合わせて分析するために必要な前提条件を述べよ。
- **Q6**：SIEMとは何か。また、SIEMを導入しても人間の分析が必要な理由を述べよ。

> **解答例**
> - Q1：内部からインターネットへの不審なファイル送信、C&Cサーバとの通信、短時間に繰り返されるログインの試み、管理者権限の取得に何度も失敗する一般ユーザ、管理者が認識していない設定変更を発見できる。一方、ログは人間までは特定できないため、他人のIDを使ったなりすましの発見は難しい。各ユーザの平均的な利用時間・時間帯、通常使うIPアドレスとアプリケーションを集めておき、ログと比較する（本ノート 2 節）。
> - Q2：ファイアウォールでは遮断ログに加えてアウトバウンド通信の許可ログを、DNSサーバではクエリログを取得する。マルウェアは許可されたポートを使って通信するため遮断ログには現れず、C&Cドメインの名前解決はDNSクエリログにしか残らないからである（本ノート 3.1）。
> - Q3：侵入した攻撃者に改ざん・消去されるおそれがあり、容量の上限に達すると古いログから上書きされる。十分な容量のログ保存専用システムへリアルタイム転送し、WORMストレージ、ハッシュ値・電子署名の付与、権限の分離で完全性を確保する（本ノート 3.3）。
> - Q4：アプリケーションを改修して利用者情報をDBMSに引き渡す（またはアプリケーション側で利用者IDを記録する）。中継装置を使う場合は、X-Forwarded-Forヘッダの値をログに出力し、実際の送信元IPアドレスを記録する（本ノート 3.4）。
> - Q5：全機器の時刻がNTPで同期されていること、タイムゾーンがそろっている（正規化されている）こと、ログが保全されていること、送信元や利用者が正しく記録されていること（本ノート 2.3、3.2）。
> - Q6：様々な機器やソフトウェアのログを一元的に収集・管理し、相関分析によってインシデントの兆候をリアルタイムに検知・通知する仕組み。設定したルールに当てはまるものしか検知できず、未知の手口や業務上の文脈は判断できないため、最終的には人間の分析力・判断力が必要である（本ノート 3.6）。

## 6. 試験対策まとめ（重要ポイント）

### 6.1 知識の確認（科目A-2向け）

- **ログの定義**：OS、アプリケーション、通信機器が稼働状態・処理の実行状況・障害や異常の発生状況を出力した記録。出力内容は機器の設定で決まる。
- **ログの種類と用途**：プロキシ・DNSクエリ・ファイアウォール許可ログ＝C&C通信、認証サーバ・VPN＝不正ログイン、Webアクセスログ＝Web攻撃の成否、EDR＝侵入後の振る舞い、クラウドサービスログ＝SaaSの不正利用。
- **ファイアウォールのアクション**：Accept（許可）、Drop（通知なしの破棄）、Reject（拒否通知及び破棄）。
- **syslog**：PRI＝ファシリティ×8＋重大度。重大度は0（emerg）〜7（debug）。従来はUDP 514番、TLSでは6514番。RFC 3164 の形式は年とタイムゾーンを含まない。
- **Windowsイベント ID**：4624（ログオン成功）、4625（失敗）、4720（アカウント作成）、1102（監査ログの消去）。
- **ログの限界**：振る舞いの記録であり人間までは特定できない。なりすまし対策には利用時間帯・IPアドレス・アプリケーションのベースラインと比較する（UEBA）。
- **PCI DSS**：監査ログを少なくとも12か月保持、直近3か月分はすぐに分析できる状態にする。
- **ログの完全性**：WORM（Write Once Read Many）、ハッシュ値・電子署名、syslogサーバへのリアルタイム転送。ハッシュ値は改ざんの「検知」、WORMは「防止」。
- **X-Forwarded-For（XFF）**：中継装置が元のクライアントIPアドレスを格納するHTTPヘッダ。ログに出力して実際のアクセス元を把握する。
- **NTP**：UDP 123番。時刻同期はログ突合せの前提。時刻源からの段数をストラタムと呼ぶ。
- **SIEM**：ログを一元的に収集・管理し、相関分析でインシデントの兆候をリアルタイムに検知・通知する。正規化して共通項目で結び付ける。
- **遠隔ロギング**：RFC 3227 の揮発性の順序では5番目（ディスクより後）。

### 6.2 記述式で問われる観点（科目B向け）

- **追加で取得すべきログを答える**：「マルウェアの不正な通信を検知するために、システム管理者はファイアウォールでアウトバウンド通信の許可ログを、キャッシュDNSサーバでクエリログを取得すべきである。C&C通信は許可されたポートで行われるため遮断ログには残らないからである。」
- **ログから攻撃の成否を判断する**：大量の失敗の後の成功（認証ログ）、攻撃リクエストへの200と大きな応答サイズ（Webアクセスログ）を根拠に「成功した可能性が高い」と書く。失敗のみなら「攻撃は受けたが侵入はされていない」。
- **ログの保全策を理由付きで書く**：「侵入した攻撃者による改ざん・消去を防ぐため、ログを発生と同時に専用のログサーバへ転送し、システム管理者が削除できない権限設定とする。」改ざんの検知にはハッシュ値の記録を挙げる。
- **時刻同期の不備を指摘する**：事例で機器ごとの時刻がずれている、タイムゾーンが混在している場合、「NTPで全機器の時刻を同期させ、ログをタイムゾーンをそろえて正規化すべきである。時刻がずれていると事象の前後関係を誤って判断するため。」
- **送信元が特定できない構成を指摘する**：負荷分散装置やプロキシの背後のWebサーバでは「XFFヘッダの値をログに出力する」、3層構造では「アプリケーションが利用者IDを記録する（DBMSに引き渡す）」。
- **なりすましへの対策**：「ログは人を特定できないため、利用者ごとの通常の利用時間帯・接続元と比較して逸脱を検知する。」
- **SIEMの導入効果と限界**：分散したログの相関分析で単体では見逃す兆候を検知できる。ただし最終判断には人間の分析が必要であり、要員の確保・手順書・教育訓練、CSIRTへのエスカレーション基準を定める。
- **証拠としての要件**：ログが取得されている・時刻が正確・改ざんされていないことを示せる、の3点。証拠として保全する際は複製にハッシュ値を記録し、複製を解析する。
