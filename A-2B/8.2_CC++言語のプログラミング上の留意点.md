## 0. 全体像 ― なぜこの分野を学ぶのか

第2章 2.3「バッファオーバフロー攻撃」では、攻撃者が長すぎる入力でスタック上のリターンアドレスを書き換え、プログラムを乗っ取る仕組みと、DEP・ASLR・スタックカナリアといった OS・コンパイラの保護機能を学びました。そこで確認した結論は、「保護機能は攻撃を難しくするが、根本原因はプログラムのバグであり、最も効果が大きいのは開発者がバグを作り込まないこと」でした。第8章 8.1「システム開発工程とセキュリティ」では、そのための取組みを開発工程（要件定義・設計・実装・テスト）全体に組み込む考え方を見ています。本ノートは、その中の**実装工程**、つまり開発者がソースコードを1行ずつ書く場面に焦点を絞ります。

本ノートで扱うのは**セキュアプログラミング**、すなわち「開発者が脆弱性を作り込まないための書き方」です。攻撃者がどう入力を組み立てるかではなく、「なぜこの書き方が危険か」「開発者はどう書くべきか」を、修正前と修正後のコードを並べて確認していきます。

> **参考**
> 試験ではC/C++言語が対象とされることが多いが、ここで解説する内容はC言語とC++言語に共通する。そのため、あえて「C/C++言語」と表記する。

本ノートは次の順で進みます。

4. **BOF以外に開発者が作り込みやすい欠陥**：整数オーバフロー、書式文字列、解放後のポインタ、競合状態（本ノート4節）
5. **system関数とOSコマンドインジェクション**：BOF対策をしても残る「入力の中身」の問題（本ノート5節）

## 1. なぜC/C++は危ないのか ― BOFを引き起こす関数と文字列の約束事

### 1.1 開発者の立場から見たBOF

第2章 2.3節で述べたように、C/C++言語には、**BOF**（Buffer Overflow：**バッファオーバフロー**）攻撃の標的となりやすい言語仕様上の問題があります。具体的には、文字列操作を行う関数の多くが、引数のサイズ（書込み先バッファの大きさ）をチェックしないという問題です。Java や Python では、配列の範囲外に書き込もうとすると言語の実行環境が例外を出して止めてくれます。C/C++ では、言語も標準関数もその検査をしないため、「書込み先の大きさを守る」責任がすべて開発者に課されています。

> **BOF(バッファオーバフロー)**
> プログラムが確保したバッファ(メモリ領域)の大きさを超えてデータを書き込むことにより、隣接するメモリ領域(スタック上のリターンアドレスなど)を上書きしてしまう現象である。攻撃者はこれを悪用して、任意のコードの実行やプログラムの異常終了を引き起こす。

BOFが起きると、CIA のうち**完全性**（メモリ上のデータやリターンアドレスが書き換えられる）と**可用性**（プログラムが異常終了する）が損なわれ、攻撃者が任意のコードを実行できれば**機密性**も失われます。攻撃側の流れとOSの保護機能は第2章 2.3 で見たとおりなので、本ノートでは繰り返しません。ここで押さえるべきなのは、第1章 1.2 で整理した対策の4機能のうち、開発者の書き方は**予防・防止**の中心であり、ほかの機能（カナリアによる検知、パッチによる回復）では代わりが利かない、という点です。

したがって、C/C++言語を用いた開発では、開発者は、まずこの問題によってBOF攻撃の標的となるバグを作り込まないよう十分に注意する必要があります。BOF攻撃の標的となる可能性の高い関数には、次のようなものがあります。

| 分類 | 関数 | 共通する危険 |
| --- | --- | --- |
| 1行入力 | `gets()` | 読み込む長さを指定する手段がない |
| 文字列のコピー・連結 | `strcpy()`、`strcat()` | 書込み先の大きさを検査しない |
| 書式付き出力 | `sprintf()`、`vsprintf()` | 書式展開後の長さを検査しない |
| 書式付き入力 | `scanf()`、`sscanf()`、`fscanf()`、`vfscanf()`、`vscanf()`、`vsscanf()` | `%s` に幅を指定しないと長さ無制限で格納する |

`v` で始まる関数（`vsprintf`、`vscanf` など）は、可変個の引数を `va_list` 型の1つの引数にまとめて受け取る版で、危険性は `v` の付かない関数と同じです。

### 1.2 ナル文字の扱い ― C/C++の文字列は「終端記号」で長さが決まる

C/C++言語をはじめ、多くのプログラム言語では、**ナル（NULL）文字**（表記方法によって `0x00`、`\0`、`%00` などと表す）が文字列の終端を示します。C の文字列は「長さ」を持たず、先頭から順に読んでナル文字に出会った位置を終わりとみなす、という約束で成り立っています。そのため、文字列を処理する関数には、ナル文字に関して次のように動作するものがあります（詳細な仕様は関数によって異なります）。

1. ナル文字を見つけると文字列の終端と認識し、読込みなどの処理を終了する
2. バッファに文字列を格納する際、末尾にナル文字を付加する

なお、ASCII の正式な名称は **NUL**（値0の制御文字）で、C の `NULL` は「どこも指さないポインタ」を表すマクロです。原本や多くの教材は「ナル（NULL）文字」と書きますが、プログラム上は `'\0'`（文字）と `NULL`（ポインタ）を混同しないようにしてください。

メモリ上の見た目は次のとおりです。`char buf[8]` に `"abc"` を格納すると、4バイト目にナル文字が入り、残りは使われません。

```
buf[0] buf[1] buf[2] buf[3] buf[4] buf[5] buf[6] buf[7]
 'a'    'b'    'c'    '\0'    ?      ?      ?      ?
 0x61   0x62   0x63   0x00
                       ↑ strlen(buf) はここまでを数えて 3 を返す（ナル文字は数えない）
```

`strlen` が返す「文字列の長さ」と、格納に必要な「バッファの大きさ」は1バイト違う、という点が、以降のすべての関数の注意点の出発点になります。

### 1.3 ナル文字に関するプログラミング上の留意点

**①の性質（ナル文字で処理を打ち切る）が招く問題**

上記①の性質をもつ関数を悪用し、入力データ中に意図的にナル文字を混入させて、不正な処理を実行させる攻撃手法があります。

例えば、ユーザが入力した任意のファイル名に対し、プログラム側で特定の拡張子を付加してファイル読込み関数に渡す処理を考えます。この場合、攻撃者が入力データの末尾にナル文字を付加すると、プログラム側で付加した拡張子が無効化されてしまいます。ファイルを開く関数は、ナル文字の位置を文字列の終わりとみなし、その後ろに付けた拡張子を読まないからです。その結果、本来は読み込ませるつもりのないファイルが読み込まれるおそれがあります。

```
プログラムの意図： [入力されたファイル名] + ".txt"  → .txt ファイルだけを開く
ナル文字の混入時： [ファイル名] [\0] ".txt"
                                 ↑ open などはここで文字列が終わったと解釈し、".txt" を無視する
```

こうした攻撃を防ぐには、開発者は、入力データに不正な文字が含まれていないかを確認すべきです。含まれていた場合は、エスケープ処理やエラー処理を行う必要があります。C で書く場合、ネットワークやファイルから「長さ付き」で受け取ったデータについては、受け取った長さと `strlen` の結果が一致するか（途中にナル文字がないか）を確かめるのが実装上の定石です。

```c
/* 修正前：受信した len バイトの途中にナル文字があっても気づかない */
void open_doc(const char *name, size_t len)
{
    char path[256];
    snprintf(path, sizeof(path), "%s.txt", name);
    /* ... fopen(path, "r") ... */
}

/* 修正後：途中のナル文字と、許可しない文字を拒否してから使う */
int open_doc(const char *name, size_t len)
{
    char path[256];
    if (len == 0 || memchr(name, '\0', len) != NULL) {
        return -1;                          /* 途中にナル文字を含む入力は拒否する */
    }
    for (size_t i = 0; i < len; i++) {      /* 英数字だけを許可する（ホワイトリスト方式） */
        if (!isalnum((unsigned char)name[i])) {
            return -1;
        }
    }
    snprintf(path, sizeof(path), "%.*s.txt", (int)len, name);
    /* ... fopen(path, "r") ... */
    return 0;
}
```

**②の性質（末尾にナル文字を付ける）が招く問題**

また、上記②の性質をもつ関数を使用する際は、開発者は格納先バッファのサイズに注意すべきです。格納する文字列の長さに加えて、ナル文字分（1バイト）の領域が必要です。これを忘れると、ナル文字1バイトが隣の領域にはみ出す **off-by-one**（1つずれ）のBOFが発生する可能性が高まります。

```c
/* 修正前：8文字の ID を格納するのに 8 バイトしか確保していない */
char id[8];
strcpy(id, "ABCD1234");      /* 8文字＋ナル文字＝9バイトを書き込み、1バイトはみ出す */

/* 修正後：文字数＋1 を確保する */
char id[8 + 1];
snprintf(id, sizeof(id), "%s", "ABCD1234");
```

**C以外の言語でも起きる**

なお、Perlの文字列処理ではナル文字を特別に扱わないため、上記のような問題は発生しにくいとされます。それでも安心はできません。例えば、`open` 関数など外部の関数（C言語で実装されたシステムコールなど）を呼び出す処理では、渡された文字列がナル文字の位置で切り捨てられる場合があります。このため、Perlでも同様の問題が生じ得ます（新しいバージョンのPerlでは、ファイル名にナル文字を含む `open` を失敗させる対策が入っていますが、開発者が入力を検査すべきことに変わりはありません）。

> **ナルバイト攻撃(Null Byte Injection)**
> 入力データ中にナル文字(`%00` など)を埋め込み、文字列の終端位置をずらすことで、拡張子チェックやパス制限などのセキュリティチェックを回避する攻撃手法である。C言語で実装された下位層の関数を呼び出すスクリプト言語やWebアプリケーションでも問題となる。

### 1.4 その他の文字 ― 区切り文字も意味をもつ

ナル文字以外にも、関数の仕様によって文字列の区切りや終端を示す文字には十分な注意が必要です。代表的なものを次に示します。

| 文字 | 16進 | エスケープ表記 | URLエンコード | どこで意味をもつか |
| --- | --- | --- | --- | --- |
| 空白文字 | `0x20` | `\s`（正規表現） | `%20` | `scanf` の `%s` は空白で読込みを終える。シェルは空白で引数を区切る |
| 改行文字 | `0x0a` | `\n` | `%0a` | `fgets` は改行で読込みを終える。ログやHTTPヘッダでは行の区切りになる |
| タブ | `0x09` | `\t` | `%09` | `scanf` の `%s` やシェルの区切りになる |

開発者は、入力値を別の関数や別のプログラム（シェル、ログ、HTTPヘッダなど）に渡すとき、「受け取り側でどの文字が区切りとして解釈されるか」を確認し、許可しない文字はエラーにすべきです。たとえばログに書く値に改行文字が混入すると、攻撃者は偽のログ行を差し込めます（第7章 7.8 のログの完全性の話につながります）。

## 2. 文字列操作関数の脆弱性と対策 ― 修正前と修正後

この節から、BOF攻撃の標的となる可能性の高い主な関数について、その基本的な仕様と対策を、①形式と機能 → ②セキュリティ上の留意点 → ③修正前のコード → ④代替関数の形式と修正後のコード、の順に解説します。どの関数も、例題は `char buf[128];` という128バイトの配列を使います。

### 2.1 ① gets関数 → fgets関数

**gets関数の形式及び機能概要**

```c
char *gets(char *dest);
```

`gets` 関数は、標準入力からユーザ入力データを読み取り、`dest` が指す配列に格納します。読取りは、ファイルの終わり又は改行文字を見つけるまで続きます。読み取った改行文字は捨て、配列に格納した文字の末尾にナル文字を付加します。

**セキュリティ上の留意点**

`gets` 関数は、格納先バッファの境界チェックをまったく行わないため、非常に危険です。引数に `dest` の大きさを渡す手段がないので、どれほど注意深く使っても安全にはなりません。BOFを引き起こす可能性が最も高い関数といえます。対策としては、開発者は、バッファに書き込むサイズを指定できる `fgets` 関数で代用すべきです。

**gets関数の使用例（修正前）**

```c
void func()
{
    char buf[128];

    gets(buf);   /* 入力データ(ナル文字を含む)のサイズがbufを超えるとBOFが発生! */
}
```

**対策の実施例：fgets関数の形式及び機能概要**

```c
char *fgets(char *dest, int n, FILE *stream);
```

`fgets` 関数は、`stream` が指すストリームから文字列を読み取り、`dest` が指す配列に格納します。読み取る文字数の最大値は `n-1` です。改行文字を読み取ったとき、又はファイルの終わりを検出したときに読取りを終了し、最後に格納した文字の後にナル文字を付加します。

なお、`gets` 関数とは異なり、`fgets` 関数は読み取った改行文字も配列に格納します。

**fgets関数による代用例（修正後）**

```c
void func()
{
    char buf[128];

    fgets(buf, sizeof(buf), stdin);   /* 最大でもbufのサイズ-1バイト分しか格納されず、
                                         ナル文字を加えてもbufのサイズを超えないため、
                                         BOFは発生しない */
}
```

実務では、開発者は戻り値（読込み失敗やファイルの終わりでは `NULL`）を確認し、残った改行文字を取り除き、長すぎて途中で切れた行を検出する処理まで書くべきです。切れた残りが「次の行」として読まれると、入力の解釈がずれるからです。

```c
/* 修正後（実務向け）：失敗・改行・切捨てをすべて扱う */
int read_line(char *buf, size_t size)
{
    if (fgets(buf, (int)size, stdin) == NULL) {
        return -1;                              /* 読込み失敗またはファイルの終わり */
    }
    size_t len = strcspn(buf, "\n");            /* 改行文字の位置を探す */
    if (buf[len] == '\n') {
        buf[len] = '\0';                        /* 改行文字を取り除く */
    } else if (len == size - 1) {
        return -2;                              /* 行が長すぎて途中で切れた。エラーとして扱う */
    }
    return 0;
}
```

> **補足**
> `gets` 関数はその危険性から、C99で非推奨とされ（正確には2007年のC99の正誤表 TC3 で非推奨）、C11規格では標準ライブラリから削除された。現在の開発では使用すべきではない。C11の附属書K(Annex K)では、代替として `gets_s` 関数が定義されている。ただし附属書Kは処理系が任意に実装する部分で、Visual C++ 以外の主要な処理系（glibc など）は対応していないため、移植性が必要なコードでは `fgets` を使うのが一般的である。

### 2.2 ② strcpy関数 → strncpy関数

**strcpy関数の形式及び機能概要**

```c
char *strcpy(char *dest, const char *src);
```

`strcpy` 関数は、`src` が指す配列を、終端のナル文字も含めて `dest` が指す配列に格納します。

**セキュリティ上の留意点**

`strcpy` 関数は、書込み先バッファのサイズを考慮しません。そのため、入力データのサイズを明示的に制限していない場合はBOFが発生する可能性が非常に高く、危険です。

なお、ナル文字も `dest` に格納されるため、`dest` にはその分のサイズを確保しておく必要があります。

この問題への対策は、開発者が、バッファに書き込むサイズを指定できる `strncpy` 関数で代用することです（下の補足のとおり、現在は `strncpy` 単独では不十分とされます）。

**strcpy関数の使用例（修正前）**

```c
void func(const char *data)
{
    char buf[128];

    strcpy(buf, data);   /* data(ナル文字を含む)のサイズがbufを超えるとBOFが発生! */
}
```

**対策の実施例：strncpy関数の形式及び機能概要**

```c
char *strncpy(char *dest, const char *src, size_t n);
```

`strncpy` 関数は、`src` が指す配列から `n` 個以下の文字を、`dest` が指す配列に格納します（ナル文字に続く文字は格納しません）。動作は次のとおりです。

- `src` が指す配列の先頭から `n` バイト以内にナル文字がない場合、格納された文字列はナル文字で終わらない。
- `src` が指す文字列が `n` 文字より短い場合、`dest` に `src` の内容を格納した後、全体で `n` 文字になるまでナル文字を書き込む。

**strncpy関数による代用例（修正後）**

```c
void func(const char *data)
{
    char buf[128];

    memset(buf, 0, sizeof(buf));            /* bufをクリアする */
    strncpy(buf, data, sizeof(buf) - 1);    /* ナル文字の1バイト分を確保するため、
                                               bufのサイズ-1バイト分しか格納しない */
}
```

開発者は、あらかじめ `buf` をナル文字でクリアしておき、かつ `sizeof(buf)-1` バイトまでしか格納しないようにします。これにより、末尾は必ずナル文字で終端され、BOFは発生しません。

> **補足**
> `strncpy` 関数は、上記のとおり終端のナル文字が保証されない点に注意が必要である。`memset` による初期化を行わない場合は、`buf[sizeof(buf) - 1] = '\0';` のように明示的に終端処理を行う。

> **補足：strncpy の評価の変化**
> 以前は「`strcpy` の代わりに `strncpy` を使えば安全」と説明されることが多かったが、現在は、終端の `'\0'` を保証しないために別のバグ（文字列の終わりが見つからず、後続の `strlen` や `printf` が隣のメモリまで読んでしまう）を生む点、および長すぎる入力を黙って切り捨てるため業務上の誤り（途中で切れたファイル名やIDをそのまま使う）を生む点が問題視されている。現在の推奨は、①コピーの前に `strlen(data) >= sizeof(buf)` を検査してエラーにする、②コピーには `snprintf(buf, sizeof(buf), "%s", data)` や `strlcpy`（BSD 由来。glibc は 2.38 以降で提供）を使う、の組合せである（第2章 2.3 の7.3節で見た修正例と同じ形）。

```c
/* 現在推奨される形：長さを検査してからコピーする */
int func(const char *data)
{
    char buf[128];

    if (strlen(data) >= sizeof(buf)) {
        return -1;                          /* 切り捨てずにエラーとして扱う */
    }
    snprintf(buf, sizeof(buf), "%s", data);
    return 0;
}
```

### 2.3 ③ strcat関数 → strncat関数

**strcat関数の形式及び機能概要**

```c
char *strcat(char *dest, const char *src);
```

`strcat` 関数は、`src` が指す文字列（終端のナル文字を含む）を、`dest` が指す文字列の末尾に連結します。`src` の先頭の文字が、`dest` の末尾のナル文字を置き換えます。

**セキュリティ上の留意点**

`strcat` 関数は、`strcpy` 関数と同様に、書込み先バッファのサイズを考慮しません。そのため、連結後の文字列のサイズを明示的に制限していない場合はBOFが発生する可能性が非常に高く、危険です。

なお、連結後に付加されるナル文字も `dest` に格納されるため、`dest` にはその分のサイズを確保しておく必要があります。

この問題への対策は、開発者が、バッファに書き込むサイズを指定できる `strncat` 関数で代用することです。

**strcat関数の使用例（修正前）**

```c
void func(const char *data)
{
    char buf[128];

    /* (bufには何らかの文字列が格納済みとする) */
    strcat(buf, data);   /* bufに格納されている文字列のサイズ+data(ナル文字を含む)の
                            サイズがbufを超えるとBOFが発生! */
}
```

**対策の実施例：strncat関数の形式及び機能概要**

```c
char *strncat(char *dest, const char *src, size_t n);
```

`strncat` 関数は、`src` が指す配列から `n` 個以下の文字を、`dest` が指す配列の最後に付加します（ナル文字及びナル文字に続く文字は格納しません）。`src` の先頭の文字は `dest` の末尾のナル文字を置き換え、連結後の文字列の末尾には終端を示すナル文字が付加されます。したがって、`dest` には「格納済みの文字サイズ（`strlen(dest)`）＋ `n` ＋ 1」のサイズを確保しておく必要があります。

**strncat関数による代用例（修正後）**

```c
void func(const char *data)
{
    char buf[128];

    /* (bufには何らかの文字列が格納済みとする) */
    strncat(buf, data, sizeof(buf) - strlen(buf) - 1);
        /* bufの残り領域から終端ナル文字の1バイトを除いたサイズ分しか連結しない */
}
```

開発者は、第3引数に「`buf` のサイズ − 格納済みの文字列長 − 1」を指定します。これにより、連結後に終端ナル文字を加えても `buf` のサイズを超えず、BOFは発生しません。

```
buf（128バイト）の使われ方
[ 格納済み strlen(buf) バイト ][ 連結できる残り ][ '\0' 1バイト ]
 ←────────── sizeof(buf) = 128 ──────────────────────────────→
 第3引数 = 128 − strlen(buf) − 1
```

> **注意**
> `strncat` 関数の第3引数は「連結する最大文字数」であり、「書込み先バッファ全体のサイズ」ではない。`sizeof(buf)` をそのまま指定する誤用が多いため注意する。

```c
/* よくある誤用：第3引数にバッファ全体の大きさを渡している */
strncat(buf, data, sizeof(buf));                    /* 格納済みの分だけはみ出しうる */

/* 正しい指定 */
strncat(buf, data, sizeof(buf) - strlen(buf) - 1);
```

なお、`buf` が初期化されておらずナル文字を含まない場合、`strlen(buf)` 自体がバッファの外まで読んでしまいます。開発者は、連結の前に `buf` が必ずナル文字で終端されていることを保証すべきです。

### 2.4 ④ sprintf関数 → 精度の指定／snprintf関数

**sprintf関数の形式及び機能概要**

```c
int sprintf(char *dest, const char *format, ...);
```

`sprintf` 関数は、`format` に続く実引数を書式 `format` に従って変換し、`dest` が指す配列に格納します。格納された文字列の末尾には、終端を示すナル文字を付加します。

**セキュリティ上の留意点**

`sprintf` 関数は、書込み先バッファのサイズを考慮しません。そのため、`format` に続く実引数のサイズを明示的に制限していない場合はBOFが発生する可能性が高く、非常に危険です。数値の `%d` でも、`int` の最小値 `-2147483648` は11文字になるため、「数値だから短い」という思い込みは通用しません。

この問題への対策は次のいずれかです。

- 開発者は、バッファに格納する最大文字数を指定できる `snprintf` 関数で代用する
- 開発者は、`format` 内で**精度**（precision）を指定する（`s` 変換の場合、実引数から格納する文字の最大長（バイト数）を指定することになる）

> **精度(precision)**
> 書式指定における精度は、変換指定子によって意味が異なる。
> - `d`、`i`、`o`、`u`、`x`、`X` 変換:出力する数字の最小の桁数
> - `e`、`E`、`f`、`F` 変換:小数点文字の後ろに出力する数字の個数
> - `g`、`G` 変換:最大の有効桁数
> - `s` 変換:書き込む最大のバイト数
>
> 精度は、ピリオド(`.`)の後に10進整数で指定する(例:`%.126s`)。

| 書式 | 実引数 | 出力 | 精度の意味 |
| --- | --- | --- | --- |
| `%.5d` | `42` | `00042` | 最小の桁数 |
| `%.2f` | `3.14159` | `3.14` | 小数点以下の桁数 |
| `%.3g` | `3.14159` | `3.14` | 最大の有効桁数 |
| `%.3s` | `"example"` | `exa` | 書き込む最大のバイト数 |

**sprintf関数の使用例（修正前）**

```c
void func(const char *data)
{
    char buf[128];

    sprintf(buf, "%s\n", data);   /* data+改行文字+ナル文字のサイズがbufを超えると
                                     BOFが発生! */
}
```

**対策の実施例1：精度を指定した例（修正後）**

```c
void func(const char *data)
{
    char buf[128];

    sprintf(buf, "%.126s\n", data);   /* dataからは最大126文字しか格納されない */
}
```

開発者が `%` と `s` の間に `.126` を指定することにより、`data` からは最大126文字までしか格納されません。これに改行文字（1バイト）と終端ナル文字（1バイト）を加えても `buf` のサイズ（128バイト）を超えないため、BOFは発生しません。ただし、書式を変更したり `buf` の大きさを変えたりすると「126」も手で直す必要があり、直し忘れがBOFを再発させます。保守性の面では次の `snprintf` のほうが優れています。

**対策の実施例2：snprintf関数の形式及び機能概要**

```c
int snprintf(char *dest, size_t n, const char *format, ...);
```

`snprintf` 関数は、`format` に続く実引数を書式 `format` に従って変換し、`dest` が指す配列に最大 `n-1` 文字（バイト）を格納します。格納された文字列の末尾には、終端を示すナル文字を付加します。

**snprintf関数による代用例（修正後）**

```c
void func(const char *data)
{
    char buf[128];

    snprintf(buf, sizeof(buf), "%s\n", data);
}
```

開発者は、第2引数に `sizeof(buf)` を指定します。この値はナル文字を含めた書込み先の大きさであり、`snprintf` は書式変換後の文字を最大 `sizeof(buf)-1` 文字までしか格納しません。これにより、ナル文字を加えても `buf` のサイズを超えないため、BOFは発生しません。（原本では第2引数を「格納する最大の文字数」と説明していましたが、正確には「ナル文字を含む書込み先の大きさ」で、格納される文字数はその−1です。）

> **補足**
> `snprintf` 関数の戻り値は、バッファサイズの制限がなかった場合に書き込まれるはずだった文字数(終端ナル文字を除く)である。戻り値が `n` 以上であれば出力が切り捨てられたことを意味するため、必要に応じて戻り値を確認し、切捨てを検出するとよい。なお、変換に失敗した場合は負の値が返る。

```c
/* 修正後（実務向け）：切捨てと変換エラーを検出する */
int ret = snprintf(buf, sizeof(buf), "%s\n", data);
if (ret < 0 || (size_t)ret >= sizeof(buf)) {
    return -1;                       /* 変換エラー、または途中で切れた */
}
```

## 3. 書式付き入力関数の脆弱性と対策 ― scanf系とその他の関数

2節の関数は「プログラム内のデータをコピーする」関数でした。この節の `scanf` 系は「外部から入ってくるデータを読む」関数で、攻撃者が入力の長さと中身を直接決められるため、より危険度が高い場面で使われます。

### 3.1 ⑤ scanf関数

**scanf関数の形式及び機能概要**

```c
int scanf(const char *format, ...);
```

`scanf` 関数は、標準入力からユーザ入力データを読み込み、書式 `format` に従って変換して、`format` に続く実引数が指すオブジェクトに格納します。

なお、`scanf` 関数の `%s` 変換では、入力データに空白、タブ、改行が現れると読込みを終了します（これらの文字は格納されません。1.4 で見た「区切り文字」の具体例です）。

**セキュリティ上の留意点**

`scanf` 関数は、書込み先バッファのサイズを考慮しません。そのため、実引数が指すオブジェクトに格納するデータのサイズを制限していない場合はBOFが発生する可能性が非常に高く、危険です。

この問題への対策は、開発者が `format` 内で格納する最大文字数を指定することです。

**scanf関数の使用例（修正前）**

```c
void func()
{
    char buf[128];

    scanf("%s", buf);   /* 入力データを書式指定に従って変換した文字列のサイズが
                           bufを超えるとBOFが発生する */
}
```

**対策の実施例：最大文字数を指定した例（修正後）**

```c
void func()
{
    char buf[128];

    scanf("%127s", buf);   /* 入力データは最大127文字までしか格納されない */
}
```

開発者が `%` と `s` の間に `127` を指定することにより、入力データは最大127文字までしか格納されません。これに終端ナル文字を加えても `buf` のサイズを超えないため、BOFは発生しません。

> **注意:scanf系関数における最大フィールド幅**
> `printf` 系関数の「精度」に相当する指定は、`scanf` 系関数(`scanf`、`sscanf`、`fscanf` など)では「**最大フィールド幅**」と呼ばれる。ピリオドを付けずに `%127s` のように指定する。`%.127s` のようにピリオドを付けた書式は `scanf` 系関数では正しい指定ではないため、注意すること。

| 関数の系統 | 長さを制限する指定 | 書き方 | 128バイトのバッファに対する値 |
| --- | --- | --- | --- |
| `printf` 系（`sprintf` など） | 精度 | `%.126s`（ピリオドあり） | 書式中の他の文字数とナル文字を引いた値 |
| `scanf` 系（`scanf`、`sscanf`、`fscanf` など） | 最大フィールド幅 | `%127s`（ピリオドなし） | 128 − 1（ナル文字分）＝127 |

`scanf` 系の戻り値は「正しく変換して格納できた項目の数」です。開発者は、戻り値が期待した項目数と一致するかを確認すべきです。一致しないのに処理を続けると、初期化されていない変数を使うことになります。

```c
/* 修正後（実務向け）：戻り値も確認する */
char name[128];
int  age;
if (scanf("%127s %d", name, &age) != 2) {
    return -1;                  /* 2項目とも読めなかった入力はエラーにする */
}
```

### 3.2 ⑥ sscanf関数

**sscanf関数の形式及び機能概要**

```c
int sscanf(const char *str, const char *format, ...);
```

`sscanf` 関数は、文字列 `str` に格納されたデータを書式 `format` に従って変換し、`format` に続く実引数が指すオブジェクトに格納します。

**セキュリティ上の留意点**

`sscanf` 関数は、書込み先バッファのサイズを考慮しません。そのため、実引数が指すオブジェクトに格納するデータのサイズを制限していない場合はBOFが発生する可能性が非常に高く、危険です。`str` がプログラム内部の文字列であっても、その中身が元をたどれば外部入力（HTTPリクエストの1行、設定ファイルの1行など）であることが多いため、開発者は「内部データだから安全」と判断すべきではありません。

この問題への対策は、開発者が `format` 内で格納する最大文字数（最大フィールド幅）を指定することです。

**sscanf関数の使用例（修正前）**

```c
void func(const char *str)
{
    char buf[128];

    sscanf(str, "%s", buf);   /* strを書式指定に従って変換した文字列のサイズが
                                 bufを超えるとBOFが発生! */
}
```

**対策の実施例：最大文字数を指定した例（修正後）**

```c
void func(const char *str)
{
    char buf[128];

    sscanf(str, "%127s", buf);   /* strからは最大127文字までしか格納されない */
}
```

開発者が `%` と `s` の間に `127` を指定することにより、`str` からは最大127文字までしか格納されません。これに終端ナル文字を加えても `buf` のサイズを超えないため、BOFは発生しません。

### 3.3 ⑦ fscanf関数

**fscanf関数の形式及び機能概要**

```c
int fscanf(FILE *fp, const char *format, ...);
```

`fscanf` 関数は、`fp` が指すファイルからの入力データを書式 `format` に従って変換し、`format` に続く実引数が指すオブジェクトに格納します。

**セキュリティ上の留意点**

`fscanf` 関数は、書込み先バッファのサイズを考慮しません。そのため、実引数が指すオブジェクトに格納するデータのサイズを制限していない場合はBOFが発生する可能性が非常に高く、危険です。画像ファイルや文書ファイルのように、利用者が外部から入手したファイルを読むプログラムでは、ファイルの中身は攻撃者が自由に作れるものとして扱うべきです（「試験に出た」の画像処理プログラムの題材がこの型です）。

この問題への対策は、開発者が `format` 内で格納する最大文字数（最大フィールド幅）を指定することです。

**fscanf関数の使用例（修正前）**

```c
void func()
{
    FILE *fp;
    char buf[128];

    /* (fpはオープン済みとする) */
    fscanf(fp, "%s", buf);   /* fpが指すファイルのデータを書式指定に従って変換した
                                文字列のサイズがbufを超えるとBOFが発生! */
}
```

**対策の実施例：最大文字数を指定した例（修正後）**

```c
void func()
{
    FILE *fp;
    char buf[128];

    /* (fpはオープン済みとする) */
    fscanf(fp, "%127s", buf);   /* ファイルのデータは最大127文字までしか格納されない */
}
```

開発者が `%` と `s` の間に `127` を指定することにより、`fp` が指すファイルのデータは最大127文字までしか格納されません。これに終端ナル文字を加えても `buf` のサイズを超えないため、BOFは発生しません。

### 3.4 その他の関数 ― 1文字ずつ読むループにも境界チェックを

上記の関数以外で、BOF攻撃への対策を十分に考慮すべき関数を次の表に示します。

**表:BOF攻撃への対策を考慮すべきその他の関数**

| 関数 | 危険度 | 対策方法 |
|---|---|---|
| `vfscanf`<br>`vscanf`<br>`vsscanf` | 高 | 最大文字数(最大フィールド幅)を指定するか、独自にデータサイズのチェックを行う |
| `vsprintf` | 高 | `vsnprintf` で代用するか、精度を指定する |
| `getchar`<br>`fgetc`<br>`getc` | 中 | これらの関数をループ内で使用して配列に格納している場合は、バッファ境界をチェックする |

> **補足**
> `getchar`、`fgetc`、`getc` は1文字ずつ読み取る関数であり、関数自体がBOFを引き起こすことはない。しかし、ループ内で読み取った文字を配列に順次格納する処理では、格納位置(添字)がバッファの範囲内にあるかを毎回確認しないと、BOFが発生する。

修正前と修正後を比べると、違いはループの条件に「添字がバッファの大きさ−1未満か」を加えるだけです。なお `getchar` の戻り値は `int` 型で受けます。`char` で受けると、ファイルの終わりを示す `EOF`（多くの処理系で −1）と値 `0xFF` の文字を区別できなくなるためです。

```c
/* 修正前：改行が来るまで無制限に格納する */
char buf[128];
int  c, i = 0;
while ((c = getchar()) != '\n' && c != EOF) {
    buf[i++] = (char)c;              /* i が 128 以上になっても書き続ける */
}
buf[i] = '\0';

/* 修正後：ナル文字の1バイトを残して止める */
char buf[128];
int  c;
size_t i = 0;
while ((c = getchar()) != '\n' && c != EOF) {
    if (i >= sizeof(buf) - 1) {
        return -1;                   /* 長すぎる入力はエラーにする（または読み捨てる） */
    }
    buf[i++] = (char)c;
}
buf[i] = '\0';
```

`vsprintf` を `vsnprintf` に置き換える例も示します。ログ出力などの自作の可変引数関数で `vsprintf` が使われていることがよくあります。

```c
/* 修正前 */
void log_msg(const char *fmt, ...)
{
    char buf[256];
    va_list ap;
    va_start(ap, fmt);
    vsprintf(buf, fmt, ap);                  /* 展開後の長さを検査しない */
    va_end(ap);
}

/* 修正後 */
void log_msg(const char *fmt, ...)
{
    char buf[256];
    va_list ap;
    va_start(ap, fmt);
    vsnprintf(buf, sizeof(buf), fmt, ap);    /* 最大 sizeof(buf)-1 文字で止まる */
    va_end(ap);
}
```

### 3.5 安全な代替関数の比較表

ここまでの内容を、開発者がコードを書くとき・レビューするときに引ける形でまとめます。

| 危険な関数 | なぜ危険か | 代替（修正後の書き方） | 代替関数を使うときの注意 |
| --- | --- | --- | --- |
| `gets(buf)` | 長さを指定する手段がない（C11で削除） | `fgets(buf, sizeof(buf), stdin)` | 改行文字が残る。戻り値 `NULL` の確認、切捨ての検出 |
| `strcpy(d, s)` | 書込み先の大きさを検査しない | 事前に `strlen(s) >= sizeof(d)` を検査し、`snprintf(d, sizeof(d), "%s", s)`。`strncpy(d, s, sizeof(d)-1)`＋終端処理、`strlcpy` | `strncpy` は終端のナル文字を保証しない |
| `strcat(d, s)` | 連結後の長さを検査しない | `strncat(d, s, sizeof(d) - strlen(d) - 1)`、`strlcat` | 第3引数は「残りの空き−1」で、全体の大きさではない |
| `sprintf(d, fmt, ...)` | 書式展開後の長さを検査しない | `snprintf(d, sizeof(d), fmt, ...)`、精度指定 `%.126s` | 戻り値が負または `sizeof(d)` 以上なら失敗・切捨て |
| `vsprintf` | 同上 | `vsnprintf`、精度指定 | 同上 |
| `scanf("%s", buf)` など `scanf` 系 | 幅指定がないと長さ無制限で格納する | `scanf("%127s", buf)`（最大フィールド幅）、または `fgets` で1行読んでから解析 | 幅はバッファの大きさ−1。ピリオドは付けない。戻り値で変換項目数を確認 |
| `getchar`／`fgetc`／`getc` のループ | 関数自体は安全だが、格納先の添字を検査しないとあふれる | ループ条件に `i < sizeof(buf) - 1` を加える | 戻り値は `int` で受けて `EOF` と比較する |
| （Windows／附属書K） | 同上 | `strcpy_s`、`strcat_s`、`sprintf_s`、`gets_s` など | C11 の附属書K由来。対応状況は処理系によって異なる |

開発者がこの表を使うときの原則は、「代替関数に置き換えれば終わり」ではなく、**①入力の長さを先に検査してエラーにする、②書込みにも大きさを指定する、③戻り値で失敗と切捨てを確認する**の3点をそろえることです。①がないと、長すぎる入力が黙って切り捨てられ、途中で切れたファイル名やIDで処理が進むという別の欠陥になります。

## 4. BOF以外に開発者が作り込みやすい欠陥

危険な関数を置き換えても、C/C++にはまだ「言語が検査してくれない」箇所が残っています。この節では、第2章 2.3 の4節で攻撃の側から見た整数オーバフローと Use-After-Free を開発者の側から掘り下げ、あわせて書式文字列と競合状態の問題を扱います。いずれも CWE（共通脆弱性タイプ一覧）に番号が振られた代表的な欠陥です。

| 欠陥 | CWE | 何が検査されていないか | 損なわれる特性 |
| --- | --- | --- | --- |
| 整数オーバフロー／ラップアラウンド | CWE-190 | 演算結果が型の範囲に収まるか | 完全性・可用性（後続でBOF） |
| 書式文字列の問題 | CWE-134 | 書式に外部入力が混ざっていないか | 機密性（メモリ内容の漏えい）・完全性・可用性 |
| 解放済みメモリの使用（Use-After-Free） | CWE-416 | ポインタの指す先がまだ有効か | 完全性・可用性（任意コード実行に至りうる） |
| 二重解放（Double Free） | CWE-415 | 同じ領域を2回解放していないか | 同上 |
| 競合状態（TOCTOU） | CWE-367 | 検査した対象と使用する対象が同じか | 機密性・完全性（権限外のファイル操作） |

### 4.1 整数オーバフローの確認 ― 演算の「前に」検査する

第2章 2.3 の4.2節で見たとおり、要素数×要素サイズのような**サイズ計算**が桁あふれすると、小さなバッファが確保され、後続のコピーでBOFになります。開発者が覚えておくべきなのは、「演算した後で結果を検査しても手遅れ」という点です。桁あふれした後の値はもっともらしい小さな値になっているため、検査をすり抜けます。

**掛け算：上限を割り算で求めてから比べる**

```c
/* 修正前：count が大きいと count * sizeof(struct rec) が桁あふれする */
struct rec *p = malloc(count * sizeof(struct rec));

/* 修正後：掛ける前に上限を確認する（または calloc を使う） */
if (count > SIZE_MAX / sizeof(struct rec)) {
    return -1;
}
struct rec *p = malloc(count * sizeof(struct rec));
/* 別解：calloc(count, sizeof(struct rec)) は内部で桁あふれを検査する */
```

**足し算：引き算の形に変えて比べる**

```c
/* 修正前：off + len が桁あふれすると小さな値になり、範囲検査をすり抜ける */
if (off + len > total) {
    return -1;
}
memcpy(dst, src + off, len);

/* 修正後：桁あふれしない形に変形して検査する */
if (len > total || off > total - len) {
    return -1;
}
memcpy(dst, src + off, len);
```

**符号付きと符号なしの混在：負の長さが巨大な長さに化ける**

```c
/* 修正前：len は外部から受け取った int。負の値なら検査を通過してしまう */
int len = read_length_field();          /* 例：-1 */
if (len > (int)sizeof(buf)) {
    return -1;
}
memcpy(buf, src, len);                  /* -1 が size_t に変換され、非常に大きな値になる */

/* 修正後：長さは符号なし型で扱い、下限と上限の両方を確認する */
int raw = read_length_field();
if (raw < 0 || (size_t)raw > sizeof(buf)) {
    return -1;
}
size_t len = (size_t)raw;
memcpy(buf, src, len);
```

**引き算：0 から 1 を引くと最大値になる**

```c
/* 修正前：len が 0 だと len - 1 が SIZE_MAX になり、範囲外を書き換える */
buf[len - 1] = '\0';

/* 修正後：0 の場合を先に除く */
if (len == 0) {
    return -1;
}
buf[len - 1] = '\0';
```

符号なし整数（`unsigned int`、`size_t`）の桁あふれは「最大値の次は0に戻る」と規格で定められていますが、符号付き整数（`int`）の桁あふれは**未定義動作**です。未定義動作は「何が起きても規格上は正しい」という意味なので、最適化を行うコンパイラは「`a + b < a` が真になることはない」と判断して、開発者が書いた検査そのものを削除することがあります。開発者は、符号付き整数については「演算の前に範囲を確認する」書き方を守り、使える環境では GCC/Clang の `__builtin_add_overflow` や C23 の `<stdckdint.h>`（`ckd_add`、`ckd_mul` など）のような、桁あふれを検出できる演算関数を使うべきです。

```c
/* C23：桁あふれしたら true を返す */
#include <stdckdint.h>
size_t total;
if (ckd_mul(&total, count, sizeof(struct rec))) {
    return -1;
}
```

### 4.2 書式文字列の固定 ― 外部入力を「書式」にしない

`printf` 系関数は、第1引数（`sprintf` なら第2引数）の**書式文字列**の中にある `%` で始まる変換指定を解釈し、その数だけ後続の実引数を取り出します。開発者が外部から受け取った文字列をそのまま書式として渡すと、入力中の `%` が変換指定として解釈されます。関数は渡されていない実引数を探してスタック上の無関係な値を取り出すため、メモリの内容が出力に漏れたり（**機密性**）、書込みを行う変換指定によってメモリが書き換えられたり（**完全性**）、不正なアドレスを読んで異常終了したり（**可用性**）します。これが**書式文字列の脆弱性**（フォーマットストリング脆弱性、CWE-134）です。

この欠陥は、BOF対策として `snprintf` に置き換えたコードにも残ります。長さの問題ではなく、「データを命令（書式）として扱っている」問題だからです。この構図は、第2章 2.8 で見た SQLインジェクションや、本ノート5節の OSコマンドインジェクションと同じです。

```c
/* 修正前：msg を書式として解釈させている */
printf(msg);
fprintf(stderr, msg);
syslog(LOG_INFO, msg);
snprintf(buf, sizeof(buf), msg);

/* 修正後：書式は定数の "%s" に固定し、msg は「データ」として渡す */
printf("%s", msg);
fprintf(stderr, "%s", msg);
syslog(LOG_INFO, "%s", msg);
snprintf(buf, sizeof(buf), "%s", msg);
```

開発者が守るべき規則は1つで、「**書式文字列には文字列リテラル（定数）だけを使う**」です。`syslog` のように一見書式付きに見えない関数も `printf` 系と同じ書式を解釈するため、見落としに注意してください。

### 4.3 メモリ解放後のポインタの扱い ― ダングリングポインタを残さない

C/C++ では、`malloc`／`new` で確保したヒープ領域を、開発者が `free`／`delete` で解放します。解放した後もポインタ変数には元のアドレスが残っており、この**ダングリングポインタ**を使うと、すでに別の用途に再利用された領域を読み書きしてしまいます（**Use-After-Free**、CWE-416）。同じ領域を2回解放する**二重解放**（**Double Free**、CWE-415）は、メモリ管理の内部構造を壊します。第2章 2.3 の4.1節で見たとおり、Use-After-Free は任意コード実行に至りうる重大な欠陥です。

```c
/* 修正前：解放後のポインタを使い、エラー経路で二重に解放している */
char *p = malloc(64);
/* ... */
if (error) {
    free(p);
    log_error(p);       /* 解放済み領域を読んでいる（Use-After-Free） */
}
/* ... */
free(p);                /* error のときは2回目の解放になる（Double Free） */

/* 修正後：使い終わってから解放し、解放直後に NULL を代入する */
char *p = malloc(64);
if (p == NULL) {
    return -1;          /* 確保失敗の確認も忘れない */
}
/* ... */
if (error) {
    log_error(p);       /* 使ってから */
    free(p);            /* 解放し */
    p = NULL;           /* ダングリングポインタを残さない */
}
/* ... */
free(p);                /* free(NULL) は何もしないため、二重解放にならない */
p = NULL;
```

`p = NULL;` は有効な習慣ですが、それだけでは不十分な場合があります。同じ領域を指すポインタを別の変数や構造体のメンバにコピーしていると、`p` を `NULL` にしてもコピー側はダングリングポインタのまま残るからです。開発者は、「この領域を解放する責任をもつのはどの関数・どのオブジェクトか」（所有権）を設計時に1か所に決め、コードレビューで確認すべきです。C++ では、`std::unique_ptr`／`std::shared_ptr` などのスマートポインタや、デストラクタで自動的に解放する **RAII** の書き方を使うと、解放忘れ・二重解放・解放後の使用を言語の仕組みで減らせます。

```cpp
// C++：所有者が1つに決まり、スコープを抜けると自動で解放される
#include <memory>
auto buf = std::make_unique<char[]>(64);
// delete[] を書く必要がなく、二重解放も起きない
```

### 4.4 競合状態の回避 ― 「検査」と「使用」の間に隙間を作らない

**競合状態**（レースコンディション）とは、複数の処理が同じ資源（ファイル、共有メモリ、変数）を扱うとき、実行の順序やタイミングによって結果が変わってしまう欠陥です。セキュリティで特に問題になるのが **TOCTOU**（Time Of Check to Time Of Use、CWE-367）で、プログラムがファイルの属性や権限を「検査した時点」と、実際にそのファイルを「使用する時点」の間に隙間があるため、その間に攻撃者が対象をすり替える（たとえばファイルを別の重要ファイルへのシンボリックリンクに差し替える）と、検査を通過したまま別のファイルを操作させられる、というものです。第2章 2.3 の5節で見た setuid プログラムのように高い権限で動くプログラムで起きると、一般ユーザが本来書き込めないファイルを書き換えられます。

```c
/* 修正前：access で検査してから open するまでの間に、path の指す先が変わりうる */
if (access(path, W_OK) == 0) {          /* 検査（Time Of Check） */
    int fd = open(path, O_WRONLY);      /* 使用（Time Of Use） */
    /* ... */
}

/* 修正後：権限を利用者のものに落としてから、検査と使用を1回の open で行う */
if (seteuid(getuid()) != 0) {           /* 実行した利用者の権限に下げる */
    return -1;
}
int fd = open(path, O_WRONLY | O_NOFOLLOW);   /* OS が open の中で権限を検査する。
                                                  シンボリックリンクはたどらない */
if (fd < 0) {
    return -1;
}
struct stat st;
if (fstat(fd, &st) != 0 || !S_ISREG(st.st_mode)) {   /* 開いた「そのもの」を fd で検査する */
    close(fd);
    return -1;
}
```

考え方は、「名前（パス）で検査して名前で使う」のをやめ、**開いた結果（ファイル記述子）に対して検査する**ことです。名前は検査と使用の間に別の実体を指しうるが、ファイル記述子は開いた実体から変わらないからです。

一時ファイルの作成も TOCTOU の典型です。

```c
/* 修正前：名前を決めてから作るまでの間に、同じ名前のファイルやリンクを置かれうる */
char *name = tmpnam(NULL);              /* mktemp も同じ問題をもつ */
FILE *fp = fopen(name, "w");

/* 修正後：名前の決定と作成を一度に、排他的に行う */
char name[] = "/tmp/example-XXXXXX";
int fd = mkstemp(name);                 /* 既存ファイルがあれば作らない。権限は所有者のみ */
if (fd < 0) {
    return -1;
}
```

マルチスレッドのプログラムでも、共有する変数の「読む→判定する→書く」が分割されていると、同じ形の競合が起きます（例：残高を確認してから引き落とす処理を2つのスレッドが同時に行い、残高以上を引き落としてしまう）。開発者は、判定と更新をミューテックスなどの排他制御で1つの不可分な処理にまとめるべきです。排他制御の考え方は科目A-1の 4.2「記憶管理と同期・排他制御」で学んだセマフォと同じです。

```c
/* 修正後：確認と更新をロックの内側で行う */
pthread_mutex_lock(&lock);
if (balance >= amount) {
    balance -= amount;
}
pthread_mutex_unlock(&lock);
```

## 5. system関数使用における注意点 ― BOF対策をしても残る「入力の中身」の問題

### 5.1 system関数とOSコマンドインジェクション

`system` 関数は、C/C++のプログラム中からOSのコマンドプロセッサ（シェル）を呼び出し、引数として渡したコマンドを実行する関数です。非常に便利な機能ですが、開発者が引数として渡す文字列のチェックを十分に行わないと、重大な問題を引き起こす原因となります。特に、ユーザの入力データから `system` 関数に渡すコマンド文字列を編集する場合は、**OSコマンドインジェクション**の危険があるため細心の注意が必要です。

> **OSコマンドインジェクション**
> 外部から入力された文字列にシェルのメタ文字(`;`、`|`、`&` など)を含めることで、プログラムが意図していない任意のOSコマンドを実行させる攻撃である。ファイルの削除・改ざん、情報漏えい、マルウェアのダウンロードなど、深刻な被害につながる。

問題の根は、4.2 の書式文字列と同じく「データ（ファイル名）と命令（コマンド）が1本の文字列に混ざり、シェルがその区切りを解釈し直す」ことにあります。Webアプリケーションでの同じ攻撃は第2章 2.8 と第3章 3.6 で扱いました。被害の大きさは、コマンドを実行するプログラムの権限で決まります。

### 5.2 system関数の使用例と問題点

次に、ユーザ入力データ（コマンドライン引数）から `ls` コマンドを編集し、`system` 関数に引き渡すプログラムの例を示します（引数の数のチェック処理などは省略）。

**system関数の使用例（修正前）**

```c
int main(int argc, char *argv[])
{
    char cmdbuf[128];

    snprintf(cmdbuf, sizeof(cmdbuf), "ls %s", argv[1]);
    system(cmdbuf);

    return 0;
}
```

上記のような単純なプログラムに、ファイル名に続けて `; rm -rf *` という入力データが与えられたとします。この場合、シェルは `;` をコマンドの区切りと解釈するため、`ls ファイル名` コマンドに続いて `rm -rf` コマンドも実行され、カレントディレクトリの中身がすべて消されてしまう可能性があります。

```
ls ファイル名; rm -rf *
```

なお、この例では `snprintf` 関数を使用しているためBOFは発生しません。しかし、BOF対策を施していても、入力データの内容そのものをチェックしなければこのような問題が生じます。「長さの検査」と「中身の検査」は別の対策である、という点が本節の要点です。

### 5.3 対策方法

このような問題を防ぐには、開発者は、入力データ中に次のような文字が含まれていないかを徹底的にチェックし、含まれていた場合はエラー処理を行うべきです。

- ファイル名として許可されない文字（例えば `;`、`|`、`&` など）
- コマンドとして特別な意味をもつメタ文字

当然のことながら、それ以前に入力データの数や文字長などのチェックも行う必要があります。外部から受け取ったデータを処理する場合は、開発者は常にこうしたチェックを行わなければなりません。

> **補足:より安全な実装方針**
> - 禁止文字を列挙して排除する方式(**ブラックリスト方式**)よりも、許可する文字(英数字など)だけを受け付ける方式(**ホワイトリスト方式**)のほうが、チェック漏れが起きにくく安全である。
> - そもそもシェルを経由する `system` 関数の使用を避け、`execve` などシェルを介さずに引数を個別に渡せる関数を使用することも有効な対策である。
> - 可能であれば、外部コマンドを呼び出さずに、言語のライブラリ関数(ディレクトリ一覧であれば `opendir`/`readdir` など)で処理を実現することが望ましい。

3つの方針を、望ましい順に修正後のコードで示します。

**修正後1（最も望ましい）：外部コマンドを使わず、ライブラリ関数で処理する**

```c
#include <dirent.h>

int list_dir(const char *path)
{
    DIR *d = opendir(path);                 /* シェルを起動しないので、メタ文字は意味をもたない */
    if (d == NULL) {
        return -1;
    }
    struct dirent *e;
    while ((e = readdir(d)) != NULL) {
        printf("%s\n", e->d_name);          /* 書式は "%s" に固定（4.2） */
    }
    closedir(d);
    return 0;
}
```

**修正後2：シェルを介さず、引数を個別に渡す**

```c
#include <unistd.h>
#include <sys/wait.h>

int run_ls(const char *name)
{
    pid_t pid = fork();
    if (pid == 0) {
        char *const args[] = { "ls", "--", (char *)name, NULL };
        char *const envp[] = { "PATH=/usr/bin:/bin", NULL };
        execve("/bin/ls", args, envp);      /* name は1つの引数として渡され、; や | は解釈されない */
        _exit(127);
    }
    int status;
    waitpid(pid, &status, 0);
    return status;
}
```

`execve` はシェルを起動しないため、`name` にメタ文字が含まれていても単なる文字として `ls` に渡されます。ただし、`-` で始まる値はコマンドの**オプション**として解釈されうるため、開発者は `--`（ここから先はオプションではないという印）を前に置くか、`-` で始まる値を拒否すべきです。また、コマンドは絶対パス（`/bin/ls`）で指定し、環境変数 `PATH` を固定することで、別の場所に置かれた同名のプログラムを実行させられることを防ぎます。

**修正後3：どうしても `system` を使う場合は、ホワイトリストで検査してから渡す**

```c
static int is_safe_name(const char *s)
{
    size_t len = strlen(s);
    if (len == 0 || len > 64 || s[0] == '-') {
        return 0;                           /* 空・長すぎる・オプションに見える値は拒否 */
    }
    for (size_t i = 0; i < len; i++) {
        unsigned char c = (unsigned char)s[i];
        if (!(isalnum(c) || c == '.' || c == '_')) {
            return 0;                       /* 英数字と . _ 以外はすべて拒否（ホワイトリスト方式） */
        }
    }
    return 1;
}

int main(int argc, char *argv[])
{
    char cmdbuf[128];

    if (argc != 2 || !is_safe_name(argv[1])) {
        fprintf(stderr, "invalid file name\n");
        return 1;
    }
    snprintf(cmdbuf, sizeof(cmdbuf), "ls %s", argv[1]);
    system(cmdbuf);
    return 0;
}
```

| 方式 | 何を検査するか | 弱点 |
| --- | --- | --- |
| ブラックリスト方式 | `;`、`\|`、`&` など危険な文字を列挙して拒否する | シェルのメタ文字は多く（`` ` ``、`$`、`>`、`<`、改行など）、列挙漏れが起きやすい |
| ホワイトリスト方式 | 許可する文字（英数字など）以外をすべて拒否する | 業務上必要な文字を許可し忘れると正常な入力が通らない（安全側に倒れる） |
| シェルを介さない（`execve`） | 検査に頼らず、シェルの解釈そのものをなくす | オプションとして解釈される値（`-` 始まり）への配慮は残る |
| ライブラリ関数で代替 | 外部コマンドを呼ばない | 対応する関数がない処理もある |

加えて、システム管理者と開発者は、万一コマンドが注入されても被害を小さくするために、プログラムを必要最小限の権限の専用ユーザで動かすべきです（第5章 5.2「ホストの要塞化」の、アクセス権の設定と最小権限の考え方）。

## 6. 欠陥を見つける仕組み ― 警告・静的解析・規約・レビュー

ここまで見た欠陥は、注意深い開発者でも書いてしまいます。そこで組織は、人の注意力だけに頼らず、**コーディング規約で書き方を決め、コンパイラと静的解析ツールで機械的に検出し、コードレビューで人が確認し、テストで動かして確かめる**、という複数の関門を開発工程に組み込みます（第8章 8.1 の開発工程全体での位置づけ）。この節では、それぞれの関門で開発者が実際に目にするものを確認します。

### 6.1 コンパイラの警告 ― 最初の、最も安い関門

コンパイラは、危険な書き方の多くを警告として報告できます。ただし既定では表示されない警告が多いため、開発者はビルド設定で警告を有効にし、CI（継続的インテグレーション）では警告をエラーとして扱う（`-Werror`）ことで、警告を残したままのコードが取り込まれないようにすべきです。第2章 2.3 の3.6節で見た保護オプション（`-fstack-protector-strong`、`-D_FORTIFY_SOURCE=2`、PIE、NX）とあわせて指定します。

```
# Makefile の一部（GCC／Clang）
CFLAGS = -O2 -Wall -Wextra -Wformat=2 -Wformat-security -Wconversion -Wsign-conversion \
         -Werror -fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE
```

本ノートで見た修正前のコードをコンパイルすると、警告は次のように見えます（ファイル名・行番号は例）。

```
$ gcc -O2 -Wall -Wextra -Wformat-security -c example.c
example.c: In function 'func':
example.c:12:5: warning: format not a string literal and no format arguments [-Wformat-security]
   12 |     printf(msg);
      |     ^~~~~~
example.c:20:13: warning: comparison of integer expressions of different signedness: 'int' and 'size_t' {aka 'long unsigned int'} [-Wsign-compare]
example.c:31:5: warning: 'strcpy' writing 9 bytes into a region of size 8 overflows the destination [-Wstringop-overflow=]
example.c:40:20: warning: '%s' directive writing up to 255 bytes into a region of size 128 [-Wformat-overflow=]
example.c:47:5: warning: implicit declaration of function 'gets'; did you mean 'fgets'? [-Wimplicit-function-declaration]

$ gcc -o example example.o
/usr/bin/ld: example.o: warning: the `gets' function is dangerous and should not be used.
```

| 警告 | 対応する本ノートの節 | 開発者がとるべき修正 |
| --- | --- | --- |
| `format not a string literal ... [-Wformat-security]` | 4.2 書式文字列 | 書式を `"%s"` に固定する |
| `comparison of integer expressions of different signedness [-Wsign-compare]` | 4.1 符号の混在 | 長さを `size_t` で扱い、負の値を先に除く |
| `writing 9 bytes into a region of size 8 [-Wstringop-overflow=]` | 1.3 off-by-one | ナル文字分を確保する |
| `directive writing up to 255 bytes into a region of size 128 [-Wformat-overflow=]` | 2.4 sprintf | `snprintf` に置き換える |
| `the 'gets' function is dangerous` | 2.1 gets | `fgets` に置き換える |

Visual C++ では、危険な関数を使うと次の警告が出ます。

```
example.c(9): warning C4996: 'strcpy': This function or variable may be unsafe. Consider using strcpy_s instead. To disable this warning, use _CRT_SECURE_NO_WARNINGS.
```

開発者が警告を消すために `_CRT_SECURE_NO_WARNINGS` を定義するのは、警告の原因を直さずに知らせだけを止める行為です。コードレビューでは、この定義や `#pragma` による警告の抑止が追加されていないかを確認します。

`-D_FORTIFY_SOURCE` を指定してビルドしたプログラムは、コンパイル時に大きさが分かるバッファへのあふれを実行時にも検査し、検出すると次のように強制終了します。これは「BOFを乗っ取りではなく停止に変える」補助策であり、根本対策（コードの修正）の代わりにはなりません。

```
$ ./example
*** buffer overflow detected ***: terminated
Aborted (core dumped)
```

### 6.2 静的解析と動的解析 ― 指摘の見た目と扱い方

**静的解析**（静的アプリケーションセキュリティテスト、SAST）ツールは、プログラムを実行せずにソースコードを解析し、データの流れや関数の使い方から欠陥の候補を指摘します。代表的なツールの指摘は次のように見えます。

```
$ flawfinder example.c
example.c:9:  [5] (buffer) gets:
  Does not check for buffer overflows (CWE-120, CWE-20). Use fgets() instead.
example.c:15:  [4] (buffer) strcpy:
  Does not check for buffer overflows when copying to destination [MS-banned] (CWE-120).
  Consider using snprintf, strcpy_s, or strlcpy (warning: strncpy easily misused).
example.c:30:  [4] (shell) system:
  This causes a new program to execute and is difficult to use safely (CWE-78).
  try using a library call that implements the same functionality if available.

$ cppcheck --enable=warning example.c
example.c:22:9: error: Buffer is accessed out of bounds: buf [bufferAccessOutOfBounds]
example.c:41:12: error: Dereferencing 'p' after it is deallocated / released [deallocuse]
example.c:44:5: error: Memory pointed to by 'p' is freed twice. [doubleFree]

$ scan-build gcc -c example.c
example.c:41:12: warning: Use of memory after it is freed [unix.Malloc]
```

`flawfinder` のように危険な関数の使用箇所を一覧にするツールは、`[5]` などの危険度と CWE 番号、推奨される代替関数を示します。`cppcheck` や Clang の静的解析（`scan-build`）は、処理の流れを追って「この添字は範囲外になりうる」「このポインタは解放後に使われる」と指摘します。

**動的解析**は、プログラムを実際に動かして欠陥を検出する方法です。開発者は、テスト用のビルドで **AddressSanitizer**（`-fsanitize=address`）を有効にすると、範囲外アクセスや解放後の使用が起きた瞬間に、その種類と行番号を報告させられます。

```
$ gcc -g -fsanitize=address -o example example.c && ./example < test-input.txt
==12345==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7ffd5a3c1e80 ...
WRITE of size 1 at 0x7ffd5a3c1e80 thread T0
    #0 0x55d1c2a0b1f2 in func example.c:22
SUMMARY: AddressSanitizer: stack-buffer-overflow example.c:22 in func
```

大量の不正な形式の入力を自動生成して与える**ファジング**（第5章 5.3「脆弱性診断」）と AddressSanitizer を組み合わせると、静的解析では見つけにくい「特定の入力でだけ起きる」あふれを見つけられます。

| 手法 | いつ使うか | 得意なこと | 弱点 |
| --- | --- | --- | --- |
| コンパイラの警告 | ビルドのたび | 書式文字列、符号の混在、明らかなあふれ | 関数をまたぐデータの流れは追えない |
| 静的解析（SAST） | コミット時・CI | 危険な関数の網羅的な洗い出し、解放後の使用、範囲外の添字 | **誤検知**（実際には問題ない指摘）が出る |
| 動的解析（AddressSanitizer など） | 単体テスト・結合テスト | 実際に起きたあふれ・解放後の使用を確実に報告 | 実行された経路しか調べられない |
| ファジング | テスト工程・継続的に | 想定外の入力による異常の発見 | 時間がかかり、網羅性は保証されない |

静的解析の指摘は、そのまますべてが脆弱性とは限りません。開発者は、指摘ごとに「本当に問題か（真陽性）」「実際には起きない（誤検知）」を判定し、問題なら修正し、誤検知なら抑止する理由を記録に残すべきです。理由のない抑止は、後から本物の欠陥を隠す原因になります。

### 6.3 コーディング規約 ― CERT C の条文の書きぶり

**コーディング規約**（コーディング標準）は、組織やプロジェクトが「こう書く／こう書かない」を文章で定めたものです。開発者ごとの書き方のばらつきをなくし、レビューやツールの判定基準をそろえる役割があります。C/C++ のセキュリティ面では、米国カーネギーメロン大学の CERT/CC が公開している **CERT C コーディングスタンダード**が代表的で、JPCERT/CC が日本語訳を公開しています。ほかに、組込みシステムで広く使われる **MISRA C** があり、IPA も「セキュア・プログラミング講座」で書き方の指針を公開しています。

CERT C の各条文は、「識別子（分類の略号＋番号＋言語）」「規則の文」「違反コード例」「適合コード例」「リスク評価」という決まった形式で書かれています。たとえば本ノート1.3・2節の内容に対応する条文は、次のような構成です（説明用に要約しています）。

```
STR31-C. 文字列の格納領域は、文字データとナル終端文字を格納するのに十分な大きさを確保する
         （Guarantee that storage for strings has sufficient space for character data
          and the null terminator）

  違反コード例（Noncompliant Code Example）
      char buf[BUFFERSIZE];
      gets(buf);                 /* 入力の長さを制限できない */

  適合コード例（Compliant Solution）
      char buf[BUFFERSIZE];
      if (fgets(buf, sizeof(buf), stdin) == NULL) { /* エラー処理 */ }

  リスク評価
      深刻度 高 / 可能性 高 / 修正コスト 中 / 優先度 P18 / レベル L1
```

識別子の `STR` は文字列（string）の分類、`31` は分類内の番号、`-C` は C 言語向けの**規則**（rule）であることを表します（規則は守らなければならないもの。これとは別に、守ることが望ましい**推奨**〈recommendation〉もあります）。リスク評価の優先度は、深刻度・可能性・修正コストをそれぞれ1〜3で評価して掛け合わせた値（P1〜P27）で、組織は優先度の高い規則（レベル L1）から順に適用を徹底します。

本ノートの各節に対応する主な条文は次のとおりです。

| 識別子 | 規則の要旨 | 本ノートの節 |
| --- | --- | --- |
| STR31-C | 文字列の格納領域は、文字データとナル終端文字を格納するのに十分な大きさを確保する | 1.3、2節、3節 |
| MSC24-C | 非推奨関数や廃止予定の関数を使用しない（`gets` など） | 2.1 |
| ARR30-C | 範囲外を指すポインタや配列の添字を作成したり使用したりしない | 3.4、4.1 |
| INT30-C | 符号なし整数の演算結果がラップアラウンドしないようにする | 4.1 |
| INT32-C | 符号付き整数の演算がオーバーフローを引き起こさないようにする | 4.1 |
| FIO30-C | 書式文字列にユーザ入力を含めない | 4.2 |
| MEM30-C | 解放済みのメモリにアクセスしない | 4.3 |
| FIO45-C | ファイルにアクセスする際の TOCTOU 競合状態を避ける | 4.4 |
| ENV33-C | `system()` を呼び出さない | 5節 |

組織が社内規約を作るときは、CERT C をそのまま参照するだけでなく、自社の開発者が迷わないように、禁止する関数・代わりに使う関数・例外を認める手続きを条文の形で明記するのが一般的です。社内規約の書きぶりの例を示します。

```
株式会社Example C/C++ セキュアコーディング規約（抜粋）

第5条（文字列操作）
 1 開発者は、gets、strcpy、strcat、sprintf、vsprintf を使用してはならない。
 2 開発者は、文字列を固定長の配列に格納する前に、格納する文字列の長さが
   配列の大きさ－1以下であることを検査し、超える場合はエラーとして処理しなければならない。
 3 文字列の格納には snprintf を用い、第2引数には格納先の sizeof を指定する。
   戻り値が負又は第2引数以上の場合は、エラーとして処理しなければならない。
 （根拠：CERT C STR31-C、MSC24-C）

第6条（書式文字列）
 開発者は、printf 系関数及び syslog の書式文字列に、文字列リテラル以外を指定してはならない。
 （根拠：CERT C FIO30-C）

第9条（外部コマンドの実行）
 1 開発者は、system 及び popen を使用してはならない。
 2 業務上やむを得ず外部コマンドを実行する場合は、execve 系関数を用いて絶対パスで指定し、
   セキュリティ担当者の承認を得て、承認記録をコードレビュー記録に添付しなければならない。
 （根拠：CERT C ENV33-C）

第12条（警告と静的解析）
 1 製品のビルドは、-Wall -Wextra -Wformat-security を指定し、警告をエラーとして扱う。
 2 静的解析ツールの指摘を抑止する場合は、抑止の理由をソースコードのコメントと
   レビュー記録の両方に残さなければならない。
```

条文には「誰が（開発者は）」「何を（どの関数を）」「どうする（使用してはならない／検査しなければならない）」と、「根拠（どの規則に基づくか）」が書かれています。科目Bで「規約にどのような規定を追加すべきか」を問われたときも、この形で答えると採点者に伝わります。

### 6.4 コードレビューのチェックリスト

**コードレビュー**は、作成者以外の開発者がソースコードを読んで欠陥を探す活動です。ツールが見落とす「設計上の意図との食い違い」（たとえば、この長さの上限は業務仕様と合っているか、このファイルはどの権限で開かれるべきか）は、人が読まないと見つかりません。レビューの品質を担当者の経験に左右させないために、組織はチェックリストを用意します。本ノートの内容をまとめたチェックリストの例を示します。

| No. | 観点 | 確認項目 | 不適合の例 |
| --- | --- | --- | --- |
| 1 | 危険な関数 | `gets`、`strcpy`、`strcat`、`sprintf`、`vsprintf` を使っていないか | `strcpy(buf, data);` |
| 2 | 境界チェック | 外部入力の長さを、格納先の大きさ−1と比べて検査しているか。超えたときはエラーにしているか | 長さを検査せずに `strncpy` で切り捨てている |
| 3 | 終端文字 | 格納先にナル文字1バイト分の領域があるか。`strncpy` の後に終端処理をしているか | `char id[8]` に8文字を格納 |
| 4 | 書式付き入力 | `scanf` 系の `%s` に最大フィールド幅（`%127s`）があるか。戻り値を確認しているか | `scanf("%s", buf);` |
| 5 | ループでの格納 | 1文字ずつ格納するループに、添字の上限の条件があるか | `while (c != '\n') buf[i++] = c;` |
| 6 | 整数演算 | サイズ計算の掛け算・足し算の**前に**桁あふれを確認しているか。長さは符号なし型か | `malloc(count * size)` |
| 7 | 書式文字列 | `printf` 系・`syslog` の書式は文字列リテラルか | `printf(msg);` |
| 8 | メモリ管理 | `malloc` の戻り値を確認しているか。解放後に `NULL` を代入しているか。解放の責任者は1か所か | `free(p);` の後に `p` を使用 |
| 9 | 競合状態 | 名前で検査して名前で使っていないか。一時ファイルは `mkstemp` で作っているか | `access()` の後に `open()` |
| 10 | 外部コマンド | `system`／`popen` を使っていないか。使う場合、入力をホワイトリストで検査しているか | `system(cmdbuf);` に外部入力を含める |
| 11 | ナル文字・区切り文字 | 外部入力の途中にナル文字や改行文字が含まれる場合を拒否しているか | 拡張子の付加だけで種類を制限 |
| 12 | 警告・解析 | 警告の抑止（`_CRT_SECURE_NO_WARNINGS`、`#pragma`）や解析ツールの抑止に理由が書かれているか | 理由なしの抑止 |

レビューアは、不適合を見つけたら「どの行が・何を検査していないか・どう直すべきか」を指摘として記録し、作成者が修正した後に再確認します。指摘の件数と種類を集計して、規約やチェックリストの見直し、開発者の教育に反映するのが、組織としての改善の流れです。

### 6.5 関門の全体像と、言語の選択

| 関門 | 誰が | 何のために | 何をするか |
| --- | --- | --- | --- |
| コーディング規約 | 組織（品質・セキュリティ担当） | 書き方のばらつきをなくし、判定基準をそろえるため | CERT C などを基に禁止事項・代替手段・例外手続きを定める |
| コンパイラの警告 | 開発者 | 最も早く安く欠陥を見つけるため | 警告を有効にし、CI では警告をエラーにする |
| 静的解析 | 開発者・CI | 危険な書き方を網羅的に洗い出すため | 指摘を判定し、修正または理由付きで抑止する |
| コードレビュー | 作成者以外の開発者 | ツールが見落とす設計との食い違いを見つけるため | チェックリストで確認し、指摘を記録する |
| 動的解析・ファジング | 開発者・テスト担当者 | 実際に動かして、特定の入力でだけ起きる欠陥を見つけるため | AddressSanitizer を有効にしたビルドでテスト・ファジングを行う |
| 保護オプション | 開発者 | バグが残っても乗っ取りを停止に変えるため | カナリア、FORTIFY、PIE、NX を指定してビルドする（第2章 2.3 の3.6節） |

これらは、すべて「C/C++ では言語が検査してくれないものを、人と道具で補う」ための仕組みです。第2章 2.3 の7.3節で触れたとおり、新規開発では、配列の範囲外アクセスや解放後の使用を言語側で防ぐ Java、C#、Rust などのメモリ安全な言語を採用することも、開発者と発注者が検討すべき根本的な選択肢です。Java の場合の留意点は、次の第8章 8.3 で扱います。

## 7. 確認問題

原本には理解度チェック・過去問題の掲載がないため、本ノートの内容から理解度チェックを作成しています。

### 7.1 理解度チェック

- 【Q1】C/C++言語のどのような特徴が、BOFの作り込みにつながるのか。
- 【Q2】`strncpy(buf, data, sizeof(buf) - 1);` だけでは不十分とされる理由と、推奨される書き方を述べよ。
- 【Q3】`strncat` の第3引数に `sizeof(buf)` を指定すると何が問題か。正しい指定とあわせて述べよ。
- 【Q4】`sprintf` の書式 `%.126s` と、`scanf` の書式 `%127s` は、それぞれ何を意味するか。128バイトのバッファを前提に説明せよ。
- 【Q5】ユーザが入力したファイル名にプログラムが拡張子を付加して開く処理で、ナル文字が問題になる理由と対策を述べよ。
- 【Q6】`printf(msg);` の問題点と修正方法を述べよ。`snprintf` を使っていれば安全か。
- 【Q7】`malloc` で確保したサイズの計算で整数オーバフローを防ぐには、開発者はどう書くべきか。
- 【Q8】`free(p);` の後に開発者が行うべきこと、およびそれだけでは不十分な場合を述べよ。
- 【Q9】`access()` で権限を確認してから `open()` する処理の問題点と、対策を述べよ。
- 【Q10】`snprintf` でコマンド文字列を作り `system` に渡すプログラムの問題点と、望ましい対策を順に述べよ。
- 【Q11】静的解析ツールの指摘をすべて修正せずに抑止する場合、開発者は何をすべきか。

> **解答例**
>
> - **Q1**：文字列操作を行う関数の多くが書込み先バッファの大きさを検査せず、言語としても配列の範囲外への書込みを検査しないこと。文字列の長さがナル文字の位置で決まり、格納にナル文字1バイト分が余計に必要なことも誤りの原因になる（1.1、1.2）。
> - **Q2**：`strncpy` は、コピー元が長いと終端のナル文字を付けないため、後続の処理がバッファの外まで読むおそれがある。また長い入力を黙って切り捨てる。推奨は、`strlen(data) >= sizeof(buf)` を先に検査してエラーにし、`snprintf(buf, sizeof(buf), "%s", data)` でコピーすること。`strncpy` を使う場合は `memset` で初期化するか、`buf[sizeof(buf) - 1] = '\0';` を書く（2.2）。
> - **Q3**：第3引数は「連結する最大文字数」であり、バッファ全体の大きさではないため、格納済みの文字列の分だけあふれる。正しくは `sizeof(buf) - strlen(buf) - 1` を指定する（2.3）。
> - **Q4**：`%.126s` は `printf` 系の精度で、実引数から書き込む最大のバイト数が126であることを表す（書式中の改行1バイトとナル文字1バイトを足して128）。`%127s` は `scanf` 系の最大フィールド幅で、最大127文字まで格納することを表す（ナル文字を足して128）。`scanf` 系にピリオドを付けた `%.127s` は正しい指定ではない（2.4、3.1）。
> - **Q5**：ファイルを開く関数はナル文字を文字列の終端と解釈するため、入力の末尾にナル文字が混入すると、プログラムが付加した拡張子が無視され、意図しないファイルが開かれる。開発者は、入力にナル文字などの不正な文字が含まれていないかを確認し、含まれていればエラー処理を行う。許可する文字だけを受け付けるホワイトリスト方式が望ましい（1.3）。
> - **Q6**：外部入力 `msg` が書式として解釈され、入力中の `%` によってメモリの内容の漏えいや書換え、異常終了が起きる（書式文字列の脆弱性）。`printf("%s", msg);` のように書式を定数に固定する。`snprintf(buf, sizeof(buf), msg)` は長さの問題を防ぐだけで書式の問題は残るため、安全ではない（4.2）。
> - **Q7**：掛け算の前に `count > SIZE_MAX / size` を確認して超える場合はエラーにする、または内部で桁あふれを検査する `calloc(count, size)` を使う。演算後に結果を検査しても、桁あふれ後の値は小さくもっともらしいため検出できない（4.1）。
> - **Q8**：解放直後にポインタへ `NULL` を代入し、ダングリングポインタを残さない（`free(NULL)` は何もしないため二重解放も防げる）。ただし、同じ領域を指すポインタを別の変数にコピーしている場合はコピー側が残るため、解放の責任をもつ箇所（所有権）を1か所に決める必要がある。C++ ではスマートポインタや RAII を使う（4.3）。
> - **Q9**：検査（access）と使用（open）の間に、攻撃者がファイルを別のファイルへのシンボリックリンクに差し替えると、検査を通過したまま別のファイルを操作させられる（TOCTOU）。権限を利用者のものに下げてから `O_NOFOLLOW` を付けて `open` し、開いたファイル記述子に対して `fstat` で検査する（4.4）。
> - **Q10**：`snprintf` でBOFは防げても、入力にシェルのメタ文字（`;` など）が含まれると任意のコマンドが実行される（OSコマンドインジェクション）。望ましい順に、①外部コマンドを使わずライブラリ関数（`opendir`／`readdir`）で処理する、②`execve` でシェルを介さず引数を個別に渡す、③やむを得ず `system` を使うなら、ホワイトリスト方式で入力を検査する（5節）。
> - **Q11**：指摘が真陽性か誤検知かを判定し、誤検知と判断した理由をソースコードのコメントとレビュー記録に残す。理由のない抑止は本物の欠陥を隠す原因になる（6.2、6.3）。

## 8. 試験対策まとめ（重要ポイント）

### 8.1 知識の確認（科目A-2向け）

- **危険な関数と代替**：`gets`→`fgets`、`strcpy`→`strncpy`（＋終端処理）／`snprintf`／`strlcpy`、`strcat`→`strncat`／`strlcat`、`sprintf`→`snprintf`／精度指定、`vsprintf`→`vsnprintf`、`scanf` 系→最大フィールド幅。`v` 付きの関数も同じ危険をもつ。
- **gets は削除済み**：C99（TC3）で非推奨、C11 で標準ライブラリから削除。附属書K の `gets_s` は処理系によって未対応。
- **ナル文字の2つの性質**：①見つけると終端と認識して処理を終える（ナルバイト攻撃で拡張子チェックを無効化）、②格納時に末尾に付加する（1バイト分の領域が必要。忘れると off-by-one）。
- **fgets と gets の違い**：`fgets` は最大 `n-1` 文字を読み、改行文字も格納する。`gets` は改行文字を捨てる。
- **strncpy の落とし穴**：`n` バイト以内にナル文字がないと終端されない。短いときは残りを `n` 文字までナル文字で埋める。
- **strncat の第3引数**：「連結する最大文字数」＝`sizeof(buf) - strlen(buf) - 1`。`sizeof(buf)` は誤用。
- **精度と最大フィールド幅**：`printf` 系の精度はピリオド付き（`%.126s`。`s` 変換では最大バイト数、`d` 系は最小桁数、`f` 系は小数点以下の桁数、`g` 系は最大有効桁数）。`scanf` 系はピリオドなし（`%127s`）。
- **snprintf の戻り値**：制限がなければ書き込まれたはずの文字数。`n` 以上なら切捨て、負なら変換エラー。
- **getchar 系**：関数自体は安全だが、ループで配列に格納するときは添字の境界チェックが必要（危険度「中」）。
- **整数オーバフロー**：演算の**前に**検査する（`count > SIZE_MAX / size`、`off > total - len`）。符号付きの桁あふれは未定義動作で、後置の検査は最適化で消されうる。
- **書式文字列の脆弱性（CWE-134）**：外部入力を書式にしない。`printf("%s", msg)`。長さの対策（`snprintf`）では防げない。
- **Use-After-Free（CWE-416）と二重解放（CWE-415）**：`free` 後に `NULL` を代入。所有権を1か所に。C++ はスマートポインタ／RAII。
- **TOCTOU（CWE-367）**：検査と使用の隙間。ファイル記述子に対して検査する、`O_NOFOLLOW`、一時ファイルは `mkstemp`（`tmpnam`／`mktemp` は不可）。
- **OSコマンドインジェクション**：`system` はシェルを経由するため、メタ文字（`;`、`|`、`&` など）が解釈される。対策はライブラリ関数での代替 ＞ `execve`（シェルを介さない）＞ ホワイトリスト方式の検査。ブラックリスト方式は列挙漏れが起きやすい。
- **CERT C**：STR31-C（ナル文字分の領域）、FIO30-C（書式にユーザ入力を含めない）、MEM30-C（解放済みメモリにアクセスしない）、ENV33-C（`system()` を呼び出さない）、INT30-C／INT32-C（整数演算）、FIO45-C（TOCTOU）。
- **静的解析と動的解析**：静的解析（SAST）は実行せずに網羅的に指摘するが誤検知がある。動的解析（AddressSanitizer）とファジングは実際に起きた欠陥を確実に示すが、通った経路しか調べられない。

### 8.2 記述式で問われる観点（科目B向け）

- **脆弱性の箇所の指摘**：ソースコードが示されたら、「◯行目で、外部から受け取った `data` の長さを検査せずに、128バイトの `buf` へ `strcpy` でコピーしている」のように、**どの行で・どの入力の・何を検査していないか**を具体的に書く。
- **なぜ危険かの説明**：「攻撃者は128バイトを超える入力を与えることで、`buf` に隣接するリターンアドレスなどを上書きし、プログラムの異常終了や、プログラムの権限での任意のコード実行を引き起こすことができる」と、因果と損なわれる特性（可用性・完全性・機密性）をセットで書く。
- **修正方法の記述**：「開発者は、`strlen(data)` が `sizeof(buf)` 以上の場合はエラーとして処理し、コピーには第2引数に `sizeof(buf)` を指定した `snprintf` を使用すべきである（書込み先の大きさを超えた書込みを防ぐため）」のように、**誰が・何を・どう直すか・なぜ防げるか**を一文でそろえる。修正後のコードを書かせる設問では、ナル文字分の「−1」を忘れない。
- **長さの対策と中身の対策の区別**：`snprintf` に置き換えたのに残る問題（書式文字列、OSコマンドインジェクション、ナル文字の混入）を問われたら、「BOFは防げるが、入力の内容を検査していないため、◯◯の問題が残る」と、対策の守備範囲の違いで説明する。
- **より根本的な対策の提案**：OSコマンドインジェクションでは「メタ文字の除去」より「シェルを介さない `execve`」「ライブラリ関数による代替」、BOFでは「メモリ安全な言語の採用」が根本対策になる理由（検査漏れに依存しない）を書けるようにする。
- **開発プロセスでの再発防止**：「同種の脆弱性を作り込まないために、組織は、CERT C を基にしたコーディング規約で危険な関数の使用を禁止し、静的解析ツールで機械的に検出し、チェックリストを用いたコードレビューで確認する」のように、規約・ツール・レビュー・テスト（ファジング）を組み合わせ、それぞれが何を補うかを説明する。
- **ツールの指摘への対応**：静的解析の指摘やコンパイラの警告を「抑止して終わり」にせず、真陽性か誤検知かを判定し、誤検知なら理由を記録する、という運用面の答えも問われる。
