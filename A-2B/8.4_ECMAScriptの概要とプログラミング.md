## 0. 全体像 ― なぜこの分野を学ぶのか

8.2 では C/C++ のメモリ操作の危うさを、8.3 では Java の型安全性とサンドボックスを学びました。本ノートで扱う **ECMAScript**（一般には JavaScript と呼ばれます）は、その2つとは性格がまったく違う言語です。JavaScript のコードは、Webサイトの事業者が書き、**利用者のブラウザの中で、利用者の権限で**実行されます。しかも近年は Node.js によってサーバ側でも動きます。つまり開発者がJavaScriptで書き損じると、その誤りはサーバだけでなく、サイトを訪れたすべての利用者のブラウザに配られることになります。

第2章 2.8 では、攻撃者がXSS（クロスサイトスクリプティング）でブラウザに不正なスクリプトを実行させる仕組みを、第3章 3.6 では、Webサイトが返すHTTPレスポンスヘッダ（CSP、Cookie属性など）による多層防御を学びました。本ノートはその「間」を埋めるものです。つまり、**開発者がJavaScriptのコードをどう書けば、そもそも脆弱性を作り込まずに済むのか**を、言語仕様のレベルから掘り下げます。攻撃の仕組みの説明は 2.8・3.6 に譲り、ここでは「なぜこの書き方が危険か」「開発者はどう書くべきか」を修正前と修正後のコードで対比します。

本ノートは次の順で進みます。

1. **ECMAScriptとは何か**：標準化の経緯、言語の3つの特徴、そしてJavaScriptがブラウザとサーバ（Node.js）のどこで動くか
2. **基本的な記述方法**：HTMLへの組込み、文・変数・データ型・文字列リテラルの規則と、それぞれに潜むバグの種（自動セミコロン挿入、`==` の型変換、エスケープ漏れ）
3. **グローバル変数とローカル変数**：`var` の省略が生む発見しにくいバグと、strictモード
4. **Cookieの取扱い**：`document.cookie` の読み書きと、Secure・HttpOnly・SameSite 属性の設定例
5. **Ajax と同一オリジンポリシ**：XMLHttpRequest による非同期通信と、ブラウザが課す「Same-Originポリシ」の仕組み
6. **JSON、JSONP、CORS**：データ形式と、オリジンをまたぐ通信を安全に行うための仕組み（`eval()` ではなく `JSON.parse()` を使う理由、サーバが返すCORSヘッダの例）
7. **安全な書き方の総まとめ**：`innerHTML` と `textContent`、`eval` の回避、`postMessage` の送信元確認、CSPヘッダ、コードレビューのチェックリスト
8. **コラム**：データベース操作（GRANT文・REVOKE文）と、APIのREST原則

科目Bの業務観点では「②情報システムの企画・設計・開発・運用におけるセキュリティ確保の推進又は支援」のうち、セキュリティ機能の設計・実装、セキュアプログラミング、セキュリティテストに対応します。科目Bでは、問題文に示された JavaScript の断片やHTTPレスポンスを読み、「どの行のどの処理が問題か」「どう修正すべきか」「CORS の設定のどこが不適切か」を記述させる出題がたびたびあります。科目A-2では、Same-Originポリシの判定条件、CORSのヘッダ名、JSONの書式、GRANT文の意味などが四肢択一で問われます。

## 1. ECMAScriptとは何か

### 1.1 ECMAScriptの標準化 ― JavaScriptとJScriptの差異を吸収する

1990年代のWebブラウザでは、ブラウザごとに微妙に異なるスクリプト言語（Netscape社の JavaScript、Microsoft社の JScript）が使われていました。開発者は、同じ処理をブラウザごとに書き分けなければなりませんでした。この問題を解決するために作られたのが **ECMAScript** です。

**ECMAScript** は、JavaScriptとJScriptの仕様の差異を吸収して標準化したスクリプト言語です。情報通信システム分野の国際的な標準化団体である「**Ecma International**」が策定しました（規格番号 **ECMA-262**）。言語仕様の規格文書は「**ISO/IEC 16262:2011**」として発行されているほか、「**JIS X 3060:2000**」としてJIS規格化されています。今日「JavaScript」と呼ばれている言語は、この ECMAScript の仕様を各ブラウザやNode.jsが実装したものだと考えてください。

> **Ecma International**
> 1961年に欧州電子計算機工業会（European Computer Manufacturers Association：ECMA）として設立された標準化団体である。現在は国際的な団体として、ECMAScriptのほか、C#やJSON（**ECMA-404**）などの規格を策定している。

ECMAScript は版（エディション）を重ねて機能が追加されてきました。セキュリティの観点で押さえておきたい版は次のとおりです。

| 版 | 主な追加機能 | セキュリティ上の意味 |
|---|---|---|
| 第3版（1999年） | 正規表現、例外処理など | JSON はこの版のオブジェクトリテラルの表記を基にしている（本ノート6.1） |
| 第5版（2009年） | **strictモード**（`"use strict";`）、`JSON.parse()` の標準化 | 宣言なしの変数代入をエラーにでき、`eval()` を使わずにJSONを解析できるようになった |
| ECMAScript 2015（第6版） | `let`・`const`、`class` 構文、モジュール | ブロックスコープで変数の影響範囲を狭められる。モジュールは自動的にstrictモードになる |
| 以降 | 毎年1回改訂（ECMAScript 2016、2017…） | 版名に年が付くようになった |

### 1.2 JavaScriptはどこで動くのか ― ブラウザとサーバ（Node.js）

セキュアプログラミングを考えるとき、最初に押さえるべきなのは「**そのコードは誰のコンピュータで、誰の権限で動くのか**」です。JavaScriptには、大きく2つの実行場所があります。

**図：JavaScriptが動く2つの場所**

```
  利用者のPC                                          事業者のサーバ（www.example.com）
 +-------------------------------------------+        +----------------------------------------+
 | ブラウザ                                    |        | Node.js（サーバサイドJavaScript）         |
 |                                           |        |                                        |
 |  タブ: https://www.example.com/            |  HTTPS |  ・リクエストを受けて業務処理を行う          |
 |  +-------------------------------------+  | <----> |  ・DB、ファイル、OSコマンドを操作できる      |
 |  | HTML + CSS + JavaScript             |  |        |  ・Set-Cookie、CSP、CORS などの           |
 |  |  ・DOMを操作して画面を書き換える       |  |        |    レスポンスヘッダを返す                  |
 |  |  ・Cookie/Web Storage を読み書きする   |  |        |                                        |
 |  |  ・fetch/XHR でサーバと通信する        |  |        |  動く権限：サーバのOSアカウント            |
 |  +-------------------------------------+  |        |  信用してはいけないもの：                   |
 |                                           |        |    リクエストのすべて（パラメータ、          |
 |  動く権限：その利用者のログイン状態         |        |    Cookie、ヘッダ、JSONの本文）             |
 |  制約：OSやファイルに直接触れない            |        +----------------------------------------+
 |        （ブラウザのサンドボックス）          |                   |
 |        他サイトとは同一オリジンポリシで隔離  |                   v
 |  利用者がいつでも改変・停止できる            |              [データベース]
 +-------------------------------------------+
```

この図から、開発者が守るべき原則が2つ導けます。

第一に、**ブラウザで動くJavaScriptは利用者（と攻撃者）の手の内にある**ということです。利用者は開発者ツールでコードを読み、書き換え、入力チェックを無効にできます。したがって開発者は、ブラウザ側の入力チェックを「使い勝手のための補助」と位置づけ、金額の計算、権限の確認、入力値の検証といったセキュリティ上の判断は、必ずサーバ側でやり直すべきです。

第二に、**ブラウザで動くJavaScriptは、その利用者のログイン状態で動く**ということです。第2章 2.8 で見たように、攻撃者がXSSでスクリプトを1行でも紛れ込ませれば、そのスクリプトは利用者のCookieを読み、利用者になりすまして操作を行えます。そのためブラウザ側の開発者は、「外部から来た文字列を、コードやHTMLとして解釈させない」書き方を徹底する必要があります（本ノート7節）。

| 観点 | ブラウザ（クライアントサイド） | Node.js（サーバサイド） |
|---|---|---|
| コードを書く人 | Webサイトの開発者 | Webサイトの開発者 |
| コードが動く場所・権限 | 利用者のPC、利用者のログイン状態 | 事業者のサーバ、サーバのOSアカウント |
| 主な危険 | DOM-based XSS、Cookieの窃取、オリジンをまたぐデータの漏えい | SQLインジェクション、OSコマンドインジェクション、ディレクトリトラバーサル |
| 主な防御策 | `textContent` の使用、`eval` の回避、CSP、HttpOnly属性、`postMessage` の送信元確認 | プレースホルダ、シェルを経由しない実行、パスの正規化、最小権限、依存パッケージの更新 |
| 参照するノート | 第2章 2.8（XSS）、第3章 3.6（ヘッダ） | 第2章 2.8（各種インジェクション）、8.1（開発工程） |

Node.js で書くサーバのコードは、言語こそ JavaScript ですが、注意すべき点は他のサーバサイド言語と同じです。たとえば開発者は、SQL文を文字列連結で組み立てずにプレースホルダを使い（第2章 2.8 の 3.4）、OSコマンドを実行するときはシェルを経由しない関数（`child_process.execFile` など）を使うべきです。また、Node.js のアプリケーションは npm で多数の外部パッケージを取り込むため、開発者は `package-lock.json` で依存パッケージの版を固定し、`npm audit` などで既知の脆弱性を定期的に確認すべきです。他人の書いたコードも、取り込んだ時点で自分のアプリケーションの一部になるからです。

### 1.3 ECMAScriptの特徴

ECMAScriptの言語としての主な特徴は次の3つです。

**① スクリプト言語であること**

一般に、スクリプト言語は習得が容易で、簡易に開発できます。そのため、ECMAScriptはC++やJavaなどに比べると、プログラミングの初級者でも取り組みやすい言語です。ただし「簡単に書けて、とりあえず動く」ことは、裏を返せば「誤りがあっても動いてしまい、気づきにくい」ことでもあります。本ノート2節以降で見る自動セミコロン挿入や暗黙の型変換は、その典型です。

**② インタプリタ型の言語であること**

ECMAScriptはインタプリタ型の言語です。事前のコンパイル（翻訳）を必要とせず、実行時にソースコードを逐一解釈し、実行可能な形式に変換します。

> **補足：現在の実行エンジン**
> 以前は「ソースコードを1行ずつ解釈して実行する」インタプリタ型の言語と説明されていたが、現在の主要なブラウザやNode.jsの実行エンジンは、実行時にソースコードを機械語へ変換する **JIT（Just-In-Time）コンパイル** を併用して高速化している。開発者から見れば「事前のコンパイルが不要で、ソースコードのまま配布・実行される」という点は変わらない。セキュリティ上は、実行時に文字列をコードとして解釈できる（`eval()` など）ことが、C/C++やJavaにはない危険の源になる（本ノート7.2）。

**③ オブジェクト指向言語であること**

ECMAScriptは、C++やJavaなどの言語と同様に、クラス、インスタンス、プロパティ、メソッドといったオブジェクト指向の概念を備えています。ただし、ここでいうクラスは、厳密な意味でのクラスとは性質が異なります。ECMAScriptは**プロトタイプベース**のオブジェクト指向言語であり、既存のオブジェクト（プロトタイプ）を基に新たなオブジェクトを生成し、その性質を継承する仕組みを採っています。

> **プロトタイプベース**
> クラスを定義してからインスタンスを生成するクラスベースの方式とは異なり、オブジェクトそのものをひな形（プロトタイプ）として複製・拡張する方式である。なお、ECMAScript 2015（第6版）以降では `class` 構文が導入された。ただし、内部的にはプロトタイプベースの仕組みに基づいている。

見た目で比べると、次の2つは同じ仕組み（プロトタイプの継承）を別の書き方で表したものです。

```javascript
// プロトタイプを直接使う書き方
var base = { greet: function () { return "Hello, " + this.name; } };
var taro = Object.create(base);   // base をプロトタイプとする新しいオブジェクト
taro.name = "Taro";
taro.greet();                     // "Hello, Taro"（greet は base から継承）

// ECMAScript 2015 以降の class 構文（内部的には上と同じくプロトタイプを使う）
class Member {
  constructor(name) { this.name = name; }
  greet() { return "Hello, " + this.name; }
}
new Member("Hanako").greet();     // "Hello, Hanako"
```

プロトタイプは、そこから作られたすべてのオブジェクトが共有しています。このため、プログラムのどこかで共通のプロトタイプが書き換えられると、無関係に見える別の処理の動作まで変わってしまいます。外部から受け取ったデータのキー名を検査せずに、オブジェクトへ再帰的にコピー（マージ）する処理を書くと、外部のデータによってプロトタイプが書き換えられる脆弱性（**プロトタイプ汚染**）につながります。開発者は、外部から受け取ったキーで任意のプロパティを書き込む処理を避け、キーを許可リストで確認するか、プロトタイプをもたない `Map` や `Object.create(null)` を使うべきです。

## 2. ECMAScriptの基本的な記述方法

### 2.1 HTMLへの組込み

ECMAScriptをHTMLに組み込むには、次のように `<script>` タグを用います。

```html
<script type="text/ecmascript">
  alert("Hello, World!");  // "Hello, World!"というダイアログを表示
</script>
```

ECMAScriptに対応していない旧バージョンのブラウザで実行すると、ECMAScriptのコードがそのまま画面に表示されてしまいます。これを防ぐため、次のようにコードをHTMLのコメントで囲む方法が古くから用いられてきました。とはいえ、今日ではそのような旧バージョンのブラウザが使われることはほとんどないと考えてよいでしょう。

```html
<script type="text/ecmascript">
<!--
  alert("Hello, World!");
//-->
</script>
```

外部のファイルに記述したECMAScriptを呼び出すには、次のように記述します。

```html
<script type="text/ecmascript" src="hello.es">
</script>
```

"hello.es" ファイルの記述内容は次のとおりです。以降の例では、この "hello.es" の中身を書き換えながら規則を確認していきます。

```javascript
alert("Hello, World!");
```

> **type属性の値について**
> 一般には `type="text/javascript"` と記述されることが多い。HTML5以降では `type` 属性を省略でき、省略した場合はJavaScriptとして解釈される。現在は省略するのが一般的で、外部ファイルの拡張子も `.js` が普通である。

外部ファイルの読み込みには、セキュリティ上の注意が2つあります。第一に、開発者がCDN（コンテンツ配信ネットワーク）など他者のサーバにあるスクリプトを読み込むと、そのサーバのファイルが改ざんされたとき、改ざんされたコードが自サイトの利用者のブラウザで実行されてしまいます。そこで開発者は、`integrity` 属性にファイルのハッシュ値を書いておき（**サブリソース完全性**：SRI）、ブラウザに「ハッシュ値が一致しないスクリプトは実行しない」よう指示できます。第二に、HTMLの中に直接コードを書く（インラインスクリプト）よりも外部ファイルに分けておくほうが、本ノート7.4 のCSPで「自サイトのファイル以外は実行させない」という厳しいポリシを適用しやすくなります。

```html
<!-- 外部のスクリプトを読み込むときは、ハッシュ値で改ざんを検知させる -->
<script src="https://cdn.example.net/lib/v3.7.1/lib.min.js"
        integrity="sha384-（配布元が公開しているハッシュ値のBase64表記）"
        crossorigin="anonymous"></script>
```

### 2.2 文の記述における規則

**① 文末にはセミコロンを付ける**

ECMAScriptでは、原則として文の末尾にセミコロン（`;`）を付けます。しかし、セミコロンは必須ではなく、省略することも可能です。省略した場合は、ECMAScriptの処理環境が前後の文脈から文末を判断して補完します（**自動セミコロン挿入**：**ASI**）。

**② 文の途中に空白、改行、タブを含めることが可能**

ECMAScriptでは、文の途中の空白、改行、タブは無視されます。そのため、前出の "hello.es" ファイルに次のように記述しても有効です。

```javascript
alert
(
  "Hello, World!"
);
```

ただし、関数の戻り値を返す `return` 文では、行末にセミコロンが自動的に補完されます。そのため、`return` の直後で改行することはできません。「`return`」で改行して次の行に戻り値を記述すると、その戻り値は返されない（`undefined` が返される）ので注意が必要です。

```javascript
// 修正前：意図した値が返らない
function getMsg() {
  return       // ここでセミコロンが自動補完される
    "Hello, World!";   // この行は実行されない
}

// 修正後：戻り値は return と同じ行から書き始める
function getMsg() {
  return "Hello, World!";
}
```

この誤りは文法エラーにならず、黙って `undefined` を返すため、テストで見逃されやすいのが厄介な点です。たとえば権限を判定する関数が `undefined` を返し、呼出し側がそれを「エラーなし」と解釈すれば、そのまま認可の誤りになります。開発者は、コーディング規約で「文末には必ずセミコロンを付ける」「`return` の直後で改行しない」と定め、静的解析ツール（本ノート7.6）で機械的に検出させるのが確実です。

また、文字列リテラルの途中で改行することはできません。後述するように、文字列リテラル中の改行文字はエスケープする必要があります。

**③ 大文字、小文字が区別される**

メソッド名や変数名などでは、大文字と小文字が区別されます。そのため、スペルが正しくても、大文字と小文字を誤ると正しく解釈されません。例えば、前出の "hello.es" ファイルに次のように記述した場合、ダイアログは表示されません。

```javascript
Alert("Hello, World!");   // 「Alert」は「alert」とは別物として扱われる
```

> **リテラル**
> 数値や文字列などの値を、プログラム中に直接記述したものをいう。例えば `"Hello, World!"` は文字列リテラル、`12345` は数値リテラルである。

### 2.3 変数の定義における規則

**① 変数は「var」を用いて定義する**

ECMAScriptでは、次のように「`var`」を用いて変数を定義します。

```javascript
var msg;                     // 変数msgを定義
var msg = "Hello, World!";   // 変数msgを定義すると同時に値を代入
```

> **let と const**
> ECMAScript 2015以降では、ブロックスコープをもつ変数を定義する `let` と、再代入できない定数を定義する `const` も利用できる。

3つの宣言の違いを表にまとめます。現在のコーディング規約では、「原則 `const`、再代入が必要なときだけ `let`、`var` は使わない」とするのが一般的です。変数の有効範囲（スコープ）と書き換えられる機会が狭いほど、意図しない上書きが起きにくいからです。

| 宣言 | スコープ（有効範囲） | 再代入 | 同じ名前での再宣言 |
|---|---|---|---|
| `var` | 関数スコープ（関数の外で宣言するとグローバル） | できる | できてしまう（上書きに気づきにくい） |
| `let` | ブロックスコープ（`{ }` の中だけ） | できる | エラーになる |
| `const` | ブロックスコープ | できない（エラー） | エラーになる |

```javascript
if (true) {
  var a = 1;    // 関数スコープ：if ブロックの外でも見える
  let b = 2;    // ブロックスコープ：この { } の中だけ
}
console.log(a); // 1
console.log(b); // ReferenceError（b は見えない）

const limit = 100;
limit = 200;    // TypeError（const は再代入できない）
```

**② 変数の定義を省略することが可能**

変数の定義を省略した場合は、初めて値が代入されたときに、自動的に変数が定義されます。例えば、前出の "hello.es" ファイルに次のように記述しても、問題なく処理が行われます。

```javascript
msg = "Hello, World!";
alert(msg);
```

ただし、「`var`」を使用せずに定義された変数は、すべてグローバル変数として解釈されます（詳細は本ノート3節で解説します）。

### 2.4 データ型における規則と特徴

**① 基本型と参照型**

ECMAScriptのデータ型には、数値型、文字列型、真偽型などの**基本型**（**プリミティブ型**）と、配列、オブジェクト、関数などの**参照型**があります。基本型の変数には値そのものが格納されます。一方、参照型の変数には、値を格納しているメモリアドレス（参照）が格納されます。

| 区分 | 型 | 値の例 | 変数に入っているもの |
|---|---|---|---|
| 基本型 | 数値型（Number） | `12345`、`3.14` | 値そのもの |
| 基本型 | 文字列型（String） | `"Hello, World!"` | 値そのもの |
| 基本型 | 真偽型（Boolean） | `true`、`false` | 値そのもの |
| 基本型 | undefined、null | `undefined`、`null` | 値そのもの（「未定義」「値なし」を表す） |
| 基本型 | Symbol（ES2015）、BigInt（ES2020） | `Symbol("id")`、`12345n` | 値そのもの |
| 参照型 | 配列、オブジェクト、関数 | `[1, 2]`、`{ id: "AA09" }`、`function () {}` | 値を格納しているメモリアドレス（参照） |

参照型の変数を別の変数に代入すると、コピーされるのは参照（アドレス）だけで、中身は共有されます。次の例で、`copy` を書き換えると `original` まで変わるのはこのためです。

```javascript
var original = { point: 100 };
var copy = original;     // 参照（アドレス）だけがコピーされる
copy.point = 0;
alert(original.point);   // 0（同じオブジェクトを指している）
```

**② データ型の扱いが柔軟**

上記のようにさまざまなデータ型がありますが、ECMAScriptは**動的型付け**の言語です。数値を格納していた変数に文字列を格納してもエラーにはならず、正常に処理が行われるため、データ型をそれほど意識する必要がありません。例えば、前出の "hello.es" ファイルに次のように記述しても、問題なく処理が行われます。

```javascript
msg = 12345;            // 変数msgに数値を格納
alert(msg);
msg = "Hello, World!";  // 変数msgに文字列を格納
alert(msg);
```

**③ 型の柔軟さの裏側 ― 等価演算子 `==` と厳密等価演算子 `===`**

型を意識しなくてよいという利点は、比較のときに落とし穴になります。ECMAScriptの**等価演算子 `==`** は、型の異なる値を比べるとき、比較の前に**暗黙の型変換**を行います。そのため、開発者の直感と異なる結果になることがあります。一方、**厳密等価演算子 `===`** は型変換を行わず、型と値の両方が等しいときだけ `true` を返します。

| 式 | `==`（等価演算子）の結果 | `===`（厳密等価演算子）の結果 |
|---|---|---|
| `"0" == 0` | `true`（文字列が数値に変換される） | `false` |
| `"" == 0` | `true`（空文字列は 0 に変換される） | `false` |
| `"1" == true` | `true`（真偽値も数値に変換される） | `false` |
| `null == undefined` | `true` | `false` |
| `"abc" == "abc"` | `true` | `true` |

フォームやURLのパラメータから受け取る値は、すべて文字列です。開発者が `==` で比較すると、利用者が入力欄を空のまま送信しただけで「0 と等しい」と判定される、といった誤判定が起きます。

```javascript
// 修正前：入力欄が空（""）でも「数量 0」と判定されてしまう
var quantity = document.getElementById("qty").value;   // 値は常に文字列
if (quantity == 0) {
  removeFromCart();
}

// 修正後：型をそろえ、変換に失敗した値を除外してから === で比較する
const quantity = Number.parseInt(document.getElementById("qty").value, 10);
if (Number.isNaN(quantity)) {
  showError("数量を数字で入力してください");
} else if (quantity === 0) {
  removeFromCart();
}
```

開発者は、比較には原則として `===`（否定は `!==`）を使い、外部から受け取った値は「何型で、どの範囲なら正しいか」を明示的に確かめてから使うべきです。なお、この例のようなブラウザ側の判定は画面の使い勝手のためのものです。本ノート1.2 で述べたとおり、注文数や金額の正しさは、サーバ側でも必ず検証しなければなりません。

### 2.5 文字列リテラルの処理における規則と特徴

**① 文字列リテラルはシングルクォートまたはダブルクォートで囲む**

ECMAScriptでは、文字列リテラルをシングルクォート（`'`）またはダブルクォート（`"`）のいずれかで囲んで記述します。どちらを用いても意味は同じです。

```javascript
alert('Hello, World!');
alert("Hello, World!");
```

ECMAScript 2015以降では、バッククォート（`` ` ``）で囲む**テンプレートリテラル**も使えます。テンプレートリテラルは `${変数}` で値を埋め込めて便利ですが、埋め込んだ値がエスケープされるわけではありません。HTMLを組み立てる用途に使えば、文字列連結と同じ危険がそのまま残ります（本ノート7.1）。

**② メタキャラクタのエスケープ処理**

次のような場合には、**メタキャラクタ**を**エスケープ処理**する必要があります。

- 文字列リテラルにメタキャラクタを含める場合
- 外部からの入力値を文字列リテラルとして扱う場合

エスケープ処理には、エスケープコード（`\`：バックスラッシュ）を用います。対象となるのは次表の文字です。なお、エスケープ処理された文字を**エスケープシーケンス**といいます。

**表：メタキャラクタのエスケープ処理で対象となる文字**

| 対象となる文字 | エスケープシーケンス |
|---|---|
| シングルクォート | `\'` |
| ダブルクォート | `\"` |
| バックスラッシュ | `\\` |
| 改行 | `\n` |
| リターン | `\r` |
| タブ | `\t` |
| 改ページ | `\f` |
| バックスペース | `\b` |

> **メタキャラクタ**
> プログラミング言語や正規表現などにおいて、特別な意味をもつ文字をいう。文字列の区切りを示すクォートや、エスケープの開始を示すバックスラッシュなどが該当する。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰでは、スクリプト中の文字列リテラルに対するエスケープ処理の不備に起因する脆弱性と、その対策方法に関する問題が出題された。

第2章 2.8 の 2.6「HTMLタグの特定の属性などにおける注意事項」（原本では 2.8.2項「スクリプトの文字列リテラルに対するエスケープ処理の例」）で解説しているように、セキュリティ対策上、最低限エスケープ処理が必要な文字は次の4つです。

- シングルクォート
- ダブルクォート
- バックスラッシュ
- 改行

それぞれの理由を「なぜ危険か」の形で整理しておきます。

| 文字 | エスケープしないと何が起きるか | 開発者がすべきこと |
|---|---|---|
| シングルクォート／ダブルクォート | 文字列リテラルをシングルクォートで囲んでいる場合はシングルクォートが、ダブルクォートで囲んでいる場合はダブルクォートが、入力値の途中で文字列を閉じてしまい、残りの部分がコードとして解釈される | 囲みに使っている方のクォートを、それぞれ確実にエスケープする |
| バックスラッシュ | 入力値中の `\` と、エスケープ処理で付加した `\` が組み合わさり、エスケープが打ち消される。その結果、不正なスクリプトの混入を防げなくなる | クォートより先に、バックスラッシュ自体も確実にエスケープする |
| 改行 | 不正なスクリプトの混入には直結しない。しかし、文字列リテラルの途中で改行できないため、処理が正常に実行されなくなる可能性がある | 処理の正常な実行のために、改行文字も確実にエスケープしておく |

もっとも、エスケープ処理は「漏れなく、正しい順序で」行わなければ効果がなく、開発者が手書きで実装すると誤りが入りやすい対策です。そこで現在は、**そもそも外部からの値をスクリプトの文字列リテラルの中に埋め込まない**設計が推奨されます。サーバ側の開発者は、値をHTMLの `data-` 属性や JSON として渡し（属性値としてのHTMLエスケープは行う）、ブラウザ側の開発者はそれをデータとして読み取るようにすれば、値がコードの構造を変える余地がなくなります。

```html
<!-- 修正前：サーバが入力値をスクリプトの文字列リテラルの中に直接埋め込んでいる -->
<script>
  var word = '（サーバが埋め込んだ検索語）';   // エスケープ漏れがあればコードの構造が変わる
  showResult(word);
</script>

<!-- 修正後：値はHTMLの属性値として（HTMLエスケープして）渡し、スクリプトはデータとして読む -->
<div id="search" data-word="（HTMLエスケープした検索語）"></div>
<script src="/js/search.js"></script>
```

```javascript
// /js/search.js：値は常に「文字列データ」として扱われ、コードとして解釈されない
const word = document.getElementById("search").dataset.word;
showResult(word);
```

## 3. グローバル変数とローカル変数の取扱い

### 3.1 2種類の変数と、同名の変数の区別

関数の内外にかかわらず、プログラム中のどこからでも参照・変更できる変数が**グローバル変数**です。グローバル変数は、関数の外で「`var`」を用いて定義します。

一方、特定の関数内でのみ参照・変更できる変数が**ローカル変数**です。ローカル変数は、使用する関数の中で「`var`」を用いて定義します。

グローバル変数とローカル変数に同名の変数を定義した場合でも、両者は明確に区別されます。例えば、前出の "hello.es" ファイルに次のように記述したとします。実行すると、まずローカル変数「`msg`」に代入された「Hello, World!」が表示され、続いて同名のグローバル変数「`msg`」に代入された「12345」が表示されます。

```javascript
function popupMsg() {
  var msg = "Hello, World!";  // ローカル変数「msg」を定義し、値を代入
  return msg;
}

var msg = 12345;              // グローバル変数「msg」を定義し、値を代入
alert(popupMsg());            // 関数「popupMsg()」の戻り値("Hello, World!")を表示
alert(msg);                   // グローバル変数「msg」の値(12345)を表示
```

### 3.2 「var」の省略が生むバグ

ただし、本ノート2.3 で述べたように、「`var`」を使用せずに定義された変数は、すべてグローバル変数として解釈されます。そのため、次のように `popupMsg()` 関数内の変数「`msg`」の定義で「`var`」を省略すると、処理結果が異なります。

```javascript
var msg = 12345;              // グローバル変数「msg」を定義し、値を代入

function popupMsg() {
  msg = "Hello, World!";      // 「var」を省略して値を代入(グローバル変数「msg」を上書き)
  return msg;
}

alert(popupMsg());            // 関数「popupMsg()」の戻り値("Hello, World!")を表示
alert(msg);                   // グローバル変数「msg」の値("Hello, World!")を表示
```

この場合、`popupMsg()` 関数内で使用される「`msg`」はローカル変数ではなく、グローバル変数として定義された「`msg`」となります。そのため、このスクリプトを実行すると、冒頭で代入した「12345」が「Hello, World!」で上書きされ、「Hello, World!」が2回続けて表示されます。

この例から分かるように、開発者は、ローカル変数を必ず使用する関数の中で「`var`」（現在であれば `let` または `const`）を使って定義する必要があります。

**図：var を省略したときの変数の見え方**

```
 グローバルスコープ（ページ全体で1つ。他のスクリプトやライブラリとも共有）
 +-------------------------------------------------------------+
 |  msg = 12345  ──(var を省略した代入で上書き)──▶ "Hello, World!" |
 |                                                             |
 |  function popupMsg() {                                      |
 |    +-------------------------------------------+            |
 |    | ローカルスコープ                            |            |
 |    |  var msg = ...  → ここに新しい msg ができる    |  ← 正しい |
 |    |  msg = ...      → 外側の msg を探して上書き    |  ← 誤り   |
 |    +-------------------------------------------+            |
 |  }                                                          |
 +-------------------------------------------------------------+
```

### 3.3 変数の取扱いにおける留意点のまとめ

グローバル変数は、プログラムのあらゆる場所からいつでも変更できます。そのため、サブプログラム間の依存度を高め、プログラムの挙動を複雑にしてしまいます。結果としてバグの温床となりやすいため、開発者は安易に使用することを避けるべきです。

特に、「`var`」を使用せずに定義されたグローバル変数は、発見が困難なバグを生み出す大きな要因となるため、避けなければなりません。ブラウザでは、1つのページに読み込まれたすべてのスクリプト（自社のコード、外部のライブラリ、広告タグなど）が同じグローバルスコープを共有します。ある開発者がうっかり作ったグローバル変数が、別のスクリプトの設定値（たとえば通信先のURLや、ログイン済みかどうかのフラグ）を上書きすれば、セキュリティ上の判断まで狂います。

> **strictモード**
> スクリプトの先頭に `"use strict";` と記述すると、**strictモード**が有効になる。strictモードでは、宣言されていない変数への代入がエラーとなるため、意図しないグローバル変数の生成を防止できる。

```javascript
"use strict";                 // ファイル（または関数）の先頭に書く

let msg = 12345;

function popupMsg() {
  mesage = "Hello, World!";   // 綴り誤りの変数への代入
  return msg;                 // strictモードでなければ、黙ってグローバル変数 mesage が作られる
}

popupMsg();                   // strictモードでは ReferenceError となり、誤りにすぐ気づける
```

ECMAScript 2015 のモジュール（`<script type="module">` や `import`／`export` を使うファイル）と `class` 構文の中は、宣言しなくても自動的にstrictモードになります。開発者は、新しく書くコードをモジュールとして構成し、変数は `const`／`let` で宣言するのが安全です。

| 書き方 | 意図しないグローバル変数 | 推奨度 |
|---|---|---|
| `var` も宣言もなしで代入 | 黙って作られる | 使ってはいけない |
| 関数内で `var` を使う | 作られない（関数スコープ） | 古いコードとの互換が必要なとき |
| `"use strict";` ＋ `let`／`const` | 代入時にエラーになる | 推奨 |
| モジュール ＋ `let`／`const` | 代入時にエラーになる（自動的にstrictモード） | 推奨 |

## 4. Cookieの取扱い

### 4.1 document.cookie による読み書き

ECMAScriptでは、`document` オブジェクトの `cookie` プロパティを用いてCookieを操作できます。Cookieの値を取得するには、次のようにします。

```javascript
var cookies = document.cookie;   // "Cookie名1=値1; Cookie名2=値2; ..." の形式の文字列を取得
```

実際に取得される文字列は、たとえば次のような見た目です。属性（有効期限など）は含まれず、「名前=値」の組がセミコロンと空白で区切られて並ぶだけです。

```
theme=dark; lang=ja; recentItem=AA09
```

逆に、Cookieの値をセットするには、次のようにします。

```javascript
document.cookie = "Cookie名=値";
```

有効期限（**expires**）、有効なドメイン（**domain**）、有効なディレクトリ（**path**）、**secure属性**などの属性情報をセットする場合は、セミコロンで区切って次のように指定します。

```javascript
document.cookie = "Cookie名=値; expires=有効期限; domain=有効なドメイン; path=有効なディレクトリ; secure";
```

### 4.2 Cookieの属性と、スクリプトで扱ってよいもの・いけないもの

Cookieの各属性の意味と攻撃との関係は第2章 2.5 と第3章 3.6 の 2.3 で詳しく学びました。ここでは開発者の視点で、「どの属性を、誰が、どこで設定するのか」を整理します。

| 属性 | 意味 | 何を防ぐか | スクリプトから設定できるか |
|---|---|---|---|
| expires／Max-Age | 有効期限（Max-Age は秒数で指定） | 期限を短くして、盗まれたときに使える期間を縮める | できる |
| domain | 送信先のドメイン | 指定すると下位のドメインにも送られる。指定しない方が送信先が狭い | できる |
| path | 送信先のディレクトリ | 同じサーバの別アプリケーションへの送信を減らす（強い隔離にはならない） | できる |
| secure | HTTPSの通信でだけ送る | 盗聴（第2章 2.5） | できる |
| SameSite（Strict／Lax） | 他サイトを起点とするリクエストに付けない | CSRF（第3章 3.6 の 2.4） | できる |
| HttpOnly | スクリプトから読ませない | XSSによるCookieの窃取（第2章 2.8 の 2.7） | **できない**（サーバだけが設定できる） |

> **HttpOnly属性**
> **HttpOnly属性**が付与されたCookieは、`document.cookie` などのスクリプトから参照できない。そのため、XSS（クロスサイトスクリプティング）によるCookieの窃取を防ぐ対策として有効である。なお、HttpOnly属性はサーバ側から `Set-Cookie` ヘッダで指定するものであり、スクリプトからは設定できない。

この表から、開発者が守るべき設計が見えてきます。**セッションIDのように、盗まれると利用者になりすまされる値は、スクリプトで扱ってはいけません**。スクリプトから読み書きできる値は、XSSがあれば攻撃者のスクリプトからも読み書きできるからです。セッションIDはサーバ側の開発者が `Set-Cookie` ヘッダで発行し、HttpOnly属性を付けて、ブラウザのスクリプトからは見えないようにします。

```javascript
// 修正前：ブラウザのスクリプトがセッションIDを受け取り、自分でCookieに保存している
//         （HttpOnly を付けられず、属性も付けていないため、HTTPでも送られ、他サイト起点のリクエストにも付く）
document.cookie = "SESSIONID=" + response.sessionId;
```

```http
# 修正後：サーバ（Node.js など）がレスポンスヘッダでセッションIDを発行する
HTTP/1.1 200 OK
Set-Cookie: __Host-SESSIONID=f3Kq9vX2mL7pR0tZ8wB4nC6yD1sH5jA; Path=/; Secure; HttpOnly; SameSite=Lax
Content-Type: text/html; charset=UTF-8
```

Node.js で書くと、次のようになります（フレームワークを使わない最小の例）。

```javascript
// サーバ側（Node.js）：ログイン成功時に、新しいセッションIDをHttpOnly付きで発行する
res.setHeader("Set-Cookie",
  `__Host-SESSIONID=${newSessionId}; Path=/; Secure; HttpOnly; SameSite=Lax`);
```

Cookie名の先頭の `__Host-` は**Cookieプレフィックス**と呼ばれる仕組みで、ブラウザは「Secure属性があり、Path=/ で、Domain属性がない」Cookieでなければ、この名前での保存を拒否します。開発者がこの名前を使うと、属性の付け忘れや、サブドメインからの上書きをブラウザ側で防げます。

一方、画面の表示テーマや言語設定のように、盗まれても被害のない値なら、スクリプトでCookieに保存してかまいません。その場合も、開発者は属性を省略せずに付けておくべきです。値にセミコロンや空白などの区切り文字が入ると別のCookieとして解釈されるおそれがあるため、値は `encodeURIComponent()` でエンコードしてから保存します。

```javascript
// スクリプトで扱ってよい値（表示設定など）を保存する例
document.cookie = "theme=" + encodeURIComponent(selectedTheme) +
                  "; Max-Age=2592000; Path=/; Secure; SameSite=Lax";   // 30日間有効
```

> **補足：Web Storage との違い**
> ブラウザには Cookie のほかに `localStorage`／`sessionStorage`（**Web Storage**）という保存領域もある。Web Storage はサーバへ自動送信されない点で Cookie と異なるが、HttpOnly のような「スクリプトから読ませない」設定はない。したがって、XSSがあれば攻撃者のスクリプトから読み出される。開発者は、セッションIDやアクセストークンなどの秘密の値を Web Storage に保存すべきではない。

## 5. Ajax と同一オリジンポリシ

### 5.1 Ajax ― ページを再描画せずにサーバと通信する

**Ajax**（Asynchronous JavaScript + XML）とは、JavaScriptなどのスクリプト言語を使ってサーバと**非同期通信**を行う技術です。Webページ全体を再描画することなく、ページの必要な箇所だけを部分的に更新できます。

Ajaxには次の利点があります。

- サーバ側での処理の終了を待たずに、クライアント側で処理を継続できる
- 通信量を削減できるため、クライアント側の体感速度が向上する

Ajaxの具体的な活用例として「Googleマップ」があります。地図をドラッグすると、ページ全体を読み直すことなく、新たに表示される範囲の地図画像だけがサーバから取得されて描き足されます。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰ問1で、Ajaxを用いたWebアプリケーションに関する問題が出題された。

Ajaxでは、一般に次のような流れで処理が行われます。

1. クライアント側のスクリプトが、XMLHttpRequestを用いてサーバに非同期でリクエストを送信する
2. サーバは、リクエストに応じた処理を行い、結果をXMLやJSONなどの形式でクライアントに返す
3. クライアント側のスクリプトは、受け取ったデータを解析し、DOM経由でページに反映する

**図：Ajaxの処理の流れ**

```
  ブラウザ                                              サーバ（www.example.com）
 +--------------------------------+
 | 画面（DOM）                      |
 |  [検索欄: テレビ ] [検索]         |
 |  結果: (ここだけ書き換わる)        |
 +--------------------------------+
        | ①スクリプトが XHR/fetch で非同期にリクエスト
        |    GET /api/items?q=%E3%83%86...  ─────────────────▶  ②検索処理
        |                                                         |
        |    200 OK  Content-Type: application/json            |
        |    {"id":"AA09","商品名":"47型テレビ",...}  ◀────────────┘
        v
   ③スクリプトがJSONを解析し、DOM経由で結果欄だけを更新
     （このとき、受け取った文字列を HTML として解釈させないこと：本ノート7.1）
```

XMLには、タグの記述によってデータが肥大化しやすい、DOMの操作も複雑になりがちである、といった難点があります。そのため、最近ではXMLに代わってJSONが広く利用されています。

> **DOM（Document Object Model）**
> HTMLやXMLの文書を構成する要素や属性などの各部分をオブジェクトとみなし、プログラムやスクリプトからそれらを参照・追加・変更・削除できるようにする仕組みである。W3Cによって標準化されている。

> **API（Application Programming Interface）**
> OSやアプリケーションなどのプログラムがもつ機能を、外部のプログラムから利用するためのインタフェースである。機能の呼出し方法や手続などが定められており、これを用いることでアプリケーションの開発を効率的に行える。

> **試験に出る**
> 情報処理安全確保支援士試験の令和元年度秋期午後Ⅰ問1で、APIの脆弱性対策に関する問題が出題された。

Ajaxのセキュリティで見落とされやすいのは、**画面の裏で呼ばれるAPIも、攻撃者から直接呼べる**という点です。画面上では「自分の注文履歴」しか表示しないつくりでも、ブラウザのスクリプトが `GET /api/orders?userId=1001` のようなリクエストを送っていれば、利用者はURLのパラメータを書き換えて直接送ることができます。APIを開発するサーバ側の開発者は、画面を経由したかどうかにかかわらず、APIの1回1回のリクエストで「ログインしているか」「そのデータにアクセスする権限があるか」をサーバ側で確認しなければなりません（認可の考え方は第6章 6.1）。

### 5.2 XMLHttpRequest ― スクリプトから通信を制御するAPI

Ajaxでサーバと通信を行う際には、**XMLHttpRequest**（**XHR**）を用います。XHRは各種ブラウザに実装されている組込みオブジェクト（API）であり、同期通信と非同期通信の双方をサポートしています。現在は、同じ目的でより簡潔に書ける **Fetch API**（`fetch()` 関数）も広く使われています。

```javascript
// XMLHttpRequest による非同期通信
var xhr = new XMLHttpRequest();
xhr.open("GET", "/api/items?q=" + encodeURIComponent(keyword));  // true（非同期）が既定
xhr.onload = function () {
  var data = JSON.parse(xhr.responseText);   // JSONの解析は JSON.parse で（本ノート6.1）
  showItems(data);
};
xhr.send();

// Fetch API による同じ処理
const res = await fetch("/api/items?q=" + encodeURIComponent(keyword));
const data = await res.json();               // 内部で JSON として解析される
showItems(data);
```

### 5.3 Same-Originポリシ（同一オリジンポリシ）

XHRを用いると、サーバとの通信をスクリプトで制御できます。ただし、悪意のあるサイトに不用意にCookieや個人情報を送ってしまわないよう、セキュリティ上の理由からブラウザの標準的な仕様で制限が設けられています。

なぜ制限が必要なのかを考えてみましょう。利用者がネットバンキング（`https://bank.example.com`）にログインしたまま、別のタブで攻撃者のサイトを開いたとします。もし攻撃者のサイトのスクリプトが自由に `https://bank.example.com` へリクエストを送り、その応答を読めるとしたら、ブラウザは利用者のCookieを付けてリクエストを送るため、攻撃者のスクリプトは利用者の残高や取引履歴を読み取れてしまいます。これを防ぐのが、ブラウザが課す次の制限です。

原本では、この制限を「次のいずれかが異なるサイトに対するリクエストの送信（**クロスドメインリクエスト**）が禁止されている」と説明しています。

- FQDN
- スキーム（http、https）
- ポート番号

この制限を「**Same-Originポリシ**」あるいは「**同一生成元ポリシ**」と呼びます（**同一オリジンポリシ**ともいいます）。スキーム、ホスト（FQDN）、ポート番号の3つの組を**オリジン**と呼び、3つすべてが一致するときだけ「同一オリジン」と判定されます。

**表：`https://www.example.com/app/index.html` から見た同一オリジンの判定**

| アクセス先のURL | 判定 | 理由 |
|---|---|---|
| `https://www.example.com/api/items` | 同一オリジン | スキーム・ホスト・ポート（443）がすべて一致（パスは関係しない） |
| `http://www.example.com/api/items` | 別オリジン | スキームが異なる（http） |
| `https://www.example.com:8443/api/items` | 別オリジン | ポート番号が異なる（8443） |
| `https://api.example.com/items` | 別オリジン | ホスト（FQDN）が異なる（サブドメインでも別扱い） |
| `https://www.example.jp/api/items` | 別オリジン | ホスト（FQDN）が異なる |

> **補足：「送信の禁止」から「読取りの制限」へ**
> 以前は「別オリジンへのリクエストの送信そのものが禁止される」と説明されることが多く、初期のXHRでは実際にそのように実装されていた。現在のブラウザでは、同一オリジンポリシの中心は「**別オリジンから受け取ったレスポンスを、スクリプトに読ませない**」ことにある。単純なGETやフォームのPOSTのようなリクエストは別オリジンにも送信され、サーバまで届く（サーバ側で処理も実行される）が、サーバが本ノート6.3 のCORSで許可していなければ、ブラウザはレスポンスをスクリプトに渡さない。このため、「リクエストが届いてしまうこと」を悪用するCSRF（第3章 3.6 の 2.4）は、同一オリジンポリシだけでは防げない。

**図：同一オリジンポリシの働き**

```
  ブラウザ（利用者は bank.example.com にログイン中。Cookie を保持）
 +------------------------------------------------------------------------+
 | タブA  オリジン https://bank.example.com                                |
 |   スクリプト --fetch--> https://bank.example.com/api/balance            |
 |               <--200 OK 残高データ--  同一オリジン：スクリプトが読める      |
 |                                                                        |
 | タブB  オリジン https://attacker.example.net （攻撃者のサイト）           |
 |   スクリプト --fetch--> https://bank.example.com/api/balance            |
 |               （ブラウザは Cookie を付けて送り、サーバは応答を返すが…）    |
 |               <--200 OK 残高データ--                                    |
 |                    x  ブラウザが遮断：CORSの許可がないので                |
 |                       スクリプトにはレスポンスを渡さない                   |
 +------------------------------------------------------------------------+
```

同一オリジンポリシは、ブラウザの中でタブやフレームを「オリジンごとの部屋」に分ける壁だといえます。ところが、Webサービスが成長すると、この壁を越えて正当に通信したい場面が出てきます。たとえば `https://www.example.com` の画面から、別のサーバ `https://api.example.com` のAPIを呼びたい、といった場合です。そこで、壁に「通用口」を開ける技術として、古くは JSONP が、現在は CORS が使われます。次の6節で、データ形式のJSONと併せて見ていきます。

## 6. JSON、JSONP、CORS

### 6.1 JSON ― 言語から独立したデータ記述形式

**JSON**（JavaScript Object Notation）とは、ECMA-262標準第3版に準拠したJavaScript（ECMAScript）を基にした、軽量のデータ記述方式です。名称にはJavaScriptとありますが、言語から独立したデータ記述形式です。JavaScriptに限らず、多くの言語やシステムでデータ交換に使用できます。現在は ECMA-404 や RFC 8259 として規格化されています。

JSONは、JavaScriptにおける**オブジェクトリテラル**の表記を利用しており、基本的な記述方法は次のとおりです。

```json
{ "名前": 値, "名前": 値, ... }
```

**表記における主な注意点**

- オブジェクトは `{`（左の中括弧）で始まり、`}`（右の中括弧）で終わる
- 配列は `[`（左の大括弧）で始まり、`]`（右の大括弧）で終わる
- 「名前」は常に文字列リテラルであり、ダブルクォート（`"`）で囲む（シングルクォートは使用不可であることに注意）
- 「値」として使用できるのは、文字列、数値、`true`、`false`、`null`、オブジェクト、配列である。これらの構造は入れ子（**ネスティング**）にできる
- 数値は10進数（整数、小数、指数）のみ使用可能である。先頭に `0` を付けたり（8進数）、`0x` を付けたり（16進数）することはできない

記述例を次に示します。

```json
{
  "id": "AA09",
  "商品名": "47型テレビ",
  "価格": 98000,
  "在庫あり": true,
  "関連商品id": ["AA101", "BC06"]
}
```

JavaScriptのオブジェクトリテラルとの見た目の違いを並べておきます。JavaScriptのコードとしては正しくても、JSONとしては誤り、という書き方が多いことに注意してください。

| 書き方 | JavaScriptのオブジェクトリテラル | JSON |
|---|---|---|
| `{ id: "AA09" }`（名前を囲まない） | 正しい | 誤り（名前はダブルクォートで囲む） |
| `{ 'id': 'AA09' }`（シングルクォート） | 正しい | 誤り |
| `{ "price": 0x10 }`（16進数） | 正しい | 誤り |
| `{ "price": 010 }`（先頭に0） | （非strictモードでは8進数） | 誤り |
| `{ "f": function () {} }`（関数） | 正しい | 誤り（関数は値にできない） |
| `{ "id": "AA09", }`（末尾のカンマ） | 正しい | 誤り |

JSONでは、項目数や内容の異なるデータも容易に扱えます。そのようなデータの格納に適しているのは、**ドキュメント型データベース**です。

> **ドキュメント型データベース**
> NoSQLデータベースの一種である。JSONやXMLなどの形式で記述されたドキュメント単位でデータを格納する。スキーマ（データ構造）をあらかじめ定義する必要がないため、項目構成の異なるデータを柔軟に格納できる。代表的な製品にMongoDBがある。

**JSONのエスケープ処理**

原本では、JSONでエスケープ処理の対象となるのは次表の文字であり、ECMAScriptの場合との違いは次の2点であると説明しています。

- シングルクォートは使用不可である（エスケープの対象外）
- スラッシュがエスケープの対象となっている

**表：JSONでエスケープ処理の対象となる文字**

| 対象となる文字 | エスケープシーケンス | JSONの規格上の扱い |
|---|---|---|
| ダブルクォート | `\"` | 必ずエスケープする |
| スラッシュ | `\/` | エスケープしてもよい（しなくてもよい） |
| バックスラッシュ | `\\` | 必ずエスケープする |
| 改行 | `\n` | 必ずエスケープする（制御文字） |
| リターン | `\r` | 必ずエスケープする（制御文字） |
| タブ | `\t` | 必ずエスケープする（制御文字） |
| 改ページ | `\f` | 必ずエスケープする（制御文字） |
| バックスペース | `\b` | 必ずエスケープする（制御文字） |

> **補足：スラッシュのエスケープ**
> 原本では「スラッシュがエスケープの対象となっている」とされているが、JSONの規格（RFC 8259）では、必ずエスケープしなければならないのはダブルクォート、バックスラッシュ、制御文字（U+0000〜U+001F）であり、スラッシュは `\/` と書いても `/` と書いてもよい（エスケープが「使える」文字）。ただし、JSONをHTMLの `<script>` 要素の中に埋め込む場合は、文字列中の `</script>` で要素が終わってしまわないよう、`/`（あるいは `<`）をエスケープしておく実装が多い。

**eval() ではなく JSON.parse() を使う**

JSONはJavaScriptのオブジェクトリテラルの表記に基づいているため、`eval()` 関数を用いて解析することもできます。しかし、`eval()` 関数は引数に与えられた文字列をスクリプトとしてそのまま実行します。そのため、JSONデータに不正なコードが含まれていると、第三者によって不正なスクリプトが実行されてしまう可能性があります。開発者は `eval()` 関数の使用を避けるか、利用するとしても最小限にとどめるべきです。JSONデータの解析には、安全な `JSON.parse()` を用いるのが望ましいです。

```javascript
// 修正前：受け取った文字列を「コード」として実行してしまう
var obj = eval("(" + xhr.responseText + ")");
// → responseText にデータ以外のコードが紛れていれば、それも利用者のブラウザで実行される

// 修正後：受け取った文字列を「データ」としてだけ解釈する
var obj = JSON.parse('{"name": "Taro", "point": 100}');  // 安全なJSONの解析
var obj2 = JSON.parse(xhr.responseText);                  // JSONの書式に合わなければ例外が発生するだけ
```

`JSON.parse()` が安全な理由は、JSONの書式（本節の表記規則）に合う文字列だけを受け付け、関数呼出しなどのコードを含む文字列は構文エラー（例外）として拒否するからです。開発者は、例外を `try … catch` で捕捉してエラー処理を行い、解析できたデータについても、項目の型や値の範囲を確認してから使うべきです。`eval()` を避けるべき理由と、代わりの書き方は本ノート7.2 でまとめます。

### 6.2 JSONP ― scriptタグの抜け道を使ったクロスドメイン通信

**JSONP**（JSON with Padding）とは、JavaScript（ECMAScript）とJSONを用いてクロスドメイン通信を実現する技術です。`<script>` タグの `src` 属性にはクロスドメイン通信の制限がなく、別ドメインのURLを指定できます。JSONPはこの特徴を利用しています。

過去の本試験問題では、JSONPを用いてターゲット型広告サービスを実現する仕組みとして、次のようなシステムが例示されています。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰ問1で、JSONPを用いたサービスの脆弱性に関する問題が出題された。

**図：JSONPを用いてターゲット型広告サービスを実現する仕組み**

- 会員サイト：`https://a-sha-kaiin.com/`
- 一般サイト：`http://a-sha.co.jp/`

```
  ブラウザ（利用者は会員サイトにログイン済み。会員サイトのCookieを保持）
 +-------------------------------------------+
 | 一般サイト http://a-sha.co.jp/ のページ     |
 |  ① 一般サイトのスクリプトが <script> を生成 |
 |     src="https://a-sha-kaiin.com/callback.json"
 +-------------------------------------------+
        |  ② GET /callback.json  + 会員サイトのCookie   ┌────────────────────────┐
        +--------------------------------------------->| 会員サイト                │
        |                                              | https://a-sha-kaiin.com/ │
        |  ③ putUserData({...会員情報...});            | Cookieで利用者を識別      │
        |<---------------------------------------------+ └────────────────────────┘
        v
  ④ ブラウザは応答を「スクリプト」として実行 → putUserData が呼ばれ、
     dispUserPoint で会員のポイントが一般サイトの画面に表示される
```

一般サイトのJSONP呼出しスクリプト（抜粋）は次のとおりです。

```javascript
function putUserData(data) {
  dispUserPoint(data.name, data.thisMonthPoint, data.totalPoint);
}

// データ提供用に用意された会員サイトのURL
var url = "https://a-sha-kaiin.com/callback.json";

// 動的にscriptタグを生成
var script = document.createElement("script");
script.setAttribute("src", url);
document.body.appendChild(script);
```

※ `dispUserPoint` は、ブラウザに表示させるために別途用意された関数です。

会員サイトから返されるJSONP型データの例は次のとおりです。JSONのデータが関数呼出しで「包まれて（Padding）」いることが名前の由来です。

```javascript
putUserData({"name": "情報太郎", "thisMonthPoint": 120, "totalPoint": 3500});
```

JSONPでは、次のように処理が実行されます。

1. クライアント（ブラウザ）は、一般サイトから取得したスクリプトによって `<script>` タグを動的に生成し、`src` 属性に指定された会員サイトのURLにリクエストを送信する。このとき、会員サイトのCookieも併せて送信される
2. 会員サイトのサーバは、Cookieなどを基に利用者を識別する。そして、利用者のデータ（JSONデータ）をコールバック関数（`putUserData`）の引数とした関数呼出しの形式で、クライアントに返す（上記の「JSONP型データの例」）
3. クライアント側では、コールバック関数 `putUserData` が実行される。そこから呼び出された関数 `dispUserPoint` により、サーバから送られてきたJSONデータがブラウザに表示される

**JSONPの危険性 ― なぜ問題になるのか**

前述の本試験問題でも取り上げられていたように、JSONPには「Same-Originポリシ」が適用されません。そのため、悪意のある第三者のサイトが同じURLを `<script>` タグで呼び出すと、個人情報などを含むJSONデータが悪用されてしまうおそれがあります。

因果の流れで整理すると、次のようになります。会員サイトのJSONPは「Cookieが付いていれば、その利用者の会員情報を返す」というつくりです。ブラウザは、どのサイトのページから `<script>` タグが生成されたかに関係なく、会員サイトのCookieを付けてリクエストを送ります。そのため、会員サイトにログインしたままの利用者が第三者のサイトを開くと、第三者のサイトが用意したコールバック関数にも会員情報が渡され、その結果、会員の氏名やポイントが第三者に読み取られます（機密性の侵害）。JSONPの応答は「データ」ではなく「どのサイトのページにでも読み込める**スクリプト**」なので、同一オリジンポリシの保護が働かないのです。

さらに、データを利用する一般サイトの側から見ても、JSONPは「会員サイトから返されたスクリプトを、無条件に自サイトのページで実行する」仕組みです。会員サイトが改ざんされれば、一般サイトの利用者のブラウザで任意のスクリプトが実行されることになります。

したがって、JSONPを活用する際には、有効な対策を検討・実施する必要があります。例えば、JSONP型データをブラウザに送信する前に、認証情報やRefererヘッダなどを用いて、リクエストが正規のものであることを確認するといった対策です。ただし、Refererヘッダは利用者の設定やブラウザの方針（Referrer-Policy）によって送られないこともあるため、確実な判定材料にはなりません。現在は、データの提供者・利用者の開発者はJSONPの使用をやめ、次の6.3 のCORSに移行するのが基本です。

> **試験に出る**
> 情報処理安全確保支援士試験の平成31年度春期午後Ⅰ問1で、Same-OriginポリシやCORSに関する問題が出題された。

### 6.3 CORS ― サーバが「読んでよいオリジン」を宣言する

前述のJSONPによるセキュリティリスクを低減する技術として、**CORS**（Cross-Origin Resource Sharing）があります。

CORSは、「Same-Originポリシ」の制約を一部解除し、クロスドメインリクエストを可能とする仕組みです。リクエストを受信するWebサーバのHTTPレスポンスヘッダに **`Access-Control-Allow-Origin`** が付加されている場合に、この制約の解除が行われます。原本では「CORSは、XMLHttpRequest（XHR）**Level 2**として、現在多くのブラウザに実装されている」と説明されています。CORSは当初 XMLHttpRequest Level 2 とともに普及しましたが、現在は WHATWG の Fetch Standard で定義されており、XHR と Fetch API の両方に適用されます。

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://a-sha.co.jp
Content-Type: application/json
```

上記の例では、`http://a-sha.co.jp` をオリジンとするスクリプトからのクロスドメインリクエストに対してのみ、レスポンスの読取りが許可されます。JSONPとの決定的な違いは、**判定を行うのがブラウザで、許可を宣言するのがサーバ**だという点です。JSONPでは誰のページからでもデータを読み込めましたが、CORSでは、データを提供するサーバの開発者が「このオリジンのスクリプトには読ませてよい」と明示したときだけ、ブラウザがレスポンスをスクリプトに渡します。

**図：CORSの仕組み（プリフライトリクエストがある場合）**

```
  ブラウザ（画面のオリジン https://www.example.com）            APIサーバ https://api.example.com
  ─────────────────────────────────────────────────────────────────────────────────
  ① プリフライトリクエスト（ブラウザが自動で送る「事前確認」）
     OPTIONS /v1/points HTTP/1.1                 ───────────▶
     Origin: https://www.example.com
     Access-Control-Request-Method: PUT
     Access-Control-Request-Headers: Content-Type
                                                 ◀───────────  HTTP/1.1 204 No Content
                                                               Access-Control-Allow-Origin: https://www.example.com
                                                               Access-Control-Allow-Methods: GET, PUT
                                                               Access-Control-Allow-Headers: Content-Type
                                                               Access-Control-Allow-Credentials: true
                                                               Access-Control-Max-Age: 600
                                                               Vary: Origin
  ② ブラウザが照合：オリジン・メソッド・ヘッダがすべて許可されている → 本リクエストへ進む
     （許可されていなければ、本リクエストは送らずにエラーにする）

  ③ 本リクエスト
     PUT /v1/points HTTP/1.1                     ───────────▶
     Origin: https://www.example.com
     Cookie: __Host-SESSIONID=...
     Content-Type: application/json
                                                 ◀───────────  HTTP/1.1 200 OK
                                                               Access-Control-Allow-Origin: https://www.example.com
                                                               Access-Control-Allow-Credentials: true
                                                               Vary: Origin
  ④ ブラウザが再度照合し、一致したときだけスクリプトにレスポンスを渡す
```

ブラウザは、GET や単純なフォーム送信と同等のリクエスト（**単純リクエスト**）であれば、プリフライトを省いて直接送信し、レスポンスのヘッダだけを照合します。PUT や DELETE のメソッド、`Content-Type: application/json` などの独自のヘッダを使うリクエストでは、本リクエストを送る前に、OPTIONS メソッドで**プリフライトリクエスト**を送ってサーバの許可を確かめます。サーバが返す主なCORSヘッダは次のとおりです。

| レスポンスヘッダ | 意味 | 設定の注意 |
|---|---|---|
| `Access-Control-Allow-Origin` | レスポンスを読んでよいオリジン | 個人情報を扱うAPIでは、許可するオリジンを1つずつ明示する |
| `Access-Control-Allow-Methods` | 許可するメソッド（プリフライトへの応答） | 必要なメソッドだけを列挙する |
| `Access-Control-Allow-Headers` | 許可するリクエストヘッダ（プリフライトへの応答） | 必要なヘッダだけを列挙する |
| `Access-Control-Allow-Credentials` | Cookieなどの認証情報付きのリクエストへの応答を読ませるか | `true` のときは、Allow-Origin に `*` を使えない |
| `Access-Control-Max-Age` | プリフライトの結果をキャッシュしてよい秒数 | 長すぎると設定変更がすぐに反映されない |
| `Vary: Origin` | Origin ごとに応答が変わることをキャッシュに伝える | オリジンに応じて Allow-Origin を変えるときは必ず付ける |

> **Access-Control-Allow-Origin の指定**
> 値に `*`（ワイルドカード）を指定すると、任意のオリジンからのアクセスを許可することになる。個人情報などを扱うリソースでは、許可するオリジンを明示的に限定すべきである。なお、Cookieなどの認証情報を伴うリクエストでは `*` を指定できない。

**CORSの設定を誤ると何が起きるか**

CORSは「壁に通用口を開ける」仕組みなので、サーバの開発者が設定を誤ると、同一オリジンポリシで守られていたはずのデータが、第三者のサイトのスクリプトから読めるようになってしまいます。典型的な誤りは、リクエストの `Origin` ヘッダの値を確認せずに、そのまま `Access-Control-Allow-Origin` に書き写して返し、しかも `Access-Control-Allow-Credentials: true` を付けてしまうことです。こうすると、どのオリジンから送られた認証情報付きのリクエストにも「読んでよい」と答えることになり、6.2 で見たJSONPと同じ危険が戻ってきます。開発者は、許可するオリジンを**完全一致の許可リスト**で判定すべきです。文字列の前方一致や部分一致で判定すると、許可したドメイン名を一部に含む別のドメインまで許可してしまうからです。

```javascript
// 修正前（Node.js）：届いた Origin をそのまま許可している（どのサイトにも個人情報を読ませる）
res.setHeader("Access-Control-Allow-Origin", req.headers.origin);
res.setHeader("Access-Control-Allow-Credentials", "true");

// 修正後：許可リストと完全一致したオリジンだけを返す
const ALLOWED_ORIGINS = new Set([
  "https://www.example.com",
  "https://admin.example.com",
]);
const origin = req.headers.origin;
if (ALLOWED_ORIGINS.has(origin)) {
  res.setHeader("Access-Control-Allow-Origin", origin);
  res.setHeader("Access-Control-Allow-Credentials", "true");
}
res.setHeader("Vary", "Origin");   // オリジンによって応答が変わることをキャッシュに伝える
```

ブラウザ側の開発者も、別オリジンのAPIにCookieを送る必要があるときだけ `credentials: "include"` を明示します。Fetch API の既定（`same-origin`）では、別オリジンへのリクエストにCookieは付きません。

```javascript
// 別オリジンのAPIに、Cookieを付けて送る必要があるときだけ明示する
const res = await fetch("https://api.example.com/v1/points", {
  method: "PUT",
  credentials: "include",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ point: 120 }),
});
```

最後に、CORSの限界を押さえておきます。CORSが制御するのは「ブラウザがレスポンスをスクリプトに渡すかどうか」だけです。サーバが受け付けた単純リクエストは、CORSの判定とは無関係にサーバで処理されるため、CORSはCSRF対策の代わりにはなりません（CSRFトークンやSameSite属性が必要です。第3章 3.6 の 2.4）。また、ブラウザ以外のプログラム（スクリプトやツール）はCORSの制約を受けないため、API自体の認証・認可は、CORSとは別にサーバ側で必ず行います。

## 7. 安全な書き方の総まとめ ― 修正前と修正後

ここまでの節で、言語仕様（型、スコープ、文字列リテラル）と関連技術（Cookie、Ajax、JSON、CORS）に潜む危険を見てきました。本節では、ブラウザで動くJavaScriptを書く開発者が特に注意すべき書き方を、修正前と修正後のコードで対比します。共通する原則はただ1つ、「**外部から来た文字列を、HTMLやコードとして解釈させない**」ことです。攻撃の仕組みそのもの（XSSの3種類、Cookieが盗まれる流れなど）は第2章 2.8 を参照してください。

### 7.1 DOMへの出力 ― innerHTML ではなく textContent を使う

第2章 2.8 の 2.9 で見たように、`innerHTML` プロパティや `document.write` メソッドは、渡された文字列にHTMLタグが含まれていれば、それをHTMLとして解釈してDOMツリーを組み立てます。外部から来た文字列（URLのパラメータやフラグメント識別子、APIの応答、`postMessage` で受け取ったデータなど）をこうした「**シンク**」に渡すと、その文字列がタグやイベントハンドラとして解釈され、利用者のブラウザでスクリプトが実行されます（DOM-based XSS）。この攻撃はサーバのログにもWAFにも現れにくいため、開発者がコードの段階で防ぐしかありません。

```javascript
// 修正前：APIから受け取った商品名を、HTMLとして解釈させている
const li = document.createElement("li");
li.innerHTML = "<b>" + item.name + "</b>（" + item.price + "円）";   // item.name にタグが含まれれば、そのまま解釈される
list.appendChild(li);

// 修正後：構造（タグ）はDOM操作で作り、外部の値は textContent でテキストとして入れる
const li = document.createElement("li");
const b = document.createElement("b");
b.textContent = item.name;                                  // 文字列はテキストとして表示されるだけ
li.appendChild(b);
li.appendChild(document.createTextNode("（" + item.price + "円）"));
list.appendChild(li);
```

`textContent` や `createTextNode` が安全なのは、渡された文字列を「テキストノード」として扱い、`<` や `"` を含んでいても画面にそのまま文字として表示するだけで、タグとして解釈しないからです。同様に、属性を設定するときは `setAttribute` を使えば値が属性値として扱われます。ただし `href` や `src` のようにURLを受け取る属性では、スキームが `https:` などの想定したものかを開発者が確認する必要があります。属性値として正しく入っても、URLのスキームによってはスクリプトとして実行されるからです。

| 用途 | 危険なシンク（外部の値を渡さない） | 安全な代替 |
|---|---|---|
| 要素の中身を書き換える | `innerHTML`、`outerHTML`、`document.write`、`insertAdjacentHTML` | `textContent`、`createTextNode`、`createElement` ＋ `appendChild` |
| 属性を設定する | 文字列連結でタグごと組み立てる | `setAttribute`（URLを受ける属性はスキームも確認） |
| HTMLをどうしても表示する | 受け取ったHTMLをそのまま `innerHTML` に入れる | 実績のあるサニタイズ用ライブラリで許可したタグだけを残してから入れる |

> **補足：テンプレートリテラルとフレームワーク**
> テンプレートリテラル（本ノート2.5）でHTMLを組み立てて `innerHTML` に入れる書き方は、文字列連結と同じく危険である。一方、ReactやVue.jsなどの主要なフレームワークは、`{item.name}` のような通常の埋込みを自動的にテキストとして扱う。ただし、各フレームワークには `dangerouslySetInnerHTML`（React）や `v-html`（Vue.js）のように「HTMLとして解釈させる」機能も用意されており、開発者がそこに外部の値を渡せば、結局 `innerHTML` と同じ危険が生じる。コードレビューでは、こうした機能の使用箇所を重点的に確認する。

### 7.2 文字列をコードとして実行しない ― eval を避ける

`eval()` 関数は、引数に与えられた文字列をスクリプトとして実行します。開発者が外部の値を含む文字列を `eval()` に渡せば、その値がコードとして実行される可能性があります。同じ性質をもつ書き方は `eval()` だけではありません。`new Function("…")`、文字列を引数にした `setTimeout("…", 1000)`・`setInterval("…", 1000)` も、文字列をコードとして実行します。

```javascript
// 修正前①：プロパティ名を文字列連結して eval で評価している
var value = eval("config." + key);

// 修正後①：プロパティ名はブラケット記法で参照し、許可したキーだけを受け付ける
const ALLOWED_KEYS = new Set(["theme", "lang", "pageSize"]);
const value = ALLOWED_KEYS.has(key) ? config[key] : undefined;
```

```javascript
// 修正前②：JSONの解析に eval を使っている（本ノート6.1）
var data = eval("(" + text + ")");

// 修正後②：JSON.parse で「データ」としてだけ解析する
let data;
try {
  data = JSON.parse(text);
} catch (e) {
  showError("データの形式が正しくありません");
}
```

```javascript
// 修正前③：setTimeout に文字列を渡している（内部で eval と同じように解釈される）
setTimeout("updateStatus('" + status + "')", 1000);

// 修正後③：関数そのものを渡す
setTimeout(() => updateStatus(status), 1000);
```

いずれの修正後のコードも、「何を実行するか」をプログラムの中で決めておき、外部の値は「データ」としてだけ使っています。こうしておけば、外部の値がどのような文字列であっても、実行される処理の種類は変わりません。さらに本ノート7.4 のCSPで `'unsafe-eval'` を許可しなければ、ブラウザは `eval()` や `new Function()` の実行そのものを拒否するため、コードに `eval` が紛れ込んでも被害を抑えられます。

### 7.3 ウィンドウ間の通信 ― postMessage では送信元オリジンを確認する

**`postMessage`** は、オリジンの異なるウィンドウやiframeの間で、同一オリジンポリシを越えてメッセージをやり取りするためのAPIです。たとえば `https://www.example.com` のページが、決済事業者 `https://pay.example.net` のiframeから「決済完了」の通知を受け取る、といった用途で使います。

`postMessage` は「どのオリジンのウィンドウからでもメッセージを送れる」APIです。受信側の開発者が送信元を確認しなければ、利用者が開いている任意のサイト（別のタブやiframeに読み込まれた第三者のページ）からのメッセージを、決済事業者からの正当な通知として処理してしまいます。また、送信側の開発者が送信先のオリジンに `"*"` を指定すると、iframeの中身が別のサイトに差し替えられていた場合にも、そのサイトに機密のデータを渡してしまいます。

```javascript
// 修正前（受信側）：送信元を確認せず、受け取ったデータをHTMLとして表示している
window.addEventListener("message", (event) => {
  document.getElementById("status").innerHTML = event.data.message;
  if (event.data.result == "ok") {          // 等価演算子 == も使っている
    completeOrder();
  }
});

// 修正後（受信側）：送信元オリジンを完全一致で確認し、データの型を検証し、テキストとして表示する
const PAYMENT_ORIGIN = "https://pay.example.net";
window.addEventListener("message", (event) => {
  if (event.origin !== PAYMENT_ORIGIN) {
    return;                                 // 想定外のオリジンからのメッセージは捨てる
  }
  const data = event.data;
  if (typeof data !== "object" || data === null || typeof data.message !== "string") {
    return;                                 // 想定外の形のデータも捨てる
  }
  document.getElementById("status").textContent = data.message;
  if (data.result === "ok") {               // 厳密等価演算子で比較する
    confirmOrderOnServer(data.orderId);     // 最終確認はサーバ側で行う
  }
});
```

```javascript
// 修正前（送信側）：送信先を "*" にしている（どのオリジンのページが受け取っても渡してしまう）
frame.contentWindow.postMessage({ orderId: id, amount: total }, "*");

// 修正後（送信側）：受け取ってよいオリジンを明示する
frame.contentWindow.postMessage({ orderId: id, amount: total }, "https://pay.example.net");
```

受信側の修正後のコードには、本ノートで学んだ3つの原則がそろっています。送信元のオリジンを `===` で完全一致させて確認すること（本ノート5.3・2.4）、受け取ったデータを `textContent` でテキストとして出力すること（7.1）、そして「決済完了」のような重要な判断をブラウザ側のメッセージだけで確定させず、サーバ側で確認すること（1.2）です。

### 7.4 CSP ― 漏れがあってもブラウザでもう一段止める

7.1〜7.3 の書き方を徹底しても、大きなアプリケーションでは見落としがゼロになるとは限りません。そこで Webサイトの開発者・運用者は、**CSP**（Content-Security-Policy）ヘッダを返し、「このページでは、どのスクリプトなら実行してよいか」をブラウザに宣言します。CSPの基本的な見た目と意味は第2章 2.8 の 2.7 で、他のセキュリティヘッダとの組合せは第3章 3.6 の 5.3 で学びました。ここでは、開発者がコードの書き方と合わせて設計するポイントを補います。

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-4AEemGb0xJptoIGFP3Nd'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; connect-src 'self' https://api.example.com
```

```html
<!-- サーバはレスポンスごとに推測困難な nonce を生成し、ヘッダと正規の script 要素の両方に同じ値を書く -->
<script nonce="4AEemGb0xJptoIGFP3Nd" src="/js/app.js"></script>
```

| ディレクティブ | 意味 | 何のためか |
|---|---|---|
| `default-src 'self'` | 個別に指定しない種類のリソースは、自サイトからだけ読み込む | 既定値を最も狭くしておく |
| `script-src 'self' 'nonce-…'` | 自サイトのファイルと、正しい nonce をもつ `<script>` だけを実行する | 攻撃者が注入したスクリプトは nonce を知らないため実行されない |
| `object-src 'none'` | プラグイン（`<object>` など）を一切読み込まない | 古いプラグイン経由のスクリプト実行を防ぐ |
| `base-uri 'none'` | `<base>` 要素による基準URLの変更を禁止する | 相対パスで読み込むスクリプトの読込み先を変えさせない |
| `frame-ancestors 'none'` | このページを他サイトのフレームに表示させない | クリックジャッキング対策（第2章 2.8 の 2.10） |
| `connect-src 'self' https://api.example.com` | fetch/XHR の通信先を限定する | 万一スクリプトが実行されても、外部へデータを送りにくくする |

CSPの効果を十分に得るには、開発者がコードの側を「CSPで縛れる形」にしておく必要があります。HTMLの中に `onclick="…"` のようなイベントハンドラ属性やインラインスクリプトを書き散らしていると、それらを動かすために `'unsafe-inline'` を許可せざるを得ず、注入されたインラインスクリプトまで実行されてしまいます。同様に、`eval()` を使うコードを残すと `'unsafe-eval'` が必要になります。開発者は、イベントハンドラを `addEventListener` で登録し、スクリプトを外部ファイルに分け、`eval` を使わないことで、`'unsafe-inline'`・`'unsafe-eval'` を含まない厳しいポリシを適用できるようにすべきです。

```html
<!-- 修正前：インラインのイベントハンドラ（CSPで 'unsafe-inline' を許可しないと動かない） -->
<button onclick="sendOrder()">注文する</button>

<!-- 修正後：HTMLには構造だけを書き、処理は外部ファイルで登録する -->
```

既存のサイトにいきなり厳しいCSPを適用すると、正規の機能が動かなくなることがあります。運用者は、まず `Content-Security-Policy-Report-Only` ヘッダで「違反を報告させるが、遮断はしない」モードで運用し、違反レポートを見ながらコードを修正してから、本番の `Content-Security-Policy` に切り替えるのが安全です。また、さらに進んだ対策として、`require-trusted-types-for 'script'` を指定してTrusted Typesを有効にすると、対応ブラウザでは `innerHTML` などのシンクに通常の文字列を渡すこと自体がエラーになり、7.1 の誤りを実行時に検出できます。

CSPはあくまで緩和策です。第3章 3.6 の 5.3 で強調したとおり、開発者は「CSPを付けたからエスケープや `textContent` は不要」と考えてはいけません。

### 7.5 サーバ側（Node.js）で書くときの対応表

Node.js でサーバ側の処理を書く開発者は、言語はJavaScriptでも、第2章 2.8 で学んだサーバ側の脆弱性にそのまま注意する必要があります。攻撃の仕組みは第2章 2.8 の各節に譲り、ここでは「どう書くべきか」を対応表にまとめます。

| 脆弱性（第2章 2.8 の節） | 危険な書き方 | 安全な書き方 |
|---|---|---|
| SQLインジェクション（3節） | SQL文を入力値の文字列連結で組み立てる | プレースホルダ（例：`db.query("SELECT * FROM items WHERE id = ?", [id])`）を使う |
| OSコマンドインジェクション（4節） | `child_process.exec` にコマンド文字列を連結して渡す（シェルが解釈する） | OSコマンドの呼出し自体を避ける。必要なら `execFile` で、コマンドと引数を分けて渡す |
| ディレクトリトラバーサル（6節） | 入力値をそのままファイルパスに連結する | ファイル名を許可リストやIDで指定させる。`path.resolve` で正規化した結果が公開ディレクトリの中にあるか確認する |
| HTTPヘッダインジェクション（5節） | 入力値をそのままレスポンスヘッダに入れる | ヘッダに入れる値から改行コードを除去する（現在のNode.jsは改行を含むヘッダ値を拒否する） |
| SSRF（7節） | 利用者が指定したURLへサーバから自由にリクエストする | 接続先を許可リストで限定し、内部向けのアドレスへの接続を拒否する |
| プロトタイプ汚染（本ノート1.3） | 受け取ったJSONを、キーを検査せずに既存のオブジェクトへ再帰的にマージする | キーを許可リストで確認する。`Map` や `Object.create(null)` を使う |

8.1 で見たように、開発工程でセキュリティを確保するには、個々の開発者の注意力に頼るのではなく、コーディング規約・静的解析・コードレビューの仕組みで誤りを見つける必要があります。本ノートの内容をコーディング規約の条文にすると、たとえば次のようになります。

## 8. コラム：データベース操作におけるセキュリティ

Ajax の裏側で呼ばれるAPIは、多くの場合、サーバ側でデータベースを操作します。第2章 2.8 の 3.3 で学んだとおり、SQLインジェクションの被害の大きさは、アプリケーションが使うデータベースのアカウントにどれだけの権限があるかで決まります。権限を付与・剥奪する手段を押さえておきましょう。

SQL文を用いたデータベースの操作において、セキュリティ上重要な意味をもつのが次の2つの文です。

- **GRANT文**：テーブルなどのオブジェクトへのアクセス権を付与する
- **REVOKE文**：GRANT文とは逆に、アクセス権を剥奪する

### 8.1 GRANT文

GRANT文は、ユーザに対し、テーブルやビューなどのオブジェクトに関する特定の権限を付与します。

**〈基本的な構文〉**

```sql
GRANT 権限名 ON オブジェクト名 TO ユーザ名;
```

**権限名**

"SELECT"、"INSERT"、"UPDATE"、"DELETE" など、実行を許可するSQLコマンドを指定します。複数種類のSQLコマンドの実行権限を一度に付与する場合は、カンマで区切って列記します。

なお、"**ALL**" もしくは "**ALL PRIVILEGES**" と記述すると、すべての権限を付与することになるため、注意が必要です。また、ユーザ名の後に "**WITH GRANT OPTION**" を指定すると、付与した権限を他のユーザに付与する権限も、そのユーザに与えることになります。

**オブジェクト名**

アクセスを許可する対象となるオブジェクトであり、テーブルやビューなどの名前を指定します。

**ユーザ名**

権限を付与するユーザ名を指定します。複数のユーザに一度に権限を付与する場合は、ユーザ名をカンマで区切って列記します。ユーザ名に "**PUBLIC**" を指定すると、すべてのユーザに権限を付与することになります。

```sql
GRANT SELECT, INSERT ON 社員表 TO USER01, USER02;
```

### 8.2 REVOKE文

REVOKE文は、ユーザに既に与えられている、テーブルやビューなどのオブジェクトに関する特定の権限を剥奪します。

**〈基本的な構文〉**

```sql
REVOKE 権限名 ON オブジェクト名 FROM ユーザ名;
```

**権限名**

GRANT文の場合と同様に、実行権限を剥奪するSQLコマンドを指定します。複数種類のSQLコマンドの実行権限を一度に剥奪する場合は、カンマで区切って列記します。"ALL" もしくは "ALL PRIVILEGES" と記述すると、すべての権限を剥奪することになるため、注意が必要です。

**オブジェクト名**

アクセス権を剥奪する対象となるオブジェクトであり、テーブルやビューなどの名前を指定します。

**ユーザ名**

権限を剥奪するユーザ名を指定します。GRANT文の場合と同様に、カンマで区切って複数のユーザを列記できます。また、"PUBLIC" も指定できます。

| 書き方 | 意味 | 注意点 |
|---|---|---|
| `GRANT SELECT ON 商品表 TO WEBAPP;` | WEBAPP に商品表の参照だけを許す | 最小権限の典型 |
| `GRANT ALL PRIVILEGES ON 商品表 TO WEBAPP;` | すべての権限を付与する | 参照だけのAPIに更新・削除の権限まで与えてしまう |
| `GRANT SELECT ON 商品表 TO WEBAPP WITH GRANT OPTION;` | 参照権限と、その権限を他人に付与する権限を与える | 権限が管理者の知らないところで広がる |
| `GRANT SELECT ON 商品表 TO PUBLIC;` | すべてのユーザに参照を許す | 意図しないアカウントからも参照できる |
| `REVOKE INSERT ON 社員表 FROM USER02;` | USER02 から社員表への追加権限を剥奪する | 異動・退職・役割変更のときに使う |

> **最小権限の原則**
> データベースの利用者には、業務に必要な最小限の権限だけを付与すべきである。安易に "ALL PRIVILEGES" や "WITH GRANT OPTION" を指定すると、権限の濫用や、SQLインジェクション攻撃を受けた際の被害拡大につながる。

データベースの管理者は、Webアプリケーションが使うアカウントを用途ごとに分け（参照用のAPIには SELECT だけ、注文登録のAPIには該当テーブルへの INSERT だけ、など）、不要になった権限は REVOKE文で速やかに剥奪すべきです。そうしておけば、仮にSQLインジェクションの脆弱性が残っていても、攻撃者が実行できる操作をそのアカウントの権限の範囲に閉じ込められます。

## 9. コラム：APIのREST原則

Ajax やCORSで呼び出すAPIは、多くの場合、REST の考え方で設計されています。

APIの設計における原則ともいえるアーキテクチャとして、**REST**（Representational State Transfer）があります。RESTは、Roy Thomas Fielding氏が2000年に、博士論文 "Architectural Styles and the Design of Network-based Software Architectures" の中で提唱しました。RESTの原則を満たすAPIを "**RESTful API**" と呼びます。

### 9.1 RESTにおける原則

| # | 原則 | 内容 |
|---|---|---|
| 1 | **Client-Server**（クライアントサーバ） | クライアントとサーバを分離・独立させる |
| 2 | **Stateless**（ステートレス） | セッションなどの状態管理をサーバ側で行わない |
| 3 | **Cache**（キャッシュ） | ネットワーク効率を向上させるため、キャッシュ制約を設ける |
| 4 | **Uniform Interface**（統一インタフェース） | コンポーネント間の統一されたインタフェースを定義する |
| 5 | **Layered System**（階層化システム） | 各コンポーネントが、相互作用している直下の層を超えて見ることができないよう、コンポーネントの動作を制約する |
| 6 | **Code-On-Demand**（コードオンデマンド） | アプレットやスクリプトの形式で、サーバからコードをダウンロードして実行する（この原則のみオプションとされている） |

例えば、2のステートレスの原則により、次のような効果があります。

- クライアントからのリクエストに処理に必要な情報がすべて含まれる。そのため、単一のリクエストデータを超えて調べる必要がなく、**可視性**が向上する。
- 部分的な障害からの回復作業が容易になるため、**信頼性**が向上する。
- リクエスト間で状態を保存する必要がなく、サーバコンポーネントがリソースを迅速に解放できる。そのため、**スケーラビリティ**（拡張性）が向上する。

> **統一インタフェースの例**
> RESTful APIでは、リソースをURIで一意に識別する。リソースに対する操作は、HTTPメソッド（GET：取得、POST：作成、PUT：更新、DELETE：削除など）によって統一的に表現される。

```
GET    /v1/items/AA09      … 商品 AA09 を取得する
POST   /v1/items           … 商品を新規に作成する（本文にJSON）
PUT    /v1/items/AA09      … 商品 AA09 を更新する
DELETE /v1/items/AA09      … 商品 AA09 を削除する
```

**セキュリティの観点から見たREST**

ステートレスの原則に従うAPIでは、サーバがセッションの状態をもたないため、クライアントはリクエストのたびに、自分が誰であるかを示す情報（アクセストークンなど。トークンの仕組みは第6章 6.9）を送ります。したがって、APIの開発者は「一度ログインを確認したから、以降のリクエストは信用する」という設計にはできず、**リクエストの1回1回で認証と認可を確認する**必要があります。たとえば `GET /v1/orders/1001` に対して、サーバは「トークンが有効か」だけでなく「注文1001はこのトークンの持ち主のものか」まで確認しなければ、URIの数字を変えるだけで他人の注文が見えてしまいます（本ノート5.1）。

また、URIで操作の対象が、HTTPメソッドで操作の種類が決まる統一インタフェースは、アクセス制御の設計を「リソース × メソッド」の表として整理しやすくする利点があります。さらに、6のコードオンデマンドは、ブラウザがサーバからJavaScriptをダウンロードして実行するWebの仕組みそのものであり、本ノートで学んだ「ダウンロードされるコードを誰がどう守るか」（SRI、CSP）の問題につながります。

## 10. 確認問題

### 10.1 理解度チェック

- **Q1**：ECMAScriptの言語としての主な特徴を3つ挙げよ。
- **Q2**：文字列リテラルにおいて、最低限エスケープ処理を行うべき文字を挙げよ。
- **Q3**：グローバル変数とローカル変数の取扱いにおける留意点を挙げよ。
- **Q4**：Ajaxとはどのような技術か。
- **Q5**：JSON、JSONPの概要について述べよ。
- **Q6**：APIのREST原則について述べよ。

> **解答例**
> - Q1：①スクリプト言語である（習得が容易で簡易に開発できる）。②インタプリタ型の言語である（事前のコンパイルを必要とせず、実行時にソースコードを逐一解釈する）。③プロトタイプベースのオブジェクト指向言語である（既存のオブジェクトを基に新たなオブジェクトを生成し、性質を継承する）（本ノート1.3）。
> - Q2：シングルクォート、ダブルクォート、バックスラッシュ、改行の4つ。囲みに使ったクォートは文字列の途中終了を防ぐため、バックスラッシュはエスケープの打消しによる不正なスクリプトの混入を防ぐため、改行は処理を正常に実行させるためにエスケープする（本ノート2.5）。
> - Q3：グローバル変数はどこからでも変更でき、サブプログラム間の依存度を高めてバグの温床になるため、安易に使わない。ローカル変数は必ず使用する関数の中で `var`（現在は `let`／`const`）を使って定義する。`var` を省略した変数はグローバル変数となり、発見困難なバグの要因になるため避ける。strictモードを使えば宣言のない変数への代入をエラーにできる（本ノート3節）。
> - Q4：JavaScriptなどのスクリプト言語からXMLHttpRequestを用いてサーバと非同期通信を行い、Webページ全体を再描画せずに必要な箇所だけを部分的に更新する技術。サーバの処理を待たずにクライアントで処理を続けられ、通信量の削減で体感速度が向上する（本ノート5.1）。
> - Q5：JSONは、JavaScriptのオブジェクトリテラルの表記を基にした、言語から独立した軽量のデータ記述形式であり、解析には `eval()` ではなく `JSON.parse()` を用いる。JSONPは、`<script>` タグの `src` 属性にクロスドメインの制限がないことを利用し、JSONデータをコールバック関数の呼出しで包んで返すことでクロスドメイン通信を実現する技術である。Same-Originポリシが適用されないため、第三者のサイトからも個人情報を含むデータを読み取られるおそれがあり、現在はCORSへの移行が推奨される（本ノート6.1、6.2）。
> - Q6：RESTはFielding氏が2000年に提唱したAPI設計のアーキテクチャで、Client-Server、Stateless、Cache、Uniform Interface、Layered System、Code-On-Demand（オプション）の6原則からなる。ステートレスにより可視性・信頼性・スケーラビリティが向上する。統一インタフェースでは、リソースをURIで識別し、操作をHTTPメソッドで表す（本ノート9節）。

### 10.2 確認問題1

次のSQL文をA表の所有者が発行したときの、利用者BへのA表に関する権限の付与の説明として、適切なものはどれか。

```sql
GRANT ALL PRIVILEGES ON A TO B WITH GRANT OPTION
```

ア　SELECT権限、UPDATE権限、INSERT権限、DELETE権限などの全ての権限、及びそれらの付与権を付与する。
イ　SELECT権限、UPDATE権限、INSERT権限、DELETE権限などの全ての権限を付与するが、それらの付与権は付与しない。
ウ　SELECT権限、UPDATE権限、INSERT権限、DELETE権限は付与しないが、それらの付与権だけを付与する。
エ　SELECT権限、及びSELECT権限の付与権を付与するが、UPDATE権限、INSERT権限、DELETE権限、及びそれらの付与権は付与しない。

*〔情報処理安全確保支援士試験・R5・午前Ⅱ〕*

> **解答・解説**
> SQLのGRANT文は、ユーザに対し、テーブルやビューなどのオブジェクトに関する特定の権限を付与する。ユーザが既に何らかの権限を有していた場合は、その権限に追加される。
>
> GRANT文の基本的な構文は次のとおりである。
>
> ```sql
> GRANT 権限名 ON オブジェクト名 TO ユーザ名;
> ```
>
> 権限名に "ALL PRIVILEGES" を指定すると、SELECT、UPDATE、INSERT、DELETEなどの全ての権限が付与される。また、"WITH GRANT OPTION" を指定すると、付与された権限を他のユーザに付与する権限（**付与権**）も併せて与えられる。
>
> したがって、利用者BにはA表に関する全ての権限と、それらの付与権が付与される。よって、**ア**が正解（本ノート8.1）。

### 10.3 確認問題2

JSON形式で表現される図1、図2のような商品データを、複数のWebサービスから取得し、商品データベースとして蓄積する。その際のデータの格納方法に関する記述のうち、適切なものはどれか。

〔条件〕

- 商品データの取得元となるWebサービスは随時変更され、項目数や内容は予測できない。
- 商品データベースの検索時に使用するキーには、あらかじめ制限を設けない。

**図1　A社Webサービスの商品データ**

```json
{
  "_id": "AA09",
  "品名": "47型テレビ",
  "価格": "オープンプライス",
  "関連商品id": [
    "AA101",
    "BC06"
  ]
}
```

**図2　B社Webサービスの商品データ**

```json
{
  "_id": "AA10",
  "商品名": "りんご",
  "生産地": "青森",
  "価格": 100,
  "画像URL": "http://www.example.com/apple.jpg"
}
```

ア　階層型データベースを使用し、項目名を上位階層とし、値を下位階層とした2階層構造でデータを格納する。
イ　グラフ型データベースを使用し、商品データの項目名の集合から成るノードと値の集合から成るノードを作り、二つのノードを関係づけたグラフとしてデータを格納する。
ウ　ドキュメント型データベースを使用し、項目構成の違いを区別せず、商品データ単位にデータを格納する。
エ　リレーショナルデータベースを使用し、商品データの各項目名を個別の列名とした表を定義してデータを格納する。

*〔情報処理安全確保支援士試験・R元秋・午前Ⅱ〕*

> **解答・解説**
> JSON（JavaScript Object Notation）は、JavaScriptを基にした軽量のデータ記述方式である。名称にはJavaScriptとあるが、言語から独立したデータ記述形式である。JavaScriptに限らず、多くの言語やシステムでデータ交換に使用できる。
>
> JSONはJavaScriptにおけるオブジェクトリテラルの表記を利用しており、基本的な記述方法は次のとおりである。
>
> - オブジェクトは `{`（左の中括弧）で始まり、`}`（右の中括弧）で終わる
> - 配列は `[`（左の大括弧）で始まり、`]`（右の大括弧）で終わる
> - 「名前」は常に文字列リテラルであり、ダブルクォートで囲む
> - 「値」には、文字列、数値、`true`、`false`、`null`、オブジェクト、配列を使用でき、入れ子にできる
>
> 図1と図2の商品データは、項目数も項目名（"品名" と "商品名" など）も異なっている。さらに、問題の条件から、取得元のWebサービスは随時変更され、項目数や内容は予測できない。
>
> このようなデータの格納に適しているのは、スキーマをあらかじめ定義する必要がなく、JSON形式のドキュメントをそのまま格納できるドキュメント型データベースである。ドキュメント型データベースでは、項目構成の違いを区別せず、商品データ単位でデータを格納できる。また、任意の項目を検索キーとして使用できる。よって、**ウ**が正解（本ノート6.1）。
>
> 他の選択肢が不適切な理由は次のとおりである。
>
> - ア：項目名と値の2階層構造では、配列やネストしたオブジェクトを含むデータを適切に表現できない。また、商品データ単位のまとまりも失われる。
> - イ：グラフ型データベースは、データ間の関係性（ネットワーク構造）の表現に適している。しかし、項目名と値をそれぞれノードの集合として関係づける方法では、個々の商品データの構造が保持されない。
> - エ：リレーショナルデータベースでは、事前にスキーマ（列構成）を定義する必要がある。そのため、項目数や内容が予測できないデータには対応できない。

## 11. 試験対策まとめ（重要ポイント）

### 11.1 知識の確認（科目A-2向け）

- **ECMAScriptの標準化**：Ecma International が策定（ECMA-262）。JavaScriptとJScriptの差異を吸収。ISO/IEC 16262:2011、JIS X 3060:2000。JSONは ECMA-404。Ecma International の前身は1961年設立の欧州電子計算機工業会（ECMA）。
- **3つの特徴**：スクリプト言語、インタプリタ型（現在の実行エンジンはJITを併用）、プロトタイプベースのオブジェクト指向（`class` 構文も内部はプロトタイプ）。
- **文の規則**：セミコロンは省略可（自動セミコロン挿入：ASI）。`return` の直後で改行すると `undefined` が返る。大文字・小文字を区別（`Alert` と `alert` は別物）。
- **変数**：`var` は関数スコープ、`let`・`const` はブロックスコープ（ES2015）。`var` を省略した変数はグローバル変数になる。strictモード（`"use strict";`）では宣言のない変数への代入がエラーになる。モジュールと `class` の中は自動的にstrictモード。
- **データ型**：基本型（数値、文字列、真偽など）は値そのもの、参照型（配列、オブジェクト、関数）は参照（メモリアドレス）を格納。動的型付け。`==` は暗黙の型変換を行い、`===` は行わない（`"0" == 0` は `true`、`"0" === 0` は `false`）。
- **文字列リテラルのエスケープ**：最低限エスケープが必要なのはシングルクォート、ダブルクォート、バックスラッシュ、改行の4つ。改行は不正なスクリプトの混入には直結しないが、処理の正常な実行のためにエスケープする。
- **Cookie**：`document.cookie` で読み書き。属性は expires、domain、path、secure など。**HttpOnly属性はサーバが `Set-Cookie` で指定し、スクリプトからは設定できない**。
- **Same-Originポリシ**：スキーム・ホスト（FQDN）・ポート番号の3つがすべて一致すれば同一オリジン。パスは関係しない。サブドメインは別オリジン。中心は「別オリジンのレスポンスをスクリプトに読ませない」こと。
- **JSONの書式**：名前は必ずダブルクォート（シングルクォート不可）。値は文字列、数値、`true`、`false`、`null`、オブジェクト、配列。数値は10進数のみ（8進数・16進数は不可）。項目構成の異なるJSONの格納にはドキュメント型データベース（MongoDB）。
- **JSONのエスケープ**：シングルクォートは対象外。スラッシュは `\/` と書ける（必須ではない）。解析は `eval()` ではなく `JSON.parse()`。
- **JSONP**：`<script>` タグの `src` 属性にクロスドメインの制限がないことを利用。コールバック関数で包んで返す。Same-Originポリシが適用されないため、第三者のサイトからもデータを読まれる。
- **CORS**：サーバが `Access-Control-Allow-Origin` で読取りを許可するオリジンを宣言し、ブラウザが判定する。`*` は任意のオリジンを許可し、認証情報付きのリクエストでは使えない。PUT・DELETEや独自ヘッダを使うリクエストでは、OPTIONS によるプリフライトリクエストが先に送られる。CORSはCSRF対策にはならない。
- **DOM**：W3Cが標準化した、文書の各部分をオブジェクトとして操作する仕組み。`innerHTML`・`document.write` は文字列をHTMLとして解釈し、`textContent`・`createTextNode` はテキストとして扱う。
- **GRANT／REVOKE**：`ALL PRIVILEGES` は全権限、`WITH GRANT OPTION` は付与権も与える、`PUBLIC` は全ユーザ。REVOKE は `FROM ユーザ名`。
- **REST**：Fielding が2000年の博士論文で提唱。6原則のうち Code-On-Demand だけがオプション。ステートレスの効果は可視性・信頼性・スケーラビリティの向上。

### 11.2 記述式で問われる観点（科目B向け）

- **問題のある行を指摘し、修正を書く**：「外部から取得した値を `innerHTML` に代入しているため、値に含まれるタグが解釈されてスクリプトが実行される。`textContent` に代入してテキストとして出力すべきである。」のように、「どの処理が」「なぜ危険で」「どう直すか」の3点をそろえて書く。
- **eval を使ってはいけない理由**：「`eval()` は引数の文字列をスクリプトとして実行するため、JSONデータに不正なコードが含まれていると利用者のブラウザで実行される。`JSON.parse()` を使えば、JSONの書式に合わない文字列は例外となり、コードは実行されない。」
- **JSONPの問題点と対策**：「JSONPはSame-Originポリシが適用されず、会員サイトのCookieが付いたリクエストに会員情報を返すため、第三者のサイトが同じURLを `<script>` タグで呼び出すと会員情報を取得できる。対策として、認証情報やRefererヘッダでリクエストが正規のものか確認するか、CORSに移行して `Access-Control-Allow-Origin` で許可するオリジンを限定する。」
- **CORSの設定の妥当性を判断する**：事例のレスポンスヘッダを読み、`Access-Control-Allow-Origin: *` や Origin の無条件な反射に `Access-Control-Allow-Credentials: true` が組み合わされていないかを確認する。答え方は「許可するオリジンを、正規の画面のオリジンだけに完全一致で限定すべきである。」
- **postMessage の受信処理**：「受信したメッセージの `event.origin` を確認していないため、任意のサイトから送られたメッセージを正規の通知として処理してしまう。`event.origin` を想定するオリジンと完全一致で照合し、一致しない場合は処理しないようにする。」
- **Cookieの扱い**：「セッションIDをスクリプトで `document.cookie` に設定しているため HttpOnly 属性を付けられず、XSSがあれば窃取される。サーバが `Set-Cookie` ヘッダで発行し、Secure・HttpOnly・SameSite 属性を付与すべきである。」
- **根本対策と緩和策を区別する**：`textContent` の使用、`eval` の排除、送信元の確認は脆弱性をなくす根本対策。CSP、HttpOnly、データベースの最小権限は、漏れがあったときの被害を抑える緩和策。設問が「根本的な対策」を求めているか「被害を軽減する対策」を求めているかを読み分ける。
- **クライアント側の検証だけに頼らない**：「ブラウザで動くスクリプトは利用者が改変できるため、入力値の検証・権限の確認はサーバ側で行う必要がある。」は、Ajax・API・REST の事例で繰り返し使える理由付けである。
- **開発プロセスでの防止**：「コーディング規約で `===` の使用や `eval` の禁止を定め、静的解析ツールで自動的に検出し、コードレビューでシンクへのデータの流れを確認する。」のように、個人の注意ではなく仕組みで防ぐ答え方を用意しておく（8.1 の開発工程とセキュリティにつながる）。
