## 0. 全体像 ― なぜこの分野を学ぶのか

ドメイン名からIPアドレスを求める、あるいはその逆の名前解決を行う**DNS**（Domain Name System）サーバは、インターネットを利用するうえで非常に重要な存在です。利用者がブラウザに `www.example.jp` と入力しても、メールサーバが `example.com` 宛てのメールを配送しても、最初に必ずDNSへの問合せが起きます。つまりDNSは、Webもメールも含めたほぼすべての通信の「入口」です。だからこそ攻撃の対象にもなりやすく、ここが乗っ取られると、利用者は正しい名前を入力したのに偽のサイトへ誘導されてしまいます。

前のノートとのつながりを確認しておきましょう。第1章 1.4 の 6節では、DNSの正常な動き（リゾルバ、コンテンツサーバとキャッシュサーバ、リソースレコード、ゾーン転送）を学びました。第2章 2.6 では、攻撃者がその仕組みをどう逆手にとるか（ゾーン転送による情報収集、DNSキャッシュポイズニング、カミンスキー攻撃、DNSリフレクション攻撃、DNS水責め攻撃など）を攻撃側の視点で見ました。本ノートはその続きで、**DNSサーバの管理者が、何を守るために、どの設定をどう変えるべきか**という防御側の視点に立ちます。

本ノートのストーリーは次のとおりです。

1. **DNSの役割のおさらい**：権威DNSサーバとキャッシュDNSサーバの違いを、守るべきものの違いとして整理します。
2. **DNSの3つの脆弱性**：ゾーン転送、キャッシュへの不正登録、サービス不能状態を、「攻撃者は何を狙い、その結果何が起きるか」の因果で確認します。
3. **9つの対策**：ソフトウェアの更新、プロトコルの強化（ソースポートランダマイゼーション、DNSSEC）、サーバ構成の分離、設定による制限を、BINDの設定例や dig の出力とともに学びます。
4. **512オクテット制限とEDNS0**：DNSSECの導入とセットで問題になる、応答サイズの制約とその解決策を見ます。

科目Bの業務観点では、主に「③利用におけるセキュリティ対策の適用」のうち「ネットワーク及び機器のセキュリティ管理」「脆弱性への対応」に対応し、DNSサーバの構築・設定を扱う点で「②企画・設計・開発・運用におけるセキュリティ確保」（アーキテクチャ設計、運用・保守）にもかかわります。科目A-2ではDNSSECの仕組み（誰が署名し、誰が検証するか）、オープンリゾルバ、ソースポートランダマイゼーションが繰り返し出題され、科目Bでは「このDNSサーバの設定のどこに問題があるか」「なぜ機能を分離すべきか」を記述させる設問が定番です。

## 1. DNSの役割のおさらい ― 誰が何を答えているか

### 1.1 権威DNSサーバとキャッシュDNSサーバ

DNSは、ドメイン名とIPアドレスを対応付ける分散型のデータベースシステムです。ドメイン名からIPアドレスを求める処理を**正引き**、IPアドレスからドメイン名を求める処理を**逆引き**といいます。

DNSサーバは、役割によって次の2つに大別されます。1.4 の 6.2 で学んだ内容ですが、本ノートの対策はすべてこの区別を前提にするので、もう一度確認しておきます。

| 観点 | **権威DNSサーバ（コンテンツサーバ）** | **キャッシュDNSサーバ（フルサービスリゾルバ）** |
|---|---|---|
| 役割 | 自ドメインの情報を管理し、問合せに応答する | クライアントの代わりに名前解決を行い、結果を一時保存する |
| 問合せてくる相手 | インターネット上の誰でも（世界中のキャッシュDNSサーバ） | 自組織の利用者（スタブリゾルバ）だけであるべき |
| 攻撃者が狙うもの | ゾーン情報の収集、サービスの妨害、踏み台（リフレクション） | キャッシュの汚染（ポイズニング）、踏み台（オープンリゾルバ） |
| 守るべきもの | ゾーン情報の完全性と、応答の可用性 | キャッシュの完全性と、利用者以外に使わせないこと |

権威DNSサーバは「自分のゾーンについて誰にでも答える」のが仕事であり、キャッシュDNSサーバは「組織内の利用者のために調べて回る」のが仕事です。この仕事の違いが、アクセス制御の違い（権威サーバは問合せを広く受け付け、キャッシュサーバは利用者を限定する）にそのまま結びつきます。

### 1.2 正常な名前解決の流れと、攻撃者が割り込む位置

1.4 の図を、攻撃者が割り込む位置を書き加えて再掲します。

```

 PC(スタブリゾルバ) --①再帰的問合せ--→ キャッシュDNSサーバ ←─ [2.3] 外部の誰でも使える（オープンリゾルバ）
                                          |                    ←─ [2.2] 偽の応答を先に送り込む（ポイズニング）
                                          |--②--→ ルートサーバ
                                          |--③--→ .jp の権威サーバ
                                          |--④--→ example.jp の権威DNSサーバ ←─ [2.1] 誰にでもゾーン転送を許す
                                          |                                  ←─ [2.3] BOF・DoS で停止させる
 PC ←--⑤回答（203.0.113.10）----------- キャッシュDNSサーバ（結果をTTLの間キャッシュ）
```

## 2. DNSの脆弱性 ― 攻撃者は何を狙うか

2.6 でも触れたように、DNSについては次の3つの脆弱性が指摘されています。

| 脆弱性 | 攻撃者の狙い | 損なわれる特性 | 2.6 で見た攻撃 |
|---|---|---|---|
| ① ゾーン転送機能によって第三者に登録情報が不正利用される | 攻撃対象のホスト一覧を集める | 機密性 | ゾーン転送要求による登録情報の収集 |
| ② 不正な情報をキャッシュに登録できる | 利用者を偽サイトへ誘導する | 完全性（→ 結果として機密性） | DNSキャッシュポイズニング、カミンスキー攻撃 |
| ③ 不正なリクエストによってサービス不能状態となる | 名前解決を止める／他者への攻撃の踏み台にする | 可用性 | BOF・DoS攻撃、DNSリフレクション攻撃 |

### 2.1 ゾーン転送機能によって第三者に登録情報が不正利用される可能性がある

**ゾーン転送**とは、プライマリDNSサーバが保持するゾーン情報（リソースレコード一式）を、セカンダリDNSサーバへ複製する仕組みです。通常は**TCP 53番ポート**を使用し、**AXFR**（全体転送）や**IXFR**（差分転送）といった方式があります。

ゾーン転送要求は、セカンダリDNSサーバとプライマリDNSサーバの登録内容を同期させるため、前者（セカンダリ）から後者（プライマリ）に対して定期的に実行されます。自社の外向けDNSサーバ（プライマリDNSサーバ）に対しては、上位プロバイダのDNSサーバをセカンダリDNSサーバとするのが一般的とされてきました（現在は、DNSホスティング事業者や複数の事業者のサーバをセカンダリにする構成も広く見られます）。その場合、自社の外向けDNSサーバに対するゾーン転送要求は、上位プロバイダのDNSサーバから行われることになります。

問題は、一般的なDNSサーバプログラムの初期設定では、ゾーン転送要求について特に制限がない点です。そのままの設定で運用されていると、悪意ある第三者は情報収集のためにゾーン転送を実行できます。ゾーン情報には、ホスト名やIPアドレス、メールサーバの所在などが含まれるため、攻撃者はそれを攻撃対象の探索（**フットプリンティング**）に悪用します。

制限のないDNSサーバに対して、攻撃者が次のコマンドを打つだけで、ゾーンの中身がまるごと手に入ります。

```
$ dig axfr example.jp @198.51.100.53

example.jp.         3600 IN SOA   ns1.example.jp. hostmaster.example.jp. 2026093001 3600 900 604800 3600
example.jp.         3600 IN NS    ns1.example.jp.
example.jp.         3600 IN NS    ns2.example.net.
example.jp.         3600 IN MX    10 mail.example.jp.
www.example.jp.     3600 IN A     203.0.113.10
mail.example.jp.    3600 IN A     203.0.113.25
vpn.example.jp.     3600 IN A     203.0.113.40      ← リモートアクセスの入口
dev-web.example.jp. 3600 IN A     203.0.113.80      ← 開発用で要塞化が甘いかもしれない
example.jp.         3600 IN SOA   ns1.example.jp. hostmaster.example.jp. 2026093001 3600 900 604800 3600
```

攻撃者から見れば、これは「どのホストが存在し、どれが狙い目か」を示した地図です。`vpn` や `dev-` のような名前は、そのまま次の攻撃（第2章 2.2 のポートスキャン、2.4 のパスワードクラック）の標的リストになります。したがって、DNSサーバの管理者は、組織の構成情報を第三者に渡さないために、ゾーン転送の許可先を限定しなければなりません（対策は本ノートの 3.6）。

### 2.2 不正な情報をキャッシュに登録することができる可能性がある

幾つかのDNSサーバプログラムの仕様上・実装上の脆弱性により、名前解決要求への応答の際に、悪意あるサイトに誘導する不正な情報をキャッシュに登録させられてしまう可能性があります。この攻撃を**DNSキャッシュポイズニング**といいます。

攻撃者は、キャッシュDNSサーバが権威DNSサーバへ問合せを行った際に、正規の応答が届くよりも先に偽の応答を送り付けます。偽の応答をキャッシュDNSサーバに受け入れさせるには、応答パケットのあて先ポート番号や**トランザクションID**などを、キャッシュDNSサーバが送信した問合せに対応する正規の応答レコードと合致させる必要があります。キャッシュDNSサーバは「送信元IPアドレス・あて先ポート番号・トランザクションID・問合せ内容が一致した最初の応答」を正しいとみなすからです。

偽の応答が大量に届いている様子をパケットキャプチャで見ると、次のようになります（キャッシュDNSサーバ 192.0.2.53 が権威DNSサーバ 198.51.100.1 に問い合わせた直後の例）。

```
10:00:00.000100 IP 192.0.2.53.53 > 198.51.100.1.53: 4a1f+ A? x7k2q.example.jp. (34)       ← 正規の問合せ（ID 0x4a1f）
10:00:00.000180 IP 198.51.100.1.53 > 192.0.2.53.53: 0001*- 1/1/1 A 203.0.113.66 (98)     ← 偽応答（送信元を詐称、ID 0x0001）
10:00:00.000190 IP 198.51.100.1.53 > 192.0.2.53.53: 0002*- 1/1/1 A 203.0.113.66 (98)     ← 偽応答（ID 0x0002）
10:00:00.000200 IP 198.51.100.1.53 > 192.0.2.53.53: 0003*- 1/1/1 A 203.0.113.66 (98)     ← 偽応答（ID 0x0003）
   ...（IDを変えながら数千通）...
10:00:00.031000 IP 198.51.100.1.53 > 192.0.2.53.53: 4a1f*- 0/1/0 (87)                    ← 本物の応答（ここでは NXDOMAIN）
```

この例では、キャッシュDNSサーバが送信元ポート番号を53番に固定しているため、攻撃者はトランザクションIDだけを当てればよい状態です。しかし、かつては送信元ポート番号、あて先ポート番号ともに53番に固定する設定となっているDNSサーバが数多く存在し、DNSキャッシュポイズニング攻撃を容易にさせていました（2008年以降、主要なDNSサーバプログラムは送信元ポート番号のランダム化を標準の動作にしています。本ノートの 3.3 で解説）。また、トランザクションIDが**16ビット**（最大**65,536通り**）しかないことも攻撃を容易にさせています。

**カミンスキー攻撃**は、2008年にダン・カミンスキー氏が公表したDNSキャッシュポイズニングの手法です。従来の攻撃は、狙った名前（例：`www.example.jp`）がいったんキャッシュされると、キャッシュの有効期限（**TTL**）が切れるまで次の機会が来ないという制約がありました。カミンスキー攻撃では、攻撃者は存在しないランダムなサブドメイン（例：`random123.example.com`、上のキャプチャの `x7k2q.example.jp`）への問合せを繰り返し発生させることで、TTLを待たずに何度でも偽応答を送り込む機会を作り出します。さらに攻撃者は、偽応答の権威セクションに偽のNSレコード（「example.jp の権威サーバは ns.攻撃者のホストである」）を、追加情報セクションにそのNSのIPアドレス（グルーレコード）を含めます。これがキャッシュに受け入れられると、ドメイン全体の名前解決を乗っ取ることができるため、従来よりも格段に攻撃の成功率と影響範囲が大きくなりました。

ポイズニングが成功すると、そのキャッシュDNSサーバを使うすべての利用者が、TTLの間、偽のIPアドレスへ誘導されます。利用者は正しいURLを入力しているので、自力で異常に気づくことは困難です。キャッシュ（DNSの応答データ）の完全性が損なわれ、その結果、偽サイトに入力した認証情報やカード番号の機密性が損なわれる、という連鎖になります。

### 2.3 不正なリクエストによってサービス不能状態となる可能性がある

幾つかのDNSサーバプログラムの実装上の脆弱性により、DNSサーバは**BOF**（バッファオーバフロー）攻撃やDoS攻撃を受けて、正常なサービスが提供できなくなる可能性があります。攻撃者は、細工したDNSパケットを送り付けてDNSサーバプログラムを異常終了させたり、処理能力を超える問合せを送り付けたりします。DNSが止まると、Webもメールも名前解決ができずに使えなくなるため、影響は組織全体に及びます。

また、再帰的な問合せを誰からでも受け付ける設定（**オープンリゾルバ**）のDNSサーバは、**DNSリフレクション攻撃**（**DNSアンプ攻撃**）の踏み台として悪用されるおそれもあります。DNSリフレクション攻撃は、送信元IPアドレスを攻撃対象のものに詐称して、オープンリゾルバに対してサイズの大きな応答が返る問合せを大量に送信する攻撃です。問合せに比べて応答のデータ量が大きく増幅されるため、攻撃対象に大量のトラフィックが集中し、サービス不能状態に陥ります。

```
図:DNSリフレクション攻撃の流れ

 攻撃者 --(送信元を 203.0.113.200 に詐称、約60バイトの問合せ)--→ オープンリゾルバ（多数）
                                                                       |
 攻撃対象 203.0.113.200 ←--(数千バイトの応答が数十倍に増幅されて集中)---+
```

オープンリゾルバの管理者は、自分のサーバが攻撃されているわけではないため被害に気づきにくいのですが、結果として他組織への攻撃に加担してしまいます。外部から試すと、オープンリゾルバかどうかは次のように見分けられます。

```
$ dig www.example.com @203.0.113.53          ← 組織外から、ある組織のキャッシュDNSサーバに問い合わせる
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 22817
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
;; ANSWER SECTION:
www.example.com.   300  IN  A  198.51.100.80    ← 部外者にも再帰的に答えている＝オープンリゾルバ

（再帰的な問合せを制限したあと）
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 22818    ← 部外者の問合せを拒否している
```

> **補足：2.6 で見たその他の攻撃との関係**
> 2.6 では、存在しないランダムなサブドメインへの問合せを大量に発生させて権威DNSサーバを過負荷にする**DNS水責め攻撃**（ランダムサブドメイン攻撃）も学びました。これも③の「サービス不能状態」に分類され、本ノートの 3.7 で扱うキャッシュDNSサーバでの問合せ数の制限や、権威DNSサーバでの応答レート制限が対策になります。

## 3. DNSの脆弱性への対策 ― 管理者は何をどう設定すべきか

### 3.1 対策の全体像

DNSの脆弱性への対策は、次の9つです。「誰が」は、いずれもDNSサーバの管理者（ネットワーク・サーバの運用担当者）です。各対策がどの脆弱性に効き、1.2 で学んだ対策の4機能のどれにあたるかを先に一覧にしておきます。

| 対策 | 主に効く脆弱性 | 何のために | 機能 | 本ノートの節 |
|---|---|---|---|---|
| ① DNSサーバプログラムのバージョンアップ | ①②③すべて | 既知の脆弱性を攻撃者に突かせない | 予防・防止 | 3.2 |
| ② DNSの送信元ポート番号のランダム化 | ② | 偽応答を一致させにくくする | 予防・防止 | 3.3 |
| ③ DNSSEC | ② | 偽応答を署名検証で見抜く | 予防・防止（検知） | 3.4 |
| ④ 公開DNSサーバと内部DNSサーバの分離 | ① | 内部の構成情報を外に出さない | 予防・防止 | 3.5 |
| ⑤ コンテンツサーバとキャッシュサーバの分離 | ②③ | 機能ごとに最適なアクセス制御をかける | 予防・防止 | 3.5 |
| ⑥ ゾーン転送の制限 | ① | ゾーン情報をセカンダリ以外に渡さない | 予防・防止 | 3.6 |
| ⑦ 再帰的な問合せの制限 | ②③ | オープンリゾルバにしない | 予防・防止 | 3.7 |
| ⑧ キャッシュサーバへの問合せ数を制限 | ③ | DoS攻撃で資源を使い切られない | 予防・防止 | 3.7 |
| ⑨ DNSサーバプログラムのバージョン情報の隠蔽 | ①②③すべて | 攻撃者に脆弱性の手掛かりを与えない | 抑止・予防 | 3.2 |

### 3.2 DNSサーバプログラムのバージョンアップとバージョン情報の隠蔽（①・⑨）

**①DNSサーバプログラムのバージョンアップ**：DNSサーバの管理者は、BOFやDoSなど実装上の脆弱性を突かれないために、すべてのDNSサーバプログラムのバージョンを最新化し、パッチを適用すべきです。既知の脆弱性を放置しないことが、あらゆる対策の前提となります。BINDのように広く使われるDNSサーバプログラムは、毎年のように深刻度の高い脆弱性が公表されるため、管理者はJPRSやJPCERT/CCの注意喚起を継続的に確認し、公表から速やかに更新する運用を決めておく必要があります（脆弱性管理の進め方は第5章 5.3）。

**⑨DNSサーバプログラムのバージョン情報の隠蔽**：DNSサーバの管理者は、DNSサーバプログラムの設定によって、バージョン情報を任意の文字列に置き換えます（実際のバージョン情報を隠蔽します）。攻撃者は、バージョン情報から既知の脆弱性を特定しようとするため、隠蔽にはそれを困難にする効果があります。攻撃者は次のような問合せでバージョンを調べます。

```
$ dig @198.51.100.53 version.bind chaos txt +short
"9.11.3"                ← 隠蔽していない：古い版であることが攻撃者に伝わる

（named.conf の options に  version "unknown";  と書いたあと）
$ dig @198.51.100.53 version.bind chaos txt +short
"unknown"
```

ただし、隠蔽はあくまで攻撃者の手間を増やす補助策です。攻撃者はバージョンがわからなくても既知の攻撃を片端から試せるため、管理者は隠蔽を理由に①のバージョンアップを後回しにしてはいけません。

### 3.3 DNSの送信元ポート番号のランダム化（②）

**ソースポートランダマイゼーション**と呼ばれるもので、多くのDNSソフトウェアに実装されています。キャッシュDNSサーバは、問合せのたびに送信元ポート番号をランダムに変化させます。これにより、攻撃者が推測しなければならない組合せが「トランザクションID（約6.5万通り）×ポート番号（最大約6.5万通り）」に増加します。

$$
2^{16} \times 2^{16} = 2^{32} \approx 43\text{億通り}
$$

本ノート 2.2 のキャプチャで攻撃者が数千通りの偽応答を送っても、当たる確率は数十万分の一以下にまで下がります。これにより、カミンスキー攻撃をはじめとしたDNSキャッシュポイズニング攻撃が成功する確率を大幅に低減することができます。

ただし、ランダム化は「当たりにくくする」対策であって「当たっても見抜ける」対策ではありません。攻撃者が十分な帯域で長時間試行すれば、確率はゼロにはなりません。そこで、偽の応答を根本的に見抜く仕組みとして、次の DNSSEC が必要になります。

| 観点 | ソースポートランダマイゼーション | DNSSEC |
|---|---|---|
| 仕組み | 推測すべき値を増やす | 応答にデジタル署名を付けて検証する |
| 効果 | 偽応答が一致する確率を下げる | 偽応答を受け取っても採用しない |
| 導入する側 | キャッシュDNSサーバだけで完結 | 権威DNSサーバ（署名）とキャッシュDNSサーバ（検証）の両方、さらに親ゾーンの協力が必要 |
| 導入の容易さ | 容易（現在の主要実装では標準） | 鍵管理の運用が必要で難しい |

### 3.4 DNSSEC（DNS Security Extensions）（③）

**DNSSEC**（**DNS Security Extensions**）は、DNSのセキュリティ拡張方式であり、DNSキャッシュポイズニング攻撃への有効な対策となります。

**仕組み**：DNSSECでは、名前解決要求に対して応答を返すDNSサーバ（権威DNSサーバ）が、自身の秘密鍵を用いて応答レコードにデジタル署名を付加して送信します（実際には、ゾーンの管理者があらかじめゾーンデータに署名してRRSIGレコードとして登録しておき、権威DNSサーバはそれを応答に含めて返します）。応答を受け取ったリゾルバ（キャッシュDNSサーバ）は、DNSサーバの公開鍵を用いてデジタル署名を検証することで、応答レコードの**作成元の正当性**と、データが改ざんされていないこと（**完全性**）を確認します。攻撃者は秘密鍵を持たないため、偽の応答に正しい署名を付けることができず、検証に失敗した応答はキャッシュDNSサーバに採用されません。

**信頼の連鎖**：では、その「公開鍵」自体が偽物でないことはどう保証するのでしょうか。DNSサーバの公開鍵の正当性は、上位ドメインのDNSサーバが署名することで保証され、ルートゾーンを起点とした**信頼の連鎖**（**chain of trust**）によって検証されます。キャッシュDNSサーバは、ルートゾーンの公開鍵（**トラストアンカー**）だけを事前に設定しておけば、そこから順に下位ゾーンの鍵を検証していけます。

DNSSECで用いられる主なリソースレコードは次のとおりです。

| レコード | 役割 | どこに置くか |
|---|---|---|
| **DNSKEY** | ゾーンの署名検証に用いる公開鍵を格納する | 自ゾーン |
| **RRSIG** | リソースレコードに対するデジタル署名を格納する | 自ゾーン（署名対象のレコードごと） |
| **DS** | 子ゾーンの公開鍵のハッシュ値を格納し、親ゾーンに登録する（信頼の連鎖を構成する） | 親ゾーン |
| **NSEC／NSEC3** | 問合せ対象の名前が存在しないこと（不存在）を証明する | 自ゾーン |

実際のレコードは次のような見た目です（値は省略しています）。

```
; 親ゾーン .jp に登録されている DS（子ゾーン example.jp の KSK のハッシュ値）
example.jp.      3600 IN DS     12345 13 2 3A1B9C...E4F7            ← 鍵タグ 12345／アルゴリズム13（ECDSA P-256）／ハッシュ方式2（SHA-256）

; 子ゾーン example.jp の DNSKEY（公開鍵）
example.jp.      3600 IN DNSKEY 257 3 13 mdsswUyr3D...==          ← 257 = KSK（鍵署名鍵）、鍵タグ 12345
example.jp.      3600 IN DNSKEY 256 3 13 oJMRESz5E4...==          ← 256 = ZSK（ゾーン署名鍵）、鍵タグ 23456

; 子ゾーン example.jp の A レコードと、それに対する RRSIG（署名）
www.example.jp.  3600 IN A      203.0.113.10
www.example.jp.  3600 IN RRSIG  A 13 3 3600 20261030000000 20260930000000 23456 example.jp. kX3vQ...==
                               ↑対象型 ↑アルゴリズム ↑有効期限      ↑署名開始      ↑署名した鍵(ZSK)の鍵タグ
```

多くのゾーンでは、鍵を2種類に分けて運用します。**ZSK**（Zone Signing Key）はゾーン内のレコードに署名する鍵、**KSK**（Key Signing Key）はDNSKEYレコード（ZSKを含む公開鍵の集合）に署名する鍵です。親ゾーンのDSが指すのはKSKだけなので、ZSKを頻繁に交換しても親ゾーンへの再登録が要らない、という運用上の利点があります。信頼の連鎖を図にすると次のようになります。

```
図:DNSSECの信頼の連鎖

 ルートゾーン .    ─ DNSKEY（トラストアンカーとしてキャッシュDNSサーバに設定済み）
      │  DS(jp) に署名
 .jp ゾーン        ─ DNSKEY ← ルートの DS(jp) のハッシュ値と一致するか検証
      │  DS(example.jp) に署名
 example.jp ゾーン ─ DNSKEY(KSK) ← .jp の DS(example.jp) と一致するか検証
                    ─ DNSKEY(ZSK) ← KSK による RRSIG で検証
                    ─ A 203.0.113.10 ← ZSK による RRSIG で検証 → 正当な応答と判断
```

検証しているキャッシュDNSサーバに `dig +dnssec` で問い合わせると、応答は次のように見えます。

```
$ dig +dnssec www.example.jp A @192.0.2.53

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41237
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1
                   ↑ ad（Authenticated Data）：キャッシュDNSサーバが署名検証に成功した印

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags: do; udp: 1232
                         ↑ do（DNSSEC OK）：DNSSECのレコードも返してほしいという要求（EDNS0を使う。4節）

;; ANSWER SECTION:
www.example.jp.   3600 IN A     203.0.113.10
www.example.jp.   3600 IN RRSIG A 13 3 3600 20261030000000 20260930000000 23456 example.jp. kX3vQ...==
```

一方、署名が改ざんされていたり、有効期限が切れていたりすると、検証するキャッシュDNSサーバは応答を返さず、`status: SERVFAIL` になります。これは「偽の答えを返すくらいなら答えない」というフェールセーフな動作です。裏を返せば、ゾーンの管理者が署名の更新（RRSIGの有効期限切れ前の再署名）や鍵の交換（KSKロールオーバ時の親ゾーンのDS更新）を誤ると、正規の利用者までそのドメインを名前解決できなくなります。DNSSECを導入する組織は、署名の自動更新と期限の監視を運用手順に組み込むべきです。

> **DNSSECは暗号化ではない**
> DNSSECはデータの**完全性と作成元の正当性**を保証する仕組みであり、通信内容を暗号化するものではありません。そのため、盗聴を防ぐ（機密性を確保する）効果はありません。利用者とキャッシュDNSサーバの間の問合せ内容を盗聴から守りたい場合は、DNS通信をTLSで暗号化する DNS over TLS（DoT、853/TCP）や DNS over HTTPS（DoH、443/TCP）を使います。DNSSECとDoT／DoHは目的が異なり、組み合わせて使うものです。

### 3.5 公開DNSサーバと内部DNSサーバ、コンテンツサーバとキャッシュサーバの分離（④・⑤）

**④公開DNSサーバと内部DNSサーバの分離**：DNSサーバの管理者は、インターネットに公開する情報を管理する公開DNSサーバと、社内ネットワーク向けの内部DNSサーバを分離して設置します。

- 公開DNSサーバには内部のゾーン情報は一切登録しない
- 内部DNSサーバには必要に応じて公開DNSサーバに登録されているゾーン情報も登録する

これにより、内部ネットワークの構成情報がインターネット側に漏えいすることを防ぎます。仮に公開DNSサーバのゾーン転送制限に不備があっても、そもそも内部のホスト名が登録されていなければ、本ノート 2.1 の dig axfr で攻撃者に渡るのは公開して差し支えない情報だけです。

**⑤コンテンツサーバとキャッシュサーバの分離**：前記に加え、DNSサーバの管理者は、DNSサーバの機能を次のように分離し、機能ごとに別個のサーバを設置します（公開用と内部用で最低**4台**のDNSサーバを設置）。

**図：DNSサーバの分離運用の例**

| 区分 | サーバ | 設置場所 | 役割 | 問合せを受け付ける相手 |
| --- | --- | --- | --- | --- |
| 公開用 | 公開コンテンツサーバ | DMZ | インターネットからの自ドメインに関する問合せに応答する。再帰的な問合せは受け付けない | インターネット全体 |
| 公開用 | 公開キャッシュサーバ | DMZ | DMZ上のサーバ（メールサーバ、プロキシサーバなど）からの外部ドメインの名前解決を代行する | DMZ上のサーバだけ |
| 内部用 | 内部コンテンツサーバ | 内部ネットワーク | 内部ネットワークのゾーン情報を管理し、社内ホストからの問合せに応答する | 社内ホストだけ |
| 内部用 | 内部キャッシュサーバ | 内部ネットワーク | 社内ホストからの外部ドメインの名前解決を代行する | 社内ホストだけ |

```
図:DNSサーバの分離運用の配置イメージ

 インターネット ──[FW]──┬── DMZ ──────────────────────────────────┐
                        │  公開コンテンツサーバ（再帰なし・誰からでも自ゾーンの問合せに応答）
                        │  公開キャッシュサーバ（DMZのメール・プロキシサーバからの再帰だけ許可）
                        └──[FW]── 内部ネットワーク ───────────────────┐
                                   内部コンテンツサーバ（内部ゾーン。社内ホストだけに応答）
                                   内部キャッシュサーバ（社内ホストからの再帰だけ許可）
```

コンテンツサーバとキャッシュサーバを同一サーバで兼用すると、キャッシュポイズニングの被害がコンテンツ情報にも及んだり、オープンリゾルバとして悪用されたりする危険性が高まります。兼用サーバでは「自ゾーンの問合せには誰にでも答える」と「再帰的な問合せは社内だけに答える」という相反するアクセス制御を1台で両立させなければならず、設定ミスが起きやすいからです。機能を分離することで、それぞれに最適なアクセス制御を適用できます。

### 3.6 ゾーン転送の制限（⑥）

DNSサーバの管理者は、ゾーン情報を第三者に渡さないために、ゾーン転送を次のように制限します。

- インターネットからのゾーン転送要求を受け付ける必要がない場合には、公開DNSサーバに対する53/TCPのアクセスをファイアウォールでフィルタリングする
- ゾーン転送はセカンダリDNSサーバにのみ許可するよう設定ファイルで設定する（例：BINDの`allow-transfer`オプション）

BINDでの設定の見た目は次のとおりです。

```
// named.conf（公開コンテンツサーバ = プライマリ）
options {
    version "unknown";                    // ⑨ バージョン情報の隠蔽
    recursion no;                         // コンテンツサーバなので再帰的な問合せは受け付けない
    allow-transfer { none; };             // 既定ではゾーン転送を誰にも許可しない
};

zone "example.jp" {
    type primary;
    file "example.jp.zone";
    allow-transfer { 198.51.100.53; };    // セカンダリDNSサーバのアドレスだけに許可する
    also-notify    { 198.51.100.53; };    // 更新時にセカンダリへ通知する
};
```

許可されていない相手がゾーン転送を要求すると、攻撃者の側では `; Transfer failed.` と表示され、DNSサーバのログには次のような行が残ります。管理者は、このログが繰り返し出ていれば、誰かが情報収集を試みている兆候として監視対象にすべきです。

```
30-Sep-2026 10:15:42.117 security: error: client @0x7f3a2c 203.0.113.99#40123 (example.jp): zone transfer 'example.jp/AXFR/IN' denied
```

IPアドレスによる制限に加え、プライマリとセカンダリで共有鍵を持ち、ゾーン転送のメッセージに鍵付きのハッシュ値（MAC）を付けて相手を認証する **TSIG**（Transaction Signature）を使うと、送信元IPアドレスを詐称されても転送を許さない、より強い制限になります。

> **補足：53/TCPを一律に遮断してはいけない**
> 以前は「ゾーン転送が不要なら53/TCPをファイアウォールで遮断する」ことが対策として広く紹介されていました。しかし近年はDNS応答サイズの増大に伴い、通常の名前解決でもTCPが使用される場合があります（後述のTCPフォールバック）。そのため、53/TCPを一律に遮断すると名前解決に支障が出るおそれがある点に注意が必要です。現在はDNSの仕様上もTCPへの対応が必須とされており、ゾーン転送の制限は、DNSサーバの設定による許可先の限定を基本とします。

### 3.7 再帰的な問合せの制限と問合せ数の制限（⑦・⑧）

**⑦再帰的な問合せの制限**：DNSサーバの管理者は、キャッシュサーバに対して再帰的な問合せを許可するホストを、DNSサーバの設定ファイルに登録します。例えば、インターネット上のドメイン名についての名前解決を許可するのは自組織のホストのみに制限します（例：BINDの`allow-recursion`オプション）。これにより、オープンリゾルバとしての悪用や、外部からのキャッシュポイズニング攻撃を防ぎます。外部の攻撃者は、カミンスキー攻撃の「ランダムなサブドメインへの問合せ」を自分でキャッシュDNSサーバに送れなくなるため、攻撃の起点そのものを失います。

**⑧キャッシュサーバへの問合せ数を制限**：DNSサーバの管理者は、キャッシュサーバに対するクライアントからの問合せ（再帰的な問合せ）数を適切な値に設定することで、DoS攻撃に備えます。上限がないと、大量の問合せでメモリや同時処理数を使い切られ、正規の利用者の名前解決まで止まってしまいます。

```
// named.conf（内部キャッシュサーバ）
acl "internal" { 192.0.2.0/24; };         // 社内ホストのアドレス範囲

options {
    recursion yes;
    allow-recursion   { internal; };      // ⑦ 再帰的な問合せは社内ホストだけに許可する
    allow-query-cache { internal; };      // ⑦ キャッシュ内容の参照も社内ホストだけに許可する
    recursive-clients 1000;               // ⑧ 同時に処理する再帰的な問合せの数に上限を設ける
    version "unknown";                    // ⑨
    // dnssec-validation auto;            // ③ DNSSECの署名検証を行う（現在のBINDでは既定で有効）
};
```

権威DNSサーバの側では、同じ内容の応答を短時間に大量に返さないよう **応答レート制限**（RRL：Response Rate Limiting。BINDでは `rate-limit` オプション）を設定しておくと、自組織の権威DNSサーバがDNSリフレクション攻撃の反射役に使われる被害を抑えられます。

> **試験対策のポイント**
> DNSキャッシュポイズニングの仕組みや、ソースポートランダマイゼーション、DNSSEC、オープンリゾルバ対策などは、情報処理安全確保支援士試験の午前・午後問題（現在の科目A-2・科目B）の双方で繰り返し出題されている頻出テーマです。各対策が「どの脆弱性」に「どのように」効果があるのかを整理して理解しておきましょう。

## 4. 512オクテット制限への対応 ― TCPフォールバックとEDNS0

### 4.1 512オクテット制限とTCPフォールバック

DNSの名前解決では通常UDP 53番ポートを使用しますが、このとき一つのパケットに格納できるデータは**512オクテット**に制限されています。データが512オクテットを超える場合、DNSサーバは**TC**（**Truncation**）**ビット**をセットして返信することによって、データが切り捨てられたことを問合せ元のホストに伝えます。それを受け取った問合せ元のホストは、TCP 53番ポートを使用して再度問合せを行います。この仕組みを**TCPフォールバック**といいます。

```
$ dig +ignore +noedns example.jp DNSKEY @198.51.100.53
;; flags: qr aa tc rd; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 0
               ↑ tc：512オクテットに収まらず切り捨てた印。通常の dig はここで自動的に TCP で再問合せする
```

TCPフォールバックでは、コネクション型のTCPを使用するため、UDPを使用する場合と比べてDNSサーバへの負荷が高まるとともに、応答時間が遅くなるという問題があります（1.4 の 3.2 で学んだ3ウェイハンドシェイクの往復が、問合せのたびに追加されるためです）。

### 4.2 EDNS0

この問題を解決するものとして、**EDNS0**（**Extension mechanisms for DNS version 0**）があります。EDNS0はDNSの拡張機構であり、通信可能であればUDPパケットサイズを最大**65,535オクテット**まで拡張することができます。EDNS0では、問合せ元が**OPTレコード**と呼ばれる疑似リソースレコードを付加し、自身が受信可能なUDPパケットサイズをDNSサーバに通知します。DNSサーバは、通知されたサイズまでのデータをUDPで返信することができます。本ノート 3.4 の dig の出力にあった `; EDNS: version: 0, flags: do; udp: 1232` が、このOPTレコードの中身です（受信可能サイズ1,232オクテット、DNSSECのレコードも要求）。

IPv6の普及によって**AAAAレコード**が増加したことや、DNSSECの導入によってデジタル署名や公開鍵などのデータが応答に含まれるようになったことにより、応答データが512オクテットを超えるケースがより現実的なものとなってきています。こうしたことから、IPv6やDNSSECのデータを取り扱うDNSサーバについては、EDNS0をサポートすることが必須とされています。

> **EDNS0の運用上の注意**
> UDPパケットサイズを大きくしすぎると、経路上でIPフラグメンテーションが発生し、パケットの喪失やフラグメントを悪用した攻撃の原因となります。そのため、2020年の「**DNS Flag Day**」では、EDNS0のバッファサイズの推奨値として**1,232オクテット**が示されています。また、ファイアウォールなどで512オクテットを超えるDNSパケットやTCP 53番ポートの通信を遮断していると、名前解決に失敗する場合があるため注意が必要です。

ネットワークの管理者は、DNSSECを導入するときに、DNSサーバの設定だけでなく経路上のファイアウォールやIPSのルールも見直すべきです。「512オクテットを超えるUDPのDNS応答は異常」として遮断する古いルールが残っていると、署名付きの大きな応答だけが届かず、特定のドメインだけ名前解決に失敗するという、原因の分かりにくい障害になるからです。

## 5. 確認問題

### 5.1 理解度チェック

- □**Q1**：DNSの主な脆弱性を3点挙げよ。
- □**Q2**：Q1で挙げた脆弱性を狙った攻撃を受けた場合の影響について述べよ。
- □**Q3**：DNSSECの仕組みと導入による効果について述べよ。
- □**Q4**：セキュリティを考慮したDNSサーバの構成、設定について述べよ。
- □**Q5**：DNSの512オクテット制限とEDNS0について述べよ。

> **解答例**
> - **Q1**：①ゾーン転送機能によって第三者に登録情報が不正利用される可能性、②不正な情報をキャッシュに登録される（DNSキャッシュポイズニング）可能性、③不正なリクエスト（BOF・DoS攻撃）によってサービス不能状態となる可能性、の3点。オープンリゾルバがDNSリフレクション攻撃の踏み台になることも③に含まれる。
> - **Q2**：①では、攻撃者がホスト名・IPアドレス・メールサーバの所在を入手し、攻撃対象の探索（フットプリンティング）に悪用する。②では、そのキャッシュDNSサーバを使う利用者がTTLの間、偽サイトに誘導され、認証情報などを盗まれる。カミンスキー攻撃ではドメイン全体の名前解決が乗っ取られる。③では、名前解決が止まってWebやメールが使えなくなる。オープンリゾルバの場合は、他組織へのDNSリフレクション攻撃に加担してしまう。
> - **Q3**：権威DNSサーバ側（ゾーンの管理者）が秘密鍵でリソースレコードにデジタル署名（RRSIG）を付け、リゾルバ（キャッシュDNSサーバ）が公開鍵（DNSKEY）で署名を検証する。公開鍵の正当性は親ゾーンに登録したDS（公開鍵のハッシュ値）によって、ルートゾーンを起点とする信頼の連鎖で保証する。これにより、リゾルバは応答の作成元の正当性と完全性を確認でき、キャッシュポイズニングの偽応答を採用しなくなる。暗号化は行わないため、盗聴は防げない。
> - **Q4**：公開DNSサーバと内部DNSサーバを分離し、さらにコンテンツサーバとキャッシュサーバを分離して最低4台で構成する。公開DNSサーバには内部のゾーン情報を登録しない。設定面では、ゾーン転送をセカンダリDNSサーバに限定し、キャッシュサーバの再帰的な問合せを自組織のホストに限定し、問合せ数に上限を設け、バージョン情報を隠蔽する。さらにソフトウェアを最新化し、ソースポートランダマイゼーションとDNSSECを有効にする。
> - **Q5**：UDPのDNSメッセージは512オクテットに制限されており、超える場合はTCビットを立てて返し、問合せ元はTCP 53番で再問合せする（TCPフォールバック）。TCPは負荷と遅延が大きいため、EDNS0で問合せ元がOPTレコードにより受信可能なUDPサイズ（最大65,535オクテット）を通知し、大きな応答をUDPのまま受け取れるようにする。IPv6（AAAAレコード）やDNSSECを扱うDNSサーバではEDNS0のサポートが必須で、フラグメンテーションを避けるため1,232オクテットが推奨値とされる。

### 5.2 演習問題（過去問題）

DNSSECに関する記述のうち、適切なものはどれか。

- ア　権威DNSサーバが、DNS問合せに対する応答時に、リソースレコードを公開鍵暗号方式で暗号化することによって、通信経路上の盗聴を防ぐ。
- イ　権威DNSサーバが、リソースレコードの受信時にデジタル署名を検証することによって、データの作成元の正当性とデータの完全性を確認する。
- ウ　リゾルバが、DNS問合せに対する応答時に、リソースレコードを公開鍵暗号方式で暗号化することによって、通信経路上の盗聴を防ぐ。
- エ　リゾルバが、リソースレコードの受信時にデジタル署名を検証することによって、データの作成元の正当性とデータの完全性を確認する。

*［情報処理安全確保支援士試験・R5秋・午前Ⅱ］*

> **解答・解説**
> DNSSEC（DNS Security Extensions）は、DNSのセキュリティ拡張方式であり、次のようにしてリソースレコード作成元の正当性とデータの完全性を検証します。
>
> - 名前解決要求に対して応答を返すDNSサーバ（権威DNSサーバ）が、自身の秘密鍵を用いてリソースレコードにデジタル署名を付加して送信する。
> - 応答を受け取ったリゾルバは、権威DNSサーバの公開鍵を用いてデジタル署名を検証し、リソースレコードの作成元の正当性と、データが改ざんされていないこと（完全性）を確認する。
>
> したがって、**エ**が適切です。
>
> - ア、ウ：DNSSECはリソースレコードの暗号化を行わないため、通信経路上の盗聴を防ぐ効果（機密性の確保）はありません。
> - イ：デジタル署名の検証を行うのは、応答を受信するリゾルバであり、権威DNSサーバではありません。
>
> **解答：エ**

「署名するのは権威DNSサーバ（秘密鍵）、検証するのはリゾルバ（公開鍵）」「暗号化はしない」という2点を入れ替えた選択肢が定番です。デジタル署名の一般原則（署名者が秘密鍵で署名し、受信者が公開鍵で検証する）に当てはめれば迷わずに解けます。

## 6. 試験対策まとめ（重要ポイント）

### 6.1 知識の確認（科目A-2向け）

- **DNSの3つの脆弱性**：ゾーン転送による情報漏えい（機密性）、キャッシュポイズニング（完全性）、BOF・DoS・オープンリゾルバの悪用（可用性）。
- **ゾーン転送**：セカンダリからプライマリへ要求する。TCP 53番、AXFR（全体）／IXFR（差分）。許可先はセカンダリに限定（BINDの `allow-transfer`）。TSIGで相手を認証するとさらに強い。
- **キャッシュポイズニングの成立条件**：送信元IPアドレス・ポート番号・トランザクションID（16ビット＝65,536通り）が一致した偽応答が本物より先に届くこと。
- **カミンスキー攻撃**：存在しないランダムなサブドメインを問い合わせさせてTTL待ちを回避し、権威セクションの偽NSでドメイン全体を乗っ取る（2008年公表）。
- **ソースポートランダマイゼーション**：推測空間を約6.5万×約6.5万に拡大し、成功確率を下げる。「確率を下げる」対策であり、根本対策はDNSSEC。
- **DNSSEC**：署名＝権威DNSサーバ（秘密鍵）、検証＝リゾルバ（公開鍵）。完全性と作成元の正当性を保証し、**暗号化はしない**（盗聴は防げない。暗号化はDoT／DoH）。
- **DNSSECのレコード**：DNSKEY（公開鍵）、RRSIG（署名）、DS（子ゾーンの公開鍵のハッシュ値、親ゾーンに登録）、NSEC／NSEC3（不存在証明）。KSK と ZSK の役割の違い。
- **dig の読み方**：`ad` フラグ＝検証成功、`do` フラグ＝DNSSECの要求、`SERVFAIL`＝検証失敗の可能性、`REFUSED`＝再帰の拒否、`tc` フラグ＝切り捨て。
- **サーバの分離**：公開用／内部用 × コンテンツ／キャッシュ で最低4台。兼用はポイズニングの波及とオープンリゾルバ化の原因。
- **オープンリゾルバ対策**：`allow-recursion` で再帰的な問合せを自組織に限定。DNSリフレクション攻撃の踏み台化とポイズニングの両方を防ぐ。
- **512オクテット制限**：超えるとTCビット → TCPフォールバック。EDNS0（OPTレコード、最大65,535オクテット）で解決。DNS Flag Day 2020 の推奨値は1,232オクテット。53/TCPの一律遮断は誤り。

### 6.2 記述式で問われる観点（科目B向け）

- **設定の問題点を指摘する**：named.conf やネットワーク構成図を読み、「キャッシュサーバが外部からの再帰的な問合せを受け付けている（オープンリゾルバである）」「ゾーン転送の許可先が限定されていない」「コンテンツとキャッシュを1台で兼用している」と、どの設定がどの脆弱性につながるかを指摘できるようにする。
- **対策を「誰が・何を・何のために・どうする」で書く**：例「DNSサーバの管理者は、外部の第三者によるキャッシュポイズニングとDNSリフレクション攻撃への悪用を防ぐために、キャッシュDNSサーバの再帰的な問合せを社内のアドレス範囲からのものだけに制限する」。
- **DNSSECの効果と限界を説明する**：「偽の応答を署名検証で検出して採用しないため、キャッシュポイズニングを防げる」「ただし暗号化しないので盗聴は防げない」「署名の期限切れや鍵交換の誤りで正規の名前解決まで失敗する（SERVFAIL）」の3点をセットで書けるようにする。
- **ランダム化とDNSSECの使い分け**：ソースポートランダマイゼーションはキャッシュDNSサーバ単独で導入できる確率的な対策、DNSSECは権威側と検証側の双方の対応が必要な根本対策、という違いを理由付きで説明させる設問に備える。
- **ログから兆候を読む**：ゾーン転送の拒否ログ、特定ドメインへの大量のランダムなサブドメイン問合せ、外部アドレスからの再帰的な問合せの急増などを、情報収集・ポイズニングの試行・水責め攻撃の兆候として判断できるようにする。
- **障害の切り分け**：DNSSEC導入後に特定ドメインだけ名前解決に失敗する事例では、EDNS0の大きな応答やTCP 53番をファイアウォールが遮断していないかを疑う、という観点を答えられるようにする。
