# 情報セキュリティ対策技術(2)アクセス制御と認証

## 6.8 シングルサインオンによる認証

システムの複雑化に伴い需要が高まっている、シングルサインオンによる認証システムについて解説する。

### 6.8.1 SSOの概要

シングルサインオン(Single Sign-On:SSO)は、認証を必要とするシステムが複数ある環境で使われる認証システムである。最初に1回認証に成功すれば、利用するシステムが変わっても、利用を許可されたシステムであれば認証プロセスを経ずにそのまま利用できる。

実際には、アクセスするサーバが変わるたびにバックグラウンドでユーザ認証が行われている。ただし、ユーザが認証プロセスを意識しなくて済む仕組みになっている。

#### SSOの必要性

社内ネットワークなどでユーザ認証を必要とするシステムが増えると、ユーザは複数の認証情報(ユーザIDとパスワードなど)を管理しなければならない。さらに、利用するシステムが変わるたびに認証情報を入力する必要がある。

この状態では、ユーザの利便性が損なわれる。また、認証情報の管理が煩雑になり、次のような行動を招いてかえってセキュリティレベルを下げるおそれがある。

- パスワードの使い回し
- 単純なパスワードの設定
- パスワードのメモ書き

こうした問題を解決するには、ユーザに必要以上の負担をかけずに、必要かつ十分なセキュリティを確保できる認証システムが求められる。このような背景からSSOが誕生した。

#### SSO導入のポイント

SSOを導入する際には、主に次の点を検討する必要がある。

**① 利用者のユーザIDとパスワードの統一**

既存の環境では、複数のユーザIDやパスワードなどの認証情報が使われている。これらを一つのDBやディレクトリサーバに集約することを前提に、実現方法を決定する。集約が難しい場合は、複数のDBなどを相互に連携させて同期をとる方法もある。

**② 複数のアプリケーションの認証インタフェースの統合**

ユーザ認証を行う複数のアプリケーションについて、認証インタフェースをWebブラウザを用いた方式に統一する。

**③ 各アプリケーションに対するアクセス制御の実施**

アプリケーション単位のアクセス制御には、次のような処理がある。

- ユーザIDごとに、システムリソースへのアクセスの可否を制御する処理
- ログインセッションのタイムアウトを厳密に管理する処理

特に高いセキュリティレベルが求められるアプリケーションには、認証成立後も定期的に認証を繰り返す機能を盛り込むべきである。高度なセッション管理を行う場合は、アクセス制御の機能と統合認証の機能が連携して動作するように設計する必要がある。

また、各アプリケーションのアクセス制御を適切に行えるよう、アクセス制御に関するポリシや手順書などを整備しておくことも重要である。

### 6.8.2 SSOを実現する仕組み

SSOでは、ユーザがシステムを利用するたびに識別情報を入力する必要がない。そのため、システム利用に伴う労力やストレスが軽減される。

ただし、SSOを利用できるのは主にWebアプリケーションシステムであり、すべてのシステムに適用できるわけではない。

SSOを実現する主な方式には、次の三つがある。

1. Cookieを用いたユーザ識別情報の共有
2. リバースプロキシサーバによるユーザ識別・認証の集約化(共有)
3. SAMLによるサーバ間でのユーザ識別情報の交換(共有)

①と②はSSOの誕生当初から用いられている方式であり、現在も多くのサイトで稼働している。一方、③はドメイン名の異なる複数のサイトにまたがる大規模なシステム環境などで、SSOを実現する仕組みとして普及しつつある。

ここでは、まず①と②の方式によるSSOシステムを解説する。

#### Cookieを用いたSSOシステム

Cookieを用いたSSOシステムは、**エージェント型SSO**とも呼ばれる。

この方式では、認証が必要なWebサーバにプラグインソフトウェア(エージェント)をインストールする。認証の際には、このエージェントが認証サーバにアクセスして認証プロセスを代行する。

1. 最初のログインでは、エージェントがクライアントの入力したユーザ情報を基に認証サーバにアクセスし、認証を行う。
2. エージェントは、認証済みの識別情報をCookieに入れてクライアントに返す。
3. 別のサーバにアクセスする際は、そのサーバのエージェントがクライアントのCookieを基に認証サーバにアクセスし、認証を行う。

**図:エージェント型SSO認証システムの動作イメージ**

```
[クライアント] ──(1) ログイン──▶ [Webサーバ A + エージェント] ──▶ [認証サーバ]
      ◀──(2) 認証済み識別情報を格納したCookie──
[クライアント] ──(3) Cookie提示──▶ [Webサーバ B + エージェント] ──(Cookie検証)──▶ [認証サーバ]
```

#### リバースプロキシ型SSOシステム

この方式では、すべてのWebサーバへのアクセスを、認証サーバを兼ねたプロキシサーバ(リバースプロキシサーバ)に集約してユーザ認証を行う。

クライアントがログインに成功すると、認証サーバが目的のサーバに代理でアクセスする。クライアントはWebサーバに直接アクセスせず、常にリバースプロキシサーバを経由する。

**図:リバースプロキシ型SSO認証システムの動作イメージ**

```
                                     ┌──▶ [Webサーバ A]
[クライアント] ──▶ [リバースプロキシ ├──▶ [Webサーバ B]
                   (認証サーバ)]     └──▶ [Webサーバ C]
```

#### エージェント型とリバースプロキシ型の比較

エージェント型とリバースプロキシ型を比較すると、次の表のようになる。

**表:エージェント型とリバースプロキシ型のメリット・デメリット**

| 方式 | メリット | デメリット |
|---|---|---|
| エージェント型 | ・導入にあたってネットワーク構成を変更する必要がない<br>・特定のサーバに負荷が集中せず、システムの規模が大きくなっても対応できる | ・各Webサーバにエージェントをインストールする必要がある<br>・エージェントが対応していないWebサーバには使用できない |
| リバースプロキシ型 | ・Webサーバにソフトウェアなどをインストールする必要がない<br>・Webサーバの種類(OSやソフトウェア)に依存しない | ・認証サーバ(リバースプロキシ)にアクセスが集中する<br>・導入にあたってネットワーク構成を変更する必要がある<br>・リバースプロキシが単一障害点になりやすい |

SSO製品を選定する際は、既存のWebサーバの種類やネットワーク構成を十分に考慮し、最適な製品を選ぶ必要がある。

近年は、SSOによってWebサーバなどのシステムリソースに強力なアクセス制御を行う製品が数多くリリースされている。各製品は、次のような様々な認証方式をサポートしている。

- 固定式のユーザIDとパスワード
- OTP(ワンタイムパスワード)
- RADIUS
- ディレクトリサーバとの連携
- デジタル証明書

これらを柔軟に組み合わせることで、セキュアなユーザ認証とアクセス制御を実現できる。

#### エージェント型、リバースプロキシ型の制限事項など

エージェント型は、Cookieを用いてサーバ間でユーザの識別情報を共有することでSSOを実現している。Cookieに依存した方式であるため、次のような制限がある。

- Cookieを共有できる範囲内(同一ドメイン内)でしか、SSOシステムを構築できない
- クライアントがCookieの使用を制限している場合は利用できない

一方、リバースプロキシ型にはCookieによる制限はない。しかし、ネットワーク構成の制約があるため、複数のドメインにまたがるシステムでSSOを実現するのは難しい。複数のドメイン間でいかに安全に認証情報をやり取りするかが大きな課題となる。

そのため現在では、これらの問題を解決するものとして、SAMLを用いたSSOシステムが普及しつつある。

#### SAMLによるSSOシステム

SAML(Security Assertion Markup Language)は、ユーザIDやパスワードなどの認証情報を安全に交換するためのXML仕様であり、OASISによって策定された。

SAMLはSOAPをベースとしており、認証情報などを「アサーション(Assertion)」と呼ばれるXML形式の情報として記述し、交換する。アサーションには次の3種類がある。

- **認証アサーション**:認証結果の伝達に用いる
- **属性アサーション**:属性情報の伝達に用いる
- **認可決定アサーション**:アクセス制御情報の伝達に用いる

SAMLによるSSOシステムは、次の二つによって構成される。

- **Identity Provider(IdP)**:ユーザのアカウント情報の管理と認証を行う
- **Service Provider(SP)**:ユーザにサービスを提供する

相互に認証を行うIdPとSPは、事前にアカウント情報を連携(ID連携)させ、"Circle of Trust"(信頼の輪)を形成する。

IdPとSPの間では、要求メッセージ(SAMLRequest)と応答メッセージ(SAMLResponse)を送受信する。これらのメッセージをHTTPやSOAPなどのプロトコルにマッピングする方法を**バインディング**といい、次のような種類がある。

- **SOAPバインディング**:SOAPを用いてアサーションを送る。
- **HTTP Redirectバインディング**:Base64エンコードしたアサーションをHTTP GETメソッドで送る。
- **HTTP POSTバインディング**:Base64エンコードしたアサーションをHTTP POSTメソッドで送る。
- **HTTP Artifactバインディング**:ArtifactをHTTPリダイレクトで送る。

HTTP RedirectバインディングやHTTP POSTバインディングなどでは、アサーションそのものをブラウザのリダイレクトによって引き渡す。しかし、アサーションはサイズが大きい。そこで、アサーションの代わりにArtifact(アサーションを参照するための識別子)を引き渡すようにしたのが、HTTP Artifactバインディングである。Artifactを受け取ったSPは、SOAPなどを用いてIdPから直接アサーションを取得する。

> **試験に出る**
> SSOやSAMLは、情報セキュリティスペシャリスト試験や情報処理安全確保支援士試験の午後問題で繰り返し出題されている。
> - Cookieを用いたSSOシステムや、SSOシステムのプロトコル、システムや認証の設計に関する問題が出題された。
> - 情報処理安全確保支援士試験の平成29年度午後Ⅰ問3では、SAMLの導入を題材にした問題が出題された。
> - 情報処理安全確保支援士試験の平成30年度午後問1では、SAMLが出題された。

> **用語解説:リダイレクト**
> Webサーバにアクセスしたクライアントを、別のURL(Uniform Resource Identifier)に参照させることで、自動的に別のページへ転送すること。

HTTP Redirectバインディングを用いたSSOシステムの例を次に示す。

1. ユーザがSPのBにアクセスし、サービスを要求する。このとき、SPのBの有効なCookieが既にあれば、そのまま⑥に進む。
2. ユーザから有効なCookieの提示がなかった場合、SPのBはSAMLRequestメッセージを発行し、ユーザをIdPにリダイレクトする。
3. ユーザはIdPのログイン画面でIDとパスワードを入力し、認証を受ける。
4. IdPはアサーションを生成し、デジタル署名を付したSAMLResponseメッセージを発行して、ユーザをSPのBにリダイレクトする。
5. SPのBは、SAMLResponseメッセージのデジタル署名やアサーションの内容をチェックし、Cookieを発行する。
6. SPのBはユーザにサービスを提供する。以降、このユーザは"Circle of Trust"内の他のSPにも、再度認証を受けずにアクセスできる。

**図:SAML(HTTP Redirectバインディング)によるSSOの動作イメージ**

```
[ユーザ(ブラウザ)]     [SP B]                    [IdP]
      │ ① サービス要求 ──▶ │                        │
      │ ◀── ② SAMLRequest を付けてリダイレクト ──── │
      │ ──────────────────────────────────────────▶ │ ③ ID・パスワードで認証
      │ ◀── ④ 署名付き SAMLResponse を付けてリダイレクト
      │ ──▶ │ ⑤ 署名・アサーション検証、Cookie発行
      │ ◀── │ ⑥ サービス提供
```

### 6.8.3 アイデンティティ管理

#### アイデンティティ管理(ID管理)の概要

ディレクトリサービスやSSO認証システムなどの技術を活用し、運用体制やワークフローなども整備する。これにより、ユーザ情報をより効率的かつセキュアに管理・コントロールする手法を「アイデンティティ管理(ID管理)」といい、近年注目されている。

一般に、ID管理は次のようなシステムと、それを運用管理するためのポリシ、手順、体制などによって実現される。

- **ディレクトリシステム**:ユーザの識別情報や属性情報(アイデンティティ情報)を一元的に管理する。
- **プロビジョニングシステム**:ユーザのアイデンティティ情報に基づいて、アクセス権限やリソースを適切に割り当てる。
- **アクセス制御(管理)システム**:ユーザのアイデンティティ情報に基づいて、システムリソースへのアクセス制御を行う。
- **ワークフローシステム**:アイデンティティ情報の追加・変更・削除に関する申請・承認・差戻しなどのワークフローや、証跡の管理などを行う。

> **試験に出る**
> 情報セキュリティスペシャリスト試験の午後Ⅰでは、ID管理に関する問題が出題された。

> **用語解説:プロビジョニング(provisioning)**
> あらかじめ設備やリソースなどを準備しておき、ユーザの要求に応じて提供することを指す用語。ID管理では、入社・異動・退職などに合わせて、各システムのアカウントやアクセス権限を自動的に作成・変更・削除する仕組みを指す。

### 理解度チェック

- **【Q1】SSOとはどのような認証システムか。**
  - 最初に1回認証に成功すれば、利用を許可された複数のシステムを、認証プロセスを経ずに利用できる認証システム。
- **【Q2】SSOを導入すると、どのような効果が期待できるか。**
  - 認証情報の入力の手間やストレスが軽減され、利便性が向上する。
  - 認証情報を一元管理できるため、管理が容易になり、セキュリティレベルの向上も期待できる。
- **【Q3】SSOはどのような方式によって実現されているか。**
  - Cookieを用いる方式(エージェント型)、リバースプロキシサーバを用いる方式(リバースプロキシ型)、SAMLを用いる方式がある。
- **【Q4】エージェント型とリバースプロキシ型のメリット・デメリットは何か。**
  - エージェント型は、ネットワーク構成を変更せずに導入でき負荷も分散されるが、各Webサーバにエージェントを導入する必要がある。
  - リバースプロキシ型は、Webサーバへのソフトウェア導入が不要だが、認証サーバに負荷が集中し、ネットワーク構成の変更が必要になる。
- **【Q5】Cookieを用いたSSOシステムには、どのような制限事項があるか。**
  - 同一ドメイン内でしか構築できない。
  - クライアントがCookieの使用を制限している場合は利用できない。

### 確認問題

#### 問題1

シングルサインオンの実装方式の一つであるSAML認証の流れとして、適切なものはどれか。

- ア IdP(Identity Provider)が利用者認証を行い、認証成功後に発行されるアサーションをSP(Service Provider)が検証し、問題がなければクライアントがSPにアクセスする。
- イ Webサーバに導入されたエージェントが認証サーバと連携して利用者認証を行い、クライアントは認証成功後に利用者に発行されるcookieを使用してSPにアクセスする。
- ウ 認証サーバはKerberosプロトコルを使って利用者認証を行い、クライアントは認証成功後に発行されるチケットを使用してSPにアクセスする。
- エ リバースプロキシで利用者認証が行われ、クライアントは認証成功後にリバースプロキシ経由でSPにアクセスする。

[情報処理安全確保支援士試験]

**解答・解説**

SAMLによるシングルサインオンシステムは、ユーザのアカウント情報の管理と認証を行うIdPと、ユーザにサービスを提供するSPによって構成される。IdPはSPからの認証要求を受けて利用者認証を行い、認証に成功するとアサーションを発行する。SPはアサーションを検証し、問題がなければクライアントはSPにアクセスできる。したがって、**アが正解**である。

- イ:エージェント型(Cookieを用いたSSO)の説明である。
- ウ:Kerberos認証を用いたSSOの説明である。
- エ:リバースプロキシ型SSOの説明である。

#### 問題2

標準化団体OASISが、Webサイトなどを運営するオンラインビジネスパートナー間で、認証及び認可の情報を安全に交換するために策定したものはどれか。

- ア SAML
- イ SOAP
- ウ XKMS
- エ XML Signature

[情報処理安全確保支援士試験]

**解答・解説**

問題文に該当するのは、SAML(Security Assertion Markup Language)である。SAMLは、異なるドメインにあるWebサーバ間で、ユーザID・パスワード・公開鍵などの認証情報やアクセス制御情報を安全に交換するためのプロトコルである。XML関連の標準化団体であるOASIS(Organization for the Advancement of Structured Information Standards)によって策定された。

SAMLは、認証に関する情報などを格納するXMLベースの証明書(Assertion)の仕様と、Assertionを交換するためのプロトコルを規定している。したがって、**アが正解**である。

- イ:SOAPは、XMLベースのメッセージを交換するためのプロトコルであり、W3Cによって標準化された。
- ウ:XKMS(XML Key Management Specification)は、公開鍵の登録・検索・検証などをXMLで行うための仕様であり、W3Cによって標準化された。
- エ:XML Signatureは、XML文書にデジタル署名を付与するための仕様であり、W3CとIETFによって標準化された。
