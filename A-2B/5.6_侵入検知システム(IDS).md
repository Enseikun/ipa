# 5.6 侵入検知システム(IDS)

侵入検知システム(Intrusion Detection System:IDS)とは、ネットワークやホストで発生している事象をリアルタイムに監視して侵入や攻撃を検知し、管理者に通知するなどのアクションを実行するシステムである。ここでは、侵入検知システムの種類や機能、構成、運用上の課題などを解説する。

## 5.6.1 侵入検知システムの概要

一般的なIDSは、1,000種類を超える攻撃パターン(シグネチャ)のデータベースをもっている。それらと実際の事象を照合することで、OSの脆弱性を突いた攻撃やファイルの改ざんなどを検知して記録できる。また、メールをはじめとした様々な手段で警告を発することも可能である。

一方、ファイアウォールは攻撃の検知を目的としているわけではなく、あくまでもアクセス制御を行う製品である。ファイアウォールのログに記録されるのは、主に中継/破棄したパケットのヘッダ情報である。しかもその量は膨大であるため、やみくもに解析を試みても、OSの脆弱性を突いた攻撃などを検知するのはほぼ不可能に近い。

> **シグネチャ(signature)**
> 既知の攻撃や不正アクセスに特徴的なパケットの内容・パターンを定義したもの。IDSやウイルス対策ソフトは、シグネチャと実際のデータを照合して攻撃やマルウェアを検知する。

## 5.6.2 IDSの種類と主な機能

IDSは、その動作形態や監視対象によって、次の二つに分類できる。

- ネットワーク型侵入検知システム(Network-Based Intrusion Detection System:NIDS)
- ホスト型侵入検知システム(Host-Based Intrusion Detection System:HIDS)

### ネットワーク型侵入検知システム(NIDS)

NIDSは、監視の対象となるネットワークセグメントに接続して使用する。センサがセグメント上を流れるパケットを取り込んでリアルタイムに監視し、あらかじめ設定されたルール(監視のポリシ)に基づいて不正アクセスや不審な事象を検知する。

検知した結果は、マネジメントコンソール(管理用のソフトウェアがインストールされた端末)の画面やメールによって通知できる。製品によっては、TCPコネクションの強制切断(RSTパケットの送信)や、ファイアウォールと連携した通信の遮断といった防御機能をもつものもある。

**図:NIDSのイメージ**

```
          インターネット
                │
        ┌───────┴───────┐
        │ バリアセグメント│──[NIDS①]
        └───────┬───────┘
                │
         ┌──────┴──────┐
         │ファイアウォール│
         └──┬───────┬──┘
            │       │
   ┌────────┴┐   ┌──┴─────────┐
   │   DMZ   │   │内部セグメント│
   │(公開サーバ)│   │   (LAN)    │
   └────┬────┘   └─────┬──────┘
     [NIDS②]         [NIDS③]

   ※各NIDSセンサの検知結果はマネジメントコンソールへ通知
```

#### 接続場所と監視方法

NIDSには適当な接続場所と、それに応じた監視方法がある。

**① バリアセグメントに接続**

NIDSをバリアセグメント(インターネットとファイアウォールの間のセグメント)に接続すると、インターネットから自分のサイトに対して、どのような攻撃がどの程度行われているのかを知ることができる。したがって、基本的にはすべてのシグネチャを監視対象とする。

ただし、この位置で検知される攻撃の多くは、ファイアウォールによって破棄されるものである。実際にどの攻撃がファイアウォールを通過したのかは、DMZでの監視結果との比較によりはじめて分かることであり、バリアセグメントの監視結果のみでは実態は分からない。したがって、DMZで監視を行わないのであれば、この構成で監視を行う意味はない。

**② DMZに接続**

NIDSをDMZに接続すると、ファイアウォールを通過してDMZに対して行われる攻撃を検知できる。前掲の図のネットワーク構成では、この位置で監視を行うことが最も重要である。つまり、このネットワークにNIDSを1台だけ導入するならば、この構成をとるのが必須である。

この場合は、次のプロトコルに関するシグネチャを監視対象として設定しておけばよいだろう。

- ファイアウォールがインターネットからDMZに中継している(DMZでサービスを提供している)プロトコル
- ファイアウォールがDMZからインターネット側に中継しているプロトコル

**③ 内部セグメントに接続**

NIDSを内部セグメントに接続すると、LANの中を飛び交う不正なパケットを検知できる。近年、悪質なマルウェアのまん延が大きな問題となっているが、NIDSで内部セグメントを監視することで、そのような事象を発見できる可能性がある。この構成では、基本的にはすべてのシグネチャを監視対象としておく必要があるだろう。

> **バリアセグメント/DMZ**
> バリアセグメントは、インターネットとファイアウォールの間に位置するセグメントである。DMZ(DeMilitarized Zone:非武装地帯)は、ファイアウォールによってインターネットと内部LANの双方から隔離されたセグメントであり、Webサーバやメールサーバなどの公開サーバを設置する。

#### 攻撃や不正アクセスを検知する仕組み

一般的なNIDSは主に、次の二つの手法を用いて攻撃や不正アクセスを検知する。

- シグネチャとのパターンマッチング
- 異常検知(アノマリ検知)

**シグネチャとのパターンマッチング**

シグネチャとのパターンマッチングとは、取り込んだパケットとNIDSに登録された膨大な数のシグネチャとを比較し、不正アクセスを検知する手法である。パケットがシグネチャと一致した場合に、攻撃として検知する。この手法は不正検知(ミスユース検知)とも呼ばれる。

パターンマッチングによって検知可能な事象には、次のようなものがある。

- ポートスキャン
- OSやサーバソフトウェアの既知の脆弱性を突いた攻撃(BOF攻撃など)
- サーバソフトウェアに対する不正なコマンドの発行
- ネットワークを通じて行われるパスワードクラッキング
- パケットを偽装するタイプのDoS攻撃

パターンマッチングによる検知には、次の留意点がある。

- シグネチャを常に最新状態にアップデートしておく必要がある
- 未知の攻撃は検知できない
- サイト独自のアプリケーションの脆弱性を突いた攻撃は検知できない

シグネチャは、ベンダが既知の攻撃を分析して作成するものである。そのため、シグネチャが提供されていない新たな攻撃(ゼロデイ攻撃など)は検知できない。また、シグネチャの多くは、広く利用されているOSや市販のサーバソフトウェアに対する攻撃パターンである。したがって、組織がサイト用に独自の仕様で開発したアプリケーションプログラムの脆弱性を突いた攻撃などは、パターンマッチングでは検知できない。

シグネチャについては、製品にプリセットされたものに加え、独自のシグネチャを登録できる製品もある。独自シグネチャを登録すれば、サイト独自のアプリケーションプログラムの脆弱性を突いた攻撃なども検知できる可能性がある。

**異常検知(アノマリ検知)**

異常検知(アノマリ検知)とは、取り込んだパケットをRFCのプロトコル仕様など(正常なパターン)と比較し、仕様から逸脱したものを異常として検知する手法である。アノマリ検知を行うことで、次のような事象を検知できる可能性がある。

- 単体では正常なパケットを大量に送り付けるタイプのDoS攻撃
- シグネチャに含まれていない未知の攻撃
- 侵入を許してしまったことによるシステムの異常な振る舞い

アノマリ検知によって検知可能な事象には、次のようなものがある。

- 大量に発行されたコマンド
- プロトコルの仕様に反したデータの流れ
- プロトコルの仕様に従っていないヘッダ情報をもつパケット
- 異常な数の応答パケット など

ただし、アノマリ検知では、正常状態の判断基準によっては誤報が多くなる可能性がある点に留意する必要がある。

> **BOF攻撃(Buffer Overflow攻撃)**
> プログラムが確保したバッファ領域を超えるデータを送り込み、メモリ上の制御情報を書き換えて、任意のコードを実行させたりプログラムを異常終了させたりする攻撃である。

### ホスト型侵入検知システム(HIDS)

HIDSは、監視の対象となるホスト(Webサーバ、DBサーバ、メールサーバなど)にインストールして使用する。インストールされたホストに常駐して、発生している事象をリアルタイムに監視し、あらかじめ設定されたルール(監視のポリシ)に基づいて、不正な操作やファイルの改ざんなどを検知する。

また、HIDSによっては、ファイアウォールやルータのsyslog、SNMPトラップなどを集約し、ネットワーク全体の状態(障害の発生状況など)を監視する機能をもつものもある。検知後は、NIDSと同様に様々なアクションをとることができる。

**図:HIDSのイメージ**

```
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  Webサーバ    │  │  DBサーバ     │  │ メールサーバ   │
  │ [HIDSエージェント]│  │ [HIDSエージェント]│  │ [HIDSエージェント]│
  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘
         │ 検知結果の通知      │                 │
         └────────────┬─────┴─────────────────┘
                      │
           ┌──────────┴──────────┐
           │ マネジメントコンソール │ ← syslog/SNMPトラップ
           └─────────────────────┘   (ファイアウォール、ルータなど)
```

HIDSの主な検知項目は次のとおりである。

- ログインの成功/失敗
- 重要なリソース(ファイル、ディレクトリなど)へのアクセス
- 不正なプログラムのインストール
- システムディレクトリに存在するファイルの書換え/削除
- Webコンテンツの改ざん
- ネットワーク環境で発生している障害

これらの事象の検知に、HIDSはOSのロギング機能やセキュリティ機能を用いている。

> **syslog/SNMPトラップ**
> syslogは、機器やOSが発生させたログメッセージをネットワーク経由で収集・転送するための仕組みである。SNMPトラップは、SNMPエージェントが障害などの事象を検知した際に、管理マネージャへ自発的に通知するメッセージである。

### NIDSとHIDSの比較

以上、NIDSとHIDSについてそれぞれ見てきた。ここで、両者を主に検知機能の面で比較し、表にまとめておく。

### NIDSとHIDSの効果的な活用方法

NIDSとHIDSの特徴を把握し、両者を組み合わせることで、監視効果をより高められる。

例えば、NIDSは、OSの脆弱性を突いた攻撃をはじめ、非常に多くの不正アクセスを検知できる。しかし、その不正アクセスによって実際にどのような被害や影響があったのかを特定するのは困難である。攻撃による影響を知るには、攻撃の対象となったサーバのログか、そのサーバを監視しているHIDSの検知結果を併用するのが効果的である。

このように、NIDSとHIDSの両製品をうまく組み合わせることで、不正アクセスを発見するだけでなく、その被害状況や侵入手口を分析できるようになる。

## 5.6.3 IDSの機能上の限界及び運用上の課題

IDSには、一般に次のような機能上の限界や運用上の課題があることが認識されている。

### NIDSの機能上の限界と運用上の課題

NIDSには、次のような機能上の限界や運用上の課題がある。

**① 誤検知への対応**

NIDSでは、監視対象となる事象が多様で複雑であるため、ある程度の誤検知や誤報は避けられない。

IDSの誤検知の割合を測る指標として、次の二つがある。

- **フォールスポジティブ(false positive)**:IDSが本来検知すべきではない事象、つまり不正ではない事象を、不正行為として検知してしまうこと
- **フォールスネガティブ(false negative)**:本来検知すべき不正行為を見逃してしまうこと

フォールスポジティブが多いと、大量の誤報が発生して管理者の負担が増え、本当に重要な警告が埋もれてしまう。一方、フォールスネガティブが多いと、実際の攻撃を見逃すことになる。両者はトレードオフの関係にあることが多い。そのため、自組織のネットワーク環境や提供サービスに合わせて監視ポリシやシグネチャを見直し、フォールスポジティブとフォールスネガティブを最小にするよう継続的にチューニングを行っていく必要がある。

> **フォールスポジティブとフォールスネガティブ**
> 
> | | 実際に不正あり | 実際に不正なし |
> |---|---|---|
> | 不正と判定 | 正しい検知(true positive) | フォールスポジティブ(誤検知) |
> | 正常と判定 | フォールスネガティブ(見逃し) | 正しい判定(true negative) |

**② NIDSの処理能力不足によるパケットの取りこぼし**

監視するネットワークのトラフィック量とNIDSセンサのスペックが見合っていないと、この問題が発生する。NIDSの負荷を高める最も大きな原因はトラフィックの量である。それに加え、検知の対象としているシグネチャの量が多いことも原因となる。また、大規模Webサイトなどで、携帯端末からのアクセスによるショートパケット(データ長の短いパケット)の量が多い場合にも、取りこぼしが発生しやすくなる。

この問題への対応策には、次のようなものがある。

- 不要なシグネチャを監視の対象から外すなどの調整を行ったうえで、NIDSの最適なスペックや構成を再検討する
- 1台のセンサで十分な性能が出せない場合には、別機種へのリプレースやNIDSセンサの負荷分散を検討する
- パケット取りこぼしの実態を把握するため、ベンチマークテストを定期的に実施する

**③ アプリケーションに対する攻撃を検知できない**

5.6.2項で解説したように、SQLインジェクションやXSSをはじめ、組織がサイト用に独自の仕様で開発したアプリケーションプログラムの脆弱性を突いた攻撃などは、ほとんど検知できない。

有効な対応策は、独自にシグネチャを作成して対応するか、Webアプリケーションに対する攻撃であれば、Webアプリケーションファイアウォール(WAF)を導入することである。いうまでもなく、これらの対策を実施するかどうかにかかわらず、Webアプリケーション自体の脆弱性をなくすことは必須である。

> **SQLインジェクション**
> ユーザの入力値をもとにSQL文を組み立ててデータベース(DB)に問い合わせ、その結果を表示するWebアプリケーションに対し、不正なSQL文を入力することで、データベース内の情報の窃取や改ざんなどを行う攻撃手法である。

> **XSS(クロスサイトスクリプティング:Cross-Site Scripting)**
> 利用者の入力データをそのままWebページに出力するWebアプリケーションの脆弱性を悪用し、悪意のあるスクリプトを利用者のブラウザ上で実行させる攻撃手法、又はそのような攻撃を許す脆弱性のことである。

**④ 一部の高性能な機種を除き、暗号化されたパケットは解析できない**

SSL/TLSなどで暗号化された通信は、NIDSではパケットの内容を解析できないため、その中に含まれる攻撃を検知できない。HTTPSを利用するWebサイトを監視する場合は、SSLアクセラレータ機能をもった負荷分散装置を使用して通信を復号し、復号後の区間にNIDSを設置するのが望ましい。その他の暗号化通信については、個別に検討が必要である。

**⑤ 攻撃は検知できても侵入を検知できない**

攻撃が行われたことは検知できても、実際に侵入が行われたことは検知できないことが多い。とはいえ、5.3節で解説した脆弱性診断の結果との突合せや、セッション情報の保存・分析などによって、検知の精度は確実に向上している。

**⑥ 不正アクセスを防御できない**

前述のように、NIDSにはTCPコネクションの強制切断などの防御機能もある。しかし、NIDSはインライン接続で使用する機器ではないため、攻撃を排除するには限界がある。防御は、IPS(Intrusion Prevention System:侵入防止システム)やWebアプリケーションファイアウォールで行うべきである。

**⑦ 正当な権限者による内部犯罪の検知は困難**

不正な手法が用いられた場合は検知可能である。しかし、正当なユーザが行う正常な行為(アクセスを許可されているファイルをクライアント環境にコピーする行為など)から、内部犯罪の可能性を判断することはできない。これについては、アクセスログの監査や情報漏えい対策製品(DLP)の導入など、別の手段を考える必要がある。

> **IPS(Intrusion Prevention System)**
> ネットワークにインライン接続され、通過するパケットを監視して、攻撃と判断した通信をリアルタイムに遮断するシステムである。IDSの検知機能に防御機能を加えたものといえる。

### HIDSの機能上の限界と運用上の課題

HIDSには、次のような機能上の限界や運用上の課題がある。

**① あくまでもOSの基本的な機能がベースであり、それ以上のことはできない**

HIDSは、OSのロギング機能やセキュリティ機能を用いて事象を検知している。したがって、リアルタイム性を求めないのであれば、HIDSの検知機能はOSの基本的な機能でも代行できる。

**② 監視対象のホストごとに導入・管理が必要となる**

HIDSは監視対象のホストごとにインストールする必要があり、対応するOSも製品によって限られる。そのため、監視対象ホストが多い場合は、導入や運用管理のコストが大きくなる。また、ホストに侵入されてしまうと、HIDS自体が停止されたり、そのログが改ざんされたりするおそれもある。

**③ 導入によって監視対象ホストの性能や可用性に悪影響を及ぼす可能性がある**

HIDSは監視対象ホスト上で常駐して動作するため、ホストの資源を消費する。そのため、導入前に十分な検討を行うとともに、導入後もチューニングが必要である。

**④ 攻撃の予兆を検知することは困難**

HIDSは、ポートスキャンなどネットワーク上で行われる攻撃の予兆となる事象を検知するのは困難である。ただし、これらはログを分析することで検知できる可能性はある。

**⑤ 正当な権限者による内部犯罪の検知は困難**

NIDSの⑦と同様の理由により困難である。ただし、あらゆる操作をロギングして分析すれば、たとえ権限者による不正行為であっても検知できる可能性はある。

> **解答:ウ**
> フォールスネガティブとは、本来検知すべき不正(ここではウイルス感染)を見逃してしまうことである。したがって、感染しているファイルを「感染していない」と判断するウが該当する。イはフォールスポジティブ(誤検知)、アとエは正しい判定である。
