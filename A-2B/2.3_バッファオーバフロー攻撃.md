# バッファオーバフロー攻撃

## 2.3 バッファオーバフロー攻撃

バッファオーバフロー（BOF）攻撃とは、C言語やC++言語で開発されたOSやアプリケーションプログラムの、入力データの処理に関するバグを突く攻撃である。コンピュータのメモリに不正なデータを書き込み、システムへの侵入や管理者権限の取得を試みる。ここでは、バッファオーバフロー攻撃について、その仕組みと対策を解説する。

> **用語：バッファオーバラン**
> バッファオーバフローは、「バッファオーバラン」と呼ばれることもある。

> **試験に出た**
> 情報セキュリティスペシャリスト試験の午後Ⅰで、バッファオーバフローの脆弱性をもつプログラムに関する問題が出題された。
> また、同試験の午後Ⅱでも、バッファオーバフローの脆弱性とその対策に関する問題が出題された。

### 2.3.1 BOF攻撃の仕組み

BOF攻撃は、対象となるメモリ領域によって次のように分類される。

- スタック領域で行われるもの（スタックBOF、スタックベースBOF）
- ヒープ領域で行われるもの（ヒープBOF、ヒープベースBOF）
- 静的メモリ領域を対象としたもの

ここでは、スタックBOFについて解説する（以降、単にBOFという場合はスタックBOFを指す）。なお、スタックBOFはスタック領域を破壊するため、スタック破壊攻撃とも呼ばれる。

スタック領域は、後述するように、サブルーチンの呼出しなどによって自動的に確保され、プログラムが一時的に使用するデータを格納するために用いられる。一方、ヒープ領域は、必要に応じて`malloc`関数や`new`演算子（C++言語の場合）を用いて動的に確保する。スタック領域は不要になると自動的に解放されるが、ヒープ領域は`free`関数や`delete`演算子（C++言語の場合）を用いて明示的に解放しなければならない。

| 項目 | スタック領域 | ヒープ領域 |
| --- | --- | --- |
| 確保 | サブルーチン呼出し時などに自動的に確保 | `malloc`関数、`new`演算子で動的に確保 |
| 解放 | 不要になると自動的に解放 | `free`関数、`delete`演算子で明示的に解放 |
| 主な用途 | リターンアドレス、ローカル変数など | 実行時にサイズが決まるデータなど |

#### スタックの概要

BOF攻撃の仕組みを理解するには、まず、プログラム実行時のスタックの使われ方を知っておく必要がある。

スタックは、最後に格納したデータを最初に取り出す後入れ先出し（LIFO：Last In First Out）のデータ記憶構造である。このような構造をもつメモリ領域をスタック領域、あるいは単にスタックと呼ぶ。また、スタックにデータを書き込むことをPUSH、スタックからデータを取り出すことをPOPと呼ぶ。

```
図：PUSH, POPのイメージ

   PUSH ↓        ↑ POP
      ┌──────┐
      │ データC │ ← 最後に格納（最初に取り出される）
      ├──────┤
      │ データB │
      ├──────┤
      │ データA │ ← 最初に格納（最後に取り出される）
      └──────┘
```

スタックには、次のような一時的なデータが格納される。

- サブルーチンを呼び出す際の戻り位置（リターンアドレス）
- サブルーチン内で定義された変数（内部変数、ローカル変数）

スタックを用いると、サブルーチンから他のサブルーチンを呼び出すことも、自分自身を呼び出すこと（recursive call：再帰的呼出し）も可能になる。

通常、プログラムや初期データなどをメモリに格納する場合は、低位のアドレスから順に使われる。これに対してスタックでは、高位のアドレスから低位のアドレスに向かって使われる。

```
図：スタックのイメージ

      通常のメモリ領域              スタック領域
 低位アドレス 0x00000000       低位アドレス 0x00000000
   ┌────────┐                ┌────────┐
   │ 使用済み │ ↓ 使用方向      │        │
   ├────────┤                │  (空き)  │
   │        │                ├────────┤
   │  (空き)  │                │ 使用済み │ ↑ 使用方向
   └────────┘                └────────┘
 高位アドレス 0xFFFFFFFF       高位アドレス 0xFFFFFFFF
```

#### 正常なプログラムの実行イメージ

以上を踏まえ、C/C++言語による簡単なプログラムが実行される様子を示す。使用するプログラムは次のとおりである（行頭の数字は行番号）。

```c
/* メインルーチン */
  1: main()
  2: {
  3:   :
  4:   :
  5:   :
  6:   sub(data);
  7:   :
  8:   :
  9:   :
 10: }

/* サブルーチン */
100: sub(char *data)
101: {
102:   int a;
103:   char buf[128];
104:   :
105:   :
106:   strcpy(buf, data);
107:   :
108:   :
109:   return;
110: }
```

**① メインルーチンのプログラムが順次実行される**

メインルーチンの1行目から順に処理が実行される。この時点では、スタックにサブルーチン用のデータは格納されていない。

**② サブルーチンが呼び出されると、戻り先がスタックに格納される**

6行目で`sub(data)`が呼び出されると、サブルーチン終了後に処理を再開する位置（7行目）がリターンアドレスとしてスタックにPUSHされる。

```
図：正常なプログラムの実行イメージ②

 低位アドレス
   ┌─────────────────┐
   │                 │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**③ サブルーチンの中で使用する変数（a、buf）の格納領域がスタックに確保される**

```
図：正常なプログラムの実行イメージ③

 低位アドレス
   ┌─────────────────┐
   │ buf（128バイト）   │
   ├─────────────────┤
   │ a                │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**④ 変数（buf）に入力データ（data）が格納される**

106行目の`strcpy(buf, data)`により、入力データ`data`が変数`buf`の領域にコピーされる。入力データが128バイト以内であれば、`buf`の領域内に収まる。

```
図：正常なプログラムの実行イメージ④

 低位アドレス
   ┌─────────────────┐
   │ buf ← data       │ （bufの領域内に収まる）
   ├─────────────────┤
   │ a                │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**⑤ サブルーチンの処理が終了すると、スタックに格納された戻り先を参照し、メインルーチンに処理が戻る**

109行目の`return`により、スタックから戻り先（7行目）がPOPされ、メインルーチンの7行目から処理が再開される。スタックに格納されていたデータは自動的に消去（解放）される。

#### BOF攻撃の実行イメージ

続いて、この手順に沿って、BOF攻撃が実行される様子を示す。

**① メインルーチンからサブルーチンが呼び出され、その中で使用する変数（a、buf）の格納領域がスタックに確保される**

ここまでは、正常なプログラムの①〜③と同じである。

**② 入力データがbufのサイズを超えるため、スタック内の他の領域まで上書きされる**

変数`buf`への入力データ`data`が、確保されていたサイズ（128バイト）よりはるかに大きいとする。プログラムでデータサイズをチェックしていない場合、C/C++言語の`strcpy`関数は、サイズの制限なしに入力データをメモリ内の変数領域（開始位置）からコピーしてしまう。その結果、確保されていた`buf`の領域を超えて、スタック内の他の領域まで上書きされる（オーバフロー状態）。

なお、スタックは高位アドレスから低位アドレスに向かって使われるが、変数へのデータの書込みは低位アドレスから高位アドレスに向かって行われる。そのため、`buf`からあふれたデータは、`buf`より高位アドレス側に格納されている変数`a`や戻り先を上書きしてしまう。

```
図：BOF攻撃の実行イメージ②

 低位アドレス
   ┌─────────────────┐
   │ buf ← data       │ ↓ 書込み方向
   ├─────────────────┤
   │ a   ← data（続き）│ （上書き）
   ├─────────────────┤
   │ 戻り先← data（続き）│ （上書き）
   └─────────────────┘
 高位アドレス
```

**③ サブルーチンの処理が終了しても、本来の戻り先には戻れなくなる**

サブルーチンの処理は終了したが、スタックに格納されていたはずの戻り先が上書きされているため、本来の戻り先（メインルーチンの7行目）には戻れない。単に不正なデータで上書きされた場合は、プログラムが異常終了する（サービス不能状態となる）。

**④ 侵入者が意図したとおりに不正なコードが実行される**

入力データ`data`には、侵入者が用いる不正な機械語のコード（Code）と、そこに処理を飛ばすための偽りの戻り先（Address）がセットされている。しかも、この偽りの戻り先が、本来の戻り先が格納されていた箇所に上書きされるように細工されている。そのため、サブルーチンの終了時に処理が不正なコードへ移り、侵入者の意図どおりにコードが実行される。

```
図：BOF攻撃の実行イメージ④

 低位アドレス
   ┌──────────────────┐
   │ 不正なコード(Code) │ ←──┐
   ├──────────────────┤     │
   │ （パディング）       │     │ 処理が移る
   ├──────────────────┤     │
   │ 偽りの戻り先(Address)│ ───┘
   └──────────────────┘
 高位アドレス
            ↓
      シェル（/bin/sh）起動 → 侵入者が操作
```

このとき送り込まれる不正なコードには、ターゲットとなったサービスをシェル（`/bin/sh`）に置き換えるものが多い。このようなコードは「シェルコード」とも呼ばれる。ターゲットのサービスが管理者（root）権限で動作していれば、侵入者は管理者権限でシェルを操作できる。

なお、起動させるプログラム自体をデータに潜ませて送り込むこの手法のほかに、ターゲットホスト上の既存のプログラム（バックドアのように機能するもの）を実行させる場合もある。

> **用語：シェル**
> UNIXにおいて、ユーザーからのコマンドを解釈してOS（カーネル）に伝えるユーザーインタフェースとなるプログラムである。代表的なものに`sh`、`bash`、`csh`などがある。

> **用語：バックドア**
> 侵入者が、一度侵入したホストに再び容易に侵入するために、密かに設置する侵入口である。特定の条件で接続を受け付けるプログラムなどが使われる。
> バックドアを仕掛けられたホストは、再び侵入される可能性がある。そのため、OSの初期化、アプリケーションの再インストール、パスワードの変更などの対処が必要となる。

#### データ実行防止とアドレス空間配置ランダム化

BOF攻撃を防止するため、近年のWindows OSには、指定されたメモリ領域でのコードの実行を禁止する機能であるDEP（Data Execution Prevention：データ実行防止）が実装されている。DEPを有効にすると、スタック領域やヒープ領域など、本来データを格納するための領域に送り込まれたコードは実行されない。そのため、前述のような、不正なコードをスタックに送り込んで実行させる攻撃を防ぐことができる。UNIX系OSでも、NXビット（No eXecute bit）などを利用した同様の機能が実装されている。

しかし、DEPを回避する攻撃手法として、return-to-libc攻撃がある。return-to-libc攻撃は、スタックに不正なコードを送り込むのではなく、共有ライブラリ（libcなど）内に既に存在する関数（`system`関数など）を呼び出すように、リターンアドレスと引数を書き換えることでBOF攻撃を成立させる。実行されるのはメモリ上の正規のコードであるため、この攻撃はデータ実行防止機能が実装されていても防ぐことができない。

> **補足：ROP（Return-Oriented Programming）**
> return-to-libc攻撃を発展させた手法として、ROPがある。ROPは、既存のプログラムやライブラリ内にある、`ret`命令で終わる短い命令列（ガジェット）を連鎖的に呼び出し、任意の処理を実行させる手法である。

そこで最近のOSは、このような攻撃の成功を抑制するため、アドレス空間配置ランダム化（Address Space Layout Randomization：ASLR）と呼ばれる技術を採用している。ASLRとは、アドレス空間における実行ファイル、ライブラリ、スタック、ヒープなどの配置をランダムにする技術である。これにより、BOF攻撃を成功させるために必要な戻り先（リターンアドレス）や、呼び出す関数のアドレスが特定されにくくなる。

また、ASLRが対象とする領域に加え、テキスト領域（プログラムのコードが格納される領域）のアドレスもランダム化できる技術として、PIE（Position Independent Executable：位置独立実行形式）がある。

> **補足：スタックカナリア**
> コンパイラによる対策として、スタック上のローカル変数とリターンアドレスの間に「カナリア」と呼ばれる値を配置し、関数の終了時にその値が書き換えられていないかを検査する技術もある。書換えが検出された場合はプログラムを強制終了させ、不正なコードの実行を防ぐ。GCCの`-fstack-protector`オプションや、Visual C++の`/GS`オプションなどで利用できる。

#### Use-After-Freeを悪用したヒープBOF

Use-After-Freeとは、解放済みのメモリ（ヒープ領域）を使ってしまうことにより、攻撃者に任意のコードの実行を許すおそれのある脆弱性である。解放済みのメモリ領域に攻撃者が用意したデータを配置させ、そのメモリ領域を参照するポインタ（ダングリングポインタ）をプログラムが使用したときに、不正なコードが実行される。

Use-After-Freeは、ASLRが有効な場合でも、共有ライブラリ内のメモリアドレスが特定されるなどして、攻撃が成立する可能性がある。また、スクリプト言語を用いて攻撃を行えるため、Webブラウザや文書閲覧ソフトなど、スクリプトの実行機能をもつ多くのソフトウェアが攻撃に悪用されるおそれがある。抜本的な対策は、当該脆弱性を修正することである。

> **試験に出た**
> 情報処理安全確保支援士試験の平成30年度午後Ⅰ問1で、Use-After-Freeの脆弱性と対策に関する問題が出題された。

#### 整数オーバフロー

BOFの一種に、整数オーバフローがある。整数オーバフローとは、整数の演算結果が格納先の型で表現できる上限値を超え、桁あふれが発生することである。整数オーバフローの脆弱性を悪用した攻撃を「整数オーバフロー攻撃」という。

例えば、確保するバッファのサイズを整数演算で求めるプログラムで桁あふれが発生すると、本来よりはるかに小さなサイズのバッファしか確保されない。その結果、後続のデータコピー処理でバッファの領域を超えた書込みが行われ、BOFが発生する。

```c
/* 整数オーバフローの例（32ビット符号なし整数の場合） */
unsigned int count;          /* 攻撃者が指定する要素数 */
unsigned int size = count * sizeof(int);
/* countが非常に大きいと size が桁あふれして小さな値になる */
int *p = malloc(size);       /* 小さな領域しか確保されない */
/* 以降、count個の要素を書き込むとヒープBOFが発生する */
```

> **補足：BOFに対するプログラミング上の対策**
>
> - `strcpy`、`strcat`、`gets`、`sprintf`など、コピー先のサイズを検査しない関数の使用を避け、`strncpy`、`strncat`、`fgets`、`snprintf`など、サイズを指定できる関数を使用する。
> - 入力データのサイズをチェックし、確保したバッファのサイズを超えないことを確認する。
> - 整数演算の前に、演算結果が型の上限値・下限値を超えないかを確認する。
> - Java、C#、Rustなど、メモリ安全性が確保された言語の採用を検討する。

### 2.3.2 BOF攻撃の手法と対策

#### setuid/setgid属性を悪用したBOF攻撃

ここでは、setuid/setgid属性をもつコマンドにサイズの大きなデータを送り付けてBOF状態を引き起こさせ、管理者(root)の権限を手に入れる手法について解説する。

##### setuid/setgidの概要

すべてのファイルやディレクトリには、ユーザ単位、あるいはユーザが所属するグループ単位に、読込み、書込み、実行などの属性(UNIX系のOSではパーミッションという)が設定されている。

setuid(set user ID)は、読込みや書込みなどと同様に、実行属性をもつファイルに設定する属性の一つである。実行されたプログラム(プロセス)のユーザ権限(実効ユーザID:Effective User ID:EUID)に、そのプログラムの所有者の権限を一時的に設定する。これにより、一般ユーザなどが使用するコマンドの中で、管理者の権限などを必要とする処理を実行できるようになる。

通常、実行中のプログラム(プロセス)には、そのプログラムを実行したユーザの権限が設定される。一方、setuid属性をもつプログラムの所有者がrootであれば、そのプロセスにはroot権限が与えられる。

また、setgid(set group ID)も、ファイルやディレクトリに設定する属性の一つである。この属性が設定されたファイルを実行すると、生成されるプロセスのグループID(GID)は、そのファイルの所有者のGIDとなる。ディレクトリに設定した場合は、そのディレクトリ内に作られるファイルのGIDが、ディレクトリのGIDを継承する。

> **パーミッションの表記**
> `ls -l`コマンドでは、setuid属性が設定されたファイルは所有者の実行権限の位置に`s`と表示される(例:`-rwsr-xr-x`)。setgid属性の場合は、グループの実行権限の位置に`s`と表示される(例:`-rwxr-sr-x`)。8進数表記では、setuidは`4000`、setgidは`2000`で表される。

##### setuid属性をもつプログラムの例

setuid属性をもつ代表的なプログラムに、UNIX系OSのパスワード変更に用いるpasswdコマンド(/usr/bin/passwd)がある。パスワード情報を格納するファイル(/etc/passwdや/etc/shadow)は、root以外のユーザには書込みが許可されていない。それでも一般ユーザが自分のパスワードを変更できるのは、passwdコマンドにsetuid属性が設定されているためである。一般ユーザがpasswdコマンドを実行すると、そのプロセスには同コマンドの所有者であるrootの権限が与えられる。

一般的なUNIX系OSでは、passwdコマンドのほかにも、pingコマンド(/bin/ping)やsuコマンド(/bin/su)など、所有者がrootでsetuid属性が設定されたプログラムが幾つかある。

##### 攻撃の仕組み

侵入者は、所有者がrootでsetuid/setgid属性をもつプログラムを実行し、非常にサイズの大きい入力データを与える。これによってBOF状態を引き起こし、root権限を手に入れる。

setuid属性をもつプログラムは、一般ユーザが実行してもroot権限で動作する。そのため、プログラムにBOFの脆弱性が存在すると、攻撃者が送り込んだ不正なコードもroot権限で実行されてしまう。

> **Column:rootkit(ルートキット)**
>
> rootkitとは、侵入に成功した攻撃者が、その後の不正な活動を行いやすくし、自身の存在を隠蔽するために使用するソフトウェアなどをまとめたパッケージの呼称(俗称)である。当初は、UNIX系のシステムに侵入してroot権限を手に入れた侵入者が、システム管理者に見つかることなくroot権限を保持して活動を続けるためのツールであった。現在では、Windowsなど"root"というアカウントが存在しない環境で同様の働きをするツールもrootkitと呼ばれている。
>
> 古くから知られているrootkitには、次のようなものがある。
>
> - UNIX環境でプロセスやネットワーク接続の状況を確認するために使用される"ps"や"netstat"などのコマンドを置き換え、特定のプロセスや接続の存在を隠蔽するもの
> - ログを改ざんするもの
>
> また、コマンドそのものを置き換えるのではなく、ファイル、ディレクトリ、レジストリなどのシステムリソースへのアクセスに伴うシステムコールを横取りし、その応答を偽装するタイプのrootkit(カーネルモードrootkit)も存在している。

#### BOF攻撃による影響

BOF攻撃は、一般に次のような流れで行われる。

1. 攻撃者が、ターゲットとなるプログラムに、想定されたバッファのサイズを超える大きなデータを送り付ける。
2. 入力データのサイズがチェックされないため、バッファに収まりきらないデータがスタック上の隣接領域に溢れ出す。
3. 溢れ出したデータにより、スタックに格納されたリターンアドレスなどが書き換えられる。
4. サブルーチンの処理が終了して制御が戻る際、書き換えられたリターンアドレスに処理が移り、攻撃者が送り込んだ不正なコードが実行される。

リターンアドレスの書換えを行い、処理をシェルなどの起動に置き換えることに成功すれば、侵入者は管理者権限でそのホストを操作できることになる。そうなれば、ホストに保存された機密情報のコピー、不正プログラムの埋込み、設定変更、ログの消去などを自在に行うことができる。このような行為を、権限の乗っ取り、もしくは権限昇格という。

なお、ネットワークを通じてサービスを提供するタイプのサーバプログラムは、管理者権限で実行されていることが多い。そのため、BOFの脆弱性が存在する場合には非常に危険である。

また、攻撃が④まで成功せず③までにとどまった場合でも、ターゲットとなったサービスは異常終了してしまう。この場合は、DoS攻撃と同様の影響を受けることになる。

#### BOF攻撃への対策

##### ソフトウェア利用者としての対策

BOF攻撃はソフトウェアのバグが原因となっている。そのため、OSや使用しているソフトウェアのバージョンアップやパッチの適用を確実に行い、既知のセキュリティホールを塞ぐことが対策の基本となる。ソフトウェア利用者としてとるべき主な対策を次に挙げる。

###### 予防・防止

- OS及び使用しているソフトウェアのバージョンを最新化し、パッチを適用する。
- 脆弱性検査を実施し、BOF攻撃に関するセキュリティホールが塞がれていることを確認する。
  - 問題箇所があれば対処する。
- ファイアウォールによって、不要なポートへのアクセスを遮断する。
- データ実行防止(DEP:Data Execution Prevention)機能を備えたCPU(NXビット/XDビット対応)及びOSを使用し、当該機能を有効に設定する。
  - ただし、この対策を行ったとしても、実行禁止に指定された領域以外にあるプログラムを起動させるタイプのBOF攻撃(return-to-libc攻撃など)は防げない。また、BOF攻撃の対象となったプログラムが異常終了することも防ぐことはできない。
- アドレス空間配置ランダム化(ASLR:Address Space Layout Randomization)技術が実装されたOSを使用する。
- setuid/setgid属性をもつプログラムに、次の手順で対処する。
  1. findコマンドを使用して、所有者がrootでsetuid/setgid属性をもつプログラムを探す。
  2. 上記プログラムの中で、不要なものを削除する。
  3. 上記2.で削除できないもののうち、setuid/setgid属性が不要なものは、パーミッションを変更してsetuid/setgid属性を解除する。

> **ASLR(アドレス空間配置ランダム化)**
> プログラムの実行ごとに、スタック、ヒープ、共有ライブラリなどが配置されるメモリアドレスをランダムに変化させる技術である。攻撃者は不正なコードやライブラリ関数の配置アドレスを予測しにくくなるため、リターンアドレスを狙いどおりに書き換えることが困難になる。

> **setuid/setgid属性をもつプログラムの検索と解除の例**
>
> ```
> # find / -user root \( -perm -4000 -o -perm -2000 \) -type f -ls
> # chmod u-s /path/to/program   (setuid属性の解除)
> # chmod g-s /path/to/program   (setgid属性の解除)
> ```

###### 検知・追跡

- ネットワーク監視型IDS、ホスト監視型IDS、IPSを用いて検知する。
- ホストのログが改ざんや消去をされずに保存されていれば、それを用いて追跡調査を行う。

###### 回復

- サーバログやIDSログなどから原因(脆弱性)を特定し、ベンダーが公開している対策手順に従って対処する。
- 不正アクセスを受けたホスト、及び当該ホストからアクセス可能なすべてのホストを対象に、データの改ざん、不正プログラムの埋込み、設定変更などの有無を徹底的に検証し、問題箇所を修復する。状況によっては、OSをクリーンインストールしてサーバ環境を再構築する。
- 予防対策と同様に脆弱性検査を実施し、問題箇所があれば対処する。

##### ソフトウェア開発者としての対策

ソフトウェア開発者としてとるべき主な対策を次に挙げる(詳細は8.2節で解説)。

- gets、strcpy、strcat、sprintfなど、BOFを引き起こす危険性の高い関数を使用しないようにする。
  - 代わりに、fgets、strncpy、strncat、snprintfなど、書込みサイズを指定できる関数を使用する。
- 入力データのレングスチェックを確実に行う。
- スタック上に埋め込んだ攻撃検知用の値によって、BOF攻撃を検知する。
  - これを実現するものとして、GNU Cコンパイラ(GCC)の拡張版であるStackGuardがある。StackGuardでコンパイルされたプログラムは、サブルーチンを呼び出す際に、スタック中の変数とリターンアドレスの間に「カナリア("カナリア値"ともいう)」と呼ばれる値を埋め込んでおく。そして、サブルーチン実行後にカナリアの値が変更されているかどうかを確認することで、BOF攻撃を検知する。改ざんを検知した場合は、プログラムを強制的に停止させる。
  - StackGuardと同様に、スタック領域に「カナリア」もしくは「guard」と呼ばれる値を埋め込んでBOF攻撃を検知する技術として、SSP(Stack Smashing Protection)がある。StackGuardはアセンブラレベルでコンパイラを拡張しているため、特定のCPUのみをサポートしている。これに対しSSPは、コンパイラが生成する中間言語のレベルでBOF検出のためのコードを生成するため、様々なCPU環境で利用できる。
- BOF防止機能を追加したライブラリを使用する。
  - これを実現する代表的なものとして、Libsafeがある。Libsafeは、プログラム実行時にBOFを引き起こす危険性の高い主な関数の呼出しを検知すると、ライブラリからの関数の呼出し順序を変更し、BOFをチェックする関数を先に実行させることで、不正なコードの実行を防ぐ。LibsafeはStackGuardとは異なり、対象プログラムを再コンパイルする必要がなく、既存の実行ファイルにも適用できる。

> **カナリア(canary)の由来**
> かつて炭鉱では、有毒ガスの発生を早期に察知するため、ガスに敏感なカナリアを坑内に持ち込んでいた。スタック上に埋め込む検知用の値は、異常をいち早く知らせるこのカナリアになぞらえて名付けられている。

### 確認問題

#### 問題1

配列を用いてスタックを実現する場合の構成要素として、最低限必要なものはどれか。

- ア スタックに最後に入った要素を示す添字の変数
- イ スタックに最初に入った要素と最後に入った要素を示す添字の変数
- ウ スタックに一つ前に入った要素を示す添字の変数を格納する配列
- エ スタックの途中に入っている要素を示す添字の変数

[情報処理技術者試験 高度共通・H24秋]

**解答・解説**

スタックはデータ記憶構造の一種であり、最後に入った要素が最初に読み出される「後入れ先出し(Last In First Out:LIFO)」の構造となっている。そのため、最後に入った要素を示す添字の変数(スタックポインタ)が最低限必要となる。

スタックは、プログラム内でサブルーチンを呼び出す際の戻り位置(リターンアドレス)のほか、サブルーチン内で定義された変数(内部変数、ローカル変数)など、一時的に使用するデータを格納する用途に使われる。スタックを用いると、サブルーチンからほかのサブルーチンを呼び出すことや、自分自身を呼び出すこと(再帰的呼出し:recursive call)も可能となる。

したがって、**アが正解**である。

#### 問題2

ルートキットの特徴はどれか。

- ア OSなどに不正に組み込んだツールの存在を隠す。
- イ OSの中核であるカーネル部分の脆弱性を分析する。
- ウ コンピュータがマルウェアに感染していないことをチェックする。
- エ コンピュータやルータのアクセス可能な通信ポートを外部から調査する。

[情報処理安全確保支援士試験・R3]

**解答・解説**

ルートキットとは、侵入に成功した攻撃者が、その後の不正な活動を行いやすくし、自身の存在を隠蔽するために使用するソフトウェアなどをまとめたパッケージの呼称(俗称)である。当初は、UNIX系のシステムに侵入してroot権限を手に入れた侵入者が、システム管理者に見つかることなくroot権限を保持して活動を続けるためのツールのことであった。現在では、Windowsなど"root"というアカウントが存在しない環境で同様の働きをするツールもルートキットと呼ばれている。

なお、イは脆弱性診断ツール、ウはマルウェア対策ソフト(ウイルス対策ソフト)、エはポートスキャナの説明である。

したがって、**アが正解**である。
