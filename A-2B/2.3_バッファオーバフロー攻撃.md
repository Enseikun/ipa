## 0. 全体像 ― なぜこの分野を学ぶのか

前回の 2.2 では、攻撃者がポートスキャンで「どのポートが開いていて、どんなサービスが動いているか」を下調べする様子を見ました。下調べを終えた攻撃者が次に狙うのは、そのサービスのプログラムに潜むバグです。その代表格が本ノートで扱う**バッファオーバフロー**（**BOF**）攻撃です。

**バッファオーバフロー（BOF）攻撃**とは、攻撃者が、C言語やC++言語で開発されたOSやアプリケーションプログラムの「入力データの処理に関するバグ」を突く攻撃です。攻撃者は、コンピュータのメモリに不正なデータを書き込むことで、システムへの侵入や管理者権限の取得を試みます。プログラムが「受け取ったデータが、用意した入れ物（バッファ）に収まるか」を確かめていないと、あふれたデータが隣の領域を書き換えてしまう ― この単純な因果が、数十年にわたって深刻な被害を生み続けてきました。

> **用語：バッファオーバラン**
> バッファオーバフローは、「バッファオーバラン」と呼ばれることもある。

> **試験に出た**
> 情報セキュリティスペシャリスト試験の午後Ⅰで、バッファオーバフローの脆弱性をもつプログラムに関する問題が出題された。
> また、同試験の午後Ⅱでも、バッファオーバフローの脆弱性とその対策に関する問題が出題された。

本ノートは次の流れで進みます。攻撃の説明は「入力が領域をはみ出して隣の管理情報を書き換える」という因果の理解にとどめ、そのぶん「開発者・システム管理者が、何を、何のために、どうすべきか」に紙幅を割きます。

1. **メモリの基礎**（第1節）：スタック領域とヒープ領域の違い、スタックの使われ方を押さえます。
2. **攻撃の仕組み**（第2節）：簡単なプログラムで、正常な実行と攻撃時の実行を図で比べます。
3. **OS・コンパイラの保護機能**（第3節）：DEP、ASLR、PIE、スタックカナリアと、それを回避しようとする攻撃との「いたちごっこ」を整理し、保護機能の有効化設定の見た目を確認します。
4. **BOFの仲間**（第4節）：Use-After-Free と整数オーバフローを扱います。
5. **setuid/setgid の悪用と rootkit**（第5節）：一般ユーザが root 権限を奪う経路と、侵入後に痕跡を隠す道具を学びます。
6. **影響と現場での見え方**（第6節）：攻撃が成功した場合・途中で失敗した場合の影響と、そのときOSやアプリが出すエラーメッセージを確認します。
7. **対策**（第7節）：ソフトウェア利用者（システム管理者）と、ソフトウェア開発者の立場に分けて整理します。

BOFはソフトウェアの脆弱性の典型例なので、「脆弱性とは何か」「CVE・CWE・CVSS・JVN で脆弱性をどう識別・評価するか」は第3章 [3.1 脆弱性の概要](3.1_脆弱性の概要.md) で、サーバを攻撃されにくい状態に整える具体策は第5章 [5.2 ホストの要塞化](5.2_ホストの要塞化.md) で扱います。本ノートを読みながら、必要に応じて行き来してください。

科目Bの4業務観点では、主に「②情報システムの企画・設計・開発・運用におけるセキュリティ確保」（セキュアプログラミング、コンパイラの保護オプション）と「③利用におけるセキュリティ対策の適用」（脆弱性への対応、パッチ管理、setuid の整理）に対応し、侵入後の再構築の判断では「④インシデント管理」にも関わります。科目A-2ではスタックの構造、DEP・ASLR・カナリアの役割の識別、rootkit の定義が繰り返し出題されています。

## 1. BOFを理解するためのメモリの基礎

### 1.1 BOF攻撃の分類 ― どのメモリ領域があふれるか

BOF攻撃は、攻撃者があふれさせる対象のメモリ領域によって、次のように分類されます。

- スタック領域で行われるもの（**スタックBOF**、**スタックベースBOF**）
- ヒープ領域で行われるもの（**ヒープBOF**、**ヒープベースBOF**）
- **静的メモリ領域**を対象としたもの

本ノートでは主にスタックBOFについて解説します（以降、単にBOFという場合はスタックBOFを指します）。スタックBOFはスタック領域を破壊するため、**スタック破壊攻撃**とも呼ばれます。

プログラムがデータを置く2つの主要な領域、スタックとヒープの違いを先に整理しておきましょう。**スタック領域**は、後述するように、サブルーチンの呼出しなどによって自動的に確保され、プログラムが一時的に使用するデータを格納するために用いられます。一方、**ヒープ領域**は、プログラムが必要に応じて`malloc`関数や`new`演算子（C++言語の場合）を用いて動的に確保します。スタック領域は不要になると自動的に解放されますが、ヒープ領域はプログラムが`free`関数や`delete`演算子（C++言語の場合）を用いて明示的に解放しなければなりません。

| 項目 | スタック領域 | ヒープ領域 |
| --- | --- | --- |
| 確保 | サブルーチン呼出し時などに自動的に確保 | `malloc`関数、`new`演算子で動的に確保 |
| 解放 | 不要になると自動的に解放 | `free`関数、`delete`演算子で明示的に解放 |
| 主な用途 | リターンアドレス、ローカル変数など | 実行時にサイズが決まるデータなど |
| あふれたときに壊れやすいもの | リターンアドレス（処理の戻り先） | ヒープの管理情報、隣接するデータやポインタ |
| 関係する脆弱性の型（CWE） | CWE-121（スタックベースBOF） | CWE-122（ヒープベースBOF）、CWE-416（Use-After-Free） |

「解放を人間が明示的に行う」というヒープの性質は、第4節の Use-After-Free（解放した後にまた使ってしまうバグ）の原因になります。ここで覚えておいてください。

### 1.2 スタックの仕組み ― 後入れ先出しと「戻り先」の記録

BOF攻撃の仕組みを理解するには、まず、プログラム実行時のスタックの使われ方を知っておく必要があります。

**スタック**は、最後に格納したデータを最初に取り出す**後入れ先出し**（**LIFO**：Last In First Out）のデータ記憶構造です。このような構造をもつメモリ領域をスタック領域、あるいは単にスタックと呼びます。また、プログラムがスタックにデータを書き込むことを**PUSH**、スタックからデータを取り出すことを**POP**と呼びます。

```
図：PUSH, POPのイメージ

   PUSH ↓        ↑ POP
      ┌──────┐
      │ データC │ ← 最後に格納（最初に取り出される）
      ├──────┤
      │ データB │
      ├──────┤
      │ データA │ ← 最初に格納（最後に取り出される）
      └──────┘
```

プログラムは、スタックに次のような一時的なデータを格納します。

- サブルーチンを呼び出す際の戻り位置（**リターンアドレス**）
- サブルーチン内で定義された変数（**内部変数**、**ローカル変数**）

スタックを用いると、プログラムはサブルーチンから他のサブルーチンを呼び出すことも、自分自身を呼び出すこと（**recursive call**：**再帰的呼出し**）もできるようになります。呼び出すたびに「戻り先」を積み、戻るたびに取り出すので、何段呼び出しても正しい順に戻れるわけです。裏を返せば、プログラムは「スタックに積まれた戻り先は正しい」と信じて処理を戻します。攻撃者が狙うのは、まさにこの信頼です。

もう一つ重要なのが、使われる方向です。通常、プログラムや初期データなどをメモリに格納する場合は、低位のアドレスから順に使われます。これに対してスタックでは、高位のアドレスから低位のアドレスに向かって使われます。

```
図：スタックのイメージ

      通常のメモリ領域              スタック領域
 低位アドレス 0x00000000       低位アドレス 0x00000000
   ┌────────┐                ┌────────┐
   │ 使用済み │ ↓ 使用方向      │        │
   ├────────┤                │  (空き)  │
   │        │                ├────────┤
   │  (空き)  │                │ 使用済み │ ↑ 使用方向
   └────────┘                └────────┘
 高位アドレス 0xFFFFFFFF       高位アドレス 0xFFFFFFFF
```

この「スタックは高位→低位に積まれるが、変数への書込みは低位→高位に進む」という向きの食い違いが、次節で見る攻撃の核心になります。

## 2. BOF攻撃の仕組み ― 正常な実行と攻撃時を比べる

### 2.1 題材のプログラム

以上を踏まえ、C/C++言語による簡単なプログラムが実行される様子を示します。使用するプログラムは次のとおりです（行頭の数字は行番号）。

```c
/* メインルーチン */
  1: main()
  2: {
  3:   :
  4:   :
  5:   :
  6:   sub(data);
  7:   :
  8:   :
  9:   :
 10: }

/* サブルーチン */
100: sub(char *data)
101: {
102:   int a;
103:   char buf[128];
104:   :
105:   :
106:   strcpy(buf, data);
107:   :
108:   :
109:   return;
110: }
```

注目すべきは106行目です。開発者は`buf`を128バイトで用意しましたが、`strcpy`関数でコピーする前に`data`の長さを確かめていません。この「確かめていない」ことが脆弱性（バグ）の正体です。

### 2.2 正常なプログラムの実行イメージ

**① メインルーチンのプログラムが順次実行される**

メインルーチンの1行目から順に処理が実行されます。この時点では、スタックにサブルーチン用のデータは格納されていません。

**② サブルーチンが呼び出されると、戻り先がスタックに格納される**

6行目で`sub(data)`が呼び出されると、サブルーチン終了後に処理を再開する位置（7行目）がリターンアドレスとしてスタックにPUSHされます。

```
図：正常なプログラムの実行イメージ②

 低位アドレス
   ┌─────────────────┐
   │                 │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**③ サブルーチンの中で使用する変数（a、buf）の格納領域がスタックに確保される**

```
図：正常なプログラムの実行イメージ③

 低位アドレス
   ┌─────────────────┐
   │ buf（128バイト）   │
   ├─────────────────┤
   │ a                │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**④ 変数（buf）に入力データ（data）が格納される**

106行目の`strcpy(buf, data)`により、入力データ`data`が変数`buf`の領域にコピーされます。入力データが128バイト以内であれば、`buf`の領域内に収まります。

```
図：正常なプログラムの実行イメージ④

 低位アドレス
   ┌─────────────────┐
   │ buf ← data       │ （bufの領域内に収まる）
   ├─────────────────┤
   │ a                │
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

**⑤ サブルーチンの処理が終了すると、スタックに格納された戻り先を参照し、メインルーチンに処理が戻る**

109行目の`return`により、スタックから戻り先（7行目）がPOPされ、メインルーチンの7行目から処理が再開されます。スタックに格納されていたデータは自動的に消去（解放）されます。

### 2.3 BOF攻撃の実行イメージ

続いて、この手順に沿って、BOF攻撃が実行される様子を示します。

**① メインルーチンからサブルーチンが呼び出され、その中で使用する変数（a、buf）の格納領域がスタックに確保される**

ここまでは、正常なプログラムの①〜③と同じです。

**② 入力データがbufのサイズを超えるため、スタック内の他の領域まで上書きされる**

攻撃者は、変数`buf`への入力データ`data`として、確保されていたサイズ（128バイト）よりはるかに大きいデータを送り込みます。プログラムがデータサイズをチェックしていない場合、C/C++言語の`strcpy`関数は、サイズの制限なしに入力データをメモリ内の変数領域（開始位置）からコピーしてしまいます。その結果、確保されていた`buf`の領域を超えて、スタック内の他の領域まで上書きされます（**オーバフロー状態**）。

なお、スタックは高位アドレスから低位アドレスに向かって使われますが、変数へのデータの書込みは低位アドレスから高位アドレスに向かって行われます。そのため、`buf`からあふれたデータは、`buf`より高位アドレス側に格納されている変数`a`や戻り先を上書きしてしまいます。

```
図：BOF攻撃の実行イメージ②

 低位アドレス
   ┌─────────────────┐
   │ buf ← data       │ ↓ 書込み方向
   ├─────────────────┤
   │ a   ← data（続き）│ （上書き）
   ├─────────────────┤
   │ 戻り先← data（続き）│ （上書き）
   └─────────────────┘
 高位アドレス
```

**③ サブルーチンの処理が終了しても、本来の戻り先には戻れなくなる**

サブルーチンの処理は終了しましたが、スタックに格納されていたはずの戻り先が上書きされているため、プログラムは本来の戻り先（メインルーチンの7行目）には戻れません。戻り先が単に不正なデータで上書きされた場合は、プログラムが異常終了します（**サービス不能状態**となる）。つまり、この段階で止まっても可用性は損なわれます。

**④ 侵入者が意図したとおりに不正なコードが実行される**

攻撃者（侵入者）は、入力データ`data`の中に、不正な機械語のコード（Code）と、そこに処理を飛ばすための偽りの戻り先（Address）をセットしておきます。しかも、この偽りの戻り先が、本来の戻り先が格納されていた箇所に上書きされるように細工されています。そのため、サブルーチンの終了時に処理が不正なコードへ移り、侵入者の意図どおりにコードが実行されます。

```
図：BOF攻撃の実行イメージ④

 低位アドレス
   ┌──────────────────┐
   │ 不正なコード(Code) │ ←──┐
   ├──────────────────┤     │
   │ （パディング）       │     │ 処理が移る
   ├──────────────────┤     │
   │ 偽りの戻り先(Address)│ ───┘
   └──────────────────┘
 高位アドレス
            ↓
      シェル（/bin/sh）起動 → 侵入者が操作
```

このとき送り込まれる不正なコードには、ターゲットとなったサービスをシェル（`/bin/sh`）に置き換えるものが多く、このようなコードは「**シェルコード**」とも呼ばれます。ターゲットのサービスが管理者（root）権限で動作していれば、侵入者は管理者権限でシェルを操作できます。ここに「なぜBOFで管理者権限が奪われるのか」の答えがあります。**乗っ取られたプログラムの権限が、そのまま攻撃者の権限になる**からです。

なお、侵入者は、起動させるプログラム自体をデータに潜ませて送り込むこの手法のほかに、ターゲットホスト上の既存のプログラム（バックドアのように機能するもの）を実行させる場合もあります。

> **用語：シェル**
> UNIXにおいて、ユーザーからのコマンドを解釈してOS（カーネル）に伝えるユーザーインタフェースとなるプログラムである。代表的なものに`sh`、`bash`、`csh`などがある。

> **用語：バックドア**
> 侵入者が、一度侵入したホストに再び容易に侵入するために、密かに設置する侵入口である。特定の条件で接続を受け付けるプログラムなどが使われる。
> バックドアを仕掛けられたホストは、再び侵入される可能性がある。そのため、OSの初期化、アプリケーションの再インストール、パスワードの変更などの対処が必要となる。

ここまでの因果を1文にまとめると、「攻撃者は、サイズを検査しないプログラムに大きな入力を与えて戻り先を書き換え、その結果、プログラムは攻撃者の用意したコードへ処理を移し、プログラムの権限で任意の操作が行われる」となります。科目Bで「BOFの脆弱性があると何が起きるか」を問われたら、この形で書けるようにしておきましょう。

| 段階 | 起きていること | 損なわれる特性 |
| --- | --- | --- |
| ②〜③で止まった場合 | 戻り先が壊れ、プログラムが異常終了する | 可用性（サービス停止） |
| ④まで成功した場合 | 攻撃者のコードがプログラムの権限で動く | 機密性・完全性・可用性のすべて |

## 3. OS・コンパイラによる保護機能 ― 攻撃と防御のいたちごっこ

BOFの根本原因はプログラムのバグですが、世の中のすべてのプログラムからバグをなくすことは現実には不可能です。そこでOSやコンパイラの開発者は、「バグが残っていても攻撃を成立させにくくする」仕組みを重ねてきました。一方、攻撃者はその仕組みを回避する手法を編み出してきました。ここではその攻防の流れを、攻撃手順ではなく「各保護機能が何を防ぎ、何を防げないか」という観点で整理します。

### 3.1 DEP/NXビット ― 「データ置き場ではコードを実行させない」

BOF攻撃を防止するため、近年のWindows OSには、指定されたメモリ領域でのコードの実行を禁止する機能である**DEP**（**Data Execution Prevention**：**データ実行防止**）が実装されています。システム管理者がDEPを有効にすると、スタック領域やヒープ領域など、本来データを格納するための領域に送り込まれたコードは実行されません。そのため、前述のような、不正なコードをスタックに送り込んで実行させる攻撃を防ぐことができます。UNIX系OSでも、CPUの**NXビット**（**No eXecute bit**）などを利用した同様の機能が実装されています（Intel社のCPUでは同じ機能を**XDビット**と呼びます）。

DEPが有効なのは、2.3 の図④で「不正なコード(Code)」が置かれていたのがスタック、つまりデータ置き場だったからです。データ置き場を「実行禁止」にすれば、偽りの戻り先に処理が移っても、CPUはそこにあるコードを実行せず、プログラムを停止させます。

### 3.2 return-to-libc攻撃とROP ― 「既にある正規のコード」を悪用する

しかし、DEPを回避する攻撃手法として、**return-to-libc攻撃**があります。return-to-libc攻撃では、攻撃者はスタックに不正なコードを送り込むのではなく、共有ライブラリ（**libc**など）内に既に存在する関数（`system`関数など）を呼び出すように、リターンアドレスと引数を書き換えることでBOF攻撃を成立させます。実行されるのはメモリ上の正規のコードであるため、この攻撃はデータ実行防止機能が実装されていても防ぐことができません。

> **補足：ROP（Return-Oriented Programming）**
> return-to-libc攻撃を発展させた手法として、ROPがある。ROPは、既存のプログラムやライブラリ内にある、`ret`命令で終わる短い命令列（ガジェット）を連鎖的に呼び出し、任意の処理を実行させる手法である。

試験で押さえるべきは、「DEPはデータ領域でのコード実行を禁じるだけなので、正規のコード領域にある関数や命令列を流用する攻撃は止められない」という限界です。この限界を埋めるのが、次の ASLR です。

### 3.3 ASLRとPIE ― 「どこに何があるか」を分からなくする

return-to-libc攻撃もROPも、攻撃者が「狙う関数や命令列がメモリのどこにあるか」を知っていることが前提です。そこで最近のOSは、このような攻撃の成功を抑制するため、**アドレス空間配置ランダム化**（**Address Space Layout Randomization**：**ASLR**）と呼ばれる技術を採用しています。ASLRとは、OSが、アドレス空間における実行ファイル、ライブラリ、スタック、ヒープなどの配置をランダムにする技術です。これにより、BOF攻撃を成功させるために必要な戻り先（リターンアドレス）や、呼び出す関数のアドレスが特定されにくくなります。

また、ASLRが対象とする領域に加え、テキスト領域（プログラムのコードが格納される領域）のアドレスもランダム化できる技術として、**PIE**（**Position Independent Executable**：**位置独立実行形式**）があります。PIEは、開発者がコンパイル時に指定して作る実行ファイルの形式です。OSのASLRが有効でも、実行ファイル自体がPIEでなければプログラム本体の位置は固定のままになる、という点が実務上の落とし穴です。

### 3.4 スタックカナリアとBOF防止ライブラリ ― 「書き換えられたら止める」

DEPとASLRが「書き換えられた後の悪用」を難しくする機能だとすれば、スタックカナリアは「書き換えられたこと自体を検知する」機能です。

> **補足：スタックカナリア**
> コンパイラによる対策として、スタック上のローカル変数とリターンアドレスの間に「カナリア」と呼ばれる値を配置し、関数の終了時にその値が書き換えられていないかを検査する技術もある。書換えが検出された場合はプログラムを強制終了させ、不正なコードの実行を防ぐ。GCCの`-fstack-protector`オプションや、Visual C++の`/GS`オプションなどで利用できる。

2.3 の図②を思い出してください。`buf`からあふれたデータは、低位から高位へ順に書き込まれるので、戻り先に届く前に必ずその手前を通過します。そこに「番兵」の値を置いておけば、戻り先が書き換えられたときには番兵も壊れている、という理屈です。

```
図：カナリアを配置したスタック（イメージ）

 低位アドレス
   ┌─────────────────┐
   │ buf（128バイト）   │ ↓ あふれたデータの書込み方向
   ├─────────────────┤
   │ a                │
   ├─────────────────┤
   │ カナリア値         │ ← 関数の終了時に「元の値のままか」を検査
   ├─────────────────┤
   │ 戻り先（7行目）    │
   └─────────────────┘
 高位アドレス
```

この発想を実装した代表的な技術が、次の3つです（第7節 7.2 で「開発者が何をすべきか」の観点から再確認します）。

- **StackGuard**：GNU Cコンパイラ（**GCC**）の拡張版です。StackGuardでコンパイルされたプログラムは、サブルーチンを呼び出す際に、スタック中の変数とリターンアドレスの間に「カナリア（"カナリア値"ともいう）」と呼ばれる値を埋め込んでおきます。そして、サブルーチン実行後にカナリアの値が変更されているかどうかを確認することで、BOF攻撃を検知します。改ざんを検知した場合は、プログラムを強制的に停止させます。
- **SSP**（**Stack Smashing Protection**）：StackGuardと同様に、スタック領域に「カナリア」もしくは「**guard**」と呼ばれる値を埋め込んでBOF攻撃を検知する技術です。StackGuardはアセンブラレベルでコンパイラを拡張しているため、特定のCPUのみをサポートしています。これに対しSSPは、コンパイラが生成する中間言語のレベルでBOF検出のためのコードを生成するため、様々なCPU環境で利用できます。
- **Libsafe**：BOF防止機能を追加したライブラリです。Libsafeは、プログラム実行時にBOFを引き起こす危険性の高い主な関数の呼出しを検知すると、ライブラリからの関数の呼出し順序を変更し、BOFをチェックする関数を先に実行させることで、不正なコードの実行を防ぎます。LibsafeはStackGuardとは異なり、対象プログラムを再コンパイルする必要がなく、既存の実行ファイルにも適用できます。

> **補足：現在の実務での位置づけ**
> StackGuard や Libsafe は、BOF対策の考え方を確立した歴史的な技術として試験に登場する。以前はこれらを個別に導入することが対策とされていたが、現在は SSP が GCC 本体に取り込まれて `-fstack-protector` 系のオプション（`-fstack-protector-strong` など）として標準的に使われ、危険な関数の実行時チェックは glibc の `_FORTIFY_SOURCE` などが担うのが一般的である。試験では「カナリア＝StackGuard/SSP」「再コンパイル不要＝Libsafe」の対応で覚えておけばよい。

> **カナリア(canary)の由来**
> かつて炭鉱では、有毒ガスの発生を早期に察知するため、ガスに敏感なカナリアを坑内に持ち込んでいた。スタック上に埋め込む検知用の値は、異常をいち早く知らせるこのカナリアになぞらえて名付けられている。

### 3.5 保護機能の比較 ― 何を防ぎ、何を防げないか

ここまでの保護機能を、「誰が有効にするか」「何を防ぐか」「何を防げないか」で並べます。どれか1つで完璧になるものはなく、重ねて使う（多層防御）ことが前提です。

| 保護機能 | 誰が有効にするか | 防ぐもの | 防げないもの |
| --- | --- | --- | --- |
| DEP／NXビット | OSの管理者（対応CPUが必要）、開発者（リンク時の指定） | データ領域（スタック・ヒープ）に送り込まれたコードの実行 | return-to-libc攻撃・ROPなど既存コードの流用、プログラムの異常終了 |
| ASLR | OSの管理者 | 攻撃者による戻り先・関数アドレスの特定 | アドレスが何らかの方法で漏えいした場合の攻撃、異常終了 |
| PIE | 開発者（コンパイル・リンク時） | プログラム本体（テキスト領域）のアドレス特定 | 同上 |
| スタックカナリア（SSP、`/GS`） | 開発者（コンパイル時） | 戻り先の書換えを検知し、不正なコードの実行前に停止 | カナリアを経由しない書換え（ヒープBOFなど）、強制終了によるサービス停止 |
| Libsafe | システム管理者（ライブラリの差し込み） | 危険な関数呼出しでのBOF | 対象関数以外でのBOF |

表の右列に共通して「異常終了」が並んでいることに注目してください。これらの保護機能は「乗っ取り」を「停止」に変えるものであり、サービスが止まること（可用性の低下）までは防げません。停止させない唯一の方法は、バグそのものを直すことです。

### 3.6 保護機能の有効化設定の見た目

開発者とシステム管理者は、保護機能が「実装されている」だけでなく「実際に有効になっている」ことを確認する必要があります。以下は、その設定や確認結果がどう見えるかの例です。

**開発者：GCC（Linux）でのコンパイル・リンク時の指定例**

```
# Makefile の一部
CFLAGS  = -O2 -Wall -fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE
LDFLAGS = -pie -Wl,-z,noexecstack -Wl,-z,relro,-z,now

example-srv: example-srv.c
	$(CC) $(CFLAGS) $(LDFLAGS) -o $@ $<
```

| 指定 | 効果 |
| --- | --- |
| `-fstack-protector-strong` | スタックカナリア（SSP）を付ける |
| `-D_FORTIFY_SOURCE=2` | `strcpy` などの危険な関数に、コンパイル時・実行時のサイズ検査を付ける（最適化 `-O1` 以上が必要。新しい環境では `3` も可） |
| `-fPIE` と `-pie` | 位置独立実行形式（PIE）で作る |
| `-Wl,-z,noexecstack` | スタックを実行不可にする（DEP/NX） |
| `-Wl,-z,relro,-z,now` | 起動後に書き換える必要のない管理表を読み取り専用にする |

多くのLinuxディストリビューションでは、これらの一部が既定で有効になっています。ただし、独自に書いたビルドスクリプト（Makefile）が既定値を上書きして無効化していることもあるため、開発者は完成した実行ファイルで確認すべきです。

**開発者：Visual C++（Windows）での指定例**

| オプション | 種類 | 効果 |
| --- | --- | --- |
| `/GS` | コンパイラ | スタックカナリア（セキュリティクッキー）を付ける |
| `/NXCOMPAT` | リンカ | DEP に対応した実行ファイルとして作る |
| `/DYNAMICBASE` | リンカ | ASLR に対応した実行ファイルとして作る |

**システム管理者：Linux で ASLR の設定を確認する例**

```
$ sysctl kernel.randomize_va_space
kernel.randomize_va_space = 2
```

値の意味は、`0`＝無効、`1`＝スタックや共有ライブラリなどをランダム化、`2`＝1に加えてヒープもランダム化（完全）です。管理者は、この値が `2` であることを確認し、トラブル対応などで一時的に `0` にした場合は必ず元に戻すべきです。

**システム管理者・開発者：実行ファイルの保護状態を確認する例**

```
$ readelf -h example-srv | grep Type
  Type:                              DYN (Position-Independent Executable file)   ← PIE で作られている

$ readelf -l example-srv | grep -A1 GNU_STACK
  GNU_STACK      0x0000000000000000 0x0000000000000000 0x0000000000000000
                 0x0000000000000000 0x0000000000000000  RW     0x10            ← RW（実行権 E なし）＝スタック実行不可

$ readelf -s example-srv | grep __stack_chk_fail
    12: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND __stack_chk_fail@GLIBC_2.4  ← カナリア検査が組み込まれている
```

`GNU_STACK` の欄が `RWE` になっていれば、その実行ファイルはスタック上のコード実行を許しており、DEP/NX の恩恵を受けていません。

**システム管理者：Windows で DEP の方針を設定する例**

```
C:\> bcdedit /set {current} nx OptOut
この操作を正しく終了しました。
```

`nx` の値は、`OptIn`（システムの構成要素と明示的に対応したアプリだけを保護）、`OptOut`（除外指定したもの以外すべてを保護）、`AlwaysOn`（常にすべて保護）、`AlwaysOff`（無効）の4種類です。管理者は、サーバでは `OptOut` 以上を選び、除外リストを最小限に保つべきです。Windows の「Windows セキュリティ」＞「アプリとブラウザーの制御」＞「Exploit Protection」の画面でも、DEP や ASLR の設定をアプリごとに確認できます。

## 4. BOFの仲間 ― Use-After-Free と整数オーバフロー

### 4.1 Use-After-Freeを悪用したヒープBOF

**Use-After-Free**（CWE-416）とは、プログラムが解放済みのメモリ（ヒープ領域）を使ってしまうことにより、攻撃者に任意のコードの実行を許すおそれのある脆弱性です。攻撃者は、解放済みのメモリ領域に自分が用意したデータを配置させ、そのメモリ領域を参照するポインタ（**ダングリングポインタ**）をプログラムが使用したときに、不正なコードを実行させます。1.1 で見たように、ヒープは開発者が明示的に解放する領域なので、「解放したのに、古いポインタを使い続ける」というバグが生まれやすいのです。

Use-After-Freeは、ASLRが有効な場合でも、共有ライブラリ内のメモリアドレスが特定されるなどして、攻撃が成立する可能性があります。また、スクリプト言語を用いて攻撃を行えるため、Webブラウザや文書閲覧ソフトなど、スクリプトの実行機能をもつ多くのソフトウェアが攻撃に悪用されるおそれがあります。利用者がWebページを閲覧しただけで攻撃が成立しうるので、ブラウザの更新が重要になるわけです。抜本的な対策は、製品の開発者が当該脆弱性を修正すること（利用者の側から言えば、修正版を速やかに適用すること）です。

開発者が自分のコードでこのバグを作り込まないための基本は、「解放したポインタにはすぐ `NULL` を代入し、以後使えないようにする」ことです。

```c
free(p);
p = NULL;   /* 解放後の p を誤って使っても、解放済み領域を参照しない */
```

> **試験に出た**
> 情報処理安全確保支援士試験の平成30年度午後Ⅰ問1で、Use-After-Freeの脆弱性と対策に関する問題が出題された。

### 4.2 整数オーバフロー ― 「計算の桁あふれ」がBOFを呼ぶ

BOFの一種に、**整数オーバフロー**（CWE-190）があります。整数オーバフローとは、整数の演算結果が格納先の型で表現できる上限値を超え、桁あふれが発生することです。整数オーバフローの脆弱性を悪用した攻撃を「**整数オーバフロー攻撃**」といいます。

例えば、確保するバッファのサイズを整数演算で求めるプログラムで桁あふれが発生すると、本来よりはるかに小さなサイズのバッファしか確保されません。その結果、後続のデータコピー処理でバッファの領域を超えた書込みが行われ、BOFが発生します。つまり、サイズ検査をしていたとしても、その検査の元になる「サイズの計算」が壊れていれば意味がない、ということです。

```c
/* 整数オーバフローの例（32ビット符号なし整数の場合） */
unsigned int count;          /* 攻撃者が指定する要素数 */
unsigned int size = count * sizeof(int);
/* countが非常に大きいと size が桁あふれして小さな値になる */
int *p = malloc(size);       /* 小さな領域しか確保されない */
/* 以降、count個の要素を書き込むとヒープBOFが発生する */
```

開発者は、掛け算の**前に**、結果が型の上限を超えないかを確認すべきです。修正後のコードは次のような形になります。

```c
/* 修正例：演算の前に上限を検査する */
if (count > SIZE_MAX / sizeof(int)) {
    return ERROR;            /* 桁あふれするサイズは受け付けない */
}
size_t size = count * sizeof(int);
int *p = malloc(size);

/* 別解：calloc は要素数×要素サイズの桁あふれを内部で検査する */
int *q = calloc(count, sizeof(int));
```

## 5. setuid/setgid属性を悪用したBOF攻撃 ― 一般ユーザが root になる経路

2.3 では「ネットワーク越しに、管理者権限で動くサービスを乗っ取る」形を見ました。もう一つの典型が、すでにホストにログインできる攻撃者（一般ユーザ権限しかもたない侵入者や内部者）が、**setuid/setgid属性**をもつコマンドにサイズの大きなデータを送り付けてBOF状態を引き起こさせ、管理者（root）の権限を手に入れる手法です。

### 5.1 setuid/setgidの概要

すべてのファイルやディレクトリには、ユーザ単位、あるいはユーザが所属するグループ単位に、読込み、書込み、実行などの属性（UNIX系のOSでは**パーミッション**という）が設定されています。

**setuid**（set user ID）は、読込みや書込みなどと同様に、実行属性をもつファイルに設定する属性の一つです。setuidは、実行されたプログラム（プロセス）のユーザ権限（**実効ユーザID**：**Effective User ID**：**EUID**）に、そのプログラムの所有者の権限を一時的に設定します。これにより、一般ユーザなどが使用するコマンドの中で、管理者の権限などを必要とする処理を実行できるようになります。

通常、実行中のプログラム（プロセス）には、そのプログラムを実行したユーザの権限が設定されます。一方、setuid属性をもつプログラムの所有者がrootであれば、そのプロセスにはroot権限が与えられます。

また、**setgid**（set group ID）も、ファイルやディレクトリに設定する属性の一つです。この属性が設定されたファイルを実行すると、生成されるプロセスのグループID（**GID**）は、そのファイルの所有者のGIDとなります。ディレクトリに設定した場合は、そのディレクトリ内に作られるファイルのGIDが、ディレクトリのGIDを継承します。

| 項目 | setuid | setgid |
| --- | --- | --- |
| 設定対象 | 実行属性をもつファイル | ファイル、ディレクトリ |
| ファイル実行時の効果 | プロセスのEUIDが、ファイル所有者のものになる | プロセスのGIDが、ファイル所有者のGIDになる |
| ディレクトリに設定した場合 | （一般的には意味をもたない） | 中に作られるファイルがディレクトリのGIDを継承する |
| `ls -l` での表示 | 所有者の実行権限の位置に `s` | グループの実行権限の位置に `s` |
| 8進数表記 | `4000` | `2000` |

> **パーミッションの表記**
> `ls -l`コマンドでは、setuid属性が設定されたファイルは所有者の実行権限の位置に`s`と表示される(例:`-rwsr-xr-x`)。setgid属性の場合は、グループの実行権限の位置に`s`と表示される(例:`-rwxr-sr-x`)。8進数表記では、setuidは`4000`、setgidは`2000`で表される。

システム管理者が実際に目にする表示は、次のようなものです。

```
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 59976  3月 14  2026 /usr/bin/passwd
    ↑ 所有者の実行権限の位置が x ではなく s ＝ setuid が設定されている
```

### 5.2 setuid属性をもつプログラムの例

setuid属性をもつ代表的なプログラムに、UNIX系OSのパスワード変更に用いる**passwdコマンド**（/usr/bin/passwd）があります。パスワード情報を格納するファイル（/etc/passwdや/etc/shadow）は、root以外のユーザには書込みが許可されていません。それでも一般ユーザが自分のパスワードを変更できるのは、passwdコマンドにsetuid属性が設定されているためです。一般ユーザがpasswdコマンドを実行すると、そのプロセスには同コマンドの所有者であるrootの権限が与えられます。

一般的なUNIX系OSでは、passwdコマンドのほかにも、pingコマンド（/bin/ping）やsuコマンド（/bin/su）など、所有者がrootでsetuid属性が設定されたプログラムが幾つかあります。

> **補足：ping の現状**
> 以前は ping も root 所有の setuid プログラムとして配布されるのが一般的だったが、現在の多くの Linux ディストリビューションでは、root 権限をまるごと与えずに済むよう、必要な特権だけを与えるケーパビリティ（file capabilities）や、一般ユーザにICMP送信を許すカーネル設定に置き換えられ、setuid が外されている。「setuid をできるだけ使わない」という方向に OS 側も進んでいる例である。

### 5.3 攻撃の仕組み

侵入者は、所有者がrootでsetuid/setgid属性をもつプログラムを実行し、非常にサイズの大きい入力データを与えます。これによってBOF状態を引き起こし、root権限を手に入れます。

setuid属性をもつプログラムは、一般ユーザが実行してもroot権限で動作します。そのため、プログラムにBOFの脆弱性が存在すると、攻撃者が送り込んだ不正なコードもroot権限で実行されてしまいます。2.3 で「乗っ取られたプログラムの権限が、そのまま攻撃者の権限になる」と述べたことの、もう一つの現れです。システム管理者が setuid プログラムの数を減らすべきなのは、**root 権限で動く入り口の数そのもの**を減らすためです。

### 5.4 rootkit ― 奪った権限を隠して保持する道具

root 権限を奪った攻撃者が次に行うのは、見つからないように居座ることです。そのための道具が rootkit です。

> **Column:rootkit(ルートキット)**
>
> **rootkit**とは、侵入に成功した攻撃者が、その後の不正な活動を行いやすくし、自身の存在を隠蔽するために使用するソフトウェアなどをまとめたパッケージの呼称(俗称)である。当初は、UNIX系のシステムに侵入してroot権限を手に入れた侵入者が、システム管理者に見つかることなくroot権限を保持して活動を続けるためのツールであった。現在では、Windowsなど"root"というアカウントが存在しない環境で同様の働きをするツールもrootkitと呼ばれている。
>
> 古くから知られているrootkitには、次のようなものがある。
>
> - UNIX環境でプロセスやネットワーク接続の状況を確認するために使用される"ps"や"netstat"などのコマンドを置き換え、特定のプロセスや接続の存在を隠蔽するもの
> - ログを改ざんするもの
>
> また、コマンドそのものを置き換えるのではなく、ファイル、ディレクトリ、レジストリなどのシステムリソースへのアクセスに伴うシステムコールを横取りし、その応答を偽装するタイプのrootkit(**カーネルモードrootkit**)も存在している。

rootkit が厄介なのは、システム管理者が調査に使う道具（`ps`、`netstat`、ログ）そのものが嘘をつくようになる点です。このため、管理者は「侵入された可能性が高いホストの上で、そのホストのコマンドを使って調べても信用できない」と考え、第7節で述べるように、OSのクリーンインストールによる再構築を選択肢に入れる必要があります。

## 6. BOF攻撃による影響と、現場での見え方

### 6.1 攻撃の流れと影響

BOF攻撃は、一般に次のような流れで行われます。

1. 攻撃者が、ターゲットとなるプログラムに、想定されたバッファのサイズを超える大きなデータを送り付ける。
2. 入力データのサイズがチェックされないため、バッファに収まりきらないデータがスタック上の隣接領域に溢れ出す。
3. 溢れ出したデータにより、スタックに格納されたリターンアドレスなどが書き換えられる。
4. サブルーチンの処理が終了して制御が戻る際、書き換えられたリターンアドレスに処理が移り、攻撃者が送り込んだ不正なコードが実行される。

攻撃者がリターンアドレスの書換えを行い、処理をシェルなどの起動に置き換えることに成功すれば、侵入者は管理者権限でそのホストを操作できることになります。そうなれば、侵入者は、ホストに保存された機密情報のコピー、不正プログラムの埋込み、設定変更、ログの消去などを自在に行うことができます。このような行為を、**権限の乗っ取り**、もしくは**権限昇格**といいます。

なお、ネットワークを通じてサービスを提供するタイプのサーバプログラムは、管理者権限で実行されていることが多いため、BOFの脆弱性が存在する場合には非常に危険です。サーバの管理者が、サービスを専用の一般ユーザ権限で動かすべきだとされるのはこのためです（[5.2 ホストの要塞化](5.2_ホストの要塞化.md) 参照）。権限を絞っておけば、乗っ取られても攻撃者が得る権限は小さくなります。

また、攻撃が④まで成功せず③までにとどまった場合でも、ターゲットとなったサービスは異常終了してしまいます。この場合は、2.7 で学ぶ**DoS攻撃**と同様の影響を受けることになります。

| 攻撃の到達点 | 攻撃者が得るもの | 組織が受ける影響 | 損なわれる特性 |
| --- | --- | --- | --- |
| ③まで（書換えのみ） | なし（サービスを止められる） | サービス停止 | 可用性 |
| ④まで（一般ユーザ権限のサービス） | そのユーザの権限での操作 | そのユーザが読める情報の漏えい・改ざん、さらなる権限昇格の足掛かり | 機密性・完全性 |
| ④まで（root 権限のサービス・setuid root） | ホスト全体の支配 | 機密情報のコピー、不正プログラムの埋込み、設定変更、ログの消去 | 機密性・完全性・可用性、責任追跡性（ログ消去） |

### 6.2 異常終了はどう見えるか ― エラーメッセージとクラッシュログの例

システム管理者にとって、BOF攻撃の最初の兆候は「サービスが原因不明で落ちる」ことであることが少なくありません。第3節の保護機能は乗っ取りを「強制終了」に変えるので、保護機能が働いた痕跡はクラッシュのメッセージとして残ります。管理者は、これを単なる不具合として再起動で済ませず、攻撃の可能性を疑って調べるべきです。

**スタックカナリア（SSP）が書換えを検知したとき（Linux、端末への出力）**

```
$ ./example-srv
*** stack smashing detected ***: terminated
Aborted (core dumped)
```

**_FORTIFY_SOURCE が危険な関数のサイズ超過を検知したとき**

```
*** buffer overflow detected ***: terminated
Aborted (core dumped)
```

**不正なアドレスへのアクセスでプログラムが落ちたとき（カーネルログ）**

```
$ dmesg | tail -n 2
[123456.789012] example-srv[2345]: segfault at 7ffd2b4c9000 ip 000055d0c3a1b1c9 sp 00007ffd2b4c8e10 error 6 in example-srv[55d0c3a1a000+2000]
```

**systemd で管理しているサービスが落ちたとき（ジャーナル）**

```
$ journalctl -u example-srv.service
Sep 30 03:12:45 host01 systemd-coredump[2350]: Process 2345 (example-srv) of user 0 dumped core.
Sep 30 03:12:45 host01 systemd[1]: example-srv.service: Main process exited, code=dumped, status=6/ABRT
Sep 30 03:12:45 host01 systemd[1]: example-srv.service: Failed with result 'core-dump'.
```

`status=6/ABRT` はプログラムが自ら中断した（カナリア検査などで止めた）ことを、`status=11/SEGV` は不正なメモリアクセスで落ちたことを示します。`of user 0` は、落ちたプロセスが root（UID 0）で動いていたことを意味します。root で動くサービスでこれが繰り返し起きていれば、管理者は最優先で調査すべきです。

**Windows のイベントログ（アプリケーション）**

```
ログの名前: Application
ソース:     Application Error
イベント ID: 1000
レベル:     エラー
説明:
障害が発生しているアプリケーション名: example-srv.exe、バージョン: 3.2.4.0
障害が発生しているモジュール名: example-srv.exe
例外コード: 0xc0000409
```

例外コード `0xc0000409` は、`/GS` のセキュリティクッキー（カナリア）検査などでスタックバッファのオーバランが検出されたことを示します。`0xc0000005` はアクセス違反で、DEP による実行禁止違反もこのコードで現れます。

| 見えたもの | 意味すること | 管理者がすべきこと |
| --- | --- | --- |
| `stack smashing detected`、`0xc0000409` | 戻り先の手前が書き換えられ、保護機能が停止させた | 直前の入力（アクセスログ・通信ログ）を確認し、脆弱性情報と照合する |
| `segfault`、`0xc0000005` の繰り返し | 不正なメモリアクセスが起きている（バグ・攻撃の両方がありうる） | 発生時刻と接続元を突き合わせ、同じ接続元から大きな入力が来ていないか調べる |
| root で動くサービスのクラッシュ | 乗っ取られた場合の被害が最大 | 最優先で調査し、必要ならサービスを一時停止して接続元を遮断する |

## 7. BOF攻撃への対策

BOF攻撃はソフトウェアのバグが原因となっています。そのため、対策は「バグのあるソフトウェアを使う側（利用者・システム管理者）」と「バグを作る側（開発者）」の2つの立場に分けて考えます。

### 7.1 ソフトウェア利用者（システム管理者）としての対策

ソフトウェア利用者としての対策の基本は、OSや使用しているソフトウェアのバージョンアップやパッチの適用を確実に行い、既知の**セキュリティホール**を塞ぐことです。システム管理者がとるべき主な対策を、1.2 で学んだ対策の機能ごとに挙げます。

**予防・防止**

- システム管理者は、既知の脆弱性を突かれないために、OS及び使用しているソフトウェアのバージョンを最新化し、パッチを適用すべきです。
- システム管理者は、塞いだつもりの穴が残っていないことを確かめるために、**脆弱性検査**を実施し、BOF攻撃に関するセキュリティホールが塞がれていることを確認すべきです（第5章 5.3 参照）。
  - 問題箇所があれば対処します。
- ネットワーク管理者は、攻撃者に脆弱なサービスへ到達させないために、**ファイアウォール**によって、不要なポートへのアクセスを遮断すべきです。
- システム管理者は、スタックに送り込まれたコードを実行させないために、データ実行防止（DEP：Data Execution Prevention）機能を備えたCPU（NXビット/XDビット対応）及びOSを使用し、当該機能を有効に設定すべきです。
  - ただし、この対策を行ったとしても、実行禁止に指定された領域以外にあるプログラムを起動させるタイプのBOF攻撃（return-to-libc攻撃など）は防げません。また、BOF攻撃の対象となったプログラムが異常終了することも防ぐことはできません。
- システム管理者は、攻撃者に戻り先や関数のアドレスを特定させないために、アドレス空間配置ランダム化（ASLR：Address Space Layout Randomization）技術が実装されたOSを使用し、有効になっていることを確認すべきです（3.6 の確認例を参照）。
- システム管理者は、root 権限で動く入り口を減らすために、setuid/setgid属性をもつプログラムに、次の手順で対処すべきです。
  1. findコマンドを使用して、所有者がrootでsetuid/setgid属性をもつプログラムを探す。
  2. 上記プログラムの中で、不要なものを削除する。
  3. 上記2.で削除できないもののうち、setuid/setgid属性が不要なものは、パーミッションを変更してsetuid/setgid属性を解除する。

> **ASLR(アドレス空間配置ランダム化)**
> プログラムの実行ごとに、スタック、ヒープ、共有ライブラリなどが配置されるメモリアドレスをランダムに変化させる技術である。攻撃者は不正なコードやライブラリ関数の配置アドレスを予測しにくくなるため、リターンアドレスを狙いどおりに書き換えることが困難になる。

> **setuid/setgid属性をもつプログラムの検索と解除の例**
>
> ```
> # find / -user root \( -perm -4000 -o -perm -2000 \) -type f -ls
> # chmod u-s /path/to/program   (setuid属性の解除)
> # chmod g-s /path/to/program   (setgid属性の解除)
> ```

`find` の結果は、例えば次のように見えます。管理者は、この一覧を前回の点検結果と比べ、見覚えのない setuid プログラムが増えていないか（侵入者が置いたバックドアではないか）も確認すべきです。

```
# find / -user root \( -perm -4000 -o -perm -2000 \) -type f -ls
  1311   60 -rwsr-xr-x   1 root  root   59976 Mar 14  2026 /usr/bin/passwd
  1325   56 -rwsr-xr-x   1 root  root   55680 Mar 14  2026 /usr/bin/su
  1407   36 -rwxr-sr-x   1 root  tty    35048 Mar 14  2026 /usr/bin/wall
 99812   20 -rwsr-xr-x   1 root  root   16784 Sep 29 02:41 /tmp/.x/update   ← 業務で使う覚えがない。要調査
```

**検知・追跡**

- システム管理者は、攻撃の試みに早く気づくために、ネットワーク監視型IDS、ホスト監視型IDS、IPSを用いて検知すべきです（第5章 5.6・5.7 参照）。
- システム管理者は、ホストのログが改ざんや消去をされずに保存されていれば、それを用いて追跡調査を行います。rootkit によるログ改ざんに備え、ログは別のサーバ（ログサーバ）へ転送して保存しておくべきです。
- システム管理者は、6.2 で見たクラッシュログを監視対象に加え、同じサービスの異常終了が繰り返されていないかを確認すべきです。

**回復**

- システム管理者は、サーバログやIDSログなどから原因（脆弱性）を特定し、ベンダーが公開している対策手順に従って対処します。
- システム管理者は、不正アクセスを受けたホスト、及び当該ホストからアクセス可能なすべてのホストを対象に、データの改ざん、不正プログラムの埋込み、設定変更などの有無を徹底的に検証し、問題箇所を修復します。状況によっては、OSをクリーンインストールしてサーバ環境を再構築します（rootkit やバックドアが残っている可能性を消し切れない場合）。
- システム管理者は、予防対策と同様に脆弱性検査を実施し、問題箇所があれば対処します。

### 7.2 脆弱性情報を読み、パッチ適用を判断する

「パッチを適用する」と一言でいっても、システム管理者は、公開された脆弱性情報が自社に関係するかを判断し、優先度を決めなければなりません。脆弱性情報の仕組み（CVE、CWE、CVSS、JVN）は [3.1 脆弱性の概要](3.1_脆弱性の概要.md) で詳しく扱います。ここでは、BOFの脆弱性情報がどう見えるかを、架空の製品で示します。

```
JVN#00000000
Example Server におけるスタックベースのバッファオーバーフローの脆弱性

公表日 : 2026/09/15
概要   : 株式会社エグザンプルが提供する Example Server には、
         スタックベースのバッファオーバーフローの脆弱性が存在します。
CVSS v3: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H  基本値 9.8
影響を受けるシステム : Example Server 3.0.0 から 3.2.4 まで
詳細情報 : 特定のリクエストヘッダの長さを検査せずに固定長の領域へ
           コピーしているため、スタックベースのバッファオーバーフロー（CWE-121）が発生します。
想定される影響 : 遠隔の第三者によって、サービス運用妨害（DoS）状態にされたり、
                 サーバの実行権限で任意のコードを実行されたりする可能性があります。
対策方法 : 開発者が提供する最新版（3.2.5 以降）へアップデートしてください。
ワークアラウンド : アップデートを適用できない場合は、当該サービスへのアクセスを
                   信頼できる接続元に限定してください。
関連文書 : CVE-2026-00000
```

読み方のポイントは次のとおりです。「想定される影響」に DoS と任意のコード実行が並んでいるのは、6.1 の表の「③で止まる場合」と「④まで成功する場合」に対応しています。CVSSのベクタ `AV:N`（ネットワーク経由で攻撃可能）、`PR:N`（攻撃に権限不要）、`UI:N`（利用者の操作不要）は、インターネットから誰でも攻撃できることを意味し、基本値 9.8 は最も深刻な「緊急」の区分に入ります。BOF系の脆弱性で見かけるCWEには、CWE-120（古典的なバッファオーバフロー）、CWE-121（スタックベース）、CWE-122（ヒープベース）、CWE-787（範囲外への書込み）、CWE-416（Use-After-Free）、CWE-190（整数オーバフロー）などがあります。

システム管理者は、この情報を資産台帳と突き合わせ、次のような判断表に沿って対応を決めます（判断基準や期限は組織のポリシで定めるものであり、下表は一例です）。

| 状況 | 対応の例 | 理由 |
| --- | --- | --- |
| 該当バージョンを使い、インターネットに公開しており、CVSS が高く、悪用が確認されている | 検証を最小限にして緊急適用する。適用までは接続元の制限や IPS のシグネチャで守る | 攻撃者がすぐに狙える状態で、放置すれば侵入される可能性が高い |
| 該当バージョンを使っているが、社内からしか到達できない | 検証環境で動作確認したうえで、計画的に早期適用する | 到達できる攻撃者が限られるが、侵入後の横展開に使われうる |
| パッチがまだ提供されていない | ワークアラウンド（機能の無効化、接続元の制限、サービスの一時停止）を実施し、パッチ公開を監視する | パッチを待つ間も攻撃は来る |
| パッチ適用で業務への影響が大きく、すぐには適用できない | リスクを評価して経営層の承認を得たうえで、代替策（WAF・IPS による仮想パッチ、監視強化）で期限付きで受容する | 受容したリスクの責任の所在を明確にするため |
| 該当バージョンを使っていない | 対応不要と記録する（資産台帳の正確さが前提） | 「確認した」という記録が監査で求められる |

### 7.3 ソフトウェア開発者としての対策

根本原因がバグである以上、最も効果が大きいのは、開発者がそもそもBOFを作り込まないことです。ソフトウェア開発者としてとるべき主な対策を次に挙げます（詳細は第8章 8.2節で解説。Webアプリケーションに固有の対策は 3.6 も参照）。

- 開発者は、コピー先の大きさを超えた書込みを起こさないために、gets、strcpy、strcat、sprintfなど、BOFを引き起こす危険性の高い関数を使用しないようにすべきです。
  - 代わりに、fgets、strncpy、strncat、snprintfなど、書込みサイズを指定できる関数を使用します。
- 開発者は、想定外の長さのデータを処理に渡さないために、入力データの**レングスチェック**を確実に行うべきです。
- 開発者は、バグが残っていても乗っ取りを防ぐために、スタック上に埋め込んだ攻撃検知用の値によって、BOF攻撃を検知する仕組みを組み込むべきです。
  - これを実現するものとして、StackGuard や SSP があります（仕組みは 3.4 参照）。現在は GCC の `-fstack-protector-strong` や Visual C++ の `/GS` を指定するのが一般的です。
- システム管理者や開発者は、再コンパイルできない既存の実行ファイルを守るために、BOF防止機能を追加したライブラリを使用することもできます。
  - これを実現する代表的なものとして、Libsafe があります（3.4 参照）。

危険な関数と代替関数の対応を、注意点とあわせて表にします。

| 危険な関数 | なぜ危険か | 代替関数 | 代替関数を使うときの注意 |
| --- | --- | --- | --- |
| `gets` | 読み込む長さを指定する手段がない | `fgets(buf, sizeof(buf), stdin)` | 末尾に改行文字が残る。なお `gets` は危険すぎるため C11 で言語規格から削除された |
| `strcpy` | コピー先の大きさを検査しない | `strncpy`、`strlcpy`、`snprintf` | `strncpy` は、コピー元が長いと終端の `'\0'` を付けない。`strlcpy` は BSD 由来で、glibc では 2.38 以降で使える |
| `strcat` | 連結後の長さを検査しない | `strncat`、`strlcat` | `strncat` の第3引数は「コピー先の全体の大きさ」ではなく「残りの空き」 |
| `sprintf` | 書式展開後の長さを検査しない | `snprintf` | 戻り値が指定サイズ以上なら切り詰めが起きている |
| `scanf("%s", buf)` | 幅指定がないと長さ無制限で読み込む | `scanf("%127s", buf)`、`fgets` | 幅はバッファの大きさ−1（終端の分）にする |
| （Windows） | 同上 | `strcpy_s`、`strcat_s` など | C11 の附属書K由来。対応状況は処理系によって異なる |

> **補足：strncpy の扱い**
> 以前は「`strcpy` の代わりに `strncpy` を使えば安全」と説明されることが多かったが、現在は、`strncpy` が終端文字を保証しないために別のバグ（文字列の終わりが見つからず、隣のメモリまで読んでしまう）を生む点が知られている。`strncpy` を使う場合は、開発者が最後の1バイトに `'\0'` を明示的に書き込むべきである。

2.1 の題材プログラムを、開発者の立場で直すと次のようになります。

```c
/* 修正前：data の長さを確かめずにコピーしている */
void sub(char *data)
{
    char buf[128];
    strcpy(buf, data);
}

/* 修正後：長さを先に検査し、コピーにもサイズを指定する */
int sub(const char *data)
{
    char buf[128];
    if (strlen(data) >= sizeof(buf)) {    /* 入力のレングスチェック */
        return -1;                        /* 長すぎる入力はエラーとして拒否する */
    }
    snprintf(buf, sizeof(buf), "%s", data);
    return 0;
}

/* strncpy を使う場合は、終端文字を自分で書く */
strncpy(buf, data, sizeof(buf) - 1);
buf[sizeof(buf) - 1] = '\0';
```

> **補足：BOFに対するプログラミング上の対策**
>
> - `strcpy`、`strcat`、`gets`、`sprintf`など、コピー先のサイズを検査しない関数の使用を避け、`strncpy`、`strncat`、`fgets`、`snprintf`など、サイズを指定できる関数を使用する。
> - 入力データのサイズをチェックし、確保したバッファのサイズを超えないことを確認する。
> - 整数演算の前に、演算結果が型の上限値・下限値を超えないかを確認する。
> - Java、C#、Rustなど、メモリ安全性が確保された言語の採用を検討する。

最後の項目は、近年とくに重視されている方向性です。Java、C#、Rust などの言語は、配列の範囲外への書込みを言語やランタイムの側で防ぐため、BOFという種類のバグそのものを大幅に減らせます。開発者と発注者は、新規開発ではメモリ安全な言語を第一候補に検討し、C/C++を使う場合は、上記の関数の置き換え、コンパイラの保護オプション（3.6）、ファジングや静的解析によるテストを組み合わせるべきです。

### 7.4 対策の全体像

| 立場 | 予防・防止 | 検知・追跡 | 回復 |
| --- | --- | --- | --- |
| 開発者 | 危険な関数の不使用、レングスチェック、整数演算の検査、メモリ安全な言語、保護オプション（カナリア・PIE・NX）付きでビルド | カナリア（StackGuard・SSP）による書換えの検知と強制停止 | 脆弱性の修正版（パッチ）の提供 |
| システム管理者 | パッチ適用、脆弱性検査、ファイアウォールで不要ポート遮断、DEP・ASLR の有効化、setuid/setgid の整理、サービスの最小権限化 | IDS/IPS、ログの保全と追跡調査、クラッシュログの監視 | 原因の特定と対策手順の実施、関係ホストの検証と修復、クリーンインストールによる再構築 |

## 8. 確認問題

### 8.1 理解度チェック

- 【Q1】スタック領域のデータ構造上の特徴を挙げよ。
- 【Q2】メモリのスタック領域とヒープ領域の違いについて述べよ。
- 【Q3】C/C++言語のどのような特徴がBOF攻撃を成立させているのか。
- 【Q4】BOF攻撃によって、なぜ管理者の権限が奪われてしまうのか。
- 【Q5】Use-After-Freeを悪用したBOF攻撃の特徴を挙げよ。
- 【Q6】setuid/setgid属性とは何か。また、なぜ必要なのか。
- 【Q7】setuid/setgid属性をもつプログラムの危険性とは何か。
- 【Q8】市販ソフトウェアに対するBOF攻撃への有効な対策としては何があるか。
- 【Q9】ソフトウェア開発者としてとるべきBOF対策としては何があるか。
- 【Q10】setuid/setgid属性を悪用したBOF攻撃への対策としては何が有効か。

> **解答例**
>
> - **Q1**：最後に格納したデータを最初に取り出す後入れ先出し（LIFO）の構造であり、PUSHで書き込み、POPで取り出す。メモリ上では高位アドレスから低位アドレスに向かって使われ、リターンアドレスやローカル変数などの一時的なデータが格納される（1.2）。
> - **Q2**：スタック領域はサブルーチン呼出し時などに自動的に確保・解放され、リターンアドレスやローカル変数を格納する。ヒープ領域は`malloc`関数や`new`演算子でプログラムが動的に確保し、`free`関数や`delete`演算子で明示的に解放しなければならない（1.1）。
> - **Q3**：`strcpy`などの標準関数が、コピー先の大きさを検査せずにデータを書き込むこと。また、言語として配列の範囲外への書込みを検査しないため、あふれたデータが、同じスタック上で隣接する変数やリターンアドレスを上書きしてしまう（2.3）。
> - **Q4**：攻撃者は、あふれたデータでリターンアドレスを書き換え、自分が送り込んだコードに処理を移させる。そのコードは乗っ取られたプログラムの権限で実行されるため、管理者権限で動くサーバプログラムや、所有者が root の setuid プログラムが狙われると、攻撃者は管理者権限を得る（2.3、5.3、6.1）。
> - **Q5**：解放済みのヒープ領域に攻撃者が用意したデータを配置させ、プログラムがダングリングポインタを使ったときに不正なコードを実行させる。ASLRが有効でも成立する可能性があり、スクリプトを用いて攻撃できるため、Webブラウザや文書閲覧ソフトが狙われやすい。抜本的な対策は脆弱性の修正である（4.1）。
> - **Q6**：setuidは、プログラムを実行したプロセスのEUIDを、そのファイルの所有者のものにする属性であり、setgidはプロセスのGIDをファイル所有者のGIDにする属性である。一般ユーザが、passwdコマンドでのパスワード変更のように、管理者権限を必要とする処理を実行できるようにするために必要である（5.1、5.2）。
> - **Q7**：所有者が root の setuid/setgid プログラムは、一般ユーザが実行しても root 権限で動作する。そのため、BOFの脆弱性があると、ログイン済みの一般ユーザ（侵入者）が送り込んだ不正なコードが root 権限で実行され、権限昇格を許す（5.3）。
> - **Q8**：OS・ソフトウェアのバージョンの最新化とパッチ適用、脆弱性検査、ファイアウォールによる不要ポートの遮断、DEP の有効化、ASLR の利用（予防・防止）。IDS/IPS による検知とログによる追跡（検知・追跡）。原因の特定と修復・再構築（回復）（7.1）。
> - **Q9**：gets、strcpy、strcat、sprintfなどの危険な関数を使わず、fgets、strncpy、strncat、snprintfなどを使う。入力データのレングスチェックを確実に行う。StackGuard・SSPなどのカナリアによる検知機能を使う。Libsafeなどの BOF防止機能を追加したライブラリを使う。整数演算の結果の範囲を確認し、メモリ安全な言語の採用を検討する（7.3）。
> - **Q10**：findコマンドで所有者が root の setuid/setgid プログラムを探し、不要なものは削除し、削除できないもののうち属性が不要なものは chmod で setuid/setgid 属性を解除する。残るプログラムにはパッチを確実に適用する（7.1）。

### 8.2 確認問題（過去問題）

**問題1**

配列を用いてスタックを実現する場合の構成要素として、最低限必要なものはどれか。

- ア スタックに最後に入った要素を示す添字の変数
- イ スタックに最初に入った要素と最後に入った要素を示す添字の変数
- ウ スタックに一つ前に入った要素を示す添字の変数を格納する配列
- エ スタックの途中に入っている要素を示す添字の変数

[情報処理技術者試験 高度共通・H24秋]

> **解答・解説**
>
> スタックはデータ記憶構造の一種であり、最後に入った要素が最初に読み出される「後入れ先出し(Last In First Out:LIFO)」の構造となっている。そのため、最後に入った要素を示す添字の変数(**スタックポインタ**)が最低限必要となる。
>
> スタックは、プログラム内でサブルーチンを呼び出す際の戻り位置(リターンアドレス)のほか、サブルーチン内で定義された変数(内部変数、ローカル変数)など、一時的に使用するデータを格納する用途に使われる。スタックを用いると、サブルーチンからほかのサブルーチンを呼び出すことや、自分自身を呼び出すこと(再帰的呼出し:recursive call)も可能となる。
>
> したがって、**アが正解**である。

**問題2**

ルートキットの特徴はどれか。

- ア OSなどに不正に組み込んだツールの存在を隠す。
- イ OSの中核であるカーネル部分の脆弱性を分析する。
- ウ コンピュータがマルウェアに感染していないことをチェックする。
- エ コンピュータやルータのアクセス可能な通信ポートを外部から調査する。

[情報処理安全確保支援士試験・R3]

> **解答・解説**
>
> ルートキットとは、侵入に成功した攻撃者が、その後の不正な活動を行いやすくし、自身の存在を隠蔽するために使用するソフトウェアなどをまとめたパッケージの呼称(俗称)である。当初は、UNIX系のシステムに侵入してroot権限を手に入れた侵入者が、システム管理者に見つかることなくroot権限を保持して活動を続けるためのツールのことであった。現在では、Windowsなど"root"というアカウントが存在しない環境で同様の働きをするツールもルートキットと呼ばれている。
>
> なお、イは脆弱性診断ツール、ウはマルウェア対策ソフト(ウイルス対策ソフト)、エはポートスキャナ（2.2 参照）の説明である。
>
> したがって、**アが正解**である。

## 9. 試験対策まとめ（重要ポイント）

### 9.1 知識の確認（科目A-2向け）

- **スタック と ヒープ**：スタックは自動で確保・解放され、リターンアドレスとローカル変数を置く。ヒープは`malloc`/`new`で確保し`free`/`delete`で明示的に解放する。解放忘れ・解放後の使用（Use-After-Free）はヒープ側の問題。
- **スタックの向き**：スタックは高位→低位に使われ、変数への書込みは低位→高位に進む。だから`buf`からあふれたデータは、高位側にある変数や戻り先を上書きする。
- **LIFO と スタックポインタ**：配列でスタックを実現するのに最低限必要なのは「最後に入った要素を示す添字」。
- **BOFの結果は2通り**：戻り先が壊れるだけなら異常終了（DoSと同じ影響）、偽りの戻り先に誘導されれば任意コード実行（シェルコード）。攻撃者の権限＝乗っ取られたプログラムの権限。
- **DEP/NX と その限界**：データ領域でのコード実行を禁止する。return-to-libc攻撃・ROP（既存の正規コードの流用）と異常終了は防げない。
- **ASLR と PIE**：ASLRはスタック・ヒープ・ライブラリなどの配置をランダム化し、PIEはテキスト領域まで対象にする。「アドレスを特定させない」対策。
- **カナリア**：ローカル変数とリターンアドレスの間に置き、書換えを検知したら強制終了。StackGuard（特定CPU、アセンブラレベル）とSSP（中間言語レベル、様々なCPU）、GCCの`-fstack-protector`、Visual C++の`/GS`。Libsafeは再コンパイル不要のライブラリ型。
- **整数オーバフロー**：サイズ計算の桁あふれで小さなバッファが確保され、後続のコピーでBOFになる。
- **setuid/setgid**：実行時のEUID（setgidはGID）をファイル所有者のものにする。`ls -l`で`s`、8進数で`4000`/`2000`。passwdコマンドが代表例。
- **rootkit**：侵入後の活動の隠蔽ツール群。ps・netstatの置換、ログ改ざん、システムコールを横取りするカーネルモードrootkit。ポートスキャナ・脆弱性診断ツール・マルウェア対策ソフトとの取り違えが選択肢の定番。
- **危険な関数と代替関数**：gets→fgets、strcpy→strncpy/strlcpy/snprintf、strcat→strncat/strlcat、sprintf→snprintf。strncpy は終端文字を保証しない点に注意。

### 9.2 記述式で問われる観点（科目B向け）

- **脆弱性の指摘**：ソースコードの抜粋が示されたら、「入力データの長さを検査せずに、固定長の領域へ`strcpy`でコピーしている」のように、どの行が・何を検査していないかを具体的に書く。
- **影響の説明**：「攻撃者は長い入力でリターンアドレスを書き換え、サーバプログラムの権限で任意のコードを実行できる。プログラムが root 権限で動いていればホスト全体が乗っ取られる。書換えにとどまった場合でもサービスが異常終了する」の形で、因果と損なわれる特性をセットで書く。
- **開発者の対策**：「開発者は、書込みサイズを指定できる`snprintf`に置き換え、入力のレングスチェックを行う（コピー先を超えた書込みを防ぐため）」のように、誰が・何を・何のためにを一文でそろえる。コンパイラの保護オプション（カナリア・PIE・NX）は「バグが残っても乗っ取りを停止に変える」補助策として位置づける。
- **管理者の対策と限界**：DEP/ASLRを有効にしても「異常終了は防げない」「既存コードの流用は DEP だけでは防げない」ため、根本対策はパッチ適用であると書ける。パッチがない間はワークアラウンド（接続元の制限、サービス停止、IPS）で守る、という時間軸の説明も問われる。
- **権限の最小化**：サービスを専用の一般ユーザで動かす、不要な setuid/setgid 属性を解除する、はどちらも「乗っ取られたときに攻撃者が得る権限を小さくするため」と理由を添える。
- **インシデント時の判断**：クラッシュログ（`stack smashing detected`、例外コード`0xc0000409`など）から攻撃を疑う根拠を示す。root 権限を奪われた可能性があるホストは、rootkit によってコマンドやログが偽装されている可能性があるため、そのホスト上の調査結果を信用せず、クリーンインストールによる再構築を選ぶ理由を説明できるようにする。
