## 0. 全体像 ― なぜこの分野を学ぶのか

5.2〜5.4 では、1台1台のサーバ（ホスト）を堅くする方法を学びました。しかし組織には何百台ものPCやサーバがあり、そのすべてを完璧に守り続けるのは現実的ではありません。そこで、ネットワークの「出入口」に関所を置き、通ってよい通信だけを通し、それ以外を止めてしまおう、という発想が生まれます。この関所が**ファイアウォール**です。

ファイアウォールを理解する土台は、1.4 で学んだTCP/IPの知識です。ファイアウォールが判断に使うのは、IPヘッダの送信元・宛先アドレスとプロトコル番号、TCP/UDPヘッダのポート番号とフラグです。1.4 で「どの装置がどの層のヘッダまで見るか」でできることが決まると学びましたが、ファイアウォールはまさにその典型で、見ている層の外側（HTTPの中身など）で起きる攻撃は止められません。また、ステートフルインスペクションという仕組みは、1.4 の3ウェイハンドシェイクの状態を追跡することで成り立っています。

本ノートは次の流れで進みます。

1. **ファイアウォールとは何か**：ACLの定義と、ルール表の読み方（上から順に評価、暗黙の拒否）、ログの見た目、役割の変化
2. **基本的な構成**：DMZの考え方と4つの構成パターン
3. **フィルタリング方式**：パケットフィルタリング型、ダイナミックパケットフィルタリング型、ステートフルパケットインスペクション型、ポジティブ／ネガティブセキュリティモデル
4. **アドレス変換機能**：NATとNAPTの変換表
5. **ルール表の読解と修正**：科目Bで問われる「どのルールを・何のために・どう直すか」
6. **ファイアウォールで防御できない攻撃**：限界と、それを補う対策
7. **拡張機能**：高可用性構成とUTM

1.2 で学んだ対策の4機能でいえば、ファイアウォールは主に「予防・防止」を担い、ログによって「検知・追跡」も支えます。多層防御の表では「境界」の層にあたり、その内側を 5.6 のIDS、5.7 のIPS、5.8 のWAFが補います。

科目Bの業務観点では「②情報システムの企画・設計・開発・運用におけるセキュリティ確保」（ネットワークのアーキテクチャ設計）と「③利用におけるセキュリティ対策の適用」（ネットワーク及び機器のセキュリティ管理、セキュリティ監視とログ分析）の中心です。科目A-2ではステートフルパケットインスペクションの特徴、DMZの目的、NAPTの動作が定番で、科目Bでは事例に載ったファイアウォールのルール表を読み、不足しているルールや許可しすぎのルールを指摘・修正させる設問がほぼ毎回のように出題されます。

## 1. ファイアウォールとは何か

### 1.1 定義とACL

ファイアウォールとは、複数のネットワークセグメント間において、あらかじめ設定されたルール（ACL）に基づいてパケットを中継したり、破棄したりする機能、あるいはその機能をもつ制御製品です。

> **ACL（Access Control List：アクセス制御リスト）**
> 通信を許可するか拒否するかを判断するための条件（送信元／宛先IPアドレス、ポート番号、プロトコルなど）を列挙したリスト。上から順に評価され、最初に一致したルールのアクションが適用されるのが一般的である。

ACLの定義の最後の一文、「上から順に評価され、最初に一致したルールのアクションが適用される」は、科目Bでルール表を読むときの大前提です。次の節で具体的に確認します。

### 1.2 ルール表（ACL）の読み方 ― 上から順に、最初の一致で決まる

架空の会社のファイアウォールに、次のルール表が設定されているとします。DMZ（2章で説明する公開サーバ用のセグメント）のWebサーバは 203.0.113.10、メールサーバは 203.0.113.25、内部ネットワークは 172.16.0.0/16 です。

| No. | 送信元 | 宛先 | プロトコル／宛先ポート | 動作 | 目的 |
|---|---|---|---|---|---|
| 1 | any | 203.0.113.10 | TCP/443 | 許可 | インターネットからWebサーバへのHTTPS |
| 2 | any | 203.0.113.25 | TCP/25 | 許可 | インターネットからメールサーバへのSMTP |
| 3 | 172.16.0.0/16 | any | TCP/443 | 許可 | 内部からインターネットへのHTTPS |
| 4 | 198.51.100.0/24 | any | any | 拒否 | 攻撃元として報告されたネットワークを遮断 |
| （暗黙） | any | any | any | 拒否 | 上記のどれにも一致しない通信 |

ファイアウォールは、届いたパケットごとに、この表を**No.1から順に**見ていき、条件がすべて一致した最初のルールの動作を実行して、そこで評価を**打ち切ります**。どのルールにも一致しなかったパケットは、表の最後にある見えないルール、つまり**暗黙の拒否**（implicit deny）で破棄されます。1.4 で学んだポート番号の表を思い出しながら、3つのパケットを評価してみましょう。

| 届いたパケット | 評価の過程 | 結果 |
|---|---|---|
| 送信元 192.0.2.7 → 宛先 203.0.113.10、TCP/443（SYN） | No.1 に一致 | 許可（Webサーバに届く） |
| 送信元 192.0.2.7 → 宛先 203.0.113.10、TCP/22（SSH） | No.1〜4 のどれにも一致しない | 暗黙の拒否で破棄 |
| 送信元 198.51.100.9 → 宛先 203.0.113.10、TCP/443 | **No.1 に先に一致**する | 許可（No.4 は評価されない） |

3つ目が落とし穴です。管理者は「198.51.100.0/24 からの通信を遮断したい」という目的でNo.4を追加しましたが、No.1 がすでに「送信元 any」でHTTPSを許可しているため、攻撃元からのHTTPSは No.4 に届く前に許可されてしまいます。このように、上のルールに条件を覆われて永遠に評価されないルールを「隠れたルール」（シャドーイング）と呼びます。管理者が攻撃元を遮断するという目的を果たすには、**No.4 を No.1 より上に移動**すべきです。

ルール表を読むときの原則をまとめます。

- **評価は上から順**：具体的な（狭い）条件のルールほど上に、一般的な（広い）条件のルールほど下に置く。拒否したい例外は、それを含む広い許可ルールより上に置く。
- **最初の一致で終わる**：後ろのルールが効くのは、前のすべてのルールに一致しなかったパケットだけ。
- **最後は暗黙の拒否**：許可ルールに書かれていない通信はすべて破棄される。「通信できない」というトラブルの多くは、必要な許可ルールの書き忘れが原因。
- **方向を意識する**：「送信元」と「宛先」を取り違えると、意図と逆の方向を許可してしまう。

多くの製品では、暗黙の拒否に一致したパケットはログに残りません。そこで運用管理者は、拒否の記録を残して攻撃の兆候を分析するために、表の最後に「any → any 拒否（ログ記録あり）」を**明示的に**書いておくことがよくあります。

### 1.3 ファイアウォールのログ

ファイアウォールは、ルールに一致したパケットの情報をログに記録します。Linux の iptables で拒否したパケットを記録すると、次のような1行になります。

```
Sep 30 10:15:22 fw01 kernel: DROP IN=eth0 OUT=eth1 SRC=198.51.100.23 DST=203.0.113.10 LEN=44 TTL=241 PROTO=TCP SPT=51234 DPT=23 WINDOW=1024 SYN
```

| 項目 | 値 | 読み方 |
|---|---|---|
| DROP | ― | 破棄した（拒否ルールに一致した） |
| IN / OUT | eth0 / eth1 | インターネット側のインタフェースから入り、DMZ側へ出ようとした |
| SRC / DST | 198.51.100.23 / 203.0.113.10 | 送信元と宛先のIPアドレス（1.4 のIPヘッダ） |
| PROTO / SPT / DPT | TCP / 51234 / 23 | TCPの送信元ポート 51234 から、宛先ポート 23（TELNET）へ |
| SYN | ― | TCPの接続開始要求（3ウェイハンドシェイクの①） |

商用のファイアウォール製品では、同じ情報が次のような形式で記録されることが多いです。

```
2026/09/30 10:15:22,fw01,deny,rule=99(cleanup),src=198.51.100.23:51234,dst=203.0.113.10:23,proto=tcp,flags=S,zone=untrust->dmz
2026/09/30 10:15:23,fw01,deny,rule=99(cleanup),src=198.51.100.23:51235,dst=203.0.113.10:25,proto=tcp,flags=S,zone=untrust->dmz
2026/09/30 10:15:23,fw01,deny,rule=99(cleanup),src=198.51.100.23:51236,dst=203.0.113.10:80,proto=tcp,flags=S,zone=untrust->dmz
```

同じ送信元から、同じ宛先の23、25、80…と宛先ポートを変えたSYNが1秒間に続いています。これは第2章 2.2 で学んだ**ポートスキャン**の典型的な痕跡です。ファイアウォールが遮断していても、運用管理者はこうしたログを監視し、「誰に狙われているか」を把握しておくべきです（1.2 のノートで学んだ「脅威を知る」）。

### 1.4 ファイアウォールがもたらすもの ― 機密性と可用性

ファイアウォールを用いることで、組織はネットワーク環境において一定レベルの機密性を確保できます。また、不要なパケットを遮断することによってネットワークの利用効率を高めることも可能になります（可用性の向上）。なお、このように正当なものを選別し、不要なものを取り除くことを**フィルタリング**（filtering）と呼びます。

### 1.5 狭義と広義のファイアウォール

上記のように、ACLに基づいてアクセス制御を行う製品を通常「ファイアウォール」と呼びます。しかし近年、侵入防御システム（IPS）やWebアプリケーションファイアウォール（WAF）、パーソナルファイアウォールと呼ばれる製品などが登場したこともあり、ファイアウォールの概念や範囲は拡大し、その境界線は曖昧になってきています。

つまり、狭義では主にネットワーク層においてACLに基づいてアクセス制御を行う製品を「ファイアウォール」と呼びます。一方、広義ではネットワークやホストに対する侵入や攻撃を防ぐ機能をもつもの全般を「ファイアウォール」といいます。したがって、広義ではマルウェアの侵入を防ぐ製品などもファイアウォールの一種ということになります。

なお、従来のファイアウォールを**ネットワークファイアウォール**と呼びます。これに対し、WAFのように特定のアプリケーションに対してファイアウォールとして機能するものを**アプリケーションファイアウォール**と呼んで区別することもあります。

> **パーソナルファイアウォール**
> 個人が使用するPCなどのホスト上で動作し、そのホストに対する外部からの接続要求の遮断や、アプリケーションによる外部への通信の許可／拒否、不審な通信の通知などを行うソフトウェア。

> **マルウェア（malware）**
> コンピュータウイルス、ワーム、トロイの木馬、スパイウェア、ボット、ランサムウェアなど、不正かつ有害な動作を行う意図で作られた悪意のあるソフトウェアの総称（第2章 2.9）。

### 1.6 攻撃を検知・防御する技術の種類

従来のネットワークファイアウォールをはじめ、ネットワーク環境やホスト環境において侵入や攻撃、不正操作などを検知あるいは防御することを目的とした技術を次の表に示します。第5章の残りのノートで1つずつ詳しく学ぶので、ここでは「それぞれが何を見て、何を止めるか」の地図として眺めてください。

**表：侵入や攻撃を検知もしくは防御する技術の種類と特徴**

| 製品の種類 | 特徴 |
|---|---|
| ファイアウォール | ・主にTCP/IPの中〜下位層で設定されたルール（IPアドレス、ポート番号など）に基づいてパケットを中継又は遮断する<br>・許可されたプロトコル（サービス）のセキュリティホールを突いた攻撃は防御できない |
| ネットワーク型IDS（NIDS） | ・接続されたネットワークセグメント中を流れるパケットを監視し、ポートスキャン、バッファオーバフロー（BOF）攻撃、サービス不能（DoS）攻撃、不正コマンドの実行など、OSやミドルウェアのセキュリティホールを突いた様々な攻撃を検知する<br>・暗号化されたパケットは監視できない |
| ホスト型IDS（HIDS） | ・特定のホストに常駐して、ログインの成功／失敗、重要資源に対するアクセス、ファイルの改ざんなど、そのホスト上で発生している様々な事象を検知する |
| 侵入防御システム（IPS） | ・従来のNIDSの機能を強化するとともに、インライン接続構成をとることで、検知した攻撃をその場で遮断できる、より強力な侵入検知・防御機能を備えた製品である |
| ホスト型IPS | ・HIDSと同様に特定のホストに常駐し、BOF攻撃、マルウェアの侵入や不正な操作などを検知して防御する機能をもったシステム<br>・デスクトップ型IPSと呼ばれることもある |
| Webアプリケーションファイアウォール（WAF） | ・クロスサイトスクリプティング、SQLインジェクションなど、Webアプリケーションの脆弱性に対する攻撃を検知し、遮断できる<br>・SSLアクセラレータ機能や負荷分散機能を備えている機種もある（SSLで暗号化されたパケットを復号して攻撃を検知／遮断できる） |
| サンドボックス | ・実環境から隔離されたセキュアな仮想環境で不審なファイルやURLへのアクセスを実行し、その結果（振る舞い）を観察することでマルウェア等を検知する<br>・MTAとして動作することで不審なメールを遮断したり、RSTパケットを送信することで不審なWeb通信の遮断を試みたりする |

> **インライン接続**
> 監視対象の通信経路上に機器を直列に挿入する接続形態。すべてのパケットが機器を通過するため、不正なパケットをその場で破棄できる。これに対し、スイッチのミラーポートなどからパケットを複製して受け取る形態を**プロミスキャスモード（パッシブ）接続**と呼び、主にIDSで用いられる。

表の「SSL」は現在の TLS のことです（SSL はすでに脆弱性のため使用が禁止されていますが、製品名や機能名には「SSLアクセラレータ」「SSLインスペクション」のように旧称が残っています）。

1.4 のカプセル化の図と重ねると、各製品の守備範囲がはっきりします。

```
 [Ethernetヘッダ][IPヘッダ][TCPヘッダ][ HTTPリクエスト（GET /item?id=1' OR '1'='1 ...） ]
                 └─────┬────────┘ └────────────────────┬──────────────────┘
          ファイアウォールが見る範囲         IPS・WAF が見る範囲（FWは中身を見ない）
          （アドレス・ポート・フラグ）
```

ファイアウォールにとって、HTTPS（TCP/443）で届いたSQLインジェクションは「許可されたWebサーバ宛てのTCP/443のパケット」にすぎません。これが表の1行目にある「許可されたプロトコルのセキュリティホールを突いた攻撃は防御できない」の意味で、6章で改めて整理します。

### 1.7 ファイアウォールの役割 ― 「盾」から「フィルタ」へ

ファイアウォールは、もともとインターネットからの不正アクセスや攻撃など、主に**インバウンド**方向のパケットから組織内のネットワークを守る「盾」として機能することを主な役割としていました。

とはいえ、一般的なファイアウォールは全く穴のない完全な盾ではありません。組織はWebやメールなど業務上必要なサービスを許可せざるを得ず、ファイアウォールは許可されたサービスを悪用した攻撃を防御できません。さらに近年は、組織内のPCがマルウェアに感染して踏み台となり、内部から外部に対して攻撃が行われたり、マルウェアがばら撒かれたりするケースが増加しました。

そのため、ファイアウォールにはインバウンド方向のパケットだけでなく、**アウトバウンド**方向のパケットについてもフィルタリングすることが重要な役割となってきました。つまり、盾というよりは、接続されているネットワークセグメント間での「フィルタ」としての役割です。

> **アウトバウンド／インバウンド**
> 組織内部から外部（インターネット）へ向かう通信をアウトバウンド、外部から内部へ向かう通信をインバウンドと呼ぶ。**出口対策**（アウトバウンド通信の制御）は、マルウェア感染後の情報漏えいやC&Cサーバとの通信を防ぐうえで重要である。

出口対策の効果は、ログで見るとよくわかります。内部のPCからは必ずプロキシサーバ経由でWebにアクセスさせる設計の組織で、ファイアウォールに次のログが残っていたとします。

```
2026/09/30 02:13:45,fw01,deny,rule=99(cleanup),src=172.16.20.35:49811,dst=198.51.100.200:443,proto=tcp,flags=S,zone=trust->untrust
2026/09/30 02:18:45,fw01,deny,rule=99(cleanup),src=172.16.20.35:49840,dst=198.51.100.200:443,proto=tcp,flags=S,zone=trust->untrust
```

深夜に、社内のPC（172.16.20.35）が、プロキシを経由せずに外部の同じアドレスへ5分おきに直接接続しようとして、拒否されています。人が操作していない時間帯の規則的な通信は、マルウェアがC&Cサーバに接続を試みている典型的な兆候です。ファイアウォールが出口で止めたので情報は漏れていませんが、このPCは感染している疑いが強く、インシデント対応（第4章 4.8）を始めるべきです。

また、ファイアウォールはフィルタとして機密性を確保するだけでなく、可用性の面でも重要な役割を担います。組織は、インターネットから自社のサイトへの快適なアクセスや、組織内からの快適なインターネット利用環境を常時提供しなければなりません。そのため、十分な処理能力をもつ機器を用いるとともに、冗長化や負荷分散なども必要になります。すべての通信がファイアウォールを通るということは、ファイアウォールが止まれば全体が止まる（単一障害点になる）ということでもあるからです。

さらに、ネットワークインフラの目覚しい発展により、インターネットに接続する組織内の基幹ネットワークでは、原本執筆時点で「1Gbps〜10Gbpsもの高速イーサネットを使用することも珍しくなくなってきた」とされていました。現在では10Gbpsは一般的になり、データセンタなどでは40Gbps・100Gbpsも使われています。そのため、ファイアウォールにもそれに応じたハイパフォーマンス（高性能）かつハイアベイラビリティ（HA：高可用性）が要求されています（7章）。

## 2. ファイアウォールの基本的な構成 ― 公開サーバをどこに置くか

インターネットの接続口では、公開サーバ（Webサーバやメールサーバなど、インターネットからアクセスさせるサーバ）の設置場所によって、次のようなファイアウォールの構成が考えられます。構成を選ぶときの問いは一つ、「**公開サーバが乗っ取られたとき、被害が内部ネットワークに及ぶか**」です。

### 2.1 構成① 公開サーバを内部ネットワークに接続

公開サーバを内部ネットワークに接続した構成です。ファイアウォールは二つのネットワークインタフェースをもち、インターネット側と内部セグメント間のパケットをフィルタリングします（下図参照）。

**図：公開サーバを内部ネットワークに接続した例**

```
インターネット
     │
  [ルータ]
     │
[ファイアウォール]
     │
─────┴──────────────── 内部ネットワーク
  │        │        │
[公開サーバ] [PC]   [社内サーバ]
```

**特徴**

- ファイアウォールによって公開サーバへのアクセスを最小限のサービスのみに制限する。
- インターネットから内部ネットワーク上の公開サーバ以外のホストへのアクセスについてはすべて遮断する。
- 構成が単純であり、導入・運用コストを低く抑えられる。
- 公開サーバが内部ネットワーク上に存在するため、万一攻撃者に公開サーバへの侵入を許してしまうと、攻撃者はそこを踏み台として内部ネットワーク上の他のホストにまで被害を及ぼす可能性がある。
- 内部からインターネットへの各種プロトコルが許可されているため、内部に侵入したマルウェアによって、C&Cサーバなどへの不正な通信が行われる可能性がある。

> **C&Cサーバ（Command and Control server）**
> マルウェアに感染したコンピュータ（ボット）に対して指令を送ったり、窃取した情報を受け取ったりするために攻撃者が用意するサーバ。

構成①の問題は、公開サーバとPCが同じセグメントにいて、その間の通信をファイアウォールが一切見ていないことです。公開サーバはインターネットから直接アクセスされる以上、最も攻撃を受けやすいホストです。そのホストが乗っ取られると、攻撃者は社内サーバまで「隣の部屋」の感覚で到達できてしまいます。

### 2.2 構成② 2台のファイアウォールに挟まれたDMZに公開サーバを接続

2台のファイアウォールを縦列に接続し、その間のセグメント（DMZ）に公開サーバを接続します。バリアセグメントと内部セグメントの間のセグメントは、両セグメントにとって緩衝的な存在となるため、一般的に **DMZ**（De-Militarized Zone：非武装地帯）と呼ばれます（下図参照）。

**図：2台のファイアウォールに挟まれたDMZに公開サーバを接続した例**

```
インターネット
     │
  [ルータ]
     │  ← バリアセグメント
[ファイアウォール1]
     │
─────┴────────── DMZ
  │        │
[Webサーバ] [メールサーバ]（公開サーバ）
     │
[ファイアウォール2]
     │
─────┴────────── 内部ネットワーク
  │        │
 [PC]   [社内サーバ]
```

> **バリアセグメント**
> インターネットとの接続ルータと、最も外側のファイアウォールとの間のネットワークセグメント。インターネットに直接面しており、最も危険度が高いセグメントである。

**特徴**

- ファイアウォール1によって公開サーバへのアクセスを最小限のサービスのみに制限する。
- ファイアウォール1、2によってインターネットから内部ネットワークへのアクセスについてはすべて遮断する。
- DMZから内部ネットワークへのアクセスについては最小限のサービスのみに制限する。したがって、万一攻撃者に公開サーバへの侵入を許してしまったとしても、そこから内部ネットワークにまで被害が及ぶ可能性を最小限にとどめることが可能である。
- ファイアウォール1、2を別のベンダーの製品や、フィルタリング方式の異なる製品にすることで、ファイアウォールのバグなどによって攻撃者に内部ネットワークへ侵入される可能性を最小限にとどめることが可能である（1.2 のノートで学んだ多層防御）。
- 機器が2台必要となるため、導入・運用コストが高くなる。
- 内部からインターネットへのHTTP、HTTPSが許可されているため、内部に侵入したマルウェアによって、C&Cサーバなどへの不正な通信が行われる可能性がある。

### 2.3 構成③ ファイアウォールに設けた第三のセグメントに公開サーバを接続

1台のファイアウォールに新たなネットワークセグメント（DMZ）を設け、そこに公開サーバを接続します。新設したネットワークセグメントは構成②と同様にDMZとなります。

**図：第三のセグメント（DMZ）に公開サーバを接続した例**

```
インターネット
     │
  [ルータ]
     │
[ファイアウォール]───────── DMZ
     │                 │        │
     │           [Webサーバ] [メールサーバ]
─────┴────────── 内部ネットワーク
  │        │
 [PC]   [社内サーバ]
```

**特徴**

- ファイアウォールによって公開サーバへのアクセスを最小限のサービスのみに制限する。
- インターネットから内部ネットワークへのアクセスについてはすべて遮断する。
- DMZから内部ネットワークへのアクセスについても最小限のサービスのみに制限する。したがって、万一攻撃者に公開サーバへの侵入を許してしまったとしても、そこから内部ネットワークにまで被害が及ぶ可能性を最小限にとどめることが可能である。
- ファイアウォールが1台で済むため、構成②に比べてコストを抑えられる。一方、ファイアウォール自体が単一障害点となるため、必要に応じて冗長化を検討する。
- 内部からインターネットへのHTTP、HTTPSが許可されているため、内部に侵入したマルウェアによって、C&Cサーバなどへの不正な通信が行われる可能性がある。

科目Bの事例で最もよく登場するのがこの構成③です。ファイアウォールのルール表は「インターネット→DMZ」「DMZ→内部」「内部→インターネット」のように、セグメントの組合せごとに読むと整理しやすくなります（5章）。

### 2.4 構成④ 複数のDMZを構成

構成③を発展させ、ファイアウォールに複数のネットワークセグメントを設けて、各ホストの用途やセキュリティレベルに応じて複数のDMZを設けた構成です。

**図：セキュリティレベルに応じて複数のDMZを構成した例**

```
インターネット
     │
  [ルータ]
     │
[ファイアウォール]──────── DMZ1（公開サーバ）
     │  │               [Webサーバ] [外部DNSサーバ]
     │  └─────────── DMZ2（中継サーバ）
     │                  [プロキシサーバ] [メール中継サーバ]
─────┴────────── 内部ネットワーク
  │        │
 [PC]   [社内サーバ]
```

**特徴**

- 各ホストの用途やセキュリティレベルに応じた最適なアクセス制御が可能となる。また、特別な用途に用いられるホストなどを別セグメントに切り離すことで、ネットワーク全体のパフォーマンス向上や負荷分散が可能となる。
- 内部からインターネットへの通信をすべて遮断し、必ずDMZ1、DMZ2上のプロキシサーバなどを経由させることで、内部に侵入したマルウェアがC&Cサーバなどと通信するリスクを低減することが可能となる。

構成④の2つ目の特徴が、1.7 で見た出口対策の実装です。内部のPCからインターネットへの直接の通信をファイアウォールで禁止し、プロキシサーバでの利用者認証やURLフィルタリングを必ず通らせれば、プロキシの認証情報を知らないマルウェアは外部と通信しにくくなり、通信の記録もプロキシのログに残ります。

> **タグVLAN**
> パケット（イーサネットフレーム）内にVLANを識別するためのタグ（IEEE 802.1Q）を付加することで、1本の物理リンク上で複数のVLANの通信を扱えるようにする技術（1.4 の8.4）。

ファイアウォールの物理的なネットワークインタフェースの数が不足する場合でも、タグVLANに対応した製品であれば、一つの物理インタフェースをVLANによって複数の仮想的なネットワークインタフェースに分割することで、複数のセグメントを構成することが可能です。

### 2.5 4つの構成の比較

| 構成 | 公開サーバの位置 | 公開サーバ侵害時の内部への影響 | コスト | 出口対策 |
|---|---|---|---|---|
| ① 内部ネットワークに接続 | 内部ネットワーク | 大きい（踏み台にされる） | 低 | 弱い（各種プロトコルを許可） |
| ② 2台のFWに挟まれたDMZ | FW1とFW2の間 | 小さい（FW2で制限）。異なる製品なら多層防御 | 高（2台） | HTTP/HTTPSは許可 |
| ③ FWの第三のセグメント | FWの別インタフェース | 小さい（同じFWで制限） | 中（1台、SPOFに注意） | HTTP/HTTPSは許可 |
| ④ 複数のDMZ | 用途別のDMZ | 小さい。用途ごとに最適な制御 | 中〜高 | 強い（プロキシ経由を強制） |

## 3. フィルタリング方式から見たファイアウォール

ファイアウォールには、パケットをフィルタリングする際の仕組みによって、次のような種類があります。3つの方式の違いは、ひとことでいえば「**1つ1つのパケットを独立に判断するか、通信の流れ（セッション）として判断するか**」です。

### 3.1 パケットフィルタリング型

**パケットフィルタリング型**（**スタティックパケットフィルタリング型**）とは、パケットのヘッダ情報に含まれるIPアドレス、ポート番号などによって中継の可否を判断するもので、ルータがベースになっている方式です。

ファイアウォールの管理者がフィルタリングの設定において利用できる情報としては、次のようなものがあります。いずれも 1.4 で学んだIPヘッダ・TCP/UDPヘッダのフィールドです。

- 送信元IPアドレス
- 送信先IPアドレス
- プロトコル種別（TCP、UDP、ICMPなど）
- パケットの方向
- 送信元ポート番号
- 送信先ポート番号
- TCPのフラグ（ACK、SYNなど）

ただし、この方式のファイアウォールは、パケットのデータ部（ペイロード）についてはチェックしません。

この方式では、ファイアウォールはルータと同様にインターネット層（第3層）のレベルでパケットを中継する（ファイアウォール自身はコネクションを確立しない）ため、クライアントとサーバが直接コネクションを確立します。

**ACLの例**

パケットフィルタリング型ファイアウォールに設定するACL（アクセス制御リスト）の例を次の表に示します。なお、内部ネットワークのアドレスは172.16.0.0/16とします。

**表：パケットフィルタリング型ファイアウォールのACLの例**

| No. | 方向 | 始点アドレス | 終点アドレス | プロトコル | 始点ポート | 終点ポート | ACK | アクション | 説明 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | Out | 172.16.0.0/16 | ANY | TCP | >1023 | 80 | ※ | 許可 | 内部からインターネットへのWeb接続 |
| 2 | In | ANY | 172.16.0.0/16 | TCP | 80 | >1023 | ON | 許可 | No.1への応答 |
| 3 | Out | 172.16.0.0/16 | ANY | TCP | >1023 | 443 | ※ | 許可 | 内部からインターネットへのWeb（SSL）接続 |
| 4 | In | ANY | 172.16.0.0/16 | TCP | 443 | >1023 | ON | 許可 | No.3への応答 |
| 5 | Out | 172.16.0.0/16 | ANY | TCP | >1023 | 21 | ※ | 許可 | 内部からインターネットへのFTP接続（制御） |
| 6 | In | ANY | 172.16.0.0/16 | TCP | 21 | >1023 | ON | 許可 | No.5への応答 |
| 7 | In | ANY | 172.16.0.0/16 | TCP | 20 | >1023 | ※ | 許可 | インターネットからのFTPデータ接続（アクティブモード）**危険！** |
| 8 | Out | 172.16.0.0/16 | ANY | TCP | >1023 | 20 | ON | 許可 | No.7への応答 |
| 9 | Out | 172.16.0.0/16 | ANY | TCP | >1023 | >1023 | ※ | 許可 | 内部からインターネットへのFTPデータ接続（パッシブモード） |
| 10 | In | ANY | 172.16.0.0/16 | TCP | >1023 | >1023 | ON | 許可 | No.9への応答 |
| 11 | In | ANY | ANY | ANY | ANY | ANY | − | 拒否 | 上記以外の内部ネットワークへのすべてのアクセス |

※ 最初に接続を確立するパケットではOFF、それ以外のパケットではON。

表の「Web（SSL）」は、現在でいう HTTPS（TLS）のことです。

この表を 1.4 の知識で読み解いてみましょう。「始点ポート >1023」は、クライアントのOSが接続のたびに自動で選ぶ一時的なポート番号（1024番以上）を表しています。「終点ポート 80」はWebサーバのHTTPのポートです。そして「ACK」欄は、1.4 で学んだTCPのコードビットです。3ウェイハンドシェイクの最初のSYNだけがACK=OFFで、それ以降のパケットはすべてACK=ONになる、という性質を利用しています。

たとえば、内部のクライアントからインターネット上のWebサーバにアクセスする場合、ファイアウォールの管理者は、上り方向（アウトバウンド）のパケットとしてNo.1のルールを登録するだけでなく、サーバからの応答を受け取るために、下り方向（インバウンド）のパケットとしてNo.2のルールも登録する必要があります。パケットフィルタリング型は、パケットを1つずつ独立に判断するので、「行きの通信を許可すれば帰りも通る」とはならないのです。

```
内部クライアント 172.16.10.5:54321                      Webサーバ 192.0.2.80:80
   ① SYN（ACK=OFF）  ─────────────────▶  No.1（Out, >1023→80, ACK=OFF可）で許可
   ② SYN/ACK（ACK=ON）◀─────────────────  No.2（In, 80→>1023, ACK=ON）で許可
   ③ ACK（ACK=ON）   ─────────────────▶  No.1 で許可
   以降のデータ      ◀────────────────▶  No.1 / No.2 で許可
```

しかし、No.2のパケットは必ずACKフラグがONになっていることが条件となり、SYNフラグがONでACKフラグがOFFになっている場合などは拒否されます。つまり、攻撃者はサーバ側からこのルールを悪用して新たなコネクションを確立することはできません。しかし、TCP ACKスキャンをはじめ、パケットを偽装した攻撃などは受ける可能性があります。攻撃者が「送信元ポート80、ACK=ON」のパケットを作れば、それが本当に応答かどうかをNo.2は確かめようがないからです。

> **TCP ACKスキャン**
> ACKフラグをONにしたパケットをターゲットに送信し、その応答（RSTパケットの有無）によって、ファイアウォールのフィルタリングの状態を調べるポートスキャンの手法（第2章 2.2）。ステートレスなパケットフィルタリングでは、ACKフラグがONのパケットが通過してしまうことを悪用する。

アクティブモードのFTPでは、クライアントがインターネット上の任意のサーバの21/TCPポートに接続して制御チャネルを確立（No.5）した後で、サーバが、クライアントからPORTコマンドで通知された1024番以上のポートに対してデータ転送のチャネル（データチャネル）を確立する必要があります。この接続をファイアウォールが常時許可している（No.7）と、攻撃者に悪用されてしまう可能性があります。No.7 は「送信元ポートが20でさえあれば、インターネットの誰からでも内部の全ホストの1024番以上の全ポートへ接続を開始してよい」という意味になり、攻撃者は送信元ポートを20に偽装するだけで内部を探索できるからです。そのため、このような場合はパッシブモードを用いて、クライアント側からサーバに対してデータチャネルを確立する（No.9）ようにする必要があります。

> **FTPのアクティブモードとパッシブモード**
> アクティブモードでは、サーバの20/TCPポートからクライアントへデータチャネルを確立する。パッシブモードでは、クライアントがPASVコマンドを送信し、サーバから通知されたポートに対してクライアント側からデータチャネルを確立する。ファイアウォールやNAPT環境では、外部からの接続を許可せずに済むパッシブモードが一般的に用いられる。

ただし、パッシブモード用の No.9・No.10 も、「内部から外部の1024番以上の任意のポートへの接続」を許可するという、かなり広いルールです。内部のマルウェアが外部の高いポート番号で待ち受けるC&Cサーバに接続する通信も通ってしまいます。パケットフィルタリング型では、FTPを安全に通すルールをどう書いても、どこかに穴が開くのです。

**特徴**

パケットフィルタリング型ファイアウォールには、次のような特徴があります。

- フィルタリング処理がOSのレベルで行われ、ファイアウォールがコネクションを確立することもないため処理効率が高い。
- 新たなプロトコルを許可する必要が生じても、単純なプロトコルであれば該当するポートへのアクセスを許可するのみで済む。その反面、管理者の安易な設定によって不正アクセスを許してしまう可能性がある。
- シンプルなアクセス制御しかできないため、複雑な処理を要するプロトコルには対応できないか、非常に脆弱なACLになる可能性がある。

パケットフィルタリング型ファイアウォールでは、次の条件をすべて満たすプロトコルであれば適切にフィルタリング処理を行うことができます。しかし、そうでない場合には適切にフィルタリングができないか、悪用される可能性の高い脆弱なACLを登録して運用することになります。

- 接続先のポート番号が固定されている
- クライアントからサーバ方向にのみセッションが確立され、その逆方向からセッションが確立されることがない
- 送信元のIPアドレス、ポート番号が変換されても問題がない
- ペイロード内にIPアドレスやポート番号が含まれていない

FTPは、データチャネルのポート番号が固定でなく（条件1に反する）、アクティブモードではサーバから接続を開始し（条件2に反する）、PORTコマンドのペイロードにIPアドレスとポート番号を含む（条件4に反する）ため、パケットフィルタリング型にとって最も扱いにくいプロトコルの代表です。

パケットフィルタリング型は古くからあるネットワークセキュリティの解説本などに登場する方式ですが、現在はこのように単純なパケットフィルタリング型のファイアウォールが使われているケースは極めて少ないでしょう。ただし、ルータやレイヤ3スイッチのACL（1.4 の8.5）は今もこの方式で動いており、試験でも仕組みの理解を問う題材として使われ続けています。

### 3.2 ダイナミックパケットフィルタリング型

**ダイナミックパケットフィルタリング型**とは、最初にコネクションを確立する方向のみを意識した基本的なACLを事前に登録しておき、実際に接続要求（TCPであればSYNパケット）があると、ファイアウォールが個々の通信を**セッション管理テーブル**に登録するとともに必要なルールを動的に生成し、フィルタリング処理を行う方式です。

ファイアウォールは、セッション管理テーブルによって、通過したパケットの応答やそれに付随するコネクションなどを総合的に管理し、自動的に必要な処理を行います。セッションが終了すると、動的に生成したルールは破棄されます。

**図：ダイナミックパケットフィルタリング型ファイアウォールによるフィルタリング**

```
[クライアント] ──①接続要求(SYN)──▶ [ファイアウォール] ──▶ [Webサーバ]
                                   │
                         ②セッション管理テーブルに登録し、
                           応答用のACLを動的に生成
                                   │
[クライアント] ◀──応答(SYN/ACK等)── [ファイアウォール] ◀── [Webサーバ]
                                   │
                         ③セッション終了後、動的ルールを破棄
```

1. クライアントがWebサーバへアクセスを要求する。
2. ファイアウォールが動的に必要なACLを生成し、フィルタリングを行う。
3. セッションが終了すると、ファイアウォールは動的に生成したルールを破棄する。

セッション管理テーブルの中身は、たとえば次のように見えます。

```
Proto  内部側                 外部側               状態          残り時間
TCP    172.16.10.5:54321   ⇔ 192.0.2.80:443     ESTABLISHED   3587秒
TCP    172.16.10.8:50100   ⇔ 192.0.2.44:443     SYN_SENT        27秒
UDP    172.16.1.53:40001   ⇔ 198.51.100.1:53    応答待ち         29秒
```

外部から届いたパケットは、この表のどれかの行の「逆向き」に一致するときだけ通されます。表にない相手からの「応答のふりをしたパケット」（3.1 のTCP ACKスキャンなど）は、ACKフラグがONでも一致する行がないので破棄されます。

**特徴**

ダイナミックパケットフィルタリング型ファイアウォールには、次のような特徴があります。

- 従来のスタティックパケットフィルタリングでは、上りも下りも別個の通信としかとらえられなかった。そのため、攻撃者の不正アクセスによって順序の矛盾したパケットが送られてきたとしても、該当する条件がACLに登録されてさえいれば中継してしまっていた。ダイナミックパケットフィルタリングでは、セッション管理テーブルによって通信の状態を把握しているため、こうした矛盾したパケットを破棄できる。
- 応答パケット用のルールは通信が行われている間だけ動的に生成されるため、常時開放しておくポートがなくなり、TCP ACKスキャンなどの攻撃にも強い。
- スタティックパケットフィルタリングでは問題だったFTPについても、ファイアウォールが動的にデータコネクション用のACLを生成し、転送が終了すれば直ちに破棄することで、セキュリティを確保できる。

### 3.3 ステートフルパケットインスペクション型

**ステートフルパケットインスペクション型**とは、Check Point社が開発して特許を取得したファイアウォールのアーキテクチャで、現在多くのファイアウォール製品に実装されています。仕組みはダイナミックパケットフィルタリング型と同じです。加えて、アプリケーションごとの通信フローなどの情報をもっており、それに基づいてレイヤを限定しないきめ細かな制御を行います。

「ステートフル」とは、個々のセッションの状態を管理して、常にその情報に基づいてフィルタリングを行うという意味です。最近では、「ステートフルパケットインスペクション型」が、従前の「ダイナミックパケットフィルタリング型」の呼称として使用されています。

> **ステートフルインスペクション**
> ステートフルパケットインスペクションは、単にステートフルインスペクションと表記されることもある。

科目Bのルール表を読むうえで最も重要な帰結は、「**ステートフルインスペクション型のファイアウォールでは、戻りの通信（応答）のルールを書かなくてよい**」ということです。3.1 の表で No.2、No.4 のように書いていた応答用のルールは、ファイアウォールがセッション管理テーブルから自動で処理します。したがって、事例のルール表には「接続を開始する方向」だけが書かれているのが普通です。

### 3.4 方式の比較

過去問題の選択肢には、ここで扱った3方式のほかに、プロキシとして通信を中継する方式も登場します。あわせて整理しておきましょう。

| 方式 | 判断の単位 | 見る情報 | 応答の扱い | 主な弱点 |
|---|---|---|---|---|
| パケットフィルタリング型（スタティック） | パケット1つずつ | IPアドレス、ポート番号、プロトコル、TCPフラグ | 応答用のルールを常時開けておく | ACKスキャン、偽装パケット、FTPなど複雑なプロトコル |
| ダイナミックパケットフィルタリング型 | セッション | 上記＋セッション管理テーブル | 通信中だけ動的に許可 | ペイロードは見ない |
| ステートフルパケットインスペクション型 | セッション＋アプリケーションの通信フロー | 上記＋アプリケーションごとの情報 | 同上 | ペイロード内の攻撃コードまでは見ない |
| アプリケーションゲートウェイ型（プロキシ型） | アプリケーションのやり取り | HTTPなどの中身 | FW自身がクライアントとサーバの双方と別々にコネクションを張る | 処理が重い。プロトコルごとにプロキシが必要 |
| サーキットレベルゲートウェイ型 | TCPコネクション | コネクションの要求 | FWが接続を受け付け、改めてサーバに接続を要求する | アプリケーションの中身は見ない |

### 3.5 アクセス制御のルール設定における考え方 ― ポジティブとネガティブ

ファイアウォールのACLをはじめ、アクセス制御のルール設定などにおいては、**ポジティブセキュリティモデル**と**ネガティブセキュリティモデル**という二つの考え方があります。

ポジティブセキュリティモデルとは、デフォルトではすべて「拒否」する状態であり、そこに許可するルール（**ホワイトリスト**、許可リスト）を登録するという考え方です。一方、ネガティブセキュリティモデルとは、デフォルトではすべて「許可」する状態であり、そこに拒否するルール（**ブラックリスト**、拒否リスト）を登録するという考え方です。

ネガティブセキュリティモデルを採用している代表例としては、シグネチャ（攻撃パターン）に一致する通信を遮断するIDS／IPSや、ブラックリスト方式のWAF、パターンファイルに基づいてマルウェアを検出するウイルス対策ソフトなどが挙げられます。これに対し、ファイアウォールのACLは、前述のACLの例（No.11で上記以外のアクセスをすべて拒否）のように、必要な通信のみを許可するポジティブセキュリティモデルで設計するのが基本です。本ノートの 1.2 で見た「暗黙の拒否」は、ポジティブセキュリティモデルを表の最後の1行で実現したものです。

> **ポジティブ／ネガティブセキュリティモデルの比較**
> ポジティブセキュリティモデルは未知の攻撃にも強いが、正当な通信を漏れなく定義する必要があり、設定・運用の負荷が高い。ネガティブセキュリティモデルは導入が容易で誤遮断（フォールスポジティブ）が起きにくい反面、定義されていない未知の攻撃は防御できない。

| 観点 | ポジティブセキュリティモデル | ネガティブセキュリティモデル |
|---|---|---|
| デフォルト | すべて拒否 | すべて許可 |
| 登録するもの | 許可するルール（ホワイトリスト） | 拒否するルール（ブラックリスト） |
| 未知の攻撃 | 強い（許可していなければ通らない） | 弱い（定義していなければ通る） |
| 運用負荷 | 高い（正当な通信を漏れなく定義） | 低い |
| 代表例 | ファイアウォールのACL、SELinuxのポリシ（5.4） | IDS/IPSのシグネチャ、ブラックリスト方式のWAF、ウイルス対策ソフトのパターンファイル |

## 4. ファイアウォールのアドレス変換機能

### 4.1 アドレス変換の2つの役割

一般的なファイアウォールやルータなどには、グローバルアドレスとプライベートアドレスを相互に変換する機能があります。この機能には、次の二つの役割があります。

1. 枯渇するグローバルアドレスを有効に活用する
2. 内部ネットワークに接続されたホストのアドレスをインターネットに公開しないことによって、セキュリティを高める

アドレス変換機能には、IPアドレスのみを変換する **NAT** と、IPアドレスに加えてポート番号も変換する **NAPT**（**IPマスカレード**とも呼ばれる）があります。

> **グローバルアドレス**
> インターネット上で一意となるように割り当てられるIPアドレス。世界で重複しないよう、**ICANN**や各地域・国のインターネットレジストリ（日本では **JPNIC**）によって管理されている。

> **プライベートアドレス**
> IPv4において **RFC 1918** で規定されている、組織内のネットワークで自由に使用することができるIPアドレス。インターネット上では経路制御されないため、そのままでは外部と通信できない。
> - 10.0.0.0 ～ 10.255.255.255（10.0.0.0/8）
> - 172.16.0.0 ～ 172.31.255.255（172.16.0.0/12）
> - 192.168.0.0 ～ 192.168.255.255（192.168.0.0/16）

役割2については、1.4 で学んだ注意点を思い出してください。アドレス変換によって内部のアドレス体系が外から見えにくくなり、外部から内部の機器へ直接接続を開始しにくくなるのは確かです。しかし、NATは通信の中身を検査せず、内部から外部へ出ていく通信（マルウェアによるC&Cサーバへの接続など）も止めません。アドレス変換はACLによるアクセス制御の**代わりにはならない**、という点を押さえておきましょう。

### 4.2 NAT

**NAT**（Network Address Translation）とは、ファイアウォールがパケットの中継時に始点（応答時には終点）IPアドレスを変換する方式です。内部から外部へ中継する場合にはプライベートアドレスからグローバルアドレスへの変換を行い、外部から内部へ中継する場合にはその逆の変換を行います。

NATでは、ファイアウォールが内部のホストに対してグローバルアドレスを一つずつ割り当てるため、使用可能なグローバルアドレスの数により、外部に同時にアクセスできるホストの数が制限されます。

なお、広義にはNAPTも含む呼称としてNATと呼ばれることもあります。

**図：NATのイメージ**

| 通信の方向 | ファイアウォールでの変換内容 |
|---|---|
| 内部 → 外部（要求時） | 始点アドレスをプライベートアドレスからグローバルアドレスに変換 |
| 外部 → 内部（応答時） | 終点アドレスをグローバルアドレスからプライベートアドレスに変換 |

具体的なアドレスで書くと、ファイアウォールのNAT変換表は次のように見えます。グローバルアドレスが3個しかなければ、同時に外部と通信できる内部ホストも3台までです。

```
内部（プライベート）      外部（グローバル）
172.16.10.5         ⇔   203.0.113.101
172.16.10.8         ⇔   203.0.113.102
172.16.10.9         ⇔   203.0.113.103
172.16.10.12        ⇔   （空きなし：変換できず通信不可）
```

公開サーバをプライベートアドレスで運用する場合には、この逆向きの使い方もします。インターネット上の利用者が接続する公開用のグローバルアドレス（例：203.0.113.10）宛てのパケットを、ファイアウォールがDMZ上のWebサーバのプライベートアドレス（例：172.31.1.10）に**宛先アドレス**を変換して中継する、という設定です（静的NAT、宛先NAT、ポートフォワーディングなどと呼ばれます）。科目Bのルール表で、許可ルールの宛先が公開用のアドレスで書かれているか、変換後のアドレスで書かれているかは製品によって違うので、事例の注記を確認してください。

### 4.3 NAPT

**NAPT**（Network Address and Port Translation）とは、ファイアウォールがパケットの中継時にIPアドレスとポート番号の両方を変換する方式であり、**IPマスカレード**（IP masquerade）という呼称で知られています。

内部から外部へ中継する場合には、ファイアウォールは、プライベートアドレスをファイアウォール自身の外部アドレス（グローバルアドレス）へ変換するとともに、送信元ポート番号を空いている任意の番号に変換します。中継したパケットに対する応答があった場合には、その逆の変換を行います（次図）。

**図：NAPTのイメージ**

クライアントPC（192.168.0.1）がインターネット上のWebサーバ（b1.b2.b3.b4）にアクセスし、ファイアウォールの外部アドレスが a1.a2.a3.a4 である場合の例を示します。

| 段階 | 通信の区間 | 始点（IPアドレス:ポート番号） | 終点（IPアドレス:ポート番号） |
|---|---|---|---|
| ① クライアントPCからインターネット上のWebサーバへのアクセス要求時 | クライアントPC → ファイアウォール | 192.168.0.1:54321 | b1.b2.b3.b4:80 |
| ② クライアントPCからの要求がファイアウォールを通過するとき（始点アドレスをプライベートアドレスからグローバルアドレスに変換するとともに、始点ポート番号を変換） | ファイアウォール → Webサーバ | a1.a2.a3.a4:12345 | b1.b2.b3.b4:80 |
| ③ WebサーバからクライアントPCへの応答時 | Webサーバ → ファイアウォール | b1.b2.b3.b4:80 | a1.a2.a3.a4:12345 |
| ④ 応答がファイアウォールを通過するとき（終点アドレス・ポート番号を元に戻す） | ファイアウォール → クライアントPC | b1.b2.b3.b4:80 | 192.168.0.1:54321 |

NAPTでは、ポート番号も変換することで一つのグローバルアドレスを複数のプライベートアドレスに割り当てられるため、一つのグローバルアドレスであっても複数のクライアントPCが同時にインターネットへアクセスできます。ファイアウォールは、変換前後のアドレスとポート番号の対応関係を**変換テーブル**で管理しています。

例示用アドレスで、2台のPCが同じWebサーバに同時にアクセスしているときの変換テーブルを書くと、次のようになります（ファイアウォールの外部アドレスは 203.0.113.1、Webサーバは 198.51.100.80 とします）。

| 内部（変換前）の始点 | 外部（変換後）の始点 | 相手（終点） |
|---|---|---|
| 192.168.0.1:54321 | 203.0.113.1:12345 | 198.51.100.80:443 |
| 192.168.0.2:54321 | 203.0.113.1:12346 | 198.51.100.80:443 |
| 192.168.0.2:54322 | 203.0.113.1:12347 | 198.51.100.80:443 |

1行目と2行目は、内部の始点ポートがたまたま同じ54321ですが、外部では12345と12346に変換されているので、Webサーバからの応答が戻ってきたときに、ファイアウォールは終点ポート番号を見てどちらのPCに返すべきかを判断できます。

NAPTには、インシデント調査で注意すべき副作用があります。外部のWebサーバのログには、社内の全PCが同じ「203.0.113.1」として記録されます。外部の組織から「203.0.113.1 から攻撃を受けた」と連絡があっても、それだけでは社内のどのPCかわかりません。調査担当者が送信元PCを特定するには、ファイアウォールのNAPTの変換ログ（いつ、どの内部アドレス:ポートを、どの外部ポートに変換したか）と、正確に時刻同期（NTP）された時刻が必要です。運用管理者は、この目的のために変換ログを取得・保存しておくべきです。

## 5. ルール表の読解と修正 ― 科目Bの観点

ここまでの知識を使って、科目Bで最も頻繁に問われる「ルール表の読解と修正」を練習します。設問は、おおむね「このルールは何のためにあるか」「業務要件を満たすために追加すべきルールは何か」「セキュリティ上問題のあるルールはどれで、どう直すべきか」の3パターンです。

### 5.1 ルール表を読む手順

1. **構成図でセグメントとアドレスを確認する**：どのアドレスがインターネット、DMZ、内部のどれにあたるかを書き出す。
2. **各ルールを文章に翻訳する**：「（送信元）が（宛先）の（サービス）に接続することを許可／拒否する。目的は〜」の形にする。ポート番号は 1.4 の表でサービス名に置き換える。
3. **業務要件と突き合わせる**：要件を満たすのに**足りないルール**（業務が止まる）と、要件にない**余計なルール・広すぎるルール**（攻撃対象が増える）を洗い出す。
4. **順序を確認する**：拒否したい例外が、広い許可ルールより下にあって効いていない（シャドーイング）箇所がないかを見る。
5. **方式を確認する**：ステートフルインスペクション型なら、戻りの通信のルールは不要。
6. **最後の行を確認する**：暗黙の拒否に任せるのか、明示的な「any→any 拒否（ログあり）」があるのか。

### 5.2 例題：問題のあるルール表

構成③（2.3）の会社で、ファイアウォール（ステートフルインスペクション型）に次のルールが設定されています。業務要件は次のとおりです。

- 要件1：インターネットから、DMZのWebサーバ（203.0.113.10）にHTTPSで接続できる。
- 要件2：インターネットから、DMZのメールサーバ（203.0.113.25）にSMTPでメールが届く。
- 要件3：内部のPC（172.16.10.0/24）は、DMZのプロキシサーバ（203.0.113.30、TCP/8080）経由でのみWebを閲覧する。
- 要件4：プロキシサーバは、インターネットのWebサーバにHTTP/HTTPSで接続する。名前解決にはISPのDNSサーバ（192.0.2.53）を使う。
- 要件5：DMZのサーバの保守は、内部の運用管理PC（172.16.1.10）からSSHでのみ行う。
- 要件6：Webサーバ上のアプリケーションは、内部のDBサーバ（172.16.5.20）にTCP/5432で接続する。
- 要件7：攻撃元として報告された 198.51.100.0/24 からの通信はすべて遮断する。

**表：現状のルール表（問題を含む）**

| No. | 送信元 | 宛先 | サービス | 動作 |
|---|---|---|---|---|
| 1 | any | 203.0.113.0/24（DMZ全体） | TCP/443 | 許可 |
| 2 | any | 203.0.113.25 | TCP/25 | 許可 |
| 3 | any | 203.0.113.10 | TCP/22 | 許可 |
| 4 | 172.16.0.0/16 | any | any | 許可 |
| 5 | 203.0.113.30 | any | TCP/80, TCP/443 | 許可 |
| 6 | 203.0.113.0/24 | 172.16.5.20 | TCP/5432 | 許可 |
| 7 | 198.51.100.0/24 | any | any | 拒否 |

### 5.3 指摘と修正

5.1 の手順で1行ずつ要件と突き合わせると、次の問題が見つかります。

| 対象 | 問題の種類 | 何が問題か | どう直すべきか | なぜそう直すのか |
|---|---|---|---|---|
| No.1 | 宛先が広すぎる | HTTPSを受けるべきはWebサーバだけなのに、DMZの全ホストのTCP/443が公開されている | 宛先を 203.0.113.10 に限定する | 公開する必要のないサーバを攻撃者に見せない（アタックサーフェスの縮小） |
| No.3 | 不要な許可 | インターネットの誰でもWebサーバにSSHで接続を試みられる（要件5に反する） | 削除する | パスワードリスト攻撃などでWebサーバの管理者権限を奪われるのを防ぐ |
| No.4 | 送信元・宛先・サービスが広すぎる（出口対策の欠如） | 内部の全ホストが、プロキシを経由せずインターネットの全ポートへ直接接続できる（要件3に反する） | 送信元 172.16.10.0/24、宛先 203.0.113.30、サービス TCP/8080 に限定する | マルウェアがプロキシを迂回してC&Cサーバと直接通信するのを防ぎ、通信をプロキシのログに残す |
| No.6 | 送信元が広すぎる | DMZのどのサーバからでも内部のDBサーバに接続できる | 送信元を 203.0.113.10 に限定する | DMZの別のサーバ（メールサーバなど）が乗っ取られたときに、DBサーバへ到達されるのを防ぐ |
| No.7 | 順序の誤り（シャドーイング） | No.1、No.2 が先に一致するため、攻撃元からのHTTPS・SMTPが許可されてしまう | No.1 より上に移動する | 最初に一致したルールで評価が打ち切られるため、例外の拒否は広い許可より上に置く必要がある |
| （不足） | 必要なルールの欠如 | プロキシサーバがISPのDNSサーバで名前解決できず、要件4のWeb閲覧が成立しない | 送信元 203.0.113.30、宛先 192.0.2.53、UDP/53・TCP/53 の許可を追加する | 暗黙の拒否により、書かれていない通信はすべて破棄されるため |
| 最終行 | ログの欠如 | 暗黙の拒否に一致した通信が記録されず、スキャンやC&C通信の試みに気づけない | 最終行に「any→any 拒否（ログ記録）」を明示する | 拒否された通信のログを監視し、攻撃や感染の兆候を検知するため |

No.2、No.5、No.8 は要件2、要件4、要件5をそのとおりに満たしているので、変更不要です。なお、No.8 は元の表では No.4 が先に一致して意味をもっていませんでしたが、No.4 を絞り込んだことで初めて有効に働くようになります。

### 5.5 ログでルールの効果を確かめる

修正後のルール表を適用した翌日、ファイアウォールに次のログが残っていたとします。

```
2026/10/01 09:02:11,fw01,deny,rule=9,src=172.16.10.23:50412,dst=192.0.2.80:443,proto=tcp,flags=S,zone=trust->untrust
2026/10/01 13:47:30,fw01,deny,rule=9,src=203.0.113.10:41022,dst=172.16.5.20:22,proto=tcp,flags=S,zone=dmz->trust
```

1行目は、内部のPCがプロキシを使わずに外部のWebサーバへ直接接続しようとして、最終行で拒否された記録です。ブラウザのプロキシ設定の漏れであることが多いですが、マルウェアが直接外部に出ようとしている可能性もあるので、運用管理者はそのPCを確認すべきです。

2行目は深刻です。Webサーバ（DMZ）から内部のDBサーバのSSHポートへの接続が試みられています。業務上、WebサーバがDBサーバにSSHで接続する理由はありません（要件6はTCP/5432だけです）。Webサーバが攻撃者に乗っ取られ、内部への侵入（ラテラルムーブメント）を試みている兆候と考えられます。修正前のルール表でもこの通信は許可されていませんでしたが、明示的な拒否の行がなかったため暗黙の拒否で黙って破棄され、ログに残らなかったことにも注意してください。拒否ログは、ルールが正しく絞られているからこそ、異常を浮かび上がらせてくれるのです。

### 5.6 記述の型

科目Bで「ルールの問題点と修正内容を答えよ」と問われたら、次の要素をそろえて書きます。

- **どのルールを**：「項番3のルールを」
- **何が問題か（リスク）**：「インターネットからWebサーバへのSSH接続が許可されており、パスワードリスト攻撃などによって管理者権限を奪われるおそれがある」
- **どう直すべきか**：「送信元を運用管理PCのIPアドレスに限定する（または削除する）」
- **何のために**：「保守用の接続を運用管理PCからに限定し、攻撃者に管理用のサービスへの接続機会を与えないため」

「追加すべきルール」を問われたら、送信元・宛先・サービス・動作の4項目をすべて書き、ルール表のどこに挿入するか（順序）まで意識します。順序が問われている場合は、「最初に一致したルールが適用されるため、〇〇のルールより上に置く必要がある」という理由を添えます。

## 6. ファイアウォールで防御できない攻撃

前述のように、パケットフィルタリングの仕組みによってファイアウォールには様々なタイプがあり、それによって確保できるセキュリティのレベルにも違いがあります。しかし、フィルタリングの仕組みが異なったとしても、一般的なファイアウォール（ネットワークファイアウォール）はあくまでもACLに基づいたアクセス制御を行う製品であり、パケットのペイロードに含まれた様々な攻撃コードや不正なデータまでは検査しません。そのため、ファイアウォールは、ACLで許可された通信に紛れ込んだ攻撃については防御することができません。

**表：ファイアウォールで防御できない攻撃の例（ACLに則っている場合）**

| 攻撃の種類 | 攻撃手法の例 | 対策の例 |
|---|---|---|
| OS、プロトコル、ミドルウェア（サーバプログラムなど）の脆弱性を突いた攻撃 | ・ポートスキャン<br>・BOF（バッファオーバフロー）攻撃<br>・パスワードクラック<br>・プロトコルベースのセッションハイジャック | ・ホストの要塞化<br>・脆弱性診断及び対策の実施<br>・IPSによる攻撃の遮断 |
| Webアプリケーションプログラムの脆弱性を突いた攻撃 | ・クロスサイトスクリプティング<br>・SQLインジェクション<br>・OSコマンドインジェクション<br>・アプリケーションベースのセッションハイジャック | ・Webアプリケーションの脆弱性診断及び対策の実施<br>・Webサーバ、DBサーバの要塞化などの対策<br>・Webアプリケーションファイアウォール（WAF）による攻撃の遮断 |
| DoS系の攻撃 | ・Connection Flood攻撃（接続元が同一ではなく、多数ある場合）<br>・反射・増幅型DDoS攻撃 | ・十分な帯域をもつネットワークや、十分な処理能力をもつファイアウォールやサーバを用いる<br>・CDNサービスを利用する |
| マルウェアの侵入 | ・コンピュータウイルス<br>・ワーム<br>・スパイウェア<br>・ランサムウェア<br>・ボット | ・ホストの要塞化<br>・ゲートウェイ型のAV製品やサンドボックスによって侵入を防ぐ<br>・個々のホストにEPPやEDRを導入する |

> **EPP / EDR**
> **EPP**（Endpoint Protection Platform）は、マルウェアのエンドポイントへの侵入を未然に防ぐことを目的とした製品。**EDR**（Endpoint Detection and Response）は、侵入後の不審な挙動を検知し、調査・封じ込めなどの対応を支援する製品である。

なぜ防げないのかを、攻撃ごとに1文で言えるようにしておきましょう。

- **脆弱性を突いた攻撃**：Webサーバの TCP/443 を公開している以上、そのポートに届くBOF攻撃のパケットも、ACL上は「許可されたHTTPS通信」と区別できない。ポートスキャンも、許可されたポートへの接続試行は通ってしまう（開いているポートがわかる）。
- **Webアプリケーション攻撃**：`' OR '1'='1` のようなSQLインジェクションの文字列は、HTTPリクエストの中（ペイロード）にあり、ファイアウォールはそこを見ない。しかもHTTPSなら暗号化されていて見えない（1.6 の図）。
- **DoS系の攻撃**：送信元が多数に分散していれば、送信元アドレスで遮断できない。反射・増幅型では、正規のDNSサーバなどからの「応答」として届く（1.4 のリフレクション攻撃）。また、回線そのものがあふれれば、ファイアウォールがいくら捨てても手前で詰まる。
- **マルウェアの侵入**：メールの添付ファイルやWebからのダウンロードは、許可されたSMTP・HTTPSの通信の中身として届く。

この表の「対策の例」の列が、そのまま第5章の残りのノート（5.6 IDS、5.7 IPS、5.8 WAF、5.9 サンドボックス）と 5.2・5.3 に対応しています。ファイアウォールは多層防御の「一枚目」であって、これだけで守るものではありません。

## 7. ファイアウォールの拡張機能

ファイアウォールには、前述の基本的な機能に加え、IPsecに準拠した**VPNゲートウェイ**機能や、他のセキュリティ製品（IDS、ゲートウェイ型AVツール、コンテンツフィルタリングツールなど）と連携する機能などがあります。

それらに加え、さらなる機能向上、あるいは処理能力や可用性の向上を図るために、様々な機能があります。ここでは、その一例を簡単に紹介します。

> **IPsec**
> IP Securityの略。パケットをIP層（OSI基本参照モデルではネットワーク層）で暗号化・認証するプロトコル群であり、VPNを実現する代表的な技術である。**IETF**（Internet Engineering Task Force：インターネット技術タスクフォース）によって標準化されている。IPv4でも利用することができ、IPv6では当初、実装が必須とされていた（1.4 で見たとおり、現在は「推奨」に改められている）。

IPsecのVPNを通すには、ファイアウォールでIKE（UDP/500、NAT越えの場合はUDP/4500）と、ESP（プロトコル番号50）を許可する必要があります。1.4 で学んだ「ポート番号」と「プロトコル番号」の違いが、ここでルールの書き方の違いとして表れます。

### 7.1 性能と接続性に関する機能

**① ハイパフォーマンス**

ファイアウォールには非常に高いパフォーマンスが求められるため、ASICなどの技術が採用されています。

> **ASIC**
> Application Specific Integrated Circuitの略。特定の用途向けに設計・製造された集積回路のこと。パケット処理などをソフトウェアではなくハードウェアで実行することで、高速な処理を実現できる。

**② 高速インタフェース対応**

ギガビットイーサネットや10ギガビットイーサネットなどの高速なネットワークインタフェースを備え、大量のトラフィックを処理できます。

**③ マルチホーミング対応**

マルチホーミング環境に対応し、インターネット（WAN）への接続用ポートを複数備えています。

> **マルチホーミング**
> 企業などのネットワークを、複数のISP（インターネットサービスプロバイダ）を経由してインターネットに接続すること。回線やISPの障害に対する耐障害性を高めたり、負荷を分散したりすることができる。

**④ IPv6対応**

IPv6の普及に伴い、ファイアウォールは標準でIPv6に対応しています。1.4 で見たとおり、IPv4とIPv6を併用する環境では、管理者はIPv6にもIPv4と同等のルールを設定すべきです。IPv4のルール表だけを整備していると、IPv6経由の通信が素通りになるおそれがあります。

**⑤ QoS（Quality of Service）**

ファイアウォールは、プロトコルごとに割り当てる帯域の最大値（あるいは最低値）を登録しておき、それに基づいて帯域制御を行う機能を備えています。たとえば、動画配信サービスへの通信が業務システムの通信を圧迫しないように、帯域の上限を設定できます。

### 7.2 高可用性（ハイアベイラビリティ：HA）

**⑥ 高可用性（ハイアベイラビリティ：HA）**

すべての通信が通るファイアウォールは、止まれば組織全体の通信が止まる単一障害点です。ファイアウォールのHAを実現するため、次のような方式が広く採用されています。

**負荷分散方式**

2台以上のファイアウォールを2台の負荷分散装置（ロードバランサ：LB）にたすきがけ接続し、負荷分散を図る方式です。

- 一方のLBがアクティブ状態となっており、負荷分散処理を行う。
- 他方のLBは通常はスタンバイ状態となっている。
- ファイアウォールの動作確認については、LBがpingコマンドなどを用いて行う。
- あるファイアウォールに障害が発生すると、LBがそれを検知し、そのファイアウォールを使用せずに運用を継続する。
- アクティブ状態だったLBに障害が発生すると、スタンバイ状態だったLBが切り替わって負荷分散処理を継続する。

**図：LBを用いたファイアウォールの負荷分散のイメージ**

```
        インターネット
             │
     ┌───────┴───────┐
  [LB1(Act)]      [LB2(Stn)]
     │  ╲         ╱  │
     │    ╲     ╱    │        ← たすきがけ接続
     │      ╳        │
     │    ╱     ╲    │
  [FW1]    [FW2]    [FW3]
     └───────┬───────┘
          [SW]（内部側も同様に LB を介して接続）
```

| 状態 | 動作 |
|---|---|
| 平常時 | LB1（Act）が複数のファイアウォールにトラフィックを振り分け、LB2（Stn）は待機 |
| ファイアウォール1障害発生時 | LB1がファイアウォール1の障害を検知し、残りのファイアウォールだけにトラフィックを振り分ける |
| LB1障害発生時 | LB2がスタンバイ状態からアクティブ状態に切り替わり、負荷分散処理を継続する |

> LB：ロードバランサ　SW：スイッチ　Act：アクティブ状態　Stn：スタンバイ状態

ステートフルインスペクション型のファイアウォールを負荷分散する場合、行きと帰りのパケットが別のファイアウォールを通ると、帰りを受けたファイアウォールのセッション管理テーブルにはその通信がないため、正規の応答が破棄されてしまいます。LBは、同じ通信を同じファイアウォールに振り分け続ける必要があります。

**ホットスタンバイ方式**

2台のファイアウォールを用いてホットスタンバイ構成をとり、耐障害性を高めた方式です。

- 一方のファイアウォールをアクティブ状態、他方のファイアウォールをスタンバイ状態とし、待機させる。
- ファイアウォール同士はHA専用のポートで接続され、VRRP（Virtual Router Redundancy Protocol）などを用いて常に動作状態を監視する。
- アクティブ状態のファイアウォールに異常が発生すると、スタンバイ状態だったファイアウォールに切り替わって処理を継続する。

**図：ホットスタンバイ方式のイメージ**

| 状態 | 動作 |
|---|---|
| 平常時 | ファイアウォール1（Act）が全ての通信を処理し、ファイアウォール2（Stn）は待機 |
| ファイアウォール1障害発生時 | ファイアウォール2がアクティブ状態に切り替わり、処理を継続する |

> **VRRP**
> 複数のルータ（ファイアウォール）を仮想的に1台のルータとして扱い、仮想IPアドレスを共有することで、障害発生時に自動的に経路を切り替えるための冗長化プロトコル。RFC 5798などで規定されている。

ホットスタンバイ方式では、HA専用のポートを通じて、アクティブ側のセッション管理テーブルをスタンバイ側に同期しておくのが一般的です。同期していないと、切替えの瞬間に通信中のセッションがすべて切断されてしまいます。

**自律負荷分散方式**

ホットスタンバイ方式と同様の構成でありながら、どちらのファイアウォールもアクティブ状態で並行稼働し、ファイアウォールが自律的に負荷分散を行う方式です（**アクティブ／アクティブ構成**）。

- 一方のファイアウォールに障害が発生した場合には、残りのファイアウォールで処理を継続する。

| 方式 | 平常時に処理する台数 | 切替えの判断 | 特徴 |
|---|---|---|---|
| 負荷分散方式 | 複数台（LBが振り分け） | LBがpingなどで監視 | 台数を増やして性能を拡張できる。LB自体も冗長化が必要 |
| ホットスタンバイ方式 | 1台（アクティブ／スタンバイ） | FW同士がVRRPなどで監視 | 構成が単純。待機側の性能は平常時に使われない |
| 自律負荷分散方式 | 2台（アクティブ／アクティブ） | FW同士が自律的に | 両方の性能を使える。1台故障時は残り1台で全量を処理できる性能が必要 |

### 7.3 構成と防御範囲を広げる機能

**⑦ 負荷分散機能**

ファイアウォールがHTTP、FTPなど特定のプロトコルに対するトラフィックを、複数のサーバに振り分ける負荷分散機能です。

**図：ファイアウォールによる負荷分散のイメージ（HTTPの場合）**

インターネットから公開用アドレス宛てに届いたHTTPのリクエストを、ファイアウォールがDMZ上の複数のWebサーバに振り分けて中継します。

```
インターネット ──HTTP（宛先：公開用アドレス 203.0.113.10）──▶ [ファイアウォール]
                                                              ├──▶ [Webサーバ1]
                                                              ├──▶ [Webサーバ2]  （DMZ）
                                                              └──▶ [Webサーバ3]
```

**⑧ マルチセグメント対応**

多数のネットワークセグメントを構成する場合に、ファイアウォールがIEEE 802.1Q（タグVLAN）に対応することで、少ない物理ポートで多数のセグメント間のアクセス制御を行うことができます（2.4 の構成④）。

**⑨ アプリケーション層の攻撃に対する防御機能**

従来のファイアウォールに、IPS機能や、アンチウイルス、コンテンツフィルタリングなどの複数の機能を統合したオールインワン型の製品もあります。そうした製品は **UTM**（Unified Threat Management：統合脅威管理）製品、もしくは単にUTMと呼ばれています。

**図：従来のファイアウォールとUTM製品の機能比較**

| 機能 | 従来の一般的なファイアウォール | UTM製品 |
|---|---|---|
| ファイアウォール（パケットフィルタリング） | ○ | ○ |
| VPN | ○ | ○ |
| IDS／IPS | － | ○ |
| アンチウイルス（ゲートウェイ型） | － | ○ |
| アンチスパム | － | ○ |
| コンテンツフィルタリング（URLフィルタリング） | － | ○ |

> ※UTM製品に実装される機能は各ベンダーの製品ごとに異なる。

UTM製品を使用すると、組織は別個に製品を購入する必要がないためコスト削減の効果があることに加え、管理するホストの数も少ないため、運用管理の手間が省けるというメリットが期待できます。その反面、次のような問題も懸念されるため、導入にあたっては十分に評価・検証する必要があります。

- ファイアウォール全体のパフォーマンスが低下する（複数の検査機能を1台で動かすため）。
- 設定が複雑になる。
- UTMが単一障害点（SPOF）となり、障害発生時には全てのセキュリティ機能が停止する。

UTM製品は、中小規模のサイトなどでは有効な選択肢と考えられますが、トラフィック量の多い大規模なサイトなどでは、むしろ必要最小限の機能に特化してハイパフォーマンス、ハイアベイラビリティを実現する製品のほうが望ましいでしょう。

なお、近年は、ポート番号ではなく通信の中身からアプリケーション（Webブラウザ上で動く特定のクラウドサービスなど）を識別し、アプリケーション単位や利用者単位でルールを書けるファイアウォールが主流になっています。これを**次世代ファイアウォール**（NGFW）と呼びます。HTTPSの TCP/443 の上で多種多様なサービスが動く現在、「ポート番号＝サービス」という前提だけでは制御しきれなくなったことが背景にあります。

## 8. 確認問題

### 8.1 理解度チェック

- **Q1**：ファイアウォールとは何か。
- **Q2**：ファイアウォールに求められる役割は何か。
- **Q3**：ファイアウォールにはどのような種類があるか。
- **Q4**：ファイアウォールはネットワーク上のどこに配置するのか。
- **Q5**：ファイアウォールでどのような攻撃を防ぐことができるのか。
- **Q6**：パケットフィルタリング型ファイアウォールはどのようなところが脆弱か。
- **Q7**：パケットフィルタリング型とダイナミックパケットフィルタリング型の違いは何か。
- **Q8**：NATとNAPTの違いは何か。
- **Q9**：ファイアウォールで防げない攻撃にはどのようなものがあるか。
- **Q10**：ファイアウォールの可用性を高めるにはどのような方法があるか。
- **Q11**：UTM製品とは何か。
- **Q12**：UTM製品を導入することによるメリットとデメリットとして何があるか。

> **解答のポイント**（原本には解答例がなかったため、本文の記述から作成して補いました）
> - Q1：複数のネットワークセグメント間において、あらかじめ設定されたルール（ACL）に基づいてパケットを中継したり破棄したりする機能、あるいはその機能をもつ制御製品。
> - Q2：インバウンド方向の不正アクセスを防ぐ「盾」の役割に加え、アウトバウンド方向も含めてセグメント間の通信をフィルタリングする「フィルタ」の役割（出口対策）。さらに、十分な処理能力と冗長化による可用性の確保。
> - Q3：フィルタリング方式では、パケットフィルタリング型（スタティック）、ダイナミックパケットフィルタリング型、ステートフルパケットインスペクション型。範囲としては、ネットワークファイアウォールとアプリケーションファイアウォール（WAFなど）、ホスト上のパーソナルファイアウォールがある。
> - Q4：インターネットとの接続口に配置し、公開サーバはDMZ（2台のファイアウォールの間、またはファイアウォールの第三のセグメント）に置く。用途やセキュリティレベルに応じて複数のDMZを設けることもある。
> - Q5：ACLに基づき、許可していないIPアドレス・ポート番号・プロトコルへのアクセス（外部からの不正な接続、内部からの不正な外部通信など）を防ぐことができる。
> - Q6：パケットを1つずつ独立に判断するため、応答用のルールを常時開けておく必要があり、ACKフラグを立てた偽装パケット（TCP ACKスキャンなど）を通してしまう。ポート番号が固定でない、逆方向から接続する、ペイロードにアドレスを含むプロトコル（FTPなど）には脆弱なACLしか書けない。
> - Q7：パケットフィルタリング型は上りと下りを別個の通信として静的なACLで判断する。ダイナミックパケットフィルタリング型は、接続要求時にセッション管理テーブルに登録して応答用のルールを動的に生成し、セッション終了時に破棄するため、常時開放するポートがなく、状態と矛盾するパケットを破棄できる。
> - Q8：NATはIPアドレスだけを変換し、内部ホストにグローバルアドレスを1つずつ割り当てるため同時接続数がアドレス数に制限される。NAPT（IPマスカレード）はIPアドレスとポート番号を変換し、1つのグローバルアドレスを複数のホストで共有できる。
> - Q9：ACLで許可された通信に紛れ込んだ攻撃。OS・ミドルウェアの脆弱性を突く攻撃、Webアプリケーションの脆弱性を突く攻撃（XSS、SQLインジェクションなど）、分散したDoS攻撃、マルウェアの侵入など。
> - Q10：LBを用いた負荷分散方式、ホットスタンバイ方式（VRRPなど）、自律負荷分散方式（アクティブ／アクティブ構成）。あわせて十分な処理能力（ASIC、高速インタフェース）をもつ機器を用いる。
> - Q11：ファイアウォールに、IDS/IPS、ゲートウェイ型アンチウイルス、アンチスパム、コンテンツフィルタリングなどの複数の機能を統合したオールインワン型の製品。
> - Q12：メリットは、別個に製品を購入しないことによるコスト削減と、管理するホスト数の減少による運用管理の省力化。デメリットは、パフォーマンスの低下、設定の複雑化、単一障害点となり障害時に全セキュリティ機能が停止すること。

### 8.2 過去問題1：pingへの応答の停止

DMZ上のコンピュータがインターネットからのpingに応答しないようにしたい。ファイアウォールのルールで"通過禁止"に設定するものはどれか。

ア　ICMP
イ　TCPのポート番号21
ウ　TCPのポート番号123
エ　UDPのポート番号161

*［情報セキュリティスペシャリスト試験・H28秋］*

> **解答・解説**
> pingは、ICMP（Internet Control Message Protocol）を用いて指定したコンピュータとの疎通を確認するコマンドである。ICMPエコー要求（Echo Request）を送信し、相手からのICMPエコー応答（Echo Reply）を受け取ることで疎通を確認するため、ICMPを通過禁止にすれば、インターネットからのpingに応答しないようにできる。したがって**ア**が正解。
>
> - イ：TCPのポート番号21は、FTPの制御用コネクションで使用される。
> - ウ：ポート番号123は、NTPで使用される（NTPは通常UDPを用いる）。
> - エ：UDPのポート番号161は、SNMPで使用される。
>
> 1.4 で学んだとおり、ICMPにはポート番号がなく、ファイアウォールではプロトコル番号（1）やタイプ（エコー要求は8）で指定する。実務では、ICMPをすべて遮断すると経路MTU探索が壊れるため、エコー要求だけを止めるのが望ましい。

### 8.3 過去問題2：ステートフルパケットインスペクションの特徴

ファイアウォールにおけるステートフルパケットインスペクションの特徴はどれか。

ア　IPアドレスの変換が行われることによって、内部のネットワーク構成を外部から隠蔽できる。
イ　暗号化されたパケットのデータ部を復号して、許可された通信かどうかを判断できる。
ウ　過去に通過したリクエストパケットに対応付けられる戻りのパケットを通過させることができる。
エ　パケットのデータ部をチェックして、アプリケーション層での不正なアクセスを防止できる。

*［情報処理安全確保支援士試験・R3秋］*

> **解答・解説**
> ステートフルパケットインスペクション型のファイアウォールでは、最初にコネクションを確立する方向を意識した基本的なACLを事前に登録しておき、実際に接続要求（TCPであればSYNパケット）があると、その通信をセッション管理テーブルに登録するとともに、戻りのパケットを通過させるために必要なルールが動的に生成され、フィルタリングが行われる。
>
> 旧来のスタティックパケットフィルタリング型のファイアウォールでは、上りも下りも別個のパケットとしてしかとらえられなかったため、順序の矛盾したパケットが送られてきたとしても、該当する条件がACLに登録されてさえいれば中継していた。一方、ステートフルパケットインスペクション型では、過去の通信の状態が管理されており、それと矛盾するパケットは不正パケットとして遮断することができる。なお、ステートフルパケットインスペクション型はダイナミックパケットフィルタリング型とも呼ばれる。したがって**ウ**が正解。
>
> - ア：NAT／NAPTの特徴である。
> - イ：SSL/TLSインスペクション（復号機能）の特徴である。
> - エ：アプリケーションゲートウェイ型ファイアウォールやIPS、WAFなどの特徴である。

### 8.4 過去問題3：ステートフルパケットインスペクション方式の特徴

ステートフルパケットインスペクション方式のファイアウォールの特徴はどれか。

ア　WebクライアントとWebサーバとの間に配置され、リバースプロキシサーバとして動作する方式であり、Webクライアントからの通信を目的のWebサーバに中継する際に、受け付けたパケットに不正なデータがないかどうかを検査する。
イ　アプリケーションプロトコルごとにプロキシソフトウェアを用意する方式であり、クライアントからの通信を目的のサーバに中継する際に、通信に不正なデータがないかどうかを検査する。
ウ　特定のアプリケーションプロトコルだけを通過させるゲートウェイソフトウェアを用いる方式であり、クライアントからのコネクションの要求を受け付け、目的のサーバに改めてコネクションを要求することによって、アクセスを制御する。
エ　パケットフィルタリングを拡張した方式であり、過去に通過したパケットから通信セッションを認識し、受け付けたパケットを通信セッションの状態に照らし合わせて通過させるか遮断するかを判断する。

> **解答・解説**
> ステートフルパケットインスペクション方式は、パケットフィルタリングを拡張した方式であり、セッション管理テーブルによって通信セッションの状態を把握し、受け付けたパケットがその状態と矛盾しないかどうかに基づいて、通過させるか遮断するかを判断する。したがって**エ**が正解。
>
> - ア：WAF（Webアプリケーションファイアウォール）の特徴である。
> - イ：アプリケーションゲートウェイ（プロキシ）型ファイアウォールの特徴である。
> - ウ：サーキットレベルゲートウェイ型ファイアウォールの特徴である。
>
> 3.4 の方式比較の表の各行が、そのまま選択肢になっている。

### 8.5 過去問題4：DBサーバの移動に伴うルールの変更

セキュリティ対策として、次の条件の下でデータベース（DB）サーバをDMZから内部ネットワークに移動するような、次のネットワーク構成の変更を計画している。このとき、ステートフルパケットフィルタリング型のファイアウォール（FW）において、必要となるフィルタリングルールの変更のうちの一つはどれか。

**〔条件〕**

1. Webアプリケーション（WebAP）サーバをインターネットに公開し、HTTPSで接続できるようにする。
2. WebAPサーバ上のプログラムだけがDBサーバ上のDBに接続でき、ODBC（Open Database Connectivity）を使用して特定のポート間で通信する。
3. SSHを使用して各サーバに接続できるのは、運用管理PCだけである。
4. フィルタリングルールは、必要な通信だけを許可する設定にする。

**〔ネットワーク構成の変更〕**

変更前はDMZ上にWebAPサーバとDBサーバが配置されており、変更後はDBサーバを運用管理PCと同じ内部ネットワークに移動する。

```
変更前:  インターネット ── [FW] ── DMZ（WebAPサーバ、DBサーバ）
                            └──── 内部ネットワーク（運用管理PC）

変更後:  インターネット ── [FW] ── DMZ（WebAPサーバ）
                            └──── 内部ネットワーク（運用管理PC、DBサーバ）
         ※DMZと内部ネットワークは、それぞれL2SW・L3SWを介してFWに接続
```

> L2SW：レイヤ2スイッチ　L3SW：レイヤ3スイッチ

| | ルールの変更種別 | 送信元 | 宛先 | サービス |
|---|---|---|---|---|
| ア | 削除 | インターネット | WebAPサーバ | HTTPS |
| イ | 削除 | 運用管理PC | 変更前のDBサーバ | SSH |
| ウ | 追加 | WebAPサーバ | 変更後のDBサーバ | SSH |
| エ | 追加 | インターネット | WebAPサーバ | ODBC |

*［情報処理安全確保支援士試験・R5春］*

> **解答・解説**
> - ア：インターネットからWebAPサーバへのHTTPS通信は、条件(1)より引き続き許可する必要があるため、削除してはならない。
> - イ：DBサーバが運用管理PCと同じ内部ネットワークに移動すると、運用管理PCからDBサーバへのSSH通信はFWを経由しなくなるため、変更前のDBサーバ宛てのSSHを許可するルールは不要となる。条件(4)より、不要なルールは削除する必要がある。
> - ウ：条件(3)より、SSHで各サーバに接続できるのは運用管理PCだけであるため、WebAPサーバからDBサーバへのSSHを許可してはならない。WebAPサーバからDBサーバへは、ODBCを許可するルールが必要となる。
> - エ：ODBCはWebAPサーバとDBサーバとの間の通信であり、インターネットからWebAPサーバへのODBCを許可する必要はない。
>
> したがって**イ**が正解。本ノート5章の例題と同じく、「同じセグメント内の通信はFWを通らない」「要件に対応しないルールは削除する」という観点で解く。

### 8.6 過去問題5：DMZと内部ネットワークの間のファイアウォール

DMZ上に公開しているWebサーバで入力データを受け付け、内部ネットワークのDBサーバにそのデータを蓄積するシステムがある。インターネットからDMZを経由してなされるDBサーバへの不正侵入対策の一つとして、DMZと内部ネットワークとの間にファイアウォールを設置するとき、最も有効な設定はどれか。

ア　DBサーバの受信ポート番号を固定し、WebサーバからDBサーバの受信ポート番号への通信だけをファイアウォールで通す。
イ　DMZからDBサーバへの通信だけをファイアウォールで通す。
ウ　Webサーバの発信ポート番号は任意のポート番号を使用し、ファイアウォールでは、いったん終了した通信と同じ発信ポート番号を使った通信を拒否する。
エ　Webサーバの発信ポート番号を固定し、その発信ポート番号からの通信だけをファイアウォールで通す。

*［情報セキュリティスペシャリスト試験・H22秋］*

> **解答・解説**
> 問題文のような仕様のシステムにおいて、DBサーバへの不正侵入を防ぐためには、DMZ上のWebサーバから内部ネットワークのDBサーバの受信ポートへ発信された通信だけを通すように、ファイアウォールを設定する必要がある。
>
> 実際に通信が発生すると、ファイアウォールは、受け取ったパケットの方向（DMZ→内部ネットワーク）と発信者のIPアドレスから、DMZ上のWebサーバからの通信であることを判断する。また、受け取ったパケットのあて先IPアドレスとあて先ポート番号から、内部ネットワークのDBサーバの受信ポートへ発信された通信であることを判断する。したがって**ア**が正解。
>
> - イ：この設定では、DMZ上のDNSサーバなど、Webサーバ以外のサーバからの通信であっても許可されてしまう。
> - ウ、エ：Webサーバに限らず、接続を要求するパケットの発信者ポート番号は通常任意の番号が使用されるが、固定／任意のいずれであっても、発信者ポート番号によって正当なアクセスと不正なアクセスを区別することはできない。
>
> 本ノート5章の例題で行った No.6 の修正（送信元をDMZ全体からWebサーバに限定する修正）と同じ観点である。1.4 で学んだとおり、送信元ポートはクライアントのOSが一時的に選ぶ番号なので、ルールの条件としては「宛先ポート」を使う。

## 9. 試験対策まとめ（重要ポイント）

### 9.1 知識の確認（科目A-2向け）

- **ACLの評価**：上から順に評価し、最初に一致したルールを適用して打ち切る。どれにも一致しなければ暗黙の拒否。ファイアウォールのACLはポジティブセキュリティモデル（デフォルト拒否＋許可リスト）で設計する。
- **狭義と広義**：狭義はネットワーク層でACLに基づいて制御する製品。広義は侵入・攻撃を防ぐ製品全般。ネットワークファイアウォールとアプリケーションファイアウォール（WAF）の区別。
- **インバウンドとアウトバウンド**：「盾」から「フィルタ」へ。出口対策はC&C通信や情報漏えいの防止に有効。
- **DMZ**：公開サーバを内部ネットワークから切り離し、侵害時の被害拡大を防ぐ緩衝セグメント。バリアセグメントは最も危険度が高い。2台構成では異なるベンダーの製品にすると多層防御になる。
- **パケットフィルタリング型**：ヘッダ情報（アドレス、ポート、プロトコル、方向、TCPフラグ）で判断し、ペイロードは見ない。応答用ルールを常時開けるため、ACKスキャンや偽装パケットに弱い。FTPのアクティブモードは危険で、パッシブモードを使う。
- **ダイナミック／ステートフルパケットインスペクション型**：セッション管理テーブルで状態を管理し、応答用のルールを動的に生成・破棄。「過去に通過したリクエストに対応する戻りのパケットを通過させる」が定番の正解選択肢。Check Point社が開発。
- **引っかけの選択肢**：「アドレス変換で構成を隠蔽」はNAT、「暗号化されたデータ部を復号」はSSL/TLSインスペクション、「データ部をチェック」はアプリケーションゲートウェイ・IPS・WAF、「リバースプロキシとして検査」はWAF、「改めてコネクションを要求」はサーキットレベルゲートウェイ。
- **NAT と NAPT**：IPアドレスのみか、ポート番号も変換するか。NAPT＝IPマスカレード。プライベートアドレスはRFC 1918（10/8、172.16/12、192.168/16）。NATはファイアウォールの代わりにならない。
- **防御できない攻撃**：許可された通信に紛れた攻撃（脆弱性を突く攻撃、Webアプリケーション攻撃、分散したDoS、マルウェア）。対策はIPS、WAF、要塞化、脆弱性診断、CDN、EPP/EDR。
- **HA**：負荷分散方式（LBたすきがけ）、ホットスタンバイ方式（VRRP）、自律負荷分散方式（アクティブ／アクティブ）。
- **UTM**：複数機能の統合。コスト・運用の省力化と引き換えに、性能低下・設定の複雑化・SPOF。

### 9.2 記述式で問われる観点（科目B向け）

- **ルールの目的を答える**：「項番〇は、（送信元）から（宛先）への（サービス）を許可し、（業務要件）を実現するためのルールである」と、送信元・宛先・サービス・目的の4点で説明する。
- **許可しすぎのルールを直す**：送信元や宛先が any やセグメント全体になっている、サービスが any になっている、要件にないサービス（インターネットからのSSH/RDPなど）が許可されている、の3パターンを探す。修正は「〇〇に限定する」「削除する」と書き、理由（乗っ取られたホストからの被害拡大を防ぐ、攻撃者に接続機会を与えない）を添える。
- **足りないルールを追加する**：暗黙の拒否で止まっている業務通信を見つける。プロキシやメール中継サーバの名前解決（DNS）、サーバからの時刻同期（NTP）、ログ転送（syslog）などの付随通信は見落としやすい。追加するルールは送信元・宛先・サービス・動作の4項目と、挿入位置を示す。
- **順序の誤りを指摘する**：拒否したい例外が広い許可ルールより下にあると効かない（最初の一致で打ち切られる）。「〇〇のルールより上に移動する」と答える。
- **出口対策を提案する**：内部から外部への直接通信を禁止し、プロキシサーバ経由（利用者認証、URLフィルタリング、ログ記録）に限定することで、マルウェアのC&C通信を妨げ、通信記録を残す。
- **構成変更に伴うルールの見直し**：サーバの移動で同一セグメント内になった通信はFWを通らなくなるため、不要になったルールを削除する。新たにFWをまたぐ通信のルールを追加する。
- **ログから読み取る**：同一送信元から多数の宛先ポートへのSYN（ポートスキャン）、内部PCから外部への規則的な拒否（C&C通信の試み）、DMZのサーバから内部への想定外のポートへの接続（侵害されたサーバからのラテラルムーブメント）。拒否ログを残すため、最終行に明示的な拒否（ログあり）を置く。
- **NAPT環境での送信元特定**：外部に記録されるのは共通のグローバルアドレスなので、FWの変換ログと正確な時刻（NTP）で内部の端末を特定する必要がある。
- **ファイアウォールの限界を踏まえた対策**：許可したHTTPS通信内のSQLインジェクションはFWでは防げないため、WAFやアプリケーションの修正を提案する、というように、攻撃が通る層に合わせて対策を選ぶ。
