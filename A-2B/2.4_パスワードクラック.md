## 0. 全体像 ― なぜこの分野を学ぶのか

2.2 のポートスキャンで、攻撃者は「どのサービスが開いているか」を調べました。開いているポートの先に SSH（22番）や Web のログイン画面が見つかったら、攻撃者が次に試みるのは「正規の利用者としてログインすること」です。脆弱性を突くよりも、正しいユーザIDとパスワードを手に入れてしまうほうが、攻撃者にとってはずっと確実で、しかも正規のログインに紛れるので見つかりにくいからです。

**パスワードクラック**とは、OSやアプリケーションプログラムに設定されたパスワードを破ることを目的として、攻撃者が何通りものパスワードや流出したパスワードリスト等を用いてパスワードを解読したり、ログインを試行したりする手法です。本ノートは次の順で進みます。

1. **攻撃の場所**：ネットワーク越しに試すオンライン攻撃と、盗んだファイルを手元で解くオフライン攻撃の違い
2. **候補の作り方**：推測・辞書・総当たり・レインボーテーブルと、それを無力化するソルト・ストレッチング
3. **試行の軸のずらし方**：リバースブルートフォース、パスワードスプレー、パスワードリスト攻撃。ここでは**認証失敗ログの見た目**を並べ、どの攻撃がどんなログのパターンを残すかを比べます
4. **対策**：予防・防止／検知・追跡／回復の3機能（1.2 で整理した対策の4機能のうちの3つ）
5. **発展**：Windows 環境の Pass the Hash と、大量流出・不正出金の事例

パスワードクラックが成功すると、攻撃者は正規の利用者になりすますので、1.2 で学んだ付加的特性のうち**真正性**がまず損なわれ、その先で機密性（情報の窃取）・完全性（改ざん）・可用性（アカウントの乗っ取りによる利用不能）が次々に損なわれます。

科目Bの業務観点では「③利用におけるセキュリティ対策の適用」の「アカウント管理とアクセス管理」「セキュリティ監視とログ分析」と、「④インシデント管理」の「事象の評価（検知）」に直結します。科目A-2では「パスワードスプレー／リスト攻撃／辞書攻撃／総当たりの識別」と「ソルトの効果」が繰り返し出題され、科目Bでは認証ログを読んで攻撃の種類を判定させる設問が典型です。

## 1. パスワードクラックの種類と実行 ― どこで試すか

### 1.1 オンライン攻撃とオフライン攻撃

パスワードクラックには、攻撃者が「どこで」パスワードを試すかによって、次の2つの方法があります。

| 方法 | 攻撃者は何をするか | 試行できる速さ | 防御側に見えるもの |
|---|---|---|---|
| **オンライン攻撃** | ターゲットとなるシステムに、ネットワークを介して実際にログインを試みながら行う | 遅い（1回ごとに通信が必要で、ロックアウトや遅延にも阻まれる） | 認証失敗ログが大量に残る |
| **オフライン攻撃** | パスワードが保存されたファイル（通常、パスワードは暗号化やハッシュ化がされている）を何らかの手段で入手し、攻撃者のローカル環境で解読する | 非常に速い（GPUで毎秒数十億回のハッシュ計算も可能） | ファイルを盗まれた後は、防御側には何も見えない |

オンライン攻撃の実体は、ログイン画面への HTTP リクエストの繰返しです。1.4 の 7.5 で見た POST リクエストのボディに、攻撃者は候補のパスワードを入れ替えながら送り続けます。

```
POST /login HTTP/1.1
Host: www.example.jp
Content-Type: application/x-www-form-urlencoded

userid=admin&password=admin123
```

オフライン攻撃の出発点は、サーバから盗み出されたパスワードファイルやデータベースのダンプです。たとえば Linux の `/etc/shadow` は、1行が次のような形をしています（値は例示）。

```
alice:$6$Xk3pQ9vL$4fQe...（以下省略）:19996:0:99999:7:::
       │  │         └ ハッシュ値
       │  └ ソルト
       └ ハッシュ方式（6 = SHA-512 ベースの crypt）
```

攻撃者はこのファイルを手に入れれば、サーバに一度もログインせずに、手元の計算機で候補を次々にハッシュ化して一致するものを探せます。オンライン攻撃では防御側のロックアウトや監視が効きますが、オフライン攻撃ではそれらが一切効かず、防御側に残る手段は「ハッシュを解きにくくしておくこと」（2.4 のソルト・ストレッチング）だけです。この非対称性が、パスワードの保存方法が重要視される理由です。

### 1.2 パスワードクラックが有効な認証システム

パスワードクラックはその仕組み上、**固定式のパスワード**（利用者が変更するまで何回も使用可能なパスワード）による認証システムに対して有効な手法です。攻撃者がいったん正しい値を見つければ、その値は次のログインでもそのまま使えるからです。逆に、ワンタイムパスワードのように1回ごとに値が変わる方式では、攻撃者が1つの値を当てても再利用できないため、パスワードクラックはほとんど意味を成しません。

> **試験に出た!**
> 情報セキュリティスペシャリスト試験の午後Ⅰ問3で、推測によるパスワードクラックに関する問題が出題された。

## 2. 候補の作り方 ― 推測・辞書・総当たり・レインボーテーブル

攻撃者が試すパスワードの候補をどう作るかで、パスワードクラックは次の4つに分かれます。先に全体を表で見ておきましょう。

| 手法 | 攻撃者が試す候補 | 破られやすいパスワード | 主な実行形態 |
|---|---|---|---|
| 推測 | ユーザIDや利用者の情報から推測した値 | ユーザIDに酷似、生年月日など | オンライン攻撃 |
| **辞書攻撃** | 辞書ファイルに登録された文字列 | 英単語、`sys`・`temp` などの業務用語 | 通常はオフライン攻撃 |
| **ブルートフォース攻撃（総当たり攻撃）** | 特定の文字数・文字種のすべての組合せ | 短い、文字種が少ない | 通常はオフライン攻撃 |
| レインボーテーブル | 事前計算した「ハッシュ値→平文」の逆引き表 | ソルトなしで保存されたパスワード | オフライン攻撃 |

### 2.1 推測によるパスワードクラック

攻撃者は、ユーザIDや利用者の情報（氏名、誕生日、社名、ペットの名前など）からパスワードを推測し、ログインを試行します。利用者がユーザIDに酷似したパスワードや、生年月日などの分かりやすいパスワードを用いている場合、この手法によって破られる可能性が高まります。試行回数が少なくて済むので、オンライン攻撃では通常この方法が用いられます。

| 試行回数 | 入力するパスワード（例） | 結果 |
| --- | --- | --- |
| 1回目 | `admin` | × |
| 2回目 | `admin01` | × |
| 3回目 | `admin123` | ▲（一致すればログイン成功） |

*図：推測によるパスワードクラックのイメージ（ユーザID「admin」の場合）*

数回で当たる可能性があるので、アカウントロックアウト（4.1 で解説）の閾値に達する前に成功してしまうことがある点が怖いところです。

### 2.2 辞書ファイルを用いたパスワードクラック（辞書攻撃）

攻撃者は、パスワードに使われそうな文字列が大量に登録されたファイル（**辞書ファイル**）を用意し、それを順次試していきます。これを**辞書攻撃**といいます。辞書ファイルには、一般的な辞書に載っている英単語のほか、`sys`、`temp` など情報システム関連の業務の中で用いられることが多い文字列や、過去の流出事件で実際に多く使われていたパスワードが収録されています。利用者がこうした文字列をパスワードにしている場合、この手法によって破られる可能性が高まります。

辞書ファイルは数百万〜数億語に及ぶため、攻撃者はオンライン攻撃ではそれほど多くのパターンを試すことができません。そのため辞書攻撃は、通常はオフライン攻撃で用いられます。

*図：辞書ファイルを用いたパスワードクラックのイメージ*

```
辞書ファイル          攻撃者               ターゲット
 password   ─┐
 sys         ├──→ 順次照合 ──→ パスワードファイル
 temp        │                   (ハッシュ値)
 welcome    ─┘
```

辞書ファイルの中身は、単なる単語の羅列だけではありません。攻撃者のツールは「単語＋数字」「先頭を大文字に」「a を @ に置換」といった変形規則を自動で適用するので、`Password1!` や `P@ssw0rd` のような「記号を入れたつもり」のパスワードも、辞書攻撃ではすぐに破られます。

### 2.3 総当たりによるパスワードクラック（ブルートフォース攻撃）

攻撃者は、特定の文字数・文字種で設定され得るすべての組合せを試します。これを**ブルートフォース攻撃（総当たり攻撃）**と呼びます。パスワード長（**レングス**）が短く、文字種が少ない場合、この手法によって破られる可能性が高まります。辞書ファイルを用いたパスワードクラックと同様、オンライン攻撃ではそれほど多くのパターンを試すことができないため、通常はオフライン攻撃で用いられます。

> **試験に出た!**
> 情報セキュリティスペシャリスト試験の午後問題で、ブルートフォース攻撃（総当たり攻撃）に関する問題が出題された。

> **補足：組合せ数の目安**
> 使用できる文字種の数を $n$、パスワード長を $L$ とすると、総当たりで試す組合せ数は $n^L$ となる。例えば数字のみ4桁では $10^4=1$ 万通りにすぎないが、英大文字・小文字・数字（62種）の8文字では $62^8 \approx 2.18 \times 10^{14}$ 通りとなる。文字種とレングスを増やすことが、総当たり攻撃への耐性を高める。

式で書くと次のとおりです。

$$
\text{組合せ数} = n^L \qquad (n: \text{文字種の数},\ L: \text{パスワード長})
$$

指数が $L$ であることに注目してください。文字種 $n$ を増やすより、長さ $L$ を1文字増やすほうが組合せ数は大きく伸びます。たとえば62種8文字（約 $2.18 \times 10^{14}$）を62種12文字にすると $62^{12} \approx 3.2 \times 10^{21}$ となり、$62^4$ 倍、つまり約1,480万倍に増えます。近年「複雑な短いパスワードより、長いパスフレーズ」が推奨されるのはこのためです。

### 2.4 レインボーテーブルと、ソルト・ストレッチング

パスワードをハッシュ化して保存していても、同じパスワードからは必ず同じハッシュ値が出ます。たとえば `password` を MD5 でハッシュ化すると、誰が計算しても次の値になります。

```
password  →  MD5  →  5f4dcc3b5aa765d61d8327deb882cf99
```

攻撃者はこの性質を利用し、よく使われるパスワードのハッシュ値をあらかじめ計算した表を作っておきます。盗んだパスワードファイルのハッシュ値をこの表で引けば、計算せずに平文がわかります。

**レインボーテーブル**とは、ハッシュ値から平文を得るためのアルゴリズムの一つですが、当該アルゴリズムによって生成したテーブルそのもの（ハッシュ値から平文を得るための逆引き表）も意味します。単純な「全候補のハッシュ値一覧」は膨大な容量になるため、レインボーテーブルはハッシュ化と縮約（ハッシュ値を別の候補文字列に変換する処理）を交互に繰り返した「チェーン」の始点と終点だけを保存し、容量と検索時間のバランスをとっています。攻撃者は事前に生成したレインボーテーブルを用いることで、効率的にパスワードクラックを行うことが可能となります。

こうした攻撃に対しては、パスワードを保存するシステムの開発者が**ソルト（salt）**を使用するのが有効な対策になります。ソルトとは、パスワードからハッシュ値を求める際に、パスワードに付加する文字列のことです。ソルトには、ユーザごとにランダムな文字列であることと、ある程度の長さ（少なくとも20文字程度）であることが求められます。これらの要件を満たしたソルトを使用することにより、同じパスワードであっても出力されるハッシュ値が変わるため、ハッシュ値から元のパスワードを特定することが困難になります。

```
ソルトなし：同じパスワードは同じハッシュ値になる（一人が破られると全員破られる）
  alice  password  → 5f4dcc3b5aa765d61d8327deb882cf99
  bob    password  → 5f4dcc3b5aa765d61d8327deb882cf99

ソルトあり：ユーザごとにハッシュ値が変わる（値は例示）
  alice  salt=Xk3pQ9vLr2Tz...  hash(salt + password) → 9b1e0c...
  bob    salt=Mw8Jd2QaYp4n...  hash(salt + password) → 47af3d...
```

ソルトが効く理由を1文で言うと、「攻撃者が事前に作った表は特定のソルトを前提にしていないので使えなくなり、ユーザごとに一から計算し直させられるから」です。なお、ソルトは秘密にする必要はありません（上の `/etc/shadow` のようにハッシュ値の隣に平文で保存されます）。ソルトの役割は「事前計算を無意味にすること」であって、「秘密を増やすこと」ではない点に注意してください。

> **試験に出た!**
> 情報セキュリティスペシャリスト試験の午後Ⅰ問3で、ソルトを使用することによる効果について出題された。

> **補足：ストレッチング**
> ソルトと併せて、ハッシュ関数を何千回〜何万回と繰り返し適用する「ストレッチング」を行うと、1回のハッシュ計算に要する時間が長くなり、オフライン攻撃の効率をさらに低下させることができる。

ストレッチングは、正規のログイン1回あたりの計算時間が数ミリ秒増えても利用者は気づかない一方、何十億回も計算する攻撃者にとっては致命的な遅れになる、という非対称性を利用しています。実務では、ソルトとストレッチングを組み込んだパスワード保存専用の関数（bcrypt、scrypt、Argon2、PBKDF2 など）を使うのが基本です。MD5 や SHA-256 を1回かけるだけの保存方式は、ソルトがあってもGPUで高速に総当たりされるため不十分とされています。

## 3. 試行の軸をずらす攻撃 ― リバースブルートフォース・スプレー・リスト

2章の手法は、どれも「1つのユーザIDに対してパスワードを次々に変える」ものでした。これに対して防御側は、同じユーザIDで何度も失敗したらロックする**アカウントロックアウト**で対抗します。すると攻撃者は、ロックアウトに引っかからないよう「何を固定し、何を変えるか」の軸をずらしてきます。本章の3つの攻撃は、その工夫の産物です。

### 3.1 4つの攻撃の比較

| 攻撃 | 攻撃者が固定するもの | 攻撃者が変えるもの | ユーザIDあたりの失敗回数 | アカウントロックアウトの効果 |
|---|---|---|---|---|
| ブルートフォース攻撃 | ユーザID | パスワード（全組合せ） | 非常に多い | 効く |
| **リバースブルートフォース攻撃** | パスワード | ユーザID（全組合せ） | 1回程度 | 効かない |
| **パスワードスプレー攻撃** | よく使われる数個のパスワード | 多数のユーザID、攻撃元IPアドレス、試行時刻 | ロック閾値未満（数回） | 効かない（閾値未満に抑えられる） |
| **パスワードリスト攻撃** | 流出したIDとパスワードの組 | リストの行 | 1回程度（しかも成功率が高い） | 効かない |

### 3.2 認証失敗ログの見た目で見分ける

科目Bでは、ログの抜粋を見て「どの攻撃が行われたか」を答えさせる設問がよく出ます。ここでは、Webサイトの認証ログ（例示用の書式）に、それぞれの攻撃がどう現れるかを並べます。

**ブルートフォース攻撃**：同じ攻撃元から、同じユーザIDへの失敗が短い間隔で連続します。最後にロックが発動しています。

```
2026-09-30T02:14:01+09:00 login result=FAIL user=admin src=203.0.113.45
2026-09-30T02:14:01+09:00 login result=FAIL user=admin src=203.0.113.45
2026-09-30T02:14:02+09:00 login result=FAIL user=admin src=203.0.113.45
2026-09-30T02:14:02+09:00 login result=FAIL user=admin src=203.0.113.45
2026-09-30T02:14:03+09:00 login result=FAIL user=admin src=203.0.113.45
2026-09-30T02:14:03+09:00 account=LOCKED user=admin failures=5
```

SSH サーバが狙われた場合も同じ形です。Linux の認証ログ（`/var/log/auth.log` など）には、次のような行が秒単位で並びます。

```
Sep 30 02:14:01 web01 sshd[2211]: Failed password for root from 203.0.113.45 port 50122 ssh2
Sep 30 02:14:02 web01 sshd[2213]: Failed password for root from 203.0.113.45 port 50124 ssh2
Sep 30 02:14:03 web01 sshd[2215]: Failed password for invalid user oracle from 203.0.113.45 port 50126 ssh2
```

**リバースブルートフォース攻撃**：同じ攻撃元から、連番のような異なるユーザIDに1回ずつ失敗します。ログにはパスワードは記録されませんが、「ユーザIDだけが規則的に変わる」ことが特徴です。

```
2026-09-30T03:00:01+09:00 login result=FAIL user=1000234561 src=198.51.100.7
2026-09-30T03:00:01+09:00 login result=FAIL user=1000234562 src=198.51.100.7
2026-09-30T03:00:02+09:00 login result=FAIL user=1000234563 src=198.51.100.7
2026-09-30T03:00:02+09:00 login result=OK   user=1000234564 src=198.51.100.7
2026-09-30T03:00:03+09:00 login result=FAIL user=1000234565 src=198.51.100.7
```

**パスワードスプレー攻撃**：多数のユーザIDに対し、攻撃元IPアドレスを次々に変え、間隔を空けて失敗します。1つのユーザIDだけを見ると「たまに失敗する普通の利用者」に見えるのが厄介な点です。

```
2026-09-30T09:00:12+09:00 login result=FAIL user=sato     src=203.0.113.10
2026-09-30T09:17:40+09:00 login result=FAIL user=suzuki   src=198.51.100.23
2026-09-30T09:31:05+09:00 login result=FAIL user=takahashi src=192.0.2.88
2026-09-30T09:48:59+09:00 login result=OK   user=tanaka   src=203.0.113.201
2026-09-30T10:02:33+09:00 login result=FAIL user=watanabe src=198.51.100.140
    （翌日、2つ目のよく使われるパスワードで同じユーザ群を一巡する）
```

**パスワードリスト攻撃**：多数のユーザIDに1回ずつアクセスし、しかも**成功が混じる割合が不自然に高い**のが特徴です。存在しないユーザIDへの失敗（`reason=no_such_user`）が多いのは、他サイトから流出したリストをそのまま使っているためです。

```
2026-09-30T01:05:11+09:00 login result=FAIL user=k.yamada@example.com  src=203.0.113.61  reason=no_such_user
2026-09-30T01:05:11+09:00 login result=OK   user=m.ito@example.net     src=198.51.100.92
2026-09-30T01:05:12+09:00 login result=FAIL user=hanako77@example.org  src=192.0.2.140   reason=bad_password
2026-09-30T01:05:12+09:00 login result=OK   user=t.kato@example.com    src=203.0.113.18
2026-09-30T01:05:13+09:00 login result=FAIL user=aoki.j@example.jp     src=198.51.100.201 reason=no_such_user
```

見分けるための着眼点をまとめると、次のようになります。

| 着眼点 | ブルートフォース | リバースブルートフォース | スプレー | リスト |
|---|---|---|---|---|
| 1ユーザIDあたりの失敗 | 多い | 1回程度 | 数回（閾値未満） | 1回程度 |
| 攻撃元IPアドレス | 少数に集中 | 少数に集中 | 分散 | 分散（ボットネットなど） |
| 試行の間隔 | 短い | 短い | 長い（分〜日） | 短い〜中 |
| 存在しないIDへの失敗 | 少ない | 多い（連番の空き） | 少ない（事前に収集したID） | 多い |
| 成功率 | 低い | 低い | 低い | **高い**（数%に達することも） |

どの攻撃も、ユーザID単位の集計では見逃しやすく、「攻撃元IPアドレス単位」「全体の失敗率・成功率の時系列」で集計し直すと浮かび上がる、という点が共通しています。

### 3.3 リバースブルートフォース攻撃

ユーザIDを固定して何通りものパスワードの組合せを試行するブルートフォース攻撃に対し、攻撃者がパスワードを固定して何通りものユーザIDの組合せを試行する手法は、**リバースブルートフォース攻撃**と呼ばれます。

リバースブルートフォース攻撃は、パスワードの文字種やレングスが少なく（数字4桁など）、かつユーザIDの文字種やレングスも少ない（ランダムな数字10桁など）場合に成功する可能性が高まります。数字4桁の暗証番号は1万通りしかないので、利用者が多いサービスでは「`1234` を使っている誰か」が必ずいる、というのが攻撃者の読みです。

> **補足**
> リバースブルートフォース攻撃では、1つのユーザIDに対するログイン失敗は1回程度にとどまるため、ユーザIDごとの失敗回数を基準とするアカウントロックアウトでは防ぐことが難しい。同一IPアドレスからの大量のログイン試行や、全体のログイン失敗率の急増などを監視する必要がある。

### 3.4 パスワードスプレー攻撃

**パスワードスプレー攻撃**とは、攻撃者がよく用いられる数個のパスワード（`Password1`、`Summer2026!` のような季節＋年など）を用意し、それをアカウントロックがかからない範囲で複数のIDに対して試行し、不正なログインを試みる攻撃です。攻撃者は、攻撃元IPアドレスを次々に変化させたり、ログイン試行から次の試行までに時間を空けたりすることで、アカウントロックを回避しつつ、攻撃の検知も困難にします。

スプレー（噴霧）という名前のとおり、攻撃者は少数のパスワードを多数のアカウントに薄く広く吹きかけます。社員数の多い組織のクラウドサービス（メールやグループウェア）が狙われやすく、ユーザIDはメールアドレスの規則（`姓.名@example.jp`）から容易に推測されます。

### 3.5 パスワードリスト攻撃

近年、会員向けのインターネットサービスサイトでパスワードリスト攻撃による被害が多発しており、大きな問題となっています。

**パスワードリスト攻撃**とは、利用者の多くが複数のサイトで同一のユーザIDとパスワードを使い回している状況に目を付け、攻撃者が何らかの手段で不正に入手したユーザIDとパスワードのリストを流用し、それらを自動的に連続入力するプログラムなどを用いて会員向けサイトへのログインを試行する手口です。なお、パスワードリスト攻撃は別名で「**クレデンシャルスタッフィング攻撃**」とも呼ばれます。

パスワードリスト攻撃に使われるユーザIDとパスワードは、利用者のPCからではなく、会員向けサービスを提供している**別の**サイトのサーバから盗み取られます。そのため、利用者がいかにパスワードを厳重に管理していたとしても、複数のサイトで同一のパスワードを使い回している限り、この攻撃により被害を受ける可能性があります。つまり、ある会社のセキュリティ対策が万全でも、無関係な他社の漏えいによって自社の会員アカウントが乗っ取られるという、自社だけでは完結しない脅威です。

> **クレデンシャル**
> ユーザID、パスワード、メールアドレス、生体情報など、利用者の識別・認証に用いられる情報を「クレデンシャル」（クレデンシャル情報）という。

> **試験に出た!**
> 情報処理安全確保支援士試験の令和2年度午後Ⅰ問1で、スマートフォンアプリにおけるパスワードリスト攻撃（クレデンシャルスタッフィング）への対策に関する問題が出題された。

パスワードリスト攻撃への対策は、一般的なパスワードクラック対策（4章）と共通する部分と、この攻撃に特有の部分があるため、4.4 でまとめて扱います。

## 4. パスワードクラックへの対策

ここからは、1.2 で学んだ対策の機能に沿って、誰が何のために何をすべきかを整理します。

### 4.1 予防・防止

| 誰が | 何をするか | 何のために（なぜ有効か） |
|---|---|---|
| システムの設計者・管理者 | 二段階認証、二要素認証、ワンタイムパスワード方式、バイオメトリック認証システムなど、パスワードクラックが困難な認証方式を導入する | パスワードが破られても、それだけではログインできないようにするため |
| システムの管理者 | アカウントロックアウトを設定する | 同じユーザIDへの連続試行（ブルートフォース・推測）を途中で止めるため |
| 利用者（とそれを規程で求める管理者） | 推測困難なパスワードを設定し、定期的に変更する（※後述の注意を参照） | 推測・辞書攻撃・総当たりで当てられにくくするため |
| システムの開発者 | パスワードからハッシュ値を求める際にソルトを使用する | パスワードファイルが盗まれても、レインボーテーブルによる逆引きを無効にするため |
| システムの管理者 | ツールなどを用いて脆弱なパスワードをチェックし、修正する | 攻撃者より先に弱いパスワードを見つけて潰すため |
| システムの管理者 | ログインの失敗（必要に応じてログインの成功も）がログに記録されるよう設定する | 攻撃を後から検知・追跡できるようにするため（3.2 のログがなければ何も判断できない） |

> **二段階認証**
> 認証を2つの段階に分けて行う方式。例えば、パスワードによる認証の後に、登録済みの携帯電話に送信された確認コードを入力させる、など。

> **ワンタイムパスワード方式**
> ログインのたびに新たなパスワードを生成し、一度しか使用できないパスワードで認証する方式。

> **バイオメトリック認証システム**
> 指紋、静脈、虹彩、顔など、利用者本人の身体的特徴（生体情報）を用いて本人確認を行う認証システム。

> **アカウントロックアウト**
> 一定回数連続してパスワードを誤入力した場合、そのアカウントを一定時間、又は管理者が解除するまで使用不能にすること。

**二段階認証 と 二要素認証** は似ていますが別物です。二段階認証は「認証を2回に分ける」ことを指し、2回とも知識（パスワードと秘密の質問）でもよいのに対し、二要素認証は「知識・所持・生体」のうち**異なる2つの要素**を組み合わせることを指します。パスワードクラックへの耐性が本質的に高いのは二要素認証のほうです。

**定期変更についての注意**：以前は「パスワードは定期的に変更する」ことが推奨されていましたが、現在は、NIST SP 800-63B（2017年）や国内の政府機関の案内などで、**漏えいの兆候がない限り定期変更を強制しない**ことが推奨されています。定期変更を強制すると、利用者が `Password1` → `Password2` のような推測しやすい連番の変更をしたり、メモに書き残したりして、かえって安全性が下がることがわかったためです。現在の考え方は「長く推測困難なパスワードを1つ決め、サイトごとに使い分け、漏えいが判明したら直ちに変更する」です。試験で原本どおり「定期的に変更する」が選択肢に出た場合は、出題年度と文脈で判断してください。

アカウントロックアウトにも副作用があります。攻撃者がわざと他人のユーザIDで失敗を繰り返せば、正規の利用者をロックさせて使えなくする（可用性を損なう）ことができます。このため実務では、恒久的なロックではなく「一定時間のロック」や「失敗ごとに応答を遅らせる」「CAPTCHA を出す」といった段階的な方式が組み合わされます。

### 4.2 検知・追跡

| 誰が | 何をするか | 何のために |
|---|---|---|
| セキュリティ監視の担当者 | ネットワーク監視型IDS、ホスト監視型IDS、IPSを用いて検知する | 短時間に大量の認証試行があった時点で気づき、IPSなら遮断まで行うため |
| システムの管理者 | ターゲットホストのログから連続してログインに失敗している箇所を探し出し、この攻撃を検知する | 3.2 のようなパターンを見つけ、攻撃元・対象アカウント・成功の有無を特定するため |

ログを使った検知ルールは、たとえば次のような形で SIEM やログ分析基盤に設定します（疑似的な記述）。

```
# ブルートフォース：同一ユーザIDへの失敗が 5分間に 10回以上
count(result=FAIL) by user  over 5m  >= 10

# スプレー／リスト：同一攻撃元IPから 1時間に 20種類以上のユーザIDへ試行
distinct_count(user) by src over 1h  >= 20

# リスト攻撃：全体のログイン成功率が平常時から急変（失敗の急増と成功の急増の両方を見る）
ratio(result=OK) over 10m  deviates_from baseline
```

### 4.3 回復

- 攻撃を受けたホストの管理者は、当該ホスト及び当該ホストからアクセス可能なすべてのホストを対象に、データの改ざん、不正プログラムの埋込み、設定変更などの有無を徹底的に検証し、問題箇所を修復します。攻撃者は正規の権限でログインしているため、どこまで手を伸ばしたかがログインしたホストだけでは判断できないからです。状況によってはOSをクリーンインストールし、サーバ環境を再構築します。
- あわせて、管理者は予防・防止に挙げた対策を実施し、同じ手口での再侵入を防ぎます。破られたアカウントのパスワードを変更し、そのアカウントのセッションを無効化することも忘れてはいけません。

### 4.4 パスワードリスト攻撃への対策

**サイト管理者・システム管理者側の対策**：前述のパスワードクラックへの対策と同様に、二段階認証、二要素認証などの導入が有効です。流出したリストのパスワードが正しくても、2つ目の要素がなければログインできないからです。また、管理者は認証時のログを定期的に分析することにより、パスワードリスト攻撃を検知できる可能性があります。とはいえ、個々の認証要求の間隔が長く、かつ毎回異なるIPアドレスから行われているような場合には、それらを一連の攻撃としてとらえることは困難です。攻撃によって認証が成功した場合には、サイト側が端末情報の確認と注意喚起（新しい端末からのログイン通知など）を行うことで、ユーザが検知できる可能性はあります。

ログイン通知メールは、たとえば次のような文面になります。利用者がこの通知で「自分ではない」と気づけることが、検知の最後の砦になります。

```
件名：【example.jp】新しい端末からのログインがありました

2026年9月30日 01:05 に、次の環境からお客様のアカウントへのログインがありました。
  端末：Windows / Chrome
  場所（IPアドレスからの推定）：海外
お心当たりがない場合は、直ちにパスワードを変更し、サポート窓口へご連絡ください。
```

**利用者側の対策**：パスワードリスト攻撃では、ユーザIDとパスワードの組合せ自体は正しいため、サイト側では通常のログインとの区別が難しいのです。したがって利用者側の最も有効な対策は、サイトごとに異なるパスワードを設定し、使い回しをしないことです。しかし、その場合、数多くのパスワードをいかにして管理するかが課題となります。

現実的な解決策としては、利用者が表計算ソフトやテキストエディタでユーザIDとパスワードのリスト（電子ファイル）を作成し、それを暗号化したりパスワードを付与したりして、アクセス制限を施した場所に保存しておく方法があります。このとき、インターネットバンキングなど重要なサービスについては、ユーザIDのリストとパスワードのリストを別々のファイルに分けて保存しておくのが望ましいとされます。1つのファイルが盗まれても、IDとパスワードの組がそろわないようにするためです。

> **補足：パスワードマネージャ**
> 近年では、パスワードを暗号化して一元管理し、サイトごとに推測困難なパスワードを自動生成・自動入力する「パスワードマネージャ」の利用も広がっている。この場合は、パスワードマネージャ自体を保護するマスターパスワードの強度と、多要素認証の設定が重要となる。

さらに近年は、パスワードそのものを使わない**パスキー**（FIDO2/WebAuthn に基づく公開鍵方式の認証）の普及が進んでいます。パスキーではサーバに秘密情報が保存されないので、サーバから漏えいしてリストになること自体が起きず、パスワードリスト攻撃の前提が崩れます（第6章で扱います）。

## 5. Pass the Hash ― パスワードを破らずに使う

ここまでの攻撃は「パスワードの平文を当てる」ものでした。Windows環境固有のパスワード攻撃として知られる**Pass the Hash**は、その発想を逆転させ、平文を知らないままハッシュ値そのものを使ってログインします。

Windowsでは、ユーザが入力したパスワードから生成したハッシュ値が一時的にメモリ（キャッシュ）に格納される仕組みとなっています。そして Windows のネットワーク認証（NTLM 認証）は、パスワードの平文ではなくこのハッシュ値をもとに応答を計算します。内部ネットワークに侵入した攻撃者は、このキャッシュに格納されたハッシュ値を取り出して再利用することで、パスワードを破ることなく、不正なログオンを成功させることが可能です。つまり Windows の認証にとってはハッシュ値がパスワードそのものと同じ価値をもち、ソルトやストレッチングでハッシュ値を解きにくくしても、この攻撃には効きません。

```
① 攻撃者が端末Aに侵入し、管理者権限を得る
② 端末Aのメモリから Administrator のハッシュ値を取り出す
      Administrator : 500 : （NTハッシュ 32桁の16進数）
③ そのハッシュ値を使って、端末B・C・…に NTLM 認証でログオンする
      （同じパスワードなら、どの端末でも同じハッシュ値が通用する）
④ 最終的にドメインコントローラの管理者アカウントのハッシュ値を得て、ドメイン全体を掌握する
```

Active Directoryで構成された企業などのネットワークにおいて、Windows機のローカル管理者アカウントである「Administrator」に同一のパスワードを設定している場合があります。このような環境で、Pass the HashによってAdministratorのパスワードから生成されたハッシュ値が攻撃者の手にわたったとすれば、ネットワーク内のWindows機が次々と陥落することになります。この「内部で横に広がる」動きを**ラテラルムーブメント（横展開）**と呼び、2.9 のマルウェアや標的型攻撃で再び登場します。

> **補足：主な対策**
>
> - ローカル管理者アカウントのパスワードを端末ごとに異なるものにする（Microsoft LAPS などの活用）
> - 管理者権限を持つアカウントの利用を必要最小限にする
> - 認証情報をメモリ上から窃取されにくくする機能（Credential Guard など）を有効にする

これらの対策は、誰が何のために行うかを言葉にすると次のようになります。端末の管理者は、1台のハッシュ値が他の端末で通用しないように、LAPS でローカル管理者のパスワードを端末ごとにランダム化すべきです。システムの管理者は、侵入された端末のメモリに強い権限のハッシュ値が残らないように、ドメイン管理者アカウントで一般の端末にログオンしない運用（1.2 の最小権限の原則）を徹底すべきです。そして端末の管理者は、管理者権限を奪われてもハッシュ値を読み出されないように、Credential Guard を有効にしておくべきです。

## 6. 事例に学ぶ ― 大量流出と不正出金

### 6.1 サイバー攻撃を助長するクレデンシャル情報の大量流出

2018年10月頃から、「Collection #1」をはじめとする延べ27億件のデータセットが海外のハッキングフォーラムに掲載されていることが確認されました（広く報じられたのは2019年1月です）。その後、同系のデータセット（Collection #2〜#5）も相次いで確認されました。これらには過去に各種サイトから流出したメールアドレスとパスワードの組合せが大量に含まれており、パスワードリスト攻撃などのサイバー攻撃に悪用されるおそれがあります。

こうしたクレデンシャル情報の大量流出は、パスワードの使い回しをしている利用者にとって特に大きな脅威となります。攻撃者から見ると、流出リストは「当たる確率の高い辞書」であり、3.5 のパスワードリスト攻撃の燃料そのものです。サイトの管理者は、会員が登録しようとしたパスワードが既知の流出パスワードに含まれていないかを照合し、含まれていれば登録を拒否する、という対策をとることもできます。

### 6.2 相次ぐ不正ログイン・不正出金等の被害とその要因

2020年9月、大手携帯電話会社が提供する電子マネー決済サービスで、攻撃者が不正に当該サービスの口座を開設した上で他人の銀行口座を紐づけ、預金を引き出す行為が多発しました。携帯電話の契約者でなくともメールアドレスのみで電子マネー決済口座を開設できたことや、一部の金融機関において、当該電子マネー決済口座と銀行口座の紐づけ時に十分な本人確認を行っていなかったことが、不正行為を誘発したとされています。

また、上記と同時期に大手ネット証券会社では、悪意のある第三者が偽造した本人確認書類を利用する等して実在の顧客と同姓同名の銀行口座を開設した上で、何らかの手段で入手したネット証券サービスのユーザID・パスワード等を用いてログインし、出金先の銀行口座を変更して不正に出金するという事件が発生しました。このケースでは、発生当時のサービス仕様としてユーザIDやパスワードが最低6文字で設定可能であり、英文字の大文字と小文字の区別もなかったことから、認証情報が推測された可能性もあります。

こうした事例のように、不正ログイン・不正出金等の被害が発生する大きな要因として、サービス仕様やシステム仕様における脆弱さが挙げられます。例えば、次のような仕様となっているサービス/システムは、第三者により不正利用されるリスクが高いと思われます。右列は、その仕様が本ノートのどの攻撃を助けるかの対応です。

| 不正利用されるリスクが高い仕様 | その仕様が助ける攻撃・不正 |
|---|---|
| アカウントの登録時、銀行口座との紐づけ時等に十分な本人確認を行っていない | 他人名義の口座開設・紐づけ |
| 二段階認証/多要素認証を実装していない | すべてのパスワードクラック |
| ユーザIDがメールアドレス | パスワードリスト攻撃（流出リストのIDがそのまま使える）、スプレー |
| ユーザIDが数字のみ | リバースブルートフォース攻撃 |
| パスワードの最低文字数が少ない | 総当たり・推測 |
| パスワードで使用できる文字種が少ない | 総当たり（$n^L$ の $n$ が小さい） |
| ログイン試行回数の制限がない | ブルートフォース・辞書攻撃（オンライン） |
| 使用できる端末の制限がない（複数の端末から自由に利用可能） | 攻撃者の端末からのログイン |
| 商品購入、送金等の処理を行う際に再認証する必要がない | 乗っ取り後の不正出金 |
| 新たな端末からの利用があっても通知されない | 利用者による検知の遅れ |
| 口座情報やメールアドレス等の変更があっても通知されない | 出金先の変更に気づけない |
| 不正ログイン/不正利用の可能性がある事象について監視していない | 事業者による検知の遅れ |

サービスを企画・設計する立場の支援士は、この一覧を要件定義のチェックリストとして使えます。「重要な操作（送金・出金先変更・メールアドレス変更）の直前には再認証を求め、変更したら旧連絡先にも通知する」という設計は、パスワードが破られた後の被害を食い止める最後の防御線です。

## 7. 確認問題

### 7.1 理解度チェック

- 【Q1】パスワードクラックはどのような認証システムに対して有効か。
- 【Q2】パスワードクラックの予防・防止のための対策としては何が有効か。
- 【Q3】パスワードクラックを検知するにはどのような方法があるか。
- 【Q4】パスワードスプレー攻撃とは何か。
- 【Q5】パスワードリスト攻撃とは何か。
- 【Q6】パスワードリスト攻撃への対策について述べよ。
- 【Q7】Pass the Hashと呼ばれる攻撃手法について説明せよ。

> **ヒント**
> Q1は1.2、Q2・Q3は4.1・4.2、Q4は3.4「パスワードスプレー攻撃」、Q5・Q6は3.5・4.4、Q7は5章「Pass the Hash」を参照。

**解答例**

- Q1：固定式のパスワード（変更するまで何回も使用可能なパスワード）による認証システム。攻撃者が一度当てた値を繰り返し使えるため。
- Q2：二段階認証・二要素認証・ワンタイムパスワード・バイオメトリック認証の導入、アカウントロックアウトの設定、推測困難なパスワードの設定、ソルトの使用、脆弱なパスワードのチェック、ログイン失敗（必要に応じて成功）のログ記録。
- Q3：ネットワーク監視型IDS・ホスト監視型IDS・IPSで検知する。ターゲットホストのログから連続したログイン失敗を探し出す。
- Q4：よく用いられる数個のパスワードを、アカウントロックがかからない範囲で複数のIDに対して試行する攻撃。攻撃元IPアドレスを変え、試行間隔を空けて、ロックと検知を回避する。
- Q5：他のサイトから不正に入手したユーザIDとパスワードのリストを流用し、使い回しを狙って自動的にログインを試行する攻撃（クレデンシャルスタッフィング）。
- Q6：サイト側は二段階認証・二要素認証の導入、認証ログの定期的な分析、新しい端末からのログイン通知。利用者側はサイトごとに異なるパスワードを設定し、パスワードマネージャ等で管理する。
- Q7：Windowsのメモリにキャッシュされたパスワードのハッシュ値を攻撃者が取り出して再利用し、パスワードを破ることなく不正にログオンする攻撃。

### 7.2 問1

Pass the Hash攻撃はどれか。

- ア パスワードのハッシュ値から導出された平文パスワードを使ってログインする。
- イ パスワードのハッシュ値だけでログインできる仕組みを悪用してログインする。
- ウ パスワードを固定し、利用者IDの文字列のハッシュ化を繰り返しながら様々な利用者IDを試してログインする。
- エ ハッシュ化されずに保存されている平文パスワードを使ってログインする。

〔情報処理安全確保支援士試験〕

**解答・解説**

Windowsでは、ユーザが入力したパスワードから生成したハッシュ値が一時的にメモリ（キャッシュ）に格納される仕組みとなっている。Pass the Hashは、このキャッシュに格納されたハッシュ値を取り出して再利用することで、パスワードを破ることなく不正なログインを成功させる攻撃であり、パスワードのハッシュ値のみでログインできる仕組みを悪用したものである。したがって**イ**が正解。

なお、アはハッシュ値を解読して平文を得るオフライン攻撃（レインボーテーブルなど）、ウはリバースブルートフォース攻撃に近い記述、エは平文保存という保存方法の不備を突くもので、いずれも Pass the Hash ではない。

### 7.3 問2

パスワードスプレー攻撃に該当するものはどれか。

- ア 攻撃対象とする利用者IDを一つ定め、辞書及び人名リストに掲載されている単語及び人名並びにそれらの組合せを順にパスワードとして入力して、ログインを試行する。
- イ 攻撃対象とする利用者IDを一つ定め、パスワードを総当たりして、ログインを試行する。
- ウ 攻撃の時刻と攻撃元IPアドレスとを変え、かつ、アカウントロックを回避しながらよく用いられるパスワードを複数の利用者IDに同時に試し、ログインを試行する。
- エ 不正に取得したある他のサイトの利用者IDとパスワードとの組みの一覧表を用いて、ログインを試行する。

〔情報処理安全確保支援士試験・令和4年度秋期〕

**解答・解説**

パスワードスプレー攻撃とは、よく用いられる数個のパスワードを用意し、それをアカウントロックがかからない範囲で複数のIDに対して試行し、不正なログインを試みる攻撃である。攻撃元IPアドレスを次々に変化させたり、ログイン試行から次の試行までに時間を空けたりすることで、アカウントロックを回避しつつ、攻撃の検知も困難にする。したがって**ウ**が正解。

なお、アは辞書攻撃、イはブルートフォース攻撃（総当たり攻撃）、エはパスワードリスト攻撃の説明である。

## 8. 試験対策まとめ（重要ポイント）

### 8.1 知識の確認（科目A-2向け）

- **オンライン攻撃 と オフライン攻撃**：ネットワーク越しに実際にログインを試すか、盗んだパスワードファイルを手元で解くか。辞書攻撃・総当たりは「通常はオフライン」、推測は「オンライン」。
- **パスワードクラックが有効なのは固定式パスワード**：ワンタイムパスワードには効かない。
- **組合せ数は $n^L$**：数字4桁は1万通り、62種8文字は約 $2.18 \times 10^{14}$ 通り。長さを伸ばす効果が大きい。
- **ソルトの効果**：同じパスワードでもハッシュ値が変わり、レインボーテーブル（事前計算した逆引き表）が使えなくなる。ユーザごとにランダム、ある程度の長さ。ソルトは秘密でなくてよい。
- **ストレッチング**：ハッシュを何千〜何万回繰り返し、オフライン攻撃の1回あたりのコストを上げる。
- **攻撃の識別（最頻出）**：ID固定でパスワードを変える＝ブルートフォース／パスワード固定でIDを変える＝リバースブルートフォース／よく使われる数個のパスワードを多数のIDへ、IPと時刻を変えてロック回避＝スプレー／他サイトの流出リスト＝パスワードリスト（クレデンシャルスタッフィング）。
- **アカウントロックアウトが効かない攻撃**：リバースブルートフォース、スプレー、リスト。IDあたりの失敗が少ないため。
- **二段階認証 と 二要素認証**：段階を分けるか、異なる要素（知識・所持・生体）を組み合わせるか。
- **Pass the Hash**：ハッシュ値だけでログインできる仕組みを悪用。平文を解読するわけではない。対策は LAPS・管理者権限の最小化・Credential Guard。
- **定期変更の扱い**：以前は推奨されていたが、現在は漏えい時以外の強制変更は推奨されない（NIST SP 800-63B）。

### 8.2 記述式で問われる観点（科目B向け）

- **ログから攻撃を特定する**：「同一IDへの短時間の連続失敗」→ブルートフォース、「多数のIDに1回ずつ、IPと時刻を分散」→スプレー、「多数のIDに1回ずつで成功率が高い、存在しないIDが混じる」→パスワードリスト攻撃、のように**根拠となるログの特徴**と**攻撃名**をセットで書く。
- **対策が効かない理由を説明する**：「パスワードリスト攻撃では、IDとパスワードの組が正しいため、アカウントロックアウトでは防げない」「スプレー攻撃では、IDあたりの失敗回数がロックの閾値未満に抑えられる」のように、攻撃の性質と対策の前提のずれを1文で述べる。
- **有効な対策を主語つきで提案する**：「サイト運営者は、流出したパスワードが正しくてもログインできないように、二要素認証を導入する」「開発者は、パスワードファイルが漏えいしても解読されにくいように、ユーザごとのソルトとストレッチングを用いてハッシュ化する」。
- **検知の集計軸を変える**：ユーザID単位だけでなく、攻撃元IPアドレス単位・全体の失敗率／成功率の時系列で監視すべきと指摘する。
- **乗っ取り後の被害を抑える設計**：重要操作時の再認証、新しい端末からのログインや登録情報変更の通知。事例の仕様の欠陥（ユーザIDがメールアドレス、試行回数制限なし等）を指摘し、改善策を示す。
- **横展開の防止**：Pass the Hash の事例では「ローカル管理者のパスワードが全端末で同一だったこと」を原因として指摘し、LAPS による端末ごとのパスワード化を提案する。
