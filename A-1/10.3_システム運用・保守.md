# レクチャーノート：サービスマネジメント・開発技術 ― システム運用・保守

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「サービスマネジメント」＞「サービスマネジメント」・「開発技術」＞「ソフトウェア開発管理技術」（システムの運用、保守、開発管理・アジャイル実践）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

前回のノート（システム構築の関連知識）では、開発を管理し、出来上がったシステムを監査・統制する視点を見ました。本ノートでは、システムが実際に稼働し始めた後の世界、すなわち日々の運用・保守と、それを支える開発管理の実践的な知識を扱います。「作って終わり」ではなく、「作った後どう動かし続けるか」という、システムのライフサイクルの後半を見る回です。

本ノートは、次の4段階のストーリーで説明します。①まず、稼働中のシステムを日々どう運用するか（コスト・資源・設備の管理）を見ます。②次に、システムやソフトウェアをどう保守し続けるかを学びます。③さらに、ソフトウェア開発を組織としてどう標準化し、成果物の権利をどう管理するかを見ます。④最後に、近年主流のアジャイル開発を実際にどう実践するか、その具体的な用語群を扱います。

本分野はサービスマネジメント・開発技術にまたがる標準レベルの分野です。用語数は多いものの、名称と特徴の対応を問う識別問題が中心であるため、それぞれの用語が「運用」「保守」「開発管理」のどの局面に位置づけられるかを意識しながら整理すると学習効率が高まります。

## 1. 稼働中のシステムをどう運用するか

まず、システムが本番稼働している間、日々どのように管理していくかを見ていきます。

### 1.1 コストをどう管理するか

**TCO（総所有コスト）**とは、システムの導入費用だけでなく、その後の運用・保守・廃棄までを含めた、システムを保有する全期間の総費用を捉える考え方です。初期費用の安さだけでシステムを選ぶと、運用段階で想定外のコストがかさむことがあるため、この総費用の視点が重視されます。運用段階では、**予実管理**（あらかじめ立てた予算と、実際にかかった費用（実績）を比較し、差異を管理する活動）や、**原価管理と配賦・課金**（システムの運用コストを利用部門ごとに配分し、利用実績に応じて費用を負担させる仕組み）によって、このコストを継続的にコントロールします。

### 1.2 何を管理するか ― 資源管理

システムを構成する資源は、種類ごとに管理する必要があります。

- **ハードウェア資源管理**：サーバや端末などの機器を、台帳等で把握・管理する。
- **ソフトウェア資源管理**：導入しているソフトウェアのバージョンやライセンス状況を管理する。
- **データ資源管理**：システムが扱うデータの所在や状態を管理する。
- **ネットワーク資源管理**：回線や通信機器の構成・状態を管理する。

こうした資源の管理を支える具体的な仕組みとして、**JCL（Job Control Language）**（コンピュータにジョブの実行順序や使用する資源を指示するための制御言語）があります。また、運用管理のベストプラクティスを体系化した**ITIL（IT Infrastructure Library）**は、資源管理を含むIT サービス全体の運用管理の指針として広く参照されています。

### 1.3 機器・ソフトウェアをどう手に入れるか

システムを構成するハードウェア・ソフトウェアの入手方法にも選択肢があります。

- **買取り**：資産として取得し、自社で保有する方法。取得費用は一度に費用化せず、**減価償却**（資産の取得費用を、耐用年数にわたって規則的に費用配分する会計処理）によって数年にわたり費用計上します。
- **レンタル**：所有権を貸主に残したまま、使用料を払って一定期間借りる方法。買取りのような減価償却の手続きは不要です。

買取りが「自社で保有し、時間をかけて費用化する」方法であるのに対し、レンタルは「保有せず、都度の使用料として費用化する」方法であるという対比で整理すると理解しやすくなります。

### 1.4 利用者を支える体制

運用中のシステムを利用者側から支える体制も欠かせません。**ヘルプデスク**は、利用者からの問い合わせや障害報告を受け付け、一次対応や関係部署への取次ぎを行う窓口です。**ユーザ管理**は、システムの利用者情報（アカウントや権限）を管理する活動で、これまでのノートで扱ったアクセス管理の実務的な運用面にあたります。サービスの提供者と利用者の間で、提供するサービスの品質水準（応答時間、稼働率など）をあらかじめ取り決めた合意書が**SLA（サービスレベル合意書）**で、運用段階でその水準が守られているかを測る基準になります。

### 1.5 設備を守る

物理的な設備の管理も運用の重要な要素です。**設備管理**とは、電源設備や空調設備といった物理的な設備を管理する活動です。特に電源に関しては、次の装置がよく使われます。

| 装置 | 役割 |
|---|---|
| **UPS（無停電電源装置）** | 停電時に、一定時間バッテリーから電力を供給し続ける |
| **CVCF（定電圧定周波数装置）** | 電圧・周波数の変動を吸収し、安定した電力を供給する |
| **AVR（自動電圧調整器）** | 入力電圧の変動を自動的に補正し、一定の電圧を保つ |

UPSが「電源が止まらないようにする（停電対策）」ことに主眼を置くのに対し、CVCFとAVRは「電源の質を安定させる（電圧・周波数対策）」ことに主眼を置くという役割の違いで整理すると区別しやすくなります。

## 2. システム・ソフトウェアをどう保守するか

運用と並行して、システムやソフトウェアを維持し続けるための活動が保守です。

### 2.1 いつ保守するか ― 保守形態

保守は、障害が起きる前か後かによって、大きく2つに分かれます。

- **予防保守**：障害が起きる前に、計画的に行う保守。
  - **日常保守**：日々のルーチンとして行う点検。
  - **定期保守**：一定周期で行う、まとまった点検・整備。
  - **ツールレス保守**：特別な工具を使わずに部品交換などができるよう、あらかじめ設計面で工夫された保守。
- **事後保守**：障害が発生した後に行う保守。
  - **臨時保守**：予定外に発生した障害への対応。
  - **緊急保守**：特に緊急性の高い障害への対応。

### 2.2 どのように保守するか ― 保守方法

保守を実施する方法にも工夫があります。**活性保守**とは、システムを停止させることなく、稼働させたまま行う保守です。**遠隔保守**とは、保守員が現地に赴かず、遠隔から行う保守です。この活性保守を実現する基盤の一つが**フォールトトレラントコンピュータ**で、構成要素を冗長化することで、一部に障害が発生してもシステム全体としては機能を維持し続けるよう設計されたコンピュータです。

### 2.3 ソフトウェアの保守を分類する

ソフトウェアの保守は、修正作業・変更作業・改良作業といった大枠のもと、国際規格をもとにした**JIS X 0161**によって、目的別に次の4種類に分類されます。

| 分類 | 内容 |
|---|---|
| **是正保守** | 発見された不具合を修正する（事後保守に相当） |
| **予防保守** | 将来問題になりうる潜在的な欠陥を、顕在化する前に修正する |
| **適応保守** | OSやハードウェアなど、稼働環境の変化に対応する |
| **完全化保守** | 性能向上や使い勝手の改善など、機能そのものを向上させる |

是正保守が2.1節の事後保守に対応し、予防保守が2.1節の予防保守に対応する一方、適応保守・完全化保守は障害の有無にかかわらず行われる保守という点で、単純な事前・事後の区分とは異なる軸を持つ点に注意が必要です。

### 2.4 バックアップの方式

データを失わないための備えとして、バックアップの取り方にも複数の方式があります。

| 方式 | バックアップの範囲 | 特徴 |
|---|---|---|
| **フルバックアップ方式** | すべてのデータ | 復元は簡単（1つのバックアップで済む）だが、取得に時間・容量がかかる |
| **差分バックアップ方式** | 直近のフルバックアップ以降に変更されたデータすべて | 復元にはフルバックアップ＋最新の差分1つが必要 |
| **増分バックアップ方式** | 前回のバックアップ以降に変更されたデータのみ | 取得は最速・最小だが、復元にはフル＋すべての増分が必要で時間がかかる |

3方式は「バックアップにかかる時間・容量」と「復元にかかる手間」がちょうど逆のトレードオフになっている点が試験でも問われる着眼点です。

### 2.5 特に緊急性の高い保守

**緊急保守**は2.1節で見た事後保守の一区分ですが、システムの停止など事業への影響が大きい障害に対して、通常の手続きを待たず即座に対応する保守として、特に重要視されます。

## 3. 開発をどう標準化し、権利をどう守るか

個々のプロジェクトの開発管理から、組織全体で開発の進め方を標準化する視点、そして成果物の権利をどう管理するかという視点に移ります。

### 3.1 開発体制の工夫 ― クロス開発

**クロス開発**とは、実際にソフトウェアが動作する環境（ターゲット環境）とは異なる、より高性能な環境（ホスト環境）でソフトウェアを開発する方式です。組込みシステムのように、対象の実行環境の性能や表示・入力手段に制約がある場合によく用いられます。

### 3.2 開発プロセスの成熟度を測る

組織のソフトウェア開発プロセスがどれだけ確立されているかを評価する代表的なモデルが**CMM（能力成熟度モデル）**です。前回のノートで扱ったプロセスアセスメントを実際に行うための、具体的な評価モデルの一つとして位置づけられます。CMMのうち、特にソフトウェア開発に焦点を当てたものを**SW-CMM**と呼び、これをソフトウェアに限らずシステム開発全般に拡張・統合した後継モデルが**CMMI**です。CMM→SW-CMM（対象を絞った特化）、CMM→CMMI（対象を広げた統合発展）という、2方向への展開として整理すると理解しやすくなります。

### 3.3 開発プロセスを標準化する ― SLCPと共通フレーム

**SLCP（ソフトウェアライフサイクルプロセス）**とは、ソフトウェアの企画から廃棄までの一連の工程を、共通の用語・区分で標準化した国際規格です。これを日本の実情に合わせて整備し、ソフトウェアの取引・開発における共通の指針としたものが**共通フレーム**です。共通フレームでは、工程を次の3つの階層で段階的に詳細化します。

- **プロセス**：最も大きな活動のまとまり。
- **アクティビティ**：プロセスを構成する個々の活動。
- **タスク**：アクティビティをさらに詳細化した、具体的な作業。

プロセスが最上位、アクティビティがその内訳、タスクがさらにその内訳という包含関係として押さえておきます。

### 3.4 成果物をどう保護するか ― 知的財産とライセンスの管理

開発した成果物を組織的に保護する活動として、**知的財産権管理**（著作権・特許権などの権利を適切に管理する活動）と**ライセンス管理**（ソフトウェアの利用許諾の契約内容や利用状況を管理する活動）があります。こうした組織的な権利管理を、技術的に裏付ける仕組みとして、コンテンツの著作権保護技術も押さえておきます。

- **AACS**：Blu-ray Discなどで使われる、コンテンツの不正コピーを防ぐ著作権保護技術。
- **CPRM**：DVD-RAMなどの記録メディアで使われる著作権保護技術。

AACSとCPRMは、いずれも記録メディアにおけるコンテンツ保護技術であり、対象とするメディアの違いで区別します。知的財産権管理・ライセンス管理という組織的な仕組みを実現する、技術的な手段の一例として位置づけられます。

## 4. アジャイル開発をどう実践するか

前回までのノートで、アジャイル開発の基本的な考え方とXPのプラクティスに触れました。本節では、その実践に使われる具体的な用語群を、スクラムを中心にまとめて整理します。

### 4.1 アジャイル開発を支える基本思想

**アジャイル開発**の価値観を明文化したものが**アジャイル宣言（アジャイルソフトウェア開発宣言）**で、「プロセスやツールよりも個人と対話を」といった4つの価値表明から成ります。こうした価値観に基づく具体的な実践項目の総称を**プラクティス**と呼び、前回のノートで扱ったペアプログラミングやリファクタリングもその一つです。プロジェクトの開始時には、目的・背景・リスクなどをチーム全員で共有するための一連の資料である**インセプションデッキ**を作成し、プロジェクトの方向性をそろえます。

### 4.2 ペアプログラミングの役割分担

前回のノートで扱ったペアプログラミングでは、キーボードを操作して実際にコードを書く役割を**ドライバ**、隣でコードを確認し助言する役割を**ナビゲータ**と呼びます。この2つの役割を短い間隔で高速に交代しながら進める形式を、特に**ピンポンプログラミング**と呼びます。チームの状態を可視化する工夫として、作業の計画・進捗をボードに書き出して共有する**プランニングボード**や、メンバーがその日の気分を表情（顔マーク）で記録して共有する**ニコニコカレンダー**も使われます。

### 4.3 スクラムの基本サイクル

**スクラム**は、アジャイル開発の代表的なフレームワークの一つで、短い期間（**イテレーション**、スクラムでは特に**スプリント**と呼びます）を繰り返しながら開発を進めます。毎日決まった時間に短時間行う進捗共有のミーティングを**日次スクラム**、1回のスプリントの終わりにチームの進め方を振り返り改善点を話し合う場を**レトロスペクティブ**と呼びます。作業の状態を可視化する道具として、タスクの進み具合をボード上で管理する**タスクボード**（作業の流れの制御という考え方に由来するものは特に**カンバン**と呼ばれます）があり、残作業量が時間とともにどう減っていくかを示すグラフを**バーンダウンチャート**と呼びます。

チームの生産性・見積もりに関する用語も押さえておきます。**ユーザストーリー**は、利用者の視点からシステムに求める機能を簡潔な文章で表現したもので、その規模・複雑さを相対的に見積もる単位が**ストーリーポイント**です。1回のスプリントでチームが実際に完了できた作業量（ストーリーポイントの合計の実績値）を**ベロシティ**と呼び、次回以降のスプリントでどれだけの作業を計画できるかの目安に使われます。

### 4.4 プロジェクトの構成と成果物

スクラムでは、次のような役割と成果物によってプロジェクトが構成されます。

| 用語 | 内容 |
|---|---|
| **スプリント** | 開発を繰り返す一定期間の単位（4.3節のイテレーションのスクラムでの呼称） |
| **プロダクトオーナ** | プロダクトの価値を最大化する責任を持ち、要求の優先順位を決める役割 |
| **アジャイルコーチ** | チームがアジャイルの考え方・プラクティスを適切に実践できるよう支援する役割 |
| **インクリメント** | 1回のスプリントで完成した、実際に動作する成果物の積み上げ |
| **プロダクトバックログ** | プロダクトに必要な要求・機能を、優先順位付けして並べた一覧 |
| **スプリントバックログ** | 1回のスプリントで取り組むと決めた作業の一覧（プロダクトバックログから抜粋） |

プロダクトバックログが「プロダクト全体」の要求一覧であるのに対し、スプリントバックログは「1回のスプリント分」に絞った作業一覧であるという範囲の違いが、両者を区別する着眼点です。

### 4.5 その他のアジャイル手法

機能（フィーチャ）の単位で計画・設計・開発を繰り返すアジャイル開発の手法を**フィーチャ駆動開発**（**ユーザ機能駆動開発**とも呼ばれます）と呼びます。スクラムが反復の「進め方の骨組み」に主眼を置くのに対し、フィーチャ駆動開発は「利用者にとっての価値の単位（機能）」に主眼を置いて開発を進めるという特徴があります。

## 5. 試験対策まとめ（重要ポイント）

- **TCO**：初期費用だけでなく、運用・保守・廃棄までを含めた総費用で捉える考え方。
- **フルバックアップ方式 と 差分バックアップ方式 と 増分バックアップ方式**：バックアップにかかる時間・容量と、復元にかかる手間が逆のトレードオフになる関係を押さえる。
- **是正保守 と 予防保守 と 適応保守 と 完全化保守**：JIS X 0161が定めるソフトウェア保守の4分類。障害対応か、環境変化・機能向上への対応かを区別する。
- **UPS と CVCF／AVR**：電源が止まらないようにするか、電源の質（電圧・周波数）を安定させるかという役割の違い。
- **CMM と SW-CMM と CMMI**：ソフトウェアに特化した展開（SW-CMM）と、対象を広げた統合発展（CMMI）という2方向の系譜。
- **プロセス と アクティビティ と タスク**：共通フレームにおける工程の階層関係（大→中→小）。
- **プロダクトバックログ と スプリントバックログ**：プロダクト全体の要求一覧か、1スプリント分に絞った作業一覧かという範囲の違い。
- **ドライバ と ナビゲータ**：ペアプログラミングにおける役割分担。コードを書く側か、確認・助言する側か。
- **ベロシティ と ストーリーポイント**：チームの生産性の実績値か、個々の作業規模の見積もり単位かという違い。
- **AACS と CPRM**：いずれもコンテンツの著作権保護技術だが、対象とする記録メディアで区別する。
