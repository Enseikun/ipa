# レクチャーノート：開発技術 ― システム開発技術＞テスト・レビューの技法

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「開発技術」＞「システム開発技術」（実装・構築、統合・テスト、品質保証）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

前回のノート（要求分析・設計技法）では、要求をどうモデル化し、どう設計構造に落とし込むかを見てきました。しかし、設計どおりに作られたつもりのソフトウェアが、本当に正しく動くとは限りません。本ノートでは視点を「作る」から「確かめる」へと移し、作られたソフトウェアの欠陥をどう見つけ、どう管理し、どう品質として保証するかを扱います。

本ノートは、次の3段階のストーリーで説明します。①まず、プログラムを実際に動かして欠陥を見つけるテスト技法を学びます。②次に、プログラムを動かさずに、人の目で成果物を確認するレビュー手法を見ます。③最後に、テストやレビューの結果をどう数値的に管理し、ソフトウェア全体の品質をどう定義・保証するかを扱います。

テスト・レビューの技法は情報処理安全確保支援士試験の科目A-2では出題数こそ多くない中優先分野ですが、ホワイトボックステストの網羅基準やブラックボックステストの手法名は、名称と特徴の対応を問う定番の識別問題として繰り返し出題されます。また、ファジングやリグレッションテストは、前回までのノートで扱ったセキュリティ・開発工程の知識ともつながる複合的な論点であり、実務プロセスとして理解しておくことが得点効率を高めます。

---

## 1. プログラムを動かして確かめる ― テスト技法

まず、プログラムを実際に実行しながら欠陥を見つけ出す、テスト技法の全体像を見ていきます。

### 1.1 仕様から確かめる ― ブラックボックステスト

**ブラックボックステスト**とは、プログラムの内部構造（ロジック）を一切見ずに、入力に対して仕様どおりの出力が得られるかどうかだけに着目してテストケースを作成する技法です。代表的な手法は次のとおりです。

| 手法 | 内容 |
|---|---|
| **同値分割** | 入力値を「同じ結果になるはずの集合（同値クラス）」に分け、各集合から代表値を選んでテストする |
| **限界値分析** | 同値クラスの境界（限界値）付近で不具合が起きやすいという経験則に基づき、境界値を重点的にテストする |
| **因果グラフ** | 入力条件（原因）と出力結果（結果）の関係をグラフ化し、それをもとに網羅的なテストケースを導出する |
| **エラー推測** | テスト担当者の経験や勘に基づき、不具合が起きそうな箇所を推測してテストケースを作る |

同値分割では、正しい入力値の集合を**有効同値クラス**、誤った入力値の集合を**無効同値クラス**と呼び、それぞれから最低1つずつ代表値を選ぶのが基本です。同値分割と限界値分析はどちらも入力値の分類に着目する点で共通しますが、同値分割が「集合の内側の代表値」を選ぶのに対し、限界値分析は「集合と集合の境目」を狙うという着眼点の違いで区別します。

### 1.2 内部構造から確かめる ― ホワイトボックステスト

**ホワイトボックステスト**とは、プログラムの内部構造に着目し、命令や分岐をどこまで実行したかという網羅の基準に基づいてテストケースを作成する技法です。網羅基準は、次のように厳密さの度合いで整理されます。

| 網羅基準 | 内容 |
|---|---|
| **命令網羅** | プログラム中のすべての命令を、少なくとも1回は実行する |
| **判定条件網羅** | すべての分岐（判定）について、真・偽の両方を少なくとも1回は通過する |
| **条件網羅** | 判定を構成する個々の条件式について、真・偽の両方を少なくとも1回はとる（判定全体の真偽は保証しない） |
| **判定条件/条件網羅** | 判定条件網羅と条件網羅を同時に満たす |
| **複数条件網羅** | 判定を構成する複数条件のすべての組み合わせを網羅する |

これらは、命令網羅を最も緩やかな基準として、判定条件網羅・条件網羅を経て、複数条件網羅に至るほど厳密さが増していく発展の関係として整理すると理解しやすい論点です。特に、判定条件網羅と条件網羅はどちらも「真偽の両方を確認する」という点で似ていますが、対象が「判定全体」か「個々の条件式」かという違いがあり、混同しやすいため注意が必要です。

### 1.3 中間的な視点と特殊なテスト

ブラックボックス・ホワイトボックスという2つの視点の中間や、特定の目的に特化したテストの考え方もあります。

**グレーボックステスト**とは、内部構造についてある程度の知識を持ったうえで、ブラックボックステストのように入出力に着目してテストを行う手法です。ブラックボックステストとホワイトボックステストの中間的な位置づけとして整理できます。

**ファジング**とは、想定外の値や不正な形式のデータ（ファズ）を大量に、機械的に入力し、プログラムが異常終了したり、想定外の挙動を示したりしないかを確認する手法です。前回までのノートで扱ったセキュリティ分野のペネトレーションテストと同様、脆弱性の検出を目的として用いられる、セキュリティテストの一種として位置づけられます。

**負荷テスト**とは、システムが想定する最大の利用量やそれを上回る負荷をかけ、性能が劣化しないか、あるいは処理が破綻しないかを確認するテストです。個々の機能が仕様どおりかを見る1.1節・1.2節のテストとは異なり、非機能要件（性能・耐久性）を確認するテストとして位置づけられます。

### 1.4 モジュールをどう組み合わせてテストするか ― ソフトウェア統合テスト

個々のモジュールを単体でテストしたあとは、モジュール同士を結合しながらテストを進めます。結合の順序によって、次の3つの方式に分かれます。

| 方式 | 進め方 | 必要な代用品 |
|---|---|---|
| **トップダウンテスト** | 上位モジュールから先に結合していく | 未実装の下位モジュールの代わりとなる**スタブ** |
| **ボトムアップテスト** | 下位モジュールから先に結合していく | 未実装の上位モジュールの代わりとなる**ドライバ** |
| **サンドイッチテスト** | 上位・下位の両方向から同時に結合を進める | スタブとドライバの両方 |

トップダウンテストでは、まだ実装されていない下位モジュールの代わりに、簡易な代用品である**スタブ**を用意して呼び出しを受け止めます。逆にボトムアップテストでは、まだ実装されていない上位モジュール（呼び出し元）の代わりに**ドライバ**を用意して下位モジュールを呼び出します。「どちらの方向から結合するか」によって、代用品として何が必要になるかが決まるという対応関係が、試験で問われる着眼点です。サンドイッチテストは、この両方の方式を組み合わせ、開発の早い段階から上下両方の結合を確認できる方式として位置づけられます。

### 1.5 修正の副作用を確かめる ― リグレッションテスト

**リグレッションテスト（退行テスト）**とは、プログラムを修正した際に、その修正が原因で、これまで正常に動作していた別の機能に悪影響（デグレード）が生じていないかを確認するテストです。修正のたびに手作業で全機能を確認するのは非効率なため、前回のノートで扱った継続的インテグレーション（CI）の仕組みと組み合わせ、自動テストとして繰り返し実行されることが一般的です。

## 2. 人の目で確かめる ― レビュー手法

プログラムを実際に動かすテストとは別に、成果物を人の目で確認する活動がレビューです。レビューは設計書やコードなど、テストでは確認しにくい上流工程の成果物にも適用できる点が特徴です。

### 2.1 レビューの形式と公式さの度合い

レビュー手法は、進め方の公式さ（厳格さ）によって次のように整理できます。

| 手法 | 内容 |
|---|---|
| **パスアラウンド** | 成果物を複数のレビューアに回覧し、各自が個別にコメントする、非同期型のレビュー |
| **ウォークスルー** | 作成者が主導し、レビューアとともに成果物を机上でたどりながら、比較的非公式に確認する |
| **デザインレビュー** | 設計工程の成果物（設計書）を対象に行うレビューの総称 |
| **インスペクション** | あらかじめ定められた役割・手順に従って行う、最も公式かつ厳格なレビュー |
| **ラウンドロビンレビュー** | 参加者が持ち回りで司会（レビューア）役を務める方式のレビュー |

インスペクションは特にプログラムコードを対象に行う場合、**コードインスペクション**と呼ばれ、レビューを進行する議長役を**モデレータ**と呼びます。パスアラウンドやウォークスルーが「作成者主体の、比較的緩やかな確認」であるのに対し、インスペクションは「役割分担された第三者主体の、厳格な検証」であるという対比が、レビュー手法を見分ける最頻出の論点です。ラウンドロビンレビューは、司会役を固定しないことで、特定の参加者に負担が偏らないようにする進め方として位置づけられます。

## 3. テストを管理し、品質を保証する

個々のテスト・レビューの結果を、組織としてどう管理し、ソフトウェア全体の品質としてどう捉えるかを見ていきます。

### 3.1 テストの進み具合をモデル化する ― 信頼度成長モデル

**信頼度成長モデル**とは、テストの進行に伴って累積の不具合検出件数がどう変化するかをモデル化したものです。この変化を描いたグラフを**成長曲線**と呼び、代表的な形状として**ロジスティクス曲線**と**ゴンペルツ曲線**があります。どちらもテスト開始直後は検出件数の増加が緩やかで、その後急激に増加し、テストの終盤に向けて再び増加が鈍化するS字型の曲線を描く点が共通しており、この鈍化の兆候が「そろそろテストを終えてよい時期」を判断する目安として使われます。

**エラー埋め込みモデル**とは、既知の欠陥をあらかじめ意図的にプログラムへ混入させておき、テストでその埋め込み欠陥がどれだけ発見されたかという発見率から、まだ見つかっていない未知の欠陥の総数を統計的に推定する手法です。信頼度成長モデルが「時間の経過とともに不具合がどう減っていくか」という推移を見るのに対し、エラー埋め込みモデルは「今どれだけの欠陥が残っているか」を1時点で推定するという、着眼点の違いで区別すると整理しやすくなります。

### 3.2 ソフトウェアの品質をどう定義するか

品質を管理するには、まず「何をもって品質が高いとするか」を定義する必要があります。**JIS X 25010**は、ソフトウェア製品の品質を、機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性といった複数の特性の組み合わせとして体系的に定義した規格です。この中の使用性（ユーザビリティ）をさらに細かく見た要素の一つが**ユーザインターフェース快美性**で、UIの見た目の美しさや心地よさに関する品質特性を指します。機能面の正しさだけでなく、こうした利用者の主観的な満足度まで品質の一部として捉える点が、この規格の特徴です。

### 3.3 品質をどう作り込むか ― 品質保証とQC活動

品質を確保する考え方は、大きく2つのアプローチに分かれます。

- **欠陥防止**：欠陥がそもそも発生しないよう、上流工程での設計の工夫や2章のレビューを通じて、あらかじめ予防する考え方。
- **欠陥除去**：発生してしまった欠陥を、1章のテストなどによって事後に検出し取り除く考え方。

欠陥防止が「発生させない」という上流の工夫であるのに対し、欠陥除去は「発生したものを見つけて直す」という下流の対応であるという対比が、設計における品質保証の基本的な考え方です。

こうした品質管理を統計的な手法で体系的に行う考え方が**QC（Quality Control）方式**であり、これをソフトウェア開発に適用したものが**SWQC（Software Quality Control）**です。品質管理では、データの性質に応じて次の2種類の分析ツール群が使い分けられます。

| ツール群 | 対象 | 代表的な手法 |
|---|---|---|
| **QC七つ道具** | 数値データの分析 | パレート図、特性要因図、ヒストグラム、散布図、管理図、チェックシート、層別 |
| **新QC七つ道具** | 言語データ（数値化しにくい定性的情報）の整理 | 親和図法、連関図法、系統図法、マトリックス図法 など |

QC七つ道具が「測定された数値をどう分析するか」に主眼を置くのに対し、新QC七つ道具は「言葉で表現された情報をどう整理し構造化するか」に主眼を置くという対比で区別すると覚えやすくなります。

## 4. 試験対策まとめ（重要ポイント）

- **同値分割 と 限界値分析**：ブラックボックステストの代表手法。集合の内側の代表値を選ぶか、集合の境界を狙うかで区別する。
- **命令網羅 と 判定条件網羅 と 条件網羅 と 判定条件/条件網羅 と 複数条件網羅**：ホワイトボックステストの網羅基準。命令網羅が最も緩やかで、複数条件網羅が最も厳密という強さの序列を押さえる。
- **グレーボックステスト**：ブラックボックスとホワイトボックスの中間的な位置づけであることを押さえる。
- **ファジング**：想定外データの大量投入によりセキュリティ上の脆弱性を検出する手法として、セキュリティ分野の攻撃的テストと結びつけて覚える。
- **トップダウンテスト と ボトムアップテスト と サンドイッチテスト**：結合の方向と、それぞれに必要な代用品（スタブ／ドライバ）の対応関係が最頻出の識別問題。
- **リグレッションテスト**：修正の副作用（デグレード）を確認するテストであり、継続的インテグレーションと結びつけて自動化されることが多い。
- **パスアラウンド／ウォークスルー と インスペクション**：レビューの公式さの度合いの違い。インスペクションはコードインスペクション・モデレータとセットで覚える。
- **信頼度成長モデル（成長曲線） と エラー埋め込みモデル**：時間経過での推移を見るか、1時点での残存欠陥数を推定するかの違い。
- **欠陥防止 と 欠陥除去**：上流での予防か、下流での検出・除去かという品質保証の基本アプローチ。
- **QC七つ道具 と 新QC七つ道具**：数値データを扱うか、言語データを扱うかで区別する。
