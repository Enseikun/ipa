# レクチャーノート：プロジェクトマネジメント・システム監査 ― システム構築の関連知識

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「プロジェクトマネジメント」＞「プロジェクトマネジメント」・「サービスマネジメント」＞「システム監査」（開発管理、システム監査、内部統制）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

これまでのノートでは、システムを「どう作るか」という開発技術そのものを見てきました。本ノートでは視点を少し引いて、その開発を計画どおりに進めるための管理と、出来上がった（あるいは運用中の）システムが適正であるかを第三者が検証する仕組みを扱います。作る技術から、それを管理し検証する技術への転換です。

本ノートは、次の4段階のストーリーで説明します。①まず、開発を計画どおりに進めるための開発管理（品質・進捗・見積り）を見ます。②次に、出来上がったシステムを第三者の目で検証するシステム監査の仕組みと、コンピュータを活用した監査技法を学びます。③さらに、コンピュータに頼らない伝統的な監査技法を見ます。④最後に、監査や統制の土台となる内部統制・ITガバナンスの考え方を扱います。

このうちシステム監査は、科目A-1（共通知識）で平均2.0問と、プロジェクトマネジメントと並んで高頻度に出題される分野です。章のタイトルの目立たなさとは裏腹に、実際の出題比重は高いため重点的に押さえる価値があります。科目A-2でも1問出題され、コンピュータ支援監査技法（CAAT）の名称と手法の対応、内部統制の基本要素は定番論点です。

---

## 1. 開発をどう管理するか ― 開発管理

システムを作る技術そのものではなく、その開発作業を計画どおりに進めるための管理の視点を見ていきます。

### 1.1 品質をどう計画し管理するか

プロジェクトにおける**品質計画・管理・評価**とは、目標とする品質の水準をあらかじめ定め、開発の過程でその水準を維持できているかを管理し、完了後に評価する一連の活動です。この品質計画を具体的に進める代表的な手法が**QFD（品質機能展開）**で、顧客の要求という定性的な「声」を、設計に反映できる技術的な品質特性へと変換し、優先順位をつけながら製品・システムの設計に落とし込む手法です。要求を整理する表（品質表）を用いる点が特徴で、9.2節で扱った要求モデルが「機能をどう表現するか」に主眼を置くのに対し、QFDは「顧客の要求をどう設計に翻訳するか」に主眼を置くという違いがあります。

### 1.2 進捗をどう管理するか

**工程管理・進捗管理**とは、計画した作業がスケジュールどおりに進んでいるかを継続的に確認し、遅延があれば対応する活動です。その代表的な可視化手法が**ガントチャート**で、横軸に時間、縦軸に個々の作業（タスク）を配置し、各作業の開始時期・終了時期を棒状のグラフで表現します。一覧性が高く、複数の作業がどの時期に並行して進むかが一目で把握できる点が特徴です。

### 1.3 規模・工数をどう見積もるか ― 見積もり手法

プロジェクトの計画段階では、規模や工数をあらかじめ見積もる必要があります。見積もりの進め方は、大きく2つの方向に分かれます。

- **トップダウン見積り法**：プロジェクト全体の規模・コストを先に概算し、それを各工程・作業に配分していく方法。
  - **類似法**：過去の類似プロジェクトの実績を根拠に、全体の規模を見積もる。
  - **標準値法**：工程ごとの標準的な工数比率などのデータをもとに、全体の規模を見積もる。
- **ボトムアップ見積り法**：個々の作業を洗い出し、それぞれの工数を積み上げてプロジェクト全体の規模を見積もる方法。
  - **標準タスク法**：作業を標準的なタスク単位に分解し、それぞれの標準工数を積み上げる。
  - **WBS（Work Breakdown Structure）**：プロジェクトの作業を階層的に細かく分解した構成図。ボトムアップ見積りの前提となる、作業を洗い出すための基礎技法。

トップダウン見積り法が「全体から部分へ」規模を配分していくのに対し、ボトムアップ見積り法は「部分から全体へ」規模を積み上げていくという、見積もりの方向の違いが両者を区別する最頻出の論点です。

## 2. 出来上がったシステムを検証する ― システム監査

開発を管理する視点から、今度は出来上がった、あるいは運用中のシステムを第三者の立場で検証する視点に移ります。

### 2.1 システム監査の基本的な考え方

**システム監査**とは、情報システムが有効かつ効率的に、そして安全に機能しているかを、独立した立場の専門家が検証・評価する活動です。前回までのノートで扱った情報セキュリティ監査は、このシステム監査のうちセキュリティの観点に絞った活動として位置づけられます。監査を行う際の拠り所となるのが**システム監査基準**で、監査人が従うべき実施上の指針が定められています。監査を実施する専門家を**システム監査人**と呼び、監査対象から独立した客観的な立場であることが強く求められます。

監査は指摘して終わりではありません。**フォローアップ（改善指導）**とは、監査で指摘した事項がその後実際に改善されているかを確認し、必要に応じて改善を指導する、監査後の工程です。監査を1回限りの点検ではなく、改善へとつなげる継続的な活動として捉える視点が試験でも問われます。

### 2.2 コンピュータを活用した監査技法 ― CAAT

**CAAT（コンピュータ支援監査技法）**とは、コンピュータを利用して監査を効率的・効果的に行う技法の総称です。具体的な手法は、次のように整理されます。

| 技法 | 内容 |
|---|---|
| **監査モジュール法** | 本番システムのプログラムにあらかじめ監査用のモジュールを組み込み、処理の中から監査に必要なデータを収集する |
| **並行シミュレーション法** | 監査人が別途用意した検証用プログラムに本番と同じデータを入力し、本番システムの処理結果と突き合わせる |
| **テストデータ法** | 監査人が用意したテストデータを本番のプログラムに投入し、結果が想定どおりかを確認する |
| **ITF法（Integrated Test Facility）** | 本番システムの中に架空の部門・勘定を設定し（この手法を**ミニカンパニ法**と呼ぶ）、テストデータを実データに混在させて処理させ、結果を検証する（この一連の進め方を**統合テスト法**と呼ぶ） |
| **スナップショット法** | 処理の途中経過を特定のタイミングで記録（スナップショット）し、後で内容を検証する |
| **トレーシング法** | プログラムの処理の流れを命令単位で追跡し、意図どおりに処理されているかを確認する |
| **コード比較法** | 本来使われるべき正しいプログラムのコードと、実際に本番で稼働しているコードを比較し、不正な変更がないかを確認する |

これらの技法は、「本番の処理にあらかじめ仕込んでおくか（監査モジュール法）」「別のプログラムで検証するか（並行シミュレーション法、テストデータ法）」「テストデータを本番に紛れ込ませるか（ITF法）」「処理の記録・流れ・コードそのものを事後に確認するか（スナップショット法、トレーシング法、コード比較法）」という、監査対象への関わり方の違いで整理すると区別しやすくなります。

## 3. コンピュータに頼らない検証 ― 伝統的な監査技法

CAATがシステムの処理そのものを対象にするのに対し、人の作業や書面に基づいて確認する、伝統的な監査技法もあります。

| 技法 | 内容 |
|---|---|
| **チェックリスト法** | あらかじめ用意した点検項目の一覧に沿って、一つずつ確認する |
| **インタビュー法** | 関係者に直接聞き取りを行う |
| **現地調査法** | 実際に現場に赴き、実物や作業の状況を目で見て確認する |
| **突合・照合法** | 関連する複数の証憑・記録を突き合わせ、内容が一致しているかを確認する |
| **ドキュメントレビュー法** | 規程やマニュアルなどの文書を閲覧し、内容の妥当性を確認する |
| **ウォークスルー法** | 実際の業務処理の流れを、担当者とともに一つずつ机上でたどりながら確認する |

**ウォークスルー法**は、前回のノートで扱ったレビュー手法のウォークスルーと同じ「作成者・担当者とともに机上でたどる」という発想を、監査という場面に適用したものです。2章のCAATが「システムの処理をコンピュータで検証する」技法であるのに対し、本章の伝統的な監査技法は「人が直接見る・聞く・照らし合わせる」技法であるという対比が、両者を区別する軸になります。

## 4. 監査と統制の土台 ― 内部統制

最後に、これまで見てきたシステム監査や開発管理が、そもそもなぜ必要とされるのかという土台にある考え方、内部統制を扱います。

**内部統制**とは、組織が業務を適正かつ効率的に遂行するために、自ら構築し運用する仕組み全般を指します。業務の有効性・効率性、財務報告の信頼性、事業活動に関わる法令の遵守、資産の保全などを目的とします。内部統制は、一般に次の**基本要素**から構成されるとされています。

- 統制環境
- リスクの評価と対応
- 統制活動
- 情報と伝達
- モニタリング（監視活動）
- ITへの対応

個々の業務プロセスに組み込まれた具体的な仕組み・手続きを**コントロール**と呼び、これらが積み重なって組織全体の内部統制を形作ります。組織が自ら構築するこの内部統制に対して、外部の監査法人や監督官庁といった第三者が検証・監督する仕組みを**外部統制**と呼びます。2章で扱ったシステム監査は、独立した第三者の立場から内部統制の実効性を検証するという意味で、外部統制的な役割を担う活動として位置づけられます。

内部統制のうち、特にIT分野に関する仕組みを経営の視点から方向づけ、統制する枠組みを**ITガバナンス**と呼びます。これは、これまでのノートで扱った情報セキュリティガバナンスの考え方を、セキュリティに限らずIT全般へと広げたものとして位置づけられます。また、内部統制の目的の一つであるコンプライアンス（法令遵守）が実際に守られているかを確かめ、問題があれば是正する活動を**法令遵守状況の評価・改善**と呼びます。これは、2.1節のフォローアップと同様、「確認して終わり」ではなく「改善につなげる」ことを前提とした、内部統制に共通する継続的な工程として捉えられます。

## 5. 試験対策まとめ（重要ポイント）

- **トップダウン見積り法（類似法・標準値法） と ボトムアップ見積り法（標準タスク法・WBS）**：全体から配分するか、部分から積み上げるかという見積もりの方向の違い。
- **QFD と ガントチャート**：品質を計画する道具か、進捗を可視化する道具かという役割の違い。
- **システム監査人の独立性**：監査対象から独立した客観的な立場であることが、システム監査の信頼性の前提となる。
- **CAATの各手法**：監査モジュール法・並行シミュレーション法・テストデータ法・ITF法（ミニカンパニ法・統合テスト法）・スナップショット法・トレーシング法・コード比較法を、監査対象への関わり方で区別する。
- **伝統的な監査技法 と CAAT**：人手・書面による確認か、コンピュータの処理を用いた確認かという対比。
- **フォローアップ と 法令遵守状況の評価・改善**：どちらも「確認して終わり」ではなく「改善につなげる」ことを前提とする継続的な工程である点を押さえる。
- **内部統制の基本要素**：統制環境、リスクの評価と対応、統制活動、情報と伝達、モニタリング、ITへの対応の6つを押さえる。
- **内部統制 と 外部統制**：組織が自ら構築するか、外部の第三者が検証・監督するかの違い。システム監査は外部統制的な役割を担う。
- **ITガバナンス**：情報セキュリティガバナンスをIT全般に広げた、経営視点での統制の枠組みとして位置づける。
