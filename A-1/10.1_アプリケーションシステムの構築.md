# レクチャーノート：開発技術 ― システム開発技術・ソフトウェア開発管理技術＞アプリケーションシステムの構築

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「開発技術」＞「システム開発技術」・「ソフトウェア開発管理技術」（再利用技術、モジュール設計、プログラミング技法）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

これまでのノートでは、要求をどうモデル化し（9.2）、どう設計技法に落とし込み、どうテスト・レビューで確かめるか（9.3）という、開発工程の「型」を見てきました。本ノートでは視点をさらに実装の現場に近づけ、実際にアプリケーションをどう組み立てるかという、より実践的な技術を扱います。

本ノートは、次の3段階のストーリーで説明します。①まず、既存の資産をどう再利用し、開発を効率化する技術を見ます。②次に、再利用や保守のしやすさを左右する、モジュール自体の設計品質を評価する基準を学びます。③最後に、プログラムそのものをどのような考え方・記法で書くか、というプログラミングの技法を扱います。

本分野は情報処理安全確保支援士試験の科目A-2では出題数こそ多くない中優先分野ですが、モジュール結合度・強度の識別問題や、プログラミングパラダイムの名称と特徴の対応は定番論点です。プログラミングパラダイムの基礎的な考え方は、基礎理論分野（アルゴリズムとプログラミング）とも重なるため、あわせて理解しておくと学習効率が高まります。

## 1. 既存の資産をどう活かすか ― 再利用技術

ゼロから作るのではなく、既存の資産をどう活かして開発を効率化するかという視点から見ていきます。

### 1.1 再利用と自動化の基本的な考え方

**再利用技術（リユーステクノロジ）**とは、過去に作成したプログラムや設計、ドキュメントといったソフトウェア資産を新たな開発に活用し、開発の生産性と品質を高める技術の総称です。これと両輪をなすのが**自動化技術**で、コード生成やテストの実行など、開発作業そのものをツールによって自動的に行わせる技術です。「既にあるものを使い回す（再利用）」ことと「作業そのものを機械にやらせる（自動化）」ことは、どちらも人手をかけずに開発を効率化するという共通の目的を持ちます。

こうした再利用・自動化を実務で支えるのが**IDE（統合開発環境）**です。エディタ・コンパイラ・デバッガなど、開発に必要な複数のツールを一つにまとめた環境で、再利用可能な部品の管理や、コード生成などの自動化機能を統合的に提供する基盤として位置づけられます。

### 1.2 何を、どう再利用するか

再利用の対象と方法は、いくつかのパターンに整理されます。

- **部品による再利用**：既存のライブラリやコンポーネントといったプログラム部品を、そのまま組み込んで利用する、最も直接的な再利用の形。
- **マッシュアップ**：複数の既存のWebサービス（外部のAPIなど）を組み合わせて、新しいアプリケーションを作り上げる手法。部品による再利用を、Web上のサービス単位に拡張したものといえます。
- **生成による再利用（リエンジニアリング）**：既存の資産からいったん設計情報を抽出し、それをもとに新しい形で作り直す再利用の形。前回までのノートで扱ったリエンジニアリングの考え方を、資産の「再利用」という目的の観点から捉え直したものです。
- **オブジェクト指向設計での再利用**：継承や委譲といった、これまでのノートで扱ったオブジェクト指向の仕組みを用いて、クラス単位で機能を再利用する方法。

部品による再利用・マッシュアップが「既存のものをそのまま使う」再利用であるのに対し、生成による再利用は「既存のものを土台に作り直す」再利用であるという対比が、これらを区別する着眼点です。

### 1.3 開発そのものを支援する仕組み

再利用を促進するには、資産を後から使いやすい形で残しておく仕組みや、そもそもコーディングの負担自体を減らす仕組みも重要です。**ドキュメンテーションジェネレータ**は、プログラムのコード中に書かれたコメントなどの情報をもとに、仕様書やAPIドキュメントを自動生成するツールで、再利用の前提となる文書化作業を自動化します。

さらに、プログラミングという工程自体を最小限にする動きとして、**ノーコード開発**（プログラミングを一切行わずに、画面上の操作だけでアプリケーションを構築する開発手法）と**ローコード開発**（最小限のコーディングでアプリケーションを構築する開発手法）があります。これらは、再利用や自動化を突き詰めた先にある発展形として位置づけられます。

## 2. モジュールをどう設計するか ― 良い構造を評価する基準

再利用しやすく、保守しやすいプログラムを作るには、モジュール（プログラムの構成単位）そのものの設計品質が重要になります。ここでは、その良し悪しを測る評価基準を学びます。

### 2.1 モジュールの独立性を測る2つの指標

モジュール設計の品質は、主に2つの指標で評価されます。

- **モジュール強度**：モジュールの内部にある処理要素同士が、どれだけ密接に関連し合っているかを表す指標。強度が高い（内部の結びつきが強い）ほど、そのモジュールは一つのまとまった役割を果たしていると評価され、良い設計とされます。
- **モジュール結合度**：モジュールとモジュールの間が、どれだけ密接に依存し合っているかを表す指標。結合度は低い（モジュール間の依存が弱い）ほど、互いに独立して修正・再利用しやすく、良い設計とされます。

「強度は高いほどよく、結合度は低いほどよい」という評価の向きの違いが、この2つの指標を混同しないための最頻出のポイントです。

### 2.2 モジュール強度の種類

モジュール強度は、内部の処理要素がどのような理由でまとまっているかによって、次のように強い順に分類されます。

| 強度（強い順） | 内容 |
|---|---|
| **機能的強度** | 一つの明確な機能を実現するために要素がまとまっている（最も強い） |
| **情報的強度** | 同じデータ構造を扱う複数の機能が、入出力を共有してまとまっている |
| **連絡的強度** | 処理の実行順序に関連があり、かつデータの受け渡しもある要素がまとまっている |
| **手順的強度** | 処理の実行順序にのみ関連があり、要素がまとまっている |
| **時間的強度** | 特定の時点（初期化処理など）に実行するというだけの理由でまとまっている |
| **論理的強度** | 似たような性質の処理を、条件分岐によって呼び分けるだけでまとまっている |
| **暗号的強度** | 実行順序以外に、まとまっている理由がほとんどない（最も弱い） |

強度が強いモジュールほど、単一の役割に特化しており、修正の影響が他の機能に及びにくいという利点があります。

### 2.3 モジュール結合度の種類

モジュール結合度は、モジュール間でどのような形の依存関係があるかによって、次のように弱い（良い）順に分類されます。

| 結合度（弱い順） | 内容 |
|---|---|
| **データ結合** | 必要なデータ項目だけを引数として渡す |
| **スタンプ結合** | 必要以上のデータ構造（レコードなど）をまとめて渡す |
| **制御結合** | 相手の処理の内容を制御するためのフラグなどを渡す |
| **外部結合** | 複数のモジュールが、外部で定義された共通のデータを直接参照する |
| **共通結合** | 複数のモジュールが、共通のデータ領域を直接読み書きする |
| **内容結合** | 他のモジュールの内部処理に直接介入する（最も強く、最も好ましくない） |

これらとは別に、オブジェクト指向設計の文脈では、結合の形として**メッセージ結合**（メッセージのやり取りだけでモジュール（オブジェクト）間が連携する、データ結合と同程度に弱く好ましい結合）や**無結合**（モジュール間に一切のやり取りが存在しない状態）も用いられます。結合度は低いほど良いという評価基準は、この2つでも変わりません。

### 2.4 分割の適切さを評価する ― 領域評価

モジュール強度・結合度が個々のモジュールの性質を評価するのに対し、モジュール分割全体の適切さを評価する考え方が**領域評価**です。あるモジュールが処理を制御している範囲（決定を行う範囲）と、その制御の影響が実際に及ぶ範囲（効果が及ぶ範囲）を比較し、効果が及ぶ範囲が制御する範囲の内側に収まっているほど、見通しのよい適切な分割であると評価します。効果の及ぶ範囲が制御する範囲を超えてしまう場合、モジュール同士の見えない依存関係が生じていることになり、これは2.3節の結合度が高くなっている兆候として捉えられます。

## 3. プログラムそのものをどう書くか ― プログラミング技法

モジュールという構造の単位を見たところで、最後にその中身であるプログラムをどのような考え方・記法で書くかを見ていきます。

### 3.1 プログラミングパラダイムの分類

**プログラミングパラダイム**とは、プログラムをどのような基本的な考え方に基づいて記述するかという、設計思想の分類です。代表的なパラダイムは次の4つです。

- **手続き型プログラミングパラダイム**：処理の手順（命令の並び）として、上から順にプログラムを記述する、最も伝統的な考え方。
- **関数型プログラミングパラダイム**：プログラムを、数学的な関数の組み合わせとして記述する考え方。同じ入力に対して常に同じ出力を返すことを重視し、外部の状態を書き換えるような**動的な副作用**を極力避けて設計することを志向します。
- **論理型プログラミングパラダイム**：処理の手順を明示的に書くのではなく、「事実」と「規則」を記述し、そこから解を導出させる考え方。事実と規則の組み合わせから変数の値を確定させていく仕組みを**ユニフィケーション**、解が見つからずに行き詰まった際に、一つ前の選択まで戻ってやり直す仕組みを**バックトラッキング**と呼びます。
- **オブジェクト指向プログラミングパラダイム**：前々回のノートで扱ったクラス・オブジェクトを中心にプログラムを記述する考え方。継承を活用し、既存クラスとの差分だけを記述する**差分プログラミング**は、このパラダイムを支える代表的な技法として、ここでも位置づけられます。

4つのパラダイムは、「手順を書くか（手続き型）」「関数の組み合わせで書くか（関数型）」「事実と規則で書くか（論理型）」「オブジェクトの相互作用で書くか（オブジェクト指向型）」という、プログラムの捉え方の違いとして整理すると理解しやすくなります。

### 3.2 プログラムの流れを図で表現する ― 構造化チャートとNSチャート

前回のノートで扱ったジャクソン法が「連接・選択・繰り返し」という3つの構造要素でデータ構造を表現したのと同じ発想を、プログラムの制御の流れに適用したのが**構造化プログラミング**です。これは、順次・選択・反復という3つの基本構造だけを組み合わせれば、どのようなプログラムも記述できるという考え方で、この理論的な裏付けを**構造化定理**と呼びます。

構造化プログラミングの考え方に基づき、プログラムの制御の流れを図として表現する表記法の総称を**構造化チャート**と呼びます。その代表的な記法が**NSチャート（Nassi-Shneiderman図）**で、矩形（長方形）を入れ子にして処理の流れを表現します。従来のフローチャートのように矢印が自由に飛ぶことがなく、必ず3つの基本構造の組み合わせとして描かれるため、構造化された記述を図の上でも強制できる点が特徴です。

## 4. 試験対策まとめ（重要ポイント）

- **部品による再利用 と 生成による再利用（リエンジニアリング）**：既存のものをそのまま使うか、作り直すかという再利用の方法の違い。
- **ノーコード開発 と ローコード開発**：コーディングを一切行わないか、最小限のコーディングを伴うかの違い。再利用・自動化を突き詰めた発展形。
- **モジュール強度 と モジュール結合度**：強度は高いほど良く、結合度は低いほど良いという評価の向きの違いが最頻出の論点。
- **モジュール強度の7分類**：機能的強度が最も強く（良く）、暗号的強度が最も弱い（悪い）という序列を押さえる。
- **モジュール結合度の6分類 と メッセージ結合／無結合**：データ結合が伝統的な分類で最も弱く（良く）、内容結合が最も強い（悪い）。オブジェクト指向文脈ではメッセージ結合・無結合がさらに弱い側に加わる。
- **領域評価**：効果が及ぶ範囲が、制御する範囲に収まっているかで分割の適切さを評価する考え方。
- **手続き型 と 関数型 と 論理型 と オブジェクト指向型**：プログラムを手順・関数・事実と規則・オブジェクトの相互作用のいずれで捉えるかという4つの発想の違い。
- **ユニフィケーション と バックトラッキング**：論理型パラダイムを支える2つの仕組み。値を確定させる仕組みか、行き詰まった際に後戻りする仕組みかの違い。
- **差分プログラミング**：オブジェクト指向プログラミングパラダイムを支える技法として、継承の活用例と結びつけて覚える。
- **構造化定理 と NSチャート**：どんなプログラムも3つの基本構造で表現できるという理論的裏付けと、それを図に落とし込んだ代表的な記法の関係。
