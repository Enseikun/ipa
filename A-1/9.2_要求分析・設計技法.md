# レクチャーノート：開発技術 ― システム開発技術＞要求分析・設計技法

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「開発技術」＞「システム開発技術」（要件定義・設計）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

前回のノート（開発環境と開発手法）では、システム開発がどのような工程・環境・進め方で行われるかという、いわば骨格を見てきました。本ノートでは、その骨格のうち特に「要件定義」と「設計」という2つの工程に踏み込み、要求をどのようなモデルで表現し、それをどのような技法でソフトウェアの構造に落とし込むかを扱います。工程全体の流れから、その内部で何が行われているかへと、視点を掘り下げる回です。

本ノートは、次の3段階のストーリーで説明します。①まず、システムに求められる要求を図として表現するための、さまざまなモデルを学びます。②次に、現代の設計の主流であるオブジェクト指向という考え方を支える基礎概念を整理します。③最後に、要求モデルを実際のプログラム構造へと落とし込む、具体的な設計技法（構造化設計技法・オブジェクト指向設計技法）を見ます。

本分野は情報処理安全確保支援士試験の科目A-2では出題数こそ多くありませんが、取りこぼしの許されない中優先分野です。特にオブジェクト指向の用語（継承・多態性など）は、モデリング図（UML）の読み取り問題や、プログラミング分野との複合問題として繰り返し出題される定番論点です。名称と特徴の対応を正確に区別できるかが得点を左右します。

## 1. 要求をどう表現するか ― ソフトウェア要求モデル

設計に入る前に、まず「何を作るべきか」という要求を、曖昧な文章ではなく図として正確に表現するためのモデルを見ていきます。

### 1.1 機能に着目するモデルとデータの流れに着目するモデル

要求をモデル化する最も基本的な視点は、「システムが何をするか（機能）」と「データがどう流れるか」の2つです。

- **機能階層モデル**：システムが持つべき機能を、大きな機能から小さな機能へとトップダウンに分解し、階層構造で表現するモデル。
- **データフローモデル（データフローダイアグラム、DFD）**：データがどこから発生し、どのような処理（プロセス）を経て、どこに格納・出力されるかという、データの流れに着目して業務やシステムを図示するモデル。

機能階層モデルが「何をするか」という処理の分解に焦点を当てるのに対し、データフローモデルは「データがどう動くか」という流れに焦点を当てるという対比で整理すると理解しやすい論点です。この2つの視点の違いは、3章で扱う設計技法における「プロセス中心アプローチ」と「データ中心アプローチ」の違いにも引き継がれます。

### 1.2 データの構造に着目するモデル ― データ指向モデル

データそのものの構造や性質に着目してシステムを捉えるモデル群を、データ指向モデルと呼びます。

- **E-Rモデル**：データを**実体（エンティティ）**、実体同士のつながりを**関係（リレーションシップ）**、実体が持つ性質を**属性**として表現するモデル。データベースの論理設計の基礎になります。
- **抽象データモデル**：データと、そのデータに対する操作をひとまとめにして扱う考え方。データの内部構造と操作をひとまとめにすることを**カプセル化**、内部の実装詳細を外部から隠すことを**情報隠蔽**と呼び、この2つの性質がオブジェクト指向の基礎になります。
- **オブジェクト指向モデル**：データとその操作を一体化した**クラス**という単位でシステムを捉えるモデル。抽象データモデルの考え方をさらに発展させたものです。
- **ペトリネットモデル**：システムの状態を「プレース」、状態の変化を「遷移」として表現し、特に並行して動く処理（並行処理）の流れをモデル化するのに向いたモデル。

E-Rモデルが「データの静的な構造」を表すのに対し、ペトリネットモデルは「状態がどう変化するか」という動的な振る舞いを表すという対比があります。抽象データモデルからオブジェクト指向モデルへの流れは、「データと操作をまとめる」という発想が徐々に洗練されていく発展として捉えると、2章のオブジェクト指向設計につながりやすくなります。

### 1.3 統一的な記法で設計を表現する ― UML

オブジェクト指向による設計を、標準化された図の記法で表現するための言語が**UML（Unified Modeling Language）**です。UMLの各図は、システムの「構造（静的な側面）」を表す図と、「振る舞い（動的な側面）」を表す図に大別されます。

| 分類 | 図の名称 | 表す内容 |
|---|---|---|
| 構造図（静的） | **クラス図** | クラス同士の関係（継承・関連など）を表す |
| | **オブジェクト図** | ある時点でのオブジェクトの状態・関係を表す |
| | **配置図** | ハードウェアやソフトウェアの物理的な配置を表す |
| 振る舞い図（動的） | **ユースケース図** | 利用者（アクター）とシステムとのやり取りを表す |
| | **ステートマシン図** | オブジェクトが持つ状態と、状態間の遷移を表す |
| | **アクティビティ図** | 処理の流れ（手順）を表す |
| | **シーケンス図** | オブジェクト間のやり取りを、時間の経過に沿って表す |
| | **コミュニケーション図** | オブジェクト間のやり取りを、関係性（構造）に着目して表す |

シーケンス図とコミュニケーション図はどちらもオブジェクト間のメッセージのやり取りを表しますが、時間軸に沿って並べるか、オブジェクト同士のつながりに着目して並べるかという表現方法の違いで区別します。

こうした設計の起点をどこに置くかという発想には、大きく2つのアプローチがあります。**プロセス中心アプローチ**は1.1節の機能階層モデルのように処理の分解を起点に設計を進める考え方、**データ中心アプローチ**はE-Rモデルのようにデータの構造を起点に設計を進める考え方です。この対比は、3章で扱う構造化設計技法とオブジェクト指向設計技法の性格の違いにも通じる、設計思想の根本的な軸として押さえておきます。

## 2. オブジェクト指向という考え方の基礎概念

要求をどう表現するかを見たところで、次はその表現を支える中心的な考え方であるオブジェクト指向の基礎概念を整理します。

### 2.1 クラスとオブジェクトの基本

**クラス**とは、オブジェクトの雛形となる定義であり、そのオブジェクトが持つべき属性（データ）と操作（振る舞い）をひとまとめにしたものです。このクラスの定義をもとに実際に生成された実体を**オブジェクト**、または**インスタンス**と呼びます。「あるクラスのインスタンスである」という言い方をするように、インスタンスはオブジェクトをクラスとの生成関係に着目して呼ぶ際の呼称であり、両者はほぼ同じものを指します。

### 2.2 クラス間の関係 ― 継承と汎化・特化、集約と分解

クラス同士は、独立して存在するだけでなく、互いに関係を持つことでより柔軟な設計が可能になります。代表的な関係が次の2種類です。

- **継承（インヘリタンス）**：あるクラス（親クラス、スーパークラス）が持つ属性・操作を、別のクラス（子クラス、サブクラス）が受け継ぐ仕組み。1つの子クラスが複数の親クラスから同時に継承することを**多重継承**と呼びます。
- **集約－分解構造（part-of関係）**：あるオブジェクトが、別のオブジェクトを部品として内部に持つ関係。集約のうち、部品となるオブジェクトが全体オブジェクトのライフサイクルに強く依存する（全体が消滅すれば部品も消滅する）強い集約関係を、特に**コンポジション**と呼びます。

継承の関係は、抽象度の観点からは**汎化－特化構造（is-a関係）**とも呼ばれます。子クラスは親クラスを「一般化（汎化）」した存在であり、逆に親クラスから見れば子クラスは「特殊化（特化）」した存在にあたります。継承の仕組みを活用し、既存のクラスとの差分（追加・変更する部分）だけを記述して新しいクラスを効率よく作成するプログラミングのスタイルを**差分プログラミング**と呼びます。

継承（is-a関係）が「〜は〜の一種である」という関係であるのに対し、集約（part-of関係）は「〜は〜の一部である」という関係であるという対比が、クラス間の関係を見分ける最頻出の論点です。

### 2.3 オブジェクト同士の連携と多態性

オブジェクト指向の柔軟性を支えるのが、オブジェクト同士の連携の仕組みと、同じ操作が状況に応じて異なる振る舞いをする性質です。

**抽象クラス**とは、具体的な処理の一部、または全部を実装せず、共通のインタフェース（操作の型）だけを定義するクラスで、直接インスタンス化することはできません。オブジェクト同士は**メッセージ**（操作の呼び出し）をやり取りすることで連携し、この仕組みを**メッセージパッシング**と呼びます。

同じメッセージを受け取っても、受け取るオブジェクトの実際のクラスによって異なる処理が実行される性質を**ポリモーフィズム（多態性）**と呼びます。これを実現する技術的な仕組みが**動的結合**で、実行時に、実際に生成されたオブジェクトの型を見てから呼び出すメソッドを決定します。これに対し、コンパイル時点で呼び出すメソッドを決定する仕組みを**静的結合**と呼びます。

ポリモーフィズムを実現する具体的な記述の仕方として、次の2つがよく対比されます。

- **オーバーライド**：サブクラスが、スーパークラスで定義された操作を、同じ名前・同じ引数のまま再定義すること。
- **オーバーロード**：同じ名前の操作を、引数の型や数を変えて複数定義すること。

オーバーライドは「継承関係にある親の操作を上書きする」動的結合の典型例、オーバーロードは「同じクラス内で引数の違いにより呼び分ける」静的結合の典型例という対応関係で整理すると覚えやすくなります。なお、継承によってスーパークラスの振る舞いを丸ごと受け継ぐのではなく、あるオブジェクトが自分の処理の一部を、別のオブジェクトに処理させて結果を利用する仕組みを**委譲**と呼びます。委譲は継承に代わる柔軟な再利用の手段として位置づけられます。

## 3. 要求モデルを構造に落とし込む ― ソフトウェア設計技法

概念を整理したところで、最後にそれらを実際のプログラム構造へと変換する、具体的な設計技法を見ていきます。

### 3.1 構造化設計技法 ― プロセス中心アプローチの具体化

1.3節のプロセス中心アプローチを、実際のモジュール分割の手順にまで具体化したものが構造化設計技法です。

**STS分割**は、データフローダイアグラムをもとに、データの流れを「源泉（Source）」「変換（Transform）」「吸収（Sink）」の3つの働きに分けてモジュールを分割する手法です。データが最も抽象化された（加工が進んだ）入力側の点を**最大抽象入力点**、同様に出力側の点を**最大抽象出力点**と呼び、この2点を境界として、入力側を源泉分割、中心部を変換分割、出力側を吸収分割としてモジュールを切り分けます。

**TR分割（トランザクション分割）**は、データの流れが複数の処理経路に分岐する点（トランザクションセンタ）に着目し、分岐後のそれぞれの処理経路ごとにモジュールを分割する手法です。STS分割が「データが流れる方向（源泉→変換→吸収）」に着目するのに対し、TR分割は「データの流れが枝分かれする点」に着目するという違いがあります。

**ジャクソン法**は、データフローではなく、入力データ・出力データが持つ構造そのものに着目してプログラム構造を導く手法です。データ構造を、次の3つの基本要素の組み合わせとして表現します。

| 構造要素 | 内容 |
|---|---|
| **連接** | 複数の要素が順番に並ぶ構造 |
| **選択** | 複数の要素のうち、いずれか一つが現れる構造 |
| **繰り返し** | ある要素が0回以上繰り返し現れる構造 |

STS分割・TR分割が「データの流れ」を手掛かりにするのに対し、ジャクソン法は「データの構造」を手掛かりにするという点が、3つの構造化設計技法を区別する着眼点です。

### 3.2 オブジェクト指向設計技法

2章で見た概念を、実際の開発サイクルの中でどう扱うかという実践面の技法も押さえておきます。**ラウンドトリップ（ラウンドトリップエンジニアリング）**とは、UMLなどの設計モデルからプログラムコードを生成する作業（前回ノートのフォワードエンジニアリング）と、コードから設計モデルを再び読み取る作業（前回ノートのリバースエンジニアリング）を繰り返し行き来しながら、設計とコードの整合性を保ち続ける開発の進め方です。前回のノートで扱ったフォワード・リバースエンジニアリングという工程の方向性の概念を、オブジェクト指向設計というより具体的な場面に適用したものとして位置づけられます。

## 4. 試験対策まとめ（重要ポイント）

- **機能階層モデル と データフローモデル**：処理の分解に着目するか、データの流れに着目するかの対比。
- **E-Rモデル と ペトリネットモデル**：データの静的な構造を表すか、状態の動的な変化を表すかの対比。
- **カプセル化 と 情報隠蔽**：抽象データモデルを支える2つの性質。データと操作をまとめるか、内部実装を隠すか。
- **クラス図・オブジェクト図・配置図（構造図） と ユースケース図・ステートマシン図・アクティビティ図・シーケンス図・コミュニケーション図（振る舞い図）**：UMLの図が静的側面と動的側面のどちらを表すかで大別する。
- **継承（is-a関係） と 集約（part-of関係）**：「〜の一種である」か「〜の一部である」かという、クラス間関係を見分ける最頻出の論点。
- **オーバーライド と オーバーロード**：親の操作を再定義するか、同名の操作を引数違いで多重定義するかの対比。動的結合・静的結合とそれぞれ対応する。
- **委譲**：継承によらず、処理を他のオブジェクトに任せる再利用の手段として押さえる。
- **STS分割 と TR分割 と ジャクソン法**：データの流れる方向、データの流れが分岐する点、データの構造そのもの、という3つの異なる着眼点で区別する。
- **プロセス中心アプローチ と データ中心アプローチ**：構造化設計技法とデータ指向モデル（E-Rモデル）それぞれの土台となる、設計思想の根本的な軸。
- **ラウンドトリップ**：フォワードエンジニアリングとリバースエンジニアリングを繰り返す、設計とコードの一貫性を保つ実践として押さえる。
