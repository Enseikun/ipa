# レクチャーノート：サービスマネジメント ― ITIL・SLAとファシリティマネジメント

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「サービスマネジメント」＞「サービスマネジメント」

---

## 0. 全体像 ― なぜこの分野を学ぶのか

前回のノート（プロジェクトマネジメント）では、プロジェクトという有期の活動をどう管理するかを見ました。本ノートでは視点をサービスの提供側に移し、システムを継続的にサービスとして提供し続けるための管理の枠組みと、それを支える物理的な設備の管理を扱います。プロジェクトが「始まりと終わりのある活動」であるのに対し、サービスマネジメントは「終わりのない継続的な活動」を対象とする点が、視点の転換にあたります。

本ノートは、次の2段階のストーリーで説明します。①まず、サービスを提供・管理するための世界標準の枠組みであるITILと、それを支える構成管理・サービスデスク・クラウド利用の形態、サービス品質の合意（SLA）を学びます。②次に、そのサービスを物理的に支える建物・設備をどう管理するかというファシリティマネジメントを見ます。

本分野は科目A-1・A-2ともに標準レベルの出題数ですが、A-2の出題対象7分野の一つであり、取りこぼしの許されない分野です。定番論点は、クラウドサービスの提供形態（IaaS・PaaS・SaaSなど）の識別と、電源設備・防災設備の名称と役割の対応です。前回までのノートで扱ったSLAや電源設備の知識ともつながるため、あわせて振り返りながら学習すると効率的です。

---

## 1. サービスをどう管理するか ― ITILとSLA

まず、システムをサービスとして継続的に提供・管理するための世界標準の枠組みを見ていきます。

### 1.1 ITILの全体像とベストプラクティス

前回のノートで名称だけ触れた**ITIL**は、特定の企業のノウハウではなく、業界で培われた優れた実践事例（**ベストプラクティス**）を体系化した、ITサービスマネジメントの指針です。自組織のプロセスを、他社の優れた事例と比較して改善点を見出す活動を**ベンチマーキング**と呼び、ITILの実践においてもこうした比較・改善の活動が重視されます。

ITILの考え方を公式な国際規格として標準化したものが**ISO/IEC 20000**です。要求事項を定めた**ISO/IEC 20000-1**（認証の対象となる規格本体）と、実践のための手引きを示した**ISO/IEC 20000-2**の2部構成になっています。前回のノートで見たPMBOKとISO 21500の関係と同様に、ITILが「事実上の標準（デファクトスタンダード）としてのベストプラクティス集」であるのに対し、ISO/IEC 20000は「公式な標準（デジュールスタンダード）としての認証規格」であるという対比で整理すると理解しやすくなります。

### 1.2 構成管理の基礎 ― インシデント、CI、CMDB

サービスの予期しない中断や品質低下を引き起こす出来事を**インシデント**と呼び、これを迅速に復旧させることがサービスマネジメントの重要な役割です。こうした管理の対象となる、サービスを構成する要素（ハードウェア、ソフトウェア、ドキュメントなど）の管理単位を**CI（構成品目）**と呼び、CIとその相互の関係性を記録・管理するデータベースを**CMDB（構成管理データベース）**と呼びます。前回のノートで扱ったハードウェア資源管理・ソフトウェア資源管理を、CIという統一された単位で体系的に一元管理する仕組みが、このCMDBとして位置づけられます。

### 1.3 利用者からの問い合わせをどう受けるか ― サービスデスクの形態

前回のノートで扱ったヘルプデスクをより体系的に整備したものがサービスデスクで、設置の仕方によって次のように分類されます。

| 形態 | 内容 |
|---|---|
| **ローカルサービスデスク** | 利用者の近くの拠点ごとに個別に設置する |
| **中央サービスデスク** | 1か所に集約して設置する |
| **バーチャルサービスデスク** | 物理的には分散していても、通信技術によって1つの窓口として機能させる |
| **フォローザサン** | 時差のある複数拠点のサービスデスクを連携させ、担当を順に引き継ぎながら24時間切れ目なく対応する |
| **コールセンタ** | 電話を主な手段として問い合わせに対応する窓口 |

ローカル・中央・バーチャルの3形態は「設置場所をどれだけ集約するか」という軸で整理できるのに対し、フォローザサンは「時間帯のカバレッジをどう広げるか」という別の軸に着目した運用形態である点が、両者を混同しないためのポイントです。

### 1.4 クラウドサービスの利用形態

自社で設備を保有せず、外部のサービスを利用する形態も広がっています。どこまでを自社で管理し、どこからをサービスとして借りるかによって、次のように整理されます。

| 形態 | サービスとして提供される範囲 |
|---|---|
| **HaaS／レンタルサーバ** | ハードウェア（サーバ機器そのもの） |
| **IaaS（Infrastructure as a Service）** | サーバ・ストレージ・ネットワークなどのインフラ |
| **PaaS（Platform as a Service）** | OSやミドルウェアなど、アプリケーションの実行基盤 |
| **FaaS（Function as a Service）** | 個々の処理（関数）の実行環境 |
| **SaaS（Software as a Service）** | アプリケーションソフトウェアそのもの |

HaaS・レンタルサーバからSaaSに向かうにつれて、サービス提供者が管理する範囲が広がり、逆に利用者が自分で構築・管理すべき範囲は狭くなっていくという抽象度の階層として整理すると、名称と特徴の対応が覚えやすくなります。

### 1.5 サービス品質を取り決める ― SLA

前回のノートで扱った**SLA（サービスレベル合意書）**は、本節で見たITILが定めるサービスマネジメントの枠組みの中で、サービス提供者と利用者があらかじめ品質水準を取り決める、中核的な文書として位置づけられます。1.4節のクラウドサービスの利用においても、提供される範囲に応じたSLAが結ばれ、稼働率や応答時間などの水準が合意されます。

## 2. サービスを支える物理的な環境 ― ファシリティマネジメント

サービスを継続的に提供するには、それを支える建物・設備という物理的な基盤も欠かせません。

### 2.1 ファシリティマネジメントの全体像

**ファシリティマネジメント**とは、建物や設備といった物理的な環境（ファシリティ）を、単なる維持管理の対象としてではなく、経営資源として総合的に計画・管理・活用する活動です。前回のノートで扱った設備管理は、このファシリティマネジメントのうち、電源や空調といった個々の設備を維持管理する実務的な一部として位置づけられます。

### 2.2 電源設備をどう構成するか

通常時に電力を供給する**主電源装置**に対し、これが使えなくなった際に代わりとなる**予備電源装置**をあらかじめ備えておくことが、電源設備の基本的な考え方です。予備電源装置の代表例が前回のノートで扱った**UPS（無停電電源装置）**で、停電時に一定時間バッテリーから電力を供給し続けます。UPSがあくまで短時間の橋渡しであるのに対し、**自家発電装置**は、電力会社からの供給が長時間途絶えた場合にも自組織で発電を続けられる設備です。「短時間の停電にはUPSで橋渡しし、長時間に及ぶ場合は自家発電に切り替える」という段階的な備えとして整理すると理解しやすくなります。電圧・周波数を安定させる**CVCF**・**AVR**も前回のノートと同様、電源が「止まらないこと」ではなく「質が安定していること」を守る、別の軸の対策として位置づけられます。

### 2.3 温度と湿度を管理する ― 空調設備

サーバ室などの温度・湿度を適正に保つ**空調設備**に加え、より高密度なサーバ環境では、水を用いてより効率的に冷却する**水冷設備**が使われることがあります。空気で冷やすか、水で冷やすかという冷却方式の違いとして押さえておきます。

### 2.4 災害・侵入から守る ― 防災設備

施設を災害や不正な侵入から守るための設備も、目的ごとに整理できます。

| 設備 | 役割 |
|---|---|
| **自動火災報知器** | 火災の発生を自動的に検知し、警報を発する |
| **窒素消火設備** | 窒素ガスなどの不活性ガスを放出して酸素濃度を下げ、消火する（水や薬剤を使わないため、サーバ機器への被害を抑えられる） |
| **広域災害対策** | 地震など、広い範囲に及ぶ災害に備える対策全般 |
| **バックアップセンタ** | 主要拠点が被災した場合に備え、遠隔地に設ける代替拠点 |
| **MDF（主配線盤）** | 建物全体の配線を集約する、中心となる配線盤 |
| **IDF（中間配線盤）** | 各フロアなどに設置され、MDFから配線を分岐させる配線盤 |
| **モニタテレビ** | 施設内外の様子を監視するための設備 |
| **入退室管理装置** | 施設への入退室を制御・記録する設備（これまでのノートで扱ったアクセス管理の物理版にあたる） |
| **ハウジング** | 自社のサーバ機器を、データセンター事業者の施設に設置し、電源・回線などのファシリティだけを借りる形態 |

自動火災報知器が「異常を検知して知らせる」のに対し、窒素消火設備は「実際に消火する」という、検知と対処の役割の違いで区別します。MDFとIDFは「建物全体を束ねるか、フロア単位の分岐か」という管理範囲の違いで区別します。ハウジングは、機器そのものは自社が所有し、設置場所と電源・回線というファシリティだけを借りる点が特徴で、1.4節で見たクラウドサービス（機能そのものをサービスとして借りる）とは対照的な、施設利用の一形態として位置づけられます。

### 2.5 その他の設備と環境配慮

ここまで見てきた予備電源装置などの、主要な設備を補助する予備的・付加的な設備を総称して**補完設備**と呼びます。また近年では、ファシリティマネジメントの役割は単なる設備の維持管理にとどまらず、環境負荷の算定・削減という持続可能性の観点にも広がっています。**GHGプロトコル**は、温室効果ガス（Greenhouse Gas）の排出量を算定・報告するための国際的な基準で、データセンターなどの設備運用が環境に与える影響を定量的に把握するために用いられます。

## 3. 試験対策まとめ（重要ポイント）

- **ITIL と ISO/IEC 20000**：ベストプラクティス集（デファクトスタンダード）か、公式な認証規格（デジュールスタンダード）かの違い。前回のPMBOKとISO 21500の関係と同じ構図。
- **CI と CMDB**：管理の単位そのものか、それを記録・管理するデータベースかの違い。
- **ローカル／中央／バーチャルサービスデスク と フォローザサン**：設置場所の集約度の軸と、時間帯のカバレッジの軸という、異なる2つの分類軸を区別する。
- **HaaS／レンタルサーバ〜SaaS**：提供される範囲が広がるほど、利用者が管理すべき範囲が狭くなるという抽象度の階層。5つの形態の並び順を押さえる。
- **UPS と 自家発電装置**：短時間の橋渡しか、長時間の対応かという時間軸の違い。CVCF・AVRは電源の質を安定させる別軸の対策。
- **自動火災報知器 と 窒素消火設備**：異常を検知するか、実際に消火するかという役割の違い。
- **MDF と IDF**：建物全体を束ねる配線盤か、フロア単位の配線盤かという管理範囲の違い。
- **ハウジング**：機器は自社所有のまま、設置場所と電源・回線だけを借りる形態として、クラウドサービスとの対比で押さえる。
- **GHGプロトコル**：ファシリティマネジメントが環境負荷の算定・削減にも役割を広げていることを示す基準。
