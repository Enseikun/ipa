# レクチャーノート：開発技術 ― システム開発技術＞開発環境と開発手法

対応範囲：情報処理安全確保支援士試験（科目A-1／科目A-2共通）「開発技術」＞「システム開発技術」・「ソフトウェア開発管理技術」

---

## 0. 全体像 ― なぜこの分野を学ぶのか

これまでのノートでは、技術要素（セキュリティ）を扱い、システムをどう守るかという視点で見てきました。本ノートからは開発技術に視点を移し、そもそも情報システムをどのような手順・環境・進め方で作り上げるかを扱います。「守る」から「作る」への転換ですが、開発工程自体にも品質・スケジュール・コストという守るべき制約があり、両者は無関係ではありません。

本ノートは、次の3段階のストーリーで説明します。①まず、システム開発が実際にどのような工程で進むか、その基本的な流れを掴みます。②次に、その工程を支える開発環境・アーキテクチャと、近年主流になりつつあるアジャイル開発などの開発手法を見ます。③最後に、開発の進め方を型として捉えるプロセスモデルと、規模・コストを数値で見積もるコストモデルを学びます。

システム開発技術・ソフトウェア開発管理技術は、情報処理安全確保支援士試験の科目A-2では各1問と出題数こそ多くありませんが、A-2に登場する以上は取りこぼしが許されない中優先分野です。特にシステム開発技術は、科目B（技能）の「情報システムの企画・設計・開発・運用におけるセキュリティ確保の推進・支援」という業務観点に直結するため、単なる用語暗記ではなく、開発の実務プロセスとして理解しておくことが得点効率を高めます。定番論点は、開発工程の順序と成果物の対応、アジャイルとウォーターフォールの対比、コストモデルの計算方法です。

## 1. システム開発の工程 ― 何を、どの順で作るか

開発環境や手法を学ぶ前に、まずシステム開発がどのような工程を経て進むのか、基本的な流れを押さえます。

### 1.1 システム開発工程の基本的な流れ

システム開発は、次のように上流から下流へ、大きな視点から小さな視点へと順に具体化していく工程として進みます。

| 工程 | 内容 |
|---|---|
| **システム要件定義** | システム全体として実現すべき機能・性能を明確にする |
| **システム設計** | システムを、ハードウェア・ソフトウェアなどの構成要素に分割する |
| **ソフトウェア要件定義** | ソフトウェアが満たすべき機能・仕様を明確にする |
| **ソフトウェア設計** | ソフトウェア全体の構造（アーキテクチャ）を設計する |
| **ソフトウェア詳細設計** | 個々のモジュール（プログラム単位）の内部処理を設計する |
| **プログラム作成及び単体テスト** | 詳細設計に基づきコーディングし、モジュール単体で動作を確認する |
| **ソフトウェア統合テスト** | モジュールを結合し、ソフトウェアとして正しく連携するかを確認する |
| **システム統合テスト** | ソフトウェアとハードウェアを結合し、システム全体として要件を満たすかを確認する |

この並びは、前半の「要件定義→設計→詳細設計」という分割していく工程と、後半の「単体テスト→統合テスト→システム統合テスト」という組み上げていく工程が、対になっていることが特徴です。どの設計工程で定義した内容を、どのテスト工程で検証するかという対応関係（設計を分割した順とテストで結合する順が逆になる、いわゆるV字の形）が、試験でも問われるポイントです。

### 1.2 各工程を精緻化する視点 ― 設計とテストの技法

上記の工程を実際に進める際には、次のような具体的な技法が使われます。

**デザインパターン**とは、ソフトウェア設計において繰り返し現れる典型的な問題とその解決策を、再利用可能な形でまとめたものです。ソフトウェア設計工程・ソフトウェア詳細設計工程で、既知の問題をゼロから考え直さずに済むという効率化の役割を果たします。

設計・テストの各局面では、対象を明確に定義する作業が欠かせません。**インタフェース設計**は、モジュール間や画面と利用者の間で、どのようにデータをやり取りするかを定義する設計作業です。これに対応してテストの設計も工程ごとに分かれており、**ソフトウェアユニットテストの設計**はモジュール単体の振る舞いを検証する観点の設計、**ソフトウェア統合テストの設計**はモジュールを結合した際の連携を検証する観点の設計です。統合テストの設計にあたっては、**リーンソフトウェア開発**（無駄な工程・成果物を徹底的に排除し、価値を生む活動に集中するという開発思想）の考え方を取り入れ、過剰なテストケースを削ぎ落とし効率よく品質を確認する工夫が意識されます。

インタフェース設計が「モジュール同士がどうつながるか」を定義する工程であるのに対し、テスト設計は「そのつながりが正しいかをどう確かめるか」を定義する工程であるという、設計と検証の対応関係として捉えると整理しやすい論点です。

### 1.3 開発工程を評価し、方針を組み込む

工程がひととおり定義できたら、それが適切に実行されているかを評価する視点と、工程の初期段階から特定の方針を組み込む視点が加わります。

**アセスメント**とは、対象を一定の基準に照らして評価することです。とりわけ**プロセスアセスメント**は、成果物そのものではなく、それを生み出す開発プロセス自体の成熟度を評価する活動を指します。個々のテスト結果を見る1.2節の技法が「作られたものの品質」を確認するのに対し、プロセスアセスメントは「作り方の質」を評価するという、対象のレベルが一段階上がった発展形として位置づけられます。

近年は、要件定義・設計の段階からあらかじめ特定の方針を組み込む「バイデザイン」の発想が重視されています。**オープンデータバイデザイン**は、公共機関などが保有するデータを、開発の初期段階から原則公開することを前提に設計する考え方です。前回のノートで扱ったセキュリティ対策における「初期段階から組み込む」発想（プライバシーバイデザインなど）と同じ設計思想を、データ公開の文脈に適用したものとして位置づけられます。

システム開発技術は特定の業種に限らず様々な業務システムに応用されます。例えば、電話とコンピュータを連携させる**CTI（Computer Telephony Integration）**は、コールセンター業務システムの代表例であり、要件定義段階で応答時間や着信振り分けといった業務要件を明確化する題材として扱われることがあります。開発工程そのものというより、開発対象となる業務システムの一例として押さえておくとよいでしょう。

## 2. 開発を支える環境と手法 ― CASEからアジャイルへ

工程の流れを押さえたところで、次はその工程を効率よく進めるための環境・アーキテクチャ・開発手法を見ていきます。

### 2.1 開発を支援するツールと資産の管理 ― CASEとリポジトリ

**CASE（Computer Aided Software Engineering）**とは、システム開発の各工程をソフトウェアツールによって支援する取り組み全般を指します。支援する工程の範囲によって、次のように分類されます。

| 分類 | 支援する工程 |
|---|---|
| **上流CASE** | 要件定義・設計など、開発の初期工程 |
| **下流CASE** | プログラム作成・テストなど、開発の後半工程 |
| **保守CASE** | リリース後の保守・改修工程 |
| **統合CASE** | 上流から保守まで、複数の工程を一貫して支援する |

CASEツールが生成・管理する設計書やプログラムなどの成果物を一元的に格納するデータベースが**リポジトリ**です。工程ごとに個別のファイルで管理するのではなく、リポジトリに集約することで、成果物間の整合性を保ちやすくなります。CASEの分類が「どの工程を支援するか」という範囲の違いであるのに対し、リポジトリはその支援を裏で支える共通基盤として位置づけられます。

### 2.2 既存資産をどう活かすか ― リエンジニアリングとその周辺

新規開発だけでなく、既存のシステムを活用・再構築する場面でも、開発技術の知識が使われます。

- **フォワードエンジニアリング**：要件定義から設計、実装へと、通常どおり上流から下流へ進める開発の進め方。
- **リバースエンジニアリング**：既存のプログラムを解析し、そこから設計書や仕様といった、より上流の情報を逆算して抽出すること。
- **リエンジニアリング**：リバースエンジニアリングで既存システムの設計情報を抽出したうえで、それをもとに新しい技術や構造で再度フォワードエンジニアリングを行い、システムを作り直すこと。

3つの用語は「開発を進める方向」で整理すると分かりやすく、フォワードは上流から下流への通常の流れ、リバースはその逆方向、リエンジニアリングはリバースとフォワードを組み合わせた往復として位置づけられます。

### 2.3 システムの構造をどう分割するか ― アーキテクチャの選択

システム全体をどのような単位に分割して構築するかも、開発の重要な設計判断です。

- **モノリシックアーキテクチャ**：システムの全機能を一つのまとまったプログラムとして実装する、伝統的な構造。
- **マイクロサービスアーキテクチャ**：機能ごとに独立した小さなサービスに分割し、それぞれを個別に開発・デプロイ・スケールできるようにする構造。

モノリシックは開発・デプロイがシンプルな反面、機能追加のたびにシステム全体に影響が及びやすいという弱点があります。マイクロサービスはこの弱点を克服する発展形ですが、サービス間の連携（通信）が複雑になるという新たなトレードオフを抱えます。この「分割の粒度と、連携の複雑さ」のトレードオフが試験でも問われるポイントです。

### 2.4 変化に迅速に対応する開発手法 ― アジャイルソフトウェア開発

従来の、工程を順番に一度だけ通過する開発の進め方に対し、短い期間で開発とレビューを繰り返しながら進める考え方の総称が**アジャイル（ソフトウェア開発）**です。要件の変化が多い開発に適しており、2.3節のマイクロサービスアーキテクチャとも相性がよいとされます。

アジャイルを実践する代表的な手法が**XP（エクストリームプログラミング）**で、次のような具体的なプラクティス（実践項目）から構成されます。

- **ペアプログラミング**：2人一組になり、1台の端末で相互にレビューしながらコーディングを進める手法。
- **リファクタリング**：外部から見た動作を変えないまま、プログラムの内部構造を整理・改善すること。

アジャイルが開発全体の考え方（上位概念）、XPがその具体的な手法の一つ、ペアプログラミングとリファクタリングがXPを構成する個々のプラクティス（下位の実践項目）という包含関係で整理すると理解しやすくなります。

## 3. 進め方の型と規模の見積もり ― プロセスモデルとコストモデル

最後に、開発全体の進め方を型としてどう捉えるか、そしてその規模・コストをどう数値化するかを見ていきます。

### 3.1 開発の進め方を型として捉える ― プロセスモデル

システム開発全体の進め方は、いくつかの典型的な型（プロセスモデル）に整理されます。

| モデル | 特徴 |
|---|---|
| **ウォーターフォールモデル** | 工程を上流から下流へ順番に進め、原則として後戻りしない |
| **プロトタイピングモデル** | 早い段階で試作品（プロトタイプ）を作り、利用者に確認してもらいながら要件を固める |
| **スパイラルモデル** | 小規模な開発（設計→実装→評価）を繰り返しながら、リスクを分析しつつ徐々に完成度を高める |
| **RAD（Rapid Application Development）** | スパイラルアプローチを土台に、**タイムボックス**と呼ばれる短い期間で区切って開発を進め、開発期間そのものを短縮する手法 |

ウォーターフォールが「後戻りしない直線的な進め方」であるのに対し、プロトタイピングとスパイラルは「試作・評価を繰り返しながら進める」という反復型の発想を持つ点が対比のポイントです。RADはスパイラルモデルの考え方をさらに進め、期間を区切ることで開発速度を優先する発展形として位置づけられます。

これらに加えて、次のような進め方も併せて押さえます。**インクリメンタルモデル**は、システムを複数の機能単位に分割し、段階的に開発・追加していく進め方です。**継続的インテグレーション（CI）**は、コードの変更を頻繁に統合し、そのたびに自動テストを実行することで問題を早期に発見する実践であり、2.4節のアジャイル開発と組み合わせて用いられます。また、開発の進め方が要件の確定度によって変わるのと同様に、それを外部委託する際の**契約モデル**も進め方に応じて選ばれます。要件が確定しているウォーターフォール型の開発では成果物の完成を約束する請負契約が、要件が変化しやすいアジャイル型の開発では稼働工数を提供する準委任契約が選ばれやすいという対応関係が、実務・試験の両面で問われる論点です。

### 3.2 規模とコストを数値で見積もる ― コストモデル

開発規模やコストを主観に頼らず見積もるための手法が、コストモデルです。

- **FP法（ファンクションポイント法）**：画面数や帳票数、データ項目数といった機能の数と複雑さから、開発規模を見積もる手法。利用者から見える機能を基準にするため、開発言語や手法に左右されにくい。
- **COCOMO**：開発するソースコードの行数（LOC）をもとに、統計的な経験式から開発工数を見積もる手法。
- **COCOMO II**：COCOMOを、ソフトウェアの再利用やオブジェクト指向開発など、現代的な開発形態に合わせて改良した後継モデル。

FP法が「利用者から見た機能の量」を基準にするのに対し、COCOMO（およびCOCOMO II）は「開発者が書くコードの量」を基準にするという、見積もりの視点の違いが対比のポイントです。COCOMOとCOCOMO IIは、旧モデルとその発展形という関係として押さえておきます。

### 3.3 開発と運用を結ぶ ― DevOps

**DevOps**とは、開発（Development）と運用（Operations）が緊密に連携し、3.1節の継続的インテグレーションなどを通じて、変更を高頻度かつ安全にリリースし続けるという文化・手法です。2.4節のアジャイル開発が「開発工程そのもの」を短いサイクルで回す発想であるのに対し、DevOpsはその発想を運用までひと続きに拡張したものとして位置づけられます。開発から運用までを分断せず一体で捉える点が、従来のウォーターフォール的な進め方との最大の違いです。

## 4. 試験対策まとめ（重要ポイント）

- **システム開発工程の8段階**：要件定義・設計を分割していく前半と、テストで組み上げていく後半が対になる構造（V字の対応関係）を押さえる。
- **上流CASE と 下流CASE と 保守CASE と 統合CASE**：CASEツールが支援する工程の範囲による分類。リポジトリはそれらを支える成果物の一元管理基盤。
- **フォワードエンジニアリング と リバースエンジニアリング と リエンジニアリング**：開発を進める方向（上流→下流、下流→上流、その往復）で区別する。
- **モノリシックアーキテクチャ と マイクロサービスアーキテクチャ**：分割の粒度と、連携の複雑さのトレードオフ。
- **アジャイル と XP と ペアプログラミング／リファクタリング**：考え方（アジャイル）→手法（XP）→実践項目（プラクティス）という包含関係。
- **ウォーターフォールモデル と プロトタイピングモデル と スパイラルモデル と RAD**：後戻りしない直線型か、試作・反復を繰り返す型か。RADはスパイラル＋タイムボックスによる高速化。
- **請負契約 と 準委任契約**：ウォーターフォール型は成果物完成を約束する請負、アジャイル型は工数提供を約束する準委任に親和性が高い。
- **FP法 と COCOMO／COCOMO II**：見積もりの基準が「利用者から見た機能量」か「開発者が書くコード量」かで区別する最頻出の識別問題。
- **プロセスアセスメント**：成果物ではなく、開発プロセス自体の成熟度を評価する活動である点を押さえる。
- **DevOps**：アジャイルの考え方を運用まで拡張し、開発と運用を一体で捉える文化・手法として位置づける。
