# レクチャーノート：ストラテジ系 ― 情報システム戦略とシステム規格

対応範囲：情報処理安全確保支援士試験（科目A-1）「ストラテジ系」＞「システム戦略」・「システム企画」＞「情報システム戦略」・「システム化計画」・「要件定義」・「調達計画・実施」

---

## 0. 全体像 ― なぜこの分野を学ぶのか

これまでのノートでは、技術要素・開発技術・マネジメント系という、情報システムを作り、動かし、管理する側の知識を見てきました。本ノートでは視点をさらに引き上げ、経営の視点から情報システムをどう位置づけ、計画し、調達するかというストラテジ系の知識を扱います。個々のプロジェクトやシステムの内側から、組織全体・経営の外側へと視点が移る回です。

本ノートは、次の3段階のストーリーで説明します。①まず、組織全体を最適化する計画をどう立て、それを個別のシステム化計画に落とし込むかを見ます。②次に、その青写真を体系的に描く手法であるエンタープライズアーキテクチャを学びます。③最後に、具体的なシステムの要求をどう定義し、外部からどう調達するかを扱います。

ストラテジ系（システム戦略・システム企画）は、情報処理安全確保支援士試験の科目A-2の出題対象7分野には含まれない、科目A-1のみの分野です。出題数自体は他分野と比べて多くありませんが、A-1では幅広く浅く出題されるため、深追いはせず典型論点の名称と特徴の対応を押さえることを優先します。

## 1. 組織全体をどう計画するか ― 全体最適化計画とシステム化計画

まず、経営の視点から情報システムをどう計画するかという、最上位の考え方を見ていきます。

### 1.1 全体最適化計画とシステム化計画の関係

**全体最適化計画**とは、個々の部門や業務ごとの部分最適ではなく、組織全体の業務とシステムを俯瞰し、経営戦略と結びつけて最適化する計画です。この全体最適化計画を踏まえ、具体的にどのシステムを、いつ、どのように情報システム化していくかを計画するのが**システム化計画**です。全体最適化計画が組織全体を俯瞰する上位の計画であり、システム化計画はそれを個別のシステムに落とし込む下位の計画であるという、包含関係として押さえておきます。

### 1.2 計画を支える基盤的な考え方

こうした計画を経営の視点から方向づけ、統制する枠組みが**ITガバナンス**です。以前のノートでは情報セキュリティガバナンスを発展させた概念として触れましたが、本節では情報システム戦略全体を経営の意思決定に組み込む、より広い枠組みとして改めて位置づけます。また、組織内に散在する知識やノウハウを共有・活用する経営管理の考え方を**ナレッジマネジメント**と呼び、全体最適化計画を支える情報基盤の一つとして位置づけられます。

### 1.3 業務とシステムをモデルで捉える

計画を具体化する過程では、対象を段階的にモデル化していきます。

- **ビジネスモデル**：組織がどのように収益を生み出すかという、事業の仕組みそのものを表すモデル。
- **ビジネスプロセスモデル**：ビジネスモデルを実現するための、業務の流れ（プロセス）を表すモデル。
- **業務モデル**：実際の業務の手順やデータの流れを、より具体的に表現したモデル。
- **情報システムモデル**：業務モデルをもとに、それを支える情報システムの構造を表現したモデル。

この4つは、ビジネスモデル→ビジネスプロセスモデル→業務モデル→情報システムモデルという順に、抽象度の高い事業の仕組みから、具体的なシステムの構造へと段階的に具体化していく発展の関係として整理すると理解しやすくなります。

### 1.4 計画の前提となる技術動向と管理基準

全体最適化計画を立てる際には、活用すべき技術動向と、拠り所となる管理基準も押さえておく必要があります。**ビッグデータ**とは、従来の管理・処理手法では扱いきれないほど大量・多様で、高速に生成されるデータ群のことで、全体最適化計画において活用の対象として位置づけられます。**BYOD（Bring Your Own Device）**とは、従業員が私物の情報端末を業務に利用する運用形態で、利便性が高い一方、以前のノートで扱ったアクセス管理などのセキュリティ上の統制が課題となります。

これらの計画・運用全般の拠り所となるのが**システム管理基準**で、情報システムの企画・開発・運用・保守にわたる管理のあるべき姿を示した基準です。以前のノートで扱ったシステム監査基準が「監査する側」の拠り所であるのに対し、システム管理基準は「情報システムを企画・運用する側」の拠り所であるという役割の違いで対比すると整理しやすくなります。

## 2. 組織の設計図をどう描くか ― エンタープライズアーキテクチャ

全体最適化計画という考え方を、具体的な設計図として体系立てて描くための方法論を見ていきます。

### 2.1 EAの基本的な考え方

組織の業務とシステムの全体像を、統一的な視点で表現する設計図の考え方を**アーキテクチャモデル**と呼びます。これを用いて、組織全体の業務とシステムを統一的に最適化するための設計手法・考え方が**EA（エンタープライズアーキテクチャ）**です。1.1節で見た全体最適化計画という「考え方」を、具体的な「設計図」として描き出すための方法論として位置づけられます。

### 2.2 EAの4つの構成要素

EAは、次の4つの階層（アーキテクチャ）から構成されます。

| 構成要素 | 内容 |
|---|---|
| **ビジネスアーキテクチャ** | 組織、業務機能、業務プロセスといった業務の構造を表す |
| **データアーキテクチャ** | 業務で扱うデータの構造・流れを表す |
| **アプリケーションアーキテクチャ** | データアーキテクチャを実現するアプリケーションの構成を表す |
| **テクノロジアーキテクチャ** | アプリケーションを支えるハードウェア・ネットワークなどの技術基盤を表す |

この4層は、「業務（ビジネス）→データ→アプリケーション→技術基盤」という、上流から下流への具体化の順で捉えると理解しやすくなります。

ビジネスアーキテクチャを具体的に記述する技法として、業務の機能を階層的に細分化して整理する**DMM（Diamond Mandala Matrix）**と、業務の処理の流れ（ワークフロー）を表現する**WFA（Work Flow Architecture）**があります。DMMが業務を「静的な機能の構造」として分解するのに対し、WFAは「動的な処理の流れ」として表現するという対比で整理すると区別しやすくなります。

アプリケーションアーキテクチャを実現する代表的な設計思想が**SOA（サービス指向アーキテクチャ）**で、業務機能を独立した「サービス」として部品化し、それらを組み合わせてシステムを構築する考え方です。これまでのノートで扱ったマイクロサービスアーキテクチャは、このSOAの発想をさらに小さな単位へと推し進めた発展形として位置づけられます。

### 2.3 システム間を連携させる ― EAI

**EAI（Enterprise Application Integration）**とは、組織内に存在する複数の異なるシステム・アプリケーションを連携させ、データやプロセスを統合する仕組み・手法です。SOAが「個々の業務機能をサービスとして部品化して組み立てる」設計思想であるのに対し、EAIは「既存の複数システムをつなぎ合わせて統合する」ための手段であるという、目的と手段の違いで対比すると整理しやすくなります。

### 2.4 現状から理想への道筋を描く ― その他の手法

EAを整理するための代表的なフレームワークが**ザックマンフレームワーク**で、「誰が・何を・どこで・いつ・なぜ・どのように」という複数の視点と、抽象度の異なる複数の階層を組み合わせたマトリクスによって、組織のアーキテクチャを体系的に整理します。

EAの検討では、現状の業務・システムの姿を表す**As-Isモデル**と、将来あるべき理想の姿を表す**To-Beモデル**を対比しながら、両者のギャップを埋める計画を立てます。こうしたモデルを描く際に参考となる、業界横断的に再利用できるよう標準化されたひな形が**EA参照モデル**で、ビジネス・データ・アプリケーション・テクノロジの各アーキテクチャに対応する参照モデル群が用意されています。

## 3. 要求をどう定義し、外部からどう調達するか

組織全体の設計図が描けたところで、最後に個別のシステムの要求をどう定義し、外部にどう発注・調達するかを見ていきます。

### 3.1 要求をどう分析し、定義するか

**要求分析**とは、利用者・関係者が本当に必要としていることを聞き出し、整理する活動です。これをもとに、実現すべき仕様として明確に文書化する活動が**要件定義**です。要件定義にあたっては、以前のノートで扱ったデータ中心アプローチ（データの構造を起点に設計を進める考え方）を、この段階から適用することもあります。

要件定義は、扱う対象によってさらに次の3種類に分けられます。

- **業務要件定義**：業務としてどのような処理・ルールが必要かを定義する。
- **機能要件定義**：システムが持つべき具体的な機能を定義する。
- **非機能要件定義**：性能、信頼性、セキュリティなど、機能以外の品質面の要件を定義する。

### 3.2 外部に発注するための文書

システムの構築を外部のベンダに依頼する際には、段階を踏んで文書をやり取りします。**RFI（情報提供依頼書）**は、発注者がベンダに製品・技術に関する情報提供を求める文書で、**RFP（提案依頼書）**は、調達したいシステムの要件を示し、ベンダに具体的な提案を求める文書です。RFIで情報を広く集めたうえで、RFPによって具体的な提案を絞り込んでいくという、調達プロセスの前後関係として押さえておきます。

### 3.3 どのように調達先を選ぶか

**調達**とは、必要な製品・サービスを外部から取得する活動全般です。公的な調達では、公告によって広く参加者を募る**一般競争入札**が原則となり、落札者の決め方には次の2つの方式があります。

- **最低価格落札方式**：入札者の中で最も低い価格を提示した者を落札者とする。
- **総合評価落札方式**：価格だけでなく、技術力や提案内容などを含めて総合的に評価し、落札者を決める。

最低価格落札方式が「価格のみ」で判断するのに対し、総合評価落札方式は「価格と質の両方」で判断するという評価基準の違いで区別します。また、調達にあたって環境負荷の少ない製品・サービスを優先的に選ぶ**グリーン購入**という考え方も、公共調達を中心に重視されています。

### 3.4 ハードウェア調達の特殊な形態 ― 半導体産業の分業構造

半導体のようなハードウェアの調達では、設計と製造が別会社に分業される独特の構造があります。自社で製造設備（工場、ファブ）を持たず、設計に特化する企業形態を**ファブレス**、逆に自社では設計を行わず、他社からの委託を受けて製造に特化する企業形態を**ファウンドリ**と呼びます。設計から製造まで自社で一貫して行う、分業しない従来型の企業形態は**IDM（垂直統合型デバイスメーカ）**と呼ばれ、ファブレス・ファウンドリという分業構造と対比されます。

このほかにも、回路設計の一部（IPコア）をライセンスとして提供する**IPプロバイダ**、ファブレス企業に代わって設計業務を代行する**デザインハウス**といった、より細分化された専門企業が分業構造に加わっています。IDMが「分業しない一貫体制」であるのに対し、ファブレス・ファウンドリ・IPプロバイダ・デザインハウスは、それぞれ設計・製造・回路設計・設計代行という工程の一部に特化した分業体制であるという対比で整理すると理解しやすくなります。

## 4. 試験対策まとめ（重要ポイント）

- **全体最適化計画 と システム化計画**：組織全体を俯瞰する上位計画か、個別のシステム化に落とし込む下位計画かという包含関係。
- **ビジネスモデル→ビジネスプロセスモデル→業務モデル→情報システムモデル**：抽象度の高い事業の仕組みから、具体的なシステム構造へと具体化していく段階を押さえる。
- **EAの4アーキテクチャ**：ビジネス→データ→アプリケーション→技術基盤という具体化の順序を押さえる。
- **DMM と WFA**：業務を静的な機能の構造として分解するか、動的な処理の流れとして表現するかの違い。
- **SOA と EAI**：業務機能をサービスとして部品化する設計思想か、既存の複数システムをつなぎ合わせる統合の手段かという目的と手段の違い。
- **As-Isモデル と To-Beモデル**：現状の姿を表すか、将来あるべき理想の姿を表すかの違い。
- **RFI と RFP**：情報提供を求める段階か、具体的な提案を求める段階かという調達プロセスの前後関係。
- **最低価格落札方式 と 総合評価落札方式**：価格のみで判断するか、価格と質の両方で判断するかの違い。
- **ファブレス と ファウンドリ と IDM**：設計に特化するか、製造に特化するか、それとも一貫して行うかという分業構造の違い。
