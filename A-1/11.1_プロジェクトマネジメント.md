# レクチャーノート：プロジェクトマネジメント ― スコープ・品質・リスクマネジメント

対応範囲：情報処理安全確保支援士試験（科目A-1）「プロジェクトマネジメント」＞「プロジェクトマネジメント」（スコープ、品質、リスク）

---

## 0. 全体像 ― なぜこの分野を学ぶのか

これまでのノートでは、開発技術・サービスマネジメントという「システムそのもの」を作り、動かし、保守する知識を見てきました。本ノートでは視点をプロジェクト運営そのものに移し、限られた期間・予算の中でどう作業範囲を定め、品質を保証し、リスクに備えるかという、プロジェクトマネジメントの中核を扱います。

本ノートは、次の3段階のストーリーで説明します。①まず、プロジェクトの作業範囲をどう定義し、分解し、進捗を数値で管理するか（スコープとWBS、EVM）を学びます。②次に、こうしたマネジメント活動全体を体系立てる知識体系と、品質をどう計画・保証・管理するかを見ます。③最後に、プロジェクトに潜むリスクをどう分析し、対応するかを扱います。

プロジェクトマネジメントは、情報処理安全確保支援士試験の科目A-2の出題対象（7分野）には含まれない一方、科目A-1では平均2.0問と、セキュリティに次いで高頻度に出題される分野です。科目A-2で出題されないからといって軽視せず、A-1対策として重点的に取り組む価値があります。定番論点は、EVMの各指標（CPI・SPIなど）の計算、WBS・OBSの役割の違い、定量的リスク分析・定性的リスク分析の識別です。

---

## 1. 作業範囲をどう定義し、進捗を数値で管理するか

まず、プロジェクトが「何を」「どこまで」行うのかを定義し、その進み具合をどう分解・測定するかを見ていきます。

### 1.1 プロジェクトの範囲を定義する ― プロジェクトスコープマネジメント

**プロジェクトスコープマネジメント**とは、プロジェクトで実施すべき作業の範囲（スコープ）を定義し、それ以外の作業を含めないように管理する活動です。範囲が際限なく広がってしまう事態（スコープクリープ）を防ぐことが主な目的です。

プロジェクトの出発点となるのが**プロジェクト憲章**で、プロジェクトの存在を正式に認可し、目的・概要やプロジェクトマネージャの権限などを記した、プロジェクトにおける最上位の公式文書です。スコープはこの憲章を土台に定義されます。チームの一体感を高め、認識の齟齬を防ぐ工夫として**コロケーション**（チームメンバーを同じ場所に集めて作業させること）があり、スコープの認識をそろえるコミュニケーション上の工夫として位置づけられます。

### 1.2 作業を分解する ― WBS

プロジェクト全体の作業は、そのままでは大きすぎて管理できないため、階層的に分解します。この分解の構成図が**WBS（Work Breakdown Structure）**で、前回のノートではボトムアップ見積りの基礎技法として扱いましたが、本節では作業範囲を分解する技法そのものとして改めて位置づけます。WBSで分解した最下位の作業単位を**ワークパッケージ**と呼び、これ以上分解せず、実際の見積り・進捗管理の対象とします。

WBSが「何を」分解するかを表すのに対し、「誰が（どの組織・担当）」その作業を担うかを表す構成図が**OBS（Organization Breakdown Structure）**です。WBSとOBSを組み合わせることで、作業と担当の対応関係（責任分担）が明確になります。前回のノートで扱った**標準タスク法**は、このWBSに基づき、標準的な作業単位ごとに工数を積み上げる見積り手法として、ここでも接続して理解できます。WBSの各要素（ワークパッケージ）について、内容・担当・スケジュールなどの詳細情報を記述した文書を**WBS辞書**と呼びます。

### 1.3 進捗と実績を数値で管理する ― EVM

**EVM（Earned Value Management、出来高管理）**とは、プロジェクトのコストとスケジュールの実績を、金額に換算した「価値」で統合的に管理する手法です。次の指標を組み合わせて使います。

| 指標 | 意味 |
|---|---|
| **PV（計画価値）** | ある時点までに計画上完了しているはずの作業の予算額 |
| **EV（出来高）** | ある時点までに実際に完了した作業を、計画時点の予算額に換算した値 |
| **AC（実コスト）** | ある時点までに実際にかかった費用 |
| **BAC（完成時総予算）** | プロジェクト完了時点での総予算 |
| **EAC（完成時総コスト見積り）** | これまでの実績を踏まえて再計算した、完了時点でのコスト見積り |

これらをもとに、プロジェクトの効率を次の2つの指数で評価します。

- **CPI（コスト効率指数）＝ EV ÷ AC**：かけた費用に対してどれだけ出来高を上げられたかを表し、1より大きければコスト効率が良い（予算内で進んでいる）ことを意味します。
- **SPI（スケジュール効率指数）＝ EV ÷ PV**：計画に対してどれだけ出来高を上げられたかを表し、1より大きければ計画より進んでいることを意味します。

どちらも「出来高（EV）を、何と比べるか」で意味が変わる点が計算のポイントで、コスト（AC）と比べればコスト効率、計画（PV）と比べればスケジュール効率になるという対応関係が、試験での計算問題の着眼点です。コストや期間の見積り自体には、過去の実績データと規模などのパラメータの統計的な関係を用いる**パラメトリック見積法**も使われ、前回のノートで扱ったFP法やCOCOMOと同じ発想の見積り手法として位置づけられます。

## 2. マネジメントを体系化する知識体系と品質マネジメント

個々の技法の背景にある、プロジェクトマネジメント全体を体系立てる知識体系と、品質をどう扱うかを見ていきます。

### 2.1 プロジェクトマネジメントを体系化する

**PMBOK**とは、米国のPMI（Project Management Institute）が策定した、プロジェクトマネジメントの知識体系をまとめたガイドです。このPMBOKの知識に基づく国際資格が**PMP（Project Management Professional）**で、PMBOKが「知識体系そのもの」であるのに対し、PMPは「その知識を身につけていることを認定する資格」という、知識と資格の関係として位置づけられます。

PMBOKが米国の団体による事実上の標準（デファクトスタンダード）であるのに対し、**ISO 21500:2012**（日本では**JIS Q 21500:2018**として規格化）は、国際標準化機構が策定した公式な標準（デジュールスタンダード）です。どちらもプロジェクトマネジメントの考え方を体系化したものですが、策定主体の性質が異なる点で区別されます。

プロジェクトを進める際に忘れてはならないのが**ステークホルダ**（プロジェクトに利害関係を持つすべての人・組織）です。1章のスコープや、本章で扱う品質の基準は、このステークホルダの要求を踏まえて定義される点が、プロジェクトマネジメント全体を貫く前提になります。

### 2.2 品質をどう計画し、保証し、管理するか

品質に関する活動を組織的・継続的に行う仕組みを**QMS（品質マネジメントシステム）**と呼びます。これまでのノートで扱ったISMS（情報セキュリティマネジメントシステム）と同じ「継続的に管理・改善する仕組み」という発想を、品質という対象に適用したものとして理解できます。

プロジェクトの品質に関する活動は、次の流れで進みます。

1. **品質計画**：プロジェクトにおいてどのような品質基準を満たすべきかを計画する。
2. **品質マネジメント計画書**：品質計画の内容（基準、責任、活動など）を文書化する。
3. **品質測定基準**：品質が達成されたかどうかを判定するための、具体的で測定可能な基準を定める。

品質を確保する活動そのものは、さらに次の2つに分かれます。

- **品質保証**：定められたプロセスが正しく実行されているかを確認し、品質が満たされる見込みを保証する活動（プロセスに着目した、予防的な活動）。
- **品質管理**：実際の成果物を検査し、基準を満たしているかを確認する活動（成果物に着目した、検出的な活動）。前回までのノートで扱ったQC七つ道具は、この品質管理の分析に用いられます。

品質保証と品質管理の違いは、以前のノートで扱った欠陥防止（予防）と欠陥除去（検出）の対比に対応する形で整理すると理解しやすくなります。

なお、品質そのものではなく、マネジメントを行う人材の実務能力を評価する手法として**インバスケット**があります。これは、未処理の案件を短時間で大量に提示し、優先順位付けや判断力を測る演習形式で、品質マネジメントの技法というより、プロジェクトマネージャなどの人材育成・評価の文脈で登場する用語として押さえておきます。

## 3. プロジェクトに潜むリスクをどう分析し、対応するか

最後に、プロジェクトの成否を左右するリスクを、どう洗い出し、分析し、対応するかを見ていきます。

### 3.1 リスクマネジメントの基本

以前のノートで扱ったリスクマネジメントの基本的な考え方は、プロジェクトマネジメントの文脈でもそのまま使われます。損失しかもたらさない**純粋リスク**と、利益ももたらしうる**投機的リスク**という分類、そしてマイナスに働く要因を**脅威**、それにつけ込まれる弱点を**脆弱性**と呼ぶ点は、セキュリティの文脈と共通です。

プロジェクトにおけるリスクマネジメントの手順も、「リスクの特定→**リスク分析**（発生確率・影響度の評価）→対応の計画→対応の実施→監視」という、以前のノートで扱ったリスクアセスメント〜リスク対応の骨格と同じ流れで進みます。対応の中身も、**リスク対策**として、回避・低減・移転などの**リスクコントロール**が用いられる点は共通しますが、プロジェクトマネジメントでは単一の対策に頼らず、複数の対応策を組み合わせて用いる**ツールミックス**という考え方が重視されます。

### 3.2 リスクを定量的に分析する

リスクを数値で表現し、客観的に分析する手法群が**定量的リスク分析法**です。

| 手法 | 内容 |
|---|---|
| **感度分析** | どの要因（変数）がプロジェクトの結果に最も大きな影響を与えるかを分析する |
| **期待金額価値分析（EMV法）** | リスクの発生確率と影響額を掛け合わせた期待値（EMV）をもとに評価する |
| **モンテカルロ法** | 乱数を用いたシミュレーションを繰り返し実行し、結果の確率分布を推定する |
| **トルネード図** | 感度分析の結果を、影響の大きい要因から順に横棒グラフで並べた図 |

感度分析とトルネード図は「分析手法とその可視化手段」の関係にあり、期待金額価値分析はEMV（Expected Monetary Value）という指標そのものの計算に基づく手法です。モンテカルロ法は、単一の期待値ではなく結果全体の確率分布を推定する点で、他の2手法よりも高度な分析として位置づけられます。

### 3.3 リスクを定性的に分析する

数値化が難しいリスクを、相対的な優先順位づけによって分析する手法群が**定性的リスク分析法**です。

- **質問書法**：関係者にアンケート（質問書）を送り、リスクに関する情報を収集する。
- **得点法**：リスクの発生確率・影響度をあらかじめ定めた尺度で点数化し、合計点でリスクの優先順位をつける。

定量的リスク分析が「数値で厳密に評価する」アプローチであるのに対し、定性的リスク分析は「相対的な優先順位で評価する」アプローチであるという対比が、3.2節と3.3節全体を貫く最も大きな軸です。

## 4. 試験対策まとめ（重要ポイント）

- **CPI＝EV÷AC と SPI＝EV÷PV**：出来高（EV）を実コスト（AC）と比べるか、計画価値（PV）と比べるかで、コスト効率かスケジュール効率かが決まる。1より大きければ良好、という判定の向きを押さえる。
- **WBS と OBS**：「何を」分解するか（WBS）、「誰が」担当するか（OBS）という軸の違い。
- **PMBOK と PMP**：知識体系そのものか、それを認定する資格かの違い。
- **PMBOK と ISO 21500（JIS Q 21500）**：事実上の標準（デファクト）か、公式な標準（デジュール）かの違い。
- **品質保証 と 品質管理**：プロセスに着目した予防的活動か、成果物に着目した検出的活動かの違い。以前のノートの欠陥防止・欠陥除去の対比と対応する。
- **純粋リスク と 投機的リスク**：損失のみか、利益ももたらしうるかという分類。以前のノートと同じ定義がプロジェクトにも適用される。
- **定量的リスク分析法（感度分析・EMV法・モンテカルロ法） と 定性的リスク分析法（質問書法・得点法）**：数値で厳密に評価するか、相対的な優先順位で評価するかの違い。
- **ツールミックス**：単一のリスク対策に頼らず、複数の対応策を組み合わせるという考え方。
